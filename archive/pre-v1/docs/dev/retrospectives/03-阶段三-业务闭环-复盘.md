## 2. 与原计划/原设想矛盾的地方，和为什么

### 2.1 跨组件关系的判断：不是每条新出现的边都需要 vendored-contract

阶段二复盘 §2.3 论证出的 vendored-contract 模式，本阶段第一次有机会被检验"是不是该无脑套用"——`crm-opportunity` 与
`erp-sales` 之间业务上关系极近（"商机赢单"直接触发"建订单"），一度是**最容易被顺手加一条同步依赖边**的地方。
但两者之间设计上是纯事件边（`crm.opportunity.won.v1`），根本不需要 gRPC 同步调用，因此也不需要 vendored-contract。
**这条不是"猜错了"，是一次成功的自我提醒**——阶段三计划文档在写作阶段就点明"两个域名字上完全不像有关系，反而更
容易被忽略这条铁律"，真做的时候确实守住了。这说明 vendored-contract 不是"跨组件关系"的通用答案，是"跨组件同步
调用"的答案，两者不能划等号——以后新增任何跨组件关系，第一个问题应该是"这是同步边还是事件边"，不是"要不要抄
vendored-contract"。

### 2.2 自己代码里的隐藏耦合，被真机测试推翻

| 想当然的假设 | 实测的真相 | 为什么会想错 |
|---|---|---|
| `erp-inventory` 的 `Receive`/`Adjust`/`GetBalance`/`ListMovements` 声明为 REST-only 就足够安全 | 这四个方法**同时**暴露在 gRPC 面（因为 proto 是一整份 `InventoryService`），"REST-only"只是一句代码注释，没有任何机制强制；被直接 gRPC 调用时 `besdk.ScopeOf` panic，而 `be-sdk-go` 的 gRPC server 当时零 panic-recovery，直接崩容器（C11） | 把"设计意图写清楚了"和"设计意图被强制执行"混为一谈——这与阶段二 §2.1 第一条"配置在语义上不自洽 ≠ 平台会报错阻断"是同一类误判的变体，只是这次误判的对象是自己的代码，不是 brickKit |
| `be-sdk-go` 三份 SDK 里最先写出来、被四个组件用过一轮的那个，并发场景一定没问题 | `StartOutboxPump` 的 `pumpOnce` 从建仓库起就是裸 `SELECT ... WHERE status='PENDING'`，没有 `FOR UPDATE SKIP LOCKED`——单进程单实例下这条坑永远不会触发，K8s 多副本一上就会真实双发（C15） | "跑了很久没出问题"被当成"这里没问题"的证据，但这条坑的触发条件（≥2 副本）在阶段三之前从来没有被真正满足过，不出问题只是因为没有满足触发条件，不是因为逻辑本身正确 |
| 新组件的 `migrate down` 只要 `down.sql` 语法本身没错就能用 | `003_seed_*.down.sql` 按反向执行顺序运行时，早于它执行的 `001_create_*.down.sql` 还没跑，外键约束会碰撞——这条路径在项目历史上**从来没有真机跑过一次**（`migrate-idempotent` 门禁只测 `up` 连跑两次），`erp-inventory`/`erp-finance` 两个不同组件各自独立踩中同一个根因（C21/C23） | `make db-reset` 是阶段三才第一次真正被用到的新能力，此前从没有真实场景逼着系统执行 `down` 方向——"语法正确"和"反向执行顺序下依然正确"是两件事，静态审查/单测都不会自动覆盖后者 |

### 2.3 SDK 跨语言移植：默认行为的方向可能刚好相反，这一次真的验证了好几遍

`be-sdk-python`/`be-sdk-ts` 是本阶段第一次把已经在 Go 上验证过的模式移植到新语言。移植时反复出现同一种失误模式：
**读了新语言底层库的文档/源码，得出"这个语言没有这条坑"的结论，实际跑起来才发现结论是错的**——

- `be-sdk-python`：读 Starlette 文档以为"GET 路由自动带 HEAD"这条 Go 版遇到过的坑（A4h）在 Python 下不存在，
  实际是 FastAPI 的 `APIRoute` 重新赋值了 `self.methods`，没有带过 Starlette 父类那一步逻辑（A9）。
- `be-sdk-ts`：以为 `@opentelemetry/api` 默认状态下 `context.with()`/`trace.getActiveSpan()` 能像 Python 的
  `contextvars` 一样天然透传，实际默认 context manager 是纯 no-op，需要显式注册 `AsyncLocalStorageContextManager`
  （A10）；以为身份转发能直接复用 Python 版 interceptor 的心智模型改用 `CallCredentials`，结果撞上 `grpc-js`
  "拒绝把调用凭据组合进 insecure channel"这条安全策略硬报错（A11）。

**这三次不是三个孤立的巧合，是同一类失误在重复**：跨语言移植时，"这个语言的等价能力默认行为和另一个语言一致"
这个假设本身就是不可靠的起点，必须每一条都真机验证一遍，不能靠读文档/读源码类比过去。这条经验值得写进方法论
（见 §4 第 5 条）——虽然只涉及两种新语言，但如果以后真的要接入第三种语言的 SDK，这条判据会立刻再被用到。

### 2.4 关于"文档写了就代表做了"的假设，被本文档自己的存在推翻

`AGENTS.md` 的 Current Status 表在阶段三主线收官时写着"Tasks 1–15 all done"——这句话在当时是失实的，Task 15
从未被真的实现过。这不是笔误，是**没有人在写下这句话之前去核对 Task 15 承诺的具体产出物（某几个测试函数）
是否真的存在于代码库里**。这条教训已经存进长期记忆（`feedback-verify-done-claims-before-trusting`），不止对
阶段三成立——以后每个阶段收尾时的自查，都不能只读计划文档自己怎么描述，要抽查具体产出物。

## 3. brickKit 平台本身：理念是否有问题，实现是否有 bug

### 3.1 真 bug：本阶段零例

与阶段二不同，本阶段全部真机验证挑出的问题最终都定位回了自己的仓库（组件/`be-sdk-*`/脚本），没有一例是 brickKit
平台自身的实现缺陷。**这本身是一个值得记录的对照**：阶段二"验平台"这个题目下大部分精力花在摸清 brickKit 的边界
行为，阶段三题目是"业务闭环"，brickKit 已经是一个被充分验证过的、可以信任的地基——这印证了阶段二复盘 §5 的
判断（20 条平台断言是常驻资产，不是一次性交付），也说明"先集中把平台摸透，再在上面盖业务"这个阶段顺序本身
是对的，不需要因为阶段三没有找到平台 bug 就反过来怀疑阶段二做得不够。

### 3.2 两次自我纠正：平台其实支持得比想象中更完整

G1（`brickkit.yaml` 的 `${VAR}` 敏感配置展开）与 G2（全局唯一 `.env`）都是"第一次判断错了，读完整条调用链才发现
平台原生支持"的例子，不是平台的缺陷——反而是平台比预想更完整的证据（G1 甚至还带了一整套明文密钥告警机制）。
这条本身没有反馈给 brickKit 的必要，值得记录的是**方法论教训**：判断"平台不支持某能力"之前，一两个关键词的
grep 没搜到不能作为结论，必须读完整条相关源码文件——这条已经写进 G1 自己的条目，这里不重复，只强调它差点导致
把一个真实敏感凭据（RSA 私钥、管理员密码）写进 git 历史，后果本可以是不可逆的。

### 3.3 值得反馈给 brickKit 的观察：跨组件"配置字面量引用另一个组件版本号"目前没有机制化手段

`infra-authz`/`infra-iam-casdoor` 被其余 13 个组件通过 `authzBundleUrl`/`iamJwksUrl` 引用，但这两项引用**不是**
依赖边——依赖边会被平台自动重写地址，而这两项是"知道对方存在，但不建立正式依赖关系"（避免污染同步调用图）,
只能手写字面量，且这个字面量里天然嵌着对方当前的版本号（brickKit 的服务名生成规则决定的）。`infra-authz` 每次
升版本，这 13 个组件里手写的字面量都要跟着改——一次性漏改过 25 处引用（C18），而这类漂移**两个现有 gate 都
抓不到**：`dependency-version-scan` 只比对正式的 `dependencies.components` 声明和顶层 `version` pin，根本不知道
`config` 段里某个字符串"恰好嵌着别的组件的版本号"这件事。

这不是要求 brickKit 支持"配置模板变量"这类通用机制（决策 105/106 已经论证过，这类抽象往往在别处产生新的复杂
度）——**只是记录一个真实存在、目前完全靠人工纪律兜底的缺口**，是否值得做、值得做成什么形态，按
[[project_user_is_brickkit_maintainer]] 的既定原则留给 brickKit 自己判断（同阶段二复盘 §3.2 观察二的处理方式）。
一个可能的方向（不代表建议）：Manifest 里允许显式声明"我引用了组件 X 的当前版本号，但不建立依赖边"，供生成期
展开成正确字面量，同时被某种扫描器识别到——但这只是本项目视角下的一个设想，具体怎么做、值不值得做，留给平台
自己判断。

## 4. 流程改进

1. **版本+tag 纪律已经两层机制化，但还有第三层缺口。** `dependency-version-scan` gate 覆盖了正式的依赖声明和
   顶层 pin；`version-check.sh` 覆盖了"代码变了但没打 tag"；§3.3 指出的"配置字面量里手写着别的组件版本号"这一层
   仍然纯靠人工——是否要补齐，留给以后决定，但至少要在这里承认这个缺口的存在，不要让它继续隐形。

2. **mock 测试等于没测，这次由 C11 再次印证，且是一个新方向。** 阶段二复盘 §4 第 3 条讲的是"补偿链正确性"这类
   业务逻辑 mock 测不出来；C11 补了一个新角度——"REST-only 方法被误经 gRPC 调用会崩容器"这类**平台层面的失效
   模式**，纯 mock 同样测不出来，因为 mock 不会真的触发一次跨进程 gRPC 调用去撞那个真实的 panic。这条值得和
   阶段二那条并列写进总纲对应章节，作为"真机验证优先"判据的第二个具体案例。

3. **迁移的 `down` 方向要在新增 `db-reset` 之前主动审查一次执行顺序，不能等真机踩了才修。** C21 第一次真机踩中
   （`erp-inventory`），C23 是同一个根因在 `erp-finance` 上的复发——但 C23 这次是**主动审查执行顺序，在真机跑
   之前就把坑找出来提前修了**，说明"学过一次教训之后主动检查"是有效的。建议正式写进 SOP-W-7 或部署手册自查
   清单：任何组件新增 `make db-reset` 前，先按反向版本号顺序通读一遍全部 `.down.sql`，假设"更早版本创建的表此刻
   还没被删掉"去审查每一条 `DELETE`/外键关系，不要只看语法对不对。

4. **seed 脚本的探测游标要跟着被探测组件的真实数据规模走。** C22/C24 都是同一类问题——`erp-inventory`
   探测 `mdm-product` 的种子数据时用固定的位置范围（`1 2 3 4`），`mdm-product` 的种子数据规模变了，探测范围
   却没跟着变。这条已经写进 SOP-W-7 的新判据，本阶段是这条判据的第一次真实触发案例，不需要再单独补规则，
   这里只做记录归档。

5. **SDK 跨语言移植方法论，值得单独提炼成一条通用检查项。** §2.3 的三个例子（A9/A10/A11）共同指向同一条经验：
   "某个语言的等价能力，默认行为方向和另一个语言一致"这个假设本身不可靠，必须逐条真机验证，不能靠类比。
   建议把这条写进总纲或 `02-reference-implementation-standard.md`——虽然目前只有 Go/Python/TS 三种语言，
   但这条经验对将来任何"把已验证的模式挪到新技术栈"的场景都成立，不止 SDK 本身。

6. **⭐ 最重要的一条：阶段收官后不写复盘就展开后续工作线，这次有了一个具体的、可指名道姓的代价。** 见 §5 完整
   分析，这里只点出结论：**这条规矩不是形式主义，这次是它第一次有了一个具体的反面案例来证明为什么需要它。**

7. **"✅ 已完成"不能直接当真，已存入长期记忆（`feedback-verify-done-claims-before-trusting`）**，不重复展开。

## 5. 是否要重新安排整体阶段编排

**结论：阶段划分本身不需要重排。阶段三的 15 个任务，每一个都有真机验证记录，主线本身做得很扎实。** 出问题的
不是"阶段三该不该分成这些任务"，是**主线出档之后、下一阶段真正开工之前，这段本该很短的收尾窗口被拉得过长、
过散**——具体表现为：

1. **三条后续工作线（测试体系扩展、种子数据丰富度整改、文档架构重构）都是有价值的真实工作，且各自都做得
   很扎实**——有 commit/tag/push、有真机验证、有独立的复盘级细节记录（`field-tested-pitfalls-log.md` 里的
   C16–C24、E3 大部分就产自这几条线程）。问题不在于工作质量。
2. **问题在于这几条线程展开时，没有人先回过头确认"阶段三主线自己真的收尾了没有"**——按 `02-阶段二复盘` 定的
   规矩，主线收官后第一件事应该是写复盘，复盘会强制回答"哪些任务真的做完了"这个问题；实际是复盘被跳过，
   直接开始了下一轮工作，Task 15（本该在主线里做完）就在这个窗口里被静默遗漏了。
3. **代价是具体的、可指认的**：Task 15 被跳过的这段时间里，`platform/b_test.go` 的 `erpSalesContainer` 硬编码
   版本号漂移、`erp-sales` 的 `receiveRealStock`/`getRealBalance` 连错物理库——这两处测试覆盖回归都是在"账没有
   及时算清"的这段窗口期里发生并且长期未被发现的，直到用户凭印象怀疑"阶段三没做完"才被系统性倒查出来。

**以后的具体做法**：阶段主线（编号任务全部做完）之后，**先写复盘，哪怕只能先写出骨架、把已知空白点列出来**，
再决定要不要展开新的工作线程；如果确实发现了阶段主线里遗漏的任务（就像这次的 Task 15），应该立刻回到当前阶段
计划文档里正式标注"未完成"，而不是让它停留在一份此前写的、后来变得失实的"✅ 已完成"表述里，靠记忆去发现。
新发现的额外工作，要么正式编号进当前阶段计划，要么明确列成"阶段 N 收尾清单"这样有出档标准的条目，不要用
三四条并行的、没有编号、没有明确"何时算做完"标准的松散线程去处理。
