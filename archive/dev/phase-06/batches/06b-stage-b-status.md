## 3. 已定且已落地

### 3.1 协议与契约（rc.2）

【已核对】的只有一件事：三个仓库打标签前 `make check` 重跑，退出码都是 0。下面各条的内容来自通道报告和控制者的裁定，控制者没有逐条去读规范原文。

- 族地址：`AUTHZ_URL`、`AUTHZ_GRPC_URL`、`IAM_URL`、`IAM_GRPC_URL` 四个键，值是 `config/vars.yaml` 里的 `$endpoint:` 引用；不再有"gRPC 端口 = HTTP 端口 + 1000"；`IAM_JWKS_URL`、`AUTHZ_BUNDLE_URL` 退役。
- 密钥：凡是 `secret: true` 的键一律 `mount: file`、键名以 `_FILE` 结尾，SDK 30 秒内重读，读失败保留上一个有效值。
- 数据库角色：属主角色（`PG_OWNER_USER` / `PG_OWNER_PASSWORD_FILE`，建表改表）与运行期角色（`PG_USER`，只有增删改查）分开；运行期建分区走属主预先建好的 SECURITY DEFINER 函数；外壳要求 PG16，单独运行最低 PG14。
- 组件清单必须声明：`readinessCheck`（`/readyz`）、`stopGracePeriodSeconds`（默认 30，SDK 内部宽限 25）、端口 `protocol`、`events`（由 be-ops 从事件契约生成）、`release.checks: [[make, conformance]]`。
- 接口必须声明权限键，漏声明一律拒绝；标 `x-be-internal` 的运维/内部接口例外。
- 权限数据加载完之前：先校验 token（缺失或无效 → 401），再对所有非公开路由返回 503。
- token 校验顺序：签名与基本字段 → 类型 → 是否作废（stale）→ 已撤销的授予 → 委托能力 → act 链。
- 事件：至少 4 段的事件名；消费者名把 `.` 换成 `__`；服务端不配退避，重试次数由 SDK 计数，超过上限写死信队列再终止；最后一次允许的投递失败时先 nak，下一次收到才进死信队列；载荷超过 64 KiB 拒绝。
- 错误名 36 个，含本轮新增的 `REQUEST_INVALID`、`DEPENDENCY_UNAVAILABLE`（带 `metadata.dependency`）、`REQUEST_CANCELLED`；槽位族成员共用族 ID 作错误域。
- 其它：空值等于没设（所有类型）；布尔接受 true/false/1/0；重试总次数 3；语句缓存键必须含成员 schema（`/* be:<schema> */` 前缀）；收缩迁移要等旧版本会话全部断开（靠会话名 `<id>@<version>`）；连续单据号的唯一性由不分区的分配表保证；SDK 内置时区数据；保留天数（outbox 14、游标和幂等键 30、已完成队列行 7、任务时间槽 30）；可选能力 `job run <name>`。

**2026-10-04 补的两类修复**（由"套件自己踩过的坑，SDK 会不会也有"的静态审查发现，各自先写红测试；三个仓库的完整集成测试之后重跑通过：Go 19 个包、Python 124 个、TS 226 个）【已核对】：

- **出站 gRPC 预算到点的分类**：预算用完那一刻 gRPC 可能报 CANCELLED、INTERNAL 或 UNAVAILABLE 而不是 DEADLINE_EXCEEDED；三个 SDK 现在一律归为 `DEADLINE_BUDGET_EXHAUSTED`（504）。TS 此前连真正的超时也没有 reason。
- **消费停止**：Go 原本正确。Python 的拉取请求在停止时被中途取消，窗口最长 5 秒；改为 1 秒拉取、等当前拉取结束、迟到的消息立刻 nak。TS 的问题不是"留下拉取请求"（实测 nats.js 取消订阅后服务器立即丢弃该请求），而是已发到进程但未处理的消息既不处理也不 nak，要等 ack_wait；真实 NATS 上复现为 30003 ms，改成与 Go 同形的拉取循环后约 1 秒。

1. **`_authz/explain` 三种语言不一致**（记录对调用者不可见时）：Python 404；TS 200 加"调用者自己一侧"的事实；Go 按 R62 处理。协议里两处写法本身矛盾。建议口径：记录不存在才 404；存在但不可见时返回 200，只给调用者自己一侧的事实、不泄露记录属性。

## 7. 这三批用了多少 agent

数字是各 agent 结束通知里的 `subagent_tokens`，只是它们自己报的量；控制者自己的消耗、子 agent 的消耗都不在内，也不清楚它和账户计费如何对应。

| 批次 | 通道数 | 各通道报告的 token（万） | 合计（万） |
|---|---|---|---|
| 采用 brickKit v1.3.1 | 3 | 项目层 35、协议与契约 42、文档 50 | 约 127 |
| 阶段 B 第一波 | 5 | Go 63、Python 63、TS 72、一致性测试 45、be-ops 43 | 约 285 |
| 阶段 B 第二波 | 7 | 协议 rc.2 51、v1.4.0 复测 20、Go 67、Python 52、TS 56、一致性测试 71、be-ops 30 | 约 347 |

第二波 Go 的 67 万是它最后一次结束通知里的数字；中途它交回过一次，那次通知是 27 万，不确定 67 万是否已经包含这 27 万。

第二波高峰时同时有 17 个 agent 在跑：6 个通道加 11 个子 agent（其中 2 个是 Go 通道恢复后重复派出的，被停掉）。子 agent 的用量没有报给控制者，所以实际消耗高于上表。

**这一批的教训**（已写进 `.superpowers/sdd/plan-06b/batch-common.md` 和记忆）：

- 需要读同一套材料的工作不拆成多个 agent；一批 2～3 个，最多 4 个；agent 不再派子 agent。
- 恢复一个中途交回的通道时，先说清它的哪些子任务还在跑，否则它会重复派。
- 不提交编译产物；推送前查一遍有没有超过 1 MB 的文件。
- 退出码不能被管道遮住（`cmd | tail` 返回的是 `tail` 的退出码；本机是 zsh，没有 bash 的 `PIPESTATUS`）。
- 协议测试向量已覆盖的行为，不在各语言里重复手写单元测试。
- 被权限检查拦下的命令，控制者不替 agent 代跑，交给用户决定。
