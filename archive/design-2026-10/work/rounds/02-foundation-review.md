# 底层设计阶段性审查

- 日期：2026-10-13。
- 范围：组件、BrickKit 理念、部署、权限与事务／恢复边界。
- 状态：阶段性判断，不覆盖既有裁定，不冻结设计或签发运行验收。
- 操作：读取文档与相关源码，核对一手资料，运行契约参考求值器的最小样例。未修改源码、启动容器、发布或向外部项目发送反馈。

## 总体判断

组件作为选配、定制与版本维护单位，部署时可以进入外壳；身份与授权分开；业务事实有唯一写入权威；不同实现遵守共同语义并分别验收。这些方向适合本项目目标，可以继续深化。

尚不能判断全部底层逻辑已合理且可交付。全量货架仍缺边界卡和客户依赖闭包，权限契约与新目标有差异，跨组件流程缺执行协议，目标版 SDK／外壳与部署组合尚未通过真实验收。知识库作为中立参考，其默认模块化单体取向与本项目独立选配、替换、Fork 和部署实验目标不同，不由此认定任何一方错误。

## 完整授予的补充证据

既有 I18 聚焦字段掩码。本次核对 `contracts/infra/authz/EVALUATION.md` 的 E6、E7、E10、E11，发现完整授予原则还涉及多维范围的绑定。

旧 E7 将持有同一权限键的角色按每个维度分别取并集，E10 再要求各维度同时满足。新目标要求先判断一整份授予的全部约束，再汇总合法授予；两种算法不等价。

最小输入为有效 `authz/2.0` bundle、同一主体的角色 a／b、相同样例读取键、无 ACL／图分支、资源维度 `legal_entity` 和 `warehouse`。a 仅授予 A／W1，b 仅授予 B／W2。通过 Python `runpy.run_path` 加载 `contracts/infra/authz/vectors/tools/reference.py`，分别调用 `evaluate(input)`；未改写参考求值器或既有向量。

| 记录维度 | 新目标的独立预期 | rc.2 参考求值器实际 allowed |
| --- | --- | --- |
| A／W1 | 允许 | true |
| B／W2 | 允许 | true |
| A／W2 | 拒绝 | true |
| B／W1 | 拒绝 | true |

命令退出码 0。标签不成为正式注册项；交叉维度记录用于检验权限谓词，不能以业务数据通常不存在该组合代替授权正确性。

这证明旧契约参考规则与新目标存在差异；没有运行三种 SDK 的同一样例或真实业务入口，不能称为已复现线上泄漏。字段入口仍按此前静态证据判断。

先确定完整授予结构和求值语义，再同步查询谓词、逐记录／动作字段判定、写入与过滤／排序、解释和向量。求值含义变化须按契约兼容规则决定新版本，不能只以文字修订或新增可选字段掩盖改变。对应 PA04／PA05／PA07／PA09／PA35，优先于全量推广。

## 外部项目配合

BrickKit 本地仓库为 `6085c375`，CLI v1.4.1，读取时工作区干净。已核对内置 `$endpoint:` 文档：支持成员地址、具名端口、版本、外壳与本机改写、引用对象随 focus 启动，但引用不产生启动先后顺序。无需再次列为新增需求。

本项目旧 0104 与 D27 的差异须在正式文档迁移时处理。BrickKit 外壳文档提到进程内直接调用，而本项目要求真实 RPC；属于项目更严格规则，应解释收益与成本，不当作 CLI 故障。

目前未发现必须新增 CLI 能力才能继续的已证实阻塞。按法人路由、能力匹配、权限及业务迁移先由项目承担；实际机制无法表达、生成或运行时，再区分指南改进、功能请求与 bug。

迁移与运行期共用属主密钥的限制已有明确接受及“不向 BrickKit 提需求”的答复。本次保留，不重新发起需求，也不声称实现了进程被攻破后的凭据隔离。旧 F06／FR06 已有修复与采纳记录；待真 K8s 或真成员外壳验证的项目不计为新目标已通过。

Casdoor tokenFormat 已知问题仍须进入真实安全验收前的修复门槛，由项目 IAM 适配与配置处理，不认定为 BrickKit CLI 故障。
