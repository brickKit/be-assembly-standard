# 冻结前复查：底层机制及其组合

范围：`tempDocs/final` 的 04-foundations；协议 01、02、03、05（只看增量事实的共同规则与认领模式）、06（参与方接口）、10、11、12、14、15、17、18、19、21；安全 01–11，重点是 03、08、10、11。只在核对引用时略读其余文档。行号以复查时的文件为准。

判定口径（维护者给的冻结规则）：只有底层问题阻塞冻结，指以下三种：共享机制之间互相矛盾；在声明的技术栈上做不出来（PostgreSQL、NATS、三种 SDK，起步单实例，高可用按 D66 预留）；几个机制合在一起兑现不了它们承诺的保证。单个组件内部的逻辑，以及只有实现时才能真正验证的边缘情形，一律算通过，在第三节简单列出。

## 汇总（能否冻结）

**结论：暂不冻结，但只差两处补充，都不需要重新设计。** 两处都在“不随恢复回退的东西”这一组：

1. 证据存储（审计组件）必须在整套恢复的回退范围之外。可是起步形态是“单实例、单数据库”，PostgreSQL 的时间点恢复以整个实例为单位，审计库会和业务库一起回退。整套恢复所依赖的“T 之后的撤权、销毁、单号、代次都能从证据补回”，在起步形态下兑现不了。
2. “运行档案”与“部署外的告警渠道”被当作机器读写的权威存储（部署恢复代次、信任材料、降级标记、部署身份），却从没定义它们是什么、需要哪些性质。这条“不回退”的链条落在一个没有定义的东西上。

两处补齐之后，本次要查的五个方面都能组合起来：

| 方面 | 结论 |
| --- | --- |
| 1. 本地事务、发件表与带（纪元，序号）的增量事实；纪元、部署恢复代次、实现实例、部署身份 | 基本只定义在一处（协议 14 的库内计数与纪元，读取方式在协议 02 第 3 步），各处用法一致。有三处遗漏，记入已知风险（R1–R3） |
| 2. 投影、水位与“可证明不存在”，对照授权视图与撤权上界 | 协议 02 第 9 步的判断表与安全 03 的续发与关闭表一一对得上：隔离、对齐中、新增投影都按无法证明处理，读取顺序同为同一快照内先读水位。整套恢复、高可用切换、成员切换三种情形下，上界按文中写法成立。协议 02 第 528 行留到冻结复查核对的“授权视图与投影两套规则的衔接”，本次核对通过 |
| 3. 证据存储、告警渠道、运行档案与信任材料 | 没有发现循环依赖：服务到方法的许可由部署声明，不来自授权视图（安全 02 第 76 行），所以审计组件接收写入不依赖授权组件；信任材料以运行档案为准，签发不依赖审计组件（协议 15 第 57 行）。但这一组的物理落点与性质没有写清（B1、B2） |
| 4. 生效点、变更键与派生键，对照工作项与幂等（协议 01） | 一致：“处理中”放回 `retry_wait` 且不计尝试次数（协议 01 第 81 行，安全 08 第 192、397 行）；`operation_id` 只有在全部子调用都已确认之后才换键，与“终局驳回占用变更键”相容。有一个遗漏：成员切换不迁移变更键的绑定（R4） |

## 一、阻塞冻结

### B1　起步形态是“单实例、单数据库”，证据存储与审计存储却必须在恢复回退的范围之外

**矛盾**

| 位置 | 内容 |
| --- | --- |
| `04-foundations/README.md:31`、`02-decisions/05-transactions-data-and-recovery.md:50`（D66） | 正式开发从单实例、单数据库起步 |
| `04-foundations/02-data-and-lifecycle.md:56-57` | 共用实例时，各库同属一个实例，实例级的故障与物理恢复都是共同的 |
| `06-protocols/15-backup-and-recovery.md:28`、`:118` | 第 3 步把全部组件库“各集群恢复到 T”，用的是物理备份加 WAL 的时间点恢复 |
| `06-protocols/15-backup-and-recovery.md:32-33`、`06-protocols/14-data-foundations.md:51`、`06-protocols/03-audit-durability.md:60` | 独立证据存储（由审计组件兼任）与审计存储“不随部署备份回退” |

PostgreSQL 的时间点恢复以实例为单位，不能把实例里的一个库排除在外。审计组件的库放在共用实例里，就会和业务库一起回到 T。

**后果：协议 15 的几项核心保证在起步形态下全部落空**

- T 之后的撤权、停用与销毁，只能从告警渠道补回；而告警渠道只在证据存储不可达时才有记录。所以收紧类记录“恢复点目标为零”（协议 15 第 303 行）不成立。
- 部署恢复代次的权威计数会随恢复回退。协议 14 第 51 行靠“取证据、各库与运行档案中见过的最大值”才不重用，这时只剩运行档案一处可依靠，而它本身没有定义（见 B2）。
- 连续单号恢复后取已用最大值，要读证据与审计存储中的签发记录（协议 14 第 86 行、协议 15 第 355 行）。这两处一起回退，就可能出现重号。
- 第 9 步的审计损失清单以“审计存储不回退”为前提（协议 15 第 351 行）。
- 另有一个次要问题：恢复模式表（协议 15 第 144-151 行）没有写审计组件在冻结与第 3–4 步时仍要运行，而第 4 步要写入证据存储。

**最小修法（只补规定，不改机制）**

1. 在 D66 或基础选择中写明：最小部署也是**两个 PostgreSQL 实例**，一个放业务库，一个放证据与审计库。后者单独备份，不在整套恢复的回退范围内，可以与业务实例同宿主（同时写明同宿主时磁盘仍是同一个故障域）。
2. 换一种做法也行：把整套恢复的第 3 步改成“先恢复到临时实例，再逐库复制回去，审计库除外”，同时写明它的恢复时间代价。
3. 在恢复模式表中补一行：审计组件全程运行，只接收转运与证据写入。
4. 同时改正 `05-operations/01-backup-and-recovery.md:12` 的日常核对项“同步复制正常”。单节点部署没有同步复制，应改为“独立实例的备份与可达性”。

### B2　“运行档案”与“部署外的告警渠道”承担机器权威的职责，却没有定义

**同一个名字承担了两种性质的职责**

| 用法 | 位置 |
| --- | --- |
| 运维人员手写的操作记录 | `05-operations/README.md:14-15` |
| 部署恢复代次与授权恢复代次的权威计数，要求同步提交 | `06-protocols/15-backup-and-recovery.md:58-59` |
| 信任材料（CA 链的轮换与吊销、服务凭据的签发登记）的权威来源：签发在运行档案同步提交后才发布 | `06-protocols/15-backup-and-recovery.md:57` |
| 6.2 核验签名时读取的三处之一 | `06-protocols/15-backup-and-recovery.md:255` |
| 部署身份与实现实例身份的保存处 | `06-protocols/14-data-foundations.md:48` |
| 组件运行时从这里得知“降级开始” | `06-protocols/15-backup-and-recovery.md:384` |

**告警渠道被要求的性质也散在各处**：要保留签名记录不少于 30 天、能批量导出给恢复工具、“接收时刻以渠道为准”（`06-protocols/15-backup-and-recovery.md:261`、`:409`）。最后一项等于要求渠道提供可信的接收时间戳。这两样东西没有一份文档说明它们是什么、由谁写、写入接口与格式、需要的可用性、只追加与防篡改怎样保证、同步写入的“同步”指什么。它们也不在组件卡上（`07-components/infra.md`），基础资源表中也没有。

**为什么阻塞**：“不回退、不重用”这条保证链（部署恢复代次 → 纪元 → 全部跨库计数，以及信任材料 → 6.2 核验 → 重放的合法性）最终落在这两样东西上。不定义它们，恢复工具、CA 签发工具与 SDK 的降级检测都没法实现，也没法验收。

**最小修法**：在基础选择中加一节（或一张表），把它们定义为部署之外的**基础资源**：

- 运行档案：只追加的签名记录存储。实现可以是部署之外、开了对象锁或版本保留的对象存储桶，或独立的 Git 仓库加签名提交。写明哪些工具写、哪些组件读、读不到时各操作怎样处理。“运维人员的记录”另起名字，与这项资源分开。
- 告警渠道：写明必需的性质：只追加、保留天数、可导出、接收时间戳由渠道签发或可信，以及最小部署的候选实现。

## 四、整体判断与重新整理的建议

**整体判断**：共享机制的核心组合是自洽的，参考模型的反例也覆盖得较全。

| 机制 | 组合关系 |
| --- | --- |
| 本地事务加发件表 | 与全部增量事实、审计第一落点同一个模式 |
| 锁内的提交后编号 | 发布位置、审计产生序号、增量事实序号、关账覆盖点、成本组件读高点共用同一段逻辑 |
| 纪元（部署恢复代次，时间线）加分叉点 | 工作项认领、投影、审计回执、安全修订、资源水位用同一套比较规则 |
| 实现实例与部署身份 | 来源更换、成员切换与环境复制都靠它们区分 |
| 证据两段写加告警渠道 | 补上整套恢复时会回退的部分 |

问题集中在一处：“不随恢复回退的东西”只写了逻辑，没有写物理落点与性质（B1、B2）。补上之后可以冻结。

**重新整理的建议**（不影响冻结，可以和 B1、B2 一起改）：

1. **把“不回退的东西”收进一张表。** 这些内容现在散在协议 14 第 48–51 行、协议 15 第 28–61 行与第 384 行、安全 03 第 17–18 行、运维手册 01 第 12–14 行。建议在基础选择中设一节，一行一样东西：证据与审计存储（独立实例）、运行档案、告警渠道、信任材料、两种代次的权威计数。每行写：物理落点、谁写、谁读、何时读、写入要求（同步、签名、只追加）、保留期限、不可达时怎样处理。协议 14、15 与安全 03 都改为指向这一节。这正是 B1、B2 的修法落点，也能消除 R9 这类两处写法不一致。
