## 2. 建议

### 判断：甲为主，乙为辅

**规则与机制并入现有终稿（甲）**；**只把“可替换的基础选择”的方案比较、改选条件、怎么换与适配器检查，恢复成 04-foundations 下的少数独立文章（乙）**。理由：

1. **规则只写在一处**（`03-documentation.md#写法`“一件事只写在一处”；A99“抽出到 be-protocol 之前，规则正文只在 06-protocols/”）。旧文档的端口契约、表结构、头字段、错误分类、先写红清单都是规则，若按“每个选择一篇”原样恢复，就会与协议 02、11、14、17、18 形成两套现行规则，违反协议 21“不保留新旧两套并行的现行规则”。所以这些内容进协议（或在 be-protocol 重建时抽出）。
2. **方案比较与“什么时候换、怎么换”在终稿里最薄**：终稿 FND README 的推荐组合表每格一两句；02-data、03-tx 有数据库、存储路线、消息运输的选择，但没有具体产品的比较、拒绝理由、迁移步骤与适配器检查。把这些全部塞进 02-data（175 行）与 03-tx（181 行）会让它们失去“跨方面取舍”的主旨。按 `03-documentation.md#拆分与重构` 的三条件检验：“客户要用人大金仓／Kafka／Iceberg”“评估换消息系统”这类任务只需要比较与步骤、不需要读整份 02-data 或 03-tx，拆开后常见任务不被迫读两份——满足拆分条件。
3. **共享语义（ID、单号、时间、金额、本地事务隔离、迁移工具、部署与客户隔离模型）不是按客户替换的选择**，它们的方案比较应当跟随规则：协议 14 是数据类协议中唯一没有“方案比较”小节的（协议 01、02、11、17、18、19 都有），给它补一节即可，不另开文章。

## 3. 冲突

### 旧内容与终稿明确矛盾（以终稿为准）

1. **分区与定位从 UUIDv7 推出**（04#选择、#列；09#读 按 ID 从时间位推单元）↔ A05、协议 14#身份与唯一性、DT02：分区键是显式列，按 ID 经身份登记表／定位索引定位。
2. **法人时区缺省 `Asia/Shanghai`，无 `mdm/org` 时用部署级 `BUSINESS_TIMEZONE` 降级**（05#选择、#端口契约）↔ A06、DF11、DF31：无隐含缺省，建立法人时必须明确，写进法人记录后不随配置变。
3. **不带范围的列表只读热窗口**（09#读）↔ 02-data#跨层查询、协议 11#列表与导出：默认“未关闭，或最近 N 天内创建”；02-data 已知风险已注明迁移时要修订。
4. **冷层摘要用 PG 文本输出、`\N`、`0x1F`／`0x1E` 分隔**（09#冷层格式）↔ 02-data#内容摘要…、安全 09a、DT06：版本化无歧义的规范编码。
5. **冷对象键带内容摘要，重复导出幂等覆盖**（09#冷层格式）↔ 协议 11#复制校验与发布：对象位置含单元 ID、代次与清单版本，写入后不覆盖。
6. **封存＝触发器拒写，写入答 `UNIT_SEALED`**（09#层与状态、#保证 G5）↔ 协议 11#封存与写屏障：所有写入口在事务内检查，迟到写入转为更正记录。（触发器作为纵深防御是否保留，可另议。）
7. **摘要链能发现已封存单元的任何改动**（09#保证 G6）↔ 02-data“防篡改的边界”：同库内可重算的链不承诺防恶意篡改。
8. **消费者按聚合流记版本、旧版本一律跳过（状态模式为默认）**（11#消费者游标；13#选择、#消费模式）↔ 0505 修订、协议 02、03-tx 事件分类：只有可覆盖的状态投影可以这样；不可遗漏的增量事实不能跳过。
9. **序列模式“保留不建，等第一个真实消费者”**（11、13#已知限制、#什么时候换）↔ 03-tx：增量与顺序消费者的协议先于成本、账务等依赖者实现。
10. **幂等键 30 天后成为新命令，“创建”会再创建一次**（11#被调方的命令幂等、#已知限制）↔ 03-tx 去重寿命、DT24：长期业务唯一性与短期请求缓存分开，已处理的财务与资金事实不因键过期而重新生效。
11. **平台表保留：发件表发布后 14 天、游标与幂等 30 天、作业 7 天**（09#分区窗口与平台表；11、12）↔ 协议 15（补发保留 7 天且不短于对齐与离线时长）、03-tx（去重寿命按最长重投、恢复窗口与业务路径确定）、协议 01#清理资格。
12. **死信在第 N+1 次收到时、处理之前写入**（12#持久消费者、#死信）↔ 03-tx、DT25：不依赖“第 N+1 次总会到达”，由最后一次失败处理接管。
13. **一个项目的所有组件用同一个运输适配器**（12#选择适配器）↔ 03-tx：不同业务运输链可以选不同的合格适配器（同一条链内单选）。
14. **持久消费者首次创建时投递流中全部消息，新装消费者补最多 7 天事件**（12#持久消费者）↔ 协议 02 的对齐与快照、03-tx“新订阅不能用当前列表证明全部历史”、DT26。
15. **外壳成员的数据库地址与外壳不同时拒绝启动**（02#外壳启动器；03#SDK 在启动时检查什么）↔ 协议 14#数据库、DF02：不同数据库目标各用一个池。
16. **收缩迁移在运行期按 `pg_stat_activity` 的在线版本把关**（08#expand 与 contract）↔ `01-engineering.md`、FND README：数据库里没有旧会话只是观察信号，退出依据客户精确基线由发布检查确认。旧机制可作为附加保护保留，但不能作为依据。
17. **参数差异**：迁移锁等待 5 秒（终稿 3 秒、重试 5 次）；事务内空闲 30 秒（终稿 10 秒）；语句缓存与超时等以终稿参数表为准。
18. **“每个组件一个数据库”被 0102 否决**（03#备选方案、#为什么不选其他）↔ 决定表 0102 修订、02-data#在线数据库怎样分离：可共用实例，也可独立库或实例。
19. **温层在同一张表里按分区与年龄分层**（09#选择）↔ 协议 11：按业务终态的归档单元，单元可以不等于分区。
20. **写入瓶颈→Citus 按 schema 分片，不改组件**（03#什么时候换）↔ 02-data#数据库的选择：按 schema 分片不能证明组件内部热点已解决，先看查询、争用与恢复预算。
21. **审计至少 6 个月、默认 3 年；订单涉税 10 年等默认口径**（09#表类别、#选择）↔ 协议 03#保留与法律保全、协议 11：按“类别×法人所在地区×客户要求”确定，没有依据的年限待确认。
22. **十进制的两种文本形式未区分**：旧 06 与协议 14 的契约金额按币种小数位格式化（`12.30`）；安全 09a 的 `Decimal` 规范编码要求无末尾零。两者用途不同（契约表示与规范摘要），但终稿没有写明区分，实现者可能把契约金额也去掉末尾零。建议在协议 14#金额… 写明。

### 终稿可能漏掉的重要保护或事实

26. 下列旧内容是“静默违反、发现代价高”的保护或数据库事实，终稿没有写，建议承接（落点见总表）：
    - a. **外壳登录角色以 `INHERIT FALSE, SET TRUE` 获授成员角色**（PG 16）：终稿只写“授予外壳登录角色”；按默认 INHERIT 授权时，外壳登录角色不切角色就直接拥有全部成员的数据权限。终稿声明外壳不是安全隔离，但这道纵深防御代价很低。
    - b. **`SET ROLE` 之后 PG 不套用目标角色的 `ALTER ROLE … SET`**：所以超时必须按事务设。终稿已经按事务设，但没写理由，日后有人改成角色级设置会静默失效。
    - c. **共享池上不同成员的同文 SQL 共用预备语句**，平台表结构不同时报“cached plan must not change result type”；旧对策是语句前缀。
    - d. **PG 队列扇出的 xmin 屏障**：不加时，较晚提交、序号较小的发布会被跳过。
    - e. **运行角色无 DDL 权限时，运行期的分区维护怎样做**：旧方案是属主创建的 `SECURITY DEFINER` 函数；终稿只说运行代码不用属主角色。
    - f. **连续编号只在幂等认领成功之后分配**：否则重复请求会占掉一个连续号。
    - g. **建分区与摘除分区的锁级别**：`CREATE TABLE … PARTITION OF` 要 `ACCESS EXCLUSIVE`、`ATTACH PARTITION` 只要 `SHARE UPDATE EXCLUSIVE`；`DETACH … CONCURRENTLY` 不能在事务块或函数中执行。
    - h. **缺法人的交易事件不能记进 default 法人**。
    - i. **事件载荷的大小上限与 claim check 的校验**（消费者校验大小与摘要、不持有生产者凭据）。
    - j. **事件跳数上限，防止事件循环**。
    - k. **收件表与游标表不分区**：主键含分区键时，两次并发投递可能都插入成功。
    - l. **个人信息的“限制处理”状态**（个人信息保护法第 47 条）。
    - m. **账簿类表不存个人信息列，只存主体的不透明 ID**。
    - n. **“创建”类命令在请求键过期后可能重复**的残余风险与应对。
