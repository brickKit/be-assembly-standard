# SDK 共同契约与一致性套件

> 状态：2026-10-13 工程协议第十八份候选，尚未冻结。承接 C30（多语言与 SDK），以及已关闭的 I11–I13 留下的教训（SDK 没有被黑盒套件验过、跨语言差异、部分运行产生易误读的通过报告）与语言中立组件协议的方向；按 D59 从零设计。现行 `docs/en/04-foundations/02-languages-and-component-protocol.md` 只作参考，其“协议 + 黑盒套件 + 三个官方实现”的结构被保留。

## 本页解决什么

组件可以用任何语言编写；项目提供 Go、Python、TypeScript 三个官方 SDK。本页回答：

1. 组件必须遵守的规则写在哪里，按什么层级检验？
2. 怎样从外部判断一个组件（无论什么语言）是否遵守？报告怎样不产生假通过？
3. 三个 SDK 怎样保持同样的语义？
4. 版本之间怎样对应？

## 方案比较

| 路线 | 判断 |
| --- | --- |
| 推荐：规则写成语言中立的组件协议；黑盒一致性套件对运行中的容器检验；三语言共用语义向量；报告区分通过、失败、未运行、不适用与检查失效，每项检查先过自检 | 任何语言都能被同一标准判断；SDK 之间的差异由向量暴露；报告不会把没跑的当作通过 |
| 规则只存在于一个 SDK 的代码中 | 其他语言只能照抄实现；差异无从发现 |
| 每个 SDK 各自写测试 | 各测各的，跨语言一致无人负责（I12 的教训） |
| 报告只给“通过／失败” | 部分运行、环境缺失、检查本身失效都会被读成通过（I13 的教训；参考模型的坏变体） |

## 组件协议

组件协议是一份独立版本化的规范（仓库 `be-protocol`），每条规则有层级：

| 层级 | 含义 | 检验方式 |
| --- | --- | --- |
| 必须 | 从外部可观察 | 一致性套件检验 |
| 应当 | 建议 | 套件给出警告 |
| 内部 | 外部不可观察（例如事务中不做网络调用） | 官方 SDK 用自己的测试与静态检查保证；第四种语言的组件书面声明并接受评审 |

## 一致性套件

套件对**运行中的容器**检验：端口、写入的表、发布的消息、日志与指标；不读源代码，所以任何语言的组件都用同一标准。

- **测试环境**：真实的数据库与消息系统；夹具组件扮演上下游；模拟的身份提供方与外部服务（用于协议 10 的能力声明验证）。
- **剖面**：按章节组成的检验集合（例如核心、事件、授权、后台工作、对外命令）。组件按自己启用的能力声明需要的剖面。
- **每项检查的结果**：

| 结果 | 含义 |
| --- | --- |
| 通过 | 检查运行且通过 |
| 失败 | 检查运行且发现违反 |
| 未运行 | 环境缺失或前置失败；**不是通过** |
| 不适用 | 组件未启用相关能力，有声明依据 |
| 检查失效 | 检查的自检没有通过，结果不可信 |

- **自检**：每项检查带一个已知违反的夹具；运行前先对它执行，必须得到“失败”。没有自检，一项永远通过的坏检查会让有缺陷的组件被判合格（参考模型的坏变体）。
- **报告**：按剖面给出完整或部分；只有声明的剖面中全部适用的必须检查都运行且通过、没有检查失效，才判“符合”。只覆盖碰巧跑完的剖面、或把未运行算作通过，都会产生假通过（参考模型的两个坏变体）。报告记录组件制品摘要、协议版本、套件版本与环境。
- **坏变体**：套件自身的回归包含每项检查的坏变体运行，确认能抓住。

## 语义向量

跨语言必须得到相同结果的计算，以向量（输入与期望输出）发布在协议仓库中，三个 SDK 在各自的持续集成中运行：

| 向量 | 依据 |
| --- | --- |
| 规范编码与摘要 | 安全 09 |
| 授予段的规范化、包含证明、查询编译 | 安全 07 |
| 十进制解析、舍入、分摊 | 协议 14 |
| 业务日期与法人时区、定时槽位（含夏令时） | 协议 14、协议 01 |
| 游标的编码与解码 | 协议 14 |
| 单元内容摘要 | 协议 11 |
| 回调与 Webhook 签名 | 协议 10 |

向量的期望值由规范决定；某个 SDK 与向量不符是该 SDK 的缺陷，不能修改向量去迁就实现。

## 官方 SDK

- Go、Python、TypeScript 三个 SDK 实现同一份协议，概念与名称相同；SDK 不得有规范之外的行为——先改规范，再改实现。
- **功能矩阵**：每项能力在每个 SDK 中的状态（已实现、已验证、未实现）公开；某个 SDK 未实现的能力，使用该语言的组件不能声明，装配准入因此拒绝（安全 09 的准入检查），不静默降级。
- **契约代码生成**：接口与事件契约（protobuf、JSON Schema）生成各语言代码；生成物记录契约摘要，构建时检查新鲜度。
- **每种语言一套锁定的技术栈**；新增官方语言需要单独决定。

## 两道准入

| 准入 | 条件 |
| --- | --- |
| 单独运行 | 任何语言；声明的剖面“符合” |
| 进入外壳 | 该语言有官方 SDK 与外壳启动器；同一外壳内成员使用同一语言与同一 SDK 版本；外壳义务的检查通过 |

## 版本对应

协议版本、SDK 版本、套件版本与 BrickKit 版本之间有兼容矩阵，随协议仓库发布；客户基线（D58）记录每个组件实际使用的精确版本。升级协议主版本时，矩阵列出每个 SDK 的对应版本与迁移说明。

| 参数 | 起始值 |

## 参考模型

[一致性报告模型](../work/checks/30-conformance-report.py)（种子 20261013，3,000 次运行）：组件声明剖面，部分领域有真实缺陷；检查可能失效（总是通过），也可能因环境缺失未运行。

| 检查 | 结果 |
| --- | --- |
| 声明剖面内有缺陷的组件，从不被判“符合” | 成立 |
| “符合”的报告中没有未运行的必须检查 | 成立 |

3 个坏变体首轮全部被发现：未运行算作通过、不做自检、报告只覆盖碰巧跑完的剖面。模型不是套件的运行结果。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| SK01 | 用 Rust 写的组件 | 通过声明剖面即可单独运行；不能进入外壳 |
| SK02 | 环境缺少消息系统，事件剖面未运行 | 报告为部分，不判符合 |
| SK03 | 一项检查的自检失败 | 结果为检查失效，不判符合 |
| SK04 | 组件未启用对外命令 | 该剖面不适用，有声明依据 |
| SK05 | Go 与 Python 的舍入结果不同 | 不符合向量的一方是缺陷；不改向量 |
| SK06 | 某 SDK 未实现严格路径 B 档 | 使用该语言的组件不能声明；装配拒绝 |
| SK07 | SDK 增加了规范没有的行为 | 不允许；先改规范 |
| SK08 | 生成的契约代码落后于契约 | 构建检查失败 |
| SK09 | 外壳中两个成员使用不同 SDK 版本 | 外壳准入拒绝 |
| SK10 | 内部规则（事务中不做网络调用） | 官方 SDK 用自己的测试保证；第四种语言书面声明并评审 |
| SK11 | 协议同一主版本内新增可选字段 | 旧组件仍然符合 |
| SK12 | 协议收紧一条必须规则 | 发新主版本 |
| SK13 | 报告缺少组件制品摘要 | 报告无效 |
| SK14 | 套件的某项检查对坏变体没有失败 | 套件自身的回归失败 |
| SK15 | 客户基线中的组件版本与报告版本不同 | 不能用该报告作为准入依据 |
| SK16 | 对外命令适配器声明“外部去重”但模拟外部不去重 | 检查失败 |
