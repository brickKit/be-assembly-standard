# 备份、恢复与一致性恢复

> 状态：2026-10-13 运行协议第十五份候选，尚未冻结。承接 C37（备份恢复／HA）、I25（数据库与消息进度的恢复不原子，外部事实与安全记录不能随旧备份回退）、D26（优先保证整套部署的一致性恢复）与[数据与生命周期的标准灾难恢复范围](../04-data-and-lifecycle.md#标准灾难恢复范围)；按 D59 从零设计。

## 本页解决什么

数据库恢复成功，不等于业务恢复成功。整套部署恢复到较早的时刻 T 之后：

1. T 之后已经发出的事件、已经执行的外部操作、已经做出的撤权与销毁，怎样不丢失、不重复、不复活？
2. 恢复的步骤、顺序与检查是什么？谁来确认可以重新开放？
3. 损失的范围怎样确定并告诉用户？
4. 高可用切换与恢复有什么不同？

## 方案比较

| 路线 | 判断 |
| --- | --- |
| 推荐：整套部署恢复到同一时刻 T；消息流重建并按各消费者在 T 的进度补发；外部事实与安全记录从独立的证据存储补回；恢复期冻结一切对外动作；以对账与检查清单决定重新开放 | 不出现幽灵事件与丢失事件；不重复付款；撤权与销毁不复活；损失范围可列出 |
| 只恢复数据库，其余照常启动 | 消息流中留有 T 之后的事件（幽灵事件），消费者却回到 T 之前；在途的外部操作被盲目重发；撤权失效 |
| 按组件分别恢复为标准能力 | 不受影响的组件可以继续服务，但跨组件事实的对齐要逐组件设计；D26 未作为标准，按专项场景设计 |

## 恢复组与备份清单

标准的恢复组是客户的整套部署：

| 状态 | 备份方式 | 恢复后的地位 |
| --- | --- | --- |
| 全部组件的数据库 | 物理备份 + 预写日志归档，支持恢复到任意时刻 | 权威；恢复到 T |
| 对象存储 | 对象版本保留与异地副本；对象在备份窗口内不物理删除（[协议 11](11-tiering.md)、[协议 12](12-attachments-and-object-storage.md)） | 按恢复后目录与附件记录核对 |
| 消息流 | 不作为权威备份；恢复时重建 | 由各组件的发件表补发 |
| 配置与密钥引用 | 随客户基线版本管理（协议 19） | 恢复到与 T 一致的基线；密钥本身按密钥管理恢复 |
| 独立证据存储（由审计组件兼任） | 只追加、单独保存与复制，不随部署备份回退 | 恢复后用于补回 T 之后的外部事实与安全记录 |
| 审计存储 | 按[协议 03](03-audit-durability.md) 单独保存 | 不回退；T 之后的审计保留，用于确定损失范围 |

**独立证据存储**保存恢复时不能丢的记录：安全记录的变更（授予、撤销、任职变化，[安全 08](../security/08-state-and-change-protocol.md)）、销毁与擦除记录、对外命令的终态与外部单号（[协议 10](10-external-integration.md)）。它由审计组件兼任（[基础能力卡](../components/infra.md#infraaudit)）：审计组件已经有回执、备份水位与“不回退”的保存，不再另设一个基础资源；证据与审计记录分开存放与查询。

写入方式：

- 一般记录（包括授予等放宽）在本地事务提交后经发件表写入，有回执，回执之前的记录在本地保留。
- **每条安全记录的变更都在本地留下记录身份与提交序号**：本地事务把证据记录身份、变更后的对象版本与属主本地的全局提交序号写进变更历史（同一事务）；提交序号在取得守卫或对象锁之后分配（或按协议 02 的锁内提交后编号），使序号的先后等于提交的先后，并按协议 14 带纪元；结论与经发件表写入的记录都携带这个提交序号。记录写的是变更本身（“从范围中移除 X”“解除与 P1 的上级关系”），不是变更后的绝对状态。证据的追加顺序不等于生效顺序（收紧在提交之前追加意图，放宽在提交之后才经发件表追加），重放只按提交序号排序。
- **收紧类记录由各自的属主记证据**：授权组件记安全记录的收紧（撤销、管理资格回收、安全处置）；员工组件记离职、任职结束与账号关联的结束；组织组件记收紧性的组织调整（撤销组织、移出上级、缩小范围）；身份适配组件记账号停用，包括它在补取或按 `P_pull` 定期拉取时从身份产品得到的控制台直接停用（拉取到的启用同样记录，使“停用后又启用”在重放时按提交序号得到启用）；数据的属主记销毁与擦除。授权组件应用来源事件时不再等待证据；由来源事实派生的撤销（例如任职结束后自动收回的授予，D30）不另记证据，恢复后来源在属主处重新办理，授权组件经投影重新派生。
- **分两段写**（先记意图，后生效）：
  1. **意图**：在本地守卫事务**之外**、事务开始之前，把收紧记录（记录身份、主体、对象、时间）写入证据并等待回执，时限 2 秒；超时或不可达时，把同一条完整记录发到部署之外、不随恢复回退的告警渠道，发送时限 2 秒；两者都失败时本地记“双通道失效”的严重告警，照样继续（不能为了证据推迟撤权）。
  2. **提交**本地事务；事务内不做网络调用。
  3. **结论**：提交成功后经发件表写“已生效”；提交失败（冲突、检查不通过）写“已取消”。
- 代价：每次收紧最多多出两段写入时限（起始各 2 秒）；批量计划的意图批量写入。
- 身份产品（例如 Casdoor）的数据库若在部署内，属于恢复组，与其他数据库恢复到同一时刻；客户自有的外部身份源不随本部署回退。

**恢复时的重放**（整套恢复的第 6 步，部署处于冻结中，没有并发写入；高可用切换不做重放，见下文“高可用与故障切换”）：逐条比较证据与告警中的记录和恢复后的数据库。“已体现”按记录身份判定：恢复后变更历史中有这条记录身份，就已体现；不按时间与 T 比较（意图早于 T、提交晚于 T 的收紧也不会漏掉）。未体现的记录**按属主的（纪元，提交序号）字典序**重放（跨对象的先后与原来一致，例如管理员交接“先授予 B、后撤销 A”；纪元按协议 14 定序）。属主采用新纪元时，把旧纪元分叉点之后的证据记录标为“随切换丢失”：它们已列入那次切换的损失范围，重放跳过它们并列入复核，不让一项已决定不再授予的权限在日后的整套恢复中回来。只有意图、序号未知的收紧排在该属主的最后：

| 证据状态 | 恢复后数据库中未体现时 |
| --- | --- |
| 已生效（含经发件表写入的放宽） | 按提交序号在属主处重新执行（员工组件重新办理离职，组织组件重新调整，身份适配组件向产品重新停用，授权组件重放自己的记录）；授权组件经正常投影得到来源事实，不在自己的投影上重放 |
| 只有意图（撤销、停用、任职结束、组织收紧） | 在该属主的已生效记录之后执行，并标为“意图未确认”供复核——多执行一次收紧是安全的 |
| 只有意图（销毁、擦除） | **不自动执行**（不可逆），列入人工复核 |
| 已取消 | 忽略 |

**重新执行的规则**：记录按原变更重新施加，不重做业务前置校验（例如“撤销组织要求部门内没有在职任职”“授予人必须是管理员”）——它们在原时刻已经校验过，而重放中途的状态不是任何真实时刻的状态；只检查被引用的对象仍然存在（不存在时按协议 07 的悬空引用处理）。D62 的“可用的授权管理员为零”在重放全部结束后才判定，重放中途不判定。重放结束后对最终状态运行一次不变量检查（可用管理员、职责分离、管理上限与包含证明）：违反的主体关闭并列入复核，由第 10 步的人裁定。只有意图的离职、停用、安全处置照常执行并标记（不能让一个可能被盗的唯一管理员账号在恢复后保留管理权）；只有意图的 Authz 内普通撤销若会使可用管理员为零，不执行而转复核，但复核期间关闭该主体的管理资格。任何原因造成的可用管理员为零，都按 D62 进入待恢复，由部署所有者的恢复凭据处理（安全 08）。重新执行写入原记录身份，所以第 6 步中断后重来时，已执行的记录按“已体现”跳过，不重复执行。任何重新执行失败时，关闭相关主体（按无法证明处理）并列入人工复核，不静默跳过。告警渠道中的记录（证据当时不可达）由人复核后执行。

例：恢复点 T 之后，管理员误把付款权授予 Bob（提交序号 107），一秒后撤销（序号 108）。证据中撤销的意图先于授予追加；按提交序号重放得到“授予、撤销”，恢复后 Bob 没有付款权。按追加顺序重放会得到相反的结果；按对象分组、对象之间任意先后重放，会让管理员交接中途出现零个管理员（参考模型的两个坏变体）。

因此，收紧类记录的恢复点目标为零，只有“双通道失效”的时间段与身份产品侧变更到适配组件拉取之间的间隔（不超过 `P_pull`，起始 1 分钟）除外。

多个数据库集群时，各集群按同一时刻恢复；跨集群的恢复不是原子的。恢复或切换使来源的纪元变化，投影与增量事实（协议 05、06 的序号）的消费者按[协议 02 的纪元变化](02-projections.md#纪元变化)对齐：新纪元的快照直接覆盖，不按版本或序号比较（它们可能被重用）。

## 发件表的保留与消费者进度

整套恢复依赖两件事，平时就要做到：

- **消费者记录进度**：每个消费者在自己的数据库中按来源记录已处理的事件（收件表，或按来源的连续序号）。
- **发件表的保留**分成两个量，互不牵连：
  - **未发布积压**：尚未发布到运输的行。D14 的保护只看它（超过阈值时按协议 17 限制受影响业务），因为这才是运输故障。
  - **补发保留**：已发布的行按固定上限保留（时间与容量，起始值见参数表），只为整套恢复时补发。它不看有哪些消费者、消费者是否确认，所以后加的消费者不需要生产者变更，下游故障也不会反向限流上游。消费者落后超过保留上限时只告警。

恢复时，每个生产者补发的范围必须覆盖各消费者在 T 的进度：可以按各消费者的进度补发，也可以把补发保留内的全部行补发、由消费者按收件表去重；但不能只补发一段比消费者落后距离更短的固定时间窗，那会漏掉落后的消费者（参考模型的“只补发固定时间窗”坏变体）。需要的行已经超出补发保留时，该消费者按[协议 02](02-projections.md) 的完整快照修复，或按协议 05 的增量事实按序号向产生方补取与对账，并记入恢复报告；恢复流程从各消费者的数据库读取进度，生产者不需要事先知道有哪些消费者。

## 恢复流程

| 步骤 | 内容 | 完成的依据 |
| --- | --- | --- |
| 1. 宣布与选择 T | 有权限的人宣布恢复，选择恢复时刻 T（数据损坏之前、日志可达的最晚时刻） | 恢复记录：原因、T、批准人 |
| 2. 冻结 | 边缘入口返回维护中；停止定时任务、后台工作、发件转发、消费者与适配器的发送；外部回调入口返回暂不可用，外部按其重试 | 所有执行者停止，确认没有在途发送 |
| 3. 恢复数据库 | 各集群恢复到 T | 恢复日志与校验 |
| 4. 推进部署恢复代次 | 部署恢复代次加一（权威计数在恢复组之外，只增不减，[协议 14](14-data-foundations.md#库内计数与纪元)），并在解冻前写入每个组件库的一行（纪元由它参与组成；与授权的恢复代次 `authz.recovery` 无关）：所有工作项的租约代次、转层与对外命令的代次推进，旧执行者即使残留也被拒绝 | 代次记录 |
| 5. 重建消息流 | 删除并重建流与持久消费者；生产者按各消费者在 T 的进度补发，事件 ID 不变，消费者按收件表去重 | 每个消费者的补发清单 |
| 6. 补回收紧与销毁 | 按上文“恢复时的重放”逐条比较证据与告警中的记录：已生效而未体现的在属主处重新执行；只有意图的收紧执行并标记，只有意图的销毁转人工；“双通道失效”的时间段列入损失范围。另外使恢复前签发的全部会话、刷新令牌与服务凭据失效（身份适配组件推进会话代次，凭据属主轮换），因为 T 之后的登出与吊销可能已随数据库回退；用户重新登录 | 重放清单、待复核清单、损失范围与复核结论 |
| 7. 外部对账 | 每个适配器查询外部在 T 之后的记录：本地处于发送或结果未知的命令先查询，不重发；外部有、本地没有的，从证据存储与外部查询补回 | 每个适配器的对账结果 |
| 8. 内部一致性检查 | 跨组件的对账：预占与订单（协议 04）、出账与来源、子账与总账（协议 05）、期间状态（协议 06）、引用（协议 07）、目录与对象（协议 11、12）、投影完整性（协议 02） | 检查清单，全部通过或差异有处置 |
| 9. 损失范围 | 用审计存储与访问日志列出 T 之后用户提交、但恢复后不存在的业务操作 | 损失清单，按用户与单据 |
| 10. 重新开放 | 开放写入之前，对外可见的连续单号从证据与外部对账取得已用的最大值，从其后继续（协议 14）。有权限的人依据检查清单与损失清单决定开放；先开放查询，再开放写入与对外动作；通知受影响的用户重新录入 | 开放记录 |

**幽灵事件**：T 之后发布到旧消息流中的事件，其源数据在恢复后不存在。保留旧消息流会让消费者处理它们（参考模型的“保留旧消息流”坏变体），所以消息流必须重建。

**外部操作**：恢复后的数据库中处于“发送中”的命令，在 T 之后可能已经执行；直接重发会重复执行（参考模型的坏变体）。

**安全记录**：只从备份恢复安全状态，T 之后的撤权就失效了（参考模型的坏变体）；重放证据存储中的记录使其继续有效。T 之后新增的授予同样重放，它们有自己的批准记录；被引用的对象在恢复后不存在时，授予成为悬空引用，按协议 07 处理。

## 部分恢复与局部修复

- 可重建的副本（投影、数据集、搜索索引）出错时，按协议 02、13 重建，不需要整套恢复。
- 普通的业务错误按业务更正流程处理（冲销、更正单据），不使用恢复。
- 只恢复一个组件不是标准能力（D26）；需要时作为专项场景设计：列出它与其他组件的全部事实关联，按本页的对账步骤逐项对齐。

## 高可用与故障切换

声明为高可用的部署，每个组件库的**全部写入同步提交**（D66）：两个备库，任一确认即完成。本节是底层预留、后期启用：正式开发起步是单实例、单数据库，本节的机制在真正上高可用时实现与实测；但库内计数带纪元、恢复流程现在就按本节的需要设计。

| 方式 | 数据损失 | 说明 |
| --- | --- | --- |
| 高可用切换（整体同步） | 已确认的提交不丢失；只可能丢失“对外已可见、备库尚未确认”的极短窗口（PostgreSQL 在等待备库确认时提交已对其他会话可见） | 前提见下文。不冻结，不执行第 4、5、6 步：切换使该集群的时间线变大，纪元随之变大；库内计数带纪元，窗口内被重用的计数按纪元与分叉点识别（[协议 14](14-data-foundations.md#库内计数与纪元)）；消费者按[协议 02 的纪元变化](02-projections.md#纪元变化)对齐。消费者自己的库切换后，按自己库中记录的进度请生产者补发（第 5 步的补发机制），不重建消息流。切换后自动启动第 8 步的对账工作项（起始 1 小时内完成），并执行第 7、9 步 |
| 降级切换 | 可能丢失最后一段已提交事务 | 两个备库都不可用而降级为异步期间切换，或无法确认提升的备库包含全部已确认提交时，按整套恢复的流程处理：冻结、推进部署恢复代次、第 5–9 步、人工开放。声明的残余风险 |
| 消息系统的集群副本 | 按其复制设置 | 消息流不是权威；丢失时按第 5 步补发 |
| 单节点部署 | 依靠备份 | 小客户的标准组合；恢复目标按备份频率声明 |

共同规则：

- **提升的前提**：新主库受理写入之前旧主库已被隔离；只提升包含全部已确认提交的备库（`ANY 1` 时取日志位置最高的那个，两个备库都要可达才能判断）；不能判断时不自动提升，按降级切换处理。
- **本地提交持久**：全部组件库 `fsync` 开启，`synchronous_commit` 为 `on`（等备库落盘），不允许 `off` 或 `local`；SDK 在启动时检查并纳入一致性套件。
- **确认之前不报成功**：`COMMIT` 前 `SET LOCAL statement_timeout = 0`，同步等待不设客户端取消；服务端取消或连接中断使等待中断时（`COMMIT` 带警告返回或连接断开），按“结果未知”处理，不报成功。对收紧与不可幂等外部调用的发出前标记（协议 01、10），SDK 立即把完整记录发到部署之外的告警渠道（与上文证据的外部告警渠道相同），并在进程内继续尝试确认（在同一对象上写一条确认行，使之前的日志一并确认）；任何重试——包括按幂等键发现“已生效”的重放——都在完成一次同步确认之后才返回成功。SDK 提供这一原语并有测试。
- **降级**：两个备库都不可用时，高可用工具降级为异步并告警，同时在部署之外的运行档案中写入“降级开始”；组件从这里得知降级，此后的收紧与发出前标记也发到外部告警渠道，使清单不依赖可能一起丢失的库。
- 证据存储（审计组件）同样整体同步，降级切换时按整套恢复处理。

服务端取消、降级时等待者被放行、高可用工具的同步模式与提升选择、切换钩子写运行档案的行为，都列入代表部署实验。

高可用是可选的部署组合，按客户基线声明；故障切换的演练与恢复演练分别进行。

## 恢复目标与演练

- 每个客户基线声明恢复点目标与恢复时间目标；标准组合的起始值见下表，实际值由代表部署实验与客户的数据量测得后承诺。
- 演练在隔离环境中进行：用真实的备份恢复，执行完整流程，记录每一步的时间与检查结果；演练中包含“T 之后有外部付款”“T 之后有撤权”“某消费者在 T 时落后”的场景。
- 演练记录进入客户的运行档案；没有演练记录，不宣称恢复目标已满足。

## 参考模型

[一致性恢复模型](../work/checks/27-consistent-recovery.py)（种子 20261013，3,000 次运行）：生产者写事实与发件表，转发发布，消费者经收件表处理；适配器执行外部命令（外部保留自己的记录）；收紧（撤销、销毁）按“意图—本地提交—结论”两段写入证据，结论带属主的提交序号；授予在提交后经发件表写入证据；多个收紧可同时等待提交、按任意顺序提交，证据的追加顺序因而不等于生效顺序；进程可在提交前后崩溃，结论与授予记录可能未送达，意图可早于 T、提交晚于 T；两个主体都是管理员；随机选择较早的时刻 T 恢复整套部署，按记录身份判定是否已体现，按属主的原提交序号重放，不重做业务校验。

| 检查 | 结果 |
| --- | --- |
| 消费者没有处理恢复后不存在的事实 | 成立 |
| 恢复后存在的每个事实都已被消费者处理 | 成立 |
| 外部不重复执行 | 成立 |
| 外部执行过的命令在本地都可知 | 成立 |
| 失效前最后一次生效的变更是撤销的主体，恢复后仍被撤销（声明损失除外） | 成立 |
| 恢复后没有销毁从未真正销毁的对象 | 成立 |
| 真正生效的销毁在恢复后重新执行或列入复核 | 成立 |
| 恢复后比实际更受限的主体都被标记、列入复核或落在声明损失内（过量收紧只在可见时允许） | 成立 |
| 重放已确认记录的过程中与重放结束后，不出现真实历史里没有过的“零个管理员”（会造成零个管理员的只有意图撤销转复核） | 成立 |

已发布行按固定上限保留；超出保留的事件由消费者修复补齐，修复规则对所有变体一致、只补超出保留的部分。15 个坏变体全部被发现（另有管理员交接的定向场景，50 个种子）：

- 消息与补发：保留旧消息流（幽灵事件）、重建消息流但不补发、只补发一段短于消费者落后距离的固定时间窗、不做消费者修复；
- 外部命令：不查询就重发发送中的命令；
- 安全记录：只从备份恢复安全状态、告警不带完整记录、先提交后写意图（中间崩溃即丢失）、按记录时间与 T 比较选择重放（意图早于 T、提交晚于 T 的撤销与销毁被漏掉）、只有意图的销毁自动执行（提交失败或崩溃的销毁被误执行）、只有意图的撤销执行但不标记（过量收紧不可见）、按证据的追加顺序重放（“授予后立即撤销”在恢复后复活）、按对象分组而对象之间任意先后（管理员交接中途出现零个管理员）、重放授予时重做“授予人必须是管理员”的校验（授予被拒绝而丢失）、只有意图的撤销即使造成零个管理员也执行。

首轮的正确版本按固定时间窗补发，模型发现在 T 时落后超过窗口的消费者会丢事件；改为覆盖各消费者在 T 的进度后成立，固定时间窗成为坏变体。各轮修改的经过见[证据记录](../work/evidence.md)。

**模型没有覆盖的条款**：属主各自记证据与在属主处重新执行（员工组件、组织组件、身份适配组件，身份产品数据库进入恢复组）、派生撤销经投影重新派生、`P_pull`、批量计划的意图批量写入、写证据的等待时限、高可用中的整体同步与降级（D66），靠 RC14、RC21–RC42 的实现测试；按原提交序号重放时，跨对象的前置条件在真实历史中已经成立，所以“不重做业务校验”只在记录缺失（声明损失、只有意图）时起作用，模型没有单独检验。模型不是数据库、消息系统或备份工具的运行结果。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| RC01 | 恢复到 T 后启动服务 | 先冻结、推进代次、重建消息流，再开放 |
| RC02 | T 之后发布的事件 | 不被处理（消息流已重建） |
| RC03 | 某消费者在 T 时落后两天 | 按它的进度补发，不丢事件 |
| RC04 | 需要补发的发件表行已被清理 | 该消费者做完整快照修复或增量事实对账，并记入损失范围 |
| RC05 | 本地处于发送中的付款 | 先查询外部，不重发 |
| RC06 | T 之后外部已收款，本地无记录 | 从证据存储与外部查询补回 |
| RC07 | T 之后撤销的权限 | 恢复后仍然撤销 |
| RC08 | T 之后执行的销毁 | 重新执行 |
| RC09 | 残留的旧执行者在恢复后提交 | 因代次不符被拒绝 |
| RC10 | 用户在 T 之后录入的订单 | 列入损失清单并通知用户 |
| RC11 | 目录指向的冷对象缺失 | 检查不通过，按协议 11 处理后才开放 |
| RC12 | 投影出错 | 重建投影，不做整套恢复 |
| RC13 | 只恢复库存组件的请求 | 不是标准能力，按专项场景设计 |
| RC14 | 异步复制的主库故障切换 | 旧主库已隔离；不冻结、不执行第 4–6 步；纪元变大，消费者对齐；执行外部对账、一致性检查与损失范围 |
| RC15 | 没有演练记录 | 不宣称恢复目标已满足 |
| RC16 | 恢复期间外部回调到达 | 入口暂不可用，外部按其重试；开放后处理 |
| RC17 | 撤销付款权时证据组件不可达，随后恢复到撤销之前 | 撤销照样生效，完整记录进入外部告警渠道；恢复后依据告警重新执行撤销 |
| RC18 | 某消费者落后超过补发保留 | 只告警，不限流上游；恢复时该消费者走快照修复或按序号补取，记入恢复报告 |
| RC19 | 新增一个消费者组件 | 生产者不需要变更 |
| RC20 | 报表组件故障一周 | 上游的订单确认不受影响 |
| RC21 | 写意图之后、本地提交之前进程崩溃，随后恢复 | 只有意图的撤销在恢复后执行并标“意图未确认”；不出现撤权复活 |
| RC22 | 证据组件与外部告警渠道同时不可达时撤权，随后恢复到撤权之前 | 声明的残余风险：恢复报告列为损失范围，要求复核该时间段的权限 |
| RC23 | 意图写于 T 之前、本地提交晚于 T，随后恢复到 T | 按“是否已体现”比较，不漏掉 |
| RC24 | 销毁只有意图，本地提交失败 | 恢复后不自动执行，列入人工复核 |
| RC25 | T 之后员工离职，随后恢复到 T | 员工组件依据证据重新办理离职，授权经投影得到 |
| RC26 | T 之后管理员在身份产品控制台直接停用账号，随后恢复 | 适配组件拉取到停用时已记证据，恢复后向产品重新停用 |
| RC27 | T 之后授予某人付款权、随即撤销，随后恢复到两者之前 | 按属主的原提交序号重放，恢复后没有付款权；不按证据的追加顺序 |
| RC28 | T 之后撤销组织（组织收紧），随后恢复 | 组织组件依据证据重新撤销，授权经投影得到 |
| RC29 | T 之后任职结束，授权组件随之自动收回授予，随后恢复 | 员工组件重新办理任职结束，授权组件经投影重新派生收回；派生的收回不另有证据 |
| RC30 | 高可用部署中授权组件的库切换，切换前刚撤销付款权 | 撤销已同步提交（D66），切换后仍在；授权组件照常服务，不等待证据重放 |
| RC31 | 两个备库都不可用、已降级为异步期间，员工库切换丢失离职 | 降级切换按整套恢复处理：冻结、推进部署恢复代次；依据外部告警渠道中的清单与证据重新办理离职后才开放 |
| RC32 | 重放“撤销组织”时，部门内的任职调出属于员工对象 | 按原变更重新施加，不重做“部门内没有在职任职”的前置校验；撤销生效 |
| RC33 | 第 6 步执行到一半中断后重来 | 已执行的记录写有原记录身份，按已体现跳过，不重复执行 |
| RC34 | T 之后管理员交接：先授予 B 管理资格，再撤销 A，随后恢复 | 按原提交序号重放，重放中途不出现零个管理员；B 的授予不重做“授予人必须是管理员”的校验 |
| RC35 | 第 6 步重放时证据组件可读、授权组件尚未开放 | 证据读取是系统方法，服务准入由部署声明的服务到方法许可决定，不依赖授权视图 |
| RC36 | 收紧的同步等待被服务端取消（`COMMIT` 带警告返回），调用方没有重试，随后切换 | 按结果未知处理，不报成功；SDK 已把完整记录发到外部告警渠道并继续尝试确认；切换后依据清单复核 |
| RC37 | 身份产品的库切换，丢失控制台里的一次停用 | 适配组件拉取到产品坐标中晚于本地记录的“启用类”变更才认作重新启用；没有这类变更时判为产品回退，重新停用并告警 |
| RC38 | 两个备库都不可用（降级）期间主库坏掉并切换 | 降级切换按整套恢复处理；运行档案中的“降级开始”让组件此前已把收紧送到外部告警渠道 |
| RC39 | 整套恢复中一条离职记录缺失（双通道失效），按原序重放后出现职责分离冲突 | 重放结束后的不变量检查发现冲突，相关主体关闭并列入复核，不进入待恢复 |
| RC40 | T 之后唯一管理员的账号被盗并被停用，停用只有意图（提交时崩溃），随后恢复 | 只有意图的停用照常执行并标记；可用管理员为零，按 D62 进入待恢复，由部署所有者恢复 |
| RC41 | T 之后用户登出，随后恢复到 T | 第 6 步使恢复前签发的会话全部失效，登出前的会话不复活 |
| RC42 | 高可用切换丢失了一次授予（分叉点之后），日后整套恢复到切换之前 | 该授予的证据已标“随切换丢失”，重放跳过并列入复核 |
