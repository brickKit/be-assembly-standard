# 审计的可靠保存

> 状态：2026-10-13 数据与业务协议第三份候选，尚未冻结。承接问题 I29（终局审查 R03）、D28、D43 与 C35；按 D59 从零设计，现行观测底层文档中的审计路径只作参考。

## 本页解决什么

D28 定了：必要的业务变更、权限与配置变化、敏感读取与导出、代操作、安全拒绝等，要按明确的动作清单可靠记录；普通低风险读取保留访问日志即可。本页回答“可靠”具体指什么：

1. 一条必需的审计记录在什么时刻算“已记录”？之后在任何时刻，它至少存在于哪里？
2. 读取和拒绝没有业务事务可以附着，怎样记录？
3. 审计组件不在线、从备份恢复、转运崩溃时，怎样保证不丢、不重？
4. 什么时候才可以删掉某一份副本？

**反例 R03**：现行做法是业务写入与审计事件在同一事务里写进 Outbox，经 broker 送到审计组件。但 Outbox 在 broker 确认后只保留 14 天，消息流只保留 7 天，两者的清理都不看审计组件是否已经保存。审计组件没装、或长期没保存成功时，期限一过，审计记录一份不剩，而且没有任何报错。

## 方案比较

| 路线 | 判断 |
| --- | --- |
| 推荐：每个组件先写本地审计表（审计专用的 Outbox）作为第一落点；转运作业送到审计组件，按记录 ID 幂等，收取应用层回执；本地副本在“收到回执且已进入审计组件的备份”之后才可删 | 任何时刻至少一份持久副本；审计组件故障或恢复都不丢；不在业务事务里做网络调用 |
| 审计事件走 Outbox 与消息流，按运输期限清理（现行） | 实现最省事，但运输期限与长期保存脱钩，R03 的丢失窗口一直存在 |
| 业务请求同步写审计组件 | 审计组件不可用时全部受审计操作停止；事务里不能做网络调用，只能在事务外写，又出现“业务提交了、审计没写”的窗口 |
| 只依赖应用日志 | 日志会被采样、轮转、丢弃，D28 明确不允许用它替代必要审计 |

## 什么需要审计

操作定义中的 `audit: required`（[安全 09](../security/09-encoding-and-profiles.md#定义资源维度操作与字段)）声明该操作必须产生审计记录。标准必需类别如下，客户可以在允许范围内扩展，不能删减：

| 类别 | 例子 | 记录时点 |
| --- | --- | --- |
| 业务变更 | 确认订单、过账、付款、库存调整 | 与业务写入同一事务 |
| 安全与配置变更 | 授予、撤销、管理资格、角色修订、有限业务设置修改 | 与安全记录的生效点同一事务（[安全 08](../security/08-state-and-change-protocol.md#生效点)） |
| 敏感读取与导出 | 查看成本、导出客户名单、下载附件原文 | 读取准入后、释放数据前，单独提交 |
| 代操作与特殊会话 | 委托代办、只读扮演、紧急访问的开始、每个请求、结束 | 会话激活与每个请求 |
| 安全拒绝 | 越权访问、包含证明失败、受保护操作缺确认 | 拒绝发生时，受容量保护约束（见下文） |
| 后台工作处置 | `dead`、`paused` 工作项的人工处置（[协议 01](01-background-work.md)） | 与处置同一事务 |

## 第一落点：本地审计表

每个组件在自己的 schema 中有一张只追加的审计表。它就是 D28 承接的“审计 Outbox”：与业务同事务写入、可靠转运；区别只在于它与业务事件的 Outbox 分开，删除资格绑定审计回执与备份水位，而不是运输期限。D28 的机制选择因此保留，R03 的丢失窗口被关闭。

| 字段 | 含义 |
| --- | --- |
| `id` | 记录身份，UUIDv7；全局唯一，转运与去重都用它 |
| `occurred_at` | 发生时刻 |
| `category` | 上表的类别 |
| `operation` | 操作键 |
| `outcome` | `succeeded`、`denied`、`failed` |
| `reason` | 拒绝或失败的 reason（安全 09 的错误分类） |
| `actor`、`represented`、`appointment`、`delegation`、`session` | 实际操作者、被代表主体、选定任职、委托与会话引用（安全 02） |
| `target` | 对象引用与修订 |
| `changes` | 业务与安全变更：字段名与变更前后的值摘要；受限字段只记摘要或掩码，不记明文 |
| `request` | 请求标识、追踪标识、调用模式 |
| `digest` | 按安全 09 的规范编码计算的记录摘要 |
| `transfer_receipt` | 审计组件回执：保存序号与链摘要；未转运时为空 |

写入失败的处理：

- **业务变更与安全变更**：审计行与业务写入同一事务，事务失败则业务也不发生。
- **敏感读取与导出**：先在一个短事务中提交审计行，再释放数据；审计行写不进去就拒绝读取。数据库在提交后、释放前崩溃，最多多出一条“读了但没交付”的记录，不会出现“交付了但没记录”（参考模型的“先放数据后记审计”坏变体）。
- **安全拒绝**：写入失败不改变拒绝结果，同时记应用错误日志并计数告警。

## 拒绝记录的容量保护

攻击或配置错误可能在短时间内产生大量拒绝。每个“主体 × 原因 × 时间窗口”设一个明细预算：预算内逐条记录；超出后同一窗口只保留一条汇总记录，带计数、首次与最后一次时刻、若干样例的引用。汇总不丢失次数，所以不是 D28 禁止的“采样替代”；但明细在超出预算后不再逐条保留，这一点要在审计说明中写明。

## 转运与回执

转运作业是[协议 01](01-background-work.md) 的 `idempotent_external` 工作项：

1. 按 `id` 顺序取出尚无回执的本地记录，批量发送给审计组件。
2. 审计组件按 `id` 幂等写入：已存在且摘要相同则直接返回原回执；已存在但摘要不同，按完整性事件告警并拒绝。
3. 审计组件为每条记录返回回执：（审计库纪元，保存序号）、所在来源链的链摘要（[协议 14 的库内计数与纪元](14-data-foundations.md#库内计数与纪元)）。
4. 转运作业在本地事务中写入回执。

转运崩溃时，下次从仍无回执的记录继续；已经写入审计组件但回执没落地的记录，会被重发，由第 2 步的幂等保证不重复。

## 本地副本的删除资格

本地审计行同时满足以下三条才可以删除：

1. 已有审计组件的回执；
2. 审计组件已完成包含该回执序号的备份（审计组件公开自己的“已备份水位”，即已进入持久备份的最大保存序号，同样带审计库纪元；回执与水位的纪元不同时不能比较，回执作废，按 `id` 重新转运——审计库切换或恢复后序号会被重用）；
3. 超过本地最短保留期。

第 2 条容易被忽略：只看回执就删，审计组件随后从更早的备份恢复时，备份之后保存的记录在两处都没有了（参考模型的“收到回执即删除”坏变体）。审计组件从备份恢复后，会宣布新的恢复代次；回执序号高于其备份水位的本地记录，回执作废，重新转运。

**永远不按 broker 确认或运输期限删除。**审计不经过 Outbox 与消息流转运时，二者的保留期与审计无关；如果组件同时发布业务事件，那是另一件事。

## 审计组件

- 只追加存储；每个来源组件一条链，链摘要逐条串接，防止事后插入或删除而不被察觉。需要防范存储管理员篡改时，定期把链摘要锚定到外部（例如打印或交给客户保管），这是可选能力。
- 定期备份，并公开已备份水位。
- 查询受权限控制，查询本身也写审计；查询结果按请求者的字段资格裁剪。
- 生产部署中，只要有组件声明了必需审计动作，就必须安装审计组件；装配检查会阻止缺少它的组合。观测方案的精简（D43）不包括审计。审计组件可以合并进外壳。

**兼任证据存储**：审计组件同时保存恢复时不能丢的独立证据（安全记录变更、销毁与擦除、对外命令终态），与审计记录分开存放与查询（[协议 15](15-backup-and-recovery.md#恢复组与备份清单)）。收紧类安全记录“先记证据、后生效”的同步写入与上文否定的“业务请求同步写审计组件”不同：它只针对收紧，失败时不阻止收紧生效（完整记录改走外部告警渠道），所以不会让审计组件的可用性拖住业务。

## 积压与故障

| 情形 | 行为 |
| --- | --- |
| 审计组件不可用 | 业务照常；本地表积压；告警 |
| 本地积压超过告警阈值（条数或最老未转运记录的时长） | 告警 |
| 本地积压超过容量上限 | 新的必需审计操作拒绝（候选 reason `AUDIT_CAPACITY_EXHAUSTED`），已有业务与普通读取不受影响；直到积压回落 |
| 审计组件从备份恢复 | 作废高于其备份水位的回执，从本地重新转运 |
| 组件从备份恢复 | 本地记录可能少于审计组件已保存的；不影响完整性：审计组件里的记录仍在，组件重新产生的记录 ID 不同 |

## 保留与法律保全

保留期按“类别 × 法人所在地区 × 客户要求”确定，不设全系统统一的法定年限（终局审查 R03 的同一结论）。法律保全可以冻结某些记录不被删除。审计记录中的个人信息按适用的法律依据保留；需要处理擦除请求时，对主体引用做假名化，不删除审计事实本身，具体规则随数据生命周期专题统一确定。

## 参数起始值

| 参数 | 起始值 |
| --- | --- |
| 转运批量 | 每批 500 条 |
| 转运间隔 | 每 5 秒，积压时连续运行 |
| 本地最短保留期 | 7 天 |
| 积压告警 | 最老未转运记录超过 15 分钟，或超过 10 万条 |
| 积压容量上限 | 按部署磁盘预算配置，起始为本地审计表 5 GiB |
| 拒绝明细预算 | 每主体每原因每分钟 20 条 |
| 审计组件备份间隔 | 每日；水位随每次备份推进 |

## 参考模型

[审计可靠保存模型](../work/checks/15-audit-durability.py)（种子 20261013，3,000 次运行）：随机产生业务写入与敏感读取，审计组件随机不可用、随机备份、随机从备份恢复，转运作业随机在“审计组件已写入、回执未落地”时崩溃，本地清理随机执行。

| 检查 | 结果 |
| --- | --- |
| 任何时刻，每条已提交的必需记录至少存在于本地或审计组件之一；排空后全部在审计组件中 | 成立 |
| 审计组件中每条记录只有一份 | 成立 |
| 敏感读取在审计记录提交前不释放数据 | 成立 |

4 个坏变体全部被发现：按 broker 确认删除本地副本（R03 的丢失）、收到回执即删除而不看备份水位（审计组件恢复后丢失）、审计组件写入不幂等（重复）、先释放读取数据再提交审计记录。模型不是 SDK、数据库或审计组件的运行结果。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| AU01 | 审计组件长期不可用，超过消息流与 Outbox 的保留期 | 本地记录仍在；恢复后全部转运 |
| AU02 | 审计组件写入成功后回执丢失 | 重发；按 `id` 幂等，不产生第二份 |
| AU03 | 同一 `id` 重发但摘要不同 | 拒绝并按完整性事件告警 |
| AU04 | 收到回执，但审计组件尚未备份到该序号 | 本地不删除 |
| AU05 | 审计组件从备份恢复 | 高于备份水位的回执作废，从本地重新转运 |
| AU06 | 业务事务回滚 | 无审计记录；事务提交则一定有 |
| AU07 | 敏感读取的审计行写入失败 | 拒绝读取 |
| AU08 | 提交审计行后、释放数据前崩溃 | 有记录、未交付；不出现交付而无记录 |
| AU09 | 某主体一分钟内触发上千次拒绝 | 预算内逐条记录，超出部分为带计数的汇总 |
| AU10 | 本地积压超过容量上限 | 新的必需审计操作拒绝，其他业务不受影响；告警 |
| AU11 | 生产组合有必需审计动作但未安装审计组件 | 装配拒绝 |
| AU12 | 选择精简观测方案 | 审计能力不受影响 |
| AU13 | 查询审计记录 | 需审计查看权限；查询本身写审计；字段按资格裁剪 |
| AU14 | 审计链中间一条被删除或篡改 | 链校验失败并告警 |
| AU15 | 记录中出现受限字段的明文 | 不允许；只记摘要或掩码 |
| AU16 | 代办与扮演会话中的请求 | 同时记录实际操作者与被代表主体、会话引用 |
| AU17 | 法律保全期间到达保留期 | 不删除 |
| AU18 | 只读扮演或紧急访问会话的开始与结束 | 都有记录，并关联通知意图 |
| AU19 | 审计库切换后保存序号被重用，生产者持有旧纪元的回执 | 回执纪元与已备份水位的纪元不同，不据此删除本地副本；回执作废，按 `id` 重新转运 |

## 依据与独立判断

原书决策总表第 62 条已要求“Outbox／Inbox／通知／审计日志必须设置保留周期”，但没有把审计的长期保存与运输期限分开；现行设计沿用 Outbox 承载审计，留下了 R03 的窗口。本页把“第一落点”“应用层回执”“备份水位”三者分开，是项目的设计选择。以备份水位作为删除前提，与数据库复制中“确认已持久复制后才清理日志”的思路相同。
