# 0206 不用行级安全；共享引擎只有一个，在 authz

**状态**：为 3.0.0 原地重写（共享移进 authz，由 SDK 投影）；已决定，随 3.0.0 统一升级落地。

## 决策

数据范围条件以 SDK 规范谓词的形式写进每条查询的 SQL，并以参数传入。不使用 PostgreSQL 行级安全。共享引擎只有一个：授权 provider 把共享和关系存为元组，SDK 把其中的直接元组投影进每个声明了资源的组件的 `besdk_authz_acl`。组件从不自己写共享表。`org` 维匹配物化路径 `dept_path`（`dept` 档精确匹配，`subtree` 档按前缀）；任何组件都不保留组织树副本。另一个组件里某条记录的子记录，经其父记录的 `_authz/check` 检查，一次一个父记录。

## 理由

静态参数化 SQL 能表达项目里的每一个维度，规则也留在评审者会读的那一个地方。RLS 给规则添了第二个家，外加一个无声的陷阱：表的属主默认绕过 RLS，策略可能存在却什么都不过滤。共享是真实需求，但一个引擎、一份契约、一套套件，比每个组件各手写一张共享表安全；投影让列表查询仍然留在本地。没有部门的人不往谓词里贡献任何部门条目，所以空路径什么都匹配不上（默认拒绝）。

## 挡下什么

- "给这张表开 RLS"；`CREATE POLICY`
- 在组件里自己写一张"把这条记录共享给用户 X"的表和一套机制
- 组织树的副本，或在副本上做递归查询来求"我的部门及下级"
- 把空的 `dept_path` 当成组织树的根
- 按跨越另一个组件父记录继承来的可见性做列表过滤（"我能看到的所有附件"）：改为逐个检查父记录
- 给不属于任何部门的表（产品分类、计量单位）加 `dept_path` 列

## 何时重新讨论

某个真实的范围无法写成规范谓词（含一跳派生和主体展开），而且没有安装具备 `graph` 能力的 provider（[0209](0209-authz-is-a-slot-family.md)）来回答它时。
