# 0201 不用 Redis，不设缓存服务器

**状态**：为 3.0.0 修订（缓存只在进程内、经 SDK）；已决定，随 3.0.0 统一升级落地。

## 决策

项目不运行 Redis，也不运行任何其他缓存服务器。缓存只存在于一个成员的进程内，经 SDK 的缓存帮手创建，带容量上限、TTL、单飞加载、指标和事件驱动的失效。凡是要在副本之间共享或要在重启后保留的东西，都是组件自己 schema 里的一张表，不是缓存。

## 理由

通常引入 Redis 要解决的问题都已经有了着落：身份是无状态的 JWT，权限是进程内的 bundle（[0202](0202-local-permission-bundle.md)），别的组件拥有的数据以本地快照保存、靠事件刷新，并发控制靠行锁、事务级 advisory 锁或任务租约，幂等键是一张表，限流归边缘。客户在一台资源有限的机器上部署整个系统；每多一个基础服务，就多一样要安装、备份、加固、监控的东西。按成员创建的缓存天然合并安全：外壳的行为和成员单独运行时完全一样。

## 挡下什么

- "加一层缓存" / "在这个查询前面放个 Redis"
- 会话或 refresh token 存在 Redis 里
- 用 Redis 做分布式锁、计数器或序列号
- 用 Redis 缓存权限、bundle 或授权判定，或者在任何地方跨请求缓存 `Can` 的结果：被撤销的共享会一直生效到缓存过期
- 模块里用包级 map 或无上限的缓存，而不是 SDK 的帮手
- 应用代码里基于 Redis 做限流
- 把 Redis 当消息队列（事件走总线，[0106](../01-architecture/0106-infrastructure-is-not-a-component.md)）

## 何时重新讨论

某个经过测量的负载无法由 PostgreSQL 加进程内内存承担，并且把数字写了下来，而且这种情况涉及不止一个组件；或者在多副本部署下，业务判定副本缓存之间的不一致窗口（最多一个 TTL）对某个点名的读取不可接受时。

完整分析：[17-caching.md，选择](../../04-foundations/17-caching.md#选择)。
