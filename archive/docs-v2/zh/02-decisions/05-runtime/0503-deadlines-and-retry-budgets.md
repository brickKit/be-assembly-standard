# 0503 每个请求都有只减不增的截止时间；重试由契约决定、受预算约束

**状态**：已决定，随 3.0.0 统一升级落地。

## 决策

- **每个请求都有截止时间，而且只会缩短**：每一跳给子调用的时间都少于自己剩下的。
- **面向用户的默认值**：普通操作 10 s；声明过的编排（比如确认订单）15 s；导出是异步任务。一次出站调用取 `min(3 s, 剩余 − 50 ms)`，剩余 50 ms 或更少就不发（`DEADLINE_EXCEEDED` / `DEADLINE_BUDGET_EXHAUSTED`）；一条数据库语句取 `min(5 s, 剩余)`。
- **gRPC 方法只有在契约声明它无副作用或幂等（`idempotency_level`）时才重试**，只在 `UNAVAILABLE` 时重试，最多 3 次，经每个 SDK 按契约生成的服务配置执行。
- **每条连接一份重试预算**（gRPC 重试节流，约为正常流量的 10%），依赖大面积不可用时停止重试；连接按成员分开，一个成员的重试风暴花不到另一个成员的预算。
- **用舱壁，不用熔断器**：每个（成员，依赖）最多 64 个并发出站调用，满了立即以 `RESOURCE_EXHAUSTED` / `OUTBOUND_LIMIT` 失败；每个成员一份连接预算（`DB_POOL_EXHAUSTED`）。
- **只有一层重试。** 代码从不在已经会重试的调用外面再套一层重试循环；更高一层的重试（reconciler、重投的事件）沿用同一个幂等键。

## 理由

单机、每个组件一个实例时，熔断器没有可以绕开的实例；保护用户的，是有界的等待（截止时间）和有界的损害（舱壁）。加副本之后，预算和连接轮换依然行为正确。由契约决定能否重试，就没人需要逐个调用判断重试是否安全，嵌套重试也不会出现，而嵌套重试会成倍放大（三层各三次，故障时底层收到 27 次调用）。3.0.0 之前任何地方都没设超时，一个挂住的依赖就能拖住登录和整条移动端链路。

## 挡下什么

- 没有截止时间的调用、语句、handler 或任务；给子调用的时间比调用方剩下的还多
- 重试非幂等方法，或在 `UNAVAILABLE` 以外的码上重试
- 组件在运行时调用外面自己套重试循环；对冲请求（hedging）
- 组件里引入熔断器库；舱壁满了把调用排队

## 何时重新讨论

多个节点出现局部故障（部分副本慢、其余正常）：加拦截器级熔断或异常实例剔除，配合 headless 负载均衡。或者固定的出站上限经测量与某个依赖不匹配：把那个依赖的上限改成自适应。
