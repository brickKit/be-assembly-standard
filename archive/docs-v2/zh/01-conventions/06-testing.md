# 测试约定

本项目有哪些测试、各测什么不测什么、什么时候写、怎么跑。目标只有一个：AI 写的测试要真的能抓住回归，而不是看起来很多、实际什么都没守住。达不到这个目标的测试比没有还糟，因为它让人以为"这里有覆盖"。测试数据从哪来见 [05-data.md](05-data.md)。

## 分层一览

| 层 | 名称 | 测什么 | 何时写 |
|---|---|---|---|
| **L1** | 契约 | 契约没有破坏性变更；每个 rpc 都真能跨进程调用 | 契约写好时 |
| **L2** | 业务规则 | 规格：不变式、合法状态转移、幂等、边界处的业务结论 | 实现之前 |
| **L3** | 单元 | 这份实现的分支：错误路径、空值、并发、SQL 拼装 | 实现之后 |
| **L4** | 集成 | 真实 PostgreSQL、NATS、gRPC；迁移可重跑；调用真实依赖 | 实现完成后 |
| **FE-1** | 前端单元 | 纯函数、composable、store；网络 mock 掉 | 代码一写好就加 |
| **FE-2** | 前端组件 | 被多个页面复用的共享组件 | 代码一写好就加 |
| **FE-3** | 端到端 | 真实浏览器加真实后端，跑通一条完整业务流程 | 页面交互稳定之后 |
| **FE-4** | 视觉回归 | 各页面间距、密度、组件用法一致 | 与 FE-3 同批 |

横切类，同样必须有：数据范围边界测试（每个声明了 `data_scopes` 维度的组件）、事件契约兼容（`make gates` 检查）、SDK 原语的并发正确性（在 `be-sdk-*` 里）、跨组件测试（每个有必需依赖的组件）。

贯穿全部的四条原则：

1. **规格先于实现。** L2 写的是这个功能应该做什么，不是代码做了什么。
2. **真实优于模拟。** mock 最多证明"调用发生了"，证明不了"结果是对的"。
3. **能机械化的判据一律机械化。** 靠人记得去查的规则，能写成门禁或脚本就写成门禁或脚本。
4. **每层只测自己那部分。** 同一个断言写在两层，就多一处要同步的地方，而它不会被同步。

## 红绿节奏与铁律

一轮：

1. 写一个失败的测试（或一小组紧密相关的）。
2. 跑一下，确认它是红的，**而且红的原因是功能还没实现**，不是编译错误、mock 配错或测试本身有 bug。
3. 写最少的代码让它变绿。
4. 跑全量，确认别的没变红。
5. 有必要就重构，然后再跑一遍全量。
6. 提交，写清这一轮锁定了哪条业务结论。

**绝不为了让测试通过而改测试。**

| 情况 | 怎么做 |
|---|---|
| 红是因为实现错了 | 改实现。这是默认情况，没有例外。 |
| 红是因为测试断言了一个错误的业务结论 | 先停下，一句话说清原断言错在哪里、为什么错，单独一个提交改它。 |
| 一个 L2 测试挡路 | 几乎总是实现或对需求的理解错了。先改设计，再改测试，绝不反过来。 |

绝不注释掉测试，绝不加 `t.Skip` 或同类跳过标记，绝不放宽断言直到它碰巧通过。这三种都把门禁变成装饰，一旦有一个门禁是装饰，别的绿也就没人敢信了。

## 卡住时

同一轮三次还没绿：按顺序走这三条。

| # | 出路 | 怎么做 |
|---|---|---|
| 1 | **把这一步切小** | 这一步通常在同时解决两三件事。拆开测试，一次只让一个小断言变绿。 |
| 2 | **去看参考实现** | 看完回来想清楚，再写自己的（[10-reference-implementations.md](10-reference-implementations.md)）。绝不照抄。 |
| 3 | **停下来说清卡在哪** | 期望什么、实际发生了什么、试过什么、怀疑是哪一层。交给人判断。 |

第三条是正确动作，不是失败。绕过去一次，下次有人照抄，抄两次这条规则就没了。

## L1 契约测试

契约没有破坏性变更（`make contract-check`），每个 rpc 都真的跨进程调用一次：真起一个服务端、真用客户端打一次。L1 不管结果对不对，只管接口存在、可达、字段没被破坏。

## L2 业务规则测试

L2 测不变式（"库存永不为负"、"可用 + 预留 = 总数"）、合法状态转移（"已完结的预留不能再取消"）、幂等（同一个 `idempotency_key` 来 N 次，结果等于一次）和边界处的业务结论（数量为零、金额为零、空列表）。

**判断一个测试属于哪一层：把这个功能的实现整个删掉、用另一种语言重写，这个测试还应该成立吗？** 应该 → L2。不应该，因为它测的是这份实现的某个细节 → L3。

- **核心交易组件**（库存、资金、薪资、提成：出一次错就是一次业务事故的地方）的 L2 用**性质测试**：人定义不变式，框架生成大量随机输入去攻击实现（Go 用 `rapid` / `gopter`，Python 用 `hypothesis`）。只靠举例的测试永远找不到"特定操作序列才触发"的 bug。
- **幂等测试要包含并发。** 多个 goroutine 或协程在同一时刻用同一个 key 调用，只有一个真正执行。只测串行重放，抓不住"先查再插"。
- **数据范围测试要证明别人的数据看不见**，不只是自己的看得见。建两条归属不同身份（owner、org、仓库、法人）的数据，用其中一个身份查，断言另一个身份的数据一条都不返回。"有权限的人看得到数据"和"没权限的人什么都看不到"这两个测试，在返回整张表的代码上都能通过。

## L3 单元测试

L3 测这份实现的分支：错误路径、空指针和空字符串、并发写冲突、SQL 拼装、每一个参数校验分支。不重复 L2 已经覆盖的结论。实现之后写，或者跟着实现一起写：写下一个 `if err != nil` 分支时就配上它的测试。

## L4 集成测试

- 在真实 PostgreSQL、NATS、gRPC 上端到端跑。`/healthz` 只报告进程本身。每个迁移连跑两次都要成功。
- **有 down 迁移的组件，至少在真实数据库上跑过一次 `migrate down` 再 `up`**；任何 `make db-reset` 在交付之前也要真跑过。down 脚本按逆序执行，删除了早先的表仍在引用的基准数据的 down 脚本，只有真执行时才会失败；审查看不出来。
- **自己发布事件来触发消费者的测试，用私有 subject**（`test.<base>.<纳秒时间戳>`）：订阅了生产 subject 的真实容器会收到同一条消息，断言可能读到的是它的结果。验证代码"发到了哪个 subject"的测试，用真实 subject。
- **消费者测试用唯一的 `aggregate_id`。** 按 `(subject, aggregate_id, version)` 去重是永久的；用固定 ID，第二次跑会被当成已处理吞掉。
- **绝不用 mock 证明跨组件调用"发生了"。** 参数传错、返回的错误没处理，它都照样绿。组件之间发生的事是 L4 的职责，要真起两个进程。
- 数据每次新建、带唯一后缀、从不清理；不用共享的固定数据集，不用内嵌或一次性数据库（[05-data.md](05-data.md#两条路径互不共享)）。

## 跨组件测试

跨组件测试让这个组件真的调用它的必需依赖。`make test-cross ID=<scope>/<name>` 只跑这个组件的测试，把每个依赖的地址从真实的依赖容器桥接到宿主机上；测试进程留在宿主机，构建缓存和竞态检测照常可用。

- 只需要这个组件和它的依赖树在跑：先 `brickkit up --focus <id>`。它会打开本地模式，`brickkit up --all` 也不会关掉，所以之后改 `deploy.yaml` 要等 `brickkit local off` 或 `brickkit local refresh` 之后才生效（[01-development-workflow.md](01-development-workflow.md#真机运行)）。
- 按名字过滤，可以只跑某两个组件之间的测试；这就是跨组件测试要以对方组件命名的原因（见下面的命名一节）。
- 范围是同步调用方向。别的组件消费这个组件发出的事件，走的是事件总线，按上面的消费者规则处理。
- 测试需要依赖方有的数据，在测试里通过依赖方的真实 API 建（[05-data.md](05-data.md#依赖方缺数据或能力时)）。

## 门禁与横切检查

- **认证**（"没 token 拒绝"、"token 没这个权限拒绝"）在 SDK 里测一次。门禁检查每个对外路由都经过它（没有裸路由）；每个组件只测自己的数据范围过滤。
- **事件契约**只增；`make gates` 把每个组件的事件文件和它的历史版本比对。
- **会被多个实例同时使用的 SDK 原语**（outbox 泵、幂等认领、连接池）至少有一个多实例并发的测试，检查每一项恰好处理一次。L1–L4 都假设只有一个进程，找不到这类 bug。
- **新门禁先证明一次自己会红**：在真实代码所在的位置（包括嵌套目录）放一个故意的违规，看它报出来，之后它的绿才可信。从没见过违规的门禁，可能一直在扫一个空目录。
- 门禁失败时先读它的输出；它会点名违反了哪条规则、哪个文件。

## 前端测试

思路与后端相同，工具不同：规格与实现分开，共享的优先于一次性的，真实环境优先于模拟。

- **FE-1** 测给定输入下逻辑算得对不对：纯函数、composable、store，网络请求 mock 掉。
- **FE-2** 测共享组件（表格、页面模板、通用卡片）。共享组件坏了，引用它的每个页面一起坏，所以它们优先于某个页面自己的组件。
- **FE-3** 用真实浏览器对着真实后端走完一条业务流程。PC 和移动端共用工具，用不同的设备配置区分。页面交互稳定之后再写；在那之前每次改 UI 都要重写它的选择器。每个测试以它验证的业务流程命名。
- **FE-4** 是 FE-3 里的一种断言方式：流程经过关键页面时顺手截图比对，自动做像素差异。基线随有意的 UI 变更更新；只有比对失败时才需要有人看图。
- **跑 FE-3 或 FE-4 之前先问用户。** 说清这次覆盖哪些流程和页面，等用户点头。成本在编写和调试（为了找选择器、查失败原因反复截图），不在跑一套已经稳定的测试。确认页面元素优先用无障碍树快照而不是截图，失败时先看文本报错和 trace 再截图，能让人录关键路径就让人录。
- **契约漂移靠生成消除，不靠测试**：前端类型和请求函数从契约生成，类型检查器在编译期就抓住漂移。

## 运行测试

| 粒度 | 何时 | 后端 | 前端 |
|---|---|---|---|
| **全量** | 部署之前、一批发布之前 | `make gates`、`make lint`、每个组件的 `make test`，`brickkit up` 之后 `make tier0` | 在根目录跑所有包的测试 |
| **一个组件** | 一个组件或一个功能做完 | `make test`；跨组件测试用 `make test-cross ID=<scope>/<name>` | 单个包 |
| **组件的一部分** | 迭代一个功能时 | `go test -run <名字>`、`pytest -k <名字>` | `vitest <模式>`、watch 模式 |

每个组件都有这些命令，而且真的能跑：

| 命令 | 做什么 |
|---|---|
| `make test` | 全部 L2、L3 测试，开竞态检测 |
| `make migrate-idempotent` | 每个迁移连跑两次 |
| `make contract-check` | 契约的破坏性变更检查 |
| `make module-check` | [02-backend.md](02-backend.md#合并安全) 的合并安全规则 |
| `make smoke` | 在项目根目录跑 `brickkit up --dry-run`：包含本组件的依赖图能解析、文件能生成，不启动任何东西 |
| `make seed`、`make seed-clean` 或 `make db-reset` | 演示数据及其撤销（[05-data.md](05-data.md#种子数据规则)） |

L4 和消费者测试指向测试库：`TEST_PG_DSN` → `brickkit_test_db`，由 `make test-db-init` 建立和刷新；绝不指向演示库 `brickkit_db`。

## 命名

| 规则 | 适用于 | 为什么 |
|---|---|---|
| 名字直接写业务结论或分支，不编号 | L2、L3 | 不打开文件就知道测什么 |
| 性质测试名字里带 `Property` | L2 性质测试 | 告诉读者这个断言背后是随机输入攻击 |
| 跨组件测试的名字写出对方组件 | 跨组件测试 | 按名字过滤就能只跑两个组件之间的测试 |
| 端到端测试以业务流程命名，不以按钮命名 | FE-3、FE-4 | 按流程过滤 |

这些规则只管新写的测试；已有的测试顺手碰到时再改名。

## 测试里人要审什么

只审 L2 测试里的不变式清单是否完整：这段逻辑该有的不变式是否都写下来了。门禁只跑已经写下的测试；没人想到的不变式，门禁再绿也从没被检查过。业务代码逐行、L3 测试、构建脚本都交给门禁。
