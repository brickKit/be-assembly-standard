# Registries

The project-wide tables a component copies from before writing its `component.yaml` and its component definition. A port, a schema, a role or a permission key is never invented: it comes from here, or a new row is appended here first. The full rules are in [protocol 19's registries](../docs/zh/06-protocols/19-config-secrets-registries-release.md#注册表) (Chinese only until development is done, D67); this page only says what each file is.

## Files

| File | Holds | Rule |
|---|---|---|
| `ports.tsv` | every component's HTTP and gRPC port, every shell's own port, every out-of-band container's host port | append-only |
| `schemas.tsv` | every component's PostgreSQL schema and login role | append-only |
| `permissions.tsv` | every permission key: `key`, `title`, `type`, `owner_component`, `deprecated` | append-only; merged in by `be-ops permissions` |
| `data-scopes.tsv` | every data-scope dimension: `component`, `dimension`, `column`, `mode`, `tables` | derived; regenerate at will |

## Current state

- `ports.tsv` and `schemas.tsv` are current: a new component's ports and schema are appended here first, as always.
- `permissions.tsv` and `data-scopes.tsv` still belong to the 2.x assembly (generated by the old `be-ops`). For components rebuilt to the new design, the resources, operations, permission keys and data-scope dimensions are written in the component definition ([security 09a](../docs/zh/06-protocols/security/09a-encoding-and-records.md)), which is the source of truth; the two files will be summarised from the component definitions once `be-ops` is rewritten, and until then nothing is appended to them and no new component is written from them.

## Rules

- **Append-only** (`ports.tsv`, `schemas.tsv`, `permissions.tsv`): a moved port breaks every dependent and every shell that hosts the component; a renamed schema is a data migration; a renamed permission key silently strips it from every role that had it. A key is retired by filling `deprecated`, and its name is never reused.
- **`_infra-` rows** are out-of-band containers (PostgreSQL, NATS, Traefik, Casdoor, object storage, observability), not components. They share the host port space with the components, so they are registered too; mutually exclusive pairs (RustFS / MinIO, Traefik / Nginx) may share a port.
- **`_shell-` rows** are the shells' own ports, the `/healthz` in each shell's `component.yaml` (`deployment.port`). Shell IDs are `be/<name>`. A member hosted by a shell keeps its own service name and its own ports.
- Ports are allocated by group (the section comments in `ports.tsv`); the `1xxxx` range is BrickKit's (10000 + container port, mapped for processes on this machine), out-of-band host ports use `2xxxx`. The shell column is a deployment choice, settled after the experiment (D40).
- A retired component keeps its row with `retired <date>: <reason>` in the note; its name, ports and schema are never handed out again. `schemas.tsv`'s `role` is the runtime role; the owner role is always `<schema>_owner` (protocol 14).
- After any change, `make registry-check`.
