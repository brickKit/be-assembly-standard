# 外壳（Shell）

外壳是**我们自己造的、平台完全不知道的东西**（brickKit 明确不做，`012` §2.21）。
它可以做的事只有一件：**把 N 个进程变成 1 个进程**。

- `go/`     → be-shell-go     （外壳一/二/三，Go）
- `python/` → be-shell-python （外壳四/五，Python）

⚠️ **一个仓库/一份镜像，可以真机部署成多个外壳实例——不是一个外壳一个仓库。** `be-shell-go`
的代码本身跟"装的是外壳一还是外壳三"无关，`internal/shell.Run(cfg)` 只认调用方给它的
`Modules` 子集；真机部署外壳一/二/三三个容器实例，用的是同一个 `be-shell-go` 镜像，只是
每个实例启动时读到的模块清单不同（`be-ops` 产出 4，见阶段四计划 Task 4）。**以后新增外壳
（阶段五/六铺满军火库、真的需要外壳四"Python 复杂大脑"时），默认先假设不需要新仓库**——除非
真的出现"这个外壳需要一套跟现有 `be-shell-go`/`be-shell-python` 完全不同的启动器逻辑"这种
情况（目前没有先例）。

外壳**不放在 `components/` 里**——它不是 brickKit 组件，不进 `brickkit.yaml`。

⚠️⚠️ **外壳态与 brickKit 自己的独立容器互斥，同一时刻只能有一个在跑（对着真实基础设施时）。**
两者是同一件事的两种运行形态，不是可以叠加的两层——同时开着会撞端口（`local: true` 的
`localPort` 直接复用组件自己注册的端口）、撞 NATS（广播语义让两边都收到同一条消息各处理
一遍）、撞 `brickkit_db` 状态。**操作纪律：切到外壳态之前先 `brickkit down` 停掉全部组装态
容器（不是只停将被合并的那几个，图简单直接全部停）；切回全拆态之前先把全部外壳容器停掉。**
完整推理见《BrickEnterprise 设计书.md》§13.9。这条不管本地用 `TEST_PG_DSN`/临时端口跑的外壳
单元测试（阶段四 Task 5 验证真实模块合并用的就是这条路径）——只管"两边都对着真实资源跑"
的那一刻。

⚠️ 每个外壳仓库在**阶段四**建起来时，各带一份 `AGENTS.md` + `CLAUDE.md`（总纲 §4 SOP-D）——
外壳的禁令比组件更容易被 AI 违反，因为「同进程直接调函数」在外壳里看起来完全合理。

外壳不许做的事（§1.5 原则二 / §13.3 铁律六）：
- ❌ 不许让两个组件模块直接互相 import
- ❌ 不许把两个组件的表放进同一个 schema、不许跨 schema JOIN
- ❌ 不许把 N 个模块的 API 合并成一个端口
- ❌ 不许在外壳里写任何业务逻辑
