# 版本升级与发布

## 什么时候用这个技能

- 已经做完一批组件的真实代码/测试/文档改动，该发布了
- 用户说"发布""ship it""跑一下版本号流程"
- 接着上次没收尾完的发布工作继续（比如上次做完 `--apply` 但还没逐个组件走完 §3）

## 前提

这个技能假设"这次真的动了什么、值得发布"这件事已经清楚——通常就是你自己刚写完的工作，直接知道。如果不确定（接手别人开了一半的活、或者隔了很久回来继续），先跑 §0 找出来，不要凭记忆。

## §0（可选）：不确定动过哪些组件时，先找出来

```bash
bash infra/scripts/list-unshipped-components.sh
```

列出每个"HEAD 已经领先自己最新 tag"的组件仓库，连同这段时间的 commit 摘要。

⚠️ 列出来的不代表都该现在一起发——可能混着这次任务范围之外、别的工作留下的半成品提交，逐条核对是不是真的该发，不能全盘照单发布。

## §1：写计划文件

为每个真正要发布的**根**组件（不用手写被它连累的下游组件——那一步下面自动算）写一段理由，存到 scratchpad（一次性输入，不提交进仓库）：

```
id: <scope>/<name>
reason: <一段话，中文，跟这个项目 changelog 一贯的语气一致——具体到测试名/pitfall
  编号，结尾用"无行为/契约变更。"或者明确指出有什么变更>
---
id: <另一个根组件>
reason: ...
```

理由文字要认真写——它会原样写进这个组件永久的版本历史（`component.yaml` 的变更记录、`brickkit.yaml` pin 旁边的注释），不是一句随手话。

## §2：先 dry-run 核对级联，再 apply

```bash
make bump-version PLAN=<计划文件>
```

看打印出来的级联结果，重点核对两件事：

- **有没有被拉进来的组件让你意外？** 有的话先停下来搞清楚为什么——通常意味着某个组件的 `dependencies.components` 声明了一条不该有的边，这本身可能是比"赶紧发布"更值得处理的问题，不要糊过去。
- **波及范围是不是明显过大**（比如一次改动却拉进了小一半的组件）？这也是该停下来想一想的信号，不是"工具算出来的，照做就行"。

确认没问题后：

```bash
make bump-version PLAN=<计划文件> APPLY=1
```

这一步会给每个组件打印"接下来"该做的具体命令——照着走，不用重新想。

## §3：逐个组件收尾（按打印出来的顺序）

对每一个：

1. **加上这次真正改的代码/测试文件**——`bump-version` 只改了 `component.yaml` 这类元数据，真正的业务改动是你自己之前写的，工具不知道那些文件是哪些。
2. **跑这个组件自己的测试，必须全绿**（Go：`go test ./backend/... -race -count=1`；Python/TS 用各自命令）。红了就停下来诊断根因，不要因为"只是要发个版本"就绕过。
3. 契约变了的话跑 `make contract-check`。
4. **写 commit message 到 scratchpad 的一个文件里，不要用内联 `-m` 夹带长文本或双引号**——`git commit -m` 遇到长文本/引号可能静默失败，之后的 `git tag` 会打在错误的旧提交上，这是真实吃过的亏。结构：一句话概括这次改了什么，空一行，理由（直接搬 §1 写好的那段，不用重写），空一行，`Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`。
5. `git commit -F <消息文件>`，**看一眼 `git log` 确认 commit 真的落在了预期内容上**再打 tag。
6. `git tag -a v<新版本> -m "<一句话>"`（工具已经在"接下来"那段里把这行拼好了，直接抄）。
7. `make image`，确认构建成功（看到"镜像里有 sh + wget"或对应语言的确认字样）——构建失败就停下，不带着一个没验证过的镜像继续走。
8. `git push origin main && git push origin v<新版本>`。

## §4：装配仓库收尾

全部组件做完后：

1. `make gates`、`make version-check`——两个都要绿。
2. **真机验证**：`brickkit up`，确认全部组件 `running (healthy)`；挑一两个跟这次改动直接相关的端点真的 curl 一下（用状态码能确认路由/鉴权链路是否正常，不是随便挑一个）；`brickkit down`（不常年挂着，见根 `AGENTS.md`）。
3. 提交装配仓库自己的改动（`brickkit.yaml`、两份 `AGENTS.md`、真机验证时重新生成的 `.brickkit/manifests`/`.brickkit/artifacts`），写一句概括性的 commit message，`git commit`，`git push`。

## 什么时候要停下来问人，不能自己一路推到底

- 任何一步测试/gate 红了，且原因不是"级联同步造成的纯字符串替换失败"这种预期之内的情况——出现任何逻辑性失败都要停。
- `bump-version` 打印的级联看起来不对劲（§2 已经说过）。
- **这批改动里其实混进了真实的行为/契约变更，不是纯粹"跳版本号"级别的事**——这种情况下的审查深度、commit 粒度该走正常开发流程的标准（SOP-W 红绿循环、W-6 人工评审五件套），不能套用这个技能"批量发布"的节奏。这个技能的前提是"代码本身已经写完、测过、review 过，剩下的只是发布动作"，不是拿它来掩盖一次真实改动该有的审查。
- 任何需要 `--force` 的操作。
- §0 找出来的候选里，有哪一条你不确定是不是这次任务范围内该发布的。

## 为什么这个技能管到 commit/push，而不是止步于"改文件"

`bump-version` 工具本身刻意不做 git 操作（见 `docs/standards/00-master-guide.md` SOP-W-11）——理由是"批量改文件"和"批量推到远端"是两类不同风险等级的操作，不该被同一次程序调用捆在一起、跳过复核。这个技能把两者重新接在一起，但接的方式不是"再造一个自动 git 的程序"，而是把**判断力**留在执行者身上：每个 commit message 的措辞、每次"这个级联合不合理""这批改动够不够纯粹到可以走批量发布节奏"，都是逐次判断出来的，不是一份写死的脚本替你判断。这正是这个技能存在的意义——把"步骤该怎么走"记下来，省得每次重新推导，但不代替"这一步该不该继续"本身需要的判断。
