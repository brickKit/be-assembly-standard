# BrickEnterprise · AI Assistant Guide

> This page is an **index and a set of prohibitions**, not a tutorial. It loads on every session, so it stays deliberately thin.
> Detail lives wherever it points to — **every pointer carries a section number, never guess.**
>
> Written for AI assistants; humans can read it too. **The human entry point is [`docs/README.md`](docs/README.md)** — it triages by reader (deployer / developer / architect / customer). Don't let a human land on this page directly.

> ⚠️ **Document language ≠ conversation language.** This repository's regulatory documents are English-primary (see [`01-documentation-standard.md`](docs/standards/01-documentation-standard.md) §6) purely so an AI reads them efficiently. That says nothing about how to talk to the human maintainer of this specific project: **they communicate in Chinese only, and every reply to them — in this project, regardless of what language the file being discussed is written in — must be in Chinese.** Do not let this file's own language pull you toward answering in English.
>
> **This slip has actually happened more than once, and the "double-check before sending" mitigation has itself proven unreliable**: even with this instruction loaded as part of the current session's own system-level context, immediately preceding the user's message, a reply has still come out entirely in English right after a long stretch of English-heavy tool output (translating a document, renaming files, running greps over English content, running a link-verification script) — more than one time. That means the failure isn't "forgetting the rule"; it's that "check the language after writing" is the same failure point as "which language the text got generated in" in the first place — you cannot reliably insert a self-check inside that same process. **The only thing that can actually work is treating Chinese as the default locked in before writing a single word, not as something verified afterward**: the very first character of any user-facing reply should already be anchored to Chinese, regardless of what language the immediately preceding tool calls or file content used. "The current task happens to be in English" must never become the default anchor for reply language.

**What this is**: an enterprise-grade, component-based ERP/CRM arsenal built on the brickKit platform. 62 components, 5 shells, one assembly-on-demand methodology. This repository (`be-assembly-standard`) is both the standard assembly template and the **arsenal index** — each component under `components/` is a git submodule.

## The one thing you must read first

**§1.5, the two non-negotiable development principles.** Everything else in this book can change; these two cannot:

1. **Every component is developed as a pure brickKit component and runs standalone.** Not one gRPC call is skipped; every port declared under `extraPorts` must actually `Listen`; it must be possible to `brickkit up` this one component alone (together with its strong-dependency tree).
   **"We're merging it into a shell eventually anyway, so why not just call the function directly in the same process" — think that once, and the K8s full-teardown goal becomes permanently unreachable.** gRPC is the physical carrier of a logical boundary; skipping it means the boundary disappears the moment things merge.
2. **Merging only ever happens at the deployment layer.** The only thing a shell is allowed to do is turn N processes into 1.

## The 23 Easiest Mistakes (each with its symptom)

The first six, plus items 11, 12, 15, 16, 17, 19, 21, 23, share one thing in common: **the code looks completely correct and the tests pass**, and the symptom is either extremely hard to connect back to the cause, or there is no symptom at all.

19–23 come from the permission system (Design Book Chapter 14). **Item 21 is the project's third path to "silently reading someone else's data"** — the first two are item 2 (`SET` without `LOCAL`) and item 16 (`os.Getenv` inside a module).

11–15 (including 13b) were **verified against brickKit's actual source code**; 11, 12, and 13 directly overturn what an older version of the Design Book said.

**Items 16, 17, and 18 only go wrong after merging into a shell** — running that one component standalone is 100% correct, tests are all green, `make smoke` passes too. They are guarded by `make module-check` (gate 9).

| # | Never | Symptom | Source |
|---|---|---|---|
| 1 | `grpc.Dial(os.Getenv("X_GRPC_ENDPOINT"))` | The value the platform injects **always starts with `http://`**, never `grpc://`. The connection fails, and **the error points at name resolution**, making it extremely hard to trace back to this. Must `TrimPrefix("http://")` | §2.1 |
| 2 | `SET ROLE` / `SET search_path` without `LOCAL` | Once the connection returns to the shared pool, **the next borrower inherits it as-is** — component A's query lands on component B's table, **no error, no crash, just silently reading and writing someone else's data**. The hardest one in the whole project to trace | Decision 3, §13.3 Iron Rule 2 |
| 3 | Components `import`ing each other | **No symptom at all** — the system even runs faster, until the day you try to tear it apart onto K8s and find you can't; the cost is a rewrite. Also never extract a "shared model package" | §13.3 Iron Rule 6, Decision 91 |
| 4 | `os.environ["X_ENDPOINT"]` / treating an empty result from `os.Getenv` as "missing" | When a weak dependency is absent, that variable **doesn't exist at all** (not an empty string) — an index access crashes at startup. This is a deliberate platform design | §3.6 |
| 5 | Writing `asset` / `assembly_role` / `slot_name` / `edge_routes` / `menus` / `domain` / `tier` / `shell` into `component.yaml` | An unknown key **errors immediately**, it is not silently ignored. All of these belong in the sibling `assembly.yaml` | §3.5, Decision 84 |
| 6 | Naming a config item `otelEndpoint` / `databaseSchema` | Hits the platform's reserved suffix `*_ENDPOINT` / prefix `DATABASE_`, and gets **skipped with only a warning** — the component never gets the value, while `up` goes fully green. Must be named `otelBaseUrl` / `pgSchema` instead | §2.7.3 |
| 7 | Checking a database, a dependency component, or NATS inside `/healthz` | One downstream hiccup marks every upstream unhealthy and restarts them; in a merged deployment **one module dragging down the probe restarts the entire group of 22 components** | §12.3.6 |
| 8 | A `FROM scratch` / `distroless` base image | The platform's health check is `CMD-SHELL`, and without a shell it fails forever. The symptom: **the component's own logs say "ready," while the platform says it's unhealthy**. The base image must ship `/bin/sh` + `wget` | §12.3.7 |
| 9 | Writing Docker labels / K8s annotation values as `true` / `8080` | Both sides only accept strings; the platform **does no automatic conversion**, and `traefik.enable: true` gets rejected on the spot. Always quote them | §5.10, Generator Iron Rule 1 |
| 10 | Writing `enabled: false` for a component the customer hasn't purchased | Everything below it in the dependency chain **cascades into not starting** — turning off HRM quietly turns off MDM too. The correct way to express "not purchased" is to **omit the whole entry from `brickkit.yaml`** | Decision 98, §9.5 |
| 11 | Assuming "swapping a base-resource implementation only means changing one field in `brickkit.yaml`" | `engine` **matches literally, character for character**: a component that says `nats` against a project that says `kafka` blocks `up` outright. Swapping the event bus means changing ~50 `component.yaml` files **plus** swapping the SDK driver (different client libraries). Object storage is the true zero-change case — **`engine` names the capability, `s3`** (default implementation RustFS, swapping to MinIO/S3/OSS is a genuine zero-change swap). The rule: **name the capability when the protocol is compatible, name the product when it isn't** (the latter makes the platform actively block a swap, because that swap really is a migration) | Design Book §2.7.3.1, Decision 105 |
| 12 | Also `TrimPrefix("http://")`-ing `STORAGE_ENDPOINT` | It is **the one variable whose name ends in `ENDPOINT` but whose value is a bare `host:port`** (component addresses are built with `http://`, but the storage resource uses bare `host:port`). Stripping it strips nothing useful, then hands a bare `host:port` to an S3 SDK that wants a URL. The base library needs **two functions running in opposite directions** for these two cases | Design Book §2.1, Decision 105 |
| 13 | Attaching Traefik routing `labels` to a platform-generated container | **The compose the platform generates builds its own non-external bridge network, and there is no field in `brickkit.yaml` that can change that.** Traefik's Docker provider can only see containers on the same network, so it **reads none of those labels at all**. Symptom: **the labels are written correctly, `docker inspect` shows them, and yet the gateway 404s while every container is healthy**. The correct approach is `expose: true` + `exposePort` + Traefik's **file provider** | Design Book §6.3.1, Decision 107 |
| 13b | Writing `app` / `brickkit.io/*` / `com.docker.compose.*` into `labels` | These three groups belong to the platform; **writing them errors immediately** (not silently dropped). `prometheus.io/*` and `traefik.http.*` are the safe ones we're allowed to produce | Design Book §5.10 |
| 14 | Allocating a `1xxxx`-range port to an out-of-band container | The entire `1xxxx` range belongs to the platform: for host-mapping a `local: true` component it prefers `10000 + container port`, falling back to an increment starting at `18080`. Out-of-band containers always use the `2xxxx` range | Master Guide §1.2, Decision 106 |
| 15 | Copying some open-source ERP's module structure directly | **No immediate symptom**, but it brings along that project's own chronic problems — most typically "every module shares one process and one database, tables can be joined across modules," which is exactly the reason this project exists (Design Book §1.1). They share one process and one database; we run independent processes with independent schemas — **the structure cannot be the same** | Master Guide §4 SOP-R |

| 16 | Reading config with `os.Getenv` / `os.environ` inside module code | One process has exactly one `environ`: after merging, 22 modules' `PG_SCHEMA` and **every entry in every `configSchema`** overwrite each other — **no error**, a module builds tables and reads/writes data against someone else's schema. This is the second path to "silently reading and writing someone else's data" (the first is item 2). Dependency addresses go through `besdk.Endpoint()`; every other config value goes **entirely through `rt.Config`** | Design Book §12.5.3, Decision 110 |
| 17 | A module calling its own `otel.SetTracerProvider` / `logging.basicConfig` / installing signal handlers / using the **default** Prometheus registry / calling **`gin.SetMode()`** (it is a **package-level variable**, not an engine field — one module setting debug mode puts all 22 other modules into debug mode too, leaking panic stack traces to the client) | For the first two, **whichever `init` runs last wins** — all 22 modules' traces end up under one `service.name`, one module's log format silently overrides everyone else's, and **everything stays green**; the third leaves `docker stop` unable to shut down cleanly; the fourth **crashes outright** (a Go `MustRegister` panic / Python's `Duplicated timeseries`), while running standalone it works 100% of the time. Pull all of these from `rt` instead | Design Book §12.5.2, Decision 110 |
| 18 | A module calling `log.Fatal` / `os.Exit` / `sys.exit`; or calling its own `gin.New()` / `sql.Open()` / `Listen` | One module hitting a **recoverable** error at startup takes down **the entire group of 22 components**. Calling its own `gin.New()` also skips the SDK's whole middleware chain — no error, the component just permanently loses tracing and RED metrics. Always return an error instead; use `besdk.NewGinEngine(rt)` for the engine, `rt.DB` for the pool, and let the caller `Listen` on the port | Design Book §12.5, §13.3 Iron Rule 7, Decision 109 |
| 19 | Changing an **already-published** key name in `registry/permissions.tsv` | Every role already granted that permission **silently loses it on the spot**, with no error. The symptom is "some users suddenly can't click a button anymore, right after a customer upgrade." Deprecation goes through a `deprecated` tombstone column; **key names are never recycled** | Design Book §14.1.2 |
| 20 | The frontend checking only `features`, not `permissions` | **The menu item is visible, and clicking it lands on a full-page 403.** `features` is **assembly-level** (was this installed in this environment), `permissions` is **user-level** (can this specific person do it) — an older version of the Design Book conflated the two | §14.1.8 |
| 21 | Using `besdk.SystemClient` on a user-request path | **Data-scope authorization is bypassed entirely, with no error — the response just comes back with "a bit more data" in it.** This is the third path to "silently reading someone else's data." `SystemClient` may only appear inside `Start()` and event handlers; `make gates` scans for this | §14.2.6 |
| 22 | Omitting the `data_scopes` section in `assembly.yaml` | `be-ops` rejects it on the spot — **this is deliberate**. "Omitted" does not mean "not needed"; not needing it still requires writing `data_scopes: none` explicitly. A security mechanism's default can only be fail-closed | §14.2.2 |
| 23 | Putting authz's reachability into `/healthz`; or business code using `gin.Engine`'s bare `GET/POST` | The former means one authz hiccup **restarts the entire group of 22 modules**; the latter bypasses the mandatory permission-key signature — **that endpoint is left completely unauthenticated with zero symptoms** | §12.3.6 / §14.1.7 |

⚠️ **The correct approach for item 15 is the three-step method in [`02-reference-implementation-standard.md`](docs/standards/02-reference-implementation-standard.md) §1**: design your own version first, consult a reference only for what you can't work out, then come back and think it through yourself — never copy. That document also covers the licensing note (borrowing logic isn't a derivative work; the line to avoid is copying source verbatim).

Two more, about money and queries: **money fields are always passed as `string`-encoded decimals** (`double` loses precision across languages); **`List` never takes an `offset` field** — deep pagination is simply inexpressible at the contract layer (Decision 53).

## Four Tables That Are Locked: Append-Only, Never Edit

| Table | Why it can't be changed |
|---|---|
| `registry/ports.tsv` | **There is no after-the-fact remedy for gRPC's extra ports**: when the platform rewrites an address it explicitly skips extra ports, and two `local: true` components colliding on the same extra port makes `brickkit up`'s generation step fail hard. This was discovered at component 30, requiring going back and fixing the previous 29 manifests (§3.5.1.1) |
| `registry/schemas.tsv` | Once a database is set up as "one component, one database" and data is in it, switching to one database with multiple schemas becomes a data migration (Decision 3) |
| `registry/permissions.tsv` | A permission key is a **persistent identifier across versions**: renaming an already-published key silently strips it from every role that had been granted it, with no error. `be-ops` output 9 aggregates it from every component's `assembly.yaml`; deprecation goes through a `deprecated` tombstone column, and key names are never recycled (Chapter 14 §14.1.2) |
| `.gitmodules` | This is exactly the "component → repository → exact commit" map the Design Book §3.4.1 calls for — it is the **only** place someone taking over this project six months from now can look up which exact code a given customer's `erp/sales@1.0.0` is |

The one port-reuse exception: the four `slot:frontend` frontend components share port 80 (the slot is mutually exclusive, they never coexist, each runs its own standalone Nginx container outside any shell).

## Repository Layout and Three Operational Prohibitions

```
components/<scope>/<name>/   One git submodule per component (scope/name is the component ID; the repo name is a flat domain-name)
components/.archived/        brickkit sync's archive area (leading dot, hidden by default in file managers)
shells/{go,python}/          Shells — not components, never listed in brickkit.yaml
tools/{be-ops,be-acceptance,be-sdk-go,be-sdk-python,be-sdk-ts}/
registry/                    Port registry + schema registry
docs/standards/               The always-valid regulatory documents, numbered 00-05 by read priority (00-Master Guide first; then, following the actual component-build workflow, documentation/reference-implementation/AI-development/testing/data-construction standards)
docs/plans/                   One execution plan per phase (historical record, not a regulatory document)
docs/design/                 Component design plans, one per component
docs/zh/                     The Chinese mirror of the English originals above (path maps 1:1 to the repo root — see 01-documentation-standard.md §6/§7)
```

| Prohibition | Why |
|---|---|
| **Always `commit & push` before `brickkit remove`** | It **deletes the archived source directory along with everything else**. If a submodule has unpushed changes, this is data loss (§9.4.2) |
| **Run `make arsenal-restore` before committing** | A `brickkit sync` moving a whole directory leaves a "the whole tree moved" diff in this repo. The pre-commit hook catches it, but running this first saves the trouble (Master Guide §3.3) |
| **Not one character of a Forked component's `metadata.id` or `version` may change** | Doing so makes every dependent's `*_ENDPOINT` **disappear entirely** — the variable name the platform injects is derived from the component ID, and the whole Fork mechanism collapses on the spot (§3.4.1) |
| **`brickkit sync`/`remove` blocks rather than auto-moving/deleting a component already registered as a submodule** | v0.2.0 used to do this with plain filesystem operations (`os.Rename`/`os.RemoveAll`), silently corrupting `.gitmodules` with no error (reported and fixed in v0.2.1, see the brickKit repo's `docs/superpowers/specs/2026-09-06-submodule-tracked-components-gap-report.md`). **Now** it raises a `SUBMODULE_GUARD` error and prints the equivalent manual commands (`git mv` / `git submodule deinit` + `git rm`) — do those, then rerun. This is expected behavior, not a bug |

**Can't find the source? Check `components/.archived/` first.**

## Common Commands

```bash
make help                        # List every target
make check                       # One-shot check of base resources (containers/image tags/ports/health/network)
make up                          # Bring up default resources in one shot (a full preflight first; if it fails, nothing is touched)
make <res>-up / <res>-down       # A single optional resource: minio/keycloak/kafka/rabbitmq/nginx/obs
make registry-check              # Port and schema registries are self-consistent
make gates                       # Iron Rule 6 import scan + SystemClient misuse + bare routes + breaking event-contract changes + missing data-scope tests
make bump-version PLAN=<file>    # Propagate a version bump across every file it touches (dependents, brickkit.yaml pin, both AGENTS.md rosters); add APPLY=1 to actually write. See Master Guide SOP-W-11
make docs-check REPO=<repo>      # Structural check of a component's four documents
make test-cross REPO=<repo>      # Run one component's cross-component L4 tests locally (requires its strong-dependency tree to be up)
make test-db-init                # Create/refresh the local test database brickkit_test_db (physically separate from the demo database brickkit_db, see "test vs. demo database" below)
make arsenal-check / -restore    # Whether the arsenal structure and brickkit.yaml are self-consistent
brickkit up --dry-run            # Compute without starting — see what would run, in what order
brickkit down                    # Stop the 14 assembly-time containers (volumes untouched) — see "containers are off by default" below
```

**For any `brickkit` command's flags, ask `brickkit <command> --help`.** Both this page and `.claude/skills/` deliberately don't duplicate the flag reference — duplicating one is a promise to maintain two, and the stale one is what makes you confidently type an `unknown flag`.

⚠️ **The 14 assembly-time component containers should default to off, not run year-round.** The base resources `make up` manages — `be-postgres`/`be-nats`/`be-casdoor` and the like — are long-lived development infrastructure and can stay up indefinitely; but the 14 component containers `brickkit up` brings up are only needed for **real-machine verification/demos**, and should go back down with `brickkit down` (no data deleted) once you're done. Leaving them up has two real costs: ① forgetting to `brickkit up` again after a change means running stale-version containers (this really happened: `infra-notification` sat at `v1.0.0` while the code had long since moved to `v1.0.2`, and nobody noticed); ② a real container on the same machine competes with a local test's temporary NATS subscriber for messages on the same subject, making assertions non-deterministic (pitfalls category E, E1/E2) — with the container not running, this class of problem simply doesn't exist, and there's no need to fall back on a defensive pattern like "tests use a private subject." |

⚠️ **Test and demo databases are physically separate: `TEST_PG_DSN` points at `brickkit_test_db`, not `brickkit_db`.** Two physically separate databases inside the same `be-postgres` instance; `make test-db-init` creates/refreshes the test one. The full reasoning (why they can't share one) is in [`docs/standards/05-data-construction-standard.md`](docs/standards/05-data-construction-standard.md) §1.

## The Platform's Four Iron Rules (brickKit side)

1. **Versions must be exact.** `1.2.0` is fine; `^1.2` / `~1.2` / `1.2.x` / `latest` are never allowed. Range versions were **argued over and rejected**, not simply unimplemented.
2. **Never touch a reserved variable.** `COMPONENT_ID`, `COMPONENT_VERSION`, anything ending in `_ENDPOINT`, and anything starting with `DATABASE_` / `REDIS_` / `MQ_` / `STORAGE_` / `SEARCH_` / `SMTP_` are injected by the platform; a `configSchema` entry with one of these names gets skipped.
3. **The health check has its own prohibitions.** Never put a dependency's availability into your own health check. **The default startup grace period is 60 seconds** (not 30); write `120` for Python, `90` for Node, nothing for Go, `300` for shell images.
4. **Start/stop follows the layer above.** Turning off the top layer cascades everything below it into not starting. The only way to narrow scope is `brickkit.yaml`'s `enabled` field — **there is no `--only`-style flag**.

> Item 3's "60 seconds" corrects an earlier version of this onboarding guide generated by `brickkit init` v0.1.1 (which said 30 seconds). The basis is Design Book §12.3.5: the platform's `startPeriodSeconds` default really is 60, with `interval`/`timeout`/`retries` hardcoded to 10s/3s/3. **The authoritative version of the platform's onboarding guide lives in the brickKit repo**; this page has taken over that file, so `brickkit skills update` no longer refreshes it (the four skills under `.claude/skills/` still refresh normally).

## Things Not to Propose (all argued over and rejected)

| Don't propose | Why |
|---|---|
| Baking the test accounts/roles `make seed` creates (like `dev.superuser`) into a migration, for convenience, so a container has them the moment it starts | Migrations run on every deployment, **including a real customer's production deployment** — baking this in means permanently burying a backdoor account with a public password and every permission into every single customer's system, the same class of risk as "a production Casdoor app must never enable the `password` grant type." The chicken-and-egg problem of "how does the first admin get in" for a real deployment already has a secure answer: `infra-authz`'s `bootstrapAdminSub` config item + `Start()`'s `EnsureBootstrapAdmin`, letting a real deployer fill in a real `sub` — no hardcoded account needed. Test accounts stay in `make seed` (manually triggered, never part of any deployment/CI flow); generic product baseline data (a default warehouse, a default legal entity + chart of accounts — anything that isn't an identity credential) still belongs in a migration. These are two different things |
| Adding a registry, config center, gateway, or long-running service to brickKit | The platform is deliberately minimal. **It's exactly because it stays restrained that we can swap the other end of a connection just by changing where a DNS name points** |
| Introducing Redis | Stateless JWTs + local digest replicas + PG row locks + gateway rate limiting already cover everything Redis is usually reached for (Decision 71). **Permissions don't need it either**: the check is an in-process map lookup (Decision 116); adding a Redis hop in the middle would only make it slower |
| Building a "role → permission" replica table plus event sync per component; or having each component ask authz on every request | Decision 116: the former turns a map lookup into a distributed cache-invalidation problem (62 tables plus 62 dependency edges); the latter is a network call on every request (Decision 16 already rejects that). The right answer is an **OPA-style local PDP**: `GET /authz/bundle` pulled into an **in-process memory map** every ~15s conditionally, **zero tables, zero migrations, zero events in any component** (Chapter 14 §14.1.4) |
| Stuffing permission keys into the JWT | Decision 116: fine for an ordinary user, but **a super-admin's full set blows past an 8KB header — the symptom is a successful login followed by every subsequent request returning 431**. A JWT only carries identity (`sub`/`roles[]`/`dept_path`/`org_id`); not a single permission key goes in it (§14.1.5) |
| Adding an explicit Deny to permissions | Decision 116: **Kubernetes RBAC explicitly has no Deny**, precisely for reasoning simplicity; AWS's Deny/Allow evaluation order is exactly what makes it hard to use. Under a pure union, "why can they see this" always has exactly one answer. The right way to express "everything except X" is to give them a role that doesn't include X |
| Building a runtime-configurable admin UI for data scoping | Decision 118: **data scoping ships with a version** (same as SAP / Odoo / PG RLS). The one system with a runtime-editable version, Salesforce, pays for it with a materialized Sharing Table, where **changing one rule in a large org takes hours to recompute in the background** — that's a materialized-view recomputation problem. A "policy-level" rule locked into code, by contrast, can be diffed and rolled back |
| Using PostgreSQL RLS for data scoping; or building a general-purpose "record sharing" engine | Decision 118: the premise that "`sqlc` can't handle dynamic WHERE clauses" is **simply wrong** — the condition just gets compiled statically as a `.sql` parameter, and once that premise falls RLS stops being worth it anyway (it also carries a silent trap: **a table's owner bypasses RLS by default**, so a policy can be written and yet filter nothing). As for a sharing engine — that's building Zanzibar, when **an instance-level need (reassign this customer to a different salesperson) is just a business feature** — changing `owner_id` is the whole fix (§14.2.1) |
| Introducing Consul / etcd / Zookeeper | The routing table is aggregated at generation time; no runtime service discovery is needed (Decision 72) |
| Packaging the event bus / object storage as a component | The zero-code pieces of infrastructure shouldn't be packaged as components — doing so turns "swap the implementation" from changing one field into changing dozens of manifests (Decision 86) |
| Making the gateway or observability stack a component | The platform's resource `kind` is a closed enum (no `gateway` / `iam` / `telemetry`), and a manifest **has no `volumes` field** — there's nowhere to mount a config file |
| Using React on the frontend | Decision 79: two-way form binding for ToB use cases, cross-platform unification, AI-generated code stays structurally clear, and the domestic ecosystem. Locked to Vue 3 + Uni-app |
| Swapping the PC side to Element Plus / Naive UI; or trying to "unify the component library across both ends" | Decision 111: PC is locked to **AntDV v4 + vxe-table**, mobile to **wot-design-uni**. **The two ends being different is by design** — mobile is card lists / QR scanning / two approval buttons, PC is dense tables and multi-level cascading long forms; sharing components buys almost nothing (AntDV's DOM dependency alone rules this out). The only thing the two ends share is `packages/design-tokens`: **share the tokens, not the components** |
| `import`ing a third-party UI component directly into a business page (including `<vxe-grid>`) | Decision 111: third-party components may only appear inside `packages/ui-kit-pc` / `ui-kit-mobile`, which expose our own component names to the outside. Same logic as `be-sdk-*`: swapping the implementation means changing one file, not 40 pages. Tables especially matter: **vxe is a "default choice, pending confirmation"** (some capabilities are commercial-tier); pages always use `<BeTable>`, and every escape hatch must be logged in `ui-kit-pc/README.md` (§12.6.6) |
| Mixing in another UI library "to make it look nicer" | Decision 111: the **only** valid reason to mix libraries is something AntDV genuinely can't do (a Gantt chart, an approval-flow designer, rich text, a code editor, a big-screen dashboard). **Two libraries' token systems never line up, so more mixing makes it look worse, not better** — and what actually ruins the look is "this page uses 16px spacing, the next page uses 20px" (§12.6.5) |
| Pulling in vue-vben-admin / antdv-pro as a dependency for the skeleton | Decision 112: its routing + permission layer is driven by a "backend menu table / static routes + role codes," while ours is driven by `/api/tenant/features` feature flags — strip out that layer and all that's left is a layout, with the whole dependency tree still attached. **Read its layout / router+access / request pieces, don't install it** (SOP-R's R-2) |
| Building the PC side as a left-hand multi-level tree (domain → component → page, three levels deep) | Decision 113: the menu is aggregated at generation time from 62 `assembly.yaml` files — there is no central menu table to reorder, and **every customer's installed component set is different, so that tree has a different shape for every customer**, leaving an AI with no idea which level a generated page belongs on. The skeleton is locked to **AWS-Console-style two-tier navigation** (service selector + favorites bar + a flat menu within each service + in-app tabs + ⌘K + an org/legal-entity switcher, §12.6.7) |
| Copying AWS Console wholesale, including "no in-app tabs" | Decision 113: AWS's pages mostly carry no form state, so a refresh loses nothing; **an unsaved ERP outbound-shipment form disappears the moment the browser refreshes**. Kingdee, Yonyou, and SAP Fiori all use in-app tabs. Two other things must change: the in-service menu is forced flat, and the region switcher becomes an org/legal-entity switcher |
| Starting a business page from a blank `<div>` and laying it out from scratch | Decision 113: AWS Console's single biggest complaint is **visual inconsistency** (every service team does its own thing), and **our disease is identical — 62 components' pages are generated by an AI in batches**. Always start from a page-level template in `ui-kit-pc`: `<BeListPage>` / `<BeDetailPage>` / `<BeFormPage>` / `<BeSettingsPage>` |
| Giving users a "layout mode" switcher, or copying thirty preference items from an admin template | Decision 114: no real customer ever switches it, and it means testing 62 components' pages under three layouts each. The user only owns four things — **favorited components, light/dark, density, language** (plus table column state, purely local). Primary color / logo / watermark / grayscale are **assembly-time configuration** (§12.6.8) |
| Exporting `packages/design-tokens` as TS constants | Decision 114: light/dark and compact mode both need to **switch tokens at runtime**, and a constant compiled into the bundle can't be swapped at runtime. **It must be a runtime-writable CSS variable**, and this must be locked in before the first page is written — **fixing it late means touching every single page**. This is the one item in the entire frontend design with a real time pressure |
| Swapping the Go side to Echo / Fiber / chi / a bare `ServeMux`; or using GORM | Decision 108: the stack is locked cell by cell. Middleware is written exactly once inside `be-sdk-go`; writing it a second time is guaranteed to be worse. GORM manages its own connections and sessions, and fights with the shell's single global pool |
| Using Flask / Django on the Python side; or synchronous `grpc`; or gunicorn with multiple workers | Decision 108: **these are physical constraints.** A WSGI synchronous handler can't get at the shared `asyncpg` pool; synchronous gRPC needs a `run_coroutine_threadsafe` bridge in every method; multiple workers means multiple processes, and the Outbox push thread runs N times over, while the shell shape is a single process |
| Using alembic to manage migrations on the Python side | Decision 108: **the reason is not "cross-language inconsistency"** (migration tools are already split by language — Go uses `golang-migrate`, Python uses `yoyo-migrations`, because a shell never spans languages) — it's that **it buys us nothing**. Zero ORM means autogenerate is completely useless, and our raw DDL (`PARTITION BY`, `DETACH CONCURRENTLY`) can only be wrapped in `op.execute("""…""")` inside alembic — a `.py` shell around nothing. **But it must be consistent within a language**: two migration tools inside the same shell means the launcher needs two separate orchestration paths |
| Writing `main.go` to "assemble everything itself" (opening the pool, `Listen`ing, installing signal handlers, initializing OTel) | Decision 109: that whole assembly gets rewritten the day of merging, and §13.7's teardown gate will fail red across the board the first time it actually runs, six months from now. `main` is exactly one line: `besdk.RunStandalone(module.New)` |
| Writing a component in Java / C# | JVM memory and startup overhead fundamentally conflict with "the customer deploys this locally on a single machine" (Decision 78) |
| Building an in-house code-generation toolchain | Tools first, AI as the fallback. Use what already exists (Decision 32) |
| Doing a partial merged deployment on K8s | `local: true` may only be paired with `deploy.target: docker`; under a K8s target the CLI's generation step errors out immediately. **Going to K8s means tearing everything apart — there is no middle state** (Decision 88) |

## Self-Check Before Writing Code (item 0 matters most)

0. **Am I changing a test just to make it pass?** By default, the implementation is what should change. When a test really is wrong, **stop and clearly state where the error is** first; changing a test gets its own separate commit ([`04-testing-standard.md`](docs/standards/04-testing-standard.md) §2.3). **When an L2 business-rule test is in the way, it is almost always the implementation or the understanding that's wrong.**
1. **Is the port and schema I'm about to write copied from `registry/`, or did I invent it myself?** Self-invented is always wrong.
2. **Am I letting two component modules recognize each other directly?** Cross-component calls only go through gRPC/HTTP + `contracts/`; no code is shared (`be-sdk-*` is the sole whitelisted exception).
3. **Does this code still hold up under "there are another 22 modules sharing this same process"?** Three questions: did I read `os.Getenv`? Did I initialize anything process-level (OTel / logging / signal handlers / the default registry)? Did I `log.Fatal` anywhere? All three must be "no" to pass (Design Book §12.5, §13.3 Iron Rule 7).
4. **Did I design this logic out of thin air, or did I actually go through SOP-R's three steps?** The order is: design it yourself first → only read someone else's implementation for the parts you can't work out → come back and write it yourself. Edge cases missed by designing in a vacuum surface three months after a customer goes live; reading someone else's implementation with an empty head just imports their chronic problems along with it.
5. **Am I forcing an `if` to paper over what should really be a slot family?** If these branches correspond to "different customer profiles, each reasonable in its own way" (a costing method, a picking strategy, an approval-routing scheme…), that's the slot-family signal in [`02-reference-implementation-standard.md`](docs/standards/02-reference-implementation-standard.md) §4 — add a new family — not another branch.
6. **Is this file already too long?** A function past 150 lines, a file past 600 lines, or an `if-elif` chain past 5 branches and still growing — check it against [`03-ai-development-standard.md`](docs/standards/03-ai-development-standard.md) §1.2. The test is **whether you, opening a brand-new session next time, can fix it correctly having read only two files.** Conversely, **forcing a pattern onto genuinely simple logic is the worse outcome** — one more layer of indirection is one more file you have to jump to and learn nothing from.
7. **Which of the four documents need to change along with what I just changed?** A boundary/contract/event changed → update `docs/design/<repo>.md` first; a feature changed → update the README; usage or structure changed → update `docs/手册.md`; a prohibition or judgment criterion changed → update that repo's `AGENTS.md`. **Documentation comes first, code comes second.**
