# BrickEnterprise 数据构建标准

本规范定义这个项目里"数据从哪来"这件事的全部内容。数据分两条完全独立的路径——**种子数据**（`make seed`，给人探索/演示用）与**测试数据**（自动化测试自建，给 `go test`/`pytest` 用）——物理隔离、生命周期不同、绝不共用。但两条路径背后是同一套哲学：数据要覆盖尽可能多的场景，跨组件需要的数据/能力自己没有时，要主动补齐而不是绕过去。这份文档把两条路径分别讲清楚，也讲清楚它们共用的那部分原则。

---

## 一、两条路径：定义、生命周期、为什么不共用

| 机制 | 用在哪 | 数据怎么产生 | 生命周期 | 能不能共用 |
|---|---|---|---|---|
| **测试自建数据**（唯一后缀） | 后端 L1-L4、前端 FE-1~4 全部自动化测试 | 每次跑测试时现造，用时间戳/随机数做唯一后缀区分 | 不清理，攒在库里也无所谓（反正下次又是新的唯一后缀） | **不能**。任何一条自动化测试都不该依赖"这行数据是另一条测试或另一次运行留下的" |
| **种子/演示数据**（`make seed`） | 人：本地探索、演示、给新组件一份开箱即用的数据 | 固定 `idempotency_key`，claim-first 幂等，重复跑不会重复建 | 持久、可整体清空（`make seed-clean` 或 `make db-reset`） | 各组件之间可以互相反查、复用（见 §四），但**绝不能被自动化测试依赖** |
| **跨组件测试的现造数据** | 跨组件集成测试（本组件真实调用真实依赖） | 测试进程通过真实 gRPC/REST 调用，在依赖组件里真实建出需要的数据形态 | 跟单组件测试自建数据同一套判据：唯一后缀，不清理 | 同上，不共用、不依赖种子数据 |

⚠️ **种子数据被清空不该让任何自动化测试变红，自动化测试的数据也不该污染人手工在探索的种子数据。** 两条路一旦被混用，"这条测试为什么突然红了"会变得极难排查——可能是别人清了种子数据，也可能是别人的测试跑完没清理，两种原因排查方式完全不同。保持互不依赖，这个问题从根上就不存在。

**物理上也是两个库，不只是逻辑上不共用**：自动化测试用的 Postgres/NATS 指向专门给测试用的数据库/消息通道（`brickkit_test_db`，`make test-db-init` 建/刷新），跟人工探索/演示用的那一份（`brickkit_db`）是同一个数据库实例里两个物理分开的库，结构镜像同一套 schema，数据互不相通。这条隔离不是过度设计——真实发生过的问题是：某些组件的集成测试会真实写入共享的、由数据库初始化脚本预置的引用行（比如默认仓库、默认法人这类基线数据），如果测试库和演示库是同一个物理库，测试跑一次就真的改一次演示数据，人工探索看到的数据会莫名其妙发生变化，且这个问题和"容器在不在跑"完全无关——是数据持久化层面的问题，不是运行时并发访问的问题，容器关掉也躲不掉。

**为什么不做成"一次性数据库"**（H2、Testcontainers 那一类做法）：这个项目的分区表、`SET LOCAL ROLE`/`search_path` 这类硬 DDL 与会话级设置，轻量嵌入式引擎装不下，而且这类做法本质是在换一种数据库实现，跟"集成测试的判据就是真实基础设施"这条原则直接冲突。真正解决"重复造数据慢、互相污染"这个问题的办法不是换一个一次性的库，而是**让数据本身是一次性的**——现有的"唯一后缀 + 不清理"就是这条路径在不引入一次性数据库前提下的正确形状，不是权宜之计，是长期该有的样子。

## 二、通用原则：不管哪条路径，数据都要覆盖尽可能多的场景

这条原则对种子数据和测试数据都成立，只是"覆盖"的方式不同：

- **种子数据**追求"多而全"——每条状态机、每个分支、每个失败路径、每个数据权限维度，都要有数据能真实触发，因为种子数据同时服务着"人能不能完整体验这个系统"这件事，量和种类本身就是目标。
- **测试数据**追求"少而准"——每一条测试只需要**刚好够验证这一条具体断言**的最小数据，不需要为了"丰富"本身去堆量。核心交易类组件的业务规则测试（不变量、状态机迁移边）除外：这类测试要用属性测试框架生成大量随机边界输入去主动攻击实现，这里的"多"是为了让随机输入尽可能撞上边界条件，跟种子数据"多而全"的目的不同，不要混为一谈。

两者不是同一种东西的"丰富版"和"精简版"，是服务不同目的、天生就该长成不同样子的两套数据——但底线是一致的：**任何组件都不该只有"一切正常"这一种数据/断言**。状态机每个状态、每个失败分支、每个数据权限维度，不管是种子数据还是测试数据，都不许只覆盖欢乐路径。

## 三、跨组件协作：需要的数据/能力，依赖组件本来没有时怎么办

这是本规范最重要的判据，对种子数据和测试数据两条路径都适用，只是具体动作不同。

### 3.1 自动化测试场景

写跨组件集成测试，需要依赖组件产生某种数据形态（比如"一个信用额度为零的客户""一个已停用的产品""一个处于某个特定状态的商机"）时：

1. **优先通过依赖组件的真实 RPC/REST 接口现场造出来。** 调 `CreateCustomer` 传 `credit_limit=0`，调 `SetStatus` 转成 `DISABLED`，都是真实存在的命令，测试可以直接调用，不需要预先存在的数据。
2. **如果依赖组件的真实契约根本没有能力产生这种数据形态**（没有对应字段、没有对应状态转换命令、没有对应组合），**正确做法是先给依赖组件的契约/实现加上这个能力，用真实调用把数据造出来，而不是绕过去、用裸 SQL 插进对方的库、或者干脆跳过这个场景不测。** 加能力本身要遵守正常的契约演进规则（只增不改，向后兼容）——这不是一次性的权宜之计，是在把依赖组件本身的完整度补齐，之后任何测试、任何调用方都能受益。
3. **裸 SQL 直接写依赖组件的数据库，永远是最后一个选项，且原则上不许用在自动化测试里。** 跨组件的边界本来就是"只能通过契约交互"，测试代码也不例外——直接写别人的库，等于在测试里悄悄建立了一条契约之外的耦合，契约怎么改都不会让这条测试报警，它只会在契约真正改动之后以别的、更难定位的方式坏掉。

### 3.2 种子数据场景

**下游可以、也应该主动要求上游丰富数据，不是被动等**：如果一个组件做演示或测试需要的数据组合（比如"一个属于华南部门、状态是 `DISABLED` 的客户"），上游组件的种子数据里还没有，正确做法是**直接去改上游组件自己的种子数据生成逻辑，把这个组合加上**——不是在下游这边绕开数据将就着测，也不是干等"以后有人加"。数据是假的，多造几种没有成本，"上游数据够丰富，下游才有得挑"是一条主动的、双向的协作关系，不是单向的等待关系。这跟 §3.1 的判据是同一个原则在两种场景下的体现：**需要的东西自己没有，就去把提供方补齐，不要绕过去。**

## 四、种子数据专属规范

种子数据（`make seed`）虽然不是自动化测试数据，但它服务的其中一个目的正是"测试"这件事本身——一整条业务链路能不能端到端跑通、一个新场景要不要走完全部组件才能验证，很多时候靠的是人真实点开系统、用真实数据走一遍，而不是靠 `go test`。这种"真实运行起来、真实点一遍"的验证方式和自动化测试同等重要，不是自动化测试的低配替代品。

我们现在拥有的所有数据，从头到尾都是模拟数据，从来没有、也永远不会是真的——这件事本身就该被当成一种自由：既然没有"污染真实数据"的顾虑，种子数据的丰富度就应该往上限去够，而不是往"够用就行"去省。

### 4.1 种子数据要同时撑起的目标——这决定了"够不够丰富"该怎么判断，不是拍脑袋定数量

1. **完美测试所有逻辑**：每条状态机、每个分支、每个失败路径都要有数据能真实触发，不是只种"一切正常"那一种。
2. **局部性测试**：有新需求时，能只对着一个组件（连同它声明的全部依赖）就把新逻辑验证完，不需要先把全套组件都启动。
3. **组件部署前的完整链路测试**：包含依赖组件在内的一整条链路，都要有数据能撑起一次端到端的真实调用。
4. **项目部署前的全方位测试**：整个装配起来后，各个角度（权限边界、跨组件事件、补偿逻辑……）都要有数据能覆盖到。
5. **用户体验/演示时的"游乐场"效果**：只有几条数据的项目没法体验——真正能体现项目完整性的是大量客户、各种角色、各种部门同时存在，打开任意一个页面都有东西可看、可查、可玩。

### 4.2 这几件事不会随"数据量大"自动达成，需要专门设计

- **数据权限维度要有真实存在感**：`org`/`owner`/`warehouse` 这类数据权限维度，只有真的存在多个部门、多个负责人、多个仓库的数据，"这个人看不到别人的数据"这类验证才有意义。种子数据如果全挂在一个万能管理员名下，数据权限这一整块能力在真实体验里完全"看不见"。
- **量要能触发分页**：列表接口如果强制游标分页，种子数据太少（比如只有五条）永远只有一页，分页这条契约在体验上完全没有存在感。
- **时间跨度要铺开**：数据应该分布在不同的时间点上，"最近 N 天"这类查询、报表趋势图、按时间分区的维护逻辑才有真实场景可验证，不是所有东西都停在"刚刚创建"。
- **负向/边界数据同样要有**：停用状态、零库存、超期未结、被拒绝的申请——失败路径不能只靠脑补，得有真数据能点开看、能拿去测。
- **数据要可发现**：数据量一旦上来，需要有地方能查到"这个固定标识对应的是什么概念"，不然新组件想复用现成数据时无从查起，还容易在不知情的情况下产生冲突。这份清单落地在 [`docs/dev/种子数据一览.md`](../dev/种子数据一览.md)——组件/数据/数量/谁负责，一个地方查得到即可，不需要每个组件各建一份。

### 4.3 冗余是可以接受的，甚至是好事

这些数据全部是假数据，不存在"污染真实数据"的顾虑。不同组件的种子数据即使概念上有重叠（比如两个组件各自造了一个"制造业客户"画像）也不需要费力去重——冗余的代价趋近于零，而"数据量大、看起来完整"本身就是要达成的目标之一，别的组件需要类似数据时，直接复用现成的也比协调"谁该拥有这份数据"更省事。

### 4.4 归属与协作原则

- **每个组件自己拥有并维护自己的种子数据**，不集中放在装配层：集中式脚本只有全部组件一起启动才用得上，单独启动一个组件时反而什么都没有，这违反了"能单独启动一个组件连同它的依赖树就该跑通"这条更根本的原则。
- **一个组件生成种子数据时，第一步永远是先让它声明的全部依赖（不区分强依赖弱依赖）都把种子数据准备好**，再执行自己那部分。不区分强弱的理由：开发和演示环境里所有组件本来就是全部一起启动的，不存在"只装一部分依赖"这种场景；而依赖关系一旦被声明，就说明这个组件真实需要它——强弱之分是给真实客户部署时"要不要买这个可选模块"这件事准备的区分，不是开发阶段该纠结的问题，在这里额外区分只会增加不必要的心智负担。这样单独对着一个组件触发种子数据生成，就能拿到一整条能跑的数据，不需要依赖任何装配层的编排。若某个声明的依赖在当前环境里确实没有装（连不上），优雅跳过那一步、只把自己分内的数据种完，不因为一个依赖缺失就整个失败退出。
- **组件自己的种子脚本和需要用到产出 id 的编排脚本之间，用组件自己的幂等表当"交接协议"**：组件的种子逻辑只管把数据灌进去，不负责把 id 打印成任何约定格式；谁需要这些 id，自己反查这张幂等表（按固定的 `idempotency_key` 查到真实的行 id），不需要发明交接协议。
- **种子数据本身是一种轻量契约**：一旦有别的组件反查过某个固定标识，这个标识就不能被随手删除或改变含义——只能增加新的，不能修改已经被引用的。需要调整时靠每个仓库自己的 git tag 查历史，不是只看镜像版本号。
- **一张表如果本身"只增不改"**（出于业务或审计原因，比如流水表、已锁定的会计期间），**它就不该有"逐行删除式"的撤销机制，只能靠整库重置来清空**——序列号不会因为删除而回退，逐行删除既做不到真正干净的复原，又违背了这张表本身"只增不改"的设计。这类组件的正确工具是 `make db-reset`（`migrate down` 再 `up`）——真正的重置，不是删除：drop 掉整个 schema 的表再按迁移重建，序列真的从 1 开始，migration 播种的基线数据也会跟着重新落地。**判据：一张表如果只增不改，它就没有 `seed-clean`，只有 `db-reset`**；能安全逐行删除的表两者都可以有，`seed-clean` 更轻量（不影响其它数据），优先用它。
- **能进真实客户部署的凭据/身份类数据，永远不能混进这套机制**：测试账号、万能密码这类东西一旦被写进"每次部署都会执行"的数据库初始化脚本，就等于给每一个真实客户的系统永久埋了一个后门——这跟"生产用的认证应用不许开密码直登授权类型"是同一类风险。这条边界不允许有例外：
  - **真正通用、任何部署都需要的基线/参考数据**（默认仓库、默认法人+基础科目表、基础计量单位这类）继续走 migration——这部分不是"测试数据"，是产品本身的一部分。
  - **真实部署"第一个管理员怎么来"这个鸡生蛋问题，答案不是种子数据，是配置驱动的自举**：让真实部署时第一个登录的人拿到自己真实的身份标识，填进一个自举配置项，容器启动时幂等授予管理角色，不需要任何人手写 SQL，也不需要任何硬编码账号。这个机制只解决"谁是第一个管理员"，跟本地测试要用的"持有全部权限键的超级测试角色"是两回事，不能互相替代。

## 五、测试数据专属规范

测试数据的生成方式（唯一后缀、不清理）与生命周期已在 §一 讲清楚，这里补充测试数据在特定测试类型下的额外要求：

- **消费者（consumer）测试**有两条独有的规矩——自己构造/发布事件触发消费者时要用测试私有的 subject（避免跟同机真实运行的容器抢消息）、去重表按唯一标识做单调去重时测试要用唯一的标识而不是固定字符串（避免去重逻辑让第二次运行静默失效）。这两条属于"怎么写好一条消费者测试"的执行细节，完整说明见 [`00-测试标准.md`](00-测试标准.md) 的 §3.4。
- **跨组件测试需要的数据形态，依赖组件真实契约做不出来时怎么办**，见 §三。
- 除此之外，测试数据不需要考虑 §四种子数据专属的那些维度（分页、时间跨度、可发现性……）——一条测试只需要精确匹配它自己的断言，不需要为了"覆盖体验完整性"这类跟这条测试无关的目标去多造数据。
