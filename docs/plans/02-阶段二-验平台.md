## ⚠️ 开工前必须先读：阶段一欠下的一笔账

阶段一计划的**增补 B** 白纸黑字要求 `be-sdk-go v0.1.0` 里定型三处签名，理由写得很清楚：

> **不留形状的代价**：`be-sdk-go` 的路由注册签名一旦发布，阶段三再加权限键参数就要改所有已写的组件——而那时 `mdm-customer` 已经在跑了。

**实际交付的 `v0.1.6` 里，这三处一个都没有**（阶段二开工前核对 `be-sdk-go` 导出符号发现）：

| 增补 B 要求的 | 现状 | 后果 |
|---|---|---|
| `besdk.GET/POST(r, path, perm PermKey, h)` + `const Public` | **不存在**。`mdm-customer` 的六条路由全是裸 `g.GET(...)` / `g.POST(...)` | 正是导读第 23 条禁的那件事：**绕开权限键的签名强制，那个接口从此无人鉴权且完全没有症状** |
| `besdk.ScopeOf(ctx) ScopeFilter` | **不存在** | `erp-sales` / `erp-inventory` 是本阶段第一批 `data_scopes` 不为 `none` 的组件，没有它就只能各写各的过滤 |
| `besdk.UserClient` / `SystemClient` | **不存在** | `erp-sales` 是**第一个真的跨组件调用**的组件。这两个名字的区别就是第三条「悄悄读到别人数据」的路径（§14.2.6），第一次调用之前必须先有它们 |

**为什么必须现在还，不能拖到阶段三：**

| 什么时候还 | 要改几个组件 |
|---|---|
| **现在（阶段二 Task 1）** | **1 个**（`mdm-customer`，六条路由） |
| 阶段二做完再还 | 5 个 |
| 阶段三（增补 B 原计划的落点） | 13 个 |
| 阶段六 | 55 个 |

这正是 §3.5.1.1「写到第 30 个组件才发现要回头改前 29 份」那条的翻版。**Task 1 是本阶段的第一个任务，不是可选项。**

⚠️ **本阶段仍然不实现权限判定**——`GET/POST` 的实现照增补 B：JWT 验签 + `Public` 放行，权限判定固定返回拒绝（fail-closed stub）；`ScopeOf` 返回「不限」。**变的只有签名的存在与否**，行为与阶段一一致。`infra-authz` 组件本体、bundle 轮询、`.sql` 谓词仍全部在阶段三。

## 四块砖的顺序，和为什么是这个顺序

设计书 §4.2 的同步图里，这四块的出边是这样的：

```
mdm-product     → （无出边）
erp-inventory   → （无出边）
erp-finance     → （无出边）
erp-sales       → mdm-customer, mdm-product, erp-inventory, erp-finance
```

**三块是枢纽（零出边），一块是链上一环。** 所以顺序是定死的：**先把三个枢纽立起来，最后用 `erp-sales` 把它们串成一条链。**

| 块 | 为什么排这个位置 | 它替本阶段验掉什么 |
|---|---|---|
| `mdm-product` | 与 `mdm-customer` 同构（只读枢纽、零依赖、`data_scopes: none`） | **证明第一块砖的模板可复用**——第二个组件应该明显比第一个快。如果不快，说明阶段一沉淀下来的是个例而不是模板 |
| `erp-inventory` | 零出边，但**被 `erp-sales` 同步调用**，是 TCC 的下游 | 幂等写接口、`GetStatus`（防薛定谔超时）、条件更新防超卖；顺带成了 `besdk.Consume` 第一个真实调用方（消费 `mdm.product.*` 维护摘要副本） |
| `erp-finance` | 零出边，但**消费事件**，是事件汇 | `besdk.Consume` 第二个真实调用方；会计期间分区（唯一不按 `created_at` 分区的表） |
| `erp-sales` | 四条强依赖边全在它身上 | **平台的依赖注入、地址改写、启停级联、弱依赖缺失——20 条里最难的那几条全靠它** |

⚠️ **`erp-inventory` 不对 `mdm-product` 建同步边**，尽管它记录的是产品的库存。理由：设计书 §4.2 的图里没有这条边，而 `product_id` 对库存来说是一个不透明外键——**校验产品存在是调用方（`erp-sales`）的事，它已经校验过了**。批次/序列号是否必填这类需要 `tracking_type` 的判断，走事件摘要副本而不是同步调用（详见 `docs/design/erp-inventory.md` §5）。
**顺手加一条同步边是本阶段最容易犯的错**——它不报错、跑得更快，直到同步图成环才发现（导读第 3 条）。

- [x] **步骤 2：实现**

```go
// authz.go
type PermKey string

// Public 是「显式公开」，不是「省略」。用空字符串做零值是刻意的：
// 漏传参数编译不过，传了空字符串是一次有意的声明。
const Public PermKey = ""

// GET 注册一条带权限键的路由。⚠️ 业务代码不许再碰 gin.Engine 的 GET/POST——

func GET(r gin.IRoutes, path string, perm PermKey, h gin.HandlerFunc) gin.IRoutes

// Public 放行，其余一律 403。阶段三换成进程内 bundle map 查找，签名不变。
func RequirePermission(perm PermKey) gin.HandlerFunc
```

```go
besdk.GET (g, "/customers",     besdk.Public, listHandler(svc))
besdk.POST(g, "/customers",     besdk.Public, createHandler(svc))
// …其余四条同理
```

⚠️ **本阶段标 `Public` 是刻意的**（增补 B 原文），不是偷懒：权限判定要到阶段三 `infra-authz` 上线才有真实现，现在标真键会让所有接口在 stub 下 403，等于把组件关掉。**阶段三要回来把这六条改成真键**——这条写进 `mdm-customer` 的 `AGENTS.md`。

- [x] **步骤 4：`ScopeOf` 与两个 client**

```go
// scope.go —— 阶段二返回「不限」，形状先立住
type ScopeFilter struct {
    Prefix string // dept_path LIKE prefix || '%'
    Exact  string
    Owner  string
    In     []string
    All    bool   // 阶段二恒 true
}
func ScopeOf(ctx context.Context) ScopeFilter

// client.go —— 这两个的**名字区别就是安全边界**

func SystemClient(dep, extra string) (*grpc.ClientConn, error)
```

#### Task 2：`make gates` 加两条扫描

阶段一的 `gates` 只有铁律六 import 扫描。Task 1 造出来的两个东西必须马上配上机器守卫，否则下一个组件就会写错。

- [x] **扫描一：`SystemClient` 不许出现在用户请求路径上**（§14.2.6、导读第 21 条）

判据：`SystemClient` 的调用只许出现在 `Start()` 函数体内、或文件名含 `handler`/`consumer` 的**事件**处理代码里；出现在 `internal/http` / `internal/grpc` 的请求处理路径上就红。

⚠️ **这条扫描抓的是「不报错、返回的数据只是多了一些」**——没有机器守，人永远发现不了。

- [x] **扫描二：业务代码不许裸用 `gin` 的路由方法**（导读第 23 条）

判据：`backend/internal/http/` 下不许出现 `\.(GET|POST|PUT|PATCH|DELETE)\(` 直接调用在 `*gin.Engine` / `*gin.RouterGroup` 上（`besdk.GET(g, ...)` 是把 `g` 当参数传，不匹配这个模式）。

⚠️ 与 `mdm-customer` 的 `module-check` 一样，**扫描前先 `sed 's://.*::'` 去掉行内注释**——这个代码库大量写"⚠️ 不许 X"的说明性注释，不去注释会把自己判成违规（阶段一 D5 踩过）。

**验证：** 故意在 `mdm-customer` 里写一行裸 `g.GET`，`make gates` 必须红；改回去必须绿。

#### Task 3：阶段一实测回填进设计书 / 总纲

总纲 §5.1 的流程要求「先改设计书」再开工。阶段一复盘的结论是**设计书本身没有说错**（`local: true`、`expose`、额外端口三处都与实测一致），但有两处**只写了结论没写推论**，容易让下一个人重踩：

- [x] **回填 1：`expose: true` 只映射主端口**

设计书 §6.3.1 讲 `expose: true` + `exposePort` 时，上下文全是前端/BFF 组件的主端口。§3.5.1.1 讲「gRPC 等额外端口完全不能事后改」时，上下文是 `local: true` 的 `localPort`。**两处都对，但没有一句话把它们连起来**：一个普通 Docker 组件想从宿主机 `grpcurl` 它的 gRPC 端口，`expose`/`exposePort` 帮不上忙，`localPort` 也帮不上忙——**没有任何机制**，只能走容器的 Docker 网络 IP。

在 §3.5.1.1 那张表下面补一行推论即可（不改结论，只把推论写出来）。

- [x] **回填 2：`local: true` 是「不生成容器」，不是「容器照跑再加个宿主机端口」**

设计书 §13.1 与 §2650 的「机制三」都写对了，但阶段一实测时仍然误用了一次（以为它能让容器照跑还带宿主机端口，结果把正在跑的容器干掉了）。在 §13.1 开头补一句**最容易误解的点**，成本一行。

- [x] **回填 3：`be-sdk-go` 五个版本的修复清单进 `docs/dev/实测踩坑记录.md` 的索引**

A4d–A4i 六条已经在踩坑记录里了，只需在 `be-sdk-go/README.md` 的「现状」段落顶部加一句总览：**v0.1.1–v0.1.6 修的六个 bug，有五个是「测试构造路径与生产构造路径不是同一条」的同一类问题**——这句话比六条细节更值钱，它是下一个基础库该怎么写测试的判据。

### Task 7–10：`erp-inventory`（物理命令枢纽）

| 项 | 值 |
|---|---|
| 端口 / schema | HTTP `8086` / gRPC `9096`；`erp_inventory` / `erp_inventory_rw` |
| 依赖 | `components: []`（理由见上文「四块砖的顺序」） |
| 数据权限 | `warehouse` 维（§14.2.2），**建表时就要有对应列** |
| 分区 | `inventory_movements` 按 `created_at` **月**分区；`inventory_balances` **不分区**（§11.2.5 注：余额表必须永远小而快） |

**本阶段最难的两件事都在这块砖上：**

- [x] **① 幂等三件套**（§4.4.2、§4.5）

```
Reserve(idempotency_key, order_id, items[]) → reservation_id
CancelReservation(idempotency_key, reservation_id)
GetReservationStatus(reservation_id) → RESERVED | CANCELLED | CONFIRMED | NOT_FOUND
```

⚠️ **`GetReservationStatus` 不是可选的**。它是防「薛定谔的超时」的唯一手段：`erp-sales` 调 `Reserve` 超时后**严禁直接调 Cancel**，必须先查真实状态（§4.5）。没有它，超时就只能猜，而猜错的两个方向——误杀（取消了其实成功的预留）和漏杀（漏掉了其实失败的）——都会静默地把库存数字搞错。

✅ 实现在 `Reserve`/`CancelReservation`/`ConfirmIssue` 三个真正的写命令上都改用了 claim-first 幂等（`INSERT ... ON CONFLICT DO NOTHING` 原子声明），比原计划设想的"先查后插"更强——真机验证过并发下不会出现两边都以为自己是第一次的窗口。

- [x] **② 条件更新防超卖，不是 `SELECT FOR UPDATE`**（§4.4）

```sql
UPDATE inventory_balances
   SET reserved_qty = reserved_qty + $1, version = version + 1
 WHERE product_id = $2 AND warehouse_id = $3
   AND on_hand_qty - reserved_qty >= $1     -- ← 防超卖在这一行，不在应用层
```

判据：`RowsAffected() == 0` 就是库存不足，返回 `FailedPrecondition`。**应用层先查再写一定有竞态**，无论查得多近。

- [x] **③ 并发测试是这块砖的核心测试**（L3，`-race` 下跑）

N 个 goroutine 同时预留同一个 SKU，库存只够其中 M 个（M < N）：**成功的必须恰好 M 个，余额必须恰好归零，一条超卖都不许有**。这条测试挂了就是真的会超卖，不许放宽。

✅ `TestReserve_并发防超卖`：100 个 goroutine 抢 30 件库存，成功恰好 30、`reserved_qty` 恰好等于 30、`-race` 无报告。**手动改回"先查后写"验证过这条测试真的会红**（判定逻辑错误被数据库 CHECK 约束兜住，但判定本身已经不对）——不是纸面判据，真的跑过对照组。

- [x] **④ 流水不可变，余额是投影**（参考 ERPNext 的 Stock Ledger Entry，见设计计划 §8）
      `inventory_movements` 只 INSERT 不 UPDATE；`inventory_balances` 是它的当前投影。**对不上时以流水为准重算**。实现里只有 `insertMovement` 一处写入口，没有任何 `UPDATE inventory_movements`。

   查证四个成熟 ERP 后，共发现 **9 条"每一种都合理、只是适配客户不同"的分歧**（详见各设计计划 §8）：

   | 分歧 | 谁发现的 | 现实中的分歧 |
   |---|---|---|
   | 成本核算法 | inventory | ERPNext 按物料配 / Odoo 按产品类别配 |
   | 补录历史策略 | inventory | ERPNext **改写**历史 / Odoo **追加**冲销层——两个成熟系统给出相反答案 |

   | 关账策略 | finance | Tryton 期间实体 / Odoo lock date / ERPNext 三套并存 |
   | 迟到单据策略 | finance | 拒绝 / 顺延下期 / 角色强改 |
   | 预留严格度 | sales | Odoo 配置项 `reservation_method` |

   > **「可替换」在交易组件上的落点是 `customer_fork`，不是 slot。**
   > slot 适合的是**没有人对它建依赖边**的位置——`frontend-*`、`slot:iam`、`slot:payroll`、`channel:*`。
   > 交易组件（erp / crm 域）的客户差异，正确形态是设计书 §9.5 的**代码级 Fork**（复制 `erp-sales` 为 `erp-sales-acme`），
   > 或分歧小到只有几个分支时用 SOP-P 的内部策略。

   **这直接回答了"最终目标"那句话**（总纲 §5.1 末）：*"每个功能组件都可以有多种实现，客户按需选择，甚至基于最接近他需求的那一个做闭源二次开发"*——**在交易组件上，"多种实现"就是多个 Fork，而这 9 条分歧正是 Fork 时最该改的地方。把它们记在设计计划里，就是给未来的 Fork 画好了改动点地图。**
