# 阶段五 B · 组合矩阵验证

> **这是唯一一份记录"部署组合怎么测"的文档**：要测什么、为什么这么测、组件参与清单、真机过程、结果、结论，全部写在同一份文档的同一个任务节里，不拆成计划/变体设计/结果这类互相引用的多份文档。准备工作（把装配仓库迁移到真实 `servedBy`）在 `docs/plans/05a-迁移到servedBy.md`，本文档只管正式的组合排列测试，默认 05a 的全部结论已经成立。
>
> **每个 Task 都是独立、完整的一节，不依赖、不引导到别的 Task 去看结果**——包括版本变体：同一个拓扑分组里的四个 Task（比如"纯外壳"的 Task 4/5/6/8）各自有一份完整的版本变体测试，不是"选一个代表性 Task 测完整、其它 Task 只抽样复核"。哪怕两个 Task 测的版本变体在道理上是同一件事，也分别在各自的环境下真机构造、各自记录，因为运行环境本身（裸进程 / Docker / K8s）往往会让"怎么构造这个变体"的具体做法不一样，写清楚这个做法本身就是这个 Task 的产出。

## 动机

现在只有 14 个真实组件，本机资源还绰绰有余；等军火库真的铺到接近 62 个组件时，光是"起一遍全部组件"这件事本身就可能撑不住本机资源，到时候再想补一遍"部署方式到底靠不靠谱"这类基础验证，成本会高得多。趁现在数量还合理，把"组件"和"外壳"两种部署形态、在"本地/Docker/K8s"三种运行环境下、以及两者混搭和多版本共存的全部排列组合，能验的都真机验一遍，每一种组合独立记录过程和结果，**包括那些肯定会出错的组合也要真机构造、记录报错内容和理由，不能因为"预期会失败"就跳过不测**。

能够部署不代表整个项目真的可用——每个任务除了"能不能起来"，都必须至少做一次真实的跨组件调用，确认协作符合预期。

## 参考资料（背景机制，不重复解释）

- `docs/dev/给brickKit的反馈.md` 第七部分——最初的 `servedBy` 提案。

- **调研结论摘要**（设计每个任务时随时回查）：
  1. `servedBy: <组件ID>@<精确版本>`，格式/自引用/链式嵌套/与 `local:true` 互斥共 6 条静态校验 + 目标存在性/运行态 2 条生成期校验 + 端口/端点变量/标签 3 条合并冲突校验，全部有 brickKit 自己的单元测试覆盖。
  2. 环境变量合并**只**覆盖 `*_ENDPOINT` 类，`COMPONENT_ID`/`COMPONENT_VERSION`/`configSchema` 配置值/资源连接变量**无条件排除**，有专门测试断言"即使同名同值也不会被合并"。
  3. `BRICKKIT_SERVED_MEMBERS`——逗号分隔版本化服务名，字典序；**零成员时是显式空字符串，不是变量缺失**。
  4. Docker：外壳的 compose service 挂上每个成员的版本化服务名作网络别名；依赖了某个 `servedBy` 成员的组件，`depends_on` 自动改指向外壳；成员自己不生成 service。K8s：成员生成一个 `selector` 指向外壳 Pod 标签、`targetPort` 用成员自己端口的 Service，不生成 Deployment/Job；NetworkPolicy ingress/egress 自动跟着调整。
  5. ⚠️ **`expose`/`exposePort`/`hostname`/`replicas`/`resources`/`serviceAccountName` 写在 `servedBy` 成员条目上完全不生效**（只有警告）。
  6. **多版本共存**：同一个外壳收编同一组件的两个不同版本——**已确认支持**（`TestResolveGroupsTwoVersionsOfSameComponentUnderOneShell`），唯一约束是端口不能撞；`EnvPrefix` 不带版本号，若两个版本的同名 config 值不同会直接报错（05a Task 0.6 收尾已确认这是合并进同一进程固有的性质，不是缺陷）。同一个 `(id, version)` 不能同时独立部署又被 `servedBy`。**两个不同外壳各自收编同一组件的不同版本**——brickKit 自己完全没有测试或文档覆盖，是真正的未知领域。
  7. `local: true` 的字段语义、K8s 下的拒绝逻辑，`servedBy` 落地前后完全没变。

### 每个任务/变体的强制要求（不满足不算做完）

1. **组件参与清单**：明确写出用了真实 14 个组件里的哪些、各自什么版本、排除了哪些、为什么排除。执行完之后要把"上一个 tag"这类相对说法替换成真实用到的确切版本号（比如 `1.0.9` → `1.0.8`），相对说法只允许出现在执行前的计划阶段。
2. **代表性沟通测试**：不能只验证"能不能部署起来"，必须至少发起一次真实跨组件调用确认协作符合预期，不用覆盖所有链路，1-2 条有代表性的就够。如果这条任务本身预期就是失败（负向验证），写清楚"不适用，本任务测的是失败本身"。
3. **结果直接写在本节的"结果"/"结论"里**，缺哪一项要写清楚"为什么没有"，不能悄悄空着。执行前先填好"组件参与清单"和"测试方法"，执行后立刻补"结果"和"结论"，不攒到最后一起写。不管结果是成功还是失败/报错/行为不符合预期，都要如实记录具体现象（报错文案、日志片段、实际观察到的行为），不能只写"通过"/"符合预期"这种无法复核的结论。
4. **禁止用"同 Task X"代替具体场景描述**：哪怕两个 Task 的构造在道理上完全一样，也要在本节内把"组件参与清单"和"测试方法"完整重写一遍，不能只写"同 Task 5b 的场景"就结束——未来审批只会直接跳到某个矩阵格子看，不会顺着文档去翻别的 Task。允许的例外是纯粹的背景说明/对比（比如"这条在 Docker 侧已验证过，这里独立复现"），前提是即使不看那句话，本节自己的步骤和结论也完整、可执行、可理解。
5. **结果里要写明真机执行的日期**，配合第 1 条的确切版本号一起构成"这次验证是在什么状态下做的"的快照，供以后组件铺到更多数量时，回头比对同一个矩阵格子"当时 vs 现在"具体发生了什么变化。
6. **鉴权面组件是任何真实业务调用绕不开的前提，必须补进组件参与清单**：Task 1 真机执行前读 `be-sdk-go` 的 `authz.go` 确认——组件启动不会因为连不上 `infra-iam-casdoor`/`infra-authz` 而失败（不阻断启动是设计好的行为），但只要"代表性沟通测试"要发起一次真的带权限键的业务调用（而不是只测端口通不通），就必须有：① 真实、能被本地 JWKS 验签通过的 JWT（需要真的走一遍 Casdoor OAuth 登录 + `infra-iam-casdoor` 拿 `id_token` 换 app token 的完整链路，各组件 `scripts/seed.sh` 的 `get_jwt()` 函数就是这么做的）；② `infra-authz` 真的可达并成功轮询过一次 `/authz/bundle`，否则具体权限键判定直接 503。因此**每个 Task 只要"代表性沟通测试"需要真实业务调用，`infra-iam-casdoor` + `infra-authz` 就要按这个 Task 当前的拓扑/环境形态一起补进"组件参与清单"**（本地裸进程任务里这两个也裸进程跑；Docker 任务里这两个也是 Docker 容器；纯外壳任务里这两个也在对应外壳里，等等），不能因为"这次测的主题不是鉴权"就默认忽略——这两个本身也是 14 个真实组件之一，不是可以当基础设施忽略不计的东西。

### 环境定义

**"纯外壳"（Task 4/5/6/8）的组件参与清单，跟"混搭"（Task 9-12）不一样，两者不是同一份拓扑测两遍**：`frontend-standard` 没有后端进程（纯前端 SPA/H5，压根不存在可以被合并的东西）、`infra-bff-mobile` 按设计明确保持独立——这两个组件结构性地永远不可能被 `servedBy`。所以：
- **纯外壳（Task 4/5/6/8）用缩减清单**：只含 11 个 Go 组件 + `infra-print`，**全部** `servedBy` 收编进各自外壳，`frontend-standard`/`infra-bff-mobile` 这次测试**不参与**（临时从 `brickkit.yaml` 里去掉，或者 `enabled: false`）。这样测出来的才是真正"零独立组件、100% 合并"的场景。
- **混搭（Task 9-12）用真实全量清单**：真实 14 个组件——12 个 `servedBy` 收编 + `frontend-standard`/`infra-bff-mobile` 独立，这本来就是本项目当前唯一的真实部署形态。

这样 Task 5 和 Task 10 就不是测同一份拓扑——一个是"能不能做到 100% 纯合并"，一个是"我们真实项目现在长什么样"，两者都有独立价值。

**"Docker+本地混合"的准确定义**：绝大部分组件走 Docker（不管是独立部署还是被某个外壳收编），额外挑 1 个**完全独立**的组件（不受 `servedBy` 影响）用 `local: true` 拉到宿主机调试——这是唯一一种 `local:true` 和"这次测的拓扑"会同时出现在同一份 `brickkit.yaml` 里的组合，brickKit 自己的回归测试（`TestLocalStillWorksAlongsideServedBy`）已经确认两者不冲突，这里在自己的真实组件上复核一遍。

**"纯本地"（Task 1/4/9）的准确定义，区别于"Docker+本地混合"**："本地"是跟"Docker+本地混合"并列的独立一档，不是它的子集——"纯本地"任务里**全部参与组件都跑成宿主机裸进程**（`go run`/`uvicorn` 之类，手动喂环境变量模拟平台注入），不借助 `local:true` 机制（那个机制的前提就是"其它组件在 Docker 里跑着"，属于"Docker+本地混合"那一档）。

## Task 1：纯独立组件 × 本地

**组件参与清单**：`erp-sales`（依赖方）+ `mdm-customer` + `mdm-product`（业务被依赖方）+ `infra-iam-casdoor` + `infra-authz`（鉴权面，代表性沟通测试要发真实业务调用绕不开的前提），其余不参与（验证的是"单个组件本地调试"这个机制本身，不需要全量组件陪跑）。五者都用 `brickkit.yaml` 当前锁定的最新版本（变体 a / baseline）。⚠️ **计划阶段的两次修正**：① 原计划只写 `erp-sales`+`mdm-customer` 两个组件，执行前读 `backend/internal/tcc/create.go` 发现 `CreateOrder`（哪怕是最简单的建草稿单）内部同时调用 `fetchActiveCustomer`（`mdm-customer`）和 `fetchActiveProducts`（`mdm-product`，用于按分类取价），不存在"只连 `mdm-customer` 就能完成一次有业务意义调用"的路径，补 `mdm-product` 进清单；② 执行前读 `be-sdk-go` 的 `authz.go` 确认，任何带权限键的真实业务调用都需要真实可验签的 JWT（走 Casdoor OAuth 登录 + `infra-iam-casdoor` 换 app token）和 `infra-authz` 提供的权限 bundle（否则 503），补 `infra-iam-casdoor`+`infra-authz` 进清单，两者本次也跑裸进程。

**测试方法**：
- [x] 真机走一遍纯本地裸进程流程：手动起五个组件各自需要的依赖（DB/NATS/Casdoor OAuth 复用装配仓库已经在跑的 `be-postgres`/`be-nats`/`be-casdoor` 基础资源），手动喂环境变量（模拟平台会注入的值，临时把这五个组件在 `brickkit.yaml` 里的 `servedBy` 换成 `local: true` 跑一次 `brickkit up --dry-run` 生成 `local-debug.*.env` 拿到清单，记完立刻 `git checkout` 复原 `brickkit.yaml`——这一步只用于读取清单，不通过 `brickkit up` 真的拉起这五个组件），宿主机直接 `go run` 起这五个组件，确认正常响应。⚠️ 注意这条不是 `local:true`（那是"Docker+本地混合"，见 Task 7）——这里验证的是"完全不碰 Docker、纯裸进程"这条路径本身走不走得通，组件本身不通过 `brickkit up` 拉起。
- [x] 走一遍 `get_jwt`（参照 `erp-sales/scripts/seed.sh` 里的实现）：向裸进程 `infra-iam-casdoor` 暴露的 `/api/iam/token` 换真实 app JWT（前提是 be-casdoor 里已有 `dev.superuser` 这个测试账号，没有就先按该组件 `make seed` 的方式补建）。

**组件参与清单**：`go-core` 外壳（收编 5 个组件，`mdm/customer` 这一项人为拆成两条记录）+ `go-infra` 外壳（鉴权面，理由同 Task 4b）。

**代表性沟通测试**：如果两个版本真的都装配成功，分别调用各自的端口，确认互不干扰；如果撞上限制，改成记录编译/启动阶段的具体报错。**实际情况：两个都装配成功，没有撞上任何限制**——走真实 Casdoor OAuth 拿 JWT，分别对 `localhost:8080`（声明 `1.0.9`）和 `localhost:8095`（声明 `1.0.5`）发起 `GET /mdm/customer/customers/211`：两个端口都返回 200 和完全相同的真实客户数据（`id=211`/`code=C000211`/`name="「本地测试」华南电子科技有限公司"`/`credit_limit=500000.00`）。

**结果**（2026-09-17 执行）：

- 之前"强制要求"里预判的"Go 单进程装不下同一 import 路径两个版本"这个限制在这个场景下**没有出现**，原因是这个限制本身的触发条件不成立：那个限制（Phase 4 研究日志 §13 记录的、`gen/<domain>/<name>` 契约包 vendoring 撞车 panic）是"两个不同的 import 路径各自内嵌了同一份 `.proto` 编译产物，各自的 `init()` 都往 Go 进程全局 protobuf 注册表里注册同一个 `.proto` 文件路径"——这里从头到尾只有**一个** import 路径（`github.com/brickKit/mdm-customer`，`go.mod` 只锁了一个版本，Go 物理上也不允许同一 module 在同一构建里出现两个版本），两条记录调用的是**同一份编译好的代码**，只是把它的 `New()` 构造函数多调用了一次——这跟"同一个 HTTP handler 在两个端口上各 `Listen` 一次"没有本质区别，Go 语言层面完全没有理由拒绝。

**结论**：`BRICKKIT_SERVED_MEMBERS_CONFIG` 里对同一个 `componentId` 声明两条不同"版本"的记录，在当前 `buildModules` 实现下**不会报错、也不会被去重**，会真的装配出两个独立监听不同端口的模块实例——但这两个实例背后是同一份 Go 代码、同一个数据库 schema，"版本不同"这个声明**在合并态里同样是纯元数据，不会让外壳真的去装配两份不同的代码**（跟 Task 4b/4c 的结论一致，这里只是换了个更极端的角度重新确认）。这本身也暴露了一个理论上的操作风险：如果有人真的手误在合并清单里把同一个组件写了两条不同端口的记录（哪怕版本号一样），`buildModules` 目前不会拦截，只会老老实实起两个完全等价、共享同一份数据的模块实例——多占两个端口、多一份连接，没有任何实际收益，也没有任何数据隔离上的危险（因为本来就是同一份数据）。这是 `be-assembly-standard`/`shells/go` 自己的实现细节，不是 brickKit 的问题；`BRICKKIT_SERVED_MEMBERS_CONFIG` 本身是否可能被 brickKit 错误地生成出重复 `componentId` 条目，不在这次裸进程构造测试的范围内（brickKit 生成这份数据的源头正确性属于其它 Task 已经验证过的"平台生成阶段"范畴）。

```
❌ 错误：外壳 shell/go-core@0.5.4 上有两个组件都要用端口 8080
   占用方：组件 mdm/customer@1.0.7
   占用方：组件 mdm/customer@1.0.9
   建议：这几个组件最终都跑在同一个外壳容器/Pod 里，端口必须互不相同
```
`error_code: PORT_CONFLICT`，`exit_code: 1`——**这不是原计划担心的"Go 单二进制装不下同一 import 路径两个版本"这个编译期限制（Task 4d 已经确认那个限制在这个项目里根本不会被触发），而是一个更早、更直接的限制：`mdm/customer` 的端口（`8080`）是 `registry/ports.tsv` 按 componentId 分配的固定值，`v1.0.7`/`v1.0.9` 两份 `component.yaml` 里的 `deployment.port` 字段都写死是 `8080`（用 `git show v1.0.7:component.yaml`/`git show v1.0.9:component.yaml` 核对过，两边完全一样，这是设计使然——同一个 componentId 无论哪个版本都应该占用注册表里给它分配的那同一个端口，因为正常情况下一个 componentId 同一时刻只会有一个版本在跑）**。brickKit 在生成阶段（不需要真的 `up`）就正确、清晰地报出这个冲突，没有含糊地让它们中的一个"悄悄不启动"或者留到运行时才崩溃。

**结论**：同一个外壳收编"真实项目里的同一个组件"的两个版本，在当前"端口按 componentId 从注册表固定分配"这个设计下**结构性地不可行**——不是因为 Go 语言限制，而是因为两个版本永远会声明同一个端口，在同一个外壳容器里必然冲突。brickKit 自己的做法是对的：在生成阶段就用一条清楚、指名道姓的 `PORT_CONFLICT` 错误挡住，而不是留到运行时才表现为其中一个模块起不来。**这个限制来自本项目"一个 componentId 一个固定端口"的注册表设计（`registry/ports.tsv`），不是 brickKit 平台的限制**——如果两个版本各自在 `component.yaml` 里声明不同的端口，理论上能绕开（Task 4d 已经用裸进程 + 人为指定不同端口的方式验证过这条路径本身没有 Go 语言层面的障碍），但那样做等于让同一个 componentId 在注册表里对应两个端口，违反了本项目"端口不能自行分配、且与 componentId 一一对应"的既有铁律，属于这个项目自己不会允许的配置，因此这条路径在真实场景下没有继续深挖的必要——生成阶段的 `PORT_CONFLICT` 报错已经是这条任务最终、最诚实的答案。

## Task 9：组件+外壳混搭 × 本地

✅ **"本地"的口径**：跟"Docker+本地混合"是并列的独立一档，不是它的子集——这次任务里**外壳和独立组件全部跑成宿主机裸进程**，不借助 `local:true`（那个机制假设其它组件在 Docker 里跑着，属于 Task 12 的范畴），不碰 Docker。

**组件参与清单**：`go-core` 外壳（裸进程，收编 `mdm-customer`/`mdm-product`/`erp-inventory`/`erp-finance`/`erp-sales`）+ `infra-bff-mobile`（完全独立，裸进程），其余组件不参与——不需要全部 14 个同时跑成裸进程，这里的重点是"合并态+独立态混着跑、且都不碰 Docker"这件事本身。版本上是变体 a / baseline：两者都用最新版本。

⚠️ **计划阶段的修正（跟 Task 1 当时同一个道理）**：原计划只写这两者，执行到"代表性沟通测试"要发一次真实的、带权限校验的 GraphQL 调用时，发现 `infra-bff-mobile` 的 resolver 会先做 `requirePermission` 校验（需要真实可验签的 JWT + 真实权限 bundle），补 `infra-authz`+`infra-iam-casdoor` 两个鉴权面组件进清单，同样跑裸进程——这两者不消耗额外的独立 Postgres 登录角色：早已迁移到 `servedBy` 之后，它们独立部署时代用的 `infra_authz`/`infra_iam_casdoor` 登录角色已经不存在，改用 `shell_go_infra` 这个真实存在、已经是 `infra_authz_rw`/`infra_iam_casdoor_rw` 成员的登录角色（`SET LOCAL ROLE` 机制在独立部署和合并部署下走的是同一条代码路径，见 `be-sdk-go` `tx.go`，不区分形态）。

**测试方法**：
- [x] 临时把 `infra/authz`、`infra/iam-casdoor` 在 `brickkit.yaml` 里的 `servedBy` 换成 `local: true`，`brickkit up --dry-run` 拿它们的 `local-debug.*.env`（多行 `APP_TOKEN_SIGNING_KEY_PEM` 完整无截断，`AUTHZ_BUNDLE_URL`/`IAM_JWKS_URL`/`CASDOOR_BASE_URL` 手工把 Docker 服务名/`host.docker.internal` 换成 `localhost`，同 Task 1 的既有判据），立刻 `git checkout` 复原 `brickkit.yaml`。
- [x] `go-core` 外壳：`go build` 出 `cmd/shell` 的二进制（不用 `go run`，直接拿到真正监听端口的 PID，收尾更干净），手动拼一份完整的 `BRICKKIT_SERVED_MEMBERS_CONFIG`（JSON 数组，5 个成员各自的 `componentId`/`version`/`httpPort`/`extraPorts`/`configEnvVars`，字段值直接从一次干净的 `brickkit up --dry-run` 生成的真实 `docker-compose.yaml` 里原样摘出来，不是凭空拼的）+ 对应的 `MDM_CUSTOMER_PG_SCHEMA`/`ERP_SALES_DEFAULT_WAREHOUSE_ID` 等具体值变量，`DATABASE_HOST=localhost`（不是 `host.docker.internal`）、`DATABASE_USER=shell_go_core`（真实存在的合并部署登录角色，密码取自根 `.env` 的 `SHELL_GO_CORE_PASSWORD`）。**踩了一个纯 bash 坑**：`BRICKKIT_SERVED_MEMBERS_CONFIG` 这个 JSON 值直接写进 `.env` 文件、`source` 读取时，bash 的引号移除机制会把 JSON 内部的双引号字符当成 shell 引号语法吃掉，报 `invalid character 'c' looking for beginning of object key string`——给整个 JSON 值套一层单引号（`KEY='[{"a":"b"}]'`）后 `source` 才能原样保留。

1. **意外发现了一个此前完全没见过的、方向相反的地址解析机制**：由于这次是"普通容器依赖一个 `local:true` 组件"（跟本文档此前全部 `local:true` 场景——local:true 组件自己依赖普通容器——方向正好相反），生成的 `infra-bff-mobile` 容器环境变量里 `MDM_CUSTOMER_ENDPOINT=http://mdm-customer-1-0-7:8080`（不是 `localhost`），同时容器的 `extra_hosts` 自动多了一条 `mdm-customer-1-0-7:host-gateway`——brickKit 生成了一个 Docker 原生的 host-gateway 别名映射，让容器内对 `mdm-customer-1-0-7` 这个别名的解析直接指向宿主机，而不是走容器网络。
2. **真机验证这套反向映射机制真实可靠**：`mdm-customer@1.0.7` 的 `local-debug` 生成的 `DATABASE_HOST`/`MQ_HOST` 已经正确是 `localhost`（`local:true` 组件自己的资源绑定，不受这次反向映射影响）；字面量地址（`AUTHZ_BUNDLE_URL`/`IAM_JWKS_URL`）照例手工处理，`go-infra` 照例手工发布对应端口；`mdm-customer@1.0.7` 用默认端口（`8080`/`9090`，不需要像其它任务那样偏移，因为这次不存在跟另一个容器化实例的端口冲突）裸进程跑起来后，**真实容器 `infra-bff-mobile` 通过 `extra_hosts` 的 host-gateway 映射，真的连上了宿主机上的这个裸进程**，返回真实客户数据；`crm-opportunity`（依赖合并部署的新版本）同样真实成功。

**结论**：Task 12e 通过，且这是整个 05b 矩阵里发现的一个此前完全没有文档记录过的真实机制：**`local:true` 的地址解析不是单向的**——不仅"`local:true` 组件自己依赖普通容器"这个方向有 v0.4.6 的 `localhost` 翻译修复（本文档 Task 8/9/12 baseline 反复验证过），"普通容器依赖一个 `local:true` 组件"这个反方向也有对应的机制（`extra_hosts` 的 Docker 原生 `host-gateway` 别名），两个方向合起来才是"`local:true` 机制在多版本+混搭场景下依然可靠"这句话的完整证据——本项目此前的全部 `local:true` 验证任务，因为构造习惯（总是把要调试的那个组件本身设成 `local:true`），从未真机触发过这个反方向，这次是第一次。
