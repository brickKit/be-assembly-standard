# 阶段五 B · 组合矩阵验证

> **这是唯一一份记录"部署组合怎么测"的文档**：要测什么、为什么这么测、组件参与清单、真机过程、结果、结论，全部写在同一份文档的同一个任务节里，不拆成计划/变体设计/结果这类互相引用的多份文档。准备工作（把装配仓库迁移到真实 `servedBy`）在 `docs/plans/05a-迁移到servedBy.md`，本文档只管正式的组合排列测试，默认 05a 的全部结论已经成立。
>
> **每个 Task 都是独立、完整的一节，不依赖、不引导到别的 Task 去看结果**——包括版本变体：同一个拓扑分组里的四个 Task（比如"纯外壳"的 Task 4/5/6/8）各自有一份完整的版本变体测试，不是"选一个代表性 Task 测完整、其它 Task 只抽样复核"。哪怕两个 Task 测的版本变体在道理上是同一件事，也分别在各自的环境下真机构造、各自记录，因为运行环境本身（裸进程 / Docker / K8s）往往会让"怎么构造这个变体"的具体做法不一样，写清楚这个做法本身就是这个 Task 的产出。

## 动机

现在只有 14 个真实组件，本机资源还绰绰有余；等军火库真的铺到接近 62 个组件时，光是"起一遍全部组件"这件事本身就可能撑不住本机资源，到时候再想补一遍"部署方式到底靠不靠谱"这类基础验证，成本会高得多。趁现在数量还合理，把"组件"和"外壳"两种部署形态、在"本地/Docker/K8s"三种运行环境下、以及两者混搭和多版本共存的全部排列组合，能验的都真机验一遍，每一种组合独立记录过程和结果，**包括那些肯定会出错的组合也要真机构造、记录报错内容和理由，不能因为"预期会失败"就跳过不测**。

能够部署不代表整个项目真的可用——每个任务除了"能不能起来"，都必须至少做一次真实的跨组件调用，确认协作符合预期。

## 参考资料（背景机制，不重复解释）

- `docs/dev/给brickKit的反馈.md` 第七部分——最初的 `servedBy` 提案。

- **调研结论摘要**（设计每个任务时随时回查）：
  1. `servedBy: <组件ID>@<精确版本>`，格式/自引用/链式嵌套/与 `local:true` 互斥共 6 条静态校验 + 目标存在性/运行态 2 条生成期校验 + 端口/端点变量/标签 3 条合并冲突校验，全部有 brickKit 自己的单元测试覆盖。
  2. 环境变量合并**只**覆盖 `*_ENDPOINT` 类，`COMPONENT_ID`/`COMPONENT_VERSION`/`configSchema` 配置值/资源连接变量**无条件排除**，有专门测试断言"即使同名同值也不会被合并"。
  3. `BRICKKIT_SERVED_MEMBERS`——逗号分隔版本化服务名，字典序；**零成员时是显式空字符串，不是变量缺失**。
  4. Docker：外壳的 compose service 挂上每个成员的版本化服务名作网络别名；依赖了某个 `servedBy` 成员的组件，`depends_on` 自动改指向外壳；成员自己不生成 service。K8s：成员生成一个 `selector` 指向外壳 Pod 标签、`targetPort` 用成员自己端口的 Service，不生成 Deployment/Job；NetworkPolicy ingress/egress 自动跟着调整。
  5. ⚠️ **`expose`/`exposePort`/`hostname`/`replicas`/`resources`/`serviceAccountName` 写在 `servedBy` 成员条目上完全不生效**（只有警告）。
  6. **多版本共存**：同一个外壳收编同一组件的两个不同版本——**已确认支持**（`TestResolveGroupsTwoVersionsOfSameComponentUnderOneShell`），唯一约束是端口不能撞；`EnvPrefix` 不带版本号，若两个版本的同名 config 值不同会直接报错（05a Task 0.6 收尾已确认这是合并进同一进程固有的性质，不是缺陷）。同一个 `(id, version)` 不能同时独立部署又被 `servedBy`。**两个不同外壳各自收编同一组件的不同版本**——brickKit 自己完全没有测试或文档覆盖，是真正的未知领域。
  7. `local: true` 的字段语义、K8s 下的拒绝逻辑，`servedBy` 落地前后完全没变。

### 每个任务/变体的强制要求（不满足不算做完）

1. **组件参与清单**：明确写出用了真实 14 个组件里的哪些、各自什么版本、排除了哪些、为什么排除。执行完之后要把"上一个 tag"这类相对说法替换成真实用到的确切版本号（比如 `1.0.9` → `1.0.8`），相对说法只允许出现在执行前的计划阶段。
2. **代表性沟通测试**：不能只验证"能不能部署起来"，必须至少发起一次真实跨组件调用确认协作符合预期，不用覆盖所有链路，1-2 条有代表性的就够。如果这条任务本身预期就是失败（负向验证），写清楚"不适用，本任务测的是失败本身"。
3. **结果直接写在本节的"结果"/"结论"里**，缺哪一项要写清楚"为什么没有"，不能悄悄空着。执行前先填好"组件参与清单"和"测试方法"，执行后立刻补"结果"和"结论"，不攒到最后一起写。不管结果是成功还是失败/报错/行为不符合预期，都要如实记录具体现象（报错文案、日志片段、实际观察到的行为），不能只写"通过"/"符合预期"这种无法复核的结论。
4. **禁止用"同 Task X"代替具体场景描述**：哪怕两个 Task 的构造在道理上完全一样，也要在本节内把"组件参与清单"和"测试方法"完整重写一遍，不能只写"同 Task 5b 的场景"就结束——未来审批只会直接跳到某个矩阵格子看，不会顺着文档去翻别的 Task。允许的例外是纯粹的背景说明/对比（比如"这条在 Docker 侧已验证过，这里独立复现"），前提是即使不看那句话，本节自己的步骤和结论也完整、可执行、可理解。
5. **结果里要写明真机执行的日期**，配合第 1 条的确切版本号一起构成"这次验证是在什么状态下做的"的快照，供以后组件铺到更多数量时，回头比对同一个矩阵格子"当时 vs 现在"具体发生了什么变化。
6. **鉴权面组件是任何真实业务调用绕不开的前提，必须补进组件参与清单**：Task 1 真机执行前读 `be-sdk-go` 的 `authz.go` 确认——组件启动不会因为连不上 `infra-iam-casdoor`/`infra-authz` 而失败（不阻断启动是设计好的行为），但只要"代表性沟通测试"要发起一次真的带权限键的业务调用（而不是只测端口通不通），就必须有：① 真实、能被本地 JWKS 验签通过的 JWT（需要真的走一遍 Casdoor OAuth 登录 + `infra-iam-casdoor` 拿 `id_token` 换 app token 的完整链路，各组件 `scripts/seed.sh` 的 `get_jwt()` 函数就是这么做的）；② `infra-authz` 真的可达并成功轮询过一次 `/authz/bundle`，否则具体权限键判定直接 503。因此**每个 Task 只要"代表性沟通测试"需要真实业务调用，`infra-iam-casdoor` + `infra-authz` 就要按这个 Task 当前的拓扑/环境形态一起补进"组件参与清单"**（本地裸进程任务里这两个也裸进程跑；Docker 任务里这两个也是 Docker 容器；纯外壳任务里这两个也在对应外壳里，等等），不能因为"这次测的主题不是鉴权"就默认忽略——这两个本身也是 14 个真实组件之一，不是可以当基础设施忽略不计的东西。

### 环境定义

**"纯外壳"（Task 4/5/6/8）的组件参与清单，跟"混搭"（Task 9-12）不一样，两者不是同一份拓扑测两遍**：`frontend-standard` 没有后端进程（纯前端 SPA/H5，压根不存在可以被合并的东西）、`infra-bff-mobile` 按设计明确保持独立——这两个组件结构性地永远不可能被 `servedBy`。所以：
- **纯外壳（Task 4/5/6/8）用缩减清单**：只含 11 个 Go 组件 + `infra-print`，**全部** `servedBy` 收编进各自外壳，`frontend-standard`/`infra-bff-mobile` 这次测试**不参与**（临时从 `brickkit.yaml` 里去掉，或者 `enabled: false`）。这样测出来的才是真正"零独立组件、100% 合并"的场景。
- **混搭（Task 9-12）用真实全量清单**：真实 14 个组件——12 个 `servedBy` 收编 + `frontend-standard`/`infra-bff-mobile` 独立，这本来就是本项目当前唯一的真实部署形态。

这样 Task 5 和 Task 10 就不是测同一份拓扑——一个是"能不能做到 100% 纯合并"，一个是"我们真实项目现在长什么样"，两者都有独立价值。

**"Docker+本地混合"的准确定义**：绝大部分组件走 Docker（不管是独立部署还是被某个外壳收编），额外挑 1 个**完全独立**的组件（不受 `servedBy` 影响）用 `local: true` 拉到宿主机调试——这是唯一一种 `local:true` 和"这次测的拓扑"会同时出现在同一份 `brickkit.yaml` 里的组合，brickKit 自己的回归测试（`TestLocalStillWorksAlongsideServedBy`）已经确认两者不冲突，这里在自己的真实组件上复核一遍。

**"纯本地"（Task 1/4/9）的准确定义，区别于"Docker+本地混合"**："本地"是跟"Docker+本地混合"并列的独立一档，不是它的子集——"纯本地"任务里**全部参与组件都跑成宿主机裸进程**（`go run`/`uvicorn` 之类，手动喂环境变量模拟平台注入），不借助 `local:true` 机制（那个机制的前提就是"其它组件在 Docker 里跑着"，属于"Docker+本地混合"那一档）。

## Task 1：纯独立组件 × 本地

**组件参与清单**：`erp-sales`（依赖方）+ `mdm-customer` + `mdm-product`（业务被依赖方）+ `infra-iam-casdoor` + `infra-authz`（鉴权面，代表性沟通测试要发真实业务调用绕不开的前提），其余不参与（验证的是"单个组件本地调试"这个机制本身，不需要全量组件陪跑）。五者都用 `brickkit.yaml` 当前锁定的最新版本（变体 a / baseline）。⚠️ **计划阶段的两次修正**：① 原计划只写 `erp-sales`+`mdm-customer` 两个组件，执行前读 `backend/internal/tcc/create.go` 发现 `CreateOrder`（哪怕是最简单的建草稿单）内部同时调用 `fetchActiveCustomer`（`mdm-customer`）和 `fetchActiveProducts`（`mdm-product`，用于按分类取价），不存在"只连 `mdm-customer` 就能完成一次有业务意义调用"的路径，补 `mdm-product` 进清单；② 执行前读 `be-sdk-go` 的 `authz.go` 确认，任何带权限键的真实业务调用都需要真实可验签的 JWT（走 Casdoor OAuth 登录 + `infra-iam-casdoor` 换 app token）和 `infra-authz` 提供的权限 bundle（否则 503），补 `infra-iam-casdoor`+`infra-authz` 进清单，两者本次也跑裸进程。

**测试方法**：
- [x] 真机走一遍纯本地裸进程流程：手动起五个组件各自需要的依赖（DB/NATS/Casdoor OAuth 复用装配仓库已经在跑的 `be-postgres`/`be-nats`/`be-casdoor` 基础资源），手动喂环境变量（模拟平台会注入的值，临时把这五个组件在 `brickkit.yaml` 里的 `servedBy` 换成 `local: true` 跑一次 `brickkit up --dry-run` 生成 `local-debug.*.env` 拿到清单，记完立刻 `git checkout` 复原 `brickkit.yaml`——这一步只用于读取清单，不通过 `brickkit up` 真的拉起这五个组件），宿主机直接 `go run` 起这五个组件，确认正常响应。⚠️ 注意这条不是 `local:true`（那是"Docker+本地混合"，见 Task 7）——这里验证的是"完全不碰 Docker、纯裸进程"这条路径本身走不走得通，组件本身不通过 `brickkit up` 拉起。
- [x] 走一遍 `get_jwt`（参照 `erp-sales/scripts/seed.sh` 里的实现）：向裸进程 `infra-iam-casdoor` 暴露的 `/api/iam/token` 换真实 app JWT（前提是 be-casdoor 里已有 `dev.superuser` 这个测试账号，没有就先按该组件 `make seed` 的方式补建）。

**组件参与清单**：`go-core` 外壳（收编 5 个组件，`mdm/customer` 这一项人为拆成两条记录）+ `go-infra` 外壳（鉴权面，理由同 Task 4b）。

**结果**（2026-09-17 执行）：

- 之前"强制要求"里预判的"Go 单进程装不下同一 import 路径两个版本"这个限制在这个场景下**没有出现**，原因是这个限制本身的触发条件不成立：那个限制（Phase 4 研究日志 §13 记录的、`gen/<domain>/<name>` 契约包 vendoring 撞车 panic）是"两个不同的 import 路径各自内嵌了同一份 `.proto` 编译产物，各自的 `init()` 都往 Go 进程全局 protobuf 注册表里注册同一个 `.proto` 文件路径"——这里从头到尾只有**一个** import 路径（`github.com/brickKit/mdm-customer`，`go.mod` 只锁了一个版本，Go 物理上也不允许同一 module 在同一构建里出现两个版本），两条记录调用的是**同一份编译好的代码**，只是把它的 `New()` 构造函数多调用了一次——这跟"同一个 HTTP handler 在两个端口上各 `Listen` 一次"没有本质区别，Go 语言层面完全没有理由拒绝。

**结论**：`BRICKKIT_SERVED_MEMBERS_CONFIG` 里对同一个 `componentId` 声明两条不同"版本"的记录，在当前 `buildModules` 实现下**不会报错、也不会被去重**，会真的装配出两个独立监听不同端口的模块实例——但这两个实例背后是同一份 Go 代码、同一个数据库 schema，"版本不同"这个声明**在合并态里同样是纯元数据，不会让外壳真的去装配两份不同的代码**（跟 Task 4b/4c 的结论一致，这里只是换了个更极端的角度重新确认）。这本身也暴露了一个理论上的操作风险：如果有人真的手误在合并清单里把同一个组件写了两条不同端口的记录（哪怕版本号一样），`buildModules` 目前不会拦截，只会老老实实起两个完全等价、共享同一份数据的模块实例——多占两个端口、多一份连接，没有任何实际收益，也没有任何数据隔离上的危险（因为本来就是同一份数据）。这是 `be-assembly-standard`/`shells/go` 自己的实现细节，不是 brickKit 的问题；`BRICKKIT_SERVED_MEMBERS_CONFIG` 本身是否可能被 brickKit 错误地生成出重复 `componentId` 条目，不在这次裸进程构造测试的范围内（brickKit 生成这份数据的源头正确性属于其它 Task 已经验证过的"平台生成阶段"范畴）。

### Task 4e：两个不同外壳各自收编同一组件的不同版本

**组件参与清单**：`go-core` 外壳（真实收编的 5 个组件）+ `go-infra` 外壳（鉴权面，理由同 Task 4b）+ 一个人为构造出来、伪装成 `go-backoffice` 的第三个裸进程（`SHELL_NAME=go-backoffice`，真实 `go-backoffice` 在这个项目里只收编 `crm/opportunity` 一个组件，这里人为让它额外收编一份 `mdm/customer`，声明版本与 `go-core` 那份不同——这个拓扑在真实 `brickkit.yaml` 里不存在，纯粹是为了验证"两个外壳同时收编同一个组件"这个理论场景本身）。三者同时跑在宿主机上，各自不同端口。

**测试方法**：
- [x] `go-core`/`go-infra` 复用 Task 4 baseline 的 `go-core.env`/`go-infra.env`（`mdm/customer` 声明版本 `1.0.9`，端口 8080）。伪装的 `go-backoffice` 进程从 `.brickkit/generated/docker-compose.yaml` 里 `shell-go-backoffice-0-5-4` 服务的真实环境变量摘出模板（`SHELL_NAME=go-backoffice`、`SHELL_HEALTH_PORT=8116`、`COMPONENT_ID=shell/go-backoffice`），把其中原本装 `crm/opportunity` 的那条 `BRICKKIT_SERVED_MEMBERS_CONFIG` 记录换成 `mdm/customer`，人为声明版本 `1.0.3`（区别于 `go-core` 那份的 `1.0.9`），端口改成 `8280`/`9280`（避免和 `go-core` 的 `8080`/`9090`冲突）。三个 `nohup ./shell-build &` 同时启动。

**代表性沟通测试**：分别调用两个外壳进程各自收编的 `mdm-customer` 端点，确认返回的行为对应各自声明的版本，互不覆盖。

**结果**（2026-09-17 执行，比原计划多发现一层）：
- **第一次尝试：用 `go-backoffice` 真实的登录角色 `shell_go_backoffice` 起进程，直接在启动阶段失败**——日志：`外壳异常退出：模块 mdm/customer 迁移失败: 迁移初始化失败: failed to open database: no schema`。这是一个真实、正确、符合设计的结果：`shell_go_backoffice` 这个 PG 登录角色是 `be-ops` 按 `brickkit.yaml` 里**真实的** servedBy 声明（`go-backoffice` 只收编 `crm/opportunity`）配出来的，从未被授予过访问 `mdm_customer` schema 的权限，所以这个角色物理上看不见这个 schema——`shell.Run` 的"铁律五"（迁移失败即中止启动，不跳过继续）在这个人为构造的错误拓扑下正确地拦住了它，没有以任何隐蔽的方式"半正常"启动。这本身就是一个值得记录的边界确认，独立于下面继续验证"两个外壳同时收编同一组件"这个理论问题的部分。
- **为了继续验证原计划要问的问题**（"两个外壳独立收编同一组件、声明不同版本，会不会互相干扰"），第二次故意把伪装的 `go-backoffice` 进程的 `DATABASE_USER`/`DATABASE_PASSWORD` 换成 `shell_go_core` 的（绕开上面确认过的、这次测试本来就不关心的 schema 授权边界，只为了让 `mdm/customer` 模块能在这个人为拓扑下真的跑起来）——这次三个进程都成功启动：`go-core`（8090）、`go-infra`（8224）、伪装的 `go-backoffice`（8116）健康检查全部 200；`mdm/customer` 在 `go-core` 里的端口（8080）和在伪装 `go-backoffice` 里的端口（8280）也都 200。
- 走真实 Casdoor OAuth 拿 JWT，对两个端口分别发起 `GET /mdm/customer/customers/211`：两边都返回 200 和完全相同的真实客户数据——因为两边用的是同一个 `shell_go_core` 角色、同一个 `mdm_customer` schema，这在数据层面从来就不是两份独立的数据，跟 Task 4d 的结论一致（"版本"只是声明，不产生真正独立的两份状态）。
- **进程独立性验证**：`kill` 掉伪装的 `go-backoffice` 进程后，立即确认它的端口（8280）连接被拒绝，同时 `go-core`（8080/8090）和 `go-infra`（8224）三个健康检查**全部继续正常返回 200，完全不受影响**——两个进程之间除了共享同一个 Postgres 实例/NATS 连接（这本来就是"合并只在部署层发生"这条铁律允许的共享基础设施，不是外壳间的耦合）之外，没有任何进程级或网络级的相互依赖，一个的生死不影响另一个。

**结论**：两个不同外壳（哪怕是本项目真实拓扑里从不会发生的组合）各自声明收编同一个组件、各自声明不同版本，在裸进程场景下**完全可以同时跑起来，互不冲突，各自独立监听、独立生死**——前提是各自的 PG 登录角色真的被授予了访问那个组件 schema 的权限；如果没有（比如这次第一次尝试用的真实 `shell_go_backoffice` 角色），会在启动阶段迁移这一步就被正确拦下来，不会造成任何"看似启动成功、实际权限不完整"的隐蔽状态。"声明的版本不同"这件事本身，跟 Task 4b/4c/4d 已经确认的结论完全一致——**在当前实现里，从头到尾都只是字符串标签，不影响装配哪份代码、不产生数据隔离**，哪怕分布在两个不同的外壳进程里也是一样。真正提供隔离的，是 PG 层面"谁被授予了访问哪个 schema 的权限"这一道边界，不是 `BRICKKIT_SERVED_MEMBERS_CONFIG` 里的任何字段。这个具体拓扑（同一组件被两个外壳同时收编）在真实 `brickkit.yaml`/brickKit 平台生成逻辑里本来就不可能出现（`servedBy` 是一对一声明），所以这里验证的是"如果有人手误在合并清单数据层面构造出这种情况，会发生什么"这个纯理论边界，不是一个真实会被触发的部署场景。

## Task 5：纯外壳 × Docker（`servedBy` 落地后的核心场景）

**组件参与清单**：11 个 Go 组件（`mdm/customer`、`mdm/product`、`erp/inventory`、`erp/finance`、`erp/sales`、`infra/authz`、`infra/iam-casdoor`、`infra/notification`、`infra/workflow`、`integration/im-dingtalk`、`crm/opportunity`）+ `infra/print`，**全部** `servedBy` 收编进 `shell/go-core`、`shell/go-infra`、`shell/go-backoffice`、`shell/py-render` 这 4 个外壳；`frontend/standard`/`infra/bff-mobile` 临时从 `brickkit.yaml` 摘掉（`enabled: false`）——这次测的是"零独立组件、100% 合并"这个此前从未真正验证过的极端场景，不是平时跑着的那份真实 `brickkit.yaml`（那份留给 Task 10 测）。版本上是变体 a / baseline：4 个外壳镜像（`0.5.4`）和全部 12 个成员的 `servedBy` 版本声明都是"本轮验证的真实 14 个组件"表格里当前锁定的版本。

**计划阶段的修正（真机踩出来的，写在最前面，因为它决定了下面整个操作方式）**：原计划以为只要给 `infra/bff-mobile`/`frontend/standard` 写 `enabled: false` 就能得到"12 个成员、4 个外壳、零独立组件"这个拓扑。真机第一次这么做后，`go-core` 只剩 2 个成员（`mdm/customer`、`mdm/product`），`erp/inventory`、`erp/finance`、`erp/sales` 全部消失；`go-infra` 少了 `infra/workflow`。逐层排查（见下方"结果"第一条）后确认：这是 brickKit 级联启停机制（`cascade` 包，见 `docs/dev/` 之外，brickKit 自己仓库的 `internal/cascade/cascade.go`）按设计工作的真实结果，不是 bug——`infra/bff-mobile` 弱依赖 `mdm/customer`、`mdm/product`、`erp/sales`、`erp/inventory`、`infra/workflow` 这 5 个组件，而 `erp/sales`/`infra/workflow` 在这份 `brickkit.yaml` 里**唯一的依赖方就是 `infra/bff-mobile`**——关掉 `infra/bff-mobile` 后，级联规则"没写 `enabled`、有上层、上层全灭 → 它也灭"精确地把 `erp/sales`、`infra/workflow` 也算成了"不该跑"，而 `erp/inventory`、`erp/finance` 又是 `erp/sales` 的下游，跟着二次级联消失。`mdm/customer`/`mdm/product` 之所以幸存，是因为它们还有另一个真实依赖方 `crm/opportunity`（`crm/opportunity` 一直保持启用）。修正做法：给 `erp/sales`、`erp/inventory`、`erp/finance`、`infra/workflow` 这 4 个组件显式写 `enabled: true`（"钉住"，短路掉"跟着上层走"这条默认规则），再配合 `infra/bff-mobile`/`frontend/standard` 的 `enabled: false`，`brickkit up --dry-run` 验证后确认 4 外壳/12 成员/零独立容器的目标拓扑正确生成，这才继续做后面的测试。

**测试方法**：

**结果**（2026-09-17 执行）：

`error_code: PORT_CONFLICT`，`exit_code: 1`——**这不是原计划担心的"Go 单二进制装不下同一 import 路径两个版本"这个编译期限制（Task 4d 已经确认那个限制在这个项目里根本不会被触发），而是一个更早、更直接的限制：`mdm/customer` 的端口（`8080`）是 `registry/ports.tsv` 按 componentId 分配的固定值，`v1.0.7`/`v1.0.9` 两份 `component.yaml` 里的 `deployment.port` 字段都写死是 `8080`（用 `git show v1.0.7:component.yaml`/`git show v1.0.9:component.yaml` 核对过，两边完全一样，这是设计使然——同一个 componentId 无论哪个版本都应该占用注册表里给它分配的那同一个端口，因为正常情况下一个 componentId 同一时刻只会有一个版本在跑）**。brickKit 在生成阶段（不需要真的 `up`）就正确、清晰地报出这个冲突，没有含糊地让它们中的一个"悄悄不启动"或者留到运行时才崩溃。

**结果**（2026-09-17 执行）：

1. **发现一个真实、根因明确的 brickKit bug：`local:true` 组件依赖 `servedBy` 成员时，生成的本地调试地址完全连不通**。生成的 `local-debug.infra-bff-mobile-1-0-19.env` 里：`MDM_CUSTOMER_GRPC_ENDPOINT=http://localhost:9090`——语法/格式完全正常，**但 `docker port <go-core 容器>` 返回空，`nc -zv localhost 9090` 直接 `connection refused`**，宿主机上根本没有任何进程监听这个端口。同一份文件里 `MDM_CUSTOMER_ENDPOINT=http://mdm-customer-1-0-9:8080`（主端口）保留的是容器内部服务名形式，同样连不通，但至少没有伪装成本地地址。
2. **读 brickKit 源码定位到精确根因**：`internal/compose/local.go` 的 `pointDependenciesAtLocalhost` 函数里，额外端口（gRPC 端口）的处理逻辑是"在 `p.debugExtraPort[service]` 里查不到映射，就直接回退成 `port = extra.Port`（组件自己声明的端口号）"——这段代码自己的注释写着"只剩一种情况：依赖自己也是 local"，但漏掉了第三种真实存在的情况：**依赖是一个 `servedBy` 成员**（没有自己的 compose service block，`mapDependencyToHost` 函数因为 `!p.rendered[service]` 在开头就直接 `return` 了，从未真的映射任何端口）。这种情况下代码错误地套用了"依赖是 local"这条回退逻辑，拼出一个看起来完全合理、实际上没有任何依据的 `localhost:9090`。主端口那条路径（`hostAccessPort`）没有这个假阳性问题——查不到映射就干脆不改这个变量，保留"看似不像本地地址、至少不会骗人"的原始形式，两条路径对"查不到"的处理不一致，是这个 bug 的直接成因。**已经写成完整的反馈文档**：`docs/dev/brickKit反馈-local组件依赖servedBy成员时本地调试地址错误.md`，包含最小复现、根因、精确到函数和行号的源码引用、修复方向建议。
3. **为了完成这条任务本身的代表性测试，手工在 brickKit 生成产物之上打了一个临时补丁**：直接编辑 `.brickkit/generated/docker-compose.yaml`，给 `shell-go-core-0-5-4`/`shell-go-infra-0-5-4` 两个服务块各自加了几行 `ports:` 映射（`go-core` 的 `9090`/`8080`，`go-infra` 的 `8223`/`8200`），用 `docker compose --env-file .env -p brickkit-be-assembly-standard -f .brickkit/generated/docker-compose.yaml up -d <service>` 局部重建这两个容器（第一次没加 `--env-file .env` 直接报 `APP_TOKEN_SIGNING_KEY_PEM`/`CASDOOR_ADMIN_PASSWORD` 等一串"变量未设置，回退成空字符串"的警告，容器进 `Restarting` 崩溃循环，补上 `--env-file .env` 后正常）——这是明确的、一次性的、测完就撤销的手工修补，不是这次验证的"最终部署"本身（最终部署仍然是 `brickkit up` 生成 + 启动的 4 个外壳），只是为了绕开上面这条已确认的 bug，不代表放弃"用 brickkit 部署"这条原则。
4. **`infra-bff-mobile` 本地进程用 `docker run --network host`（本机没有装 Node.js，用已有的 `brickenterprise/infra-bff-mobile:1.0.19` 镜像 + `--network host` 模拟真正的宿主机裸进程——网络命名空间跟宿主机共享，`localhost` 解析行为与真实裸进程完全一致，只是省去装 Node 工具链）跑起来，`/healthz` 200**。手工把生成的本地调试 env 文件里的 `AUTHZ_BUNDLE_URL`/`IAM_JWKS_URL`（手写字面量，Task 1b 已经确认过的既有限制，不是新发现）和 `MDM_CUSTOMER_ENDPOINT` 换成 `localhost` 对应端口，过程中还顺手修了一个自己踩的小坑（`OTEL_BASE_URL=''` 这种给 bash `source` 用的引号写法，`docker run --env-file` 不做 shell 风格的引号剥离，会把两个单引号字符原样当值传进去，导致 OTel SDK 解析 URL 失败直接崩溃退出——去掉引号后正常）。
5. **原计划的 GraphQL 端到端测试撞上了一个此前已知、跟这次改动无关的项目自身缺口**：`POST /graphql` 直接报 `{"errors":[{"message":"PersistedQueryOnly", ...}]}`——`infra-bff-mobile` 的 Persisted Operations 清单（`contracts/persisted-operations.json`）目前是空对象 `{}`，这是 Task 2 已经记录过的已知缺口（`frontend-standard` 还没有真实构建产出这份清单，空清单是刻意的 fail-closed 默认值，不是这次改动引入的新问题）。**改用直接对着 `localhost:9090` 发起真实 gRPC 调用**（`grpcurl -plaintext -proto contracts/mdm/customer/v1/customer.proto ... localhost:9090 mdm.customer.v1.CustomerService/BatchGet`，这正是 `infra-bff-mobile` 的 GraphQL resolver 内部会调用的同一个方法，只是绕开被持久化查询限制卡住的 HTTP 层，直接验证地址本身），返回真实客户数据（`id=211`/`code=C000211`/`name="「本地测试」华南电子科技有限公司"`）——先用 `~/go/bin/grpcurl -plaintext localhost:9090 list` 得到 `server does not support the reflection API`（这本身就是有效证据：一个真正无人监听的端口应该是 `connection refused`，收到这个应用层响应说明 TCP 握手和 gRPC 协议层都成功了），再用真实 proto 定义发起 `BatchGet` 调用拿到完整数据，双重确认了打了临时端口补丁之后这条链路端到端可用。
6. **收尾**：`docker rm -f` 掉临时的 `bff-mobile-local-test` 容器，`brickkit down` 停掉全部 4 个外壳容器（连带清除了手工加的临时端口映射，因为下次 `brickkit up` 会用干净的生成产物重新渲染），`git checkout -- brickkit.yaml` 复原。

**结论**：Task 8 的拓扑本身（4 外壳 servedBy + 1 个完全独立组件 `local:true`）能够共存、互不干扰，这一点确认成立，`servedBy` 那条路径全程没有被 `local:true` 的额外调试进程影响。但这次真机验证的分量主要不在"拓扑能不能共存"上，而在于**意外发现并完整根因定位了一个 brickKit 平台级 bug**：`local:true` 组件依赖任何一个 `servedBy` 成员时，生成的本地调试环境变量当前完全不可用（额外端口给出一个看似合理实则错误的地址，静默失败；主端口保留容器内部地址，同样连不通）。这是"外壳合并部署"成为平台默认推荐形态之后，`local:true` 这个最常用的开发调试手段**必然会越来越频繁撞上**的一个真实缺口，已经写成完整反馈文档（含精确到函数/行号的根因）交给 brickKit；这次任务本身的代表性测试靠手工临时补丁绕过完成，不代表问题已经解决。
