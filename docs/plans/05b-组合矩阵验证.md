# 阶段五 B · 组合矩阵验证

> **这是唯一一份记录"部署组合怎么测"的文档**：要测什么、为什么这么测、组件参与清单、真机过程、结果、结论，全部写在同一份文档的同一个任务节里，不拆成计划/变体设计/结果这类互相引用的多份文档。准备工作（把装配仓库迁移到真实 `servedBy`）在 `docs/plans/05a-迁移到servedBy.md`，本文档只管正式的组合排列测试，默认 05a 的全部结论已经成立。
>
> **每个 Task 都是独立、完整的一节，不依赖、不引导到别的 Task 去看结果**——包括版本变体：同一个拓扑分组里的四个 Task（比如"纯外壳"的 Task 4/5/6/8）各自有一份完整的版本变体测试，不是"选一个代表性 Task 测完整、其它 Task 只抽样复核"。哪怕两个 Task 测的版本变体在道理上是同一件事，也分别在各自的环境下真机构造、各自记录，因为运行环境本身（裸进程 / Docker / K8s）往往会让"怎么构造这个变体"的具体做法不一样，写清楚这个做法本身就是这个 Task 的产出。

## 动机

现在只有 14 个真实组件，本机资源还绰绰有余；等军火库真的铺到接近 62 个组件时，光是"起一遍全部组件"这件事本身就可能撑不住本机资源，到时候再想补一遍"部署方式到底靠不靠谱"这类基础验证，成本会高得多。趁现在数量还合理，把"组件"和"外壳"两种部署形态、在"本地/Docker/K8s"三种运行环境下、以及两者混搭和多版本共存的全部排列组合，能验的都真机验一遍，每一种组合独立记录过程和结果，**包括那些肯定会出错的组合也要真机构造、记录报错内容和理由，不能因为"预期会失败"就跳过不测**。

能够部署不代表整个项目真的可用——每个任务除了"能不能起来"，都必须至少做一次真实的跨组件调用，确认协作符合预期。

## 参考资料（背景机制，不重复解释）

- `docs/dev/给brickKit的反馈.md` 第七部分——最初的 `servedBy` 提案。
- brickKit 仓库 `docs/zh/patterns/shell-implementers-guide.md`（造壳指南）+ `docs/zh/patterns/servedby-deployment-checklist.md`（部署方检查清单）——`servedBy` 的权威使用文档。
- brickKit 仓库 `AGENTS.zh.md` §5.7、§9.21——平台侧对这个功能的正式说明与边界论证。
- **调研结论摘要**（设计每个任务时随时回查）：
  1. `servedBy: <组件ID>@<精确版本>`，格式/自引用/链式嵌套/与 `local:true` 互斥共 6 条静态校验 + 目标存在性/运行态 2 条生成期校验 + 端口/端点变量/标签 3 条合并冲突校验，全部有 brickKit 自己的单元测试覆盖。
  2. 环境变量合并**只**覆盖 `*_ENDPOINT` 类，`COMPONENT_ID`/`COMPONENT_VERSION`/`configSchema` 配置值/资源连接变量**无条件排除**，有专门测试断言"即使同名同值也不会被合并"。
  3. `BRICKKIT_SERVED_MEMBERS`——逗号分隔版本化服务名，字典序；**零成员时是显式空字符串，不是变量缺失**。
  4. Docker：外壳的 compose service 挂上每个成员的版本化服务名作网络别名；依赖了某个 `servedBy` 成员的组件，`depends_on` 自动改指向外壳；成员自己不生成 service。K8s：成员生成一个 `selector` 指向外壳 Pod 标签、`targetPort` 用成员自己端口的 Service，不生成 Deployment/Job；NetworkPolicy ingress/egress 自动跟着调整。
  5. ⚠️ **`expose`/`exposePort`/`hostname`/`replicas`/`resources`/`serviceAccountName` 写在 `servedBy` 成员条目上完全不生效**（只有警告）。
  6. **多版本共存**：同一个外壳收编同一组件的两个不同版本——**已确认支持**（`TestResolveGroupsTwoVersionsOfSameComponentUnderOneShell`），唯一约束是端口不能撞；`EnvPrefix` 不带版本号，若两个版本的同名 config 值不同会直接报错（05a Task 0.6 收尾已确认这是合并进同一进程固有的性质，不是缺陷）。同一个 `(id, version)` 不能同时独立部署又被 `servedBy`。**两个不同外壳各自收编同一组件的不同版本**——brickKit 自己完全没有测试或文档覆盖，是真正的未知领域。
  7. `local: true` 的字段语义、K8s 下的拒绝逻辑，`servedBy` 落地前后完全没变。

### 环境定义

**"纯外壳"（Task 4/5/6/8）的组件参与清单，跟"混搭"（Task 9-12）不一样，两者不是同一份拓扑测两遍**：`frontend-standard` 没有后端进程（纯前端 SPA/H5，压根不存在可以被合并的东西）、`infra-bff-mobile` 按设计明确保持独立——这两个组件结构性地永远不可能被 `servedBy`。所以：
- **纯外壳（Task 4/5/6/8）用缩减清单**：只含 11 个 Go 组件 + `infra-print`，**全部** `servedBy` 收编进各自外壳，`frontend-standard`/`infra-bff-mobile` 这次测试**不参与**（临时从 `brickkit.yaml` 里去掉，或者 `enabled: false`）。这样测出来的才是真正"零独立组件、100% 合并"的场景。
- **混搭（Task 9-12）用真实全量清单**：真实 14 个组件——12 个 `servedBy` 收编 + `frontend-standard`/`infra-bff-mobile` 独立，这本来就是本项目当前唯一的真实部署形态。

这样 Task 5 和 Task 10 就不是测同一份拓扑——一个是"能不能做到 100% 纯合并"，一个是"我们真实项目现在长什么样"，两者都有独立价值。

**"Docker+本地混合"的准确定义**：绝大部分组件走 Docker（不管是独立部署还是被某个外壳收编），额外挑 1 个**完全独立**的组件（不受 `servedBy` 影响）用 `local: true` 拉到宿主机调试——这是唯一一种 `local:true` 和"这次测的拓扑"会同时出现在同一份 `brickkit.yaml` 里的组合，brickKit 自己的回归测试（`TestLocalStillWorksAlongsideServedBy`）已经确认两者不冲突，这里在自己的真实组件上复核一遍。

**"纯本地"（Task 1/4/9）的准确定义，区别于"Docker+本地混合"**："本地"是跟"Docker+本地混合"并列的独立一档，不是它的子集——"纯本地"任务里**全部参与组件都跑成宿主机裸进程**（`go run`/`uvicorn` 之类，手动喂环境变量模拟平台注入），不借助 `local:true` 机制（那个机制的前提就是"其它组件在 Docker 里跑着"，属于"Docker+本地混合"那一档）。
