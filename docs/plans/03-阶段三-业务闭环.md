**这一阶段做什么：** 对应设计书 §9.6.1 的**档 2**。加 9 个组件（`infra-iam-casdoor`、`infra-authz`、`infra-workflow`、
`infra-notification`、`integration-im-dingtalk`、`infra-print`、`infra-bff-mobile`、`frontend-standard`、`crm-opportunity`），
凑成设计书 §5.13「切片」列（= 附录 H 打勾）的 **14 个**。同时引入两种新语言，`be-sdk-python`、`be-sdk-ts` 要先建起来。

**这一档目标不只是"业务链能跑通"，还有一件同等重要的事：权限判定要从阶段二的 fail-closed stub 换成真实的
`infra-authz`。** 阶段二五个组件的接口全标 `Public` 是刻意的临时状态（阶段二计划 Task 1 原文），本阶段要回去换成
真实权限键——否则"业务闭环"跑通的其实是一条权限全放行的闭环，验不到设计书第 14 章的任何承诺。

**要跑通的链路**（设计书附录 E，本阶段在其基础上延伸）：

```
CRM 赢单 → 建单 → 锁库存 → 生成应收 → 审批 → 钉钉通知 → 打印送货单 PDF
```

⚠️ **`infra-print` 选 Python、`infra-bff-mobile`/`frontend-standard` 选 TS，理由不是业务，是阶段四要靠它们验
Python 外壳与"跨语言合不进外壳"这两件事**（设计书 §9.6.1）。业务功能仍然只做到"能把这条链压出来"为止，
不追求完整——不做多级审批、不做通知模板管理界面、不做打印模板设计器。

**出档条件：** 附录 E 延伸链路真机跑通一遍 + Saga 补偿与超时查询各走一遍 + DLQ 进出各一遍 + 阶段二五个组件的
权限判定从 stub 切到真实 bundle、真机验证过 403/200 两条路径都对。

## 九个组件 + 两个 SDK 的顺序，和为什么是这个顺序

设计书 §4.2 同步图里，本阶段新增组件的出边是这样的：

```
infra-iam-casdoor  → （无出边，日常认证走浏览器直连官方镜像，见 §6.1）
infra-authz        → （无出边，被拉取 bundle 不算依赖边，见 §14.1.4）
infra-workflow     → （无出边，铁律：严禁反向同步调用业务组件）
infra-notification → （无出边，铁律：只发不查）
infra-print        → （无出边，纯渲染引擎）
infra-bff-mobile   → 调用后端组件的 batchGet（读，非侵入业务边界）
frontend-standard  → 只认网关，不进同步图
crm-opportunity    → mdm-customer, mdm-product
```

**七块零出边或近零出边，一块（`crm-opportunity`）有真实强依赖。** 顺序原则与阶段二相同：先把地基类的立起来，
最后用有依赖边的那一块把全链路串起来。但本阶段比阶段二多一层——**权限判定本身是这一档的地基**，所以顺序上
还要满足"`infra-authz` 必须早于阶段二五个组件回填真实权限键"这一条：

| 顺序 | 块 | 为什么排这个位置 |
|---|---|---|
| 1 | `be-sdk-python`、`be-sdk-ts` | 两个新语言的组件都要用它们；`be-sdk-python` 必须晚于已经被真组件用过一轮的 `be-sdk-go`（总纲 §3.5.1：反过来做两边一定分叉） |
| 2 | `infra-authz` | 本阶段真正的地基。阶段二五个组件的路由要"回填真实权限键"，必须先有真实的 bundle 可拉；`ScopeFilter` 中间件要下场，必须先有真实数据权限判定源 |
| 3 | 阶段二五个组件回填真实权限键（Task 6） | **在新组件铺开之前先把旧账还掉**——这正是阶段二 Task 1"现在还账改 1 个组件，拖到阶段三还要改 13 个"那条判据的翻版：本阶段自己的九个新组件从第一天起就该用真实权限键写，不该重复"先标 Public 再回填"这一步 |
| 4 | `infra-iam-casdoor`、`infra-workflow`、`infra-notification`、`integration-im-dingtalk`、`infra-print` | 五个零出边的基建砖，谁先谁后互不影响，按 Python 组件（`infra-print`）需要 `be-sdk-python` 已经就绪这一条硬顺序排在 SDK 之后即可 |
| 5 | `infra-bff-mobile`、`frontend-standard` | 两个 TS 组件，`frontend-standard` 要通过 `be-sdk-ts` 生成的 API client 与 `infra-bff-mobile` 的 GraphQL 端点联调，所以排在基建砖之后 |
| 6 | `crm-opportunity` | 唯一的链上一环，且是**触发**这条链的起点（"CRM 赢单"），必须等 `mdm-customer`/`mdm-product`（已有）与所有下游基建砖都真实存在，才能把全链路盘一遍 |

⚠️ **`crm-opportunity` 不对 `erp-sales` 建同步边。** 两者之间是**事件边**（`crm.opportunity.won.v1`），设计书
§1.4 铁律"CRM 与 ERP 零同步边，仅事件握手"——阶段二复盘 §2.3 已经论证过跨组件同步调用要用 vendored-contract
模式，但那是给"确实需要同步调用"的边界用的；`crm-opportunity` 完全不需要同步调用 `erp-sales`，**顺手加一条比
阶段二任何一次都更容易犯错**，因为这次两个域名字上完全不像会有关系，反而更容易被忽略这条铁律。

## 第 0 部分 · 两个新 SDK 与门禁扩展（Task 1–3）

#### Task 1：`be-sdk-python` 建仓库 → CP-7 → 实现 ✅（骨架部分）

**与 `be-sdk-go` 的关系不是"照着抄一遍"，是"逐个能力对应着搬"**（总纲 §3.5.1、决策 100）：两份 SDK 的公开 API
要同名、同参数顺序、同语义，否则同一个人在两种语言间切换要重新学一遍，AI 也会把 Go 的写法直接套过来。

- [x] `Config`（**从第一个提交起就实现对 camelCase→SCREAMING_SNAKE_CASE 转换**，含幂等性回归测试）、
      `Endpoint()`（剥 `http://` 前缀，二值返回，导读第 1 条）、`WithTx`（`SET LOCAL ROLE`，铁律二）——三者是
      "结构三件套"，真实实现，九门禁 + 19 条测试全绿，`with_tx` 真机连了本机 `be-postgres` 验证
- [x] `RunStandalone`/`NewGinEngine` 等价物（`run_standalone`/`new_fastapi_app`）、`Module`、`Runtime`：真实实现，
      对齐 be-sdk-go **首次提交**的范围（不是 Task 1 全部完成的范围，见下）
- [ ] OTel 初始化与 Blackhole 降级、Outbox/Inbox、`besdk.Consume`：**仍是签名 + `NotImplementedError` 的骨架**，
      对齐 be-sdk-go 首次提交把 `otel.go`/`outbox.go`/`events.go` 等留给"下一轮 TDD"的做法（当时是 Task 7）。
      本阶段计划里没有再切一个独立的"Task 1b"，但这些骨架必须在 Task 9（`infra-notification`/`integration-im-dingtalk`
      需要 `Consume`）与 Task 10（`infra-print` 需要 OTel/日志）之前用 TDD 填平——**开工到那两个 Task 时先回来补这里**
- [x] ⚠️ **`RequirePermission`/`ScopeOf`/`UserClient`/`SystemClient` 与本条原计划有一处刻意偏离，记录在案**：
      原计划要求"本阶段第一次实现就带真实判定，不像阶段二 `be-sdk-go` 先立 stub 形状"。实现时判断这样做代价更高
      ——`be-sdk-go` 自己在 Task 1 开工时**仍然是** fail-closed stub（真实 bundle 轮询是 Task 5 才与三个 `be-sdk-*`
      一起补），若 `be-sdk-python` 单独先做真实判定，会造成"Python 版比 Go/TS 版先进"的临时不对称，且要为一个
      当时还没有真实服务器可对照测试的契约设计并锁死实现。**改为按 be-sdk-go 当前形状写**（签名真实、判定 stub），
      Task 5 时三者一起换成真实 bundle 轮询。理由写在 `be-sdk-python` 的 `authz.py` 模块文档里，不是漏读任务清单
- [x] `configEnvVarName` 等价物：与 `be-sdk-go` 逐字对应的算法移植，回归测试覆盖 camelCase 与已是
      SCREAMING_SNAKE_CASE 两种输入

**验证（已完成部分）：** 九门禁全绿；19 条测试全部真机跑过（不是 mock）。过程中发现一个真实的平台级差异
——**`asyncpg.Pool` 会在 `release()` 时自动 `RESET ALL`，Go 的 `database/sql` 不会**——这让最初设计的"看下一个
借用者是否读到脏值"这种回归测试方法在 asyncpg 下测不出 `SET` 与 `SET LOCAL` 的区别（故意改坏代码复现过，测试
仍然绿），改成直接 spy 执行的语句本身才真正锁死。已记入 `docs/dev/实测踩坑记录.md` A6。

**验证（尚未做，随 OTel/Outbox/events 骨架填平时一起补）：** 用一个最小假组件真机 `brickkit up` 一次，走完

#### Task 3：`make gates` 扩展 + 两张表转正 ✅ 已完成

阶段一/二 `make gates` 的三条扫描（铁律六 import、`SystemClient` 误用、裸 `gin` 路由）目前只扫 Go 代码。本阶段
第一次出现 Python/TS 组件，扫描器要跟上：

- [x] `SystemClient` 误用扫描的 Python/TS 版：判据不变（只许出现在 `Start()`/事件 handler，不许出现在请求路径），
      语法层面按各自语言的 AST 或正则适配。**实际实现**：Go 保留 `go/ast`；Python/TS 没有对应语法树可用，
      退化成逐行正则（`system_client(`/`systemClient(`），已知精度上限（不理解字符串字面量）记在源码注释里，
      靠"这两个目录本来就是约定死的、不该有别的东西"这条硬约定兜底
- [x] 裸路由扫描的 TS 版：`infra-bff-mobile` 的 GraphQL resolver 层没有"裸 `gin.GET`"这个概念，判据要改成
      "resolver 是否经过权限键包装"——**这条不是照抄 Go 版能过的，要重新设计判据**，写清楚"GraphQL 场景下权限键
      强制长什么样"。**实际实现**：`BareGinScan` 改名 `BareRouteScan`（CLI 子命令 `bare-gin-scan` → `bare-route-scan`）；
      Python 版判据只认装饰器形态（`@router.get(...)`）与 `add_api_route` 直调，不认任意 `.get(...)`——
      `dict.get()`/配置读取里的 `.get(` 极常见，纯文本匹配会把这些全部误判；TS 版判据是"resolver 字段的值
      是否以 `requirePermission(` 开头"，不是就再看它是否长得像函数（箭头函数/`function` 关键字），是则违规
- [x] **新拍板并写回文档的两个目录约定**（此前全仓库都没有文档化，写这两条扫描时才发现空白）：Python 组件的
      `backend/app/http`、`backend/app/grpc`（对应 Go 的 `backend/internal/http`/`grpc`，写进总纲 SOP-B）；
      TS GraphQL BFF 的 resolver map 一律放 `src/resolvers/`（`docs/design/infra-bff-mobile.md` 待决问题 #1
      就此了结）
- [x] `registry/permissions.tsv`/`registry/data-scopes.tsv` 从阶段一"空表 + 校验"转正：`be-ops` 产出 9/10 开始
      真的扫描全部已发布组件的 `assembly.yaml`，聚合出这两张表的真实内容——这是这两张"只增不改"的表第一次真正
      被写入数据。**实际实现**：新增 `internal/authzreg` 包；`permissions.tsv` 只增不改（新 key 追加、已有 key
      允许刷新 title/type/owner_component、`deprecated` 列本命令从不自动设置也不清空、孤儿 key 打警告但不删行、
