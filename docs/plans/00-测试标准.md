# BrickEnterprise 测试规范

本规范定义这个项目里"测试"这件事的全部内容：有哪些类型的测试、每种测试测什么/不测什么、什么时候写、怎么写、用什么工具跑、每个组件的测试基础设施应该长什么样。**这是唯一需要遵守的测试规范**——写代码前、写测试前，先确认自己要做的事在这份文档里对应哪一节，照着做。测试要用的数据从哪来、组件间数据怎么协作，是独立的另一份规范，见 [`00-数据构建标准.md`](00-数据构建标准.md)。

目标只有一个：**让 AI 写出的测试真的能拦住回归，而不是看起来很多、其实什么都没守住**。达不到这个目标的测试比没有测试更糟——它会给人一种"这里被测过"的错觉。

---

## 一、测试体系总览

这个项目的测试分两条主线（后端 / 前端），外加一组横切范畴（不属于任何单一组件，但同样强制）：

| 类型 | 简称 | 属于 | 测什么 | 谁写 | 什么时候写 |
|---|---|---|---|---|---|
| 契约测试 | **L1** | 后端 | 契约本身没有破坏性变更；每个 rpc 能跨进程调通 | 组件自己 | 契约写完立刻 |
| 业务规则测试 | **L2** | 后端 | **规格**：不变量、状态机合法迁移边、幂等、边界情形的业务结论 | 组件自己 | 实现之前 |
| 单元测试 | **L3** | 后端 | **这一版实现**的分支：错误路径、空值、并发、SQL 拼得对不对 | 组件自己 | 实现之后 |
| 集成测试 | **L4** | 后端 | 真 PG / 真 NATS / 真 gRPC 端到端；迁移能重跑；跨组件调用真实依赖 | 组件自己 | 实现完成后 |
| 单元/逻辑测试 | **FE-1** | 前端 | 纯函数、composable、store，mock 掉网络请求 | 组件自己 | 写完就补 |
| 组件测试 | **FE-2** | 前端 | 被多个业务页面复用的共享组件 | 组件自己 | 写完就补 |
| 端到端测试 | **FE-3** | 前端 | 真浏览器 + 真后端，覆盖完整业务流程 | 组件自己 | 页面稳定后 |
| 视觉回归测试 | **FE-4** | 前端 | 页面间距/密度/组件用法一致 | 组件自己 | 与 FE-3 同批 |
| 权限/数据权限边界测试 | — | 后端，横切 | "自己的数据看得到、别人的数据看不到" | 组件自己 | 声明了 `data_scopes` 就必须有 |
| 事件契约测试 | — | 装配层，横切 | `events/*.json` 只增不删不改 | 门禁自动比对 | 每次改事件契约 |
| SDK 并发正确性测试 | — | 语言基础库，横切 | 多实例并发使用同一个 SDK 原语（Outbox pump、幂等表操作）时不出错 | `be-sdk-*` 自己 | 每个横切原语至少一条 |
| 跨组件测试 | — | 后端，横切工具 | 本组件真实调用它的强依赖，不再靠 mock 或跳过 | 组件自己，用 `make test-cross` 跑 | 有强依赖边的组件都要有 |

**四条总原则，贯穿全文：**

1. **规格先于实现**：L2 测试在写实现之前写，测的是"这个功能应该怎样"，不是"这段代码干了什么"。先写实现再补测试，写出来的必然是"描述现有实现的测试"——防得住回归，防不住"一开始就理解错了需求"。
2. **真实优于模拟**：能用真 Postgres/NATS/gRPC 就不用 mock。 mock 能证明的最多是"调用发生了"，证明不了"调用的结果是对的"——而"结果对不对"才是测试存在的理由。
3. **能机制化的判据，必须机制化**：任何"人记得住就靠人查"的规则，只要能写成一个 `make` 门禁或脚本检查，就必须写成——人不可能对着几十个组件逐条记住所有规则，门禁会。
4. **测试是规格文档，不是产量指标**：一层测试测的东西被另一层重复测了一遍，不是"更保险"，是多了一处将来要同步维护、又不会同步维护的地方。每一层只测该它测的那部分。

## 二、测试驱动的开发流程

### 2.1 一个功能从设计到交付的顺序

```
① 设计业务逻辑        写清楚要做什么、为什么这样做
② 查参考实现          自己先设计一版，理不清的地方才去看现实项目怎么做，不要凭空想象
③ 写契约              .proto / .openapi.yaml / events/*.json —— 把设计变成可执行的类型
④ 写 L2 测试           不变量、状态机迁移表、属性测试 —— ⚠️ 在实现之前，测的是规格
⑤ 写实现              红 → 绿 → 重构，一个规则一轮，每轮一次 commit
⑥ 补 L3 测试           边界、错误路径、并发 —— 实现之后，测的是这个实现
⑦ 集成 + 门禁         真 PG / 真 NATS / grpcurl，跑齐所有门禁
```

⚠️ **③ 在 ④ 之前、④ 在 ⑤ 之前，这两个顺序都不能反：**

- **契约先于测试**：测试要引用契约生成的类型。没有契约就只能测 `map[string]any`，那种测试重构一次实现就全废。
- **测试先于实现**：这是"规格"与"实现"之间唯一的分界线。测试写在实现之后，写出来的必然是照着已经写好的代码描述一遍——它能防止以后改坏，但完全防不住"这段代码从第一天起就没做对需求"。

### 2.2 红-绿-重构：一次会话一个循环，一个循环一次 commit

```
1. 写一条（或一小组同源的）失败测试
2. 跑它，确认是红的 —— ⚠️ 并确认「红的原因是功能没实现」，不是测试自己写错、编译不过、mock 配错
3. 写最小实现让它变绿
4. 跑全量测试，确认没有把别的测试弄红
5. 重构（可选）；重构后再跑一次全量
6. commit：一句话说清"这一轮守住了什么业务结论"，不是"改了哪些文件"
```

### 2.3 铁律：不许为了让测试通过而改测试

这是最常被违反的一条规矩，而且违反者总能找到一个听起来合理的理由（"这个断言太严格了""实际行为其实是对的"）。判断表：

| 情形 | 怎么做 |
|---|---|
| 测试红了，是实现不对 | 改实现。**默认都是这一种，没有例外** |
| 测试红了，是测试真的写错了（断言了一个错误的业务结论） | 先停下来，用一句话说清"原来的断言错在哪、为什么错"。改测试要**单独一次 commit**，不许和实现改动混在一起 |
| **L2 业务规则测试挡路** | **几乎一定是实现或者对需求的理解错了，不是测试错了。** L2 是规格——它挡路时该改的是设计，改完设计再回来改测试，绝不允许先斩后奏 |

**永远不许做的三件事**：注掉测试、加 `t.Skip`/等价跳过标记、放宽断言让它凑巧过。这三种做法的共同点是让门禁从"真的能拦住东西"退化成"摆设"——而门禁一旦有一处是摆设，人就没法再信任任何一处的绿。

### 2.4 卡在同一个循环三轮还不绿：三条出路，按顺序试

| # | 出路 | 具体做法 |
|---|---|---|
| 1 | **把这一步切小** | 三轮不绿通常不是"难"，是这一步同时在解决两三件事。把测试拆成更小的断言，一次只让一条绿 |
| 2 | **去看参考实现** | 这正是"理不清才去读"的时机（见 §2.1 的②）。读完回来自己想清楚再写，**不要照抄** |
| 3 | **停下来说清卡在哪** | 说清"期望什么 / 实际什么 / 试过什么 / 怀疑是哪一层出的问题"，交给人判断 |

出路 3 不是失败，是正确动作——发现问题说不清楚就该停，而不是硬着头皮绕过去。绕过去一次，下一次遇到类似情况就会有人有样学样地再绕一次，规矩很快就名存实亡。

## 三、后端测试：四层详解（L1-L4）

### 3.1 L1 · 契约测试

**测什么**：契约本身没有破坏性变更（工具自动比对，如 `buf breaking` 之于 `.proto`）；每一个 rpc 真的能被跨进程调通（不是编译通过就算数，要真的起一次 server 打一次 client）。

**不测什么**：业务行为——L1 完全不关心调用的结果对不对，只关心"这个接口存在、能连上、字段没有被破坏性修改"。

**什么时候写**：契约刚写完就写，不用等实现。

### 3.2 L2 · 业务规则测试——四层里最重要的一层

**测什么**：**规格**。具体是四类东西：

- **不变量**：任何时候都必须成立的性质（"库存总数不能为负""可用量+已预留量恒等于总量"）。
- **状态机的合法迁移边**：哪些状态转换允许、哪些不允许（"已完结的预留不能再取消"）。
- **幂等**：同一个命令带同一个 `idempotency_key` 重放 N 次，结果必须和执行一次完全一样。
- **边界情形的业务结论**：数量为零、金额为零、列表为空这类边界下"应该发生什么"。

**不测什么**：实现细节——哪个函数被调用了、用了哪张表、内部怎么组织代码。L2 测试换一种语言、换一种数据结构、把整个实现推倒重写，只要对外行为符合规格，这条测试就该原样通过。

**判分界线的一句话判据**：

> **把这个功能的实现整个删掉、用另一种语言重写一遍，这条测试还应该成立吗？**
> 应该成立 → L2。不应该成立（因为测的是这一版实现的某个具体写法）→ L3。

例（`erp-inventory` 这类库存组件）：

```go
// L2：这是规格。实现从 Go 换成 Rust、从行级锁换成乐观锁，它照样必须成立。
func TestProperty_库存总数永不为负(t *testing.T) { /* 属性测试，随机操作序列攻击 */ }
func TestProperty_available_reserved_之和恒等于total(t *testing.T) { /* … */ }
func Test状态机_已完结的预留不能再取消(t *testing.T) { /* 迁移边 */ }
func TestProperty_Reserve严格幂等(t *testing.T) { /* 同一 key 重试 n 次，结果必须一致 */ }
```

```go
// L3：这是在测"这一版实现"。换掉条件更新的写法，这个测试就该跟着改，不是规格。
func Test条件更新_RowsAffected为0时返回库存不足错误(t *testing.T) { /* … */ }
func TestReserve_产品ID为空时返回InvalidArgument(t *testing.T) { /* … */ }
```

**⚠️ 强制要求：核心交易类组件的 L2 必须用基于属性的测试**（不能只写 Example 测试）。核心交易类组件指涉及库存、资金、薪酬、佣金这类"算错一次就是真实业务事故"的组件。做法：人类定义不变量，测试框架生成大量随机边界输入去攻击实现（Go 用 `rapid`/`gopter`，Python 用 `hypothesis`）。只写 Example 测试的话，那些"只在特定操作顺序下才触发"的 bug 一个都测不出来——而这类 bug 恰恰是 AI 生成代码最容易留下的那种。

**⚠️ 幂等测试必须覆盖并发场景，不能只测"重放一次"**：一个命令声称幂等，真正的风险从来不是"顺序重放两次"，而是"两个并发请求带着同一个 key 同时到达"。claim-first 幂等的正确实现是原子 `INSERT ... ON CONFLICT DO NOTHING` 声明成功才做真正的写；如果实现用的是"先查表判断是否存在、不存在再插入"，两个并发请求会在"查不到"的窗口里都以为自己该执行，各自把工作做一遍。L2 的幂等测试必须包含一条"多个 goroutine/协程并发带同一个 key 调用，只有一次真正执行"的用例，不能只测串行重放。

**⚠️ 数据权限边界测试必须验证"看不到别人的"，不能只测"看得到自己该看的"**：任何声明了 `data_scopes` 的组件，测试常见的错误做法是只覆盖两种情形——"有权限的人能看到数据"和"完全没权限的人看不到任何数据"。**这两种情形都不能证明范围过滤逻辑本身是对的**：一段错误地返回全表数据的代码，在"零权限用户"这一测上会失败，但在"有权限用户"这一测上完全正常，两条测试都是绿的，问题却依然存在。**正确做法：真实建两条归属不同的数据（不同的 `owner`/`org`/`warehouse`……），用其中一个身份去查，断言返回结果里没有另一个身份名下的数据。** 这是这一类组件唯一能真正证明范围过滤有效的测试形状，缺了它就等于范围过滤逻辑从未被验证过。

### 3.3 L3 · 单元测试

**测什么**：这一版实现的具体分支——错误路径、空指针/空字符串、并发写冲突、SQL 拼接是否正确、参数校验的每一个 if 分支。

**不测什么**：已经被 L2 覆盖过的业务结论——重复一遍不会更保险，只会多一处将来两边都要改、又只改了一边的地方。

**什么时候写**：实现完成之后补，或者在红绿循环里跟实现同步写（比如刚写完一个 `if err != nil` 分支，立刻给它配一条测试）。

### 3.4 L4 · 集成测试

**测什么**：真 Postgres / 真 NATS / 真 gRPC 下端到端跑通；数据库迁移能重复执行（同一份 up 迁移连跑两次都必须成功——这是幂等迁移，不是幂等业务逻辑）；健康检查接口只报告本进程存活，不查任何依赖（否则一个依赖抖动会连带拖垮所有上游的健康状态）。

**不测什么**：业务规则的所有分支——那是 L2 的职责，L4 跑得慢、出错难定位，塞进业务分支测试只会让这一层既慢又不好维护。

**⚠️ 任何存在"反向迁移"（down migration）的组件，必须真机执行过至少一次 `migrate down` 再 `up`，不能只靠代码审查判断 down 脚本对不对。** down 迁移按版本号倒序执行，一份 down 脚本写的时候容易默认"更早版本创建的表这时候已经不存在"，但真实顺序恰好相反——更早版本的表要等它自己那一份 down 跑到才会被清理。这类问题只有真的执行一次 `migrate down` 才会暴露，代码审查看不出来。任何提供 `db-reset`（`migrate down` 再 `up`）作为清空手段的组件，落地前必须真机验证过这个命令本身能跑通。

**⚠️ 消费者（consumer）测试有两条独有的规矩：**

1. **自己构造/发布事件触发消费者时，用测试私有的 subject，不要用真实生产 subject。** 如果同一台机器上真实运行的容器正订阅着同一个生产 subject，广播式的订阅机制会让真实容器和测试的临时订阅者同时收到消息，谁先抢到去重表的认领谁的产出就留在数据库里——断言可能读到的是别人的结果，而不是这次测试自己触发的那一次。做法：把 subject 换成带时间戳/随机数的测试私有名字（如 `test.<base>.<纳秒时间戳>`），消费逻辑本身不应该按 subject 做业务判断，这样切换完全安全。**这条只适用于"测试自己发布事件去触发消费者"**；验证"业务逻辑真的发到了正确的生产 subject"这件事本身的测试，必须用真实 subject，不能也用私有 subject 蒙混过去。
2. **去重表按 `(subject, aggregate_id, version)` 做单调去重时，测试必须用唯一的 `aggregate_id`，不能用固定字符串。** 去重逻辑一旦生效就是永久的（同一个组合"处理过"这件事会持久化），第二次跑测试套件时如果 `aggregate_id` 是写死的字面量，这个组合早就"处理过"了，消费函数根本不会被真正调用——断言读到的是"从来没被处理过"的初始状态，看起来像是功能坏了，实际是测试自己的数据设计问题。做法：`aggregate_id` 也要按测试实例生成唯一后缀，跟 L4 集成测试"每次现造数据、带唯一后缀"的通用判据是同一件事。

**⚠️ 禁止用 mock 验证跨组件调用"发生了"。** 类似"验证调用了库存服务"这种测试，在"调用了但参数传错了""调用了但没处理返回的错误"两种真实故障场景下都会保持绿色——它只能证明代码路径被执行到，证明不了任何业务结果。跨组件之间真实发生了什么，属于 L4 的职责范围（真的起两个进程去验证），组件内部的调用关系才用 mock 或者依赖注入去测。

**⚠️ L4 集成测试的数据判据是"每次现造，带唯一后缀，不清理"，不是复用一份共享的固定数据，也不引入一次性/嵌入式数据库**（H2、Testcontainers 那一类做法）。完整原因、跨组件测试需要的数据形态怎么产生、种子数据的完整策略，见 [`00-数据构建标准.md`](00-数据构建标准.md)。

## 四、跨组件测试：怎么让一个组件的测试打真实依赖

跨组件的集成测试（本组件真实调用它的强依赖）默认情况下很容易被环境变量缺失这类条件挡住而在日常被跳过——测试环境本身够不到依赖组件的内部端口，写了也白写，跨组件验证长期只能靠人手工搭好网络才跑一次。

`make test-cross REPO=<仓库名>` 解决的正是这个问题：读这个组件声明的强依赖，给每一条依赖起一个轻量转发容器，把依赖的地址桥接到测试运行的宿主机上，测试进程本身仍然在宿主机跑（用宿主机的构建缓存、并发/竞态检测都正常），跑完自动清理转发容器。

**使用方式：**

- 只需要"这个组件连同它的强依赖树"在运行，不需要整个装配一起启动——这就是局部性测试的含义：只跑这一个组件自己的测试，打的是真实的强依赖，别的组件在不在跑都不影响结果。
- 支持过滤，只跑匹配某个名字的测试。
- **目标范围是"本组件调用它的依赖"（同步调用方向）**。"别的组件消费本组件发出的事件"是完全不同的另一件事（涉及事件总线、可能跟同机真实运行的容器抢消息），不在这个工具的覆盖范围内，需要单独处理（见 §3.4 消费者测试的两条规矩）。
- **命名约定**：新写的跨组件测试要在名字里体现"这是在测跟哪个组件之间的交互"，方便配合过滤参数只跑"某两个组件之间"的那一批（完整命名约定见 §八）。

跨组件测试需要的数据怎么产生，见 [`00-数据构建标准.md`](00-数据构建标准.md) 的 §三。

## 五、扩展测试范畴

除了 L1-L4 这套稳定的四层，下面几类范畴同样是强制要求（不是"可选加分项"）：

### 5.1 权限/数据权限边界测试

无 token 应该拒绝、有 token 但无权限应该拒绝，这两条是身份验证中间件本身的职责，在语言基础库层面测一次即可，不需要每个组件重复验证——但**门禁必须能确认每一个对外接口真的经过了这层中间件**，不能有裸路由绕过去。

真正只有每个组件自己才能验证的，是"自己的数据能看到、别人的数据看不到"这条范围过滤逻辑本身（因为这段逻辑是每个组件手写的，不是共享的中间件）——完整判据见 §3.2。任何声明了数据权限维度的组件，必须至少有一条这种形状的测试，这一条由装配层的门禁自动检查（读组件的数据权限声明，检查测试文件里有没有"越权/超出范围被拒绝"形状的用例）。

### 5.2 事件契约破坏性变更检测

事件的 schema 演进只能"只增不删不改"——新增字段、新增事件类型都可以，删除已有字段、修改已有字段类型、删除已有的事件主题都不许。这条由装配层门禁自动比对每个组件的事件契约文件与其历史版本，检测出违规。

### 5.3 SDK 并发正确性测试

被全部组件共用的语言基础库，它的横切能力（事件投递轮询、幂等表操作、连接池管理……）在"多实例同时运行"场景下的正确性，是 L1-L4 这套单组件视角完全测不到的一类问题——L1-L4 全部假设"只有一个进程实例在跑"，测不出"两个实例同时争抢同一批未处理事件、各自都以为自己该处理"这类问题。这类原语的测试要求：至少一条"多个实例并发使用同一个原语"的用例，验证结果只被处理一次、不重复、不遗漏。

### 5.4 前端视觉回归测试

见 §6.4 FE-4。

## 六、前端测试：四层详解（FE-1 ~ FE-4）

前端测试的分层判据和后端是同一套思路，只是工具换了：规格与实现分开、共享的东西比业务专属的东西优先级更高、真实环境优于模拟环境。

### 6.1 FE-1 · 单元/逻辑测试

**测什么**：纯函数、组合式函数（composable）、状态管理（store），网络请求全部 mock 掉。

**判据**：这一层测的是"给定输入，逻辑本身算得对不对"，不关心真实网络往返、不关心界面渲染。

### 6.2 FE-2 · 组件测试

**测什么**：被多个业务页面复用的共享 UI 组件（表格、表单模板、通用卡片这一类）。改坏一个共享组件等于同时改坏所有引用它的页面，这类组件的测试优先级天然高于某个业务页面自己专属的一次性组件。

### 6.3 FE-3 · 端到端测试

**测什么**：真浏览器 + 真后端（完整装配跑起来），覆盖完整的业务流程，不是某个孤立的界面交互。PC 端与移动端可以共用同一套端到端测试工具，用不同的设备画像区分，不需要各自独立的一整套工具链。

**⚠️ 何时开始写**：等页面的交互形态基本稳定下来再开始批量补。页面还在被大幅调整的阶段，每一次界面改动都要连带改一遍端到端测试的选择器和断言，这个阶段投入端到端测试的性价比很低——不是"忘了写"，是刻意排在页面稳定之后。**骨架和目录约定要提前定好**，等真正开始写的时候直接往里填，不用重新设计。

**判据**：按"验证的业务流程"命名测试，不按"点了哪个按钮"命名——这样才能用名字过滤出"某一条业务流程相关的全部端到端测试"，否则这一层的可筛选性名存实亡。

**⚠️ 执行前必须先获得用户明确同意，不能自作主张直接跑。** 这条判据不是针对某一个具体工具（Playwright/Cypress/Selenium/Puppeteer 都一样）——贵的不是"用了哪个框架"，是"AI 需要真实驱动浏览器、通过截图或读取渲染后 DOM 来调试选择器、排查失败原因"这件事本身，换任何同类工具成本量级都差不多。动手之前，先告诉用户这一次打算测试的具体范围（哪条业务流程、覆盖哪些页面/断言），再等用户确认要不要现在就跑、要跑多大范围——是否执行、执行到什么程度，由用户做最终决定。这条同样适用于 §6.4 的视觉回归测试，因为它复用同一套端到端流程一起跑。

**成本主要来自"写/调试"阶段，不是"运行"阶段**：已经写好、稳定的测试套件跑一遍，走的是文本形式的测试报告（哪几条过、哪几条挂、挂在哪个断言），成本跟普通单元测试相近；真正烧 token 的是第一次写这条测试时反复截图确认选择器对不对、失败后反复截图排查原因。降低这部分成本的做法：

- 优先用无障碍树快照（结构化文本）确认页面元素，而不是每次都截整页图去"看"；
- 失败时先看纯文本的错误堆栈和 trace 文件，排查不出来才动用截图；
- 关键操作路径尽量由人录制，减少 AI 盲猜选择器反复试错的轮次。

### 6.4 FE-4 · 视觉回归测试

**测什么**：不同页面之间的间距、密度、组件用法是否一致。做法是端到端测试流程走到关键页面时顺手做一次截图对比，不是另外起一遍浏览器单独跑一套"纯截图"的测试——视觉回归是端到端测试的一种断言方式，不是独立的测试类型。基线随界面改动一起更新。

⚠️ 执行前的用户确认要求跟 §6.3 完全一样（同一套浏览器流程），不再重复。视觉回归**必然**要截图——这是它的定义决定的，换任何工具都躲不开；但比对环节本身是自动化的像素级 diff，产出"通过/不通过 + 差异百分比"这种文本结果，不需要 AI 用视觉理解去逐张看图。真正需要动用视觉理解能力的，只有比对失败之后、要判断"这处差异是真 bug 还是预期的界面调整"这一步。

### 6.5 前端契约漂移：靠机制杜绝，不靠多写测试

手写的前端类型定义（注释里写着"逐字对应后端契约"，但没有任何机制保证这一点）不应该靠反复补充测试去发现漂移——那是把一个可以从根源消除的问题，变成一项永远交不完的维护税。正确做法是**建立从后端契约（`.openapi.yaml`/GraphQL schema）自动生成前端类型与请求函数的机制**：类型检查工具本身在编译阶段就会拦下所有漂移，装好之后每新增一个接口零额外成本，不需要另外为"契约有没有漂移"这件事专门跑测试。

## 七、组件测试基础设施：目录、命令、怎么调试

每个组件的测试不是零散文件的堆砌，而应该有统一、可预测的基础设施，让任何人（或 AI）打开一个从没见过的组件都能立刻知道怎么跑测试、怎么调试。

### 7.1 三种运行粒度：什么时候跑哪一种

不分语言，后端 Go/Python、前端 TypeScript 都是同一套三种粒度，只是命令不同：

| 粒度 | 什么时候跑 | 后端怎么跑 | 前端怎么跑 |
|---|---|---|---|
| **① 全量** | 部署前、阶段收尾、给整个装配一次全量验收 | 全部门禁 + 每个组件的 `make test` | 根目录一次性跑全部前端包的测试 |
| **② 组件完整** | 一个组件/一个功能写完了 | `make test`；`make test-cross REPO=<x>` 把跨组件 L4 也跑起来（§四） | 针对单个前端包跑测试 |
| **③ 组件内子集** | 迭代开发某个新功能，想确认"这部分还没被我搞坏" | 按名字/正则过滤，只跑匹配的测试 | 按文件/pattern 过滤，watch 模式下按依赖关系自动只重跑相关的 |

③ 不需要额外工具——三种语言的原生测试运行器都自带按名字/路径过滤的能力，前提是测试名字本身可预测（见 §八）。命名混乱的话，这一层粒度就名存实亡，只能靠人肉翻文件找测试。

### 7.2 一个组件应该具备的命令

| 命令 | 做什么 | 什么时候用 |
|---|---|---|
| `make test` | 跑本组件的全部 L2 + L3 测试（开启并发/竞态检测） | 日常开发、每个红绿循环结束时 |
| `make migrate-idempotent` | 同一份数据库迁移连跑两次都必须成功 | 每次改动迁移文件 |
| `make contract-check` | 契约破坏性变更检测 | 每次改动契约 |
| `make smoke` | 只装这一个组件（连同强依赖树）真实启动，用真实协议（HTTP + gRPC）各打一次，健康检查转正常 | 每次真机验证前 |
| `make test-cross REPO=<本组件仓库名>`（装配层根目录跑） | 局部化的跨组件 L4 测试，见 §四 | 有强依赖边、想验证真实调用链路时 |
| `make seed` | 灌一套覆盖各种状态/分支/权限维度的种子数据（若本组件有种子数据） | 本地探索、演示、手工验证新功能 |
| `make seed-clean` 或 `make db-reset` | 撤销/重置种子数据，怎么选见 [`00-数据构建标准.md`](00-数据构建标准.md) | 需要清空重来时 |

**这些命令必须真的存在、真的能跑**——一个组件如果只在文档里说"应该有测试"，却没有一条能一键跑起来的命令，等于没有测试基础设施。

### 7.3 需要真实基础设施时怎么接

L4 集成测试与消费者测试需要真实的 Postgres / NATS，这些应该指向专门给自动化测试用的数据库/消息通道，与人工探索/演示用的那一份物理分开——完整原因见 [`00-数据构建标准.md`](00-数据构建标准.md) 的 §一。

### 7.4 调试的基本手段

- **只跑一条或一小撮测试**：三种语言的原生测试运行器都自带按名字/路径过滤的能力，前提是测试名字本身可预测（见 §八）。
- **跨组件测试的过滤**：`make test-cross` 支持带过滤参数只跑匹配某个名字的用例，配合跨组件命名约定可以只跑"某两个组件之间"的那一批。
- **门禁失败时先看输出，不用先读代码**：任何一个门禁失败，输出会直接指出违反了哪一条判据、涉及哪个文件——门禁存在的意义就是让人不需要逐行读代码也能定位问题，读代码是门禁指出问题之后才做的事，不是排查的第一步。
- **卡住时的完整处理流程见 §2.4。**

## 八、测试命名与可发现性约定

命名可预测是"只跑一小撮测试"这件事成立的前提——命名混乱的话，过滤这件事就名存实亡，只能靠人肉翻文件找测试。

| 约定 | 用在哪 | 目的 |
|---|---|---|
| 测试名字直接描述业务结论或实现分支，不用编号 | L2/L3 常规测试 | 看名字就知道测的是什么，不用打开文件 |
| 属性测试单独标出（如带 `Property` 字样） | L2 属性测试 | 提示读者"这条断言背后是随机输入攻击，不是单一样例" |
| 跨组件测试名字里体现"对方组件是谁"（如带对方组件名的驼峰形式） | 跨组件 L4 测试 | 配合 `make test-cross` 的过滤参数只跑某两个组件之间的测试 |
| 端到端测试按"验证的业务流程"命名，不按"点了哪个按钮" | 前端 FE-3/FE-4 | 配合过滤参数按业务流程筛选 |

⚠️ 这些约定只对**新写**的测试强制生效，不要求回头重命名已经存在的测试——重命名没有收益也没有紧急性，顺手改到就改，不必须专门起一轮任务。

**种子数据的可发现性**：见 [`00-数据构建标准.md`](00-数据构建标准.md)。

## 九、人工审查：与测试相关的部分

人不可能逐行读完整个系统所有组件的实现，审查因此只集中在**不可逆、且门禁本身守不住的地方**。与测试直接相关的一条是：

> **L2 业务规则测试的不变量清单是否列全了。** 审查者只看"这个组件所有该有的不变量是不是都列出来了"，不看具体怎么实现的。**漏掉一条不变量，任何门禁永远都发现不了**——门禁只会去跑已经写下来的那些测试，一条从未被想到过的不变量，不会因为门禁全绿就自动被验证。

**不需要人工审查的**：业务代码逐行、L3 单元测试、构建脚本——这些由门禁和 L2 覆盖，真出问题会在门禁或已有测试里变红，不需要预先靠人眼排查。
