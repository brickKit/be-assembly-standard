## Task 0：把 `be-assembly-standard` 迁移到真实 `servedBy`

### 0.1 计划：`infra/shell-compose.yml`/`shell-up`/`teardown-up` 是否可以退休

**要验证的核心判断**：`servedBy` 落地后，"外壳态"和"全拆态"可能不再需要是两个互斥的部署状态，只是同一份 `brickkit.yaml` 里"谁写了 `servedBy` 谁没写"的区别，一条 `brickkit up` 就能生成正确的混合拓扑（部分组件独立、部分组件被外壳收编）。

**具体步骤**：
1. 现状快照：记录当前 `brickkit.yaml`（阶段四遗留的 `local:true` 版本）、`infra/shell-compose.yml`、`Makefile` 里 `shell-*`/`teardown-*` 目标的真实内容，作为"旧方案"的对照基线。
2. 挑 1 个最小可行子集做实验（不动全部 14 个组件，先证明机制本身）：在一个**临时分支/临时 `brickkit.yaml` 副本**里，把 `mdm/customer`/`mdm/product` 两个零依赖组件从 `local: true` 改成 `servedBy: infra/go-core-shell@1.0.0`，`infra/go-core-shell` 作为一条新的普通组件条目（指向已经存在的 `brickenterprise/be-shell-go` 镜像，随便一个已构建过的 tag）。
3. `brickkit up --dry-run`，检查生成的 compose 是否：① 外壳容器自己的 service 正常生成；② `mdm/customer`/`mdm/product` 没有生成独立 service；③ 外壳 service 挂了这两个组件的网络别名；④ 依赖 `mdm/customer` 的其它组件（比如 `crm-opportunity`），`depends_on` 是否正确指向了外壳而不是 `mdm/customer` 自己。
4. 如果第 3 步完全符合预期，把**剩余 9 个 Go 组件 + 4 个外壳整体**一起做这个替换（正式的 0.4 节内容），此时再回头判断 `infra/shell-compose.yml`/`Makefile` 那几个目标要不要删——不在这一步就删，先留着做对照，等 0.4/0.5 全部跑通、新旧两条路径生成的最终拓扑（`docker ps` 输出）逐字对比一致之后再删。
5. 记录一个明确的决策：删，还是保留（如果发现有旧方案做得到、新方案做不到的事，比如健康检查探针的具体参数、启动顺序控制粒度，就不删，把差异记录清楚）。

**验证标准**：第 3 步的 4 项检查全部通过，且第 4 步全量替换后 `docker ps`/`kubectl get pods` 展示的最终拓扑跟旧方案（阶段四已经验证过、写在 `docs/plans/04-阶段四-做外壳验拆回.md` Task 6 的记录）完全一致。

### 0.1 真机执行记录（2026-09-14，最小子集实验）

**做法**：新建一个临时 local source（`sources:` 新增一条 `servedby-poc-source`，指向 scratchpad 下一个临时目录），写一份最小 `component.yaml` 声明 `infra/go-core-shell-poc@1.0.0`（镜像用已经构建过的 `brickenterprise/be-shell-go:local`，端口 9000，`healthCheck.path: /healthz`）。把 `mdm/customer`/`mdm/product` 的 `local: true`/`localPort` 两行改成 `servedBy: infra/go-core-shell-poc@1.0.0`。其余 12 个组件原样不动（仍是阶段四遗留的 `local: true`/独立部署混合状态）。

**⚠️ 真实撞到的问题（不是纸面推演）**：第一次 `brickkit up --dry-run` 直接报错：

```
❌ 错误：外壳 infra/go-core-shell-poc@1.0.0 下两个成员对同一个透传标签给出了不同的值
   标签键：prometheus.io/port
   mdm/customer@1.0.7：8080
   mdm/product@1.0.8：8082
```

根因：`mdm/customer`/`mdm/product` 的 `component.yaml` 都在 `deployment.labels` 里声明了 `prometheus.io/port`，值分别是各自的端口号——这是两个组件本来就该有、且理所当然应该不同的值，不是巧合冲突。`servedBy` 的 labels 合并规则是"同名同值跳过，同名不同值报错"（跟 env 变量的合并规则形状一样），但**跟 env 变量的合并不同，labels 没有做"只合并某一类、其它类无条件排除"这层收窄**——`*_ENDPOINT` 类环境变量因为语义上"整个外壳内必须一致"，合并+冲突检测是对的；但 `prometheus.io/port` 这类**语义上就是"每个组件各不相同"**的标签，被套用同一条合并规则，导致任何两个都声明了各自 `prometheus.io/port` 的组件，只要被收编进同一个外壳，必定 100% 撞车报错——这跟 `COMPONENT_ID`/`COMPONENT_VERSION` 在 env 合并里"因为必然不同所以被无条件排除"是同一类问题，只是这次发生在 labels 侧，而 labels 侧没有对应的收窄处理。

**临时绕过方式**（只为了让这次最小实验能继续往下验证，不是正式修法）：临时从 `mdm/customer`/`mdm/product` 的 `component.yaml` 里删掉 `prometheus.io/port` 这一行（保留 `prometheus.io/scrape`/`prometheus.io/path`，这两项两个组件本来就写的同一个值，不受影响），验证完立刻 `git checkout -- component.yaml` 还原，两个组件仓库确认过还原后 `git status` 干净。

**绕过之后，`brickkit up --dry-run` 成功，生成结果符合预期**：

```yaml
infra-go-core-shell-poc-1-0-0:
  environment:
    - BRICKKIT_SERVED_MEMBERS=mdm-customer-1-0-7,mdm-product-1-0-8
    - COMPONENT_ID=infra/go-core-shell-poc
    - COMPONENT_VERSION=1.0.0
  networks:
    brickkit-net:
      aliases:
        - mdm-customer-1-0-7
        - mdm-product-1-0-8
```

`mdm-customer-1-0-7`/`mdm-product-1-0-8` 没有生成独立 service（确认 `grep -c` 命中 0）。挑了一个真实存在弱依赖的独立组件 `infra-bff-mobile`（未受这次实验影响，仍然独立部署）核对地址路由：

```yaml
infra-bff-mobile-1-0-17:
  environment:
    - MDM_CUSTOMER_ENDPOINT=http://mdm-customer-1-0-7:8080
    - MDM_PRODUCT_ENDPOINT=http://mdm-product-1-0-8:8082
```

地址正确指向外壳容器的网络别名 + 各成员自己的端口——跟阶段四手写 `shell-compose.yml` 达到的效果一致，且不需要我们自己写任何 `extra_hosts`/别名逻辑。`erp-sales`/`erp-inventory`/`infra-workflow` 这几个仍是 `local: true` 的组件，`infra-bff-mobile` 拿到的地址走的还是旧的 `host.docker.internal`+`extra_hosts: host-gateway`——确认 `local:true` 和 `servedBy` 在同一份 `brickkit.yaml` 里确实互不干扰，不是只信 brickKit 自己的回归测试。

**清理**：`git checkout -- brickkit.yaml`、两个组件仓库 `git checkout -- component.yaml`，删除临时 source 目录，`.brickkit/manifests/` 下这次实验产生的缓存文件手动清掉，`brickkit restore` 确认"14 个活跃，0 个归档，0 个激活"，`git status --porcelain` 全仓库确认干净。

**结论**：
1. 核心判断成立——`servedBy` 确实能在一条 `brickkit up` 里正确生成"部分独立、部分收编"的混合拓扑，网络别名、地址路由、`local:true` 共存全部符合预期，`infra/shell-compose.yml`/`shell-up`/`teardown-up` 大概率真的可以退休（留到 0.4 全量切换、跟旧拓扑逐项对比后再做最终决定，不在这里就下最终结论）。
2. **发现一个值得反馈给 brickKit 的真实问题**：`servedBy` 的 labels 合并没有像 env 变量合并那样，把"语义上必然因组件而异"的标签（`prometheus.io/port` 是最常见、几乎每个组件都会写的例子）排除在合并范围之外，导致这类标签在任何多成员外壳里几乎必然撞车。这个问题会**直接挡住 0.4 节的全量迁移**（我们 11 个 Go 组件的 `component.yaml` 全部声明了各自的 `prometheus.io/port`），需要在 0.4 之前决定怎么处理——要么我们自己把这类标签从 `servedBy` 成员的 `component.yaml` 里移除、只在外壳自己的条目上写一份（跟"合并后指标只能走一个共享端口"这个事实保持一致），要么等 brickKit 那边看有没有必要收窄 labels 合并规则。这条已经计划单独写一份回信给 brickKit（见 Task 14 或者提前处理，视后续判断）。

### 0.2 计划：`be-ops` 产出 4/7/8 是否还需要

**要验证的具体问题**：
- 外壳启动器现在装配一个模块需要哪些数据：componentId（来自 `BRICKKIT_SERVED_MEMBERS`）、HTTPPort（缺口，需要另找来源）、Schema（缺口，需要另找来源）。
- `shellenv`（产出 7）产出的跨组件地址改写，是不是已经被平台原生的 `*_ENDPOINT` 合并机制完全取代。
- `shelldepends`（产出 8）产出的外壳间启动顺序，是不是已经被平台原生的 `depends_on` 改写完全取代。

**具体步骤**：
1. 对 0.1 步骤 2 的最小子集实验，检查生成的 compose 里 `mdm/customer`/`mdm/product` 对应的模块，端口/schema 信息有没有任何来源——如果外壳容器只拿到了 `BRICKKIT_SERVED_MEMBERS`（一串版本化服务名字符串），没有拿到端口/schema，就确认了"外壳启动器需要另一个数据来源"这个缺口真实存在。
2. 评估两个候选方案：① 外壳启动器代码里维护一份编译期静态映射（componentId → schema/端口，从 `registry/ports.tsv`/`registry/schemas.tsv` 生成，构建时嵌入二进制，不依赖运行时文件）；② 继续用 `be-ops shell-config` 产出一份轻量数据文件，只保留端口/schema 这两项，去掉已经被 `BRICKKIT_SERVED_MEMBERS`/平台原生合并取代的部分。两个方案各自的优缺点记录下来，选一个。
3. 决定后，实际去改 `tools/be-ops/internal/shellconfig`（如果选方案②，简化产出内容）或者废弃它（如果选方案①）。

**验证标准**：不管选哪个方案，`shells/go`/`shells/python` 的模块装配代码最终能拿到装配一个模块所需的全部数据（componentId、端口、schema），且不再依赖 `shellenv`（产出 7）/`shelldepends`（产出 8）产出的数据（这两项预期会被平台原生机制完全取代，真机确认后可以直接废弃这两个 `be-ops` 子命令）。

### 0.3 计划：`shells/go`/`shells/python` 接上真实 `BRICKKIT_SERVED_MEMBERS`

**具体步骤**：
1. `shells/go/cmd/shell/main.go`：把 `buildModules` 从"读 `SHELL_CONFIG_JSON` 拿到全部声明的模块列表，无条件实例化"，改成"读 `os.LookupEnv("BRICKKIT_SERVED_MEMBERS")`（注意用 `LookupEnv` 不用 `Getenv`，要能区分变量不存在 vs 空字符串），按逗号切分成版本化服务名集合，用 0.2 确定的数据来源拿到每个 componentId 对应的完整信息（端口/schema），只实例化真的在这个集合里的模块"。
2. 变量不存在（`ok == false`）时的行为：这种情况理论上不应该发生在一个真的被 `servedBy` 收编的外壳容器里（平台总会至少注入一个空字符串）——如果真的读不到，说明这个容器可能不是被正常 `servedBy` 收编启动的（比如手动 `docker run` 忘了传这个变量），选择直接 `log.Fatal` 报清楚的错误，而不是静默退化成"全部实例化"的旧行为（旧行为是过渡期的兼容写法，迁移完成后不应该再保留，否则会掩盖真实的配置错误）。
3. `shells/python/main.py` 同理。
4. 新增/更新单元测试：`t.Setenv`/`monkeypatch` 分别测试"变量不存在报错"、"变量是空字符串则不实例化任何模块"、"变量包含部分成员则只实例化那几个"三种情况。

**验证标准**：三种情况的单元测试全部通过；真机场景下（0.1 的最小子集实验）外壳容器实际启动后，只有 `BRICKKIT_SERVED_MEMBERS` 里列出的模块被实例化，用日志或者 `/healthz` 之外的一个内部诊断端点确认（如果没有现成的诊断端点，看启动日志里逐个模块的初始化记录）。

### 0.4 计划：`brickkit.yaml` 全量真机切换

**具体步骤**：

2. 12 个组件（11 个 Go + `infra-print`）逐个从 `local: true`/`localPort` 改成 `servedBy: <外壳ID>@<外壳版本>`，删掉 `local: true`/`localPort` 两行。
