## Task 0：把 `be-assembly-standard` 迁移到真实 `servedBy`

### 0.1 计划：`infra/shell-compose.yml`/`shell-up`/`teardown-up` 是否可以退休

**要验证的核心判断**：`servedBy` 落地后，"外壳态"和"全拆态"可能不再需要是两个互斥的部署状态，只是同一份 `brickkit.yaml` 里"谁写了 `servedBy` 谁没写"的区别，一条 `brickkit up` 就能生成正确的混合拓扑（部分组件独立、部分组件被外壳收编）。

**具体步骤**：
1. 现状快照：记录当前 `brickkit.yaml`（阶段四遗留的 `local:true` 版本）、`infra/shell-compose.yml`、`Makefile` 里 `shell-*`/`teardown-*` 目标的真实内容，作为"旧方案"的对照基线。
2. 挑 1 个最小可行子集做实验（不动全部 14 个组件，先证明机制本身）：在一个**临时分支/临时 `brickkit.yaml` 副本**里，把 `mdm/customer`/`mdm/product` 两个零依赖组件从 `local: true` 改成 `servedBy: infra/go-core-shell@1.0.0`，`infra/go-core-shell` 作为一条新的普通组件条目（指向已经存在的 `brickenterprise/be-shell-go` 镜像，随便一个已构建过的 tag）。
3. `brickkit up --dry-run`，检查生成的 compose 是否：① 外壳容器自己的 service 正常生成；② `mdm/customer`/`mdm/product` 没有生成独立 service；③ 外壳 service 挂了这两个组件的网络别名；④ 依赖 `mdm/customer` 的其它组件（比如 `crm-opportunity`），`depends_on` 是否正确指向了外壳而不是 `mdm/customer` 自己。
4. 如果第 3 步完全符合预期，把**剩余 9 个 Go 组件 + 4 个外壳整体**一起做这个替换（正式的 0.4 节内容），此时再回头判断 `infra/shell-compose.yml`/`Makefile` 那几个目标要不要删——不在这一步就删，先留着做对照，等 0.4/0.5 全部跑通、新旧两条路径生成的最终拓扑（`docker ps` 输出）逐字对比一致之后再删。
5. 记录一个明确的决策：删，还是保留（如果发现有旧方案做得到、新方案做不到的事，比如健康检查探针的具体参数、启动顺序控制粒度，就不删，把差异记录清楚）。

**验证标准**：第 3 步的 4 项检查全部通过，且第 4 步全量替换后 `docker ps`/`kubectl get pods` 展示的最终拓扑跟旧方案（阶段四已经验证过、写在 `docs/plans/04-阶段四-做外壳验拆回.md` Task 6 的记录）完全一致。

### 0.1 真机执行记录（2026-09-14，最小子集实验）

**做法**：新建一个临时 local source（`sources:` 新增一条 `servedby-poc-source`，指向 scratchpad 下一个临时目录），写一份最小 `component.yaml` 声明 `infra/go-core-shell-poc@1.0.0`（镜像用已经构建过的 `brickenterprise/be-shell-go:local`，端口 9000，`healthCheck.path: /healthz`）。把 `mdm/customer`/`mdm/product` 的 `local: true`/`localPort` 两行改成 `servedBy: infra/go-core-shell-poc@1.0.0`。其余 12 个组件原样不动（仍是阶段四遗留的 `local: true`/独立部署混合状态）。

**⚠️ 真实撞到的问题（不是纸面推演）**：第一次 `brickkit up --dry-run` 直接报错：

```
❌ 错误：外壳 infra/go-core-shell-poc@1.0.0 下两个成员对同一个透传标签给出了不同的值
   标签键：prometheus.io/port
   mdm/customer@1.0.7：8080
   mdm/product@1.0.8：8082
```

根因：`mdm/customer`/`mdm/product` 的 `component.yaml` 都在 `deployment.labels` 里声明了 `prometheus.io/port`，值分别是各自的端口号——这是两个组件本来就该有、且理所当然应该不同的值，不是巧合冲突。`servedBy` 的 labels 合并规则是"同名同值跳过，同名不同值报错"（跟 env 变量的合并规则形状一样），但**跟 env 变量的合并不同，labels 没有做"只合并某一类、其它类无条件排除"这层收窄**——`*_ENDPOINT` 类环境变量因为语义上"整个外壳内必须一致"，合并+冲突检测是对的；但 `prometheus.io/port` 这类**语义上就是"每个组件各不相同"**的标签，被套用同一条合并规则，导致任何两个都声明了各自 `prometheus.io/port` 的组件，只要被收编进同一个外壳，必定 100% 撞车报错——这跟 `COMPONENT_ID`/`COMPONENT_VERSION` 在 env 合并里"因为必然不同所以被无条件排除"是同一类问题，只是这次发生在 labels 侧，而 labels 侧没有对应的收窄处理。

**临时绕过方式**（只为了让这次最小实验能继续往下验证，不是正式修法）：临时从 `mdm/customer`/`mdm/product` 的 `component.yaml` 里删掉 `prometheus.io/port` 这一行（保留 `prometheus.io/scrape`/`prometheus.io/path`，这两项两个组件本来就写的同一个值，不受影响），验证完立刻 `git checkout -- component.yaml` 还原，两个组件仓库确认过还原后 `git status` 干净。

**绕过之后，`brickkit up --dry-run` 成功，生成结果符合预期**：

```yaml
infra-go-core-shell-poc-1-0-0:
  environment:
    - BRICKKIT_SERVED_MEMBERS=mdm-customer-1-0-7,mdm-product-1-0-8
    - COMPONENT_ID=infra/go-core-shell-poc
    - COMPONENT_VERSION=1.0.0
  networks:
    brickkit-net:
      aliases:
        - mdm-customer-1-0-7
        - mdm-product-1-0-8
```

`mdm-customer-1-0-7`/`mdm-product-1-0-8` 没有生成独立 service（确认 `grep -c` 命中 0）。挑了一个真实存在弱依赖的独立组件 `infra-bff-mobile`（未受这次实验影响，仍然独立部署）核对地址路由：

```yaml
infra-bff-mobile-1-0-17:
  environment:
    - MDM_CUSTOMER_ENDPOINT=http://mdm-customer-1-0-7:8080
    - MDM_PRODUCT_ENDPOINT=http://mdm-product-1-0-8:8082
```

地址正确指向外壳容器的网络别名 + 各成员自己的端口——跟阶段四手写 `shell-compose.yml` 达到的效果一致，且不需要我们自己写任何 `extra_hosts`/别名逻辑。`erp-sales`/`erp-inventory`/`infra-workflow` 这几个仍是 `local: true` 的组件，`infra-bff-mobile` 拿到的地址走的还是旧的 `host.docker.internal`+`extra_hosts: host-gateway`——确认 `local:true` 和 `servedBy` 在同一份 `brickkit.yaml` 里确实互不干扰，不是只信 brickKit 自己的回归测试。

**清理**：`git checkout -- brickkit.yaml`、两个组件仓库 `git checkout -- component.yaml`，删除临时 source 目录，`.brickkit/manifests/` 下这次实验产生的缓存文件手动清掉，`brickkit restore` 确认"14 个活跃，0 个归档，0 个激活"，`git status --porcelain` 全仓库确认干净。

**结论**：
1. 核心判断成立——`servedBy` 确实能在一条 `brickkit up` 里正确生成"部分独立、部分收编"的混合拓扑，网络别名、地址路由、`local:true` 共存全部符合预期，`infra/shell-compose.yml`/`shell-up`/`teardown-up` 大概率真的可以退休（留到 0.4 全量切换、跟旧拓扑逐项对比后再做最终决定，不在这里就下最终结论）。
2. **发现一个值得反馈给 brickKit 的真实问题**：`servedBy` 的 labels 合并没有像 env 变量合并那样，把"语义上必然因组件而异"的标签（`prometheus.io/port` 是最常见、几乎每个组件都会写的例子）排除在合并范围之外，导致这类标签在任何多成员外壳里几乎必然撞车。这个问题会**直接挡住 0.4 节的全量迁移**（我们 11 个 Go 组件的 `component.yaml` 全部声明了各自的 `prometheus.io/port`），需要在 0.4 之前决定怎么处理——要么我们自己把这类标签从 `servedBy` 成员的 `component.yaml` 里移除、只在外壳自己的条目上写一份（跟"合并后指标只能走一个共享端口"这个事实保持一致），要么等 brickKit 那边看有没有必要收窄 labels 合并规则。这条因为会直接挡住 0.4 节全量迁移，不等到 Task 14 收尾才反馈——已提前写成一次性反馈文档 `docs/dev/brickKit反馈-servedBy的labels合并漏了排除规则.md`，交给 brickKit 判断修复方向。0.4 节开始前先看有没有回音，没有的话就先按方向一（我们自己临时去掉这批标签）继续推进，不空等。

### 0.2 调研记录：`be-ops` 产出 4/7/8 是否还需要——结论比原计划预期的更深一层

**没有照原计划的步骤 1（真机跑一次实验）走**：0.1 的真机实验已经留下了足够的证据（见上面 0.1 记录里贴出的生成 compose 片段——外壳容器只拿到 `BRICKKIT_SERVED_MEMBERS=mdm-customer-1-0-7,mdm-product-1-0-8`，没有端口/schema/任何 config 值），不需要重新起一次容器验证同一件事。这次改成直接读 `be-ops`/`shells/go`/brickKit 三边源码，把"外壳启动器到底还缺什么数据、这些数据本该从哪来"这件事看透。

**读代码读出来的结论，跟原计划预期的不一样**：原计划只预期缺"端口/schema"，实际缺口更大——缺**整个模块自己的 `configSchema` 解析结果**（`pgSchema`、`otelBaseUrl`、`authzBundleUrl`、`iamJwksUrl`，以及未来任何组件自己声明的 configSchema 项）。逐条说清楚：

1. **产出 4（`shellconfig`）本来就没绑定 `local:true`，不用动**：`tools/be-ops/internal/shellconfig/gen.go` 的 `Gen` 只读 `genyaml.ComponentSpec`（来自每个组件自己的 `component.yaml`/`assembly.yaml`，跟 `brickkit.yaml` 此刻写的是 `local:true` 还是 `servedBy` 完全无关），产出 `ComponentID`/`Version`/`Schema`/`HTTPPort`/`ExtraPorts`——这几项从一开始就不依赖 `local:true`，迁移到 `servedBy` 之后原样可用，不需要因为这次迁移改代码。
2. **产出 7（`shellenv`）的"地址改写"那部分逻辑，被 `servedBy` 原生取代**：`shellenv.Gen` 的核心工作是把 `local-debug.<service>.env` 里 `http://localhost:<port>` 形式的依赖地址，按"同外壳用 127.0.0.1、跨外壳用 host.docker.internal"改写——这正是 `internal/shell.exportDependencyEndpoints`（`shells/go/internal/shell/shell.go:122`）加上产出 7 联手做的事。`servedBy` 落地后，brickKit 自己在生成阶段就把 `*_ENDPOINT` 类变量直接合并进外壳容器自己的 `environment`（0.1 真机验证过：`MDM_CUSTOMER_ENDPOINT=http://mdm-customer-1-0-7:8080` 直接在外壳的 compose service 里，不需要任何改写），这部分逻辑确认可以整个删掉，`exportDependencyEndpoints` 那个 `os.Setenv` 循环也一并删。
3. **但产出 7 还有第二个职责，原计划没意识到，且这部分职责在 `servedBy` 下反而没了数据来源**：`shellenv.Gen` 的输入 `localDebug map[string]map[string]string` 来自 brickKit 生成的 `local-debug.<service>.env` 文件（`brickKit` 仓库 `internal/compose/local.go:469` 的 `localEnvFiles`）——这份文件不只包含依赖地址，还包含这个组件**完整的 `configSchema` 解析结果**（`pgSchema`/`otelBaseUrl`/`authzBundleUrl`/`iamJwksUrl` 等），这些值经过 `shells/go/internal/shell/shell.go:180` 的 `besdk.NewShellRuntime(... Env: m.Env ...)` 直接喂进每个模块自己的 `rt.Config`——这是模块读自己配置项的**唯一来源**（十七条第 16 条：模块代码零 `os.Getenv`，只走 `rt.Config`）。
   **关键点**：`local-debug.*.env` 只在组件是 `local: true` 时才生成（`internal/compose/local.go` 整个文件就是 `local: true` 专属机制），`servedBy` 成员根本不会有这份文件——`servedBy` 成员既不生成容器，也不是 `local:true`，brickKit 目前**没有为它生成任何等价的产物**。也就是说，产出 7 现在唯一还有意义的那部分职责（把模块自己的 `configSchema` 值喂给它），换了 `servedBy` 之后反而彻底没了数据来源，不是"被原生取代"，是"原来的数据源不存在了"。
4. **不过这份数据 brickKit 自己其实是算出来过的，只是没存下来**：读 `internal/shell/shell.go:112` 的 `Resolve(cfg, graph, states, env *inject.Result)`，参数 `env` 是**全部组件**（含 `servedBy` 成员）已经跑完注入引擎、算出完整 `[]inject.Var` 的结果——`Resolve` 内部只是从这份已经算好的结果里挑出 `Source == inject.SourceEndpoint` 的那一部分去合并，其余的（`pgSchema` 等 configSchema 值）算是算了，只是没有被写进任何生成物，直接在内存里被丢弃。**这跟产出 7 自己文档注释那句"自己另算的那份，早晚和平台的算法分叉"说的其实是同一类风险**——地址改写那部分我们不用再算了（brickKit 自己在合并；我们算了才叫"另算一份"），但 configSchema 解析这部分，"另算一份"仍然是唯一可行路径，因为 brickKit 根本没打算把这部分暴露出来给 `servedBy` 场景用。
5. **产出 8（`shelldepends`）确认整个退休**：跟产出 7 的地址改写部分是同一类——外壳之间的启动顺序现在由 `servedBy` 原生的 `depends_on` 改写覆盖（0.1 真机验证过 `infra-bff-mobile` 的 `depends_on` 正确指向外壳），`shelldepends.Gen` 算的那条边完全重复。

**决定用哪个候选方案（在原计划①②基础上做了修正）**：
不是"registry.tsv 编译期静态映射"（候选①——`authzBundleUrl`/`iamJwksUrl` 这类值根本不在任何 registry 表里，它们是 `brickkit.yaml` 每个组件条目自己手写的 `config:` 字面量，逐环境可能不同，编译期写死这条路完全走不通），也不是"继续用 brickKit 生成的产物做数据源"（0.2 执行前设想的候选②——这条路现在没有数据源了，见上面第 3 点）。

改成**候选②的修正版：把 `configSchema` 解析这件事挪进 `be-ops` 自己做，但只做"配置合并"这一层最简单、最不容易跟平台分叉的部分，不碰地址改写**：
- 扩展 `genyaml.Load`：除了现在已经读的 `component.yaml`/`assembly.yaml`，新增解析 `brickkit.yaml` 根文件里每个组件条目的 `config:` 块（字面量覆盖）+ `component.yaml` 的 `configSchema.properties.<key>.default`（缺省值）——合并规则是"`brickkit.yaml` 里写了就用那个值，没写就退回 `component.yaml` 的 `default`，两边都没有就不产出这个 key"，跟 brickKit 自己的注入引擎对 `configSchema` 项的既有语义一致（读的是同一份 `brickkit.yaml`/`component.yaml`，不是凭空猜一份新算法，风险跟"另算地址改写"不是同一个量级——这里没有"同外壳/跨外壳"这类需要跟平台判断口径保持一致的分支逻辑，纯粹是两份已知 YAML 的字段合并）。
- `shellconfig.Module` 新增一个 `Config map[string]string` 字段承载这份合并结果。
- 产出 7（`shellenv`）、产出 8（`shelldepends`）两个包整体删除，连同 `tools/be-ops/cmd`/`Makefile` 里调用它们的子命令/目标。
- `shells/go/cmd/shell/main.go`：`buildModules` 不再读 `SHELL_ENV_JSON`，`ModuleSpec.Env` 直接来自产出 4 新增的 `Config` 字段；`internal/shell/shell.go` 的 `exportDependencyEndpoints` 整段删除（含它的调用点），因为 `*_ENDPOINT` 现在已经是外壳容器自己 `os.Environ()` 里现成的值，`besdk.Endpoint()`/`MustEndpoint()` 直接就能读到，不需要外壳自己再 `os.Setenv` 一遍。
- `shells/python` 同理对称修改。

这份决定目前只是"调研 + 决定方向"，实际代码改动放进 0.2 的下一步（跟 0.3 一起做，因为两者互相依赖——0.3 本来就要改 `buildModules`，一次改完比分两次改更不容易中间态出错）。

### 0.2 原计划（存档，已被上面的调研结论取代，保留是为了看清判断是怎么被推翻的）

**要验证的具体问题**：
- 外壳启动器现在装配一个模块需要哪些数据：componentId（来自 `BRICKKIT_SERVED_MEMBERS`）、HTTPPort（缺口，需要另找来源）、Schema（缺口，需要另找来源）。
- `shellenv`（产出 7）产出的跨组件地址改写，是不是已经被平台原生的 `*_ENDPOINT` 合并机制完全取代。
- `shelldepends`（产出 8）产出的外壳间启动顺序，是不是已经被平台原生的 `depends_on` 改写完全取代。

**具体步骤**：
1. 对 0.1 步骤 2 的最小子集实验，检查生成的 compose 里 `mdm/customer`/`mdm/product` 对应的模块，端口/schema 信息有没有任何来源——如果外壳容器只拿到了 `BRICKKIT_SERVED_MEMBERS`（一串版本化服务名字符串），没有拿到端口/schema，就确认了"外壳启动器需要另一个数据来源"这个缺口真实存在。
2. 评估两个候选方案：① 外壳启动器代码里维护一份编译期静态映射（componentId → schema/端口，从 `registry/ports.tsv`/`registry/schemas.tsv` 生成，构建时嵌入二进制，不依赖运行时文件）；② 继续用 `be-ops shell-config` 产出一份轻量数据文件，只保留端口/schema 这两项，去掉已经被 `BRICKKIT_SERVED_MEMBERS`/平台原生合并取代的部分。两个方案各自的优缺点记录下来，选一个。
3. 决定后，实际去改 `tools/be-ops/internal/shellconfig`（如果选方案②，简化产出内容）或者废弃它（如果选方案①）。

**验证标准**：不管选哪个方案，`shells/go`/`shells/python` 的模块装配代码最终能拿到装配一个模块所需的全部数据（componentId、端口、schema），且不再依赖 `shellenv`（产出 7）/`shelldepends`（产出 8）产出的数据（这两项预期会被平台原生机制完全取代，真机确认后可以直接废弃这两个 `be-ops` 子命令）。

### 0.3 计划：`shells/go`/`shells/python` 接上真实 `BRICKKIT_SERVED_MEMBERS`

**具体步骤**：
