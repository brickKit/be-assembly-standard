## 顺序原则，和为什么

1. **骨架先于迁移**：外壳启动器要先能"装 0 个模块也启动成功"，再往里加真实模块——这是阶段一"先立最小可运行骨架，
   再填内容"这条节奏在外壳工程上的应用，不是新规则。
2. **`be-ops` 的产出 4/7/8 要等外壳骨架先长出真实形状**：产出 4（合并清单）要读外壳启动器实际认得的配置格式，
   产出 7（环境变量表）要对齐外壳启动器实际读 env 的方式——**先有骨架，`be-ops` 才有真实的生成目标**，反过来
   做（先臆想一份格式，`be-ops` 先生成，外壳骨架再去适配）大概率走两遍。
3. **迁移顺序沿用组件各自当初被建出来时验证过的依赖顺序**：`mdm-customer`/`mdm-product` 零依赖，最先迁；
   `erp-inventory`/`erp-finance` 次之；`erp-sales` 要等前两个都迁完（它是唯一同时调三个强依赖的组件）；
   `infra-authz`/`infra-iam-casdoor` 再之后（`erp-sales`/`crm-opportunity` 等组件的权限判定要靠它们）；
   `crm-opportunity` 最后（触发全链路的起点）。**不是重新论证一遍依赖图，是直接照抄阶段二/三已经验证过的
   那张图**——合并顺序和当初的建造顺序没有必然关系，但这次刚好一致，省得重新排一遍。
4. **Python 外壳（Task 7）可以和 Go 外壳的迁移（Task 5–6）并行**：两者除了都要复用 Task 2/3 的骨架经验之外
   没有依赖关系，`infra-print` 不依赖任何 Go 组件。
5. **验收（Task 9–11）必须等全部迁移完成之后**：合并态业务闭环用的是附录 E 全链路，链路上的每一环都要真的在
   外壳里——迁移过程中的中间态没有验收意义，只有调试意义。

#### Task 2：`be-sdk-go` 补外壳级构件 + `be-shell-go` 骨架 ✅ 已完成（CP-18 已建仓库）

⚠️ **本任务的核心判断：外壳启动器不能重新发明一遍 `RunStandalone` 已经做对的事。** `be-sdk-go` 的
`RunStandalone` 目前是"一个进程只装一个模块"的形状（`standalone.go`）：一次 `Bootstrap`（OTel）、一个连接池、
一次 `newModule` 调用、`Listen`。外壳要做的是"一个进程装 N 个模块"——**如果 `be-shell-go` 自己从零重新实现
读环境变量/建连接池/起 gRPC server 这些逻辑，等于把 A4g 那次真实教训（"测试用的构造路径和生产用的构造路径
不是同一条路径"）在 11 倍的爆炸半径上重演一遍**。正确做法：`be-sdk-go` 把 `RunStandalone` 内部已经用得很稳的
几块拆成可独立调用的导出函数，`be-shell-go` 直接复用这几块，只是循环调用 N 次、每次传不同的 `rt`：

- [x] `be-sdk-go@v0.2.6/v0.2.7` 新增导出函数：`NewShellRuntime`（构造单个模块的 `Runtime`，连接池由调用方
      传入不再自己开）、`InitShellAuthz`（整个外壳只调一次，不是每模块各调——发现 `authzRuntime` 是包级
      全局单例，照搬 `RunStandalone` 会导致后面的调用悄悄覆盖前面的、且 N-1 个 bundle 轮询 goroutine 永久
      泄漏，这条不是从设计书推演出来的，是读 `authz.go` 源码时发现的真实缺口）、`ServeHTTP`/`ServeExtraPort`
      （`serveHTTP`/`serveExtraPort` 的导出别名）、`BuildPGDSN`/`BuildNATSURL`（外壳级共享连接串复用，不是
      每模块各一份）。`Bootstrap` 本来就是导出的，外壳直接复用，只调一次。4 条新测试全绿，`make test`
      （-race）全量回归无破坏
- [x] `be-shell-go` 骨架（`shells/go/`，CP-18 已建仓库、已 submodule add 接进军火库）：
      - `internal/shell.Run`：`Bootstrap` 一次 → 开一个共享 `*sql.DB`/`*nats.Conn` → `InitShellAuthz` 一次 →
        按 `cfg.Modules` 顺序逐个调 `New` → 按同一顺序逐个跑迁移 → `errgroup.Group` 一起 `Listen` → 任一失败
        或 `ctx` 取消，全部优雅退出
      - 迁移执行：`golang-migrate/v4/source/iofs` 直接吃 `*besdk.Module.Migrations`（各组件 `migrations` 包
        用 `//go:embed *.sql` 导出的 `fs.FS`），DSN 用外壳共享串 + 按模块 `schema` 追加
        `search_path`/`x-migrations-table`——与全拆态迁移容器共用同一份 `.sql` 文件，不新建一份
      - 共享连接池：`besdk.WithTx(ctx, db, role, schema, fn)` 本来就是参数化的，外壳传共享 `db` +
        每个模块自己的 role/schema 直接复用，不需要单独抽一层（`_调研记录/04-阶段四.md` 待核实清单第 3 条
        已确认）
      - **外壳自己的健康检查（`Config.HealthPort`）**：计划原文没有覆盖到，写骨架时发现"11 个模块各有
        各的 `/healthz`，谁的代表整个容器"这个问题平台不会替外壳回答——加了一个独立于任何模块的最小
        `/healthz`（不查任何模块、不查任何依赖，同既有判据），供 Task 4/8 的 `shell-compose.yml` 健康检查
        探测
      - 空转验证：3 条测试全部用假模块，不依赖任何真实组件仓库/真实 Postgres（`sql.Open` 是懒的，`nats.Connect`
        需要真实可达的 NATS）——两个假模块共享 DB/NATS 但各自字段独立、`ctx` 取消后优雅关闭且 `Stop`
        都被调用、`HealthPort` 独立于任何模块响应
      - **单模块 `Start()` 里 panic 不崩溃整个进程**：写测试时才发现的真实缺口——`RunStandalone` 的等价
        调用不需要这层 `recover`（单模块进程整个崩溃退出正是正确行为，Docker 重启策略负责），外壳把 N 个

        `recover` 并转成清楚指出 `componentID` 的 error，测试验证过 recover 真的生效
      - `go.mod` 遇到一次生态地板上移（`golang.org/x/sync@v0.23.0` 要求 `go >= 1.26`，第三次同类问题，
        见 D0/C16）——核实只是 `errgroup` 这一个小包的要求，改用 `v0.22.0`（同样支持 `errgroup.Group`，
        `go.mod` 地板仍是 `1.25.11`）原地解决，不牵动全项目的 Go 版本，真机 `docker build`（`golang:1.25-alpine`）
        构建通过
