## 顺序原则，和为什么

1. **骨架先于迁移**：外壳启动器要先能"装 0 个模块也启动成功"，再往里加真实模块——这是阶段一"先立最小可运行骨架，
   再填内容"这条节奏在外壳工程上的应用，不是新规则。
2. **`be-ops` 的产出 4/7/8 要等外壳骨架先长出真实形状**：产出 4（合并清单）要读外壳启动器实际认得的配置格式，
   产出 7（环境变量表）要对齐外壳启动器实际读 env 的方式——**先有骨架，`be-ops` 才有真实的生成目标**，反过来
   做（先臆想一份格式，`be-ops` 先生成，外壳骨架再去适配）大概率走两遍。
3. **迁移顺序沿用组件各自当初被建出来时验证过的依赖顺序**：`mdm-customer`/`mdm-product` 零依赖，最先迁；
   `erp-inventory`/`erp-finance` 次之；`erp-sales` 要等前两个都迁完（它是唯一同时调三个强依赖的组件）；
   `infra-authz`/`infra-iam-casdoor` 再之后（`erp-sales`/`crm-opportunity` 等组件的权限判定要靠它们）；
   `crm-opportunity` 最后（触发全链路的起点）。**不是重新论证一遍依赖图，是直接照抄阶段二/三已经验证过的
   那张图**——合并顺序和当初的建造顺序没有必然关系，但这次刚好一致，省得重新排一遍。
4. **Python 外壳（Task 7）可以和 Go 外壳的迁移（Task 5–6）并行**：两者除了都要复用 Task 2/3 的骨架经验之外
   没有依赖关系，`infra-print` 不依赖任何 Go 组件。
5. **验收（Task 9–11）必须等全部迁移完成之后**：合并态业务闭环用的是附录 E 全链路，链路上的每一环都要真的在
   外壳里——迁移过程中的中间态没有验收意义，只有调试意义。

## 第 0 部分 · 调研与外壳骨架（Task 1–3）

#### Task 1：SOP-R 调研

按 [`02-reference-implementation-standard.md`](../standards/02-reference-implementation-standard.md) §1 的三步法：
先想清楚自己的方案，再去看别人怎么做，最后自己决定怎么写——**这次"别人"不是某个开源 ERP，是 brickKit 平台自己
关于合并部署的第一手材料**：

- [ ] 通读 brickKit 仓库 `组件合并部署.md` 全文（不是只读设计书 §13 的转述——转述发生在阶段零，本阶段是第一次
      真正要动手实现，原文里第 4/7 节的实现细节转述时可能被简化过，要回去核对）
- [ ] Go 侧：调研"一个进程内跑多个独立 `http.Server`/`grpc.Server`，各自 `Listen` 不同端口，用
      `errgroup.Group`（或等价机制）统一管理生命周期、任一个失败就整体优雅关闭"这类现成模式——**不是要抄一个
      框架**，是确认这个形状在 Go 生态里是不是常规做法，有没有已知的坑（比如 `errgroup` 的 `WithContext` 取消
      语义、多个 `Listen` 共享同一个 OS 信号处理器怎么避免重复注册）
- [ ] Python 侧：调研单进程内跑多个 ASGI app 各自绑定端口的可行做法（`uvicorn` 是否支持一个进程多个
      `Server` 实例；或者干脆每个模块起一个 `asyncio.Task` 跑自己的 `uvicorn.Server().serve()`）——本阶段只有
      1 个 Python 模块，这条调研主要是为阶段五/六真的有第二个 Python 组件时不用重新调研
- [ ] 核对 `module.New(ctx, rt) (*besdk.Module, error)` 的公开性：确认这个函数确实放在每个组件的
      `backend/module/` 包（不在 `internal/` 下），外壳能正常 `import` 到——**已核对 `mdm-customer` 一例为真**
      （`backend/module/module.go` 的包注释原话："外壳启动器与 be-ops 产出 4 都按它生成"），本任务要把全部
      11 个 Go 组件都核一遍，确认没有一个把 `module.New` 不小心放错目录
- [ ] 判断 `be-shell-go` 引入 11 个组件模块的具体方式：**直接把每个组件当成普通 Go 依赖**（`go.mod` 里
      `require github.com/brickKit/mdm-customer v1.0.5` 这一类，像用任何第三方库一样，因为这些仓库本来就是
      公开 tag 过的独立 Go module），不是用 `go.work` 做本地多仓库联调（`go.work` 更适合"边改组件边改外壳"的
      本地开发场景，最终构建产物不应该依赖它）——**本地开发时可以用 `go.work` 提效，但 `Dockerfile` 构建必须
      只依赖 `go.mod`/`go.sum`**，否则镜像构建会因为找不到 `go.work` 引用的本地路径而失败

**验证：** 调研记录写完后，能不能不看设计书、只看调研记录，把"外壳启动器大致要做哪几件事"讲清楚——讲不清楚
说明调研深度不够，要继续读。

#### Task 2：`be-sdk-go` 补外壳级构件 + `be-shell-go` 建仓库 → CP-18 → 骨架

⚠️ **本任务的核心判断：外壳启动器不能重新发明一遍 `RunStandalone` 已经做对的事。** `be-sdk-go` 的
`RunStandalone` 目前是"一个进程只装一个模块"的形状（`standalone.go`）：一次 `Bootstrap`（OTel）、一个连接池、
一次 `newModule` 调用、`Listen`。外壳要做的是"一个进程装 N 个模块"——**如果 `be-shell-go` 自己从零重新实现
读环境变量/建连接池/起 gRPC server 这些逻辑，等于把 A4g 那次真实教训（"测试用的构造路径和生产用的构造路径
不是同一条路径"）在 11 倍的爆炸半径上重演一遍**。正确做法：`be-sdk-go` 把 `RunStandalone` 内部已经用得很稳的
几块拆成可独立调用的导出函数，`be-shell-go` 直接复用这几块，只是循环调用 N 次、每次传不同的 `rt`：

- [ ] `be-sdk-go` 新增导出函数（具体签名留给实现时定，方向已经明确）：
      - 一个"构造单个模块的 `Runtime`"的函数（读该模块自己的 env 前缀、建该模块自己的 `configSchema` 映射，
        **但连接池由调用方传入，不再自己开**——这是和 `RunStandalone` 最大的差异点，池必须是外壳级共享的）
      - 一个"起 HTTP/gRPC server 并注册进统一生命周期管理"的函数（`serveHTTP`/`serveExtraPort` 现在是
        `standalone.go` 内部私有函数，导出后供外壳按模块循环调用）
      - `Bootstrap`（OTel）保持**只调一次**，在外壳启动最开始——这是唯一一处"进程级只做一次"的地方，不能
        按模块循环调
- [ ] `be-shell-go` 骨架（`shells/go/`）：
      - 读取 `be-ops` 产出 4 生成的合并清单（这一步依赖 Task 4，骨架先写成"读一份手写的临时清单"占位，
        Task 4 做完后换成真正读生成产物）
      - 共享连接池：一个 `*sql.DB`，每个模块通过 `SET LOCAL ROLE`/`SET LOCAL search_path` 切换身份
        （设计书 §13.3 铁律二的实现），**这一段逻辑如果 `be-sdk-go` 的 `WithTx` 已经是这个模式，直接复用，
        不要在外壳里再写一遍事务包装**
      - 按拓扑序跑迁移（铁律五：合并后平台不再管迁移，外壳自己按序跑，失败即中止启动）
      - 健康检查聚合：**外壳自己的 `/healthz` 只查"进程还活着"，不聚合任何模块的状态**（设计书 §13.6：
        "健康检查……一个容器一个 probe，任何一个模块把进程拖死，整组一起重启"——这不是要外壳去检查 11 个模块
        分别健不健康，是外壳作为一个容器整体只有一个 probe，这个 probe 依然遵守"不查依赖"这条铁律）
      - 空转验证：**先不装任何真实模块**，跑一个假的最小 `module.New` 验证整套骨架能启动、能优雅关闭、
        单个模块 panic 不拖垮整个进程（同 `be-sdk-go` C11 的教训：gRPC 面必须有 panic-recovery，外壳这里
        风险更高——11 个模块共享一个进程，任何一个模块的一次 panic 现在能拖走另外 10 个）

**验证：** 用一个假的、什么都不做的 `module.New` 实现，起 `be-shell-go`，确认容器 `healthy`、能优雅关闭
（`docker stop` 走 SIGTERM，确认所有 `Listen` 都正确退出，不是被强杀）；故意让假模块的 `Start()` 返回一个
panic，确认外壳能 `recover` 住且日志清楚指出是哪个模块 panic 的，不崩溃整个进程。

#### Task 3：`be-shell-python` 建仓库 → CP-19 → 骨架

同 Task 2 的判据，Python 版。**本阶段只准备装 1 个模块**（`infra-print`）——骨架仍然要按"能装 N 个"的设计写
（不能因为现在只有 1 个就写死成单模块专用），但验收范围只到"装 1 个模块能跑通"，不需要在没有第二个 Python
组件之前假想多模块场景硬造一个测试。

- [ ] `be-sdk-python` 是否需要同 Task 2 一样拆出可复用构件——**大概率需要**，判断方式一致：`run_standalone`
      现在是"一个进程一个模块"的形状，外壳需要的是"每个模块自己的 `Runtime`，池共享"这个模式
- [ ] ASGI 应用的合并方式：`Starlette`/`FastAPI` 支持用 `Mount` 把多个子应用挂在同一个 `uvicorn.Server`
      下共享一个端口，但设计书 §13.3 铁律三要求"每个组件的 `deployment.port` 必须独立"——**不能用 `Mount`
      这种"同端口不同路径"的方案**，必须是"同进程、不同端口，每个模块各自的 ASGI app 各自绑一个
      `uvicorn.Server` 实例，用 `asyncio.gather` 一起跑"

**验证：** 同 Task 2，用假模块验证骨架本身（能起、能优雅关闭、单模块异常不拖垮进程），这次额外验证
"1 个模块"这个退化场景本身没有因为"只有一个"而抄了近路（比如误把外壳级的池/配置逻辑跳过，直接照抄
`run_standalone` 的单模块逻辑）——**外壳骨架必须走"N 模块"的那条代码路径，即使 N=1**，否则阶段五/六真的
装第二个 Python 模块时，骨架代码本身还要重写一遍。

- [ ] **产出 7（每外壳环境变量表）**：按设计书 §13.8.2 的规则——同外壳依赖用

      `brickkit up --dry-run` 生成的 `local-debug.*.env` 作为输入，只重写依赖地址那几行，其余原样**（§13.8.2
      原话："自己另算的那份，早晚和平台的算法分叉"）——这意味着 Task 4 依赖每个即将合并的组件先在
      `brickkit.yaml` 里被标成 `local: true`（否则平台不会为它生成 `local-debug.*.env`），这一步的具体时机
      在 Task 5/6 迁移时同步做，不是 Task 4 自己单独一步
- [ ] **产出 8（shell-compose 的 `depends_on`）**：外壳一必须最先起（主数据在里面），其余外壳依赖它做
      `batchGet` 校准对账——本阶段只有 1 个 Go 外壳 + 1 个 Python 外壳，`depends_on` 关系比设计书 §13.8.3
      描述的"五外壳"简单得多（Python 外壳的 `infra-print` 零依赖，不需要等 Go 外壳启动完成）

**验证：** 用 Task 5 迁移的头两个组件（`mdm-customer`/`mdm-product`）跑一遍产出 4/7/8 的生成，人工核对生成的

确认生成过程能报错而不是静默生成一份错误清单。
