## 整体结构：三个维度交叉，不是"排完 12 个再叠版本"

⚠️ **2026-09-16 结构性修订**（正式开始执行前的最后一次计划审查）：原计划把"多版本共存"当成 Task 1-12 做完之后再展开的独立一层（Task 13），审查时发现这个安排低估了它——多版本必须跟"环境"“拓扑"两个维度交叉着测，不是叠在最后的附加层。同时发现"纯外壳"这个拓扑分类此前从未真正"纯"过（见下面组件参与清单的说明）。修订后是三个维度：

- **维度一·环境**：本地 / Docker / Docker+本地混合 / K8s（4 档，K8s 不跟前两者混——Pod 与宿主机网络隔离，`local:true` 在 K8s 下被平台直接拒绝，这条 `servedBy` 落地前后没有变化）。
- **维度二·拓扑**：纯组件 / 纯外壳 / 混搭（3 档）。
- **维度三·版本**：单版本（baseline）/ 多版本的若干子场景（同外壳两版本、独立+servedBy 撞车、两个外壳分served两版本、一个合并一个独立、多版本+混搭+本地调试）。

**三个维度不做机械全排列**（4×3×N 会炸成几十个任务，且大部分格子测的是同一件事）。维度一、二先排出 12 个 baseline 任务（Task 1-12，单版本），维度三（Task 13 的各子场景）分别挑**最有信息量的环境/拓扑组合**去测、并写明为什么选它、为什么不需要测其它格子——这个理由本身就是交付物的一部分，不是偷懒的借口。**肯定会报错的组合也要真机构造、记录报错内容和理由**，不能因为"预期会失败"就跳过不测。

1. **Task 0**：把 `be-assembly-standard` 自己从"挪用 `local:true`"迁移到真实 `servedBy`——✅ 已完成。
2. **Task 1-12**：组合矩阵本体（维度一 × 维度二 的 12 个单版本 baseline，见下面的矩阵总览）。
3. **Task 13**：多版本共存——维度三跟前两个维度交叉的部分，6 个子场景。
4. **Task 14**：`local:true` + K8s 目标的负向验证——确认"生成阶段直接报错"这条反复引用的结论真的成立，本项目从没真机验证过。

**"Docker+本地混合"的准确定义**：绝大部分组件走 Docker（不管是独立部署还是被某个外壳收编），额外挑 1 个**完全独立**的组件（不受 `servedBy` 影响）用 `local: true` 拉到宿主机调试——这是唯一一种 `local:true` 和"这次测的拓扑"会同时出现在同一份 `brickkit.yaml` 里的组合，brickKit 自己的回归测试（`TestLocalStillWorksAlongsideServedBy`）已经确认两者不冲突，我们要做的是在自己的真实组件上复核一遍，不是重新怀疑这个结论。

**"纯本地"（Task 1/4/9）的准确定义，区别于"Docker+本地混合"**：这次审查确认"本地"是跟"Docker+本地混合"并列的独立一档，不是它的子集——意味着"纯本地"任务里**全部参与组件都跑成宿主机裸进程**（`go run`/`uvicorn` 之类，手动喂环境变量模拟平台注入），不借助 `local:true` 机制（那个机制的前提就是"其它组件在 Docker 里跑着"，属于"Docker+本地混合"那一档）。Task 9（混搭×本地）因此是：至少一个外壳用 `go run` 方式跑在本地、至少一个独立组件也跑成裸进程，两者之间做一次真实调用确认互通。

## Task 13：多版本共存（维度三，跟前两个维度交叉，不是排完 12 个才展开的独立附加层）

⚠️ **每个子场景都要明确写出"选了哪个环境/拓扑去测、为什么选它、为什么不需要测其它格子"**——这个理由本身是交付物的一部分。子场景列表（真机调研阶段已经摸清楚哪些有 brickKit 自己的测试佐证、哪些完全没有）：

- [ ] **13.1 同一个外壳收编同一组件的两个不同版本**：brickKit 自己有单测佐证（`TestResolveGroupsTwoVersionsOfSameComponentUnderOneShell`），但那是在 brickKit 自己仓库的隔离 fixture 里验证的，不是我们的真实组件——挑一个真实组件（比如 `mdm-customer`）真的准备两个版本，收编进同一个外壳，真机确认地址、端口、迁移都正确，且两个版本不会像 Go 语言限制那样互相冲突（这条本身可能会真的撞上"同一个 Go 二进制装不下同一 module 两个版本"这个已知的结构性限制——如果撞上了，这条子任务的产出就是确认这个限制真的成立，不是失败）。**选 Docker 环境测**（这是最贴近真实部署的形态，且这条已知风险跟环境无关，是 Go 编译期的限制，本地裸进程/K8s 不会有不同表现，不需要重复测三遍）。
- [ ] **13.2 同一个 `(id, version)` 不能同时独立部署又被 `servedBy`**：文档说是"重复声明"这条通用规则的推论，但调研没有找到直接对应的代码位置——真机构造这个场景（同一个精确版本，一条独立声明、一条 `servedBy` 声明），确认到底是报错还是别的行为，不能只信文档。**选 `--dry-run` 测，不需要真的起容器**——这类校验发生在 manifest 解析/resolve 阶段，比生成部署文件更早，Docker/K8s/本地不会有任何差异，跑 `--dry-run` 就能拿到结论，真起容器纯属浪费。
- [ ] **13.3 两个不同外壳各自收编同一组件的不同版本**——brickKit 自己完全没有测试或文档覆盖，是真正的未知领域。真机构造：外壳 A 收编 `mdm/customer@1.0.7`，外壳 B 收编 `mdm/customer@2.0.0`，确认能不能正常生成、两边地址是否正确隔离、有没有意外的交叉污染。**Docker 和 K8s 都要测**——地址解析机制两边不同（Docker 网络别名 vs K8s Service+Selector），这是唯一一个"不同环境下代码路径本身就不一样"的多版本场景，不能只测一边就下结论。这条如果真机验证通过，值得单独写一份"回复给 brickKit"的文档，因为这是连他们自己都没验证过的场景，我们的结果对他们也是新信息。
- [ ] **13.5（新增）一个版本合并进某个外壳、另一个版本完全独立部署**：brickKit 自己 `shell-implementers-guide` 文档明确描述过这个场景（"老调用方留在旧版本、独立部署，新调用方切到新版本、合并部署，两者不需要任何协调"），但只是文档转述，本项目从没真机验证过——这恰好是最贴近真实客户升级场景的组合，比 13.1/13.3 更常见。**选 Docker 测**，理由同 13.1。
- [ ] **13.4 多版本 + 混搭拓扑 + `local:true` 调试的组合**：在 13.1/13.3/13.5 任意一个场景成立的基础上，叠加"其中一个版本被临时拉到本地调试"（Docker+本地混合环境）——这是矩阵最深的一层。**选 13.5 的场景来叠**（一个合并一个独立，再把那个独立的临时拉到 `local:true`），因为这是最贴近真实开发者会遇到的组合：主线版本合并部署稳定跑着，新版本本地调试。

**验证：** 每个子场景独立真机验证，能保留成永久断言的（不依赖任何我们自己手工构造的临时环境、单纯是 brickKit 机制本身）比照 `TestPlatform26/27` 的先例固化下来；只能在特定人为构造场景下才能验证的，完整记录过程留档到 `docs/plans/04b-组合测试记录.md`。
