# 阶段四附加 · 部署矩阵验证

> **这是一份临时插入的计划，不是阶段五的一部分，也不打算重新编号进主线任务序列。** 动机很直接：现在只有 14 个真实组件，本机资源还绰绰有余；等军火库真的铺到接近 62 个组件时，光是"起一遍全部组件"这件事本身就可能撑不住本机资源，到时候再想补一遍"部署方式到底靠不靠谱"这类基础验证，成本会高得多。趁现在数量还合理，把两大部署方案（brickKit 原生独立部署 / 外壳合并部署）在三种运行环境（本地、Docker、K8s）下的组合，能验的都真机验一遍。
>
> **前置阅读**：`docs/dev/给brickKit的反馈.md` 第七部分——这份计划里"外壳 + K8s"这个组合，直接依赖那份提案里 `servedBy` 概念能不能落地；本计划把它拆成"不依赖 brickKit 表态、我们自己现在就能做的部分"和"要等 brickKit 回应才能做到理想状态的部分"两半，不是傻等。
>
> **不新建任何组件**，纯粹是对现有 14 个组件 + 两个外壳仓库的部署方式做验证，产出主要是真机验证记录和一份面向未来部署者的选型说明，不涉及业务代码改动。

## 六种组合，现状一览

| # | 方案 | 环境 | 现状 | 本计划要做的事 |
|---|---|---|---|---|
| 1 | brickKit 原生独立部署 | Docker | ✅ 阶段一到四持续在用，早已反复验证 | 不重做，Task 1 里过一遍确认仍然成立即可 |
| 2 | brickKit 原生独立部署 | 本地（`local: true` 调试） | ✅ 阶段一到四持续在用（每个组件的 `local-debug.*.env`） | 同上，Task 1 确认 |
| 3 | brickKit 原生独立部署 | K8s | ⚠️ 只做过 `--dry-run` 级别的清单校验（`TestPlatform14/15/16`），**从没真的 `apply` 到一个真实集群跑起来过** | **Task 2**：真机在 `minikube` 上跑一遍，不是纸面推演 |
| 4 | 外壳合并部署 | Docker | ✅ 阶段四 Task 6–12 反复真机验证 | 不重做，Task 1 里过一遍确认仍然成立 |
| 5 | 外壳合并部署 | 本地（外壳进程本身跑在宿主机上，不进容器） | ⚠️ 大量间接验证过（`TEST_PG_DSN`/`TEST_NATS_URL` 驱动的 `go test`），但从没有真的用 `go run cmd/shell` 起一个长期存活的宿主机进程去验证过 | **Task 1** 里补一次轻量的真机验证 |
| 6 | 外壳合并部署 | K8s | ❌ 目前结构性做不到——`local: true`（我们现在挪用来表示合并）在 K8s 下被平台直接拒绝，即使不拒绝，地址也没有平台原生支持的表达方式 | **Task 3**：不等 brickKit 表态，先用手写 K8s 清单（跟 `infra/shell-compose.yml` 是手写的同一个道理）验证"外壳镜像本身能不能在 K8s 里正常跑起来、被其它 brickKit 生成的资源正确访问到"这件事本身是不是可行 |

**本地 ↔ K8s 不在验证范围内**：Pod 所在的网络命名空间和宿主机是隔开的，`minikube` 这类本地开发集群理论上能通过 `host.minikube.internal` 桥过去，但这只在本地开发集群、且驱动支持的前提下成立，真实生产 K8s 集群完全没有"宿主机"这个概念——这是 brickKit 自己 `local: true` 在 K8s 下直接拒绝的同一条理由，我们不打算挑战它，只在 Task 4 的选型说明里如实写清楚这条限制。

## Task 1：确认已验证过的四个组合仍然成立 + 补一次外壳本地真机验证

- [ ] brickKit 原生独立部署 × Docker：`make check` + `brickkit up`（14 个组件全部 `healthy`）+ `make tier0`/`make tier1` 全绿——这条本质是"复跑一次既有验收清单确认没有回归"，不是新验证。
- [ ] brickKit 原生独立部署 × 本地：挑 1-2 个组件（比如 `mdm-customer`），真机走一遍 `local: true` 调试流程（`brickkit up --dry-run` 生成 `local-debug.*.env`，宿主机直接 `go run`/`uvicorn` 起这个组件，确认它能正常响应、其它容器能通过 `host.docker.internal` 连到它）。
- [ ] 外壳合并部署 × Docker：`make shell-up`，确认 4 个外壳容器 + 2 个独立组件全部 `healthy`——同样是复跑既有验收，不是新验证。
- [ ] 外壳合并部署 × 本地（新验证）：不用 `go test`，真的用 `go run ./cmd/shell`（`shells/go`）在宿主机上起一个外壳进程，指向真实的 `TEST_PG_DSN`/`TEST_NATS_URL`（或者本机 `make up` 起的基础资源），确认它能长期存活、`/healthz` 正常、至少一条真实业务路由 fail-closed 403——验证的是"外壳作为一个长期存活的宿主机进程"这件事本身，不是"`go test` 进程生命周期内跑一段代码"，这两者理论上应该等价，但没有真机验证过就不该假设成立。`shells/python` 同理跑一遍。

**验证：** 四个组合各自的真机验证记录（命令、输出、关键断言）直接写进本节对应的 checkbox 下面，同阶段一到四各任务的既有记录方式一致，不另开新章节。

## Task 2：brickKit 原生独立部署 × K8s，真机跑一遍（不是 `--dry-run`）

- [ ] 确认本机 `minikube` 可用（`minikube start`，已经有一个现成 profile）。
- [ ] ⚠️ **`deploy.target` 没有对应的 CLI 覆盖参数**（读过 `internal/cli/up.go` 确认：只有 `--context` 能覆盖 `deploy.context`，`target` 只能写在 `brickkit.yaml` 里）——临时把 `brickkit.yaml` 的 `deploy.target` 从 `docker` 改成 `k8s`，同时剥离全部 `local: true`（复用 `infra/scripts/strip-shell-local.py`），两处都是临时的、不 commit 的改动，验证完用 `git checkout -- brickkit.yaml` 一起恢复——同 `weekly-teardown-gate.sh` 的既有判据：改之前先确认 git 工作区干净。
- [ ] `brickkit up`（此时会走 `deploy.target: k8s` 那条代码路径）生成清单并真实 `apply` 到 `minikube`——`deploy.context` 如果没写，需要确认它会不会正确使用当前 `kubectl` 的 ambient context（`minikube` 默认会把自己设成当前 context），必要时显式配上 `deploy.context: minikube` 或用 `--context` 覆盖。
- [ ] 确认全部 14 个组件的 Deployment/Service/迁移 Job 真实起来、`kubectl get pods` 全部 `Running`，健康检查真实通过（不是"清单里写了健康检查"这种间接证据）。
- [ ] 挑一条真实存在强依赖的调用链（比如 `erp-sales` → `mdm-customer`），真的在集群内部发一次请求，确认地址解析、鉴权链路（如果这一步方便配置的话）都正常——不满足于"两个 Pod 都 Running"这种弱证据。
- [ ] 收尾：`kubectl delete` 或对应的 `brickkit down --target k8s`，确认清理干净；`git checkout -- brickkit.yaml` 恢复外壳态基线；`minikube stop`（如果不是长期要用的话）。

**验证：** 这是全新的真机验证，此前从未在这个项目里发生过——这条命令即使一次性跑通也要记录下真实耗时（`minikube` 冷启动 + 镜像拉取/构建可能明显比 Docker Compose 慢），供以后判断"日常要不要也接入 K8s 验证"时参考真实成本。

## Task 3：外壳合并部署 × K8s，手写清单验证概念可行（不依赖 brickKit 表态）

⚠️ **这条不是"正式支持"，是一次概念验证（POC）**——目的是在 `docs/dev/给brickKit的反馈.md` 第七部分那个 `servedBy` 提案落地之前，先确认"外壳镜像本身能不能在 K8s 里正常跑、被其它组件正确访问到"这件事本身是可行的，不是纸上谈兵。跟 `infra/shell-compose.yml` 是手写的同一个道理——`be-ops` 没有产出 1（网关路由表）那一层，本来就不指望平台自动生成这部分。

- [ ] 手写 `infra/shell-k8s/`（Deployment + Service，仿照 `internal/k8s` 生成物的既有形状，字段对齐 `brickkit up --dry-run --target k8s` 生成出来的真实清单风格，不是随手编一份格式不一致的 YAML）：4 个外壳（`go-core`/`go-backoffice`/`go-infra`/`py-render`）各一份。
- [ ] 剩余 2 个独立组件（`frontend-standard`/`infra-bff-mobile`）走 brickKit 正常的 K8s 生成路径（这两个组件从来不需要 `local: true`，不受 Task 2 那条剥离步骤影响）。
- [ ] 全部 `apply` 到同一个 `minikube` 集群的同一个 namespace，确认：外壳自己的 Pod 健康；**独立组件的 Pod 里，`*_ENDPOINT` 指向外壳 Service 的地址能真实连通**（这一步目前只能靠我们手工在生成出来的清单里改地址来模拟"如果 `servedBy` 存在，平台会算出什么地址"——记录下这一步具体是怎么手动改的，为将来对照 `servedBy` 真正落地之后的效果留一个基线）。
- [ ] 挑一条跨越"外壳"和"独立组件"的真实调用链，验证端到端可达。

**验证：** 这条真机验证成立，就足以支撑"外壳 + K8s 在技术上是可行的，缺的只是平台原生表达这件事的方式"这个判断——写进 `docs/dev/给brickKit的反馈.md` 第七部分作为补充证据（如果 brickKit 后续真的采纳了 `servedBy`，这条手工验证也顺便成了迁移到那个方案之后的一份真机基线，能直接对照结果是否一致）。
