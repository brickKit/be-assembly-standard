## Task 1：跟随 brickKit `servedBy` 开发节奏做增量真机验证（持续任务，不是一次性做完）

⚠️ **这个任务没有"完成"这一天**——brickKit 那边把 `servedBy` 拆成好几个阶段在做（目前是"字段+静态校验"落地，`internal/shell` 的合并/生成逻辑还没写），他们每完成一个阶段，大概率会像前两次一样发来一份"请你们真机验证一下"的请求文档（放在 `docs/dev/brickKit请求-*.md`/`brickKit提问-*.md`，一次性文档，验证完可以删）。本任务记录的是**方法论和已经收到的具体请求各自的处理结果**，收到新请求时在这里补一个新的子任务，不需要另开新文档。

**核心方法论（每次收到新请求都按这个顺序过一遍）**：
1. 先分清楚"这条要验证的行为，依赖的是 brickKit 已经真实存在的代码，还是他们正在写、还没落地的代码"——前者能立刻真机验证，后者只能等，不能靠读设计文档"推演出"一个假装验证过的结论（这正是整个 `servedBy` 这条线一直在强调的纪律）。
2. 能立刻验证的，如果验证对象是 brickKit 自身已有机制（不依赖 `servedBy` 代码），且用的是本机已安装的**正式版** `brickkit`，就直接写成 `tools/be-acceptance/platform/` 的永久断言（继续沿用现有编号，不是单独的一次性记录）——这是最优结果，测试用例被真正保留下来，以后 `servedBy` 真的发布了也不需要重新证明这一半。
3. 如果验证对象是 `servedBy` 相关、但 brickKit 还没打 tag/还没发布到本机安装的版本里，需要从 brickKit 仓库源码临时构建一个开发版二进制才能测——这一类**不能**直接变成 `be-acceptance` 的永久测试（正常环境里没有这个开发版二进制，测试会全员 SKIP，价值不大），先把真实跑过的命令、完整输出、结论记录在本任务对应的子任务里；等 brickKit 正式发布带这个功能的版本后，再把这几条正式挪进 `platform/`，成为永久断言——这样"记录一切"和"尽量保留成真测试"两条路径都不浪费，是同一个流程的两个阶段，不是二选一。
4. 有些问题是"语言/工具链本身的结构性限制"（比如 Go 的 `go.mod` 每个 module path 只能锁一个版本），这类不需要靠写代码运行去"证明"——这是 Go 工具链公开、稳定的既有语义，直接给出清楚的技术论证即可，跟"读代码猜行为、没真机验证过"是两回事：这条论证本身是可以脱离任何具体运行结果、独立成立的事实，不属于需要真机验证的范畴。
5. 每次验证完，回信写进 `docs/dev/回复-*.md`（一次性文档），关键结论同步补进本任务的子任务记录——回信文档删掉之后，本任务这里的记录才是唯一留存的历史。
