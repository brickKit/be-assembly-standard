# 组件间调用与错误

本页说明组件之间、用户与组件之间怎样调用，错误怎样表达，时限、重试与熔断怎样取舍，以及这些选择的比较、改变的条件与步骤。调用模式与凭据只在[安全 02 的入口与调用模式](../06-protocols/security/02-trusted-identity-and-attributes.md)；时限、重试、熔断与出站并发的规则在[协议 17 的组件之间的调用](../06-protocols/17-runtime-and-resources.md#组件之间的调用)；授权与安全类的结果在[安全 09a](../06-protocols/security/09a-encoding-and-records.md#求值结果与错误)；头字段、数值与 reason 目录的格式在组件协议中规定。

## 选择

- **两个调用面**：系统调用走 gRPC 系统面（HTTP/2 加 protobuf），用户请求走 HTTP 用户面（REST 加 OpenAPI）。系统面上的调用方是已认证的服务，按部署声明的“服务到方法”许可准入；服务代理用户的请求走用户面，带原用户的凭据并另加服务身份的验证（安全 02）。gRPC 端口从不经边缘对外。
- **契约**：系统面的 proto 包名带主版本；用户面的路径挂在组件自己的前缀下，每个操作在资源定义中登记（安全 06、09a）；列表按不透明游标分页（协议 14）。同一主版本内的变化按协议 19 的兼容规则，破坏性变化用新的主版本路径并存，并公告弃用与下线日期。
- **每个聚合根在系统面提供按身份批量读取**，上限写在契约里（每次最多 500 个身份），超限拒绝而不截断；不逐个调用（决定 0304）。
- **一个错误对象**：用户面是 RFC 9457 problem details，带 Google AIP-193 `ErrorInfo` 的字段（给机器看的 `reason`、定义它的 `domain`、字符串 `metadata`）；gRPC 用 `google.rpc.Status` 加 `ErrorInfo` 携带同一个对象；移动聚合的 GraphQL 放在 `extensions` 里。一个错误穿过三者都不变。
- **reason 目录**：每个组件在契约中声明自己的 reason，只追加，带各种界面语言的消息模板；由前端翻译，服务端不翻译。服务端只在没有前端参与的地方生成文本（通知、打印、邮件），用接收者的语言（[协议 14 的多语言文本](../06-protocols/14-data-foundations.md#多语言文本与标准码)）。
- **内部错误不外泄**：只给通用消息与追踪身份，原始错误只进日志。调用者看不到的记录答 404，读取与命令一致（决定 0212）。
- **时限与重试**：截止时间逐跳传递、只减不增；能不能重试由契约声明；只有一层重试；重试有预算；出站并发有上限；按每个下游熔断（A103）。

## 方案比较

**调用面**：

| 方案 | 判断 |
| --- | --- |
| **采用**：系统面 gRPC，用户面 REST | 截止时间、带预算的重试、keepalive 与负载均衡由协议承担，每种语言的 gRPC 库都实现了；强类型契约带破坏性变更检查；“人用 REST、组件用 gRPC”是一条较弱的模型也能遵守的规则 |
| 组件之间也用 REST + OpenAPI | 每一处截止时间、重试与类型检查都要在每种语言里自己做 |
| Connect-RPC | 优势是浏览器能调用同一份 proto，而这正是系统面不允许的；Python 实现还年轻。留作逃生口：connect-go 的服务端也说 gRPC 线上协议 |
| Twirp | 没有截止时间、重试与均衡 |
| GraphQL | 只在客户端要聚合很多来源时有用，那是移动聚合的事，不是组件之间的事 |
| 只用消息 | 等着看“缺货”的用户没法等一条事件（[事务与消息](03-transactions-and-messaging.md)） |
| 服务网格（Linkerd、Istio） | 每个 pod 一个 sidecar；外壳对它来说是一个应用，成员身份就丢了 |

**错误**：

| 方案 | 判断 |
| --- | --- |
| **采用**：RFC 9457 携带 AIP-193 字段，加 reason 目录 | 每个 HTTP 客户端都认识的标准媒体类型；与 gRPC 的 `ErrorInfo` 是同一个 reason；可以测试（断言 reason 而不是一句话）、可以翻译 |
| 自造的 `{code, message, details}` | 不是标准，每个客户端各自发明解析方式 |
| Google 的 JSON 错误形式 | 绑定 Google 网关的惯例；AIP-193 的字段成为 RFC 9457 的成员后，它提供的东西 RFC 9457 都有 |
| 不带目录的 RFC 9457 | 前端只能显示服务端的文本，没有东西可以拿来测试 |
| 服务端按 `Accept-Language` 翻译 | 每个组件都要维护每种语言的文本；语言是前端偏好 |
| 整个用户面用 GraphQL 或 OData | 路由级的权限登记与边缘的按路径路由难得多，每个组件多一种查询语言 |

**时限与故障**：

| 方案 | 判断 |
| --- | --- |
| **采用**：截止时间预算、契约决定的重试、重试预算、出站并发上限、按下游熔断 | 每一跳的最坏情况都有界；截止时间、重试策略与限流是 gRPC 规范的一部分，每种语言都一样；熔断让调用方在下游持续失败时快速失败，保护自己的并发与连接（A103 取代原有决定 0503 的“只用舱壁、不用熔断”：单实例时熔断没有可绕开的实例，但快速失败仍然保护调用方） |
| 代理或网格的离群检测（Envoy、Istio） | 不写代码就能剔除坏副本；但每个 pod 一个 sidecar，外壳中丢失成员身份 |
| 对冲请求 | 有副本时能削减尾延迟；只有一个副本时负载翻倍、毫无收益 |
| 自适应并发上限 | 上限跟着实测延迟走；需要稳定的流量来学习，更难推理 |
| 每次调用一个固定超时、没有预算 | 子调用可能活得比调用方长，失败在用户放弃之后才到 |

## 什么时候换

- **浏览器必须直接调用 proto**（会重新打开调用面这一条）：用 connect-go 的处理器提供同一批契约。
- **多节点且出现部分故障**（一些副本坏了、另一些正常）：客户端按请求均衡加离群检测，或经服务网格。
- **一条有副本的读路径实测有尾延迟问题**：只对那个读方法启用对冲。
- **固定的出站上限对某个依赖明显不合适**：把那个依赖的上限改成自适应的。
- **对外开放接口**：加上外部应用的认证、配额与公开的版本承诺（协议 10），不改错误模型与路径。
- **合作方要客户端库**：从 OpenAPI 契约生成。

## 怎样换

- 连接复用、均衡、对冲、离群检测、限流器都在 SDK 的客户端链或生成的服务配置里：组件代码、契约与版本钉不变；路由的截止时间只经它的声明改变。
- connect-go：改 SDK 里的服务端处理器，客户端与契约不变。
- 新的错误字段、头或 reason 是对协议与目录的追加，忽略它们的客户端照常工作；一个操作的破坏性变化用新的主版本路径。

## 替换时的检查

调用的检查覆盖：截止时间随调用传递且只减不增，剩余时间不够时不发出调用；只有契约声明幂等的方法在下游不可用时重试，且不超过预算；嵌套调用不出现第二层重试；出站并发满时立即失败；熔断打开后快速失败、冷却后试探；外壳中的出站连接与重试预算按成员。错误的检查覆盖：同一个 reason 经 gRPC、REST 与 GraphQL 到达调用方不变；未声明的 reason 被门禁发现；内部错误不带原始信息；不可见的记录在读取与命令上都答 404。

## 已知限制

- reason 目录的完整程度取决于声明：门禁抓得到代码里没声明的 reason，抓不到组件本该有却没有的。
- `metadata` 只放字符串（与 AIP-193 一致），数字与日期由产生方格式化。
- 列表没有精确总数。
- 404 只在回答里隐藏存在性，在耗时上不隐藏；不尝试等时响应。
- 出站上限按进程计；没有跨副本的全局限流，那要在边缘做。
- 异步工作没有端到端的截止时间：一条事件或一个工作项每次尝试有界，总体由最大尝试次数限定（协议 01）。
- 系统面不用流式、有消息大小上限：大批量传输走对象存储。
- 外壳重启对它的全部成员是同一次故障。
