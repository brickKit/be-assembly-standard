# 金额、数量与单位

金额、单价、成本、数量、比率怎么存、怎么传、怎么舍入，币种怎么跟着每个金额走，计量单位怎么换算。加金额、单价、数量或比率的列或字段，对它们做运算，把一个金额拆到多行，或者在单位之间换算之前，先读这篇。

## 范围

覆盖：列规格、币种成对、ISO 4217 小数位、舍入模式、尾差分摊、税额舍入、每个官方 SDK 里的十进制实现以及让它们保持一致的向量、计量单位与换算。不覆盖：契约里的十进制字符串编码，这是一条决策（[0301](../02-decisions/03-contracts-and-data/0301-money-as-strings-lists-by-cursor.md)）；外币重估的会计规则，属于 erp/finance 的设计；汇率契约，等 mdm/currency 建成后归它。

## 选择

- **固定 scale 的 `NUMERIC` 列；舍入在 SDK 里按币种做。** 列的 scale 是容量，不是精度：存进去的值已经按币种或单位允许的位数舍入过了。
- **列规格**：金额 `NUMERIC(19,4)`；单价与成本 `NUMERIC(19,6)`；数量 `NUMERIC(19,6)`；汇率 `NUMERIC(19,10)`；比率（折扣、税率）`NUMERIC(9,6)`。
- **币种总是跟着金额走。** 每个带金额的单据头都有 `currency CHAR(3)`（ISO 4217 字母代码）；行沿用单据头的币种。每个法人有本位币。外币单据快照汇率、汇率日期和汇率类型。分录同时存交易币金额和本位币金额。
- **汇率归一个新组件 mdm/currency**：币种、汇率类型、每日汇率。和其他 mdm 枢纽一样，所有人都读它，它不调用任何人。
- **每个官方 SDK 里一份十进制实现**，是解析、格式化、舍入、分摊金额的唯一地方。组件自己手写的十进制代码删掉。共享向量让 Go、Python、TypeScript 保持一致。
- **舍入**：默认四舍五入远离零（国内税务口径）；可选银行家舍入（half-even）。小数位来自 SDK 内置的 ISO 4217 表；项目可以加现金舍入（例如瑞士法郎舍到 0.05）。
- **分摊**：把一个总额按权重分到各行时用最大余数法，所以各部分加起来总是等于总额。
- **税额**按行舍入或按单舍入；每个算税的组件声明用哪一种。
- **单位**：全局的单位类别，每类一个基准单位；产品专属换算（A 产品一箱是 12 个，B 产品一箱是 24 个）优先于全局换算；换算系数是 `NUMERIC(24,12)`；每个单位可以带它的 UN/ECE 第 20 号建议书代码；数量按单位的舍入规则舍入；按序列号追踪的产品，数量是整数。

**状态**：已定；随 3.0.0 统一升级落地。今天每个金额列都是 `NUMERIC(18,2)`，单价和标准成本也一样；只有销售订单和商机有币种列；没有汇率；三个组件各自带着自己的十进制代码，规则还不一样（其中一份拒绝负数）。mdm/currency 在本轮新建，先于其他组件升 3.0.0；它还没有登记表行。

## 端口契约

### 列

| 种类 | 列 | 说明 |
|---|---|---|
| 金额 | `NUMERIC(19,4)` | 与单据头上的 `currency` 成对 |
| 单价、成本 | `NUMERIC(19,6)` | 每个 0.0035 元的五金件、按克计价的原料 |
| 数量 | `NUMERIC(19,6)` | 按单位的舍入规则舍入 |
| 汇率 | `NUMERIC(19,10)` | 单据上同时有 `fx_rate_date date` 和 `fx_rate_type text` |
| 比率 | `NUMERIC(9,6)` | 折扣、税率；`0.130000` 就是 13 % |
| 换算系数 | `NUMERIC(24,12)` | 毫克换千克，还能更小 |
| 币种 | `CHAR(3)` | ISO 4217 字母代码，大写 |
| 本位币金额 | `NUMERIC(19,4)` | 分录上与交易币金额并列 |

新迁移里金额列的 scale 小于 4 时，门禁失败。

### 线上

- 金额、单价、数量、比率都是十进制字符串（[0301](../02-decisions/03-contracts-and-data/0301-money-as-strings-lists-by-cursor.md)）：可选的 `-`、数字、可选的 `.` 加数字。不允许指数、千分位分隔符、`NaN` 或 `Infinity`、开头的 `+`。其他写法一律以 `INVALID_ARGUMENT` 失败。
- 金额按它的币种小数位格式化：人民币 `"12.30"`、日元 `"1230"`、科威特第纳尔 `"1.234"`。以前看到 `"12.30"` 的消费方，现在看到的仍是 `"12.30"`。
- 每个带金额的消息旁边都带 `currency`；缺的地方作为新字段加上（[0302](../02-decisions/03-contracts-and-data/0302-contracts-are-additive-only.md)）。
- 单价最多 6 位小数，汇率最多 10 位，比率最多 6 位。

### 舍入与分摊

| 操作 | 规则 |
|---|---|
| 舍入金额 | 舍到币种的小数位（ISO 4217），项目配置了现金舍入时舍到那个步长；默认模式 `HALF_AWAY_FROM_ZERO`，需要时用 `HALF_EVEN` |
| 舍入数量 | 舍到单位的舍入规则 |
| 按权重分摊总额 | 最大余数法：先把每一份向下取到最小货币单位，再按余数从大到小，每份补一个最小单位；余数相同时排在前面的行优先。各部分之和总是等于总额 |
| 按行算税 | 每行的税额各自舍入，单据税额是它们的和 |
| 按单算税 | 对单据总额算税并舍入一次，再分摊到各行 |

### 向量

计划新建的 `brickKit/be-protocol` 仓库里的 `vectors/money/*.json`（不放在一致性套件里）：每个用例写明操作（`parse`、`format`、`round`、`allocate`、`tax_line`、`tax_document`、`round_qty`）、输入、币种或单位、模式，以及期望的输出或错误。每个官方 SDK 读同一批文件。

## 备选方案

| 问题 | 方案 | 长处 | 短处 |
|---|---|---|---|
| 存储 | 整数最小单位（Stripe：`BIGINT` 分） | 精确、快 | scale 必须跟着每个值走；单价和汇率仍然需要十进制 |
| | **固定 scale 的 `NUMERIC`**（ERPNext `decimal(21,9)`、Dynamics 365 `numeric(32,16)`） | 简单；一种列类型容纳所有币种 | 舍入必须在应用里按币种做 |
| | 浮点加按币种舍入（Odoo） | — | 有已知的精度问题 |
| | SAP 的两位小数 CURR，日元移位存储 | — | 出了名的坑 |
| 契约 | **十进制字符串** | 每门语言里都精确 | 要自己解析 |
| | `google.type.Money`（units + nanos） | 标准 proto 类型 | 两个字段、九位小数，与 0301 冲突 |
| | 整数最小单位 | 紧凑 | scale 是隐含的 |
| 十进制库 | Go：`math/big.Rat`、`shopspring/decimal`、`cockroachdb/apd`；Python：标准库 `decimal`；TypeScript：`decimal.js`、`big.js` | — | 每个官方 SDK 自选一个；定义行为的是向量，不是库 |

## 为什么选它

- **处处精确**：线上是字符串，库里是 `NUMERIC`，内存里是十进制类型；什么都不经过浮点。
- **一种列形状容纳所有币种**：四位小数容得下所有在用 ISO 4217 币种的小数位（日元、韩元 0 位，科威特第纳尔、巴林第纳尔、阿曼里亚尔 3 位，智利 UF 4 位）。
- **舍入是和币种、税务绑定的业务规则**，所以放在一个库、一套测试里，而不是散在每个组件里。
- **海外客户和多公司都在范围内**，所以从第一张表起，每个金额都要带币种，每张外币单据都要快照汇率。
- **已有消费方看不到变化**：人民币金额的格式和以前完全一样；`currency` 是新字段。

## 为什么不选其他

- **整数最小单位**：每个值旁边都得带上它的 scale，而单价和汇率不是钱，仍然需要十进制，于是就有了两种表示。
- **浮点**：会丢分，而且 Go、Python、TypeScript 的舍入各不相同。
- **`google.type.Money`**：两个字段、固定九位小数，违背 0301 的"一个十进制字符串"。
- **像今天这样用 `NUMERIC(18,2)`**：存不下 0.0035 的单价、三位小数的币种，标准成本也会在成本滚算中累积舍入误差。

## 什么时候换

- **某一列需要超过 15 位整数**（对极大金额做累计的报表）：只放宽那一列的精度。其他都不变。
- **某个币种或某种税制需要别的舍入模式**：在各 SDK 里加上这种模式和向量；组件通过配置选用。
- **项目需要现金舍入**：配置步长；不改代码。

## 怎么换

- **舍入模式或现金步长**：在做舍入的那个组件的项目配置里改（它的配置键或税务规则声明），只能从向量覆盖到的模式里选。
- **某个 SDK 内部的十进制库**：SDK 内部的改动；向量必须保持绿，组件察觉不到。
- **放宽一列**：在拥有方组件里写一个 expand 迁移，发一个版本（契约一侧见 [0302](../02-decisions/03-contracts-and-data/0302-contracts-are-additive-only.md)：字符串格式本来就允许更多位数）。
- **汇率来源**：mdm/currency 由一个集成组件或手工录入喂数；消费方只从 mdm/currency 读汇率，所以换来源不碰任何消费方。

## 一致性测试

上面的金额向量，每个官方 SDK 都跑。要先写红的测试：

- SDK：每条向量都通过；日元格式化不带小数，科威特第纳尔带三位；100.00 按三个相等权重分摊得 33.34、33.33、33.33，加起来是 100.00；数量按单位的舍入规则舍入；`NaN`、`Infinity`、指数和千分位分隔符都被拒绝。
- 门禁：新迁移里金额列的 scale 小于 4 时，`make gates` 失败。
- 组件，每迁到 SDK 的库一个：删掉旧的手写十进制代码，它的测试由向量替代，而不是并排留着。

## 相关决策

- [0301](../02-decisions/03-contracts-and-data/0301-money-as-strings-lists-by-cursor.md)：金额是十进制字符串。计划修订：每个金额都与一个币种成对。
- [0302](../02-decisions/03-contracts-and-data/0302-contracts-are-additive-only.md)：`currency` 和本位币字段是新增的，绝不替换已有字段。
- [0104](../02-decisions/01-architecture/0104-variants-become-slot-families.md)：舍入和分摊是 SDK 内部策略，不是槽位族。
- 计划中、尚未编号："汇率归 mdm/currency"。

## 已知限制

- **mdm/currency 是 3.0.0 统一升级的前提**：做币种换算或重估的组件从它读汇率，所以它先发布。
- **重估、已实现和未实现汇兑损益**是 erp/finance 的业务逻辑，不在本文设计。
- **按行还是按单舍入税额**是每个组件自己的声明；对同一张单据算税的两个组件必须声明同一种。
- **列的 scale 是容量。** 能存 4 位小数，不代表某个金额可以带 4 位：由币种决定，而且只有 SDK 做舍入。
- **已有契约只增地加上 `currency`**；忽略它的旧消费方，在更新之前仍然默认整个部署只有一种币种。
