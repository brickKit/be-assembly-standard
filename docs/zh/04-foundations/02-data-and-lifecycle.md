# 数据与生命周期

本页说明数据的权威归属、共享语义与生命周期：谁拥有什么、数据库怎样选择与分离、冷热怎样分层、跨层怎样查询、灾难后怎样恢复。共同的数据库使用规则、身份、单号、时间、金额与迁移见[协议 14](../06-protocols/14-data-foundations.md)；转层见协议 11，备份与恢复见协议 15，附件与对象存储见协议 12。

三类替换要分清：PostgreSQL 与 RustFS 是**基础资源**；存储访问与冷查询的适配在 **SDK** 里；`infra/attachment` 是**附件业务组件**。三者的替换责任不同，不能一概说成“换数据库”或“换附件组件”。

## 数据归属

每类业务事实只有一个明确的写入者；其他组件通过契约读取、订阅事件，或维护声明过的投影（协议 02）。关联表、迁移状态、平台表、对象存储的桶、搜索索引同样要有属主、凭据、权限、生命周期与恢复责任。

- **存货成本**：成本子账归独立的成本组件，引用库存的数量事实与必要的价格、费用事实，保留计价依据、暂估与调整的关联；财务按成本事实过账。成本调整不改写库存的数量历史；来源与处理范围要支持完整性核对、重算与恢复（[财务与结算](../00-overview/guides/finance-and-settlement.md#存货计价)）。
- **业务伙伴**：客户与供应商共享统一的伙伴基础身份，角色资料、权限与业务状态分别管理；应收应付与信用政策保留各自的业务权威。伙伴由 `mdm/partner` 承接，角色按法人开通（[领域与边界](../00-overview/02-domains-and-boundaries.md#业务伙伴与角色)）。
- **联络资料**：正式联络基础资料由伙伴主数据维护；CRM 与采购的私有业务关系留在各自的能力中，不能借共享的联络资料向其他上下文泄露。历史快照按协议 07。
- **核心字段语义在建表前确定**：主键与人读单号、时刻与业务日期、法人、金额与币种、数量与单位、并发版本、扩展字段（协议 08）、权限范围。每种语言与客户 Fork 都保留相同的外部语义。
- **账簿**：标准财务每个法人一个正式会计账簿，其他报告口径采用受控调整与报表（D51）；调整与正式账务事实的来源、权限、版本与差异可以核对。
- **审批修订**：审批中的关键修改采用新修订并重新审批，旧版本与审批依据保留；存储与生命周期支持审计与执行前复核，不只保留最后一版可编辑的记录（协议 09）。

## 重复主数据的确认与合并

系统查重、提示疑似重复与字段冲突；正式合并默认由有权限的人确认（D22，安全 08 的业务确认）。大批量可以先审核合并计划，再批量执行；查重分数或联络信息相同，不能直接改变主体身份。

合并保留原身份的映射、来源与变更记录；未经确认不改变角色、业务引用或权限关系；合并不自动扩大权限，也不改写历史单据的快照与已执行的事实。审核与执行之间资料可能变化，执行前复核。误合并的拆回要检查之后的业务与关联，不承诺随时一键回退。合并后的别名解析、历史引用不改写、在途引用、资格引用与悬空引用的修复见协议 07。幂等请求的去重、按明确 ID 更新同一记录，不属于合并。

## 发生时归属与当前责任

业务对象分别表达**发生时的组织归属**与**当前负责的归属**（D15）。历史业绩默认保留发生时的口径；正在处理的单据通过明确的交接调整当前责任。人员调岗不自动搬走他的全部旧单据；交接也不改变原交易的法人或账务事实。

需要按现在的组织重算的管理报表另设清晰的口径，不静默覆盖历史归属；必要的历史更正通过有记录的业务过程处理。读取与操作仍按调用者当前有效的授权判断，发生时的归属不是永久的访问权。投影、搜索、报表与冷数据保留各自判定所需的归属信息；数据集同时保存发生时的组织与当前组织（协议 13）。各实体何时确定发生归属、哪些信息需要快照、哪些对象允许交接，随组件设计逐项确定。

## 数据库的选择

推荐 PostgreSQL 作为在线交易的标准数据库：短事务、约束、条件更新、JSON 扩展与各组件明确的 SQL；不为适配任意数据库而退到最低能力交集。

三种替换层次要分开：

| 层次 | 候选 | 收益 | 代价与适用场景 |
| --- | --- | --- | --- |
| 同一 SQL 方言与协议 | PostgreSQL 的不同部署、兼容发行版 | 保留较多 SQL 与客户端约定 | 兼容程度、版本、扩展、角色、分区与恢复仍要验收 |
| 跨数据库方言 | 其他关系型引擎 | 满足客户指定的环境或约束 | 驱动、SQL、迁移、锁、精度、平台表与测试都要适配；按客户要求做专项 |
| 在线、分析、冷层 | 单库分区、独立冷层、独立分析引擎 | 分别处理在线性能、长期保留与分析隔离 | 复制、清单、权限、新鲜度、恢复与跨层查询的成本 |

更换 PostgreSQL 的部署，不证明任意数据库可以换。线协议兼容不等于隔离级别、DDL、锁与恢复兼容。连接池、事务超时、隔离级别、重试、语句缓存、属主与运行角色，要在单跑与外壳下分别验证。一个实例容纳多个 schema，不意味着允许跨组件 SQL 或共享事务。

**只读副本**用于容许明确延迟的读取负载，不代替历史分离或备份。库存可用量、额度资格与提交时的不变量仍由写权威判断；写后立即读取，要用响应中的状态、回到权威，或验证副本的水位。副本中的对象授权属性，不能比该路径允许的新鲜度更旧。

**分片**不能只按 schema 证明热点已解决：整个库存 schema 落在一个节点上时，组件内部的热点仍在。先看查询与索引、争用与恢复预算，再决定只读副本、历史分离、组件数据分离，或组件内部的分片键。

数据库共享只适用于约定的可信组件；外壳的登录角色可以切换到多个成员的角色，不能当作被入侵代码之间的安全墙。

## 在线数据库怎样分离

实例是一套 PostgreSQL 服务及其数据目录；一个实例可以有多个数据库，一个数据库可以有多个 schema。分离改变的是数据的物理位置与连接目标；业务权威、接口与本地事务责任仍归原组件。

| 形态 | 适用目的 | 仍共享的边界与代价 |
| --- | --- | --- |
| 共用实例、共用数据库、每组件独立 schema | 小到中型的基础组合；集中维护与连接预算 | CPU、内存、磁盘、WAL、实例故障与物理恢复；schema 的分工不提供机器隔离 |
| 共用实例、每组件独立数据库 | 分开数据库访问与部分管理，满足明确的交付条件 | 仍共享实例资源、WAL、实例级故障与物理恢复；每个连接只指向一个数据库，不能因此承诺独立容量 |
| 同一宿主、独立实例 | 分别设置版本、连接与资源上限，分别重启 | 宿主与底层磁盘的故障仍然相关；需要额外的备份、恢复与调度；限制资源不等于增加硬件 |
| 不同宿主、独立实例 | 独立配置容量，按真实故障域改善隔离 | 更多网络、运维与恢复责任；仍要核对共享存储、供电等；换机器不自动证明高可用 |

例如销售、库存、财务起初共用实例；库存的写负载成为独立瓶颈后，迁到另一个实例。只读副本、历史库、分析库与组件在线库的分离，分别解决读取、历史积累、重分析与在线隔离；不能把任何“多一个库”都称为扩容成功。层级依据见 [PostgreSQL 数据库管理概述](https://www.postgresql.org/docs/18/manage-ag-overview.html)。

**迁移步骤**：清点业务表、平台状态、身份与角色、权限投影、迁移历史、发件表与收件表、作业与幂等记录、对象引用；固定来源版本与写入切点；复制并校验；切换连接与部署；验证真实业务与恢复；最后退出旧的写入路径。标准可以用维护窗口；在线迁移另外验证增量追赶、旧写入者隔离与切点。目标已经写入之后，不能只改回旧地址来撤销新事实，按[选配变更](../00-overview/05-change-and-retirement.md)处理。纪元的推进按协议 14（单库恢复、删库重建与主版本升级都推进部署恢复代次）。

外壳的共享池按数据库目标划分：同一目标的成员共享一个池，不同目标各用一个池（协议 14）。多数据库或多实例的组合，可以把对应组件先单跑，也可以用按目标分池的外壳并验证身份与总预算。外壳能否共享池取决于相同的数据库、凭据与成员预算，这不是禁止独立数据部署的理由。迁移不引入跨组件 SQL，也不把多库提交伪装成本地 ACID。

## 冷热分层

区分在线业务、可交互的历史、封存的历史与分析副本。冷热是访问与维护方式的差异，不要求第一天就装两套数据库。按访问、修改、恢复与成本目标制定类别，而不是统一设置“几个月后变冷”：每个类别声明自己的驻留期，过了驻留期、又满足封存条件的单元才转层（[协议 11 的转层候选与驻留期](../06-protocols/11-tiering.md#转层候选与驻留期)）。持续修改的主数据、未完成的单据、待重试的消息、业务余额、长期的去重证据，不能只凭年龄搬走。

| 类别 | 设计重点 |
| --- | --- |
| 在线可变数据 | 完整权限、写入一致性、索引与延迟预算 |
| 已完成的历史 | 终态判定、迟到更正、期间锁与关联完整性 |
| 冷归档 | 格式与清单版本、校验、搬运与恢复、重复执行与副本完整性 |
| 分析投影 | 新鲜度、权限重评、重建、原始来源与恢复 |
| 清理与销毁 | 数据类别的最短与最长保留、保全、个人信息、审计证明 |

没有明确法规或客户合同的保留年限标为待确认；会计资料与个人信息可能有不同约束，分别处理。

### 存储路线与选配条件

| 路线 | 用途 | 收益、代价与升级信号 |
| --- | --- | --- |
| 同一 PostgreSQL 的表与分区 | 在线可变数据、仍常查的业务历史；小型客户的最低路线 | 不增加查询服务，关系、定位与权限集中；历史仍占用主库的存储、备份与恢复预算 |
| 独立的 PostgreSQL 历史库或实例 | 历史需要频繁的详情、关联、分页，主库的恢复或争用超出预算 | 继续关系型读取；增加路由、版本与恢复责任；属主仍是原组件，不给其他组件任意 SQL 权限 |
| 对象存储上的 Parquet 加版本清单 | 真正封存、偶发查询的历史与可核对的数据包 | 开放格式与压缩，在线主库可以减负；要维护查询、校验、清单、擦除与恢复，不能当作第二个在线事务库 |
| Iceberg 等表格式 | 冷数据需要多引擎并发维护、频繁更正与删除、结构演进 | 有快照与元数据协议，增加目录与维护成本；不作为所有小客户的必装项 |
| 独立分析引擎 | 重聚合、探索或数据集扫描影响交易预算 | 隔离分析负载；投影、口径与新鲜度独立验收，不接替历史事实与正式账簿 |

**产品与做法的比较**（主流产品塑造了这里的形状：SAP 的归档对象、可归档性检查、驻留期与保留期之分与法律案件，SAP Data Aging 的“默认只读当前”，Salesforce 的可检索、可恢复归档，ERPNext 的按字段匿名化，Dynamics 365 的只读长期保留）：

| 做法 | 为什么不作为标准路线 |
| --- | --- |
| 每个组件一个归档 schema | 只是把问题挪了个地方：两个 schema、结构漂移、要路由，不省空间 |
| pg_partman 管理分区与保留 | 配置在组件 schema 之外，需要高权限的后台进程，它的保留逻辑绕过保全、封存与校验；借鉴它的预建分区与按边界判断 |
| TimescaleDB 压缩 | 许可与托管服务受限，转换是一次迁移，压缩块的擦除代价高；只作某一张超大只追加表的一次性候选 |
| Citus 列存 | 依赖扩展，只适合只追加的数据 |
| PostgreSQL 湖扩展（pg_duckdb、pg_lake、parquet_s3_fdw） | 一条 SQL 横跨冷热很方便，但扩展需要高权限，托管服务很少支持，隔离交给了扩展 |
| 全表 CDC 进分析库 | 物理上就是读别的组件的 schema，没有契约（分析走数据集，协议 13） |
| 软删除或“有效”标记 | 只是回收站，不是生命周期，没有保留、保全与销毁 |
| 在 Go 组件里嵌入 DuckDB | 需要 cgo；冷读的执行位置按下文的读取端口选择 |

**升级信号**：客户已有湖仓，或擦除多到重写 Parquet 太贵 → 表格式；用户经常查历史 → 受控的冷读工作者，数据量大到要聚合或跨单元排序时 → 独立分析引擎；个人信息很多的组件（人事）→ 评估按主体加密后销毁密钥；某一张账簿或审计表在线超过约 1 TB 又不能封存 → 评估对这一张表的一次性转换；信创数据库交付 → 实测方言后再承诺。

选择在线、分析或冷层时，迁移责任覆盖原业务组件的事实、引用与权限，不能只更换基础资源的名称；历史路径是声明的生命周期能力，不等于两个组件可以共同写同一事实。

优先设计**按业务属主路由的能力端口**，冷读的执行位置按资源预算选择：嵌入读取适合受限扫描，重读可以由受控的工作者承担。DuckDB 等作为读取适配的候选评估，不接受用户的任意 SQL 或对象 URL，也不读全桶。依据：[DuckDB Parquet 读取](https://duckdb.org/docs/stable/data/parquet/overview)、[Iceberg 快照与提交规范](https://iceberg.apache.org/spec/)；它们提供技术能力，不提供本项目的业务权限。

### 分区、归档单元与唯一性

分区服务于增长、查询与维护，归档单元服务于业务完整性，两者不必相同。一个月份中有长期未完成的订单时，不能因为多数记录已经终态就整月删除：可以继续保留整块，或采用明确的终态聚合搬运并维护位置目录。订单及其明细、关联事实必须能一起解释，但不要求把不同权威组件的表合成一次搬运事务。

大规模追加的流水与明确按时间增长的表，在建模阶段确定不可变的切分键；小型有界的主数据与活跃余额，不机械地按月分区。月或周的粒度按数据与管理开销选择。业务日期不等于技术创建时间；导入的旧记录、父子记录的 ID 时间不同、财务按期间分区时，都不能只凭 ID 的时间推导位置——分区键是表上的显式列（协议 14）。

PostgreSQL 原生分区表的唯一约束与主键必须包含分区键：`(id, created_at)` 不单独保证 `id` 跨全部分区唯一。业务单号、外部事实 ID、幂等键或对象位置，分别选择不分区的身份登记、可以证明固定的键映射，或明确的复合身份，登记与业务修改同事务（协议 14 的身份登记表）。不把随机 ID 的低碰撞概率当作业务唯一规则的数据库保证。[官方分区限制](https://www.postgresql.org/docs/current/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS)

未来的分区提前创建，边界完整、不重叠；异常边界不能跳过告警后称维护成功。DDL 有自己的权限、锁预算与崩溃恢复，不进入普通请求的热路径。并发摘除分区仍有锁与适用限制，核对目标版本与引用关系，不承诺“`CONCURRENTLY` 就不会阻塞”。

## 生命周期状态

每个归档单元、数据版本与处理进度保存在原属主的目录中（协议 11 的单元目录）。物理搬运与法律保全、处理限制分别建模，不用一串状态码涵盖所有正交的条件。

| 阶段 | 前置条件与提交证据 | 失败与竞争的处理 |
| --- | --- | --- |
| 选择与封存 | 确认所选聚合已经终态、来源处理完整、没有未交接的任务；与写入路径共享封存状态与版本的裁决 | 写入先赢则重新选择；封存先赢则迟到的写入转为明确的更正；所有写入口都检查，不只是归档任务之间互斥 |
| 复制 | 封存版本的稳定集合、不可变的对象 key 与版本、导出任务的身份与进度 | 网络操作在数据库事务外；重试不覆盖已发布的内容，失效的工作者不能发布新目录 |
| 校验 | 行数、主子完整性、类型与内容摘要、完整读回、索引与定位、权限所需的属性 | 任一差异保留来源，不以行数相同代替内容一致 |
| 发布读路由 | 在本地事务内校验来源版本与任务代次，原子发布清单版本与范围 | 只有验证过的清单能成为权威路径；新旧副本共存时由目录决定读哪份，不双计 |
| 宽限与退出在线层 | 查询支持已满足；备份与恢复窗口明确；正在使用旧路径的读取已结束或可以重试 | 宽限期加读取租约与快照引用管理；摘除分区与清理中断后可以从目录继续，不留静默缺口 |
| 删除来源或销毁 | 转层删除来源时已有验证过的副本；最终销毁另验保留到期、当前保全与审批、关联与全部副本 | 保全与删除通过共同的控制点决定先后；备份恢复后重放销毁与限制记录；不能只靠昨天的检查结果删除 |

“先复制再删”还不够：复制后又有写入、发布后旧读仍在进行、销毁前又新增保全，都要有明确的裁决。单元的锁或租约只保护协作中的工作者；执行提交还要验证代次（带纪元，协议 14），租约过期的旧工作者不能继续改目录。文件清理只删除目录证明无人引用且已过恢复窗口的对象。

### 内容摘要、历史更正与结构演进

- **摘要编码**：摘要的输入使用版本化、无歧义的类型编码（安全 09 的规范编码），显式区分 null、空字符串、普通文本与分隔字符，固定十进制、时刻与时区、二进制、列顺序与记录顺序。不能直接用数据库的 text 输出加未转义的分隔符：不同内容可能得到相同的字节。格式与摘要版本写进清单，用跨语言的独立向量验证。
- **防篡改的边界**：摘要与链可用于内容一致性检查，以及在有可信锚点时检测变更；不能凭同一个库里一条可重算的链承诺防恶意篡改。需要时声明锚点、签名或保存身份与威胁边界。
- **保留**：保留策略校验最短、最长与保全条件；延长不能绕过明确的最长限制，不照搬“全系统永久保存”的默认。
- **更正**：封存后的更正用受控的新版本或调整事实加关联表达；事实保留原内容，当前责任与合法擦除用受控的元数据维护。不可变文件遇到允许的字段擦除时，生成新文件与清单，按保全与恢复规则清理旧版本。稳定的替代标识只是假名化手段，不自动证明匿名化；法律资格按真实数据、映射与目标地区核对。
- **解冻**：默认恢复受限读取，不自动重开原业务的写入。旧结构读入新版本要有明确的转换、原始摘要的核对与转换后结果的校验；丢列或填默认值后，不能再要求与原结构的摘要相同。事件、数据集、导出与备份各有副本清单，不能只清理在线表就记为全系统擦除完成。

## 跨层查询

查询要定义按 ID、按条件列表、跨层排序与分页、报表、导出与解冻的行为。冷查询可以更慢或异步，但必须明确告诉调用者；不能静默返回不完整的数据。冷单据能否再修改由业务规则决定。

- **游标**绑定筛选、稳定的排序键、目录与数据版本、计划摘要（安全 07、协议 14）；冷热重叠的范围由权威目录去重。目录变化时，保留可用的快照，或明确要求重试，不让游标跳到另一套集合。跨层的总计、混合排序与导出覆盖声明的完整范围；能力不足时返回明确的“不可完成”。
- **快照与当前授权分开**：撤权或当前责任变更，不能因为游标绑定了旧快照而永久保留访问。长查询与文件领取按声明的节点重验授权；授权变化后选择安全中止或重新生成，不要求继续旧分页还保证绝对完整。默认的在线窗口与显式的历史或冷热查询分别向用户说明；普通列表不能悄悄漏掉请求范围里的冷单据。
- **默认读取范围**：不能只按创建时间截断。ERP 有大量很早创建、至今未关闭的单据（未收款的发票、未完成的采购、长期挂账）；“最近 N 天”会让“全部未收款发票”这类常用列表静默漏掉旧单据。默认范围定为“未关闭，或最近 N 天内创建”，与“关闭后才封存”的分层一致（协议 11）。
- **恢复核对**：恢复目录、定位索引、清单版本与真实对象要一起核对。目录标记为冷、对象却缺失时是故障，不能回答“记录不存在”；对象存在、目录却未发布时是待恢复的副本，不能未经验证直接开放。

## 灾难恢复

标准优先设计并验证客户整套部署的一致性恢复，覆盖业务数据、对象与冷数据引用、消息与作业、配置与权限等必要状态（协议 15）。选择性的组件历史恢复按场景专项设计；普通纠错与可重建的投影仍可以采用验证过的局部修复，不要求所有故障都整套回滚。

组件能独立部署，不证明可以任意时间点单独回退。数据库或 schema 恢复成功，也不证明订单、库存、财务与消息之间已经对齐：备份清单、恢复点与恢复组、存储版本、状态校验、对账补齐与恢复服务的条件一起设计。

- **外部事实**：发货、付款等外部事实不随备份回退，恢复后必须核对，不盲目重放副作用。
- **安全记录**：恢复旧权限不能忽略之后的撤销记录与安全事件；收紧、销毁控制与外部执行证据保存在独立的证据存储中（审计组件兼任），不随部署备份回退。找不到必要证据时，暂停受影响的动作，写明数据损失与人工核对的范围，再决定恢复服务。
- **流程**：先进入维护与执行冻结；恢复数据库及对应的对象与清单版本；推进部署恢复代次（协议 14）；核对运输保留、收件表与业务去重、全部未决作业；再通过权威外部结果的查验、业务对账与之后撤权、销毁记录的重放，形成可用状态。数据库的恢复点与消息系统的进度不保证原子：旧数据库配上已经前进的消费确认，可能缺事实；旧的去重记录配上未清理的消息，又可能重复。两种情况分别恢复，不能直接启动消费者盲跑。
- **可重建与不可重建**：可重建的副本先清楚地重建；真实的账簿与外部事实，不能用当前列表伪造完整历史。

具体的工具、恢复目标与资源成本在实验中验证；不凭有备份文件就宣称可以恢复。

高可用切换不同于整套恢复：全部写入同步提交，切换不丢已确认的写入，不冻结系统（D66，底层预留、后期启用）。

## 对象存储

RustFS、其他 S3 实现或客户提供的 S3 服务都是候选资源。所用的子集要验：认证、签名、预签名、长度限制、元数据、版本、列举、并发、错误、桶权限与恢复。标称“S3 兼容”不等于与项目的使用方式兼容。小客户可以共用已有的存储服务；数据积累更多时增加独立存储与冷查询，按运维、网络、恢复与查询负载选择，不只看数据总量。对象属主、附件授权、SDK 适配与“不设纯转发存储组件”的取舍见[附件与存储](../00-overview/guides/files-and-attachments.md)；部署时共用存储不授予跨属主的读取权限。

**开发环境的第二个实现**：SeaweedFS（单进程模式，`make seaweedfs-up`，与 RustFS 互斥，S3 接口同在宿主机 9000，组件与测试的地址不用改）。它用来证明对象存储可以替换，不是推荐的默认。

- **已验证**：两个 SDK 用到的子集——自签 SigV4 的上传、预签名读取、密钥轮换后从下一次上传起生效、没有凭据的一方只靠预签名读取、匿名访问被拒绝；两个 SDK 的对象存储与事件集成测试在 SeaweedFS 4.48 上全部通过。
- **实测**（RustFS 1.0.0-beta.12 与 SeaweedFS 4.48 交替，performance 电源模式），两者各有长短：
  - **大事件路径**（上传、预签名读回，每秒 50 与 200 个 100 KiB，各两遍，每项 10 秒）：SeaweedFS 写入到收到的 p50 在 50/s 时为 RustFS 的 0.94–0.98 倍，200/s 时 0.76–0.96 倍；存储进程的 CPU 约为 RustFS 的 1.4–1.6 倍（200/s 0.9 对 0.59 核）。
  - **只上传 10 分钟**（每秒 50 个 100 KiB，对象累积到 3 万个）：上传 p50 SeaweedFS 4.9 ms、RustFS 6.7 ms，都不随对象数变慢；平均 CPU SeaweedFS 0.20 核、RustFS 0.26 核。
  - **RustFS 的后台扫描**：对象累积到约 1.7 万个以后，每约 60 秒有一次 8–10 秒、约 1.8 核的扫描（容量统计、生命周期、自愈），空闲时也照样；2 万个对象时空闲平均 0.19 核，没有对象时约 0.09 核。上传不受影响。对象更多时扫描更长，规模化之前要实测。大事件对象靠部署的生命周期规则到期删除（组件协议 P6.14），按 MinIO 的同类设计，生命周期也由这个扫描执行（RustFS 上未单独验证），所以不关；可以调慢（`RUSTFS_SCANNER_SPEED`、`RUSTFS_SCANNER_CYCLE`），效果与对过期的影响未测。SeaweedFS 没有这样的周期性开销。
  - 默认仍是 RustFS：已经在全部测量里使用，两者的差别不足以换（版本与选型的原则：优点明显才换）。
- **未验证**：存储一致性套件的其余项（分段上传、范围读取、生命周期、对象锁、桶策略），随附件组件一起验。

## 更换存储时的共同验收

数据库切换核对数据类型、时刻与金额、索引、唯一性、隔离与锁、幂等、发件表，并跑旧数据与在途任务。文件切换核对内容、元数据、引用、权限、失效链接与校验。冷层切换核对格式版本、清单、排序分页、保留与保全。每条路径先写明停机或并行迁移的方案、数据校验与失败恢复。更换数据库、对象存储或冷层时，同时验证必要状态与关联引用可以恢复，不只检查单项存储能读回来。容量适配只有在对应的硬件、数据形状与负载下测量后，才形成客户承诺。

## 停用组件的历史

业务组件不再启用时，历史数据与关联对象仍要有明确的属主、查询、权限、保全与恢复责任；不能只保留库文件而没有可用的查阅路径。标准保留原组件的受限查阅，完全卸载走专项历史迁移（[选配变更、替换与停用](../00-overview/05-change-and-retirement.md#业务组件的停用与退出)）。

## 成长路线与验收

设计当前级别，以及以后增加分区、归档、冷查询、分析库的触发条件。小客户可以选择较简的运行形态，契约为升级路线预留位置；冷层不要求全部在首批实现。验收包含分区窗口、旧数据与在途任务的升级、备份恢复、关联数据、跨层权限、搬运故障、重复执行与查询结果的完整性；容量、恢复时间与查询预算作为带环境条件的测量，不从文档的缺省值推导保证。具体反例见[数据、事务与恢复的验收反例](../01-conventions/validation/data-and-consistency-matrix.md)。

## 已知风险与待定

- 冷读的具体引擎、所在仓库、语言依赖与部署，在需要冷层时选定；DuckDB 等作为候选评估。
- 没有法规或合同依据的保留年限待确认；会计资料与个人信息分别处理。
- 各实体的发生归属时点、快照字段与可交接的对象，随组件设计逐项确定。
- 合并冲突的细则、联系人关联的失效，随伙伴的详细模型设计。
- 平台级的导入按客户上线与导入的协议（协议 16）后续设计。
- 正式文档迁移时，现行的数据生命周期文档中“不带范围的列表只读热窗口”的规则，按本页的默认读取范围修订。
