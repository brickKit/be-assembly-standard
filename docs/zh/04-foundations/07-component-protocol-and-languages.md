# 组件协议与语言

本页说明组件怎样做到用任何语言编写、怎样做到基础设施可替换，每种语言锁定的技术栈，以及这些选择的比较、改变的条件与步骤。组件协议的层级、一致性套件与报告只在[协议 18](../06-protocols/18-sdk-and-conformance.md)；外壳的义务在[协议 17](../06-protocols/17-runtime-and-resources.md#外壳义务)；组件代码怎样写见[组件实现约定](../01-conventions/06-component-implementation.md)。

## 选择

- **每个组件自己选语言**。组件必须遵守的规则不住在某一种语言的 SDK 里，而在**组件协议**：线上格式、表结构、配置键这一层（仓库 `be-protocol`，单独版本化）。
- **是否符合从外部判断**：一致性套件对运行中的容器检验它的端口、它写的表、它发的消息、它的日志与指标，不读源码，所以各种语言的组件用同一组用例（协议 18）。
- **官方 SDK 是参考实现**：Go、Python、TypeScript 三个 SDK 实现同一份协议，用同一组名词；任何 SDK 都不能有规范没写的行为，要先改规范。首批 Go 先做完整实现（D75）。
- **两道准入分开**：能单独运行——任何语言的组件，通过适用于它的套件剖面就能进组合；能进外壳——只有这种语言既有官方 SDK、又有该 SDK 的外壳启动器时才行，因为外壳是一个进程、一个运行时、一个 SDK 版本。
- **每种语言锁一套栈**（见下表）。一种语言出现第二个组件之前，先给它锁定一列，并决定是否为它做官方 SDK。
- **允许 JVM 或 CLR 语言**：内存与启动开销写进组件 `BRICKKIT.md` 的“部署前准备”，作为提醒而不是禁令。

**基础设施的可替换性**用“端口加检查”的做法：只用在基础设施与跨组件机制的边界上，业务逻辑从不是端口（错了就重写）。三条同时满足才算端口：它是基础设施或跨组件共用的机制；主流平台确实有不止一种合理实现，而且今天就能说出第二个实现的名字；换实现不改任何组件代码。端口背后的实现有三种：

| 种类 | 放在哪里 | 由什么选 | 例子 |
| --- | --- | --- | --- |
| SDK 适配器 | 编进每个官方 SDK，按地址的 scheme 或一个配置值选用 | 一个共享配置值 | 消息运输、密钥来源、冷存储 |
| 可替换的成员组件 | 独立的组件，成员共用一份契约 | 组合中装哪个成员，加上指向它的地址引用 | 授权成员、身份成员 |
| 标准协议背后的产品 | 没有项目代码：PostgreSQL 线协议、S3 API 或 OTLP 后面的产品 | 共享配置中的地址 | 数据库引擎、对象存储、观测后端 |

每个端口有四样东西：线上层面的契约、默认实现、具名的备选、一组检查。只有一个实现的端口如实标为“单适配器端口”：它的价值在统一的语义与检查，不在能换。

## 锁定的技术栈

外壳在一个进程里运行多个模块：有些格子在那里物理上混不了（同步的处理框架用不上共享的异步连接池，两种连接池类型不能同时交给模块，两个模块都用默认的指标注册表会让第二个启动即崩溃），另一些能启动、然后悄悄出错（最后一个初始化日志或追踪的模块替所有模块做主）。锁定 HTTP 框架，SDK 的中间件链（追踪、请求身份、截止时间、错误映射、指标、授权）在每种语言里只写一遍。确切的版本以各 SDK 仓库的依赖锁为准。

| 层 | Go | Python | TypeScript |
| --- | --- | --- | --- |
| HTTP | Gin；移动聚合的 GraphQL 用 gqlgen（从 schema 生成），挂在 Gin 上 | FastAPI 跑在 uvicorn 上（请求用 httptools 解析），单进程、单事件循环；出站用 aiohttp | Fastify |
| gRPC | `grpc-go` | `grpc.aio` | `@grpc/grpc-js` + ts-proto |
| 数据库 | `database/sql` + `pgx`，`sqlc`，手写 SQL | `asyncpg`，手写 SQL | `pg`（node-postgres），手写 SQL |
| 迁移 | `golang-migrate`，纯 SQL 文件 | SDK 自带的迁移入口，纯 SQL 文件（A111） | SDK 自带的迁移入口，纯 SQL 文件（A111） |
| 消息 | `nats.go` JetStream | `nats-py` JetStream | `@nats-io/jetstream` |
| 十进制 | `cockroachdb/apd` | `decimal` | `decimal.js` |
| 令牌验证 | `golang-jwt` + `keyfunc` | PyJWT（一律传受众） | `jose` |
| 日志与指标 | `slog`；每个模块一个 Prometheus 注册表 | 标准 `logging` 配 SDK 的 JSON 格式；每个模块一个注册表 | `pino`；每个模块一个注册表 |
| 追踪 | OpenTelemetry Go | OpenTelemetry Python | OpenTelemetry JS，不用自动插桩 |
| 对象存储 | `aws-sdk-go-v2` | aiohttp 加 SDK 自带的 SigV4 签名（只有上传对象与预签名读取两种请求） | `@aws-sdk/client-s3` |
| 测试 | `testing` + `testify` + `rapid` | `pytest` + `hypothesis` | `vitest` + `fast-check` |

任何地方都不用 ORM：SDK 要在每个事务里切换角色与 `search_path`，ORM 与查询构造器做不到或会隐式缓存语句。绝不使用：Go 的 Echo、Fiber、chi 或裸 `ServeMux`、GORM、`lib/pq`；Python 的 Flask、Django、同步 gRPC、SQLAlchemy、alembic、gunicorn 或多个 worker。同一种语言内迁移工具统一，每个组件镜像里是同一个迁移入口；三种语言的迁移状态表相同（`be-protocol` 的 P5.12），所以 Python 与 TypeScript 不用自带状态表的迁移工具，由 SDK 实现迁移入口（A111）。同一个依赖库在整个系统里只用一个版本，这个版本取当前最新、实测可用的那个，升级时为全部组件一起换（[底层选择的原则](README.md#原则)）。

Python 的出站 HTTP 对照过 httpx：同一个探针按 100/s 经 HTTP 调用下一个探针，aiohttp 每次调用的 CPU 从 4.1 毫秒降到 2.6 毫秒、一跳 p50 从 3.3 毫秒降到 1.9 毫秒（代表部署实验第 4 步）；aiohttp 本来就随对象存储的客户端装着，所以不多一个依赖，组件间调用、取发行方公钥与取大载荷都用它。uvloop 同次实测只省 5%–10%，在测量的波动之内，暂不采用。对象存储同样实测过：大载荷的生产者一端只发两种请求（上传对象、签发预签名读取地址），经 aioboto3 每次上传加签名约 4.3 毫秒 CPU，其中大半是 botocore 为每次调用构建与校验请求模型；改为 SDK 自带的 SigV4 签名加 aiohttp 后约 1.1 毫秒，8 个并发时上传延迟 p50 从 28 毫秒降到 10 毫秒。签名与 botocore 对同样输入的结果逐字节相同（SDK 的测试拿 botocore 作参照）。aioboto3 因此不再是 SDK 的依赖；以后要用到更多的 S3 能力（分片上传、生命周期管理）时，再按同样的实测比较。

TypeScript 的栈对照过市场方案：Fastify 而不是 Hono、Express 或 NestJS（它的钩子正好放下 SDK 的中间件链，每个成员一个实例天然隔离）；node-postgres 而不是 porsager/postgres、Kysely、Drizzle 或 Prisma（前者默认隐式缓存预编译语句，其余是查询构造器或 ORM，Prisma 做不到每个事务切角色）；grpc-js 而不是 connect-node（后者没有服务配置里的重试与重试预算）。

## 方案比较

**规则放在哪里**：

| 做法 | 判断 |
| --- | --- |
| **采用**：协议加黑盒套件，SDK 作为参考实现 | 任何语言；对所有组件同一个判定；套件同时是 SDK 的回归测试。代价是要维护一份规范；官方语言以外的“内部”规则只能靠评审 |
| 锁死一种语言 | 规则只有一处，扫源码的门禁覆盖全部代码；但组件用不上更好的生态，“可替换”止步于语言 |
| sidecar 运行时（Dapr） | 语言中立的构件；但每个组件多一个进程、每次调用多一跳，外壳中的成员会丢掉各自的身份，也管不到 schema、角色与发件表的规则，还与 BrickKit 已经做的装配重复 |
| WebAssembly 组件模型 | 一个沙箱承载多种语言；但 PostgreSQL、gRPC、消息客户端在 WASI 下都不成熟 |
| 一个原生核心库绑进每种语言 | 难的部分只实现一次；但每种语言一层 FFI，镜像不开 cgo，各运行时的异步模型不同，核心一次崩溃连带全部语言 |
| 每种语言各自约定，不做黑盒套件 | 不用写规范；但语言之间的漂移要到生产上才发现（旧 SDK 三种语言之间就查出过几十处差异） |

**基础设施的可替换性怎样做**：

| 做法 | 判断 |
| --- | --- |
| **采用**：端口加检查 | “可替换”是一个检查结果；契约与语言无关；每个端口只有一个地方 |
| 不抽象，只有一个实现 | 代码最少；但以后要换就得改每个组件，第二个实现永远没被证明可行 |
| 通用的多后端抽象（ORM 方言、可移植的消息 API） | 最小公分母掩盖了每个后端自己的保证（事务内角色切换、`SKIP LOCKED`、消息系统的确认语义），边缘处会漏 |
| 在一个实现里加配置开关 | 所有客户的变体挤在一份代码里（[参考实现的几种做法都合理时](../01-conventions/08-reference-implementations.md#几种做法都合理时)） |

## 什么时候换

- **协议表达不了某个语言生态必需的能力**：可选的在小版本里扩展协议，变成必须的在大版本里扩展。
- **一种语言出现第二个组件**：锁定它的栈，决定是否做官方 SDK。
- **同一种非官方语言的几个组件在单机上吃紧内存**：做官方 SDK 与外壳启动器，再为这种语言建外壳仓库。
- **锁定的某个库停止维护，或出现变通补不上的能力缺口**：在 SDK 中为该语言的全部组件一次性更换这一格，绝不只为某一个组件换。
- **升为端口**：第二个实现说得出名字、并且有客户或测试环境需要它时，先写契约与检查，再写第二个适配器。**降为单适配器端口**：几种实现在实践中收敛到一个、也没人需要别的时，检查保留作回归测试。**SDK 适配器改为成员组件**：当实现需要自己的进程、发布节奏或数据库时。
- 把两种语言合进一个进程永远不是一次“换”。

## 怎样换

- **用新语言写一个组件**：组件仓库写明所用语言、协议版本与栈；通过适用的套件剖面；别的组件都不动。
- **把一个组件换一种语言重写**：组件 ID、契约、schema、事件不变；发一个新版本，附新的套件报告。原语言有外壳、新语言没有时，部署文件把它移出外壳。
- **协议的小版本**：先改规范与向量，再改套件，再改各 SDK；组件在自己升上去之前，一直按它声明的协议版本受测。
- **更换某个端口背后的实现**：读那个方面的底层选择中的“怎样换”；对目标跑该端口的检查，红了就停；改一次共享值（成员组件则换成员并改地址引用的指向）；组件代码不动——不得不动，说明端口的契约不完整，去补契约。
- **新加一个适配器**：在每个官方 SDK 里都写一份，否则写明哪些语言有它；注册它的 scheme 或配置值并加进检查矩阵；先看到检查对一个故意写坏的假适配器跑红，再相信它的绿；写进对应的底层选择。

## 已知限制

- 没有任何进程混用多种语言；所用语言没有外壳启动器的组件永远单独运行。
- 官方语言之外，“内部”规则套件看不见，只能靠评审，扫源码的门禁也不跑。
- 套件需要真的 PostgreSQL 与消息系统，每个组件要跑几分钟；它在发版时跑，不是每次保存都跑。
- TypeScript 有启动器的设计但没有外壳路线（[部署与运行](01-deployment-and-runtime.md#sdk外壳与运行引擎)）。
- JVM 或 CLR 组件每个进程要几百 MiB 内存、启动要几秒；在单机上这是不选它的主要理由。
- `be-protocol` 发布第一个正式版本之前，规范是候选版，还会随代表组件调整。
