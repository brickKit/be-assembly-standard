# 标识与编号

组件怎么标识自己的行、怎么引用别的组件拥有的行、id 与分区和游标是什么关系，以及人看到的单据编号（`SO202610-00012`、凭证号）怎么分配。加表、改主键、写游标、给单据编号之前，先读这篇。

## 范围

覆盖：组件自有表的主键、对别的组件记录的引用、从 id 派生的分区键、列表游标、单据编号（含无缺号的凭证号）。不覆盖：幂等键（[11-consistency-across-components.md](11-consistency-across-components.md)）、事件 id（[13-event-contracts.md](13-event-contracts.md)）、平台自有的用户 id `sub`（[21-identity-provider.md](21-identity-provider.md)）、租户与法人的标识（租户文档，计划中，07 号文件）。

## 选择

- **每个自有主键都是 UUIDv7**（RFC 9562），存成 PostgreSQL 的 `uuid`，由组件经 SDK 在插入之前生成，绝不靠列的默认值。
- **对别的组件记录的引用是 `TEXT`**，不透明，没有外键。拥有方可能是一个 fork、一个外部系统，或者用的是别的 id 方案。
- **分区表上，`created_at` 就是 id 里嵌着的时间戳**（毫秒精度）。所以按 id 查找时能指明分区，只探一个分区，而不是每个分区都探。
- **契约里的 id 是不透明字符串**，目前是小写带连字符的 UUID，不加类型前缀。可读性交给单据编号。
- **两个例外**：必须严格单调的计数器（授权 tuple 日志的 revision、outbox 的发布序号）用 `BIGINT GENERATED ALWAYS AS IDENTITY`；以标准代码为键的参考表（币种、计量单位）用代码本身作 `TEXT` 自然键。
- **单据编号来自 SDK 里唯一的一套编号机制**：组件自己 schema 里的一张序列表，按法人和期间划分范围，格式由一个配置值决定。会计凭证号**对每个法人按期连续、无缺号**。其他单据号可以有缺号，但绝不重复。

**状态**：已定。随 3.0.0 统一升级落地：12 个有库的组件用 `uuid` 主键重建迁移基线，演示库和测试库重置（没有生产数据）。今天的主键是 `BIGSERIAL`，订单号是 `"SO" + id`，只有 erp/finance 自己写代码给凭证编号。

## 端口契约

### 列

| 表的种类 | 主键 | 说明 |
|---|---|---|
| 普通表 | `id uuid PRIMARY KEY` | id 来自 SDK |
| 按时间分区的表 | `PRIMARY KEY (id, created_at)`，按 `created_at` 分区 | `created_at` = id 里嵌的时间，由同一次 SDK 调用给出 |
| 严格有序的计数器 | `BIGINT GENERATED ALWAYS AS IDENTITY` | 只用在顺序必须单调、对缺口敏感的地方 |
| 以标准代码为键的参考表 | `code TEXT PRIMARY KEY` | ISO 4217 币种、UN/ECE Rec 20 单位代码 |

- 分区表上按 id 查找写成 `WHERE id = $1 AND created_at = $2`，`$2` 由 `$1` 算出。只有拥有方会从 id 推出时间；谁也不去解析别的组件的 id。
- 存放别的组件 id 的引用列是 `TEXT NOT NULL`（或可空），绝不是 `uuid`，也绝不加外键。

### 线上

- proto 里是 `string`，JSON 里是字符串，规范形式是 36 个字符的小写写法（`0192f0c4-7b1e-7cc3-9a52-3f1d2e4b5a60`）。
- 调用方把它当不透明的值：不解析，不按 id 排序，不对版本位做任何假设。格式可以只增地变化；类型永不改变（[0302](../02-decisions/03-contracts-and-data/0302-contracts-are-additive-only.md)）。
- 一个端点是否接受客户端生成的 id（离线草稿、幂等创建），是这个端点契约的一部分。接受时，不是合法 UUIDv7 的值一律以 `INVALID_ARGUMENT` 失败。

### 游标

- `List` 按游标分页（[0301](../02-decisions/03-contracts-and-data/0301-money-as-strings-lists-by-cursor.md)）。默认排序是 `created_at DESC, id DESC`；游标编码最后一行的这一对值，对调用方不透明。
- UUIDv7 在多副本之间不是严格单调的。keyset 分页只需要一个全序，这一对值就给出了全序。

### 单据编号

序列表 `besdk_number_series`，由 SDK 的平台迁移建在每个组件自己的 schema 里（SDK 拥有的表一律带 `besdk_` 前缀，组件 SQL 从不碰它们）：

| 列 | 类型 | 含义 |
|---|---|---|
| `series` | `TEXT` | 哪一套编号，例如 `sales_order`、`voucher` |
| `scope` | `TEXT` | 法人 id，或组件声明的其他范围 |
| `period` | `TEXT` | 期间键，由法人时区下的业务日期得出（[05-time-and-calendars.md](05-time-and-calendars.md)）；凭证用会计期间 |
| `next_value` | `BIGINT` | 下一个要发出的号 |
| `gapless` | `BOOLEAN` | 这个号段的分配模式，见下 |
| `updated_at` | `timestamptz` | — |

主键 `(series, scope, period)`。

两种分配方式，由组件按序列声明：

| 方式 | 怎么做 | 保证 | 用于 |
|---|---|---|---|
| **无缺号** | 在单据所在的同一个事务里对序列行 `SELECT … FOR UPDATE`，就地加一 | 期间内连续；回滚会把号还回去；同一范围内按提交顺序编号 | 会计凭证、发票类单据 |
| **允许缺号** | 在一个单独的短事务里预留一段号，再从内存里发 | 唯一，同一进程内递增；崩溃或回滚后留下缺号 | 订单、发货单、多数单据 |

- 无缺号的号只在幂等认领成功之后才分配，所以重复的请求绝不会占掉一个号。
- 格式是组件的一个配置值（例如 `ORDER_NO_FORMAT`，默认 `SO{yyyy}{mm}-{seq:05}`）。占位符：`{le}`（法人代码）、`{yyyy}`、`{yy}`、`{mm}`、`{seq:N}`（补零到 N 位）。格式里的日期都是业务日期。
- 单据表负责唯一性：`UNIQUE (legal_entity_id, <编号列>)`。
- 什么时候分配编号，是拥有方组件的业务决定（sales：在确认时或创建时）。别的组件按 id 引用单据；编号是给人看的。

## 备选方案

| 方案 | 大小 | 顺序 | 可合并 | 泄露什么 | 在哪生成 | 谁在用 |
|---|---|---|---|---|---|---|
| `BIGSERIAL` / identity | 8 B | 严格递增 | 否 | 业务量 | 库里 | Odoo、ERPNext 的一部分 |
| UUIDv4 | 16 B | 随机 | 是 | 无 | 任何地方 | 早期微服务 |
| **UUIDv7**（RFC 9562） | 16 B | 按毫秒有序 | 是 | 创建时间 | 任何地方；PostgreSQL 18 还有 `uuidv7()` | SAP RAP 的托管 UUID 键、新一代 SaaS |
| ULID | 16 B（文本 26 个字符） | 按毫秒有序 | 是 | 创建时间 | 库外 | 与 v7 等价，但不是 RFC，没有原生类型 |
| Snowflake 类 | 8 B | 有序 | 每个节点要一个 worker id | 时间与节点 | 需要协调 | Twitter、Discord；Dynamics 365 的 RecId 按块分配 |
| 带前缀的 id（TypeID、`ord_01h…`） | 文本 | 同 v7 | 是 | 同 v7 | 库外 | Stripe 风格 |

单据编号：每个序列一个数据库 sequence（快，允许缺号）、一行加锁的计数器（无缺号，串行）、或按块分配（快，允许缺号）。

## 为什么选它

- **可合并**：集团合并报表、并购、把一家公司搬到另一套部署、把脱敏的生产数据拷进测试环境，都不会撞键。
- **任何地方都能生成**：移动端的离线草稿或幂等创建，在到达服务器之前就知道自己的 id。
- **不泄露业务量**：相隔两周的两个 `BIGSERIAL` 订单 id，能算出这段时间下了多少单。有了客户门户和供应商门户之后，这就是真实地送出去的商业情报。
- **按 id 裁剪分区**：`created_at` 从 id 派生，一次查找只碰一个分区。
- **是标准**：RFC 9562，在库外生成，所以支持的每个 PostgreSQL 版本上都能用。
- **凭证号按期连续无缺号**，符合国内会计实务：凭证号在每个期间内连续编排。

## 为什么不选其他

- **`BIGSERIAL`**：泄露数量，任何合并都会撞键，客户端也没法生成。
- **UUIDv4**：随机插入散布在整棵 B-tree 上，也没法裁剪分区。
- **ULID**：和 v7 性质相同，却没有标准，也没有原生类型。
- **Snowflake**：要在多副本和外壳成员之间协调 worker id，这是我们本来不需要的活动部件。
- **带前缀的 id**：每个工具都得解析前缀，正则到处蔓延；可读的东西已经由单据编号给人了。
- **库默认值（`uuidv7()`）**：只有 PostgreSQL 18 有，而且插入之前不知道 id。
- **凭证用 sequence**：会留下缺号，而凭证编号不允许缺号。

## 什么时候换

- **id 方案**：不换。有实测依据的例外：某张超大的明细表，证明 16 字节确实是瓶颈时，它自己的主键可以用 `BIGINT GENERATED ALWAYS AS IDENTITY`，并且仍然不向组件之外暴露任何东西。
- **无缺号编号**：当某个法人的凭证过账撞上串行计数器的吞吐上限（每秒几十到一百张左右），并且业务接受缺号或换一个编号时点（例如在期末结账时编号）时。
- **编号格式**：客户想要别的格式时随时可换；它是配置。

## 怎么换

- **编号格式**：改 `config/<scope>-<name>.yaml` 里组件的格式键。新号用新格式；已有单据保留原号；序列按期间划分，所以不需要重置任何东西。
- **把某个序列从无缺号改为允许缺号**：改拥有方组件里这个序列的声明，发一个版本。这是业务决定，写进组件的设计文档。
- **id 方案**：不可更换。改它就要重写每张表和每个引用，所以只定一次。

## 一致性测试

共享向量放在计划新建的 `brickKit/be-protocol` 仓库的 `vectors/numbering/`（格式占位符、跨时区午夜时由业务日期得出的期间键），每个官方 SDK 都读。要先写红的 SDK 测试：

- 生成的 id 是第 7 版，同一个生成器在同一毫秒内生成的 id 递增；
- 从 id 推出的时间与一起设定的 `created_at` 相同，精确到毫秒；
- 同一范围、同一期间里并发 100 次无缺号分配，得到一段连续的号，没有缺口也没有重复；
- 按法人、按期间分别计数；
- 允许缺号的序列回滚后留下缺号，但绝不重号；
- 端点接受客户端生成的 id 时，不是合法 UUIDv7 的值被拒绝。

组件测试（以 erp/sales 为样板）：分区表上按 id 取单条只扫描一个分区（用 `EXPLAIN` 断言）；订单号无法从订单 id 推出。

门禁：新迁移里自有主键不是 `uuid` 时，`make gates` 失败（统一升级之前发布的文件是冻结的，只给警告）。

## 已知限制

- UUIDv7 会暴露精确到毫秒的创建时间。连这一点都要紧的地方，只对外暴露单据编号。
- 无缺号编号让每个法人、每个期间的过账串行：吞吐上限是每个法人每秒几十到一百张左右凭证。这是为了凭证号连续而有意做出的取舍。
- 跨组件的引用没有外键；悬空引用靠拥有方答"不存在"来发现，而不是靠数据库。
- 3.0.0 重建会丢弃现有的演示数据和测试数据；种子数据重新生成。
