# 观测

本页说明日志、指标与追踪用什么、为什么、什么时候换后端、怎样换。两档方案（D43）、输出契约、业务健康指标与必需告警只在[协议 17 的观测](../06-protocols/17-runtime-and-resources.md#观测)；业务审计与运行日志分开，规则在[协议 03](../06-protocols/03-audit-durability.md)；日志字段、指标名与脱敏规则的格式在组件协议中规定。

## 选择

- **OpenTelemetry** 做追踪，指标经 OpenTelemetry 的指标接口接到同一个 Prometheus 注册表；每一跳都用 W3C Trace Context 与 Baggage 传播。Baggage 只作追踪，不成为用户或授权的属性（安全 02）。
- **指标用 Prometheus 拉取**，不开采集器也能看；每条序列带 `component` 标签；外壳暴露一个汇总的指标端点（协议 17 的外壳义务）。
- **日志是标准输出上的 JSON 行**，别无其他；采集器从容器运行时取日志。写日志从不卡在网络上。
- **每个成员有自己的遥测身份**：外壳里的服务名是成员的组件 ID，绝不是外壳的名字。
- **日志级别由 SDK 按结果的类别决定**（例如客户端错误与服务端错误分开），不由各组件自己定：ERROR 因此有意义。
- **后端中立**：OTLP 就是端口；默认栈是 Tempo、Loki、Prometheus、Grafana，镜像钉到确切版本；基本档只要求本地持久的日志与指标（D43）。
- **脱敏在 SDK 中**：日志不写密钥、令牌、受限字段的值与个人信息原文；三种语言共用脱敏向量（协议 18）。

## 方案比较

| 方案 | 判断 |
| --- | --- |
| **采用**：OpenTelemetry 追踪 + Prometheus 拉取 + 标准输出日志经采集器 | 代码层面厂商中立，每个官方 SDK 都讲 OTLP 与 Prometheus，后端是部署时的决定；指标不需要采集器，日志不依赖网络，适合资源有限的单机。代价是三种信号三条路径 |
| 只用 Prometheus 拉取，不做追踪 | 最简单；但一次跨销售、库存、财务的慢确认跟不下去 |
| 所有信号都走 OTLP 推送 | 一条管道；但没有采集器就什么都看不到，采集器配错了一切都看不见 |
| SDK 直接把日志发到日志库 | 不需要采集器；但写日志进了请求路径，网络一抖就阻塞或丢失 |
| 厂商 SDK（Datadog、阿里云 ARMS、腾讯云 APM 等） | 开箱功能多；但每个组件、每种语言都绑定一个厂商，客户用的是别的平台就用不上 |
| 其他接收 OTLP 的后端（SigNoz、OpenObserve 等） | 不是代码层面的选择：它们替换默认后端，见下文 |

## 什么时候换

- 客户已有一个接收 OTLP 的观测平台（SigNoz、OpenObserve、云 APM、Datadog）：换后端，组件不动。
- 资源受限的部署只用基本档；需要集中检索与看板、或诊断需求变高时升到完整档（D43、[规模阶梯](01-deployment-and-runtime.md#规模阶梯)）。

## 怎样换

1. 改采集器的导出目标（平台自己采日志时也改日志的接收端）；平台提供采集器时，把遥测地址指过去。
2. 保留 Prometheus 拉取，或者让采集器拉取指标端点再转发。
3. 组件、SDK 与版本钉都不改。遥测不发送到客户声明之外的目的地（D42）。

## 替换时的检查

在固定的部署条件下演练（[测试与验证的观测分档对照](../01-conventions/02-testing-and-validation.md#代表部署对照实验)）：组件与外壳重启后日志仍可查；受保护请求与跨成员的故障能按追踪身份关联；外壳中每个成员的追踪带自己的服务名，出现外壳自己的名字就说明有埋点漏了；指标汇总后按成员可分；必需告警按协议 17 触发；采集或告警接收方故障时的丢失边界与恢复；日志中没有密钥、令牌与个人信息原文。

## 已知限制

- 一条异步流程是若干个由链接连起来的追踪，不是一棵树。
- Prometheus 每个容器只拉取一个端口：外壳必须提供汇总端点，否则只看得到一个成员。
- 日志采集依赖容器运行时的日志驱动；采集器停机期间写的日志，只有运行时保留着才会被补读。
- 开启采样时按追踪采样；被采样掉的请求仍有它的日志与指标。
- 业务审计不靠运行日志：日志可以采样与短期保留，审计不可以（协议 03）。
