# 数据库引擎与连接

本页说明在线数据库的引擎选了什么、和哪些引擎比较过、什么时候换、怎样换、换之前要证明什么。在线数据库的分离形态与替换层次见[数据与生命周期](02-data-and-lifecycle.md#数据库的选择)；数据库的使用规则（schema、角色、事务入口、超时、连接池）只在[协议 14 的数据库](../06-protocols/14-data-foundations.md#数据库)。

## 选择

- **PostgreSQL 方言族**。外壳要求 PostgreSQL 16 及以上：外壳登录角色以不继承的方式获授成员角色（协议 14）；单独运行的下限随客户基线声明（D58）。
- **“可替换”的意思是**：换成另一个说 PostgreSQL 线协议、并且通过数据库检查的引擎。SDK 里不做多方言抽象：每个组件都要的机制（事务内的角色切换、分区、队列认领、应用锁、错误分类、平台表）在 SDK 的 PostgreSQL 方言层里只有一份；业务 SQL 留在各组件的存储层。
- **一切访问经 SDK 的事务入口**，发件转发、消费者、生命周期作业也一样，所以外壳的登录角色自己不需要任何业务权限。
- **连接池有上限**；外壳中每个成员在共享池里有自己的预算（协议 17）。
- **连接池代理可选**；用的话必须是事务模式，迁移绕过它直连数据库。
- 外部产品（身份产品等）用各自的角色连库，绝不用超级用户。

## 方案比较

| 引擎 | 长处 | 对本项目的短处 |
| --- | --- | --- |
| **PostgreSQL**，含托管服务（RDS、Aurora PostgreSQL、Cloud SQL、AlloyDB、Azure Flexible Server、阿里云 RDS PostgreSQL、PolarDB PostgreSQL 版） | 需要的机制全都有；生态最全（CloudNativePG、Patroni、pgBackRest） | 单写节点；横向扩展要靠分区、只读副本或分片扩展 |
| MySQL 8、MariaDB、TiDB、OceanBase（MySQL 模式） | 很多运维团队熟悉；TiDB 能横向扩展 | schema 就是数据库；没有事务内的角色切换；DDL 不是事务性的；分区表不支持外键 |
| CockroachDB | 分布式、强一致 | 没有应用锁，只有 SERIALIZABLE，分区语义不同；商业许可 |
| YugabyteDB（YSQL） | PostgreSQL 兼容度高，Apache-2.0，可多地域 | 应用锁、部分 DDL 与分区要逐项验证；资源占用重 |
| Citus（PostgreSQL 扩展） | 按 schema 分片：每个 schema 整个落在一个工作节点上，与“每组件一个 schema”的约束一致 | 需要协调节点；部分扩展与 DDL 受限；按 schema 分片不解决组件内部的热点 |
| 人大金仓 KingbaseES（PostgreSQL 模式）、瀚高 HighGo | 在信创名录里；内核源自 PostgreSQL | 版本对应关系、不继承授权的语法、扩展都要实测 |
| openGauss、GaussDB、海量 Vastbase | 在信创名录里 | 从较早的 PostgreSQL 分叉：分区语法、角色、函数都有差异 |
| 连接池代理（PgBouncer、PgCat、Supavisor、Odyssey、CloudNativePG 的 pooler） | 减少后端连接数 | 事务模式下不保留会话状态，所以一切设置都必须在事务内 |

**为什么选 PostgreSQL**：这里每一种隔离与协调机制都是它原生的：事务内的角色切换、声明式分区、`SKIP LOCKED`、事务级应用锁、事务性 DDL。它覆盖的托管服务与源自它的国产发行版最广，“客户允许用哪种数据库”通常在这个家族里就有答案。机制都放在 SDK 的同一层里，认证一个新引擎就是跑一次检查，而不是逐个审查组件。

**为什么不选其他**：

- **MySQL 系**：没有事务内的角色切换，组件身份模型就要换一套机制；DDL 不是事务性的，失败的迁移会只执行一半；分区表没有外键；每个组件的存储层都要移植。
- **CockroachDB**：没有应用锁，只有 SERIALIZABLE（库存余额这类热点行会不停中止），而且是商业许可。
- **openGauss 及其衍生版**：分叉点恰好在 SDK 方言层所在的地方有差异，预计要改 SDK，不作承诺。
- **多方言抽象**：只有一种真实方言时写的抽象只能靠猜（[AI 编码习惯](../01-conventions/09-ai-coding.md#何时用设计模式)），也会把每个组件退到最低能力交集。

## 什么时候换

- **单库写入成为瓶颈**（实测，并且已经做了查询与索引、分区、只读副本与历史分离之后）：先确认热点不是组件内部的同一行；是组件之间的总量时，评估独立实例或按 schema 分片（[数据与生命周期](02-data-and-lifecycle.md#数据库的选择)）。
- **客户强制要求信创数据库**：对候选库跑数据库检查，看能力矩阵，选通过的那个。
- **某个组件需要独立的实例或存储能力**：按[在线数据库怎样分离](02-data-and-lifecycle.md#在线数据库怎样分离)迁移；它通过自己的配置拿到自己的连接目标，在外壳里得到自己的池。
- **连接数成为限制**（大量进程连同一个实例）：加一个事务模式的连接池代理。

## 怎样换

- **换成家族内的另一个引擎或托管服务**：把共享的数据库连接值指向新实例，对它执行装配工具生成的建库、建角色与授权脚本（不依赖服务自带的默认超级用户），再跑数据库检查。组件不改。
- **按 schema 分片**：在协调节点与工作节点上装扩展，让每个组件的 schema 成为分布式 schema，再跑数据库检查。组件不改。
- **连接池代理**：运行连接指向代理，迁移连接指向数据库本身。
- **家族之外**（MySQL、CockroachDB）：这不是一次更换。它意味着每个官方 SDK 新写一套方言层、每个组件的存储层都要移植，要当成一个项目来规划。

## 替换时的检查

数据库检查以一个连接目标为参数，分三层：SDK 的事务语义（事务内设置、重试、超时、认领）；能力清单里每项能力一条探针；几个形状不同的组件的 L2 测试。输出一张“引擎 × 能力”矩阵，结论分三档：可用、降级、不可用。

| 档 | 引擎 |
| --- | --- |
| 支持 | PostgreSQL（客户基线声明的主版本）；托管 PostgreSQL 服务 |
| 很可能可用，待实测 | 人大金仓、瀚高；按 schema 分片的 Citus |
| 未验证，预计要改 SDK | openGauss、GaussDB、海量 Vastbase；YugabyteDB |
| 不支持 | CockroachDB；MySQL、OceanBase（MySQL 模式）、达梦 |

要先证明会红的检查：成员超出自己的连接预算时拿到“连接池耗尽”、另一个成员照常；外壳登录角色不切换角色就访问不到任何成员的表；运行角色执行 DDL 失败，而经属主建立的受限函数预建分区成功，受限函数对其他角色不可执行；两个成员对结构不同的平台表发出同一段 SQL，不报“缓存的计划改变了结果类型”；迁移中出现属主变更、授权、建 schema 或角色名时扫描失败；组件代码里发 `SET ROLE` 时扫描失败。

## 已知限制

- **只有 PostgreSQL 家族**：离开它，就要在每个官方 SDK 里新写方言层，并移植每个组件的存储层；业务 SQL 大量使用 `ON CONFLICT`、`RETURNING`、`ANY($1)`、interval 与 `JSONB`。
- **信创发行版还没实测**；检查对某个库跑过之前，不承诺它。
- **单写节点**：横向扩展走按 schema 分片或组件分离，这条路设计上留好了，还没测过。
- **所有进程共用一个实例的连接上限**：连接预算让总数如实，但没法让服务器变大。
- **属主凭据在服务容器中可见**（迁移与服务由同一镜像执行），运行时代码不使用它（[已接受的平台限制](README.md#跨方面的约束)）。
- **高可用与备份**按 D66 与[协议 15](../06-protocols/15-backup-and-recovery.md)；工具（pgBackRest、WAL-G、CloudNativePG）在代表部署实验中选定。
