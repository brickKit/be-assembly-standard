# AI 编码习惯

本页说明代码怎样写才便于 AI 读懂与修改：何时用设计模式、本项目已定的模式、长业务函数的注释、人要审什么、什么时候整体重写。一次会话读多少、组件仓库的布局与代码地图见 [AI 导航](05-ai-navigation.md)；测试的分层与节奏见[测试与验证](02-testing-and-validation.md#实现测试的分层与节奏)。

写代码的 AI 与人类工程师的失败方式不同，付出的成本也不同：它每次会话都从零开始，没有上一次的记忆，上下文有限；它没法“回头再看那个文件，我大概记得”；对它来说，整份重写一个文件，可能比在三个补丁上小心加第四个更便宜。下面的规则都由此而来。

## 何时用设计模式

模式从来不是强制的；合适的地方就该用。判据只有一条：

> **一个全新会话里的 AI，只读少数几个文件，能不能把一条新规则写对？**

| 有帮助 | 为什么 |
| --- | --- |
| 文件小、职责单一 | 每碰一个文件都要整份读进上下文：在 600 行的文件里改三行，要花 600 行的上下文 |
| 注册表集中在一处 | 一个文件列出全部规则，全集一眼可见；分散在各处只能靠搜索去猜，漏一个就是漏改一处 |
| 显式优于隐式 | 反射注册、自动发现的装饰器、按命名约定扫描，静态阅读看不见 |
| 一种情况一个文件，文件名就是情况 | 看到 `rule_volume_discount.go` 不用打开就知道该改哪个文件 |
| 状态迁移集中在一张表里 | AI 最常见的错误是某个入口忘了检查前置条件；声明在一张表里，结构上就不可能漏（[图与表的状态迁移表](04-diagrams-and-tables.md#状态迁移表)） |

| 有害 | 为什么 |
| --- | --- |
| 深继承链、多层抽象基类 | 看懂一个方法要跳四个文件；跳到第三个 AI 就开始猜 |
| 元编程、反射、动态分派 | 静态推断不出实际走哪条路径 |
| “万一以后要扩展”的提前抽象 | 多一层就多一个要跳的文件，今天毫无收益 |
| 一个模式散布在多个包里 | AI 改了 A 包，漏了 B 包里对应的改动 |

模式的价值在于把一段长逻辑变成几个结构清晰的短文件，而不是把逻辑撒满整个代码库。一个模式只待在一个包里。

**值得停下来考虑的信号**：

| 信号 | 症状 | 用什么 |
| --- | --- | --- |
| 分支超过 5 个还在加 | 每加一种情况都要改一个长函数，可能碰坏别的分支 | 策略：一种情况一个文件，登记进一张表 |
| 函数超过 150 行、文件超过 600 行 | 每次改动都要读完整个文件 | 先按职责拆，再看拆出来的部分像哪种模式 |
| 同一个流程跑好几遍，只有中间一两步不同 | 复制了三份，修错只修了一份 | 模板方法或责任链 |
| 一个状态迁移的合法性在不止一处检查 | 某个入口漏了检查，数据进入不该有的状态，什么都不报错 | 显式状态机，每条边只在一处声明 |

**不该用的时候**：简单资源的普通增删改查，直接写最清楚；只有两个分支、看不到第三个，`if … else` 比一个接口、两个实现、一张注册表好懂；“万一以后需要”，等第二个真实实现出现再抽象，那时才知道该沿哪条缝切。最后一条最容易违反，因为“留出扩展空间”听起来总是对的。检验方法：**你现在能说出第二个实现具体是什么吗？**说不出就先别抽象。

**用了模式之后的文件组织**：

```
internal/pricing/
├── pricing.go             接口 + 注册表 + 执行顺序：读这一个文件就知道有哪些规则
├── rule_base_price.go     一条规则一个文件
├── rule_customer_tier.go
├── rule_volume_discount.go
└── pricing_test.go        每条规则一个测试，外加对整条链的性质测试
```

拆对了的标志：一个新会话要加一条折扣规则，只读 `pricing.go` 与任意一个 `rule_*.go`，新建一个文件、在注册表里加一行：读两个文件，改零个已有的规则文件。拆错了的标志：还得去改别的规则文件（链的顺序或数据流不干净），或者要跳三层才找到接口（层太多）。

## 本项目已定的模式

这些不需要再判断，直接用；它们的分支数与扩展速度都可以预见。

| 组件 | 位置 | 模式 | 为什么 |
| --- | --- | --- | --- |
| `erp/sales`、`erp/purchase` | 定价与折扣 | 策略 + 责任链 | 定价规则是最客户化、改得最频繁的部分；加一条规则就是加一个文件 |
| `erp/sales` | 订单与确认过程的状态 | 显式状态表 | 迁移的合法性集中在一处（协议 04） |
| `erp/inventory` | 出入库的单据类型 | 策略 | 收货、发货、调拨、盘点、退货各有各的校验，都落进同一张流水 |
| `erp/costing` | 计价方法 | 策略，按成本声明的范围选择 | 移动平均、先进先出、标准成本、定期盘存是计价的替换点（D27、D46、协议 05b） |
| `erp/billing` | 出账政策 | 策略 | 按订单、按交货、按里程碑或工时，各有各的额度来源（协议 05） |
| `erp/finance` | 会计事实 → 分录 | 每种事实一条过账规则 | 新增一种事实就是新增一条规则，不碰已有的（协议 05 的会计事实契约） |
| `infra/notification` | 渠道路由 | 策略 + 注册表 | 渠道并存，按装了哪些渠道组件注册 |
| `infra/print` | 渲染后端（PDF、ZPL） | 策略 | 两种输出除了输入参数毫无共同点 |
| `hrm/payroll-*` | 薪资项计算 | 策略 + 拓扑排序 | 薪资项互相依赖；顺序错了数字就错 |
| 跨组件流程的协调者 | 步骤与补偿 | 命令，持久化为工作项 | 每一步可重试、可补偿，重启后能续上（协议 01、04） |
| 装配工具 | 各项产出 | 每项产出一个包，统一接口 | 新增一项产出不碰已有的 |

## 长业务函数的注释

复杂的业务函数超过 50 行时，带一段用自然语言写的决策树注释；分支不直观的地方再配一张 Mermaid 流程图。没有的话，审查时打回。组件级的决策表写在组件的 `docs/design.md`（[图与表的决策表](04-diagrams-and-tables.md#决策表)），函数里的注释指向它，不复制它。

## 人要审什么

没有人能逐行读完一个大型的 AI 生成代码库。审查的时间花在不可逆、门禁看不见的地方：

| # | 审什么 | 为什么是它 | 在哪 |
| --- | --- | --- | --- |
| 1 | 契约 | 最不可逆：一旦有人消费，就只能兼容地演进（协议 19） | `contracts/` |
| 2 | 迁移 | 第二不可逆：主键、切分键、索引在建表时定死，有数据后再改就是一次数据迁移 | `migrations/` |
| 3 | L2 测试里的不变量清单 | 只看该有的不变量是否都列了；门禁只跑已经写下的测试 | 组件的测试目录 |
| 4 | `docs/design.md` 的边界与依赖 | 边界画错或多一条同步边，会污染整张架构图；必需依赖保持无环（检查 34） | `docs/design.md` |
| 5 | 门禁输出 | 不用读代码；失败的门禁会点名位置 | 项目与组件的门禁 |

不审：逐行业务代码、L1 测试、构建脚本、镜像文件。门禁与测试覆盖它们；那里真有问题，总会有东西变红。

## 整体重写而不是打补丁

一段逻辑跑偏了（早期判断没站住，几轮补丁朝不同方向打），诚实的修法可能是重写而不是再打一个补丁。

**该重写的时候**：

- 同一段逻辑已经朝不同方向补了好几次，改一行都要先在脑子里重放那些历史；
- 问题不是错误，而是一个设计判断本身错了，在它上面继续盖只会让偏差越积越多；
- 它是种子或演示数据：假数据，没有历史要迁移，重写的成本约等于删掉重建。

**怎么做**：

1. 把要重写的文件复制到仓库之外的草稿位置，只作对照参考（Git 已经保存了每个版本）。
2. 重写作为单独一次提交落地，提交信息写为什么重写。
3. 照常跑全部门禁；不因为是重写就降低标准。重写碰到的范围更大，这是要多验证而不是少验证的理由。
4. 删掉草稿副本。
5. 如果重写是因为发现早先的方向错了，把它写到下一个读者会看的地方：“看起来对、其实错”的教训写进组件 `AGENTS.md` 的易错点，改变了的设计判断写进 `docs/design.md`。
