# 数据约定

本项目的数据从哪里来。有两条相互独立的路径：给人用的种子数据和给自动化测试用的测试数据；背后是同一条原则：尽量覆盖更多场景，依赖方缺东西时去源头补。现在灌了哪些种子数据见 [../seed-data.zh.md](../seed-data.zh.md)。

## 两条路径互不共享

| 路径 | 谁用 | 怎么产生 | 生命周期 | 能否共享 |
|---|---|---|---|---|
| **测试数据** | 所有自动化测试：L1–L4、FE-1–FE-4 | 每次运行现建，用时间戳或随机后缀保证唯一 | 从不清理；可以堆积，下次运行换新后缀 | **绝不**：任何测试都不依赖别的测试或上一次运行留下的行 |
| **跨组件测试数据** | 跨组件测试 | 测试调用依赖方真实的 gRPC 或 REST 接口，在依赖方那里建出需要的形态 | 同测试数据 | 同测试数据 |
| **种子数据**（`make seed`） | 人：探索、演示、让新组件一建好就有数据 | 固定 `idempotency_key`，先认领；重跑不会再建 | 持久；用 `make seed-clean` 或 `make db-reset` 清掉 | 组件之间可以互相查找、复用种子数据；测试绝不依赖它 |

清掉种子数据永远不会让测试变红，测试也永远不会改动人正在探索的数据。混在一起，"这个测试为什么突然红了"就有两个毫不相干的原因，要走两条毫不相干的排查路线。

**它们是两个物理上分开的库**，在同一个 PostgreSQL 实例里：测试用 `brickkit_test_db`（`TEST_PG_DSN`，由 `make test-db-init` 建立和刷新），运行中的项目用 `brickkit_db`。两边 schema 结构相同，数据互不相通。有的测试会写迁移种下的基准行（默认仓库、默认法人）；共用一个库的话，每跑一次测试演示数据就真的变一次，跟容器开没开无关。

**不用一次性数据库。** 分区表和 `SET LOCAL ROLE` / `search_path` 塞不进内嵌引擎，而换一种数据库实现与"集成就是真实基础设施"直接冲突。解决"重建数据慢、互相污染"的办法是让数据本身可以随用随弃：唯一后缀、从不清理。这是长期形态，不是权宜之计。

## 尽量覆盖更多场景

- **种子数据追求多而全**：每个状态机的每个状态、每个分支、每条失败路径、每个数据范围维度，都有能真正触发它的数据。数量和多样性本身就是目的。
- **测试数据追求少而准**：刚好够验证一个断言的最少数据。例外是性质测试，它的大量随机输入是为了撞到边界，不是为了看起来完整。
- 两者的底线相同：**任何组件都不能只有"一切正常"的数据或断言。**

## 依赖方缺数据或能力时

**在测试里。** 测试需要依赖方有某种形态的数据（信用额度为零的客户、停用的产品、处在某个阶段的商机）：

1. 在测试里通过依赖方的真实接口现建。
2. 依赖方的契约根本没有办法造出这种形态时，**先给依赖方补上这个能力**（和任何契约变更一样只增不改），再通过它造数据。不绕过，不跳过这个场景。
3. 测试里不允许用裸 SQL 直接写别的组件的库。那会在契约之外悄悄建立耦合；契约以后怎么变，这个测试都不会报警。

**在种子数据里。** 下游需要的组合（华南部门的一个已停用客户）上游的种子数据还没有，下游就直接去上游组件的种子脚本里加上。不在下游将就，也不干等。数据是假的，多几种变化不花成本，上游数据丰富，下游才有东西可挑。

## 种子数据规则

种子数据也在服务测试：人打开运行中的系统、用像样的数据走一遍，是检查一整条链路的方式，和自动化测试同样重要。数据从头到尾都是假的，这本身是一种自由：丰富度往上限推。

**种子数据要同时服务的目标**：每个分支和失败路径都能被触发；一个组件加它的依赖能单独检查；一个组件交付前它的整条链路能跑通；整个项目交付前从各个角度都能验证（权限边界、事件、补偿）；人随便打开一个页面都有东西可看。

**"数据多"不会自动带来的东西**：

- **数据范围维度要真实存在**：有多个部门、多个负责人、多个仓库、多个法人，每个里面都有测试账号。数据全挂在一个全能账号下，数据范围就完全体验不到。
- **数量要够翻页**：游标分页的列表只有五行，永远看不到第二页。
- **时间要分散**：数据分布在过去的不同日期（用绝对值 `now() - interval` 设，重跑不会越跑越早），"最近 N 天"查询、趋势图、分区维护才有东西可验证。
- **要有负面数据**：停用的记录、零库存、逾期未结、被驳回的申请。
- **要能被发现**：[../seed-data.zh.md](../seed-data.zh.md) 列出每个组件灌了什么、多少、归谁。改种子数据时在同一个提交里更新它。

**归属与协作**：

- **每个组件拥有自己的种子数据**（在自己仓库里 `make seed`）。集中脚本只有全部组件一起跑时才可用，单独起一个组件就什么都没有。
- **组件的 `make seed` 先跑它声明的每个依赖的种子**（必需和可选一视同仁），再跑自己那部分。对一个组件跑，就得到一整套完整数据。连不上的依赖跳过，不算失败。
- **交接用组件自己的幂等表。** 种子脚本只负责把数据灌进去，不负责打印 ID。谁需要 ID，谁按固定的 `idempotency_key` 去查。用 `psql` 时加 `-tA -q`，否则 `SET` 的回显会混进取到的值里。
- **种子脚本链接另一个组件灌下的行时，幂等键里要带上被链接行的真实 ID。** 那些 ID 每次清掉重灌都会变；用位置编号做的键会永远绑定第一轮的 ID，链接静默地指向已经不存在的行。
- **种子数据是一份轻量契约。** 被别的组件查找引用的标识只能新增，不能删除，也不能改变含义。
- **冗余可以接受。** 两个组件各灌一个"制造业客户"没问题；复用已有的比协调归属便宜。
- **删除不等于重置。** 有只增表（账本、已锁定的会计期间）的组件没有 `make seed-clean`，只有 `make db-reset`（`migrate down` 再 `up`）：逐行删除复原不了，序列也不会回退。行可以安全删除的组件两个都可以有；优先用 `seed-clean`，它不碰别的数据。
- **负面路径来自真实的业务失败。** 组件刻意不对外开放某种写入（异常待办、通知记录）时，靠让一条真实业务流程失败来产生数据（超出信用额度的订单），绝不伪造契约禁止的那次写入。
- 种子数据里每个人类可读的名字都以 `「本地测试」` 开头，任何界面上都能一眼认出；`seed-clean` 靠这个前缀加固定键找到自己的行。
- `grpcurl` 输出的 proto 字段是小驼峰（`reservationId`），手写的 REST JSON 是下划线。解析带下划线的字段之前先看一眼真实输出。

**凭据绝不进入每次部署都会运行的东西。**

- 每个部署都需要的基准数据（默认仓库、默认法人和科目表、计量单位）属于迁移：它是产品的一部分。
- 测试账号、测试角色、测试应用只在 `make seed` 里，它只手工运行，从不出现在任何部署或 CI 流程中。迁移里的测试账号，就是在每个客户的系统里埋一个密码公开的后门。
- 真实部署的第一个管理员来自配置：部署者把自己的身份填进 infra/authz 的初始管理员设置，组件启动时幂等地授予管理员角色。这和本地开发需要的"拥有全部权限的测试角色"是两回事。

## 测试数据规则

- 生成方式和生命周期：唯一后缀，从不清理（第一节）。
- 自己触发消费者的消费者测试用私有 subject 和唯一的 `aggregate_id`（[testing.zh.md](testing.zh.md#l4-集成测试)）。
- 依赖方契约造不出的数据形态：见[依赖方缺数据或能力时](#依赖方缺数据或能力时)。
- 测试数据不考虑种子数据特有的维度（翻页、时间分散、可发现性）；它只对准自己的断言。
