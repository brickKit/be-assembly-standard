# 工程规范

本页说明规则归谁、必须重审的规范、可配置与可定制的承接顺序、有限业务设置、配置生效与密钥轮换、版本与升级、客户交付版本的维护。配置、密钥、注册表、版本与产物的完整协议见协议 19；SDK 的共同契约与一致性套件见协议 18；文档、图表与 AI 导航的规范见本目录的另外三篇。

## 规则归谁

| 层 | 拥有什么 | 产出的文档与检查 |
| --- | --- | --- |
| BrickKit | 清单、三层装配、地址派生、构建、部署与发布命令 | 真实命令、版本、平台反馈与真机记录 |
| 组件协议与族契约 | 外部行为、错误、配置、事件、资源与一致性要求 | 规范、schema、向量、黑盒套件 |
| SDK | 协议在各语言的实现与运行机制 | 语言 API、示例组件、平台表、测试与版本 |
| 业务组件 | 数据、业务规则、接口、事件与业务权限映射 | 边界卡、业务规格、图与表、测试、运维说明 |
| 装配项目（本项目） | 客户选项、精确版本、配置、部署、环境与验收 | 注册表、组合清单、工具、交付证据 |
| 客户 Fork | 项目团队维护的客户偏离版本、来源与兼容责任 | 差异、升级与迁移说明、兼容验收；客户决定是否实施升级 |

## 必须重审的规范

正式开发前必须按终局设计重审的规范：契约优先与业务规格；语言与技术栈的准入；生成代码的新鲜度；配置的权威来源与密钥轮换；注册表身份；数据库的属主与运行角色；接口权限的注册；事件与错误的命名；Fork 的版本与来源；依赖升级；外壳成员；发布检查；数据与测试隔离；文档的路由与语言；AI 一次任务的读取与变更范围。它们已写进本目录的规范与相应协议（组件实现约定、种子与测试数据、开发流程与发布、AI 编码习惯、文档规则、AI 导航，协议 14、18、19）；随重建的 SDK 与工具落地时，按真实的命令与检查再核对一遍，不一致的先改文档。

每条规范写明目的、适用条件、违反时的症状与验证方法；机械检查要另外证明自己真的能捕捉违规（检查带坏变体，协议 18）。规范之间冲突时，记录影响与裁定，不靠追加例外让读者猜。全局推荐见[底层选择](../04-foundations/README.md)。

规则改变时分别评估：语法兼容、业务含义、权限、数据、在途的副作用。新增字段或枚举也可能影响旧消费者。破坏性迁移要有部署版本的准入与旧任务、旧客户端的明确处理；数据库里当前没有旧会话，不能证明旧版本不会再启动（协议 14、19）。

## 共享语义

金额与数量在外部是十进制字符串，单位与汇率、舍入依据随值传递；时刻用 UTC，业务日期按法人的日历；身份稳定，正式单号另有规则。精度、舍入与分摊顺序、日期依据、未知字段与枚举、规范化编码由协议 14、安全 09 与三种语言的共同向量确定；不把不同数据库的 text 输出或浮点 JSON 当作跨语言标准。

组件声明必需的审计动作与风险分类：敏感读取与导出、必要的变更、代操作、安全拒绝；普通低风险查询与长期业务审计分别处理。声明格式是操作定义上的 `audit: required`（安全 09），必需类别见协议 03，缺漏由一致性套件检查。

## 可配置与可定制

| 变化 | 承接方式 |
| --- | --- |
| 资源与运行预算 | 带范围与关联约束的配置 |
| 客户的业务参数 | 所属业务组件维护的有限设置，客户授权人员通过界面调整（见下节） |
| 几种模型都合理 | 统一契约的替换能力，或受控适配 |
| 某客户独有的规则 | 独立版本的 Fork，或明确的扩展点 |
| 模型与外部语义改变 | 新契约版本、调用方迁移与数据转换 |

客户特有的需求按下面的顺序选择承接方式，前一种不够用才进入下一种：

1. 有限业务设置；
2. 属主组件保存的扩展字段（协议 08）；
3. 客户扩展组件：订阅核心事件、拥有自己的数据，通过前端的扩展位显示；
4. 可替换位置上的族成员；
5. Fork。

越往后，每次标准升级的适配成本越高。每个 Fork 在客户版本清单中列出偏离点，并记录每次升级的适配工时，作为把某个偏离改成扩展或族成员的依据。Fork 不复用已发布版本的产物身份；保留组件 ID 的 Fork 与“新身份的实现替换”是两条不同的路径，后者允许有控制地修改装配与调用方。

## 有限业务设置

部署与运行参数由 BrickKit 配置管理，组件经运行时读取。有限业务设置归所属的业务组件：客户授权人员通过管理界面调整，组件负责范围与关联校验、版本与生效规则、审计。同一项设置不能同时交给部署配置与业务界面，争夺权威；存储模型、接口与界面随各组件设计，不为此新增通用配置组件。

组件写明允许调整的项目、管理权限与合法范围。算法与模型的变更按扩展、替换或 Fork 处理；界面不提供任意编程，也不能关闭必需的权限、职责分离或库存与会计的完整性控制。设置的生效时点、适用范围与历史解释逐业务定义；审批在途的版本规则继续适用。

**验收**：越权修改、无效组合、并发更新、生效边界、旧业务的依据、升级迁移、单跑与外壳一致。

## 配置生效与密钥轮换

不新增配置中心，也不要求小客户运行密钥服务器。

| 类别 | 权威与变更方式 | 必须检查 |
| --- | --- | --- |
| 装配与部署的值 | BrickKit 三层文件与生成结果；组件通过运行时读取 | 键、类型、范围、必需条件与成员隔离；密钥只引用；改了目标值不等于运行中已生效 |
| 有限业务设置 | 所属组件的版本化设置，客户有权限的人调整 | 合法组合、范围、并发、生效点与旧业务的解释；不在部署配置中重复维护 |
| 身份与连接等密钥 | 每个部署、每个属主的明确来源，经受控的文件或密钥载体交付，由 SDK 使用 | 实际版本、读取资格、可用期、刷新与连接重建、失效保护；不打印内容，不复制进任务载荷 |

- **生效方式**：每个可变配置声明需要重新部署、允许动态更新，还是随业务版本生效，并记录目标版本与实际应用的版本。先解析并核对完整的候选快照，再原子地应用到声明的组件与范围；无法保证同时更新的多个成员，用共同的切换控制或维护窗口。错误的候选不覆盖当前合格的配置，部分成员成功不算全部完成。
- **变更重新校验**：减少组件、降低能力档位、改法人路由、换身份、授权或消息系统的地址、缩短保留期，都要重新校验能力、在途状态与安全条件；收紧运行预算时处置超额的作业，不强行删除已持久化的业务（[选配变更](../00-overview/05-change-and-retirement.md)）。
- **密钥轮换**：常规轮换分四步：准备新值；各使用方能读取并验证新版本；切换为新值；退役旧值。数据库密码用两个交替的运行登录角色（协议 14、19）；服务凭据分别考虑现有连接与新连接，支持重叠时写明截止时间，不支持时安排受控维护，或做可以验证的身份转换。签名密钥先发布新公钥（预先发布的备用密钥）并验证各消费者，再切换签名；旧的验签材料保留到合法的旧凭证与容许的时钟误差结束（[RFC 7517](https://www.rfc-editor.org/rfc/rfc7517.html) 的密钥集合）。泄露后的撤销按安全处置规则，不等常规宽限。
- **刷新的证据**：SDK 重新读取文件，不证明远端已接受新凭据；文件的修改时间与大小相同，也不证明内容没换。刷新失败时有错误、告警与有上限的旧值使用策略；过期或已撤销的值、严格动作不得无限沿用“上一次成功的值”。缓存、长连接、后台重试、跨实例与外壳分别验证实际生效。密钥的恢复责任与备份一起记录。

## 版本与升级

- **每次改动都升版**：版本精确；改代码不升 `metadata.version` 或原地修改已发布的版本，会让构建跳过已有镜像、容器继续跑旧代码。Go 组件同一提交带两个标签（BrickKit 用的裸版本 `X.Y.Z` 与 Go 用的 `vX.Y.Z`）；主版本为 2 及以上时模块路径以 `/vX` 结尾；外壳只带裸标签。**版本号不重复使用**：Go 的公共代理在有人取一个公开模块版本时自动缓存它，校验和库永久记下它的哈希，两者都删不掉；删掉标签再用同一个号发新代码，别人取到的是旧代码或校验失败，BrickKit 的缓存也会静默给出旧内容（A110）。版本号的含义与发布顺序见[开发流程与发布](10-development-workflow.md#版本)。任何修复都发布新版本与产物，不改写已有的标签、镜像或锁所指的内容。
- **停用与退出**：有历史的业务组件停用或退出运行前，先交接未完成的业务与依赖，保留明确的历史访问、授权、数据与对象、恢复责任（[选配变更、替换与停用](../00-overview/05-change-and-retirement.md#业务组件的停用与退出)）。
- **角色升级**：升级给普通业务角色新增的权限，经客户授权管理人员确认后才加入；标准角色提供版本化的参考模板，客户实际的角色保持自己的明确授权；支持审核后的批量变更计划。系统管理角色单独处理（安全 04）。
- **流程升级**：审批流程与相关配置的变更默认影响新实例，在途实例保留绑定的版本；组件或引擎升级时保留所需的旧执行语义，或提供明确的迁移。升级验收包含停在不同节点的实例与权限撤销（协议 09）。
- **正式升级**：允许预告的维护窗口，但必须保留客户数据，并验证受影响业务的暂停、迁移与在途接续、失败恢复与恢复服务的条件；连续服务的方案另作专项验收（[部署与运行](../04-foundations/01-deployment-and-runtime.md#正式客户升级与维护窗口)）。
- **网络**：正常联网的安装与升级优先验证；完全离线交付按具体需求专项设计，在真实断网条件下验收。
- **前端**：同一入口在构建时组合选中的页面模块，生成确定的版本，一起验证与发布；改一个页面要重建所在的入口，不同入口分别发版（协议 20）。页面模块的边界、注册与装配生成另定；客户的有限业务设置与已选页面的权限菜单仍按运行时语义处理。

## 客户交付版本的维护

稳定维护线与责任分工已获用户同意（D55）：需求与维护由项目团队统一承担，AI 执行，客户决定是否升级。

采用有限的稳定交付版本线：必要的安全与重大正确性修复优先回补，新功能在后续版本推进。标准版与项目承接的客户定制、Fork 都由项目团队维护，不以客户自己写代码、合并补丁或维护旧版为交付前提。客户选择升级或暂缓；项目团队准备适配、验证、迁移与恢复材料，并配合实施；必要修复的部署变化也由客户决定。

组件可以独立发版。客户交付基线（D58）记录实际选择的组件、SDK、外壳、基础资源与适配器的精确版本与验证范围，不要求所有组件用同一个版本号；实验版本不能自动称为正式的稳定交付基线。

| 路线 | 优势 | 代价 |
| --- | --- | --- |
| 采用：稳定维护线与后续功能版本分开 | 客户在支持窗口内先取得必要修复，再安排功能升级；项目团队承接定制适配 | 修复回补、依赖与组合升级的验收增加；要明确版本与客户组合清单 |
| 未采用：只维护最新功能线 | 维护范围较小，迭代集中 | 客户取得修复通常要同时跟进功能升级，团队也要频繁迁移客户定制 |

“稳定”不表示无须打补丁或冻结安全控制。修复尽量少改变功能；不能可靠回补时，说明必要的升级与影响，并提供可行的临时保护方案，由客户决定实施安排；不承诺所有修复都可以完全不升级。稳定线以已记录的组件、依赖与客户组合为对象，包括仍保留查阅的停用组件与必要的运行环境。第三方的 SDK、身份产品、数据库或存储的支持边界变化，可能要求升级基线：团队说明继续维护的条件、替代或升级方案与限制，由客户选择。暂缓升级不等于所有旧依赖永远可以安全维护；不默认强制更新、停止客户实例或外传遥测。

客户 Fork 允许继续偏离：项目团队记录来源、差异、精确版本与受影响的修复，用 AI 完成必要的适配与验收。客户自己做的、未记录的修改先核清再纳入维护清单；标准补丁不能未经验证直接覆盖定制，也不自动证明所有组合兼容。知识库场景中“禁止 Fork、统一核心”的做法不照搬。

### 客户版本清单与升级交付

| 记录 | 最少要表达 |
| --- | --- |
| 客户当前组合 | 组件、SDK、外壳与基础资源的精确版本、来源与产物、配置与环境、当前已验证的范围 |
| 定制差异 | 偏离标准的能力与契约、代码与数据的差异、历史与在途状态、受标准修复影响的范围 |
| 支持与修复 | 受支持的基线与组合、必要的修复与适用条件、未修复的限制、维护责任、支持退出与升级路径 |
| 升级候选 | 目标的精确组合、功能与权限变化、数据、依赖与定制的适配、验证证据、维护窗口与恢复办法 |
| 客户决定与实施 | 接受、暂缓或拒绝及适用范围；实际执行的版本、结果与后续处理；不把“候选已准备好”记成“已部署” |

流程：团队先分析受影响的版本与客户差异，由 AI 形成修复或升级候选，跑对应组合的契约、业务与恢复验收，再交付客户可以审查的变更与实施材料；客户选择后，通过 BrickKit 配合执行，并核对实际版本与业务结果。暂缓的客户保留当前组合的记录、已知限制与可选的处理方案。

发行候选清单还记录源码、契约与生成工具的来源、依赖锁、可校验的产物摘要、实际的许可与支持条件，核对已知的安全与正确性问题及处置范围。精确版本号不代替产物与来源的核验；没有纳入支持、或有未解决的必需安全缺口的候选，不能只因构建成功就作为合格交付。

**验收**：受支持基线上的修复效果、安全拒绝与业务回归、依赖与外壳版本的传播、旧数据与在途状态、页面与客户扩展的兼容、迁移与失败恢复、受影响版本与修复适用范围的清单。修复只在最新主干通过，不证明适用于旧的稳定线。

**依据**：[PostgreSQL 版本政策](https://www.postgresql.org/support/versioning/)把新功能大版本与受支持版本的修复发布分开；[SemVer](https://semver.org/) 说明版本号怎样表达兼容性、已发布内容不能原地修改。它们不替本项目决定支持周期；PostgreSQL 的具体版本编号方式也不等同于本项目的组件版本。

## AI 用于开发

AI 用于开发与维护，不等于 ERP 产品中的业务 AI 能力（`ana/ai` 只留位）；也不代替测试与实际环境的证据。客户数据用于开发时仍遵守其访问与处理边界，不能因为使用 AI 或允许公网访问，就默认传送客户资料。

## 已知风险与待定

- 正式交付前确定：支持期、基线数量、选定与退出条件、修复分类与处置时效、客户通知方式与升级路径；不照搬季度 LTS、固定月数或供应商的周期，现在也不建立多个发布分支。
- 客户版本清单的格式、交付渠道与命令另定；现在不创建客户数据仓库或发送通知。
- 发行候选的扫描、签名与验证工具按交付环境设计，不为此默认增加常驻服务。
- 配置与密钥的协议键、刷新能力与命令，绑定目标版 SDK 与部署方案后确定（协议 19）。
