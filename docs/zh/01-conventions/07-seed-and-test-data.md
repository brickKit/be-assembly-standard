# 种子与测试数据

本页说明开发与测试用的数据从哪里来：给人用的种子数据，给自动化测试用的测试数据。两条路径互不共享，背后是同一条原则：尽量覆盖更多场景，依赖方缺东西时去源头补。正式部署的初始数据（基准数据、初始管理员）不属于本页，见[安全 02 的可信身份](../06-protocols/security/02-trusted-identity-and-attributes.md)与[协议 16](../06-protocols/16-go-live-and-import.md)；测试怎样分层见[测试与验证](02-testing-and-validation.md#实现测试的分层与节奏)；现在灌了哪些种子数据见[种子数据清单](../03-seed-data.md)。

## 两条路径

| 路径 | 谁用 | 怎样产生 | 生命周期 | 能否共享 |
| --- | --- | --- | --- | --- |
| 测试数据 | 全部自动化测试（L1–L4、FE-1–FE-4） | 每次运行现建，用时间戳或随机后缀保证唯一 | 从不清理；可以堆积，下次运行换新后缀 | 绝不：任何测试都不依赖别的测试或上一次运行留下的行 |
| 跨组件测试数据 | L3 跨组件测试 | 测试调用依赖方真实的接口，在依赖方那里建出需要的形态 | 同测试数据 | 同测试数据 |
| 种子数据 | 人：探索、演示、让新组件一建好就有数据可看 | 固定幂等键，先认领；重跑不会再建 | 持久；用组件的清除或重置命令清掉 | 组件之间可以互相查找、复用种子数据；测试绝不依赖它 |

清掉种子数据永远不会让测试变红，测试也永远不会改动人正在看的数据。混在一起，“这个测试为什么突然红了”就有两个毫不相干的原因，要走两条毫不相干的排查路线。

**两个物理上分开的库**，在开发环境的同一个 PostgreSQL 实例里：测试用 `brickkit_test_db`，运行中的项目用 `brickkit_db`。两边结构相同，数据互不相通。有的测试会写迁移种下的基准行（计量单位、科目模板）；共用一个库的话，每跑一次测试，演示数据就真的变一次。

**不用一次性数据库**：分区表、事务内的角色与 `search_path` 切换塞不进内嵌引擎，换一种数据库实现又与“集成就是真实基础设施”（L2 起连真实的 PostgreSQL 与消息系统）直接冲突。解决“重建数据慢、互相污染”的办法是让数据本身可以随用随弃：唯一后缀、从不清理。这是长期形态，不是权宜之计。

## 尽量覆盖更多场景

- **种子数据追求多而全**：每个状态机的每个状态、每个分支、每条失败路径、每个授权维度，都有能真正触发它的数据。数量与多样性本身就是目的。
- **测试数据追求少而准**：刚好够验证一个断言的最少数据。例外是性质测试，它的大量随机输入是为了撞到边界。
- 两者的底线相同：**任何组件都不能只有“一切正常”的数据或断言。**

## 依赖方缺数据或能力时

**在测试里**，测试需要依赖方有某种形态的数据（信用额度为零的客户、停用的产品、处在某个阶段的商机）：

1. 在测试里通过依赖方的真实接口现建。
2. 依赖方的契约根本造不出这种形态时，**先给依赖方补上这个能力**（与任何契约变更一样按协议 19 的兼容规则），再通过它造数据。不绕过，不跳过这个场景。
3. 测试里不用 SQL 直接写别的组件的库：那会在契约之外悄悄建立耦合，契约以后怎么变，这个测试都不会报警。

**在种子数据里**，下游需要的组合上游的种子还没有（某个组织下一个已停用的客户），下游直接去上游组件的种子脚本里加上，不在下游将就，也不干等。数据是假的，多几种变化不花成本；上游数据丰富，下游才有东西可挑。

## 种子数据

种子数据也在服务验证：人打开运行中的系统、用像样的数据走一遍，是检查一整条链路的方式，与自动化测试同样重要。数据从头到尾都是假的，这本身是一种自由：丰富度往上限推。

**要同时服务的目标**：每个分支与失败路径都能被触发；一个组件加它的依赖能单独检查；一个组件交付前它的整条链路能跑通；整个项目交付前从各个角度都能验证（权限边界、事件、补偿）；人随便打开一个页面都有东西可看。

**“数据多”不会自动带来的东西**：

- **授权维度要真实存在**：多个法人、多个组织单元、多个任职、多个仓库，每个里面都有测试账号，并有跨任职、无任职的账号。数据全挂在一个全能账号下，授权与数据范围就完全体验不到。
- **数量要够翻页**：游标分页的列表只有五行，永远看不到第二页。
- **时间要分散**：数据分布在过去的不同日期（用相对当前时间的绝对值设定，重跑不会越跑越早），“最近 N 天”的查询、趋势图、转层与期间才有东西可验证。
- **要有负面数据**：停用的记录、零库存、逾期未结、被驳回的申请。
- **要能被发现**：[种子数据清单](../03-seed-data.md)列出每个组件灌了什么、多少、归谁、各测试账号能看到什么。改种子数据时在同一次提交里更新它。

**归属与协作**：

- **每个组件拥有自己的种子数据**，在自己的仓库里提供种子命令。集中脚本只有全部组件一起运行时才可用，单独起一个组件就什么都没有；根项目的命令只按依赖顺序调用各组件。
- **组件的种子命令先跑它声明的每个依赖的种子**（必需与可选一视同仁），再跑自己那部分；对一个组件运行，就得到一整套完整数据。连不上的依赖跳过，不算失败。
- **先探测再灌**：种子脚本先检查需要的服务与健康检查，不满足就报错退出，不灌一半。
- **交接用组件自己的幂等记录**：种子脚本只负责把数据灌进去，不负责打印身份。谁需要某条数据的身份，谁按固定的幂等键去查。
- **链接另一个组件灌下的行时，幂等键里带上被链接行的真实身份**：那些身份每次清掉重灌都会变；用位置编号做的键会永远绑定第一轮的身份，链接静默地指向已经不存在的行。
- **种子数据是一份轻量契约**：被别的组件查找引用的标识只能新增，不能删除，也不能改变含义。
- **冗余可以接受**：两个组件各灌一个“制造业客户”没问题；复用已有的比协调归属便宜。
- **经真实接口建数据**：种子脚本调用组件的真实接口，不直接写库；数据因此顺带把真实的鉴权与业务校验走了一遍。
- **负面路径来自真实的业务失败**：组件刻意不对外开放某种写入（异常待办、通知记录）时，靠让一条真实业务流程失败来产生数据（超出信用额度的订单），绝不伪造契约禁止的那次写入。
- 种子数据里每个人类可读的名字都以 `「本地测试」` 开头，任何界面上都能一眼认出；清除命令靠这个前缀加固定的幂等键找到自己的行。

**清除与重置**：

| 组件的情形 | 提供什么 |
| --- | --- |
| 行可以安全删除 | 清除（只删自己灌的行）与重置都可以有；优先用清除，它不碰别的数据 |
| 有只追加的表（账本、流水、已锁定的期间） | 只有重置（迁移回退再前进，清空该组件的全部数据）；逐行删除复原不了，计数也不会回退。重置只用于开发与测试库，正式部署只向前（协议 14） |
| 管理员会修改的配置类数据（打印模板等） | 没有清除；重灌时已存在的一律跳过，管理员改过的绝不被覆盖 |
| 没有对外的写入口（统一待办、通知记录） | 没有种子命令；数据来自真实业务失败 |
| 连接真实外部渠道（IM、银行、电子开票） | 不灌种子：假凭据什么都测不出，真凭据每跑一次都会打扰真实的人 |

## 凭据与部署

**凭据绝不进入每次部署都会运行的东西**：

- 每个部署都需要、又不依赖客户信息的基准数据（科目模板、计量单位、标准代码）属于迁移：它是产品的一部分。法人、组织与依赖法人的数据（仓库、期间、科目表的启用）不进迁移：它们在安装或上线时经组织组件与各属主建立（协议 16、A06），测试需要的由测试数据现建。
- 测试账号、测试角色、测试客户端只在手工运行的种子命令里，从不出现在迁移、装配产物、任何部署或 CI 流程中。迁移里的测试账号，就是在每个客户的系统里埋一个密码公开的后门。
- 真实部署的第一个管理员来自安装认领（[安全 02](../06-protocols/security/02-trusted-identity-and-attributes.md)、[安全 08 的安装认领](../06-protocols/security/08-state-and-change-protocol.md#安装认领管理员恢复与紧急访问)），与本地开发用的“拥有全部权限的测试角色”是两回事。

**种子与测试怎样取得真实的用户令牌**：浏览器入口只走授权码加 PKCE（[协议 20](../06-protocols/20-frontend.md)）。种子脚本与需要用户身份的自动化测试，经身份成员中一个只在开发与测试环境存在的客户端，用测试账号换取真实令牌（例如开启密码授权的本地客户端）。换取路径是：身份产品中的测试客户端 → 身份适配组件的开发换取入口 → 平台令牌。这个客户端由种子命令在开发环境建立，适配组件的开发换取入口由只在开发与测试环境存在的配置打开；两者都绝不出现在迁移、装配产物或正式部署中。正式部署的上线检查同时确认身份产品中没有开启密码授权的客户端、身份适配组件没有开启开发换取入口。种子脚本建的是它自己的客户端，从不改动正式的登录客户端。

## 测试数据

- 生成方式与生命周期：唯一后缀，从不清理（[两条路径](#两条路径)）。
- 自己触发消费者的消费者测试，用测试私有的主题（例如 `test.<主题>.<纳秒时间戳>`）：订阅了正式主题的运行中容器会收到同一条消息，断言可能读到的是它的结果。验证代码“发到哪个主题”的测试用真实主题。
- 消费者测试用唯一的事实身份与聚合身份：收件表按事实身份去重是持久的，用固定的身份，第二次运行会被当成已处理吞掉（[协议 02](../06-protocols/02-projections.md)）。
- 依赖方契约造不出的数据形态：见[依赖方缺数据或能力时](#依赖方缺数据或能力时)。
- 测试数据不考虑种子数据特有的维度（翻页、时间分散、可被发现）；它只对准自己的断言。
- L2 以上与消费者测试只连测试库，绝不连演示库。
