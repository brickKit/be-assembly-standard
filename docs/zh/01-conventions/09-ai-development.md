# AI 开发约定

写代码的 AI 与人类工程师的失败方式不同，付出的成本也不同。它每次会话都从零开始，没有上一次的记忆，上下文窗口有限；它没法"回头再看那个文件，我大概记得是怎么回事"；对它来说，整份重写一个文件可能比在前三个补丁上小心加第四个更便宜。下面的规则都由此而来。

## 何时用设计模式

模式从来不是强制的；合适的地方就该用。判据只有一条：

> **一个全新会话里的 AI，只读少数几个文件，能不能把一条新规则写对？**

要照顾的读者是 AI：它从零开始、上下文有限、看不到运行时状态，也不会"过一阵子就想起那个文件在哪了"。

| 有帮助 | 为什么 |
|---|---|
| **文件小、职责单一** | 每碰一个文件都要整份读进上下文：在 600 行的文件里改三行，要花 600 行的上下文 |
| **注册表集中在一处** | 一个文件列出全部规则，全集一眼可见；分散在各处只能靠搜索去猜，漏一个就是漏改一处 |
| **显式优于隐式** | 反射注册、自动发现的装饰器、按命名约定扫描，静态阅读看不见 |
| **一种情况一个文件，文件名就是情况** | 看到 `rule_volume_discount.go` 不用打开就知道该改哪个文件 |
| **状态转移集中在一张表里** | AI 最常见的错误是某个入口忘了检查前置条件；声明在一张表里，结构上就不可能漏 |

| 有害 | 为什么 |
|---|---|
| **深继承链、多层抽象基类** | 看懂一个方法要跳四个文件；跳到第三个 AI 就开始猜 |
| **元编程、反射、动态分派** | 静态推断不出实际走哪条路径 |
| **"万一以后要扩展"的提前抽象** | 多一层就多一个要跳的文件，今天毫无收益 |
| **一个模式散布在多个包里** | AI 改了 A 包，漏了 B 包里对应的改动 |

模式的价值在于把一段长逻辑变成几个结构清晰的短文件，而不是把逻辑撒满整个代码库。一个模式只待在一个包里。

**值得停下来考虑的信号**：

| 信号 | 症状 | 用什么 |
|---|---|---|
| `switch` / `if-elif` 超过 5 个分支还在加 | 每加一种情况都要改一个长函数，可能碰坏别的分支 | 策略模式：一种情况一个文件，登记进一张表 |
| 函数超过 150 行、文件超过 600 行 | 每次改动都要读完整个文件 | 先按职责拆，再看拆出来的部分像哪种模式 |
| 同一个流程跑好几遍，只有中间一两步不同 | 复制了三份，修 bug 只修了一份 | 模板方法或责任链 |
| 一个状态转移的合法性在不止一处检查 | 某个入口漏了检查，数据进入不该有的状态，什么都不报错 | 显式状态机，每条边只在一处声明 |

**不该用的时候**：

| 情况 | 为什么不用 |
|---|---|
| 简单资源的普通 CRUD | 直接写就是最清楚的 |
| 只有两个分支，看不到第三个 | `if a {} else {}` 比一个接口、两个实现、一张注册表好懂得多 |
| "万一以后需要" | 等第二个真实实现出现再抽象，那时才知道该沿哪条缝切 |

最后一条最容易违反，因为"留出扩展空间"听起来总是对的。检验方法：**你现在能说出第二个实现具体是什么吗？** 说不出就先别抽象。

**用了模式之后的文件组织**：

```
backend/internal/pricing/
├── pricing.go             接口 + 注册表 + 执行顺序：读这一个文件就知道有哪些规则
├── rule_base_price.go     一条规则一个文件
├── rule_customer_tier.go
├── rule_volume_discount.go
└── pricing_test.go        每条规则一个测试，外加一个对整条链的性质测试
```

拆对了的标志：一个新会话要加一条折扣规则，只读 `pricing.go` 和任意一个 `rule_*.go`，新建一个文件、在注册表里加一行：读两个文件，改零个文件。拆错了的标志：还得去改别的规则文件（链的顺序或数据流不干净），或者要跳三层才找到接口（层太多）。

## 本项目已定的模式

这些不需要再判断，直接用；它们的分支数和扩展速度都可以预见。

| 组件 | 位置 | 模式 | 为什么 |
|---|---|---|---|
| erp/sales、erp/purchase | 定价与折扣 | 策略 + 责任链 | 定价规则是最客户化、改得最频繁的部分；Fork 加一条规则就是加一个文件 |
| erp/sales | 订单状态机 | 显式状态表 | 转移的合法性集中在一处 |
| erp/inventory | 出入库单据类型 | 策略 | 收货、发货、调拨、盘点、退货各有各的校验，都落进同一张流水表 |
| erp/finance | 业务单据 → 会计凭证 | 策略，每种单据一个翻译器 | 新增一种单据就是新增一个翻译器，不碰已有的 |
| infra/notification | 渠道路由 | 策略 + 注册表 | 渠道并存，按装了哪些渠道组件注册 |
| infra/print | 渲染后端（PDF、ZPL） | 策略 | 两种输出除了输入参数毫无共同点 |
| hrm/payroll-es | 薪资项计算 | 策略 + 拓扑排序 | 薪资项互相依赖；顺序错了数字就错 |
| 每个组件 | Saga 补偿步骤 | 命令模式 | 每一步都可逆、可持久化，重启后能续上 |
| be-ops | 各项产出 | 每项产出一个包，统一接口 | — |

## 长业务函数的注释

AI 生成的复杂业务函数超过 50 行时，带一段用自然语言写的决策树注释；分支不直观的地方再配一张 Mermaid 流程图。没有的话审查时打回。

## 一次会话做多少

| 单位 | 大小 | 规则 |
|---|---|---|
| **一次会话** | 一个任务，或一个任务里的 2–4 轮红绿 | 上下文用掉一半就收尾、提交、开新会话；留出的余量才能让下一次会话读周边代码 |
| **一轮红绿** | 一个测试加让它变绿的最少代码 | 三轮还不绿：这一步太大，切小（[testing.zh.md](testing.zh.md#卡住时)） |
| **一次提交** | 一轮 | 出问题时能精确回到上一个全绿状态 |

新会话开始时读这些，不多读：

1. 项目的 `AGENTS.md`（自动加载）；
2. 组件的 `AGENTS.md`：它的边界和它自己的易错点；
3. 组件的 `docs/design.md`：为什么这样设计；
4. 所依据计划里的当前任务，只读这一个；
5. 将要改的源文件。

不通读每一份约定文件，不读无关的组件。需要某条规则时，`AGENTS.md` 的"查找路由"表会指到确切的文件和小节。

## 人要审什么

没有人能逐行读完一个大型 AI 生成代码库。审查的时间花在不可逆、门禁看不见的地方：

| # | 审什么 | 为什么是它 | 在哪 |
|---|---|---|---|
| 1 | **契约** | 最不可逆：一旦有人消费，就只能向后兼容地增加 | `contracts/` |
| 2 | **迁移** | 第二不可逆：主键、分区键、索引在建表时定死，有数据后再改就是一次迁移 | `migrations/` |
| 3 | **L2 测试里的不变式清单** | 只看该有的不变式是否都列了；门禁只跑已经写下的测试 | `*_test.go`、`tests/` |
| 4 | **`docs/design.md` 的边界与依赖** | 边界画错或多一条同步边，会污染整张架构图；同步调用图保持无环 | `docs/design.md` |
| 5 | **门禁输出** | 不用读代码；失败的门禁会点名位置 | `make gates`、组件自己的门禁 |

不审：逐行业务代码、单元测试、构建脚本、Dockerfile。门禁和测试覆盖它们；那里真有问题，总会有东西变红。

## 整体重写而不是打补丁

一段逻辑跑偏了（早期判断没站住，几轮补丁朝不同方向打），诚实的修法可能是重写而不是再打一个补丁。对 AI 来说，重写往往比在脑子里叠三层历史再加第四层更便宜。

**该重写的时候**：

- 同一段逻辑已经朝不同方向补了好几次，改一行都要先在脑子里重放那些历史；
- 问题不是 bug，而是一个设计判断本身错了；在它上面继续盖只会让偏差越积越多；
- 它是种子或演示数据：假数据，没有历史要迁移，重写的成本约等于删掉重建。

**怎么做**：

1. 把要重写的文件复制到仓库之外的草稿位置，只作对照参考（Git 已经保存了每个版本）。
2. 重写作为**单独一个提交**落地，提交信息写为什么重写。
3. 照常跑全部门禁；不因为是重写就降低标准。重写碰到的范围更大，这是要多验证而不是少验证的理由。
4. 删掉草稿副本。
5. 如果重写是因为发现早先方向错了，把它写到下一个读者会看的地方："看起来对、其实错"的教训写进组件 `AGENTS.md` 的易错点，改变了的设计判断写进它的 `docs/design.md`。
