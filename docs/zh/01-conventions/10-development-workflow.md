# 开发流程与发布

本页说明一次改动怎样从想法走到发布的版本：七步循环、动手前的自问、提交、真机运行、版本与发布。代码由 AI 写、人来审，所以每一步都切到一次会话放得下的大小，人只审不可逆的东西（[AI 编码习惯的人要审什么](09-ai-coding.md#人要审什么)；一次会话读多少见 [AI 导航](05-ai-navigation.md#每次会话读多少)）。版本、产物与客户基线的完整规则见[协议 19](../06-protocols/19-config-secrets-registries-release.md)；平台命令的用法以 BrickKit 的技能与 `brickkit <命令> --help` 为准。

## 七步循环

每个组件、组件里的每个功能，都走同样的七步：

```
① 设计业务逻辑    docs/design.md：边界、数据、契约、事件、依赖；按边界卡展开
② 查参考实现      先自己设计，卡住的地方才看参考
③ 写契约          contracts/：接口、事件、错误
④ 写业务规则测试  L2：不变量、状态迁移、幂等、权限与数据边界，写在实现之前
⑤ 实现            一轮红绿一条规则，一轮一次提交
⑥ 补单元测试      L1：错误路径、空值、校验
⑦ 集成            L3 跨组件业务链、全部门禁、文档
```

**③ 在 ④ 之前、④ 在 ⑤ 之前，顺序不能反。** 测试要用契约生成的类型；没有契约就只能测无类型的数据，第一次重构就作废。实现之后才写的测试只能描述已有的代码：防得住回归，防不住“从一开始就理解错了需求”。

第 ① 步见[文档规则的组件文档](03-documentation.md#组件的文档)与边界卡，第 ② 步见[参考实现](08-reference-implementations.md)，第 ④–⑦ 步见[测试与验证](02-testing-and-validation.md#实现测试的分层与节奏)。

**文档先于代码**：边界、契约、事件变了，先写进组件的 `docs/design.md`；配置或依赖变了，写进 `BRICKKIT.md`；新的禁令写进 `AGENTS.md`。文档与代码在同一次提交里改。

## 动手之前

每次写代码之前回答这几问：

1. **我是不是在为了让测试通过而改测试？** 默认改的是实现。测试真错了，先停下来说清错在哪里（[一轮红绿与铁律](02-testing-and-validation.md#一轮红绿与铁律)）。
2. **端口、schema、角色、权限与资源定义是从注册表抄的吗？** 自己编的一律是错的（[协议 19 的注册表](../06-protocols/19-config-secrets-registries-release.md#注册表)）。
3. **我是不是让两个组件互相认识对方的代码？** 调用只经契约；能跨边界的代码只有 SDK、被调方发布的契约包与族契约包（[组件实现约定](06-component-implementation.md#调用其他组件)）。
4. **同一个进程里再放二十个模块，这段代码还成立吗？** 不读进程环境、不做进程级初始化、不退出进程（[合并安全](06-component-implementation.md#合并安全)）。
5. **我是先自己设计、再去看参考的吗？**（[三步法](08-reference-implementations.md#三步法)）
6. **我是不是用一个 `if` 把几类客户的变体塞进了一个组件？** 先看能否设计明确的替换点（[几种做法都合理时](08-reference-implementations.md#几种做法都合理时)）。
7. **这个文件是不是已经太长？** 函数过 150 行、文件过 600 行、分支过 5 个还在加（[何时用设计模式](09-ai-coding.md#何时用设计模式)）。
8. **这次改动牵涉哪几份文档？** 先改它们。

## 提交

- 一轮红绿一次提交。提交信息写这一轮锁定了哪条业务结论，不写改了哪些文件。
- 改测试的提交单独一次，并写清原断言错在哪里。
- 提交信息用英文（D74），先写进文件，再 `git commit -F <文件>`。打标签之前先看 `git log --oneline -1`：命令行里引号没配对的提交信息可能静默失败，标签就会打在上一个提交上。
- 标签一律用带注释的标签（`git tag -a`）；`git push --follow-tags` 会不声不响地跳过轻量标签。

## 真机运行

- **改动项目共享状态的命令一次只跑一个**：组件的增删与升级、构建、启动与停止、本地模式、`config/`、部署文件、注册表与密钥文件。并行的工作等待项目锁，而不是互相踩；项目的命令都经项目锁运行。
- **先构建**：启动从不构建镜像；镜像标签就是组件版本，版本没升就会复用旧镜像。
- **一次只跑一个组件**：只拉起这个组件与它需要的一切（BrickKit 的聚焦运行）。本地模式打开时，本地部署文件整体替换项目的部署文件，之后改项目的部署文件不起作用：先关闭本地模式，或改完后刷新本地副本。
- **然后对着它测**：跨组件的测试打到真实的依赖容器上（[测试与验证](02-testing-and-validation.md#实现测试的分层与节奏)）。
- **容器默认关着**：基础资源（PostgreSQL、消息系统、身份产品、对象存储）可以常开；组件容器只在真机验证与演示时需要，用完停掉（不删数据卷）。一直开着的容器在下次改动后跑的是旧版本，还会与本地测试抢同一个主题的消息。
- **拆回验证**：外壳合并之后，每个组件仍然必须能独立运行。外壳的成员清单一变，就把每个成员当独立容器真的跑一遍（[协议 17](../06-protocols/17-runtime-and-resources.md)）。
- **在编辑器里调试**用本地部署文件的调试模式，绝不写进项目的部署文件。
- **平台行为不对时**，写出复现、报给 BrickKit；绝不在组件里绕过去。

## 版本

- **每次改动都升版本**，只改测试或文档也一样。组件清单中的版本、Git 标签、镜像内容三者始终一致：清单会被拷进镜像，构建会跳过已有镜像的版本。
- **先升版本，再动手**：一开始就把版本升上去，发布之前随便改；已经发布的版本绝不原地修改。
- 版本精确；Go 组件按[工程规范的版本与升级](01-engineering.md#版本与升级)带两个标签，Go 构建按同一节设置私有模块。
- **重建的版本从头算**（A107）：组件、外壳与工具在开发期（代表部署实验与重建）用 `0.x`，第一个正式版本是 `1.0.0`；原有决定 0302 的“契约只做加法”从 `1.0.0` 起约束。重建复用原仓库：旧代码在 `legacy/v<旧主版本>` 分支，旧标签全部删除，本机的旧镜像、Go 模块缓存与 BrickKit 的两层缓存（用户级的仓库缓存 `~/.cache/brickkit/repos/`、项目的 `.brickkit/manifests/` 与 `.brickkit/artifacts/`）清空，所以旧版本号可以重新使用；BrickKit 按“版本不可变”缓存，不清空时会把同号的旧内容静默当成新版本。`be-acceptance` 已发布的 `v1.0.0`（参考模型与文档检查）保留，之后照常递增。将来有外部使用者时，他们也要设 `GOPRIVATE`，否则在用过的旧版本号上取到旧代码；到时如不希望这样，正式版本改从没用过的号起，届时再定。
- **用工具传播，不手工找**：把这次真正改了的组件全部写进一份计划，先预览连锁影响（下游的依赖钉、外壳的成员清单与依赖锁），确认后再写；项目这边用 BrickKit 的升级命令让组件清单、部署文件与配置保持一致，最后用不启动任何东西的预检发现版本漂移。一批改动一份计划：每个组件单独跑一次，同一个下游会被升两次。

## 发布

按版本传播工具给出的顺序，逐个组件：

1. 它自己的测试与门禁全绿。
2. 在组件仓库提交并推送（外壳与工具在各自的仓库）。
3. 用 BrickKit 的发布命令发布。说明文件放在组件目录之外（目录里未跟踪的文件过不了干净检查）。发布说明先写使用方必须做什么（某个键的含义变了、某个接口退役了），再写新增了什么。
4. Go 组件补上 `v` 标签并推送；外壳与工具不做这一步。
5. 本地构建镜像。

第 2–4 步由一条发布命令完成：它拒绝不干净的工作区与主分支以外的分支；第一处失败就停，绝不强推，也绝不删除或移动已经推送的东西；修好原因后重跑，已完成的步骤会直接通过。

6. 回到根项目：提交子模块指针与升级命令改出的内容，真机跑一遍，停掉容器。

- **外壳排在它的成员之后**：成员发布时，传播工具已经改好外壳的成员清单与依赖锁，外壳随后在它自己的仓库里走同样的步骤；绝不在根项目里发布外壳或给外壳打标签。
- **子模块地图**：`.gitmodules` 与子模块指针说明每个组件、外壳与工具从哪个仓库、哪个提交构建；它们只经 `git submodule` 命令改变，指针与需要它的升级一起提交。
- 只为测试做的版本只打本地标签，从不推送，测完删掉。
- 只有已经有内容要推送时才新建远端仓库；新建或删除任何仓库之前先告诉维护者。
- 组件源码有未提交或未推送的改动时，BrickKit 的移除命令在写任何东西之前就停下；绝不用强制选项越过，它会连同这些改动删掉源码。登记为子模块的组件先提交并推送，再注销子模块，然后重新移除。
- Fork 出来的组件保留原来的组件 ID（所有依赖方的地址变量名由它推导），版本照常推进；依赖方用升级命令移动版本钉。
- 正式交付的镜像以摘要引用，产物签名与来源证明随发布生成（协议 19 的供应链）；开发阶段可以只在本地构建、不推送镜像。
