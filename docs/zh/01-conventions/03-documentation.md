# 文档规则

本页说明项目文档放在哪里、写给谁、怎样写、用什么语言、怎样与代码一起维护。图与表的写法见[图与表的规范](04-diagrams-and-tables.md)；AI 怎样从入口找到需要的信息与代码，见[AI 导航与信息定位](05-ai-navigation.md)。

## 写给谁

主要读者是在这里做开发的 AI，能力强弱都有：**按较弱的模型能读懂来写**。次要读者是维护者本人，以及从客户角度了解项目的人。

AI 读文档的方式决定了写法：每次会话从零开始，上下文有限，可能只读到某一段，不会“大概记得那份文件在哪”。所以每份文档要能单独读懂、能被精确链接到某一节，规则要附带“违反了会看到什么”。

## 三个区域

| 区域 | 在哪里 | 放什么 | 规则 |
| --- | --- | --- | --- |
| 正式 | 根 `AGENTS.md`、`README.md`、`docs/`、每个组件与外壳的文档 | 现在成立的结论 | 不链接开发区与归档区 |
| 开发 | `dev/` | 计划、测试记录、AI 路由测试、进行中的工作、台账 | 可以链接任何地方；所服务的工作结束后归档 |
| 归档 | `archive/` | 已结束工作的冻结文档 | 不再修改，正式文档不链接 |

正式文档只写现在成立的内容。怎样走到这一步（发生了什么、先后顺序、哪个故障引出哪条规则）是历史，在 Git、版本的发布说明与开发区里。从事故得来的规则保留症状与理由，去掉故事。

## 文档的三层

| 层 | 在哪里 | 放什么 |
| --- | --- | --- |
| 系统层 | 本项目（装配项目）的 `docs/` 与根 `AGENTS.md` | 产品与全景、组件货架与客户组合、跨组件的协议与流程、决定、底层选择、规范、运维手册、全局术语表、系统级的图（C4 的系统上下文与容器、组件依赖、事件拓扑） |
| 组件层 | 每个组件的仓库 | 组件文档（下一节）、本组件的术语、状态迁移表、决策表、权限点、组件内流程、ER 图 |
| 代码层 | 代码、契约、迁移、测试 | 真实存在的实现；事实类的图与索引从这里生成 |

**知识跟着决策放**：跨组件的放系统层，组件内的放组件仓库。组件只写自己边界内的事与它**依赖的上游**，不写谁在调用它、谁订阅它的事件——那是系统层的事实，由系统层生成（事件拓扑、依赖图）。这样一个组件单独发布时，它的文档不必因为多了一个使用者而改。边界卡里写“下游缺席时本组件一侧的表现”是例外：它描述的仍是本组件自己的行为。

同一份知识只在一层维护，别处链接。

**项目级全景**：系统层有一份覆盖全部组件的全景（货架、选择关系、边界卡），因为客户与维护者需要从一处看到全部能力与组合。全景有过时的风险，过时的全景读起来像权威，所以用三条控制：全景只写能力、取舍与组件关系，具体的版本、配置键、接口回到组件文档与契约核对，不另抄一份；能生成的清单（组件清单、依赖、事件、权限键）从代码生成；组合与闭包由检查 34 核对。

## 正式文档的结构

| 目录 | 内容 |
| --- | --- |
| `00-overview/` | 产品与原则、领域与边界、组件货架、选择关系与客户组合、变更与停用、选型说明、路线 |
| `01-conventions/` | 工程规范、测试与验证（含验收矩阵）、文档规则、图与表的规范、AI 导航与信息定位 |
| `02-decisions/` | 决定记录：为什么这样做、不要再提什么；决定优先于规范 |
| `03-seed-data.md` | 演示数据与测试账号 |
| `04-foundations/` | 底层选择：跨方面的取舍（部署与运行、数据与生命周期、事务与消息），以及每个可替换的底层方面一篇（前端技术栈、数据库引擎、消息运输、组件协议与语言、调用与错误、边缘、观测）：选了什么、方案比较、什么时候换、怎样换、替换时的检查、已知限制；规则只在协议中 |
| `05-operations/` | 运维手册：备份与恢复、升级与维护窗口、观测与告警、客户上线、高可用（底层预留） |
| `06-protocols/` | 完整设计：安全与各协议（规则、理由、独立预期、参考模型） |
| `07-components/` | 组件边界卡；重建组件时写进各组件仓库 |

`docs/README.md` 是这棵树的索引：每个目录放什么、按什么顺序读。

**决定记录**只收会约束以后改动的决定：忘了它，就会有人推翻它或重新争论。每条写决定本身与两三句理由；较小的决定留在它所影响的文档里。

## 组件的文档

每个组件与外壳都有：

| 文件 | 读者 | 内容 |
| --- | --- | --- |
| `BRICKKIT.md` | 使用这个组件的项目与它们的 AI | 用途（拥有什么、不拥有什么、那归谁）；部署之前（要建的数据库与角色、密钥）；依赖；配置（每个必需的键）；契约；外壳声明。**不写相对链接**：它会在别的项目的缓存里被单独读取 |
| `AGENTS.md` | 修改这个组件的 AI | 代码地图（[AI 导航](05-ai-navigation.md#组件仓库的标准布局与代码地图)）；构建与测试；设计决定；易错点（不要做什么、症状、原因）；改代码之前；最后是 BrickKit 维护的一块 |
| `CLAUDE.md` | Claude Code | 只有一行 `@AGENTS.md` |
| `README.md` | 代码托管平台上的人 | 怎样在项目中使用、哪份文档回答哪个问题、开发 |
| `docs/design.md` | 修改设计的人 | 只写结论：边界（以及明确不属于本组件的）；拥有的数据（表、分区、终态）；契约面（方法、路径与权限键、幂等端点、状态端点）；发布与消费的事件；依赖，以及为什么不依赖某个看似应依赖的组件；在同步调用图中的位置；分区与归档；数据范围或为什么没有；参考过的实现；未决问题 |
| 组件层的图与表 | 修改组件的 AI 与人 | 见[图与表的规范](04-diagrams-and-tables.md#每层放什么) |

- `docs/design.md` 在开工前就存在，并随设计变化：实现中发现设计错了，先改文档。
- **一个事实只有一个家**：依赖与配置键在 `component.yaml`，接口在契约，历史在 Git；文档解释它们说不出的东西。
- **两种读者**：正在修改这个组件的人（需要准确、当前的细节），和第一次通过这个组件了解项目的人（需要足够的背景，看出它为什么存在、怎样嵌入）。完成一份组件文档前，两种都检查一遍。
- `brickkit lint --strict <ID>` 检查一个组件或外壳的文档结构，必须零警告。
- 需要时，组件内的子目录可以有自己的 `AGENTS.md`（[局部的 AI 说明](05-ai-navigation.md#局部的-ai-说明)）。

## 写法

- **只写最终做法**：正式文档不写“候选”“按第几轮复查补充”“现行实现是……”，也不写修改经过；状态在开发区维护，修改经过在 Git 与开发区。
- **实现状态只写在两处**：一个组件有没有实现、是哪个版本，只在[组件索引](../00-overview/09-component-index.md)（生成）；这个版本做什么、不做什么（答“能力不支持”的），只在组件自己的 `BRICKKIT.md` 与 `docs/design.md` 的实现状态。其余正式文档（协议、流程、规范、术语表、边界卡、已定的模式）只写终局，不写“已实现”“还只有设计”；读者要知道现状时，链到组件索引。写在别处的现状不会随发布更新，过时了读起来仍像权威。
- **每份的骨架**：一句话说明这份回答什么问题、写给谁；解决什么问题；做法（规则与步骤）；为什么这样做（简短，指向决定记录）；独立预期；参考模型（一段，写实际覆盖与不覆盖）；已知风险与待定。不是每份都需要全部几节，但“已知风险与待定”统一放在末尾，写明由什么实验或设计来定，属于首批还是后期。
- **能单独读懂**：不写“见上文”“如前所述”（AI 可能只读到这一段）；需要一起读的文档互相指向，不靠 AI 推断第二份存在。
- **禁止必附症状与原因**：每条“不要”写明违反后会看到什么、为什么。症状是 AI 发现自己做错的唯一线索。
- **现状与历史分开**：描述“现在”的一节不累积“怎样变成这样”。
- **不在一格、一段里累积**：每做一个任务、每加一个组件就多一条的内容，给它单独可寻址的位置：一个文件、一行一项的表、编号列表。
- **可寻址**：长期存在的文档用稳定的标题或表格行，能被链接到。
- **一件事只写在一处**：同一个机制在多份文档中出现时，写在主文档，其他地方一句话引用（例如来源水位只在协议 02）。规则之间冲突时，立刻改正并记录裁定，不靠追加例外。
- **有意的、有限的重复**：少数“静默违反、发现代价高”的规则，有意在每次都加载的根 `AGENTS.md` 中重复（易错点表）；其他内容不重复。
- **路由按请求者的原话**：路由表按提问的人会用的词组织（“谁能调这个接口”“怎样测权限边界”），不按问题的摘要；路由表总以兜底一行结束（[AI 导航](05-ai-navigation.md#入口即路由)）。
- **根据情况选表达方式**：图、表、代码、编号步骤、填好的样例、文字都是选项，哪种最好懂用哪种，没有必须的也没有禁止的（[图与表的先选表达方式](04-diagrams-and-tables.md#先选表达方式)）。
- **名字用代码的标识符**：文档、图与表里的组件 ID、事件、权限键、状态名、表名，与代码完全一致；业务叫法放进术语表（[AI 导航](05-ai-navigation.md#术语表)）。
- **编号稳定**：决定（D）、问题（I）、独立预期（AT、PJ……）、覆盖要求（C）的编号一经发布不改不复用；预期编号由检查 33 核对唯一与连续。
- **客户路线与开发路线**：面向客户的从全景、选择关系、选型说明进入，不要求先读源码或开发规则；面向开发的从边界、协议、规范与验收进入。
- **状态分开标明**：计划中的仓库与已有源码、已实现与已验证，分别标明；正式切换前核对目录覆盖、链接、状态与证据。
- **依据**：引用外部产品或标准时写明出处与查询的版本；产品资料证明的是供应商的能力，不是本项目的适配已经完成。

## 拆分与重构

- **默认在原文档上修改或增补**。
- **内容变复杂时重构**：同一份文档被反复增补、例外叠着例外、要读几遍才懂时，整体重写；重写前后逐条对照，细节一条不丢。规范是规格，不是记录，可以放手重写。
- **拆分的条件**（三条同时成立）：这部分内容遮住了原文档本身的目的；它回答的是另一个问题，而不只是相关的话题；拆开后，常见任务不会被迫两份都读。拆分的方法是列出会查阅每个候选文档的任务：大多数任务都要两份都读，就是同一份文档。
- 拆成新文件、给长期存在的文件改名、跨很多文件重组链接，先向维护者提出，不单方面执行。

## 语言

开发完成之前，正式文档只写中文（D67），结构为多语言留位置：

- 项目文档放在 `docs/zh/` 下；以后增加其他语言时，按同样的相对路径与文件名放 `docs/<语言>/`，文档之间的链接在各语言里是同一段文字。
- 根文档与组件文档（`AGENTS.md`、`README.md`、`BRICKKIT.md`、组件的 `docs/design.md`）直接用中文写在主文件名下，不另放译本。BrickKit 的文档检查认得中文的章节标题（例如“组件定位”“部署前准备”“项目约定”“查找路由”“易错点”），按这些标题检查结构。以后增加其他语言时，按 BrickKit 的后缀规则放译本（`<名字>.<语言>.md`），BrickKit 的工具按这个后缀找译本。
- 增加其他语言后，各语言版本的 `##` 章节相同、顺序相同，同一次提交一起改；以哪种语言为准，在增加语言时决定。
- 术语表为每个概念保留代码标识符一列，供翻译对齐。
- 镜像检查（`make docs-mirror`）保留，按语言启用；只有中文时不要求镜像。
- 代码全部用英文：标识符、注释、日志与错误信息（D74）。
- 提交信息与 tag 的注释用英文（D74）；照样先写进文件，再 `git commit -F`。
- 开发区只用中文。与维护者的对话、汇报一律用中文，不论讨论的文件是什么语言。

开发完成后，由用户决定何时补充其他语言。

## 过程记录

设计过程中的问题台账、证据记录与复查记录放在开发区，所服务的设计工作结束后进入归档；决定与 AI 选择的结论写进决定记录。正式文档不链接开发区或归档（`make docs-boundary` 检查，现行内容引用归档即失败）；需要保留的结论先迁入正文或决定记录，再归档。

## 文档与代码一起维护

- 文档是版本的一部分：和它描述的代码在同一次提交里改。
- 意图类的文档（协议、状态迁移表、决策表、带失败分支的时序图）**先改**：需求变了，先改它、评审它，再改代码；测试读同一张表。
- 事实类的图与索引（依赖图、ER 图、事件拓扑、接口文档、组件清单）**从代码生成**，不手写；CI 检查生成物是否最新（[图与表的规范](04-diagrams-and-tables.md#意图类与事实类)）。
- 评审清单有一条：“意图变了，文档与图表先改了吗”。

## 检查

| 检查 | 管住什么 |
| --- | --- |
| 链接检查 | 本地链接与锚点有效 |
| 文档边界（`make docs-boundary`） | 正式文档不链接开发区、归档与本机路径 |
| 镜像（`make docs-mirror`） | 多语言启用后，各语言的文件与章节对应 |
| 组件文档结构（`brickkit lint --strict`） | 组件与外壳的文档齐全、结构正确 |
| 预期编号（检查 33） | 独立预期的编号唯一、连续、各前缀只属于一份文档 |
| 表格结构 | 每行的列数与表头一致 |
| 名字存在性 | 文档与图表里的标识符在代码中存在（开发开始后启用） |
| 生成物最新 | 事实类的图与索引与代码一致（开发开始后启用） |
| AI 路由测试 | 不了解项目的 AI 能否从入口找对文档（[AI 导航](05-ai-navigation.md#怎样检验导航)） |
