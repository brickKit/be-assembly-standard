# 测试与验证

本页说明验证分哪几种、每类对象最少要证明什么、代表部署对照实验怎样做、选配变化必测哪些情形、改动的两次考试、证据怎样记录、独立复核与冻结的条件。每个覆盖要求的设计依据、独立预期、参考模型与将来的验证映射，以及预期编号的登记，见协议 21；一致性套件的结果分类与自检见协议 18。具体的验收矩阵在 [validation/](validation/) 下。

## 三种验证

| 验证 | 做什么 | 不能据此声称 |
| --- | --- | --- |
| 设计审查 | 检查覆盖、理由、参考模型、状态与跨层约束；先找反例 | SDK、业务或部署已经正确 |
| 最小实验 | 验证可能推翻结构的关键假设（代表部署实验） | 完整组合或容量已经验证 |
| 实现验收 | 证明具体版本按规格运行 | 未测过的组合、存储、授权成员或客户 Fork 也通过 |

三者分别记录，不用一类代替另一类。测试从对象与能力展开：组件、协议的多个实现、外壳、多实例任务、跨事务流程、持久数据、前端、客户 Fork、交付环境。每条记录写：对象 → 必须证明的结果 → 测试或实验 → 责任方 → 档位与命令 → 环境与版本 → 证据与限制。

被测对象从[组件货架](../00-overview/03-catalog.md)与[选型说明](../00-overview/guides/README.md)绑定到具体的组件、成员与适配器，不只写“权限方案”“消息系统”或“外壳”；抽象能力的测试不等于所有候选实现都通过。实现测试按[分层](#实现测试的分层与节奏)组织用例；专项检查增加的是验收目标，不要求机械地新增一层；一次测试可以服务多个目标，但每个目标必须有真实的断言。

意图类的表（状态迁移表、决策表、权限矩阵、流程的步骤与分支）是测试的依据：测试读同一张表，每格一条用例，包括“不允许”的格子（[图与表的规范](04-diagrams-and-tables.md)）。

## 每类对象最少要证明什么

| 对象 | 最少要证明 |
| --- | --- |
| 授权与身份替换 | 正反权限矩阵、数据与字段边界、受限的授权管理与间接提权、撤销与陈旧、迁移后语义相同 |
| SDK 与协议 | 同一版本的向量与黑盒套件对各语言实现成立 |
| 套件与门禁 | 正确实现通过；指定的坏变体只在预期的地方失败；空的或部分运行不能冒充合规 |
| 外壳 | 同版成员单跑与合并时的权限、错误、任务、观测、配置与资源行为等价 |
| 并发与恢复 | 真实实例竞争；进程退出、重投、应答丢失后业务不变量成立 |
| 数据生命周期 | 搬运与恢复、跨层完整性与权限、保全与清理、旧状态升级 |
| 附件与物理对象 | 三种语言的存储适配按同一契约验证行为、凭据隔离、错误与资源；父记录授权、扫描状态绑定内容、重复上传与覆盖、链接与撤权、引用、删除与保全的竞争、处理幂等、对象与元数据对账、迁移恢复 |
| 替换与 Fork | 切换步骤、调用适配、权限与数据迁移、失败恢复、来源可追溯 |
| 业务停用与退出 | 停用后原组件的受限查阅与合法维护、停用与提交的竞争、未完业务与依赖、迟到事件与外部结果、历史单据、关联与对象、当前权限；完全卸载另验迁移部分失败与对账恢复 |

## 实现测试的分层与节奏

目标只有一个：AI 写的测试要真的能抓住回归，而不是看起来很多、实际什么都没守住。达不到这个目标的测试比没有更糟，它让人以为“这里有覆盖”。测试数据从哪里来见[种子与测试数据](07-seed-and-test-data.md)。

### 分层

层按被测的范围划分，[协议 21 的验证映射](../06-protocols/21-verification-and-migration.md#覆盖要求的验证映射)用同一套定义。

| 层 | 范围 | 测什么 | 何时写 |
| --- | --- | --- | --- |
| L1 单元与向量 | 一个组件的代码，或 SDK 对共同语义向量 | 这份实现的分支：错误路径、空值、参数校验、SQL 组装；金额、编码、错误映射等共同向量（协议 18） | 随实现一起写：写下一个错误分支时就配上它的测试 |
| L2 组件黑盒 | 一个组件真起进程，连真实的 PostgreSQL 与消息系统，经契约调用 | 契约（每个接口真能跨进程调用，没有破坏性变更）；业务规则（不变量、合法的状态迁移、幂等、边界处的业务结论）；权限与数据边界；迁移能连跑两次 | 业务规则的测试写在实现之前 |
| L3 跨组件业务链 | 几个组件的真实部署 | 跨组件的流程、事件、补偿与恢复；组件之间发生的事 | 参与的组件能运行之后 |
| L4 部署与环境 | 整套部署 | 外壳与单跑的等价、升级与回退、恢复演练、多副本、引擎矩阵、性能 | 代表部署实验与发版之前 |
| FE-1 前端逻辑 | 纯函数、组合函数、状态仓库；网络替换掉 | 给定输入下逻辑算得对不对 | 代码写好就加 |
| FE-2 前端共享组件 | 被多个页面复用的组件（表格、页面模板、通用卡片） | 共享组件的行为；它坏了，引用它的页面一起坏，所以优先于单个页面的组件 | 代码写好就加 |
| FE-3 端到端 | 真实浏览器对真实后端 | 一条完整的业务流程；PC 与移动端共用工具，用设备配置区分 | 页面交互稳定之后 |
| FE-4 视觉回归 | FE-3 经过关键页面时的截图比对（亮色与暗色各一份） | 间距、密度、组件用法一致；基线随有意的界面变更更新 | 与 FE-3 同批 |

**判断一个测试属于 L1 还是 L2**：把这个功能的实现整个删掉、用另一种语言重写，这个测试还应该成立吗？应该，就是业务规则，写在 L2，经契约测；不应该，它测的是这份实现的细节，写在 L1。

贯穿各层的四条原则：

1. **规格先于实现**：L2 的业务规则写这个功能应该做什么，不是代码做了什么。实现之后才写的测试只能描述已有的代码，防得住回归，防不住“从一开始就理解错了需求”。
2. **真实优于模拟**：替身最多证明“调用发生了”，证明不了“结果是对的”；参数传错、返回的错误没处理，替身照样绿。组件之间发生的事由 L3 真起进程证明。
3. **能机械化的判据一律机械化**：靠人记得去查的规则，能写成门禁或脚本就写成门禁或脚本。
4. **每层只测自己那部分**：同一个断言写在两层，就多一处要同步的地方，而它不会被同步。

### 各层的硬要求

- **核心交易**（库存、出账与核销、收付款、薪资与提成：出一次错就是一次业务事故的地方）的 L2 用**性质测试**：人定义不变量，框架生成大量随机输入攻击实现（Go 用 `rapid`，Python 用 `hypothesis`，TypeScript 用 `fast-check`）。只靠举例的测试找不到“特定操作序列才触发”的错误。
- **幂等测试包含并发**：多个协程在同一时刻用同一个键调用，只有一个真正执行。只测串行重放，抓不住“先查再插”。
- **数据边界测试证明别人的数据看不见**，不只是自己的看得见：建两条归属不同主体的数据，用其中一个身份查，断言另一条一条都不返回（[权限验收矩阵](validation/authorization-matrix.md)）。
- **迁移**：每个迁移连跑两次都成功；有回退脚本的组件，至少在真实数据库上跑过一次回退再前进，重置命令在交付前真跑过。回退脚本删掉了早先的表仍在引用的基准数据，只有真执行时才会失败。
- **消费者测试**：自己发布事件触发消费者的测试用测试私有的主题与唯一的聚合身份（[种子与测试数据](07-seed-and-test-data.md#测试数据)）；验证“发到哪个主题”的测试用真实主题。
- **会被多个实例同时使用的 SDK 原语**（发件表发布、幂等认领、工作项认领、连接池）至少有一个多实例并发测试，检查每一项恰好处理一次；只假设一个进程的测试找不到这类错误。
- **认证**（没有凭据拒绝、凭据没有这个权限拒绝）在 SDK 里测一次；门禁检查每个对外路由都经过它，组件只测自己的数据边界。

### 一轮红绿与铁律

一轮：写一个失败的测试（或一小组紧密相关的）→ 跑一下，确认它是红的，**而且红的原因是功能还没实现**，不是编译错误、替身配错或测试本身有错 → 写最少的代码让它变绿 → 跑全量，确认别的没变红 → 必要时重构，再跑全量 → 提交，写清这一轮锁定了哪条业务结论。

**绝不为了让测试通过而改测试**：

| 情况 | 怎么做 |
| --- | --- |
| 红是因为实现错了 | 改实现。这是默认情况，没有例外 |
| 红是因为测试断言了一个错误的业务结论 | 先停下，一句话说清原断言错在哪里、为什么错，单独一个提交改它 |
| 一个 L2 测试挡路 | 几乎总是实现或对需求的理解错了：先改设计文档，再改测试，绝不反过来 |

绝不注释掉测试，绝不加跳过标记，绝不放宽断言直到它碰巧通过。这三种都把门禁变成装饰；一旦有一个门禁是装饰，别的绿也就没人敢信。预期本身有误时，同样先改设计文档再改测试（[协议 21 的从预期到测试](../06-protocols/21-verification-and-migration.md#从预期到测试)）。

### 卡住时

同一轮三次还没绿，按顺序走：

1. **把这一步切小**：这一步通常在同时解决两三件事。拆开测试，一次只让一个小断言变绿。
2. **去看参考实现**：看完回来想清楚，再写自己的（[参考实现](08-reference-implementations.md)），绝不照抄。
3. **停下来说清卡在哪**：期望什么、实际发生了什么、试过什么、怀疑是哪一层，交给人判断。这是正确的动作，不是失败；绕过去一次，下次就有人照抄。

### 门禁

- 新门禁先证明一次自己会红：在真实代码所在的位置（包括嵌套目录）放一个故意的违规，看它报出来，之后它的绿才可信。从没见过违规的门禁，可能一直在扫一个空目录（协议 18 的检查带坏变体）。
- 门禁失败时先读它的输出；它会点名违反了哪条规则、哪个文件。

### 前端测试的取证

- 跑 FE-3 或 FE-4 之前先问用户：说清这次覆盖哪些流程与页面，等用户同意。成本在编写与调试（为找选择器、查失败原因反复截图），不在跑一套已经稳定的测试。
- 确认页面元素优先用无障碍树快照，不用截图；失败时先看文本报错与执行轨迹，再截图；能让人录关键路径就让人录。
- 契约漂移靠生成消除，不靠测试：前端的类型与请求函数从契约生成，类型检查在编译期抓住漂移。

### 运行粒度与命名

| 粒度 | 何时 | 跑什么 |
| --- | --- | --- |
| 全量 | 部署之前、一批发布之前 | 项目的全部门禁与检查；每个组件的测试；部署后的冒烟 |
| 一个组件 | 一个组件或一个功能做完 | 组件的全部测试；跨组件的测试对着真实依赖跑 |
| 组件的一部分 | 迭代一个功能时 | 按名字过滤的测试，或监视模式 |

每个组件提供同样的标准命令，并且真的能跑：全部测试（开竞态检测）、迁移连跑两次、契约的破坏性变更检查、合并安全检查（[组件实现约定](06-component-implementation.md#合并安全)）、不启动任何东西的装配预检、种子数据及其撤销。L2 以上与消费者测试只连测试库，绝不连演示库（[种子与测试数据](07-seed-and-test-data.md)）。

| 命名规则 | 适用于 | 为什么 |
| --- | --- | --- |
| 名字直接写业务结论或分支，不编号；对应独立预期时带预期编号（[AI 导航的追踪链](05-ai-navigation.md#追踪链)） | L1、L2 | 不打开文件就知道测什么，并能生成“预期 → 测试”对照 |
| 性质测试名字里带 `Property` | 性质测试 | 告诉读者这个断言背后是随机输入攻击 |
| 跨组件的测试名字写出对方组件 | L3 | 按名字过滤就能只跑两个组件之间的测试 |
| 端到端测试以业务流程命名，不以按钮命名 | FE-3、FE-4 | 按流程过滤 |

测试里人只审 L2 的不变量清单是否完整：门禁只跑已经写下的测试，没人想到的不变量，门禁再绿也从没被检查过（[AI 编码习惯的人要审什么](09-ai-coding.md#人要审什么)）。

## 代表部署对照实验

在重建当前范围之前开展（D41；[路线](../00-overview/06-roadmap.md)第 2 步），用于部署选择与结构验证；完整的性能基线仍在重建之后（第 4 步）。

组件选配、运行拓扑、部署引擎分别作为变量，默认方案等实测后确定。先控制变量，再补代表组合，不盲目做完整笛卡尔积。

| 维度 | 代表范围 | 控制与限制 |
| --- | --- | --- |
| 组件选配 | 少组件的真实业务闭环；较完整的已实现组合 | 从所选版本的必需依赖闭包派生成员；不把未开发的组件假装装入；少组件样板不代表所有客户 |
| 运行拓扑 | 全部单跑；兼容成员合进外壳；重任务独立的混合形态 | 同一组成员、精确版本、配置、契约与基础资源；不借合并改变业务调用或事务语义 |
| 部署引擎 | Docker 作对照；Podman 为重点候选；Kubernetes 按支持目标另验 | 记录引擎、工具与宿主的版本，实际运行方式，持久卷、网络与权限；比较引擎时固定拓扑、组件与负载 |

**另加两个对照组**：全部单跑但数据库前加事务模式的连接池代理；只用 PostgreSQL（PostgreSQL 队列适配器代替 JetStream）的最小基础资源档。目的是分清外壳实际省下的是语言运行时的内存、数据库连接，还是基础资源的进程：Go 运行时的常驻内存较小，Python 较大，数据库每个后端连接也占内存。如果连接池代理组与外壳组的整套资源接近，Go 成员的进程内合并可以降为可选，而不是默认推荐。

**前提**：先明确代表链路、目标协议与 SDK、组件与外壳的版本，按新设计开发实验所需的最少条件（D59：按新设计重建，不升级现有组件）。旧的发布版本可以形成标明限制的基线，但不能证明目标架构。安全与一致性的前提不满足时，记录缺口，不跳过检查，也不用替身签发客户方案的通过结论。

**规模前提**按[规模阶梯与扩展信号](../04-foundations/01-deployment-and-runtime.md#规模阶梯)组织：默认的小公司基线、业务广但低资源或容许等待、较高并发或诊断需求，分别取代表组合。客户人数、成员数量与容器数量不混成一轴。本机资源不足的完整货架与多故障域实验明确留“未测”，不用分批的结果假称全部组件已同机运行通过。

**收敛顺序**：

1. 固定少组件组合与一个引擎，验证单跑下真实的授权请求、跨组件调用、持久事件与业务完成，再比较外壳与混合；生成成功或健康检查通过不算业务通过。
2. 固定组合与拓扑，对照 Docker 与 Podman；把必要的适配、维护步骤与限制记为交付成本，不只比较启动耗时。
3. 对较完整的组合复核代表格，覆盖后台、批量、渲染等争用；改变成员数量时写明是哪一项带来差异，不与引擎差异混算。
4. 验证重启、资源争用、依赖中断、在途恢复、升级与拆回。不支持的格写明原因；结构性失败反馈到设计后再测，“该格未跑”不算通过。

| 证据 | 必须比较的结果 |
| --- | --- |
| 正确性与安全 | 相同的业务效果、拒绝与数据范围、事件与任务恢复、重复保护；性能好不能抵消行为错误 |
| 客户整套资源 | 空闲与代表负载下的 CPU、内存、连接；数据库、身份、消息、存储与观测等基础资源；磁盘与维护对象 |
| 请求与业务完成 | 响应尾延迟、真正完成的时间、错误与“处理中”的比例、积压年龄；负载、数据形状与重复测量的条件明确 |
| 物理独立性的代价 | 成员故障影响哪些业务、资源争用、能否局部扩容与发布、组合升级与拆回的步骤 |

输出包括精确的版本与环境、命令与参数、所选的代表格、实际结果、限制、必要的适配与待修复项，并据此给出候选的保留、拆分或淘汰理由。最低的客户预算、容量与默认配置在实验后确定；较完整的样板也不代表以后的全部货架已经验证。

**观测分档的对照**在固定的部署条件下单独进行：各档演练组件与外壳重启后日志仍可查、受保护请求与跨成员故障可以关联、事件与作业积压、磁盘容量风险可以告警，以及采集或告警接收方故障时的丢失边界与恢复。记录各档的资源、保存与查询条件、定位步骤与限制；完整方案通过不代表基本方案通过，基本方案精简也不取消业务审计的验收。

## 组合变更的必测情形

沿用各专题的业务预期，绑定[选配变更的共同流程](../00-overview/05-change-and-retirement.md)，不另定义更宽的权限或事务语义。

| 编号 | 变化或反例 | 必须断言 |
| --- | --- | --- |
| ST01 | 少组件初装，缺所选业务的必需依赖或权限能力；合格组合作正例 | 缺件拒绝并说明原因，合格闭环可用；缺可选能力只按声明降级 |
| ST02 | 已有授予、共享与字段规则后，切到能力较少的授权成员 | 不丢规则、不静默放宽；未承接的状态阻止切换，显式改变业务范围另审 |
| ST03 | 同一法人配置了两个权威、缺一个范围；多渠道多选 | 冲突与缺口阻止对应范围启用；多选按明确的路由，不双重执行 |
| ST04 | 新增消费者或渠道，又移除有待发送或未知回调的旧成员 | 历史初始化与待处理的责任明确，不自动重发全部历史，不丢结果，不盲目切换重试 |
| ST05 | 复制后来源又写入、旧工作者延迟执行、目标部分发布 | 切点与版本、代次有效；未完成的范围暂停；只有合格的权威可以写 |
| ST06 | 目标开始新写或已有外部执行后，要求退回旧方案 | 保留新事实，按可验证的恢复或反向转换处理，不只改回旧地址或重放副作用 |
| ST07 | 单跑进外壳与拆回，成员版本与数据库目标不匹配 | 组合被拒或走已支持的路径；同版的身份、状态、端口行为一致；共享池不误指其他库 |
| ST08 | 配置字段改对了但运行仍是旧值；无效候选；跨成员部分生效 | 显示实际应用的版本，错误不覆盖合格的快照，部分不算完成，不放宽必需控制 |
| ST09 | 密钥同长度替换、读取失败、新旧连接、多副本更新不同步 | 检测实际版本；连接、签名与验证按规则切换；过期或撤销的值不无限沿用 |
| ST10 | 新旧前端、SDK、工作者组合，旧版稍后又恢复上线 | 能力、数据、作业与权限语义按准入处理，未知不伪装兼容；破坏性迁移后旧写入者被拒 |
| ST11 | 基本与完整观测切换；低资源的广业务组合；作业预算收紧 | 必需的审计与告警保留，不删除业务队列；背压与实际的诊断、资源条件可以验证 |
| ST12 | 停用或卸载组件后仍有历史依赖、附件、在途与更正 | 退出被阻止或交接明确；历史与当前授权可用；依赖闭包不只按现有菜单判断 |

每项同时记录：管理身份、来源与目标的精确组合、变化的切点、正例与反例、副作用与对账、恢复服务的条件、实际命令；不支持的格保留限制。ST 的适配与切换验证复用 PA、DT 的细节断言，不只比较生成物或健康检查。

## 改动的两次考试

[改动的循环](10-development-workflow.md#改动的循环)的 ② 与 ⑥ 各考一次：让一个不了解项目的 AI 回答这次改动的业务问题，看文档是否写对、写全，以及写代码之后是否还与代码一致。测试证明代码做到了测试写的东西，考试证明文档说的就是代码做的事；两种漂移测试都发现不了，第 7 步的考试查出过真缺陷（一个跨对象的加锁顺序）和一批“改了代码没回写文档”的地方。

| | ② 考设计 | ⑥ 考一致性 |
| --- | --- | --- |
| 什么时候 | 意图改完、写契约与代码之前 | 实现与测试都完成之后 |
| 考生读什么 | 只读文档 | 文档与代码 |
| 查什么 | 设计本身对不对、写没写全 | 写代码时改了的行为有没有回写进文档 |

- **考生**：一个只加载仓库自己的项目设置的新会话（无头会话，例如 `claude -p --setting-sources project`），只拿到仓库与题目，不给设计以外的提示；子 agent 带着当前会话的指令，不算零了解。能力较弱的一档模型也考，不只看最好的成绩。
- **题目**：改动者按这次改动出几道业务问题（某种情况下规则怎样、失败时怎样、改了谁受影响），并先写好参考答案。
- **判**：答错、答不出、或要读代码才答得出，是文档的缺口，修文档，不修题目；考生指出设计与代码不一致，按缺陷修；参考答案自己错了，改正参考答案（考生照着文档答对，说明文档比改动者的记忆可靠）。
- **记录**：题目与结果放在开发区，正式文档不链接、不抄写（题目进了文档，考试就作废）。
- **什么时候不考**：只在一个组件里、不改业务规则的改动；新组件与跨组件的改动两次都考。

## 证据

“规范写了”“测试存在”“执行通过”分别记录；“通过”还要写对象、精确版本、参数、硬件与引擎、实际命令、结果与观察日期。待实现、待验证、不适用与需要用户裁定的，都写明。一致性套件的结果分五类：通过、失败、未运行、不适用、检查失效；只有声明的剖面中全部适用的必须检查都运行且通过、没有检查失效，才判“符合”（协议 18）。

参考模型（`be-acceptance` 仓库的 `models/`）演算协议的关键条款：正确版本通过、每个坏变体被发现，说明模型能检验它声称检验的条款；模型不是 SDK、数据库或消息系统的运行结果，不能代替实现验收。关键的交错用定向场景固定构造，不只靠随机运行命中。

生成的文件、dry-run 与健康检查不是业务闭环或容量的证据。旧的测试是否仍证明新的规格，要检查它的断言后再承接。

## 独立复核与冻结

独立复核者从用户目标、冻结候选与证据进入，先找反例，再核对作者的理由；可以用新的会话完成。

冻结条件：所有适用项都有设计与验收的去处；结构性问题已闭环；必要的先行实验已通过；保留的限制可以理解；未完成的实现已排期；通过独立复核与用户确认。冻结的是设计基线，不是对尚未实现内容签发的运行合格证明。

## 已知风险与待定

- 验收矩阵（PA、DT、ST）全部是理论验收规格，尚未执行；具体的契约版本、接口、错误映射与运行命令随实现绑定。
- 代表部署实验的具体实施计划（版本、链路、命令、每项改动与耗时预算）在重建计划中写，经用户确认后执行。
- 观测分档对照的具体用例、阈值与命令待补。
