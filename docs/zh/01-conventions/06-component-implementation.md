# 组件实现约定

本页说明后端组件的代码怎样写，才能既独立运行、又能安全地合进外壳：仓库布局与入口、运行时是唯一入口、合并安全、健康检查与镜像、权限与资源、调用其他组件、数据库、事件与契约。组件必须遵守的外部行为由[协议 18 的组件协议](../06-protocols/18-sdk-and-conformance.md)与各协议规定；各语言锁定的技术栈见[组件协议与语言](../04-foundations/07-component-protocol-and-languages.md)；配置键与注册表见[协议 19](../06-protocols/19-config-secrets-registries-release.md)。

## 两条原则在代码里的意思

[产品的两条不变的原则](../00-overview/01-product.md#两条不变的原则)落到代码上：

1. **每个组件都是完整的 BrickKit 组件，能独立运行**：对其他组件的每一次调用都经契约走真实的网络调用；声明的每个端口都真的在监听；只带上它依赖的组件就能把它拉起来。
2. **合并只发生在部署层**：外壳把几个成员放进一个进程，除此之外什么都不做：没有业务逻辑，不共享表与 schema，不合并成员的接口端口，不让成员互相导入代码。

“反正最后都在同一个外壳里，直接调函数好了”违反第一条；外壳里的边界一旦消失，这个组件就再也不能单独部署。

## 仓库布局与入口

布局按 [AI 导航的标准布局](05-ai-navigation.md#组件仓库的标准布局与代码地图)，同一种语言的组件完全相同。另外：

- **一个模块入口**：组件只有一个构造模块的入口，单独运行与合进外壳调用的是同一个；模块交回它的接口处理器、系统调用的注册函数与启动、停止钩子。模块自己从不监听端口：单独运行时由 SDK 的启动器监听，合并时由外壳监听。
- **迁移随包、由清单启动**：迁移文件嵌在组件的包里（`<包>/migrations/`），由同一个程序的 `migrate` 入口执行；组件清单声明这条迁移命令，BrickKit 在服务启动之前用组件自己的镜像执行它（协议 14 的结构迁移），外壳的每个成员因此仍然要有自己的镜像。模块的 `serve` 入口从不迁移。
- **生成的契约包单独发布**：Go 组件从契约生成的代码是一个独立发布的模块，调用方直接导入它（见[调用其他组件](#调用其他组件)）。
- 迁移文件按四位序号命名（`NNNN_<名字>.up.sql`）；需要重置命令的组件（[种子与测试数据](07-seed-and-test-data.md#种子数据)中有只追加表的）另提供回退脚本（`NNNN_<名字>.down.sql`），只用于开发与测试库，正式部署只向前（协议 14）。

## 运行时是唯一入口

模块需要的一切都从 SDK 交给它的运行时取；模块代码不从进程读任何东西。

- **配置**：只经运行时读取组件声明的键，键名就是配置声明里的大写下划线名；类型不符或必需键缺失时启动失败（协议 18、19）。
- **依赖地址**：只经运行时的地址访问器读取；SDK 负责把平台注入的形式转成可以拨号的地址，并区分接口端口与系统调用端口。
- **缺席的可选依赖**：没有这个依赖时，访问器返回“不存在”，模块按边界卡声明的方式降级；不把它当作空字符串，也不因为缺变量在启动时失败。
- **连接**：数据库连接池与消息连接由启动器或外壳按共享的连接键建好交给模块；模块从不自己开连接池。
- **日志、追踪、指标**：用运行时提供的记录器、追踪器、指标器与模块自己的指标注册表。

## 合并安全

代码完成之前，下面三个问题都要回答“没有”：

| 问题 | 合并之后的症状 |
| --- | --- |
| 模块代码有没有读进程环境？ | 一个进程只有一份环境：成员互相覆盖 schema 名与其他所有键，某个模块静默地读写了别的组件的 schema |
| 有没有初始化任何进程级的东西？（全局的追踪提供者、日志的全局配置、信号处理、默认的指标注册表、框架的全局模式开关） | 最后一个初始化的赢，一切照样全绿：全部追踪落在一个服务名下；一个模块开了调试模式，所有模块都进调试模式，错误堆栈直接发给客户端；默认注册表在第二个模块注册时直接崩溃 |
| 有没有退出进程？（致命日志、直接退出） | 一个模块的可恢复错误拖垮整个外壳，同一进程里的成员一起停 |

模块里也绝不绕过 SDK 自建 HTTP 引擎、数据库连接或监听：自建的引擎会丢掉 SDK 的整条中间件链（请求身份、追踪、指标、访问日志、崩溃恢复、错误映射、授权），而且不报错。组件的合并安全检查命令扫描以上全部；外壳一侧的义务见[协议 17 的外壳义务](../06-protocols/17-runtime-and-resources.md#外壳义务)。

## 健康检查与镜像

- 健康检查只报告这个进程是否活着，绝不检查数据库、消息系统、授权或其他组件：下游一次抖动就会让所有上游同时被判不健康、被重启，在外壳里就是所有成员一起重启（协议 17）。
- 健康检查同时应答 `GET` 与 `HEAD`，由 SDK 注册，组件不自己注册。
- 启动宽限期按语言给起始值（[协议 17 的参数起始值](../06-protocols/17-runtime-and-resources.md#参数起始值)），实测后调整。
- 基础镜像要带 `/bin/sh` 与 `wget`：健康检查经由 shell 执行。用 `scratch` 或 distroless，组件日志说“已就绪”，平台却永远报不健康。

## 权限与资源

- 每个对外的操作在资源定义中声明：资源类型、维度、操作与字段（[安全 09a](../06-protocols/security/09a-encoding-and-records.md)、[安全 06](../06-protocols/security/06-security-contracts-and-capabilities.md)）。操作定义是路由注册的一部分：没有登记的路由、resolver 或任务，构建、启动或装配检查失败；公开接口要显式声明。
- 权限键与资源类型的命名、登记与退役按[协议 19 的注册表](../06-protocols/19-config-secrets-registries-release.md#注册表)：在注册表登记后才使用，已发布的不改名。
- 前端的隐藏不是安全边界：拒绝数据的是后端（协议 20）。

## 调用其他组件

- **只经契约**：组件之间不导入代码，不共享模型包，不复制别人的生成代码，不读写别人的表。能跨边界的代码只有 SDK、被调方发布的契约包与族契约包；复制一份生成代码，同一个协议定义会在一个进程里注册两次，调用方与被调方进了同一个外壳时，第二次注册直接崩溃（决定 0101）。
- **替用户读取**：经被调方的用户面，转发原用户的凭据并另加服务身份的验证；被调方按这位用户的授权过滤。用户凭据不能用于系统方法（[安全 02 的入口与调用模式](../06-protocols/security/02-trusted-identity-and-attributes.md)）。
- **系统面**：系统命令（例如销售确认时向库存发起预占）与按身份的批量读取用组件的服务身份，按部署声明的“服务到方法”许可准入。系统方法从不返回按用户范围过滤的行（原有决定 0208）。
- **系统结果不原样进入用户响应**：按身份补全不是授权的例外：调用方已有身份，不证明用户能看补全的字段。批量读取的结果用于合法的内部计算；要放进用户响应时，先按用户的读取契约与字段许可裁剪。把系统结果原样返回，或用服务身份代替用户取受范围约束的数据，响应会静默多出用户不该看到的数据。
- **关联数据经数据属主的批量读取**，绝不跨 schema 连接查询。每个聚合根在系统面提供按身份批量读取的方法，上限写在契约里，超限拒绝而不截断，调用方自己切分；不逐个调用（[原有决定 0304](../02-decisions/10-earlier-decisions.md#0304-按身份批量读取每次最多-500-个上限是契约的一部分)）。
- 时限、重试与熔断按[协议 17 的组件之间的调用](../06-protocols/17-runtime-and-resources.md#组件之间的调用)；基础组件不同步调用业务组件（D68）。

## 数据库

规则在[协议 14 的数据库](../06-protocols/14-data-foundations.md#数据库)；写代码时最容易错的几条：

- 一切数据库访问经 SDK 的事务入口：它在事务内用 `SET LOCAL ROLE` 与 `SET LOCAL search_path` 切到本组件的角色与 schema，并按事务设置超时。不带 `LOCAL` 的设置会留在池里的连接上，下一个借到它的人把查询打到你的 schema 上：不报错，不崩溃。超时必须按事务设：`SET ROLE` 之后，PostgreSQL 不套用目标角色上用 `ALTER ROLE … SET` 设的参数。
- 事务里不发网络调用，不嵌套事务（[事务与消息的本地事务](../04-foundations/03-transactions-and-messaging.md#本地事务)）。
- 迁移是纯 SQL，迁移状态表在组件自己的 schema 里，每个迁移能连跑两次；运行时代码不使用属主角色。
- 当队列用的行（发件表、工作项）原子认领，跨组件写入的幂等键用原子插入认领（协议 01、事务与消息）。

## 事件与契约

- `contracts/` 是接口的唯一事实来源：系统调用、用户接口与事件的定义都在这里；前端的类型与请求函数从契约生成，从不手写。
- 业务变更与发件表在同一事务提交，由后台发布（协议 02）。
- 事件类型的命名与登记按[协议 19 的注册表](../06-protocols/19-config-secrets-registries-release.md#注册表)；契约的演进按协议 19 的兼容规则：新增不自动等于兼容，含义变化按破坏性变化处理。
