# 路线

本页说明设计与开发的范围怎样划分、开发按什么顺序进行、设计修订怎样进入正式文档，以及问题反馈与项目完成后的整体总结。设计与实施的任务都要落到具体的组件与选择关系上（[组件货架](03-catalog.md)、[选择方式、关系与客户组合](04-selection.md)、[选型说明](guides/README.md)）；某个方案在选型说明中出现，不等于它进入近期的开发或发版清单；例如授权的静态与关系图计划、长期的策略引擎评估，在[授权的选型说明](guides/authorization.md)中分别标明。

## 三条范围线

| 范围线 | 内容 | 现在做到什么程度 |
| --- | --- | --- |
| **长期产品蓝图** | 完整的组件货架与以后的新能力：边界、扩展点、依赖与可选组合 | 参与设计，边界卡与选择关系写全；不全部开发 |
| **底层设计冻结** | 全部适用的底层方面、项目规范与验收要求 | 本次设计全部审清，经用户确认后冻结 |
| **近期实施与证明** | 按新设计重建当前范围的组件、SDK 与工具（D59），以及证明部署与代表性替换所需的工作 | 按下面的五步进行 |

以后的功能参与设计，但不全部进入近期实施。已有组件需要拆分、合并或删除时，先说明对当前业务闭环、契约、注册的身份、数据与 Fork 的影响，再更新实施计划。

**规模**：业务组合、负载、资源与可接受的延迟分别设计，默认按小公司的规模开发。没有统一的最终数字，不妨碍定义配置、专项组件、监控与部署的扩展路线；不再重复询问规模，也不虚构容量。

**高可用**：底层设计已经为高可用留好位置（D66：高可用部署整体同步提交，两个备库任一确认），但正式开发从单实例、单数据库开始，后期按客户需要启用（[部署、运行与资源](../04-foundations/01-deployment-and-runtime.md)）。

## 开发的五步

按 D59，现有代码（阶段 06 的组件、SDK、工具与外壳）只作参考和教训，不作为设计边界或迁移对象；终局设计视为第一个正式版本。开发分五步，顺序不变：

1. **设计写到可冻结**（D56）：设计的每一部分都到达可冻结，用户确认后迁入正式文档（下一节）。
2. **代表部署实验**（D41）：按新设计开发实验所需的少量代表组件、SDK 与外壳，比较外壳与独立进程、Docker 与 Podman、连接池代理与只用 PostgreSQL 等关键选择，根据结果修订设计。实验规格见[代表部署对照实验](../01-conventions/02-testing-and-validation.md#代表部署对照实验)。
3. **重建当前范围**：按新设计重建当前阶段约 20 个组件覆盖的业务范围（组件数量可能因边界调整略有增减），连同 SDK、外壳与工具。开工时：
   - **组件仓库骨架与文档分发**：为当前重建范围的组件建仓库，把边界卡与组件层的图与表写进各仓库的 `BRICKKIT.md`、`docs/design.md` 与 `AGENTS.md`（[文档规则](../01-conventions/03-documentation.md#组件的文档)）；远期组件的卡片留在系统层，开工时再建仓库。建仓库是对外操作，届时先经用户确认。
   - **事实类图与索引的生成工具**：在 be-ops 中从组件声明、迁移、契约生成依赖图、ER 图、事件拓扑、部署图与各种索引（[图与表的规范](../01-conventions/04-diagrams-and-tables.md#意图类与事实类)、[AI 导航](../01-conventions/05-ai-navigation.md#生成的索引)），与第一批组件一起开发。
4. **全部部署模式的测试与开销测量**：用这 20 多个组件跑完整的部署矩阵（单独运行、外壳、混合、多副本 × Docker、Podman、Kubernetes）与完整的性能基线，测量整套开销，作为向客户与 BrickKit 证明这些部署模式真实可用的依据。
5. **扩展货架**：之后按客户需求与替换验证的需要，分批开发其余组件，覆盖代表性的业务与替换组合，而不是以当前组件的数量限定设计。

各处文档中的“重建当前范围”“部署矩阵”即指第 3、4 步。需要改变顺序时，用明确的验证目标与成本说明来决定。

**部署组合按实测定案**：组件独立开发与验证；“外壳优先”只是取向，不是结论。代表实验比较少组件与较完整的组合、单独运行与外壳与混合、Docker 与 Podman，同时衡量资源与物理独立性的代价。

**身份方案**：先沿 Casdoor、Keycloak 与通用 OIDC 或目录的适配路线设计与验证；精简的本地身份保留为评估项，不进入已承诺的开发清单。最低部署的实测不能满足、或客户需求明确时，再提出方案、安全验收与实施范围；需要先行的资源实验另行安排（[身份的选型说明](guides/identity.md)）。

## 设计与正式文档

终局设计已在 2026-10-15 冻结，并整体替换了原有的正式文档：旧文档与设计过程的记录在归档与 Git 中，现行的规则只在本目录与正式文档中。之后的大修订（新增一组组件、重写一个协议、实验或实现推翻了某个结构）按[协议 21 的设计修订进入正式文档](../06-protocols/21-verification-and-migration.md#设计修订进入正式文档)进入正文；小修订直接改正式文档，与代码同一次提交。

## 问题反馈

真实发现问题才向 BrickKit 或知识库反馈，不为反馈的数量去找问题。

- 具体的错误、实质的覆盖缺口、可以定位的说明矛盾：核对版本、上下文与已有的反馈后及时提交，写明反例与证据的边界。
- 平台问题按最小复现与新旧行为整理；只反馈在本项目重建后验证过的问题。通用能力的需要作为功能请求提出（询问能否支持），新版本发布后由本项目验证。
- 知识库的差异先区分：是本项目的独特选择，还是通用知识有错。业务选择不同、本项目尚未完成自己的协议、或尚未证明平台不支持，不直接记成对方的问题。本项目的独特做法作为案例记录，不当作知识库的错误。
- 知识库的反馈经独立的贡献分支与 PR 提交，由维护方审查；平台的反馈按它的贡献方式提交。阶段成果与最终完成分开记录。

设计可以推翻任何现有结构，但执行前必须写明迁移与验收。

## 项目完成后的整体总结

整体总结在这些条件都满足后准备：用户确认的任务范围已完成；关键协议与实现一致；声明支持的组合以及必要的恢复与升级验收已完成。长期货架中未实现的部分保持计划状态，不把若干代表组合的通过扩写成所有组合通过；如果只完成了某个阶段，报告的标题与结论写明是哪个阶段。

| 材料 | 最少保存的证据 | 价值 |
| --- | --- | --- |
| 项目背景与范围 | 目标、约束、所选能力、版本或提交、实施范围与未完成的蓝图 | 读者知道成果适用于哪些客户与条件 |
| 组件与替换 | 独立的业务闭环；真实的替换、多选与按范围路由；迁移步骤与改动成本 | 向 BrickKit 说明组件装配与部署理念怎样在业务中成立 |
| 部署与资源 | 同版本、同负载下单独运行、外壳与混合，各运行引擎与观测档位的整套资源、延迟与故障影响 | 证明收益与代价，不只展示进程数减少 |
| 正确性与恢复 | 权限的允许与拒绝、跨组件的事实、并发与崩溃、升级与恢复的结果、已知限制 | 证明业务上的保证，而不只是健康检查或生成物正确 |
| AI 开发与维护 | 契约、SDK 与组件的变更过程，实际的修复，Fork 的适配，可以重现的检查；效率数据有基准才比较 | 为知识库提供有证据的工程经验，不以模型名称证明优势 |
| 问题与经验 | 失败过的路径、反馈与处理状态、独特选择的理由、尚未验证的项 | 提供可复用的判断，项目事实与通用推荐分开 |

材料随实施保存版本与可重现的入口。任务完成后先组织成一份项目整体总结，再按读者整理成 BrickKit 的使用与验证报告、知识库的项目案例；两份用同一套证据，不复制整套项目文档。对外发送前核对可以分享的范围，去掉密钥与客户的私有资料；知识库案例通过 PR 提交，不自动合并。届时按任务范围、材料完整度与用户要求确定提交的内容与时间，现在不宣称已经成功。

## 已知风险与待定

- 代表部署实验的结果可能改变部署的推荐组合与部分底层选择；实验之后修订设计，再开始第 3 步。
- 当前重建范围的组件数量随边界调整可能略有增减，以[组件货架](03-catalog.md)的“当前重建”为准。
