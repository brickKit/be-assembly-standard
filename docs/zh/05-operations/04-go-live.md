# 客户上线

规则见[协议 16](../06-protocols/16-go-live-and-import.md)。本手册是从旧系统迁入的操作清单。

## 准备

- 确认上线切点（每个法人的一个业务日期，从当天开始，协议 16 的上线切点）与切点所在的会计期间；在财务中声明法人的上线切点（上线窗口内，业务确认），切点之前的期间成为“上线前”（协议 06）。
- 每个法人与薪资组声明新系统的第一个计薪期间；确认未完成订单、合同周期、已批准未休的假在切点处的承接口径（协议 16），避免重复出账、重复发薪、重复扣假。
- 列出要迁入的内容：主数据、员工与任职、期初库存与成本、应收应付与银行、固定资产、总账余额、未完成单据、有效合同、进行中的项目、假期余额、薪资的年度累计、用户与授权。只列客户实际选用的组件。
- 为每类内容取得旧系统的导出与对账口径；约定差异的处理人。
- 准备外部身份到平台主体的映射（安全 02）；授权按批量计划导入，不直接写入。
- 确认主机的电源与 CPU 节能设置：对延迟敏感的部署，主机用高性能的调速（Linux 的 `performance`，或 BIOS 的高性能档），并限制 CPU 的深度休眠。代表部署实验里，同一份代码在节能模式下延迟与每次操作的 CPU 约多 1.6 倍，200/s 的事件路径排队几秒；负载越低、CPU 睡得越深，低负载下的延迟反而越高。云主机多半已经固定，自己的机器要查。容量估算要写明数字在哪种电源模式下测得。
- 用 PostgreSQL 队列做消息运输的部署：在数据库实例上设 `idle_in_transaction_session_timeout`（PostgreSQL 17 起再设 `transaction_timeout`），并监控最老在途写事务的年龄。实例里任何一个开着的写事务都会让全部订阅停住，原因与取值见[消息运输的 PostgreSQL 队列的取舍](../04-foundations/06-message-transport.md#postgresql-队列的取舍)。
- 确认正式部署中没有开发与测试用的东西：身份产品中没有开启密码授权的客户端，身份适配组件没有开启开发换取入口，没有测试账号、测试角色与种子数据（[种子与测试数据](../01-conventions/07-seed-and-test-data.md#凭据与部署)）。

## 试迁移（至少两次）

1. 在独立环境中按激活顺序导入：主数据与任职 → 期初库存与成本、应收应付与银行、固定资产、假期与薪资累计 → 期初总账与信用的期初应收占用 → 未完成单据、期初合同与项目加载 → 库存与信用的期初分支全部成功 → 激活。期初业务类型不产生总账分录，总账只由期初凭证承接。
2. 每个批次：校验报告无错误（或按声明跳过）→ 确认 → 写入 → 对账门槛通过 → 激活。不通过的批次保持“已加载”，修正源数据后重来，或丢弃。
3. 记录每次的耗时、失败与差异；最后一次与正式切换使用同一流程。

## 对账与签字

| 对账 | 两侧 |
| --- | --- |
| 主数据 | 客户、供应商、产品、员工的数量 |
| 库存 | 按仓库的数量与金额 |
| 应收应付 | 账龄 |
| 银行 | 各账户余额与未达账项 |
| 固定资产 | 原值与累计折旧 |
| 总账 | 试算平衡；控制科目等于子账 |
| 未完成 | 订单、合同的剩余量 |

差异逐项解释或修正；客户负责人按对账清单签字，签字记录进入上线档案。

## 正式切换

1. 冻结旧系统（切点前）。
2. 差额迁移：冻结之后的补录以期初调整进入，在对账中单独列出。
3. 按顺序激活全部批次。
4. 抽样核对。
5. 开放；期初业务类型关闭，此后的调整走正常更正流程。

## 退回

- 激活之前发现问题：丢弃批次（先取消已建的期初分支；已写入的行与来源身份登记一并删除）或整库重建（推进部署恢复代次，协议 14），不影响旧系统。
- 激活并开放之后：不退回，按更正流程处理。
