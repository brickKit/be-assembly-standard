# 文档标准

## 1. 适用范围与效力

本文档规定本仓库文档该如何组织、何时拆分、如何互相指路、以及随时间如何演进。它管到项目级的规范文档（`AGENTS.md`、`docs/standards/*.md` 系列），并给组件级文档（日常由 `00-master-guide.md` 的 SOP-D 管）补上一层跨文档的判断标准——它不取代 SOP-D 的四份文档清单，只补 SOP-D 没覆盖的判断：一份文档什么时候该拆、体量增长到什么程度算出问题、一组文档之间该怎么互相指路。

主要读者：在本仓库做开发工作的 AI 助手，不论能力档位高低——把"效果较弱或投入算力较少的模型"当作本文档的写作基准，而不是例外情况。次要读者：人类维护者，阅读任何双语文档时看它在 `docs/zh/` 下的对照版（见 §6）。

冲突优先级与 `AGENTS.md` 一致：设计书 > 总纲 > 阶段计划 > `AGENTS.md`。本文档和 `00-master-guide.md` 处在同一层级。

## 2. 八条规则

### 2.1 现状与历史叙事永远分离

"当前状态"这类章节回答的是"现在什么是真的"——当前版本号、当前阶段、当前待解决的问题。它绝不能演变成"事情是怎么一步步走到这里的"这种编年记录。历史叙事——发生过什么、为什么、学到了什么——属于编年体文档（阶段计划、复盘、踩坑记录），没有人会去那里查"现在是什么状态"。

**违反症状**：一个"当前状态"表格单元格每次会话都在长，把今天的事实和上个月的调试故事混在一起，直到查"X 现在是什么版本"都得读完一整段多页的文字。

### 2.2 单个格子/段落里不许有追加式内容

任何按累积方式增长的内容——每次会话加一条、每个任务加一条、每个组件加一条——都需要自己独立可寻址的位置：一份专门的文件、一行一条的表格、或一个编号列表。它绝不能活在一个表格单元格里、或一段没有内部锚点的连续大段文字里。

**症状**：一个曾经只有一句话的表格单元格，现在变成了几千字节的无结构散文；没有人能不读完前面所有内容就跳到"关于组件 X 的那部分"。

### 2.3 按"最小化被迫多读"的轴线拆分文档

当一段内容可能同时属于多份文档时，不要按表面主题相似度去拆（"这两份都提到了测试"）。要按这条轴线拆：做任务 A 的人只需要读文档 A，做任务 B 的人只需要读文档 B——A、B 两边都真正需要的内容，放在它天然该归属的那一份文档里存一份，而不是复制一份，也不是逼着人多读一份。

**怎么用**：拆之前先列出真正会去查每份候选文档的任务有哪些。如果大多数任务两份都要查，那它们还不是真正意义上的两份文档。

### 2.4 路由表用关键词触发，不用叙事式问题描述

路由表的一行该写得接近读者真会敲进搜索框的那句话——"权限边界怎么测"，而不是"关于验证授权是否真的按预期限制访问的一些考量"。永远配一条明确的兜底规则：路由表里找不到匹配项，就查全部 `docs/standards/*.md` 文件——它们是一个封闭集合，永远有效的规范文档全在里面。

**违反症状**：路由表的一行读起来像这个问题历史的摘要，而不是一个查找键。

### 2.5 任何长期存在的参考文档都需要内部可寻址性

一份会被别处指着引用的文档（"见 §12.4"、"见决策 105"）必须有稳定的、编号的锚点——编号章节，或者一张有稳定行键的表格（比如决策表）。体量本身不是问题，没有锚点才是。一份 3000 行但章节编号严谨的文档，比一份 200 行但通篇不分段的文档更好导航。

### 2.6 冗余是刻意的、有边界的选择

极少数会被悄悄违反、又极难察觉的规则——代码看起来完全正确、测试也能过，而这个 bug 只会以一种很难联想回这条规则的方式暴露出来——值得直接复制进常驻加载的入口文件，即便代价是在别处也有一份更详细的记录。这不是"不惜一切代价避免冗余"，而是"只为极少数漏掉代价很大又很难发现的规则，刻意冗余一份"。

### 2.7 经常需要一起用到的文档必须显式互相指路

绝不要指望 AI 自己推断出"这里应该还有第二份文档，而且相关"。如果任务 X 通常需要文档 A 和文档 B 两者，A 就必须说明这一点并指向 B，反过来也一样。

### 2.8 "一份文档一个任务"自检

每份文档都要能一句话回答：这份文档回答什么问题，给谁看？如果一份文档想同时服务两种不同的问题或两种不同的读者——比如"这里记录发生过什么"和"这里是当前的规范"——就该按 §2.3 的轴线判据把它拆开。

## 3. 什么时候该把一份文档拆成独立文件

三条同时成立就拆：

1. 内容已经多到留在原处会遮蔽父文档自己的主要用途（父文档开始过不了 §2.8 的自检）。
2. 这段内容回答的是一个跟父文档真正不同的问题——不只是相关主题（§2.3）。
3. 拆分不会逼着日常任务同时读旧文档和新文档（把 §2.3 的轴线判据用在这次拆分本身上）。

三条都成立就立刻拆。一份规范性的标准文档描述的是当前最佳实践，不是历史记录——可以随意重写。这和 `04-testing-standard.md`、`05-data-construction-standard.md` 当初从 `00-master-guide.md` 里拆出来时用的是同一条规则。

## 4. 组件文档要同时服务两种读者

每一份组件级文档——本节管的那四份：`docs/design/<仓库名>.md`、`README.md`、`docs/手册.md`、`AGENTS.md`+`CLAUDE.md`——定稿前都要对着两种不同的读者过一遍：

1. **正在开发或修改这个组件的人**——需要精确、当下有效、可操作的细节：契约是什么、坑在哪、测试怎么跑。
2. **想通过读这一个组件来理解整个项目的人（人类或 AI）**——需要足够自成一体的上下文，能看懂这个组件为什么存在、依赖什么、在整体里处于什么位置，而不需要先读完其他每一个组件的文档。

写或改一份组件文档时，要明确对着这两个角度都过一遍。只服务读者 1 的文档读起来像一份没有上下文的变更日志；只服务读者 2 的文档又会含糊到没法真正拿来开发。

这四份文档不是收尾工作，是开发流程里的四个具体步骤：设计文档在开工之前写；README 和 AI 助手导读在搭骨架时写；手册随实现同步长出来。下面 §4.1~§4.4 是每一份具体到"填什么空"的模板；§4.5 是检查这四份结构是否齐全的机械门禁。

### 4.1 设计文档（`docs/design/<仓库名>.md`）——装配仓库里，开工前写

一个组件动手之前必须先有它。**没有它就开工，等于把设计决策直接写进代码，半年后没人知道为什么。**

它必须回答这九个问题：

| # | 问题 |
|---|---|
| 1 | **边界**：什么归这个组件、什么明确不归它——写出"不归我"的那几条，比写"归我"的更有用。另外：本组件要不要行级数据权限？要 → 列出维度与落在哪些表；不要 → 明确写清理由。 |
| 2 | **拥有的数据**：表清单、哪些分区、分区键与粒度、哪些是终态。 |
| 3 | **契约面**：gRPC rpc 清单（必含批量查询）、对外 REST 路径、哪些接口要幂等键、哪些要状态查询接口。每条 REST 路径要标注它的权限键。 |
| 4 | **事件**：发布哪些、消费哪些，每个是核心交易事件还是旁路分析事件。 |
| 5 | **依赖**：强依赖谁（同步调用）、弱依赖谁（可选）——同样重要的是，**为什么明确不依赖某个读者可能以为它会依赖的东西**。 |
| 6 | **在系统同步调用图里的位置**：加上这条依赖会不会引入环、有没有违反你的平台强制的跨域边界规则。 |
| 7 | **分区与归档策略**：热数据是什么、多久归档、终态列表。 |
| 8 | **参考实现**：完整模板见参考实现标准——看了哪个项目的哪个模块、借鉴了什么、许可证、用法分类，以及读完之后有没有发现"该拆成槽位族"的分歧（这一项必须在开工前就填，不能事后补）。 |
| 9 | **待决问题**：现在确实拿不准、留给实现阶段或下一个阶段回答的。 |

⚠️ **它随开发进度修订，不是写完就冻结。** 实现过程中发现设计不对，**先改这份**，再改代码——顺序反了，这份文档一周内就会失真，之后就没人再看它了。

### 4.2 README（组件仓库根目录）——搭骨架时写

给"要不要装它、怎么装"的人看。固定七节，不多不少：

```markdown
# <仓库名> · <名称>

一句话说清它是什么。

## 它能做什么
功能清单，每条一行。写用户视角的能力，不写实现细节。

## 需要哪些基础资源
| 资源 | 形态 | 为什么需要 | 怎么起 |
（列出这个组件需要的每一项基础资源，以及怎么把它启动起来。）

## 怎么起来
### 作为完整装配的一部分（正常路径）
### 单独跑（开发调试）
两段各给可复制的完整命令，含前置条件与预期输出。

## 怎么用
最小可用示例：主协议一条请求，如果有次要协议再来一条。
完整 API 参考在 docs/手册.md。

## 配置项
| 环境变量 | 来自 | 默认 | 说明 |
⚠️ 平台注入的保留变量单独列一段，明确标注"由平台注入，不要手工设置"。

## 参考实现
| 项目 | 看的模块 | 借鉴了什么 | 许可证 | 用法 |
从设计文档的参考实现一节搬过来——包括那些"借鉴的是推理过程、不是代码"的情况。
半年后会有人问"这个算法哪来的"，AI 需要知道该去读哪个模块。

## 边界与禁令
把设计文档里"明确不归我"的那几条抄过来，加上这个组件特有的禁令。
```

### 4.3 手册（`docs/手册.md`）——随实现同步长出来

给"已经装了、要用它/要改它"的人看。固定六节：

```markdown
# <仓库名> 手册

## 1. 项目结构
目录树 + 每个目录一句话职责。

## 2. 功能详解
每个功能一小节：做什么 → 怎么调（完整请求/响应示例）→ 边界条件 →
失败时返回什么 → 与哪些组件/事件相关。
⚠️ 幂等接口要写清幂等键怎么构造；有状态查询接口的要写清什么时候该调它。

## 3. 完整契约清单
gRPC rpc 逐条、REST 路径逐条、事件逐条（发布的与消费的分开列）。
这是 contracts/ 的索引——那个目录才是真相源。

## 4. 数据模型
表清单、分区策略、哪些字段是摘要副本、归档规则。
⚠️ 不贴完整 DDL——那在 migrations/ 里，贴一份必然过期。

## 5. 开发
本地怎么跑测试、怎么改契约、怎么加一次迁移、每个 CI 门禁分别在守什么。

## 6. 排障
这个组件特有的故障与症状对照表。通用的部分指向项目级的排障参考。
```

### 4.4 `AGENTS.md` + `CLAUDE.md`（组件仓库根）——搭骨架时写骨架，定稿时校准

给 AI 助手看。遵守所有 AI 向文档都该遵守的两条硬规则：不许出现"如上所述"这类需要回头翻的引用（AI 可能只拿到文件片段）；每条禁令都要带上原因和它的可观察症状。

`CLAUDE.md` 只有一行 `@AGENTS.md`——有些工具只读 `CLAUDE.md` 不读 `AGENTS.md`，而 `AGENTS.md` 是好几个其他 AI 编程工具会自动读取的跨工具约定。两个文件都要放，内容只写一份。

`AGENTS.md` 固定六节：

```markdown
# <仓库名> · AI 助手导读

一句话：它是什么、在哪个域、什么角色。

## 身份证
| 项 | 值 |
组件 ID / 仓库名 / 端口 / schema+role / 语言 / 装配角色 / 阶段。
⚠️ 端口与 schema 名从项目的登记表里抄，不许自创——以后改一次要回头改所有依赖方。

## 边界
**先写"不归我"。** 这是半年后有人想往这里塞不该塞的东西时，唯一能拦住他的东西。
每条"不归我"都要写清归谁、为什么。

## 契约面与事件
rpc 清单 + 事件清单（发布的与消费的分开）。这是 contracts/ 的索引——那个目录才是真相源。
⚠️ 哪些接口不暴露到 REST、为什么。

## 依赖，以及为什么不依赖某某
三张小表：强依赖 / 弱依赖 / 明确不依赖。第三张才是真正带设计意图的那张。

## 这个组件特有的坑
| 不许 | 症状 | 出处 |
只写**这个组件**特有的。全项目通用的那份清单在装配仓库根 AGENTS.md 里，别抄过来——
抄一份就是承诺维护两份，而过期的那份会让 AI 自信地写错。

## 改代码前的自查
三到五条，针对这个组件。例如：
- 我加的这条依赖，会不会让同步调用图成环？
- 我这个查询是不是跨了不该跨的 schema 边界？
```

⚠️ **"这个组件特有的坑"一节绝不能抄通用禁令。** 装配仓库根的 `AGENTS.md` 已经载了那份项目级清单，组件文档里再抄一遍，就是两份会分叉的副本。这一节只写"只有做这个具体组件时才会踩到"的坑。

### 4.5 四份文档的统一门禁

在组件的完整验收流程里加一条门禁，只做机械检查（内容质量是 review 的事，不是门禁的事）：

| 检查 | 判据 |
|---|---|
| 四份都在 | 设计文档（在装配仓库）、README、手册、`AGENTS.md`、`CLAUDE.md` |
| README 七节齐全 | 按标题名匹配 |
| 手册六节齐全 | 同上 |
| 设计文档九问齐全 | 同上 |
| `AGENTS.md` 六节齐全 | 同上 |
| `CLAUDE.md` 指向 `AGENTS.md` | 含 `@AGENTS.md` |
| **`AGENTS.md` 里没有回头引用类语言** | 不含"如上所述"/"见上文"/"前面提到过"这类表述 |
| 没有占位符 | 全文不含 `TBD`/`TODO`/"待补"字样 |

## 5. 默认动作是修改/扩充，不是重构

默认动作永远是往现有文档里加内容或改内容。把一份文档拆成新文件（§3）、给一份长期存在的文件改名、或者跨多份文档重新组织引用关系——这些事 AI 可以主动提议，但只在 §3 的判据明确成立、或者发现了真实的结构性问题时才提（就像促成本文档诞生的那种问题：一份"每次都自动加载"的文件悄悄长过了它自己声明的设计初衷）。提给人类做决定，不要单方面执行波及面很广的重构。

## 6. 语言策略

分两档：

- **第一档——英文为主，配中文镜像。** 默认判据是：正常一次会话真的会通读、读得快慢有意义的文档：`AGENTS.md`、本文档、`02-reference-implementation-standard.md`、`03-ai-development-standard.md`、`04-testing-standard.md`、`05-data-construction-standard.md`、`00-master-guide.md`。文件名和内容都是英文——一份文档一旦定为第一档，文件名要跟着内容一起转，不存在"文件名永远保持中文、内容却是英文"这种长期例外。（`04-testing-standard.md` 和 `05-data-construction-standard.md` 曾经短暂处于"内容已经译成英文、文件名还没跟上"的过渡态——那是一项待办，不是稳定的最终状态；改名补上这个缺口的代价是全项目扫一遍引用，这个代价足够低，以后需要时随时可以再做一次。这一整套后来又重新编号过一次，从最初按拆分顺序编号，改成现在这套按阅读优先级编号——见 §7，顺序对应组件真实开工的流程：先写文档（SOP-D）→再查参考（SOP-R）→模式/会话判据（SOP-P）贯穿实现全程→再是测试驱动的实现本身→种子数据放最后。）
  ⚠️ **`00-master-guide.md` 是唯一一份不满足"通读"这条判据、却仍然在第一档的文档。** 它自己的 §W-4 依然写着不需要通读全文——这条没有变，按上面这条判据的字面意思它本该留在第二档。它转第一档是项目维护者明确拍板的：这是全项目体量最大、修改最频繁的文档，维持中英双份镜像的成本相当可观，但维护者判断这个成本值得付出，纯粹是为了让 AI 读它、改它更舒适，不取决于按节查阅这件事本身能省下多少时间。还有一条次要但真实的一致性理由：其余每一份第一档标准都会按名字和节号引用它（比如"总纲 §4 SOP-R 的 R-2 表"），保留中文会让这些引用点上凭空多一次语言切换，转英文正好去掉这个摩擦。这里的教训可以推广：**"反正只是按节查阅"不该单独构成拒绝转换的理由——那只是需要如实披露的一个因素，不是一票否决**，只要真正承担同步成本的人已经说了这个成本可以接受。
- **第二档——只保留中文，不做转换。** 按章节号/决策编号查阅、不通读、且没有像上面那样被明确拍板破例的文档——设计书是其中最典型的一份——外加阶段计划、复盘、踩坑记录、组件级文档、运维/维护手册。一份按章节查阅的大型参考文档默认归第二档，不看它名义上属于哪个系列，除非像上面那样被明确拉进第一档。第二档里的历史记录类文档还有一条额外要求：只能搬地方，不能重写内容。

**中文镜像约定**：AI 自己日常工作的那棵目录树保持纯英文——不在它每天要读的文档旁边混进中文文件。每一份第一档文档的中文版都放在 `docs/zh/` 下，路径和它相对仓库根目录的路径完全一致，只是根从仓库根目录换成了 `docs/zh/`。所以 `AGENTS.md` 的中文版是 `docs/zh/AGENTS.md`，`docs/standards/04-testing-standard.md` 的中文版是 `docs/zh/standards/04-testing-standard.md`。内容要和英文原版严格保持一致——第一档文档的每一处改动，都要在同一次提交里把同样的改动带进它在 `docs/zh/` 下的镜像。`CLAUDE.md` 不需要镜像（它只是一行 `@AGENTS.md` 引用，本身没有内容）。

⚠️ **"严格保持一致"指的是文字内容，不是每个相对链接的字面字节。** 镜像版本在 `docs/zh/` 下比英文原版多套了一层或几层目录，所以任何相对 markdown 链接（`](docs/...)`、`](../...)`）都要相应调整 `../` 的层数才能真正从镜像文件所在的位置解析到目标——原样复制文件会悄悄弄断它包含的每一个相对链接。每次更新镜像文件后要验证这一点：挑几个链接，确认它解析出来的路径真的存在。
