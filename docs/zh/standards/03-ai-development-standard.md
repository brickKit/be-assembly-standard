# AI 驱动开发标准

由 AI 来写实现，它的失败模式和成本结构都跟人类工程师不一样。它每次会话都是从零开始、没有上一次会话的记忆，上下文有限；它没法"这个文件以后再看，我大概记得怎么回事"；重写一整个文件对它来说甚至可能比小心翼翼地在已经打了三层补丁的基础上再叠第四层更便宜——这跟人类工程师的直觉正好相反。这份文档里的每一条判断都不是针对某个特定业务领域的，它们全都直接来自这个差异，适用于任何一个由 AI 主要负责写代码、人负责审查的代码库。

## 一、什么时候用设计模式

设计模式从不强制，但适合的地方必须用。判据只有一条：

> **这样做是让这段逻辑更容易被读懂和扩展，还是更难？**

**"谁需要觉得容易"这件事已经定了：按 AI 能不能快速看懂来判。** 人类审查者默认已经有设计模式的基础知识——这不是瓶颈所在。真正的瓶颈在 AI：它每次会话都是全新的、上下文有限、看不到运行时状态，也不会"过一阵子慢慢想起来那个文件在哪"。

所以"更容易"有一个具体的、可测的定义：

> **一次全新会话的 AI，能不能在只读少量文件的情况下，把一条新规则加对？**

### 1.1 什么帮 AI，什么害 AI

| 帮 AI | 为什么 |
|---|---|
| **小文件、单一职责** | AI 每次改一个文件都要把它整个读进上下文。600 行的文件改 3 行，成本是读 600 行；60 行的文件改 3 行，成本是读 60 行。 |
| **注册表集中在一处** | 一个文件里列全所有规则，AI 一眼看到**全集**。散在各处它只能靠搜索猜，而猜漏一个就是漏改一个。 |
| **显式优于隐式** | AI 推不出运行时魔法。反射注册、装饰器自动发现、约定命名扫描——这些人能靠积累的经验补上，AI 会直接看漏。 |
| **一种情况一个文件，文件名 = 那种情况** | 像 `rule_volume_discount.go` 这样的名字，不用读内容就告诉 AI 该改哪个文件。 |
| **状态迁移集中成一张表** | AI 最常见的错误就是"某个入口忘了判前置状态"。把每条迁移边集中声明在一处，这类错误就变得结构性地不可能发生。 |

| 害 AI | 为什么 |
|---|---|
| **深继承链 / 多层抽象基类** | 要读懂一个方法得跳好几个文件，AI 跳到第三层就开始猜。 |
| **元编程、反射、动态派发** | AI 无法静态推断实际执行的是哪段代码。 |
| **为"以后可能要扩展"提前抽象** | 多一层间接就是多一个要跳转的文件，而今天的收益是零。 |
| **一个模式铺开到多个包** | AI 拿不到全貌，很容易在 A 包改完却漏了 B 包该对应改的地方。 |

⚠️ **最后一条尤其要注意**：设计模式的收益来自"把一段长逻辑变成结构清晰的几个短文件"，**不是**"把逻辑摊到整个代码库"。模式应当收在一个包里。

### 1.2 该用模式的四个信号

出现任意一个，就值得停下来考虑：

| 信号 | 症状 | 用什么 |
|---|---|---|
| **一个 `switch`/`if-elif` 链已经超过 5 个分支，而且还在长** | 加一种新情况要改一个已经很长的函数，改的时候容易碰到不该碰的分支 | **策略（Strategy）**：一种情况一个文件，注册进表 |
| **一个函数超过 150 行，或一个文件超过 600 行** | AI 每次改它都要把整个文件读进上下文；人每次改它都要先滚半天才找到位置 | 先按职责拆开，再看拆出来的部分像哪个模式 |
| **同一段流程要跑好几遍，每遍只有中间一两步不同** | 复制粘贴出三份，其中一份修了 bug，另两份没修 | **模板方法（Template Method）** 或 **责任链（Chain of Responsibility）** |
| **状态迁移的合法性判断散落在多处** | 某个入口漏判一个前置状态，数据进了不该进的状态，而且不报错 | **显式状态机**：每条迁移边集中声明在一处 |

### 1.3 不该用模式的三种情况

| 情况 | 为什么别用 |
|---|---|
| **简单资源上的纯 CRUD** | 直接写就是最清楚的形态。套一层抽象只是让读的人多翻一个文件。 |
| **只有两个分支，且看不见会长出第三个** | `if a {} else {}` 比一个策略接口+两个实现+一个注册表好懂得多。 |
| **为"以后可能要扩展"提前抽象** | 默认判据该是：拿不准就不拆。胶水成本是实打实的；"以后"往往不来。等第二个真实实现真的出现时再抽——那时你才知道该沿哪条线抽。对 AI 而言额外的代价是：每一层预先做的抽象，都是它必须跳转、却什么都学不到的文件。 |

⚠️ **最后这条最容易违反**，因为"给未来扩展留口子"听起来永远正确。判据是：**你现在能不能具体说出第二个实现是什么**。说不出来就先别抽。

### 1.4 用了模式之后的文件组织

模式的收益一半来自"一个长文件变成结构化的多个短文件"，所以落地时要真的拆开：

```
backend/internal/pricing/
├── pricing.go          # 接口 + 注册表 + 执行顺序。读这一个文件就知道有哪些规则
├── rule_base_price.go  # 一条规则一个文件
├── rule_customer_tier.go
├── rule_volume_discount.go
├── rule_promotion.go
└── pricing_test.go     # 每条规则一个测试 + 一个组合链的属性测试
```

**判断拆对了没有，用一个动作**：让一次**全新会话、对本项目零上下文**的 AI，去加一条新的折扣规则。

**拆对了的标准**：它只需要读 `pricing.go`（看接口和注册表）+ 随便一个 `rule_*.go`（看长什么样），然后新建一个文件、在注册表加一行。**读两个文件，改零个文件。**

**拆错了的症状**：它还得改别的规则文件（说明链的执行顺序或数据流没设计干净），或者要跳三层才找到接口定义（说明抽象层数过多，见 §1.1）。

## 二、一次工作会话该装多少

| 单位 | 大小 | 判据 |
|---|---|---|
| **一次会话** | 一个任务，或一个任务里的 2~4 个红绿循环 | 上下文用到一半就该收尾、提交、开新会话。留一半余量，是为了让下一次会话真的能读周围的代码，而不是只能读自己写过的东西。 |
| **一个红绿循环** | 一条测试 + 让它变绿的最小实现 | 三轮还不绿，说明**这一步太大了，切小**（见 §四）。 |
| **一次 commit** | 一个红绿循环 | 出错时能精确回滚到"上一个全绿状态"。 |

**一次新会话开始时，固定要读这几样**（多了浪费上下文，少了只能靠猜）：

1. 仓库根目录那份自动加载的 AI 助手导读（自动加载，不用手动读）
2. 当前这个工作单元自己的 AI 助手导读——它的身份、边界、这个单元特有的坑
3. 这个单元的设计文档——为什么这样设计
4. 当前阶段计划文件里**当前那一个任务**（不是整份文件）
5. 即将要改的那几个具体源文件

**不该读的**：完整的设计书（几千行）、完整的总纲、系统里跟当前工作无关的任何部分。需要查某条具体规则时，用根目录 AI 助手导读里的路由表去定位到具体那一节——不要出于猜测去通读整份源文档。

## 三、人到底该审查什么

在一个主要由 AI 写代码的大代码库里，没有人能逐行读完每一处实现。审查时间应该集中在**不可逆的地方，以及门禁本身守不住的地方**：

| # | 审什么 | 为什么是这个而不是别的 |
|---|---|---|
| 1 | **契约** | **最不可逆的一样。** 契约一旦有了消费者，就只能向后兼容地追加。这里出错，代价是所有依赖方一起承担。 |
| 2 | **迁移** | **第二不可逆的一样。** 分区键、主键、索引在建表那一刻就定死了；数据进去之后再改，本身就是一次迁移。 |
| 3 | **业务规则测试里的不变量清单** | 只看"这个逻辑该有的不变量是不是都列出来了"，不看具体怎么实现的。**门禁永远抓不住一条漏掉的不变量**，因为门禁只会去跑已经写下来的那些测试。 |
| 4 | **设计文档的边界一节和依赖一节** | 边界画错、或者多建了一条本不该有的同步依赖边，是唯一能污染整张架构图的错误。 |
| 5 | **门禁的输出** | 不用读代码。一条红的门禁输出会直接告诉你该去看哪里。 |

**不需要审的**：业务代码逐行、普通单元测试、构建脚本、Dockerfile。这些由门禁和上面说的测试覆盖；真出了问题，会在门禁或已有测试里变红。

## 四、允许整体重写，不只是增量打补丁

持续开发的过程里，某段逻辑会走到这样一种状态：因为当时的判断没扛住时间考验，或者经过几轮迭代方向本身跑偏了——诚实的解法不是"补一下错的那一小块"。**AI 写代码的成本结构跟人完全不同**——重写一整个文件对 AI 来说，可能真的比在脑子里重建三层历史、再小心翼翼在上面叠第四层更便宜。没必要死守"能不动就不动"——那是只对人类工程师成立的经验法则。

**什么时候该整体重写而不是再打一次补丁：**

- 同一块逻辑已经被朝不同方向打了好几次补丁，现在哪怕只改一行，都得先在脑子里把好几轮历史叠好才搞得清当前状态。
- 问题不是一个 bug，而是意识到**当时那个设计判断本身就是错的**。继续在这个地基上加东西只会让偏差越滚越大；重写迟早要发生，现在做比以后在更多依赖方之上再做要便宜。
- **种子/演示类数据的重写门槛可以更松**：这类内容本来就是假数据，没有"迁移历史记录"的负担，重写成本约等于"删了重建"。如果现状不是真正想要的样子，一次性重新设计整个覆盖范围，比一条条零散地加数据更快也更干净。

**流程：**

1. 动手前，把要重写的文件复制一份到本地临时位置（不进版本控制），纯粹作为写新版本时手边的对照——不是为了留档（版本控制本来就留着每一个旧版本，需要时一条命令就能查到）。
2. 重写产出**单独一次 commit**，message 里说清楚**为什么**重写，而不只是改了什么——这样几个月后才能准确查到"这段逻辑什么时候被推倒重来过、当时是为了什么"。
3. 重写之后照常跑一遍这个组件完整的验收门禁。**门槛不因为"是重写不是打补丁"而降低**——重写引入新 bug 的风险不比增量修改低，改动面通常还更大，这是该多验证一遍的理由，不是少验证的理由。
4. 验证通过、提交完成后，删掉临时对照副本——它的使命结束了，真正的历史记录已经在版本控制里了。
5. 如果这次重写是因为意识到之前的方向错了，值得把这一点记录到一个持久的地方：技术层面"看起来对、实际错"的教训记进踩坑记录；设计判断本身需要更新的，记进该组件自己的设计文档——不然下一个人读到旧文档，会照着它把同一个错误方向重新做一遍。
