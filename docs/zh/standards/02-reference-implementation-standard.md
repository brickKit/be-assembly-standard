# 参考实现标准

设计业务逻辑时，几乎总该先去看成熟的现实软件是怎么解决同一个问题的。这不是谦虚——一个经过几十年真实部署打磨出来的领域模型，早就吸收了从零设计几乎必然漏掉的边界情形，而这些漏掉的边界情形，要等到客户上线三个月后才会暴露。

这份文档管的是**怎么负责任地参考一个现实实现**——操作顺序、该记录什么、过程中唯一值得留意的一个信号。它刻意保持跟具体业务领域无关：「哪个域该看哪个现实项目」是另一张、项目专属的表（见总纲 SOP-R 的 §R-2），不属于这份标准。

## 一、三步法（顺序不能反）

| 步骤 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **1a. 先自己设计一版** | 在打开任何参考资料之前，先按自己项目的约束勾出一版设计 | 带着自己的方案去读别人的实现，才看得出差别在哪；空着脑袋去读只会照搬 |
| **1b. 理不清的地方才去看参考实现怎么做** | 领域模型怎么切、状态机有哪些状态与合法迁移边、哪些字段是必须的、边界情形怎么处理 | 这一步是查资料，不是抄作业 |
| **1c. 回来自己想清楚再写** | 把学到的东西对照自己项目的真实约束重新消化 | 参考项目的技术栈和组件边界通常跟你的完全不是一回事（语言不同、进程/数据库拓扑也不同）。照搬既不可能也不正确——目的从来不是搬运代码，只是借鉴推理过程 |

**闭源产品同样值得参考。** 看不到源码，但能观察一个成熟产品**在真实世界里怎么被使用**：哪些功能客户天天用、哪些从来没人点、哪些流程被吐槽了二十年。这类信息往往比源码更能帮你判断"这块该不该独立成一个可单独交付的东西"（这个判断由客户愿不愿意单独为它付钱来驱动）——而这个判断比任何实现细节都更早、也更重要。

**关于许可证**（一小段，不必紧张）：为了借鉴**推理过程**去参考一个实现，然后独立地（哪怕换一种语言）重新实现一遍，这不构成衍生作品。真正要避免的只有一件事——打开对方的源文件、逐行照抄或机械转写。走上面这个三步法就不会碰到这条线。如果确实需要直接使用代码，仅限许可证宽松的项目（Apache-2.0 / MIT / BSD），并在 `NOTICE` 文件里保留原始声明。

## 二、参考过什么该怎么记录

在开工之前记下来，作为该组件设计文档的一部分（具体落在哪一节，见文档标准里的模板）：

```markdown
## 参考实现

| 项目 | 版本/commit | 看的模块 | 借鉴了什么 | 许可证（已复核） | 用法 |
|---|---|---|---|---|---|
| Odoo | 17.0 | `addons/product/models/product_uom.py` | 计量单位换算因子的表设计与舍入策略；它专门处理了哪些边界情形 | LGPL-3 | 借鉴逻辑 |
| Apache OFBiz | 18.12 | `applications/product/entitydef/entitymodel.xml` | Product/UoM 实体关系的完整度 | Apache-2.0 | 借鉴逻辑 |
| 某闭源产品 | —— | —— | 多计量单位换算在真实场景里怎么用：哪几种换算天天用、哪些从来没人用 | 闭源 | 借鉴实际应用 |

**明确没有参考的**：（写出来，避免下一个人以为漏查了）

**要避免的**：
- [写清楚在参考项目里发现的具体反面模式，以及为什么本项目不照搬]
```

**"用法"列的三个合法值：**

| 值 | 含义 |
|---|---|
| 借鉴逻辑 | 读了它的实现，理解了它为什么这么做，然后自己独立设计并实现。**绝大多数行都是这一栏** |
| 借鉴实际应用 | 闭源产品，或者只看了文档/使用体验，没看源码 |
| 已复制代码 | 真的直接用了它的代码。**只能出现在 Apache-2.0 / MIT / BSD 项目上**，且 `NOTICE` 里必须有原始声明，这里必须写清哪个文件的哪一段 |

## 三、对照参考实现时值得留意的一种常见通病

参考多个同领域的成熟实现时，会浮现一个值得明确点名的规律：多个真实系统共享同一批结构性弱点，往往是因为它们继承自同一套架构传统更早期的形态。在阅读时认出这一点，正是做这件事本身的意义——这是一个刻意不重蹈覆辙的机会。

| 弱点 | 该怎么设计规避 |
|---|---|
| 所有模块共享同一个进程和同一个数据库，跨模块表关联成了常态，本该有的边界只是一条"软"约束，天天被突破 | 独立进程 + 独立 schema，靠真实的访问控制（不是约定）强制成一堵物理墙 |
| 定制靠运行时打补丁或往基础实现上挂钩子，每次升级都可能打断每一处定制 | 一份干净的、独立版本管理的 Fork + 锁死的契约，让升级变成一次显式的、刻意的合并——而不是一次会跟被打过补丁的代码悄悄互相影响的自动合并 |
| 元数据驱动一切（动态字段、通用的"单据类型"抽象），没有任何静态类型能让 AI 或 IDE 在运行前就抓到一个错误 | 契约先行（用 schema 语言而不是数据库表描述契约）+ 强类型的实现语言 |
| 报表直接查询实时交易表，一次繁重的分析查询会拖垮核心交易系统 | 报表必须走汇总表或专门的分析组件，绝不走实时交易路径 |
| 表无限增长，系统最终被自己的历史数据拖垮 | 每一张会增长的表从第一天起就按分区设计，配一条明确的归档策略 |

## 四、识别"槽位族"信号

对照参考资料时会反复遇到一种具体情形：**同一个功能，几个成熟系统给出的实现真的不一样——关键在于这个限定词——而且每一种都合理，只是适配的客户画像不同。**

**这不是"要不要做成可配置"的问题。这是一个信号，说明这个功能需要一个可插拔的实现族，而不是带一个开关的单一实现。**

判断完全取决于那个限定词——"每一种都合理"：

- 如果读下来发现其中一种**明显更好** → 那就是你的默认实现。不需要族。
- 如果好几种都**各有道理、只是服务的客户画像不同** → 这里存在真实的、独立的市场需求，值得建一个正式的族。

举例说明（重点是判断方式本身，不是这几个具体案例）：

| 功能 | 现实中的分歧 | 结论 |
|---|---|---|
| 成本核算方法 | 移动加权平均 / FIFO / 标准成本+差异 / 分批实际成本——四种在不同行业各自正确，公司自己的会计师往往还会指定其中一种 | 需要可插拔族 |
| 仓库拣货策略 | 先到期先出 / FIFO / 就近库位 / 波次拣货 | 需要可插拔族 |
| 审批路由 | 组织层级逐级 / 金额分级 / 矩阵式 / 规则引擎驱动 | 需要可插拔族，但——取决于你的架构——这类业务逻辑可能必须落在业务侧组件而不是通用基础设施组件里；在把这当成纯技术决策之前，先确认你的平台有没有"基础设施组件不许含业务规则"这类禁令 |
| 单据编号规则 | 流水号 / 按年月分段 / 按组织+类型分段 | **不是**族——这是一个单一的配置项 |
| 核心主数据记录上有哪些字段 | 各家差别都只是"多几个字段、少几个字段" | **不是**族——那是定制/Fork 的事，不是架构问题 |

**认出这个信号之后该做什么（顺序不能反）：**

1. **先正式注册这个新族，再写任何实现**：起名、定义共享的"槽位"契约是什么、确认族里每个成员必须暴露**完全一致**的契约面、明确每个成员适配哪种客户画像、决定默认装哪一个。
2. 更新项目里用来追踪这类信息的中心登记表（端口/schema 册、组件总数、架构附录——只增不改，不许修改已有条目）。
3. **确认"能不能成为一个可插拔槽位"这条硬约束**：系统里不能有任何东西对它建依赖边。一旦有别的东西直接依赖它，它就不能是一个槽位——这种情况下正确的形态是"一个组件+内部策略"（见 AI 驱动开发标准的模式使用判据）或者干脆整仓 Fork。
4. 到这一步才写族里每个成员各自的设计与实现。

⚠️ **绝不许在一个组件里写 `if costingMethod == "fifo"` 这种分支去掩盖这个信号。** 那等于把多个客户真实不同的需求塞进同一份代码里，从此每个客户的需求都会牵制到其他客户——正是这套纪律想要防住的"牵一发而动全身"。**唯一的例外**：分歧小到只是几个分支，且看得见的未来不会长出第五种（判据见 AI 驱动开发标准里"什么时候不该用"的信号）。

这条纪律也是"客户可以基于最接近他需求的族成员做闭源二次开发"这件事能成立的物理前提：族越贴合第四步发现的真实分歧，客户 Fork 的起点就越接近他真正想要的东西，后续需要的定制工作也就越少。
