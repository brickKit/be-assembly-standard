# 有限表达、包含证明与完整查询

本页给出授权中反复出现的三件事的具体形状与算法：

| 问题 | 谁在用 | 本页的回答 |
| --- | --- | --- |
| 一份授予的范围与条件能写成什么样 | 全部 | 一套有限的段表达：每个已声明维度恰好一个原子，原子只有少数几种形式 |
| 某人能授出、能分享、能委托的，是否真的包含在他的上限里 | [管理](04-authorization-administration-and-appointments.md)、[共享与委托](05-sharing-delegation-and-impersonation.md) | 逐维比较的包含证明，必要时沿一个维度拆分；给出见证，或具体失败的维度 |
| 列表怎样一次查出完整、正确的集合，每行的字段怎样定 | [求值](01-authorization-evaluation.md)、[共同接口](06-security-contracts-and-capabilities.md)的 `PlanAuthorizedQuery` | 每段编译成一个 SQL 谓词，整体取 OR；同一组谓词同时给出“命中了哪些段”，字段按命中段取并集 |

三件事共用同一套表达，这是本页的核心：只要表达足够受限，包含、求交与查询编译都能用简单、可验证的算法完成，不需要通用的策略蕴含求解器。

术语：**段**（segment）是一份授予展开后、绑定一个资源类型与一个操作的执行视图；**原子**是段在某一个维度上的条件；**上限**是管理职责、共享治理或委托来源能授出的最大段集合。

## 方案比较

| 路线 | 判断 |
| --- | --- |
| **采用**：段 = 每维一个原子的合取（乘积集合），原子种类有限，且每种在求交下封闭 | 包含可以逐维判断，求交可以逐维计算，查询可以逐段编译；AI 与三种语言都能各自实现，并用同一组向量核对。代价：客户确实需要更复杂的条件时，要新增原子种类或走专项适配 |
| 通用策略语言（Rego、Cedar 等）加部分求值 | 表达力强；但“A 是否包含于 B”一般不可判定或代价无界，部分求值剩下的条件也未必能翻译成 SQL。适合作为声明了有限子集的提供方，不作为共同表达 |
| 各维度分别汇总 | 结构最简单，但会把两份授予的维度交叉组合，已证实会扩大访问（见[为什么不能按维度压平](#为什么不能按维度压平)）。不采用 |

采用路线的限制是有意的：标准表达覆盖知识库 D3 列出的常见范围种类与 D6 的参数化条件。超出时先补规范、原子种类与验收，再给客户启用；不能为了接入一条复杂规则，让整个求值退化成“不能证明就放行”。

## 有限表达

### 资源先声明维度

每个资源类型由属主组件声明自己的授权维度。段只能引用已声明的维度；资源声明的修订进入 `DefinitionRef`（[安全 06](06-security-contracts-and-capabilities.md#共同标识与封装)）。

| 维度种类 | 例子 | 记录上的事实 |
| --- | --- | --- |
| 值集合 | 法人、仓库、渠道、品牌、单据状态 | 一个稳定的值；已知 null 与未取得要能区分 |
| 组织树 | 部门 | 一条路径，按路径段比较；没有部门时为 null |
| 主体 | 负责人、创建人（资源声明是哪种当事人） | 一个平台主体 ID |
| 关系 | 项目成员、汇报线、团队 | 由关系属主提供的成员关系；本页只规定接口的形状 |
| 记录 | 逐条共享 | 记录的稳定 ID |
| 金额区间 | 单据金额、信用额度 | 十进制金额 + 币种（或统一的计量依据），作为一个复合事实 |

### 原子只有这些形式

| 维度种类 | 允许的原子 | 不允许的 |
| --- | --- | --- |
| 值集合 | `ALL`；`IN {v1…vn}`（可以为空集） | 通配、前缀、排除（“除了某某”只能在管理界面编译成 `IN`，不进入执行视图） |
| 组织树 | `ALL`；若干项 `EXACT p` 或 `SUBTREE p` 的并 | 按字符串前缀匹配；把空路径当作根 |
| 主体 | `ALL`；`IN {主体}`；`SELF`（求值前实例化，见下节） | 按姓名、邮箱、登录名匹配 |
| 关系 | `ALL`；`RELATED(关系类型, 锚点, 最大深度)` | 未声明的关系类型；没有深度上限的递归 |
| 记录 | `ALL`；`IN {记录 ID}` | 按 ID 的规律推断 |
| 金额区间 | `ALL`；`[lo, hi]`，两端各自开或闭、可以无界，绑定一个币种 | 无币种的比较；浮点数；跨币种的隐式换算 |

每种原子在求交下封闭：两个 `IN` 的交还是 `IN`；两个子树的交是较深的那个子树或空；`EXACT` 与 `SUBTREE` 的交是落在子树里的那些 `EXACT`；两个同币种区间的交还是区间，不同币种的交为空。所以委托派生、扮演求交与规范化都不会产生表达不了的结果。

跨币种需要比较时，由业务属主声明一个派生事实（例如按记账汇率换算的本位币金额，写明汇率依据与取值时点），把它当作另一个金额维度；授权层不自行换算。

### 段的规范化

一份授予在进入执行视图前按下面的顺序规范化。规范化的结果是确定的：同一输入在三种语言中得到同一组段与同一个摘要（摘要编码见[安全 09a 的规范编码与摘要](09a-encoding-and-records.md#规范编码与摘要)）。

1. **每个已声明的维度都必须显式出现。**缺维度是声明错误，不是 `ALL`；资源新增维度后，旧授予在客户确认如何补齐之前，不能用于新版本（安全 06：新的限制须经语义识别）。
2. **同一维度的多个原子先求交**，合成一个原子。
3. **不可满足的段从执行视图删除**：显式空集、求交为空、空区间。管理视图保留并提示，因为它通常意味着配置错误。
4. **授予内的“或”展开成多段**（析取范式）：`法人甲 AND 仓库一 AND (本人 OR 甲部门)` 展开为两段，每段都保留法人甲与仓库一。展开数受预算限制。
5. **范围、条件、有效期与资格绑定都相同的段合并**，字段取并集。这一步不改变语义：两段覆盖同一组记录，任何一条记录要么同时命中两段，要么都不命中。资格绑定不同的段不合并，因为需要选定任职的动作只能使用与所选任职相容的段。
6. **被包含的段可以删除**（可选的优化）：若 s1 ⊆ s2，两者资格绑定相同，且 s1 的读、写字段都包含在 s2 中，删掉 s1；解释仍指向原授予。执行视图随来源变化整体重算，删除不影响撤销某一份来源。

### 预算（起始值，待实测）

| 预算 | 起始值 | 超出时 |
| --- | --- | --- |
| 一个主体在一个资源类型、一个操作上规范化后的段数 | 64 | 授予变更时拒绝或提示合并；请求时列表不可完成，单对象仍可以逐段求值 |
| 一个 `IN` 原子的值个数 | 1,000 | 授予时拒绝，建议改用组织树或新增维度 |
| 一个组织树原子的项数 | 64 | 授予时拒绝，建议合并成上层子树或新增维度 |
| 一份授予展开的段数 | 8 | 授予时拒绝 |
| 委托链派生的段数 | 64 | 该委托路径不可用，不截断 |
| 一次变更计划的原子比较次数 | 100,000 | 计划拒绝或要求分批，不跳过检查 |
| 关系或图提供方一次返回的完整候选集 | 10,000 个 ID | 列表不可完成或转有界异步，不截断后冒充完整 |

预算在**授予时**优先检查，让超限尽量在管理界面暴露，而不是在用户查询时变成不可完成。这些数字是实验的起点，按代表部署实验调整；默认的小公司组合远低于它们。

## 主体相对的原子

`SELF` 与“本人部门”在不同的人身上指不同的东西，所以必须先实例化成具体的值，才能求值、比较或编译。

| 情形 | `SELF` 指谁 | “本人部门”从哪来 |
| --- | --- | --- |
| 本人直接请求 | 实际操作者的平台主体 | 授予绑定的那份任职实例的部门 |
| 个人委托下代办 | **被代表主体（委托人）**，不是受托人 | 委托人来源授予绑定的任职实例 |
| 只读扮演 | 被查看主体 | 被查看主体相应授予绑定的任职实例 |
| 授出时做包含证明 | 候选授予的**受授人**，不是管理者 | 受授人候选绑定的任职实例 |

两条规则让这件事保持简单：

- **“本人部门”只能出现在绑定了任职实例的授予里。**按安全 04，任职的部门、法人或岗位变化会结束旧实例、生成新实例，所以一份授予绑定的部门在它的生命周期内不变。实例化后它就是一个固定的 `SUBTREE` 或 `EXACT`，包含证明与查询都按固定值处理。没有任职绑定的直接授予只能写具体的组织节点。
- **实例化的结果连同所用事实的修订一起记录**（任职实例与修订、主体 ID）。事实变化后不沿用旧的实例化结果；没有部门时实例化为空集（永不匹配），不扩展成全组织。

`SELF` 只指平台主体本身，不自动扩展到关联同一员工的其他账号；需要按人员覆盖多个账号的业务，用声明的关系维度表达。

## 单对象求值：三值逻辑

每个原子对一条记录给出三种结果之一：**成立**、**不成立**、**未知**（所需事实未取得、过期、来源不可信或水位不相容）。已知 null 对正向比较是“不成立”，不是“未知”。

段内按三值逻辑求与：任一原子不成立，段不成立；全部成立，段成立；其余为未知。段之间求或：任一段成立则成立；全部不成立则不成立；其余为未知。

| 汇总结果 | 含义 |
| --- | --- |
| 成立 | 允许；字段取**所有成立段**的字段并集，未知段的字段不参与 |
| 不成立 | 明确拒绝，按存在性保护对外表达 |
| 未知 | 无法证明，按保护处理，不当作拒绝后返回“没有数据” |

这与安全 01 的“局部未知的分支不贡献许可；已有独立完整的授予能证明时，只采用它已证明的字段”一致。字段因为未知段而没有给出时，对外仍是掩码，内部解释记录的原因是“未证明”，不是“无权”。

## 完整查询

### 编译

一个列表请求的完整集合是：请求的筛选 AND（段 1 的谓词 OR 段 2 的谓词 OR …）。每段的谓词是它各原子谓词的 AND。所有值都作为参数传入，SQL 文本只由声明过的列名与固定模板组成。

| 原子 | 关系型谓词（示意） | 下推条件 |
| --- | --- | --- |
| `ALL` | 省略 | — |
| `IN {…}` | `col = ANY($n)`；空集为 `FALSE` | 列在本组件的表上 |
| `EXACT p` | `dept = $n` | 同上 |
| `SUBTREE p` | `dept = $n OR dept LIKE $m ESCAPE`，`$m` 为转义后的 `p/%` | 按路径段的边界；方言可以改用 ltree 或闭包表，语义不变 |
| `EXACT p`、`SUBTREE p`（行上只存组织单元 ID 时） | `dept_id = ANY(SELECT id FROM 组织投影 WHERE path = $n OR path LIKE $m ESCAPE)` | 本组件或数据集存储保存了组织树的受控投影，且投影的来源水位满足新鲜度（[协议 02](../02-projections.md)、[协议 13 的授权列](../13-search-reports-and-datasets.md#授权列)）；否则不可下推 |
| `SELF`（已实例化） | `owner = $n` | 同上 |
| 区间 | `amount IS NOT NULL AND currency = $c AND amount >= $lo AND amount < $hi`（按开闭取符号） | 金额与币种列都在本表 |
| `RELATED` | `EXISTS (SELECT … FROM 关系投影 …)` | 本组件保存了关系的受控投影，且投影带完整性水位（[协议 02](../02-projections.md)）；否则不可下推 |
| 记录 `IN`（共享） | `EXISTS (SELECT … FROM 共享投影 WHERE 段 ID = …)` | 共享行引用它所属的段，不是与段脱钩的 ACL 行 |

一段中只要有一个原子不可下推，这段就不能参与列表。这时只有两条合格的路径：提供方返回带完整性证明、未截断、在预算内的候选 ID 集，编译为 `id = ANY($n)`；或者该列表用途声明为不支持，改走有界异步。不能丢掉这一段，再把剩下的结果当作完整集合返回。

### 命中位图与逐行字段

同一组段谓词在 SELECT 里再算一次，得到每行“命中了哪些段”的位图。逐行可读的字段就是命中段的读字段并集；SDK 唯一的输出映射按它掩码。单对象与列表使用同一份编译结果，所以不会出现“详情能看成本、列表里却掩码”，或者反过来；字段也就不会按类型笼统计算、忽略记录实际的完整范围。

逐行的动作状态（列表上的审批按钮）用相同的办法：把操作 K 的段在已取回的行属性上求值，或在 SELECT 中加 K 的位图。行属性不足以求值时，该动作状态为未知，不当作不允许。

### 排序、筛选、分组与聚合用到受限字段

请求按受限字段 f 排序、筛选、分组或求和时，必须先证明：**所有可见行上 f 都可读**。证明方法复用[包含证明](#包含证明)：对每个可见段 v，在同一列表操作的段中找到一个段 t，使 v 的范围与条件包含于 t，且 f 在 t 的读字段中。

| 查询用法 | 需要的证明 | 证明不成立时 |
| --- | --- | --- |
| `count(*)`，普通列表（掩码） | 只需可见性 | — |
| 按受限字段排序、筛选、分组；`sum`、`avg`、`min`、`max`；以它为条件的 `having` | 每个可见段都被某个读 f 的段包含 | 拒绝这一查询用法；普通的掩码列表仍可用 |
| 调用方显式选择“只看 f 可读的行” | 不需要上面的证明；筛选收窄到读 f 的段的并集 | — （结果集合变小，响应明示） |

这个证明条件是充分的，不是必要的：f 可读的行可能由几段的并集覆盖，而不被任何单段包含，这时会拒绝一个其实安全的查询。这是有意的保守，换取可判定与可预算。显式的“只看 f 可读的行”不泄露 f 的值，但必须由调用方明确选择，不能在后台悄悄收窄（安全 01 的 AE14）。

全文搜索与派生存储（搜索引擎、报表投影）同步段谓词所需的列，并在各自的查询中施加同一组段（[协议 13](../13-search-reports-and-datasets.md)）。

### 分页与游标

- 多段的结果按稳定 ID 去重，命中位图取或，然后统一排序、分页。可以改写成每段一条子查询再 UNION，但不能每段各取一页再合并截断。
- 分页用 keyset 游标。游标绑定**计划摘要**：该主体在该资源类型上的规范化段集合、筛选、排序与资源定义的版本；不绑定整份安全视图的修订号，否则任何人的授予变化都会打断全部用户的翻页。取下一页时重新编译；摘要相同则继续，不同则返回“查询条件已变化，请重新查询”（错误键在[安全 09a 的错误表](09a-encoding-and-records.md#求值结果与错误)登记）。这比证明新旧集合的包含关系简单，而且撤权后不会沿旧游标继续发出旧权限下的数据。
- 冷热分层时，计划必须覆盖请求涉及的全部层；某一层不能施加同一组段时，整体不可完成（[协议 11](../11-tiering.md)）。

## 包含证明

### 用在哪里

同一个算法回答“候选段是否在上限之内”：

| 场合 | 候选 | 上限 |
| --- | --- | --- |
| 管理者授出或扩大普通授予 | 候选授予展开后的每个段 | 管理者持有的管理职责单元的可授出段 |
| 机构共享 | 共享产生的读取段 | 资源治理允许分享的段 |
| 创建个人委托 | 拟委托的每个段 | 委托人当前的完整段与可委托 profile 的交 |
| 再下放管理职责 | 子职责的可授出段 | 父职责的可授出段 |
| 角色模板升级的差异 | 新角色修订的段 | 旧修订的段；不被包含的就是“扩权”，需要客户确认 |
| 受限字段排序的证明 | 每个可见段 | 含该字段的段 |

### 逐维规则

候选段与上限段的资源类型、操作必须相同；上限列出多个可授出的操作时，按操作分别比较。在候选段非空时，两个乘积集合的包含**等价于**每个维度分别包含，所以逐维比较是正确的，不是近似。

| 维度 | 候选包含于上限，当且仅当 |
| --- | --- |
| 任意 | 上限为 `ALL`；候选为 `ALL` 时，只有上限也为 `ALL` 才成立 |
| 值集合、记录、主体 `IN` | 候选集合是上限集合的子集 |
| 组织树 | 候选的每一项都被上限的某一项覆盖：`SUBTREE q` 覆盖它下面的任何节点或子树；`EXACT q` 只覆盖 `EXACT q`。`EXACT` 永远不覆盖 `SUBTREE`，即使那棵子树目前只有一个节点，因为树会长出新节点 |
| 主体 | 候选 `SELF` 先实例化为受授人；上限为 `ALL`，或上限的 `IN` 含受授人 |
| 关系 | 上限为 `ALL`；或关系类型与锚点相同，且候选深度不超过上限。不同关系类型之间、关系与组织树之间不做推理，结果为“无法证明” |
| 金额区间 | 币种相同，候选下界不低于上限下界、上界不高于上限上界；端点相等时，上限为开而候选为闭则不包含。上限有区间而候选为 `ALL`，不包含 |
| 读、写字段 | 候选的读字段是上限读字段的子集；写字段同理 |
| 有效期 | 候选的时间窗在上限的时间窗之内 |

### 一份上限不够时：沿一个维度拆分

候选可能被几份上限的并集覆盖，却不被其中任何一份单独包含。例如上限一是“法人甲、仓库一”，上限二是“法人甲、仓库二”，候选是“法人甲、仓库一与二”。

标准算法只做一种拆分：选一个候选取值为有限 `IN` 的维度，把候选按该维度的每个值拆成小段，要求每个小段被**某一份**上限单独包含。全部成立则通过，见证记录每个值由哪份上限覆盖。这一步是多项式的，结果可以解释。更一般的集合覆盖（同时沿多个维度拆，或依赖区间拼接）不做：两个范围的额度不能拼成一个更大的额度，这正是要防止的。

### 见证与结果

通过时返回**包含见证**：候选段的摘要、所用上限段的 ID 与修订、每个维度使用的规则、拆分方式、实例化所用的事实与修订、算法版本与消耗的预算。见证用于审计与解释，不是可以带到以后复用的许可（安全 06）；生效节点重新计算（计算本身很便宜）。

不通过时，按维度给出原因，管理界面据此告诉操作者具体哪一项超了：

| 原因 | 含义 | 处理 |
| --- | --- | --- |
| 超出 | 已知候选比上限宽（例如多了一个仓库、额度更高、多了字段） | 拒绝，指出维度与差额 |
| 无法证明 | 原子组合不在规则表内，或事实未知、不相容 | 拒绝或转合格的上级；不删掉难比较的条件后通过 |
| 超预算 | 比较次数或拆分规模超限 | 拒绝或要求分批 |

## 求交：委托和扮演的派生段

委托在使用时，派生段 = 委托人当前的每个完整段 ∩ 委托边的创建上限段（多层链逐边求交）；只读扮演 = 被查看主体当前的每个读取段 ∩ 会话上限。求交逐维进行：

| 维度 | 交 |
| --- | --- |
| `ALL` 与任意 X | X |
| 两个集合 | 集合的交 |
| 组织树 | 每对项：两个子树取较深的（不相交为空）；`EXACT` 与子树取落在子树内的 `EXACT`；两个 `EXACT` 相等才保留 |
| 区间 | 同币种取更紧的上下界（端点相等时取开的端点）；不同币种为空 |
| 字段 | 交集 |
| 有效期 | 交集 |

`SELF` 在求交前已按[主体相对的原子](#主体相对的原子)实例化为委托人或被查看主体，所以求交是纯集合运算。结果为空的派生段删除。来源的多份完整段各自与上限求交，不把甲的范围与乙的额度拆开拼接（安全 05 的 SD07）。派生段数受预算限制，超限则该委托路径不可用，不截断。

## 提供方要声明的能力

安全 06 的能力声明在本页细化为一张“原子 × 算法”的支持表。提供方（标准、静态、关系图、策略引擎）对每种原子分别声明能否求值、能否给出完整查询、能否参与包含证明：

| 原子 | 单对象求值 | 完整查询 | 包含证明 |
| --- | --- | --- | --- |
| 值集合、记录、主体、区间、组织树 | 所有合格的提供方必须支持 | 所有合格的提供方必须支持（经 SDK 编译到属主的表） | 所有合格的提供方必须支持 |
| 关系 | 关系图提供方或关系属主提供 | 需要本地投影与完整性水位，或完整的候选集 | 只支持同类型、同锚点 |
| 提供方私有的表达 | 允许在它内部使用 | 只有给出完整候选集或等价谓词时 | 不参与；涉及它的授出一律转专项 |

装配检查按“资源 × 操作 × 列表用途 × 实际用到的原子”匹配，而不是按提供方的名称。例如某客户只有“本人、部门、法人、仓库、额度”，标准成员就足够；启用项目成员继承时，才要求关系能力与投影。

## 为什么不能按维度压平

把一个主体在某权限键上的全部授予压平成“每个维度一个取值集合”再相与，会把不同授予的维度交叉组合：两份授予“法人甲、仓库一”与“法人乙、仓库二”压平后是 {甲, 乙} × {一, 二}，多出“甲与二”“乙与一”。参考模型的 FLATTEN 用例复现了这一点；与段脱钩、只按关系名匹配的共享行也有同类的问题。

所以要求：授权包下发规范化后的段集合；查询逐段编译、整体取 OR；字段按命中位图逐行掩码；共享行引用它所属的段。提供方给不出段（只能给压平的集合）时，不能声明完整段能力。

## 参考模型

[有限表达模型](../../../work/checks/08-finite-expressions.py)（种子 20261013）用 Python 实现上述原子、规范化后的段、逐维包含、单维拆分、求交、受限字段排序的证明，以及到 SQL 的编译；随机生成用例，并在 SQLite 内存库中执行编译出的 SQL，与内存求值逐行对照。

| 检查 | 结果 |
| --- | --- |
| 包含证明的正确性 | 1,686 个被判定包含的用例中，候选命中的每条记录都被上限命中 |
| 求交 | 4,000 对段，求交结果与逐条“同时命中”完全一致（399 条记录） |
| 单维拆分 | 333 个拆分覆盖，每条被覆盖的记录都落在单份上限内 |
| 受限字段排序的证明 | 853 个被证明可排序的字段，在每条可见行上都可读 |
| SQL 编译 | 500 个计划、20,923 行，结果集合、命中位图与字段掩码都与内存求值一致 |
| keyset 分页 | 每页 7 行逐页取完，与完整有序集合一致 |
| 反例 | 压平授予放出了两份授予之外的组合（FLATTEN）；“权限点、范围、条件分别是子集”的逐维授出检查接受了交叉配对，段包含与单维拆分都拒绝它（PERDIM） |

10 个坏变体全部被发现（8 类，其中开闭比较 3 个）：`EXACT` 覆盖子树、子树求交取浅、包含忽略币种、下界开闭比较错误、上界开闭比较错误、区间求交时端点开闭取错、SQL 用裸前缀、字段掩码不看命中段、排序证明不看范围、空部门匹配树。开闭类的变体只有在用例落在端点上时才会被发现，所以用例生成特意让金额与区间端点重合。

这些结果只说明算法设计在模型上自洽、编译模板的逻辑正确。它不是三门 SDK 的运行结果，不覆盖 PostgreSQL 方言、并发、冷热层、关系投影或任何提供方，也不算作 FX 或 PA 场景执行通过。

## 依据与独立判断

知识库授权决定 D3 的“授予内各维度取交集、授予之间取并集”、D5 的“每一行取覆盖该行的授予中最宽的字段级别”，以及 D4 把部分求值作为查询下推的路线，与本页一致；本页把它们落实为可以编译、可以证明的有限表达。

知识库《权限系统设计》“配置化与代码的边界”一节中防越权授予的规则写作“权限点 ⊆ 自己的，范围 ⊆ 自己的范围，条件不宽于自己的”。按维度分别比较时，它会接受本页 FX16 的交叉配对，与同库 D3 的配对原则冲突（参考模型的 PERDIM 用例）；这是知识库表述上的问题。本项目按 D35 把管理上限与本人业务使用权分开（与 AWS permissions boundary、Kubernetes RBAC 的 `escalate` 与 `bind` 同类的思路），而知识库 D12 只列出“只能授予自己拥有的”一种；这是本项目的独立选择，也是知识库的一处覆盖缺口。

本页的算法是项目的设计，知识库与外部资料都不替它证明正确性；正确性依靠上面的参考模型、之后的三语言向量与真实数据库的验证。
