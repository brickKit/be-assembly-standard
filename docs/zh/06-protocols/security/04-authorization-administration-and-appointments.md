# 授权管理上限与任职生命周期

本页定义授权管理的行为：管理者能授出什么、怎样证明没有越界、各种管理动作检查什么、角色模板怎样升级、批量怎样生效、任职变化怎样影响授予、管理员怎样交接、上限怎样收紧、最后一名管理员怎样保护。业务许可的公式见[安全 01](01-authorization-evaluation.md)，主体与属性的取证见[安全 02](02-trusted-identity-and-attributes.md)，管理的提交与收紧见[安全 03](03-authorization-acceptance-and-revocation.md)；本页只补管理对象、包含关系与生命周期。

默认小公司可以集中管理，集团可以启用受限的分级管理（D35）。两者使用同一套完整授予与管理上限的语义；分级管理不是扮演，也不要求管理员先拥有全部被管理的业务操作权。

## 依据

| 已定要求 | 本页保持的结果 |
| --- | --- |
| 完整授予配对（D09） | 管理者每份授出资格也保持对象、动作、范围、条件与字段的绑定，不能分别取最宽再组合 |
| 管理与使用分开 | 业务许可不推出管理权；管理上限本身也不授予业务数据的访问 |
| 新任职的授予人工确认（D30） | 任职事实、权限建议与生效的授予分开；预先审核的计划在生效时仍重新验证 |
| 普通管理员正常卸任（D36） | 结束他的管理资格；合法的普通授予按自身的绑定继续；代办仍依赖相应的上游资格 |
| 普通角色升级经客户确认（D37） | 模板发布不自动扩展客户实际的角色或已绑定的授予 |
| 共同安全与必需控制（D07、D10） | 上限收紧、角色退役、本人自审与其他必需控制，不能被旧角色或兼任绕过；不引入管理员可配置的 Deny |

## 方案与管理对象

| 方案 | 判断 |
| --- | --- |
| **采用**：明确的管理职责单元、持有资格与有限的完整上限；客户角色版本与授予显式绑定 | 容易说明“谁管理哪部分、能授出什么”；卸任、收紧与普通授予可以分别处理；适合集中与分级 |
| 管理者只能授出他本人的业务许可 | 结构较少，但违反“管理与使用分开”，迫使管理员获得不需要的业务数据与动作权限 |
| 在任意策略语言之间自动证明上限 | 表达广，但不能保证可判定、预算或跨实现一致；只有有限可证明的表达进入标准路径，其余明确适配或交给合格上级处理 |

管理职责单元是机构的授权边界，不是一个永久的管理员账号。它有稳定的身份、管辖范围、上限与治理来源；管理者通过有效的管理资格持有它。管理者退出与职责单元撤销分开，不把某个人的任职期限当作所有下级治理关系的寿命。

| 对象 | 最少记录与责任 |
| --- | --- |
| 管理职责单元 | 稳定的 ID 与修订、所管的法人、组织、人员与授权对象、允许的管理动作、可授出的完整上限段、有效期与治理的父来源 |
| 管理持有资格 | 实际主体、职责单元、所需的任职或其他资格与有效期；由合格的管理路径确认，不从职务名自动推出 |
| 客户实际角色的版本 | 稳定的角色 ID、不可变的内容修订、操作、字段与条件的模板、来源与退役状态；不能只存“销售经理”这个名字 |
| 普通业务授予 | 稳定的授予 ID 与修订、受授主体、实际角色的内容版本或明确的直接操作、范围、条件与字段、资格绑定与有效期 |
| 管理或角色的变更计划 | 明确的目标与候选状态、影响清单、各绑定的修订、所用的上限证明、确认人、有效期、幂等键与处置记录 |
| 来源与接管记录 | 谁在什么资格与上限下授出、归哪个治理单元管理、实际的变更依据与后续接管；不覆盖原授予的来源 |

这些对象是行为模型，不登记新的权限键或组件 ID。作用域支持集中管理员的显式全范围，但只对声明的部署与资源成立；不把空值、未知的组织或未安装的能力当作全权。

## 授出的包含关系与完整见证

一次新增或扩大授予，先检查管理者当前的身份、管理动作与目标对象的资格，再把候选的角色与授予展开为安全 01 的完整段。每个候选段必须在一份合法完整的管理上限段内得到包含证明；多个上限可以通过显式拆成不同的候选段配合，不按维度、金额或字段独立取并集。

| 比较项 | 标准路径的证明要求 |
| --- | --- |
| 管理目标 | 候选的主体、任职、角色或授予与被影响的治理域，都属于许可的目标集合；人员在本部门，不意味着他全部跨法人的权限都归本部门管理员 |
| 操作 | 每个候选操作属于该上限明确的可授出集合；未知、退役或未来的键不借通配生效 |
| 范围 | 候选资源集合包含于上限资源集合，法人与仓库等配对保持；全集、空集、ID 集合与组织子树分别校验 |
| 条件 | 候选段成立必然使相应的上限条件成立；金额按同币种或单位比较，区间边界一致；不能把两个范围的额度拼成一个更大的上限 |
| 字段 | 候选的读、写字段各自包含于对应的上限字段集，派生依赖与普通字段的分类也合格；写权仍遵守安全 01 的读写组合 |
| 时间与资格 | 候选的有效期、任职或其他业务资格与要求，不超过治理的许可；未来生效的先登记待确认，不提前可用 |
| 再下放管理 | 管理职责的再下放必须有独立的许可、目标与深度上限，不能从普通授予动作或业务角色的内容推出 |

- **支持的证明**：有限集合包含、明确的组织路径段与子树包含、相容类型的区间收窄、条件合取的加强、字段集合包含；多个 OR 分支先展开成完整段再逐段证明。这不是任意布尔或策略语言的通用蕴含求解器。逐维规则、单维拆分、见证与失败原因见[安全 07 的包含证明](07-finite-expressions-containment-and-queries.md#包含证明)。
- **证明不了就不通过**：无法证明、来源缺失或超出预算时，拒绝或转合格的上级；不能删掉难证明的条件后通过。
- **例子**：管理资格甲只可授“法人甲、仓库一、审批 ≤100”，资格乙只可授“法人乙、仓库二、审批 ≤50”，据此不能授出“甲与二”或“乙 ≤100”；合法的原配对可以分别形成两份授予。
- **相对表达**：`self`、相对任职的组织等表达，按候选受授主体与绑定事实展开，不把管理者自己的本人或部门表达复制过去误当包含。无法证明未来的绑定变化仍在上限内时，绑定该资格的修订，变化后按下文失效或复核；不能因为语法字符串相同就判为相等。
- **上限不是使用权**：上限只给出最大可授出的集合，执行仍需要明确的管理动作；它不提供业务使用权。这与 [AWS permissions boundary 对最大权限与实际授予的区分](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html)相近，但本项目不照搬 AWS 的资源策略或 Deny 合并算法。
- **普通授予的有效期**：受机构治理上限与受授资格约束，不按授予操作人的任职终点裁剪；管理者只在本次操作生效时必须合格。所以个人卸任后，普通授予能按 D36 继续；机构上限的撤销或收紧仍执行下文的影响闭包。

## 各种管理动作的检查

| 动作 | 需要检查的实际影响 |
| --- | --- |
| 新增或扩大普通授予 | 目标资格与每个候选完整段的授出包含证明，不能只看角色名 |
| 收回或缩小授予 | 专门的回收权与被影响的授权域；不要求回收者同时有权重新授出旧的宽许可；也不能借管理一个人员，撤掉他不归自己管的跨域授予 |
| 修改角色内容 | 该角色版本与所有目标授予的实际变化；不能只因有“编辑角色”的入口就影响未获管辖的成员 |
| 绑定或替换角色版本 | 每份绑定都按候选的新内容重新证明；发布角色修订不代替绑定的确认 |
| 下放管理权 | 管理的父来源、可管理的动作、目标、上限、期限与深度；禁止环，也禁止自己绕道扩大同一管理资格 |
| 管理员交接 | 交接权、接任者的有效资格、职责单元与边界；接任是新的管理资格确认，不是继承卸任者的登录凭据 |
| 管理上限收紧、治理单元撤销 | 对新的管理与已发授权的依赖闭包、收紧与停用的处置；不同于正常卸任 |

- **回收只作用于有权管理的授权域**：一份宽授予跨越多个管辖域时，只能执行有完整影响证明的分段收窄，或由覆盖整体的上级处理；不能通过删掉整份授予，间接撤销另一个法人的合法权限。
- **不能给自己扩权**：管理者给自己或已关联的其他账号配置业务权限，同样不能超过他明确的授出上限；业务资格或修改角色不能成为扩大管理上限的入口。小公司合法的集中配置，不默认要求第二名员工。需要独立确认的管理扩权、紧急访问等，由受保护操作清单声明（[安全 08](08-state-and-change-protocol.md)）；不能自己绕过该清单，缺合格的确认者时转上级或受控的部署恢复，不临时取消要求。
- **管理变更是高风险动作**：管理状态与接受裁决由授权组件同一属主持有，在同一守卫事务中完成 A 与 B：重新验证当前的管理持有资格、治理上限、目标修订与影响计划后提交；不能用旧的管理 Check 更新授权。所选实现不能把管理生效纳入同一保护事务时，必须有等价的 B 档管理提交屏障，否则不启用该管理能力。普通业务中在先的 A 可以限定继续，但不能用来让已经失去资格的管理员稍后发布未生效的授权计划。跨属主的资格变化先执行安全 03 的收紧协议，异步批次也在各生效点重新验证。

## 角色模板、客户角色与版本升级

标准模板、客户实际的角色、任职建议、有效的授予，是四种对象。模板升级只生成差异与候选，不改客户实际的角色。客户角色的新修订默认不自动替换已绑定的修订：明确的确认计划选择哪些绑定采用新内容，防止同名的角色被就地扩权。

已发布的权限键不改名、不复用；权限含义的变更仍要审查兼容与迁移（[协议 19](../19-config-secrets-registries-release.md)）。新功能安装后，客户可能需要做一次权限配置才能使用，交付界面与说明要明确这一状态，不能为了避免配置而自动扩权。

| 差异 | 处理 |
| --- | --- |
| 新操作或新字段；范围或条件放宽 | 展示实际的扩权，合格的管理者确认、并证明受影响对象的上限后生效 |
| 客户主动收窄 | 记录修订，执行收紧协议，更新明确的目标绑定，保留旧证据 |
| 权限退役、必需控制、安全修复 | 执行受保护的升级规则：旧角色修订不能继续启用已退役的键或绕过当前的控制；具体的兼容与受影响动作按升级契约处理 |
| 相同键的含义变化，资源类型或字段的解释变化 | 按语义破坏性变更审查，不冒充“只是模板新增字段”；冻结前确定迁移的版本 |
| 客户自定义角色、Fork | 保留实际内容与来源，比较具体差异；不按名字强行覆盖 |

- 角色不默认任意继承；复用权限组也必须展开并绑定具体的版本。以后启用继承时，声明无环、深度、实际内容的展开与变更影响的能力，不能借继承让未确认的权限自动进入旧角色。
- 系统角色的保护、最后一名管理员的保护、专用超级用户对已注册未退役键的特殊补齐，按 D37 另有受保护的规则；普通角色不能冒充它们。生产环境默认无人持有超级用户；秘密不可输出与必需的业务控制仍不能绕过。演示数据中的角色不直接作为正式的客户模板。

## 变更计划与批量生效

- **计划的内容**：保存不可变的候选、目标全集或完整的枚举证据、角色、授予、任职与治理的修订、影响与包含证明、确认的身份、终点与幂等键。预览与确认都受管理数据的访问控制，只展示必要的权限事实，不因管理员能管理角色就展示所有业务敏感值。
- **提交时重新验证**：预览通过不是永久许可。原依赖的修订变化时，暂停失效的部分、重新计算剩余的候选，由合格的人员确认；不能自动采纳变宽的新上限、角色内容或已转部门的目标。减少影响的变化也要有可证明的相容规则，不凭直觉忽略。
- **整批与分批**：小计划可以声明整批本地原子提交；大计划采用有界的批次，明确每一份是已生效、被拒、待处理还是终止。每批绑定相同的候选语义并重新验证当前的证明；不能部分生效后返回“整批未执行”。取消只停止未生效的部分，已生效的部分需要新的收紧或回收计划，不能盲目回滚他人后续的修改。
- **动态集合与幂等**：新增的人员、角色使用者或授权域不自动进入审核过的计划；动态的成员集合采用固定的全集或可证明的截止水位。重复确认与重试不再授出一次，也不延长有效期；未知的结果按安全 03 的许可与业务事实查询恢复。

## 任职事实与授予生命周期

员工与账号可以不是一一对应；任职使用不可复用的资格实例与明确的修订。任职结束后重新任职，是新的资格实例，不让旧任职的授予复活。改法人、部门、岗位或资格条件等有安全含义的变化，默认结束旧的资格绑定、创建新的资格与候选授权；显示名等不影响资格的修改，另有明确的字段分类。

| 变化 | 默认处理 |
| --- | --- |
| 任职尚未生效 | 可以准备权限建议；未满足时间与确认条件不能产生有效的授予 |
| 新任职，或有安全含义的变化 | 员工属主提交事实，生成候选建议；合格的管理者确认后授出；不把维护岗位等同于授权 |
| 原任职结束或到期 | 关闭该资格的新接受与读取证据；撤销关联的授予与管理持有资格；时间保证按安全 03，不等定时清理 |
| 仍有其他兼任 | 其他合法的完整授予分别保留，不能按账号全量删权；需要所选任职的动作不借另一个任职混用 |
| 独立的直接授予 | 标明依据与复核政策，不因任职变化一律删除或永久保留；必要的事实不清时，暂停它未证明的部分 |
| 在一个法人离任、全部离职 | 员工属主声明失效的范围，处理对应的资格；账号是否停用由身份组件的生命周期政策与受控绑定决定，不把单个任职结束推成删除整个账号 |
| 重新入职、账号重新启用 | 重新验证当前的资格与明确的确认，不恢复旧的资格实例、已撤销的授予或旧的管理持有关系 |

- 授权保存受授主体、账号或员工与资格绑定的受信关系及修订，跨账号的撤销按这些绑定展开；不靠姓名、邮箱，也不只找“最近登录的账号”。关系、员工与组织的版本各有自己的域，不比较裸版本的大小来忽略冲突。
- 建议的状态有待确认、有效、受控暂停、到期或已撤销等执行视图，理由与生命周期分别记录；通用状态与生效点见[安全 08 的通用生命周期](08-state-and-change-protocol.md#通用生命周期)，逐字段的编码见安全 09。恢复失效的资格不能改旧记录的有效期，让旧的审计事实消失。
- 跨组件的变化使用安全 03 的“先收紧、后由属主完成；先取得完整的正向事实、后放开”。重复与乱序的事件按资格实例与修订幂等收敛；完整回填不能被局部同版本的记录阻塞（[协议 02](../02-projections.md)）；同步停止时，不能凭投影最后一行仍是 active 就继续新接受。
- 预先审核的调岗计划仍绑定明确的新资格、模板或客户角色的版本、受授人员、范围与生效时点，实际生效前重新验证。审核后计划或管理资格发生变化时，未生效的部分暂停重审；旧任职的终点不因等待新授权而延长。

## 管理员交接、再下放与上限收紧

- **正常卸任**终止个人的管理持有资格，机构职责单元与合法的普通授予保留。接任者通过独立的合法确认获得该职责，原来源不改名。没有合格的接任者时，由已声明的上级接管管理；没有上级时进入受控恢复；普通的合法业务授予继续按自身的资格与必需控制判断，不凭空新建管理员。
- **再下放**：机构治理的父来源与个人的代办来源分开。允许再下放时，子职责的上限必须包含于有效父职责的完整上限，子管理者有自己的有效资格；父管理员正常卸任不自动终止合法的机构边界。父职责被撤销或收紧，则影响子治理能力，不能以“已经交接”为由保留越界的下放。子职责无环与最大深度是装配或治理 profile 的显式约束。
- **上限收紧**：先关闭相关的管理路径、建立影响闭包，按安全 03 的裁决协议保护已发授予的越界部分。已发授予的有效段按[安全 08 的有效段计算](08-state-and-change-protocol.md#有效段的计算)取“授予 ∩ 当前上限”，收紧立即生效。部分越界的授予保持生效（只在交集内）并标记待复核，复核的结论生成收窄修订或接受现状；只有交集无法计算（提供方私有的表达）时才暂停，否则会停掉仍在上限内的合法访问。不能只限制未来的授出、却让已发出的越界业务许可无限留存，也不能把所有授予一律永久删除。
- **安全事件**：安全事件、发现原授予越权、组织撤销、治理单元废止，不套用正常卸任的规则；分别声明需要冻结的账号、服务、管理或业务域，恢复资格，以及对已有接受与已执行事实的处置。通常管理上限的变化，不等同于代办人上游个人权限的变化；代办的协议见[安全 05](05-sharing-delegation-and-impersonation.md)。

## 最后管理员、恢复与业务交接

- **不变量**：普通的管理变更不能使部署失去合格、可用的受保护管理资格。在同一裁决域检查当前的账号状态、资格期限、治理边界与声明的认证与恢复条件，不能只数某个角色表有几行。这一检查约束授权组件内的普通管理变更（权限回收、角色修改、管理资格变更）。
- **来源事实不受阻止**（D62）：员工组件的离职与任职结束、身份组件的账号停用是来源事实，照常生效。授权组件应用这些事件后发现可用的管理员为零时，部署进入“待恢复”，按[安全 08 的待恢复](08-state-and-change-protocol.md#待恢复)经部署所有者的管理员恢复退出；员工组件办理离职时给出提示。
- **安全处置优先**：安全强制停用、已经发生的外部账号失效，不能为保留“最后管理员”而继续开放受侵的身份；这些场景关闭相关的资格，没有可用管理员时转管理员恢复（安全 08）。这项保护不阻止必要的安全处置，也不自动授出超级用户；初始化、紧急恢复与当前管理数据的恢复代次见安全 02、03，操作与结果留据。
- **业务交接独立于授权交接**：审批任务与业务责任的交接按 D38 的绑定职责规则解析合法的接任者（[协议 09](../09-approval-and-workflow.md)），不能因为被任命为管理员就批准他人的单据。已作出的审批事实与业务归属保留，当前资格仍按适用的节点检查；没有合法候选时暂停转人工，不自动通过，也不提前授予新权。

## 依据与独立判断

知识库的完整授予与兼任、任职、委托、授权架构提供中立参考；本项目的管理员正常卸任、受限分级管理与客户角色确认以 D35–D37 为准，不把普通的机构授予等同于依赖个人当前权限的委托。

[Kubernetes RBAC 对角色创建与绑定的限制](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#restrictions-on-role-creation-or-update)提醒，编辑角色也可能造成间接扩权；本项目独立采用完整的管理上限，不要求管理者拥有全部被授出的业务权。[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)用于核对每个入口都检查与最小访问的原则；这些来源不证明本项目的包含算法或状态协议已通过验收。
