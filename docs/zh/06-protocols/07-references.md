# 跨组件引用的生命周期

组件之间只用身份引用对方的数据：订单引用客户与产品，出库引用仓库，凭证引用法人与科目，审批引用员工。没有跨库外键。被引用的对象会被暂停、退役、合并、销毁，引用方却不知道。本页回答：

1. 不同用途的引用，各自要求被引用对象在什么时刻、处于什么状态？
2. “先查存在、再本地提交”之间的并发间隙怎样处理？
3. 合并、暂停、销毁之后，旧引用怎样解析？
4. 属主暂时不可达、对象不存在、调用者无权查看，怎样区分？谁负责发现与修复悬空引用？

依据的决定：D15（发生时归属与当前责任分开）、D20–D22（业务伙伴、正式联络资料、合并默认由人确认）。重复主数据的确认与合并的取舍见[数据与生命周期](../04-foundations/02-data-and-lifecycle.md#重复主数据的确认与合并)。

## 两类引用

| 类别 | 用途 | 要求 | 例子 |
| --- | --- | --- | --- |
| 历史引用 | 记录已经发生的事实 | 稳定身份 + 发生时的快照；对象之后的变化不影响引用的有效性 | 已开账单中的客户、已过账凭证中的科目、出库单中的产品 |
| 资格引用 | 新业务要求对象此刻可用 | 提交时证明对象当前可用于该用途；提交后转为历史引用 | 新建订单的客户与产品、新排班的员工、入库的仓库 |

一条资格引用在业务提交之后就成为历史引用：订单确认后客户被暂停，已确认的订单仍然有效；是否继续执行（发货、收款），由后续环节自己的资格检查决定。

## 引用方的声明

每个引用字段在组件的资源定义中声明：

| 声明项 | 含义 |
| --- | --- |
| 目标 | 属主组件与资源类型 |
| 类别 | 历史引用或资格引用 |
| 用途 | 资格引用要求的用途，例如“可销售”“可采购”“可收货” |
| 作用范围 | 法人等维度：客户角色按法人开通，产品按法人可售 |
| 快照字段 | 发生时需要保存的显示字段（名称、税号、单位等），只存必要的 |
| 生命周期行为 | 目标被暂停、退役、合并、销毁时，本组件怎样处理（见下文） |

## 被引用对象的生命周期

| 状态 | 新的资格引用 | 已有的引用 |
| --- | --- | --- |
| `active` | 允许（按用途与作用范围） | 正常 |
| `suspended` | 拒绝 | 继续有效；后续环节可以按自己的规则拒绝执行 |
| `retired` | 拒绝 | 继续有效；属主保留可以解析的身份与当前数据 |
| `merged` | 拒绝，提示存续对象 | 历史引用保持原身份与快照；解析时返回存续对象 |
| `destroyed` | 拒绝 | 属主只保留身份墓碑；引用方的快照按擦除规则处理 |

| 当前状态 | 事件 | 守卫条件 | 结果状态 | 发出的事件 |
| --- | --- | --- | --- | --- |
| `active` | 暂停 | — | `suspended` | 状态变化 |
| `suspended` | 恢复 | — | `active` | 状态变化 |
| `active`、`suspended` | 退役 | — | `retired` | 状态变化 |
| `active`、`suspended`、`retired` | 合并（经人确认，D22） | 不会形成别名环 | `merged` | 已合并（附存续对象） |
| `merged` | 拆回误合并 | — | 合并前的状态（`active`、`suspended` 或 `retired`） | 状态变化；别名作废 |
| 任一非 `destroyed` 状态 | 销毁 | 不在法律保全中 | `destroyed` | 已销毁（附要擦除的字段类别） |
| 任一状态 | 销毁 | 在法律保全中 | 不变 | 拒绝 |

状态由属主维护，变化以事件发布（属主的状态投影，[协议 02](02-projections.md)），并在属主的批量读取接口中返回。身份不复用；别名与墓碑永久保留。

## 资格引用的提交检查

与授权的默认路径（[安全 03 的有界本地授权](security/03-authorization-acceptance-and-revocation.md#默认路径有界本地授权)）是同一个思路：

- **取证**：引用方在提交前取得资格证据，来源二选一：
  - 自己保存的属主状态投影——只限在组件卡上声明为“水位来源”的属主；投影行是完整的，且属主的来源水位在 W 之内（[协议 02 的来源水位](02-projections.md#来源水位)）；
  - 同步调用属主的资格查询，返回状态、修订与用途结论。

  资源状态的流没有声明为水位来源的属主（例如伙伴、产品；它们发布的数据集流是水位来源，但不用于资格判断），一律用同步资格查询。
- **提交事务内核对**：证据在发出查询（或补取）后 W 之内有效；过期则重新取证，不在事务里做网络调用。
- **保证**：属主在 t0 暂停对象后，依赖旧证据的新引用不晚于 t0 + W 提交。只在草稿创建时检查、提交时不再核对，引用可能在暂停很久之后才提交（参考模型的“只在草稿时检查”坏变体）。
- **绝对阻断**：需要绝对阻断的情况（例如法律冻结、制裁名单），不只依赖引用时的检查：执行环节（发货、付款、开票）各自再次检查对象状态，形成多道防线。

这里不要求每个引用都由属主持锁协调；有界窗口对大多数主数据足够，确实需要严格保证的业务按执行环节的检查补足。

## 合并与别名

合并按 D22 由有权限的人确认后执行：

1. 属主在一个本地事务中把被合并对象转为 `merged`，记录别名“被合并 → 存续”，保留原身份、原数据与合并记录。
2. 禁止形成环：存续对象如果本身经别名链指向被合并对象，合并被拒绝。
3. 解析沿别名链走到底：A 并入 B、B 再并入 C，解析 A 得到 C。只走一步会停在已合并的 B（参考模型的“只解析一跳”坏变体）。
4. 属主发布“已合并”事件。引用方：
   - **历史引用不改写**：原身份与快照保持，展示时可以附“已并入某某”；
   - **在途业务**（未完成的订单、待处理的任务）是否把当前引用改到存续对象，按引用方声明的行为；需要改时写一条带合并引用的变更记录，不改写已发生的事实；
   - **权限不因合并扩大**（D22）：引用方基于原对象的授权关系，不自动转到存续对象。
5. 拆回误合并：属主把原对象恢复为合并前的状态（合并记录保存这个状态，所以暂停不会因拆回被悄悄解除）并作废别名；已经改到存续对象的在途引用，按变更记录逐条复核，不承诺一键回退。

## 属主的解析结果

属主的批量读取与资格查询，对每个身份返回以下之一：

| 结果 | 含义 | 引用方的处理 |
| --- | --- | --- |
| 当前数据 | 对象存在，附状态与修订 | 正常 |
| 别名 | 已合并，附存续对象的身份 | 按上节处理 |
| 墓碑 | 已销毁，只有身份 | 历史引用保留身份；快照按擦除规则处理 |
| 不存在 | 从未存在过 | 报告为数据错误；不自动删除引用方的业务数据 |
| 不可见 | 调用者无权查看 | 对用户按“不存在”处理，不泄露对象是否存在；组件以服务身份解析时可以区分 |
| 不可达 | 属主暂时无法回答（调用失败、超时） | **不当作不存在**：资格引用无法证明，提交拒绝或暂缓；历史引用照常显示快照 |

把“不可达”当作“不存在”去清理引用，是最难察觉的数据损坏之一：一次属主故障就会让大量业务记录丢失关联（参考模型的“不可达视为不存在”坏变体）。

## 悬空引用的发现与修复

- 引用方以对账工作项（[协议 01](01-background-work.md)与[协议 02 的对账](02-projections.md)）定期批量解析自己的引用：结果为别名的按合并规则处理；为墓碑的确认擦除已执行；为“不存在”的列入数据修复清单并告警。
- 修复是人工处理：确认是录入错误、导入错误还是属主数据丢失，再按业务流程更正；不自动删除引用方的业务记录。
- 跨法人一致性：资格检查包含作用范围；对账也核对“引用的客户角色在该法人下曾经开通”，不一致的列入修复清单。

## 销毁与擦除

对象被销毁（例如个人信息的合法擦除）时，属主发布“已销毁”事件，附需要擦除的字段类别。引用方对自己快照中声明的个人信息字段做假名化，保留业务事实与金额；审计中的主体引用按[协议 03 的保留与法律保全](03-audit-durability.md#保留与法律保全)处理。法律保全中的对象不能销毁。

- **限制处理**：权利人要求暂停处理而不删除时，属主把相关个人信息标为“限制处理”：除保存、法律要求与权利人同意的用途外不再使用（不进新的导出、数据集、通知与搜索），解除时恢复；状态随引用方的快照同样传递。
- **账簿不存个人信息**：账簿、流水与证据类的只追加表不放个人信息列，只存主体的不透明身份；擦除只需处理主体资料与快照，不改写只追加的记录。

## 参数起始值

| 参数 | 起始值 |
| --- | --- |
| 资格证据的有效期 W | 30 秒；用于法律冻结类状态的用途另设更短的值，并在执行环节再查 |
| 引用对账周期 | 每日 |
| 别名保留 | 永久（与身份不复用的原则一致） |

## 参考模型

[引用生命周期模型](../../../tools/be-acceptance/models/19-reference-lifecycle.py)（种子 20261013，3,000 次运行）：随机合并（含链式合并）、暂停、资格引用（证据请求与提交之间有随机间隔，其间可能暂停）、属主随机不可达时的核对。

| 检查 | 结果 |
| --- | --- |
| 任意身份解析到最终的存续对象；会形成环的合并被拒绝 | 成立 |
| 属主不可达时，引用不被删除或改写 | 成立 |
| 资格引用不晚于暂停时刻加 W 提交 | 成立 |
| 合并与暂停不改变历史引用中的快照 | 成立 |

5 个坏变体全部被发现：允许合并成环、只解析一跳、不可达视为不存在、只在草稿时检查资格、合并后用存续对象刷新快照。模型不是 SDK、数据库或真实主数据组件的运行结果。

**模型没有覆盖的条款**：模型只建了同步资格查询的路径，没有建出经投影取证时的来源水位；水位机制本身由[内部来源水位模型](../../../tools/be-acceptance/models/35-internal-source-watermark.py)演算（授权组件的同一机制），资格引用经投影的路径（RF19）靠实现测试。拆回误合并、销毁与擦除也不在模型中。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| RF01 | 新建订单时客户已暂停 | 资格引用被拒绝 |
| RF02 | 订单确认后客户被暂停 | 订单仍有效；发货与收款按各自的检查决定 |
| RF03 | 资格证据取得后、提交前客户被暂停 | 提交不晚于暂停后 W；超过有效期须重新取证 |
| RF04 | A 并入 B，B 再并入 C | 解析 A 得到 C |
| RF05 | C 尝试并入 A，而 A 已经经链指向 C | 拒绝，避免成环 |
| RF06 | 已开账单引用的客户被合并 | 账单保留原客户身份与快照，显示“已并入” |
| RF07 | 在途订单引用的客户被合并 | 按订单组件声明的行为处理，写变更记录，不改写已发生事实 |
| RF08 | 合并后，基于原客户的共享与授权关系 | 不自动转到存续客户 |
| RF09 | 误合并被拆回 | 原对象恢复；已改到存续对象的在途引用逐条复核 |
| RF10 | 属主服务不可达时的列表显示 | 显示快照；不清理引用 |
| RF11 | 属主不可达时提交资格引用 | 无法证明，拒绝或暂缓 |
| RF12 | 对账发现引用的身份“从未存在” | 列入修复清单并告警，不自动删除业务记录 |
| RF13 | 用户请求的对象对其不可见 | 对用户表现为不存在 |
| RF14 | 客户在法人甲开通、在法人乙未开通，乙的订单引用它 | 资格检查按作用范围拒绝 |
| RF15 | 客户因个人信息擦除被销毁 | 引用方快照中的个人信息字段假名化，业务事实与金额保留 |
| RF16 | 法律保全中的对象请求销毁 | 拒绝 |
| RF17 | 身份被复用 | 不允许；别名与墓碑永久保留 |
| RF18 | 产品退役后，历史出库单查询 | 正常显示快照与当前数据 |
| RF19 | 资格证据取自本地投影，但属主的来源水位已超过 W | 无法证明，改用同步资格查询或拒绝 |

## 已知风险与待定

- 各组件的引用字段声明（目标、类别、用途、作用范围、快照字段、生命周期行为）随组件设计逐个写入资源定义。
- 业务伙伴、产品、组织、员工各自的生命周期状态细节与合并规则，随主数据组件设计确定；本页给出共同框架。退役能否恢复为 `active`，随各主数据组件的设计确定。
- 擦除事件的字段类别与各组件的假名化规则，随数据生命周期的设计统一。
- 哪些状态可以退役、合并或销毁（状态迁移表的起始状态），是本页给出的共同框架；各主数据组件可以按业务收紧。
- 以上预期尚未在 SDK、数据库或主数据组件上运行。
