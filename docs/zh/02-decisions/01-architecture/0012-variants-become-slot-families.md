# 0012 槽位族需要多种合理实现，而且没有依赖边

## 决策

一个功能成为槽位族——每种变体一个组件，契约完全相同，客户在组装时装一个（`slot`）或多个（`channel`）——必须同时满足两个条件：(a) 成熟系统对它给出真正不同的实现，每一种都适合某一类客户；(b) 没有任何组件对这个位置建依赖边。真实的槽位都属于这一类：前端（`slot:frontend`）、身份（`slot:iam`）、按国家划分的薪资（`slot:payroll`），以及 IM 等外部通道（`channel:im`）。若 (a) 成立而 (b) 不成立——交易组件内部的分歧通常都是这样（成本核算方法、拣货策略、审批路由、关账、定价）——标准组件只提供一种默认实现，需要别的实现的客户，基于该组件做客户 Fork。如果分歧只有两三个分支、看得见的未来也不会再多出一种，可以作为内部策略留在组件里。先设计并登记这个族，再实现任何成员。

## 理由

依赖边写的是精确的组件 id，注入的变量名里带着实现的名字，所以被其他组件依赖的位置无法靠组装来替换——替换它就要改每一个依赖方。反过来，配置开关会把每个客户的变体塞进同一份代码里，为一个客户做的改动可能弄坏另一个客户。Fork 让每个客户的分歧留在自己的副本里，从最接近的标准组件起步。如果某一种实现明显优于其他，它就是默认实现。

## 挡下什么

- 把"让客户选先进先出还是移动加权平均成本"做成槽位族（`slot:costing`，单独的成本核算或拣货组件）——这些位置长在 `erp/inventory` 内部，而其他组件依赖它；正确做法是标准组件提供一种默认方法，需要别的方法的客户做客户 Fork
- 每来一个新客户就多一个分支的 `if costingMethod == "fifo"`，或"加一个设置，让客户自己选算法"——例外是只有两三个分支、看得见的未来不会再多的小型内部策略
- 其他组件直接依赖某个族成员（依赖 `infra/iam-casdoor`，而不是在本地验签）
- 把普通设置做成族（单据编号规则就是一个配置键），或者把"主数据多几个字段"做成族（那是 Fork）

## 何时重新讨论

某个存在分歧的位置不再有任何依赖方时——它就可以成为槽位族；或者某个族的各变体在实际使用中收敛到同一种实现时——族随之收缩为这一个。
