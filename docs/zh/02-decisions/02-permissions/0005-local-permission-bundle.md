# 0005 权限判定基于本地 bundle

## 决策

`infra/authz` 在 `GET /authz/bundle` 发布完整的"角色 → 权限键"策略。每个进程里的 SDK 大约每 15 秒拉取一次（条件 GET，大多返回 `304`），放进进程内的 map，权限判定就是一次 map 查找。没有任何组件持有权限表或角色副本，也没有组件在每个请求上去问 authz。SDK 的路由注册函数把权限键作为必填参数，调用时漏写权限键就编译不过；用框架原生方法注册的裸路由由 `make gates` 拦下。

## 理由

这是标准的本地 PDP 形态（OPA、Istio）：判定在内存里完成，没有网络往返。每个请求都去问授权服务，就是每个请求多一次网络调用；在每个组件里维护副本，则把一次查找变成分布式缓存失效问题，每个组件都要多出表、迁移和事件消费者。变更（包括角色调整和踢人下线）在大约 15 秒内生效。authz 不可达时继续使用最后一份 bundle；第一份 bundle 到达之前，业务请求返回 `503`，`/healthz` 照常健康。

## 挡下什么

- 在业务组件里建角色表或权限表，或用事件把角色同步到各组件
- 每个请求都"问一下 authz 这个用户能不能做 X"
- 把 authz 是否可达放进 `/healthz`——authz 抖一下，外壳里所有模块一起重启
- 用 Redis 缓存权限（[0004](0004-no-redis.md)）
- 引入 SpiceDB、OpenFGA 或仿 Zanzibar 的集中式授权服务
- 用框架原生的 `GET` / `POST` 注册路由，而不是带权限键的版本

## 何时重新讨论

策略大到在每个进程的内存里放不下，或者某个需求要求比轮询间隔更快生效、且缩短间隔也满足不了时。
