# 原有决定（0101–0509）

终局设计之前，项目已有一组决定。按 D59，旧代码不约束设计，但与终局设计一致的方向照常有效。本页按原编号与原分组承接它们：承接的写成现在的规则；修订的写修订后的规则与修订依据；被取代的保留要点并写明取代者。每条写明决定、理由、挡下什么、何时重新讨论、落在哪里；完整规则在“落在”所指的文档中，本页不重复细节。去向总表见[决定目录](README.md#原有决定的去向)。

## 架构

### 0101 组件之间禁止导入代码

- **决定**：一个组件的代码绝不导入另一个组件的代码。能以代码形式跨越组件边界的恰好三类：官方 SDK；组件发布的生成契约包（只有生成的消息类型与客户端，不含逻辑）；可替换成员共用的族契约包（授权、身份，只有生成代码与契约文件，没有逻辑与默认行为）。其余一律经契约调用，两个组件在同一个外壳里也一样。SDK 同步的协议向量与 schema 是测试数据，不算第四类。
- **理由**：两个组件一旦共享代码，不报错也没有警告，直到要拆开部署时才发现拆不动。生成契约包直接导入而不复制：同一份生成代码的两个副本进了同一个进程，会把同一批类型注册两次，启动即崩溃。族契约不属于任何一个成员，所以单独成包。门禁扫描每个组件的导入。
- **挡下什么**：外壳成员之间跳过调用直接调函数；共用的模型或工具包；为复用一个函数导入别人的业务、存储或服务包；复制别人的契约文件自己生成；导入某个成员自己的生成包而不是族契约包；族契约包里带逻辑；直接读别人的表（0102）。
- **何时重新讨论**：业务代码永远不重新讨论。新增第四类可共享的包，必须与上面三类同样性质：不含业务逻辑、没有组件语义、一个进程里只有一份也安全。
- **落在**：[产品的两条不变的原则](../00-overview/01-product.md#两条不变的原则)、[组件实现约定的调用其他组件](../01-conventions/06-component-implementation.md#调用其他组件)、协议 18。

### 0102 每个组件一个 schema（修订：数据库可以共用，也可以分开）

- **决定**：每个组件拥有一个 schema 与两类角色（属主角色只供迁移，运行角色只有业务所需的权限），从注册表照抄；迁移状态表在自己的 schema 里；从不读、写或连接查询别的组件的 schema，别人的数据经契约、事件或数据集取得。库的身份只来自配置（属主角色、运行角色、schema 都必填、没有默认值、互不推导）。一切访问经 SDK 的事务入口，事务内用 `SET LOCAL` 切换。SDK 的平台表在组件自己的 schema 里，组件 SQL 不碰。外壳登录角色以不继承的方式获授成员的运行角色，从不获授属主角色。没有归档 schema：封存的历史按协议 11 转层到组件自己的冷存储。
- **修订**：原决定是“所有组件共用一个数据库”。现在多个组件可以共用实例或数据库，也可以按隔离、热点与恢复预算分开（[在线数据库怎样分离](../04-foundations/02-data-and-lifecycle.md#在线数据库怎样分离)）；外壳按数据库目标分池。分开改变的是物理位置，不改变“不跨 schema”。
- **理由**：每个成员的角色是一道权限墙，外壳借出连接后切到成员的角色，提交时自动复位；库身份只从配置来、在一处 SDK 代码里切换，模块就不会误借别人的 schema。属主与运行角色分开，运行期 SQL（一次注入、一条写错的语句）删不了表。
- **挡下什么**：跨 schema 的连接查询、视图、外键与报表；迁移状态表放在公共 schema；不带 `LOCAL` 的角色切换；从 schema 推导角色、给 schema 写默认值、把角色名写进迁移；服务以属主角色运行；组件 SQL 读写 SDK 的表；模块自己开连接池；自己编 schema 或角色名；第二个存放旧数据的 schema。
- **何时重新讨论**：某个组件需要 PostgreSQL 提供不了的存储能力。
- **落在**：[协议 14 的数据库](../06-protocols/14-data-foundations.md#数据库)、[数据库引擎与连接](../04-foundations/05-database-engine.md)。

### 0103 每种语言一套锁定的技术栈

- **决定**：每种语言内部，技术栈逐格锁定，就是官方 SDK 自己的栈；该语言的组件不能自选。任何地方都不用 ORM。每个后端组件只导出一个模块入口，单独运行与外壳中走同一个入口；模块从运行时取得配置、连接、日志与遥测，不读进程环境、不初始化进程级状态、不退出进程。一种语言只有一个组件时由它自己选栈并写进它的说明；出现第二个组件之前，先给这种语言锁定一列。
- **理由**：外壳在一个进程里运行多个模块，有些格子物理上混不了，另一些能启动然后悄悄出错；锁定框架，SDK 的中间件链在每种语言里只写一遍。
- **挡下什么**：按组件选框架；ORM 与查询构造器；同一种语言出现第二种迁移工具；在入口里自己开连接池、监听、装信号处理或初始化遥测；在还没有锁定一列的语言里加第二个组件。具体的禁用清单见“落在”。
- **何时重新讨论**：表中某个库停止维护，或出现变通补不上的能力缺口；或者出现更新、实测性能更好、适配更好的选择（[底层选择的原则](../04-foundations/README.md#原则)，用户 2026-10-18）：在 SDK 中为该语言的全部组件一次性更换这一格。
- **落在**：[组件协议与语言的锁定的技术栈](../04-foundations/07-component-protocol-and-languages.md#锁定的技术栈)、[组件实现约定](../01-conventions/06-component-implementation.md)。

### 0104 槽位族需要多种合理实现且没有依赖边（修订：D27）

- **原决定要点**：一个功能做成可互换的组件族，要同时满足“成熟系统有真正不同的实现”与“没有组件对这个位置建依赖边”；否则做客户 Fork，或两三个分支的内部策略。
- **修订**：D27 改为优先设计明确的替换点：有独立选配与维护价值、不破坏不变量的，形成独立组件与共同契约（例如成本组件替换计价方法），需要同一一致性边界的留在原组件内经明确接口选择，深度变化才 Fork。原决定中“有依赖的算法差异优先完整 Fork”的排除规则被取代；“不用配置开关把各客户的变体塞进一份代码”“其他组件不直接依赖可替换的成员”仍然有效。
- **落在**：[选择方式](../00-overview/04-selection.md)、[参考实现的几种做法都合理时](../01-conventions/08-reference-implementations.md#几种做法都合理时)、D27。

### 0105 任何语言，一份协议（与 0109 合并）

- **决定**：组件可以用任何语言编写，成为项目成员靠的是语言中立的组件协议，不是语言。进项目、单独运行：当前版本的一致性报告全绿；进外壳：该语言还要有官方 SDK 与外壳启动器。其他语言的组件写明所用协议版本与语言、自己的栈，评审时按协议的“内部”规则逐条核对。JVM 或 CLR 的内存与启动开销是提醒，写进 `BRICKKIT.md`，不是禁令。
- **理由**：住在某一种语言 SDK 里的规则，没法拿去检查另一种语言的组件；对容器做黑盒检查才能一视同仁。外壳是一个进程、一个运行时，所以合并只限于有 SDK 与启动器的语言；这个限制只多花内存，从不影响正确性。
- **挡下什么**：把不同语言的成员合进一个进程；没有全绿报告的组件；为某个组件的语言在官方 SDK 里加特例；JVM 或 CLR 组件对开销只字不提。
- **何时重新讨论**：协议表达不了某个语言生态必需的能力，或太多要紧的规则只能停留在套件测不到的“内部”层。
- **落在**：协议 18、[组件协议与语言](../04-foundations/07-component-protocol-and-languages.md)。

### 0106 基础设施不是组件

- **决定**：消息系统、对象存储、边缘网关、观测栈、身份产品服务器都在组件图之外运行，不是 BrickKit 组件。组件经共享配置访问它们；换法取决于端口的种类：标准协议背后的产品改地址与凭据，消息运输换 SDK 的适配器（通过检查才能用），身份与授权产品前面是可替换的成员组件。
- **修订**：原决定要求同一项目的全部组件用同一个总线适配器；现在不同的业务运输链可以选择不同的合格适配器，同一条链内单选（[消息运输与事件信封](../04-foundations/06-message-transport.md)）。
- **理由**：这些东西里没有项目的代码，包成组件只会多出空的仓库，并把基础设施放进依赖图。
- **挡下什么**：把消息系统、网关、采集器、看板或策略引擎服务器做成组件；组件对基础设施建依赖边；组件直接使用总线客户端而不经 SDK；组件代码读产品专属的配置。
- **何时重新讨论**：写了必须作为其中某一项的一部分运行的真正代码（例如有自己发布周期的网关插件）时，那份代码成为组件；基础设施本身仍然不是。身份适配组件随附的边缘插件属于身份适配组件（协议 20）。
- **落在**：[组件协议与语言的端口](../04-foundations/07-component-protocol-and-languages.md#选择)、[部署与运行](../04-foundations/01-deployment-and-runtime.md)。

### 0107 授权与身份成员的地址是共享变量中的引用，不是依赖边

- **决定**：任何组件都不为了取得授权视图、验证令牌而对授权或身份成员建依赖边；这些地址是共享变量中指向已安装成员的 `$endpoint:` 引用，由 BrickKit 解析，从不手写服务名、端口，也不做端口算术（gRPC 地址是成员自己声明的 `grpc` 端口）。引用不产生启动顺序，可以互相引用；成员不在时可选键不注入、必填键让启动前报错。换成员只改引用指向。调用它们业务接口的组件照常声明依赖。
- **修订**：原决定中的 `IAM_ISSUER` 与 `TENANT_ID` 两键随令牌规格与“不再使用租户”（A53）改变；身份成员切换时，各消费者用于补取与批量读取的身份来源地址是一个单独的部署变量（安全 11）。
- **理由**：依赖钉的是精确版本，若每个组件都对授权与身份建边，两者任何一次发版都会逼全部组件发版；手写服务名是一份必然漂移的副本。
- **挡下什么**：把授权或身份成员写进依赖；手写主机名、服务名或端口；由 HTTP 地址算出 gRPC 地址；每个请求都去身份组件验证令牌；指望平台先启动授权或身份。
- **何时重新讨论**：BrickKit 去掉或改变 `$endpoint:` 的解析；某个族多了一份需要平台先启动其成员的契约。
- **落在**：[协议 19 的配置](../06-protocols/19-config-secrets-registries-release.md#配置)、安全 11。

### 0108 一个外壳一个仓库、一个镜像、一份成员清单（修订：成员清单由客户基线生成）

- **决定**：每个外壳和组件一样是独立仓库，以子模块检出，在自己的仓库发布，只打裸版本标签。一个外壳对应一个镜像与一份成员清单；外壳不写逻辑；启动器在 SDK 里；迁移从成员自己的镜像执行，不在外壳里。外壳注册的成员、成员清单与依赖锁三者一致。
- **修订**：外壳的成员清单与依赖锁由工具从客户的交付基线生成，外壳构建纳入该客户的升级交付（[部署与运行](../04-foundations/01-deployment-and-runtime.md)）；外壳的成员组合在代表部署实验后确定（D40）。
- **理由**：外壳会被别的装配项目复用，都需要用同一份成员清单构建出同一个镜像；成员清单是对镜像内容的承诺。
- **挡下什么**：外壳代码提交在本项目里、启动器复制进每个外壳；在本项目里发布外壳或给外壳打 `v` 标签；外壳里的业务逻辑、路由、数据访问或成员之间的调用；成员换了新版本而外壳不升版本；外壳注册的成员与清单不一致；混放不同语言或不同 SDK 版本的成员；由外壳运行成员的迁移。
- **何时重新讨论**：从来没有别的项目复用外壳时，外壳可以搬回项目里。
- **落在**：[部署与运行](../04-foundations/01-deployment-and-runtime.md)、[协议 17 的外壳义务](../06-protocols/17-runtime-and-resources.md#外壳义务)。

### 0109 规则写在语言中立的组件协议里，由黑盒套件检查

- **决定**：组件要做到的一切，在线上格式、表结构与配置键这一层只写一次（组件协议，独立仓库 `be-protocol`，单独版本化）。每条规则分三级：必须（套件检验）、应当（套件警告）、内部（官方 SDK 用自己的测试与静态检查保证，其他语言书面声明并接受评审）。组件发版需要一次全绿的套件运行。SDK 里不许有规范没写的行为：先改规范与向量，再加一条先跑出红的套件用例，再改各 SDK。协议的小版本只增加可选的面。
- **理由**：组件可以用任何语言写，住在某一个 SDK 里的规则当不了规则；三个 SDK 过同一套套件，它们的等价才有证据。
- **挡下什么**：只存在于某个 SDK 里的规则；没有全绿套件运行就发版；协议规则的按语言变体；手工把向量拷进 SDK；先写实现、后写从没见过红的套件用例。
- **何时重新讨论**：要紧的规则从外面观察不到、太多只能停在“内部”；或维持三个 SDK 等价的成本超过自由选语言的好处。
- **落在**：协议 18、A99（规则在重建 `be-protocol` 时从安全与协议文档中抽出）。

## 权限

### 0201 不用 Redis，不设缓存服务器

- **决定**：项目不运行 Redis 或任何其他缓存服务器。缓存只存在于一个成员的进程内，经 SDK 创建，带容量上限、有效期、并发回源只回源一次、指标与由事件触发的失效；要在副本之间共享或扛过重启的东西，是组件自己 schema 里的表。
- **修订**：原决定中“绝不跨请求缓存授权判定”由 D57 修订：授权视图是带有效期的本地数据，在有效期内经权威核验（安全 03）；其余授权结果仍不跨请求缓存。
- **理由**：通常引入 Redis 要解决的问题都已有着落（会话在身份适配组件，授权视图在本地，别人的数据以快照保存、靠事件刷新，并发控制靠行锁、事务级应用锁与租约，幂等是一张表，限流归边缘）；客户在资源有限的机器上部署，每多一个基础服务就多一样要安装、备份、加固、监控的东西。按成员创建的缓存天然合并安全。
- **挡下什么**：在查询前面放一层 Redis；会话、令牌、分布式锁、计数器、序号、限流或消息队列放在 Redis；模块里用包级或无上限的缓存。
- **何时重新讨论**：见[底层选择的缓存一行](../04-foundations/README.md#推荐组合与改选条件)。
- **落在**：底层选择 README、[协议 17 的多副本](../06-protocols/17-runtime-and-resources.md#多副本)。

### 0202 权限在本地判定（修订：D57 有界本地授权）

- **原决定要点**：每次访问判定都在组件自己的进程里做，依据定期拉取的授权包与组件 schema 中的直接授予投影；热路径上没有网络跳；授权服务不可达时继续用最后一份。
- **修订**：D57 的有界本地授权：每个组件持有授权视图与投影，在有效期（`W_read`、`W_high`）内经权威核验；过期按保护处理，不再“无限期使用最后一份”；可选严格路径（持久接受与提交屏障）。授权组件不可达时，高风险操作先停，普通读取在有效期内继续（安全 03）。“业务组件不持有权限表与角色副本”“健康检查不查授权”“路由注册必须带操作定义”仍然有效。
- **落在**：安全 03、[协议 17 的过载与依赖故障](../06-protocols/17-runtime-and-resources.md#过载与依赖故障)。

### 0203 令牌只承载身份，主体归平台所有（修订：令牌内容）

- **决定**：令牌只说明调用者是谁，不带任何权限键、功能开关或数据范围规则；主体身份由平台签发与持有，身份产品自己的标识只在身份适配组件的关联中，换身份产品不改写任何归属、授予或审计行（安全 02 的稳定主体）。验证时签名算法取自公钥、密钥标识必填，并校验签发者、受众、有效期与令牌用途，请求上只接受访问令牌。
- **修订**：令牌也不再携带角色、部门、租户与语言（安全 02；语言从用户资料取得，协议 14），访问令牌的有效期按协议 19 的参数（浏览器入口按 D61），受众不再是租户（A53）；浏览器不持有应用令牌，会话在身份适配组件的服务端（D61）。
- **理由**：身份随用户数增长，策略随角色数增长，各放在能保持小的地方；放在令牌里的权限只有令牌过期时才会变。
- **挡下什么**：把权限、范围或功能开关放进令牌；把身份产品的标识当用户身份；接受用途或签发者、受众不符的令牌；前端根据令牌内容判定访问并当作安全措施。
- **何时重新讨论**：对权限永不重新讨论；新增身份属性的前提是支持的每个身份成员都能签发它。
- **落在**：安全 02、[协议 20 的登录与会话](../06-protocols/20-frontend.md)。

### 0204 权限是纯并集，管理员不能加 Deny（修订：按完整授予判定）

- **决定**：管理员可以加的规则里没有负权限、黑名单与规则顺序；“这个人为什么能做这件事”只有一种答案：给出它的那条授予。要表达“除 X 以外的一切”，就给一个不含 X 的角色。委托链上取交集，行事者不超过被代表的人（安全 05）。
- **修订**：原决定的并集是“各角色的键、每键取最高档位、维度取值求并集”；终局设计按每一份完整授予逐份判定，按维度压平汇总被证明会放宽访问，已退役（安全 01、06、07）。业务上的强约束（本人自审、期间锁、冻结、安全处置）单独建模，不是管理员可加的负权限（安全 01、08）。
- **挡下什么**：“除了某人”“禁止某类人导出”这样的负权限；规则之间的优先级；把安全处置或业务约束当作 Deny 来配置。
- **何时重新讨论**：某项监管要求只能表述为凌驾于所有授予之上的禁令，而且任何角色拆分都无法表达它时。
- **落在**：安全 01、05、07、08。

### 0205 数据范围的规则随版本发布

- **决定**：决定一个操作能触及哪些行的规则（资源类型的维度、操作、字段、关系与共享）是组件版本的一部分，在资源定义中声明，只能随新版本改变；维度不能缺省，安全设置不能默认关闭。谁得到哪一部分是授权组件中的运行时数据。
- **理由**：写在版本里的规则可以评审、对比、测试与回滚，同一版本对每个客户都一样；真正每天在变的是谁得到什么。
- **挡下什么**：在运行时编辑规则或在后台界面写公式；先全部查出来再在调用方过滤（分页当场出错）；列表与单条检查不一致；因为“用不上”而省略维度声明；在用户请求路径上用组件的服务身份。
- **何时重新讨论**：某个客户必须在两次发布之间修改行规则（不是授予），而且频率高到发布节奏跟不上时。
- **落在**：安全 09a 的资源定义、安全 07。

### 0206 不用行级安全；共享引擎只在授权组件

- **决定**：数据范围的条件由 SDK 按授予段编译成参数化 SQL（安全 07），不使用 PostgreSQL 的行级安全。共享与关系只在授权组件，组件不自建共享表。任何组件都不保留组织树的副本；没有部门的主体不贡献任何部门条件，空路径不是树的根。
- **理由**：静态参数化 SQL 能表达项目里的每一个维度，规则留在评审者会读的地方；行级安全给规则添了第二个家，还有一个无声的陷阱：表的属主默认绕过它，池化连接上的会话设置与外壳也让它难以正确使用，结果也无法解释。
- **挡下什么**：给表开行级安全、建策略；组件自建共享机制；组织树副本与递归查询；把空部门路径当作根；按跨越另一个组件父记录继承来的可见性过滤列表；给不属于部门的表加部门列。
- **何时重新讨论**：某个真实的范围无法写成有限表达，而且没有安装能回答它的授权成员时。
- **落在**：安全 07、FX06。

### 0207 授予放在授权组件（修订：完整授予与有限表达）

- **决定**：谁得到规则的哪一部分（授予、期限、共享、委托）是授权组件持有的运行时数据，由有权的管理者编辑；业务组件不持有任何授权表，也不提供授予管理接口；每个资源维度恰好有一个属主组件。
- **修订**：原决定中的档位（本人、部门、子树、全部）、多角色取最高档、取值求并集、未写档位视为本人，被安全 07 与 09a 的有限表达（含树原子）与完整授予段取代。
- **理由**：授予集中在一处，就只有一个管理界面、一条审计线，每个判定只有一种解释。
- **挡下什么**：业务组件里的仓库授权、法人授权一类表与编辑它们的接口；用一个“管理员”权限键扩大范围；两个组件声称拥有同一个维度；用事件把授予同步进组件自己的表。
- **何时重新讨论**：某项授予取决于只有属主组件才有的行属性时：那是规则，属于组件的版本。
- **落在**：安全 04、07、09a。

### 0208 两个调用面：组件之间用 gRPC，人用 HTTP（修订：系统面的信任）

- **决定**：系统调用走 gRPC 系统面，用户请求走 HTTP 用户面；服务代理用户的请求走用户面，带原用户的凭据并另加服务身份的验证。用户凭据不适用于系统方法，服务凭据不适用于普通用户数据接口；浏览器与移动应用不直接调用 gRPC。
- **修订**：原决定中“系统面上的调用方由 `be-caller` 指明、可信度与网络相同、服务令牌以后启用”被安全 02 取代：每部署的信任根与服务凭据，按部署声明的“服务到方法”许可准入，`be-caller` 只是与验证结果核对的标签。
- **理由**：一条任何开发者都能遵守的规则；范围受限的读取不会因疏忽而用组件自己的身份发出。
- **挡下什么**：返回按用户范围过滤的行的系统方法；信任传播的用户标签来判定访问；在用户请求路径上用服务身份；代理用服务身份替用户取数据。
- **何时重新讨论**：浏览器必须直接调用 proto 契约，或需要支持用户 gRPC（单独声明调用模式与兼容版本，安全 02）。
- **落在**：安全 02、[组件间调用与错误](../04-foundations/08-calls-and-errors.md)。

### 0209 授权是可替换的成员

- **决定**：授权由一个可替换的成员组件提供，经族契约访问，组件不依赖某个成员、不调用成员私有的接口。列表与单条检查一致是契约的一部分。成员提供的能力在装配时核对：组件声明所需能力，成员提供不了时装配准入失败（安全 09b），不在运行时悄悄降级。换成员时按安全 10 的切换协议迁移，装不下的状态阻止切换。
- **修订**：原决定的运行时能力协商改为装配准入；静态策略与关系图成员改为远期，策略引擎（Cedar、OPA）只在有真实需求时评估。
- **挡下什么**：依赖某个成员或它的私有接口；能力靠假设而不是声明；成员悄悄丢掉装不下的东西；基于成员私有接口做管理界面；由策略条件决定列表返回哪些行之外的行为。
- **何时重新讨论**：某个客户的模型即便新增一项能力也放不进族契约；或族在实践中收敛到一个成员。
- **落在**：安全 06、09b、10，[授权选型](../00-overview/guides/authorization.md)。

### 0210 委托与扮演不超过被代表的人；代理人只留位子

- **决定**：一个主体代表另一个主体行事时，有效权限是行事者自己的权限与链上每一层上限的交集，每次请求现算，不快照：被代表的人被撤权，所有代表他的人同时失去。休假代办、只读扮演（通知被查看者、全程记录）按安全 05；AI 代理人只在契约中留位子，不开发。
- **挡下什么**：委托或扮演超过被代表的人，或在其被撤权后仍保有权限；把委托人的权限复制进代理人的角色；能写入的扮演、不记录的扮演、被查看者永远不知道的扮演；现在就开发代理人。
- **何时重新讨论**：项目开始做 AI 代理人，或监管要求生产环境关闭扮演时。
- **落在**：安全 05、[业务 AI 只留位子](../00-overview/03-catalog.md)。

### 0211 字段级权限在源头执行

- **决定**：只有部分人能看的字段由资源定义中的字段声明守护；属主组件在答复离开它之前掩码；写入不可读的字段被拒；按调用者不能读的字段排序、筛选或汇总，一律拒绝（`FIELD_NOT_QUERYABLE`）；字段只在它所在的行可见时才可见。事件属于系统面，不原样展示给人。
- **理由**：在源头掩码是唯一绕不过去的地方；按受限字段排序与筛选会泄露它想藏的值。
- **挡下什么**：在前端、移动聚合或调用方掩码；每个组件单独一张字段权限表；按看不到的字段排序或合计；用字段权限扩大可见的行。
- **何时重新讨论**：同一个人对同一个字段，必须在某些行上可见、另一些行上不可见，而行级范围表达不了时。
- **落在**：安全 01、07、09a。

### 0212 看不见的记录答 404，读取与命令一致

- **决定**：记录不存在与“存在但调用者看不见”答同一个 404，读取与命令一样；403 永远意味着“看得见，但不能做这件事”。命令先检查可见性再查幂等键，看不见这条记录的人重放命令，得不到存下的结果。
- **修订**：状态不允许由原来的 400 改为各业务的 reason（409 或 422，安全 09a）；请求参数中越界的维度取值按 A106。
- **挡下什么**：对范围外的记录答 403；能区分“被隐藏”与“不存在”的错误详情或 reason；把存下的幂等结果返回给看不见记录的调用者。
- **何时重新讨论**：法律或审计要求系统告诉用户某条记录存在但不予提供时。
- **落在**：[安全 09a 的求值结果与错误](../06-protocols/security/09a-encoding-and-records.md#求值结果与错误)。

## 契约与数据

### 0301 金额是与币种成对的十进制字符串；列表按游标分页

- **决定**：每份契约里的金额、单价、数量、汇率与比率都是十进制字符串，每个金额带币种（ISO 4217）；每个法人有本位币，外币单据快照汇率、日期与类型；汇率归 `mdm/currency`。解析、格式化、舍入与分摊只在 SDK 中做，三种语言共用向量。每个列表按不透明游标分页，契约里没有偏移量。
- **理由**：浮点会丢精度，三种语言的舍入各不相同；不带币种的金额没有意义；深偏移量每翻一页都更慢，还会在翻页时重复或漏掉行。
- **挡下什么**：浮点或 JSON 数字表示金额；没有币种的金额；组件里手写舍入；汇率放在业务组件里；列表请求里的偏移量或页码；“跳到第 N 页”（改用筛选缩小结果）。
- **何时重新讨论**：永不；某一列需要更多整数位时只加宽那一列。
- **落在**：[协议 14 的金额与列表](../06-protocols/14-data-foundations.md#金额数量汇率与单位)、[列表：游标、排序与筛选](../06-protocols/14-data-foundations.md#列表游标排序与筛选)。

### 0302 契约只做加法（从新版本发布之后约束）

- **决定**：已发布的契约（接口、事件、错误 reason）只增不减：字段不删、不改名、不改类型或编号，事件类型与 reason 不删不复用，字段的含义与单位不变，新字段对现有消费者是可选的。破坏性变化由人决定，以新的主版本（用户面的新路径前缀、系统面的新版本包、事件的新版本）与旧的并存发布，旧的经弃用与下线公告后才删除。门禁检查破坏性变化。
- **修订**：按 D59，这条从新设计的第一个正式版本发布之后开始约束；协议 19 补充：新增字段或枚举也可能影响旧消费者，“追加”不自动等于兼容，含义变化按破坏性变化处理，旧版本的退出依据客户基线。
- **理由**：消费者（包括客户 Fork 与客户的其他系统）会继续对着旧版本运行；破坏性变化迫使每个消费者同步修改、同步发布，漏改的事件消费者会在运行时失败。
- **挡下什么**：改名、改类型、复用编号；删除废弃的字段、方法、事件或 reason；把可选字段改成必填；名字不变却改变含义；用请求头或查询参数做破坏性变化；下线日期之前删除旧操作。
- **何时重新讨论**：永不原地修改；错得无法修补的契约按新主版本并存。
- **落在**：[协议 19 的版本与产物](../06-protocols/19-config-secrets-registries-release.md#版本与产物)、协议 10 的开放接口。

### 0303 测试账号不写进迁移

- **决定**：迁移里只放每个部署都需要、又不依赖客户信息的产品基线数据（科目模板、计量单位、标准代码）；法人与依赖法人的数据（仓库等）在安装或上线时建立。测试用户、角色、密码、客户端与演示数据只由开发者手动运行的种子命令创建，绝不由任何部署或 CI 步骤创建。
- **修订**：首个管理员不再按身份源的登录名或邮箱指定（原 `BOOTSTRAP_ADMIN_LOGIN`，不区分大小写匹配会被抢先登录利用），改为安装认领：精确身份预先登记或一次性离线确认（安全 02、08）。种子与测试取得真实令牌的方式按 A101。
- **理由**：迁移在每一次部署时都会运行，写进迁移的账号就是一个密码公开、拥有全部权限的后门。
- **挡下什么**：迁移里的测试账号、默认密码或演示数据；种子步骤直接插入授权表；在部署、镜像入口或 CI 里对真实环境运行种子；为了方便测试，在正式环境的登录客户端开启密码授权。
- **何时重新讨论**：涉及身份与凭据时永不。
- **落在**：[种子与测试数据的凭据与部署](../01-conventions/07-seed-and-test-data.md#凭据与部署)、安全 02、08。

### 0304 按身份批量读取每次最多 500 个，上限是契约的一部分

- **决定**：每个聚合根在系统面提供按身份批量读取，用于补全调用方已经持有的身份；一次最多 500 个，上限写在契约里，由运行时在组件代码之前执行，超限拒绝而不截断。更多的调用方自行切分；组件从不逐个调用来解析一组身份；批量读取不用来枚举或搜索（那是带游标的列表）。
- **理由**：没有上限，一个请求就能让被调方在一个截止时间内加载无限多行；写进契约，每种语言与每个评审者读到的都是同一个数字。
- **何时重新讨论**：某个实测的调用方在热路径上每次需要更多，并且切分的代价超过了对被调方的保护时，只为那个方法以追加放宽。
- **落在**：[组件实现约定的调用其他组件](../01-conventions/06-component-implementation.md#调用其他组件)、[组件间调用与错误](../04-foundations/08-calls-and-errors.md)、协议 02（不完整行的取回）。

### 0305 3.0.0 一次性重建基线（已被 D59 取代）

- **原决定要点**：只对 3.0.0 统一升级，在没有任何生产数据的条件下，允许整体替换已发布的迁移与线上格式，不做兼容层，并列明打破的每一处；以后不得援引。
- **取代**：D59 把同样的条件推广为整体重建：终局设计视为第一个正式版本，不承担现有代码与契约的迁移兼容；组件、契约与数据库按新设计重建，版本统一从 `3.0.0` 起（A110）。进入正式的版本发布之后，迁移只向前，契约按 0302 约束。

### 0306 自有主键用 UUIDv7；单号由 SDK 分配

- **决定**：每个自有主键是 UUIDv7，由组件在插入前经 SDK 生成，不靠列默认值；对其他组件记录的引用是不透明文本、不建外键。必须严格单调的计数与以标准代码为键的参照表是例外。给人读的单号来自 SDK 唯一的一套编号机制，按法人与期间划分范围；凭证等连续序列不缺号，其他允许缺号但永不重复。
- **修订**：原决定中“分区表的创建时间就是身份里的时间戳、按身份只探一个分区”被 A05 取代：分区键是显式列，按身份经身份登记表定位。库内计数带纪元（A48）。
- **理由**：UUIDv7 合并时不冲突、可以在到达服务端之前生成（离线草稿、幂等的新建）、不泄露业务量，时间前缀保持索引局部性；可读性是单号的职责。
- **挡下什么**：自增主键；列默认值生成主键；身份里带类型前缀；指向别的组件记录的外键；由身份拼出的单号；组件自己写编号代码；会出现缺号的凭证编号。
- **何时重新讨论**：身份总体上永不；连续编号撞上串行吞吐上限、业务接受换编号时点时。
- **落在**：协议 14 的身份与唯一性、单号。

### 0307 业务日期按法人日历

- **决定**：时刻（`timestamptz`，线上 UTC）与业务日期（`DATE`，不在时区之间换算）从不混用。业务日期是某个时刻在其法人业务时区里的民用日期；数据库会话时区永远是 UTC，业务 SQL 不问数据库“今天”。事件带单据的业务日期，消费者按业务日期记账。会计期间是带起止日期的行（期间归财务，D05）。显示时业务日期原样显示，时刻按法人时区并标明时区；没有按用户的时区偏好。
- **修订**：法人时区与会计年度起始没有隐含的默认值，建立法人时明确，可以来自部署配置声明的默认值并写进法人记录（A06）；定时任务按法人时区，不再用部署级的业务时区；13 期与 4-4-5 由财务组件支持。
- **理由**：一张单据对所有人属于同一天；集团公司可能分布在不同国家，时区不能是部署级常量；共享连接池上的会话时区不安全。
- **挡下什么**：业务 SQL 里的“今天”、会话级时区设置；业务日期存成时刻或取自处理事件的时间；整个部署一个业务时区；每年一份迁移去建期间。
- **何时重新讨论**：用户需要按自己的时区看时刻时（只是显示偏好）。
- **落在**：[协议 14 的时间、日历与期间](../06-protocols/14-data-foundations.md#时间日历与期间)、组织卡。

### 0308 一个客户一套部署；公司是部署内的法人（不再使用“租户”）

- **决定**：一个客户一套部署，没有多个客户共用数据库的模式；一个客户下的多家公司是法人，是部署内的业务维度：每张交易单据与相关事件带法人，单号按法人与期间划分，每个法人有自己的日历与本位币，法人是授权维度。
- **修订**：设计中不再使用“租户”这个词，令牌与契约中不预留租户字段（A53）；预留的令牌字段不证明支持共享 SaaS（[底层选择的跨方面约束](../04-foundations/README.md#跨方面的约束)）。
- **理由**：客户之间的隔离就是部署本身，这是最强的隔离；集团多公司现在就需要，必须在一套安装里共用主数据、用户与角色。
- **挡下什么**：任何表里的租户列；一套部署服务几个互不相干的客户；同一集团、共用主数据的各家公司各自一套部署；交易单据或事件缺少法人（缺法人的拒收，协议 14）。
- **何时重新讨论**：共享的多客户产品成为产品决策时，作为专项设计。
- **落在**：[系统视图](../00-overview/08-system-views.md)、[术语表](../00-overview/07-glossary.md)、协议 14。

## 运行时

### 0501 事务里不发网络调用

- **决定**：持有打开的数据库事务期间，不发任何网络调用（其他组件、外部服务、直接往消息系统发布）。事务要在数据库之外产生效果，只有同一事务里写下的一行：发件表（提交后发布事件）或工作项（提交后在事务外执行，带重试与升级处理）。官方 SDK 强制：事务内的出站调用拒绝开始，一个工作单元里不开第二个事务、不同时持有两条连接；其他语言的组件把它作为“内部”规则说明怎样守住。
- **理由**：事务里的网络调用会在下游的耗时内一直持有行锁；重试事务体会把调用再发一遍；连接池有上限时，等第一条连接时再占第二条，正是池子自己死锁的方式。写成同一事务里的一行，效果当且仅当业务变更提交时才存在。
- **挡下什么**：事务中间调用别的组件或外部服务；绕过发件表直接发布；提交后尽力而为地调一下、失败了没有东西重试；嵌套事务；为“就这一个处理函数”关掉守卫。
- **何时重新讨论**：规则本身永不；真正需要在提交前拿到同步答复的步骤（用户等着的预占），按协议 04 的分支协议设计，放在事务之外。
- **落在**：[事务与消息的本地事务](../04-foundations/03-transactions-and-messaging.md#本地事务)、协议 01、04。

### 0502 默认 READ COMMITTED，配一架明确的阶梯；只重试序列化失败与死锁

- **决定**：默认隔离级别是 READ COMMITTED，单个事务可以声明更严的级别，默认值永不改变。每个不变量点名它的手段，取阶梯上第一个能表达它的那一级：约束；条件更新；按固定顺序加行锁（请求里的重复项在加锁前拒绝）；键里带组件 schema 的事务级应用锁；只对这一个事务用 SERIALIZABLE 并写明原因。每个事务用 `SET LOCAL` 设定自己的超时；成员角色上的设置在 `SET ROLE` 之后不生效，不作为保护（协议 14）。运行时只重试序列化失败与死锁，在新事务里重跑整个事务体，次数有限、带退避；锁超时与语句超时在这一层不重试。应用锁只用事务级的。
- **理由**：ERP 的热点（每个产品与仓库一行库存、一个法人的期间）争用激烈；READ COMMITTED 下对它们的条件更新会等待、然后基于最新的行继续，全局更严的级别会把同样的争用变成中止。每个不变量点名一级阶梯，评审就能逐条核对。
- **挡下什么**：“为了保险”调高默认级别；按请求顺序给多行加锁；会话级锁与不带 schema 的锁键；不带 `LOCAL` 的设置或依赖角色级设置定超时；组件代码自己给事务套重试循环。
- **何时重新讨论**：出现一类实测、反复发生、阶梯上任何一级都表达不了的异常时。
- **落在**：[协议 14 的数据库](../06-protocols/14-data-foundations.md#数据库)、事务与消息的本地事务。超时的起始值见协议 14 的参数表（事务内空闲由原 30 秒改为 10 秒）。

### 0503 截止时间只减不增；重试由契约决定、受预算约束（修订：采用熔断）

- **决定**：每个请求都有截止时间，随调用逐跳传递、只会缩短；方法能不能重试由契约声明，只在下游不可用时重试，次数有上限，每个（成员，依赖）有重试预算；只有一层重试，更高一层的重试沿用同一个幂等键；出站并发有上限，满了立即失败、不排队；不用对冲请求。
- **修订**：原决定“用舱壁，不用熔断器”被 A103 取代：按每个下游维护熔断，让调用方快速失败、保护自己的并发与连接（协议 17）。
- **理由**：有界的等待与有界的损害保护用户；由契约决定能否重试，就没人需要逐个调用判断，也不会出现成倍放大的嵌套重试。
- **何时重新讨论**：多节点出现部分故障时加离群检测与按请求均衡；某个依赖的固定上限经实测不合适时改为自适应。
- **落在**：[协议 17 的组件之间的调用](../06-protocols/17-runtime-and-resources.md#组件之间的调用)、[组件间调用与错误](../04-foundations/08-calls-and-errors.md)。

### 0504 一种错误对象，由目录中的 reason 标识

- **决定**：一种错误对象原样穿过每个面：用户面是 RFC 9457 problem details 带 AIP-193 `ErrorInfo` 的字段，系统面是带 `ErrorInfo` 的 `google.rpc.Status`，移动聚合的 GraphQL 放在 `extensions` 里，运行时负责映射。`domain` 加 `reason` 标识错误：每个组件在契约中声明自己的 reason，只追加，带各界面语言的消息模板；平台的 reason 随组件协议发布，组件不在自己的 domain 下抛它们。前端负责翻译。内部错误一律答通用的 reason 与追踪身份，原始错误只进日志。运行时产生的每个非成功回答都带 reason；取消与依赖不可用有专门的 reason，不落进内部错误。日志级别跟随结果类别，由 SDK 决定。
- **修订**：授权与安全类结果的 reason 在安全 09a 登记；错误目录的最终名称与格式在重建 `be-protocol` 时写入组件协议。
- **理由**：错误经多跳到达浏览器或手机，每一跳不必重新发明；机器 reason 让错误可测、可翻译；内部错误由运行时映射，按构造就不会泄露。
- **挡下什么**：第二种错误形状；不在目录里的 reason；改名、删除或复用 reason；服务端翻译的消息作为唯一标识；错误详情中的数据库消息、堆栈、密钥或个人信息；把依赖有意义的 reason 映射成更含糊的；把取消或连不上的依赖报成内部错误。
- **何时重新讨论**：通知与打印之外也需要服务端文本时，以追加的方式增加。
- **落在**：[组件间调用与错误](../04-foundations/08-calls-and-errors.md)、安全 09a。

### 0505 信封是二进制模式的 CloudEvents（修订：投影的接收规则）

- **决定**：信封是 CloudEvents 1.0 的二进制模式：信封在消息头里，载荷就是业务对象；项目的扩展属性同样在头里，字段清单只在协议 02 的 S2。契约文件就是注册表，构建时检查；没有运行期的 schema 注册服务。跳数超过上限或发现环的事件按协议 02 的接收规则处理（隔离或停住，不跳过）。
- **修订**：原决定的“消费者按聚合流记游标、比游标旧的版本一律跳过、默认状态模式”被协议 02 的接收规则取代：只有可覆盖的状态投影按版本处理；不可遗漏的增量事实按序号处理，不能跳过（事务与消息的事件分类）；先看实现实例与纪元，再比较版本；用水位的消费者按来源的连续位置推进。
- **理由**：信封必须经得起换运输；CloudEvents 的命名是中立的标准，各种运输都能带头。
- **挡下什么**：自定义的消息头；在载荷里重复信封；把业务数据放进头；靠消息系统的顺序保证正确性的消费者。
- **何时重新讨论**：外部方订阅事件时，从契约文件生成 AsyncAPI，线上不变。
- **落在**：[消息运输与事件信封](../04-foundations/06-message-transport.md)、[协议 02 的接收规则](../06-protocols/02-projections.md#接收规则)。

### 0506 事件至少送达一次（修订：流的划分与新消费者的初始化）

- **决定**：发布只经发件表，与业务变更同一事务写入，消息系统确认持久化之后才标为已发布，不可用时等待重试、永不丢弃。送达至少一次，消费者以收件表或连续位置去重，与业务写入同一事务；带外部副作用的处理按业务键幂等。不承诺恰好一次。发件表是回放的事实来源，消息系统的保留只是运输缓冲。
- **修订**：原决定中“每个主题第一段一个流、每（组件，主题）一个持久消费者、新消费者从流里全部消息开始、可丢的信号走不持久的通道”改为：每条记录的事件只进一个分区，分区键只由记录身份算出（协议 02 的 S2）；新消费者经对齐与快照取得历史，不能用流里剩下的消息证明全部历史（协议 02、事务与消息）；发件表的保留不短于对齐与离线的时长（协议 15）；死信不依赖“第 N+1 次投递总会到达”，由最后一次失败的处理接管。流与持久消费者的命名、默认保留与去重窗口在重建 `be-protocol` 时写入组件协议。
- **挡下什么**：直接往消息系统发布，或删除尚未确认的发件行；假设恰好一次的消费者；没有幂等键的外部副作用；单跑与外壳、各副本之间名字不同的持久消费者。
- **何时重新讨论**：某个客户统一用 Kafka（建适配器并通过检查），或某个流实测负载过高（按分区拆分，仍用 JetStream）。
- **落在**：[消息运输与事件信封](../04-foundations/06-message-transport.md)、协议 02、15，[事务与消息](../04-foundations/03-transactions-and-messaging.md)。

### 0507 幂等键按调用方划分命名空间，并绑定到命令

- **决定**：命令的幂等键属于它的调用方，被调方按（调用主体，键）记录；键绑定命令、目标与规范化输入的指纹，同一个键换了内容即失败，进行中的认领答“处理中”，已完成的返回存下的结果。认领是原子的（插入并在冲突时不做）。检查按固定顺序：校验参数，授权目标，再查或认领键，再检查状态，最后写入；返回旧结果前重新验证调用者的资格。事件处理为下游命令使用的键由事件派生，重投就是带同一个键的重试。
- **修订**：键的保留由原来的固定 30 天改为按最长重试、重放、死信重投、恢复窗口与业务重启路径确定；短期的请求结果缓存与长期的业务唯一性分开，已处理的财务与资金事实不因键过期而重新生效（事务与消息的去重寿命、DT24）。
- **挡下什么**：所有调用方共用的键空间；对内容不同的请求返回存下的结果；先普通查询再插入来认领；在检查授权之前查键；任何一层用新键重试同一个意图。
- **何时重新讨论**：两个不同调用方必须共享同一个命令结果时：那是业务引用（一个订单号），不是共享的幂等键。
- **落在**：[事务与消息的本地事务](../04-foundations/03-transactions-and-messaging.md#本地事务)、协议 10 的开放接口。

### 0508 后台工作只经 SDK 的工作项

- **决定**：组件里每一项不由请求触发的工作，都在模块的一处声明，由 SDK 运行与监督（协议 01 的工作项：每副本、单例、定时、队列与对账）。启动钩子只做一次性初始化，从不启动循环；失败的工作按退避重启，一个停下不影响其他，单跑与外壳一致；每次运行有时限。不用外部调度器与数据库调度扩展。需要独立进程时分三步：工作留在进程里；重的工作挤占邻居时，把它的组件移出外壳、单独设资源上限；实测仍不够，才经“跑一次就退出”的入口从外部触发，它抢的是同一个认领，谁触发都只执行一次。
- **修订**：定时任务按法人时区，不再用部署级的业务时区；对账不再是单独的种类，并入工作项。
- **理由**：一个监督器在两种形态与每种语言里行为一致，多副本时不需要领导者也正确；在业务事务里入队，异步命令当且仅当业务写入提交时才存在。
- **挡下什么**：模块代码里的定时器、线程或睡眠循环；从启动钩子启动循环；提交后在后台调一下却没有工作项；没有时限的工作。
- **何时重新讨论**：作业量大到数据库撑不住（入队改走消息运输），或出现跨多人、多天的长流程（评估工作流引擎）时。
- **落在**：[协议 01](../06-protocols/01-background-work.md)、[组件实现约定](../01-conventions/06-component-implementation.md)。

### 0509 边缘只做流量处理，认证与授权留在服务里（修订：D61）

- **决定**：边缘负责 TLS、路由、请求体上限、超时、粗粒度限流、追踪与请求身份、剥掉可伪造的头；不充当唯一一道认证或授权，不套用数据范围，不按业务内容路由，不缓存接口响应，不重试带请求体的请求；永不路由 gRPC 端口、健康与指标端点、内部操作。每个服务自己验证令牌并判定授权，不管前面有没有边缘。路由由声明生成，以路径段为界，从不手写。边缘自己产生的回答带平台的错误对象。
- **修订**：D61 让边缘按会话缓存短期令牌（由身份适配组件随附的插件实现），并在 `TOKEN_STALE` 时换取新令牌、重试一次已缓存请求体的请求；这不改变“服务自己验证”。
- **理由**：“每个组件都能独立运行”也包括前面没有网关时照样安全；只在边缘验证，绕过边缘或单独部署一个组件就等于全部敞开。
- **挡下什么**：只在网关验证令牌再信任网关设置的头；在边缘判定权限、范围、字段或配额；把内部端点暴露到外部；手写路由；以字符串比较的前缀规则。
- **何时重新讨论**：客户的安全架构要求在网关上再加一层认证时，它加在边缘前面，不取代服务里的验证。
- **落在**：[边缘入口](../04-foundations/09-edge.md)、协议 20。
