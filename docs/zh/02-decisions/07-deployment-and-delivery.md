# 部署、交付与维护

每条决定写明：决定了什么、为什么、没有采用什么、现在落在哪里。来源与日期见[决定目录](README.md)。

## D25 标准交付允许预告的维护窗口，连续升级另做专项验收

- **决定**：标准允许明确、预告且经验证的维护窗口：受影响的业务在迁移与验证期间暂停，完成后恢复；连续运行的客户另选经过专项验收的在线升级方案。正式客户的数据必须保留；多副本或滚动部署本身不证明在线升级能力。
- **理由**：单机、私有化与资源受限的组合可以用清楚的维护计划可靠升级，不让全部客户承担并行升级的复杂度。
- **不采用**：从初期把升级期间持续服务作为标准要求。
- **落在**：[部署与运行的升级与维护窗口](../04-foundations/01-deployment-and-runtime.md#正式客户升级与维护窗口)、[协议 17](../06-protocols/17-runtime-and-resources.md#维护窗口中的升级)、[运维手册](../05-operations/02-upgrade-and-maintenance.md)。

## D32 客户授权人员调整有限业务设置，部署参数仍由 BrickKit 管理

- **决定**：有限业务设置归所属业务组件，由客户授权的人员经管理界面调整，有范围校验、版本与生效规则和审计；部署与运行参数由 BrickKit 的配置管理。只开放组件明确允许的设置，不能关闭必需的权限、职责分离与完整性控制；不提供任意编程的设置界面。
- **理由**：客户在标准能力内调整日常参数，不为改一个阈值走部署。
- **不采用**：业务参数由维护方审核、随版本交付。
- **落在**：[工程规范的有限业务设置](../01-conventions/01-engineering.md#有限业务设置)、[协议 19](../06-protocols/19-config-secrets-registries-release.md)；扩展字段见协议 08。

## D40 组件独立开发，外壳优先候选，组合与引擎测后确定

- **决定**：组件独立开发与验证，外壳在装配与部署时合并；外壳优先是候选取向，与失去的独立发布、扩容与故障边界一起比较，按客户与实测选择单跑、外壳或混合。Podman 是重点候选，未定为默认。外壳不引入跨组件源码调用、共享业务表或共同事务；引擎选择与是否合并是两个独立维度。
- **理由**：客户需要的组件数量与部署成本各不相同；先证明模式成立，再形成交付组合。
- **不采用**（作为固定默认）：默认独立进程、外壳按需。两种取向都作为可验证方案。
- **落在**：[部署与运行](../04-foundations/01-deployment-and-runtime.md)、协议 17。
- **修订**（2026-11-02，代表部署实验之后）：默认引擎由 D80 定为有根 Podman；默认的拓扑与外壳的成员组合见 [A112](09-ai-choices.md)，连接池代理与运输见 A113、A114。

## D41 先补最小目标条件并做部署对照，再推广重建

- **决定**：先补齐最小必要的目标版 SDK、代表组件与外壳，验证少组件与较完整组合、单跑、外壳、混合、Docker 与 Podman 的代表格；按结果修订底层方案，再按新设计重建当前范围的组件（D59 之后读作“重建”，不是升级旧组件）。完整容量与长期性能基线在重建之后。
- **理由**：在小范围内检验部署选择、外壳兼容、共享故障与引擎差异，不把未验证的假设批量推广。
- **不采用**：先完成全部组件，再比较部署方式。
- **落在**：[路线](../00-overview/06-roadmap.md)、[测试与验证的代表部署对照实验](../01-conventions/02-testing-and-validation.md#代表部署对照实验)。

## D42 无公网交付不作为当前必选条件，正常联网路径优先验证

- **决定**：当前不把完全无公网的安装与升级作为标准的硬性门槛，优先设计与验证可联网的正常路径；完全离线交付在具体客户需要时另作专项。联网不改变精确版本、配置与依赖声明，也不意味着允许外传客户数据；终端断网草稿（D24）不变。
- **理由**：用户没有要求限制公网访问，先把正常交付与代表部署证明完整。
- **落在**：[部署与运行的网络前提](../04-foundations/01-deployment-and-runtime.md#私有化交付的网络前提)。

## D43 基本与完整观测方案分别交付与验证

- **决定**：提供基本与完整两档观测。基本档保留持久、可定位的结构化日志、关键指标、必要告警、链路关联与扩展接口；集中检索与完整追踪存储按需增加；完整档作为验证样板。必需的业务审计不因精简而取消；不向外部平台回传客户遥测。
- **理由**：小客户按需选择观测后端，同时保留最低的可运维能力。
- **不采用**：所有部署配齐完整观测栈。
- **落在**：[协议 17 的观测](../06-protocols/17-runtime-and-resources.md#观测)、[支撑能力的选型说明](../00-overview/guides/supporting-capabilities.md)。

## D54 标准停用保留原组件的受限查阅，完全卸载走专项迁移

- **决定**：有历史的业务组件停止新业务后，保留原组件的受限历史查阅与必要的运行与安全维护；完全卸载另做专项的历史迁移与验收。先完成或交接未完的业务与依赖；当前授权、字段限制、审计、保全与恢复继续适用。
- **理由**：保留真实的单据结构、权限语义与必要查询，不以通用表或 PDF 冒充全部历史。
- **不采用**：标准开发独立的历史迁移与查阅路线，验证后卸载原组件。
- **落在**：[业务组件的停用与退出](../00-overview/05-change-and-retirement.md#业务组件的停用与退出)。

## D55 团队与 AI 维护客户版本，稳定修复与功能升级分开

- **决定**：有限的稳定维护线：必要的安全与重大正确性修复优先回补，新功能在后续版本推进。标准版与客户定制、Fork 的需求、修复、适配与验证由项目团队统一承担，AI 执行；客户决定是否升级，团队准备材料并配合实施。不默认强制升级、远程停服或外传客户资料；用 AI 开发维护不等于提前启用 ERP 的 AI 业务功能。
- **理由**：客户减少功能升级频率、保留自身定制与升级安排；团队承担回补与组合验收的成本。
- **不采用**：只维护最新功能线。
- **落在**：[工程规范的客户交付版本的维护](../01-conventions/01-engineering.md#客户交付版本的维护)、协议 19。

## D58 交付以每客户精确基线为单位，不引入货架发行版

- **决定**：每个客户一份精确的交付基线（组件、SDK、外壳、基础资源与适配的精确版本与验证范围），各自组合、各自验证；不定义跨客户共享的标准发行版。
- **理由**：与客户按需选配、定制与 Fork 的方式一致。
- **不采用**：货架发行版（一组一起测过的版本作为发行与支持单位，客户版本是发行版加偏离）。
- **代价**：验证工作随客户数增长；版本扇出与依赖同步靠交付工具自动化。
- **落在**：[协议 19 的客户基线与升级](../06-protocols/19-config-secrets-registries-release.md#客户基线与升级)。

## D63 当前重建范围加入采购

- **决定**：当前重建范围的候选加入 `erp/purchase`；代表业务链补上“采购 → 入库 → 暂估 → 票据匹配 → 成本调整”。范围的最终确认在实施与实验计划中。
- **理由**：成本的暂估、票据单价调整与应付匹配都依赖采购与收货事实。
- **不采用**：保持原范围、把成本中与采购相关的部分标为未验证；把成本移出范围。
- **落在**：[组件全景的当前重建范围](../00-overview/03-catalog.md)、[路线](../00-overview/06-roadmap.md)。

## D75 首批实现范围：重机制先保留形状，SDK 先做 Go 的完整实现

- **决定**：首批实现本地事务与发件表、增量事实（纪元与序号）、后台工作项、有界本地授权与生效点、安全处置与管理员恢复、内部来源的水位与对齐、整套恢复（证据存储、运行档案、恢复工具、证据重放、外部对账、告警渠道的签名核验），冷热分层完整实现（在线层、目录、驻留期与候选选择、封存与写屏障、冷层的复制校验发布与释放、冷读取、解冻、销毁与擦除）。授权的严格路径、影子投影、授权与身份成员的切换、高可用、事件签名只保留形状：契约、字段、状态与独立预期都保留，实现时先返回“能力不支持”或走最简路径。SDK 先做 Go 的完整实现；Python 与 TypeScript 先实现代表组件用到的子集，共用语义向量与一致性套件，以后补齐时行为一致。
- **修订**（用户 2026-10-16）：冷热分层原定首批只做在线层与目录，冷层只留形状；改为在重建的底层阶段完整实现并验证，因为分层影响每个业务组件的表结构、列表与读取，等业务组件写完再补代价最大。
- **理由**：三种语言都实现完整的组件协议，工作量远超维护能力；首批只有一个授权成员与一个身份成员，起步是单实例（D66），这些重机制首批用不到；语言中立的协议与一致性套件保证以后补齐不改行为。
- **不采用**：三种 SDK 一开始全量实现；重机制首批全部实现。
- **落在**：[协议 18 的官方 SDK](../06-protocols/18-sdk-and-conformance.md#官方-sdk)、[路线](../00-overview/06-roadmap.md)。

## D80 默认容器引擎是有根 Podman，无根 Podman 与 Docker 同等支持

- **决定**：交付的默认容器引擎是有根 Podman，容器内以非 root 用户运行；客户要求引擎本身不以 root 运行时用无根 Podman；客户已经在用 Docker、或要用只支持 Docker 的周边工具时用 Docker。维护者 2026-11-02 定。
- **理由**：代表部署实验同一批测量里，Podman 与 Docker 的 CPU 与延迟看不出差别（无根 Podman 整套多 6%，在波动内）；Podman 没有常驻的守护进程：同一批里平台自己的内存 Podman 135 MiB、Docker 548 MiB，每台机器省约 0.4 GiB（Docker 的守护进程在另一批里因构建镜像涨到约 0.7 GiB）。有根与无根之间：有根整套少 9–10% 的 CPU（网络由内核转发，不经用户态的 pasta）；开机回来只要启用系统级的 `podman-restart.service`（它在系统的 systemd 里，等得到网络在线），同一台机器上第一次真重启就全部回来、没有重启；无根真重启三次才通过，要 linger、让用户级的开机单元等网络、Ubuntu 上 AppArmor 的 `podman` 配置、存储在另一块盘时的挂载顺序这四项主机设置，缺一项就开机不回来或回来了连不上。
- **修订**（同日，开机实测之后）：起初定为无根 Podman（理由是引擎不以 root 运行、权限面更小）；三次真重启查出无根的四项主机设置，有根第一次就通过，维护者改定为有根。无根的准备步骤保留在部署模式指南里。容器在 Podman 上怎样看护与开机拉起，后来由 D81 定为 Quadlet 单元。
- **不采用**：无根 Podman 为默认（引擎不以 root 运行，但开机与网络的主机准备多、容易漏，CPU 多 9–10%）；Docker 为默认（适配与生态最好，但守护进程的内存是持续的代价）；不定默认、按客户选（交付与文档要按三套写）。
- **代价**：引擎以 root 运行，容器被攻破时影响比无根大；靠容器内的非 root 用户与镜像的最小权限缓解。与 Docker 装在同一台机器时，Docker 把转发策略设为丢弃，要在 `DOCKER-USER` 链放行 Podman 的网桥，且开机时补回（Docker 每次启动重建自己的链）。
- **落在**：[部署与运行](../04-foundations/01-deployment-and-runtime.md)、[部署模式](../00-overview/guides/deployment-modes.md)、[底层选择](../04-foundations/README.md)。

## D81 Podman 上交付用 Quadlet 单元，compose 只给开发机

- **决定**：单机交付用 Podman 时（有根或无根，D80），部署文件写 `podman: { units: quadlet }`：BrickKit 把每个组件与每个迁移生成为一个 Podman Quadlet 单元，由 systemd 看护与开机拉起。`compose`（不写 `podman.units`）只用于开发机：只有它能与本机进程（`mode: local`、`debug`）、焦点运行混用。维护者 2026-11-02 定（AI 推荐）。
- **理由**：同一台机器（Ubuntu 26.04、Podman 5.7.0、BrickKit v1.12.0 与 v1.12.1、12 个组件单跑）真重启四次：有根、无根的 Quadlet 单元都一次就全部回来、全部 healthy，开机只靠生成的单元，不用 `podman-restart.service` 与让它等网络的附加配置（无根的单元自动等网络）；组件在它依赖的组件健康之后才启动；`down` 之后再重启什么都不回来。迁移只由 `up` 跑，全部成功才换上组件的新单元：迁移失败时组件照旧，之后的开机回来的也是原来那份（v1.12.1 上真重启验证）。compose 那条路开机只拉起重启策略为 `always` 的容器、不按依赖顺序、要手工启用开机单元并（无根时）让它等网络，缺一项要等下一次重启才发现。Quadlet 还在组件不健康时杀掉并重启它（只看存活检查的组件），日志进 journald。BrickKit 与知识库的单机部署篇也都推荐它，compose 在 Podman 上是过渡做法。
- **不采用**：继续用 compose 加 `podman-restart.service`（开机路径靠手工补的主机设置，缺了静默失败）；等 BrickKit 修好开机时的迁移再改（那一处只影响 systemd 的状态，组件照常；v1.12.1 已改为开机不跑迁移）。
- **代价**：有根时只有 root 能 `up`、`down`（单元装进 `/etc/containers/systemd`），部署脚本与 AI 要固定用同一个身份（换了身份在同一个项目目录里 `up`，BrickKit v1.12.1 起报 `DEPLOYED_ELSEWHERE` 拒绝）。单元从项目目录挂入文件型的配置，项目目录与 `.brickkit/` 要留在原处。开机不跑迁移，库结构以上一次 `up` 为准。Podman 至少 5.3，BrickKit 至少 v1.12.1。
- **落在**：[部署模式](../00-overview/guides/deployment-modes.md)、[部署与运行](../04-foundations/01-deployment-and-runtime.md)。
