# 参考实现

本项目的业务逻辑从看成熟软件怎么解决同一个问题开始。被几十年真实部署打磨出来的领域模型，已经吸收了从零设计几乎必然漏掉的边界情况，而那些边界要等客户上线三个月后才冒出来。本文件讲怎么参考、哪个组件看哪个项目，以及阅读时要留意的那个信号。

## 三步法

顺序要紧，绝不能反。

| 步 | 做什么 | 为什么 |
|---|---|---|
| **1. 先自己设计一版** | 打开任何参考之前，先按本项目的约束画出自己的设计 | 手里有自己的方案，才看得出差别在哪；空着脑袋去读，只会抄一份出来 |
| **2. 只在卡住的地方看参考** | 领域模型怎么切、有哪些状态、哪些转移合法、哪些字段必填、边界情况怎么处理 | 这一步是调研，不是抄作业 |
| **3. 回来自己想清楚再写** | 把学到的东西和本项目的约束对齐 | 参考项目的技术栈和边界与我们不同（另一种语言、单进程单库）；目的是借思路，从来不是搬代码 |

## 闭源产品与许可

- **闭源产品也值得参考。** 看不到代码，但看得到它怎么被用：客户天天用哪些功能、哪些从来没人点、哪些流程被骂了二十年。这能判断一样东西值不值得做成可单独售卖的组件，而这个判断比任何实现细节都更早。
- **许可**：读一个实现是为了它的思路、然后独立重写，不构成衍生作品。要避免的是打开对方的源文件逐行转写；按三步法走就离这条线很远。原样使用的代码只能来自 Apache-2.0、MIT 或 BSD 项目，并在 `NOTICE` 文件里保留原始声明。

## 记录参考了什么

开始实现之前，在组件的 `docs/design.md` 里加一节"参考实现"：

```markdown
| 项目 | 版本 | 参考的模块 | 借鉴了什么 | 许可 | 用法 |
|---|---|---|---|---|---|
| Odoo | 17.0 | `addons/product/models/product_uom.py` | 计量单位换算系数和舍入策略 | LGPL-3 | 借鉴思路 |
| 某闭源产品 | — | — | 哪些换算天天用、哪些从不用 | 闭源 | 借鉴真实用法 |

**刻意避开的**：<在参考里发现的反模式，以及本项目为什么不重复它>
```

`用法`只取三个值之一：**借鉴思路**（读了实现、明白了为什么、自己独立设计和实现；几乎每一行都是这个）、**借鉴真实用法**（闭源，或只看了文档和交互）、**复制代码**（只限 Apache-2.0 / MIT / BSD，配 `NOTICE`，并在这里写清是哪个文件哪一段）。

## 要绕开的结构性弱点

大多数开源 ERP 共有同一批结构性弱点；读它们正是为了不重复。

| 弱点 | 本项目怎么避开 |
|---|---|
| 所有模块共用一个进程和一个数据库，跨模块 JOIN 是常态，边界天天被越过 | 独立进程、独立 schema，用数据库角色隔开，而不是靠约定 |
| 靠运行时打补丁和钩子做定制，每次升级都可能弄坏定制 | 整个组件 Fork 出来、契约不变；升级是一次有意识的合并 |
| 一切元数据驱动（动态字段、通用单据类型），类型检查器什么都看不到 | 契约优先（Protobuf、OpenAPI）加静态类型语言 |
| 报表直接查实时交易表，拖慢核心系统 | 报表走汇总表或分析组件 |
| 表无限增长，最后被自己的历史数据压垮 | 从第一个迁移起就分区，并有归档策略 |

## 槽位族信号

对比参考时有一种情况反复出现：**几个成熟系统对同一个功能给出了不同的实现，而且每一种都合理，只是适配的客户不同。** 这不是"要不要做成可配置"的问题，但也还不足以成为一组可互换组件（槽位族）的理由。它是必要条件，不是充分条件；分歧长在哪里，决定它是什么形态。

- **其中一种明显更好** → 那就是默认实现，没有别的事要做。
- **几种都站得住，而且所在位置没有任何组件对它建依赖边** → 槽位族：每个槽位装一个成员（channel 族可以并装多个），每个成员暴露完全相同的契约。符合条件的是这类位置：前端、身份提供方（组件通过配置而不是依赖边找到它）、薪资、通知渠道。
- **几种都站得住，但长在被别的组件依赖的组件里**（所有 `erp/*`、`crm/*` 交易组件）→ **不是槽位**。依赖方钉死了那个组件，换成另一个成员会断掉这条边。正确的形态是这个组件的**客户 Fork**（为该客户复制一份，`metadata.id` 不变，因为依赖方的地址变量由它推导；改那几处，版本照常走，依赖方用 `brickkit upgrade` / `make bump-version` 移动版本钉）；分歧只有几个分支、看得见的将来不会再长出新变体时，用**内部策略**（[ai-development.zh.md](ai-development.zh.md#何时用设计模式)）。

| 功能 | 分歧 | 结论 |
|---|---|---|
| 成本核算法 | 移动加权平均、先进先出、标准成本加差异、分批实际成本 | 真实存在，但长在被依赖的 erp/inventory 里 → 客户 Fork |
| 拣货策略 | 先到期先出、先进先出、就近库位、波次拣货 | 同上 → 客户 Fork |
| 审批路由 | 组织层级、金额分级、矩阵式、规则引擎 | 审批人由业务组件算好交给 infra/workflow，而业务组件是被依赖的 → 客户 Fork |
| 身份提供方 | Casdoor、Keycloak | 没有人对它建依赖边 → 槽位族 |
| 单据编号 | 流水号、按年月分段、按组织和类型分段 | 一个配置项 |
| 主数据记录的字段 | 各家只差几个字段 | 客户 Fork |

确认一个槽位族成立之后（多种合理变体，**并且**该位置没有依赖边），按这个顺序：

1. **写任何实现之前先把这个族记下来**：族名、每个成员完全一致的契约、每个成员适配哪类客户、默认装哪一个。新增一个族是一条决策记录（[../decisions/README.zh.md](../decisions/README.zh.md)）。
2. 把每个成员的端口和 schema 追加进 `registry/`（[registries.zh.md](registries.zh.md)）。
3. 然后才设计和实现每个成员。

**绝不在一个组件里写 `if costingMethod == "fifo"` 把几类客户的变体塞在一起**：那样每个客户的需求都会约束其他所有客户。在被依赖的组件里，这种情况该做成 Fork；唯一的例外是分歧只有两三个分支、看得见的将来不会再长出新变体，写成内部策略。

槽位族和 Fork 也是让定制变便宜的东西：客户从最接近自己需要的那个成员或那份 Fork 起步。
