## erp-inventory：库存流水与预留

**采纳进**：[`erp-inventory.md`](../erp-inventory.md) §2.1（流水与余额投影）、§2.2（防超卖）、§8（参考实现）、§9-1（并发测试）

### 1. ERPNext 的 Stock Ledger Entry——"不可变流水"这个说法只对了一半

模块：`erpnext/stock/doctype/stock_ledger_entry/` + `erpnext/stock/stock_ledger.py`

每一行 SLE 都存自己的完整状态：`actual_qty`（变动量）、`qty_after_transaction`（这一行之后的余额）、
`valuation_rate`、`stock_value`、`stock_value_difference`、`incoming_rate`/`outgoing_rate`，还有
`stock_queue`（一个 JSON 数组 `[[qty, rate], …]`，是每一行的 FIFO/LIFO 队列快照）。**余额是物化进每一行的，
不是读时投影出来的。** 取消是打 `is_cancelled` 标记，从不删除。

这就导致**补录一张过去日期的单据 = 改写历史**：会排一个 `Repost Item Valuation` 任务
（`erpnext/stock/doctype/repost_item_valuation/`），状态有 Queued/In Progress/Completed/Failed/
Skipped/Cancelled，跑在 RQ 的 `long` 队列（30 分钟超时），按 voucher 或按 item+warehouse+date 圈定范围。
`update_entries_after` 会把该 item-warehouse 之后**所有**的 SLE 按 `(posting_datetime, creation)`
顺序重放一遍，通过 `process_sle()` 原地改写那五个字段，再重建 `Bin`（他们的小余额缓存：`actual_qty`、
`stock_value`、`reserved_qty`）。

**为此付出的代价，具体列出来：**

- **级联无界**：`repost_affected_transaction` 会收集同一张凭证影响到的**其他**物料的 `(voucher_type,
  voucher_no)`——一张消耗 A 生产 B 的生产单，重算 A 会连带排一个 B 的重算任务。级联深度跟着 BOM 层数走，
  没有上限。
- **专门造出来扛这件事的机制**：两把 advisory lock（`sle_processing_gate()` 按 item-warehouse 一把，
  `repost_gate()` 300 秒让步一把）、检查点存进压缩过的 `reposting_data_file`、每 2000 行提交一次、
  死锁/超时就重新入队、`deduplicate_similar_repost()` 与 `skip_reposts_covered_by_dependents()`
  合并冗余任务、失败要通知 Stock Manager 角色。
- **现实里的失败模式**：补录取消后重算任务卡在 Queued 不动（[#41493](https://github.com/frappe/erpnext/issues/41493)、
  [#25192](https://github.com/frappe/erpnext/issues/25192)）；流水和总账**设计上就是最终一致**，不是强一致；
  他们专门做了一个"库存流水差异报表"去找漂移。
- 负库存检查：`diff = qty_after_transaction + actual_qty - reserved_stock`（`reserved_stock` 只算
  posting time 之前的预留），可以按物料或全局关掉这条检查。

### 2. Odoo 的 stock.quant 预留模型

模块：`addons/stock/models/stock_quant.py`

行的键是 `(product, location, lot, package, owner) + in_date`。
`available_quantity = quantity - reserved_quantity`——**是计算出来的，不是存储列**
（`_compute_available_quantity`）。是的，可用量 = 数量 − 已预留。

并发控制：`_update_reserved_quantity` → `_update_available_quantity`，全程只发一条锁语句：

```sql
SELECT id FROM stock_quant WHERE id IN %s ORDER BY lot_id LIMIT 1 FOR NO KEY UPDATE SKIP LOCKED
```

注意 `LIMIT 1` + `SKIP LOCKED`：它只抢**一行**当序列化令牌，抢不到**不等待**，直接跳过。
`_gather` 按移除策略选候选行，`_get_reserve_quantity` 预先算好 `(quant, qty)` 的配对列表。

**痛点是结构性的，不是实现细节**：**quant 的键上完全没有唯一约束**。并发事务因此会创建重复的
quant 行，靠 `_merge_quants()` / `_clean_reservations()` / `_unlink_zero_quants()`
（合起来叫 `_quant_tasks()`）事后清理——而这套清理是**打开库存视图页面时触发**的
（`stock.skip_quant_tasks` 开关），不是硬 cron。合并的 `GROUP BY` 里带了 `in_date`，
导致相差一秒的两行永远合并不了（[#55127](https://github.com/odoo/odoo/issues/55127)）；
大表上这套合并还很慢（[#22866](https://github.com/odoo/odoo/issues/22866)）。
`_should_bypass_reservation()` 让供应商位置/盘点位置/生产位置直接跳过预留、自由为负。

### 3. stock.move 状态机

模块：`addons/stock/models/stock_move.py`

状态：`draft`（New）→ `waiting`（等别的移库）/ `confirmed`（等可用）→ `partially_available`
→ `assigned`（Available）→ `done`；`cancel` 可以从任何状态发生。**终态只有 `done` 和 `cancel`。**

迁移触发：`_action_confirm`（有 `move_orig_ids` 或 `procure_method = make_to_order` 时
draft → waiting，否则 → confirmed）、`_action_assign`（创建 move line，confirmed/waiting/
partially_available → assigned 或 partially_available）、`_action_done`、`_action_cancel`，
外加 `_recompute_state`——它是从 move line **反推**出 move 的状态，不是单独维护的。

`stock.move.line`（`stock_move_line.py`）是子表（`move_id`/`move_line_ids`，两边都带
`picking_id`）。v17 起的一个关键变化：`reserved_uom_qty` 与 `qty_done` 合并成了一个
`quantity` 字段 + 一个 `picked` 布尔。不变式是"move line 数量之和 == quant 上的
`reserved_quantity`"，由 create/write/unlink 里的 `_synchronize_quant` 维护——**quant
上的预留量是 move line 的派生聚合值，不是独立维护的**。

### 4. 批次 vs 序列号

- **Odoo：一张表。** `addons/stock/models/stock_lot.py`（`stock.lot`，v16 前叫
  `stock.production.lot`）。区分批次/序列号靠**产品上的字段**（`product_id.tracking` ∈
  `none`/`lot`/`serial`），不是靠批次表本身。**数据库层没有任何约束强制序列号数量=1**——
  纯业务逻辑（`_onchange_serial_number` 把数量强制设成 1.0，报错文案是"只能处理 1.0 个…
  唯一序列号"）。`(product, name, company)` 的唯一性是 Python `@constrains`，不是 SQL
  唯一索引。
- **ERPNext：两张表分开。** `Serial No`（每个序列号一份独立文档，自带状态机）与 `Batch`。
  v15 起加了 `Serial and Batch Bundle` + `Serial and Batch Entry` 子表作为连接对象，
  从 SLE 通过 `serial_and_batch_bundle` 关联；SLE 自己也冗余存了 `batch_no`/`serial_no`
  两列，但已知会出现该填而没填的空值（[#42997](https://github.com/frappe/erpnext/issues/42997)）。

### 5. 预留过期/软预留——**两家都没有，这是明确的负面发现**

- ERPNext 的 `Stock Reservation Entry`（`erpnext/stock/doctype/stock_reservation_entry/`）：
  没有 TTL 字段，没有定时释放任务。状态是 Draft → Partially Reserved → Reserved →
  Partially Delivered → Delivered → Closed/Cancelled，只能靠取消或履约释放。
- Odoo 的"预留方式"（`at_confirm`/`manual`/`by_date` + 提前几天）管的是**什么时候开始预留**，
  从不管**什么时候失效**。取消预留是人工按钮（`do_unreserve`）。

**结论：限时租约式的预留，两个参考系统都没有，这段是我们自己设计的，不是借来的。**

### 意外发现 / 陷阱清单

1. **ERPNext 的流水不是真不可变**——repost 会 `UPDATE` 历史行。"不可变流水 + 投影余额"是
   愿景，实现是一个会被重写的物化余额。
2. Odoo 的锁是 `LIMIT 1 … SKIP LOCKED`——一个令牌，不是真正锁住要改的那些行。配合"quant
   键上没有唯一约束"，说明这是**刻意容忍重复**的设计，不是疏忽。
3. 重复 quant 的清理是**打开界面触发**的，而且有已知 bug 合不掉并发恰好制造出来的那种行。
4. ERPNext 的两把 advisory lock 恰恰印证了我们的设计方向：按 `(item, warehouse)` 把写操作
   串行化是对的。
5. 一张多物料凭证触发的重算级联没有上限——这正是它必须做成异步任务、以及流水与总账会短暂
   不一致的原因。
6. 取消在两个系统里都不是删除（`is_cancelled` 标记 / `cancel` 状态）。
7. "序列号数量必然是 1"在两个系统的数据库层都**没有约束**，只在业务代码里管。
8. 两个系统的预留都没有幂等键，也没有租约语义——我们的 TCC `Reserve`/`Cancel` 没有可抄的参照实现。

## erp-finance：会计引擎

**采纳进**：[`erp-finance.md`](../erp-finance.md) §2.1（凭证状态机）、§2.2（期间三态）、§2.3（幂等过账约束）、
§2.4（应收台账分家）、§3.1（跨组件期间锁）、§8（参考实现）

### 1. Tryton 的 `account` 模块——查证确认它确实比 Odoo 严谨

链路：`fiscalyear.py` 的 FiscalYear → `period.py` 的 Period（`type`: standard|adjustment）→
`move.py` 的 Move → Move Line。凭证状态**只有 draft/posted**——没有取消状态；
`Move.cancel()` 写的是一笔**反向**凭证。posted 是终态。

每张凭证两个号：`number`（创建时给）与 `post_number`（过账时从期间/年度的
`post_move_sequence` 取）。**只有过账号要求连续无缺口**——这个设计本身就值得抄。

期间与会计年度**都是三态**：`open → close → locked`。`close→open` 允许反关账；
**locked 是终态**。还有第三层粒度：`JournalPeriod`（日记账 × 期间），可以只关某个期间里
的销售日记账，其他日记账照开。

强制方式**纯 Python，没有数据库约束**：`Line.check_modify()` → `check_journal_period_modify()`
在改动被关闭的日记账-期间时抛 `msg_modify_line_closed_journal_period`；`Period._check()`
拦住"这个期间已经有凭证还想改结构"；`Move.cancel()` 在已关闭期间里抛 `CancelWarning`。
SQL 约束只管行的形状（`credit_debit`、`second_currency_sign`），从不管期间状态。
`FiscalYear.close()` 会**表级锁**防止并发建期间，要求全部凭证已过账、非递延科目余额为零；
`reopen()` 会删掉递延分录。

对比之下，**Odoo 完全没有期间实体**——只有公司级的 `period_lock_date`/`fiscalyear_lock_date`/
`tax_lock_date`（17 版新增了不可逆的"硬锁定日期"），按角色分层，某些流程下甚至会**静默把
记账日期往后推**而不是拒绝。所以查证结论是：**Tryton 确实更严谨**。

### 2. 跨组件的期间锁——现实里几乎没有先例，但有三条可参考

单体框架内部管期间锁是常态，**微服务形态几乎没有先例**。但查到三条有价值的：

- **ERPNext 最接近我们的形态**：`accounts/doctype/accounting_period/` 有一张 `closed_documents`
  子表，列出**哪些单据类型**受这个期间控制；这份清单由 `period_closing_doctypes` 这个 hook
  填充，**其他 app 可以往里注册自己的单据类型**；强制检查在框架层的
  `validate_accounting_period_on_doc_save()` 里，不在会计模块内部。还有 `exempted_role`
  可以豁免特定角色。
- **Oracle Fusion**：期间状态是**一等可查实体**（`GL_PERIOD_STATUSES.CLOSING_STATUS`
  ∈ N/F/O/C/P——注意"未来可录"与"从未开启"是两个不同的状态，不是简单的开/关），
  **每个子账本各自维护自己的期间状态**；"有子账期间未关就不许关总账期间"这条规则把关账
  做成了一次协商过程。
- **SAP**：MM 期间（MMPV/MMRV）与 FI 期间（OB52）**完全独立**——FI 期间还开着，MM 期间
  一关，货物移动照样会失败。两边靠配置手工同步，很重。

**关于竞态**：老实说，没有一家系统乐观地解决过它，因为**关账在现实里从来不是一次 API 调用，
是一段人工/批处理流程**，带着例外报告。设计含义：跨组件的"这个期间开不开"查询应该是**建议性
的用户体验提示**，权威判断必须在**过账事务内部**再查一次（我们的分区键正好是期间，天然适合）。
迟到的单据不该被拒绝，而应该按会计惯例记进**下一个开放期间**——这是标准做法，不是我们的妥协。
其他组件如果只能硬删除历史单据，那这把锁形同虚设；只要它们遵守"改历史只能走反向冲销"，
这条竞态窗口本身危害有限。

### 3. ERPNext 的会计维度与单号序列

**会计维度**解决的是"科目表分段爆炸"问题：不用为每个项目/分支开新科目，用维度切片看损益。
存储方式是**额外列**：`accounting_dimension.py::make_dimension_in_accounting_doctypes()`
在 `accounting_dimension_doctypes` hook 列出的每个单据类型（GL Entry、各类发票、日记账…）
上创建一个 Link **自定义字段**（运行时 DDL）。子表 `Accounting Dimension Detail` 只存
每个公司的默认值/是否必填标记。**定义是行，值是运行时建出来的列**——这是为了让过滤走索引。
我们用 `sqlc` + 迁移做不了运行时 DDL，Fork 时的选择是：固定 `dim1..dimN` 列 vs jsonb+
表达式索引 vs EAV（慢）。

**单号序列**：`frappe/model/naming.py::parse_naming_series` + `getseries()`，每个前缀
一行计数器存在 `tabSeries` 表，`SELECT … FOR UPDATE` 后 INSERT/UPDATE，**跟业务单据在
同一个事务里**。已知问题：同前缀的插入全部串行化（热点行锁）；回滚/作废/删除会留缺口，
历史上引发过 `DuplicateEntryError`；手工改号会导致状态不同步。**Tryton 的创建号/过账号
分离是更好的答案。**

### 4. AR/AP 台账 vs 总账——三家给出了两种答案，而且 ERPNext 自己换过

- **Odoo**：没有独立子账。`account.move.line` + `account_type`（应收/应付）+ `partner_id`；
  账龄是报表，核销靠同一批行上的 `full_reconcile_id`。
- **Tryton**：一样——往来单位 + 凭证行上的 `reconciliation` 外键；`account_invoice` 是
  独立模块，指向自己的凭证。
- **ERPNext**：**曾经**和上面一样，**v14 起新增了物化的 Payment Ledger Entry**
  （只覆盖应收应付，`account_type` + 带符号的 `amount`，不是借贷两列）。官方说明的动因：
  旧设计下每次核销都要**撤销重记总账凭证**。

对我们的约束而言这条判断更有分量：总账是**不可变且按期间分区**的，如果核销状态挂在总账
行上，一次核销就要去改一个可能已经归档的旧分区——这与"分区表只增不改"直接冲突。**所以拆
应收台账不是可选优化，是我们这套约束下唯一可行的答案**——判定为一次性架构分叉，不是槽位族
（"每种都合理、只是客户不同"这条不成立，对我们的约束只有一个答案可行）。

### 5. 幂等过账——三家都没做，这段防护是我们自己加的

三家的做法都是"源单持有一个指向凭证的外键，建之前先看有没有"——**这在单体单库单事务里
成立，跨进程重投时不成立**：
- Tryton：`invoice.move` 是 Many2One，`get_move()` 一看有值就直接返回；`Move.origin`
  是可追溯的 Reference 字段，**没有唯一约束**。
- ERPNext：GL Entry 带 `voucher_type` + `voucher_no`；`general_ledger.py::make_gl_entries`
  **不做去重**——调用方必须自己先调 `make_reverse_gl_entries()`。这正是 ERPNext 反复出现
  重复 GL 记录 bug 的根源。

**所以这个概念能借鉴，安全性借鉴不到**。要补的是三家都没有的东西：在**凭证头**（不分区）
上建 `(source_component, source_doc_type, source_doc_id, source_revision)` 的唯一索引，
先插入、唯一冲突就说明已经过账过，直接确认收到。加 `source_revision` 是为了让"源单被修改
后重新推送"产生一组新的冲销+重记凭证，而不是被直接吞掉。

**分区陷阱**：PostgreSQL 不能在跨分区的情况下强制唯一索引，除非唯一键本身包含分区列——
所以这把锁必须留在**不分区的头表**上。期间必须从源单的业务日期推导，不能用消息到达时间，
否则重投的消息会落进不同的分区，头上的唯一约束才拦不住。

**可以做成槽位族的两条真分歧**：期间关账策略（Tryton 的期间实体+日记账粒度+零余额前置校验
/ Odoo 的锁日期+角色分层+静默顺延 / ERPNext 三套机制并存）；迟到单据策略（拒绝/顺延下期/
角色强改）。两条都固定住"期间状态可查"这个契约，策略本身可以变。

### 意外发现 / 陷阱清单

1. 锁的粒度 Tryton 有**三层**（年度/期间/日记账-期间）——现在做便宜，事后补贵。
2. `closed` ≠ `locked`：一个可逆一个终态，是**两个状态**，不是一个布尔。
3. 关账本身**可能失败**（有未过账凭证、科目余额不为零）——这是一个工作流，其他组件要有
   "关账被拒绝"的应对路径。
4. Tryton 在年度关账时会表级锁——连单体系统都觉得这个并发问题是真实存在的。
5. ERPNext 的跨模块强制用的是框架级 save hook，维度用的是运行时 DDL——两者对我们都是奢侈品，
   要显式规划替代方案。
6. **没有一个系统在数据库层面防止重复过账**——不能假设这个安全性能直接照搬。
7. 没有系统真正删除记录；取消 = 反向凭证。

## erp-sales：销售订单与定价

**采纳进**：[`erp-sales.md`](../erp-sales.md) §2.1（订单状态机）、§2.2（订单行快照）、§3.1（TCC 链顺序）、
§3.2（定价模型）、§5（信用额度三方分工）、§8（参考实现）

### 1. Odoo `sale.order` 状态机

模块：`addons/sale/models/sale_order.py`，`SALE_ORDER_STATE`：
`draft`（报价单）→ `sent`（已发送报价）→ `sale`（销售订单），加一个 `cancel`。
**17 版没有 `done` 状态**——16 版有 `('done', "Locked")`，17 版把它换成了一个独立的
`locked` 布尔（`action_lock`/`action_unlock`，`_is_readonly()` 判断
`state == 'cancel' or locked`）。**这条值得记住：他们把一个状态降级成了一个正交布尔**，
说明"锁定"这个语义天生就不该是生命周期状态机的一部分。

迁移：`action_quotation_sent()` 要求 `state == 'draft'` → `sent`；`action_confirm()`
要求 `_can_be_confirmed()`（`state in {'draft','sent'}`）→ `sale`，重置 `date_order`，
再调钩子 `_action_confirm()`。`action_draft()` 把 `['cancel','sent'] → draft`
（**取消不是终态**，这一点出乎意料）。`action_cancel()` 在 `locked` 时拒绝执行，
只取消**草稿**发票，→ `cancel`。非 draft/cancel 状态下删除会被拦。

**报价单和订单是同一张表 + 一个状态字段**，没有单独的报价单对象。发货与开票是分开的
独立文档，在独立模块里：`stock.picking`（`stock`，靠 `procurement_group_id` 与
`stock.move.sale_line_id` 关联）与 `account.move`（`account`，靠
`sale.order.line.invoice_lines` 关联）。订单本身只带**派生**状态：`invoice_status`/
`qty_to_invoice`，由产品的 `invoice_policy`（`order`=按订单量开票 / `delivery`=按
发货量开票）驱动。

### 2. 确认订单这个事务里到底发生了什么

`sale_stock/models/sale_order.py` 重写 `_action_confirm()`，在 super 之前先调
`order_line._action_launch_stock_rule()`。**全程同步，一个数据库事务**：补货运算走
拉式规则 → 建 `stock.move` → `stock_move._action_confirm()` 合并 move、分配到
picking（`_assign_picking`）、应用推式规则。没有 cron。

预留是**有条件的**。`_action_confirm()` 末尾：状态是 `confirmed`/`partially_available`
且通过 `_should_assign_at_confirm()` 判断的 move 会被 `_action_assign()`。这个判断
在以下情况为真：move 本身绕过预留、`picking_type_id.reservation_method == 'at_confirm'`
（默认值）、或 `reservation_date <= 今天`。

**库存不足从不阻止确认订单，也从不报错。** `_action_assign()` 能预留多少就预留多少，
预留不完就留成 `partially_available`，完全没有就是 `confirmed`/`waiting`。**订单照样
是 `sale` 状态**，与库存状态无关。欠单（backorder）是**在发货验证时才创建**的，
远远晚于确认——`stock_picking.button_validate` → `_check_backorder` →
`_create_backorder`，受 `picking_type_id.create_backorder`（`ask`/`always`/`never`）
控制。

### 3. 定价——两家结构性地不一样

**Odoo**（`product/models/product_pricelist_item.py`）：价格表是一张**扁平的有序表**。
适用范围（`applied_on`）∈ `0_product_variant`/`1_product`/`2_product_category`/
`3_global`（+ 对应外键）、`min_quantity`、生效日期区间。算价：`base`（`list_price`/
`standard_price`/`pricelist` 递归引用）→ `compute_price`（`fixed`/`percentage`/
`formula`，`formula` 下再走 `price_discount`/`price_round`/`price_surcharge`/
`price_min_margin`/`price_max_margin`，按这个顺序）。**赢家选择是纯排序，第一条命中
就是答案**：`_order = "applied_on, min_quantity desc, categ_id desc, id desc"`。

**metasfresh**（`de.metas.business/.../pricing/rules/`）：一条**可组合的规则链**，
不是有序表。`IPricingRule` 有 `applies(ctx, result)` / `calculate(ctx, result)`；
`AggregatedPricingRule` 依次跑配置好的规则，每条规则修改一个共享的 `IPricingResult`。
`PriceListVersionPricingRule` 解析：定价系统 → 价格表（按国家/币种/销售或采购）→
价格表版本（按日期生效，取订单承诺日期对应的那个）→ 产品价格，产出**三个**价格：
`priceStd`、`priceList`、`priceLimit`。折扣单独走 `Discount.java`，**从业务伙伴上**
（不是从价格表上）查折扣方案（`bpartnerBL.getDiscountSchemaId`），方案的"档位"
（break）同时看数量**和**金额（`PricingConditionsBreakQuery` 带 `qty` 与
`priceStd` 两个维度），一个档位贡献一个折扣百分比，还可能覆盖三个价格中的任意一个。
另外还有营销活动定价作为独立的第三层规则——Odoo 没有这层。

**两者的真实分歧**：

| | Odoo | metasfresh |
|---|---|---|
| 模型 | 一张有序表，一行赢 | 多阶段规则链，可组合 |
| 结果 | 一个数字 | `priceStd`+`priceList`+`priceLimit`+折扣（可拆开、可打印） |
| 折扣挂在哪 | 价格表（价格表挂在客户上） | 业务伙伴，独立于价格表 |
| 可扩展性 | 加行 | 给链加一个规则类 |
| 底价 | 公式参数（`price_min_margin`） | 一等字段 `priceLimit` |

### 4. 信用额度检查

`credit_limit` 是 `res.partner` 上一个**按公司区分的 float 字段**，**归属 `account`
模块**（`addons/account/models/partner.py`），**不归销售模块**。已用额度是**实时算出来
的，从来不是维护的余额**：`_credit_debit_get()` 直接 SQL 扫 `account_move_line` join
`account_account`，对 `asset_receivable` 类科目、`parent_state = 'posted'`、
未核销（`reconciled IS NOT TRUE`）的行求和金额。不落存储，每次访问重算，查询前先 flush。

销售模块**只展示**：`sale.order.partner_credit_warning` 是一个非存储计算字段，
委托给 `account` 模块的 `_build_credit_warning_message`。**它从不阻止确认订单。**
硬拦截统一是第三方/OCA 插件才有的能力。17 版起，已确认未开票的订单也会计入已用额度。

**查证结论：两个成熟系统的信用额度都不硬拦，我们"预留失败即整单失败"比两家都严——
这是刻意选择，不是默认值。**

### 5. 单号与订单行快照

单号：`ir.sequence.next_by_code('sale.order')`，在 `create()` 里、`name` 为空或
`"New"` 时分配，序列日期用 `date_order`。**创建（草稿）时就分配**，不是确认时——
报价单永远不转订单也会消耗一个号。

快照：**全部快照，没有一处 join**。`sale.order.line` 的 `name`/`price_unit`/
`discount`/`product_uom`/`tax_id` 全部是 `compute=..., store=True,
readonly=False`——算一次，然后当普通可编辑列存着。`product_id` 只作为外键留着方便追溯。
`_compute_price_unit` 在 `qty_invoiced > 0` 后会拒绝重算。**这正是跨服务边界时想要的
形态**：调一次产品/定价服务，把值写进自己的行，之后不再依赖对方。

### 意外发现 / 陷阱清单

1. **Odoo 的取消不是终态**——`action_draft()` 能把已取消的订单救活。要不要允许这样
   得自己明确决定。
2. **Odoo 17 去掉了 `done` 状态**，改用 `locked` 布尔——不要照抄 16 版的状态表。
3. 取消订单只取消**草稿**发票；已过账的发票不受影响——补偿不是对称的，"下游有些效果
   天生不可逆"要提前规划。
4. **库存和信用额度都不阻塞确认订单**——两个成熟系统都把它们做成建议性提示。
   我们跨进程同步 `Reserve` 且失败即整单失败，比两者都严格，是刻意的设计取舍。
5. 欠单决策发生在**发货验证**，不是订单确认——Odoo 把"部分履约怎么办"这个决定推给
   人，且推得很晚。
6. Odoo 的价格表赢家由 SQL `_order` 子句决定，不是打分函数——便宜，但"为什么是这个
   价"只能靠重新跑一遍排序来回答。
7. metasfresh 的 `priceLimit` 是真实字段；Odoo 的底价只是公式的一个参数。要审计
   "绝不能低于某价"这件事，前者是结构性支持，后者不是。

**四条槽位族候选**（每条都是两个成熟系统给出不同答案，且 Odoo 自己至少有一条已经做成
了配置项，这是"该建族"判据的佐证）：预留严格度（Odoo `reservation_method`）、
缺货策略（Odoo `create_backorder` + `picking_policy`）、开票基准（Odoo
`invoice_policy`）、定价引擎形态（Odoo 有序表 vs metasfresh 规则链）。
