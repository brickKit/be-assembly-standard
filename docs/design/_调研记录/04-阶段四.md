## 1. 通读 brickKit《组件合并部署.md》，与设计书第 13 章逐条对照

全文 9 章，逐章核对下来，**设计书第 13 章是这份文档的忠实转译，没有发现互相矛盾的地方**。值得单独摘出来的，
是原文比设计书转译版本更细的几处：

- **§4.2/§4.3 讲的是同一道关卡的两半，不是两道要各自过**——原文明确提醒"这是第一次做外壳的人最容易浪费一轮
  的地方"，设计书 §13.1 已经把结论（"不要用网络别名"）直接写出来了，但没有转译"为什么会有人先去试网络别名"
  这条背景——本记录 §3 补全。
- **§4.4 迁移状态表要求**："合并后多个模块更容易共用一个库——迁移状态表的主键必须含组件标识，否则两个模块
  的迁移互相顶掉"——设计书没有单独提这条，本记录 §5 核实这条对本项目是否成立。
- **§7 连接池合并**的两个前提条件（同一个 database、同一个认证角色）与本项目"一组件一 schema、`SET LOCAL
  ROLE`"的既有设计（Decision 3、§13.3 铁律二）完全对得上，且原文额外指出"这个决定有时序性，要在建库之前做"
  ——本项目从 Decision 3 起就是这个形态，属于"不知不觉中已经满足了以后才会用到的前提条件"，不需要补动作。
- **§4.5 签名**：外壳镜像本地构建、不在任何签名覆盖范围内——设计书 §13.3 铁律五下方有提，措辞一致。

## 2. ⭐ 一个值得诚实记录的张力：brickKit 自己的文档说"以 Go 为主的项目，别做"

原文第 1 章给了一张按运行时空跑内存排的表，结论很直接：

| 你的项目 | 结论 |
|---|---|
| 以 Go / Rust 为主 | **别做。** 20 个组件合起来 0.4G，合并省下的那点内存换不回你要付的账 |

**本项目 62 个组件规划里目前一个 JVM/.NET 组件都没有**（Chapter 12.4 的技术栈锁定表只锁了 Go/Python/TS，
Java/C# 被 decision 78 明确拒绝），而阶段四要合并的 11 个组件全部是 Go。按 brickKit 这份文档自己的判断标准，
**这次合并从纯内存收益的角度看几乎不划算**——不该被这份调研记录悄悄略过。

但设计书 §13.0 给出的理由本来就不是纯内存收益，是三条更广的运维/交付理由：

1. **Docker 守护进程与 62 个容器本身的运维开销**（不是单个进程的内存，是容器数量本身——每个容器有自己的
   日志驱动、健康检查轮询、网络命名空间），这条 brickKit 的表没有覆盖到（它只算了进程 RSS）。
2. **客户可能只买 5–10 个组件，但基础设施容器一个都不能少**——固定成本在组件数少的场景占比更高。
3. **§9.6.1 档 3 自己的验收目标写的是"验合并不磨掉组件性"，不是"省内存"**——这次合并的真正产出是**证明
   这套机制在 62 个组件铺满之前就已经跑通、文档化、有回归测试**，等到阶段四/五/六真的出现 Python/TS 复杂
   大脑这类组件数多、单进程内存确实大的外壳时，机制已经是现成的，不用从零摸索。

**结论：这次合并的动机站得住，但不是 brickKit 自己文档里那个"典型场景"（JVM 内存）**。如果以后有人（包括
AI 自己）拿 brickKit 这份文档来质疑"阶段四是不是不必要"，答案是：不必要的是"为了省 Go 的内存"，必要的是
"在 62 个组件铺满之前，用最小代价把这套跨语言都要用到的机制验证、机制化、写进回归门禁"——这条理由第 9.6.1
节自己已经讲得很清楚，本记录只是把 brickKit 文档带来的表面疑问显式解掉，不需要因此修改阶段四计划的范围。

## 3. ⛔ 路线 A（Docker 网络别名）根本走不通，不要在实现时重新试一遍

原文 §4.2.1/§4.2.3 的推理链：

1. Docker 网络别名（`aliases`）看起来是最直觉的方案——把外壳容器挂上全部 11 个组件的版本化服务名作为别名。
2. 但它要求这 11 个服务名在平台侧"空着"（没有同名 service 存在，Docker 内嵌 DNS 才会用别名兜底）。
3. 现有开关（`enabled: false`、从 `brickkit.yaml` 删掉、`local: true`）里，**只有 `local: true` 能腾出
   这些名字**，但 `local: true` 一旦生效，会在每个依赖方容器里写 `extra_hosts`（落在 `/etc/hosts`），而
   glibc/musl 的解析顺序是 `hosts: files dns`——**先查文件命中就不问 DNS 了**，网络别名因此被 `/etc/hosts`
   完全盖住，一行都不会生效。

**实现时的判据：不要"两条路都接上试试看哪条更稳"——直接只用 `local: true`，网络别名配置写了也是死代码，
留着反而会在排障时把人引向错误方向。** 这条已经是设计书 §13.1 的既有结论，本节只是把"为什么第一次做外壳的
人会想岔"这条背景显式记下来，免得 Task 2 实现时重新犹豫一遍。

## 4. 🔍 产出 7（跨外壳环境变量表）的"跨外壳"分支，本阶段的真实依赖图里可能一次都不会被触发

这是本次调研里**最值得在开工前想清楚**的一条，因为它直接影响 Task 4 该做多少工作、该怎么验证。

**推演过程**：

- brickKit 对每个 `local: true` 组件生成一份 `local-debug.<服务名>.env`，其中把每一条依赖地址都改写成
  `http://localhost:<对方的 localPort>`——这份文件的**隐含假设是"只有一个本地进程，其余都是真实容器"**
  （设计书 §13.8.1 原话）。
- 当**两个互相依赖的组件都是 `local: true`，且真的落在同一个物理进程（同一个外壳）里**时，这份文件对
  "对方的地址是 `localhost:<对方端口>`"这句话恰好是**正确的**——因为两者确实共享同一个 `localhost`
  网络命名空间。这种情况下，brickKit 自己朴素生成的 `local-debug` 文件不需要任何改写就是对的。
- 只有当**两个互相依赖的组件都是 `local: true`，但落在两个不同的物理进程（不同外壳）**时，"localhost"
  才会指向错误的进程——这正是设计书 §13.8.1 表格里"跨外壳：外壳二的 `crm-lead` → 外壳一的
  `mdm-customer`"那一行要解决的问题，也是产出 7 真正有不可替代价值的场景。
- **本阶段的真实依赖图里，核对一遍发现没有这种情况**：11 个 Go 组件全部落在同一个外壳（互相之间的依赖天然
  是"同外壳"，不需要改写）；`infra-print` 是本阶段唯一的另一个 `local: true` 组件，但**它零依赖，也没有
  任何一个 Go 组件把它声明成 `component.yaml` 里的正式依赖**（核实过 `erp-sales`/`crm-opportunity` 的
  `dependencies.components`，都没有 `infra/print`）——"打印送货单"这条业务动作是 `frontend-standard`
  （独立容器，不是 `local: true`）直接调用 `infra-print` 的入口，不经过任何后端组件的依赖声明，`erp-sales`
  只是 UI 上那个按钮的位置，不是同步调用链的一环（`docs/design/frontend-standard.md` §1.1 与
  `docs/design/infra-bff-mobile.md` §"不归我"表都确认了这一点）。

**结论（一条可证伪的预测，留给 Task 4/5 真机验证）**：产出 7 在本阶段的"跨外壳改写"分支大概率**不会被真实
触发**——需要它的场景要等阶段五/六真的出现第二个 Go 外壳或 Python 外壳装了多个互相依赖的模块才会出现。
**这不代表 Task 4 可以跳过产出 7**：机制必须现在就写对（阶段五/六会立刻用到），只是验证方式要相应调整——
不能指望本阶段的真实依赖图里天然长出一个跨外壳案例来验证它，Task 4 的验证步骤需要**故意构造一个假的、
两个组件分属不同 local 进程的 fixture** 去验证跨外壳分支本身是对的，不能只用真实的 11+1 个组件验证
（那样只会验证到"同外壳不需要改写也是对的"这半条，验不到"跨外壳需要改写"那半条）。

## 5. ✅ 迁移状态表主键冲突这条坑，本项目已经被既有约定规避

原文 §4.4：**"合并后多个模块更容易共用一个库——迁移状态表的主键必须含组件标识，否则两个模块的迁移互相顶掉"**。

核对本项目现状：Design Book §11.2.3（"迁移状态表必须落在每个组件自己的 schema 里"）从阶段一起就是既有铁律，
每个组件的 `schema_migrations_<component>` 表本身就落在各自独立的 schema 下（不是共享一张全局
`public.schema_migrations`）——**这条坑对本项目不成立，不需要为合并部署额外做任何事**。这是"以前定的规矩
恰好在未来的场景里生效"的一个正面案例，值得记下来但不需要转成任务。

## 6. ✅ `module.New` 位置核查：11 个 Go 组件全部确认在 `backend/module` 公开包

外壳要能 `import` 每个组件的装配入口，前提是这个函数不在 Go 的 `internal/` 目录下（Go 语言规则：
`internal/` 包只能被同一个 module 树内的代码 `import`，外部 module 引用会在编译期直接报错）。逐个核对
11 个组件的目录结构，**全部确认 `module.New` 落在 `backend/module/module.go`，不在 `internal/` 下**——
以 `mdm-customer` 为例，`backend/module/module.go` 包注释原话："外壳启动器与 `be-ops` 产出 4 都按它生成"，
说明这条设计从阶段一起就是刻意的，不是巧合。11 个组件（`mdm-customer`/`mdm-product`/`erp-inventory`/
`erp-finance`/`erp-sales`/`infra-authz`/`infra-iam-casdoor`/`infra-workflow`/`infra-notification`/
`integration-im-dingtalk`/`crm-opportunity`）逐一核实，无一例外。

`internal/` 目录下的 `service`/`http`/`grpc`/`repo`/`partition` 等真实实现细节保持完全不可见——外壳能拿到
的只有 `module.New` 返回的 `*besdk.Module`（handler + 迁移 + 后台循环的集合），符合 §13.3 铁律七"模块只
交回零件"的设计意图。

## 7. 🧭 `be-shell-go` 引入 11 个组件模块的方式：当普通 Go 依赖装，不是 `go.work`

核对每个组件的 `go.mod`，module path 统一是 `github.com/brickKit/<组件仓库名>`（例如
`github.com/brickKit/mdm-customer`）——这些仓库本来就各自打了 tag（`v1.0.x`），**完全符合一个普通 Go
module 依赖的形状**。

**判断：`be-shell-go` 的 `go.mod` 直接 `require` 这 11 个模块的当前版本 tag，像引用任何第三方库一样，
不使用 `go.work`。** 理由：

- `go.work` 是**本地多仓库联调**的工具（一次改多个仓库、互相看得到彼此的未提交改动），不适合作为最终构建
  产物的依赖管理方式——`Dockerfile` 里的 `go build` 只应该依赖 `go.mod`/`go.sum` 锁定的版本，不应该依赖
  一份假设"这些仓库目录都在本地某个相对路径下"的 `go.work` 文件（CI/生产构建环境不会有那些目录）。
- 用普通依赖版本锁定，还顺便复用了这个项目已有的全部版本纪律基础设施——`be-shell-go` 升级某个组件版本
  就是改一行 `go.mod` + `go mod tidy`，`bump-version` 工具（SOP-W-11）以后完全可以把 `shells/go/go.mod`
  也纳入级联更新范围，不需要为"外壳怎么引用组件"另设计一套版本管理。
- `go.work` 仍然可以、也应该在**本地开发**时使用（比如同时改 `erp-sales` 和 `be-shell-go` 时不想每次都
  提交 tag 才能联调），但这只是开发者本机的便利文件，`.gitignore` 掉，不进任何仓库的版本控制，更不能让
  `Dockerfile` 依赖它。

## 8. 🧭 Go 侧"一个进程内起多个 HTTP/gRPC Server"的现成模式

Go 生态里让"多个长驻 goroutine 各自做自己的事、任一个失败就整体优雅退出"这件事，标准做法是
`golang.org/x/sync/errgroup`：

```go
g, ctx := errgroup.WithContext(ctx)
for _, m := range modules {
    m := m
    g.Go(func() error { return serveHTTP(ctx, m.Port, m.Handler) })
    if m.GRPCPort != 0 {
        g.Go(func() error { return serveExtraPort(ctx, m.Name, m.GRPCPort, m.RegisterGRPC, logger) })
    }
}
if err := g.Wait(); err != nil { ... }
```

`errgroup.WithContext` 的语义正好符合外壳需要的"任一个 `Listen` 失败，取消其余全部、优雅退出"——这与
`be-sdk-go` 现有 `RunStandalone` 里"单个模块失败就退出整个进程"的既有判据是同一种机制，只是外壳这里从
"1 个模块"变成"N 个模块"，每个模块各自的 `serveHTTP`/`serveExtraPort` 调用保持不变（这也是 §"be-sdk-go
补外壳级构件"这条判断成立的技术依据——`serveHTTP`/`serveExtraPort` 已经是可以直接复用的独立函数，只是
目前是 `standalone.go` 内部私有的，导出即可用，不需要重写）。

⚠️ **需要额外注意的一点（Task 2 实现时验证）**：`errgroup` 默认只返回**第一个**非 nil 错误，其余 goroutine
的错误会被丢弃——外壳场景下，"哪个模块先失败"这个信息比 `RunStandalone` 单模块场景更重要（不知道是哪个
模块出问题，排障范围是 11 个模块）。实现时应该在每个 `g.Go` 内部先用 `logger.Error` 把模块名和错误一起
记下来，再把错误返回给 `errgroup`——不能只依赖 `errgroup.Wait()` 返回的那一个错误做诊断。

## 9. 🧭 Python 侧同一个问题的现成模式

Python 的 `asyncio` 生态里，同一个进程内跑多个 ASGI app 各自绑定不同端口的现成写法是各自建一个
`uvicorn.Server` 实例（不经过 `uvicorn.run()`，那个入口是给"单进程单 app"设计的），用 `asyncio.gather`
一起跑：

```python
servers = [uvicorn.Server(uvicorn.Config(app=m.app, port=m.port, ...)) for m in modules]
await asyncio.gather(*(s.serve() for s in servers))
```

`asyncio.gather` 默认在**任一个协程抛异常时不会立即取消其余的**（要显式传 `return_exceptions=False` 且
自己处理取消逻辑，或者用 `asyncio.TaskGroup`——Python 3.11+ 的新 API，行为更接近 Go 的 `errgroup`：一个
子任务失败会自动取消组内其余任务）。**建议直接用 `TaskGroup`**（如果目标 Python 版本 ≥ 3.11，需要在
Task 3 开工前核实 `be-sdk-python`/`infra-print` 当前锁定的 Python 版本），语义上与 Go 侧的 `errgroup` 保持
一致，两个外壳"任一模块失败即整体退出"这条行为不应该因为语言不同而不一致。

本阶段只有 1 个 Python 模块（`infra-print`），这条调研主要是为阶段五/六真的有第二个 Python 组件时不用
重新调研——**Task 3 的骨架仍然要写成"跑一个 `TaskGroup`/`gather` 循环"的形状，即使循环体当前只跑一次**，
不能因为"现在只有 1 个"就走单模块的近路（同 Task 3 自己判据里已经写的"外壳骨架必须走 N 模块的那条代码
路径，即使 N=1"）。
