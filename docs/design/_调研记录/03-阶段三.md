## infra-iam-casdoor：适配层与 claims 镜像

**采纳进**：[`infra-iam-casdoor.md`](../infra-iam-casdoor.md) §3.2（镜像同步 + 顺序保证）、§4（事件）、§8（参考实现）；
连带改了 [`infra-authz.md`](../infra-authz.md) §4（新增一条消费边）与设计书 §6.1（两句被第 14 章推翻的话）。

### 1. 🧭 设计书 §6.1 与第 14 章互相矛盾，且矛盾指向一个真实的实现难题

不是文字瑕疵，是两条硬约束顶在一起：

| 约束 | 出处 | 原文大意 |
|---|---|---|
| 登录流不经过适配层 | §6.1 | 浏览器直连 Casdoor 走标准 OIDC |
| JWT 必须带 `roles[]` / `dept_path` / `org_id` | §14.1.5 | 而这些数据在 `infra-authz` 的表里，Casdoor 不知道 |

**推导**：Casdoor 是签发者，签发时不问任何人（否则就"经过适配层"了）；那么它签的 token 里要有角色，
角色就只能**在签发之前**已经在 Casdoor 里。→ 唯一解是镜像同步。

**这条推理不依赖任何外部项目的实现细节**，所以标 🧭。它推翻的是 §6.1 那句"分配在 iam"——如果角色本来就
分配在 iam（Casdoor）里，这个问题根本不存在；正因为第 14 章把角色挪去了 `infra-authz`（为了换 Keycloak 时
不迁数据），才需要镜像这一步。**§6.1 那句话是决策 115 之前的世界观残留**，已回写。

### 2. ⛔ 一条走错又被推翻的路：让 Casdoor 直接签带角色的 token

**这一节记的是错误答案，保留它是因为它比正确答案更有教育意义。**

初版设计（本文件与设计计划的第一版）是这样的：Casdoor 仍然直接签发业务组件要验的那个 JWT，
本组件负责把 `infra-authz` 的角色**镜像**进 Casdoor 的用户属性，让它签得出 `roles[]`。为了防止
"authz 改完角色立刻写 `stale_since` → 组件 401 → 前端刷新 → Casdoor 还没同步到、刷回来还是旧角色 → 再 401"
这个**转不出去且服务端零报错**的死循环，还专门设计了一条"等镜像落地确认再写 `stale_since`"的握手
（新增一个 `infra.iam.claims.synced.v1` 事件 + `infra-authz` 多消费一条边）。

**被一句提问推翻**：*"Casdoor 的镜像不是只用来做用户登录么？只要用户登录了，理论上不应该管 Casdoor 事情了吧？"*

回头核对，这条路同时踩了三个独立的否决点，任何一个都足够：

| 否决点 | 说明 |
|---|---|
| **踢人链路是断的** | §14.1.6 要求"踢人 → refresh token 已撤销 → 刷新失败 → 登出"，而 `infra-authz.md` §3 把撤 refresh token 列为 **authz 自己的接口**。token 若由 Casdoor 签，authz 撤不了，除非反过来调 Casdoor——直接违反 authz 设计计划 §5 的"不依赖 iam，方向是反的" |
| **死循环是自找的** | 它整个来自"镜像必然异步"这个前提。换成签发时现问 authz，前提消失，那套握手也就不需要存在了 |
| **把刚拆开的东西粘回去** | §14 把角色放进 authz 图的就是换 Keycloak 时角色数据一行不迁；往 Casdoor 镜像一份等于自毁这条 |

**更要命的是，`infra-authz.md` 早就写了正确答案，是我没对照**：它的 §3 里 `ResolveClaims` 的说明白纸黑字写着
"给 `iam` 适配层：`sub` → `roles[]` / `dept_path` / `org_id`。**登录与刷新时各调一次**"——
"登录时调一次"只有在**适配层站在签发路径上**时才成立。写新组件时没有回头读被依赖方的设计计划，
是这次的直接教训（阶段二复盘 §2.1 记的 `erp-finance` 字段名猜错，根因完全一样）。

### 3. 🧭 正确形态：两个 token，Casdoor 登录完就退出

```
① 浏览器 ↔ Casdoor       纯 OIDC，认证 100% 归它 → 身份 token（无角色）
② 前端 → 适配层 换一次    验 Casdoor 签名 → 调 authz ResolveClaims → 签出应用 token
③ 业务组件               验适配层的 JWKS（iamJwksUrl 指向适配层，不是 Casdoor）
④ 刷新走适配层            重新调 ResolveClaims，角色天然最新
```

**"登录完就不该再管 Casdoor 了"这条直觉是对的**，且它同时解掉了上面三个否决点：踢人由适配层作废自己的
refresh token（authz 通过事件通知）、死循环因为"现问不缓存"而不可能发生、Casdoor 里一个角色字段都不写。

**代价必须写明**（设计计划 §5 也记了）：适配层成为签发方，要管签名密钥、JWKS、密钥轮换、refresh token 存储；
且**登录与刷新这条路上多了 `infra-authz` 这一环**——authz 挂掉时已登录的人做业务不受影响（§14.1.9 fail-static），
但新登录和刷新会失败。这是"角色零延迟、且不可能签出旧角色"换来的账。

### 4. 🔍 Casdoor webhook 的投递保证与签名机制

`webhook_deliveries` 这张去重表的设计（去重键取什么、要不要轮询兜底）取决于 Casdoor 到底给不给：
① 稳定的投递 ID；② 签名头；③ 失败重投。**三个都没确认过。**

**最坏情况的对策已经想好**：如果 webhook 既没有投递 ID 也没有签名，就退化成"定期轮询 Casdoor 的用户列表
+ 按 `updated_time` 增量对账"，`webhook_deliveries` 换成 `user_sync_cursor`。这条退化路径不影响其他任何
组件——`infra.iam.user.*.v1` 事件照发，下游看不出区别。→ 设计计划 §9 第 2 条。

### 5. 🔍 钉钉 unionid 的来源——**这条会牵连 `infra-notification`**

`infra-notification` 要把审批通知发给某个人，需要这个人的钉钉 id。链路上唯一可能持有它的是 Casdoor
（如果客户用钉钉扫码登录，Casdoor 作为 OIDC Provider 对接钉钉时会拿到 unionid）。

**没确认的是**：Casdoor 把第三方登录拿到的 unionid 存在哪、能不能通过 API 读出来。

**两条分支**（开工时二选一，`infra-notification` 的设计要能兼容两者）：

| 分支 | 如果 Casdoor 存了 unionid | 如果没存 |
|---|---|---|
| 数据来源 | `infra.iam.user.*.v1` 事件带上 `im_accounts` | 需要人工维护一张"系统用户 ↔ 钉钉用户"映射表 |
| 归谁 | 本组件（从 Casdoor 读出来发事件） | `infra-notification`（它自己的通道偏好表里多一列） |

→ 本组件设计计划 §9 第 3 条；`infra-notification` 的设计计划要在它的 §9 里记同一条的另一半。
