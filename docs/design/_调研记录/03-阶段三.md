## infra-iam-casdoor：适配层与 claims 镜像

**采纳进**：[`infra-iam-casdoor.md`](../infra-iam-casdoor.md) §1.1（登录方式范围）、§3.2（两个 token）、§3.3（签发方的责任）、§4、§8；
连带改了设计书 §6.1（两句被第 14 章推翻的话）与**附录 D 的登录时序图**。

### 1. 🧭 设计书 §6.1 与第 14 章互相矛盾，而矛盾底下藏着"谁签 token"这个从没被问过的问题

不是文字瑕疵，是两条硬约束顶在一起：

| 约束 | 出处 | 原文大意 |
|---|---|---|
| 认证流不经过适配层 | §6.1 | 浏览器直连 Casdoor 走标准 OIDC |
| JWT 必须带 `roles[]` / `dept_path` / `org_id` | §14.1.5 | 而这些数据在 `infra-authz` 的表里，Casdoor 不知道 |

**关键在于：这两条只有在"Casdoor 直接签业务组件要验的那个 token"这个隐含前提下才矛盾。**
而这个前提从来没有被明写过——它只是**决策 115/116 之前的世界观残留**，留在 §6.1 的一句话
（"JWT 携带权限 Claims"）和附录 D 的一张时序图（"IAM-->>FE: 返回 JWT (含权限 Claims)"）里。

**角色被挪进 `infra-authz` 之后，从来没有人回头问过"那现在谁签这个 token"。** 一旦问出来，
前提就松动了：认证归 Casdoor、签发归适配层，两条约束同时成立（详见 §3）。

⚠️ **我第一版没问出这个问题，而是接受了那个前提、去解它带来的难题**（结果就是下面 §2 那条走错的路）。
**这是本阶段最值得记的方法论教训：当两条约束"看起来必然矛盾"时，先找出那个没被明写的隐含前提。**

### 2. ⛔ 一条走错又被推翻的路：让 Casdoor 直接签带角色的 token

**这一节记的是错误答案，保留它是因为它比正确答案更有教育意义。**

初版设计（本文件与设计计划的第一版）是这样的：Casdoor 仍然直接签发业务组件要验的那个 JWT，
本组件负责把 `infra-authz` 的角色**镜像**进 Casdoor 的用户属性，让它签得出 `roles[]`。为了防止
"authz 改完角色立刻写 `stale_since` → 组件 401 → 前端刷新 → Casdoor 还没同步到、刷回来还是旧角色 → 再 401"
这个**转不出去且服务端零报错**的死循环，还专门设计了一条"等镜像落地确认再写 `stale_since`"的握手
（新增一个 `infra.iam.claims.synced.v1` 事件 + `infra-authz` 多消费一条边）。

**被一句提问推翻**：*"Casdoor 的镜像不是只用来做用户登录么？只要用户登录了，理论上不应该管 Casdoor 事情了吧？"*

回头核对，这条路同时踩了三个独立的否决点，任何一个都足够：

| 否决点 | 说明 |
|---|---|
| **踢人链路是断的** | §14.1.6 要求"踢人 → refresh token 已撤销 → 刷新失败 → 登出"，而 `infra-authz.md` §3 把撤 refresh token 列为 **authz 自己的接口**。token 若由 Casdoor 签，authz 撤不了，除非反过来调 Casdoor——直接违反 authz 设计计划 §5 的"不依赖 iam，方向是反的" |
| **死循环是自找的** | 它整个来自"镜像必然异步"这个前提。换成签发时现问 authz，前提消失，那套握手也就不需要存在了 |
| **把刚拆开的东西粘回去** | §14 把角色放进 authz 图的就是换 Keycloak 时角色数据一行不迁；往 Casdoor 镜像一份等于自毁这条 |

**更要命的是，`infra-authz.md` 早就写了正确答案，是我没对照**：它的 §3 里 `ResolveClaims` 的说明白纸黑字写着
"给 `iam` 适配层：`sub` → `roles[]` / `dept_path` / `org_id`。**登录与刷新时各调一次**"——
"登录时调一次"只有在**适配层站在签发路径上**时才成立。写新组件时没有回头读被依赖方的设计计划，
是这次的直接教训（阶段二复盘 §2.1 记的 `erp-finance` 字段名猜错，根因完全一样）。

### 3. 🧭 正确形态：两个 token，Casdoor 登录完就退出

```
① 浏览器 ↔ Casdoor       纯 OIDC，认证 100% 归它 → 身份 token（无角色）
② 前端 → 适配层 换一次    验 Casdoor 签名 → 调 authz ResolveClaims → 签出应用 token
③ 业务组件               验适配层的 JWKS（iamJwksUrl 指向适配层，不是 Casdoor）
④ 刷新走适配层            重新调 ResolveClaims，角色天然最新
```

**"登录完就不该再管 Casdoor 了"这条直觉是对的**，且它同时解掉了上面三个否决点：踢人由适配层作废自己的
refresh token（authz 通过事件通知）、死循环因为"现问不缓存"而不可能发生、Casdoor 里一个角色字段都不写。

**代价必须写明**（设计计划 §5 也记了）：适配层成为签发方，要管签名密钥、JWKS、密钥轮换、refresh token 存储；
且**登录与刷新这条路上多了 `infra-authz` 这一环**——authz 挂掉时已登录的人做业务不受影响（§14.1.9 fail-static），
但新登录和刷新会失败。这是"角色零延迟、且不可能签出旧角色"换来的账。

### 4. 🔍 Casdoor webhook 的投递保证与签名机制

`webhook_deliveries` 这张去重表的设计（去重键取什么、要不要轮询兜底）取决于 Casdoor 到底给不给：
① 稳定的投递 ID；② 签名头；③ 失败重投。**三个都没确认过。**

**最坏情况的对策已经想好**：如果 webhook 既没有投递 ID 也没有签名，就退化成"定期轮询 Casdoor 的用户列表
+ 按 `updated_time` 增量对账"，`webhook_deliveries` 换成 `user_sync_cursor`。这条退化路径不影响其他任何
组件——`infra.iam.user.*.v1` 事件照发，下游看不出区别。→ 设计计划 §9 第 2 条。

### 5. 🧭 登录方式的范围定了，而它连带决定了"钉钉通知发给谁"怎么解

**范围（已定）**：账号密码注册+登录、微信、QQ、Google。**没有钉钉。**

这四种全部是 Casdoor 侧的配置，适配层零代码——**不管用户用哪种方式认证，Casdoor 产出的都是同一个标准
OIDC 身份 token，适配层根本不知道用户是扫码还是输密码进来的**。以后加飞书/企业微信/LDAP/SAML 同理。

**但"没有钉钉登录"有一个连带后果**：Casdoor 拿不到用户的钉钉身份（unionid），而阶段三的审批通知恰恰要
发钉钉。所以链路只能改成：

```
Casdoor 持有手机号（注册时填 / 管理员录）
  → infra-iam-casdoor 把手机号放进 infra.iam.user.*.v1 事件
  → infra-notification 存进 user_contacts 快照，派发时把手机号给适配器
  → integration-im-dingtalk 用"手机号查 userid"接口换成钉钉 id（它自己缓存）
```

**分工的判据**：手机号是**跨平台通用的自然标识**，钉钉 userid 是**平台特有的**——所以前者可以在链路上传递，
后者必须由对应的适配器自己解析。这条是族级规矩，对后面四个 IM 适配器同样成立
（见 `integration-im-dingtalk.md` §1.1）。

⚠️ 另一半的风险记在 `infra-notification.md` §9 第 2 条：**社交登录注册的用户可能没填手机号**，
那样通知发不出去。对策是记 `SUPPRESSED` + 在待办界面显示"未能通知"，而不是静默失败。

🔍 **待核**：钉钉那个"手机号查 userid"接口的权限要求与频率限制（→ dingtalk 设计计划 §9 第 1 条）。

### 6. 🧭 明确没有参考、且不打算参考的

**Ory Hydra / Zitadel / Authentik 这类"自己实现 OIDC Provider"的项目**：不是没查，是**问题不成立**——
我们不实现 Provider，Casdoor 官方镜像才是 Provider。评估它们等于重新讨论"要不要自己写 IdP"，
那个问题决策 86（零代码的东西不包成组件）与决策 87（JWT 本地验签）早就答完了。

**Casbin**：`infra-authz` 设计计划 §8 已经判过（只看模型分层、不引入）。本组件与它更无关——
我这一层不做任何判定。

## infra-workflow / infra-notification / integration-im-dingtalk：通知链路三件套

**采纳进**：[`infra-workflow.md`](../infra-workflow.md)、[`infra-notification.md`](../infra-notification.md)、
[`integration-im-dingtalk.md`](../integration-im-dingtalk.md) 三份的 §1/§3/§4/§8。

> 三份放在一起调研、一起写，因为它们是一条链：workflow 建待办 → notification 决定发给谁走哪个通道 →
> dingtalk 真的调 API。**分开写必然互相猜**——阶段二 `erp-finance` 消费 `sales.order.created.v1` 时字段名
> 猜错（复盘 §2.1），根因就是两份设计计划各写各的。

### 1. 🧭 三条铁律推导出的边界，比"职责划分"更硬

设计书 §6.6 给 workflow 三条禁令（严禁业务规则判断 / 严禁直查业务库 / 严禁反向同步调用业务组件），
§6.9 给适配器一条（严禁业务逻辑）。把它们当公理往下推，很多看起来"可以商量"的设计其实只有一个答案：

| 推论 | 从哪条来 |
|---|---|
| 审批人只能由业务组件算好传进来 | 铁律一：算审批人 = 业务规则 |
| 待办列表要显示的字段只能是**创建时传入的快照** | 铁律二：不能回查业务库 |
| 审批结果只能靠**事件**回给业务组件 | 铁律三：不能反向同步调用 |
| `exception` 任务不能有"重试"按钮 | 铁律三：重试 = 反向调用业务组件 |
| 适配器不能自己重试 | §6.9 + §6.7"重试逻辑不要重复写" |

**这几条我原本以为是设计选择，推完发现全是被约束定死的**——所以 `infra-workflow.md` §1.2 专门列了
"三种看起来很合理、但会让本组件变质的需求"，因为它们每一条单独看都很小、都顺手能做。

### 2. 🧭 通知中心的入口：为什么不给同步 `Notify` rpc

三选一的取舍，最后选了"只走事件"：

| 方案 | 否决/采纳理由 |
|---|---|
| 同步 `Notify` rpc | ❌ `infra-notification` 是 `default` 但可被裁；任何同步调用方都要建依赖边，而**通知发不出去绝不该让业务动作失败**。且 workflow 铁律三本来就不能同步调它——主要来源都走不了同步，再为别人开一个口就是两套幂等两套重试 |
| 通用意图事件（`infra.notification.requested.v1`，谁要通知谁发这条） | ⏸ **暂不做**。它要求所有发布方统一改，而阶段三只有**一个**通知场景（审批待办）。SOP-P 的判据："逻辑本身简单却硬套模式是更糟的结果" |
| 消费来源方自己的领域事件 ✅ | 阶段三只消费 `infra.workflow.task.created.v1` 一条。**泛化的触发点写死在设计计划 §3.1**：来源事件超过 5 条时改成通用意图事件 |

### 3. 🧭 族级 subject 与包名——这是"加一个通道不用改通知中心"的全部机密

`channel:im` 有五个成员，`slot:iam` 有两个。**族内契约面必须完全一致**（§5.11），落到具体就是三条：

| 东西 | 必须是族级 | 反例（写成实现级会怎样） |
|---|---|---|
| proto 包名 | `integration.im.v1` / `infra.iam.v1` | 换通道/换 IdP 时调用方要改 import 路径 |
| 派发 subject | `infra.notification.dispatch.im.v1` | 通知中心要知道装了哪些适配器 = 把装配期知识搬进运行时 |
| 回调 subject | `integration.im.result.v1`（`adapter` 放 payload） | **每加一个适配器都要改通知中心的消费列表**，族就白分了 |

⚠️ **写 `infra-notification.md` 时我第一版把回调写成了 `integration.im.dingtalk.result.v1`（实现级），
写 dingtalk 那份时才发现不对、回头改的。** 记一笔是因为：这种错在单个组件的视角里看不出来，
**只有把族里两份文档摆在一起才暴露**——这正是 SOP-D 要求"跨组件对照着看"的意义。

### 4. 🧭 NATS 是广播，所以适配器必须自己过滤

`besdk.Consume` 用的是 `nc.Subscribe` 不是 `QueueSubscribe`（阶段二踩坑记录 E1 实测确认）。
五个 IM 适配器订同一个 subject → **每个都会收到每一条**。所以每个适配器收到后第一件事是
"看 `target_adapters` 里有没有我，没有就丢弃"。

**漏掉这一步的症状**：装了三个 IM 通道的客户，每条通知收到三遍。⚠️ 这条要写进族级 `AGENTS.md`，
因为它对后面四个成员同样成立，而且**单装一个通道时测不出来**。

### 5. 🧭 `retryable` 划出的分工线

重试策略归通知中心（§6.7），但"这个错误值不值得重试"只有适配器知道（钉钉的错误码是钉钉特有的）。
所以回调事件带一个 `retryable` 布尔：**适配器判"值不值得"，通知中心定"隔多久、几次"**。

两边都判 → 打架（外面 3 次 × 里面 3 次 = 实际 9 次）；都不判 → 给离职员工重试五次。
细则见 `integration-im-dingtalk.md` §4.1 那张错误码表。

### 6. ⭐ 判掉了设计书 §5.11.1 悬着的"审批路由"那一行

§5.11.1 的示例表里，「审批路由」的结论栏一直写着"槽位族信号，**但要先确认它不违反 §6.6**"。
现在 workflow 真的设计出来了，可以确认并判掉：

1. **审批路由根本不在 workflow 里**——"这张单该谁审"由业务组件算好后通过 `assignee` 传入（铁律一）；
2. 所以这条分歧长在 `erp-sales` / `erp-purchase` 这类业务组件内部，而它们**都被 `crm-*`/BFF 建了强依赖边**；
3. 按 §5.11 硬约束 → **不能做成 slot，落点是业务组件的 `customer_fork`**。

与阶段二那 9 条分歧的判定完全一致（复盘 §4 第 5 条）。**已回写设计书 §5.11.1。**
