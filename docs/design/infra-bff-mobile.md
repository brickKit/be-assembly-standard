# infra-bff-mobile · 移动端聚合层 设计计划

| 项 | 值 |
|---|---|
| 组件 ID | `infra/bff-mobile` |
| 仓库名 | `infra-bff-mobile` |
| 端口 | HTTP `8500`（**无 gRPC**）；`exposePort=28500` ← 抄 `registry/ports.tsv` |
| schema / role | **无**（§6.5 铁律：严禁直连 DB。`registry/schemas.tsv` 里那一行是注释） |
| 语言 | **TypeScript**（全系统第一个） |
| 框架栈 | GraphQL Yoga + DataLoader + `be-sdk-ts`（设计书 §12.4 TS 那一列 / §11.4.3） |
| 合并部署时进 | **不进外壳，保持独立容器**（§13.5：跨语言合不进来） |
| 装配角色 | `default` |
| 阶段 | 第三阶段 |

> 规范源是设计书 **§6.5**（职责与两条铁律）与 **§11.4.3**（GraphQL 的三条硬限制）。

## 1. 边界

**归我：**

- **展示聚合**：一个页面需要的数据，前端发**一个**查询，我并发去调各组件拼好返回。
- **防 N+1**：所有对后端的读取走 DataLoader 绑定各组件的 `batchGet`（§6.5 强制）。
- **弱网优化**：Persisted Queries（§11.4.3 强制 `persisted_queries_only: true`）。
- **按装配裁剪 schema**：这个环境没装的组件，对应的字段不该出现（§3.3）。

**不归我：**

| 什么 | 归谁 | 为什么 |
|---|---|---|
| **任何业务逻辑** | 各业务组件 | §6.5 铁律一。**包括看起来无害的**："这张单能不能取消"要问 `erp-sales`，不许我按 `status` 字段自己判 |
| **任何数据库** | 各业务组件 | §6.5 铁律二：**严禁直连 DB**。我一张表都没有，连 `event_outbox` 都没有 |
| 金额计算、库存判定 | 业务组件 | §8.4：核心商业逻辑严禁放前端，而我在前端与后端之间——**放我这里等于放前端** |
| 鉴权判定本身 | 各业务组件的 `be-sdk` | 我**透传** JWT（§6.3），下游各自判。我不是安全边界（§14.1.8 说前端不是，我同理） |
| 写操作的编排 | 业务组件 | 见 §3.2 |

⚠️ **`data_scopes` 段仍然必须写**（§14.2.2：省略会被 `be-ops` 拦下），值是 **`none`**——我没有数据，
行级过滤由**下游组件**执行。这是"显式声明不需要"的典型场景。

## 2. 拥有的数据

**无。一张表都没有，也没有 schema。**

这不是"暂时还没有"，是 §6.5 的铁律二。写在这里是为了让下一个人不要"顺手加一张缓存表"：

| 看起来很合理的表 | 为什么不许建 |
|---|---|
| 查询结果缓存表 | 缓存要失效，失效要知道业务语义 → 立刻违反铁律一。**要缓存就用进程内内存 + 短 TTL**，重启即清 |
| Persisted Query 注册表 | **构建期产物**：前端构建时生成查询清单，随镜像发布、运行时只读（§3.4）。运行时可写就意味着有人能注册任意查询 |
| 用户偏好/最近浏览 | 那是业务数据，归对应的业务组件或 `infra-notification` 式的专门组件 |

**终态列表**：不适用（无持久化数据）。

## 3. 契约面

**gRPC：无。** 我**只作为客户端**调别人的 gRPC，不对外提供 gRPC（`registry/ports.tsv` 里 gRPC 列是 `-`）。

**对外：GraphQL over HTTP，单一端点 `POST /graphql`**（`exposePort=28500`，经网关暴露）。

⚠️ **`GET /healthz` 与 `GET /.well-known/...` 之外没有别的 REST 路径**——GraphQL 的全部表面积就是那一个端点。

### 3.1 ⭐ schema 手写，不从 proto 生成

**这是刻意的决定，理由是 BFF 存在的意义本身：**

| | 手写 schema ✅ | 从 62 份 proto 生成 ❌ |
|---|---|---|
| schema 长什么样 | **按前端页面裁剪**：`orderDetailPage(id)` 一个查询喂满一个页面 | 62 个组件契约的机械并集 |
| 前端要发几个查询 | 1 个 | 5 个，然后自己在客户端拼 |
| 结果 | 正是 §6.5 要的"展示聚合" | **丢掉了 BFF 存在的理由**——那样还不如让前端直接调网关 |

**代价说清楚**：后端契约变更不会自动传导过来，要人工同步。⚠️ **对策是 CI 检查，不是靠记性**——
`make contract-check` 里加一条：把我引用的各组件 proto 字段与它们当前的 `contracts/` 比对，对不上就红。
这条记进阶段三 Task 11 的验证清单。

### 3.2 ⚠️ 写操作（mutation）要不要经过我：本阶段**不做**

GraphQL 天然有 mutation，但本阶段**我只提供 query**。理由：

- 写操作往往是 TCC/补偿链的入口（`erp-sales` 的 `ConfirmOrder`），**它的幂等键、超时状态内省、补偿都在业务组件里**（§4.4/§4.5）；
- 我若代理写操作，就要转发幂等键、处理超时后的"薛定谔状态"——**那是业务编排，违反铁律一**；
- 前端写操作直接走网关到业务组件的 REST，路径更短、语义更清楚。

⚠️ 将来真要加 mutation，判据是：**它必须是纯转发（一进一出、不组合多个写）**。一旦出现"先调 A 再调 B"，
那就是编排，必须退回业务组件。记进 §9 第 2 条。

### 3.3 ⭐ 按装配裁剪：没装的组件，字段不该存在

62 个组件里客户可能只买了 10 个。我依赖的组件**大多是弱依赖**（§5），所以：

```
启动时读 be-sdk-ts 的 Endpoint(dep) 二值返回
  → 该组件没装（键根本不存在，不是空串，§3.6）
  → 构建 schema 时**不注册**它对应的字段与 resolver
```

⚠️ **不能用"注册了但返回 null"糊弄**：GraphQL 的 introspection 会把字段暴露出去，前端按 schema 写了查询、
运行时永远拿到 null——**症状是页面空白但不报错**。字段不存在时前端会在**构建期**就报错，那才是对的时机。

⚠️ 这条与 `/api/tenant/features`（`infra-iam-casdoor` §3.1）是**同一件事的两半**：前端靠 features 决定
渲染哪些菜单，靠我的 schema 决定能查哪些字段。**两边必须由同一份装配清单驱动**，否则会出现
"菜单点得进去但查询报字段不存在"。

### 3.4 三条硬限制（§11.4.3，全部强制）

| 限制 | 值 | 不做会怎样 |
|---|---|---|
| `max_depth` | **5** | 恶意/手滑的深层嵌套查询把下游打满。GraphQL 的经典 DoS 面 |
| `max_complexity` | **100** | 同上，深度不够时用广度打 |
| `persisted_queries_only` | **true** | 弱网下每次都传完整查询文本；且等于允许客户端发任意查询 |

**Persisted Queries 的形态**：前端构建时生成 `查询哈希 → 查询文本` 清单，**随我的镜像发布**（构建期产物，
不是运行时可写，见 §2）。运行时只接受清单里的哈希。⚠️ **这意味着前端与我的版本要配套发布**——记进 §9 第 3 条。

## 4. 事件

**发布：** 无。
**消费：** 无。

⚠️ **我完全不碰事件总线**，`component.yaml` 里连 `kind: mq` 的资源依赖都不声明。
理由：事件的用途是"改变某处状态"，而我不持有任何状态（§2）。**一个只读聚合层需要消费事件，
通常意味着它偷偷缓存了什么**——那是 §2 那张表禁的。

## 5. 依赖

**强依赖**：无。

⚠️ **一条强依赖都不能有，这是本组件形态决定的**：客户只买了一部分组件，而我要在任何装配组合下都能起来。
把任何组件写成强依赖，等于宣布"没买它就别想用移动端"。

**弱依赖**（`optional: true`，缺失时不注入 `*_ENDPOINT`，见 §3.6）：

| 组件 | 用途 | 缺失时降级成什么 |
|---|---|---|
| `mdm/customer` | `BatchGet` 客户 | schema 里不注册客户相关字段（§3.3） |
| `mdm/product` | `BatchGet` 产品 | 同上 |
| `erp/sales` | `BatchGet` 订单、`ListOrders` | 同上 |
| `erp/inventory` | `BatchGetBalance` | 同上 |
| `infra/workflow` | `ListTasks`——移动端待办是本阶段的主要场景 | 同上 |

**明确不依赖：**

| 谁 | 为什么不建依赖边 |
|---|---|
| **任何数据库 / NATS** | §6.5 铁律二 + §4。`component.yaml` 的 `dependencies.resources` 是空的——**全系统罕见** |
| `infra-iam-casdoor` | 验签走 `iamJwksUrl` 配置项（它是 `slot:iam`，建依赖边会废掉槽位机制） |
| `infra-authz` | `authzBundleUrl` 配置项。⚠️ 我**要**判权限键（每个 resolver 一个，§14.1.7 对 TS 侧同样成立），但那是 `be-sdk-ts` 的进程内 map 查找，不是依赖边 |
| `infra-print` | 打印是业务组件的事，前端直接走网关要 PDF |

## 6. 在同步图与三枢纽里的位置

**我在同步图上有 5 条出边（全部是弱依赖），零入边。**

**无环证明**：我的下游要么是零出边的枢纽（`mdm-*`、`erp-inventory`、`infra-workflow`），
要么是 `erp-sales`（它的出边全指向零出边节点）。**没有任何组件对我建边**（前端只认网关，不进同步图），
所以我永远是 DAG 的**根**，不可能出现在任何环里。

⚠️ **我横跨 CRM 与 ERP 两个域读数据，但这不违反 §1.4 的"CRM 与 ERP 零同步边"**——那条铁律禁的是
**业务组件之间**建跨域同步边（会让两域的事务耦合）。**展示层的聚合恰恰是设计书 §4.7"展示上推"指定的做法**：
跨域数据由 BFF/前端分别调、再聚合，而不是在后端建边。

## 7. 分区与归档策略

**不适用——本组件零持久化数据（§2）。**

唯一的"状态"是进程内的两样东西，都随重启清空、都不需要归档：

| 东西 | 生命周期 |
|---|---|
| DataLoader 的批次缓存 | **单次请求内**（这是 DataLoader 的标准用法：per-request 实例，不是全局单例） |
| authz bundle 的内存 map | 由 `be-sdk-ts` 管，15 秒轮询刷新（§14.1.4） |

⚠️ **DataLoader 必须是 per-request 实例**。做成全局单例的症状是**跨请求缓存命中，A 用户看到 B 用户的数据**——
这是"悄悄读到别人数据"的又一条路径，而且**测试极难发现**（单请求测试永远正确）。

**明确没有参考的**：Apollo Federation / GraphQL Mesh 这类**联邦网关**。**不是没查，是前提不成立**——
联邦解决的是"很多团队各自维护子图、需要自动组合"，而我们是**一个 BFF、一份手写 schema、按页面裁剪**（§3.1）。
引入联邦等于把"机械并集"这个我们刻意拒绝的形态又请回来。

**要避免它的什么：**

| 项目 | 它的做法 | 我们为什么不这么做 |
|---|---|---|
| 常见 BFF | 为了"性能"在 BFF 层加 Redis 缓存 | §2：缓存失效要懂业务语义 → 违反铁律一。且决策 71 已拒绝引入 Redis |
| 常见 GraphQL 服务 | 全局单例 DataLoader | §7：跨请求命中会让 A 看到 B 的数据 |
| 常见做法 | BFF 直连数据库"少一跳" | §6.5 铁律二。少那一跳换来的是它同时依赖 62 个 schema 的表结构 |

**读完之后，这里有没有「多种实现都合理、只是适配客户不同」的分歧？**

**无。** 核过 §5.11.1 的判据：BFF 的技术形态分歧（GraphQL / REST 聚合 / tRPC）确实现实存在，
**但它不满足"每一种都合理、只是适配客户不同"**——它是**一次性技术选型**，与客户画像无关，而且
**前端与 BFF 由同一份查询语言耦合**（前端代码里写的就是 GraphQL 查询），换 BFF 形态等于重写前端。
设计书 §6.5 已经选定 GraphQL，本组件照做。**不新增槽位族。**
