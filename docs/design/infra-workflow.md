# infra-workflow · 审批待办中心 设计计划

| 项 | 值 |
|---|---|
| 组件 ID | `infra/workflow` |
| 仓库名 | `infra-workflow` |
| 端口 | HTTP `8201` / gRPC `9201` ← 抄 `registry/ports.tsv` |
| schema / role | `infra_workflow` / `infra_workflow_rw`（归档 `infra_workflow_archive`） |
| 语言 | Go |
| 框架栈 | Gin + `database/sql`+`pgx stdlib` + `sqlc` + `golang-migrate`（设计书 §12.4） |
| 合并部署时进 | 外壳三 `go-infra` |
| 装配角色 | `default` |
| 阶段 | 第三阶段 |

> 规范源是设计书 **§6.6**。那一节开头三句是**铁律**，本文件全部设计都是它们的推论：
> **严禁包含业务规则判断、严禁直接查询业务数据库、严禁反向同步调用业务组件。**

## 1. 边界

**归我：**

- **待办的存储与分发**：接收业务组件登记的任务，维护"谁的待办箱里有什么"。
- **两类任务**：`approval`（要人做决定：同意/驳回）与 `exception`（要人去改数据，见 §1.1）。
- **审批动作与历史**：谁在什么时候做了什么、附言是什么，只增不改。
- **完成后发事件**：结果通过 `infra.workflow.task.completed.v1` 回给业务组件——**这是我唯一的回话方式**。

**不归我：**

| 什么 | 归谁 | 为什么 |
|---|---|---|
| **"这张单该谁审"** | **调用方（业务组件）** | §6.6 铁律一。金额分级、逐级上报、矩阵审批全是**业务规则**，判定权在业务组件；我只接收它算好的 `assignee` 并存下来。⚠️ 这条是本组件最容易被侵蚀的边界，见 §1.2 |
| **"审批通过之后该干什么"** | 业务组件 | 我发事件，它自己决定是过账、发货还是解冻。我不知道也不该知道 |
| 单据本身的任何数据 | 业务组件 | §6.6 铁律二。我只存一份**展示用快照**（标题、几个摘要字段），不 join、不回查 |
| 发通知给人 | `infra-notification` | 我发 `task.created` 事件，它决定发钉钉还是邮件（§4） |
| 补偿/重试的编排 | 业务组件自己（`erp-sales` 的 TCC 链） | 决策明确：我们不引入 Temporal 式编排引擎，补偿在发起方（§8） |

### 1.1 `exception` 任务：不给"重试"按钮，是刻意的

设计书 §6.6 原话：*业务规则校验失败时，不暴露"重试"按钮，而是创建异常待办任务，通知用户修正数据后重新提交。*

**为什么不给重试**：重试意味着我要能再次触发业务组件的某个动作——那就是**反向同步调用**（铁律三）。而且"原样重试"对一个因为数据不对而失败的操作几乎总是再失败一次。

**所以 `exception` 任务的闭环是**：我把人引到业务界面 → 人在那边改数据、重新提交 → **业务组件成功后显式调我的 `CloseTask`**。我全程不知道它做了什么，只知道"这条待办可以关了"。

⚠️ **阶段二欠的那笔账在这里还**：`erp-sales` 的 TCC 补偿链连续失败 3 次后标 `SUSPENDED` + 告警，当时留了"接 workflow 待办"这一步没做（`erp-sales` 设计计划 §4.4.4）。本阶段它改成调 `CreateTask(type=exception)`。

### 1.2 ⚠️ 边界侵蚀预警：三种看起来很合理、但会让本组件变质的需求

| 需求听起来是 | 真正在要求 | 正确落点 |
|---|---|---|
| "金额超过 10 万要多一级审批" | 我去读单据金额、按规则算审批链 | **业务组件**算好审批链，分多次调 `CreateTask`（或一次带上后续节点） |
| "审批人休假时自动转交给副手" | 我持有组织/代理关系 | 阶段五 `mdm-org` 上线后由业务组件查它；本阶段不做 |
| "待办列表要显示这张单的客户名和金额" | 我去 join 业务库 | 调用方**在 `CreateTask` 时把要展示的字段作为快照传进来**（同 `erp-sales` 订单行快照的先例） |

**三条的共同点**：每一条单独看都很小、都"顺手就能做"，做完之后本组件就同时违反了铁律一和铁律二，而且**不会有任何症状**——直到有人想把审批换成另一套实现，才发现它已经和业务缠死了。

## 2. 拥有的数据

| 表 | 分区键 | 粒度 | 说明 |
|---|---|---|---|
| `workflow_tasks` | 不分区 | — | 待办主体。含来源四元组、`assignee`、状态、**展示快照 JSONB** |
| `workflow_task_actions` | 不分区 | — | 审批历史，**只增不改**：谁、什么动作、附言、时间 |
| `command_idempotency` | 不分区 | — | 跨组件写命令的幂等声明（claim-first，见 §3.1） |
| `event_outbox` / `event_inbox` | `created_at` | 周 | 标准两张（§3.10、§11.2.5） |

强制字段全部符合 §11.2.1。

**数据权限**：`data_scopes` **两维**（§14.2.2 明确把"`infra-workflow` 待办"列进需要行级过滤的清单）：

```yaml
data_scopes:
  - { dimension: owner, column: assignee_sub,       mode: equals, tables: [workflow_tasks] }
  - { dimension: org,   column: assignee_dept_path, mode: prefix, tables: [workflow_tasks] }
```

⚠️ **`assignee_dept_path` 是"被指派人的部门"，不是"单据所属部门"**——待办的可见性跟着**人**走，不跟着单据走。写错成后者的症状是：部门主管看不到自己下属手上那张跨部门单据的待办。

**终态列表**（归档扫描靠它，§11.5.2）：`APPROVED` / `REJECTED` / `RESOLVED` / `CANCELLED`。活跃态只有 `PENDING`。

⚠️ **`workflow_tasks` 不分区**——跟随设计书 §11.2.5 的清单（那张表里有 `infra-notification`，**没有** `infra-workflow`）。理由是待办只在"需要人介入"时产生，量级远低于交易流水。⚠️ **但这条判断有前提**：如果客户把审批开到"每张单都要审"，量级会逼近订单量。记进 §9 第 2 条，实现后按真实数据复核。

## 3. 契约面

**gRPC（`infra.workflow.v1.WorkflowService`）：**

| rpc | 类型 | 幂等键 | 说明 |
|---|---|---|---|
| `CreateTask` | 命令 | ✅ `idempotency_key` | 登记待办。入参含 `assignee`、来源四元组、展示快照 |
| `CloseTask` | 命令 | ✅ `idempotency_key` | 业务组件主动关闭（`exception` 修好了、或单据已在别处完成） |
| `CancelTask` | 命令 | ✅ `idempotency_key` | 来源单据作废，待办跟着作废 |
| `GetTaskStatus` | 读 | — | ⭐ **必须支持按 `idempotency_key` 查，不只按 `task_id`**——见 §3.1 |
| `BatchGetTasks` | 读 | — | §3.8 强制的 `batchGet` |
| `ListTasks` | 读 | — | 按 `assignee`/状态/来源筛，**走 `ScopeFilter`** |

**对外 REST 路径前缀：** `/infra/workflow/**`

| 路径 | 权限键 | 说明 |
|---|---|---|
| `GET /tasks` | `infra.workflow.task.view` | 我的待办。数据权限两维在这里生效 |
| `GET /tasks/{id}` | `infra.workflow.task.view` | 详情 + 审批历史 |
| `POST /tasks/{id}/approve` | `infra.workflow.task.act` | 同意 |
| `POST /tasks/{id}/reject` | `infra.workflow.task.act` | 驳回（必须带附言） |
| `GET /admin/tasks` | `infra.workflow.admin` | 全局视图，**绕过 owner 维但不绕过 org 维** |

⚠️ **`CreateTask`/`CloseTask`/`CancelTask` 三条不暴露到 REST**——它们是组件间协议，不是人类操作。人能创建的待办只有一种可能："人代表某个业务组件创建"，那等于给了一条绕过业务规则的路。

### 3.1 ⭐ `GetTaskStatus` 必须能按 `idempotency_key` 查——阶段二用真机测试换来的教训

设计书 §4.5 要求跨组件写接口配一个 `GetStatus`。**阶段二 `erp-inventory` 第一版把它做成了只能按 `reservation_id` 查，直到 `erp-sales` 写真故障注入测试时才发现这是错的**——因为**超时恰恰是唯一拿不到返回值（也就拿不到 id）的场景**，那时调用方手里只有自己生成的 `idempotency_key`。为此 `erp-inventory` 连发了 `v1.0.1`（补请求字段）和 `v1.0.2`（补响应字段）两个版本（复盘 §2.1）。

**所以本组件从第一版就要求**：

```
GetTaskStatus(task_id) 或 GetTaskStatus(idempotency_key) → PENDING | APPROVED | REJECTED | RESOLVED | CANCELLED | NOT_FOUND
                                                            且响应里必须回带 task_id
```

⚠️ **`NOT_FOUND` 与 `CANCELLED` 不许合并成一个"没有"**（同 `erp-inventory` 的先例）：前者说明请求根本没到（可安全重试），后者说明已被作废（重试是错的）。

**幂等实现走 claim-first**（`erp-inventory` 的先例，比"先查后插"强）：先原子 `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING` 声明，声明成功才做真正的写。**"先查 `command_idempotency`、查不到再插入"在并发下有窗口**，两个同 key 的请求可能各建一条待办。

## 4. 事件

**发布：**

| subject | 分级 | 何时发 | payload 要点 |
|---|---|---|---|
| `infra.workflow.task.created.v1` | 核心 | 待办登记成功 | `task_id`、`assignee`、`title`、来源四元组、任务类型。**`infra-notification` 靠它触发通知** |
| `infra.workflow.task.completed.v1` | 核心 | 审批完成（同意/驳回）或 `exception` 被关闭 | `task_id`、来源四元组、`action`、`actor`、附言。⭐ **这是我回话给业务组件的唯一通道**（设计书 §4.3 事件图里的那条边） |
| `infra.workflow.task.cancelled.v1` | 核心 | 待办作废 | `task_id`、来源四元组、原因 |

⚠️ **三条全部标核心**：漏一条 `completed` 的后果是**业务单据永远停在"审批中"，而没有任何报错**——审批的人明明点了同意，单子就是不动。这是典型的"不报错、无症状"故障，必须走 Outbox + 至少一次投递。

**消费：** **无，一条都不消费。**

⚠️ **这是刻意的，而且是本组件最重要的一条约束。** 消费任何业务事件都意味着我要建立"哪个事件对应关掉哪条待办"的映射——**那就是业务规则**（铁律一）。单据作废时由业务组件显式调 `CancelTask`，不靠我去听事件猜。

## 5. 依赖

**强依赖**：无。
**弱依赖**：无。

**明确不依赖：**

| 谁 | 为什么不建依赖边 |
|---|---|
| **所有业务组件** | ⭐ §6.6 铁律三：**严禁反向同步调用业务组件**。方向永远是"它们调我 + 我发事件"，我这边零出边。一旦加一条（哪怕只是"审批前回查一下单据还在不在"），同步图立刻有成环风险，而且我就依赖上了业务语义 |
| `infra-notification` | 走事件。⚠️ **不能同步调它**：它可能根本没装（`default` 但可被裁），而待办登记不该因为通知发不出去而失败 |
| `infra-authz` | 同所有组件：走 `configSchema` 的 `authzBundleUrl` 拉 bundle，不是依赖边（§14.1.4） |
| `mdm-org` | 阶段五才有。审批人代理/组织树相关需求本阶段一律不做（§1.2） |

**谁依赖我**（入边，写在这里免得漏看）：

| 谁 | 强/弱 | 调什么 |
|---|---|---|
| `erp-sales` | **弱依赖**（`optional: true`） | `CreateTask`——补偿失败 3 次后建异常待办。⚠️ 它必须用 `besdk.Endpoint()` 的二值返回判断我在不在，缺失时只打日志（§3.6） |

## 6. 在同步图与三枢纽里的位置

**我在同步图上零出边，只有入边。** 形态与三枢纽里的 `erp-inventory`（物理命令枢纽）同类：被调用、被消费，自己不指向任何人——**所以不可能引入环**。

与 §1.4 的"CRM 与 ERP 零同步边"无关：我是 infra 层，两边都可以调我，而我谁都不调，不构成跨域耦合。

⚠️ **`erp-sales → infra-workflow` 是本阶段第一条真实的弱依赖边**，也是平台验收用例 5 的天然场景（阶段二时 `infra/workflow` 还不存在，正好验了"弱依赖缺失时不注入 `*_ENDPOINT`"；**本阶段它存在了，要反过来验"装上之后变量确实注入、调用确实通"**）。这条写进阶段三计划 Task 14 的验证清单。

## 7. 分区与归档策略

| 数据 | 热 | 归档条件 | 归档去哪 |
|---|---|---|---|
| `workflow_tasks` | `PENDING` 的永远热 | 终态且超过 **12 个月** | `infra_workflow_archive` |
| `workflow_task_actions` | 跟随主表 | **跟随主表一起归档**（§11.2.4） | 同上 |
| `command_idempotency` | 最近 90 天 | 超过 90 天直接删 | 不归档 |
| `event_outbox` / `event_inbox` | 已发布 30 天内 | 超过 30 天 | 清理（§11.7） |

⚠️ **归档判据是"终态 **且** 够老"，不能只判时间**（§11.5.2）：一条 14 个月前建、至今没人审的待办**不能归档**——它还是活的，而且它恰恰是最需要被人看见的那种。

## 8. 参考实现

> 完整调研过程见 [`_调研记录/03-阶段三.md`](./_调研记录/03-阶段三.md) 的「infra-workflow」一节。下表是精炼版。

| 项目 | 版本/commit | 看的模块 | 借鉴了什么 | 许可证（已复核） | 用法 |
|---|---|---|---|---|---|
| Odoo | 📋 开工前填 | `mail.activity`（待办模型）与它和业务单据的关联方式 | **轻量待办箱的形状**：一条 activity 挂在任意单据上，只有"谁、什么时候、做什么"，不含流程定义。与我们要的形态最接近 | LGPL-3 | 借鉴逻辑 |
| ERPNext | 📋 开工前填 | `ToDo` doctype + `Workflow` doctype 的分工 | **反面参考**：它把"待办"和"状态机流转规则"放进了同一层，于是 Workflow 里塞满了业务条件（`condition` 字段存 Python 表达式）——正是 §6.6 铁律一要禁的东西 | GPL-3 | 借鉴逻辑 |
| Camunda / Flowable | — | BPMN 引擎的定位与代价 | **明确不走这条路**：BPMN 引擎的价值在于"流程可视化编排 + 长事务状态持久化"，而我们的长事务补偿在发起方自己手里（`erp-sales` 的 TCC 链）。引进来会多一套流程定义语言、一个新的运行时状态源 | Apache-2.0 | 借鉴实际应用 |
| 钉钉审批 / 飞书审批 | — | 它们的审批单形态、审批人配置界面 | **选配测试的素材**：客户天天用的是"谁审、能不能加签、能不能撤回"，几乎没人用复杂的分支条件——佐证轻量形态够用 | 闭源 | 借鉴实际应用 |

**明确没有参考的**：Temporal / Cadence 这类**工作流编排引擎**。**不是没查，是定位不同**——它们解决的是"跨服务长事务的状态机持久化与重放"，而我们对这个问题的答案是设计书 §4.4 的 TCC + Saga，写在发起方组件里。把它引进来等于让本组件从"待办箱"变成"编排中枢"，而铁律三（严禁反向同步调用业务组件）已经堵死了编排所需的前提。

**要避免它的什么：**

| 项目 | 它的做法 | 我们为什么不这么做 |
|---|---|---|
| ERPNext `Workflow` | `condition` 字段存可执行表达式，运行时求值 | 违反铁律一；且表达式是运行时字符串，**AI 读不懂也测不了**（同 `infra-authz` 拒绝 Odoo `ir.rule` 的理由） |
| 多数 BPM 产品 | 待办中心直接查业务库渲染列表 | 违反铁律二。我们靠 `CreateTask` 时传入的**展示快照**（§1.2 第三行） |
| 常见做法 | 审批通过后由待办中心**回调**业务组件的接口 | 违反铁律三。我们只发事件，回不回、怎么回是业务组件的事 |

**读完之后，这里有没有「多种实现都合理、只是适配客户不同」的分歧？**

⭐ **有一条，而且它正是设计书 §5.11.1 示例表里悬了很久的那一行——现在可以判掉了。**

§5.11.1 列着「审批路由：组织层级逐级 / 金额分级 / 矩阵式 / 规则引擎」，结论栏写的是"槽位族信号，**但要先确认它不违反 §6.6**"。现在本组件真的设计出来了，可以确认：

1. **审批路由根本不在本组件里**——按 §1 的边界，"这张单该谁审"由业务组件算好后通过 `assignee` 传进来。所以这条分歧长在 `erp-sales` / `erp-purchase` 这类**业务组件**内部；
2. 而那些业务组件**都被 `crm-*` 或 BFF 建了强依赖边**，按 §5.11 硬约束**不能做成 slot**；
3. **结论：审批路由的落点是业务组件的 `customer_fork`，不是 slot。** 与阶段二那 9 条分歧的判定完全一致（复盘 §4 第 5 条：可替换在交易组件上的落点是 Fork）。

**本组件自身没有新分歧**：待办箱的形态被 §6.6 三条铁律定死了，不存在"多种都合理"的空间——BPMN 那种更重的形态不是"另一种合理选择"，是**被铁律三排除的**（它需要回调业务组件）。
