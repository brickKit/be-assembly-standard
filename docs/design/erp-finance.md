## 1. 边界

**归我：** 会计科目表、总账分录、应收/应付台账、**会计日历与期间锁**、对账。设计书 §2.6 称本组件为**事件汇枢纽**——别人发生的事，在这里变成会计语言。

**不归我：**

| 什么 | 归谁 | 为什么 |
|---|---|---|
| 客户的**信用额度值** | `mdm-customer` | 额度是客户主数据的属性（§5.3）。本组件持有的是**已用额度**（`credit_exposure`），两者相减才是可用额度——**分别归两个组件是刻意的**：额度是"给他多少"（商务决定），已用是"用了多少"（会计事实） |
| 订单、发票单据本身 | `erp-sales` | 本组件收到"订单已创建"事件后生成**凭证**，凭证不是订单。改订单是销售的事，改凭证是财务的事，**两者不能互相改** |
| 库存的**数量** | `erp-inventory` | 本组件消费 `erp.inventory.adjusted.v1` 生成存货科目凭证，只关心金额；数量的真相源在库存 |
| 付款的实际执行（走银行接口） | `integration-payment-*`（阶段六） | 本组件记应收应付，不碰支付通道 |
| 多币种、汇率 | `customer_fork` | 设计书 §5.5 明确：**标准版仅支持单币种（本位币）** |

**数据权限判定**（§11.2.1 强制在建表前判定）：**需要**，维度是 `legal_entity`。

```yaml
data_scopes:
  - { dimension: legal_entity, column: legal_entity_id, mode: in,
      tables: [finance_journal_entries, finance_journal_entry_lines, ar_ledger, ap_ledger] }
```

理由与**成本判断**：设计书 §14.2.2 把 `legal_entity` 维明确列给"多公司集团的 `erp-finance`"。阶段二只有一个默认法人，过滤逻辑到阶段三才实现——**但列必须现在就建**。判据是 §11.2.1 的原话："分区表回头加列的代价比建表时多两个数量级"，而 `finance_journal_entry_lines` 正是分区表。**现在加一列几乎零成本，将来加要停机迁移。**

⚠️ 本组件同样不需要 `dept_id`/`dept_path`/`owner_id` 三列——`legal_entity_id` 是业务列，不是权限专用列（同 `erp-inventory` 的 `warehouse_id`）。

## 2. 拥有的数据

| 表 | 分区键 | 粒度 | 说明 |
|---|---|---|---|
| `fiscal_years` | 不分区 | — | 会计年度 |
| `accounting_periods` | 不分区 | — | 会计期间，**三态**（见 §2.2） |
| `accounts` | 不分区 | — | 会计科目表 |
| `finance_journal_entries` | **不分区** | — | 凭证**头**。⚠️ 不分区是必需的，见 §2.3 |
| `finance_journal_entry_lines` | `accounting_period` | **会计期间** | 分录明细。**全系统唯一不按 `created_at` 分区的表**（§11.2.5） |
| `ar_ledger` / `ap_ledger` | 不分区 | — | 应收/应付台账，**可变**，见 §2.4 |
| `customer_credit_exposure` | 不分区 | — | 每客户已用额度的物化值 |

**终态列表：**
- `finance_journal_entries`：`POSTED` 是终态。**过账之后永不修改、永不删除**——要改只能记一笔**红字冲销凭证**（借鉴 Tryton，§8）。
- `accounting_periods`：`LOCKED` 是终态；`CLOSED` **不是**（可以 reopen）。

### 2.1 凭证的状态机：两个状态，冲销不是第三个状态

```
DRAFT ──post──▶ POSTED（终态）
                  │
                  └── 要改？记一笔反向的新凭证（reversal），原凭证一个字不动
```

⚠️ **没有 `CANCELLED` 状态，这是刻意的。** 查证 Tryton 的 `account.move` 只有 draft/posted 两态，`Move.cancel()` 写的是一笔**反向凭证**而不是把原凭证标成取消。理由是会计原则：账一旦过账就是历史事实，"撤销"本身也是一笔要留痕的事实。ERPNext 与 Odoo 在这一点上做法相同（"cancel 从来不是 delete"）。

**两个单号，不是一个**（同样借鉴 Tryton）：

| 字段 | 何时分配 | 要求 |
|---|---|---|
| `entry_no` | 创建（DRAFT）时 | 唯一即可，**允许有缺口** |
| `post_no` | 过账（POSTED）时 | ⚠️ **同一期间内必须连续无缺口**——审计要求 |

分开的理由：草稿可能被删或永不过账，如果只有一个号，删一张草稿就在正式账上留一个洞。

### 2.2 会计期间：三个状态，不是一个布尔

```
OPEN ──close──▶ CLOSED ──lock──▶ LOCKED（终态）
  ▲               │
  └───reopen──────┘
```

⚠️ **`CLOSED` 与 `LOCKED` 必须分开**（Tryton 的做法）。只做一个 `is_closed` 布尔会在第一次"月底关账后发现漏了一张单，要不要开回去"时露馅：**关账是可逆的日常操作，锁定是不可逆的年度操作**，两件事合并成一个开关，就只能在"永远能改"和"永远不能改"之间二选一。

### 2.3 ⚠️ 幂等过账：唯一约束必须落在**不分区**的凭证头上

本组件的凭证由**消费事件**生成，而事件会重投。防重复过账靠一条唯一约束：

```sql
UNIQUE (source_component, source_doc_type, source_doc_id, source_revision)
```

⚠️ **这条约束是这份设计计划里最容易做错的一处，有三个坑叠在一起：**

| 坑 | 说明 |
|---|---|
| **① PostgreSQL 的分区表不能建不含分区键的唯一约束** | 如果把这条约束建在按 `accounting_period` 分区的明细表上，PG 会直接拒绝（除非把 `accounting_period` 塞进唯一键，而那就等于"同一张源单在不同期间可以过两次账"——正好是要防的事）。**所以凭证头必须不分区**，约束建在头上 |
| **② `inbox` 去重挡不住这个** | `besdk.Consume` 的 `event_inbox` 防的是"**同一条消息**投两次"；唯一约束防的是"**两条不同消息**指向同一张源单"（比如 `created` 与一条补发的 `updated` 都试图建凭证）。**两层都要有，缺一不可** |
| **③ 期间必须从源单的业务日期推导，不能用消息到达时间** | 消息延迟几小时跨了月底，用到达时间会把凭证记进下一个期间——而期间就是分区键，**同一张源单重投两次会落进两个不同分区，唯一约束在头上才拦得住** |

查证结论：**Tryton / Odoo / ERPNext 三家都没有这条约束**。它们靠"源单持有指向凭证的外键，建之前先看有没有"——那在单体单库单事务里成立，跨进程重投时不成立。ERPNext 因此有反复出现的重复 GL 条目 bug。**这一条是我们自己加的，不是抄来的。**

### 2.4 应收台账与总账分家（借鉴 ERPNext v14 的转向）

```
finance_journal_entry_lines   分区、只增不改 —— 总账，是历史
ar_ledger / ap_ledger         不分区、可变   —— 应收应付台账，是当前状态
```

理由（查证得来）：ERPNext 早期与 Odoo/Tryton 一样，**没有独立的应收子账**——应收就是"科目类型=应收"的总账行加一个往来单位维度，核销靠在总账行上改 `reconciliation` 字段。ERPNext v14 专门新增了物化的 `Payment Ledger Entry`，公开的动因是：**每次核销都要把总账凭证撤销重记**。

对我们这个形态，这个动因更强：总账明细是**按期间分区且只增不改**的，如果核销状态挂在总账行上，一次核销就要去改一个可能已经归档的旧分区的行——**那与"分区表只增不改"直接冲突**。所以分家不是可选优化，是我们这套约束下的必然结果。

⚠️ **这是一次性的架构分叉，不是槽位族。** 判据（R-4）："每一种都合理、只是服务的客户画像不同"——这里不成立，对我们的约束而言只有一个答案是可行的。

### 3.1 期间锁是"一个组件的状态约束别人的写操作"，怎么做才对

这是本阶段唯一一处这种形态，也是最容易做错的地方。查证三家的做法后，结论如下：

| 做法 | 谁这么做 | 我们抄不抄 |
|---|---|---|
| 框架级 save 钩子，其他模块注册"我这些单据受期间控制" | ERPNext（`closed_documents` + `period_closing_doctypes` hook） | **抄不了**——那是单体框架的特权，我们是独立进程 |
| 期间状态是一等可查实体，**每个子账各有各的期间状态**，关账是一次协商 | Oracle Fusion（`GL_PERIOD_STATUSES`） | **抄形态**：期间状态可查 |
| 各模块期间锁完全独立，靠配置同步 | SAP（MM 期间 / FI 期间分开） | 不抄，太重 |

**我们的做法（三层，缺一层就有洞）：**

1. **`CheckPeriodOpen` 是咨询性的，不是权威的。** 上游（`erp-sales`）改历史单据前先问一句，用来给用户一个**及时的、体面的**报错。
2. **权威判定发生在本组件的过账事务内部**——过账时在同一个事务里读期间行并判状态。这一层不可绕过。
3. **迟到的凭证记进下一个开放期间**，不是拒绝。会计上这叫"以后期间调整"，是标准做法。

⚠️ **check 与 write 之间的竞态是接受的，不是遗漏。** 三家系统都没有乐观地解决它，因为**关账在现实中不是一次 API 调用，是一段人工流程**。上游拿到的 `OPEN` 只代表"问的那一刻是开的"；真正的保护在第 2 层。把 `CheckPeriodOpen` 当成权威判定来用，才是错的——这条写进 `AGENTS.md`。

## 4. 事件

**发布：**

| subject | 分级 | 何时发 | payload 要点 |
|---|---|---|---|
| `finance.credit.rejected.v1` | 核心交易事件 | 过账应收时发现该客户已用额度超限 | `customer_id`/`order_id`/`exposure`/`limit` |
| `finance.voucher.posted.v1` | 旁路分析事件 | 凭证过账后 | `entry_no`/`post_no`/`period`/`amount` |

⚠️ `finance.credit.rejected.v1` 的消费者是 `erp-sales`（§4.3 事件图）——**这是本阶段唯一一条"事件反向流回上游"的边**，也是信用额度模型能成立的关键（见 §5）。

**消费：**

| subject | 来自 | 干什么 |
|---|---|---|
| `sales.order.created.v1` | `erp-sales` | 生成应收凭证 + 累加 `credit_exposure` |
| `erp.inventory.adjusted.v1` | `erp-inventory` | 生成存货科目凭证 |
| `mdm.customer.created.v1` / `.updated.v1` | `mdm-customer` | 维护客户摘要副本（含**信用额度值**），供 §5 的判定用 |

⚠️ **本组件是本阶段第一个真的使用 `besdk.Consume` 的组件**（`mdm-*` 都只发不收）。inbox 幂等 / `hop_count` 防环 / version 单调这三条，在阶段一只被 SDK 自己的测试验过——**这里是它第一次跑在真组件里**。按阶段一的经验，这条路径大概率会压出 SDK 的 bug；**压出来就修 SDK，不要在组件里绕**。

## 5. 依赖

**强依赖：** 无。
**弱依赖：** 无。

**明确不依赖：**

| 谁 | 为什么不建依赖边 |
|---|---|
| `erp-sales` / `erp-inventory` | 本组件**只消费它们的事件**，不同步调它们。§4.2 同步图里本组件没有出边——这正是"事件汇枢纽"的含义 |
| **`mdm-customer`** | ⚠️ 反直觉：本组件要用客户的**信用额度值**，但**不同步调 `mdm-customer` 取它**。走事件摘要副本（§4 消费段）。理由同 `erp-inventory` 对 `mdm-product`：加一条同步边就把事件汇变成链上一环，而摘要副本的最终一致窗口（几百毫秒）对"额度值刚改就下单"这个场景是可接受的 |

**信用额度的三方分工**（本阶段最绕的一处，写清楚免得实现时各写各的）：

| 谁 | 持有什么 | 怎么来的 |
|---|---|---|
| `mdm-customer` | **额度值**（`credit_limit`） | 它的主数据 |
| `erp-finance` | **已用额度**（`credit_exposure`） | 消费 `sales.order.created.v1` 累加，收款时冲减 |
| `erp-sales` | 两者的**本地缓存快照** | 消费两边的事件 |

**判定发生两次，是刻意的**：
1. `erp-sales` 建单前用本地缓存**快速预判**（§8.2 的"本地缓存校验信用额度"）——挡住绝大多数明显超限的单，零网络开销。
2. `erp-finance` 过账时用权威值**再判一次**，超限就发 `finance.credit.rejected.v1`，`erp-sales` 消费后把订单转为挂起。

⚠️ 查证发现 **Odoo 与 ERPNext 在信用额度上都不硬拦**——Odoo 的 `partner_credit_warning` 只是一段提示文字，从不抛异常，硬拦是第三方插件。所以"预判 + 事后补偿"不是我们偷懒，**是比两个成熟系统更严的做法**。

## 6. 在同步图与三枢纽里的位置

本组件是三枢纽之一——**事件汇枢纽**。§4.2 同步图里指向它的是 `erp-sales`、`erp-purchase`，**它不指向任何人**，是 DAG 叶子节点。

⚠️ **注意区分两张图**：本组件在**事件图**里有一条出边（`finance.credit.rejected.v1` → `erp-sales`），而 `erp-sales` 在**同步图**里有一条指向本组件的入边。这**不构成环**——设计书 §4.3 明确"事件图允许环但必须收敛"，而同步图里本组件零出边。**把事件边画进同步图去判环，是本阶段最容易犯的分析错误。**

## 7. 分区与归档策略

| 数据 | 热 | 归档条件 | 归档去哪 |
|---|---|---|---|
| `finance_journal_entry_lines` | 未关账期间 + 最近 12 个月 | **已 `LOCKED` 的期间**（§11.7：只有已关账期间才能归档） | `erp_finance_archive` |
| `finance_journal_entries`（头） | 永久热 | 不归档 | —— |
| `ar_ledger` / `ap_ledger` | 未核销的永久热 | 已核销且超过 24 个月 | `erp_finance_archive` |
| `accounts` / `fiscal_years` / `accounting_periods` | 永久热 | 不归档 | —— |

⚠️ **归档判据是期间状态 `LOCKED`，不是时间。** 这是本组件与其它分区表最大的不同：别的表"够老就能归档"，会计凭证**只有锁定的期间才能动**——一个 18 个月前但因为审计争议还没锁定的期间，一行都不许归档。

⚠️ **头不归档、明细归档，是刻意的不对称。** §11.2.4 要求"子表跟随主表分区"，但这里反过来：头是不分区的（§2.3 的唯一约束要求），明细才分区。**归档明细时头留下**——因为头上那条幂等唯一约束必须永远有效，否则一张三年前的源单重投事件时会重新过一遍账。**这条与 §11.2.4 的字面要求冲突，是本设计计划要回填进设计书的一条**（见 §9 第 1 条）。

- **多币种**——标准版不做（§5.5），没去看它们的汇率模型。

**要避免它的什么：**

| 项目 | 它的做法 | 我们为什么不这么做 |
|---|---|---|
| ERPNext | `make_gl_entries` **不去重**，重复过账要靠调用方先调 `make_reverse_gl_entries` | 唯一约束兜底（§2.3）。他们因此有反复出现的重复 GL bug |
| ERPNext | 会计维度用**运行时 DDL**（定义一行、值一列，给每个单据类型动态加 Custom Field） | 我们是 `sqlc` + 迁移，运行时加列做不到也不该做。维度用固定列，够不够留待客户提 |
| Frappe naming series | 单号计数器一行 + `SELECT FOR UPDATE`，与业务同事务 | 热点行锁把同前缀的插入全串行化；且回滚留缺口。改用 Tryton 的两号分离（§2.1） |
| Odoo | **没有期间实体**，只有公司级 lock date；某些流程会**静默把记账日期往后推** | 有期间实体（§2.2）。"静默改日期"是最难查的一类问题 |

**读完之后，这里有没有「多种实现都合理、只是适配客户不同」的分歧？**

**有两条，都是新发现的族候选：**

| 分歧 | 现实中的分歧 | 判定 |
|---|---|---|
| **关账策略** | Tryton：期间实体 + 日记账级粒度 + 零余额前置校验；Odoo：公司级 lock date + 角色分层；ERPNext：三套机制并存（会计期间 / 冻结日期 / 期末结转凭证） | ⭐ 族候选。三家给出三种，各自服务不同规模的客户（小客户嫌 Tryton 繁琐，集团客户嫌 Odoo 太松） |
| **迟到单据策略** | 拒绝 / 顺延到下期 / 有权限的角色可强改 | ⭐ 族候选。本阶段选"顺延到下期"（§3.1） |

⚠️ 按 R-4 第 3 步：`erp-sales` 对本组件建了强依赖边，**所以这两条不能做成 slot**（§5.11 硬约束）。正确形态是"一个组件 + 内部策略"（SOP-P）或 `customer_fork`。判断写进出档复盘。
