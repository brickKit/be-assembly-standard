## 2. 与原计划/原设想矛盾的地方，和为什么

### 2.1 "11 个 Go 组件合成 1 个外壳"——本文档自己最初的假设，被已经锁死的数据反证

本阶段计划文档最初通篇假设"阶段四把 11 个 Go 组件合成 1 个外壳"，Task 4 写 `be-ops` 产出 4 核对
`registry/schemas.tsv`（阶段一就锁死、只增不改的表）时才发现：这张表从建库那天起就已经把 60 个组件按设计书
§13.2 的最终五外壳方案完整分组过，11 个 Go 组件当时就分进了 `shell_go_core`/`shell_go_backoffice`/
`shell_go_infra` 三个不同的 `shell_login_role`，不是阶段四临时决定的。

**这不是一个小笔误，是一次贯穿多个上游判断的连锁反应**：Task 1 调研时判断"产出 7 的跨外壳改写分支本阶段
大概率不会被触发"，前提正是"11 个组件都在同一个外壳"——三路分组后，`crm-opportunity`（`go-backoffice`）
强依赖 `mdm-customer`/`mdm-product`（`go-core`）、`erp-sales`（`go-core`）弱依赖 `infra-workflow`
（`go-infra`），两条边立刻变成真实的跨外壳依赖，Task 1 的判断被直接推翻。**这说明什么**：`registry/`
下的锁定文件是本项目真正的事实来源，比任何一版计划文档的文字描述都更该被信任——下次任何一次"这一步该怎么
分组/怎么切"的判断，第一件事应该是去读锁定数据文件，不是先读计划文档的叙述性描述再决定要不要相信它。

### 2.2 "先验两个组件、混合形态运行一段时间"——技术上直接不可行

原计划设想 Task 5"只把 `mdm-customer`/`mdm-product` 标成 `local: true`，其余 9 个仍是独立容器"这种部分
合并的中间态，方便分阶段验证。开工后发现 `genyaml.Gen` 的 `Local` 字段推导逻辑是"`assembly.yaml` 的
`shell` 字段非空就置 `local: true`"，不区分"这个组件现在就绪了没有"——11 个组件的 `shell` 字段全部已经
声明好了，重新跑一次 `be-ops gen`，**11 个会一起变成 `local: true`**，不是只有 2 个。如果这时候只有 2 个
组件的真实模块代码被 `be-shell-go` 真的 `import` 了，另外 9 个组件的依赖方会拿到指向"没有任何进程在监听"的
地址，直接连接失败——这不是"部分合并"，是"部分弄坏"。

**调整后的做法**（保留原计划"先验两个、再验剩下九个"这条节奏，只是换了"验"的对象）：先用 `be-shell-go`
自己仓库里的真实模块集成测试（`TEST_PG_DSN`，不碰真实 `brickkit.yaml`）逐步验证"这份真实代码在合并态下
真的能跑"，`brickkit.yaml` 的真实切换留到全部 11 个模块都验证完之后一次性、原子式做完。**这条经验值得
沉淀**：当一个平台的某个字段是"声明式、全有或全无"的设计（这里是"一个组件属于哪个外壳"），就不要指望能
在真实资产上做"渐进式、部分启用"的中间态验证——渐进验证要么挪到不影响真实资产的隔离环境，要么干脆放弃
中间态、一次性原子切换。

### 2.3 vendored-contract 模式与"同进程合并"的物理冲突——一次先错后对的架构判断

阶段二立的 vendored-contract 模式（逐字复制被依赖组件的生成代码到自己仓库）在阶段三运行良好，因为阶段三
里调用方和被调方从来没有被编译进同一个二进制过。阶段四把 `erp-sales`/`crm-opportunity`/`infra-iam-casdoor`
真的和它们调用的组件塞进同一个 Go 进程（哪怕只是测试文件把多个外壳的模块放进同一个测试包）之后，两份
import path 不同、内容相同的生成代码在 protobuf **进程级全局注册表**里重复注册同一个文件/类型全名，直接
panic——这条坑在阶段一到三从未出现过一次，因为触发条件（"调用方和被调方编译进同一个二进制"）在合并之前
根本不成立。

**第一次修复尝试是错的，且这次没有把错误方案铺到多仓库范围才发现**：设想"嵌套 go module + 外壳
`replace` 去重"，写了一个最小复现程序验证后确认技术上不可行——Go 的 module system 无法把两个不同
import path 的包合并成一份编译实例，即使 `replace` 也不行。**这正是长期记忆
`feedback-verify-novel-mechanism-before-multi-repo-change` 记录的那条教训（阶段四早前一次真实违反）
这次被正确执行的样子**：先用一个隔离的最小复现程序验证，而不是直接在 `erp-finance`/`erp-inventory`/
`infra-authz`/`infra-workflow`/`mdm-customer`/`mdm-product` 六个仓库上直接铺开这个假设再发现装不下。
真正的解法——把"生成物契约包"本身提升为跟 `be-sdk-*` 同类的铁律六第二类白名单（设计书 §13.3 已经回填
这条新条款）——**这次复发了两次**（第一次是 go-core 外壳内部的边，第二次是凑齐 go-infra 五个模块时才
在 `infra-authz`/`infra-iam-casdoor` 这一对上再次撞见），说明"发现一次就以为全部同类问题都排除了"这个
假设本身也值得警惕——**一类问题在一条边上被修复，不代表所有同构的边都已经被检查过**，只有真的把全部
模块凑齐再跑一遍，才能确认整张依赖图上再没有同类的边。

### 2.4 Python 的 ASGI 编排：读文档得出的技术方案，写代码时被证伪

原计划设想用 `asyncio.gather` 编排多个 `uvicorn.Server`，写骨架时发现 `run_standalone` 自己既有的
`_serve_http`/`_serve_extra_port` 依赖一个外部传入的 `stop_event`（等它被 set 才优雅退出），而
`Module.start` 的既有约定是"取消时必须返回"（靠 `asyncio.Task.cancel()`）——两种停止方式混着用，
`asyncio.gather` 本身没有对应的编排原语能同时协调两者。改用 `run_standalone` 自己已经在用的
`asyncio.wait(..., FIRST_COMPLETED)` + 手动 `stop_event.set()` + 对 pending 任务 `.cancel()`，只是把
"1 个模块的任务集合"换成"N 个模块的任务集合拼在一起"，不引入 `asyncio.TaskGroup` 这个新概念（避免在
同一个 SDK 生态里制造第二套不完全一致的停止语义）。**这条与阶段三 §2.3 的教训同构**：跨语言/跨场景挪用
一个"看起来等价"的编排原语之前，要先确认目标场景已经有的既有约定（这里是 `stop_event` vs
`Task.cancel()` 两种停止信号）跟这个新原语能不能真的对接上，不能只看"这个原语理论上能编排多个协程"这一层。

### 2.5 根 `Makefile` 的 `make up`/`make down`——计划文档对既有工具的假设是错的

计划原文假设"现有的 `make up`" 已经管着 `brickkit up`/`brickkit down`，Task 8 真机核对 `Makefile` 后
发现不是——它只管 5 个基础资源，从来没有包过 14 个组装态容器的启停。改为新增 `make teardown-up`/
`make teardown-down` 两个不冲突的命令承担这个角色，不是复用/悄悄改写已有的、被日常依赖的
`make up`/`make down` 语义。**这条本身是个小事，但值得记录的是它差点被漏掉的方式**：计划文档写"现有的
`make up`"这几个字时没有配一条"已核对 Makefile 确认属实"的验证记录，直到真机执行这一步才发现文字描述
和真实代码不一致——这提醒以后写计划文档时，任何"现有的 X 已经做了 Y"这类断言，最好在写下的同时就核对
一次源码，不要假设自己记得对。

## 3. brickKit 平台本身：理念是否有问题，实现是否有 bug

### 3.1 真 bug：本阶段零例，第二次零例

与阶段三一致（阶段二是 1 例，Manifest 缓存旁路 bug）。本阶段验证的核心命题——"合并部署会不会磨掉组件性"
——本质上是**我们自己的外壳代码、SDK、工具链要不要对合并负责**，brickKit 平台自己的职责边界在"把 N 个
组件的容器变成 1 个"这个动作本身（`local: true`/`localPort`/依赖地址改写），设计书 §13.1 从一开始就明确
"合并只发生在部署层，外壳只负责把 N 个进程变成 1 个"——这条边界这次被真机验证反复印证：找到的每一个真
bug，都出在边界**我们这一侧**（外壳启动器怎么共享连接池、怎么导出依赖地址、怎么隔离 panic），没有一个
出在 brickKit 生成 `local: true`/改写地址这一层本身。这进一步支撑阶段三复盘 §3.1 的判断：先集中把平台
摸透（阶段二），业务/工程能力盖在上面（阶段三/四）不容易牵连出平台层面的新 bug，这不是运气，是阶段顺序
本身选对了。

### 3.2 没有需要反馈给 brickKit 的观察

阶段二复盘 §3.2、阶段三复盘 §3.2/§3.3 各自都记录过至少一条"值得反馈给 brickKit 的观察"（G1/G2 的自我
纠正、跨组件配置字面量版本号的机制化缺口）。本阶段没有类似的条目——不是因为没有发现问题，而是本阶段
发现的全部问题（vendored-contract 与合并不兼容、`besdk.Endpoint()` 依赖地址导出、`errgroup` 共享 `gctx`
拖垮整个外壳）性质上都属于"我们自己的外壳/SDK 该怎么正确使用 brickKit 已经提供的机制"，不属于"brickKit
本身该不该多做点什么"——`local: true`/依赖地址改写这些 brickKit 侧的机制本身在本阶段全程正确工作，
没有出现需要平台方判断"要不要支持"的新能力缺口。

## 4. 流程改进

1. **⭐ 新教训：验收/编排脚本本身也需要被验收，不能只验一次就假设它会一直正确。** 本阶段最重的两个发现
   （铁律六扫描器从未递归、`teardown-up` 在基线变化后静默失效）**都不是业务逻辑 bug，是"检查代码是否正确
   的代码"自己出了错**，而且都属于同一种失效模式：脚本在**写下来的那一刻是对的**，后来**它依赖的前提
   （目录结构里业务代码在哪一层、`brickkit.yaml` 是否已经有 `local: true`）发生了变化**，脚本自己却没有
   跟着改，也没有任何测试覆盖到这个"前提变了"的场景——两次都是"没有报错、看起来跑成功了，实际什么都没
   验证到/什么都没做到"，比一次直接的 FAIL 更危险，因为它会一直安静地骗过日常检查直到有人恰好按计划自己
   写的"故意验证一次"这条判据去真机复现。**这条经验的通用形式**：任何一个门禁/编排脚本，只要它依赖某个
   "现在的项目状态长什么样"的隐含假设（目录结构、配置文件的默认值、另一个仓库的接口形状），这个假设一旦
   在未来某次不相关的改动里变了，脚本本身没有办法自动感知——**唯一可靠的检查方式是定期真的按脚本自己
   声称的用途走一遍，而不是只看它的退出码是不是 0**。本项目已经有的三条相关纪律（`make gates` 六个 gate、
   `make tier0`/`tier1`/`tier2`、`weekly-teardown-gate.sh`）之所以能抓住这两个问题，正是因为它们要求
   "真的执行一次，不是读代码猜"——这条方法论本身在本阶段被验证了三次（见下一条），值得继续坚持，但
   §4 这条本身在提醒：**光有"定期真机验证"的纪律还不够，验证脚本自己的正确性也是需要被主动检查的对象**，
   不能默认"这段代码是去年写的、去年测过，现在应该还对"。

2. **⭐ 最重要的一条方法论确认：任务自己写的"故意改坏，确认能抓到"这条验证要求，三次独立抓到了否则会
   一直隐藏的真 bug。** Task 10 的铁律六扫描器递归缺陷、Task 11 的 panic 隔离缺陷、Task 12 的
   `teardown-up` 基线漂移——三次都不是"读代码看出来的"，是**真的照着任务自己的验证指令做了一遍"故意
   破坏，看它红不红"或者"真的跑一次它声称能做的事，看它做没做到"**才发现的。三次里至少两次（铁律六、
   panic 隔离）如果只是"看代码逻辑合理就跳过真机验证"，大概率会一直隐藏到合并部署真的出现对应故障时才被
   发现，而那时候排查难度会高得多（症状会是"外壳合并部署后行为诡异"，不是一条清楚指向具体文件行号的
   测试失败）。**这条经验不是新知识**（阶段二/三复盘都提过"真机验证优先"），本阶段的贡献是**把它从"应
   该这样做"的原则，升级成三次独立、可指名道姓的具体反例**——值得作为总纲"真机验证优先"判据下新增的
   第三/四个具体案例（前两个是阶段二/三各自贡献的）。

3. **版本纪律漂移这条缺口，阶段三复盘 §4 第 1 条已经指出过，本阶段又添了三个新实例，仍未系统性解决。**
   `go.mod` 地板（D0 同类第 3 次）、`be-sdk-python` 的 `pyproject.toml` 版本字段（打 tag 时漏改）、
   `mdm-customer` 容器名硬编码版本号（`closedloop/tier0_test.go`，**第 7 次**复发）——前两类目前仍然
   完全靠人工纪律，第三类这次终于换成了动态发现（`dockerContainerByPrefix`）从根上解决，不再需要"记得
   改"。**这条建议维持阶段三复盘 §4 第 1 条已经写下的结论不变**：是否要为"打 tag 时字段没同步"这一类
   补一个机制化检查，留给以后决定，但连续两个阶段都在复发，这个缺口不该继续被当作"下次小心点就行"来
   处理——如果阶段五还有类似复发，可能就是时候真的做点什么了，不是继续记录。

4. **跨语言/跨场景挪用一个"看起来等价"的技术方案之前，要先核对目标场景已有的约定接不接得上。** §2.4
   （Python ASGI 编排）与阶段三复盘 §2.3（SDK 跨语言移植的默认行为方向）是同一类教训的两次独立复现——
   这次是"编排原语的停止语义对不上"，上次是"框架默认行为方向不一致"，具体表现不同，但共同结论一致：
   "这个方案在另一个语言/场景里从道理上讲得通"不能替代"这个方案要接上的既有约定，实测确实接得上"。这条
   经验已经横跨两个阶段独立验证成立，值得正式写进 `02-reference-implementation-standard.md`，不再只是
   一条复盘里的观察。

5. **大的架构判断，第一手事实来源要查锁定数据文件，不是计划文档的叙述性描述。** §2.1 的教训——`registry/
   schemas.tsv` 从阶段一起就已经写好了本阶段最终要用的分组方案，本文档最初的版本却通篇假设"11 个组件合
   成 1 个外壳"，直到 Task 4 真机核对源数据才发现。以后任何跨越多个阶段的架构性判断，动笔写计划之前，
   先去读一遍相关的锁定数据文件（`registry/*.tsv`、已经存在的 `assembly.yaml`/`component.yaml` 字段），
   不要只依赖脑子里对"之前定过什么"的记忆或旧版计划文档的转述。

6. **主线收官后立刻写复盘这条规矩，本阶段被完整兑现，值得作为一个正面案例记录。** 与阶段三形成对照——
   阶段三主线收官后被三条并行工作线插队，复盘被推迟到很久以后、由用户怀疑"是不是没做完"才倒查出来；
   阶段四 Task 12 出档检查通过后，直接进入这份复盘的写作，没有被别的任务打断。这不是运气，是阶段三那次
   代价具体、可指名道姓的教训真的被记住并执行了——值得在这里明确记一笔，作为"流程改进真的落地了"的一个
   可验证的正面样本，而不是只在坏的时候才写复盘。

## 5. 是否要重新安排整体阶段编排

**结论：阶段划分本身不需要重排，本阶段的任务顺序原则（骨架先于迁移、`be-ops` 产出等外壳骨架先长出真实
形状、迁移顺序沿用既有依赖图、Python 外壳与 Go 外壳并行、验收放在全部迁移完成之后）全部按原计划的顺序
原则执行，没有出现需要中途打乱顺序的情况。**

与阶段三不同的是，本阶段**没有**在出档后立刻发现一条被跳过的编号任务——Task 1 到 Task 12 逐条真机验证，
每一条的"[x]"都对应真实存在的产出物（代码、测试、真机验证记录），这份复盘写作过程中重新通读整份计划
文档，没有发现类似 Task 15 那样"写着完成、实际从未实现"的情况。**这本身值得作为阶段三教训真正生效的
又一个证据**，与 §4 第 6 条呼应，不再单独展开。

唯一值得记录的、与"编排"相关的观察：Task 4 那次架构级推翻（§2.1）发生在阶段**内部**、任务**执行过程
中**，而不是跨阶段的编排问题——它没有导致任务顺序被打乱（Task 5/6 仍然按原计划的依赖序进行，只是"验证
对象"从"直接改真实 `brickkit.yaml`"变成"先在 `be-shell-go` 自己仓库里验证"），说明本阶段的任务粒度和
顺序原则本身有足够的弹性去吸收一次期中的架构修正，不需要因为这次推翻去反思"任务是不是分得不对"。
