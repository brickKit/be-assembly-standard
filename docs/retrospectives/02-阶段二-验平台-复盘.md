## 2. 与原计划/原设想矛盾的地方，和为什么

这部分不是罗列"改了什么"，是每一条都问一遍**为什么原来的想法是错的、错在哪一类**——因为不同的"错误类型"需要不同的应对：

### 2.1 平台行为被想当然，实测推翻（应对：以后不猜，先拿隔离 fixture 试）

| 想当然的假设 | 实测的真相 | 为什么会想错 |
|---|---|---|
| `enabled: false` 级联到强依赖方会报错阻断 | `exitCode=0`，两个组件都标"不启动"并各自给出理由——优雅降级，不是校验失败 | 把"这个配置在语义上不自洽"和"平台选择用错误码表达它"混为一谈了。**声明式配置系统里，`enabled:false` 是一种正常的运行时状态而不是一种非法输入**，这个区分本该在设计阶段就想清楚 |
| `brickkit up`/`up --dry-run` 成功后 `.brickkit/artifacts/` 会被填充 | 只有 `brickkit add` 才分发 artifacts，`up` 完全不碰这个目录 | 想当然地把"起容器"和"分发元数据"当成同一个生命周期动作。查 brickKit 源码（`internal/cli/artifacts.go` 的 `downloadArtifacts` 只被 `add.go`/`add_local.go` 调用）才发现这是两条独立路径 |
| `local: true` 的额外端口也会跟主端口一样换成 `localPort` | 只有主端口换，额外端口（如 gRPC）永远维持 Manifest 声明的原始端口 | 对"影子进程"这个抽象的心智模型不完整——`local:true` 只是说"主端口换成你在 IDE 里跑的那个"，没有"额外端口也一起换"这层承诺，而额外端口的"没有事后补救手段"这条铁律本来就该提醒自己多想一步 |
| 用例 9 第一次复现：双源（`source-a`/`source-b`）fixture 里 `foo/bar` 改名后 bug 不存在 | 换成单源、干净隔离的 fixture 后，bug 真实存在——第一次的"不存在"是未改名的 `source-b` 副本顶替上来的假阳性 | 这不是对平台的误判，是**测试方法论**的失误：验证一个"缓存该不该失效"的假说时，测试环境里不能留一个"备用真相来源"，否则看到的永远是"有没有备胎"而不是"缓存对不对" |

**共同教训**：平台的边界行为（启停语义、分发时机、端口映射范围）不能靠读文档/凭直觉判断，必须拿隔离 fixture 真跑一次——这正是 `be-acceptance/platform/` 这套断言存在的意义,也是它现在成了"以后每加一块平台表面积就该往里加断言"的常驻资产（§5 会展开）。

### 2.2 设计书本身写反了顺序（应对：这条不是平台的错，是我们自己的错，见 §7 待回填）

`erp-sales` 设计计划实现时发现，设计书 §8.2 描述的 TCC 步骤顺序把"校验信用额度"排在"预留库存"**之后**——这是错的：信用额度校验是纯本地缓存读取，零网络成本；排在预留库存（一次真实 gRPC 调用）之后，会导致信用不足的订单**先白白占了一次库存、再触发一次补偿**，两次网络往返换来一个本该在进程内就能拒绝的结果。`erp-sales` 实现时已经把顺序改对（先信用检查、后预留库存），但设计书 §8.2 本身还没有跟着改——这是 §7 待办清单的第一项。

**这条和 2.1 不一样**：2.1 是"平台行为我们猜错了"，这条是"我们自己当初设计书写的时候没想清楚代价顺序"，责任在自己不在 brickKit。区分这两类很重要，因为处理方式不同——前者是"以后要靠测试不靠猜"，后者是"设计评审时要多问一句'这一步的失败代价是不是比它前面那一步低'"。

### 2.3 跨组件调用没有先例，是这个阶段"论证出来的"而不是"想错的"

`erp-sales` 是全阶段第一个需要真正跨组件同步调用（gRPC）的组件。`besdk.UserClient`/`SystemClient` 只给裸 `*grpc.ClientConn`，不给类型化 client stub；而铁律六不许 import 其他组件仓库的 Go 代码——**设计书、总纲、SOP 三本源文档都没有先例**。这不是"想错了"的一类问题（没有可推翻的错误假设），是"设计书范围没覆盖到"——现场论证出 `contracts/vendor/` 只读镜像 + 本地生成客户端 stub 的方案，记进了 `erp-sales` 设计计划 §9。

**这类"论证出来的新模式"和前两类的处理方式都不同**：它不需要回填一条"改正"，需要的是**把它提升成总纲/设计书里的标准做法**，这样下一个需要跨组件调用的组件（阶段三往后几乎每个链上组件都需要）能直接照抄，而不是重新走一遍论证。这条也放进 §7 的建议里。

### 2.4 版本纪律漂移——写这份复盘的过程中顺带发现的

核对 `git submodule status` 时发现：`mdm-customer`、`mdm-product`、`erp-inventory` 三个仓库的 `go.mod` 早就升级到了修复后的 `be-sdk-go v0.1.9`（`erp-inventory` 还多了更早一笔权限路由迁移），但 `component.yaml` 的 `version` 字段和对应的 git tag 从未跟着打——**代码已经变了，版本号却停在旧值**。`be-ops`、`be-acceptance` 也有类似情况（分别多了一笔 Makefile 改进提交、和一整个 20 条平台断言测试层的三笔提交，都没打 tag）。

这不是平台的错，也不是设计书的错，是纯粹的**执行纪律缺口**：修 `be-sdk-go` 的 bug 时，"顺手把所有受影响的下游组件 go.mod 也升级"这个动作做了,但"升级完要不要跟着发一个新版本"这个后续步骤没有被机械化检查覆盖——不像 `make gates` 那样有扫描器守着，纯靠人（AI）记得。已经在这次复盘写作时一并修复（六个仓库补齐版本号+tag，`brickkit up --dry-run` 验证过版本链无冲突，真机重新部署验证过全部健康）。这条经验放进 §4 的流程改进里。

## 3. brickKit 平台本身：理念是否有问题，实现是否有 bug

### 3.1 真 bug（已走完整闭环）

本地源组件改名（`metadata.id` 变了，目录不变）后，`Client.Manifest()` 的缓存旁路判断只看"这个源还提供这个 id/version 吗"，没有意识到"内容还在，但内容的身份已经不是请求的那个了"，于是继续沿用改名前的缓存 Manifest——与设计文档"Fork 件的 `metadata.id`/`version` 一个字都不能改，改了依赖方的 `*_ENDPOINT` 整个消失"这句明确承诺矛盾。已报告（`brickKit` 仓库 `docs/superpowers/specs/2026-09-08-local-source-manifest-cache-masks-metadata-id-mismatch.md`）、已修复（v0.2.2，commit `f8e1fa9`）、已独立复核（升级 CLI 后重跑 `make tier1`、手工重跑三段裸命令、`brickKit` 自己的 `go test ./...` 也确认无回归）。

这条本身没有"理念问题"——**理念（Fork 件身份不可变）从设计书到 brickKit 自己的行为承诺都是一致且正确的，是这一处具体实现掉了链子**。值得记一句的是它的性质：这类"高风险不可变字段"（`metadata.id`/`version`）的约束，光靠文档措辞强调("一个字都不能改")是不够的，恰恰是这种被反复强调"极其重要、不许出错"的字段，最值得配一条针对性单测去验证"改了之后系统会不会正确地报错/正确地失效缓存"——而不是假设"写了警告文档，实现自然会对齐"。

### 3.2 不算 bug，但值得反馈给 brickKit 的观察

**观察一：`besdk.Consume` 用普通 `nc.Subscribe` 不是 `nc.QueueSubscribe`。** 这本身是对的选择——事件通知语义要求每个订阅者都收到一份广播，不是竞争消费。但它有一个不直观的副作用：本地测试进程和同一台机器上真实运行的容器如果订阅了同一个 subject，会**同时**收到测试发布的消息，容易把"旧容器碰巧处理成功"误判成"测试通过"（本阶段真的踩到过一次，见 `实测踩坑记录.md` 类别 E 的 E1）。这不是要求 brickKit 改行为，是建议它自己的文档/测试指南里明确点一句"本地测试与真实部署共享同一个 NATS/PG 时，验证消费者逻辑前要先确认没有另一个订阅者在偷跑"——这个坑几乎每个用 `Consume` 的组件在真机验证阶段都会踩一次。

**观察二：组件版本号与 git tag 是否同步，平台目前没有任何主动提示。** §2.4 那次漂移完全是我们自己的纪律问题，但如果 `brickkit up`/`add` 在解析 `local` source 或 submodule 时，能顺手做一个"这个目录的 HEAD commit 与它声称的 `component.yaml` 版本对应的 git tag 是否一致"的健康检查（类似 npm 的"working directory not clean"提示），会在纪律松懈的瞬间就被拦下来，而不是像这次一样要等到人工核对 `git submodule status` 才发现。这只是一个建议方向，不是必须做的功能——**是否值得做、值得做成什么形态，留给 brickKit 自己判断**（按 [[project_user_is_brickkit_maintainer]] 的既定原则：改动必须利好所有用户，不是单单迁就这个项目的习惯）。

## 4. 流程改进：设计书/计划/组件怎么写更好

1. **版本+tag 纪律要机械化，不能只靠约定。** §2.4 的漂移证明"改完代码记得打版本号+tag"这条隐性约定单靠人记不住。建议：SOP-W 的"任务完成判据"里显式加一句"这个组件的 `component.yaml` version 字段与它最新的 git tag 是否一致"，理想情况下配一个轻量脚本（`make version-check` 之类，检查 submodule 是否有已提交却未打 tag 的改动）——留给写阶段三计划时决定要不要现在就加。

2. **跨组件调用的 vendored-contract 模式应该提前写进总纲，不要等下一个需要它的组件重新论证。** `erp-sales` 现场论证出来的方案本身没有问题，但阶段三往后几乎每个"链上组件"（不是枢纽）都会需要跨组件调用——如果这个模式只停留在 `erp-sales` 自己的设计计划 §9 里，下一个需要它的人（哪怕还是这个 AI 助手）大概率要重新读一遍源码、重新论证一遍，而不是直接抄。建议阶段三写计划时，把这个模式正式提升进 `docs/plans/00-总纲.md` 的 SOP-B 或专门开一节。

3. **TCC/补偿类逻辑，mock 测试等于没测。** `erp-sales` 的补偿链正确性完全靠故障注入测试（真的让 `erp-inventory` 返回库存不足、真的用 `context.WithTimeout` 制造超时）验出来的——`erp-inventory` 缺 `idempotency_key` 查询路径这个契约缺口，纯 mock 测试根本发现不了，因为 mock 不会"恰好触发平台级的真实超时行为"。这条已经是总纲的既有判据（真机验证优先于 mock），这次是一次有力的正面案例，值得在总纲对应章节引用这个具体例子。

4. **测试基础设施共享陷阱要写进方法论，不能只是踩坑记录里的一条。** E1（本地测试进程与真实容器共享 NATS/PG 导致假阳性）目前只记在 `实测踩坑记录.md`——那份文档的定位是"症状/根因/怎么改"，不负责"以后怎么系统性避免"。建议阶段三写计划或改总纲时，把"验证某个组件的消费者逻辑前，先确认它自己的真实容器没有同时订阅同一个 subject"这条提升成总纲测试方法论章节里的一条通用检查项。

5. **SOP-R 三步法在槽位族判定上验证出了一条新边界，要正式写进设计书。** 9 条"每种做法都合理，只是适配客户不同"的分歧（成本核算法、补录策略、拣货策略……）按 R-4 逐条判下来**一条都不能做成 slot**——因为它们全部长在被强依赖的交易组件内部（`erp-inventory`/`erp-finance`/`erp-sales`），而 slot 的硬约束是"没有任何组件对它建依赖边"。这条判据本身没有写进设计书 §5.11，只停留在这次阶段计划文档的叙述里——这是 §7 待办的核心项，也是这次复盘认为**最值钱的一条产出**：它第一次把"客户差异在交易组件上该怎么落地"从"看着办"变成了可复用的判据（`customer_fork` 而不是 slot）。

## 5. 是否要重新安排整体阶段编排

**结论：不需要增删或重排阶段。** 阶段二的标题就是"验平台"，找到真 bug、推动修复本来就是它的题中之义,不是计划失控。但有两点值得记录，供以后类似"验证型"阶段参考：

- **发现真 bug 后的连锁修复成本，之前没有被预算进任务量估计。** 这次不只是"改一行代码"——`be-sdk-go` 一个 Config 修复，牵连了 4 个已发布组件（`erp-sales`/`erp-inventory`/`erp-finance` 当场跟进，`mdm-customer`/`mdm-product`/`erp-inventory` 三个仓库的版本号后来又补了一轮）；`GetReservationStatus` 的契约缺口修复分了两步（先补请求字段，才发现响应字段也要补）。以后的"验平台"类任务，如果发现的是平台级或跨组件契约级的 bug，应该默认预留"修复会波及 N 个已发布组件，每个都要走完整的版本发布流程"这个隐藏成本，而不是只算"改这一处代码"的成本。

- **`be-acceptance/platform/` 这 20 条断言现在是常驻回归资产，不是阶段二专属的一次性交付物。** 阶段三如果启用新的平台表面积（K8s 部署目标的实际集群验证、market 类型的安装源等），正确做法是往这套测试里**加断言**，而不是为新表面积另起一套验收机制——`make tier1` 应该随着项目推进单调增长，每条新断言都是"平台升级后重跑就是回归测试"这句话字面意义上的落实。

完整的 20 条清单与逐条验证方式见 `tools/be-acceptance/platform/README.md`，这里只做归类提炼：

|---|---|---|
| 一次写对、直接验证通过 | 14 | 1、3、6、7、10a、11、13、14、15、16、17、19、20、10b（后者是"补造假组件验真扛住"，不是推翻假设） |

**这张表本身的结论**：20 条里有 5 条（25%）在写测试的过程中修正了对平台行为的原始理解，1 条（5%）揪出了平台真 bug——**验证型断言的价值不在"证明系统符合预期"，在"逼着你把没验证过的假设一条条摊开来看"**。这也是为什么 §5 建议把这套断言当成随项目推进持续增长的常驻资产,而不是阶段二结束就归档的一次性工作。
