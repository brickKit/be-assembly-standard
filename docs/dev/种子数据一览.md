# 本地开发种子数据一览

> ⚠️ **只给本地开发/测试用，不用于生产部署。** 这里灌的是假数据（假客户、假产品、假商机、一个万能测试账号），目的是让刚打开这个仓库的人不用从零建数据，`make seed-data` 一条命令就能有东西可点、可查、可测。真正部署给客户时，这些数据一条都不会跟着走——`make seed-data`/`seed-data-clean` 从不出现在任何部署脚本或 CI 流程里，纯手动触发。
>
> ⚠️ **这份文档取代了原来的 `infra/seed-data/README.md`**——那个目录已经删掉了。数据本身全部归各组件自己拥有（总纲 SOP-W-7），装配层现在只剩"按顺序调用谁的 `make seed`"这一件事，薄到直接写进根 `Makefile` 的 `seed-data`/`seed-data-clean` 两个目标里就够了，不再需要一个单独的目录/脚本文件。这份文档纯粹是"数据可发现性"落地的地方（SOP-W-7 判据），不是任何脚本的说明书。

⚠️ **`erp-inventory`/`erp-finance` 都没有 `seed-clean`，只有 `db-reset`**：`erp-inventory` 的 `inventory_movements` 表"只增不改"（该组件 `AGENTS.md` 既有判据）；`erp-finance` 的理由更硬——`LockPeriod` 是契约里唯一的终态，没有任何 rpc 能把 `LOCKED` 期间转回去。两者逐行 `DELETE` 都做不到干净复原（`BIGSERIAL`/期间内计数器不会因为 `DELETE` 回退），所以 `make seed-data-clean` 不会清理这两个组件的数据——想清空用 `make -C components/erp/inventory db-reset` / `make -C components/erp/finance db-reset`（`migrate down` 再 `up`，真正的重置，但会清空该组件**全部**数据，不止 seed 灌的那部分），见总纲 SOP-W-7"delete 不是 reset"判据。`infra-print` 也没有 `seed-clean`——模板走版本管理，重跑 `seed` 只追加新版本，不需要撤销机制。

⚠️ **`infra-workflow`/`infra-notification` 刻意没有自己的 `make seed`**：`infra-workflow` 的 `CreateTask`/`CloseTask`/`CancelTask` 明确不暴露 REST（组件间协议，"人能创建待办只有一种可能'人代表某个业务组件创建'，那等于给了一条绕过业务规则的路"，见该组件 proto 顶部注释）；`infra-notification` 更彻底——gRPC 契约里连一个写命令 rpc 都没有，通知记录完全是事件消费的副产物。种子脚本直接 grpcurl 伪造一条写命令正是这两条设计禁令想挡住的事。真正诚实的做法是让真实业务流程真的失败一次：`crm-opportunity` 的 `seed-opp-11` 是一条刻意用超额度客户建的 `WON` 商机，赢单后 `erp-sales` 真实拒绝确认、真实建了一条 `infra-workflow` 异常待办（`assignee_sub`/`assignee_dept_path` 正确带着华东归属），这条待办又真实触发了一条 `infra-notification` 记录——两个组件因此都不需要自己造假数据，也各自有真实的、归属正确的数据可看。

`integration-im-dingtalk` 判定不需要种子数据：它桥接的是用户真实的个人钉钉团队+真实手机，任何"种子数据"要么用假凭据（测不出真东西），要么用真凭据（每次 `make seed` 都会真的给用户手机发消息，入侵性太强，不适合可重跑的演示脚本）。

所有人类可读的名字字段都带 `「本地测试」` 前缀，方便在任何界面/查询结果里一眼认出——各组件自己的 `seed-clean` 也是靠这个前缀 + 固定的 `idempotency_key`/用户名找到自己灌的数据，不会误删真实数据。

## 怎么用

```bash
make seed-data          # 灌数据，可以重复跑（幂等——命令内部全部走固定 idempotency_key/ON CONFLICT）
make seed-data-clean    # 清空能清的部分（哪些组件清不了、为什么，见上面两条 ⚠️）
```

登录方式：走前端/`frontend-standard` 正常的 Casdoor 登录页，用户名 `dev.superuser`、密码 `DevSeed123!`（或 `dev.sales.east`/`dev.warehouse.south`/`dev.finance.viewer`，体验不同角色/数据权限范围）。

## 为什么要建一个 ROPC 测试应用

`crm-opportunity`（以及 `erp-sales`/`erp-finance`）的建档/赢单/过账接口需要真实登录态（`besdk.ScopeOf(ctx)` 取 `owner_id`/`dept_path`），`infra-iam-casdoor` 自己的 `make seed` 为此会在 Casdoor 里建一个**只在本地环境存在**的 OIDC 应用 `local-dev-seed-app`（开了 Resource Owner Password Credentials 授权类型）；各组件自己的种子脚本用测试用户的用户名密码换一个真实 JWT，再拿这个 JWT 走真实 REST 接口建数据——不是直接写库，这批数据因此也顺带验证了一遍真实鉴权链路。

⚠️ **`local-dev-seed-app` 只应该存在于本地/测试环境**——生产环境的 OIDC 应用（`brickkit-app`）不许开 `password` 授权类型（见 `infra-iam-casdoor` 的 `docs/手册.md` §6），种子脚本建的是一个独立的、专门给本地开发用的应用，不会碰 `brickkit-app`。

## 依赖

`make seed-data`/`seed-data-clean` 假设 `brickkit up` 已经把 14 个组件全部起来（各组件自己的 `scripts/seed.sh` 会在关键步骤前探测端口/健康检查，起不来就直接报错退出，不会留一半数据）。需要 `curl`、`python3`、`docker`（各组件 `make seed` 内部会再拉 `fullstorydev/grpcurl` 镜像，不需要本机装 `grpcurl` 二进制）。上表每一行都可以单独跑（如 `make -C components/erp/inventory seed`），各自会自动链式调用它们需要的组件（身份类 + 强依赖）各自的 `make seed`，不需要根 `Makefile` 的编排。

## 这不是什么

- **不是测试数据**——这里灌的是给人"打开项目就能体验"的演示数据，进的是 `brickkit_db`。测试用的是另一个物理分开的库 `brickkit_test_db`（`make test-db-init` 建/刷新，见根 `AGENTS.md`"测试库与演示库分开"）——两者结构镜像同一套 schema，但数据互不相通：你在前端点开的、这套种子数据建出来的客户/商机，不会被任何组件的 `go test`/`pytest` 碰到；反过来 `erp-inventory`/`erp-finance` 这类会真实写共享引用行（仓库余额、法人过账序号）的测试，也不会污染这里的演示数据。不是 H2 那种进程内数据库替身——两个库都是真实 Postgres，`be-sdk-go`/`be-sdk-python`/`be-sdk-ts` 的测试全部对着真实 Postgres/NATS 跑，见根 `AGENTS.md` 的"real verification only"纪律。测试数据与种子数据的完整边界判据见 [`../plans/00-数据构建标准.md`](../plans/00-数据构建标准.md)。
- 不是 CI 用的 fixture（CI 目前不存在；未来如果要建 CI，`seed-data` 这套东西可以直接复用，但现在纯粹是人手工跑）。
