# Field-Tested Pitfalls Log

> **This document tracks exactly one thing**: pitfalls where writing code/config "looked right, `compose config` or a similar static check passed, and only running it revealed the problem."
>
> What does *not* go here:
> - **Design decisions** (why this architecture was chosen) → the Design Book
> - **Operational steps for deployment staff** → `docs/ops/部署手册.md` (its troubleshooting table is a "symptom → what to do" guide for deployers; this document is a "root cause → why" guide for developers/an AI — the two can overlap on an entry, one terse and one detailed, and don't need to replace each other)
> - **Project-level AI-assistant prohibitions** (the "23 easiest mistakes" kind of thing) → the root `AGENTS.md`
>
> Every entry has four fixed columns: **Symptom / Root Cause / Fix / Found In**. Grouped by category; add a new entry to its matching category, and open a new category only if none fits.

## Category G: Misjudging brickKit's Own Platform Capabilities — Wrong on the First Pass, Only Realized the Right Direction After Reading the Full Call Chain

> This class runs **opposite** to the earlier categories: it isn't "looked right, only running it revealed the problem" — it's "a first quick check (one grep, one or two files read) concluded the platform doesn't support some capability, and only reading all the way through the actual call chain revealed the platform genuinely does support it natively, often more completely than assumed." Listed here because it's just as dangerous as the earlier categories — designing a workaround around a wrong "the platform doesn't support this" conclusion (e.g. writing a real secret directly into `brickkit.yaml`) has an equally irreversible consequence (a secret ends up in git history).
