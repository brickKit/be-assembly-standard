# 给 brickKit 的一些经验分享

> **这不是一份 bug 报告，是一份经验分享。** 我们是 `be-assembly-standard`——基于 brickKit 装配的一个企业级组件化 ERP/CRM 军火库，目前已经真机验证 14 个组件、跑通了一条完整的业务闭环（商机赢单 → 建单 → 锁库存 → 生成应收 → 审批 → 通知 → 打印）。这份文档记录的是我们在这个过程中沉淀出的一些判断，觉得可能对你、对其他 brickKit 用户、甚至对未来会发生的一种场景有用——**往后大概率会有用户直接把 brickKit 的 GitHub 仓库交给一个 AI，让它自己读完再去设计项目方案**。如果这份文档里的内容将来能被这样的 AI 读到，也许能让它少走我们走过的弯路。
>
> **全部内容都以"这是一种可行方案，仅供参考"的方式呈现，不是"你必须这样做"。** 用不用、怎么用，由你和未来的使用者自己判断。
>
> **有一类内容我们特意没有放进来**：我们自己在 brickKit 之上设计的权限体系（一套本地策略决策点、权限键注册表、数据范围过滤的机制）。这完全是我们产品自己的架构决定，跟 brickKit 本身没有关系，不构成什么通用建议，所以不在这份文档的讨论范围内。
>
> 下面第一、二部分（测试、种子数据与测试数据）是我们觉得最通用、任何基于 brickKit（乃至任何多组件系统）的项目都会遇到的问题；第三、四部分是两套方法论，供参考；第五部分是几条具体的平台使用体会。

## 一、测试怎么分层、怎么推进

我们给自己定的目标只有一个：**让 AI 写的测试真的能拦住回归，而不是"数量很多但什么都没守住"**。分层判据、节奏、命名规范这些，我们完整写成了独立的[测试标准](../standards/04-testing-standard.md)，这里摘最核心的部分。

### 1.1 测试分四层，外加几个跨领域类别

| 类型 | 测什么 | 什么时候写 |
|---|---|---|
| **L1 契约测试** | 契约本身没有破坏性变更；每个接口真的能跨进程调通 | 契约刚写完那一刻 |
| **L2 业务规则测试** | **规格本身**：不变量、合法的状态迁移、幂等性、边界情况下"该发生什么" | 实现之前 |
| **L3 单元测试** | 这一版具体实现的分支：错误路径、空值、并发、SQL 拼得对不对 | 实现之后 |
| **L4 集成测试** | 真实数据库/真实消息队列/真实 RPC 端到端；迁移能反复干净地重跑；跨组件调用打到真实依赖 | 实现完成之后 |

**四条贯穿全程的原则**：① 规格先于实现——测试要先写，测的是"这个功能应该做什么"，不是"这段代码做了什么"；② 真实优于模拟——mock 最多证明"调用发生了"，永远证明不了"结果是对的"，而"结果对不对"才是测试存在的全部意义；③ 能机制化的判据必须机制化——任何"靠人记得检查"的规则，能写成脚本判据就必须写成脚本判据；④ 测试是规格文档，不是产量指标——一层测试重复测另一层已经测过的东西，不是"多一层保险"，是多一处以后要同步、又大概率不会被同步的地方。

**最有价值的一条判据，也是最容易讲清楚给别人听的一条**：

> **把这个功能的实现整个删掉，换一种语言从头重写，这条测试还应该成立吗？** 应该成立 → 这是在测规格（L2）。不应该成立（因为测的是这一版实现的某个具体细节）→ 这是在测实现（L3）。

这条判据的好处是它不依赖对任何具体测试框架的理解，随便读一条测试代码套一下这句话就知道它写错了层。

**核心交易类组件**（涉及库存、资金、薪酬这类"错一次就是真实事故"的逻辑）我们要求 L2 必须用基于属性的测试（property-based testing，Go 用 `rapid`/`gopter`，Python 用 `hypothesis`）——人定义不变量（比如"库存总数永远不能为负"），框架生成大量随机边界输入去攻击实现。纯举例式的测试永远抓不到"只在特定操作序列下才触发"的 bug，而这恰好是 AI 生成代码最容易留下的一类问题。

**幂等性测试必须覆盖并发**，不能只测"重放一次"——真正的风险从来不是"顺序重放两次"，而是"两个并发请求同时带着同一个幂等键到达"。一个错误但常见的实现是"先查是否存在，不存在再插入"，这在两个并发请求都落进"还没查到"这个窗口期时会各自执行一次；正确的实现应该是一条原子的 `INSERT ... ON CONFLICT DO NOTHING`，认领成功才真正执行。

**权限/数据范围类的边界测试有一个容易被忽略的陷阱**：常见的错误做法是只测两种情况——"有权限的人能看到数据"和"完全没有权限的人看不到任何数据"。**这两种测试都无法证明过滤逻辑本身是对的**：一段错误返回整张表的代码，同样能通过"零权限用户"测试（它根本走不到那一步），也能完美通过"有权限用户"测试——两条测试全绿，bug 依然存在。**正确做法是真实建两条归属不同的数据（不同的所有者/部门/仓库……），用其中一个身份去查，断言结果里完全不包含另一个身份的数据。** 这是唯一能真正证明"看不到别人的"这件事的测试形状——不这样做，这类过滤逻辑其实从来没有被验证过。

### 1.2 红绿重构节奏

一次会话推进一个"红-绿-重构"循环，一个循环一次提交。**最重要的铁律是不许为了让测试通过而去改测试**——测试红了，默认改的是实现；测试真的写错了，要单独一次提交说明原断言错在哪；**L2 测试挡路时，几乎一定是实现或者对需求的理解错了，不是测试错了**。三件事绝对不允许：注掉一条测试、加跳过标记、放宽断言让它凑巧通过——这三者的共同点是把一道"真的能拦住东西"的关卡降级成了摆设，而一旦一道关卡变成摆设，别的关卡的绿灯也会开始让人不敢信。

**同一个循环卡三轮还是红，按顺序试三条路**：① 把这一步切得更小；② 去看一个参考实现（读完自己想清楚再写，不要照抄）；③ 停下来，说清楚卡在哪、试过什么、怀疑是哪一层出的问题，交给人判断。第三条不是失败，是正确动作——一个问题说不清楚的时候就该停下，而不是硬着头皮绕过去。

### 1.3 跨组件测试：让一个组件的测试打到真实依赖

跨组件集成测试很容易在日常里被跳过——测试环境本身连不到依赖组件的内部端口，写了也白写，跨组件验证最后变成"只在有人手工搭好网络的时候才跑一次"。我们的解法是一个命令：只把"这个组件 + 它的强依赖树"跑起来，不需要整个装配都在跑，测试进程本身仍在宿主机上跑（构建缓存、并发检测都正常），跑完自动清理。**这条对任何"组件数量一多，集成测试就自然被大家默契跳过"的项目都值得考虑。**

### 1.4 两个跨领域的扩展测试类别，值得单独提

- **事件契约破坏性变更检测**：事件的 schema 只能新增，不能删除或修改已有字段/事件类型。这条完全可以自动化——拿当前的事件契约文件跟它的历史版本做对比，删字段、改类型、删事件名，一律拦下来。我们发现这条判据完全可以在门禁里机制化，不需要每次改契约都指望人记得检查。
- **SDK 并发正确性测试**：如果项目里有一份被所有组件共用的基础库（横切能力：事件投递轮询、幂等表操作、连接池管理……），"多个实例同时跑"这个维度的正确性，是单组件视角的分层测试完全测不出来的——L1-L4 全都假设"只有一个进程实例在跑"，永远发现不了"两个实例同时抢同一批未处理事件，各自都以为自己该处理"这类问题。这类基础能力至少需要一条"多实例并发使用同一个原语"的测试，断言结果恰好被处理一次——不重复、不遗漏。

### 1.5 前端测试分层与运行粒度

前端同样分四层（FE1 单元/逻辑、FE2 组件、FE3 端到端、FE4 视觉回归），思路跟后端一致：规格与实现分离、共享优先于一次性、真实优先于模拟。**FE3/FE4 我们特意推迟到页面交互形态基本稳定之后再统一补**——页面还在大改的阶段写端到端测试，每次 UI 变动都要连带重写选择器和断言，投入产出比很差；这不是"忘了写"，是刻意排序。**端到端测试涉及真实驱动浏览器，成本主要在"写/调试"阶段，不在"运行"阶段**——已经写好、稳定的测试套件跑一次成本跟普通单测差不多，真正烧资源的是第一次写测试时反复截图确认选择器、反复截图排查失败原因。降低这个成本的办法：优先用无障碍树（结构化文本）确认页面元素，而不是每次都截整页图；失败时先看纯文本的报错堆栈和 trace 文件，截图作为最后手段；关键交互路径尽量由人记录下来，减少 AI 靠试错去猜选择器的轮次。

我们还发现一个通用的运行粒度模型很好用：**全量**（部署前、阶段收尾时跑）/**单组件完整**（一个组件/功能刚做完）/**组件内子集**（迭代中确认"这部分还没坏"）——不管是后端还是前端，这三档粒度背后是同一套思路，只是命令不同，这个模型本身跟具体技术栈无关。

## 二、种子数据与测试数据怎么规划

这是我们觉得**最值得单独拿出来讲**的一部分——任何基于 brickKit 装的项目，只要用到数据库，都会遇到"测试用的数据"和"演示/体验用的数据"该怎么分、怎么造这个问题。完整版是我们的[数据构建标准](../standards/05-data-construction-standard.md)，这里摘核心判断。

### 2.1 两条路径必须物理隔离，不只是逻辑上不共用

我们把数据分成完全独立的两条路径：

| 机制 | 用途 | 怎么产生 | 生命周期 |
|---|---|---|---|
| **测试构建数据**（带唯一后缀） | 全部自动化测试 | 每次跑测试都现造，用时间戳/随机数加后缀区分 | 永不清理——攒在数据库里没关系（下次跑又是新的唯一后缀） |
| **种子/演示数据**（`make seed`） | 给人探索、演示、给一个新组件开箱即用的数据 | 固定的幂等键，claim-first 幂等，重跑不会重建 | 长期存在，可以整体撤销 |

**这两者绝对不能物理共用同一个数据库**，哪怕看起来只是"逻辑上不共用"也不够——我们真实踩到过这个问题：一些组件的集成测试会真的写入数据库初始化脚本预置的共享引用行（比如默认仓库、默认法人这类基线数据），如果测试库和演示库是同一个物理数据库，跑一次测试就会真的改变演示数据，用户打开系统探索时会发现数据莫名其妙变了。**这是一个数据持久化问题，不是运行时并发访问问题**——跟"容器有没有在跑"完全无关，停掉容器也躲不开，因为写下去的行就留在磁盘上。我们的解法是在同一个数据库实例里再建一个物理独立的库（不需要另起一个数据库实例），两边镜像同一套表结构，但数据永不相通。

**我们也评估过用轻量级/一次性数据库（类似 H2、Testcontainers 那种做法）替代真实基础设施来跑测试**，结论是不建议——这类做法本质上是换了一个数据库实现，而"集成测试的判据就是真实基础设施"这条原则会因此打折扣。真正该解决的问题不是"数据库太重、跑起来慢、容易互相污染"，而是**让数据本身变得一次性**——"唯一后缀、不清理"这个模式已经是这条路径该有的长期形态，不是权宜之计。

### 2.2 不管哪条路径，数据都应该尽量覆盖场景——但"覆盖"的方式不同

- **种子数据追求"多而全"**：每一条状态机分支、每一种失败路径、每一个数据范围维度都应该有真实能触发它的数据，因为种子数据同时承担着"人能不能完整体验这个系统"这个目标，量本身就是目标之一。
- **测试数据追求"少而准"**：每条测试只需要恰好够验证这一条断言的最小数据，不需要为了"丰富"本身去堆量。例外是核心交易组件的属性测试——那里需要框架生成大量随机边界输入去主动攻击实现，但这个"多"是为了增加撞上边界条件的概率，跟种子数据的"多而全"不是一回事，不要混为一谈。

两者不是"丰富版"和"精简版"的关系，是服务于不同目的、天然长得不一样的两份数据。但底线相同：**任何组件都不该只有"一切正常"这一种数据或断言**——状态机的每个状态、每条失败分支、每个数据维度，不管是种子数据还是测试数据，都不能只覆盖正常路径。

### 2.3 跨组件协作：依赖没有你需要的数据/能力时该怎么办

这是我们认为**最重要的一条判据**，测试场景和种子数据场景各有对应的做法：

**自动化测试场景**：写一条需要依赖组件产出某种数据形态的跨组件集成测试时——

1. **优先通过依赖组件真实的接口现场产出**。调用创建接口传入需要的参数、调用状态变更接口切到需要的状态，这些都是已有的真实命令，不需要预先造数据。
2. **如果依赖组件的契约压根没有产出这种数据形态的能力**（没有对应字段、没有对应状态迁移、没有对应组合），**正确做法是先把这个能力补进依赖组件的契约/实现里，再通过真实调用产出数据——不是绕开它，不是拿原生 SQL 直接写依赖组件的数据库，也不是干脆跳过这个场景不测**。补这个能力依然要遵守契约演进的规矩（只增不删、向后兼容）——这不是一次性权宜之计，是把依赖组件本身的完整性补全，未来所有测试和调用方都受益。
3. **拿原生 SQL 直接写另一个组件的数据库，永远是最后的选择，在自动化测试里原则上不允许**。跨组件边界的全部意义就是"只通过契约交互"，测试代码也不例外——绕过契约直接写库，等于悄悄建立了一条契约之外的耦合，之后契约怎么变，这条测试都不会报警，只会在某天契约真的变了之后，以更难排查的方式坏掉。

**种子数据场景**：**下游组件可以、也应该主动要求上游组件丰富它的数据，而不是被动等待**。如果一个组件做演示或测试时需要某种数据组合（比如"某个部门、某种状态的客户"）而上游组件的种子数据里还没有，正确做法是**直接去上游组件自己的种子数据生成逻辑里把这个组合加上**——不是在下游绕开它将就现有的，也不是坐等"以后有人加"。数据是假的，多加几种组合成本几乎为零，"上游数据够丰富，下游才有得挑"是一种主动的、双向的协作关系，不是单向等待关系。这跟自动化测试场景是同一条原则的两种落地：**需要一个自己没有的东西，去修供给它的那一方，而不是绕开它**。

### 2.4 种子数据专属的几条设计原则

种子数据不是自动化测试数据，但它承担的目标之一恰好就是"测试"本身——一条完整业务链路能不能端到端跑通，一个新场景要不要跨多个组件才能验证，这些往往要靠人真的打开跑起来的系统走一遍，不是靠 `go test`。这种"真的跑起来、真的点一遍"式的验证跟自动化测试同等重要，不是它的低配替代品。

**几件不会随着"数据量大"自动发生、需要刻意设计的事**：
- **数据范围/归属维度要有真实存在感**：如果所有种子数据都挂在一个全能管理员账号下，"某人看不到别人的数据"这类能力在实际体验里根本无从验证。
- **量要足以触发分页**：如果一个列表接口强制用游标分页，种子数据太少（比如只有五条）会永远只有一页，分页这个契约在体验里毫无存在感。
- **时间要打散**：数据应该分布在不同时间点上，"最近N天"这类查询、趋势图表、按时间分区的维护逻辑才有真实场景可验证——不能所有数据都是"刚刚创建"。
- **负向/边界数据也要有**：禁用状态、零库存、逾期未结、被拒绝的申请——失败路径不能只存在于想象里，要有真的能点进去、能拿去测试的数据。
- **数据要可发现**：数据量上去之后，需要有地方能查到"这个固定标识符对应什么概念"，否则新组件想复用现成数据无从下手，还可能在不知情的情况下产生冲突。这份清单本身应该集中维护——组件/数据/数量/归属，一处就能查全，不需要每个组件各自维护一份。

**冗余是可以接受的，甚至是件好事**：反正所有数据都是假的，不存在"污染真实数据"的顾虑。哪怕不同组件的种子数据在概念上有重叠，也不需要费力去重——冗余的代价接近于零，而"看起来完整的大量数据"本身就是要达成的目标之一。

**归属与协作原则**：
- **每个组件自持自己的种子数据**，不要集中在装配层——集中式脚本只有在所有组件都一起跑起来时才能用，单独起一个组件时它拿不到任何东西，这违背了更基础的原则："单独起一个组件（连同它的依赖树）应该就能正常工作"。
- **一个组件生成种子数据时，第一步永远是先确保它声明的每一个依赖（不区分强弱）都已经有种子数据**，再跑自己那部分。不区分强弱依赖的理由是：开发/演示环境里所有组件本来就是一起启动的，不存在"只装部分依赖"这种场景；而依赖关系一旦声明，就说明这个组件真的需要它——强弱之分是给真实客户"要不要额外购买这个可选模块"这个部署时问题用的，不值得在开发时期费心区分，徒增心智负担。
- **组件自己的种子脚本和需要这些产出 id 的编排脚本之间，用组件自己的幂等表当"交接协议"**——组件的种子逻辑只管把数据灌进去，不负责把 id 按什么约定格式打印出来，谁需要这些 id 自己去查（用固定的幂等键去查那张幂等表，拿到真实的行 id）。
- **种子数据本身是一份轻量契约**：一旦别的组件查过某个固定标识符，这个标识符就不能被随意删除或改变含义——只能新增，不能修改已经被引用的那个。
- **表本身是"只增不改"的性质**（出于业务或审计原因，比如一张流水表、一个已锁定的会计期间），就不该有逐行删除式的撤销机制——只能靠整库重置来清空。序列不会因为删了几行就回退；逐行删除既做不到真正干净的复原，也违背了这张表本身"只增不改"的设计。这类组件正确的工具是"迁移降级再升级"式的真重置，不是删除：把 schema 下所有表都丢弃、从迁移重新建，序列真的从 1 重新开始，迁移里种的基线数据也会重新落地。**规则：只增不改的表没有"清理"，只有"重置"；能安全逐行删除的表两者都可以有，"清理"更轻量（不动其他数据），优先用它。**
- **能触达真实客户部署环境的凭据/身份数据，绝对不能混进这套机制**：一旦测试账号或万能密码被写进"每次部署都会跑"的数据库初始化脚本，就等于给每一个真实客户的系统永久埋了一个后门——这条边界没有例外。真正每个部署都需要的通用基线数据（默认仓库、默认法人和基础科目表这类，不含身份凭证）依然走数据库初始化，那不是"测试数据"，是产品本身的一部分。真实部署"第一个管理员怎么进来"这个鸡生蛋问题应该靠配置驱动的自举机制解决，而不是种子数据——真实部署方把自己的真实身份标识填进一个配置项，容器启动时幂等地赋予管理员角色，不需要任何人手写 SQL，也不需要在任何地方硬编码账号。这个机制只解决"第一个管理员是谁"，跟本地测试需要的"一个拥有全部权限的超级测试角色"是两件不同的事，不能互相替代。

### 2.5 测试数据的额外规则

除了唯一后缀、不清理这两条通用规则外，消费者类测试（订阅事件触发处理逻辑的那类）还有两条自己的规矩：① 测试自己构造/发布事件去触发消费逻辑时，要用测试私有的主题/频道名，不要用生产环境的真实名字——如果同一台机器上真的有一个容器订阅着同一个生产名字，广播式的订阅机制会让真实容器和测试的临时订阅者同时收到消息，谁先抢到去重表的那一行，谁的处理结果就会留在数据库里，断言可能读到的是别人的产出而不是这次测试真正触发的那次。② 如果去重表按照某个唯一标识做单调去重，测试必须用唯一标识而不是固定字符串——去重逻辑一旦生效就是永久的，用固定字符串会导致测试套件第二次跑的时候，这个组合早就被判定"已处理过"，消费函数根本不会再被真正调用一次，断言读到的会是"从未处理"的初始状态，看起来像是功能坏了，其实是测试数据设计的问题。

## 三、参考实现方法论

我们给自己定了一套"怎么负责任地参考一个现实项目"的流程，完整版是[参考实现标准](../standards/02-reference-implementation-standard.md)，这里摘两条觉得比较有分享价值的。

**三步法，顺序不能反**：① 先按自己项目的约束设计一版；② 只在设计不出来的地方去看一个成熟的现实实现——领域模型怎么划分、状态机有哪些合法状态和迁移、哪些字段是必填、边界情况实际怎么处理；③ 回来结合自己项目的真实约束想清楚再写。**带着自己的方案去读别人的实现，才看得出差别在哪；空着脑袋去读，只会产出一份复制品。** 闭源产品同样值得参考——虽然看不到源码，但能观察一个成熟产品在真实世界里"实际怎么被使用"：哪些功能客户天天点，哪些从来没人碰，哪些流程被抱怨了很多年——这类信息对判断"某个东西值不值得独立拆分出来"往往比源码本身更有价值。

**识别"槽位族"信号**：对比多个参考实现时经常会遇到一种情况——**同一个功能，几个成熟系统里有真正不同的实现，而且关键是：每一种实现都合理，只是适配不同的客户画像。这不是一个"要不要做成可配置"的问题，而是一个信号：这个功能需要一族可插拔的实现，而不是带一个开关的单一实现。** 判断的关键完全在于"每一种都合理"这个限定词——如果读完发现某一种明显更好，那就是默认实现，不需要成一个族；如果几种实现各自站得住脚、服务的是真正不同的客户群体，那就是一个真实的市场分歧，值得做成正式的可插拔族。识别出这个信号后：先正式注册这个族（命名、定义共享的"槽位"契约、确认每个成员的契约面必须完全一致、明确各自适配什么客户画像、决定默认装哪一个）；确认"没有任何东西对它建立依赖边"这条硬约束（否则它就不该是一个可插拔的槽位，正确形态是"一个组件+内部策略"或者干脆整仓 fork）；再动手写每个成员的实现。**严禁在一个组件里写类似 `if strategy == "A"` 的分支把这些真正不同的需求硬塞进同一份代码**——那等于把多个客户的分歧压缩进同一份实现，谁的需求都会被别人的需求牵制。

## 四、AI 驱动开发的几个判据

这部分是我们在"AI 写、人审"这个组合下摸索出的判断标准，完整版是[AI 开发标准](../standards/03-ai-development-standard.md)。核心前提：**AI 写实现的失败模式和成本结构跟人类工程师完全不同**——它每次会话都是全新的、没有上一次的记忆，上下文窗口有限；对它来说，整体重写一个文件有时候反而比小心地在已经打了三个补丁的基础上再叠一层更便宜，这跟人类工程师的直觉恰好相反。

**要不要用设计模式，判据只有一句话**：这段逻辑是更容易读懂和扩展，还是更难？**由谁来判断"容易"已经确定了：按 AI 能不能快速看懂来判**——人类审查者可以默认已经具备设计模式的知识背景，这不是瓶颈；真正的瓶颈是 AI：它每次会话从零开始，上下文有限，看不到运行时状态，也不会"过一阵子自然就想起来那个文件在哪"。所以"容易"有一个具体的、可检验的定义：**一个全新会话的 AI，只读了少数几个文件，能不能把一条新规则加对？** 帮 AI 的：小文件+单一职责、把规则集中注册在一个地方、显式优于隐式、一个文件对应一种情形、状态迁移集中到一张表里。害 AI 的：深继承链、元编程/反射/动态分发、"为将来可能的扩展"提前抽象、逻辑分散在多个包里。**值得停下来考虑用一个模式的四个信号**：`switch`/`if-elif` 链已经过 5 个分支且还在长；函数超 150 行或文件超 600 行；同一套流程重复跑好几次、只有中间一两步不一样；状态迁移的合法性在不止一处被检查。**三种不该用模式的情形**：简单资源的纯 CRUD；只有两个分支且看不到可预见的第三个；单纯"为将来可能需要"而提前抽象——这条最容易违反，因为"给未来留余地"听起来永远是对的，判据是"你现在能不能具体说出第二种实现会是什么样"，说不出来就不要现在抽象。

**一次会话该装多少**：一个任务，或者一个任务里的 2-4 个红绿循环；上下文用到一半就该收尾提交，开一个新会话——给下一个会话留足空间，才能让它真的去读周围的代码，而不是只能读自己刚写的那部分。新会话开头该固定读什么（仓库级导读、当前任务单元的导读、这个单元的设计文档、当前任务本身、马上要改的具体源文件），不该读什么（完整设计文档、完整总纲/主导读、跟当前工作无关的部分）——需要某条具体规则时，通过路由表定位到具体章节，而不是把源文档整份投机性地读一遍。

**人类实际上只需要审查五样东西**，因为没有人能读完一个大型、AI 编写代码库里的每一行实现：契约（一旦有消费者就只能向后兼容地追加，这是最不可逆的东西）、迁移（分区键/主键/索引在建表时就定死，数据进去之后再改就是一次迁移）、业务规则测试里的不变量清单是否列全（这条门禁本身抓不到——它只会跑已经写下来的测试，一个没人想到的不变量不会因为门禁全绿就被验证过）、设计文档的边界和依赖章节（画错边界或多建一条不该有的同步依赖，是唯一能污染整张架构图的错误）、门禁的输出本身。**不需要审查的**：业务代码逐行、普通单元测试、构建脚本——这些已经被门禁和测试覆盖，真出问题会自己变红，不需要人提前盯着看。

**什么时候允许整体重写，而不是继续打补丁**：同一段逻辑已经朝不同方向被反复打过几次补丁，理解现状本身就要先在脑子里叠好几层历史；或者问题根本不是一个 bug，而是发现最初的设计判断就是错的，继续在这个基础上建只会让偏差越滚越大；**种子/演示类数据值得一个更宽松的重写门槛**——这类内容天生是假数据，没有"迁移历史记录"这个包袱，重写的成本跟"删掉重建"差不多，与其一点点在现有基础上加，不如整份按新判据重新设计一遍。

## 五、平台侧的几个具体建议

以下是我们在实际使用中遇到的一些具体点，供参考：

1. **`IMAGE_UNAUTHORIZED` 这条报错信息容易把人导向错误方向**。我们遇到过的真实情况是：本地压根没有配置任何私有镜像仓库凭据，报错却提示"未授权"——排查后发现真正的原因是本地 Docker daemon 里根本不存在这个 tag 的镜像（只是改了组件版本号，没有重新构建）。如果这条报错能明确区分"权限问题"和"本地找不到这个 tag 的镜像"，会省掉不少排查时间。

2. **依赖版本号是纯字符串精确匹配，但没有一致性校验，这个坑我们复发了四次**。场景是：某个组件升级版本后，别的组件（或顶层的版本锁定）里对它的引用字符串忘了同步更新，`brickkit` 会把新旧版本号解析成两个完全独立的节点，各自生成迁移和启动指令——不报错也不警告，实际后果是真的多起一份容器、真的撞端口。我们最后自己写了一个校验去补这个洞（比对每个组件声明的依赖版本 vs 被依赖组件自己的真实版本，以及顶层版本锁定 vs 组件自己的真实版本）。这类"同一个逻辑组件因为版本字符串不完全一致被拆成两个节点"的校验，如果平台原生就做，可能能帮很多用户避开这个坑——它不是我们这个项目独有的场景，任何一个组件数量较多、版本迭代频繁的装配都会遇到。

3. **`1xxxx` 整个端口段被平台保留用于宿主机映射的 fallback，但我们没有在任何面向用户的文档里找到这条说明**，是读了平台源码才发现的规律。我们因此踩了好几次端口冲突——选了几个看起来"挪开了官方默认端口"的新端口，结果全部撞在这个保留段上。如果这条规则能在文档里更显眼地提前说明，会省掉这类踩坑。

4. **资源的 `engine` 字段该写"能力名"还是"产品名"，我们没有找到现成的判断依据**，是自己摸索出一条规则：协议兼容的资源写能力名（比如对象存储写 `s3`，这样换 RustFS/MinIO/S3 之间是真正的零改动）；协议不兼容的资源写产品名（比如消息队列写 `nats`，这样换成 Kafka 时平台会主动报错阻断，因为那本来就是一次迁移，不该被"看起来只是改一个字段"这种假象掩盖）。如果这条判断依据能写进文档，可能会帮用户在设计装配清单时少走一次弯路。

5. **有一个真实存在、做得也很周全的能力，我们险些因为搜索不够彻底而误判成"平台不支持"**：平台对 `components[].config` 字段其实有一整套配套机制——`${VAR}` 形式的环境变量展开，以及专门扫描"看起来像密钥的键名"（含 password/secret/token/credential 等子串）、如果没写成 `${VAR}` 就主动告警的功能。我们第一轮只搜了一两个关键字没搜到，就差点下结论"不支持"，甚至已经写了一半"建议加这个功能"的反馈草稿，后来往下读源码才发现平台早就做了，而且做得比我们以为的更完整。这条不是功能缺失，而是**可发现性**问题——如果这套机制能在核心文档里放到更显眼的位置，能帮其他用户避免我们险些踩到的那个后果不可逆的坑（把真实密钥明文写进被 git 追踪的文件）。
