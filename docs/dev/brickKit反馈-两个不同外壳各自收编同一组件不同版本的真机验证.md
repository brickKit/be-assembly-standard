# brickKit 反馈：两个不同外壳各自收编同一个组件的不同版本——一份你们自己没有测过的场景，我们真机验证了

> **这份文档是一次性的**：只针对这一个具体场景，看完可以直接删掉，跟 `docs/dev/` 里其它长期文档性质不一样。完整过程、四条独立复现（裸进程/Docker/K8s/Docker+本地混合）的原始记录都在我们自己 `docs/plans/05b-组合矩阵验证.md` 的 Task 4e/5e/6e/8e 四节，这里只摘要结论，方便你们判断要不要采纳。
>
> **这不是一份 bug 报告，是一个正面结果的通知。** 我们知道你们自己的调研结论里写过"两个不同外壳各自收编同一组件的不同版本——brickKit 自己完全没有测试或文档覆盖，是真正的未知领域"，我们这次趁着阶段五做组合矩阵验证，顺手把这个场景真机走了一遍，四种运行环境各自独立复现，结果是好消息，想着你们大概率会关心。

## 先说结论

**这个场景在生成层面完全支持、地址路由完全正确，真机也确实能跑通**——不管是裸进程手工拼环境变量，还是真实 Docker/K8s 部署，`servedBy` 的地址生成机制严格按 `componentId`+`version` 这个复合键工作，不会因为两个版本"分别挤在两个不同外壳容器/Pod 里"就产生任何地址串扰或覆盖。

**唯一真正的门槛，不在 brickKit 这一层，在我们自己项目的数据库权限模型这一层**：我们的 `be-ops` 工具按 `brickkit.yaml` 里**真实**的 `servedBy` 声明，生成每个外壳登录角色该有的 schema 授权。这个场景是我们人为在数据层面之外强加的一个"额外收编"关系（正常情况下一个组件只会被一个外壳 `servedBy`），`be-ops` 自然不会替这种从未被真实声明过的场景预先授权——这不是 bug，是我们这套"权限跟着声明走"的设计在一个它没被设计要覆盖的场景下的正确反应，跟你们平台本身没有关系。

## 怎么复现的（四条独立记录，不是抄同一份结论四遍）

**共同的构造方式**：`shell/go-core` 正常收编 `mdm/customer@<新版本>`（以及其它 4 个正常成员），额外让 `shell/go-backoffice`（正常收编 `crm/opportunity`）也收编 `mdm/customer@<旧版本>`——同一个真实组件，两个版本，分别 `servedBy` 两个不同的外壳。

1. **裸进程**（Task 4e）：手工拼装 `BRICKKIT_SERVED_MEMBERS_CONFIG` 分别喂给两个外壳进程。两个实例各自独立监听、独立生死，互不冲突；第一次用真实的 `shell_go_backoffice` PG 角色时，因为它从未被授权访问 `mdm_customer` schema，在迁移阶段就被正确拦下（不是"看似启动成功、实际权限不完整"的隐蔽状态）。
2. **Docker**（Task 5e）：真实 `brickkit up`。`docker-compose.yaml` 生成结果显示 `BRICKKIT_SERVED_MEMBERS` 正确区分两个外壳各自的成员列表，`erp/sales`/`crm/opportunity` 注入的 `MDM_CUSTOMER_ENDPOINT` 精确指向它们各自依赖声明的那个版本，没有出现"同容器优先/就近覆盖"。第一次真实 `up` 因为 `shell_go_backoffice` 角色权限不足而 `unhealthy`（`failed to open database: no schema`），手动补 `GRANT`（schema USAGE + 表 CRUD + 序列权限 + 角色成员关系共 4 条）后完整跑通，两个版本对同一条真实查询返回完全相同的数据。
3. **K8s**（Task 6e）：真实 `brickkit up` apply 到 minikube。两个版本各自拿到独立的 K8s Service（`selector` 分别指向各自的外壳 Deployment），除了 `CrashLoopBackOff` 代替了 Docker 侧的"容器不断重启"（两种编排器各自的重启语义），根因和修复方式跟 Docker 侧完全一致。额外验证了跨 Pod 通过 K8s Service 名访问，同样成功。
4. **Docker+本地混合**（Task 8e）：在前三条基础上，额外让一个完全独立的组件（`infra/bff-mobile`）用 `local: true` 拉到宿主机，确认这层额外的本地调试状态不影响上述结论——依赖边地址解析这部分交给你们 v0.4.6 已经修好的 `local:true`+`servedBy` 机制处理，人为额外收编、没有任何依赖边指向的那个探测实例仍然需要手工端口映射（这个不在你们那条修复的覆盖范围内，我们已经确认过原因：那条修复走的是 `mapDependencyToHost`，前提是有一条真实声明的依赖边可循，这里没有）。

四条独立复现，四次都是同一个结论：**生成/路由永远正确，数据库 schema 授权永远是唯一的真实门槛**。

## 我们没有要求你们做什么

跟我们最初 `servedBy` 提案文档里第七部分说的一样，这份文档不是在要求你们改什么——这个场景本来就是我们自己数据库权限模型的正交限制，不是你们平台的缺陷。**我们分享这个结果，纯粹是因为你们自己的调研笔记里明确标注这是"未知领域"，现在有了四份独立、完整的真机证据，想着这个正面信息对你们、或者未来会读到这份仓库的其他 brickKit 用户可能有用**——如果哪天你们决定要把这个场景变成一个受支持的正式功能（比如 `be-ops` 这类工具的角色/授权生成逻辑要不要专门跟进多外壳收编同一组件的场景），至少现在有真实数据可以参考，不用从零开始摸索"这条路径到底通不通"这个问题本身。
