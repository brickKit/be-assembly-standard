## 1. 这一阶段实际验证/发现了什么

## 2. 与原计划/原设想矛盾的地方，和为什么

### 2.1 阶段五的范围本身发生了替换——不是我们规划错了，是环境在阶段边界上刚好变了

阶段四复盘 §7 待完成事项第 3 条写的阶段五范围是"补齐 `infra-storage`/`infra-attachment`/`infra-dlq-monitor`/`mdm-supplier`/`mdm-org` 五个组件，凑成最小可交付形态"——**这件事完全没有发生**。真正发生的是：阶段四复盘落笔的同一时间窗口（2026-09-14），brickKit 正式发布了 `servedBy`，把阶段四里我们自己手搭的整套模拟层（`local:true` 反着用、`infra/shell-compose.yml` 手写编排、`Makefile` 的 `shell-up`/`teardown-up` 互斥切换脚本）变成了一个平台已经不再需要我们自己维护的过渡态——继续在这套模拟层上添 5 个新组件，等于在一个即将被替换的地基上继续盖楼。**这不是重新规划，是把"先把地基换真"这件更紧迫的事插到了"加组件"前面**，05a 因此产生，05b 的全部组合验证也只有建立在真实 `servedBy` 之上才有意义（用模拟层测出来的"能不能合并到 K8s"这类结论，本来就不能代表真实机制的行为）。

**这说明什么**：阶段边界上的"下一步做什么"判断，不能只看上一份复盘写的计划文字，还要看这段时间外部依赖（这里是 brickKit 自己的发版节奏）有没有发生足以改变优先级的变化——这条经验本身跟阶段四 §2.1 学到的"`registry/` 锁定文件比计划文档的文字描述更该被信任"是同一个母题的另一个实例：**判断"接下来该做什么"之前，先确认支撑那份计划的外部前提是否还成立**，不管这个前提是一张锁定表，还是一个上游平台的发版状态。

### 2.2 "合并部署只能 Docker 交付"——从阶段一沿用到阶段四的判断被反转

这条铁律的完整表述曾经是："上 K8s 意味着先把所有外壳拆回独立容器，没有部分合并部分上 K8s 这种中间态"（`local: true` 只能配 `deploy.target: docker`，K8s 目标下 CLI 生成阶段直接报错，这是当时唯一存在的合并机制的真实限制）。05a 迁移到 `servedBy` 时读 brickKit 源码（`internal/k8s/servedby.go`）顺手发现：**`servedBy`（现在唯一的合并机制）原生支持 K8s**，这条限制从一开始就只属于已经退休的 `local:true` 外壳合并用法，不属于 `servedBy`。05b Task 6（纯外壳×K8s）、Task 11（组件+外壳混搭×K8s）真机确认：`brickkit up` 原生生成的 Deployment/Service 结构正确，跨外壳依赖通过 K8s 原生的 Service+CoreDNS 解析，完整业务链路端到端可用。

**这条反转值得单独强调的原因**：它不是一次"发现文档写错了"的小修正，是这个项目从阶段一起反复强调的一条硬约束（"上 K8s 意味着先拆回独立容器"）被证明只是**特定实现（`local:true`）的限制，不是这件事本身的物理限制**——`local: true`+K8s 依然真实报错（05b Task 13 再次确认），但那已经是一条边缘用法（本机裸进程调试单个组件）的限制，不再是"合并部署"这件事整体的限制。`docs/ops/部署手册.md` §五已经把这条反转写成本阶段"最值得强调的变化"，纠正了手册旧版本的错误描述。

### 2.3 "先摸透平台、后面阶段不太会再牵连出平台层面新 bug"——这个假设在本阶段没有成立，但推翻的原因是健康的

阶段四复盘 §3.1 的判断是："先集中把平台摸透（阶段二），业务/工程能力盖在上面（阶段三/四）不容易牵连出平台层面的新 bug，这不是运气，是阶段顺序本身选对了"——阶段三 0 例、阶段四 0 例，两次印证了这条判断。**本阶段直接反例**：7 个真实平台 bug，是阶段二（1 例）的 7 倍，是阶段三/四总和（0 例）的 7 倍。

**但这不是对阶段四那条判断的否定，是那条判断的适用边界被看清楚了**：阶段三/四验证的是 brickKit 已经成熟、稳定运行了多个阶段的既有机制（gRPC 地址改写、资源生成、组件生命周期）；本阶段验证的 `servedBy` 是一个**在本阶段期间才正式从开发状态发布的全新机制**（从 v0.3.0 起步，本阶段结束时到 v0.4.6）——我们是这个功能第一批做真实项目端到端压测的用户，`servedBy` 落地前 brickKit 自己甚至主动来向我们请求验证（见 §1 表"brickKit 自己主动发来的验证请求"一行）。**一个刚发布的新机制被真实项目第一次全量压测时冒出一串真 bug，这是这类工作本该有的样子，不是异常**——阶段四那条"先摸透平台"的判断依然成立，只是它成立的对象是"平台已经稳定的部分"，不覆盖"平台刚刚发布、还没有被真实项目验证过的部分"。**以后任何阶段如果又要第一次采用 brickKit 某个新发布不久的机制，应该提前预期一轮类似的 bug 密度，不该假设"前几个阶段都很干净，这次也会很干净"**。

### 2.4 出档整理过程中自己发现并当场纠正的两处疏漏

写 05b Task 15（出档）时，回头核对已删除的历史反馈文档才发现两处本阶段自己制造的小疏漏，**都是当场发现、当场补齐，不是留到复盘才暴露**：

1. **Task 14 的"servedBy 有 6 条静态校验"数错了，实际是 7 条**：intro 段落列出的条目其实有格式/自引用/链式嵌套/与 `local:true` 互斥/重复声明共 5 条静态校验+2 条生成期校验，但 14.1–14.5 的测试清单只覆盖了 5 条，"格式错误"和"与 `local:true` 互斥"两条从未单独测过——且历史上这两条只在 brickKit 尚未发布 tag 的开发版二进制上验证过，从未在本仓库正式安装的 CLI 上确认过。发现后当场补测 14.6/14.7，确认这两条行为从开发版到正式版没有回归。
2. **Task 8e 曾经的一个错误推测被后续 Task 12e 自己推翻**：Task 8e 一度以为 brickKit v0.4.6 的 `local:true`+`servedBy` 地址修复能让某个手工端口映射补丁彻底退休，真机重新验证后发现这个判断是错的——修复只覆盖"某个组件真实声明依赖边"的情形，对"人为额外收编、没有任何依赖边指向它"的探测场景完全不适用。

**这说明什么**：一份计划文档 intro 段落里"数了几条"这类看似不会出错的元信息，也值得在真正动手测之前核对一次源头（这里源头是"到底有哪几类 servedBy 校验"），不能只凭写 intro 时的记忆——这跟阶段四 §2.5"计划文档对既有工具的断言最好当场核对源码"是同一类教训的又一次复现，值得合并成一条更通用的提醒：**任何"列了几条/共有几类"这种数字性质的断言，写下的同时就该有一次可追溯的核对动作，不要假设自己数对了**。

## 3. brickKit 平台本身：理念是否有问题，实现是否有 bug

### 3.1 真 bug：7 例，全部走完"反馈→修复→自己重新编译验证"闭环，无一例外

| # | 问题 | 发现于 | 修复版本 |

| 2 | `collectTargets` 判断"该不该跳过生成独立容器"只查了 `c.Local`，没查 `c.ServedBy`，导致真实 `brickkit up` 直接报 `no such service`，一个容器都起不来 | 05a 0.4 | v0.4.1 |

**这 7 例全部集中在 `servedBy` 这一个功能面上**，且全部发生在这个功能从开发状态走向成熟发布的这几周窗口内——跟阶段二发现的那 1 例（Manifest 缓存旁路）性质不同：那一例是平台运行多年后仍然潜伏的边界 bug，这 7 例是一个新功能第一次被真实项目端到端压测时的正常产出。**没有一例出在平台已经稳定运行的基础机制上**（gRPC 地址改写、独立组件生成、版本精确匹配——这些在本阶段全程正确工作，Task 1–3/7 的全部真机验证都没有在这些机制上撞到任何新问题）。

### 3.2 值得反馈但不是 bug 的观察

**两个不同外壳各自收编同一个组件的不同版本**——brickKit 自己的调研笔记明确标注这是"未知领域"，本阶段用四种独立运行环境（Task 4e/5e/6e/8e：裸进程/Docker/K8s/Docker+本地混合）各自真机复现，结论一致：生成/路由层面完全支持，真正的门槛在我们自己项目的数据库权限模型（`be-ops` 不会为一个从未被真实声明过的"额外收编"关系预先授权 schema），不是 brickKit 的缺陷。已经写成一份新的一次性反馈信件（`docs/dev/brickKit反馈-两个不同外壳各自收编同一组件不同版本的真机验证.md`），单纯是把这个正面结果告知 brickKit，不要求他们做任何改动。

## 4. 流程改进

1. **"先隔离验证再动真实仓库"这条阶段四教训，本阶段被正面验证有效，没有再违反**：05a 0.1 节"最小子集真机实验"（只挪两个零依赖组件、建一个临时外壳镜像）先于 0.4 节"全量真机切换"（12 个组件一次性正式迁移）——先在一个小范围、可以随时 `git checkout` 丢弃的实验里验证核心判断（"外壳态和全拆态能不能共存于同一份 `brickkit.yaml`"），确认成立之后才铺开到全部 12 个组件正式发版。这正是阶段四那次真实违反（嵌套 go module+replace 的错误推测直接铺开 5 仓库重构才发现装不下）之后应该长期保持的做法，这次全程贯彻。

2. **"不直接采信对方的'已修复'说法，自己重新编译验证"这条自查习惯，本阶段再次被证明必要，不是过度谨慎**：§3.1 第 5 条（PEM 截断）v0.4.4 发布后如果直接采信"已修复"关闭这条反馈，会把一个实际只解决了一半的问题误判成已解决——`local:true` 场景在 v0.4.4 下依然会在特定边界条件（PEM 结尾恰好是 Base64 填充的 `=`）下截断密钥。这条习惯此前在阶段四相关记忆里已经记录过一次代价（brickKit 回复"已修复"实际只修一半），本阶段是它第二次真实生效，值得继续保持，不因为"这次好像修好了"就放松验证力度。

3. **"每个任务做完就停下汇报"配合"每个大 Task（含全部子变体）做完才 commit 一次"，在 05b 12 个 Task 家族 + 2 个负向验证任务上完整贯彻，没有一次因为"反正后面还要改"而留着脏状态跨 Task 传递**：每个子任务的模式高度一致——临时改一处 `brickkit.yaml`/`component.yaml` → 真机验证 → 立刻 `git checkout --` 还原 → 确认 `git status --short` 干净 → 才进入下一个子任务。这套节奏在 14 个 Task 家族（含 b/c/d/e 全部子变体）上重复了几十次，没有一次因为"这次先不还原，等会儿一起处理"而产生跨任务的状态污染，是本阶段全程零"意外触发不在测试范围内的额外容器/报错"的直接原因（唯一一次真实撞到"额外触发"是 Task 1c 主动构造出来、并记录成方法论经验的情况，不是意外）。

4. **⭐ 新教训：数字性质的断言（"共有几条/几类"）跟"现有的 X 已经做了 Y"这类事实性断言一样，值得在写下的同时核对源头，不能凭记忆**——这是 §2.4 第 1 条的直接推论，与阶段四 §2.5 的教训同构，值得合并记忆：以后写任何计划/复盘文档，只要出现"共 N 条"/"一共 M 类"这种可数的枚举性断言，最好在落笔的同时快速核对一次真实来源（源代码、上游文档、或者自己即将罗列的那份清单本身数一遍），不要假设自己记的数字是对的。
