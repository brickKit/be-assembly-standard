# brickKit 提问：外壳"按需跳过未激活成员"的机制，想请你们用真实外壳验证一下

> **这份文档是一次性的**：只针对 `servedBy` 设计的一个具体细节确认，判断完之后可以直接删掉，跟 `给brickKit的反馈.md` 那份长期文档性质不一样——学的是你们自己那份"回复"文档的做法。

## 背景

`2026-09-13-shell-served-by-design.md` 定稿之后，我们（brickKit 这边）在准备开工前想到一个场景，想请你们用真实的 Go/Python 外壳启动器验证一下这个设计是否可行。

**场景**：某个组件 `mdm/customer` 被 `servedBy: infra/shell-go-core`，同时它是别的组件的**弱依赖**。本地开发时，如果当前没有任何在跑的组件真的需要这个弱依赖，cascade 会把它判定为"不跑"，`brickkit sync` 会把它的源码目录归档——这整套判定完全独立于 `servedBy`，是 brickKit 现有的既有行为（`brickkit sync` 只挪源码目录，从不改 `brickkit.yaml`，参见 AGENTS.md §9.17）。

**问题**：外壳镜像是静态编译的，`mdm/customer` 的代码已经打包进 `infra/shell-go-core` 镜像里。cascade 判定它"不跑"之后，`servedBy` 这条设计目前只会让**平台不再给它生成 `*_ENDPOINT`**（依赖它的组件正确地拿不到这个地址，符合弱依赖语义）——但外壳进程自己完全不知道这件事，如果外壳启动逻辑是"把编译进去的模块全部启动"，`mdm/customer` 的代码、它的数据库连接、可能还有迁移逻辑，照样会在本地跑起来，只是没人能连上它。这没有正确性问题，但如果本地移除一个弱依赖成员的本意是省资源，这个设计目前达不到这个效果。

## 我们想加的东西

在外壳容器上额外注入一个新的保留变量：

```
BRICKKIT_SERVED_MEMBERS=mdm-customer-1-0-7,erp-inventory-2-0-0
```

值是**这次生成时 cascade 判定为运行中的所有 `servedBy` 成员的版本化服务名**，逗号分隔，直接来自 `internal/shell.Resolve` 已经算出来的成员列表，不需要新的计算逻辑。

这条约定**完全可选**：外壳实现者可以选择在启动时读这个变量，跳过初始化任何编译进去、但不在这个列表里的模块（包括跳过它的迁移、跳过打开它的资源连接）；不读也没有任何后果，只是拿不到"本地移除弱依赖成员真的省资源"这个好处。平台不会检查外壳有没有真的照做——跟 `labels` 透传（AGENTS.md §9.22）是同一个哲学：平台只是把它已经知道的信息交出去，不强制、也不理解外壳拿它做了什么。

我们会把这条写进九条实现者指南的第 10 条，作为推荐做法。

## 想请你们确认的具体问题

1. **值的格式**：逗号分隔的版本化服务名（`mdm-customer-1-0-7`）够用吗，还是你们的启动器更适合别的格式（比如 JSON 数组、换行分隔）？
2. **读取时机**：你们的 Go/Python 外壳启动器目前是怎么组织"启动哪些模块"这个决策的？这个变量插进去，是不是能在你们现有的启动流程里自然地用上，还是会跟你们已有的某种机制（比如 `be-ops` 产出的那份 JSON）产生冲突或者重复？
3. **变量名**：`BRICKKIT_SERVED_MEMBERS` 这个名字有没有跟你们现有环境变量撞车，或者有更好的命名建议？

只针对这一个细节确认，不需要展开成新一轮完整评审。确认完我们就会把这条写进 spec 开工。
