# 实测踩坑记录

> **这份文档只管一件事**：写代码/配置时"看起来对、`compose config` 或类似静态检查也通过、一跑起来才发现不对"的坑。
>
> 不放这里的东西：
> - **设计决策**（为什么选这个架构）→ 设计书
> - **给部署人员的操作步骤**→ `docs/ops/部署手册.md`（它的故障表是给部署人员看的"症状→怎么办"，本文档是给开发者/AI 看的"根因→为什么"，两边可以有重复条目，一个简一个详，不用互相替代）
> - **AI 助手的项目级禁令**（21 条最容易写错的那种）→ 根 `AGENTS.md`
>
> 每条固定四栏：**症状 / 根因 / 怎么改 / 发现于**。按类别分组，新条目加进对应类别，没有合适类别再开一类。

## 类别 E：本地测试与真实部署共用基础设施时的干扰

> 这类坑的共同点：`go test` 单独跑、只看断言结果时"全绿"，但断言其实读到的是**另一个进程**（同一台机器上真实跑着的容器）写下的数据，不是被测代码自己产生的——本仓库的 `TEST_PG_DSN`/`TEST_NATS_URL` 约定让本地测试进程与 `brickkit up` 起的真实容器共用同一个 Postgres/NATS，这是"真机验证优先于 mock"的代价之一，不是这套约定本身错了。
