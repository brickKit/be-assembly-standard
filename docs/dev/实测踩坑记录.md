# 实测踩坑记录

> **这份文档只管一件事**：写代码/配置时"看起来对、`compose config` 或类似静态检查也通过、一跑起来才发现不对"的坑。
>
> 不放这里的东西：
> - **设计决策**（为什么选这个架构）→ 设计书
> - **给部署人员的操作步骤**→ `docs/ops/部署手册.md`（它的故障表是给部署人员看的"症状→怎么办"，本文档是给开发者/AI 看的"根因→为什么"，两边可以有重复条目，一个简一个详，不用互相替代）
> - **AI 助手的项目级禁令**（21 条最容易写错的那种）→ 根 `AGENTS.md`
>
> 每条固定四栏：**症状 / 根因 / 怎么改 / 发现于**。按类别分组，新条目加进对应类别，没有合适类别再开一类。

## 类别 B：Docker / Compose 自身的行为，容易被想当然

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| B1 | `required variable POSTGRES_PASSWORD is missing a value`，而 `.env` 文件明明写对了 | Compose 把"第一个 `-f` 指向的文件所在目录"当项目目录（这里是 `infra/`），默认去那里找 `.env`，而我们的 `.env` 在仓库根 | 所有 `docker compose` 调用一律带 `--env-file <仓库根>/.env`。**不要**用 `--project-directory .` 去修——那会让 `./traefik/traefik.yml` 之类的相对挂载也去仓库根找，而 Docker 对不存在的挂载源会默默建一个空目录，症状变成"容器 healthy 但配置是空的" | Task 1 |
| B2 | `docker ps` 里某容器的端口显示成 `9000-9001->9000-9001`，而不是 `9000->9000` | 容器用**端口范围**发布时（如 `-p 9000-9001:9000-9001`），`docker ps --format` 输出的是范围形式。写死 `:$port->` 的正则匹配不到 | 正则改成 `:$port(-[0-9]+)?->`，允许可选的范围后缀 | Task 2（`port_owner`） |
| B3 | `ss -ltnp` 查到端口被占，但进程名那一列是空的 | `ss -p` 对不是当前用户拥有的进程（如 root 起的 docker-proxy）**静默拿不到名字**，这是 `ss` 的权限模型，不是报错 | 区分"查到监听但拿不到名字"与"完全没查到"，前者提示"权限不足看不到名字，试 sudo ss -ltnp" | Task 2（`port_owner`） |
| B4 | `make check` 失败时 `$?` 是 `2`，不是脚本自己 `exit 1` 那个值 | GNU Make 的约定是"recipe 出错就返回 2"，不透传子进程的原始退出码 | 两者都是非零，`&&`/`||` 链式判断不受影响；**不要**写死 `[ "$?" -eq 1 ]` 去判断某个 `make` 目标的结果——要判就判非零，或者直接调用底层脚本拿到它本来的退出码 | Task 2 |

## 类别 C（续）

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| C2 | `registry-check.sh` 报 `端口重复：9000: _infra-rustfs _infra-minio` 和 `非 frontend 组件占用 80：_infra-traefik`/`_infra-nginx`，而这两对根本没冲突 | 去重规则是在"带外容器段"加进 `ports.tsv` 之前写的，没考虑到 `_infra-*` 行之间本来就是**互斥替换件**（rustfs/minio 都是存储、traefik/nginx 都是网关，两两永不同时跑），字面意义上共用端口是设计如此 | 判据改成"冲突双方只要有一个不是 `_infra-` 前缀才算真冲突，两边都是 `_infra-` 就跳过"。已用一次故意改坏 `ports.tsv`（把某组件端口改成和带外资源撞车）反向验证：**真冲突依然能被抓出来**，不是把检查整个关掉了 | Task 4 |
| C3 | `be-ops registry check --root /path` 总是校验当前目录（`.`）而不是 `--root` 指定的路径，不报错，只是悄悄用错了根目录 | Go 的 `flag.Parse` **遇到第一个非 flag 参数就停止解析后续 flag**。子命令词 `check` 排在 `--root` 前面（`args = ["check", "--root", "/path"]`），`fs.Parse(args)` 一读到 `"check"` 就当成"没有更多 flag 了"，`--root` 从未被解析到，`root` 停留在默认值 `"."` | 子命令词必须在调用 `fs.Parse` 之前手工摘掉：先判断 `args[0] == "check"`，再 `fs.Parse(args[1:])`。写多命令 CLI 时，任何"动词 + flag"的组合都要注意这一点，不能指望 flag 包自己跳过动词 | Task 8（`cmd/be-ops/main.go`） |
| C4 | 铁律六扫描器最初实现（只在"当前装配根下已知的组件仓库映射表"里查 import 路径）会漏掉计划给的测试用例 3：`import "github.com/brickKit/be-common-model"` 没有对应的 `components/*/go.mod`，扫描器判定"查无此仓库"从而放行 | 把判据错误地理解成"这条 import 指向的是不是我认识的另一个组件"，而铁律六真正要禁的是"任何指向 `github.com/brickKit/` 组织、又不在 `be-sdk-*` 白名单里的 import"——被抽出去的"公共 model 包"往往根本不是本次装配里的组件（可能是完全独立的第三方仓库），永远不会出现在 `components/` 下，靠"认不认识"来判定必然漏检 | 判据改成：命中 `github.com/brickKit/` 前缀 + 不在白名单 + 不是自己 module 本身，就判违规；"认识哪个组件"只用来给违规的 `To` 字段挑一个好看的标签，不参与放行判断 | Task 9（`gates.ImportScan`） |
