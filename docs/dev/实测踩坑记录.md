# 实测踩坑记录

> **这份文档只管一件事**：写代码/配置时"看起来对、`compose config` 或类似静态检查也通过、一跑起来才发现不对"的坑。
>
> 不放这里的东西：
> - **设计决策**（为什么选这个架构）→ 设计书
> - **给部署人员的操作步骤**→ `docs/ops/部署手册.md`（它的故障表是给部署人员看的"症状→怎么办"，本文档是给开发者/AI 看的"根因→为什么"，两边可以有重复条目，一个简一个详，不用互相替代）
> - **AI 助手的项目级禁令**（21 条最容易写错的那种）→ 根 `AGENTS.md`
>
> 每条固定四栏：**症状 / 根因 / 怎么改 / 发现于**。按类别分组，新条目加进对应类别，没有合适类别再开一类。

## 类别 A：第三方镜像的实际行为，和文档/直觉不一致

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| A1 | `be-nats` 反复重启，日志是 nats-server 的用法说明（`flag provided but not defined: -max_payload`） | `--max_payload` **不是 nats-server 的 CLI 参数**（`--help` 里没有），只能写配置文件。塞进 `command:` 数组会被当成未知 flag，打印用法后退出，`restart: unless-stopped` 让它死循环 | 新增 `infra/nats/nats.conf`（只放 `max_payload: 8MB` 一行），`command` 里加 `-c /etc/nats/nats.conf`，`--jetstream`/`--store_dir`/`--http_port` 三个是合法 CLI flag 不用搬。已验证 `GET /varz` 里 `max_payload=8388608` | Task 3 |
| A2 | `be-otel`/`be-loki`/`be-tempo` 全部 `unhealthy`，日志 `exec: "/bin/sh": stat /bin/sh: no such file or directory` | 这三个镜像**没有 `/bin/sh`**（`grafana/prometheus` 是完整系统镜像，健康检查一次就过）。`CMD-SHELL` 形态的健康检查需要 shell 去解释命令，没有就必然失败。`otelcol-contrib` 二进制自己也没有内建的 healthcheck 子命令 | 这三个 service **不定义 `healthcheck`**——Compose 的 `--wait` 对没有健康检查的服务只等到 `running` 就放行。想确认真的活着，从宿主机侧 `curl`（宿主机有 curl，容器里没有）：`:13133/`、`:3100/ready`、`:3200/ready` | Task 3 |
| A3 | 修完 A2 之后，`curl :3100/ready` 短暂返回 503，body 是 `"Ingester not ready: waiting for 15s after being ready"` | **不是 bug**：Loki 单体模式下 ingester 加入 ring 之后，官方文档记录的 `min_ready_duration` 会让它再等约 15 秒才报 ready，给 ring 状态收敛留缓冲 | 等 15–20 秒重新 `curl`，会变成 `ready`。不需要重启、不需要改配置 | Task 3 |
| A4 | Casdoor 反复重启，`panic: pq: password authentication failed`，而 PostgreSQL 自己 healthy | beego 的 `ExpandValueEnv` **只在"整个配置值就是一个 `${VAR}`"时才展开**；写成 `"user=... password=${POSTGRES_PASSWORD} host=..."`（嵌在字符串中间）那段是字面量，不会被替换 | 整串 DSN 由 compose 拼好（compose 自己的插值没有这个限制），作为一个变量 `CASDOOR_DSN` 注入，`app.conf` 里只写 `dataSourceName = ${CASDOOR_DSN}` | Task 1 |

## 类别 B：Docker / Compose 自身的行为，容易被想当然

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| B1 | `required variable POSTGRES_PASSWORD is missing a value`，而 `.env` 文件明明写对了 | Compose 把"第一个 `-f` 指向的文件所在目录"当项目目录（这里是 `infra/`），默认去那里找 `.env`，而我们的 `.env` 在仓库根 | 所有 `docker compose` 调用一律带 `--env-file <仓库根>/.env`。**不要**用 `--project-directory .` 去修——那会让 `./traefik/traefik.yml` 之类的相对挂载也去仓库根找，而 Docker 对不存在的挂载源会默默建一个空目录，症状变成"容器 healthy 但配置是空的" | Task 1 |
| B2 | `docker ps` 里某容器的端口显示成 `9000-9001->9000-9001`，而不是 `9000->9000` | 容器用**端口范围**发布时（如 `-p 9000-9001:9000-9001`），`docker ps --format` 输出的是范围形式。写死 `:$port->` 的正则匹配不到 | 正则改成 `:$port(-[0-9]+)?->`，允许可选的范围后缀 | Task 2（`port_owner`） |
| B3 | `ss -ltnp` 查到端口被占，但进程名那一列是空的 | `ss -p` 对不是当前用户拥有的进程（如 root 起的 docker-proxy）**静默拿不到名字**，这是 `ss` 的权限模型，不是报错 | 区分"查到监听但拿不到名字"与"完全没查到"，前者提示"权限不足看不到名字，试 sudo ss -ltnp" | Task 2（`port_owner`） |
| B4 | `make check` 失败时 `$?` 是 `2`，不是脚本自己 `exit 1` 那个值 | GNU Make 的约定是"recipe 出错就返回 2"，不透传子进程的原始退出码 | 两者都是非零，`&&`/`||` 链式判断不受影响；**不要**写死 `[ "$?" -eq 1 ]` 去判断某个 `make` 目标的结果——要判就判非零，或者直接调用底层脚本拿到它本来的退出码 | Task 2 |

## 类别 C：本仓库脚本自己的逻辑漏洞

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| C1 | `make obs-up` 报"端口已被占用"，但占用者正是它自己要用的那个容器 | `optional.sh` 的端口预检**没有先判断容器是否已存在**就直接查端口——容器已存在时它自己发布的端口被当成"被别人占用"。`check.sh`/`up.sh` 都遵循"容器存在就交给 compose 处理，只有不存在时才查端口"，`optional.sh` 漏了同一条 | 加一行 `docker inspect "$cont" >/dev/null 2>&1 && continue`，跳过已存在的容器 | Task 3（复现方式：改坏 nats/otel 配置后重跑 `obs-up` 才暴露） |

## 类别 C（续）

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| C2 | `registry-check.sh` 报 `端口重复：9000: _infra-rustfs _infra-minio` 和 `非 frontend 组件占用 80：_infra-traefik`/`_infra-nginx`，而这两对根本没冲突 | 去重规则是在"带外容器段"加进 `ports.tsv` 之前写的，没考虑到 `_infra-*` 行之间本来就是**互斥替换件**（rustfs/minio 都是存储、traefik/nginx 都是网关，两两永不同时跑），字面意义上共用端口是设计如此 | 判据改成"冲突双方只要有一个不是 `_infra-` 前缀才算真冲突，两边都是 `_infra-` 就跳过"。已用一次故意改坏 `ports.tsv`（把某组件端口改成和带外资源撞车）反向验证：**真冲突依然能被抓出来**，不是把检查整个关掉了 | Task 4 |

## 类别 D（续）

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| D0 | 计划里所有 `go.mod` 示例都写 `go 1.22`，但 `go mod tidy` 把 `be-sdk-go` 的 `go.mod` 自动改成了 `go 1.25.0` | `go 1.22` 从来不是一条论证过的锁定决策（设计书 §12.4 只锁框架选型，没锁 Go 语言版本的具体补丁号），只是计划文档里 go.mod 示例代码顺手写的数字，**从没针对真实依赖版本核实过**。而 gin/grpc/otel/prometheus/nats.go 的**最新版**全部要求 `go >= 1.25`（逐个查了这几个库最近几个版本的 `go.mod`：gin v1.10.x 还只要 1.20，v1.11.0 跳到 1.23，v1.12.0 到 1.25.0——是**整个生态在过去一年逐步抬高门槛**，不是某一个库的个例） | 采用 `go 1.25` 作为项目实际锁定版本（本机已装 Go 1.26，工具链自动匹配，成本为零；换成旧版依赖库换取 1.22 反而损失安全补丁，没有任何好处）。已修正计划文件里全部 4 处 `go 1.22` 示例。**这条会影响全部 62 个 Go 组件的 `go.mod` 与阶段四的 `go.work`**，写新组件时不要再照抄旧版计划文本里的 `1.22` | Task 6 |

## 类别 D：计划文档本身写的验证步骤，和实际环境/实现对不上

> 这类不是代码 bug，是"计划写的时候环境是 A，跑到这一步环境已经变成 B"，或者"计划假设了一个从没被创建的东西"。按 `docs/README.md` 的规矩，操作层跑不通就不该迁就理论层——已经把计划本身的验证步骤改成实测过的版本。

| # | 计划里写的 | 实际情况 | 改成什么 | 发现于 |
|---|---|---|---|---|
| D1 | 期望 `make check` 报 `postgres`/`rustfs` 端口被 `my-postgres`/`my-rustfs` 占用 | 那两个冲突在 Task 1 已经解决（容器已停），照抄旧期望值会让人对着不会再发生的现象核对 | 改成两个可控复现（临时启动已停容器 / 临时停掉一个健康容器），不依赖机器当时凑巧处于什么状态 | Task 2 |
| D2 | 验证语义 3 要跑 `make rustfs-down`，期望报"默认资源"错误 | 这个 Makefile 目标从没被创建过——默认资源本来就不该有单独的 `-down` 目标（停一个不停别的没有意义） | 改成直接测 `bash infra/scripts/optional.sh rustfs down`，验证守卫逻辑本身 | Task 3 |
