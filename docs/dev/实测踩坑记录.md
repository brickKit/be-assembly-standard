> **这份文档只管一件事**：写代码/配置时"看起来对、`compose config` 或类似静态检查也通过、一跑起来才发现不对"的坑。
>
> 不放这里的东西：
> - **设计决策**（为什么选这个架构）→ 设计书
> - **给部署人员的操作步骤**→ `docs/ops/部署手册.md`（它的故障表是给部署人员看的"症状→怎么办"，本文档是给开发者/AI 看的"根因→为什么"，两边可以有重复条目，一个简一个详，不用互相替代）
> - **AI 助手的项目级禁令**（21 条最容易写错的那种）→ 根 `AGENTS.md`
>
> 每条固定四栏：**症状 / 根因 / 怎么改 / 发现于**。按类别分组，新条目加进对应类别，没有合适类别再开一类。

## 类别 F：Git 本身的行为，和直觉不一致

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| F1 | 建好 `infra-authz` 仓库并 `git submodule add` 挂载后，核对 `git submodule status` 时 `tools/be-sdk-go` 显示成 `(v0.1.7-3-g3521e4c)`——像是 HEAD 领先最新 tag 3 个提交，而 `bash infra/scripts/version-check.sh`（用的是 `git describe --tags`）明明报告它就在 `v0.1.9`，两个命令对同一个仓库给出不一致的答案 | **`git submodule status` 内部调用的是不带 `--tags` 的 `git describe`**，这个变体只认**带注解的 tag**（`git tag -a`），完全忽略轻量 tag（`git tag vX.Y.Z`）。`tools/be-sdk-go` 的 `v0.1.6`/`v0.1.7` 当初是带注解打的，但 `v0.1.8`/`v0.1.9` 是后来某次会话手滑打成了轻量 tag——HEAD 精确落在 `v0.1.9`（轻量）这个提交上，但 `git describe`（不带 `--tags`）看不见它，只能找到 3 个提交之前那个带注解的 `v0.1.7`，于是拼出 `v0.1.7-3-g3521e4c`。`components/erp/finance` 当时也处于同一种状态（`v1.0.0`/`v1.0.1` 全是轻量 tag），但因为它的历史里**一个带注解的 tag 都没有**，`git describe` 直接整体失败，`git submodule status` 在这种"完全找不到"的情况下会退化去试 `--tags` 兜底，反而显示正常——**"历史上有没有任何一个带注解的 tag"这个看似无关的因素，决定了同一类问题会不会在 `git submodule status` 里表现出来**，纯轻量 tag 的仓库反而歪打正着不受影响 | 把 HEAD 所在的这个 tag 删掉重打成带注解的（`git tag -d vX.Y.Z && git tag -a vX.Y.Z <同一个 commit> -m "..."`），强制推送替换远端的 tag（`git push origin :refs/tags/vX.Y.Z && git push origin vX.Y.Z`）——commit SHA 不变，父仓库 submodule 记录的指针不用动。**`version-check.sh` 已经补一条判据**（`git cat-file -t <tag>` 必须是 `tag` 不能是 `commit`）防止同类漂移再次不被发现；这条检查关心的是**任意时刻 HEAD 落在的那个 tag 本身够不够格**，不去追溯清理历史上更早的轻量 tag（那些不影响 `git submodule status` 当前的显示） | Task 4（`infra-authz` `git submodule add` 之后核对 `git submodule status` 时发现，真的对比了两个命令的输出、查了 `git submodule--helper` 的 describe 调用方式，不是猜的） |

## 类别 G：对 brickKit 平台自身能力的误判——第一次判断错了，读完调用链才发现想错了方向

> 这类坑和前面几类**方向相反**：不是"看起来对、跑起来才发现不对"，而是"第一次快速核对（grep 一下、读一两个文件）觉得平台不支持某个能力，实际顺着调用链读完才发现平台原生就支持，而且往往支持得比我们以为的更完整"。放这里是因为它和前面几类同样危险——按错误的"平台不支持"结论去设计绕行方案（比如把真实密钥直接写死进 `brickkit.yaml`），后果同样是不可逆的（密钥进了 git 历史）。

| # | 症状 | 根因 | 怎么改 | 发现于 |
|---|---|---|---|---|
| G1 | `infra-iam-casdoor` 需要三项真正敏感的 `brickkit.yaml` 级配置（`casdoorAdminPassword`/`webhookSharedSecret`/`appTokenSigningKeyPem`）。第一次核对时只在 `internal/config` 目录下搜了一遍 `ExpandEnv`/`envsubst`/`${VAR}`，**没搜到就直接下结论**"brickKit 不支持 config 字段的环境变量展开"，打算写真实值进 `brickkit.yaml`（一份被 git 追踪的文件）或者放弃整机验收，甚至已经写了一条"给 brickKit 提功能反馈"的草稿文档 | 第一次核对**只看了有没有搜到关键字，没有验证"搜不到"是不是因为搜错了范围**——展开逻辑其实就在同一个 `internal/config/parse.go` 里（`ExpandEnv`/`expandEnvNode`），只是没被第一轮 grep 命中。往下读才发现这不只是"支持"，而是**专门为 `components[].config` 做了一整套配套机制**：`configEnvRefs()` 在展开前专门记录哪些 config 项写的是 `${VAR}`（存进 `Component.ConfigFromEnv`，和 `resources[].password` 的 `PasswordFromEnv` 对称）；`internal/cli/up_secrets.go` 还有一条专门扫描 `config` 里"看起来像密钥的键名"（含 `password`/`secret`/`token`/`credential`/`privatekey`/`apikey`/`accesskey` 子串）**若未写成 `${VAR}` 就主动告警**的功能（brickKit 内部编号"35.17"，`design/008-安全与治理.md` §12.5/§12.6 有文档）。真机验证：`casdoorAdminPassword`/`webhookSharedSecret`/`appTokenSigningKeyPem` 全部命中告警的关键字列表，写成 `${VAR}` 之后 `brickkit up --dry-run` 确认零告警；真实部署确认三个值都从 `.env` 正确展开进了容器（`docker exec` 能看到真实的 RSA 私钥、密码），且展开只发生在被 `.gitignore` 排除的 `.brickkit/generated/docker-compose.yaml` 里，`.brickkit/manifests/`/`.brickkit/artifacts/`（这两个目录本身是刻意提交进 git 的）只含 `configSchema` 的**声明**，不含任何解析后的真实值 | 已删除那份错误的"给 brickKit 提反馈"草稿（草稿本身没有提交，及时发现）。**这条提醒**：核对"平台支不支持某个能力"时，grep 一两个关键词没搜到**不能直接下结论**——要么换更宽的检索范围重搜，要么直接读一遍那个功能理应所在的源文件（本例是 `internal/config/parse.go` 整个文件，而不是搜 `ExpandEnv` 这一个符号名）；朝着"平台不支持"这个方向下结论时，代价往往是"绕开平台去发明一个更笨的办法"，而这个例子里更笨的办法（明文写密钥进 git）后果是不可逆的 | Task 7（`infra-iam-casdoor` 敏感配置怎么处理，用户主动要求"以防万一"复核后，读 `internal/config/parse.go`/`internal/cli/up_secrets.go` 源码发现） |
