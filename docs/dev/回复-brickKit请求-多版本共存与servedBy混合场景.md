## 结论先说

## 场景一：同一个组件两个版本，一个独立部署、一个被外壳收编

**"非外壳那一半"（`legacy/caller`/`new/caller` 各自拿到正确版本的地址）已经真机验证通过，并且固化成了永久断言**——这一半完全不依赖 `servedBy`，用的是"精确版本+版本化服务名"这个你们已有的机制，本机装的是你们的正式版 `brickkit`（v0.2.2）就能验证。真实生成的 compose 片段：

```yaml
legacy-caller-1-0-0:
  environment:
    - FOO_BAR_ENDPOINT=http://foo-bar-1-0-0:19001
new-caller-1-0-0:
  environment:
    - FOO_BAR_ENDPOINT=http://foo-bar-2-0-0:19004
```

跟你们的预判逐字一致。已经写成 `TestPlatform26_同一个组件ID两个精确版本同时声明地址互不干扰`（`tools/be-acceptance/platform/h_test.go`，`be-acceptance@v0.3.17`）。

一次没命中的尝试，记下来免得你们的用户也踩：最初把两个版本的 `component.yaml` 内容分别写 1.0.0/2.0.0，但都放在同一个 local 源目录里（先后覆盖着写）——`brickkit up` 直接报 `COMPONENT_NOT_FOUND`（"安装源里有这个组件，但版本不是要的那个"）。根因很直接：一个 local 源的一个组件目录物理上只能同时存在一份 `component.yaml`，天然只服务一个版本。正确做法是两个独立的源目录，各自只放一个版本——这条不算你们的问题，是我们自己第一次没想清楚 local 源的物理限制，但既然是"真实会撞上的坑"，建议在文档里提一句更好。

**"外壳那一半"（真正走 `servedBy` 的地址重定向）现在还测不了**——真机确认过：即使 `servedBy` 字段写对、通过静态校验，`up --dry-run` 现在仍然会给这个组件生成一份独立的 compose service（`internal/shell.Resolve` 还不存在，这个字段暂时对生成结果零影响）。这不是 bug，是当前开发阶段的真实边界，等你们做到这一步再补验证。

## 场景二：同一个外壳同时收编同一个组件的两个版本——结构性不可行，不需要靠运行去证明

这条我们没有去"跑"，因为它是 Go 语言工具链本身的既有语义，不需要可执行验证：

- `go.mod` 的 `require` 指令按 module path 精确匹配，一次编译里一个 module path 只能解析到唯一一个版本。
- 真机确认过：`mdm/customer`（以及我们全部真实组件）的 `go.mod` 都是裸 `module github.com/brickKit/mdm-customer`，没有用 Go 的语义化导入版本（`/v2` 后缀）写法。
- 即使想用这条机制，它也只在**主版本号**边界生效（需要组件作者主动把 module path 改成 `.../v2`），`1.0.7`→`2.0.0` 这种数字变化不会自动触发它。

结论：**一个 Go 外壳镜像物理上做不到同时静态编译进同一个组件的两个版本**——不止我们，任何用 Go 写外壳、且组件不主动采用语义化导入版本的用户都会撞上同一个限制。建议在指南里明确写这条边界（"两个版本的同一组件应该分别收编进两个不同的外壳镜像"），而不是留给用户自己在真机上撞一次才发现。这条限制大概率对其它静态编译/静态链接的语言（Rust、C++ 这类）同样成立，只是我们没有对应的组件去验证，不能替你们下结论，只确认了 Go 这一个语言。

## 场景三：同一个 ID 同一个精确版本重复声明——确认属实

真机复现，`CONFIG_INVALID`，"重复声明了 foo/bar@1.0.0"——跟你们的预判完全一致。同样固化成了永久断言 `TestPlatform27_同id同精确版本重复声明直接拒绝`。

## 额外顺手验证的：5 条 `servedBy` 静态校验（用你们仓库当前 HEAD 临时构建）

你们仓库最新提交（"新增 servedBy 字段与静态校验"）已经实现了 `internal/config/validate.go` 的 `validateServedBy`，虽然还没打 tag、本机安装的正式版里没有——我们从源码临时 `go build` 了一个开发版二进制（没有替换本机安装的正式版），真机跑了这 5 种情况，全部按设计正确报错：

1. `servedBy` 与 `local: true` 同时声明在同一个组件上 → 报错，措辞清楚。
2. `servedBy` 指向的目标本身是 `local: true` → 报错，措辞清楚。
3. 链式嵌套（外壳被另一个外壳收编）→ 报错，措辞清楚。
4. 格式错误（`servedBy` 没写 `@版本`）→ 报错，指出正确格式。
5. 自引用 → 报错。

顺带确认一条你们大概率已经知道、但值得写下来的现状：`servedBy` 指向一个根本不存在的组件 ID（比如拼错了）现在**不会报错**——这条检查按你们自己的设计说明本来就在 `internal/shell.Resolve`（存在性判断需要依赖图+cascade 结果），不在当前这批静态校验的范围内，不是遗漏。

这 5 条我们没有写进 `be-acceptance` 的永久断言——正常环境里没有这个开发版二进制，写了也是全员 SKIP。真实的命令与完整输出记录在我们自己 `docs/plans/04b-部署矩阵验证.md` 的 Task 1.2 里，等你们正式发布带 `servedBy` 的版本、我们把本机 `brickkit` 升级上去之后，会正式把这 5 条也补进永久断言。
