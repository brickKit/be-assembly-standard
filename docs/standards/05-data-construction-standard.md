# BrickEnterprise Data Construction Standard

This specification defines everything about "where data comes from" in this project. Data splits into two completely independent paths — **seed data** (`make seed`, for a human to explore/demo with) and **test data** (built by automated tests themselves, for `go test`/`pytest`) — physically isolated, with different lifecycles, never shared. Behind both paths sits the same philosophy: data should cover as many scenarios as possible, and when a cross-component need or capability doesn't exist yet, fix it at the source instead of working around it. This document explains both paths in full, and the principles they share.

---

## 1. The Two Paths: Definitions, Lifecycles, Why They're Never Shared

| Mechanism | Used for | How data is produced | Lifecycle | Can it be shared? |
|---|---|---|---|---|
| **Test-built data** (unique suffix) | All automated tests: backend L1–L4, frontend FE-1–4 | Built fresh on every test run, disambiguated with a timestamp/random-number suffix | Never cleaned up — accumulating in the database is fine (next run gets a fresh unique suffix anyway) | **Never.** No automated test should ever depend on "this row was left behind by another test or another run" |
| **Seed/demo data** (`make seed`) | Humans: local exploration, demos, giving a new component data to work with out of the box | A fixed `idempotency_key`, claim-first idempotent — rerunning doesn't rebuild it | Persistent, can be wiped wholesale (`make seed-clean` or `make db-reset`) | Components may look each other up and reuse it (§4), but it must **never be depended on by an automated test** |
| **Data built on the fly for cross-component tests** | Cross-component integration tests (this component making real calls to real dependencies) | The test process makes real gRPC/REST calls, building the needed shape of data for real inside the dependency component | Same rule as single-component test-built data: unique suffix, no cleanup | Same as above — not shared with, and not dependent on, seed data |

⚠️ **Wiping seed data should never turn any automated test red, and automated-test data should never contaminate the seed data a human is exploring by hand.** The moment these two paths get mixed up, "why did this test suddenly turn red" becomes extremely hard to diagnose — it could be that someone wiped the seed data, or that someone else's test ran and didn't clean up, and the two causes require completely different investigation paths. Keeping them mutually independent removes the problem at the root.

**They are physically two databases, not just logically unshared**: the Postgres/NATS an automated test uses points at a database/message channel dedicated to testing (`brickkit_test_db`, created/refreshed by `make test-db-init`), which is a physically separate database inside the same database instance as the one used for human exploration/demos (`brickkit_db`) — the two mirror the same schema structure, but their data never touches. This isolation isn't over-engineering — a real problem actually happened: some components' integration tests genuinely write to shared reference rows pre-loaded by the database's init scripts (baseline data like a default warehouse or a default legal entity), and if the test database and the demo database were the same physical database, running a test once would really mutate the demo data — a human exploring the app would see data change for no apparent reason. This problem has nothing to do with "whether a container happens to be running" — it's a data-persistence-layer problem, not a runtime-concurrent-access problem, and stopping the container doesn't dodge it.

**Why not use a "throwaway database"** (the H2/Testcontainers style of approach): this project's partitioned tables and hard DDL like `SET LOCAL ROLE`/`search_path` session-level settings don't fit inside a lightweight embedded engine, and that style of approach is fundamentally swapping in a different database implementation — which directly conflicts with the principle that "an integration test's criterion is real infrastructure." The real fix for "rebuilding data repeatedly is slow and causes cross-contamination" isn't swapping in a throwaway database — it's **making the data itself disposable**. The existing "unique suffix + no cleanup" pattern is the correct shape of this path without introducing a throwaway database — it isn't a stopgap, it's how this should look for the long term.

## 2. General Principle: Regardless of the Path, Data Should Cover as Many Scenarios as Possible

This principle holds for both seed data and test data — only the way "coverage" is achieved differs:

- **Seed data** aims for "many and complete" — every state machine, every branch, every failure path, every data-scope dimension should have data that can genuinely trigger it, because seed data is simultaneously serving "can a human fully experience this system" — volume and variety are themselves the goal.
- **Test data** aims for "few and precise" — each test only needs the minimum data **exactly sufficient to verify this one specific assertion**; there's no need to pile on volume for the sake of "richness" itself. The exception is business-rule tests for core transactional components (invariants, state-machine transition edges): these need a property-based testing framework to generate large volumes of random boundary inputs that actively attack the implementation — the "many" here is about maximizing the chance random inputs hit boundary conditions, a different purpose from seed data's "many and complete," and the two shouldn't be conflated.

These are not a "rich version" and a "lean version" of the same thing — they're two data sets that serve different purposes and are naturally meant to look different. But the floor is the same for both: **no component should have only the "everything's fine" kind of data or assertion.** Every state of a state machine, every failure branch, every data-scope dimension — whether it's seed data or test data — must never cover only the happy path.

## 3. Cross-Component Collaboration: What to Do When a Dependency Doesn't Have the Data/Capability You Need

This is the most important judgment criterion in this specification, applying to both seed data and test data — only the concrete action differs.

### 3.1 The Automated-Test Scenario

When writing a cross-component integration test that needs a dependency component to produce some shape of data (say, "a customer with a zero credit limit," "a disabled product," "an opportunity in some specific stage"):

1. **Prefer producing it on the spot through the dependency component's real RPC/REST interface.** Calling `CreateCustomer` with `credit_limit=0`, or calling `SetStatus` to flip it to `DISABLED`, are both real, existing commands the test can call directly — no pre-existing data required.
2. **If the dependency component's real contract simply has no capability to produce this shape of data** (no matching field, no matching state transition command, no matching combination), **the correct move is to add that capability to the dependency's contract/implementation first, and produce the data through a real call — not to work around it, insert directly into its database with raw SQL, or simply skip testing this scenario.** Adding the capability still has to follow the normal rules of contract evolution (additive only, backward compatible) — this isn't a one-off stopgap, it's filling out the dependency component's own completeness, and every future test and every future caller benefits from it.
3. **Writing directly into a dependency component's database with raw SQL is always the last resort, and is disallowed in automated tests as a matter of principle.** The whole point of a cross-component boundary is "interaction only through the contract," and test code is no exception — writing directly into someone else's database quietly establishes a coupling outside the contract. No matter how the contract changes afterward, this test will never sound an alarm about it — it will simply break later, in some other, much harder to diagnose way, once the contract actually changes.

### 3.2 The Seed-Data Scenario

**A downstream component can, and should, proactively ask an upstream component to enrich its data — not passively wait.** If a component doing a demo or a test needs some data combination (say, "a customer belonging to the South China department with status `DISABLED`") that the upstream component's seed data doesn't yet have, the right move is to **go directly into the upstream component's own seed-data generation logic and add that combination** — not to work around it downstream and make do with what's there, and not to sit around waiting for "someone to add it eventually." The data is fake, adding a few more variations costs nothing, and "the upstream data is rich enough that downstream actually has something to pick from" is an active, bidirectional collaboration relationship, not a one-way waiting relationship. This is the same principle as §3.1 applied to a different scenario: **when you need something you don't have, fix it at the provider — don't work around it.**

## 4. Seed-Data-Specific Rules

Seed data (`make seed`) isn't automated-test data, but one of the purposes it serves is exactly "testing" itself — whether a whole business chain runs end to end, whether a new scenario needs to walk through every component to verify — often depends on a human actually opening the running system and walking through it with real data, not on `go test`. This "actually run it, actually click through it" style of verification is just as important as automated testing — it is not a lesser substitute for automated testing.

Every piece of data we have, from start to finish, is simulated — it has never been, and will never be, real. That fact itself should be treated as a freedom: since there's no concern about "contaminating real data," seed-data richness should be pushed toward its upper bound, not economized down to "just enough."

### 4.1 The Goals Seed Data Must Serve at Once — This Determines How to Judge "Rich Enough," Not a Number Picked Out of Thin Air

1. **Perfectly testing all logic**: every state machine, every branch, every failure path needs data that can genuinely trigger it — not just seeding the "everything's fine" case.
2. **Local testing**: when there's a new requirement, it should be possible to verify the new logic against just one component (together with everything it declares as a dependency), without first having to bring up the entire assembly.
3. **Full-chain testing before a component ships**: the entire chain, dependencies included, needs data that can support one real end-to-end call.
4. **All-around testing before a project ships**: once the whole assembly is up, data needs to cover every angle (permission boundaries, cross-component events, compensation logic…).
5. **A "playground" experience for user exploration/demos**: a project with only a handful of rows can't really be experienced — what actually demonstrates a project's completeness is a large number of customers, every kind of role, every department existing at once, so that opening any page at random has something to look at, query, and play with.

### 4.2 Things That Don't Happen Automatically Just from "Lots of Data" — They Need Deliberate Design

- **Data-scope dimensions need a genuine presence**: dimensions like `org`/`owner`/`warehouse` only make "this person can't see someone else's data" a meaningful thing to verify once there really are multiple departments, multiple owners, multiple warehouses in the data. If all the seed data hangs off one all-powerful admin account, the entire data-scoping capability is effectively invisible in the actual experience.
- **Volume needs to be enough to trigger pagination**: if a list endpoint enforces cursor-based pagination, too little seed data (say, only five rows) always fits on one page — pagination as a contract has no real presence in the experience.
- **Time needs to be spread out**: data should be distributed across different points in time, so that "last N days"-style queries, trend charts, and time-partition-based maintenance logic have real scenarios to verify against — not everything sitting at "just created."
- **Negative/edge-case data needs to exist too**: a disabled status, zero inventory, an overdue unsettled balance, a rejected application — failure paths can't be imagined in the abstract; there needs to be real data you can click into and real data you can test against.
- **Data needs to be discoverable**: once the data volume goes up, there needs to be somewhere to look up "what concept does this fixed identifier correspond to," or a new component wanting to reuse existing data has nowhere to look, and risks colliding with it unknowingly. This list lives in [`docs/dev/种子数据一览.md`](../dev/种子数据一览.md) — component/data/quantity/who owns it, all queryable in one place; no need for every component to build its own copy of this.

### 4.3 Redundancy Is Acceptable — Even a Good Thing

All of this data is fake; there's no concern about "contaminating real data." Even when different components' seed data conceptually overlaps (say, two components each independently create a "manufacturing customer" profile), there's no need to work hard to deduplicate — the cost of redundancy is close to zero, and "a large volume of data that looks complete" is itself one of the goals to achieve. When another component needs similar data, directly reusing what already exists is cheaper than coordinating "who should own this data."

### 4.4 Ownership and Collaboration Principles

- **Every component owns and maintains its own seed data**, not centralized at the assembly layer: a centralized script is only usable once every component is up together — starting one component alone leaves it with nothing, which violates the more fundamental principle that "bringing up one component alone, together with its dependency tree, should just work."
- **When a component generates its seed data, the first step is always to make sure everything it declares as a dependency (no distinction between strong and weak) has its seed data ready**, before running its own part. The reason not to distinguish strong from weak: in a dev/demo environment every component is already brought up together — there is no scenario of "only installing part of the dependencies"; and once a dependency relationship is declared, that means this component genuinely needs it — the strong/weak distinction exists for a real customer's deployment-time question of "should I buy this optional module," not something worth agonizing over at development time; drawing that extra distinction here only adds unnecessary mental overhead. This way, triggering seed-data generation against just one component gets you one complete, runnable set of data, with no dependency on any assembly-layer orchestration. If some declared dependency genuinely isn't installed in the current environment (unreachable), skip that step gracefully and just finish seeding its own part — a missing dependency should never cause the whole thing to fail and exit.
- **Between a component's own seed script and an orchestration script that needs the ids it produced, use the component's own idempotency table as the "handoff protocol"**: a component's seed logic is only responsible for getting the data in — it's not responsible for printing ids out in some agreed-upon format. Whoever needs those ids looks them up themselves (by querying that idempotency table with a fixed `idempotency_key` to get the real row id) — no handoff protocol needs to be invented.
- **Seed data is itself a lightweight contract**: once another component has looked up some fixed identifier, that identifier can no longer be casually deleted or have its meaning changed — only new ones may be added, never a modification of one already referenced. When adjustments are needed, use each repository's own git tags to look at history — don't rely solely on the mirrored version number.
- **If a table is "append-only" by nature** (for business or audit reasons — a ledger table, a locked accounting period, say), **it should not have a row-by-row deletion-style undo mechanism at all — it can only be emptied by a full database reset.** A sequence doesn't roll back because rows were deleted; row-by-row deletion can neither achieve a genuinely clean restoration nor does it honor that table's own "append-only" design. The correct tool for this kind of component is `make db-reset` (`migrate down` then `up`) — a genuine reset, not a deletion: it drops every table in the schema and rebuilds from migrations, the sequence really does start at 1 again, and the baseline data seeded by migrations lands again too. **The rule: if a table is append-only, it has no `seed-clean`, only `db-reset`**; a table that can be safely deleted row by row may have both — `seed-clean` is lighter-weight (doesn't touch other data), prefer it.
- **Credentials/identity data that could reach a real customer's deployment must never be mixed into this mechanism**: the moment a test account or a universal password gets written into a database-init script that "runs on every deployment," it permanently buries a backdoor into every real customer's system — the same class of risk as "a production authentication app must never enable a direct password-login grant type." This boundary allows no exceptions:
  - **Genuinely universal baseline/reference data that every deployment needs** (a default warehouse, a default legal entity plus a base chart of accounts, base units of measure) still goes through a migration — this isn't "test data," it's part of the product itself.
  - **The chicken-and-egg question of "how does the first admin get in" for a real deployment is answered by configuration-driven bootstrapping, not seed data**: the first person to log in at a real deployment gets their own real identity fed into a bootstrap config item, and the container idempotently grants the admin role on startup — nobody hand-writes any SQL, and no account is hardcoded anywhere. This mechanism only solves "who is the first admin"; it's a different thing from the "superuser test role holding every permission key" that local testing needs, and the two can't substitute for each other.

## 5. Test-Data-Specific Rules

How test data is generated (unique suffix, no cleanup) and its lifecycle are already covered in §1; this section adds the extra requirements test data has under specific test types:

- **Consumer tests** have two rules of their own — when a test constructs/publishes an event itself to trigger a consumer, use a test-private subject (to avoid competing for messages with a real container running on the same machine); when a dedup table does monotonic deduplication by a unique identifier, the test must use a unique identifier rather than a fixed string (to avoid the dedup logic silently swallowing a second run). These two are execution-level details of "how to write a good consumer test" — full explanation is in [`04-testing-standard.md`](04-testing-standard.md) §3.4.
- **What to do when a cross-component test needs a shape of data that the dependency's real contract can't produce** — see §3.
- Beyond that, test data doesn't need to account for the dimensions specific to §4's seed data (pagination, time spread, discoverability…) — a test only needs to precisely match its own assertion; there's no need to create extra data in service of goals like "experience completeness" that have nothing to do with that particular test.
