# BrickEnterprise 部署选型指南

> **这份文档回答一个问题：这么多种部署方式，我该选哪一种？** 部署手册（[`部署手册.md`](部署手册.md)）回答的是"选定了之后具体怎么做"；这份文档回答的是"选之前要知道什么"——每一种形态是什么、适合谁、好处代价各是什么、真机踩过什么坑。
>
> **怎么读这份文档**：
> 1. 先看下面的矩阵，找到你关心的格子（一般来说，你只需要关心**一个**格子——你打算怎么部署，就是哪一个格子）。
> 2. 矩阵里每个格子都有一句话摘要和跳转链接，点进去看那一节。
> 3. **每一节都是独立、完整的**——不会要求你先读懂别的小节才能看懂这一节。你只看你需要的那一节就够了，不用从头读到尾。
> 4. 看完、想清楚要选哪个之后，去 [`部署手册.md`](部署手册.md) 照着操作。
>
> 如果你还不确定"拓扑"和"环境"这两个词是什么意思，先看下面这一小段——这是看懂矩阵必须知道的最小背景知识。

## 两个独立的选择维度

部署一套 BrickEnterprise，要做两个互相独立的决定：

**第一个决定：拓扑——组件之间要不要合并？**

- **纯独立组件**：每个组件各自一个进程/容器，互相之间走真实网络调用（gRPC/HTTP）。
- **纯外壳**：把多个组件的工作负载合并进同一个进程（我们管这个合并单元叫"外壳"），对外表现还是各自独立的地址，但物理上共享一个进程、一个连接池。
- **组件+外壳混搭**：大部分组件合并进外壳，少数组件（结构上没法合并的，比如纯前端、无状态网关型组件）继续独立部署——这是本项目当前真实的生产部署形态。

**第二个决定：环境——这套东西实际跑在哪？**

- **本地裸进程**：全部组件都是宿主机上的普通进程（`go run`/`uvicorn` 之类），完全不经过容器/编排平台。
- **Docker**：brickKit 平台（`brickkit up`）生成并管理真实的 Docker 容器。
- **K8s**：brickKit 平台对接真实 Kubernetes 集群，生成 Deployment/Service。
- **Docker+本地混合**：绝大部分组件在 Docker 里正常跑着，你单独挑一个组件（通常是你正在改代码的那个）用 `local: true` 拉到宿主机，改代码不用重新 build 镜像，其余组件保持真实运行不受影响。

这两个决定互相独立，可以任意组合——3 种拓扑 × 4 种环境 = 12 种组合，全部都是本项目真机验证过、确认可用的组合，不存在"理论可行但没人试过"的格子。

## 这两个维度背后，其实是一条真实的成长路径

矩阵看起来是 12 个平等的格子，但实际选择起来，拓扑这条线是有真实先后顺序的，不是"12 选 1"随便挑：

**拓扑怎么选，本质上是"规模"和"要不要精细控制每个组件的资源"驱动的：**

1. **规模还小的时候（包括开发阶段），用纯独立组件**——不管是人写代码还是 AI 驱动开发，每个组件各自一个进程，边界最清楚，只需要盯着当前这一个组件，不需要理解合并拓扑。哪怕部署给客户，只要组件数量不多、单机资源够用，也直接用纯独立组件（对应 Docker 环境）就行，不需要一上来就上外壳。**这也是本地开发的通用默认起点**：只要项目真实拓扑还没用上外壳，本地就应该用纯独立组件裸进程开发；一旦真实拓扑已经把一部分组件合并进外壳，本地开发的默认才会跟着变成"组件+外壳混搭"（本地环境要跟真实拓扑对齐，不是永远停留在最初的默认）。
2. **组件数量多起来、单机装不下这么多独立容器的基线开销了，才需要考虑外壳合并**——这不是一个"从一开始就该选"的选项，是规模变大之后被迫做的取舍，把尽量多组件塞进尽量少的容器，换取更低的资源开销。
3. **真正上云、有 K8s 集群之后，选纯外壳、混搭、还是纯独立组件，直接跟集群资源多少挂钩，是一条谱系而不是三个孤立选项**：
   - 集群资源紧张 → **纯外壳**：尽量合并，把整体开销压到最低。
   - 集群资源不紧张也不算特别充裕 → **组件+外壳混搭**：大部分留在外壳里省资源，只把真正需要独立伸缩的那几个组件挑出来单独部署——这是纯外壳（省资源但没法单独控制某个组件）和纯独立组件（能精细控制但开销大）之间的平衡点。
   - 集群资源充裕 → **纯独立组件**：不再需要为了省资源牺牲颗粒度，每个组件都能独立控制自己的副本数和资源配额。

**"纯独立组件"会在这条路径的两端都出现，但原因完全不同**：开发阶段用它是因为规模小、要专注；云原生规模化的终态用它是因为资源足够充裕、不需要再为了省资源而合并。中间"单机 Docker 装不下、上云资源又有限"这段，才是外壳/混搭真正派上用场的地方。

**环境这条线，跟拓扑选择基本互相独立，只有一个例外**——Docker+本地混合这一档，不管你的生产拓扑最终选的是纯独立组件、纯外壳还是混搭，它的作用永远只有一个：让你方便地本地调试其中一两个组件，同时不牺牲其余部分的真实性。**它不是一个部署目标，纯粹是开发期的调试手段**，跟"打算怎么部署给客户"这个问题没有关系——选它不代表你的拓扑选择本身，只代表你现在正在本地改代码。

## 1. 纯独立组件 × 本地裸进程

**这是什么**：全部组件都是宿主机上的普通进程（`go run ./cmd/module`、`uvicorn app:app` 这类），互相之间没有 Docker 网络、没有 K8s Service，就是普通的 `localhost:<端口>` 网络调用。因为不经过 brickKit 平台的容器编排，平台原本会自动注入的环境变量（依赖地址、资源连接串、鉴权配置）需要你自己手动模拟出来喂给每个进程。

**什么时候用**：这是本地开发的通用默认起点——不管项目现在有没有外壳、不管是人工写代码还是 AI 驱动开发，只要还没有用上外壳合并，这就是日常开发默认会用的形态：改一行代码、`Ctrl+C` 重启、几秒钟就能看到效果，不需要经过"改代码 → build 镜像 → 重新起容器"这一整套流程，也不需要理解"这个组件现在有没有被合并进某个外壳"这层间接性。AI 驱动开发尤其受益于这一点——上下文只需要装下这一个组件的代码和边界，不用同时理解整个合并拓扑——但这不是它专属的场景，任何人本地改一个组件都会自然用到它。等项目的真实拓扑已经用上外壳了，本地开发的默认形态会变成第 9 节（组件+外壳混搭×本地裸进程），这里说的是外壳出现之前的默认。

**好处**：
- 迭代速度最快，IDE 调试器直接 attach 到进程，不需要跨容器/跨网络命名空间的额外步骤。
- 心智负担最低——没有容器、没有编排层，出问题时只有"这个进程本身"和"它连的那个地址"两个变量，排查范围最小。
- 不需要 Docker/K8s 环境，笔记本电脑就能跑。

**代价 / 局限**：
- **不是 brickKit 真正管理的部署形态**——`brickkit up` 生成的是 Docker Compose 或 K8s manifest，裸进程完全在这套机制之外。这意味着两件事：一是你要自己动手把每个进程需要的环境变量拼出来（依赖地址、`DATABASE_*`/`MQ_*` 连接串、`AUTHZ_BUNDLE_URL`/`IAM_JWKS_URL` 这类鉴权配置），平台不会替你做；二是这里验证出来的结论，理论上不能直接当成"Docker/K8s 下也一定这样"的保证——虽然本项目已经交叉验证过，几乎所有业务层面的结论（契约兼容性、版本共存）在四种环境下都是一致的，但底层机制（健康检查、地址生成方式）本身在裸进程下根本不存在，这层差异要自己心里有数。
- 没有健康检查、没有平台的地址自动改写——所有"平台会帮你做什么"的假设都不成立。
- 组件数量一多，手动维护每个进程的启动脚本和环境变量会变得繁琐。

**真机验证过的注意事项**：
- 需要真实发起一次带权限的业务调用（不只是测端口通不通）时，必须先让 `infra-iam-casdoor`/`infra-authz` 也以同样的裸进程形态跑起来——真实业务调用需要一个能通过本地 JWKS 验签的 JWT（走一遍 Casdoor OAuth 登录换 token 的完整链路），并且 `infra-authz` 真的可达、成功轮询过一次 `/authz/bundle`，否则具体的权限键判定会直接 503。这两个组件本身也是普通组件之一，不能当成"背景设施"默认忽略。
- 有些手写字面量配置项（比如 `authzBundleUrl`/`iamJwksUrl` 这类）在真实容器化部署下写的是 Docker 网络地址（`http://host.docker.internal:...` 这类），裸进程场景下这些地址根本连不通，需要手动换成 `localhost` 对应的真实端口——这不是 bug，是这类手写字面量本来就假设了容器化网络这个前提，纯裸进程场景下这个前提不成立，需要手动纠正。
- **构造"依赖方用旧版本代码"这类测试场景时要格外小心连带影响**：依赖方一旦切换到某个旧版本的源码，它自己 manifest 里全部的依赖声明（不只是你想测的那一条）都会变成那个历史时间点的快照——任何跟你当前真实拓扑不一致的依赖边，都可能连带触发额外的、你没打算启动的组件，甚至因为缺少某项配置直接失败。构造这类场景时要检查**全部**相关方向的依赖边，不能只盯着自己想测的那一条关系。同样，*其他没有直接参与这次测试*的组件，如果恰好对被你换成旧版本的那个组件有依赖，也会被连带影响。

## 2. 纯独立组件 × Docker

**这是什么**：每个组件各自一个 Docker 容器，`brickkit up` 生成并管理全部容器的 compose 编排——网络、地址注入、健康检查、启动顺序全部是平台原生机制，不需要你手动模拟任何东西。

**什么时候用**：组件数量还不多、单机资源完全够用的阶段——这通常是项目早期，或者客户购买的组件数量还比较少的时候。**这不是一个需要长期坚持的选择**：一旦组件数量多起来、单机跑不下这么多独立容器的基线开销，就应该转向外壳合并（见第 6 节）；这个转折点不是规划出来的，是资源用起来之后自然会撞到的门槛。在门槛出现之前，这是"平台怎么设计、就怎么跑"的最标准形态，没有任何额外的手工步骤。

**好处**：
- 完全对应"每个组件都能独立 `brickkit up`"这条本项目最核心的设计铁律——爆炸半径最小，升级/重启某一个组件完全不影响其它组件。
- 平台原生生成正确的依赖地址、健康检查、启动顺序，不需要任何手工介入。
- 排查问题时边界最清楚——每个容器的日志、资源占用、健康状态都是独立的，不会互相干扰。

**代价 / 局限**：
- **资源开销是这个拓扑的天生代价**：每个组件独立一个容器，意味着每个组件都有一份独立的 Web 框架运行时基线开销（Gin/FastAPI 进程本身的内存占用）、独立的数据库连接池。组件数量铺开到几十个之后，这些基线开销会在单机上明显累积——这也是"纯外壳"这个拓扑存在的直接原因（见下面第 6 节）。
- 对小客户/本地化部署场景，"每个组件一个容器"这件事本身可能超出对方硬件的承受范围。

**真机验证过的注意事项**：
- 这是本项目验证过的、业务链路走得最完整的一类场景——真实的库存预留/确认/取消 TCC 三步链条（含一次真实的"库存不足"负向场景），跨容器的真实 gRPC 调用全程正确。
- **"依赖方新、被依赖方旧"这类版本错配场景，Docker 下比裸进程更容易构造**——不需要碰任何源码或重新 build 镜像，只改一行 manifest 里的依赖版本声明，`brickkit up` 就能自动算出正确的多版本共存拓扑，同一次部署里一个组件的两个精确版本可以真实同时跑着，各自服务各自的调用方。
- **想测试"声明成一个非当前 checkout 版本"这类场景时，要改的是 `.brickkit/manifests/<组件ID>-<版本号>.yaml` 这份归档文件**（或者让子模块工作区真的 checkout 到对应的 tag，两者殊途同归）——不是想当然地去改 `brickkit.yaml` 顶层的版本号字段就完事，这是 brickKit 在 Docker 场景下真正读取"某个非当前版本的组件"依赖/配置的地方。

## 3. 纯独立组件 × K8s

**这是什么**：每个组件各自生成一个 K8s Deployment + Service，`brickkit up` 对接真实 K8s 集群（`--context` 参数指定目标集群）完成部署，网络发现走 K8s 原生的 Service + CoreDNS 机制。

**什么时候用**：这是云原生规模化路径里**资源最充裕的一端**——跟"纯外壳 × K8s"（第 7 节，资源紧张）、"混搭 × K8s"（第 11 节，资源适中）合起来看，三者是同一条谱系上资源从紧到松的三个点。**不是"随便一个上了 K8s 的客户"都该默认选它**：如果集群资源紧张，先看第 7/11 节；只有当资源已经宽裕到不用再纠结"要不要为了省资源而合并"，纯独立组件才是最优选择——每个组件是一个独立的 Deployment，天然支持独立设置副本数、独立的资源 request/limit，拿到最细颗粒度的独立伸缩能力。

**好处**：
- 真正的水平弹性伸缩能力——每个组件的负载曲线可能完全不同，独立部署意味着可以针对每个组件单独调整副本数和资源配额，不会因为合并而被同一个容器的资源上限互相牵制。
- 跨机器调度、故障自愈这些 K8s 原生能力，对每个组件都独立生效。

**代价 / 局限**：
- 运维复杂度是这个组合里最高的——需要客户自己具备 K8s 集群管理能力，不是简单的"装个 Docker 就能跑"。
- 需要额外安装 `kubectl`——**brickKit 平台本身不会用 `minikube kubectl --` 之类的方式代替**，`kubectl` 必须在执行部署的机器上单独装好。
- 组件数量多的情况下，K8s 层面需要管理的 Deployment/Service 对象数量也会同比例增多（这是"纯独立组件"拓扑本身的特点，换到 K8s 上不会变化）。

**真机验证过的注意事项**：
- **`deploy.target: k8s` 下，`expose: true` 的组件必须配 `hostname`，不能沿用 Docker 场景下用的 `exposePort`**——K8s 是通过 Ingress + 域名路由对外暴露服务的，不是映射宿主机端口；如果漏配 `hostname`，`brickkit up --dry-run` 阶段就会直接报错拦下，不会等到真的部署才失败。
- K8s/minikube 场景下，有些原本假设"跟 Docker 网络在同一台机器"的资源地址字面量，需要换成 K8s 场景对应的地址形式（比如 minikube 场景下用 `host.minikube.internal` 而不是 Docker 场景的 `host.docker.internal`）——这类地址是手写字面量，不会因为换了编排器就自动帮你改对。
- 真机部署的耗时比"K8s 部署天生很慢"这种直觉预期的要快，不需要因为担心耗时过长而对这个组合有额外的心理负担。

## 4. 纯独立组件 × Docker+本地混合

**这是什么**：绝大部分组件是真实 Docker 容器，正常经过 brickKit 完整的容器编排；额外挑 1 个（也只应该挑 1 个）完全独立的组件，用 `local: true` 拉到宿主机变成裸进程——这是唯一一种"裸进程调试"和"真实拓扑陪跑"能同时出现在同一份 `brickkit.yaml` 里的组合。

**什么时候用**：**这一档的作用跟"你打算怎么给客户部署"完全无关，它永远只是开发/测试期的一个调试手段**——不管你的生产拓扑最终选的是纯独立组件、纯外壳还是混搭，只要你想"方便地只测某一个组件"又不想牺牲其余部分的真实性，就会用到这个组合。具体到这个组合：你正在改某一个组件的代码，但又不想牺牲"其余组件都是真实容器、有真实的平台生成机制在起作用"这个环境真实性——比如你需要验证你改的这个组件跟其它真实容器之间的真实交互，同时又想要"改代码不用重新 build 镜像"这个开发体验。

**好处**：
- 不用为了调试一个组件就牺牲整套环境的真实性——除了你正在改的那一个，其余组件仍然是真实容器、真实健康检查、真实的平台地址注入机制。
- 比"全部裸进程"（第 1 节）更贴近真实生产行为，因为大部分组件经过的仍然是 brickKit 真实生成的机制，不是你自己手工模拟出来的。
- 改代码到验证生效的循环，跟纯裸进程一样快，不需要为这一个组件重新 build 镜像。

**代价 / 局限**：
- 需要理解 `local:true` 这个机制具体怎么改地址——虽然理解成本不算太高，但如果不清楚这层机制，遇到"为什么这个地址连不上"这类问题时会比较难排查。
- 只适合"挑 1 个组件做本地调试"这个场景，如果你同时想改好几个组件，这个组合的价值会打折扣（不如直接切到第 1 节的纯裸进程）。

**真机验证过的注意事项**：
- **`local:true` 的地址生成不是简单的字面量替换，是用 `extra_hosts` 把服务名本身重新映射到宿主机网关**——依赖方原本拿到的 `*_ENDPOINT` 字符串格式没有变化，只是这个服务名在容器内部的 DNS 解析结果被改成指向宿主机，而不是真的换了个网络协议或地址格式。这个机制本身跟本项目一直以来的文档描述是一致的，只是第一次被真机拆解清楚了具体手法。
- brickKit 官方的回归测试（`TestLocalStillWorksAlongsideServedBy`）确认 `local:true` 跟这个拓扑不冲突，本项目在自己真实的组件上复核过一遍，结论一致。

## 5. 纯外壳 × 本地裸进程

**这是什么**：把多个组件的工作负载合并进一个进程（外壳），这个外壳本身以裸进程形式在宿主机上跑，不经过任何容器/K8s 编排——你需要准确复刻 brickKit 真实会给这个外壳注入的一整套环境（合并成员的清单+每个成员的配置、`DATABASE_*`/`MQ_*`/`IAM_JWKS_URL`/`AUTHZ_BUNDLE_URL`/`OTEL_BASE_URL` 这类标准环境变量，跟普通独立组件是同一套约定）。

**什么时候用**：这一档通常不是普通部署者会主动选择的组合，更多是**验证"外壳本身能不能脱离平台编排独立存活"这件事**——比如给外壳这个合并单元自己写单元/集成测试时，或者开发工具链本身需要在裸进程环境下验证外壳内部的多模块编排逻辑对不对。

**好处**：
- 验证"外壳只是把 N 个进程变成 1 个"这个定义本身是不是成立——裸进程环境下没有容器/K8s 这层额外的编排介入，能最直接地确认外壳内部的模块编排、健康检查、跨模块调用、后台异步任务这些机制的正确性完全来自外壳自己的代码，跟容器化与否无关。
- 排查外壳内部逻辑问题时，不需要额外考虑容器网络这层因素。

**代价 / 局限**：
- **需要精确复刻平台会注入的环境**——这比第 1 节的独立组件裸进程更复杂一层，因为外壳需要知道"自己合并了哪些成员、每个成员各自的配置是什么"这份数据，正常情况下这份数据是平台自动生成注入的，裸进程场景下要自己拼出来。
- 同样不是 brickKit 真正管理的部署形态，这里验证出来的机制层面结论仅供参考，实际部署仍然要以 Docker/K8s 下的真实行为为准。

**真机验证过的注意事项**：
- 裸进程下外壳内部的健康检查、跨模块真实业务调用（完整的 TCC 链条）、后台异步任务推送三者都能正确工作——说明合并这件事本身不会改变任何一个模块自己的业务行为，"外壳只是把 N 个进程变成 1 个"这句话在裸进程环境下同样成立。
- 外壳声明清单里，**某个成员的"版本号"字段确认是纯元数据**——从外壳装配到底层 SDK，全链路都没有任何一处会拿这个版本号做判断或校验。声明一个旧版本号不会让外壳报错，也不会让它真的去装配一份旧代码（物理上也做不到——裸进程运行的始终是当前工作区实际编译进这个可执行文件的那份代码）。**外壳镜像/可执行文件里实际跑的是哪份代码，只取决于你构建它那一刻的源码状态**，跟清单里写的版本号标签完全无关，这条责任完全落在"什么时候该重新构建"这件事本身，不是平台的职责。
- **同一个外壳同时声明收编同一个组件的两个不同"版本"，在当前实现下不会报错也不会被去重**，会真的装配出两个独立监听不同端口的模块实例——但这两个实例背后是同一份代码、同一个数据库 schema，"版本不同"这个声明在合并态里同样只是标签，不代表真的装配了两份不同的代码。如果你手误在合并清单里给同一个组件写了两条记录，这两个实例会各自正常工作、互相之间没有数据隔离上的风险（因为本来就是同一份数据），只是白白多占用了资源。

## 6. 纯外壳 × Docker

**这是什么**：把能合并的组件全部合并进外壳，外壳自己是一个正常的 Docker 容器，被合并的成员不再各自生成独立容器——这是"用尽量少的容器装下尽量多组件"这条需求在 Docker 环境下最彻底的形态。

**什么时候用**：单机上跑纯独立组件（第 2 节）已经装不下了——组件数量多到每个组件独立一份运行时基线开销在单机上明显吃紧，这时候才需要外壳合并，把尽量多组件塞进尽量少的容器。这是本项目"客户在自己机器上本地化部署一整套 ERP/CRM"这个核心场景，随着组件数量增长自然会走到的解法，**不是一开始就该跳过第 2 节直接选它**——相比"纯独立组件"，容器数量能从几十个压缩到个位数，宿主机的内存/CPU 基线开销大幅下降。

**好处**：
- **单机资源开销显著降低**：一个外壳容器只有一份 Web 框架运行时基线、一份数据库连接池，不是被合并的每个组件各自一份——这是这个拓扑存在的核心价值。
- 容器数量少，启动时间也相应变快，日常运维（看日志、重启）需要面对的对象也更少。
- brickKit 原生支持，`expose`/`exposePort` 这类只对独立容器有意义的字段在合并成员身上自动失效（只警告不报错），不需要额外清理。

**代价 / 局限**：
- **爆炸半径变大**：外壳内某个模块要发布新版本，意味着整个外壳镜像都要重新构建、整个外壳容器都要重启（虽然单个模块运行时的 panic 已经验证过不会拖垮外壳内其它模块，但"发布新代码"这件事本身天然是外壳级别的）。
- **"外壳要不要单独发版"是一件需要你主动管理的事**——外壳声明收编了某个成员的新版本号，**不会**让外壳镜像自动拿到那份新代码；外壳镜像实际编译进去的代码，只取决于外壳自己的构建流程在构建那一刻的状态。这条一致性责任完全在外壳自己身上，不是平台会替你保证的。
- 调试合并进外壳的某一个组件时，需要多一层"这个组件现在实际上在哪个外壳容器里"的认知，不像独立组件那样一眼就能定位。
- **同一个外壳不能收编同一个真实组件的两个不同版本**——这是结构性的限制：本项目"一个组件一个注册表固定端口"的设计意味着两个版本必然声明同一个端口，在同一个外壳容器里注定冲突，`brickkit up` 会在生成阶段直接报错拦下，不会留到运行时才表现为其中一个模块起不来。

**真机验证过的注意事项**：
- "零独立组件、100% 合并"这个极端形态真实可用：容器数量能压缩到只剩外壳本身，跨外壳的依赖调用正确可达，完整业务链路能处理真实请求。
- "外壳要不要单独发版"这条责任现在有机制化的保障——本项目用一条专门的版本一致性扫描门禁持续盯着"外壳锁定的成员版本"和"外壳自己发布的版本标签"这两件事是否自洽，不再需要靠人记得手动核对。

## 7. 纯外壳 × K8s

**这是什么**：把能合并的组件全部合并进外壳，外壳本身是一个正常的 K8s Deployment，被合并的成员各自生成一个指向外壳 Pod 的 Service（不生成 Deployment），对外看起来"每个组件仍然有自己的地址"，但流量最终都落在外壳的 Pod 上。

**⚠️ 这是需要特别强调的一档**：很长一段时间里，这个组合在本项目里被认为是**做不到**的——旧版本的合并机制只能配 Docker 目标，上 K8s 必须先把所有外壳拆回独立容器，"部分合并、部分上 K8s"被认为是不存在的中间态。**这个判断已经被反转**：现在的合并机制原生支持 K8s，已经真机验证确认可用。

**什么时候用**：真正上云、有 K8s 集群，但**集群资源比较紧张**——这是云原生规模化路径里资源最紧的一端：先把尽量多组件合并进外壳，把整体开销压到最低，跟"纯独立组件 × K8s"（第 3 节，资源充裕端）、"混搭 × K8s"（第 11 节，资源适中的平衡点）构成一条完整的谱系，资源从紧到松分别对应纯外壳→混搭→纯独立组件。过去这类场景被认为做不到——要么合并省资源、要么上 K8s，两者不能兼得——现在可以同时拿到。

**好处**：
- 同时拿到"外壳合并省资源"和"K8s 弹性伸缩"两边的好处，不再需要二选一。
- `brickkit up` 原生生成正确的 Deployment/Service 结构，跨外壳的依赖调用通过 K8s 原生的 Service + CoreDNS 机制解析，不需要任何额外的手工配置。

**代价 / 局限**：
- K8s 运维复杂度这一层的代价（需要集群管理能力、需要 `kubectl`）跟"纯独立组件 × K8s"（第 3 节）是一样的，合并这件事本身不会降低这层复杂度，只是降低了资源开销这一层的代价。
- "外壳要不要单独发版"这条责任在 K8s 下同样成立，跟选择 Docker 还是 K8s 作为部署目标完全无关——外壳镜像的构建流程仍然是唯一的责任方。
- 同一个外壳不能收编同一个真实组件的两个不同版本——这条限制在 K8s 下同样成立（根因是本项目自己的端口注册表设计，跟编排器无关），K8s 下的报错形态可能是容器不断重启进入 `CrashLoopBackOff`，跟 Docker 侧的"容器持续重启退出"是同一个根因在两种编排器下各自的呈现方式。

**真机验证过的注意事项**：
- `brickkit up` 原生生成的 Deployment/Service 结构完全正确，跨外壳依赖通过 K8s 原生机制解析，完整业务链路端到端可用——这个组合已经在真实 K8s 集群上跑通过完整的部署流程。
- K8s 下有一个 Docker 场景不存在的实操差异：**验证/调试时想临时替换外壳内某个文件再让效果生效，Docker 下可以"复制文件进运行中的容器再重启这个容器"，K8s 下这个手法不成立**——K8s 的 Pod/容器重启语义不会保留容器可写层跨重启的内容，任何验证性质的文件替换都要走"改源码 → 重新构建镜像 → 让集群拉到新镜像 → 触发滚动更新"这条更重的路径。这不是 bug，是两种编排系统对"容器重启后还留着什么"这件事的既有设计差异，日常运维不太会撞见，但做验证性质的调试时需要心里有数。

## 8. 纯外壳 × Docker+本地混合

**这是什么**：外壳化部署（多个组件合并进外壳容器）作为主体形态，额外挑 1 个完全独立的组件用 `local: true` 拉到宿主机调试，其余组件保持真实的外壳合并容器不受影响。

**什么时候用**：同第 4 节——这一档永远只是本地调试手段，跟生产拓扑选择无关。具体到这个组合：你的生产拓扑已经是"外壳合并"了，但你正在改的是某一个仍然独立部署的组件（比如结构性无法合并的那类），想要"改代码不用重新 build"这个开发体验，同时又不想牺牲外壳这一侧的真实性。

**好处**：
- 跟第 4 节（纯独立组件×混合）类似的好处——不用为了调试一个组件牺牲整套环境的真实性，外壳那一侧继续以真实合并容器的形态运行。
- 特别适合验证"独立部署的组件跟已经合并进外壳的组件之间的真实交互"这类场景，因为外壳那一侧是真实的，不是模拟出来的。

**代价 / 局限**：
- 需要同时理解"外壳合并"和"`local:true` 本地调试"这两层机制，认知负担比单一维度的组合更高一些。
- 只适合调试**结构性独立**的那类组件（比如纯前端、BFF），如果你想调试的是一个已经被合并进外壳的组件，这个组合帮不上忙——那种场景应该用第 12 节（混搭×混合）。

**真机验证过的注意事项**：
- `local:true` 组件依赖某个被外壳收编的成员时，地址解析开箱可用——**依赖边地址**（brickKit 自动生成的那类 `*_ENDPOINT`）不需要任何手工干预。
- **但手写字面量配置项不受这个自动机制覆盖**：如果某个配置项（比如指向鉴权服务的地址）是手写在配置文件里的字面量、不是 brickKit 根据依赖声明自动生成的地址，这类值不会跟着 `local:true` 自动改写，仍然需要手动同步成正确的地址——这是"手写字面量"和"依赖边自动生成"这两条机制天生的边界，不是哪边的 bug。

## 9. 组件+外壳混搭 × 本地裸进程

**这是什么**：一部分组件合并进外壳、一部分组件独立部署，两者都以裸进程形式跑在宿主机上——这是"组件+外壳混搭"这个真实生产拓扑，搬到最轻量的本地裸进程环境下。

**什么时候用**：**这是日常开发的默认环境，但有一个前提——你的项目真实拓扑已经用上外壳了**。在那之前，本地开发的默认是第 1 节（纯独立组件×本地裸进程）；一旦生产部署已经把一部分组件合并进外壳，本地开发环境也应该跟着变成混搭，这样本地验证出来的地址解析、跨进程调用才跟真实拓扑一致——你不需要为了改一个组件而起一整套容器，直接裸进程跑起你需要的那几个组件（包括外壳形态的和独立形态的），验证一次真实的跨进程调用（包括真实的鉴权链路），比反复重新 build 镜像要快得多。

**好处**：
- 跟第 1 节一样，迭代速度快、调试方便，同时因为这个拓扑本身就贴近真实生产形态（混搭），验证出来的业务逻辑结论更有代表性。
- 能同时验证"独立组件"和"外壳内的合并组件"两种形态下的地址解析、跨进程调用是不是都正确，不需要分开两次验证。

**代价 / 局限**：
- 跟第 1、5 节一样，需要自己手动拼出平台原本会自动注入的环境（依赖地址、外壳合并成员清单、鉴权配置），比真实容器化部署多一层手工步骤。
- 这里验证出来的机制层面结论（不是业务逻辑结论）仅供参考，真实的地址生成、健康检查这类机制以 Docker/K8s 下的真实行为为准。

**真机验证过的注意事项**：
- **这个组合可能是第一次真正触发某个组件自己完整代码路径的场景**——很多验证任务在测试跨组件调用时，习惯直接用底层协议工具绕开某个组件自己的业务代码去连它的下游（比如跳过 GraphQL 网关直接拿 gRPC 工具连后端），这样固然能验证"网络通不通"，但永远不会真正执行这个组件自己写的那部分代码（网关到后端调用之间的那一层 resolver/转发逻辑）。如果你需要验证的正是这一层自己的代码，要确保你的验证方式真的从最外层入口发起（比如真实构造一次带真实鉴权的完整请求），而不是绕过去直连下游——绕过去的验证方式即便长期全绿，也可能只是从来没有真正执行到那条代码路径。
- 多个独立组件各自依赖同一个下游组件的不同版本这种情况，裸进程下**没有任何机制会阻止或提示你**——只要两个实例各自监听不同端口、调用方分别配好各自的地址，系统不会做任何一致性检查，两条链路会各自独立正常工作。这跟 Docker/K8s 下"生成阶段会有一些静态检查介入"形成对比——裸进程完全绕开了那层检查，版本管理上的混乱局面只能靠开发者自己的纪律避免，系统不会替你兜底。
- 一个组件的多个版本可以同时存在，一个走合并部署、一个走完全独立部署，两条路径互不需要协调——新老版本各自按各自的路径正常工作，不需要额外的同步机制。

---

## 10. 组件+外壳混搭 × Docker

**这是什么**：一部分组件合并进外壳容器、一部分组件独立部署为容器，`brickkit up` 生成并管理这整套混合拓扑——**这是本项目当前真实的生产部署形态**，也是绝大多数客户实际会用到的组合。

**什么时候用**：真实客户部署，尤其是本地化、单机部署的场景——这里的混搭是**结构性**的：一部分组件（比如纯前端、无状态网关型组件）设计上就没法合并进任何外壳，不管资源够不够用都要独立部署；剩下能合并的组件合并进外壳省资源。**这跟第 11 节（混搭×K8s）"因为集群资源适中而主动选择混搭"是两个不同的驱动因素**——这里即使单机资源很充裕，也依然会是混搭，因为总有几个组件结构上就是独立的。如果你在犹豫单机部署"到底该选哪个组合"，这个通常就是正确答案。

**好处**：
- 兼顾"外壳合并省资源"和"结构性独立组件保持灵活"两方面的好处，是最贴近真实需求的选择。
- 平台原生支持，不需要任何手工介入即可生成正确的混合拓扑（谁合并进哪个外壳、谁独立部署，全部由清单声明驱动）。

**代价 / 局限**：
- 拓扑本身比单一维度（纯独立/纯外壳）更复杂——排查问题时，既要考虑"外壳内部版本一致性"这套心智模型，又要考虑"独立组件之间的版本兼容性"这套心智模型，两者都要具备。
- 判断"这个组件现在到底是被合并了还是独立部署"这层认知负担依然存在，尤其是在组件数量比较多的时候。

**真机验证过的注意事项**：
- 这是本项目"当前唯一的真实部署形态"，独立容器到外壳容器之间的跨容器网络调用路径已经真机验证成立。
- **外壳升级、独立组件没跟着升级（或反过来）这两个方向都验证过协作正常**——只要契约本身没有破坏性变更，谁先谁后升级都不影响业务层面的正确性，版本管理上真正需要注意的只是"契约变更必须是只增不改"这条早就存在的铁律，跟这个拓扑本身无关。
- **运维脚本自己也可能有 bug，不能盲目信任"跑过很多次都没问题"就假设它一直安全**：本项目真机验证过程中发现过一个验收脚本自己的缺陷——它的前置检查只看配置文件是否干净，没有检查"是不是已经有一套真实部署正在跑着"，导致在特定顺序下会静默把一个正在使用的真实部署整个销毁掉（不是停止，是连容器带网络一起删除）。这类问题提醒我们：任何会做"清场重建"这类操作的运维脚本，在真实环境里执行前最好养成先确认"现在到底有没有东西在跑"的习惯，不要完全依赖脚本自己的前置判断。

## 11. 组件+外壳混搭 × K8s

**这是什么**：一部分组件合并进外壳 Deployment、一部分组件独立部署为各自的 Deployment，全部对接真实 K8s 集群——这是"组件+外壳混搭"这个真实生产拓扑，铺到 K8s 规模化部署场景下的形态。

**什么时候用**：真正上云、**集群资源不紧张也不算特别充裕**——这是"纯外壳 × K8s"（第 7 节，资源紧张、尽量合并）和"纯独立组件 × K8s"（第 3 节，资源充裕、全部拆开）之间的平衡点：纯独立组件在资源不够宽裕时开销太大，纯外壳又很难针对某一个特别需要弹性伸缩的组件单独调整资源——混搭刚好解决这个矛盾，把大部分组件留在外壳里省资源，只把真正需要独立控制资源/副本数的那几个组件挑出来单独部署。**跟第 10 节"结构性混搭"不同，这里的混搭是主动的资源调优决策**，不是"有些组件没法合并"这种结构性约束——同一个组件，在这里可能因为负载特别高被主动拆出来独立部署，即使它本来完全可以合并。

**好处**：
- 拿到"合并省资源"和"独立组件精细伸缩"两边的好处，不需要在第 7 节（纯外壳×K8s）和第 3 节（纯独立组件×K8s）之间二选一。
- 独立 Pod 和外壳 Pod 之间的跨 Pod 网络路径（K8s Service 发现机制）已经真机验证成立，是本项目第一次在真实 K8s 环境下验证这条完整路径。

**代价 / 局限**：
- 这是整个矩阵里运维复杂度和心智负担叠加最多的一格——K8s 集群管理能力 + 外壳版本一致性管理 + 独立组件版本兼容性管理，三层都要具备。
- 大部分适用于第 3、7、10 节的注意事项，在这一格里同时成立（`hostname` 必填、`kubectl` 需单独装、外壳要不要单独发版、独立组件版本错配处理），这里不重复展开，选这个组合之前建议也扫一眼那几节。

**真机验证过的注意事项**：
- 真实全量拓扑（外壳+独立组件混搭）在 K8s 目标下一次部署成功过，独立 Pod 到外壳 Pod 的跨 Pod 网络路径真机确认可用。
- 多个独立组件各自依赖同一个下游组件的不同版本这种场景，K8s 生成阶段的行为跟 Docker 侧完全一致：不冲突、不报错、不会悄悄选一个版本共用，Service 命名与路由天然按精确版本区分。真正会拦人的只有资源绑定这道正交的、必要的手续（新摘出来的独立组件必须显式声明用哪个数据库/消息队列资源），不是版本本身的冲突。

## 12. 组件+外壳混搭 × Docker+本地混合

**这是什么**：主体是"组件+外壳混搭"这个真实生产拓扑，绝大部分组件（不管是独立部署还是合并进外壳）都在 Docker 里正常跑着，额外挑 1 个完全独立的组件用 `local: true` 拉到宿主机做本地调试——**这是最贴近真实开发场景的组合**：正在改的那个组件通常恰好就是结构性独立部署的那一类（外壳内部的组件本身不适合单独拉出来调试，见第 8 节的边界）。

**什么时候用**：同第 4/8 节——这一档永远只是本地调试手段，跟生产拓扑选择无关。具体到这个组合：你在一个已经跑着真实生产拓扑（大部分组件合并、少数独立）的环境里，需要改动并验证某一个独立部署的组件，同时要求它跟其余全部组件（不管合并的还是独立的）的真实交互都保持真实、不打折扣。

**好处**：
- 在整个矩阵里最贴近"真实生产拓扑 + 快速本地迭代"这两个诉求的交集——除了正在改的那一个组件，其余全部组件都以最终生产会用的真实形态运行。
- 依赖边地址解析（brickKit 自动生成的那部分）全程正确，不需要手工介入。

**代价 / 局限**：
- 这是整个矩阵里需要同时理解的机制最多的一格：外壳合并机制 + 独立组件版本管理 + `local:true` 地址解析机制，三者叠加。
- 手写字面量配置项（不是依赖边自动生成的地址）同样不受 `local:true` 自动机制覆盖，仍需手动同步——这条限制跟第 8 节一样，不是这个组合特有的新问题，是同一条边界在更复杂拓扑下的延续。

**真机验证过的注意事项**：
- **`local:true` 的地址解析不是单向的，这一点在这个组合下第一次被完整验证到**：
  - "`local:true` 的组件依赖一个普通容器"这个方向——依赖边地址自动正确解析成指向宿主机的地址，开箱可用。
  - "一个普通容器依赖一个 `local:true` 的组件"这个反方向——brickKit 会生成一种 Docker 原生的网络别名映射（把这个组件的服务名直接映射到宿主机网关），同样开箱可用，不需要手工端口映射。
  - 这两个方向都验证过，之所以要特别强调，是因为大部分调试场景习惯把"要调试的那个组件"设成 `local:true`（对应第一个方向），第二个方向（别的组件反过来依赖这个正在本地调试的组件）容易被忽略，但确实也是开箱可用的，不用担心。
- 多个独立组件各自依赖同一下游组件不同版本、一个版本合并进外壳另一个版本独立部署——这两类多版本共存场景，`local:true` 这层额外的本地调试状态完全不改变它们在生成阶段的行为，该怎么处理见第 9/10/11 节里对应的内容（这里不重复展开），跟拓扑其余部分完全独立，可以放心叠加使用。

## 一条贯穿全部 12 种组合的共同结论：多版本共存

不管选哪一种组合，只要涉及"新旧版本混跑"这类场景，结论都是一致的：

- **依赖方和被依赖方谁先谁后升级**：完全兼容，只要契约本身遵守"只增不改"这条铁律，跟部署形态无关。
- **一个组件的多个版本能不能同时存在**：能，但**只有独立部署或者分别合并进不同外壳才行**——同一个外壳不能同时收编同一个组件的两个版本（会撞端口，这是本项目端口注册表设计决定的结构性限制，不是哪种环境的问题）。
- **谁负责保证"外壳声明的版本"和"外壳镜像里实际的代码"一致**：永远是外壳自己的构建流程，平台不会、也没有能力替你检查一个已经构建好的镜像内部实际编译了什么。
- **系统会不会主动帮你发现版本管理上的混乱**：裸进程环境完全不会，纯靠你自己的配置纪律；Docker/K8s 的生成阶段会做一些静态检查（比如资源绑定是否声明），但这些检查针对的是"部署declares是否完整"，不是"版本选择是否合理"——版本选得对不对，最终还是要靠人的判断，平台提供的是"生成不出自相矛盾的部署清单"这个底线保证，不是"帮你做版本管理决策"。
