# Identifiers and numbering

How a component identifies its own rows, how it refers to rows other components own, how ids relate to partitions and cursors, and how the human-readable document numbers people see (`SO202610-00012`, a voucher number) are allocated. Read it before adding a table, changing a primary key, writing a cursor, or numbering a document.

## Scope

Covered: primary keys of a component's own tables, references to other components' records, partition keys derived from ids, list cursors, document numbers including gap-free voucher numbers. Not covered: idempotency keys ([11-consistency-across-components.md](11-consistency-across-components.md)), event ids ([13-event-contracts.md](13-event-contracts.md)), the platform-owned user id `sub` ([21-identity-provider.md](21-identity-provider.md)), tenant and legal-entity identifiers (the tenancy document, planned, file 07).

## Choice

- **Every own primary key is a UUIDv7** (RFC 9562), stored as PostgreSQL `uuid`, generated by the component through its SDK before the insert, never by a column default.
- **A reference to another component's record is `TEXT`**, opaque, with no foreign key. The owner may be a fork, an external system, or use another id scheme.
- **On a partitioned table, `created_at` is the timestamp embedded in the id** (millisecond precision). A lookup by id therefore names its partition and probes one partition, not all of them.
- **Contracts carry ids as opaque strings**, currently lowercase hyphenated UUIDs, with no type prefix. Readability is the job of the document number.
- **Two exceptions**: a counter that must be strictly monotonic (the authorization tuple log revision, an outbox publish sequence) is `BIGINT GENERATED ALWAYS AS IDENTITY`; a reference table keyed by a standard code (currency, unit of measure) uses the code as a `TEXT` natural key.
- **Document numbers come from one SDK numbering mechanism**: a series table in the component's own schema, scoped by legal entity and period, formatted by a configuration value. Accounting voucher numbers are **gap-free and continuous within each period** for each legal entity. Other document numbers may have gaps but never repeat.

**Status**: decided. It lands with the 3.0.0 sweep: all twelve components with a database rebuild their migration baselines with `uuid` keys, and the demo and test databases are reset (there is no production data). Today keys are `BIGSERIAL`, order numbers are `"SO" + id`, and only erp/finance numbers its vouchers, with code of its own.

## Port contract

### Columns

| Table kind | Primary key | Notes |
|---|---|---|
| ordinary | `id uuid PRIMARY KEY` | id from the SDK |
| partitioned by time | `PRIMARY KEY (id, created_at)`, partitioned on `created_at` | `created_at` = the id's embedded time, set from the same SDK call |
| strictly ordered counter | `BIGINT GENERATED ALWAYS AS IDENTITY` | only where order must be gap-sensitive and monotonic |
| reference by standard code | `code TEXT PRIMARY KEY` | ISO 4217 currency, UN/ECE Rec 20 unit codes |

- A lookup by id on a partitioned table is `WHERE id = $1 AND created_at = $2`, with `$2` computed from `$1`. Only the owning component derives a time from an id; nobody else parses another component's id.
- A reference column holding another component's id is `TEXT NOT NULL` (or nullable), never `uuid`, never a foreign key.

### On the wire

- proto `string`, JSON string, the canonical 36-character lowercase form (`0192f0c4-7b1e-7cc3-9a52-3f1d2e4b5a60`).
- Callers treat it as opaque: no parsing, no ordering by id, no assumptions about version bits. The format may change additively; the type never does ([0302](../02-decisions/03-contracts-and-data/0302-contracts-are-additive-only.md)).
- Whether an endpoint accepts an id generated by the client (an offline draft, an idempotent create) is part of that endpoint's contract. When it does, anything other than a valid UUIDv7 fails with `INVALID_ARGUMENT`.

### Cursors

- `List` pages by cursor ([0301](../02-decisions/03-contracts-and-data/0301-money-as-strings-lists-by-cursor.md)). The default order is `created_at DESC, id DESC`; the cursor encodes the last row's pair and is opaque to the caller.
- UUIDv7 is not strictly monotonic across replicas. Keyset paging needs only a total order, and the pair gives one.

### Document numbers

The series table `besdk_number_series`, created in each component's schema by the SDK's platform migration (every table the SDK owns carries the `besdk_` prefix, and component SQL never touches one):

| Column | Type | Meaning |
|---|---|---|
| `series` | `TEXT` | which numbering, for example `sales_order`, `voucher` |
| `scope` | `TEXT` | the legal entity id, or another scope the component declares |
| `period` | `TEXT` | the period key, from the business date in the legal entity's time zone ([05-time-and-calendars.md](05-time-and-calendars.md)); for vouchers, the accounting period |
| `next_value` | `BIGINT` | the next number to hand out |
| `gapless` | `BOOLEAN` | the series' allocation mode, below |
| `updated_at` | `timestamptz` | — |

Primary key `(series, scope, period)`.

Two allocation modes, declared per series by the component:

| Mode | How | Guarantee | For |
|---|---|---|---|
| **gap-free** | `SELECT … FOR UPDATE` on the series row in the same transaction as the document; incremented there | continuous within the period; a rollback returns the number; numbers are allocated in commit order per scope | accounting vouchers, invoice-like documents |
| **gapped** | a block of numbers reserved in its own short transaction and handed out from memory | unique, increasing within a process; gaps after a crash or rollback | orders, deliveries, most documents |

- A gap-free number is allocated only after the idempotency claim has succeeded, so a duplicate request never consumes one.
- The format is a configuration value of the component (for example `ORDER_NO_FORMAT`, default `SO{yyyy}{mm}-{seq:05}`). Placeholders: `{le}` (legal entity code), `{yyyy}`, `{yy}`, `{mm}`, `{seq:N}` (zero-padded to N digits). Dates in the format are business dates.
- The document table enforces uniqueness: `UNIQUE (legal_entity_id, <number column>)`.
- When a number is allocated is the owning component's business decision (sales: at confirmation or at creation). Other components refer to the document by id; the number is for people.

## Alternatives

| Scheme | Size | Order | Mergeable | Leaks | Generated | Seen in |
|---|---|---|---|---|---|---|
| `BIGSERIAL` / identity | 8 B | strictly increasing | no | volume | in the database | Odoo, parts of ERPNext |
| UUIDv4 | 16 B | random | yes | nothing | anywhere | earlier microservices |
| **UUIDv7** (RFC 9562) | 16 B | by millisecond | yes | creation time | anywhere; PostgreSQL 18 also has `uuidv7()` | SAP RAP managed UUID keys, newer SaaS |
| ULID | 16 B (26 characters as text) | by millisecond | yes | creation time | outside the database | equivalent to v7, not an RFC, no native type |
| Snowflake-style | 8 B | ordered | needs a worker id per node | time and node | needs coordination | Twitter, Discord; Dynamics 365 RecId uses block allocation |
| Prefixed ids (TypeID, `ord_01h…`) | text | as v7 | yes | as v7 | outside the database | Stripe style |

Document numbers: a database sequence per series (fast, gaps allowed), a locked counter row (gap-free, serialised), or a block allocator (fast, gaps allowed).

## Why this choice

- **Mergeable**: group consolidation, an acquisition, moving one company to another deployment, copying masked production data into a test environment: none of these collide.
- **Generated anywhere**: an offline mobile draft or an idempotent create knows its id before it reaches the server.
- **No volume leak**: two `BIGSERIAL` order ids two weeks apart reveal how many orders were placed in between. Once customer and supplier portals exist, that is real business intelligence handed out.
- **Partition pruning by id**: with `created_at` derived from the id, a lookup touches one partition.
- **A standard**: RFC 9562, generated outside the database, so it works on every supported PostgreSQL version.
- **Gap-free vouchers per period** follow Chinese accounting practice: voucher numbers run continuously within each period.

## Why not the others

- **`BIGSERIAL`**: leaks counts, collides on any merge, and cannot be generated by a client.
- **UUIDv4**: random inserts scatter across the B-tree and give no partition pruning.
- **ULID**: the same properties as v7 without a standard or a native type.
- **Snowflake**: needs worker-id coordination across replicas and shell members, a moving part we do not otherwise need.
- **Prefixed ids**: every tool must parse the prefix, and regular expressions spread; the document number already gives people something readable.
- **A database default (`uuidv7()`)**: PostgreSQL 18 only, and the id is unknown until after the insert.
- **A sequence for vouchers**: leaves gaps, which voucher numbering does not allow.

## When to switch

- **The id scheme**: never. A measured exception: one very large detail table where the 16 bytes are shown to be the bottleneck may use `BIGINT GENERATED ALWAYS AS IDENTITY` for its own key, still exposing nothing outside the component.
- **Gap-free numbering**: when voucher posting for one legal entity hits the throughput ceiling of a serialised counter (tens to around a hundred vouchers a second) and the business accepts gaps or a different numbering point (numbering at period close, for example).
- **A number format**: whenever the customer wants another format; it is configuration.

## How to switch

- **A number format**: change the component's format key in `config/<scope>-<name>.yaml`. New numbers use it; existing documents keep theirs; the series is keyed by period, so nothing needs resetting.
- **A series from gap-free to gapped**: a change to that series' declaration in the owning component, released as a version. It is a business decision, recorded in the component's design document.
- **The id scheme**: not switchable. A change rewrites every table and every reference; that is why it is decided once.

## Conformance tests

Shared vectors in `vectors/numbering/` of the planned `brickKit/be-protocol` repository (format placeholders, period keys from business dates across a time-zone midnight), read by every official SDK. SDK tests, red first:

- a generated id is version 7, and ids generated within one millisecond by one generator increase;
- the time derived from an id equals the `created_at` set with it, to the millisecond;
- 100 concurrent gap-free allocations in one scope and period yield a continuous run with no gap and no duplicate;
- counting is separate per legal entity and per period;
- a gapped series leaves a gap after a rollback but never repeats a number;
- where an endpoint accepts a client-generated id, one that is not a valid UUIDv7 is rejected.

Component tests (erp/sales as the model): a get-by-id on a partitioned table scans exactly one partition (asserted from `EXPLAIN`); an order number cannot be derived from the order's id.

Gate: a new migration whose own primary key is not `uuid` fails `make gates` (files released before the sweep are frozen and only warned about).

## Decision records

- [0301](../02-decisions/03-contracts-and-data/0301-money-as-strings-lists-by-cursor.md): lists page by cursor; the cursor here is keyset over `created_at, id`.
- [0302](../02-decisions/03-contracts-and-data/0302-contracts-are-additive-only.md): ids were always strings in contracts, so moving to UUIDv7 changes no field type.
- [0104](../02-decisions/01-architecture/0104-variants-become-slot-families.md): a numbering scheme is one configuration key, not a slot family.
- Planned, not yet numbered: "own primary keys are UUIDv7"; "the 3.0.0 baseline rebuild replaces released migrations once, because no production data exists".

## Known limits

- A UUIDv7 reveals its creation time to the millisecond. Where even that matters, expose only the document number.
- Gap-free numbering serialises posting per legal entity and period: the throughput ceiling is tens to around a hundred vouchers a second per legal entity. It is a deliberate trade for continuous voucher numbers.
- References across components have no foreign key; a dangling reference is detected by the owner answering "not found", not by the database.
- The 3.0.0 rebuild discards the existing demo and test data; seed data is regenerated.
