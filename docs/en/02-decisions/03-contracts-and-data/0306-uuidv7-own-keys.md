# 0306 Own keys are UUIDv7; document numbers come from the SDK

**Status**: decided; lands with the 3.0.0 sweep.

## Decision

- **Every own primary key is a UUIDv7** (RFC 9562), stored as PostgreSQL `uuid` and generated by the component through its SDK before the insert, never by a column default.
- **A reference to another component's record is `TEXT`**, opaque, with no foreign key; contracts carry every id as an opaque string.
- **On a partitioned table `created_at` is the timestamp embedded in the id**, so a lookup by id probes one partition.
- **Two exceptions**: a counter that must be strictly monotonic (the authorization tuple log revision, an outbox publish sequence) is `BIGINT GENERATED ALWAYS AS IDENTITY`; a reference table keyed by a standard code (currency, unit of measure) uses the code as a `TEXT` key.
- **Document numbers people read** come from one SDK numbering mechanism: a series table in the component's own schema, scoped by legal entity and period, formatted by configuration. Accounting voucher numbers are gap-free and continuous within each period for each legal entity, with posting serialised per legal entity; other document numbers may have gaps but never repeat.

## Why

UUIDv7 keys merge without collision (group consolidation, an acquisition, moving a company to another deployment, masked production copies), can be generated before the record reaches the server (offline drafts, idempotent creates), and do not reveal business volume the way consecutive integers do to portal users. Their time prefix keeps index locality and lets the id name its partition. Readability is the document number's job, and Chinese accounting practice expects vouchers numbered continuously within each period.

## What this rules out

- `BIGSERIAL` or `SERIAL` own keys; a key generated by a column default; a type prefix inside an id
- Foreign keys to another component's records; parsing another component's id
- Document numbers built from the id (`"SO" + id`) or numbering code written inside a component
- A voucher numbering scheme that can leave a gap within a period

## Revisit only if

- Ids: never in general. One very large detail table where the 16 bytes are measured to be the bottleneck may use an identity key of its own, exposed nowhere outside the component.
- Gap-free vouchers: when posting for one legal entity hits the throughput ceiling of a serialised counter (tens to around a hundred vouchers a second) and the business accepts another numbering point.
