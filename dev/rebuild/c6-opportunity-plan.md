# C6：`crm/opportunity` 的子计划

阶段“按依赖顺序重建其余组件”的第六个组件（[components-plan.md](components-plan.md) 的 C6）。照 C2–C5 的做法：先定首批范围与源头要补的能力，按改动的循环做，每一步先写红的测试，改坏检查，发布，真机格从空库到 L3。数据与改坏检查放 `c6-data/`。

## 依据与牵动

- 边界卡 `docs/zh/07-components/crm.md#crmopportunity`（范围：当前重建）；决定 A71（商机发布“请求报价”，销售生成带商机参考的报价；报价与订单事件带商机参考，商机按客户设置手动或自动标记赢单）；组合页 `04-selection.md` 的“服务销售”“CRM 与销售协作”；`erp-trade.md` 的 `erp/sales` 卡（`crm/opportunity` 是上游，只经事件；缺时报价照常手工创建）；业务流程 `order-to-cash.md` 第 1 步；协议 02（投影）、07（引用：客户的资格）、08（扩展字段）、13（列表与搜索）、安全 01–09；参考实现 EspoCRM、SuiteCRM（阶段与赢率、漏斗；先自己设计）。
- 上下游现在的状态（2026-11-12 读）：
  - `erp/sales` 3.0.49：报价 `draft → sent → accepted`（转订单）／`cancelled`／`expired`；`erp.quotation.changed.v1` 有商机参考的位置但“本版为空”；“合同与商机的参考”在实现状态里答“能力不支持”；**没有消费请求报价**。
  - `mdm/partner` 3.0.40：资格查询的用途 `sell`（客户角色）已有。
  - 仓库 `brickKit/crm-opportunity`：C0 已把旧代码挪到 `legacy/v2`，`main` 只有说明 README，挂在 `components/crm/opportunity`；注册表的端口与 schema 在 P2 核对。

## P0 的结果（草稿，2026-11-12，AI 定，待复核）

**首批做的**：

| 能力 | 怎样做 |
| --- | --- |
| 商机 | 法人、客户（伙伴）、名称、币种、预计金额、预计成交日、负责人、阶段、概率、可选的产品明细（产品、数量、单位，只给请求报价预填，本组件不校验产品）；新建时向 `mdm/partner` 取资格（用途 `sell`，协议 07 的资格引用） |
| 阶段 | 首批一条固定的管道：`qualification`、`needs_analysis`、`proposal`、`negotiation`（进行中，缺省概率 10/25/50/75），终态 `won`、`lost`；向前可跨步，向后要明确回退并写原因；阶段历史一表 |
| 赢单与输单 | 手动；或按部署的设置自动（配置键，缺省 `manual`，另有 `quotation_accepted`、`order_confirmed`）；输单要原因；赢单后金额不再改，改要明确重开（写原因，回到赢单前的阶段） |
| 请求报价 | 命令在本组件的事务里发事实 `crm.opportunity.quote_requested.v1`（事实身份是请求身份）；销售消费、生成带商机参考的报价草稿，重复投递只生成一张 |
| 销售结果回到商机 | 订阅销售的报价与订单的完整状态事件，只取带商机参考的：记下关联的报价与订单（显示用），按设置自动赢单；销售没装时只手工记结果 |
| 漏斗与预测 | 按法人、币种、阶段：个数、金额合计、按概率加权的金额；预测方法（按阶段概率加权）是替换点；不折算币种 |
| 数据范围 | 法人（值集合）、负责人（主体，“销售只看自己的商机”）；负责人是本组件自己的字段，缺 `crm/customer` 时就是创建人 |
| 事件 | 完整状态 `crm.opportunity.changed.v1`；事实 `stage_changed`、`quote_requested`、`won`、`lost` |
| 恢复与审计 | 整套恢复的核对（`CheckService`，照其他组件）；赢单、输单、重开的审计（`infra/audit` 可选） |

**不在首批**（理由与触发）：

| 能力 | 理由 | 触发 |
| --- | --- | --- |
| 可配置的管道与阶段（按法人或业务线） | 首批一条固定管道够演示与测试；配置要版本化与迁移已有商机 | 第一个要第二条管道的客户 |
| 部门维度 | 要 `mdm/org` 的部门投影，边界卡的必需依赖没有它 | 客户要按部门看商机时：加可选依赖 `mdm/org`，照销售复制部门路径 |
| `crm/customer` 的负责人 | 那个组件远期 | `crm/customer` 重建时：建商机时取它的负责人作缺省 |
| 竞争对手、联系人角色、产品目录校验 | 边界卡没要求；产品由销售在生成报价时校验 | 客户要求时 |
| 币种折算的漏斗 | 要 `mdm/currency`，首批按币种分开 | 客户要合并的预测时 |
| 扩展字段（协议 08） | 其余已重建组件首批都没做 | 协议 08 的整体实现 |

**源头要补的（P2b，排在本组件的契约之后，因为销售要按它解析事件）**：

1. `erp/sales`：订阅 `crm.opportunity.quote_requested.v1`（只订阅、不声明依赖，同成本订阅采购：两边都声明会精确版本互相钉住）；按事实身份去重生成报价草稿（法人、客户、币种、负责人、明细；客户或产品不合格时的处理在 P1 定）；报价记商机参考，接受转订单时带到订单；`erp.quotation.changed.v1` 与 `erp.sales_order.changed.v1` 带出它；发布，连锁。

**要问维护者的**：没有（阶段、自动赢单的缺省、数据范围能从边界卡、A71 与已有组件的做法推出；推不出的按 AI 定记在设计的未决问题）。
