## AI 定下的取舍（记进复核清单）

| 项 | 取舍 | 理由 |
| --- | --- | --- |
| 一个进程承载多个探针 | 同一份探针代码按组件 ID 出几个变体：`test/probe-go`、`-go2`、`-go3`、`-go4`，`test/probe-py`、`-py2`；各有自己的端口、schema、流与清单；镜像入口按 `COMPONENT_ID` 选变体（入口代码，不是模块代码） | 外壳按组件 ID 承载成员，“外壳承载 1、2、4 个探针”与“同一外壳内的调用”都需要不同的 ID；同一份代码保证测出的差异只来自拓扑 |
| 变体的清单放哪 | 每个变体一个子目录（`probes/go2/` 等），只有清单、文档与一个按标签取主探针模块构建的 `Dockerfile` | BrickKit 按标签里 `metadata.id` 找清单，一个 ID 一个目录；变体不复制代码 |
| 一跳的耗时 | `/api/probe/call` 回答里加 `elapsed_us`：调用方从发出到收到回答的时间（探针 3.1.0，阶段性变化） | 驱动经 HTTP 打到调用方，端到端时间里含驱动那一跳；路径本身的代价要在调用方测 |
| 事件路径的完成 | `Write` 与大事件以对方探针记下的 `received_at` 减去写入方的 `written_at` 计（同一个数据库实例，同一时钟）；`Relay` 以 `relayed_at` 计 | 计划要求“按业务结果判定完成，不只看响应码” |
| 负载的形状 | 开环的固定速率（按计划时刻发出，延迟从计划时刻算，避免协调遗漏）；加压按 50/s 的台阶上升，到 p99 超过路由时限或错误率超过 1% 停 | 计划的“空闲、50/s、200/s、加压” |
| 采集口径 | 进程：容器里全部进程的常驻内存与 CPU 时间（`/proc`）；容器：cgroup 的 `memory.current` 与 `cpu.stat`；平台：Docker 守护与网络进程；基础资源单列 | 计划的“统一按进程计，容器与平台另报” |
| 格的部署文件放哪 | `dev/rebuild/experiment-cells/<格>/`，每格一个 BrickKit 项目 | 实验专用、随开发区归档；第 8 步起业务组件的格也放这里 |
| 外壳登录角色与探针 | 探针的 schema 行不写外壳登录角色（按格由哪个外壳承载而定）；实验的准备脚本按格授予 | 同一探针在不同格里进不同的外壳 |
