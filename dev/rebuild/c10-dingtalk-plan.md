# C10：`integration/im-dingtalk` 的子计划

阶段“按依赖顺序重建其余组件”的第十个组件（[components-plan.md](components-plan.md) 的 C10）。数据与改坏检查放 `c10-data/`。

## 依据与牵动

- 协议 10：对外命令（记录、状态、结果未知、能力声明）、入站回调（验签、去重、留原文、立即答成功、关联）、凭据与出站网络、通知的路由与投递、**交互按钮**（签发、传递、回调、执行、回显）、失败与积压；协议 09（决定的提交）；协议 01（后台工作）；安全 02（核对发布者的服务身份与主题相符）；决定 D68（渠道不调用业务组件、不记录决定，只经事件读员工）；边界卡 `integration.md` 的 IM 渠道一节（验证故事：在 IM 中点同意，所属组件核对动作令牌后执行；令牌已用或任务版本已变被拒；回调伪造被丢弃）。
- 现在的状态（2026-11-13 读）：
  - 仓库 `brickKit/integration-im-dingtalk`：旧代码在 `legacy/v2`，主分支只有 README；注册表的端口与 schema 要核对（见 P1）。
  - 通知组件 3.0.5 只有站内渠道；设计写着“外部渠道、免打扰与摘要、交互按钮以后做（随 C10）”。
  - 线协议第 18 章的意图只为动作令牌留了形状；第 17 章的流程内核不签发令牌、不收动作。
  - SDK 有公开路由（`httpx.Route.Public`，回调入口用）与对外命令包 `extcmd`（第 13 章：命令的写入、状态表、发送与查询的作业）。
  - 没有钉钉的测试环境：外部系统用模拟器（计划原文）。

## P0 的结果：首批范围（AI 定，待复核；P1 的设计考试之后改过，见 `c10-data/exam-p1/result.md`）

| 项 | 首批 | 理由 |
| --- | --- | --- |
| 通知组件怎样把投递交给渠道 | **渠道成员的共享契约**（线协议新的一章“渠道成员”）：系统面 `be.channel.v1.ChannelService.Deliver`（投递身份、收件主体、类别、标题、链接、可选的动作、时效），按“调用方 + 投递身份”幂等，答“已受理”或“没有渠道账号”；通知组件按部署配置的渠道（`NOTIFICATION_CHANNELS`）调用 | 协议 10：通知组件协调、渠道成员投递，每次投递是渠道的一条对外命令；共享契约让以后的飞书、企业微信同形状接入，通知组件不认识具体渠道 |
| 默认渠道 | 审批待办、到期提醒、安全提醒：站内 + 部署配置的 IM 渠道；其余只有站内。偏好按“类别 × 渠道”，IM 渠道可关（必须送达的类别也只保证站内） | 协议 10：必须送达的类别转站内 |
| 渠道账号 | 渠道成员自己的绑定表（平台主体 ↔ 钉钉用户），**只由用户本人**经钉钉的身份授权（OAuth）建立，管理员只能结束；没有绑定答“没有渠道账号”，通知组件记下（站内照写） | 考试 M4：管理员能改映射就能以别人的身份审批；员工组件没有 IM 账号的字段 |
| 投递 | 渠道成员把一次投递写成对外命令（SDK `extcmd`），工作项发给钉钉（工作通知或互动卡片）；能确认的只到“已发送”，不写“已送达”；结果事实 `integration.im_dingtalk_delivery.recorded.v1` | 协议 10 的对外命令与“不能确认送达时不写已送达” |
| 交互按钮 | **做**：流程内核在配置了动作来源时，为每个处理人签发**动作授权**（身份不是秘密，绑定任务、处理人、版本、安全版本、允许的动作、7 天内的到期），意图带上它；按钮上的一次性随机值由渠道成员生成、只存摘要（秘密不经事件与发件表，考试 M1）。回调：渠道验签、去重、存 `received` 并登记工作项、核对随机值与绑定，在自己的流上发共享的动作事件（带受众）；流程内核按 `FLOW_ACTION_SOURCES` 订阅，在消费者的事务里核对与决定；可重试的结果不记在授权上；最终的拒绝给用户发一条站内消息 | 边界卡的验证故事；D68 |
| 按钮上的动作 | 同意；驳回只在流程不要求驳回意见时给（采购与收付款的流程都要求意见，所以首批卡片只有“同意”与“在系统中处理”的链接） | 协议 09：驳回必须附意见的流程，按钮不能代替意见 |
| 回显 | 决定之后内核照常撤回待办意图（第 18 章的撤回）；渠道收到撤回时更新卡片为“已处理”留到以后（首批卡片不更新，撤回只影响站内） | 互动卡片的更新要钉钉的卡片实例接口，模拟器里可以做，但通知组件还没有“撤回投到外部渠道的消息”这条路；记下 |
| 免打扰、摘要、每人速率 | 不做（记进通知组件的未决问题） | 首批一个渠道、一个发送方，量小 |
| 模拟器 | 集成测试里是进程内的假钉钉；格里由 L3 测试在本机起一个 HTTP 服务扮演钉钉（发消息接口记录收到的卡片；测试自己按配置的密钥签名回调）；组件的 `DINGTALK_API_URL` 指向它 | 不多一个容器 |

## 全局约束

- 同一个库全系统一个版本：SDK 改了就全系统换（`sdk-unify.py`，`--moved` 只给钉对了的已发布组件）。
- 发布单独一条命令，开头先重跑检查；组件发布前跑 `make layout-check`，加了用户面操作的跑 `make seed-ops-check`。
- 按钮随机值、绑定的 `state` 与签名密钥是秘密：只在渠道成员与钉钉、用户浏览器之间，库里只留摘要；不进日志、事件与审计。
- 长任务（全系统换 SDK、格、探针测试）放后台并配监视。
