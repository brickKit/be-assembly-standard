# 预占参与方进 SDK 的计划（SF03）

> 2026-11-07，维护者在 L1b 的铺开里定：协议 04 参与方的分支状态机“进 SDK”（结构问题 SF03）。`erp/credit` 与 `erp/inventory` 的分支几乎逐行各写了一遍：预占先插入再连带十来列更新、取消留墓碑、确认时遇到暂存已过期就地到期、到期作业、消耗完才“已消耗”、按分支身份与内容摘要幂等。协议 04 改一条参与方的规则，要在两处各改各的。
>
> 按 `f-plan`。SDK 不得有规范之外的行为：先在 be-protocol 写规范与向量，再写 Go 的实现，组件再改用它（[SDK 共同契约](../../docs/zh/06-protocols/18-sdk-and-conformance.md)）。设计的决定是 AI 定的，标“待复核”。

## 现状

| | `erp/credit` | `erp/inventory` |
| --- | --- | --- |
| 分支表 | `branch`：额度、客户、法人、币种、金额、已消耗、引用、状态、原因、可用额度、内容摘要、暂存期限、版本 | `branch`：法人、引用、状态、原因、缺货、内容摘要、暂存期限、确认时刻、版本；`branch_line`：产品、仓库、数量、已消耗 |
| 消耗 | `consumption`（身份、分支、金额）：`Consume` 命令 | `consumption`（身份、分支、内容摘要、流水）：出库命令 `Issue` 同时消耗 |
| 锁的顺序 | 额度行，再分支 | 余额行（产品 + 仓库升序），再分支 |
| 调整、期初分支 | 答“能力不支持” | 同左 |

两边相同的：状态集合与迁移、墓碑、按分支身份与内容摘要幂等（取消墓碑上的预占答 `cancelled`、内容不同答冲突）、确认遇到暂存过期就地到期并释放、到期作业分批在后台事务里逐个释放、取消释放未消耗的部分、只有已确认的能消耗、消耗完才 `consumed`、查询不留墓碑、每次变化发分支事件。不同的只是“占什么、还什么、消耗什么”。

## 设计（AI 定，待复核）

- **规范**：be-protocol 新一章“预占的参与方”：分支的状态、命令与迁移（协议 04 的表写成规则）、幂等与冲突、墓碑、暂存期限与到期（与确认在同一行上原子裁决）、消耗的幂等、锁的顺序（先资源、后分支）、每次变化在同一事务里发分支事件；状态迁移写成语义向量（当前状态、暂存是否过期、命令与内容是否相同、消耗后是否还有剩余 → 结果状态、对资源的动作、回答）。调整与期初分支只留形状（参与方答“能力不支持”），随修订与上线导入再写。能力 `reserve-participant`，属主 `sdk`。
- **SDK 的包**（be-sdk-go，名字在 R2 定）：
  - 生命周期是一张表（阶段 × 命令 → 结果），与向量逐条核对；
  - 分支的通用列在 SDK 的表里（迁移给出：身份、状态、原因、内容摘要、暂存期限、确认时刻、版本、时间），消耗的幂等记录也在 SDK 的表里（消耗身份、分支、内容摘要）；
  - 驱动：预占、确认、取消、查询、消耗与到期作业的事务、锁的顺序、墓碑、幂等；
  - 组件只实现一个接口：锁住资源（在分支之前）、占用（足够与否、拒绝的原因）、归还未消耗的部分、记一次消耗并答还有没有剩余、发分支事件（载荷由组件定：它的契约里的 `Branch`）；组件自己的明细（信用的金额与额度、库存的行）在组件的表里，以分支身份关联。
- **Python 与 TypeScript**：功能矩阵标“未实现”，有该语言的参与方时再做（协议 18 的首批范围）。
- **组件**：`erp/credit`、`erp/inventory` 改用 SDK 的包；契约（proto、事件）不变，行为不变（集成测试锁住，事件序列前后相同）；顺带做 L1b 的另两条：SF01（一格多个结果：确认遇到过期、消耗未完与消耗完成为两条不同的格）、SF02（信用的订单占用只经额度模块的几个函数写）。

## R0 的结果（2026-11-07）

两个参与方对协议 04 迁移表每一格的回答相同：墓碑拒绝迟到的预占（答 `cancelled`）、同一分支同一内容答第一次、内容不同答冲突（`AlreadyExists`）；暂存期内确认成为 `committed`、再确认不变；过期的暂存在确认时就地到期并归还、到期作业同样让它到期；已结束的（`consumed`、`released`、`expired`、`rejected`、`cancelled`）再确认、再取消都不变、版本不动；查询不认识的分支答 `ABSENT`、不留墓碑；调整答“能力不支持”（`Unimplemented`）。

不同的地方（都是“消耗”这一格的外形，规范要允许，SDK 的接口要容得下）：

| | `erp/credit` | `erp/inventory` |
| --- | --- | --- |
| 消耗的命令 | 分支服务的 `Consume`（金额） | 库存服务的 `Issue`（出库，同时消耗；按行） |
| 不是已确认、超出剩余 | 错误 `STATE_CONFLICT`（`FailedPrecondition`），文字“only a committed branch is consumed; it is …”“more than the branch has left” | 出库的问题（`Issued = false`）：`branch_not_committed`、`exceeds_branch`，不是错误 |
| 消耗身份换内容 | `CONTENT_CONFLICT`：“consumption … was used with other content” | 同一原因：“consumption … was issued with other content” |
| 分支上另有的 | 可用额度的快照 | 确认时刻、缺货的明细 |

所以 SDK 的消耗答一个结果（照做、拒绝及原因、冲突），由组件按自己的契约答出去；拒绝的文字由组件给。

真机的验证（建格、种子两遍、确认订单的场景）随 `layout-plan.md` 的 L6 一起做。

## 全局约束

- 改动的循环：意图（R1 的规范）→ 考设计 → 契约 → 先写红的测试 → 实现 → 核对 → 发布；组件的契约不变。
- 每个仓库动手前升版本；按依赖顺序发布（be-protocol → be-sdk-go → 组件 → 外壳）。
- 只改结构不改行为：R0 锁住现在的回答，R3、R4 之后同一套测试照样过；R0 发现的缺陷另记，修不修单独定。
- 长任务（全部组件的级联测试）放后台配监视。
