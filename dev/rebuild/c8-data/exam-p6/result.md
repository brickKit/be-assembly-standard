# C8 P6 一致性考试的结果

考生：一个没参与写作的子代理（2026-11-13），对照线协议第 18 章、SDK 的 `notify` 与内核、通知组件的设计与代码、发送方的清单、格与 L3。答卷 `answer.md`。

## 必须改（4 条，全部处理）

| # | 发现 | 处理 |
| --- | --- | --- |
| M1 | 发送方核对比的是事件头的来源与载荷的发送方，两者都是发布方自己写的：配置里的一个发送方能冒充另一个（发消息、用大序号撤掉对方的消息） | 发送方以意图所在的流为准（消息系统按服务身份限制谁能在哪个流上发布），来源与载荷里的发送方都要等于流的属主（线协议 P18.8，alpha.126；通知 3.0.2）。**统一待办有同一个漏洞**（WF01 取事件头的来源），一并修（3.0.7）。两边都加了在自己的流上冒充来源的集成测试，改回旧写法时变红 |
| M2 | 链接的 pattern `^/` 放过 `//evil.example` | pattern 改为 `^/([^/\\].*)?$`（线协议 alpha.126），schema 的正反例与 SDK 的单元测试加反例 |
| M3 | 岗位展开成功不记结果，意图还在等别的岗位时每轮重展：换人后两任都收到、已写入的可能被记成过期、不同日期互相覆盖 | 展开成功记 `expanded`（迁移 0002），只展开一次；键带日期；补了测试（岗位换人后新的持有人收不到），改坏检查变红 |
| M4 | 测试索引说员工投影在格里验证，实际没有任何测试走到真实的 `flow.Employees` | 如实改写：真实员工投影没有自动测试，第一个发岗位收件人的发送方上线时在格里测（`itest/AGENTS.md`、设计的实现状态） |

## 可不改

C1（测试顺序的说法）、C7（包注释、数据表说法）照改；C2、C3、C4、C5、C6 不改，理由在答卷里：分不出的 `malformed` 原因只影响排障列表；占位行随 400 天清理；`be_work_item` 与 SDK 的流程内核同样的读法；订阅名的冲突在现有领域名下不会发生；“当时的持有人”与按发送方给的日期展开说的是同一件事。

## 过程中出的错

修 P18.8 时一条命令里先跑改文件的脚本（中途断言失败）、再 `make check | tail` 接发布，检查失败被管道吞掉，线协议 alpha.125 带着不过的检查发了出去；补发 alpha.126，兼容矩阵把 alpha.125 标为不要用。记忆里那条“测试与发布不接管道”是第三次犯，改写成“发布永远单独一条命令，开头先重跑检查”。
