# C10 P1 设计考试的答卷（摘录）

考生：一个没参与写作的子代理（2026-11-13，只读），对照子计划、线协议第 20 章与 P17.19、P17.20、P18.11、通知组件的设计与现有代码、钉钉渠道成员的设计 ID01–ID12，以及协议 10、协议 09、边界卡、D68 与 SDK 现状。处理见 `result.md`。

## 必须改

- **M1** 令牌原文在意图事件里，与“令牌不进事件正文”矛盾：会落到所属组件的发件表（7 天）、消息系统（7 天）、对象存储（1000 个收件人的意图必然超过 64 KiB，P6.14 的预签名地址）、补发、通知组件的死信表；订阅采购流的别的组件也读得到。建议方案 B：所属组件只签发非秘密的授权身份，按钮上的一次性随机值由渠道成员生成、只存摘要，动作事件带授权身份。
- **M2** 动作事件没有受众：采购与收付款都订阅钉钉的流，每一次正常点击都会在另一个所属组件里写一条“摘要不在本组件”的安全审计。`Deliver` 要带发送方与意图身份，动作事件带 `audience`，不是自己的静默确认。
- **M3** 事件路径上的授权：SDK 有为一个主体做判断的路径（`authz.Subject` 用本地视图，`internal/host/build.go:153-158` 有先例），但 `flow/decisions.go:121-122` 把视图过期、无法证明都当成没有权限；记在令牌上就永久答回去。要区分可重试与最终的拒绝；用 Check 返回的截止时刻；在消费者的事务里决定。
- **M4** 映射由管理员维护：管理员把审批人 X 映射到自己的钉钉用户，就能以 X 的身份审批，绕过职责分离。首选用户本人经钉钉授权绑定，管理员只能结束。
- **M5** 通知组件现有投递全在一个事务里（`delivery.go:58-80`）；`pending` 行会被当成已有结果（:208-212）；被取代的意图的外部投递永远 `pending`，令牌原文留 90 天。
- **M6** 第 13 章与 SDK 没有本地到期作废、没有清除秘密参数；`manual` 之后重发没有令牌；钉钉不去重时每次读取超时都要 24 小时后人工处理，是运维噪声。
- **M7** 回调“立即答成功”之后崩溃，回调就丢了：要有 `received` 状态与工作项。
- **M8** 外部调用在投递的一轮里逐个进行，渠道不可达时拖住站内消息；没有按协议 10 退避。外部投递要按行认领、退避、断路。
- **M9** NT07 说必须送达的类别也可以关外部渠道，NT09 说必须送达的类别改偏好答 `REQUEST_INVALID`，现有 `Route` 对必须送达一律写入、不看渠道。

## 建议改

S1 令牌最长 7 天、核对用的时刻与宽限；S2 签发时记主体的安全版本，执行时更大就拒；S3 锁顺序加令牌、L3 的“令牌已用”要用手工的另一个动作覆盖；S4 没有动作来源时不签发、意图写明接受哪些渠道的动作；S5 被拒时用户没有任何反馈；S6 `Deliver` 现在就带发送方、意图、合并键与序号，幂等记录保留到到期之后；S7 意图 schema 的 `unevaluatedProperties: false` 与 P6.33 冲突，混合版本时全部意图被拒；S8 依赖方向与地址注入没写清，边界卡说 IM 渠道必需依赖通知组件；S9 外壳里共用总线连接，“只有渠道成员能在它的流上发布”的前提不成立，要写明；S10 回调方案要核实（钉钉推荐 Stream 模式，可能不需要公开入口；`outTrackId` 重复投放是否报已存在）；S11 卡片标题要按纯文本放；S12 文档小问题（P17 不在本版的句子断了、NT 编号乱序、P20.3 没列 `failed`、用词）；S13 通知组件对渠道成员错误的分类没写。

## 可不改

回调原文改为摘要后无法再验签（可另存密文摘要与签名参数）；免打扰与速率推迟；首批卡片只有“同意”；模拟器不多一个容器；“事件里只发摘要”在“只有渠道成员能在自己的流上发布”的前提下成立。
