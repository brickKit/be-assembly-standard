## 现状（2026-11-02 盘点）

- 黑盒套件只有核心剖面（`conformance/profile/checks.py`，约 16 项：生命周期、数据库、信封、可观测）；事件只有 CK-EV-09，CK-BUS、CK-WK、CK-IDEM 一项都没有。
- Go SDK 的 `features.json`：事务、发件表、运输、消费者、工作项、定时、幂等、投影都是 verified（SDK 自己的测试）；`projection-watermarks`（水位来源）、`projection-shadow` 是 `not_implemented`。
- 线协议第 09 章写明“水位来源的回声、补取与连续位置随后续任务加入”：**水位来源还没有线协议条款**，设计只在项目协议 02（S6、来源水位各步、PJ19 起的独立预期）。
- 探针（`be-acceptance/probes/CONTRACT.md`）只有写事件、收事件、调用；没有后台工作项与水位来源的接口。
- 检查编号在 SDK 测试里的覆盖不齐：例如 CK-BUS-02…07、CK-EV-04、CK-EV-09、CK-EV-10、CK-WK-01、04、05、06、CK-PJ-01…03 在 Go SDK 的测试里没有被点名（可能由按条款编号命名的测试覆盖，T1 核对）。

## 全局约束

- 每个改动走改动的循环（意图 → 考设计 → 契约 → 先写红的测试 → 实现 → 核对 → 发布）；行为变了先改 `be-protocol` 的条款与向量，再改 SDK（`be-sdk-go` 的 AGENTS.md）。
- 版本每次改动都升，按依赖顺序发布：协议 → SDK → 验收（探针、套件）→ 父仓库指针。
- 测试先断言前提成立（故障打到了目标、依赖真的不在），不跳过；进记录的运行当场存输出到 `experiment-data/`（交接“推进方式与停点”的做法照用）。
- 测试用自己的 schema 或自己清理，不往共用测试 schema 里留东西（T10）。
- 这一阶段不新做业务组件；Python 补齐是第 6 项，这一项只做 Go，但协议条款写成语言中立的。
- **探针契约**（维护者 2026-11-02 定）：这一项给探针加的接口（后台工作项、水位来源）Go 探针先实现，契约里标明“Python 探针随第 6 项补齐”；套件对 Python 探针把这些剖面报为“不适用——未实现”，不算“符合”。
- 底层的热路径照“越底层越要想性能”：改了认领、转发、消费的语句，量一次（固定负载下的耗时），离谱就查；电源敏感的测量在 performance 模式下成对交替。

### T1 覆盖地图与“每条检查都有测试”的检查

- **要做到什么**：一张表，第 05（事务部分）、06、07、09 章与项目协议 01、02 的每条规则，写明它由哪个测试守着（Go SDK、黑盒套件，或“还没有”）；并有一个机械检查：协议里出现的每个 `CK-` 编号，至少被一个测试点名（Go SDK 或套件），否则失败。
- **依据**：协议 18 的“剖面”“报告”（只覆盖碰巧跑完的剖面会假通过）；`feedback_green_without_testing`。
- **验收**：检查在当前代码上运行，列出没被点名的编号并以非零退出（红）；表里每个“还没有”都分到后面的某个任务。
- **可能动到**：`be-protocol`（检查放在协议仓库，读 SDK 与套件的测试文件；或放在 `be-acceptance` 的 doc-checks，T1 里定）。

**结果（2026-11-02）**：`tools/be-acceptance/doc-checks/35-protocol-coverage.py`（`make protocol-coverage`，`CH=05,06,07,09` 只看这一项的章）：按规则行，测试点名了规则编号或它的检查编号（含范围写法）就算；Go 的测试只用包（名字以 `test` 结尾的，如 `events/transporttest`）一起扫。第 05、06、07、09 章 95 条要测试守的规则：起初 Go 70 条被点名，逐条核对后给 20 个按行为起名的测试补上编号，到 91 条；套件 7 条，Python 58 条。地图：`foundations-01-coverage.md`（`--markdown` 生成）。

### T1b 补 Go SDK 缺的测试

- **要做到什么**：T1 查出的缺口各有一个测试：P6.11（转发按流与分区取租约，租约不承担正确性：停顿后恢复的旧持有者只能排队取编号锁）、P6.33（载荷里不认识的字段忽略；读模型按聚合订阅时收到以后加的动作与主版本）、P7.3（queue 工作项与业务写入同一个事务，回滚不排入）、P7.11（`idempotent_external` 的所有尝试带同一个 `operation_id`，接管后先查询对方再决定）；只测了一部分的补齐：P5.3（`PG_POOLER_PREPARED=false` 时用 `CacheDescribe`）、P5.15（开始时发现 dirty 要失败并写明版本与文件）、P7.2（三种工作项身份与 `operation_id` 的格式）、P9.10（投影行的实现实例与纪元）。
- **依据**：各条规则。
- **验收**：`make protocol-coverage CH=05,06,07,09` 以 0 退出（Go 95 / 95）；新测试若测出缺陷，按改动的循环先修；每个新测试做一次改坏代码的反向检查。

**结果（2026-11-02，`be-sdk-go` alpha.47）**：8 个新测试与 1 处补编号；规则的行为都已实现，新测试一次通过，所以每个都做了改坏代码的反向检查，全部变红、还原后无残留（`foundations-01-data/t1b-mutations.txt`）。`make protocol-coverage CH=05,06,07,09`：Go 95 / 95；它以 `protocol-coverage-go` 进了 `make gates`。P6.33 里“读模型收到不认识的类型就标为不完整并取回”是组件的映射，留给 T4 的黑盒 CK-EV-10。

### T2 共用测试 schema 不再越积越多

- **要做到什么**：`be-sdk-go` 的 `be_bus_test` 与其他共用测试 schema 里，测试跑完不留下流、订阅与消息（2026-11-02 时 1602 个订阅、1056 条消息）；测试互相看不见彼此的东西。
- **依据**：本项目 `be-sdk-go` alpha.44 的发现（清理测试数到别人的 521 条过期消息）。
- **验收**：整套集成测试跑两遍，前后共用 schema 的行数不增长；查询命令与前后行数存进记录。
- **回退**：只动测试代码。

### T3 组件连接池上的通用计划排查

- **要做到什么**：组件自己的数据库连接池（`db/pool.go`，`Prepared` 时缓存语句）上，SDK 发出的每条“取第一条”类语句——发件表转发的取行、收件表、工作项认领、幂等键认领——在统计落后（从没 analyze、积压突增）时不随积压变慢。
- **依据**：P6.28 的做法（两条路各沿按位置排序的部分索引、按参数规划）；`experiment-data/14-07-pgqueue-plan/`、`14-08-pgqueue-inflight-index/` 的方法。
- **验收**：每条语句一个“积压 20 对 2 万”的测试，在自己的从没 analyze 过的 schema 上，门槛按实测定（像 pgqueue 的“小 + 1 ms”），对改之前的代码红、改之后绿；改法（索引、执行方式）实测过，代价写进提交说明。
- **回退**：SDK 的迁移只加不删；改执行方式的可以回到原来的配置。

### T4 事件剖面（含消息运输）进黑盒套件

- **要做到什么**：黑盒套件对一个组件（Go 探针）跑事件剖面：CK-EV-01…10、CK-BUS-01…10 中适用于黑盒的那些（发件表与提交同事务、锁内编号、纪元、转发顺序、信封、大事件、跳数、死信、消费者的去重与收件表），每项一个自检用的坏变体。
- **依据**：协议 18；线协议第 06 章；探针契约。
- **验收**：对 Go 探针“符合”；每个坏变体被抓到（套件自检）；环境缺消息系统时报“部分”而不是“符合”（SK02）。
- **可能动到**：`be-acceptance/conformance/profile/`、探针（可能要加只读的观察接口，按上面“探针契约”一条：Go 探针先行）。

### T5 后台工作

- **要做到什么**：① 副本在跑一个工作项时被杀，租约到期后另一个副本接管，结果只生效一次（实验套件 E 没有触发：工作项要在被杀时正在跑）；② 后台任务领取的空闲轮询（P6.32 之后剩下的空转）：没有到期任务时不为每次轮询付全表的代价，有按时间排定的任务时按时取到（不能照搬“没有就跳过”）；③ 后台工作剖面（CK-WK-01…10）进黑盒套件。
- **依据**：线协议第 07 章、项目协议 01；实验报告“限制与未测”。
- **验收**：①的定向测试先断言“被杀时那一项正在跑”，再断言接管与只生效一次；②量空闲时每次轮询的代价（固定负载、performance 模式），改之前与之后成对；③对 Go 探针“符合”，坏变体被抓到。
- **可能动到**：`be-sdk-go/work`、探针（加一个后台工作项的接口）、套件。

### T6 水位来源的线协议条款与向量

- **要做到什么**：线协议第 09 章（或新的一章）补上水位来源：回声行、补取接口（请求即探测）、锁内的提交后编号与连续位置、消费者的对齐与接收规则、纪元变化与来源更换；每条带检查编号与向量，语言中立。
- **依据**：项目协议 02 的 S6、“来源水位”各步、PJ19–PJ28、PJ32 起的独立预期；模型 35；安全 03 对内部来源的使用。
- **验收**：`be-protocol` 的 `make check` 通过；每条规则有检查编号；向量覆盖模型 35 的定向场景；COMPAT 记一行。
- **回退**：协议只做加法。

### T7 Go SDK 实现水位来源与对齐

- **要做到什么**：`be-sdk-go` 的 `projection-watermarks` 从 `not_implemented` 到 verified：来源一侧（回声行、补取、连续位置）与消费者一侧（水位、对齐、取回）；模型 35 的定向场景（主库切换后丢行、复制延迟、对齐）各成一个集成测试。
- **依据**：T6 的条款；模型 35（3000 次随机运行与三个定向场景各 50 个种子）。
- **验收**：向量全过；定向测试在真实 PostgreSQL 与两个运输上通过；模型的坏变体（例如补取读副本）对应的测试在故意改坏时变红；热路径量一次。
- **回退**：SDK 的迁移只加不删；水位来源按流声明，不声明的流行为不变。

### T8 水位来源剖面进黑盒套件

- **要做到什么**：套件的水位来源剖面（含 SK17：补取时不核对消费者连续位置上的行要被抓到），对一个声明为水位来源的探针流跑。
- **依据**：协议 18 的 SK17；T6 的条款。
- **验收**：对 Go 探针“符合”；SK17 与其他坏变体被抓到。

### T9 参考模型 13、14、37 的关键交错落成定向测试

- **要做到什么**：每个模型的关键交错（崩溃在认领与完成之间、只插入的认领、完成标记在事务外；部分字段的事件与读穿修复、严格大于规则；只比较代次不比较纪元）与坏变体，各成一个 Go SDK 的集成测试；坏变体用“故意改坏代码时变红”验证。
- **依据**：`be-acceptance/models/13-job-recovery.py`、`14-projection-repair.py`、`37-epoch-counters.py` 的检查与坏变体。
- **验收**：测试通过；每个坏变体做一次改坏代码的反向检查，记下结果。

### T10 故障注入

- **要做到什么**：探针链在 Docker 上，背景负载下：① 进程在事务中、转发中、处理中被杀；② 消息系统停 2 分钟；③ 消费者的库回退到旧备份（备份后又有新事件），之后靠来源的补发保留与对齐回到一致。每次之后核对不变量。
- **依据**：实验的故障套件（`conformance/cells/faults.py`）；协议 15、项目协议 02 的补发与对齐。
- **验收**：每种故障先断言打到了目标（被杀的进程确实在那一步、库确实回退了），再断言不变量全成立；运行输出存进 `experiment-data/`。
- **回退**：只在实验格里做。

### T11 收尾与门槛核对

- **要做到什么**：三条门槛逐条对上证据；`features.json` 与 COMPAT 更新；正式文档里受影响的地方（事务与消息、协议 02）跟上；记录与交接；复盘。
- **验收**：T1 的检查通过（每个检查编号都有测试）；套件对 Go 探针四个剖面“符合”；记录写明每条门槛的证据。
