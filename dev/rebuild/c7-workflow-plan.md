## P0 的结果（草稿，2026-11-12，AI 定，待复核）

**首批做的**：

| 能力 | 怎样做 |
| --- | --- |
| 共享任务契约 | 属主是线协议（`be-protocol` 的 `schemas/flow/task.v1.schema.json`；P2 改：生产方是 SDK 的流程内核，SDK 不能引用组件的契约）：任务身份（流程管理方 + 任务 ID）、任务类型、单据引用（组件、类型、ID、单号）、摘要（只放发布方标明可公开的字段，见“不在首批”）、候选处理人（主体）、状态、截止、版本、法人；发布方在自己的流上发布，事件类型 `<领域>.<组件名>_task.changed.v1`（例 `erp.purchase_task.changed.v1`）引用共享 schema |
| 流程内核（SDK） | 组件声明单据类型的流程（代码里的版本化定义：步骤、分配规则、步骤形式）；实例（单据引用、关键修订号、依据摘要、流程版本、发起责任主体）与 `running → approved／rejected／returned／withdrawn／superseded`；任务的待处理、已决定、`superseded`、`paused`；决定在一个本地事务里检查（任务待处理、处理人是候选、当前资格、职责分离以人为单位、修订未变、每任务至多一个决定、幂等键）；放行核对（`approved` 且修订与依据摘要相同） |
| 分配 | 岗位持有人（`mdm/org` 的岗位，`mdm/employee` 的任职与账号关联的投影：岗位 → 人 → 账号）与指定个人；解析时排除发起人（以人为单位）；投影不完整时等待；没有合法处理人时任务 `paused` 并告警 |
| 步骤形式 | 单人、任一（第一个同意完成，其余 `superseded`）；会签与法定人数见“不在首批” |
| 决定动作 | 内核在组件的用户面登记标准路由（同 SDK 的冷热分层路由那样由 SDK 登记）：同意、拒绝，带任务版本与幂等键；前端从待办直接发给所属组件 |
| 修订与取代 | 关键字段的新修订让实例 `superseded`、任务 `superseded`，按新修订启动新实例（采购订单的修订 PO06） |
| 迁移的业务 | 采购订单（PO03–PO06）、采购申请（PR02–PR03）、付款申请（PR03）、调拨与收付（BE02）：审批人改为流程定义的岗位持有人（采购：法人的采购负责人岗位；付款：财务负责人岗位，种子随 P6 定）；没有装员工组件时退回按账号比较（协议 09 第 4 条），风险照写 |
| 统一待办 | 部署配置列出“任务类型 → 发布方”（同财务的 `FINANCE_FACT_SOURCES`），只收选定发布方的投影，其余拒绝并记安全事件；按版本覆盖；我的待办（候选包含我、待处理）、已办（我决定过的、历史）；每个任务的所属组件与动作入口（由组件推出，不取投影里的地址）；所属组件的投影久未更新时标“可能不是最新” |

## P1 的设计（草稿，2026-11-12，AI 定，待复核）

- **流程内核**：线协议第 17 章 `tools/be-protocol/spec/17-flow-kernel.md`（P17.1–P17.17）：流程定义、实例、分配与任务、决定的检查顺序与原因（`TASK_NOT_PENDING`、`NOT_ASSIGNEE`、`SELF_APPROVAL`、`REVISION_CHANGED` 等）、唯一决定与幂等、标准路由 `POST /be/flow/tasks/{id}/decisions`、任务投影；不在本版的写明。
- **统一待办**：组件设计 `components/infra/workflow/docs/design.md`（WF01–WF07）：发布者核对按部署配置 `WORKFLOW_TASK_SOURCES`、按版本覆盖、我的待办与已办只按“候选包含我”、读取任务带动作入口与 `stale`、不保存决定不转发动作；共享任务契约 `infra.workflow.task.v1` 属主是它。
- **采购**（P4 写进它的设计）：任务类型 `erp.purchase.order.approval`、`erp.purchase.requisition.approval`；单步、任一；处理人由法人的采购政策新加的“审批人”给出：岗位代码（`approver_position`，要员工组件）或指定个人（`approver_principal`）；政策要审批而两者都没配时，提交答 `NO_APPROVER_CONFIGURED`。关键字段：订单的供应商、币种、明细（产品、数量、单位、单价）与合计；申请的明细。状态的对应：订单的驳回（回到草稿）是流程定义的 `returned`，申请的驳回（终态 `rejected`）是 `rejected`；取消待审批的单据是撤回（`withdrawn`）；已批准订单的修订（PO06，只有已批准的能修订）让 `approved` 的实例 `superseded`、按新修订启动新实例；取消已批准的是 `superseded`。收货（PO07 起的执行）开始前调放行核对（P17.7）。原来的批准与驳回路由保留（契约只加不改），经内核作决定（没带幂等键时以“任务 + 调用者 + 决定”为键）。职责分离由按账号改为按人；没有装员工组件时只能比较账号，风险照写。
- **收付款**（P4 写进它的设计）：任务类型 `erp.payment.request.approval`、`erp.payment.entry.approval`；新的按法人的付款政策（`payment_policy`，版本化）：审批人（岗位代码或指定个人）；两者都没配时提交答 `NO_APPROVER_CONFIGURED`，在向财务认领之前判断（什么也不认领）。关键字段：付款申请的收款方、账户、币种、金额与行；调拨与收付的种类、账户、金额、日期。驳回回到草稿是 `returned`；`approved` 之后、放行之前的驳回（PR03 允许）与认领失效退回草稿（PR08）、取消：`approved` 的实例 `superseded`，`running` 的实例 `withdrawn`；执行（PR05）与过账（BE02 批准即过账）前调放行核对。放行（PR04）不是审批步骤，仍按“放行人不是申请人”，比较改为按人（同一个员工投影）。
- **员工**（随 P4，只改文档）：`mdm/employee` 的设计说任职结束由 `infra/workflow` 转交任务，与协议 09 不符（重分配归流程管理方）；改成流程管理方。
- **待办的订阅**：按配置在启动时建；`component.yaml` 的 `events.subscribes` 怎样表达随配置变化的订阅，P2 用 `brickkit lint` 核对（不行就向 BrickKit 提功能请求，先列出首批已知的两个发布方）。
- **种子**（P6）：CN01 的采购审批岗位 `PUR-MGR`，ES01、US01 的采购政策不要审批；三个法人的付款审批岗位 `FIN-MGR`；`test.buyer.lead` 与 `test.finance.lead` 关联到担任这两个岗位的员工（员工的种子），所以原来的审批人照旧能批，而且是因为岗位。
