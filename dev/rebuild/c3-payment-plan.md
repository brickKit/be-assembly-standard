# C3：`erp/payment` 的子计划

阶段“按依赖顺序重建其余组件”的第三个组件（[components-plan.md](components-plan.md) 的 C3）。2026-11-10 维护者定先做 C4 `erp/finance`（收付款的事实要按财务定义的会计事实契约发布，付款认领与核销在财务）；C4 2026-11-11 完成后重定了 P0。照 C2 的做法（[c2-purchase-plan.md](c2-purchase-plan.md)）：先定首批范围与源头要补的能力，按改动的循环做，每一步先写红的测试，改坏检查，发布，真机格从空库到 L3。数据与改坏检查放 `c3-data/`。

## 依据与牵动

- 边界卡 `docs/zh/07-components/erp-finance.md#erppayment`（范围：当前重建，先做线下登记，D47）；业务流程 `docs/zh/08-flows/order-to-cash.md` 第 6 步、`procure-to-pay.md` 第 6 步；协议 05（付款认领、预收与款到发货、不针对伙伴未清项的资金流、共同规则）、06（关账的封存）、09（审批）、10（对外命令、适配器的能力声明、对账）、13、14、15、16，安全 01–09；决定 D47。
- 上下游现在的状态（2026-11-10 读文档）：
  - `erp/finance`（C4，没重建）：付款认领与付款建议的属主、核销与预收。边界卡的缺件写法：缺时付款不受未清项约束，只能线下登记并人工核对。
  - 支付与银行适配器（`integration/payment-*`、`integration/bank-*`）：不在当前重建；缺时只能线下登记。
  - `infra/workflow`（C7）：缺时审批在本组件页面里。
  - `erp/sales`：订单读取（`OrderService.Read`，任一组件）已有，收款带订单参考时可以核对。
- 仓库：`brickKit/erp-payment`（2026-11-10 维护者同意后建，挂在 `components/erp/payment`）。

## P0 的结果（2026-11-11 重定，AI 定，待复核）

C4 之后重读：财务已有付款认领（`ClaimService`：认领、续期、确认、释放、读取、到期未清项，只对本组件开放）、资金事实与会计事实的共享契约（`fund_fact.v1`、`accounting_fact.v1`，本组件在自己的流 `erp.payment` 上用 `erp.payment.fund_fact.v1`、`erp.payment.accounting_fact.v1` 发布）、核销与认领的正式化与冲回（ST02–ST05、CL07、CL09）、资金调拨与科目收付的规则键（`fund_transfer`、`bank_charge`、`bank_interest`）。所以 11-10 草稿里“不在首批”的付款认领与付款建议挪进首批。仍然只有线下登记：支付与银行适配器不在当前重建。

**首批做的**（受理、批准、执行、到账分别表达，D47）：

| 能力 | 怎样做 |
| --- | --- |
| 公司银行账户 | 按法人维护：开户行、账号（受限字段，只给有权的人看全）、币种、状态（启用、停用）；收付款都记在一个账户上 |
| 收款登记 | 线下登记：法人、公司账户、金额与币种（账户的币种）、到账日期、银行流水号、付款方（伙伴；不知道是谁时留空，财务记暂挂）、可带销售订单参考（经 `erp/sales` 的订单读取核对；财务的预收放行台账不在首批，参考只随事实带过去）；登记即到账，发布资金事实 `receipt`；登记错了用冲正（发布 `reverses_fact_id` 指向原事实的冲正事实），不改不删 |
| 付款建议 | 按法人、到期日查财务的到期未清项（`DueItems`，只列可用余额大于零的应付与客户贷方余额），勾选生成付款申请 |
| 付款申请 | 收款方（伙伴）、公司账户、金额、用途与参考号，针对一个或几个财务的未清项（应付；退款针对客户贷方余额）；**提交时认领**（每个未清项一条认领，数量是本次要付的金额；超出可用余额被财务拒绝，申请留在草稿）；审批（协议 09：审批人不是申请人，按账号）；驳回或撤回时释放认领；等审批时认领快到期由后台工作续期 |
| 付款执行（线下） | 已批准的申请执行前**确认认领**（确认后财务不再让它到期）；登记执行：实付金额（可少于申请金额，部分付款）、付款日期、银行流水号；发布资金事实 `payment`（或 `refund`），带认领与各自的实付数量，财务按实付正式化；没付的部分释放；银行退回已付的款：冲正事实（财务冲回认领、未清项重开） |
| 资金调拨与科目收付 | 公司账户之间调拨（同一法人、同一币种）、手续费与利息；经审批；发布会计事实（规则键 `fund_transfer`、`bank_charge`、`bank_interest`） |
| 银行对账（手工） | 按账户登记对账单行（用户面录入或成批提交 JSON），与已登记的收付款按金额、日期、流水号匹配；没匹配上的作为差错登记（单边、金额不符）并处理（补登记收付款、标为已核对） |
| 事件与系统面 | 资金事实与会计事实是不可遗漏的增量事实（协议 05 的共同规则，`FactService.Read` 按身份读回）；收款单、付款申请的完整状态事件 |
| 没装财务时 | 边界卡的缺件写法：付款申请不针对未清项、不认领，只线下登记，人工核对；事实照样发布（以后装上财务时按序号补取） |

**不在首批**（理由与触发）：

| 能力 | 理由 | 触发 |
| --- | --- | --- |
| 经适配器的对外支付（对外命令、结果未知时查询而不重发、恢复后不盲目再付款） | 支付与银行适配器不在当前重建 | 第一个支付或银行适配器开工；边界卡的三个验证故事随它做 |
| 关账的封存与解封 | 财务的关账批次不在首批（没有协调方） | 财务做关账批次时 |
| 预收放行认领、预付与员工借款 | 财务的放行台账、预付申请不在首批 | 财务做这些时 |
| 银行账户的期初余额与未达账项 | 协议 16 的数据迁移 | 客户上线迁移 |
| 统一待办 | `infra/workflow` | C7 |
| 外币收付（账户币种不是法人本位币） | 财务首批只按汇率快照过账，收付款要取汇率快照：`mdm/currency` 已有汇率，可以做 | P1 定：倾向做（事实带汇率快照） |

**要问维护者的**：没有（业务规则都能从边界卡、协议 05、09 与财务的契约推出；推不出的按 AI 定记在设计的未决问题）。
