# 6-01 主数据四个组件：单跑与进外壳、种子数据

## 1. 结论

- **四个主数据组件建成并发布，单跑与进外壳都跑通**：
  - `mdm/org` 3.0.1、`mdm/currency` 3.0.1、`mdm/partner` 3.0.0、`mdm/product` 3.0.0（种子修正之后：currency 3.0.2、partner 3.0.1、product 3.0.1）；契约各 `contract/v3.0.0-alpha.1`。
  - D6-S：三个安全组件、四个主数据组件、两个探针全部单跑。
  - D6-H：`be/go-infra` 3.0.20 承载三个安全组件、四个主数据组件与 Go 探针（8 个成员），Python 探针单跑。
  - 两格的剖面全部符合（剖面对探针与外壳生成流量，主数据组件本身不在剖面里，见第 5 节）。
- **种子数据经真实接口灌入，重跑不重复**：四个组件依次灌两遍，计数一致；数据库里各表的行数与唯一键数相同（第 3 节）。单跑与外壳两格都做了。
- **真机查出四处问题，单元与集成测试都没覆盖到**，已修（第 4 节）：
  - 种子重跑时给已暂停的产品设开通被拒（409）；
  - 币种种子重跑报的汇率条数少一条（计数方式）；
  - 两个种子程序头部写的数量与实际不符；
  - `cells secure` 只等探针拿到授予，外壳里的主数据组件还没拿到时种子就开始写，答 404。
- **外壳承载 8 个成员**：全部成员在约 0.5 秒内就绪（外壳的 `ready` 行 `startup_ms` 526）；进程级的键按 P2.11 只在设置了它的成员之间比较，没有冲突。

## 4. 真机查出、已修好的

| 现象 | 原因 | 修在 |
| --- | --- | --- |
| 产品种子第二遍失败：`PUT …/legal-entities/…` 答 409 `the product is suspended` | 第一遍先开通、再暂停；第二遍再设开通时产品已暂停，组件按规则拒绝 | `mdm/product` 3.0.1：种子跳过已暂停或退役的产品（它们的开通第一遍已设好） |
| 币种种子第二遍报 254 条汇率 | 汇总行数的是“这一遍写了几次”；第二遍不再写已更正的那条 | `mdm/currency` 3.0.2：已存在的更正也计数 |
| 伙伴、产品种子程序头部写 80 个伙伴、60 个产品 | 注释没随程序改 | `mdm/partner` 3.0.1、`mdm/product` 3.0.1 |
| D6-H 里 secure 一结束就灌种子，组织答 404 | 外壳里每个成员各自刷新授权视图；`cells secure` 只等探针接受令牌。没有授予时写操作答 404（看不见），列表答 200 的空列表，所以不能用读取判断 | be-acceptance：secure 对每个主数据组件发一个空请求体的写操作，等到 400（操作已授予、请求体无效，什么也不写） |

开发途中的问题（L2 与 `brickkit lint` 查出）：

- 审计的变更记录拒绝整数与空值（规范化编码只收字符串化的数字）：be-sdk-go alpha.24、be-sdk-python a21 在生成变更时保留整数（`UseNumber`）、去掉空值。
- `DB.Tx` 包装错误之后，组件里的 `err == errNone` 判断失效：四个组件改用 `errors.Is`。
- 伙伴组件的子模块目录还叫 `customer`，`brickkit lint` 报 `MANIFEST_INVALID`：父仓库里 `git mv` 到 `components/mdm/partner`。
- 文档的 lint 提醒（配置表缺必需的键、AGENTS 的托管段、代码地图的路径、README 的小节）：currency 与 org 随之升到 3.0.1。
- 刚推送的契约标签：开发时 `go.mod` 先写了 `require`，标签推送前 Go 已经问过代理，代理缓存了“找不到”二十多分钟，格的镜像构建（容器里没有 `git`）要等它过期。之后先推送标签、再写 `require`；按提交哈希问代理能立刻解析，但不刷新按版本号缓存的地址（知识库 PR #23 的反馈）。

## 5. 剖面

| 格 | 组件 | 结果 |
| --- | --- | --- |
| D6-S | `test/probe-go`、`test/probe-py`（核心剖面） | 符合；CK-OBS-05 只对外壳 |
| D6-H | `be/go-infra`（外壳剖面：CK-LC-05/06/08、CK-LC-12、CK-OBS-01、CK-LC-14、CK-OBS-05）、`test/probe-go`、`test/probe-py` | 符合 |

外壳剖面的 CK-OBS-01 核对全部 8 个成员的日志行（含四个主数据组件），CK-OBS-05 核对服务过用户面请求的成员各有请求指标（种子的请求让四个主数据组件都在其中）。时间：D6-S 2026-10-20 02:15，D6-H 02:22（secure 修好之后的那一次）。

剖面工具（`cells profile`）只对探针生成流量、对外壳观察成员；主数据组件本身没有剖面。要让业务组件也有剖面，需要按它的 OpenAPI 生成流量，记进后续。

## 6. 后续

- 业务组件自身的剖面：按组件的 OpenAPI 与操作定义生成流量（be-acceptance）。
- be-sdk-python 的记录校验仍用 fastjsonschema：实测 jsonschema-rs 0.59.0 每次校验快 4–18 倍（知识库 PR #23 的记录 20），但用在每次审计写入（约 3 µs）与每次视图刷新，不在请求的热路径上，暂不换。jsonschema-rs 原生支持 2020-12，能去掉现在“改成 draft-07”的变通；协议的 schema 用到 2020-12 的新关键字、或视图大到刷新耗时可见时再换。
- 来源方法四份同形：第 7 步的消费者适配器会暴露不一致；三个以上消费者时评估族契约。
- 组织的补取与水位回声（S6）、伙伴的供应商等角色、产品的条码与图片：按 D75 答“能力不支持”，随后续阶段实现。
- 项目的 `registry/permissions.tsv` 还是旧设计的键，随重建的注册表工具一起改。
- 组件仓库的布局与[AI 导航的标准布局](../../../docs/zh/01-conventions/05-ai-navigation.md#组件仓库的标准布局与代码地图)不一致（规则冲突，待用户决定，见交接）。
