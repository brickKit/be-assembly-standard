# 7-01 交易链五个组件：单跑与进外壳、种子数据、L3、业务负载、R2b

## 1. 结论

- **五个组件建成并发布，单跑与进外壳都跑通**：
  - 最终版本：`erp/inventory`、`erp/credit` 3.0.2，`erp/sales`、`erp/billing`、`infra/print`（Python）3.0.3；契约各 `contract/v3.0.0-alpha.1`。
  - D7-S：三个安全组件、四个主数据组件、五个交易链组件、两个探针，全部单跑。
  - D7-H：`be/go-infra` 3.0.26 承载安全与主数据组件和 Go 探针，`be/go-core` 3.0.24 承载四个交易组件，`be/py-render` 3.0.22 承载打印与 Python 探针。
  - 两格的剖面全部符合（D7-S 两个探针；D7-H 两个探针与三个外壳）。
- **种子数据经真实接口灌入**：两格各灌两遍，等后台做完之后比较各表的行数与版本号总和，相同（第 3 节）。
- **每个账号看到的行数两格一致**：数据范围按法人、部门生效，没有授予的账号全是 0。
- **L3 交易链 6 项通过**（be-acceptance 新的 `conformance/scenarios`，第 4 节）：
  - 订单从确认走到打印的账单；
  - 信用或库存拒绝时，释放另一方的预占；
  - 取消释放两边；
  - 认领与作废；
  - 部门移动经事件改变销售的可见范围。
- **负载驱动能按业务链出负载**（第 5 节）：
  - `load -flow bill` 每条链下单、确认、交货、草拟、开具；
  - D7-H 上 10 条/秒，300 条全部走完。
- **真机、实测与 R2b 查出的问题都从源头修了**（第 6 节）。
- **发布说明缺了**：本步 3.0.1 起的版本都是手打的标签，没有用 `brickkit release --notes`，标签说明只有一行版本号（第 7 节）。

## 3. 种子数据与可见范围

每格各灌两遍，`make seed-data` 约 2 分钟，重跑约 1.5 分钟。第一遍的输出：

| 组件 | 灌了什么 |
| --- | --- |
| `erp/inventory` | 5 个仓库（1 个停用），559 行期初入库 |
| `erp/credit` | 3 条政策，240 个额度（每档 60，另 60 个客户角色没有额度行），1 个暂停 |
| `erp/sales` | 5 张价格表，20 张报价，三个法人 160、30、20 张订单 |
| `erp/billing` | 74 张账单：42 张开具、17 张草稿、15 张作废；9 张打印过，3 张有副本 |

- **订单的分布**：草稿 68、已确认 82、取消 42、完成 23。确认被拒的三种原因都有：CN01 没有额度 6、超额 5、库存不足 5；ES01 超额 3；US01 没有额度 1、超额 1。
- **按账号的可见行数**：见数据目录的 `accounts.txt`。种子数据清单（`docs/zh/03-seed-data.md`）照它写。

## 4. L3 场景

`conformance/scenarios/test_trading_chain.py`。每个测试自己建单据，只依赖种子数据的固定标识。每格约 5 秒。

| 测试 | 证明 |
| --- | --- |
| 订单到打印的账单（销售、库存、信用、出账、打印） | 确认时库存多预占 3、信用占用加上含税合计；交货出库并消耗预占；草拟认领全额；开具编号；打印得到 PDF；正式化后订单完成，信用占用回到原值 |
| 信用拒绝释放库存 | 超过 20,000 的订单被拒（`over_limit`），库存预占回到原值 |
| 库存拒绝释放信用 | 北京仓预占两罐被拒（`insufficient_stock`），信用占用回到原值 |
| 取消释放两边 | 确认后取消，库存与信用都回到原值 |
| 认领与作废 | 第二张草稿没有剩余可认领，被拒；作废后可以再草拟，金额相同 |
| 部门移动 | 部门从华东挪到华南，华东的销售看不到订单、跨两区的仍看得到（事件到达约 1 秒） |

协议 04 的 RS06（最后一次提交与本地确认之间崩溃）要在一步的中间停进程，属于故障注入（套件 C），不在 L3 里。

## 5. 业务负载（冒烟）

- **做法**：`python -m cells world` 写出 CN01 的 16 个不受信用控制的客户、上海仓 8 种不追踪的货物，并补足库存；然后 `load -flow bill -rate 10 -duration 30s`。
- **结果**：300 条链全部走完，链 p50 206 ms、p99 250 ms；350 张订单（含预热）全部完成。
- **限制**：这是在省电模式下跑的，只证明能出负载，不是性能结论（`experiment-data/7-10/`）。

## 6. 查出并修好的问题

| 问题 | 怎样发现 | 修在哪 |
| --- | --- | --- |
| Debian 镜像里平台的健康检查用 `HEAD /readyz`，Python SDK 答 404，打印永远不健康 | D7-S 起不来 | 协议 P1.6 要求 `GET` 与 `HEAD` 都答（be-protocol alpha.21）；be-sdk-python a26、be-sdk-go alpha.30；BrickKit 反馈 FRB-008 |
| 打印 3.0.1 改了清单，代码的版本常量还是 3.0.0（启动时会被拒） | `be/py-render` 的成员核对测试 | 两个 SDK 的清单核对加上 `metadata.id` 与 `metadata.version`（a28、alpha.32；中间一版错用了 `metadata.name`）；Python 的组件与外壳从安装的包读版本 |
| 销售种子的三种拒绝只出现“没有额度”；“超额”的订单先被库存拒 | 按原因数一遍种子 | 三种轮流、超额用服务行（`erp/sales` 3.0.2） |
| 种子刚结束就取快照，“重跑不变”的比较失败 | D7-S 全流程 | 不是种子的问题：取消与完成的后半段还在后台跑几秒；比较前等两次快照相同（全流程脚本的 `settle`） |
| 剖面在 Debian 镜像里用 `nc` 查 gRPC 端口，误报没监听 | D7-H 第一次剖面 | 没有 `nc` 时用 python3（be-acceptance `52c125c`）；剖面只在新起的格上跑 |
| 库存的到期工作项一个事务释放多个分支，打乱全局加锁顺序，可能死锁 | R2b 的考生读代码 | 每个分支一个事务（`erp/inventory` 3.0.2） |
| 销售确认流程、取价、部门路径，出账的编号与草稿到期，打印的上限，信用的 `receivables_tracked`：文档与代码不一致或缺 | R2b | 各组件文档与注释（3.0.2、3.0.3） |

## 7. 没做完、要知道的

- **发布说明**：3.0.1 起的十几个版本没有发布说明（第 1 节）；已发布的标签不改，下一次发布起用 `brickkit release --notes`。
- **打印没有种子**：随组件提供的账单模板在启动时登记；打印快照记在出账的账单上，不需要种子。
- **身份组件的种子**：没有 `CASDOOR_URL` 时脚本报错并被 Makefile 忽略，账号已在所以无害；应改为打印一行“跳过”。没改，因为改 `infra/iam-casdoor` 牵动外壳与配置字面量。
- **按调用方的渲染配额**：记在打印设计的未决问题。
- **`be/go-core` 3.0.20 误带的 55 MB 构建产物**：仍在历史里，改写历史要用户决定。
