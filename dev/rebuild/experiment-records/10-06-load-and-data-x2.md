# 10-06 负载加倍与数据加倍（B5）

计划：[step10-plan.md](../step10-plan.md) 第 1 节 B5、5.1。问题：资源怎样随负载、随数据量增长。同时加倍分不出各自的影响，所以分开：每格先跑 7 次/秒、20 个用户，再在同一份数据上跑 14 次/秒、40 个用户（负载对负载，同一格）；一倍基线（2 万张订单、2,000 个产品、500 个客户）与两倍基线（4 万张、4,000 个、1,000 个）的格在同一晚依次跑（数据对数据，同一负载）。

## 1. 结论

**负载加倍：核数只多约一半，每千次请求的 CPU 少约四分之一；数据加倍：服务不变，数据库多 10–15%。延迟两样都不变。**

每千次请求的 CPU 秒（组件 / 基础资源 / 平台）与请求 p95：

| 格 | 数据 | 7 次/秒 | 14 次/秒 | p95 7 → 14 次/秒（ms） |
| --- | --- | --- | --- | --- |
| D9-S（单跑） | 一倍 | 29.7 / 37.1 / 16.1 | 22.4 / 28.1 / 8.8 | 51.4 → 48.7 |
| D9-X（混合） | 一倍 | 26.4 / 38.1 / 12.9 | 20.2 / 28.4 / 7.0 | 50.8 → 48.6 |
| D9-S-x2 | 两倍 | 29.8 / 42.5 / 16.2 | 22.4 / 30.8 / 8.7 | 51.0 → 49.1 |
| D9-X-x2 | 两倍 | 26.5 / 41.9 / 13.0 | 20.6 / 30.7 / 7.1 | 51.2 → 48.5 |

- **负载**：14 次/秒时组件的核数是 7 次/秒的 1.51–1.56 倍（D9-S 0.208 → 0.314），PostgreSQL 1.50–1.56 倍（0.230 → 0.358），平台 1.07–1.09 倍。按核数算，组件每多 1 000 次请求要 15.1 秒（D9-S：(0.314 − 0.208) 核 ÷ 7 次/秒），约是 7 次/秒时平均 29.7 秒的一半——另一半是不随负载变的底价（有数据空闲时组件 0.103 核）。所以每千次的 CPU 组件少 22–25%、基础资源少 24–28%、平台少 45–46%。
- **数据**：组件每千次不变（29.7 对 29.8、26.4 对 26.5），基础资源 7 次/秒多 10–15%（37.1 → 42.5、38.1 → 41.9）、14 次/秒多 8–10%，几乎全在 PostgreSQL（每千次 32.9 → 37.4–37.7 秒）；有数据空闲时 PostgreSQL 0.11 → 0.14–0.15 核（多 24–37%）。PostgreSQL 不含页缓存的内存不变（7 次/秒与空闲 555–613 MiB，两倍数据的格不比一倍的多），含页缓存的多（有数据空闲 3.2–3.3 → 3.6–4.1 GiB）。
- **延迟**：14 次/秒的 p95 反而低 2–3 ms（48.5–49.1 对 50.8–51.4），各操作的 p95 也都持平或略低（出账 61–62 对 64–65 ms；列表略高 12.3–12.6 对 11.1–11.5）；数据加倍时只有发货 p95 多约 3 ms（35.3–35.7 → 37.6–38.8）。开具到订单完成 p50 3.4–3.6 ms，不变。
- **正确性**：八段负载（四格、各两段）的请求全部成功（6 300 或 12 600 次），订单全部完成；一倍的两格结果摘要相同，两倍的两格相同。
- 同一批里混合对单跑：组件每千次 26.4 对 29.7（少 11%），与 [10-01](10-01-pooler-and-pgqueue.md) 的少 12% 一致。

所以这条链在单机上还远没到负载上限：14 次/秒时整套约 0.83 核（D9-S：组件 0.314、基础资源 0.393、平台 0.123），延迟不升。数据量对服务没有影响，只让数据库多做一些。
