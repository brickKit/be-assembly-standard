# 4-03 全面复测：固定速率下找出的底层成本与修复

## 1. 结论

**找出并修好了六处问题，其中五处所有功能测试都通过、只有按操作设了合理上限的测量才看得出。** 另有三类属于预期的上限，写进报告、不当作缺陷。修复后的第三轮复测（同一套测量：11 个阶段全部通过、408 项测量）的对比在第 5 节的“修复后”一列。

| 问题 | 怎样被发现 | 修复 | 版本 |
| --- | --- | --- | --- |
| Python 监听没关 Nagle：保持连接上每个响应多等约 40 ms | 试运行：Python 调用方的写入在客户端 46 ms、服务端只记 4 ms | 监听写明 `IPPROTO_TCP`；协议 P1.19，剖面 CK-LC-14 | 协议 `alpha.4`，`be-sdk-python` `a4` |
| 发件转发器逐条上传大载荷：一个分区每秒只能转发一两百个大事件 | 第一轮：100 KiB 事件 200/s 时发出 p50 3.6 s | 同一批的上传最多 8 个并发，发布仍按顺序；Python 复用 S3 客户端（每次新建要多花约 17 ms，一次上传从 26 ms 降到 9 ms） | `be-sdk-go` `alpha.5`，`be-sdk-python` `a5` |
| PostgreSQL 队列跟不上积压 | 第二轮：Python 订阅 50/s 就追不上（到达 p99 3–11 s） | 领取不再扫描全部积压；推进有进展时不等轮询；拆开 `OR`、按主键定位被领取的行；总线迁移 `0002` 按位置建到期索引；协议 P6.28 | 协议 `alpha.5`，`be-sdk-go` `alpha.6`，`be-sdk-python` `a6` |
| 低负载下事件反而慢：转发器每 250 ms 轮询 | 第二轮：50/s 发出 p50 约 120 ms，200/s 只要 15 ms | 提交后唤醒本成员的转发器（`AfterCommit`）；协议 P6.29 | 协议 `alpha.6`，`be-sdk-go` `alpha.7`，`be-sdk-python` `a7` |
| Python 每个请求的 CPU 偏高 | 第二轮：Python 调用方 HTTP 出站 110–160/s 就单核跑满 | 剖析找出 httpcore 每次用连接锁都导入未安装的 `sniffio`；加 `sniffio` 与 `httptools` | `be-sdk-python` `a7` |
| 测量条件不一致：对象存储桶在各格之间累积到 10 万个对象 | 第二轮：同一路径的对象存储 CPU 一格比一格高 | 准备每格时清空探针的前缀 | `be-acceptance` `6e01bc5` |

这三项的修复（T4.6c）与之后的第四至六轮、电源模式的发现，见 [4-04](4-04-d-row.md)。

第三轮途中还暴露了工具本身的一个缺陷：格的主机端口段（30000 + 端口）落在 Linux 的临时端口范围里，测量期间另跑的测试随机拿到 38090，D-H1 格起不来；改为 10000 + 端口（`be-acceptance` `542457e`），已完成的格保留、续跑。

## 2. 测了什么、为什么

计划第 4 步在启动 D 行正式测量（约 1881 项、两天）之前，先用一套短而全的测量检查整条链路：工具改动、SDK 修复与 BrickKit v1.8.2 之后，所有相关测试与全部格都跑一遍；不只看通过与否，也看性能是否合理。用户要求：“有些测试可能通过了，但性能上可能有问题，但我们没有察觉”。

## 4. 怎样跑

一个分阶段的脚本（11 个阶段），一个监视脚本每 30 秒检查一次：

1. 协议的检查；2–3. Go SDK 单元与集成测试；4–5. Python SDK 单元与集成测试（Go 一律 `-count=1`）；6. 验收工具（剖面、负载驱动、探针）；7. 三个外壳的测试与 `lint`；8–10. D-S、D-X、D-H2 由 BrickKit 部署后跑剖面检查；11. 全格测量 `experiment-cells/campaign-check.yaml`：全部 15 格，每条路径的每种操作在 50/s 与 200/s 各 10 秒（预热 3 秒）。

监视按操作类型设合理上限（`be-acceptance/conformance/cells/watch.py` 的 `LIMITS`）：固定速率下一跳或请求的 p50（echo 1 KiB 10 ms、60 KiB 25 ms、work 30 ms、写入与转发 30 ms、大事件 60 ms），事件到达 p99 2 s；固定速率下的错误、吞吐不足、测量前系统没有静止也报。第二轮起区分“预期的上限”：200/s 下只有出站并发已满或等数据库预算、并且某个组件容器的 CPU 到 1 核以上，计为“CPU 跑满”只计数不唤醒；50/s 下任何异常都报。

| 100 KiB 大事件，Go → Go，200/s，发出 | p50 3.6 s、p99 6.9 s | p50 65 ms、p99 120 ms |

| Python 调用方每请求 CPU（100/s，本机两个进程） | HTTP 出站 4.77 ms、gRPC 3.48 ms | HTTP 3.96 ms、gRPC 3.19 ms（单独实测） |

第三轮新看出的两项（待修，见 `step4-plan.md` 的 T4.6c 与留到后续的项）：

| 项 | 读数 | 原因 |
| --- | --- | --- |
| 提交后唤醒转发器的 CPU 代价 | 50/s 写入时写入方 Go 的 CPU 0.16 → 0.45 核，PostgreSQL 0.52 → 1.05 核（发出 p50 从 120 ms 降到 11 ms） | 每个事件单独走一整轮转发（租约、编号、查询、标记已发布约 4 个事务），原来 250 ms 一批 |

## 6. 观察与异常

- **为什么测试发现不了**：功能测试只问“对不对”；四处底层成本都让请求照样成功，只是慢。合理上限把“慢得离谱”变成一条会被报出的规则，这次两个问题（大事件上传、PostgreSQL 队列）都是被它抓到的。
- **PostgreSQL 队列的执行计划**：积压刚涌进来时统计信息还没更新，数据库以为只有 1 行到期，选了“两个部分索引取出全部行再排序”与“按订阅扫描全部行再逐行比对”的计划（一次 10–34 ms）；`ANALYZE` 之后走主键顺序扫描（0.1 ms）。积压暴涨正是统计信息最容易过时的时候，所以改成不依赖统计信息的写法。
- **监视自己的问题**：第一轮的监视按“每出一项结果通知一次”，几百项时太吵；改为有问题立即报、平时 5 分钟一条汇总，再按类别把预期的上限只计数（用户的规则随之写进用户级指令）。
- **流程上的偏差**：第二轮发现缺陷后没有当场停下，而是跑完以一次找全；用户指出与规则不符后，规则细化为“缺陷当场停、预期上限跑完再一次修”。
- **对象存储**：清空前缀后，对象存储每千次上传的 CPU 是否仍随格上升，看第三轮（未清空时：50/s 稳定在约 6 CPU 秒/千次，200/s 从 5.1 升到 11.2）。

## 7. 影响

- 协议：P1.19、P6.28、P6.29；总线迁移 `0002`。
- SDK：`be-sdk-go` `alpha.5`–`alpha.7`、`be-sdk-python` `a4`–`a7`；探针 3.2.2–3.2.4；外壳到 3.0.4／3.0.5。
- 测量工具：合理上限、预期上限的分类、每格清空对象存储、端口段改到 10000 + 端口。
- 文档：底层选择的“部署时可切换的底层实现”；锁定技术栈的 Python HTTP 一行；AI 编码习惯的“性能与可读性”。
- 留到后续：Go 每请求 CPU 的剖析、Python 的 `uvloop` 与 aiohttp 实验、消息运输文档的吞吐数字（`step4-plan.md` 的“留到后续的项”）。
