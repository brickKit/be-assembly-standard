# 5-02 带真实身份、授权与审计的格：剖面与通信代价

## 1. 结论

- **三个安全组件在格里跑通，单跑与进外壳都可以**：
  - D5-S：身份、授权、审计三个组件单跑，Go 与 Python 探针单跑并开启守卫（`PROBE_GUARD`）。
  - D5-H：`be/go-infra` 外壳承载三个安全组件与 Go 探针，Python 探针单跑。
  - 两格的剖面全部符合（探针 3.2.19、外壳 3.0.19，2026-10-20 00:02）。
- **真机查出七处问题，单元与集成测试都没覆盖到**，全部已修好并发布（第 3 节）：
  - 两处让组件起不来：授权组件的注册表多写了 `mount: file`；外壳把进程级的键要求成全部成员一致。
  - 一处让授权组件拒绝探针的定义：修订域保留了组件 ID 里的 `-`。
  - 两处是日志与就绪不合协议：启动阶段的日志不是结构化行；`ready` 行写得比真正就绪早。
  - 两处在检查与格工具：剖面检查的前提，以及格工具认不出 D5 开头的格。
- **带真实授权之后的通信代价**（第 4 节，performance 电源模式，每格两遍）：
  - **HTTP**：一跳的 p50 多 0.15–0.35 ms；每千次 CPU（调用方加被调方）多约 0.5 秒，也就是每个请求约多 0.5 ms CPU，用于两端核验令牌、检查操作。
  - **gRPC**：几乎不变（p50 差 0–0.1 ms，每千次 CPU 多 0.2–0.4 秒）。系统调用本来就是 mTLS，多出来的只是操作检查。
  - **安全组件进外壳**：与单跑基本相同，数据库连接峰值从 20 降到 10。
- **对照格第 2 遍的事件路径变慢**：变慢的是发布一侧，原因在环境，详见第 5 节。

## 2. 测了什么

| 格 | 组成 | 作用 |
| --- | --- | --- |
| D5-S0 | Go、Python 探针单跑，不带安全组件 | 对照 |
| D5-S | 三个安全组件与两个探针全部单跑，探针开守卫：每个请求带身份组件签发的令牌，每个探针持有授权组件的视图，审计记录转到审计组件 | 带真实安全的单跑 |
| D5-H | `be/go-infra` 承载三个安全组件与 Go 探针，Python 探针单跑 | 安全组件进外壳 |

起格的步骤：
1. `cells create`、`prepare`、`brickkit build`、`up`；
2. `cells secure`：两个测试用户经身份组件的开发换取各登录一次，绑定平台主体；安装认领指定管理员，`up` 重启授权组件；管理员经生效点把每个探针的每个操作授予负载用户。

剖面用 `cells profile`。测量用 `campaign-round5a.yaml`：三格交替各两遍，每种操作 50/s 与 200/s 各 10 秒，performance 电源模式（运行脚本记下原来的 power-saver，结束时恢复）。

## 4. 通信代价

调用（`campaign-round5a.yaml`，三格交替各两遍，取两遍的中位数）。CPU 是调用方与被调方每千次的 CPU 秒之和：

| 路径 | 操作 | 负载 | p50 ms：对照 / 单跑 / 外壳 | p99 ms：对照 / 单跑 / 外壳 | 每千次 CPU 秒：对照 / 单跑 / 外壳 |
| --- | --- | --- | --- | --- | --- |
| Go → Python | echo 1 KiB HTTP | 50 | 1.10 / 1.42 / 1.40 | 1.50 / 1.92 / 1.93 | 2.10 / 2.68 / 2.97 |
| Go → Python | echo 1 KiB HTTP | 200 | 0.92 / 1.26 / 1.36 | 1.43 / 1.91 / 1.98 | 1.47 / 2.01 / 2.17 |
| Python → Go | echo 1 KiB HTTP | 50 | 0.80 / 0.95 / 0.93 | 1.09 / 1.28 / 1.33 | 2.37 / 2.93 / 3.12 |
| Python → Go | echo 1 KiB HTTP | 200 | 0.68 / 0.85 / 0.81 | 1.02 / 1.27 / 1.25 | 1.71 / 2.28 / 2.25 |
| Go → Python | echo 60 KiB HTTP | 200 | 1.74 / 2.09 / 2.06 | 2.55 / 2.98 / 3.07 | 2.84 / 3.34 / 3.35 |
| Go → Python | echo 1 KiB gRPC | 50 | 1.50 / 1.45 / 1.52 | 2.28 / 2.28 / 2.15 | 3.03 / 3.20 / 3.47 |
| Go → Python | echo 1 KiB gRPC | 200 | 1.00 / 1.13 / 1.01 | 1.82 / 1.96 / 1.82 | 1.83 / 2.24 / 2.10 |
| Python → Go | echo 1 KiB gRPC | 200 | 0.93 / 0.93 / 0.92 | 1.43 / 1.43 / 1.39 | 2.18 / 2.52 / 2.56 |
| Python → Go | work 10 ms HTTP | 200 | 10.80 / 10.97 / 10.97 | 11.66 / 11.68 / 11.73 | 11.82 / 12.49 / 12.51 |

- **HTTP 一跳**：带守卫后 p50 多 0.15–0.35 ms，每千次 CPU 多约 0.5–0.6 秒。驱动打到第一个探针、第一个探针转发原用户的令牌给第二个，两端都要核验令牌（EdDSA）、对照视图检查操作。
- **gRPC 一跳**：p50 差在 0.1 ms 之内，每千次 CPU 多 0.2–0.4 秒。对照格的系统调用也是 mTLS，带守卫后多的只是操作检查。
- **外壳**：安全组件进外壳与单跑没有可分辨的差别（差在两遍的波动之内）；外壳多承载成员时的 CPU 略高，同样在波动之内。
- **Python 的 work 200/s** 在三格里都卡在 CPU 上（错误率约 0.55，D 行的预期上限），不计入比较。
- **资源**：组件的常驻内存对照 136 MiB、单跑 147 MiB、外壳 151 MiB；数据库连接峰值对照 8、单跑 20、外壳 10（三个安全组件各自的池合成了外壳的一个池）。

事件（`campaign-round5b.yaml`，对照与单跑交替各两遍，到达时间 p50/p99 ms）：

| 路径 | 操作 | 负载 | 对照第 1 遍 | 对照第 2 遍 | 单跑第 1 遍 | 单跑第 2 遍 |
| --- | --- | --- | --- | --- | --- | --- |
| Go → Python | 写入 | 200 | 3.2/5.6 | 3.2/6.2 | 3.3/6.0 | 3.7/7.4 |
| Go → Python | relay | 200 | 3.4/6.3 | 3.6/9.8 | 3.5/8.4 | 3.5/7.5 |
| Go → Python | 大事件 | 200 | 24.7/47.9 | 26.1/50.9 | 25.6/48.9 | 27.1/72.7 |
| Python → Go | 写入 | 200 | 5.9/26.3 | 6.9/25.5 | 8.2/31.2 | 17.4/45.5 |
| Python → Go | relay | 200 | 12.1/38.4 | 11.2/41.2 | 28.3/85.8 | 14.8/50.7 |
| Python → Go | 大事件 | 200 | 47.1/95.3 | 48.0/111.0 | 52.6/126.8 | 51.3/112.1 |

- **Go 写入方**：带守卫与否没有差别。
- **Python 写入方在 200/s**：带守卫后到达变慢，而且两遍之间差得多（写入 p50 8 与 17 ms，relay 28 与 15 ms）。Python 在 200/s 本来就站在 CPU 上限边上（D 行），核验令牌每次多花的 CPU 让它更靠近上限，排队就时有时无。50/s 没有差别。归为预期上限：Python 组件在 200/s 写入时需要订阅并发或更多副本（D 行的结论同样适用）。

## 5. 对照格第 2 遍的事件路径

第一轮第 2 遍的对照格（不带安全组件）里，三项事件路径比第 1 遍慢得多，监视脚本当场报出：

| 项 | 第 1 遍 | 第 2 遍 |
| --- | --- | --- |
| Go → Python 大事件 200/s，到达 p50 / p99 | 27.5 / 596 ms | 2549 / 4452 ms |
| 同上，发布 p50 / p99 | 21.8 / 612 ms | 157 / 3393 ms |
| Go → Python 大事件 50/s，到达 p99 | 13.5 ms | 98 ms |
| Go → Python relay 200/s，到达 p99 | 6.6 ms | 46 ms |

- **慢在发布一侧**：大事件要先把载荷上传到对象存储。当时 RustFS 占约 13% CPU；同机还有远程桌面（约 14%）与编辑器（约 12%）在后台运行。
- **复测没有复现**：第二轮（第 4 节）同一格同样的操作两遍都正常，例如大事件 200/s 的到达是 24.7/47.9 ms 与 26.1/50.9 ms。
- **定性为环境原因，不是代码缺陷**：多半是对象存储在对象多时的周期性扫描（D 行记过，RustFS 约每 60 秒一次），叠加同机的其他负载。第一轮第 1 遍的大事件 200/s p99 已有 0.6 s，同属这一类。
- **影响**：第一轮里对照格的大事件与 relay 不用作比较，事件路径的代价以第二轮为准。

## 6. 其他发现

- **安装认领要两步启动**：认领要的是平台主体，可平台主体要到第一次登录时才由身份组件绑定，所以格先起、先登录，再写认领、重启授权组件。安全 08 按外部身份认领的设计能免去这一步，留给后续评估。
- **三个安全组件的用户面没有 OpenAPI**：第 5 步的契约说明写的是“由组件仓库里的 OpenAPI 描述”，实际没有写。第 6 步的组件起由测试核对路由与 OpenAPI 一致，三个安全组件随后补上。
- **审计查询没有游标**：只按条数截取，与协议 14 的“只用游标分页”不符；随审计组件补全时改。
- **发布脚本的坑**：`set -e` 不因 `&&` 链中间的失败而退出，守卫拒绝时会跳过提交，把标签打在旧提交上；`! cmd` 同样不触发。之后的脚本每条链都以显式的失败退出结尾。
- **Python 的一项集成测试偶发**：`test_members_share_one_pool_and_never_each_others_schema` 在一次完整集成测试中没有在 5 秒内就绪，之后整套连跑 3 遍、单独跑 6 遍都通过；已加上失败时打印外壳输出的诊断，断言不变。
