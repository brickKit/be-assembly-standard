# 10-08 基础资源放在集群外与集群内（B7）

计划：[step10-plan.md](../step10-plan.md) 第 1 节 B7、5.4。问题：K 行（单节点 minikube）一直让组件的 Pod 访问宿主机 Docker 里的基础资源（PostgreSQL、NATS、RustFS、Casdoor）；把这四个也放进同一个集群（命名空间 `be-base`）开销差多少。同一批：先集群外（参照），再导出 Casdoor 的库、停 Docker 的基础资源、在集群里起同样的四个，跑集群内的格，最后撤掉集群里的、恢复 Docker 的。

## 1. 结论

**放进集群后整套每千次少约 9%，延迟不变，但这个数混了两个因素，不能全算在“放进集群”上。** 业务结果相同。

每千次请求的 CPU 秒（7 次/秒）：

| 格 | 组件 | 基础资源（PostgreSQL / NATS / RustFS / Casdoor） | 集群的平台 | Docker 守护进程 | 合计 | p50 / p95（ms） |
| --- | --- | --- | --- | --- | --- | --- |
| K9-X（基础资源在 Docker） | 25.4 | 40.0（34.8 / 1.9 / 2.7 / 0.7） | 13.9 | 8.8 | 88.1 | 22.9 / 51.9 |
| K9-X-cb（基础资源在集群里） | 24.5 | 35.0（33.4 / 1.2 / 0.1 / 0.3） | 15.6 | 5.1 | 80.2（少 9%） | 22.2 / 51.1 |

- **省下的主要是 Docker 那一份**：基础资源不在 Docker 里了，Docker 的守护进程（这时只剩 minikube 节点这个容器与 Traefik）每千次 8.8 → 5.1 秒；集群的平台（节点里除去 Pod 的部分：kubelet、控制面、kube-proxy、CNI）反而多 1.7 秒（13.9 → 15.6），基础资源的流量改走集群网络。两项相抵，净省约 2 秒。
- **基础资源少的 5 秒大半来自数据状态不同，不来自位置**：Docker 里的基础资源用了很久，RustFS 的桶里攒着之前各轮的对象，空闲时也在后台扫描（每千次 2.7 秒、空闲约 0.015 核）；集群里的是新起的、只导入了 Casdoor 的库，RustFS 几乎是空的（0.06 秒、0 核），PostgreSQL 推测也没有宿主机那一份里之前的其他库（没有核对）。K9-X 有数据空闲时 RustFS 0.015 核、PostgreSQL 0.113 核。PostgreSQL 本身 34.8 对 33.4 秒（少 4%），NATS 1.9 对 1.2 秒。
- **延迟不变**：p50 22.9 对 22.2 ms、p95 51.9 对 51.1 ms，各操作的 p95 持平；开具到订单完成 p50 3.7 对 3.4 ms。
- **内存**：集群的平台多约 0.7 GiB（含页缓存 1.7 → 2.4 GiB，不含 0.68 → 0.75 GiB），Docker 一份少约 0.1 GiB。
- **正确性**：两格的 6 300 次请求全部成功，订单全部完成，结果摘要相同（集群内的格以集群外的为参照）。

对选择的含义（给维护者）：基础资源放进单节点集群，CPU 与延迟上看不出值得一提的差别（真正因位置省下的约 2–4 秒、2–5%，在这一格一遍的波动附近）；内存上集群的平台多约 0.7 GiB。要比得更干净，得让两边的基础资源从同样的空状态起（集群外也新起一套），这次没有做。
