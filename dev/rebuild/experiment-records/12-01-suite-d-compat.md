# 12-01 套件 D：多版本兼容（D 行七格与其余五种形态的冒烟）

计划：[step12-plan.md](../step12-plan.md)。问题：版本不整齐时（滚动升级的窗口、客户基线里各组件升级的节奏不同、外壳与单跑的组件用着不同的 SDK），哪些组合照常工作，哪些被明确地拒绝，有没有“看起来成功、其实错了”的组合。V1–V7 是正确性测试，不是性能测量：没有切电源模式，计时读数照记、不比较。

## 1. 结论

**线上兼容成立：SDK 版本不同的组件之间，调用、错误、截止时间、追踪与事件都照常互通；只做加法的契约与迁移，新旧两版可以并存。** 测的过程中查出七处“版本不整齐时会出错”的地方（G1–G7），六处已修，一处（G7）要 BrickKit 配合；另有一处设计上的空白（F1，破坏性迁移之后没有机制拒绝旧版）维护者定为不急。

| 格 | 问的 | 结果 |
| --- | --- | --- |
| V1 | 同一组件新旧两版共用库与流 | 扩展迁移时两版都能写，新版读得到旧版的行，消费方收到两版的事件。原先旧版的迁移遇到更新的库就失败、旧版起不来、`brickkit up` 中止（G4）；修好后第二次 `up` 正常，D、P、K 三种形态都通过。收缩迁移之后旧版的写入答 500 `INTERNAL`（列不存在），不是明确的拒绝（F1，未改） |
| V2 | 契约新旧互调 | 不认识的请求字段被忽略，旧消费者照常消费带新字段的事件，新类型被运输过滤、订阅不卡住。调用旧版没有的方法原先答 500 `INTERNAL`、调用旧版没有的路由答 404 `NOT_FOUND`（G1、G2）；修好后系统面答 501 `CAPABILITY_UNSUPPORTED` 并写明依赖与方法；用户面对还没升级的被调方仍是 404（被调方的回答不改写，测试标为预期失败） |
| V3 | 事件新旧（投影） | 已有部门的未知动作让投影那一行先标为不完整、随后从 `mdm/org` 取回；法人的事件不进部门投影；多一个字段的 `changed.v1` 照常生效；没有死信。开测前读代码发现，按类型订阅的投影根本收不到来源新加的动作（销售改为按聚合订阅，3.0.16） |
| V4 | Go SDK 版本不同（alpha.23 ⇄ alpha.37） | 两个面、两个方向的调用、事件与转发、错误原因与域、截止时间逐跳缩短（剩 200 毫秒时 150 毫秒后 504 `DEADLINE_EXCEEDED` 并点名依赖，剩 40 毫秒时不发出）、追踪与请求编号都一致。六种形态都跑了：D、P、K、L 全过；LD、LP 只有大事件不通（G7） |
| V5 | Python 旧 SDK（a20）⇄ Go 新 SDK（alpha.37） | 同 V4，全过 |
| V6 | 两个外壳用不同的 SDK；同一外壳里成员要求不同的 SDK | 两个 Go 外壳（alpha.37 与 alpha.35）各承载一个探针，互通。同一个 Go 模块里一个成员要求 alpha.23、一个要求 alpha.37，构建照常成功，二进制里只有 alpha.37（F4）：Go 的模块图本身保证“不早于任何成员的要求”。Python 外壳用 `override-dependencies` 统一 SDK，可能比成员的要求旧，原先没人检查（G5）；现在外壳启动时核对成员声明的最低版本（P1.21） |
| V7 | 外壳编进的成员版本与项目声明的不同 | `brickkit up` 拒绝，点名外壳、成员与两个版本，给出三种修法；`brickkit lint` 不报 |

另外两处与版本无关、在本步的格里才第一次碰到的问题：Python 外壳里一个成员在事件循环上做 CPU 工作会卡住全部成员（G6）；混合形态里大事件的取件凭证两边取不到（G7）。

对选择的含义（给维护者）：

- **滚动升级可以做，但只对扩展迁移成立。** 收缩迁移（删列、改名）之后，还在跑的旧版写入会撞上 500。维护者定的规则是破坏性变化所有组件一起更新；违规时的兜底（库里记“最低可运行版本”）没做（F1）。
- **外壳里的 SDK 版本由外壳的构建决定**，成员按自己钉的版本测过、在外壳的版本上运行，靠 SDK 在同一主版本内向后兼容。Go 由构建保证、Python 由启动检查保证（P1.21）。
- **混合形态（一部分组件以本机进程运行）要求对象存储在部署里只有一个名字**（P6.14）；开发机上要让本机也能解析 `host.docker.internal`，并等 BrickKit 的 FRR-020。

## 3. 发现与处理

| # | 发现 | 怎样处理 |
| --- | --- | --- |
| F1 | 破坏性迁移之后没有机制拒绝旧版写入：旧版撞上 500 `INTERNAL` | 维护者定为不急；规则是破坏性变化所有组件一起更新。兜底的做法（收缩迁移在库里记最低可运行版本，旧版启动时以 78 拒绝）留在计划第 8 节。G4 修好之后，旧版的迁移遇到更新的库会按成功结束，所以收缩之后回退一个组件，它能起来、到读写时才报 500：兜底比修之前更有用 |
| F2 | 线协议没写消费者遇到未知字段与类型怎样做 | P6.33（`be-protocol` alpha.29）：忽略未知字段；按类型订阅的只收列出的类型；读模型按聚合订阅，不认识的类型标为不完整并取回 |
| F3 | 兼容矩阵没有 | `be-protocol` 的 `COMPAT.md`（alpha.29 起，之后每版加一行） |
| F4 | 同一外壳里的 SDK 版本由 Go 的模块图统一 | V6 第二部分证实；SK09、协议 17、18 按实际改写：进程里只有外壳构建出的一个 SDK，不早于任何成员的要求 |
| F5 | 探针单跑时的 SDK 很旧，进外壳就变新，第 4、9、10 步用探针比较单跑与外壳时两边 SDK 不同 | **没做**：要用只升 SDK 的探针重量一格第 9 步的基础开销（性能测量，要 performance 模式与安静的机器），留在计划 9.1 |
| G1 | 新版经系统面调旧版没有的方法，旧版的 gRPC 服务器答 `Unimplemented`（无 ErrorInfo），调用方当作 500 `INTERNAL` | P3.10（没注册的方法或路由答 501 `CAPABILITY_UNSUPPORTED`）、P4.29（调用方把不带 ErrorInfo 的 `UNIMPLEMENTED` 当作它）；`be-protocol` alpha.30，`be-sdk-go` alpha.38、`be-sdk-python` a34 |
| G2 | 经用户面调旧版没有的路由答 404 `NOT_FOUND`，与“看不见的记录”同一个原因 | 同上；对还没升级的被调方，调用方不改写它的 404，测试标为预期失败 |
| G3 | （计划里没有编号，记录时补上）读代码发现销售的部门投影按类型订阅，`mdm/org` 以后加的动作被运输过滤，投影悄悄过期（PJ36 在实现里从不发生） | `erp/sales` 3.0.16 按聚合订阅，不认识的动作标为不完整，新的队列工作项立刻取回；改过滤条件要换订阅名（持久订阅保留原设置，P6.18），订阅名改为 `org-unit-events` |
| G4 | 旧版的迁移遇到比自己新的库就失败（`no migration found for version 2`），旧版起不来、`brickkit up` 中止 | P5.32（遇到被较新版本迁移过的库什么也不做、按成功结束），两个 SDK；BrickKit 文档补了这条要求（FRR-019，v1.10.5，已关闭） |
| G5 | Python 外壳不检查 SDK 是否早于成员的要求；连带查出探针的包版本从 3.2.21 起停在 3.2.20，`be/py-render` 3.0.29、3.0.30 一承载探针就拒绝启动 | P1.21（`be-protocol` alpha.32）：成员在包元数据里声明 `be-sdk>=<钉的版本>`，外壳启动时核对，没有声明或不满足的拒绝（`be-sdk-python` a35）；探针的版本改为读包元数据；`make pin-check` 查 Python 组件的包版本与声明的最低 SDK；`be/py-render` 的测试用启动器自己的检查核对编进来的成员 |
| G6 | Python 外壳里两个成员共用一个事件循环，被调方在循环上烧 500 毫秒 CPU，调用方的 150 毫秒尝试上限触发不了，0.5 秒后答出自己请求的 504、点不出依赖 | 合并安全加第四问（Python 模块不在事件循环上做 CPU 密集或阻塞的工作）、根 `AGENTS.md` 的易错点。探针先改成线程（3.2.27）：仍争 GIL，计时器晚 30–180 毫秒，一次又答出自己的超时；再改成探针自己管的工作进程（3.2.28），烧 CPU 时循环最多晚 0.2 毫秒，两轮通过。`ProcessPoolExecutor` 不能用：它的子进程会重新导入外壳的主模块。`infra/print` 的渲染本来就在工作进程里 |
| G7 | 混合形态（LD、LP）里大事件的预签名凭证带着生产方看到的对象存储主机名（容器 `host.docker.internal`、本机进程 `localhost`），签名覆盖主机名，两边互相取不到，成为死信 | P6.14 写明部署里每个组件的 `OBJECT_STORE_URL` 用同一个主机名（`be-protocol` alpha.33）；维护者在本机 `/etc/hosts` 加了 `127.0.0.1 host.docker.internal`，实测同一个地址在本机进程、Docker 容器、无根 Podman 容器都取得到，换成 `localhost` 答 403（`g7-hostname/`）；BrickKit 本地模式会把这个名字改写成 `localhost`，提了 FRR-020（只在本机解析不了时才改写），新版本后重跑 LD12-V4、LP12-V4 |

## 5. 没测的、与计划不同的、中间的失败

- **F5 的对照没做**（第 3 节）。交接时漏写进剩余清单，2026-11-01 核对时补上。
- **V6 第二部分与 V7 的原始输出当时没存**，2026-11-01 下午在新的版本上重做并存下：V6 第二部分的版本与当时相同；V7 当时是 `be/go-core` 3.0.39（编进销售 3.0.15）配上声明销售 3.0.16 的项目，重做时用 3.0.41（编进出账 3.0.16）配上声明出账 3.0.17 的项目（把销售换回旧版会先撞上它对货币旧版本的精确依赖，测不到外壳这一层），结果与当时记下的一样。
- **G6 的几次手动调用**当时只打在终端上，抄进了 `p121/manual-calls.txt` 并注明来源。
- **中间的失败都是工具的问题**，结果不计：
  - `pairs/`：第一次跑 V4、V5，Python 的几项“超时慢了”：被调方在调用方放弃后仍做完 500 毫秒的计算，Python 在事件循环上做，下一个请求要等它；测试改为两次之间等 0.7 秒（`pairs2/`）。这与 G6 是同一个原因，当时只当作测试的顺序问题处理。
  - `v1-try1`、`v3-try1`：测试缺环境变量；`v1-try2`：升级到收缩版本那一步失败（随后查明是 G4）。
  - `v6-try1`–`try4`：格工具第一次碰到两个不同版本的外壳：同一成员列了两次、删除要写版本、删一个版本连带删了另一个、删除之后部署文件还留着已删的兼容版本，都已修好（`be-acceptance` 1.0.13）。
  - `smoke-try1`：先起了 K 行的节点，它发布了全部组件的宿主机端口，其余各行的容器与转发器绑不上；改为 K 行最后。
  - `smoke-try2`：追踪测试只读 `docker logs`，P 行与 L 行读不到被调方的日志；加了按引擎读日志的 `cells/logs.py`（本机进程读会话日志）。
  - `smoke/` 的 K12-V4：NodePort 刚建好就调用，第一次被重置；`nodeports` 改为等每个宿主机端口都能应答（`be-acceptance` 1.0.18），`smoke-k2/` 重跑通过。
  - `p121/py-r2/`：G6 的线程版本，一项仍失败（第 3 节）。
- **遍数**：每格一遍（D12-py-a35 修好后两遍）。都是有或没有的断言，没有比较计时。
