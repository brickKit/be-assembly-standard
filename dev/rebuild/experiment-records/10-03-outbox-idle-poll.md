# 10-03 发件转发器只轮询有行的分区（P6.32）改前改后

计划：[step10-plan.md](../step10-plan.md) 5.8。起因：一格单跑空闲时，数据库每秒约 1 650 条语句，85–90% 来自发件转发器每 250 ms 对每个分区做一次完整的编号事务，发件表空着也照做。P6.32 改成轮询先用一条只读语句找出有行要转发的（流，分区），只对它们编号与转发；计数的核对（语句每秒约 1 650 → 634 条）在计划里。本记录量 CPU：改前与改后放在同一批，只在这一批内比。

## 1. 结论

**空闲时整套少约三分之一的 CPU，负载时每千次请求少 17%；延迟、提交后的唤醒与结果都不变。**

| 段 | 部分 | 改前（D9-S-sdk35） | 改后（D9-S） | 变化 |
| --- | --- | --- | --- | --- |
| 空库空闲（核） | 基础资源 | 0.171 | 0.102 | −40% |
| | 其中 PostgreSQL | 0.147 | 0.077 | −48% |
| | 组件 | 0.143 | 0.093 | −35% |
| 有数据空闲（核） | 基础资源 | 0.213 | 0.145 | −32% |
| | 其中 PostgreSQL | 0.187 | 0.119 | −36% |
| | 组件 | 0.151 | 0.104 | −31% |
| 7 次/秒（每千次 CPU 秒） | 基础资源 | 49.2 | 38.8 | −21% |
| | 其中 PostgreSQL | 44.0 | 34.7 | −21% |
| | 组件 | 36.8 | 29.9 | −19% |
| | 平台 | 16.2 | 16.2 | 不变 |
| | 合计 | 102.2 | 84.9 | −17% |

- 改动碰不到的部分在这一批里不变：平台（Docker 的守护进程）空闲都是 0.104 核、负载都是 16.2 秒，NATS、Casdoor 的读数也相同，所以这一批前后两格的条件一致。差别（19–48%）远大于 D 行两遍之间的波动（组件每千次 6.5%，[9-01](9-01-other-rows-chain.md)）。
- 每个组件的 CPU 都少了：负载时空闲成分大的组件少得多（`mdm/currency` 14.5 → 8.7 秒、`mdm/partner` 16.0 → 10.7、`erp/billing` 19.3 → 14.2），业务最重的 `erp/sales` 60.5 → 55.7；`infra/iam-casdoor` 不发事件，4.4 对 4.4。
- 延迟看不出差别：p50 22.7 对 23.1 毫秒，p95 50.2 对 52.3（在 D 行两遍的 3.4 毫秒以内）；开具到订单完成 p50 都是 3.6 毫秒、p95 4.6 对 4.5，提交后的唤醒（P6.29）照常。
- 正确性：两格 6 300 次请求全部成功，315 张订单全部完成；结果摘要相同。
- 组件的内存：不含页缓存的部分相同（负载时 378 对 377 MiB）。含页缓存的合计改后多约 100 MiB，每个容器多 6–9 MiB、全是页缓存：页缓存记在最先读到那个文件的 cgroup 上，与进程自己的内存无关，不比较。

还剩的空转：后台任务的领取轮询（每个组件每秒约 8.5 次，计划 5.8 的计数），后台任务有按时间排定的，不能照搬“没有就跳过”，是下一个候选，未改。
