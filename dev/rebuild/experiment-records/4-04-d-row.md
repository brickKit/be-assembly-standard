# 4-04 D 行的结果：性能跟进之后的复测、电源模式与几处唤醒、往返和领取

## 1. 结论

- **T4.6c 的修复在全格上兑现**：第三轮看出的三项（提交后唤醒转发器的代价、PostgreSQL 队列每条消息的往返、Python 的大事件路径）与 Python 的出站 HTTP，第四轮全部改善，最大的一项从秒级降到几十毫秒（第 5.1 节）。
- **电源模式决定了一半的数字**：同一份代码、同一套测量，performance 与第四轮（多半是 power-saver）相比，延迟与每次操作的 CPU 约为 0.6 倍；200/s 下有 Python 参与的事件路径，power-saver 下排队几秒，performance 下几十毫秒（第 5.2 节）。从此每一轮都记下电源模式，报告的数字全部在 performance 下。
- **D 行测量里又找到并修好三处，全部只有测量看得出**：
  - 事件转成后台任务再转成调用（relay），全部格 p50 约 250 ms：任务执行器提交后不唤醒（P7.21）。修好后 7–10 ms（第 5.3 节）。
  - PostgreSQL 队列的到达下限约 55 ms：订阅方只靠 100 ms 轮询（P6.30，发布时 `NOTIFY` 唤醒）。修好后 50/s 写入到收到 6–9 ms。第一版一条通知唤醒订阅的全部读取者，并发 4 时数据库 CPU 翻倍，改为一条通知只唤醒一个（第 5.4 节）。
  - Python 的每个事务在归还连接时多一次会话重置的往返：asyncpg 的默认行为，占 PostgreSQL 每个短事务约 27% 的 CPU。改为事务入口拒绝会话级语句、连接池不再重置（P5.30）（第 5.6 节）。
- **订阅并发是 Python 吞吐的开关**：Python 订阅在 PostgreSQL 队列上逐条处理，200/s 时大事件排队约 2.5 s；同时处理 4 条后为 40 ms，代价是数据库 CPU（第 5.5 节）。默认值保持 1（用户 2026-10-19 定），取舍写进消息运输的正式文档；部署方用配置项 `BUS_SUBSCRIPTION_CONCURRENCY` 调大（P6.31，第十轮验证），依赖到达顺序的订阅由组件声明、始终逐条处理。
- **后台任务的领取不随积压变慢**：领取语句用 `OR` 跨两个部分索引时，到期的任务一多就整批取出再排序，2 万条到期时每次领取约 8 ms；改为先取过期的租约、再按到期时间取最早的一条，各走自己的有序索引（P7.22），约 1.3 ms，与 40 条时相当（第 5.8 节）。
- **两天的正式测量没有跑**：用户 2026-10-18 定下“测量按小时算，不按天”。D 行的结果由几轮各约 1 小时的短测拼成，每个数字写明来自哪一轮；全部格都在 performance 下测过一遍。

## 5. 结果

### 5.1 T4.6c 的修复，第三轮对第四轮

两轮的电源模式都没有记录（同一台机器、同一天）；下表的差别远大于电源模式的影响。

| 项 | 第三轮 | 第四轮 | 修复 |
| --- | --- | --- | --- |
| Python 调用方 HTTP echo 1 KiB，200/s，一跳 p50 | 226 ms（p99 1.6 s） | 1.2 ms | 出站改用 aiohttp |
| Python → Python 大事件，200/s，写入请求 p50 | 1.27 s | 83 ms | 自签 SigV4、出站 aiohttp |
| Go → Go 大事件，200/s，到达 p50 / p99 | 1.84 s / 2.51 s | 70 ms / 246 ms | 转发器只转发写过的分区；Go 自签 SigV4 |
| Python 外壳内、PostgreSQL 队列的大事件，50/s，到达 p50 / p99 | 2.43 s / 3.16 s | 55 ms / 151 ms | 同上，加队列先领取后推进 |
| Go 写入 50/s：写入方 CPU / PostgreSQL CPU | 0.45 / 0.80 核 | 0.20 / 0.34 核 | 唤醒只转发写过的分区（每个事件约 25 个事务降到 2 个） |

### 5.2 电源模式

第五轮对第四轮，同一版本、同一配置，144 项（`experiment-data/4-03/round5/vs-round4.txt`）：

| 指标 | 第五轮 ÷ 第四轮（中位数） | 范围（p10–p90） |
| --- | --- | --- |
| 一跳 p50 / p99 | 0.56–0.60 | 0.44–0.98 |
| 请求 p50 / p99 | 0.62–0.66 | 0.13–0.92 |
| 事件到达，50/s | 0.56–0.59 | 0.27–0.68 |
| 事件到达，200/s | 0.17–0.19 | 0.00–0.62 |
| 调用方每千次的 CPU | 0.56–0.64 | 0.49–0.83 |
| 探针与外壳的常驻内存 | 不变（2 MiB 以内） | — |
| 空闲 CPU | 约 0.5 | — |

- 固定 10 ms 计算的 `work` 几乎不变（约 0.93）：它按墙钟计算，不随频率缩短。
- 200/s 的事件到达差得最多：power-saver 下 Python 参与的事件路径排队（Go → Python 大事件 p50 4.5 s 对 28 ms），performance 下不排队。第四轮看到的“Python 事件的上限”多半是电源模式造成的。
- 除去 `work` 与排队的项，同一种操作在各路径上的倍数在约 ±15% 内，这同时包含两轮的随机误差，是每项随机误差的上界。
- 版本之间的对比不受影响：版本二分与休眠验证都在同一种模式下成对跑（`experiment-data/4-03/power/`）。新版低负载下写入延迟略高（约 0.1–0.5 ms），是做的事更少、CPU 睡得更深；让每个核都不进深度休眠（每核一个最低优先级、每 50 µs 醒一次的进程）后差别几乎消失（performance 下 +0.48 ms 缩到 +0.11 ms）。

### 5.3 后台任务的唤醒（P7.21）

第五轮（修复前）对第六轮（修复后），同一电源模式，D-S 与 D-H1 的 16 项（`experiment-data/4-03/round6/relay-round5-vs-round6.txt`）：

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| relay 完成，50/s，p50 / p99 | 251–263 ms / 499–510 ms | 7.4–9.8 ms / 10–14 ms |
| relay 完成，200/s，p50 | 62–272 ms | 6.7–17.5 ms |
| 接收方 CPU，50/s | Go 0.10、Python 0.19 核 | Go 0.12、Python 0.27 核 |

- **原因**：Go 探针的 relay 是 SDK 的后台任务，执行器每 500 ms 轮询，排入任务的事务提交后没有唤醒；Python 探针自己的 relay 队列同样 500 ms 轮询。与已修的发件转发器（P6.29）是同一类问题。
- **修复**：排入时登记提交后的信号，工作者等轮询计时器或这个信号，一项一个信号、至多每个工作者一个；轮询只兜底别的副本、重试与接管。新测试把轮询设成 1 小时，去掉唤醒时失败。市场上 River、Oban 也在插入后立即唤醒执行器。
- **代价**：每做完一项工作者立刻再领一次，看还有没有；接收方 CPU 多约 10%–40%（Python 更明显）。
- **为什么前几轮没发现**：监视只检查事件“到达”，没检查“转成调用完成”；已补上，按 relay 比到达多出的部分判断（PostgreSQL 队列上到达本身含订阅方的轮询）。

### 5.4 PostgreSQL 队列的唤醒（P6.30）

D-S-pg，第六轮（只有轮询）→ 第七轮（发布时唤醒，一条通知唤醒订阅的全部读取者）→ 第八轮（一条通知只唤醒一个读取者，加 P5.30），订阅并发 1：

| 项（D-S-pg，Go → Go） | 只有轮询 | 唤醒 |
| --- | --- | --- |
| 写入到收到，50/s，p50 | 55.7 ms | 5.6–5.8 ms |
| 写入到收到，200/s，p50 | 52.9 ms | 5.7–5.9 ms |
| 大事件，50/s，p50 | 61.8 ms | 11.1–11.4 ms |
| 接收方 CPU，写入 50/s | 0.04 核 | 0.07 核 |
| PostgreSQL CPU，写入 50/s | 0.33 核 | 0.37–0.38 核 |

- 唤醒把到达的下限从半个轮询间隔（约 55 ms）降到 NATS 之上几毫秒；代价是接收方与数据库多一些 CPU：每条消息醒一次，空领取与推进读取位置不再由一批消息分摊。
- **惊群**：第一版一条通知把订阅的全部读取者都叫醒，只有一个领得到。并发 4 时 Go 写入 50/s 的接收方 CPU 0.13 核、PostgreSQL 0.70 核；改为一条通知一个令牌、至多每个读取者一个后，0.07 核、0.52 核，与并发 1 相当。第七轮里 Python → Python 大事件在并发 4 时反而变慢（50/s 133 ms、200/s 3.6 s）也是这个原因，修好后 17.5 ms、105 ms。
- **轮询保留**：监听连接断开、连接池代理的事务模式下 `LISTEN` 用不了、被 xmin 屏障挡住的行，都靠轮询兜底；不为延迟丢掉这几种部署方式。

### 5.5 订阅并发

| 项（D-S-pg，第八轮） | 并发 1 | 并发 4 |
| --- | --- | --- |
| Go → Python 大事件 200/s，到达 p50 | 2 651 ms | 40 ms |
| Go → Python relay 200/s，p50 | 686 ms | 26 ms |
| Go → Python 写入 200/s，p50 | 31.6 ms | 9.7 ms |
| PostgreSQL CPU，Go → Python 大事件 200/s | 1.08 核 | 2.04 核 |
| 接收方（Python）CPU，同上 | 0.48 核 | 0.87 核 |

- 并发 1 时 Python 订阅进程只用约 0.5 核，排队来自串行的数据库往返（领取、处理事务、确认）与对象存储取回；并发 4 把它们重叠起来。Go 订阅每次往返更快，200/s 下并发 1 也不排队。
- NATS 上收益小：200/s 的大事件快约 25%–35%（Python → Python 73 → 48 ms），因为本来就不排队。
- **默认值保持 1**（用户 2026-10-19 定）：PostgreSQL 队列本身是为了少运行一个消息服务的妥协，调大并发的取舍写进正式文档的“PostgreSQL 队列的取舍”（`docs/zh/04-foundations/06-message-transport.md`），由使用方选择。
- **部署方的配置项（P6.31）**：订阅的成员读 `BUS_SUBSCRIPTION_CONCURRENCY`（1–64，按成员设）。实际并发：组件声明依赖到达顺序的订阅（`Ordered`）始终为 1；否则取部署方的值，没有时取组件的声明，再没有时为 1。第八、九轮的 `-c4` 格由探针自己的键 `PROBE_SUB_CONCURRENCY` 设定，探针 3.2.12 起删掉这个键，格的 `subscription_concurrency` 改写这个配置项。

| 项（第十轮，200/s） | D-S-pg（未设，1） | D-S-pg-c4（配置项 4） | 第九轮 c4（探针的键） |
| --- | --- | --- | --- |
| Go → Python 大事件，到达 p50 | 2 523 ms | 40 ms | 40 ms |
| Go → Python relay，p50 | 539 ms | 22 ms | 20 ms |
| Python → Python 大事件，到达 p50 | 2 511 ms | 105 ms | 99 ms |

配置项与原来探针的键效果相同，端到端生效。

### 5.6 事务的固定往返（P5.30）

第七轮 D-S-pg 的语句统计里，调用最多的四条是 `UNLISTEN *`、`RESET ALL`、`CLOSE ALL`、`SELECT pg_advisory_unlock_all()`（各 10–20 万次），来自 asyncpg 连接池每次归还时的默认会话重置。最小基准（短写事务，8 并发，每轮 4000 个，3 轮，`experiment-data/4-03/txbench/`）：

| 写法（asyncpg） | 客户端 CPU / 事务 | PostgreSQL CPU / 事务 |
| --- | --- | --- |
| 现在的写法（归还时重置） | 0.20–0.25 ms | 0.32–0.34 ms |
| 不做会话重置 | 0.16–0.20 ms | 0.23–0.25 ms |
| 再合并 `BEGIN` 与事务内设置 | 0.14–0.17 ms | 0.21–0.22 ms |

| 写法（pgx，本来就不重置） | 客户端 CPU / 事务 | PostgreSQL CPU / 事务 |
| --- | --- | --- |
| 现在的写法 | 0.15 ms | 0.19–0.20 ms |
| 合并 `BEGIN` 与事务内设置 | 0.12–0.13 ms | 0.20–0.23 ms |

- **采用**：Python 的两个连接池（数据库、总线）不再做会话重置；asyncpg 在调用自定义重置之前仍回滚还开着的事务。重置原来也兜着违规写法，现在由事务入口直接拒绝：不带 `LOCAL` 的 `SET`、`set_config(…, false)`、`RESET`、`DISCARD`、`LISTEN`、`UNLISTEN`、会话级咨询锁（P5.30，Go 与 Python 都加了，Go 因此也多了这层保护）。函数或 `DO` 块内部的会话设置由 P5.31 补上（见下一节）。
- **不采用**：合并 `BEGIN` 与设置。asyncpg 上只再省约 10%，要改最核心的事务入口；pgx 上客户端省、数据库多（简单协议用不上缓存的预备语句），延迟不变。
- **第八轮的整体效果**（D-S，对第六轮）：有 Python 参与的路径，PostgreSQL CPU 少约 5%–20%、Python 进程 CPU 少约 5%–10%，200/s 的延迟明显下降（Python → Go 写入 16 → 6 ms）；只有 Go 的路径差别在波动之内。语句统计里重置语句已经没有了。

### 5.7 函数与 `DO` 块里的会话设置（P5.31）

P5.30 拒绝的是语句本身；写在函数或 `DO` 块里的 `set_config(…, false)` 它看不到。以前 Python 的会话重置能清掉，Go 本来就清不掉。外壳里同一数据库目标的成员共用连接池，这样的设置会被同一外壳的其他成员继承：例如时区被改成东京，下一个借到这条连接的成员算出的业务日期就错了。

- **核对推送值（两个 SDK）**：`TimeZone`、`DateStyle`、`IntervalStyle`、`client_encoding`、`standard_conforming_strings`、`application_name` 变化时由服务端主动推送（在 PostgreSQL 16 上用 asyncpg 与 pgx 验证过，函数里改的也推送；`SET LOCAL` 在事务结束后推送回原值）。每条连接建立时记下这几项；事务结束、归还之前比较，不同就关掉这条连接，并记录成员、参数与前后的值。不增加往返。
- **迁移检查**：新规则 `SESSION_IN_BODY` 检查函数、过程与 `DO` 块的正文（不带 `LOCAL` 的 `SET`、`RESET`、`set_config(…, false)`、会话级咨询锁）；运行时的事务入口对 `DO` 块做同样的检查。两个 SDK 按协议的同一组向量验证。
- **不在此列**：角色、`search_path` 与各项超时每个事务开始时都会重设；服务端不推送、只影响性能的设置（如 `work_mem`）不检查；动态 `EXECUTE` 的字符串不检查。
- **测试**：用一个改时区的函数制造泄漏，下一个事务拿到新连接、仍是 UTC，日志点名 P5.31；去掉核对时两个 SDK 的测试都失败（继承了东京时区、同一条连接）。
- **第九轮**（与第八轮同样的三格，performance）：第九轮 ÷ 第八轮的中位数，延迟 p50 0.99–1.02、组件 CPU 1.01–1.02、PostgreSQL CPU 0.95–1.02（不含排队的上限项），都在波动之内；核对没有可测量的成本。
- 协议 `alpha.12`；`be-sdk-go` `alpha.14`、`be-sdk-python` `a12`；探针 3.2.11；外壳 3.0.11。

### 5.8 后台任务的领取（P7.22）

第七轮的语句统计里，后台任务的领取每次约 0.4–0.5 ms：语句用 `OR` 把“过期的租约”与“到期的待办”放在一个条件里，跨两个部分索引，数据库只能把两边符合的行都取出来再排序。与 P6.28 修过的总线领取是同一种写法，积压越多越慢。

- **改法**：先取一条过期的租约；没有时再按到期时间取最早的一条待办。两步各走自己的有序部分索引（迁移 `0008_work_claim_order`：到期索引只按 `run_at` 排序，取代原来的 `(job, run_at)` 索引）。几个任务种类混在一起时也只读一行。
- **测量**（`be-sdk-go` 的集成测试，同一数据库）：2 万条到期时，原来的语句每次领取约 8 ms，40 条时约 1.3 ms；新的语句分别约 1.3 ms 与 1.1 ms。新测试在原来的语句上失败。协议的记录另有一组单独执行语句的数字：2 万条时 3–8 ms 对 0.1–0.2 ms。
- **最小基准**（`experiment-data/4-03/claimbench/`，pgbench 1 个客户端，事务里领取后回滚，两种写法交替各 3 次，performance）：积压 40、2 000、2 万条时，`OR` 写法每次 0.35–0.39、0.86–0.93、5.44–5.53 ms，拆开写 0.39–0.41 ms 不变；2 万条时 `OR` 写法的计划是全表扫描再排序。积压很小时拆开写略慢（约 0.05 ms）。
- 只有 Go 的 SDK 有后台任务执行器；Python 的 SDK 子集里没有（`features.json` 标为未实现），只随协议带上迁移，以后补齐时按 P7.22 写。协议 `alpha.13`；`be-sdk-go` `alpha.15`。

### 5.9 对象存储的第二个实现

MinIO 的镜像已拿不到，开发环境的可选存储换成 SeaweedFS（用户 2026-10-19 定）：单进程模式，S3 接口发布在宿主机 9000，与 RustFS 互斥，组件与测试的地址不用改；凭据由 `AWS_*` 环境变量建成管理员身份，匿名被拒绝，关掉默认的匿名统计上报（`-master.telemetry=false`）。

- **正确性**：两个 SDK 的对象存储与事件集成测试在 SeaweedFS 4.48 上全部通过（Go 的对象存储两项与两种运输的事件链，Python 的对象存储三项与 Go↔Python 互通四项），先打在临时容器上，再经 `make seaweedfs-up` 与项目凭据跑一遍。
- **性能**（D-S 的大事件，两遍，每遍先 SeaweedFS 后 RustFS）：

| 项 | SeaweedFS ÷ RustFS |
| --- | --- |
| 写入到收到 p50，50/s | 0.94–0.98（两遍之间同一项最多差 5%） |
| 写入到收到 p50，200/s | 0.76–0.96（Go 发出的路径快约 20%；两遍中位差 2%，最多 14%） |
| 存储进程的 CPU（第二遍） | 中位 1.46：50/s 0.26 对 0.19 核，200/s 0.9 对 0.59 核 |
| 存储的内存 | 相当，约 0.5–0.6 GiB |

- **只上传 10 分钟**（`storage/uploads/`，每秒 50 个 100 KiB，对象累积到 3 万个，先空闲 2 分钟）：上传 p50 SeaweedFS 4.9 ms、RustFS 6.7 ms，都不随对象数变慢；平均 CPU SeaweedFS 0.20 核、RustFS 0.26 核。RustFS 在对象到约 1.7 万个后每约 60 秒扫描一次（8–10 秒、约 1.8 核），上传不受影响；另测 2 万个对象完全空闲 5 分钟，平均 0.19 核，扫描照样（没有对象时约 0.09 核）。前面几处“RustFS CPU 1.4 核”的读数，是 10 秒的窗口碰上了一次扫描。
- **结论**：两者各有长短——大事件路径上 SeaweedFS 延迟略低、CPU 多约一半；只上传时 SeaweedFS 更快，RustFS 因为扫描平均 CPU 更高。默认仍是 RustFS（已在全部测量中使用，差别不足以换），SeaweedFS 是验证过的替换件。存储一致性套件的其余项（分段、范围读取、生命周期、对象锁、桶策略）没有测，随附件组件一起验。正式文档写在数据与生命周期的“对象存储”一节。
- 测量工具只采 `be-rustfs`，第一遍没有 SeaweedFS 的 CPU；`be-acceptance` `1ca033b` 把 `be-seaweedfs` 加进基础资源的名单后跑了第二遍。

### 5.10 PostgreSQL 队列的发布与 `NOTIFY`（P6.30 的修正）

P6.30 让发布在插入消息的同一条语句里 `NOTIFY`。发了通知的事务在提交时取一把全实例的锁，持有到提交写盘完成，于是并发的发布只能一个接一个提交，享受不到合并写盘。

| 单行插入，pgbench，5 轮的中位数（次提交/秒） | 1 个并发 | 8 | 16 | 32 |
| --- | --- | --- | --- | --- |
| 只插入 | 2 941 | 2 004 | 13 261 | 27 573 |
| 同一条语句里通知（P6.30 原来的写法） | 3 048 | **436** | **1 144** | **1 880** |
| 插入提交后单独通知 | 2 707 | 2 021 | 8 013 | 15 236 |

8 个并发时 5 轮里 4 轮在 433–437，一致；16、32 个并发时各轮相差很大（这台机器写盘的波动），但三种写法的高低每轮相同。只发通知的语句不分配事务号、不写盘，持锁很短。

改了三次，每次量到了下一处代价：

| 版本 | 写法 | Go 并发发布（8 个发布方，条/秒） | Python 顺序发布，CPU / 条 | 第十至十二轮看到的 |
| --- | --- | --- | --- | --- |
| `alpha.15` / `a13`（原来） | 通知在插入的语句里 | 3 486–3 592 | 0.14–0.17 ms | — |
| `alpha.16` / `a14`（协议 `alpha.14`） | 发布路径里，插入后再执行一条 `pg_notify` | 10 219–10 439 | 0.23–0.26 ms | 第十一轮：Python 发布方 200/s 时发布 p50 变长（写入 13 → 19 ms），它的 CPU 不变——按顺序发布的转发器每条多等一次往返 |
| `alpha.17` / `a15`（协议 `alpha.15`） | 交给传输的后台通知者，一条消息一个通知、不合并，待发的上限 4 096、超出丢掉由轮询读到 | 12 652–12 871 | 0.28–0.40 ms | 第十二轮：第十一轮变长的项回到第十轮的水平（发布 p50 是第十轮的 0.99 倍，中位数） |
| `a16`（Python 独有） | 通知者用自己的连接，不借连接池 | 同上 | 0.21–0.28 ms | 第十三轮（两遍）：非上限项的发布 p50 是基线（第十轮与复现两遍）的 0.96 倍（p10–p90 0.83–1.04），完成 0.99 倍（0.89–1.09）；站在上限边上的那一项两遍都跟上了（77 与 80 ms） |

- Go 的数字来自 `BenchmarkConcurrentPublish`（`be-sdk-go`，每次 8 000 条，3 次）；Python 来自顺序发布 5 000 条的最小基准（`pypub/`，3 轮）。
- 不合并通知：唤醒是一条通知一个令牌，合并会让并发的读取者少醒。Go 不需要专用连接：借还连接便宜，并发发布已经到每秒 1.28 万条。
- 基准第一次运行时往共用的测试总线留下了 4.8 万条消息，让一个“新订阅越过别的流”的测试超出了 2 秒的界限；基准改为结束时删掉自己的消息。
- **站在上限边上的一项**：D-S-pg-c4 的 Python → Go 大事件 200/s。Python 发送方的 CPU 约 0.8–0.95 核，单线程的事件循环接近跑满；跟得上时发布 p50 约 80 ms（第九轮、第十轮复现两遍），跟不上时积压到秒级（第十轮 1 004 ms，第十一轮 1 877 ms，第十二轮 2 559 ms）。跟不上的几次存储的 CPU 更低（0.45 核对 0.60 核），说明上传本身变少了。通知多出的 CPU 可能把它推过了边，所以 `a16` 把这部分再省回约 0.1 ms；之后第十三轮两遍都跟上了。它仍站在 Python 单进程的上限边上（报告的“已知的上限”），以后偶尔跟不上也属于这个上限。

### 5.11 写入的最高持续速率

写入加压（一个事务写业务行与发件行，从 50/s 每级乘 1.5，`ramp/`）：Go 两条边在 D-S 与 D-S-pg 上都到加压的最后一级 4 325/s 仍持续（再上一级超过 5 000/s 的上限）；Python 570–854/s，单进程的 CPU 先到上限。试运行时的“Go 约 1 900/s、数据库连接预算用满”是节能模式与旧版本下的读数，已不成立。加压只量写入请求本身，不量事件的发出与收到；发布的上限见第 5.10 节。

## 6. 观察与异常

- **第七轮那次 relay 1.9 s 的停顿，很可能是事务号屏障**：D-S-pg 的 Go → Go relay 200/s，发布 p50 4.4 ms 正常，收到 p50 1.9 s、最大 4.3 s，像是约 4 秒里订阅方一条都读不到；同一格紧接着两次重测为 9.6 与 13.5 ms。PostgreSQL 队列只读事务号低于最老在途事务的行，而事务号是整个实例共用的：实测另一个数据库里一个开着 6 秒的写事务，让屏障停了 6 秒（只读事务不算）。当时实例里是哪个写事务开了几秒，事后查不到。正式文档的“PostgreSQL 队列的取舍”已改写这条注意事项，并给出防护。同一轮里 Python 订阅并发 1、200/s 的几项每次相差很大（同一项 32 ms 与 177 ms），是这个上限的临界状态。
- **第十轮有一项没有复现的变慢，原因未明**：D-S-pg-c4 的 Python → Go 大事件 50/s 到达 p50 175 ms（第八、九轮 14 ms），200/s 924 ms（约 80 ms）。延迟全部在发布这一段：发布 p50 170 ms，在 0–365 ms 之间均匀分布；收到只比发布晚约 5 ms。重跑三次都没有复现：只跑大事件一次（`round10-recheck/`，13.4 与 83 ms），按第十轮的完整顺序两遍（`round10-repro/`，发布 p50 10.6–10.9 与 78–84 ms）。排除的：①转发器没被唤醒——同一部署、同一发送方紧接着之前的小事件发布 p50 约 5 ms；②对象存储变慢——RustFS 上传 10 分钟时间线（第 5.9 节）p99 稳定在 9 ms，它的周期扫描不拖慢上传；③事务号屏障——它只挡读取（收到），发件表的编号在提交之后、没有屏障。再出现时先取：发送方的日志、发件表各行的写入与发布时刻（是否成批）、上传的耗时。
- **并发 4 下有一项变差**：第八轮 D-S-pg-c4 的 Go → Python relay 50/s p50 32 ms（第七轮 14 ms），同类的其他项都没变，按波动记下。
- **第十三轮第二遍 D-S-pg 的 Python → Python relay 200/s 完成 p50 2 746 ms**（第一遍 1 255 ms，前几轮 444–674 ms）：订阅并发 1 的 Python 订阅在 200/s 下排队，属于第 5.5 节的上限，读数本来就跳得很大；并发 4 的同一项为 34–35 ms。
- **测量的启动脚本出过三次错，都已改正**：①第十轮复查的脚本由上一轮的替换路径生成，清单的文件名被改成不存在的名字，脚本立刻退出；原电源模式记在脚本外面，没跟着生成，恢复读到空值，机器停在 performance，手工恢复为 balanced。②对象存储对比第一次没带测量的环境变量，测量立即失败，但清单的退出码是 0，脚本照样切到下一个后端。③第二次把每个阶段的结果数写成 9（D-S 是 4 条边乘 2 档负载，8 项），完整的一个阶段被判为失败，只补跑了另一个阶段。现在的做法：原电源模式的记录与恢复放在同一个脚本里（`trap` 恢复，之后两次都恢复正确）；每个阶段按结果文件数核对，预期数按格算。
- **停在格与格之间要看“上一格完成”，不要看“下一格开始”**：第五轮按“出现 D-H2 的开始行”停下，D-H2 已经开始重建，留下半成品的部署文件被提交了一次，已从上一个提交恢复。
- **监视的盲点**：一个指标只要有一个环节没检查，“全部正常”就可能是假的（relay）。新加的检查项要覆盖操作的最终完成，分段的部分按差值判断。
- **两个 SDK 的集成测试不能同时跑**：同时执行 `GRANT CONNECT ON DATABASE` 时报 `tuple concurrently updated`；改为依次跑。另有一个外壳测试（`TestEachMemberServesItsSystemSurfaceOnItsOwnPort`）在整套集成测试的负载下偶发超时（5 秒内没等到就绪），单独重复 8 次全过；等待放宽到 15 秒，单独一次提交写明原因（`be-sdk-go` `b70ec54`）。
