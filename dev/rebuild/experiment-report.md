- **内存预算**（B3、B4，[10-05](experiment-records/10-05-memory-cap.md)）：整套容器放进 6 GiB、4 GiB 的预算（减去 Docker 自己约 0.7 GiB）都照常跑完，让出去的只是页缓存，延迟与 CPU 不变；不能回收的部分约 1.2 GiB 加 Docker 约 0.7 GiB，估计 2–2.5 GiB 才开始挤进程，没有再往下量。

### 进程底价：一个进程空闲时占多少（第 4 步，D 行细测）

回答：单跑一个组件、或外壳每多承载一个成员，要付出多少内存与 CPU。

| 进程 | 常驻内存 | 空闲 CPU |
| --- | --- | --- |
| Go 探针单跑 | 29 MiB | 0.012 核 |
| Python 探针单跑 | 101 MiB | 0.017 核 |
| Go 外壳承载 1、2、4 个 | 30、31、33 MiB（每多一个成员约 1–2 MiB） | 0.012、0.022、0.040 核 |
| Python 外壳承载 1、2 个 | 102、103 MiB（多一个成员约 1 MiB） | 0.021、0.031 核 |

- **读法**：一个进程的底价几乎全在运行时本身（Go 约 29 MiB、Python 约 100 MiB），成员的增量只有 1–2 MiB。四个 Go 组件单跑约 117 MiB，合进一个外壳约 33 MiB；两个 Python 组件单跑约 202 MiB，合进一个外壳约 103 MiB。空闲 CPU 来自每个成员的后台轮询（发件转发、后台任务、订阅），每个成员约 0.01 核。
- **口径**：进程的常驻内存（含共享的文件页）与 CPU 时间，30 秒空闲窗口的中位数；performance 电源模式（第五轮）。常驻内存与电源模式无关，空闲 CPU 在节能模式下约多一倍。

**读法**

- **合进外壳省的是 CPU，不是延迟**：同一 Go 外壳内的调用仍走网络（原则一），一跳只比跨容器快约 0.1 ms；两个成员共用一个进程，调用的 CPU 从约 1.8 降到 1.4（每千次）。外壳到外壳与单跑一样。
- **Python 的一跳约是 Go 的 2–3 倍，调用方 CPU 约 2.5 倍**：Python 作调用方时每千次约 2.5 CPU 秒，Go 约 1.0。1 KiB 下 HTTP 比 gRPC 快一些（两种语言都是）。
- **事件**：NATS 上写入到收到 3–6 ms；100 KiB 大事件经对象存储 9–13 ms（50/s）。PostgreSQL 队列加上发布时唤醒（P6.30）之后写入到收到 6–9 ms，只比 NATS 多几毫秒；它的代价在数据库：同样 50/s 的写入，PostgreSQL 的 CPU 约 0.4 核，NATS 格约 0.2 核。
- **事件转调用（经后台任务）**：50/s 下 7–10 ms（P7.21 之前 p50 约 250 ms）。
- **误差**：同一份代码、同一电源模式下隔几小时重测（第八轮对第六轮的 Go → Go 各项），p50 相差 0–12%、p99 相差 8–20%；差别在 10% 以内的比较按“差不多”看。电源模式的影响见 4-04（约 1.6 倍）。

### 带真实身份、授权与审计的代价

回答：每个请求都核验令牌、对照授权视图检查操作、把审计记录转给审计组件，通信要多花多少。对照格（不带安全组件）、单跑格与外壳格交替各测两遍，performance 电源模式（[5-02](experiment-records/5-02-security-cells.md)）。

| 路径 | 对照 | 带安全组件，单跑 | 带安全组件，进外壳 |
| --- | --- | --- | --- |
| HTTP 一跳，Go → Python，1 KiB，50/s：p50 ms / 每千次 CPU 秒 | 1.10 / 2.10 | 1.42 / 2.68 | 1.40 / 2.97 |
| HTTP 一跳，Python → Go，1 KiB，200/s | 0.68 / 1.71 | 0.85 / 2.28 | 0.81 / 2.25 |
| gRPC 一跳，Go → Python，1 KiB，200/s | 1.00 / 1.83 | 1.13 / 2.24 | 1.01 / 2.10 |
| 写入到收到，Go 写入，200/s：p50 / p99 ms | 3.2 / 5.9 | 3.5 / 6.7 | — |
| 写入到收到，Python 写入，200/s | 6.4 / 25.9 | 8.2–17.4 / 31–46 | — |

**读法**

- **用户面的每个请求多约 0.5 ms CPU、0.15–0.35 ms 延迟**：令牌（EdDSA）的核验与操作检查，两端各做一次。
- **系统面几乎不变**：组件之间的调用本来就走 mTLS，多出来的只是操作检查。
- **安全组件进外壳与单跑一样**：外壳省的是进程与数据库连接（连接峰值 20 降到 10），通信代价没有可分辨的差别。
- **Python 在 200/s 的写入更靠近 CPU 上限**：多出的那点 CPU 让排队时有时无（两遍之间差一倍），应对办法与上限表的 Python 一行相同。

### 已知的上限

回答：负载上去时先撞到什么。performance 电源模式。

| 上限 | 读数 | 怎样提高 |
| --- | --- | --- |
| Python 单进程的 CPU（每次 10 ms 计算的调用） | 单跑约 85 次/秒，同一外壳里调用方与被调方共用一个核时约 70 次/秒；超出的请求排队并超时 | 多进程或多副本；Go 在 200/s 下没有碰到 |
| 同一 Python 进程既写又收 100 KiB 大事件 | 每个事件写入方约 9 ms、接收方约 4 ms CPU，一个进程约 75 个/秒；200/s 时到达 p50 约 2–3 s | 把写入方与接收方放进不同进程，或加副本 |
| 订阅默认逐条处理（Python，PostgreSQL 队列） | 200/s 的大事件到达 p50 约 2.5 s，事件转调用约 0.7 s；进程 CPU 不到 0.5 核，排队来自串行的数据库往返 | 部署方把 `BUS_SUBSCRIPTION_CONCURRENCY` 设为 4：大事件 40 ms、写入 10 ms；代价是数据库 CPU 约多 0.5–1 核（200/s）。默认为 1，依赖到达顺序的订阅始终为 1 |
| PostgreSQL 队列的发布 | 经 Go SDK、8 个并发的发布方每秒约 12 700 条（P6.30 修正之前约 3 500 条：通知与插入在同一事务里，提交只能一个接一个）；Python 单个发布方每条约 0.2–0.3 ms CPU | 量更大时用 NATS JetStream |
| PostgreSQL 队列的事务号屏障 | 同一实例里任何一个写事务开着多久，全部订阅就停多久（另一个数据库里开着 6 秒的写事务让屏障停了 6 秒；只读事务不算） | 实例上设 `idle_in_transaction_session_timeout`，监控最老在途写事务；不能接受时把总线放进单独的实例或改用 NATS JetStream |
| 写入的最高持续速率（一个事务写业务行与发件行） | Go 到加压的最后一级 4 325 次/秒仍持续（再上一级超过 5 000/s 的上限，未测），NATS 与 PostgreSQL 队列相同；Python 570–854 次/秒，单进程的 CPU 先到上限。试运行时的“Go 约 1 900/s、数据库连接预算用满”是在节能模式与旧版本下测的，已不成立 | Go 在这个范围内没有碰到上限；Python 用多进程或多副本 |

### 四种形态上的进程底价与每一跳

回答：换一种运行形态，服务本身的开销变不变。探针在 D、P、K、L 四行，每一层的四种形态在同一批里挨着跑（底价与外壳的一跳：2026-10-28 01:04–05:26；单跑的一跳：05:30–06:42），200 次/秒（[9-02](experiment-records/9-02-probes-all-rows.md)）。

| 项 | Docker | Podman | Kubernetes | 本机进程 |
| --- | --- | --- | --- | --- |
| 一个 Go 探针空闲：常驻 MiB / 核 | 32.4 / 0.010 | 34.1 / 0.010 | 11.7（Pod 的 cgroup）/ 0.010 | 35.6 / 0.010 |
| 一个 Python 探针空闲 | 101.8 / 0.016 | 102.1 / 0.017 | 89.0 / 0.017 | 99.6 / 0.013 |
| Go 外壳承载 1 / 2 / 4 个：空闲核 | 0.010 / 0.018 / 0.031 | 0.010 / 0.015 / 0.024 | 0.010 / 0.018 / 0.032 | 0.010 / 0.017 / 0.029 |
| Go → Go gRPC 1 KiB：每千次 CPU 秒（调用方 / 被调方），p50 ms | 0.46 / 0.35，0.27 | 0.45 / 0.34，0.26 | 0.49 / 0.36，0.27 | 0.47 / 0.35，0.27 |
| Python → Python gRPC 1 KiB | 1.46 / 0.93，1.34 | 1.45 / 0.99，1.39 | 1.49 / 0.96，1.34 | 1.13 / 0.84，1.19 |
| 事件转调用（relay）Go → Go：p50 ms | 5.6 | 6.1 | 7.2 | 7.8 |

- **服务本身的开销四种形态一样**：底价、外壳每多一个成员（Go 约 1.2–1.8 MiB）、每一跳的 CPU 与延迟，三种容器形态之间差在 10% 以内；差别只在平台。
- **事件路径在 Kubernetes 与本机进程慢 1.6–2.2 毫秒**：本机进程经回环连消息服务与数据库，走 Docker 的用户态代理；同步调用不受影响。
- **本机进程里的 Python 每一跳少约 20% CPU**：容器里的 Python 探针当时是官方 `python:3.15.0-alpine` 镜像（musl、GCC，只开 LTO，没有 PGO），本机的是 uv 装的 python-build-standalone（Clang，PGO、完整 LTO、BOLT、mimalloc 与 tail-call 解释器）。10-04 单独量过：差别几乎全是 alpine 的构建，生产用的 slim 与 python-build-standalone 只差 2–5%（见下面“容器里的 Python 构建”）；探针已改用 slim。

### 外壳省的不是数据库连接

回答：合并进外壳省下的，是不是主要来自每个进程各一份的数据库连接池。单跑的 12 个组件前面放一个事务模式的 PgBouncer（每个组件一个 5 条连接的池，迁移绕过它），与单跑、混合、全部进外壳放在同一批里（Docker，2026-10-28，[10-01](experiment-records/10-01-pooler-and-pgqueue.md)）。

| 格 | 组件 CPU（每千次） | 组件内存（不含页缓存） | 后端连接（峰值合计） | PostgreSQL 内存 | 整套（每千次） | p50 / p95 ms |
| --- | --- | --- | --- | --- | --- | --- |
| 单跑 | 36.5 | 374 MiB | 103 | 549 MiB | 101.2 | 22.6 / 50.5 |
| 单跑 + PgBouncer | 36.2 | 378 MiB | 56 | 344 MiB | 110.6（多 9%） | 24.4 / 54.6 |
| 全部进外壳 | 28.3（少 22%） | 242 MiB（少 35%） | 69 | 807 MiB（见下） | 88.2（少 13%） | 22.3 / 50.3 |

- **连接池代理省的是数据库那边的内存**（约 200 MiB，后端连接从 103 降到 56），组件一点不省；它自己每千次多 12.5 CPU 秒、p50 多 1.8 毫秒。
- **外壳省的在组件进程与平台**：连接比代理还多，组件 CPU 与内存却少了两到三成。两者解决不同的问题，可以叠加。
- **外壳让数据库每条连接变大**：外壳的一条连接轮流为几个成员服务、为它们各缓存一套表，每条的私有内存约是单跑的 2.4 倍（10.1 对 4.2 MiB）；连接从 102 条降到 63 条，PostgreSQL 的内存反而多约 210 MiB，抵掉了外壳在组件上省下的约 130 MiB（[10-02](experiment-records/10-02-postgres-backend-memory.md)）。所以全部进外壳省的是 CPU 与平台，整套内存不一定省；外壳的连接池上限、连接的最长寿命可以再调，未量。

回答：事件从 NATS JetStream 换成 PostgreSQL 里的队列，整套多花多少（同一批，[10-01](experiment-records/10-01-pooler-and-pgqueue.md)）。

| 拓扑 | NATS JetStream（每千次） | PostgreSQL 队列 | 差 |
| --- | --- | --- | --- |
| 单跑 | 101.2 | 102.8 | 多 2% |
| 混合 | 94.0 | 94.4 | 多 0.4% |

- **看不出差别**：PostgreSQL 为队列多做的事每千次 2.1–2.5 秒、多 26–39 MiB，大致抵掉 NATS 自己的 1.8 秒；NATS 空闲只占 0.006–0.008 核、约 20 MiB。业务延迟与事件链走完的时间一样（开具到订单完成 p95 4.5 对 4.7 毫秒）。

## 第三部分：逐个模式的介绍

18 个模式是 6 种运行形态 × 3 种拓扑。同一种形态的三种拓扑部署步骤几乎一样，所以按形态分 6 节：每节先写“是什么”与“怎样部署”（三种拓扑共用，只写这一形态特有的），再用一张表写每种拓扑的优势与劣势、适合谁、另做过的测试与限制。资源与性能的数字在第一、二部分，这里不重复；故障、多版本与多实例（套件 C、D、E）是第 11–13 步，还没测。

**三种拓扑**：S 全部单跑，12 个组件各一个进程；H 全部进外壳，`be/go-infra`（安全 3 个与主数据 4 个）、`be/go-core`（库存、信用、销售、出账）、`be/py-render`（打印）三个进程；X 混合，只有 `be/go-infra` 一个外壳，交易的 5 个组件单跑。

**通用的部署步骤**（每种形态都照这个做，各节只写不同的地方）：

1. 准备基础资源：PostgreSQL、NATS JetStream（或只用 PostgreSQL 队列，见“只用 PostgreSQL”）、对象存储、Casdoor。本实验里它们在宿主机的 Docker 里（装配项目的 `make up`），每种形态共用这一套。
2. 在装配项目里加组件与外壳：`brickkit add <组件 ID>@<版本>`；`brickkit.yaml` 就是锁文件。
3. 写 `deploy.yaml`：`target`，组件列表；进外壳的成员写在外壳的 `members` 下；要从宿主机访问的写 `expose`。H 的样子：

   ```yaml
   target: docker            # 或 podman、k8s
   components:
     - id: be/go-infra
       members:
         - id: infra/iam-casdoor
         - id: infra/authz
         # …… 其余安全与主数据成员
     - id: be/go-core
       members:
         - id: erp/inventory
         # …… 信用、销售、出账
     - id: be/py-render
       members:
         - id: infra/print
   ```

   S 是 12 个组件各占一行、没有 `members`；X 是 `be/go-infra` 带 7 个成员，其余 5 个各占一行。
4. 填 `config/`：每个组件的配置键；密钥写 `${VAR}` 或 `file://.secrets/…`，不写明文。
5. `brickkit build` 构建镜像，`brickkit up` 起来，`brickkit status` 看状态；种子数据用装配项目的 `make seed-data`。
6. 停：`brickkit down`。

### D：Docker

**是什么**：每个进程一个 Docker 容器，由 BrickKit 生成 compose 文件；基础资源在同一个 Docker 里。

**怎样部署**：通用步骤，`target: docker`。容器的重启策略是 `unless-stopped`。

| | S 全部单跑 | H 全部进外壳 | X 混合 |
| --- | --- | --- | --- |
| 优势 | 隔离最好，每个组件可单独升级、单独看资源 | 组件 CPU、内存与平台开销都最少（第一部分） | 交易组件仍可单独升级与观察；低流量的合并省一部分 |
| 劣势 | 进程与数据库连接最多；Docker 守护进程常驻约 0.55–0.7 GiB | 成员共进退：一个成员出事整个外壳受影响，升级一个成员要重建外壳；外壳的数据库连接更大，整套内存不一定省（10-02） | 省得比 H 少（组件 CPU 少约 12%） |
| 适合谁 | 中型客户；要逐个组件排查、升级的交付；开发与演示 | 小型客户、内存预算紧；业务广但活动少的客户 | 中型客户的默认候选：热组件单独、其余合并 |
| 另做过的测试 | B1 连接池代理、B2 只用 PostgreSQL、B3/B4 内存预算、B5 负载与数据加倍（10-01、10-05、10-06） | B3/B4 内存预算（10-05）；外壳里 PostgreSQL 的内存（10-02） | B2、B5（10-01、10-06） |
| 限制 | 单机；基础资源与组件同一台机器 | 同左；一个外壳只能合并同一语言、同一 SDK 版本的成员 | 同左 |

### P：Podman

**是什么**：同 D，换成 Podman（默认无根）；基础资源仍在 Docker 里。不需要常驻的守护进程，每个容器一个 `conmon`。

**怎样部署**：通用步骤，`target: podman`。镜像要在 Podman 的存储里：本实验用 Docker 构建后载入 Podman（`docker save | podman load`），也可以从镜像仓库拉。无根时网络经用户态的 pasta 转发；要有根就用 root 的 `podman.socket`，与 Docker 同机时还要在 `DOCKER-USER` 链里放行 Podman 的网桥（0-11，10-07）。

| | S 全部单跑 | H 全部进外壳 | X 混合 |
| --- | --- | --- | --- |
| 优势 | 不要 root、不要守护进程；平台常驻约 0.14 GiB | 同 D·H；`conmon` 随容器数减少 | 同 D·X |
| 劣势 | 无根的用户态网络每千次约 13 秒、p50 多约 1.4 毫秒（有根可省掉大部分，10-07） | 成员共进退，同 D·H；pasta 一个进程转发全部流量，容器少了它不少 | 同 D·X |
| 适合谁 | 要求无根或不允许常驻 root 守护进程的单机（RHEL 系） | 同左，加上内存预算紧 | 同左，中型客户 |
| 另做过的测试 | B6 有根对无根（10-07） | B6（10-07） | — |
| 限制 | 有根运行时引擎以 root 运行，安全上退了一步；只有 Podman 的机器上的有根没有单独量 | 同 D·H | 同 D·X |

### K：Kubernetes（单节点）

**是什么**：每个进程一个 Deployment（外壳的成员各有自己的 Service），本实验是单节点 minikube；基础资源在集群外的 Docker 里，Pod 经宿主机地址访问（也测过放进集群，B7）。

**怎样部署**：通用步骤，`target: k8s` 加 `k8s:` 块（`context`、`namespace`、`createNamespace`）。镜像要让集群拉得到：推到镜像仓库，或单节点时 `minikube image load`。本实验为了从宿主机打负载另加了 NodePort 的 Service；真实部署用 Ingress，未测。

| | S 全部单跑 | H 全部进外壳 | X 混合 |
| --- | --- | --- | --- |
| 优势 | 自动重启、可按组件扩容；组件本身的开销与 D 一样 | 集群里 Pod 最少；组件 CPU 少 14%、内存少 32% | 热组件可单独扩容，其余合并 |
| 劣势 | 集群的控制面与 kubelet 常驻约 2 GiB（不含页缓存约 0.75），发布端口另占约 0.3 GiB；小客户不划算 | 扩容的粒度是整个外壳 | 省得少（组件 CPU 少 8%，看不出差别） |
| 适合谁 | 已经有 Kubernetes、要自愈与扩容的中型与集团型客户 | 同左，Pod 数受限时 | 集团型客户的候选 |
| 另做过的测试 | — | — | B7 基础资源放进集群（10-08） |
| 限制 | 单节点：没有跨节点网络，多节点的数字不能直接套用；单副本迁入 Kubernetes 不自动获得高可用 | 同左 | 同左 |

### L：本机进程

**是什么**：全部组件由 BrickKit 的 `mode: local` 从源码在宿主机上直接运行（Go 用 `go run`，Python 用 `uv run`），不用容器；基础资源仍在 Docker 里。

**怎样部署**：通用步骤，每个组件（或外壳）写 `mode: local`；宿主机要有组件的工具链（Go、uv）与源码。`brickkit up` 在前台运行，关掉它所有本机进程一起停；一个本机进程崩溃时其余本机进程也停，容器照常（0-05）。令牌的签发者必须写成固定字符串，写成 `$endpoint:` 时本机组件会拒绝全部令牌（协议 19）。

| | S 全部单跑 | H 全部进外壳 | X 混合 |
| --- | --- | --- | --- |
| 优势 | 不用装容器环境，一次启动、一次关闭；整套 CPU 与 D 一样 | 进程最少；`go run` 的包装随进程数减少（435 → 116 MiB） | 同左的折中 |
| 劣势 | 只活在一次 `up` 会话里，不能长期运行；`go run` 包装常驻约 0.4 GiB；数据库流量经 Docker 的用户态代理 | 同左；一个进程崩溃全部停 | 同左 |
| 适合谁 | 开发与演示；不想装容器环境的试用 | 同左，机器内存小时 | 同左 |
| 另做过的测试 | — | — | — |
| 限制 | 不在 BrickKit 的长期运行范围内，套件 C 不跑；工具链来自宿主机，版本不受镜像固定 | 同左 | 同左 |

### LD、LP：一部分组件在本机，其余在 Docker 或 Podman

**是什么**：只有少数组件以本机进程运行（本实验是销售与库存，或交易外壳 `be/go-core`），其余在 Docker（LD）或 Podman（LP）里。用途是只改一两个组件时从源码直接跑它们，其余照常在容器里。

**怎样部署**：通用步骤，`target: docker` 或 `podman`，要在本机跑的组件或外壳写 `mode: local`。本机组件依赖外壳的成员时要 BrickKit v1.10.2 起（FRB-010：之前成员会被再发布一次、占住端口）。

| | S 全部单跑 | H 全部进外壳 | X 混合 |
| --- | --- | --- | --- |
| 优势 | 只有改动的组件从源码跑，其余用发布的镜像；整套开销与全在容器里看不出差别（多 2–4%） | 合并照样省：组件 CPU 少 20%、内存少 35–36% | 组件 CPU 少 11–13%、内存少 22–23% |
| 劣势 | 本机进程连数据库与消息系统经宿主机端口，Docker 的用户态代理多转发一份（每千次 4–5 秒）；本机部分只活在 `up` 会话里 | 同左；本机的外壳崩溃时它的成员全部停 | 同左 |
| 适合谁 | 开发与调试一两个组件 | 调试外壳本身 | 同 S |
| 另做过的测试 | — | — | — |
| 限制 | 同 L | 同 L | 同 L |

## 套件 C、D、E 的结论与限制

套件 C（故障与运维）、D（多版本兼容）、E（多实例与多数据库）是第 11–13 步，还没测；第 11 步的计划见 [step11-plan.md](step11-plan.md)。

**限制与未测**（到第 10 步为止）：多台机器与高可用；TypeScript 组件；本机进程的长期运行；多节点 Kubernetes 与 Ingress；14 次/秒以上的负载；内存预算低于 4 GiB 时先坏的是什么；只有 Podman 的机器上的有根 Podman；后台任务领取的空闲轮询（P6.32 之后剩下的空转）。
