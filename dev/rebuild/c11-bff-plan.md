# C11：`infra/bff-mobile` 的子计划

阶段“按依赖顺序重建其余组件”的第十一个组件（[components-plan.md](components-plan.md) 的 C11）。数据与改坏检查放 `c11-data/`。

## 依据与牵动

- 边界卡 `docs/zh/07-components/infra.md` 的 `infra/bff-mobile`：
  - 页面形状的聚合查询，批量加载；没有业务数据，没有数据库。
  - 不越过组件边界读数据；按调用者的授权调用各组件；缺件时对应字段为空并标明。
  - 写操作直接转给属主组件。
  - 必需依赖是身份与被聚合的组件（D68 的例外：作为移动入口的组合层，被聚合的组件按客户装配明确列出、随入口发版）。
  - 验证故事：一个下游超时时其余部分照常返回并标明缺失。
- A108：Go 实现，GraphQL 用 gqlgen 挂在 Gin 上，可以进 Go 外壳。
- 底层选择“边缘”：聚合只给移动端，PC 直接调各组件。
- 协议 20：移动入口的会话与令牌（浏览器入口经边缘会话、原生应用存刷新令牌）。
- 协议 17：外壳与资源。
- `supporting-capabilities` 的待验证：用户身份与字段控制、扇出预算与缺件行为，随组件设计验证。
- 易错点“系统面的结果原样放进用户响应；用服务身份替用户取受范围约束的数据”：本组件是这条最容易犯的地方。
- 现在的状态（2026-11-13 读）：
  - 仓库 `brickKit/infra-bff-mobile`：旧版（2.x，TypeScript）在 `legacy/v2`，主分支只有 README。
  - 注册表有端口 8500（不暴露 gRPC）与 2.x 的权限键 `infra.bff-mobile.*`：已发布的键只追加、不改名，新设计的键怎样定见 P1。
  - 旧版设计按意图参考过：手写 schema 按页面裁剪、按装配裁剪字段、只认持久化查询、深度与复杂度上限、按数据范围选读路径。新设计不照抄，按终局的 SDK 与规范重写。

## P0：首批范围（AI 定，待复核）

| 项 | 首批 | 理由 |
| --- | --- | --- |
| 服务哪些页面 | 移动入口 C13 的首批页面：审批（我的待办、任务详情带单据摘要、同意与驳回）、我的通知（列表、已读）、产品查询（搜索、详情、各仓库的可用量）、客户查询、我的销售订单、我的商机 | 边界卡“外勤、审批、移动查询”；C1–C10 已重建的组件都有 |
| 读路径 | 一律经各组件的**用户面**、转发调用者的凭据（SDK 出站调用的 `ForwardUser`），由属主按调用者的授权与数据范围判断；名称补全用属主的批量读取（用户面的批量接口）；**从不经系统面取用户数据** | 易错点：系统面不按调用者过滤 |
| 写路径 | 只有任务的决定：前端给出待办条目里的“动作入口”（组件 + 路径），本组件只转发到部署里登记的、被聚合的组件，带幂等键；不编排多个下游 | 协议 09：动作发给任务所属的组件；不能变成开放的转发代理 |
| 缺件与超时 | 每个根字段与每次下游调用有自己的时限（从请求的截止时间逐跳缩短）；一个下游失败，只有它那部分为空，GraphQL 的错误带 `extensions.code` 与缺的组件；没装的可选组件，对应字段不注册 | 边界卡的验证故事；旧设计的“按装配裁剪” |
| 查询的限制 | 只认持久化查询（清单由移动入口构建产出，部署配置给出）；深度、复杂度上限；批量 id 有上限 | 公开的 GraphQL 入口不能接受任意查询 |
| 授权 | `/graphql` 是受保护的路由，有自己的操作（使用移动入口）；真正的判断在下游 | 每条路由要有操作定义；本组件不是数据的安全边界 |
| 事件与数据库 | 都没有 | 只读聚合；缓存只在一次请求里（批量加载） |
