# 第 12 步计划：套件 D，多版本兼容

> 2026-11-01 起草。依据：[实验计划](experiment-plan.md)的“套件 D：多版本兼容”与“步骤与检查点”第 12 步；[测试与验证](../../docs/zh/01-conventions/02-testing-and-validation.md)的 ST07、ST10；协议 [02](../../docs/zh/06-protocols/02-projections.md)（PJ36）、[17](../../docs/zh/06-protocols/17-runtime-and-resources.md#外壳义务)、[18](../../docs/zh/06-protocols/18-sdk-and-conformance.md)（SK09、兼容矩阵）、[19](../../docs/zh/06-protocols/19-config-secrets-registries-release.md#版本与产物)；数据协议 14 的“扩展与收缩”（DF23）。正式运行等维护者审完计划、下令。

## 1. 要回答什么

套件 A–C 里每格的版本都是整齐的一套。生产上不会一直这样：滚动升级时新旧两版同时在跑，客户基线里各组件升级的节奏不同，外壳与单跑的组件可能用着不同的 SDK。套件 D 回答：版本不整齐时，哪些组合照常工作，哪些被明确地拒绝，有没有“看起来成功、其实错了”的组合。

| 格 | 做什么 | 必须断言（实验计划） |
| --- | --- | --- |
| V1 | 同一组件新旧两版同时运行，共享数据库与消息（滚动升级的窗口）；反例：新版做了破坏性迁移 | 只做加法时两版都能读写、结果一致；破坏性迁移后旧版的写入被拒（ST10） |
| V2 | 契约新旧：旧调用方 → 新被调方；新调用方 → 旧被调方 | 追加的字段被忽略；新调用方用到旧版没有的操作时得到明确的“能力不支持”，不静默成功 |
| V3 | 事件新旧：新生产者的事件给旧消费者；旧事件重放给新消费者 | 未知字段忽略；未知事件类型按协议 02 处理，不丢、不卡住消费 |
| V4 | Go SDK 版本不同的两个组件互相调用、互发事件 | 信封、错误映射、截止时间与追踪的传递一致 |
| V5 | 跨语言加跨版本：旧版 Python SDK 的组件 ⇄ 新版 Go SDK 的组件 | 同 V4 |
| V6 | 两个 Go 外壳用不同的 Go SDK 版本；同一外壳内试图装两个 SDK 版本不同的成员 | 外壳之间照常通信；同一外壳内的版本不一致在构建或启动时被拒，不带病运行（SK09） |
| V7 | 外壳承载的成员版本与项目声明的不同 | 启动被拒并指出不一致（协议 17 的外壳义务、BrickKit 的版本核对） |

V1–V7 是正确性测试，不是性能测量：不切电源模式，不要求整夜安静（遇到计时才有意义的读数，例如 V1 的切换窗口，照记但不比较）。

计划要断言的几件，现在的规则或实现里还没有，或说不准。按改动的循环，先写清意图，再写会红的测试：

| # | 发现 | 依据 | 怎样处理 |
| --- | --- | --- | --- |
| F1 | **破坏性迁移之后，没有任何机制拒绝旧版本写入**。SDK 的迁移只记 `schema_migrations` 的版本，`serve` 不比较库里的迁移版本与自己认识的版本；协议 14 只规定“收缩只在旧版本全部退出后发”（DF23 是发布前的检查）。旧版本写到被删的列时会撞上 SQL 错误，不碰那一列的写入照常成功 | `be-sdk-go` 的 `db/migrate.go`；`be-protocol` `spec/05-database.md` P5.11–P5.16；协议 14 第 153、222 行 | V1 的反例先照现状测，预期失败（红）。机制要维护者定（第 8 节），定了再改协议与 SDK |
| F2 | **线协议没写消费者遇到未知字段、未知事件类型怎样做**。`spec/06-events.md` 里搜不到；项目协议 02 的 PJ36 只管投影（标为不完整并取回，不隔离、不跳过） | `spec/06-events.md`；协议 02 第 401 行 | AI 定（第 7 节）：线协议加一条，非投影的消费者忽略未知字段、对未知类型确认并记一次日志，投影按 PJ36；先写规则与向量，再测 |
| F3 | **协议 18 说的兼容矩阵还没有**：“协议版本、SDK 版本、套件版本与 BrickKit 版本之间有兼容矩阵，随协议仓库发布”，`be-protocol` 里没有这个文件 | 协议 18 第 126 行 | 先写矩阵（第 4 节第 1 步）：逐个读 `be-protocol` alpha.19–alpha.28 的发布，标出哪些改了线上的格式或语义。V4、V5 按矩阵的预言断言：标为兼容的组合必须互通，标为不兼容的必须被明确拒绝 |

| F5 | **探针单跑时的 SDK 很旧，进外壳就变新**：`test/probe-go` 3.2.21 要求 `be-sdk-go` alpha.23（组件都是 alpha.37），`test/probe-py` 3.2.20 用 `be-sdk-python` a20（组件是 a33）。编进外壳时，Go 的模块图把它升到外壳的版本（`be/go-core` 3.0.39 是 alpha.37）。所以探针的 X 格（一个单跑、一个在外壳里）一直是跨 SDK 版本在互相调用；而用探针比较“单跑对外壳”时，两边的 SDK 版本也不同，例如 P6.32（alpha.36，空闲时发件转发器少空转）只在外壳一侧 | `probes/go/go.mod`、`probes/py/pyproject.toml`、`shell/be/go-core/go.mod`；`D9-probe-*/cell.yaml` | 旧探针正好当 V4、V5 的“旧版”。另起一项核对：第 4、9、10 步用探针比较单跑与外壳的结论（基础开销、通信细分）是否受 SDK 版本差的影响，用 3.2.22（只升 SDK）重量一格对照；结果写进本步的记录，影响结论的回改原记录 |

## 3. 用什么测（AI 定）

**协议与契约的格（V2–V6）用探针，不用业务组件**。探针（`be-acceptance` 的 `probes/`，[契约](../../tools/be-acceptance/probes/CONTRACT.md)）有用户面与系统面的调用（`echo`、`work`、`call`）、一张表与它的事件（`write`）、消费对方的流，没有业务逻辑，加字段、加方法、加事件类型不会把只为测试的东西带进业务组件。V1 的“共享数据库与消息”也用探针：它有迁移与表。

**业务组件只用在两处**：
- V3 的投影一侧（PJ36）：销售的部门投影是链上唯一的投影。不为它给 `mdm/org` 发版本，而是由测试工具直接向 `BE_MDM_ORG` 流写一条信封合法、带未知字段的部门事件，和一条未知类型的事件（与第 11 步一样，从外部注入，组件不加钩子）。
- V7：用已发布的外壳（`be/go-core` 3.0.38 编进的是销售 3.0.14）配上声明销售 3.0.15 的项目，看 BrickKit 与启动器哪一层拒绝。

11-01 的 R4 已经顺带碰到过 V1 的一种：只升库存时，BrickKit 让 3.0.8 与 3.0.9 共用同一个 schema 并存。本步在探针上有控制地复现这种并存，并补上反例。

**专门发的版本**（探针在 `be-acceptance` 仓库，按开发阶段的版本规则只升最后一位；用过的版本号不再用）：

| 版本 | 内容 | 用在 |
| --- | --- | --- |
| `test/probe-go` 3.2.22、`test/probe-py` 3.2.21 | 只把 SDK 升到组件现在的版本（`be-sdk-go` alpha.37、`be-sdk-python` a33），契约不变 | V4、V5 的“新版”：与旧版只差 SDK，不混进契约的变化 |
| `test/probe-go` 3.2.23、`test/probe-py` 3.2.22 | 只做加法：`write` 的请求与事件加一个可选字段；系统面加一个方法 `Note`；用户面 `call` 支持 `op: note`；加一种事件类型 `test.probe.noted.v1`；一个扩展迁移（新的可空列） | V1 正例、V2、V3 |
| `test/probe-go` 3.2.24 | 收缩迁移：删掉 3.2.21 还在写的那一列（3.2.24 自己的代码不再用它） | V1 反例 |

收缩之后的 3.2.24 本身是一致的（代码与结构对得上），以后的格从空库起，用它没有问题；“破坏性”只是对旧版而言。

## 4. 步骤

1. **兼容矩阵**（F3）：读 `be-protocol` 的发布记录与 `spec/` 的改动，写 `be-protocol` 的 `compat.md`（或 `capabilities.json` 旁的一张表）：每个 alpha 改了什么、是否影响线上（信封、错误映射、截止时间、追踪、事件格式），由此推出 SDK 版本两两之间是否兼容。发 `be-protocol` 新的 alpha。
2. **未知字段与类型的规则**（F2）：线协议 `spec/06-events.md` 加规则与向量；两个 SDK 按规则实现（多半只需补测试），发版本。
3. **探针的三组版本**（第 3 节）：先写会红的一致性测试，再改探针，`brickkit release --notes` 发布。
4. **测试工具**（第 5 节）。
5. **D 行逐格跑 V1–V7**，每格出结果就写进记录；V1 的反例预期红（F1）。
6. **探针的 SDK 对照**（F5）：D 行用 3.2.22 的探针重量一格第 9 步的基础开销，与旧探针那一格同一批比较。
7. **其余五种形态的冒烟**（P、K、L、LD、LP 各跑 V1 正例与 V4）：服务名、地址、镜像标签随形态不同。
8. 记录 12-01、报告的“套件 D”一节、交接；实测之外的发现交 kb（多半是反馈：未知字段的规则、兼容矩阵的做法）。

### 5.1 各格怎样搭（2026-11-01 定）

同一组件的两个版本：`brickkit.yaml` 写两条（新版是默认版本，旧版带 `requiredBy`），部署文件给旧版一条 `id@版本` 的条目与自己的宿主机端口，`config/<名>@<版本>.yaml` 是旧版的配置；`brickkit up --dry-run` 生成两个服务（`test-probe-go-3-2-22`、`-3-2-23`），各跑一次迁移，共用同一个 schema 与流（在格的副本里试过）。格工具（`cells create`）按组件 ID 记录，不认识两个版本，由兼容工具在 `cells create` 之后补上这几处。

| 格 | 组件 | 测什么 |
| --- | --- | --- |
| D12-V1 | `test/probe-go` 3.2.23（默认）与 3.2.22（旧，端口 18610），`test/probe-go2` 3.2.23 消费 `test.probe_go` | 正例：两版各写、读回（旧版写的行 `label` 为空）、两版的事件都被消费。反例：默认换成 3.2.24（收缩），旧版仍在跑：旧版写入失败的样子（预期 500 `INTERNAL`，列不存在）、它不碰那一列的写入照常成功、旧版重启时迁移怎样（库里的迁移版本比它认识的新） |
| D12-V2 | Go：`test/probe-go` 3.2.23 ⇄ `test/probe-go2` 3.2.22；Python：`test/probe-py` 3.2.22 ⇄ `test/probe-py2` 3.2.21；互为下一个、互相消费 | 新调旧的 `Note`（两个面）得到什么；旧调新照常；给旧版的写入带上不认识的 `label`；新版发的 `noted` 旧版收不到、订阅不卡住，带 `label` 的事件旧版照常消费 |
| D12-V3 | 业务链（同 D9-S，销售 3.0.16、出账 3.0.15） | 向 `BE_MDM_ORG` 注入：已有部门的未知动作（投影标不完整、修复取回）、法人的事件（不进部门投影）、`changed.v1` 多一个字段（照常生效）；订阅不卡住、没有死信 |
| D12-V4 | `test/probe-go` 3.2.21（alpha.23）⇄ `test/probe-go2` 3.2.22（alpha.37） | 两个面、两个方向的调用；事件互发；错误原因（`NO_NEXT_PROBE`）与 `domain` 穿过；截止时间与追踪编号在两侧日志里对得上 |
| D12-V5 | `test/probe-py` 3.2.20（a20）⇄ `test/probe-go` 3.2.22（alpha.37） | 同 V4 |
| D12-V6 | 两个不同 SDK 的 Go 外壳各承载一个探针（`be/go-core` 3.0.40 是 alpha.37，较早的一版是更早的 SDK）；另在临时模块里把要求不同 SDK 的两个成员编进一个外壳 | 外壳之间照常通信；构建、启动器、`make pin-check` 对 SDK 不一致各说什么 |
| D12-V7 | `be/go-core` 3.0.39（编进销售 3.0.15）配上声明销售 3.0.16 的项目 | 谁拒绝（BrickKit 的检查或外壳启动器），报错是否点名成员与两个版本 |

## 6. 时长

估计（实验计划写 3–4 天）：矩阵、规则与探针的三组版本约 1 天；测试工具约 1 天；D 行 7 格约半天（每格起格 5–10 分钟，测试几分钟）；五种形态的冒烟约 2–3 小时；探针的 SDK 对照约 1 小时（性能测量，performance 电源模式，要机器安静）；记录半天。V1 反例的机制（F1）若维护者定了要做，另加协议与两个 SDK 的改动与发布，约 1 天。

## 7. 已定的做法（AI 决定，供复核）

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 测什么组件 | 探针为主，业务组件只在 V3 的投影与 V7 | 只为测试的字段、方法、事件类型不进业务组件；探针本来就是为协议测试做的 |
| 版本分三组 | SDK 升级、只做加法、收缩各发一个版本 | 一次只变一样，结果才看得出原因 |
| 投影一侧的事件 | 测试工具直接写进流，不给 `mdm/org` 发版本 | 与第 11 步的外部注入一致；业务组件不为测试发版本 |
| 未知字段与类型（F2） | 线协议加一条：非投影的消费者忽略未知字段，对未知类型确认并记一次日志；投影按 PJ36 | 契约只做加法（决定 0302）意味着旧消费者一定会收到它不认识的字段与类型；不确认会让流卡住，与“不丢、不卡住”相反；投影要知道自己缺了什么，所以标不完整并取回 |
| 正确性测试的条件 | 不切 performance、不要求整夜安静 | 用户级规则：只有受电源影响的性能测量才切 |

## 8. 要维护者定的

- **F1：破坏性迁移之后怎样拒绝旧版本**（与 G4 一起）。现状已跑出（第 9 节的 V1）：收缩迁移后旧版写入答 500 `INTERNAL`；扩展迁移后旧版的迁移就失败，旧版重启不了、`brickkit up` 整体中止。2026-11-01 问维护者。可能的方向：收缩迁移在 SDK 的表里写一个“最低可写的组件版本”，低于它的版本启动时拒绝（以 78 退出并说明），已经在跑的在下一次取连接或下一个事务时拒绝；或者交给部署：BrickKit 在 `up` 时比较库里的版本与要启动的版本。

## 9. 进度

- 2026-11-01：计划起草；维护者下令开始。
- 2026-11-01 第 1、2 步（F2、F3）：`be-protocol` 3.0.0-alpha.29 发布：`COMPAT.md`（兼容矩阵：alpha.19–alpha.29 之间改的都是各自内部的行为，信封、错误体、截止时间与追踪没有变，任意两版线上兼容；alpha.24 新加的错误原因由调用方按 gRPC 码归类，也兼容；各 SDK 版本实现的协议版本）与 P6.33（消费者忽略载荷里不认识的字段；按类型订阅的只收它列出的类型；读模型按聚合订阅，不认识的类型不取载荷、标为不完整并取回）。
