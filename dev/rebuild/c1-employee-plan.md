# C1：`mdm/employee`

> 2026-11-10 起，按 `f-plan`；阶段计划 [components-plan.md](components-plan.md) 的 C1。仓库 `brickKit/mdm-employee`（子模块 `components/mdm/employee`，C0 建）。推进方式照根 `AGENTS.md`。

## 依据与牵动

- **边界卡**：`docs/zh/07-components/mdm.md` 的 `mdm/employee`：员工、任职、员工与账号的映射（非一一对应）、员工与收款伙伴的映射、受限的个人资料；入职、调岗、离职（生效日期）；任职查询；水位来源与补取；离职、任职结束、账号关联结束先写意图证据（协议 15）。
- **适用协议**：02（投影与水位来源）、07（生命周期）、08、13、16（导入与期初任职）；安全 02（同一员工的多个账号算一个人）、04（任职关联授予）、08（账号与员工关联是受保护操作，第 21 行）。决定 D06、D09、D30、D62、D66、D69。
- **牵动别的组件**（开工时已查）：
  - `infra/authz`：已有确认与受保护操作（3.0.18 起）、账号状态变更的确认（3.0.25），**没有**“账号与员工关联”的确认对象，**没有**任职关联授予（设计文档“没有做”一节）；
  - `mdm/partner`：员工往来角色的开通与暂停经它的接口（D69）；
  - 身份成员 `infra/iam-casdoor`：订阅入职事件开通账号或提示身份管理员（边界卡），本组件只发事件；
  - `infra/workflow`（C7）：任职结束驱动待办重分配（协议 09），到 C7 时接。

## E0 的结果（2026-11-10，AI 定，待复核）

**首批做的**（对应边界卡与安全 04、08）：

| 能力 | 怎样做 |
| --- | --- |
| 员工的生命周期 | 预入职 → 在职 → 离职（生效日期；生效后全部任职结束）；工号在法人内唯一；协议 07 的生命周期 |
| 任职 | 资格实例（法人、部门、岗位、有效期），不可复用：结束后重新任职是新实例；同一人同一岗位的有效期不重叠；改法人、部门、岗位结束旧任职、建新任职（安全 04 的“有安全含义的变化”），显示类字段原地改 |
| 账号与员工的关联 | 非一一对应；建立与结束是受保护操作：先在授权组件建确认（E4），本组件核对确认后生效；关联保存两侧身份与修订，不按姓名、邮箱、工号自动匹配（安全 02） |
| 安全来源 | 离职、任职结束、账号关联结束先在事务外写意图证据，再提交，结论随事务（协议 15，照 `mdm/org` 的做法）；本组件是水位来源，流带记录读取（SDK 已有） |
| 事件 | 员工、任职、账号关联的完整状态事件；任职开始与结束 |
| 查询 | 员工列表与详情（受限字段按授权的可读字段遮蔽）、某人当前的任职、某岗位的持有人、某账号关联的员工 |
| 最后管理员的提示（D62） | 离职时问授权组件这个人的账号里有没有授权管理员；是就在响应里提示，不阻止 |

**`infra/authz` 一侧（E4）首批做的**：账号与员工关联的确认对象（安全 08 第 21 行：建立与结束都要独立确认人或部署所有者确认）；确认人的独立性按自然人判断（关联同一员工的账号算一个人，读本组件的水位来源）；任职关联的授予：授予可以绑定一个任职实例，任职结束（读本组件的事件与水位）时自动撤销绑定它的授予与管理持有资格（D30 的前一半）。

**不在首批**（理由与什么时候做）：

| 能力 | 理由 | 触发 |
| --- | --- | --- |
| D30 的后一半：新任职自动生成授予建议 | 建议要按模板或角色推出候选、由管理者提交确认，是授权管理的一整块（安全 04 的计划与模板）；首批由管理者手工授出并绑定任职，效果相同、只是没有建议 | 客户要“调岗后给出建议”，或 `infra/workflow` 做好后一起做（建议成为待办） |
| 员工往来角色（D69） | 使用者是报销与薪资，都在“远期”；`mdm/partner` 也还没有这个角色 | 第一个 `hrm/expense` 或薪资组件开工 |
| 身份成员订阅入职事件自动开通账号 | 客户配置项，首批由身份管理员在 Casdoor 开账号，再在本组件建关联 | 客户要求自动开通 |
| 导入与期初任职（协议 16） | 首批经接口逐条建（种子也走接口）；批量导入是协议 16 的一整块 | 第一次上线迁移或 C14 |
| 本人资料变更申请 | 边界卡写“远期” | 员工自助开工 |
| 任职结束驱动待办重分配（协议 09） | 消费方是 `infra/workflow` | C7 |

**阶段计划要补的一类前置工作**：后面的组件要用到已重建组件还没做的能力时，先回源头补（“依赖方缺能力时去源头补”）：这次是 `mdm/org` 的岗位（E0b）；C2 `erp/purchase` 要 `mdm/partner` 的供应商角色，C3、C4 很可能还要别的。每个组件的 E0 都列出它需要、源头还没有的能力，排在它前面做。
