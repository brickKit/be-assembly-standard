## 待定（定稿前要回答）

| 问题 | 候选 | 倾向 |
| --- | --- | --- |
| 审计的契约放哪 | 计划只列了授权与身份两个契约仓库；审计是被调方，按“被调方发布契约包” | 放在 `infra-audit` 仓库的子目录里单独发布（同探针的做法），不另建仓库；建仓库要用户确认 |
| **契约的线格式（需要用户决定）** | 安全 09a 规定安全记录的摘要按 RFC 8785 的规范 JSON 计算，“冻结时由字段表统一生成 protobuf 与 JSON Schema”，没说线上传哪一种；系统面按底层选择走 gRPC + protobuf。A：安全记录（视图分片、授予段、定义）也写成 protobuf 消息，接收方还原成规范 JSON 再核对摘要；B：信封（随机数、分片号与状态、恢复代次、回执）写成 protobuf，安全记录本身作为规范 JSON 字节放在 `bytes` 字段里，按 JSON Schema 校验，摘要直接对收到的字节核对 | 推荐 B：摘要的依据原样到达，两种语言都不用在热路径上把 protobuf 逐字节还原成规范 JSON（A 一旦两边还原得不一致，视图就核对不过、授权全部失效）；契约仍是生成的类型，调用面照常是 gRPC + protobuf。选 A 要为还原规则写全部向量 |
| Casdoor 能否提供账号的变更序号或管理事件 | 边界卡写明“待代表部署实验核实，核实前按外部来源声明” | **初步（读源码，2026-10-18）：给不出可靠的变更序号**。操作记录表（`record`）有自增编号、经 API 的操作都会记，但记录是在请求处理之后另起协程异步写入：崩溃时可能丢，编号顺序也不保证与变更生效的顺序一致，另有“只记写操作”的设置；webhook 可配重试，但没有序号、不保证顺序。所以按外部来源声明，正确性靠定期的全量状态比较（账号的停用状态与更新时间），操作记录与 webhook 只用来更快发现。本步用最小复现确认（在控制台停用一个账号，看记录与 webhook），结论写进边界卡 |
| 边缘的会话缓存与失效推送 | 边界卡列入代表部署实验 | 不在本步（计划的“只实现到”没有它）；记进后续 |
| 外壳 | 计划：基础外壳 `be-go-infra` 承载身份、授权、审计与主数据 | 本步先单跑通过 L2，再在一格里进外壳跑剖面 |

## 风险

- **契约改动的连锁**：契约包一改，SDK、探针、外壳都要跟着升版本，和第 4 步的修复一样一路发下去；按依赖顺序发，每层测完再发下一层。
- **Casdoor 的行为未知**：变更序号或管理事件若不存在，授权的新鲜度只能按外部来源声明，安全 03 的相关保证要在边界卡写明降级。
- **授权是每个请求都读的**：视图核验的性能直接进每个请求，按“性能与可读性”的规矩，写完先量。
