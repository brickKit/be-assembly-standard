## 决定（起草时）

| 问题 | 候选 | 决定 |
| --- | --- | --- |
| 预占分支的命令用族契约还是各写一份 | 新建族契约仓库 `contract-erp-reservation`（仓库动作）；库存与信用各发布同形的 `ReservationService` | **AI 决定**：各写一份同形的（同第 6 步来源方法的决定）；第三个参与方（预算）出现时评估族契约 |
| 新单据怎样取法人的证据（R1 的设计问题） | 法人的投影（`mdm/org` 是水位来源，但补取 S6 还没做）；同步调用 `mdm/org` 的来源读取 | **AI 决定**：确认订单与正式化账单时，在事务外同步读取法人（`SourceService.Read`），状态不是 `active` 就拒绝；与伙伴开通角色的做法一致。客户与产品各用属主的资格查询（W 内提交） |
| 单据上的伙伴与产品显示字段 | 投影；引用时快照 | **AI 决定**：快照（协议 07 的快照字段：名称、税号、单位等只存必要的），建明细与确认时取；不建伙伴与产品的投影 |
| 外币订单的汇率 | 报价时快照；确认时快照；出账时另取 | **AI 决定**：订单币种与法人本位币不同时，确认订单时按业务日期取 `spot` 有效汇率并快照（协议 14）；报价只显示参考；账单沿用订单的快照（财务的账簿规则不在本步） |
| 信用额度的币种 | 按法人本位币换算；按订单币种的额度 | 照边界卡：额度按（伙伴、法人、币种），订单用同币种的额度，不换算；没有该币种额度的客户按信用政策“不控制”或“拒绝”（政策在额度记录上） |
| 库存维度 | 产品、仓库、批次、序列号全做；只做产品与仓库 | **AI 决定**（设计阶段再确认）：产品、仓库、批次；序列号产品的出库必须指定序列号（边界卡的验证故事），本步序列号只做到“必须指定、存在且在库” |
| 销售单据的数据范围 | 不带维度；法人、部门、负责人 | 带维度：法人（值集合）、部门（组织树，按订单负责人的部门）、负责人（主体），兑现种子清单里测试账号“预定的范围”；授权组件第 5 步已支持这三种 |
| 单号 | 全局序列；按法人连续 | 按法人连续（协议 14 的单号、账单“按法定要求连续”）：订单与账单各一条序列，`db.NextNumber` 在签发的事务中取号；格式在设计阶段按协议 14 定 |
| 打印怎样接 | 出账同步调打印并存 PDF；按需渲染 | **AI 决定**：按需渲染：账单提供“取 PDF”，调用时把账单数据交给打印渲染，不存 PDF（附件组件不在本步）；打印缺席时答“依赖不可用” |
| 发布说明 | 注释标签只写一句；`brickkit release --notes` | 照交接：`brickkit release --notes <文件>`，使用方必须做的在前、新增在后；Go 的 `v` 标签用同一份说明 |
| be-sdk-python 的记录校验 | fastjsonschema；jsonschema-rs | 照第 6 步的决定，在本步开头换成 jsonschema-rs（打印第一个用） |

## 第 7 步报告要写的发现

- **销售是第一个消费别的组件事件的已重建组件**：组件定义要写 `Subscribes: true`，清单要声明 `BUS_SUBSCRIPTION_CONCURRENCY`（SDK 生成的 `configSchema` 会提示）；L2 里测试自己扮演 `mdm/org` 发事件（SDK 的运输、`Row.Headers`、`events.Subject`），投影按需补取、事件改写、对齐都走通了。
- **SDK 的列表编译只按本表的列下推组织树维度**（`authz/sql.go` 的 `tree` 原子），定义里的 `LocalProjection` 下推没有实现；销售把部门路径复制到单据上并随事件改写，部门移动到改写之间有一个窗口（投影的新鲜度）。记为已知风险，也考虑在 be-sdk-go 实现按投影下推。
- **契约里的“规范 JSON”与 SDK 的 `canon.Encode` 不一致**：来源方法的 `data` 在契约注释里叫“规范 JSON”，主数据组件与销售都用 `json.Marshal`；`canon.Encode`（RFC 8785）拒绝 `null`，而载荷里有可空字段。要么改契约的说法，要么让规范编码允许 `null`，在第 7 步报告里提出。
- **授权视图是定期取的**：测试中途加的授予要等下一次取到（`Eventually`）。**列表没有授予时答 200 与空页**，不是 403（安全 07）。
- **出站调用要标幂等**：SDK 只重试标了 `calls.Idempotent()` 的调用；协议 04、05 的命令都按业务身份幂等，忘了标就丢掉重试（出账写测试时查出）。可以考虑让 SDK 或 lint 提示“带业务身份的命令没有标幂等”。
- **Python SDK 的子集补到了能做一个业务组件**：列表、文档核对、任一组件可调都补齐了；搜索（P9.6–P9.8）、幂等键、后台工作项、金额与业务日期仍未实现，下一个 Python 业务组件开工前要先补。`be/py-render` 的镜像随打印进外壳要换成 Debian slim（T7.9）。
- **就绪检查要答 `HEAD`**：打印的镜像是 Debian slim，平台的健康检查 `wget --spider` 在那里是 GNU wget，用 `HEAD` 查 `/readyz`；BusyBox（Alpine）的 wget 用 `GET`，所以 Go 组件一直没碰到。be-sdk-python 对 `HEAD /readyz` 答 404，打印在 D7-S 里永远不健康。从源头改：协议 P1.6 写明 `GET` 与 `HEAD` 都答（RFC 9110 要求支持 `GET` 的地方支持 `HEAD`，be-protocol 3.0.0-alpha.21），两个 SDK 都答（be-sdk-python 3.0.0a26、be-sdk-go 3.0.0-alpha.30），打印 3.0.1、`be/py-render` 3.0.21。可以向 BrickKit 提：平台的健康检查在不同基础镜像上发的方法不同。
- **版本常量与清单会漂移**：打印 3.0.1 改了 `component.yaml` 与 `pyproject.toml`，代码里的版本常量还是 3.0.0（启动时会因 `COMPONENT_VERSION` 不符而拒绝），单元测试没发现。两个 SDK 的清单核对加上 `metadata.id` 与 `metadata.version` 对照组件定义（be-sdk-python 3.0.0a28、be-sdk-go 3.0.0-alpha.32；中间一版错把 `metadata.name` 当成 ID，没先拿真实清单试就发了，随即改正）；Python 的组件与外壳改为从安装的包读版本（打印 3.0.2）。
- **销售的种子三种拒绝只出现一种**：三种拒绝挂在同一个状态上，先匹配的“没有额度”包揽了 CN01 与 US01；“超过 20,000”的订单要 900 件，库存先拒（`insufficient_stock`），信用根本没看到。改为三种轮流、超额用服务行（不占库存），`erp/sales` 3.0.2（`erp/billing` 3.0.2 跟着改依赖，`be/go-core` 3.0.23）。核查种子要按原因数一遍，不能只看“有被拒的”。
- **“重跑不改动”要等后台做完再比**：种子刚结束时，取消与完成的后半段（信用分支的释放）还在后台跑几秒；紧接着取的快照会和重跑后的不同，看起来像重跑改了数据。比较之前先等两次相隔 15 秒的快照相同（格的全流程脚本的 `settle` 一步）。
- **剖面查 gRPC 端口在容器里用 `nc`**：Debian slim 的镜像没有 `nc`，`be/py-render` 承载的探针被判“就绪时 gRPC 端口没监听”；改为没有 `nc` 时用 python3 连，两样都没有时报“查不了”而不是“没监听”（be-acceptance 的 `cells/observe.py`）。剖面只能在一次新起的格上跑：停了再起的容器带着上一次的日志（“就绪”两行），新进程也还没有请求指标。
- `erp-credit` 的 README 修了一句（新仓库不是重开），随 3.0.1 发布。

## 风险
