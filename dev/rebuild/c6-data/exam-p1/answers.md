# 参考答案（出题时写）

1. 两张：同一请求的重复投递按事实身份（= 请求身份）去重只生成一张；两个幂等键是两个请求。商机上看到两个 `quote_request`，销售的报价事件到达后各标 `drafted` 并记报价身份；`sales_link` 两张报价。依据：OP05、OP08、验证故事 1。
2. 手工赢单（`win`，`crm.opportunity.close`），可给赢单金额；请求报价照样发布事实，没人消费，停在 `requested`。依据：OP06、依赖表、验证故事 2。
3. 订单的完整状态事件里状态变成 `confirmed` 且带商机参考、商机在进行中时 → `won`；金额 = 订单不含税合计；操作者是系统，触发记订单身份。币种不同：用预计金额并在阶段历史原因里写明。报价被接受那一刻不赢单（设置不是 quotation_accepted）。依据：OP08。
4. 重开（写原因）→ 回到关闭前的阶段，概率为那个阶段的缺省；然后修改金额；再赢单。赢单后直接改金额答 `WON_AMOUNT_LOCKED`。依据：OP02、OP07。
5. (a) 回退 `revert`，写原因；(b) 目标等于当前答 `STAGE_ORDER`；(c) 推进可以跨步 `advance`。概率变目标阶段缺省，命令可给。依据：OP03。
6. 只记下关联单据（`sales_link`），不改状态，不自动重开；由人决定。依据：OP08、未决问题。
7. 数据范围按负责人维度：张三（授予限定为本人）只看自己负责的；改负责人要 `crm.opportunity.assign`，普通销售没有；漏斗只算他看得见的商机，加权金额 = 金额×概率/100。依据：命令与查询、OP04、术语。
8. 资格查询答 `role_not_opened` → `CUSTOMER_NOT_ELIGIBLE`；法人或币种不可用 `REFERENCE_INVALID`；不可达 `DEPENDENCY_UNAVAILABLE`，什么也没改。依据：OP01、拒绝的原因。
9. 销售按它的规则拒绝并发布“拒绝请求”的事实（名字在销售 P2b 定），商机订阅后把请求标 `rejected` 记原因；草稿可以不完整，税率与价格由销售人员补齐后再发出（销售 P2b 的规则，未决问题）。销售的文档现在还没写这些（空白）。依据：OP08、未决问题。
10. 两边都声明会把精确版本互相钉住，任何一边发布都要另一边再发布；只订阅不需要依赖；销售没装时流不存在，订阅等待。依据：规则要点、事件。
11. 替换 `forecast` 模块（Fork），查询的形状不变。依据：规则要点、部署与替换。
12. 销售的报价事件按版本覆盖、可以重放；重新投递请求不会生成第二张草稿（按事实身份去重）。设计没写谁触发重放（空白）。依据：整套恢复之后。
