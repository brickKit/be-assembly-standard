我已经读完设计文档、边界卡、A71、协议 07/02/14、安全 07、销售与伙伴的设计、BRICKKIT.md 和事件 schema，正在整理答案。

先说结论里最要紧的一点：**crm/opportunity 的设计假定了 erp/sales 的几项能力，但 erp/sales 现有文档和契约里都没有。**

- 销售没有消费 `crm.opportunity.quote_requested.v1`。
- 销售没有“拒绝请求报价”的事实。
- 订单事件没有商机参考。
- 报价事件没有请求身份。

下面逐题回答，最后一节汇总空白与矛盾。

## 逐题回答

**1. 两个不同幂等键各请求一次，第一次的事件被投递两次**

- **商机侧（opportunity 的 design.md，OP05）**：两个不同的键是两个请求，各生成一个请求身份，各写一行 `quote_request`（状态 `requested`），各发一个 `quote_requested.v1`，事实身份等于请求身份。同一键重放才答同一个请求。“一个商机可以有多个请求（改了需求再要一张报价）”。
- **销售侧**：设计的验证故事 1 和“整套恢复之后”一节说“销售按事实身份去重”。
- **张数**：按这些文字推算，销售应生成 **2 张**草稿，每个请求身份一张；重复投递的那次不产生第三张。
- **商机上能看到**：design.md 的 OP08 说，报价事件带请求身份时，商机把对应请求标为 `drafted`；`sales_link` 按单据身份与版本覆盖。读取商机会返回请求报价和关联的销售单据（“命令与查询”表）。所以应有 2 个请求，各自 `drafted`，并有 2 条报价的 `sales_link`。
- **文档没写**：销售怎样消费这个事件、怎样去重。erp/sales 的 design.md 和 BRICKKIT.md 都没有消费 `quote_requested` 的描述。报价事件 schema（`erp.quotation.changed.v1`）只有 `opportunity_ref`，没有请求身份字段，所以“报价带请求身份”目前没有载体。

**2. 装配里没有 erp/sales**

- **赢单**：手工赢单，用 `crm.opportunity.close`（OP06）。依据是“依赖”表的 `erp/sales` 一行：“赢单与输单手工照常”。验证故事 2 也这样写。
- **请求报价**：不会失败。同一行写“请求报价照样发布，没有人消费，请求停在 `requested`”。“事件”一节写“销售没装时流不存在，订阅不报错、只等待”。
- **文档没写**：商机界面或读取是否提示“销售未安装”。商机一直停在 `requested` 的请求没有超时，也没有取消命令。

**3. 设置为 `order_confirmed`，报价被接受、转订单草稿、订单确认**

- **赢单时刻**：OP08 写明，`order_confirmed` 设置下，订单变成 `confirmed` 时，商机若在进行中就 → `won`。报价被接受、订单还是草稿（erp/sales 的 `draft`）时，商机不赢单，只记下 `sales_link`。
- **金额**：赢单金额等于订单的不含税合计，即订单事件 `totals.net`。
- **操作者**：系统。触发记单据身份，阶段历史写触发（“拥有的数据”表的 `stage_change` 一行）。
- **币种不同**（订单 USD，商机 CNY）：OP08 写“币种不同时用预计金额，并在阶段历史的原因里写明”。即赢单金额取商机的预计金额，币种仍是 CNY；这一点在“未决问题”里写成“同币种时用合计，否则预计金额”。
- **依据的衔接问题**：商机要认出这张订单属于自己，必须靠“带商机参考”。但 `erp.sales_order.changed.v1` 的 schema 里没有商机参考字段，只有 `quotation_id`；报价事件只有 `opportunity_ref`（字符串，描述为“crm/opportunity later”）。见下文空白第 1 条。

**4. 商机已赢单，要把金额改大**

- **直接改**：拒绝，错误 `WON_AMOUNT_LOCKED`（OP02）。赢单后金额、币种、客户、明细都不能改；名称与预计成交日可以改。
- **做法**：先 `reopen`（OP07），需要 `crm.opportunity.close` 和写明原因。
- **重开后的状态**：回到关闭前的阶段，概率回到那个阶段的缺省值（10、25、50、75），清掉赢单金额与关闭原因。
- **之后**：商机在进行中，可以改金额，再赢单。
- **文档没写**：重开时，原来手工给的概率是否保留，文档只说回到缺省值，没说用户先前改过的概率是否丢失。

**5. 商机在 `proposal`**

阶段顺序是 qualification < needs_analysis < proposal < negotiation（“术语”表）。OP03 的规则如下。

- **(a) 改到 qualification**：这是回退，用 `revert`，目标在当前之前，要写明原因。需要权限 `crm.opportunity.edit`。概率改为目标阶段的缺省值，命令里给了概率就用给的。写一行阶段历史，发 `stage_changed`。
- **(b) 改到 proposal**：目标等于当前，答 `STAGE_ORDER`。
- **(c) qualification 的商机直接改到 negotiation**：这是推进，可以跨步（“推进可以跨步（目标在当前之后）”），用 `advance`，同样需要 `crm.opportunity.edit`。概率变为 negotiation 的缺省 75，除非命令里给了值。
- **文档没写**：`edit` 能否直接改阶段字段。OP02 的可改字段里没有阶段，只有 `advance` 和 `revert`。

**6. 商机已输单，之后客户接受报价并确认订单（`order_confirmed`）**

- OP08 写明：商机已赢单或已输单的“只记下，不改状态”。所以商机仍是 `lost`，`sales_link` 更新，阶段历史没有新行。
- “输单之后客户又下了单，由人决定要不要重开”（OP08 与“未决问题”）。人要赢单，必须先 `reopen`，再 `win`。直接 `win` 在 `lost` 上被拒绝（OP06）。
- **文档没写**：是否有任何提示告诉人“已输单的商机有订单到达”，例如通知或读取里的标记。

**7. 普通销售张三与销售主管李四**

- **张三看到谁的商机**：资源 `crm.opportunity` 有两个维度，法人（值集合）和负责人（主体）。验证故事 5 与“规则要点”写明“销售只看自己的商机”，按负责人字段。所以张三看到自己负责的商机，限于他被授予的法人。
- **能否交给王五**：`assign` 是另一个操作 `crm.opportunity.assign`，OP04 写“给‘销售主管’而不给普通销售”。所以张三不能，李四可以。
- **关闭的商机也能交接**（OP04）。
- **漏斗**：漏斗按法人、币种、阶段，算个数、金额合计和加权金额（加权金额 = 预计金额 × 概率 / 100，“查询里算，不存”）。“命令与查询”表写“只算看得见的商机”。
- **漏斗数字的算法依据**：安全 07 的“排序、筛选、分组与聚合用到受限字段”一节：对受限字段求和、分组，需要证明所有可见行上该字段可读，证明不成立就拒绝这一查询用法。
- **文档没写**：商机的金额、概率字段是否被资源定义标为受限字段，设计没有列出字段级的读写范围。所以漏斗对张三能否直接求和，设计没有回答。

**8. 新建商机时的引用问题**

- **客户在该法人下没有客户角色**：OP01 要向 `mdm/partner` 取资格，用途 `sell`。伙伴的资格规则是“伙伴 `active` 并且该法人下该用途的角色 `active`”才 `eligible`。否则回答缺的部分，如 `role_not_opened`。商机拒绝，错误 `CUSTOMER_NOT_ELIGIBLE`，细节带 `role_not_opened`（design.md“拒绝的原因”）。
- **法人或币种不存在**：`REFERENCE_INVALID`（同上，“法人或币种不可用”）。
- **mdm/currency 不可达**：`DEPENDENCY_UNAVAILABLE`，“什么也没改，可以重试”。依据协议 07：不可达不等于不存在，资格引用无法证明时拒绝或暂缓。
- **时间约束**：资格在 30 秒内提交（协议 07 的 W）。设计写“资格在有效期内提交”。取证在事务之外（“事务里不调用别的组件”）。
- **文档没写**：币种“活跃”是什么意思，`mdm/currency` 的设计与契约没读，也没在商机文档里引用。

**9. 销售收到请求，客户已不合格；草稿没有税率**

- **销售怎么处理**：design.md 写“哪些情形拒绝，归销售”。erp/sales 的文档写到：确认时取证客户资格；报价的新建要不要取客户资格，**文档没写**。边界卡和 sales 的 design.md 都没有“从请求生成草稿时取资格”的规则。
- **商机怎么知道**：design.md 写“销售拒绝请求报价的事实把请求标为 `rejected` 并记原因”，订阅里有“销售拒绝请求报价的事实（名字在销售的 P2b 定）”。但 erp/sales 的事件清单（`events/` 目录）里没有这个事实，**销售那边文档没写**。
- **草稿没有税率**：design.md 的“未决问题”最后一行：税率与价格由销售人员补齐后再发出（“销售 P2b 的规则；商机不知道税率”）。erp/sales 的报价 schema 里 `tax_rate` 是必填，`tax_source` 只有 `manual`，BRICKKIT.md 写“税率本版由人录入”。所以人补税率，这一点两边一致。
- **文档没写**：请求没有价格表项时，草稿是否可以带 0 单价或空单价。

**10. 为什么互相不声明依赖，怎么找到对方的事件**

- **为什么**：design.md“规则要点”第一条：两边都声明，会把精确版本互相钉住，任何一边发布都要另一边再发布，见 C5 的教训。
- **怎么找**：靠订阅流名与事件名。商机订阅销售的流 `erp.sales` 的 `erp.quotation.changed.v1`、`erp.sales_order.changed.v1`，以及拒绝事实（“事件”一节）。销售订阅商机的流 `crm.opportunity` 的 `quote_requested.v1`——这一半**销售文档没写**，在 sales 的设计里“商机与客户关系只经事件”只出现在“以后”。
- **文档没写**：C5 的教训具体是什么，design.md 只引用了名字，也没写事件名、流名由谁登记在装配注册表里。

**11. 预测改成“按历史赢率”**

- **改哪里**：design.md“规则要点”的“预测”一条：方法是替换点，Fork 时换掉 `forecast` 模块。
- **漏斗查询的形状变不变**：“查询的形状不变”。
- **文档没写**：历史赢率需要的数据（按阶段、按负责人、时间窗口）要不要新增表或字段。设计只有 `stage_change` 一张阶段历史，可以算，但没有说明。部署设置里也没有切换预测方法的配置项。

**12. 整套恢复后，请求停在 `requested`，销售已有草稿**

- design.md“整套恢复之后”：请求停在 `requested` 的，“销售那边按事实身份去重，重新投递不会生成第二张草稿；销售的事件按版本覆盖关联单据，重放安全”。
- 按这个说法：恢复后补发 `quote_requested` 时，销售识别出事实身份已处理，不再生成；销售的报价完整状态事件再次到达商机，OP08 把请求标为 `drafted`，覆盖 `sales_link`。
- **依据缺口**：这一路径依赖“报价带请求身份”，见问题 1。
- **文档没写**：恢复核对（`CheckService`）有没有检查“请求 `requested` 但销售已有草稿”这类差异。design.md 只说了“存在性与版本：商机（审计过的对象）”。

## 文档的空白与矛盾

1. **erp/sales 没有承接 A71 的商机部分。**
   - 报价事件有 `opportunity_ref`（可空字符串，说明“crm/opportunity later”），没有请求身份字段。
   - 订单事件（`erp.sales_order.changed.v1`）没有商机参考字段，只有 `quotation_id`。
   - erp/sales 的 BRICKKIT.md 写“本版答‘能力不支持’的：……合同与商机的参考”，design.md“实现状态”也写了。
   - 因此商机的验证故事 1 和 3 现状下做不出来。边界卡写“订单事件带商机参考”，这与 sales 的 schema 对不上。
   - 订单的商机参考可以靠 `quotation_id` 间接找到报价，再找商机，但商机的 OP08 说“只取带商机参考”的单据，没有这样的间接路径，也没人定。
2. **erp/sales 没有消费 `quote_requested`，也没有“拒绝请求报价”的事实。** 商机的订阅一节写“名字在销售的 P2b 定”，但 erp/sales 的文档里没有 P2b 这个编号，也没有计划。erp/sales 的 design.md 事件一节、依赖一节也没有订阅商机流。
3. **请求身份没有载体。** OP08 写“报价带请求身份的，把那个请求标为 `drafted`”。现有报价 schema 无此字段。同样，“销售按事实身份去重”要求销售记下已处理的事实身份，销售的“拥有的数据”表里没有这张表。
4. **资格语义不完全一致。** 商机 OP01 用 `sell` 资格取客户；销售的报价新建是否取资格没写。商机请求时客户可能已不合格（问题 9），销售端的处理“归销售”但销售文档没写。
5. **边界卡与设计不一致。**
   - 边界卡 crm.md 的必需依赖只有 `mdm/partner`、身份、授权，design.md 加了 `mdm/org`、`mdm/currency`（design.md 标“AI 定，待复核；装配项目的边界卡与组件索引随 P1 改”）。
   - 组件索引（09-component-index.md）的 `crm/opportunity` 一行也还是旧依赖。
   - 边界卡写赢单“按客户的设置”，design.md 用部署配置键 `OPPORTUNITY_AUTO_WIN`，“客户的设置”与“部署设置”措辞不同。
6. **决定 A71 与设计的措辞差异。** A71 写“商机按客户设置手动或自动标记赢单”。边界卡的不变量写“赢单后不再修改金额（修改需新商机或明确重开）”，design.md 用 `reopen`，两者一致，但设计加了“名称与预计成交日可以改”，边界卡没有。
7. **币种不同时赢单金额的含义不清。** 订单 USD、商机 CNY 时，赢单金额取预计金额，但 `won.v1` 事件带“赢单金额与币种”，币种是哪个没写。漏斗又“按法人、币种”分组（“按币种折算的漏斗”不在首批）。
8. **报价被接受与订单确认的区别。** 设置 `quotation_accepted` 时，报价变成 `accepted` 就赢单，金额是报价的不含税合计；此时订单还只是草稿，后来订单被取消，商机已经赢单，也没有自动输单或回退（OP08：“没有自动输单”）。文档没有说这种情形怎么处理。
9. **字段级授权没有写。** 资源 `crm.opportunity` 只写了两个维度，没写字段（金额、概率、赢单金额的读写范围），漏斗聚合依赖安全 07 的受限字段证明。
10. **负责人维度的初值。** design.md 写“缺省创建人”，创建人是主体，OP01 写负责人是“主体”。但 `crm/customer` 不存在时，新建商机时指定别人当负责人是否需要 `assign` 权限，文档没写；普通销售新建商机并直接指定别人，会绕过 OP04 对 `assign` 的限制。
11. **阶段重开后的概率。** 手工概率在 `revert`、`reopen` 后是否保留，OP03 与 OP07 都只写回到缺省值。
12. **请求报价没有终结命令。** 请求长期停在 `requested`（销售没装、或销售既没生成也没拒绝），没有超时、取消或撤回，设计也没有对账。
13. **文档编号指向了不存在的东西。** design.md 引用“销售 P2b”和“C5 的教训”，erp/sales 的文档里没有 P2b；装配项目阶段计划 C6 的 P0（`dev/rebuild/c6-data/` 目前是未跟踪的新目录）我按你的要求没有读。
14. **BRICKKIT.md 缺失。** 商机组件只有 README.md 和 design.md，没有 BRICKKIT.md，所以配置键 `OPPORTUNITY_AUTO_WIN` 的定义、订阅清单、部署前准备都只在 design.md 里；任务说要读的 `components/crm/opportunity` 的契约事件 schema 也不存在（目录下没有 `contract/`），商机自己发布的事件（`changed`、`stage_changed`、`quote_requested`、`won`、`lost`）都没有 schema 可对照。
15. **协议 07 的取证方式。** 协议 07 写伙伴不是水位来源，一律用同步资格查询，商机的设计与此一致；但 `mdm/partner` 的事件里只有角色的完整状态事件，没有客户被暂停的专门事实，商机不订阅伙伴，所以“客户已不合格”商机只能在下次编辑（OP02 的“客户（重新取资格）”）时发现。文档没写这个后果。

以上均只读，没有改任何文件。
