下面按题作答。每题末尾标出依据，简称见文末。我没有读任何 `.go` 文件，也没有改任何文件。

先说一个贯穿全篇的前提：`crm/opportunity` 目前只有设计，没有 BRICKKIT.md，也没有契约目录。`erp/sales` 的现状与设计里“销售消费请求报价、带商机参考”对不上，所以多数题的答案是“按商机设计应当如此”。销售那一半的行为，文档没写。

## 逐题回答

**1. 两个不同的幂等键各请求一次报价，第一次的事件被投递两次**

- **生成几张草稿**：按设计是两张。
  - 不同的幂等键会生成两个请求身份，写两行 `quote_request`，发两个事实 `quote_requested.v1`，事实身份各不相同。
  - 同一个事实投递两次，销售按事实身份去重，只生成一张草稿。
  - 所以第一个请求一张、第二个请求一张，合计两张。
  - 依据：opportunity 的 OP05（“同一键重放答同一个请求”“一个商机可以有多个请求”）、验证故事 1。
- **商机上能看到什么**：
  - 读取商机能看到两条请求（`quote_request`），状态是 `requested`。
  - 销售的报价事件到达后，请求变 `drafted`，同时在 `sales_link` 里多两条报价记录（单号、状态、不含税合计、最后看到的版本）。
  - 阶段仍是 negotiation，不变。
  - 依据：opportunity 的“拥有的数据”、OP08、“命令与查询”（读取带请求报价与关联的销售单据）。
- **销售那边文档没写**：erp/sales 的 design.md 与 BRICKKIT.md 都没写它订阅 `crm.opportunity` 流、消费请求报价、按事实身份去重。依据是 sales 的 design.md“依赖”“事件”和 BRICKKIT.md“契约索引”：订阅只列了 `mdm.org_unit.>`。

**2. 装配里没有 erp/sales**

- **怎样赢单**：只能手动。用 `crm.opportunity.close` 赢单，可以给赢单金额，不给就用预计金额，概率变 100。依据：OP06、验证故事 2、“依赖”表的 `erp/sales` 一行。
- **请求报价会怎样**：
  - 只要商机在进行中，请求照样被接受。
  - 事实照样发布，没有人消费，请求永远停在 `requested`。
  - 不报错。销售的流不存在，订阅“只等待”。
  - 依据：“依赖”表、“事件”一节末尾。
- **文档没写**：界面或接口怎样提示“没人处理”，以及请求怎样撤销或超时。

**3. 部署设置为 `order_confirmed`**

- **赢单时刻**：
  - 订单的确认过程结束、订单变成 `confirmed` 之后，商机消费到 `erp.sales_order.changed.v1`（带商机参考），那一刻商机从进行中变 `won`。
  - 订单只是 `draft` 或 `confirming` 时不赢；确认被拒、订单回到 `draft` 时也不赢。
  - 报价被接受转成订单草稿，在这个设置下也不触发赢单。
  - 依据：OP08、术语“自动赢单”、sales 的 SO04（只有确认过程结束订单才是 `confirmed`）。
- **金额**：赢单金额等于订单的不含税合计（事件里的 `totals.net`）。依据：OP08、验证故事 3。
- **操作者**：系统，触发记订单身份。阶段历史多一行，发 `stage_changed` 与 `won`。依据：OP08、`stage_change` 表的“触发”列。
- **订单是 USD、商机是 CNY**：赢单金额改用预计金额，并在阶段历史的原因里写明。依据：OP08、未决问题“自动赢单的金额”。

**4. 商机已赢单，要把金额改大**

- 直接改会被拒，错误是 `WON_AMOUNT_LOCKED`（金额、币种、客户、明细都锁）。只有名称与预计成交日能改。依据：OP02、状态表。
- 正确做法分四步：
  1. 用 `reopen` 重开，要写明原因，权限是 `crm.opportunity.close`。
  2. 重开后用 `edit` 改金额，权限是 `crm.opportunity.edit`，要带版本。
  3. 需要时再 `win`，可以给新的赢单金额。
  4. 重开会清掉赢单金额与关闭的原因，所以第 3 步是必须的。
- **重开后的阶段与概率**：回到关闭前的阶段，概率回到那个阶段的缺省（10、25、50、75）。例如赢单前在 negotiation，现在就是 negotiation、75。依据：OP07、OP02、OP06。
- **文档没写**：赢单金额与预计金额是两个字段，“把金额改大”具体改哪个没说清。重开后再赢单是否再发一次 `won` 事实，也没说，设计只写了“已赢单再赢单不再发事实”。

**5. 商机在 proposal**

- **(a) 改到 qualification**：这是回退 `revert`。
  - 必须写明原因，权限是 `crm.opportunity.edit`。
  - 概率变 qualification 的缺省 10，命令里给了概率就用给的。
  - 写一行阶段历史，发 `stage_changed`。
- **(b) 改到 proposal**：目标等于当前，被拒，错误是 `STAGE_ORDER`。
- **(c) qualification 直接改到 negotiation**：这是推进 `advance`，允许跨步，不需要原因，权限是 `crm.opportunity.edit`。概率变 75，阶段历史一行。
- 依据：状态表的“推进”“回退”行、OP03。
- **文档没写**：
  - `advance` 能不能把目标设成 `won` 或 `lost`。
  - 推进与回退要不要带版本。设计只在 OP02 写了版本，只有新建与请求报价明确要幂等键。

**6. 商机已输单，之后客户接受报价并确认了订单（`order_confirmed`）**

- 商机只记下：`sales_link` 更新为订单已确认，阶段、概率、状态都不变，也不自动重开。
- 要不要重开由人决定。依据：OP08 末尾、未决问题“输单之后客户又下了单”。
- **文档没写**：
  - 谁来通知销售，因为完整状态事件不带关联单据。
  - 重开后订单事件不会重新到达，所以不会触发自动赢单，只能手动赢单。
  - 商机输单时，已发出的请求与销售那边的报价都不受影响，也没有任何东西通知销售商机已输。

**7. 张三与李四**

- **张三看得到谁的商机**：
  - 资源 `crm.opportunity` 有两个维度，法人（值集合）和负责人（主体）。按“销售只看自己的商机”，他只看到自己负责、且在被授权法人内的商机。
  - 看不见的答 404。
  - 依据：design“命令与查询”与 OP04、AGENTS.md 的权限一行、安全 07 的维度表。
  - 张三与李四各自的具体授予，设计没写。
- **张三能不能把自己的商机交给王五**：不能。改负责人要 `crm.opportunity.assign`，这个操作给销售主管、不给普通销售。依据：OP04。被拒时的错误形式，设计没写。
- **李四**：他有 assign 权限，任何状态的商机都能交接，包括已关闭的。交出去之后，张三就看不到那个商机了。
- **漏斗里张三看到的数字**：
  - 只算他看得见的商机。
  - 按法人、币种、阶段分组，给个数、金额合计、加权金额，加权金额等于预计金额 × 概率 / 100，查询时算、不存。
  - 可以按负责人、预计成交日范围筛选。
  - 依据：design“命令与查询”、术语“加权金额”、安全 07“排序、筛选、分组与聚合用到受限字段”。
- **文档没写**：
  - 赢单与输单阶段的金额用哪个（预计金额还是赢单金额）。
  - 金额字段是否是受限字段。如果是，安全 07 规定聚合要求每个可见段都能读该字段，否则这类聚合会被拒。
  - 加权金额的舍入方式。

**8. 新建商机时的引用检查**

- **客户在该法人下没开客户角色**：伙伴的资格查询答 `role_not_opened`，商机答 `CUSTOMER_NOT_ELIGIBLE`，细节带 `role_not_opened`，什么都不建。依据：OP01、partner design.md 的“资格”一节。
- **法人或币种不存在（或不活跃）**：答 `REFERENCE_INVALID`。依据：OP01、design 的拒绝原因表。
- **`mdm/currency` 不可达**：答 `DEPENDENCY_UNAVAILABLE`，什么也没改，可以重试。不当作“币种不存在”。依据：design 的拒绝原因表、协议 07 的“不可达”一行（第 95 行）、partner 的 AGENTS.md 易错点。
- **取证顺序**：多个引用同时有问题时先报哪个，文档没写。

**9. 客户已不合格，以及草稿没有税率**

- **销售怎样处理**：按商机设计，销售拒绝请求，发“拒绝请求报价”的事实，商机把那个请求标为 `rejected` 并记原因（OP08）。
  - 销售怎样决定拒绝、销售人员怎样补救，归销售的 P2b，文档没写。
  - 那个事实叫什么名字，也要等销售的 P2b 定。
  - sales 的 design.md 没写报价创建时是否检查客户资格，只写了订单确认前取证。
  - 依据：opportunity 的“边界”“订阅”、OP05、sales 的 design.md。
- **草稿没有税率**：商机不知道税率，销售生成的草稿可以不完整，由销售人员补齐税率与价格后再发出。依据：opportunity 的未决问题最后一行。
- **与 sales 契约的冲突**：sales 的报价事件 schema 里 `tax_rate` 与 `unit_price` 都是必填。“草稿可以不完整”怎样表达，对不上（见下节）。

**10. 为什么互相不声明依赖，怎样找到对方的事件**

- **为什么不声明**：声明会把精确版本互相钉住，任何一边发布都要另一边再发布（C5 的教训）。所以两边都只订阅。
- **销售那边**：erp-trade 边界卡与 sales design.md 都写“只经事件”，sales 的依赖表也确实没有商机。
- **怎样找到对方的事件**：
  - 靠流名与事件类型约定。商机订阅销售的流 `erp.sales`（`erp.quotation.changed.v1`、`erp.sales_order.changed.v1`，外加拒绝请求的事实）。
  - 销售应订阅商机的流 `crm.opportunity` 里的 `quote_requested.v1`。
  - 对方没装时，流不存在，订阅不报错、只等待。
- 依据：opportunity design 的“规则要点”第一条、“事件”末段；crm.md 与 erp-trade.md 的“可选依赖与缺件”。
- **文档没写**：销售订阅 `crm.opportunity` 这一点，sales 一侧完全没写。也没写没有声明依赖时，对方的事件 schema 怎样获得与核对。

**11. 预测改成“按历史赢率”**

- 改的是 `forecast` 模块。这是 Fork 时的替换点，换掉它即可，漏斗查询的形状不变（法人、币种、阶段的个数、金额合计、加权金额）。
- 没有配置开关。依据：design“规则要点”的“预测”、“部署与替换”、crm.md 的“替换与 Fork”。
- **文档没写**：`forecast` 模块的接口，以及“历史赢率”用全部数据还是只用看得见的数据。

**12. 整套恢复后，请求停在 `requested`，销售那边已有草稿**

- 设计的说法：销售按事实身份去重，重新投递不会生成第二张草稿；销售的事件按版本覆盖 `sales_link`，重放安全。依据：“整套恢复之后”一节。
- 一致性靠的是：销售的报价事件重新到达，商机把请求标成 `drafted`。依据：OP08。
- 恢复核对（`CheckService`，操作 `crm.opportunity.system.recover`）只核对存在性与版本。
- **文档没写**：
  - 谁来重发请求报价事实，是靠 sales 设计里的流补发（`ResendService`）还是别的机制。商机的设计没提到补发、投影对齐与纪元。
  - 商机库回滚到请求之前时，销售那边带这个请求的草稿怎么办。

## 文档的空白与矛盾

**与 erp/sales 现状对不上**

1. sales 的 design.md 与 BRICKKIT.md 都没写订阅商机的请求报价、销售拒绝请求的事实，也没写生成草稿、按事实身份去重的行为。sales 的 design.md“实现状态”还把“合同与商机的参考”列为答“能力不支持”的项。商机验证故事 1 与 3 的上游行为，目前没有文档支撑。
2. `erp.quotation.changed.v1` 的 `opportunity_ref` 描述是“crm/opportunity later”，sales 的 design.md 写“本版为空”。而商机的 OP08 要靠它挑出带商机参考的报价。
3. `erp.sales_order.changed.v1` 的 schema 里根本没有商机参考字段，只有 `quotation_id`。商机设计要求“订单事件带商机参考”，也没说可以经报价关联推出订单所属商机。
4. 报价事件里没有“请求身份”字段，OP08 的“报价带请求身份的，把那个请求标为 `drafted`”无从实现。
5. 报价事件 schema 里 `tax_rate`、`unit_price` 是必填，`tax_source` 只有 `manual`。商机的“草稿可以不完整”与它对不上。
6. 请求事件不带部门，而 sales 的报价有部门维度，草稿的部门从哪来，没写。
7. “销售拒绝请求的事实”没有名字、没有 schema，商机的订阅清单因此不完整。

**与边界卡、决定的不一致或含混**

8. crm.md 边界卡与组件索引里，`crm/opportunity` 的必需依赖只有 `mdm/partner`、身份、授权，设计加了 `mdm/org` 与 `mdm/currency`。设计自己标了“待复核”，随 P1 改。
9. 边界卡的不变量写“阶段只按声明的顺序推进”，OP03 允许推进跨步，按字面读有出入。
10. 边界卡写“赢单后不再修改金额（修改需新商机或明确重开）”，设计还允许赢单后改名称与预计成交日，这是增补。
11. A71 与边界卡写“按客户的设置”，设计把它定成部署设置 `OPPORTUNITY_AUTO_WIN`，“客户”在这里指部署方，措辞容易混淆。
12. 数据范围上，sales 的报价与订单带部门维度（经理看本部门及下级），商机首批不做部门维度，销售主管的可见范围没说明。

**设计自身的空白**

13. 重开时概率回到阶段缺省，用户之前自定义的概率会丢。
14. 重开后再赢单是否再发 `won` 事实，没说。
15. 商机输单或赢单时，已发出的请求与销售那边的草稿怎么办，没写。
16. 请求长期停在 `requested`（销售没装、没处理）的出口，没写。
17. 自动赢单取订单的不含税合计，订单草稿阶段可能被改价，与报价金额不同，没说明用哪个时点的值。
18. 漏斗里赢单与输单阶段的金额口径、金额字段的受限性、加权金额的舍入，都没写。
19. 推进能否以 `won`、`lost` 为目标，没写。
20. “系统”作为赢单操作者，它的身份与授权方式没写。
21. 角色与授予（普通销售、销售主管各有哪些操作和范围）没有文档。
