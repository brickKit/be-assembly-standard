# AI 路由题库（2026-10，15 题）

> 开发文件。考法与评分见 [README.md](README.md)。**考生绝不能看到本文件**：考场副本排除 `dev/`。请求原文按请求者的说法写，不照抄文档标题；中英混排。

## 只改一个组件或已有设计（4 题）

### Q01（中）
- **请求**：“我们有个客户仓库很大，想按批次先到期先出来拣货，这个规则该写在哪？要不要给库存组件加个开关？”
- **必经**：`AGENTS.md` 查找路由“新需求、新功能、放在哪里” → `docs/zh/07-components/`（`erp-trade.md` 的 `erp/warehouse`）；`docs/zh/01-conventions/08-reference-implementations.md` 的“几种做法都合理时”或 D27。
- **结论**：落在 `erp/warehouse`（复杂仓储，远期组件），拣货策略是它的替换点；简单出入库不需要它；不在 `erp/inventory` 里加开关。
- **必含**：拣货策略属于仓储作业而不是库存核心；不用配置开关塞客户变体；`erp/warehouse` 是远期，需要先建（注册表登记、建仓库）。
- **陷阱**：在 `erp/inventory` 里加 `if pickingStrategy == ...`。

### Q02（英）
- **请求**: "Sales reps should only see their own orders, and sales managers should see everything in their department. How do we build that?"
- **必经**：`AGENTS.md` 查找路由“某个表只让一部分人看到一部分行” → 安全 07（有限表达）、授权选型；资源定义（安全 09a）。
- **结论**：不写新代码逻辑：`erp/sales` 的资源定义声明负责人与组织维度，具体谁看什么是授权组件中的授予（管理员配置）；查询由 SDK 按授予段编译。
- **必含**：规则随版本（资源定义），授予是运行时数据；不用行级安全；没有部门的人不贡献部门条件；“别人的数据看不见”要有测试。
- **陷阱**：在 `erp/sales` 里自建一张“谁能看哪些订单”的表；用 RLS。

### Q03（中）
- **请求**：“客户付款到账以后，能不能自动把对应的发票核销掉？”
- **必经**：`AGENTS.md` → 边界卡（`erp-finance.md` 的 `erp/payment` 与 `erp/finance`）→ 协议 05 的“核销：财务本地事务内的分配”。
- **结论**：核销是 `erp/finance` 的本地事务；`erp/payment` 只发布收付款事实。自动匹配的规则落在财务。
- **必含**：核销在财务、不在收付款组件；只用未清项的可用余额；收款差额的容差按法人声明（起始 0，不自动核销差额）。
- **陷阱**：让 `erp/payment` 直接改发票状态。

### Q04（中）
- **请求**：“确认订单的时候，要同时把库存和客户信用额度锁住，能不能用一个分布式事务包起来？”
- **必经**：`AGENTS.md` 查找路由“发布或消费事件；跨组件写入；预占” → 事务与消息、协议 04。
- **结论**：直接作答：不用分布式事务；销售作为协调者按协议 04 的预占分支分别向库存与信用预占，可查询、可取消，中间状态明确。
- **必含**：事务里不发网络调用；业务属主持久协调；结果未知时查询，不盲目补偿；外壳不提供共同事务。
- **陷阱**：两阶段提交、把三个组件合进一个事务或一个外壳。

## 需要新组件（2 题）

### Q05（英）
- **请求**: "A customer wants to collect card payments through Stripe. Where does that go?"
- **必经**：`AGENTS.md` → 组件全景（`03-catalog.md` 的支付通道）→ 协议 10。
- **结论**：新组件 `integration/payment-stripe`（远期，货架上已有身份），作为 `erp/payment` 的通道适配；按协议 10 处理回调与结果未知。
- **必含**：适配组件不自行放行业务；回调先验证再查询；结果未知不重发付款；需要先在注册表登记并建仓库。
- **陷阱**：把 Stripe 代码写进 `erp/payment` 或 `erp/finance`。

### Q06（中）
- **请求**：“老板想给每个部门定年度采购预算，超了就不让下单，这个放哪个组件？”
- **必经**：`AGENTS.md` → 组件全景或边界卡（`erp/budget`）→ 决定记录 A68 或财务与结算选型。
- **结论**：`erp/budget`（远期新组件）：预算版本与预算占用，占用沿用协议 04 的分支，请购与采购订单作为协调者。
- **必含**：不放进财务或采购内部；占用是可查询的分支；需要先建组件。
- **陷阱**：在采购组件里加一张预算表。

## 与已有决定冲突（3 题）

### Q07（中）
- **请求**：“权限判断有点慢，加个 Redis 缓存一下吧？”
- **必经**：`AGENTS.md` 查找路由“加缓存；Redis” → 底层选择 README 的缓存一行、原有决定 0201、安全 03。
- **结论**：冲突，停下交给人：项目不运行缓存服务器（0201）；授权视图本来就在本地，按有效期核验（D57）。
- **必含**：引用 0201 与 D57；重新讨论的条件（实测负载、跨多个组件）。
- **陷阱**：直接加 Redis。

### Q08（英）
- **请求**: "Let's just turn on PostgreSQL row-level security for the data scopes, it's simpler."
- **必经**：`AGENTS.md` → 决定记录（原有决定 0206）→ 安全 07。
- **结论**：冲突，停下：不用行级安全（0206）。
- **必含**：理由（属主默认绕过、池化连接与外壳、不可解释）；查询按授予段编译成参数化 SQL。
- **陷阱**：照做。

### Q09（中）
- **请求**：“管理员想加一条规则：销售部的人都能导出客户名单，除了张三。”
- **必经**：`AGENTS.md` → 决定记录（原有决定 0204）→ 安全 01。
- **结论**：冲突，停下：管理员不能加负权限（0204）；做法是给张三一个不含导出的授予组合，或把导出权限拆成单独的授予。
- **必含**：引用 0204；业务强约束与安全处置不是管理员可配置的 Deny。
- **陷阱**：设计一个 Deny 规则。

## 部署、运维与数据（3 题）

### Q10（中）
- **请求**：“有人误删了一大批订单数据，怎么恢复？”
- **必经**：`AGENTS.md` 查找路由“上线、备份与恢复” → 运维手册 01（什么时候用整套恢复、整套恢复的步骤）→ 协议 15。
- **结论**：直接作答：误删大量数据用整套恢复（选 T、冻结、恢复数据库、推进代次、补回收紧、外部对账、损失范围、重新开放）；只坏一个组件不是标准能力。
- **必含**：审计库不随恢复回退；外部对账；损失清单与“禁止重新录入”。
- **陷阱**：只恢复订单组件的库。

### Q11（英）
- **请求**: "Memory is tight. Can we merge erp/sales and erp/inventory into one process?"
- **必经**：`AGENTS.md` 查找路由“几个组件放进一个进程；外壳” → 部署与运行、协议 17 的外壳义务。
- **结论**：直接作答：可以放进同一个外壳（部署层合并），但它们仍是两个组件，照样经契约调用；外壳不是共同事务，也不是安全隔离。
- **必含**：同一语言与 SDK 版本；成员预算；成员不读进程环境；单跑与外壳行为一致，拆回要验证（D40）。
- **陷阱**：在外壳里让销售直接调用库存的函数。

### Q12（中）
- **请求**：“为了方便测试，能不能在数据库迁移里直接建一个管理员测试账号？种子脚本要登录怎么办？”
- **必经**：`AGENTS.md` 查找路由“演示数据；测试账号” → 种子与测试数据的“凭据与部署”、原有决定 0303。
- **结论**：冲突：测试账号绝不进迁移；种子经开发与测试环境专用的客户端与换取入口取得令牌，正式部署的上线检查确认没有它们。
- **必含**：迁移里的测试账号就是公开密码的后门；首个管理员靠安装认领；种子经真实接口建数据。
- **陷阱**：在迁移里建账号，或开启正式登录客户端的密码授权。

## 编码与排障（3 题）

### Q13（英）
- **请求**: "My component reads PG_SCHEMA with os.Getenv. Works fine standalone, but in the shell it sometimes writes into another component's schema. Why?"
- **必经**：`AGENTS.md` 易错点第二行 → 组件实现约定的合并安全。
- **结论**：直接作答：外壳中一个进程只有一份环境，成员互相覆盖；配置只经 SDK 的运行时读取。
- **必含**：不读进程环境；一切数据库访问经 SDK 的事务入口；`SET LOCAL`。
- **陷阱**：建议给每个成员加环境变量前缀。

### Q14（中）
- **请求**：“客户列表要加一个关键字搜索，顺便能搜客户的信用额度吗？”
- **必经**：`AGENTS.md` → 协议 14 的列表（列表内搜索）、安全 07 或 01 的字段限制。
- **结论**：直接作答：列表内搜索由 SDK 在同一条 SQL 里与授权条件、游标一起执行；受限字段按字段类别分列，无权读的用户搜不了它（`FIELD_NOT_QUERYABLE`）；信用额度本身属于 `erp/credit`，客户列表补全它要按用户的读取许可裁剪。
- **必含**：搜索不能泄露受限字段；拼音与首字母；限制处理的行搜不到。
- **陷阱**：把信用额度直接拼进一个搜索列，或跨 schema 连接查询。

### Q15（中）
- **请求**：“重建以后我们发第一个版本，版本号写多少？Go 组件要打几个标签？”
- **必经**：`AGENTS.md` 项目约定“版本” → 开发流程与发布的版本、工程规范的版本与升级。
- **结论**：直接作答：组件从 3.0.0 起（Go 模块路径 `/v3`），外壳 2.0.0，工具 v1.0.0；主版本 2 及以上的 Go 组件同一提交打 `3.0.0` 与 `v3.0.0` 两个标签，外壳只打裸标签。
- **必含**：每次改动都升版本；已发布的版本不原地修改；旧代码在 `legacy/` 分支。
- **陷阱**：从 1.0.0 开始（与已发布的标签冲突）。
