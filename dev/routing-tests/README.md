# AI 路由测试：考法、评分与过关线

> 开发文件（`dev/`），06d 使用，阶段结束后随 `dev/` 整体归档。正式文档不得链接本目录，本目录的任何内容也不得被抄进正式文档（题目泄漏进文档 = 考试作废）。
> 依据：`dev/phase-06/spec.md` §7。题库在同目录 [questions.md](questions.md)。

## 1. 测什么

一个对本项目零了解的 AI（Opus / Sonnet / Haiku 三档），只拿到项目路径和一句请求者的原话，能不能：

1. **找对路**：从 `AGENTS.md` 出发，经正式文档（`AGENTS.md`、`docs/en/01-conventions/`、`docs/en/02-decisions/`、`docs/en/03-seed-data.md`、`.claude/skills/`、各组件的 `BRICKKIT.md` / `AGENTS.md` / 契约）走到答案所在的文件和章节，不进 `dev/`、`archive/`、brickKit 仓库、依赖方源码；
2. **判对结论**：改动请求按 `brickkit-plan-change` 的四种结论之一（只改一个组件 / 先改上游 / 需要新组件 / 冲突停下交人）；不是改动的请求直接作答，不硬套改动流程；
3. **答对内容**：答案里有该有的要点，没有与决策、约定相反的建议，没有编造的命令、文件、配置键，没有 brickKit 0.x 的旧做法。

正式文档是按"写给较弱的模型"的标准写的（`docs/en/01-conventions/08-documentation.md`），所以三档模型**各自**都要过关，不是取最好成绩。

## 3. 开考前准备

1. **核对题目前提。** 06b/06c 会补接口、改键名、写出 `BRICKKIT.md`，题目里的"现状"可能已经变了。逐题检查「开考前核对」一栏：
   - 期望路径里的文件和章节真实存在（尤其是 `components/<scope>/<name>/BRICKKIT.md` 的 Purpose / Dependencies / Configuration / Contracts / Before you deploy 各节）；
   - `AGENTS.md` 末尾的组件表（brickkit 维护的块）已经由 `brickkit add` 填好每个组件一行——几乎所有改动题的必经第 2 步都是"组件表 → `BRICKKIT.md`"，表是空的就不能开考；
   - 题目假设"还没有"的能力确实还没有（例如 Q01 的调拨、Q04 的待办转交、Q07 的客户账期）；已经被实现的，换一道同类题或把期望答案改成"已有，在哪里"；
   - 配置键名以 06b 之后的实际 `configSchema` 为准（题目里的 `DEFAULT_WAREHOUSE_ID`、`DINGTALK_APP_SECRET` 等按约定推算）；
   - 决策原文变过的，按新原文核对相关题的要点（例如 0007 已收窄为"只拉 bundle / 验 token 不建边"，Q20、Q24 按它写）；
   - G 类（Q29–Q31）的「必含」逐条对照 06b 写成的 `BRICKKIT.md`：文件里没写的点**删掉**，不能留成必含，只读那一份文件的考生无从得知；
   - 部署文档（06e 在 `docs/en/`、`docs/zh/` 里新增的编号部署文件夹）在 06e 之前不存在；若开考时已存在，把它加进 Q23 的期望路径。

   核对引起的题目修改**单独提交**，提交信息写明改了哪题、为什么（前提失效 / 键名变化 / 路径变化）。开考后不再改题。

2. **准备考场副本**（防止考生读到本题库，也避免真实仓库的记忆被注入）：

   ```bash
   SHA=$(git -C /home/zhijie/Desktop/github/be-assembly-standard rev-parse --short HEAD)
   EXAM=<scratchpad>/exam-$SHA
   rsync -a --exclude .git --exclude dev/ --exclude brickkit-feedback/ --exclude node_modules/ \
     /home/zhijie/Desktop/github/be-assembly-standard/ "$EXAM"/
   test ! -e "$EXAM/dev" && echo "dev/ 已排除"
   ```

   `archive/` 保留在副本里：它在真实仓库里就在那儿，考生走进去要扣分，这本身就是被测的行为。
   记下父仓库 commit 和每个 submodule 的 commit（`git submodule status`），写进运行记录的「环境」。

3. **外部使用者视角的考场**：每题一个空目录，只放那一份英文 `BRICKKIT.md`（不放 `.zh.md`，不放别的）：

   ```bash
   mkdir -p <scratchpad>/exam-ext-Q29 && cp "$EXAM/components/erp/sales/BRICKKIT.md" <scratchpad>/exam-ext-Q29/
   ```

## 4. 考法

**每题一个全新的考生，零上下文。** 不复用之前的会话，不续接之前的 agent；提示里不出现题目类别、期望结论、任何文件名或决策编号；三档模型各跑全部 31 题（共 93 次），题与题之间互不共享。

**启动方式**（二选一，运行记录里写明用的是哪种）：

- **首选：在考场副本里启动独立会话。** 这样加载的是副本里的 `CLAUDE.md`（即 `@AGENTS.md`，与真实使用者相同），而新路径没有任何自动记忆：

  ```bash
  cd "$EXAM" && claude -p --model <haiku|sonnet|opus> --output-format stream-json --verbose \
    --allowedTools <只读工具：Read、Grep、Glob，以及只读的 Bash> \
    "<下面的提示模板>" > <运行目录>/Qxx.jsonl
  ```

  工具名和参数以当时 `claude --help` 为准。`stream-json` 里的工具调用就是**客观的阅读记录**，评分以它为准，考生自报的阅读记录只用来对照。
  "没有自动记忆"只对项目级记忆成立：用户级的 `~/.claude/CLAUDE.md`（若存在）仍会加载。开考前看一眼它的内容，在运行记录「环境」里写明它是否存在、有没有与本项目相关的内容；有的话临时移开再考。
- **备选：控制者用子 agent 工具派发**（general-purpose，指定 model）。缺点是可能带上控制者会话所在仓库的上下文；只在首选方式不可用时用，并在记录里说明。

**提示模板（逐字使用，只替换尖括号）**

A–F 类（Q01–Q28）：

```
你是一个刚被叫来在某个软件项目里干活的 AI 助手，之前没有接触过这个项目。
项目仓库在：<EXAM>
项目维护者提出了下面的请求：

「<请求原文，逐字>」

请在这个仓库里查资料，然后回答。要求：
1. 只读：不要修改、新建或删除任何文件；不要启动、构建或停止任何东西（不要运行 brickkit up、build、add、remove、upgrade、release、local，不要运行 make 目标，make help 除外）。可以运行 `brickkit <命令> --help`。
2. 回答分三部分：
   【阅读记录】按实际顺序列出你打开过的每个文件（相对路径；能写出章节标题或行号范围就写）和你运行过的每条命令，不要事后整理或省略。
   【判断】如果这是一个改动请求：该由哪个（些）组件来做、按什么顺序，或者为什么不应该直接去做；如果不是改动请求，写"不涉及改动"。
   【回答】给请求者的具体回答。
```

G 类（Q29–Q31）：

```
你是另一个项目里的 AI 助手。你们打算使用一个别人发布的组件，手上只有这个组件的说明文件：<EXAM_EXT>/BRICKKIT.md
本机上的其它目录与这件事无关，不要去找。
你们项目的维护者问：

「<请求原文，逐字>」

只读，不要修改任何文件。回答分两部分：【阅读记录】（按实际顺序列出你打开过的每个文件和运行过的每条命令）、【回答】。
```

**原文保存**：每次作答的完整输出（`stream-json` 或子 agent 的最终回复）原样存进运行目录，不截断、不润色。

## 5. 评分

每题三个维度，各 0–2 分，满分 6 分。

### 路径（P）

| 分 | 定义 |
|---|---|
| 2 | 到达了该题全部「必经」文件和章节；没有读任何禁止范围；额外文件不超过 3 个 |
| 1 | 没有读禁止范围，且满足下面任一条：漏了恰好 1 个「必经」项、而答案维度仍有 1 分或 2 分；额外文件 4 个或更多 |
| 0 | 读了禁止范围中的任何一项（不管答得多好）；或漏了 2 个或更多「必经」项；或漏了 1 个「必经」项、且答案维度 0 分；或没有阅读记录、阅读记录与 `stream-json` 明显不符 |

- **起点**：A–F 类在首选考法下 `AGENTS.md` 总是随 `CLAUDE.md` 自动加载，所以不单独检查"从哪里开始"；题目把 `AGENTS.md` 的某一行列为必经，指的是考生的行动顺着那一行走了（第一个主动打开的相关文件正是那一行指向的文件，或考生在回答里引用了那一行）。G 类没有自动加载，起点就是给出的 `BRICKKIT.md`。
- **「必经」项**：期望路径里标「必经」的每一条算 1 项；一条里写了"A 或 B""任选其一""至少其三"的，按写法满足即算到达。
- **额外文件**：考生主动打开（Read / `cat` / `sed` / `head` 等读出内容）的、不在本题「必经」「可选」列表里的文件。不算额外：自动加载的 `AGENTS.md` / `CLAUDE.md`；列表中文件的中文版本（`.zh.md` 译本，或 `docs/zh/` 下与 `docs/en/` 同路径的文件）；只列目录（`ls`、Glob）；`brickkit <命令> --help`。读本题负责组件的源码不算禁止，但计入额外文件。
- **搜索与禁止范围**：在全仓（或项目根）做的搜索，输出里列出了 `archive/`、`dev/`、依赖方源码下的路径或行，**不算**违规；打开读取这类文件的内容（Read / `cat` / `sed` / `head` 等），或把搜索限定在禁止目录里（如 `grep -r X archive/`），**算**违规，路径 0 分。
- 中文版本（`AGENTS.zh.md`、`*.zh.md`、`docs/zh/` 下与 `docs/en/` 同路径的文件）与英文主文件等价。
- 经决策索引（`docs/en/02-decisions/README.md`）而不是 Where to look 到达同一份决策，不扣分。
- G 类读了给出文件以外的任何文件 = 0。

### 结论（O）

| 分 | 定义 |
|---|---|
| 2 | 与期望结论一致。改动题：组件和顺序都对（先改上游类要说对上游是谁、顺序是先上游后消费方）。冲突题：**停下来，不给出直接动手的实现方案**，指出冲突的决策（编号或文件名）及其理由，交给人决定。非改动题：直接作答，没有凭空开出改组件代码的计划 |
| 1 | 方向对但不完整：结论类别对但漏了一个组件、顺序颠倒；冲突题停下来了，但没指出是哪条决策（只说"好像不太好"）；非改动题答对了但附带了一个不必要的改代码建议 |
| 0 | 结论类别错（例如把"需要新组件"判成在现有组件里加分支）；**冲突题没有停**——直接给了实现步骤、或"先这样做，以后再说"、或给出变通做法绕开决策 |

**结论按实质判，按后端组件判。** 考生不知道四种结论的名字（提示里没给），阅卷人看的是它说要改哪些组件、按什么顺序、停没停，再映射到四种结论：

- **前端永远是消费方，不是上游。** 结论只看后端组件：恰好一个后端组件要改，再加前端跟进 → Fits one component（+ 前端跟进）；某个后端上游必须先于后端消费方改 → Needs a provider's contract first。前端跟进**永远不会**把一道题变成"先改上游"。
- 所以考生说"先改 X（后端）发版，再改前端"，而期望是 Fits one component（X）时，给 2 分；说出前端跟进不扣分，没说也不扣分。
- 组件的 `assembly.yaml`（菜单、权限键声明）是那个组件的一部分：改它算改那个后端组件。
- 冲突题：**决策本身认可的做法**（例如 0004 的默认实现 + 客户 fork、0013 的改 `owner_id` / 调整部门归属）作为供人选择的方向列出，不算"变通做法绕开决策"；自行动手实现才算。
- 每道题的「相邻答法给分」写死了常见的相邻答法给几分，阅卷以它为准；没列到的答法按上表定义判。

### 答案（A）

| 分 | 定义 |
|---|---|
| 2 | 覆盖该题全部「必含」要点，没有事实错误 |
| 1 | 覆盖至少一半「必含」要点，没有严重错误 |
| 0 | 少于一半；或有任一**严重错误**：与决策或约定相反的建议、编造不存在的命令/文件/配置键/错误码、brickKit 0.x 的旧机制（平台注入 `DATABASE_*`、`resources:` 资源绑定、`servedBy`、`local: true`、`otelEndpoint`/`pgSchema` 这类驼峰键） |

「加分」要点不加分，只在运行记录里记一笔，用来区分答得好与刚好及格。

### 计分

- 单题得分 = P + O + A（0–6）。
- 类别得分率 = 该类得分之和 ÷（题数 × 6）。总分率 = 31 题得分之和 ÷ 186。
- 每个模型单独计分、单独判定。
- 不计分但要记录：回复语言（`AGENTS.md` 要求对维护者用中文）、是否擅自动了文件、用时、token。
- 解读路径分时注意：Q16、Q22、Q26 的请求原文是请求者的自然说法，但与 Where to look 或 skill 的标题用词很近，偏易；这几题拿满分不能单独说明路由好用。

## 6. 过关线

每个模型都要同时满足：

1. **总分率 ≥ 90%**，即 186 分中 ≥ 168 分；
2. **冲突类 100%**：Q16–Q20 每题的结论维度都是 2 分（停下来、指出决策、交给人）。任何一题没停，本轮该模型不过，不管总分多少。

三个模型都过关，06d 才算完成。

## 7. 答错之后：错题映射到文档修改

原则：**改正式文档，不改题**——除非题本身错了。这和"不为通过测试去改测试"是同一条纪律（`docs/en/01-conventions/06-testing.md` 的铁律）。

| 失分处 | 通常说明 | 修哪里 |
|---|---|---|
| P：没从 Where to look 找到入口，或找到了错的行 | 路由行的关键词不是请求者会用的说法 | `AGENTS.md`（及 `AGENTS.zh.md`）Where to look：在对应行补请求者的说法，或加一行；不复述题目原文，写这一类请求的常见说法 |
| P：到了入口文件但没走到下一份必需文件 | 两份需要一起读的文档没有互相指向 | 在前一份文档对应章节加链接（`08-documentation.md` 写作规则 7） |
| P：读进了禁止范围（`archive/`、源码、brickKit 仓库） | 正式文档里缺了它想找的事实，只好去挖 | 把那个事实写进该在的正式文档（组件事实进该组件 `BRICKKIT.md`/`AGENTS.md`，项目规则进 `docs/en/01-conventions/`）；**绝不**加指向 `dev/`、`archive/` 的链接 |
| O：冲突题没停 | 决策的「What this rules out」没覆盖这种说法，或 `AGENTS.md` 没把这类请求路由到决策 | 在该决策的 rules out 里补这种请求的说法；必要时在 Where to look 加路由 |
| O：把新组件判成在现有组件里加分支，或槽位族 / 客户 fork 判反 | `BRICKKIT.md` 的 Purpose 没写清"不归我、归谁"，或 0004 / slot-family 一节的判据不够直白 | 该组件 `BRICKKIT.md` Purpose 的 does-not-own；`10-reference-implementations.md#slot-family-signal` 的表 |
| O：先改上游类漏了上游或顺序反了 | 消费方的 `BRICKKIT.md` 没写它依赖上游的哪个契约/事件 | 消费方 `BRICKKIT.md` Dependencies / Contracts |
| A：漏了要点或说错事实 | 叶子文档缺这个事实，或写得有歧义 | 对应叶子文档（约定文件、决策、组件文档、skill 以外的项目文件） |
| A：说出了 brickKit 0.x 的旧做法 | 有正式文档还残留旧说法，或缺新说法让模型凭记忆补 | 找出残留处修掉；缺的补上 |
| 问题在 brickKit 的 skill 本身（`.claude/skills/brickkit-*` 措辞误导） | 不是本项目文档能修的 | 不改 skill 文件（会被 `brickkit skills update` 覆盖）；复现后作为反馈候选，按 spec §2 进 `brickkit-feedback/` |

**题本身错了**（期望答案与正式文档、决策不符；前提已失效；措辞有歧义，两种结论都说得通）：先停下，用一句话写清错在哪，单独一个提交修题，不和文档修改混在一起。不能因为三个模型都答成某样就认定题错——先看正式文档是不是本来就写成那样。

**重考**：

1. 文档修完后，错题用**同一档模型**重考（新考场副本、新会话）；
2. 再从已答对的题里随机抽 **5 题**回归（每类至少 1 题，其中至少 1 道冲突题；抽取方法和抽到的题号写进记录）；
3. 回归中有原来对、现在错的题，说明修文档改坏了别处，回到上表继续修；
4. 直到该模型按第 6 节过关。
