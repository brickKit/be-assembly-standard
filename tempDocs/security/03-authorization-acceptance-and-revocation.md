# 授权接受、撤销与时间保证

> 状态：2026-10-13 第三份安全候选规格，尚未冻结；同日按 [D57](../work/02-decisions.md#d57-高风险操作默认用有界本地授权客户可选持久接受) 整份改写：默认路径为有界本地授权，持久接受与提交屏障改为可选的严格路径。承接[完整授予求值](01-authorization-evaluation.md)、[可信身份及属性](02-trusted-identity-and-attributes.md)与[状态与变更协议](08-state-and-change-protocol.md)；不修改正式契约、SDK 或部署。

## 目标与保证边界

默认小公司、按客户情形选择配置和专项能力的前提保持。本页把“权限当前有效”落实为明确的期限、检查时点与失败行为：撤权之后多久内一定不再放行；授权服务不可用时业务怎样继续、何时停止；对撤权严格性要求更高的客户，可以启用更强的保证。

本页给出协议行为和起始实验参数，不将高性能、零延迟或跨系统原子提交当作已实现能力。所有 provider 都遵守第一份完整授予语义；时间能力不足时阻止对应功能启用，不因实现只会返回布尔值而降低保证。

撤销权限、停用账号、任职失效、撤销服务身份、冻结业务、修改内容和撤销已接受业务是不同操作。普通撤权阻止其作用域内的新放行；取消已提交的业务须走业务控制，不能凭删除用户权限回滚已发生的库存或会计事实。安全记录本身“何时变了”由第八份的生效点定义；本页定义“变了之后各组件何时不再放行”。

## 两条路径

| 路径 | 保证 | 对授权服务的依赖 | 适用 |
| --- | --- | --- | --- |
| 默认：有界本地授权 | 撤权在 authz 提交于 t0 之后，任何依赖旧权限的放行不晚于 t0 + W，业务提交不晚于 t0 + W + `C_commit`（W 按操作类别取值，高风险操作很短） | authz 不进入请求路径；短暂不可用时，有效期内照常处理，超期即拒绝或暂缓 | 标准版的全部操作，含付款、审批、授权管理、敏感导出 |
| 严格：持久接受（A 档） | 撤权在先就一定不能新接受；接受在先可在激活期限内完成限定提交 | authz 进入关键动作的同步路径，不可用时这些动作暂停 | 客户或业务要求“撤权后绝不再接受新的关键动作” |
| 严格：提交屏障（B 档） | 撤销完成之后，声明范围内旧许可不能再产生业务提交 | 另需各业务属主的本地提交守卫、参与者登记与撤销恢复，故障时撤销可能长期待完成 | 在 A 档之上，要求“撤销完成后未提交的旧动作全部禁止” |
| 不可作为任何路径：单次远程 Check 或无期限缓存后直接提交 | 只说明检查所用快照上的资格 | — | 检查与提交之间的间隙没有上界 |

表中的“授权管理”指业务组件中发起授权管理的入口；授权管理本身的生效由 Authz 在自己的权威状态上、在同一守卫事务内判定（[第四份](04-authorization-administration-and-appointments.md)、[第八份](08-state-and-change-protocol.md#生效点)），不使用本地视图，因此不适用 W。默认路径只针对业务组件的放行与提交。

默认路径与严格路径共用第一份的求值语义、第八份的生效点和本页的期限规则；严格路径是在默认路径之上加的能力，不是另一套权限模型。启用哪条路径按“部署 × 操作”声明在 profile 中：客户可以只对付款启用 A 档，其他操作仍走默认路径。组件声明自己的最低要求，部署只能选择满足它的路径；未知动作不默认归低风险。

默认路径的撤权窗口必须在产品说明中写明，不能称为即时撤销。读准入的检查同样只保证其准入节点；已在途输出的停止边界另见下文。B 档针对声明的业务提交范围，不自动成为“所有网络字节或外部副作用即时停止”的保证。

## 收紧变更与依赖域

由所选 Authz 成员承担安全视图的发行、收紧裁决，以及严格路径中的接受裁决，内部算法／关系 provider 可以替换；不为每个业务组件另建接受权威，不新增名为协调器的必装业务组件。账号、任职、组织和资源仍有自己的事实属主，接受权威保存的是经证明的安全视图与裁决记录。

在一个部署内，基础实现可先用保守的统一安全裁决域。生效点（[第八份](08-state-and-change-protocol.md#生效点)）、严格路径的接受事务和撤销／安全收紧事务访问同一持久守卫：接受持共享冲突锁至提交，收紧持排他冲突锁，资格视图更新和失效代次一起提交。不能用无锁 SELECT 读版本后另外 INSERT 接受记录；也不能在事务建立旧快照后获取锁，却继续按旧事实判断。锁、隔离和重试须证明实际等价行为，不能仅写“使用事务”。

多个接受可并行持共享守卫，各自按唯一动作键写记录；不要求每次接受都更新全部署热计数器。以后按主体、任职、资源关系、策略等依赖域细分锁与失效代次时，须完整声明依赖集合，固定加锁顺序，保证新规则／新增关系也命中相应守卫，防止漏掉负面查询和幻读。没有证明前继续用保守域，不能只锁一份碰巧匹配的授予就称全局安全。

收紧有两种来路，分别处理。**安全处置**（管理员在授权管理中发起的紧急停用、冻结、撤销访问关系）先由合格管理路径在裁决权威关闭相应新接受，再由事实属主完成业务变更及受控视图更新；**来源事实**（员工组件提交的离职与任职结束、IAM 的账号停用、组织调整）由各自属主照常提交，按下文“内部来源的收紧与来源水位”取得上界，不要求属主先同步调用 Authz（D62 的同一原则：事实不由授权系统拒绝）。安全处置中途崩溃保持关闭，恢复后核对状态再完成，不能超时自动重新开放。管理编排承担跨组件流程，主数据属主不因此调用所有消费者。放宽／新增资格反向处理：先取得完整已提交事实，再开放经过确认的授予，不能先开后补。

相关安全属性的所有管理、批量、导入和恢复写入口均执行该协议；属主校验所需收紧／变更依据，不能允许客户端绕过编排直接改停用或任职字段。事实提交后回执／投影丢失时仍保持保护，完整回读与对账后再完成；正向资格也不在等待完整事实期间提前开放。

### 内部来源的收紧与来源水位

员工组件、IAM 适配组件与组织组件是 Authz 的**内部来源**。它们的收紧（离职、任职结束、账号停用、组织撤销）经各自的发件表进入事件流，Authz 应用它们。为给这段传播一个上界，Authz 对每个内部来源维护**水位**（与[协议 02 的来源水位](../protocols/02-projections.md#来源水位)同一机制）：

1. **探测**：Authz 向来源发出带随机数的探测，记下发出时刻 `m_p`。`m_p` 与之后的新鲜度判断都取 **Authz 主库的事务时间**，所以多个 Authz 副本、进程重启都使用同一个时钟；主库切换时，全部水位作废，等待新的回声。
2. **回声**：来源收到探测后，把带同一随机数的回声事件写进与变更相同的发件表；来源的流若按键分区，回声写入每个分区。
3. **保序发布**：来源的发件转发按提交顺序发布，遇到尚未提交的较小序号时等待，不跳过。
4. **按连续位置推进**：Authz 记录每个分区“连续已应用的流位置”（处理失败、等待重投的事件之后的位置都不算连续）；某来源的水位 = 各分区连续已应用位置之内最后一条回声的 `m_p` 的最小值。只要有一个事件在等待重投，水位就停在它之前。
5. **补取路径**（D64）：流停滞或中断时，Authz 直接按序号向来源的查询接口拉取该序号之后的变更与回声（不经消息系统），应用后同样推进水位。
6. **续发与关闭**：回答核验时，在同一个读快照中先读水位、再读安全状态。视图依赖某来源时，高风险操作只在其水位不早于 `当前时刻 − D_src_high` 时续发，普通读取用 `D_src_read`；超过的，相应风险档的分片关闭，与 authz 不可用时同样拒绝或暂缓。

**IAM 成员由外部产品承载时**（Casdoor、Keycloak 及其目录联邦）：账号可以直接在产品中停用，不经适配组件的发件表。适配组件收到探测后，先向产品拉取截至此刻的变更（产品的变更序号、管理事件或全量状态比较），写入发件表，再写回声，使产品侧的变更也落在回声之前。产品无法提供这类拉取时，账号状态按外部来源对待，上界按下一段的 `D_source` 声明，不按 `D_src` 对外承诺。

这样不需要来源与 Authz 的墙钟同步。**预定的结束时间**（已登记的离职日期、任职有效期终点）随视图下发为段的有效期终点，组件到点在本地失效，不等事件。

保证：来源在时刻 s0 提交收紧，依赖旧资格的判定不晚于 s0 + `D_src` + W（`D_src` 取该操作风险档的值），提交另加 `C_commit`。产品说明写明两档的上界：高风险操作分钟内，普通读取以 `D_src_read` 计。

外部 IdP 已停用、但本系统尚未得知，是另一段延迟：声明来源通知／轮询和对账的实际边界，无法证明就不承诺从外部停用瞬间起零延迟。本系统得知后才进入自己的收紧协议；高风险动作需要的来源健康／新鲜度也检查，不能凭旧的“账号 active”长期接受。用户界面区分请求已受理、已关闭新接受、来源／属主联动待完成和已达到目标保证。

## 默认路径：有界本地授权

### 授权视图与核验

组件在本地对授权视图求值。视图由所选 Authz 成员发行，至少包含：发行权威与恢复代次、适用部署与能力、完整适用域、安全修订号（各依赖域的水位），以及按第八份算出的有效段。发行者必须具备相应裁决与完整性证据：失联的投影、只同步了一部分的视图，不能被发行为“当前完整视图”。

组件定期向 authz 发出核验请求，带上自己持有的视图修订。authz 在收到请求时**重新计算**当前完整视图：没有变化就回答“该修订此刻仍是当前视图”，有变化就返回新视图。这样的回答，无论是否携带新内容，都由 authz 本次计算产生，可以续期。缓存、代理或组件自己重放的旧回答都不能续期（参考模型的“重放”坏变体）。

authz 可以在收紧提交后向组件推送“修订已变”的提示，让组件立即重新核验；推送只用来加速，本身不续期，丢失也不影响上界。收紧时，authz 在生效点提交后即对受影响范围回答新修订；范围暂时关闭或事实未补齐时，不续发旧视图，其他已完整证明的合法范围分别判断。

### 有效期的计算

视图的有效期从组件**发出**那次核验请求的时刻起算，用组件自己的单调时钟，扣除时钟速率误差的余量：

```text
valid_until = 发出请求时的单调时钟读数 + W ×（1 − 漂移上限）
```

本地时钟最慢时，这段本地时长对应的真实时长不超过 W。计时源必须**计入系统挂起**（Linux 用 `CLOCK_BOOTTIME` 或等价时钟；普通的 `CLOCK_MONOTONIC` 在挂起时不前进，挂起十分钟后旧视图仍会显得有效）。SDK 另做停顿检测：相邻两次调度检查之间的时钟增量超过 `T_stall`，或单调时钟与墙钟的差值突变超过同一阈值，即作废全部视图并重新核验；虚拟机暂停、容器冻结后恢复的场合由此覆盖。

这样计算有三个后果，都由参考模型验证：

- 不需要组件与 authz 的墙钟同步；墙钟相差数分钟也不影响上界。
- 网络再慢，回复晚到也不会延长有效期：authz 的回答至早在请求发出后才计算，所以发出时刻是保守的起点。从收到回复时起算、或用 authz 返回的时间戳比较，都会突破上界（两个坏变体）。
- 进程重启或检测到停顿后没有可信的时钟基准，旧视图一律作废，重新核验。

authz 回答核验时，在主库上读取已提交的安全状态，不读只读副本或缓存；否则“收紧提交之后的核验都得到收紧后的视图”不成立。

W 按操作类别取值：普通读取用 `W_read`，高风险操作用较短的 `W_high`（起始值见参数表）。同一视图可以对普通读取仍有效、对高风险操作已过期。组件按 `W_high` 的一半左右主动核验，使短暂的 authz 不可用不影响业务（续期余量）。

### 判定与提交检查

一次请求取所有必要证据有效期的最小值作为 `cutoff`，至少包括：身份与会话状态、服务准入（适用时）、授权视图、任职与委托的有效期、资源兼容要求。判定在 `cutoff` 之前进行。

**写操作在业务事务内、提交前再检查一次 `cutoff`。**事务开始时视图有效、提交前已过期的，事务回滚，换新视图重试（幂等键保证不会重复执行）。只在请求开始时检查一次，长事务会在撤权之后很久才提交（参考模型的坏变体）。这个检查是本地时钟比较，不在事务里做网络调用（现行 0501 的原则）。

### 撤权的保证

撤权在 authz 的生效点于 t0 提交后：

- 任何在 t0 之前发出核验请求的视图，有效期在 t0 + W 之前结束；任何在 t0 之后发出的核验请求，得到的都是收紧后的视图。
- 因此依赖旧权限的判定不晚于 t0 + W；提交前的截止检查之后，到发出 `COMMIT` 的时间受 `C_commit` 约束（数据库端强制），所以业务提交不晚于 t0 + W + `C_commit`；`COMMIT` 发出后的刷盘与复制等待属于故障模型。

这是本页对默认路径唯一的上界写法；产品说明、独立预期与参考模型都以它为准。

这个保证不覆盖：外部身份源已停用、但本系统尚未得知的那段时间（见“收紧变更与依赖域”最后一段）；t0 之前已经提交的业务事实；已经发出的输出（见下文）。端到端的失效说明分别报告外部发现延迟、内部生效时刻、视图有效期终点和输出阶段，不能把几个期限相加后仍称为“W 秒撤权”。

### 授权服务不可用时

| 情形 | 行为 |
| --- | --- |
| 不可用时间短于续期余量 | 业务照常；视图在有效期内持续可用 |
| 超过 `W_high` | 高风险操作拒绝或暂缓（返回可重试的保护错误）；普通读取在 `W_read` 内继续 |
| 超过 `W_read` | 普通受保护读取也停止；不沿用过期视图（不提供无期限的“失效静态”） |
| 恢复后 | 重新核验；恢复代次变化时旧视图全部作废 |

不可用期间产生告警。客户如需更长的普通读取容忍时间，可在 profile 允许的范围内调大 `W_read`，同时接受更长的撤权窗口；`W_high` 的调整范围更窄，不能为了可用性把高风险操作改成长期缓存。

### 新内容、旧关系与兼容水位

有界陈旧授权不等于可以用旧权限读任何新内容。访问收紧与内容／owner／组织变化的流程，先取得相应安全变化的裁决引用，再在资源版本上保存最小安全水位；读取必须使用不早于该水位的合格授权视图。目录、冷层、搜索、报表和附件父记录保留该关联，不靠客户端传不传 revision 决定是否执行。

本系统内由不同调用者并发发起的内容变更，也不能只携带发起者知道的旧 revision。资源发布路径须在当前裁决域取得安全因果下界，并证明内容／范围使用的事实与之相容；收紧与发布重叠时，按已登记的资源发布／变更意图确定先后，无法证明则不发布为可读新版本。先受理安全收紧再异步补元组的路径，在补齐前保持该域关闭或拒绝新内容读取。

候选路径为：属主准备绑定修订／内容的发布意图，权威在同一裁决守卫内核对来源和变更状态、登记发布顺序并返回水位证明，属主只在对应修订提交时一并保存证明。收紧完成后才发起的发布登记不能取得收紧前水位；并发在先的发布登记可以稍后落库，属于明确记录的重叠顺序。若业务要求按物理内容提交时点也阻止这种旧发布，须采用 B 档的资源发布屏障，不能只多做一次 Check。

具体 provider 的一致性 token 只能代表自己的修订域，不作为可跨 provider 比大小的全局整数。它提供最低快照约束，不自动把权限库与业务库合成一个原子提交；替换成员需转换完整水位和语义，无法转换则受控重建／阻止切换。[SpiceDB 官方一致性说明](https://authzed.com/docs/spicedb/concepts/consistency)支持最低修订和内容关联，本项目的接受／提交屏障为额外协议。

## 严格路径（可选）：持久接受与提交屏障

客户或业务按 D57 启用。启用前须确认：所选 Authz 成员具备持久接受能力；相关业务属主具备意图记录与（B 档时）提交守卫；接受承受 authz 进入关键动作同步路径的可用性代价。小部署默认不启用。

### 节点与返回含义

| 节点 | 权威与含义 | 不代表什么 |
| --- | --- | --- |
| `P`：意图准备 | 业务属主持久化不可执行的命令意图，绑定主体、动作、内容与资源修订 | 请求到达、草稿或 P 均不构成已获授权，不发业务后续 |
| `A`：授权接受 | 安全接受权威在与适用撤销同一串行裁决域内，验证资格并持久化该意图的限定许可 | 不证明业务事务已经成功，不是普通 Check 的返回时刻 |
| `B`：业务激活／提交 | 业务属主在本地事务核对限定许可、意图、当前业务控制，提交业务事实／过程状态与 Outbox | 不意味着跨组件后续或外部付款已经完成 |
| `R_auth`／`R_commit`：撤销完成 | 前者完成新接受的裁决更新；后者还完成声明范围内各提交属主的屏障 | 接收撤销请求、消息已发布或某一实例刷新不等于全部撤销保证已成立 |

客户端至少能区分未接受、已接受待激活／处理中、业务拒绝／终止、已提交及未知待查询。错误或超时不把未知结果写成未执行；具体线字段和错误键在 schema 阶段登记。本稿标签不是生产状态名。

同一动作有不同法律或业务承诺节点时，由该业务契约定义 B；不能把全 ERP 都等同于一次 SQL 更新。审批决定、单据确认、业务执行分别有自己的动作与依据，审批已提交不自动冻结后续执行者的当前服务资格或必需业务控制。

这些是逻辑节点，按实际权威边界拆分：安全与业务状态确由同一属主拥有、可在同一事务保护时，可以合并 A／B 的持久提交并保留完整绑定与记录；不能因为组件碰巧共库或处于同一外壳就跨属主合并事务。下文准备／接受／激活流程针对分属安全与业务权威的路径。

### A 档的准备、接受与激活

1. 业务属主验证输入形状与必要旧／候选事实，创建持久 P，保存明确动作键、调用身份、资源修订、内容摘要、模型／业务规则版本和允许激活终点。P 不能发布可执行事件；相同键不同内容拒绝。
2. 属主在本地事务之外向接受权威申请 A，证明自己的服务身份、当前用户／合法代办证据和 P 的真实性。真实性来自认证属主的受控意图证明或权威回读，不信客户端自报的摘要；验证协议在 schema 阶段选定。权威核对必要安全来源与兼容水位。
3. 权威在守卫保护的同一事务里重验身份状态、完整授予、任职／委托资格、有效期、控制范围和风险要求，持久化唯一 A 及许可。许可期限不得晚于接受时已知的相关资格终点和 P 的激活终点。未提交接受记录前不返回可用许可。
4. 业务属主验证许可出处、用途和全部绑定，在本地事务核对 P 尚未终止、内容／资源修订一致、激活期限仍成立，以及冻结、期间锁、本人自审和适用审批依据等业务控制；原子标记消费许可、提交 B 与 Outbox。任一不满足则不产生 B。
5. 属主可靠回报结果，权威保留接受与最终处置关联；业务后续只从已提交 B 的过程／Outbox 启动。有 A 无 B 时，只能恢复这次限定激活或终止意图，不能借它执行任意系统任务。

资格有效期决定能否进入 B 的初次激活窗口，不给未来新动作续权。B 已合法建立的持久业务后续按其业务契约继续；它不复用已到期用户 token。跨组件的预占／执行仍按各属主状态协议检查，A 不把这些事务合成一个事务。

| 并发顺序 | A 档的固定预期 |
| --- | --- |
| `R_auth → A` | 若本次请求失去全部适用资格，拒绝；另一份仍合法的完整授予可按同一求值语义接受 |
| `A → R_auth → B` | 普通撤权不追溯取消该限定 A；仅在激活期限、意图及当前业务控制合格时允许 B |
| `Check → R_auth → 申请 A` | 旧 Check 不作许可，申请 A 必须按撤销后事实重验 |
| `A → 新修订／业务冻结 → B` | 内容或当前业务控制不合格则拒绝，不借旧接受改新内容 |
| `P → 撤权／资格到期 → 申请 A` | P 不构成接受依据，不通过新资格检查即拒绝 |

普通撤权之后恢复合法旧 A 不是重新接受动作；API 和审计要能辨认原接受引用。用户刷新页面或修改内容再提交是新动作，不能拿旧 A 的动作键获得旧资格。

### 许可绑定、幂等与未知结果

许可最少绑定部署与裁决权威代次、动作唯一键、业务属主／目标接口、真实与被代表主体、选定履职／委托引用、资源身份与修订、关键内容摘要、许可操作／范围、授权模型与资格证据、风险档、接受记录及激活终点。摘要采用版本化的无歧义编码，承接 I20，不用裸分隔字符串拼接。

许可是这一份持久接受的证明，不是通用 bearer 全权令牌；读取它不允许扩大操作、转移到另一资源或跨部署使用。可采用签名／MAC 或认证回读，但不能让全部业务组件持有可伪造任意接受的共用签发密钥。具体机制须符合第二份身份规格。

相同动作键与相同绑定重试返回原接受／结果，不延长激活终点；绑定不同拒绝。权威响应丢失先查原键，不换键制造第二次接受；属主事务响应丢失查权威业务状态，不重复扣减／付款。接受与业务两处状态不一致属于需要恢复的过程，不以响应先后猜事实。

未消费许可到期后，属主用同一业务事务守卫将 P 终止，迟到回执不重新激活。关闭接受记录前核对属主有权威终态／消费证据；属主不可达时保留待对账，不仅凭权威时钟到期把已经提交的 B 当失败。清理不得使旧动作键可重新执行；保存终态／墓碑或有证明的重放边界，具体保留与生命周期协议共同设计。

### B 档的提交屏障

B 档复用上述完整求值、意图与许可，另外要求参与业务属主具备本地持久提交守卫。其保证是针对目标撤销范围：撤销完成之后，旧代次下尚未建立 B 的动作不能再提交。普通收回一份授予仍按剩余合法授予重验；冻结整个主体／服务／动作域则按冻结范围关闭。

1. 权威在持久事务里关闭该范围的新 A，登记撤销操作、目标新代次和参与业务属主集合，状态为撤销处理中。登记／成员变更同样受裁决保护：新属主必须取得当前代次和关闭状态才能服务，不能遗漏后来启动的副本或组件。
2. 各业务属主在自己的数据库中，将目标范围的提交守卫推进到新代次／关闭状态。安装屏障与所有相应 B 事务访问同一冲突守卫，并持锁至事务结束：B 先持锁则先提交，安装等待；安装先完成则旧 B 被拒绝。所有写入口、重试和后台恢复都经过守卫。
3. 属主只在屏障持久提交后回执。回执覆盖该属主的全部写实例：它们共享权威守卫；分库或分区各是声明的参与者。只让一个进程刷新缓存不能代表属主完成。失联旧实例若仍能写入，必须有数据库／基础资源强制失效证据，不能把“从成员列表删掉”当隔离。
4. 权威收齐同一撤销代次、同一参与集合版本的合格回执，才持久标记 `R_commit` 完成。重复／乱序回执幂等，超时、分区或无法隔离旧写者时保持待完成并告警，不答撤销已达到 B 保证。
5. 恢复、扩容与重启先读取当前关闭状态并验证本地守卫，不允许从旧策略或旧数据库快照恢复写准入。重新开放由有权管理者以新的代次显式完成，不能自动复用旧许可。

各守卫只由自己的属主事务维护，不让组件直读／写别的组件数据库。该协议避免把一次 RPC 放在持锁的业务事务中：准备和接受在事务外，激活仅做本地守卫检查。小部署的 A 档不承担分布式屏障；需要 B 档时装配相应接受能力及属主适配，不能仅把轮询间隔改小就声称启用。

`R_commit` 之前可能已有 B 正在持锁或刚提交；其事实保留。已经建立 B 的后续是否停止，由撤销请求声明的业务冻结／取消范围另定。要求停止这些后续时，相关执行属主也要登记、实施自己的执行屏障并处理已在途外部动作，不能把用户资格撤销回执替代业务停止回执。

## 代次与修订的区分

| 标识 | 用途 | 变化的影响 |
| --- | --- | --- |
| 裁决权威／恢复代次 | 表示当前受信裁决历史，正常无损重启保持；恢复／切换按协议更新，不复用 | 旧许可必须经过明确兼容或终止处置；旧写者须实际隔离，不能只改名称 |
| 安全修订及依赖域水位 | 表示已处理的授予、资格和收紧状态 | 新 A／新读取证据按最新适用视图求值；普通撤权不因此自动抹掉此前合法 A |
| 属主提交守卫代次 | B 档撤销范围的本地防旧提交依据 | 旧代次许可不能越过新守卫，重新开放也不恢复旧许可 |
| 资源／内容修订 | 表示许可对应的实际业务内容 | 不相容的新内容不能用旧 A 激活；读取同时检查安全下界 |

这些值分别携带域和语义，不能共用一个 `version` 随意比较。尤其不能让每次普通撤权都改变恢复代次，否则会与 A 档“合法先接受可限定继续”的保证矛盾。

默认路径同样使用这些区分：视图携带恢复代次与安全修订；恢复代次变化时旧视图作废；安全修订用于新内容的水位检查。

## 敏感输出、流式与缓存

一次请求取所有必要证据终点的最小值作为 `cutoff`，至少包含身份／会话状态、服务准入（适用时）、授权视图、任职／委托有效期及资源兼容要求。考虑时钟不确定性后，读取准入、字段计算及响应释放必须在该终点前；长查询不得只在开始检查一次，然后到期后仍完整发出数据。

缓存按部署、真实／被代表主体、履职／上限、动作、资源类型／修订、完整授权与模型版本、字段用途及风险 profile 隔离。推送、轮询和 HTTP 304 不独立续期：只有发行者重新证明当前完整视图合格，才能产生新终点。冷启动、时钟异常、版本倒退、恢复到旧代次或缺必要证据时不开放旧缓存。

敏感读／导出属于高风险操作：默认路径使用 `W_high` 的视图，启用严格路径时在权威读取准入点检查当前资格；两条路径都使用绑定内容／字段范围的短输出许可；后续页、输出批次及结果领取重验。普通有界读取也不得读取晚于许可支持的新内容，见下节。服务端不能用分页游标或静态导出文件延长旧授权。

分块／流式输出每批在交付前验证剩余期限，批次有最大持续时间与字节预算，不能在一次早期检查后无限流出。已经发送或用户已保存的数据不能追回；本协议的普通读取保证是新准入和服务器新增输出的边界，实际网络中已发字节到达客户端的时刻不受应用控制。

批次不能只在开始符合期限，还须在剩余窗口内完成服务器交付；做不到则中断未交付部分，不在下一轮补发。被中断的导出／下载不能标完整成功，续传重新检查资格与内容版本。已交给网络缓冲的字节属于已发数据，不能用应用取消声称追回。

要求“严格撤销完成后不再新增发送”的出口，须另外实施输出准入／在途批次屏障，关闭旧输出、收齐保护出口的停止证据才宣告其撤销保证。无法对直接存储预签名 URL 做逐请求控制时，选择有界 URL 到期路线或经受控代理读取；不能把应用撤权写成 URL 即刻逐个失效。未实现相应屏障的出口不能声明这一更强能力。

## 到期、长连接与服务凭据撤销

时间窗沿用左闭右开：到达终点即不合格，不等待清理作业。时钟不确定性以保守边界检查，不能把时钟容忍简单加到资格终点上延长业务权限。期限与本地单调时钟的转换考虑网络耗时及误差；跨重启不能复用旧单调时间基准，无法证明时重新取证。

mTLS 连接建立证明握手时的对端凭据，不给连接中的未来请求永久准入。每请求还检查服务当前准入证据／代次，流式调用按批次重验；服务撤销进入同一收紧及所需屏障流程。证书或用户 token 过期与身份撤销分别验证，关闭连接用于加速，不作为唯一安全机制。

未知密钥、续期／取证失败、证据超期或 issuer／信任代次改变时，按声明的失败规则保护；尚在允许终点内的完整旧证据仅可用于默认路径中获准的有界操作；启用严格路径的操作仍须经过持久接受。签发、缓存和连接处置的测量范围覆盖所有实际实例，而不只验证第一次握手。

## 起始实验参数与可配置边界

以下是待审、待测的起始 profile，不是已有 SDK 默认值、客户容量或法规承诺。参数可按场景缩短或在获准风险范围调整，变更必须整体验证；不得把高风险操作改成长期缓存来换性能。

| 参数 | 起始候选 | 适用路径与验证要求 |
| --- | --- | --- |
| 普通读取的视图有效期 `W_read` | 30 s；实验同时测 5 s 档 | 默认路径；从发出核验请求起算，重复缓存返回不能续期 |
| 高风险操作的视图有效期 `W_high` | 5 s | 默认路径；付款、审批、授权管理、敏感导出；调整范围窄于 `W_read` |
| 组件主动核验的间隔 | `W_high` 的一半左右 | 默认路径；使短于续期余量的 authz 不可用不影响业务 |
| 单调时钟速率误差上限 | 0.1 % | 默认路径；超出或无法证明时按保护处理；计时源计入挂起 |
| 停顿检测阈值 `T_stall` | 2 s | 默认路径；超过即作废全部视图 |
| 事务提交时限 `C_commit` | 2 s | 默认路径；提交前的截止检查到发出 `COMMIT` 的最长时间，由数据库端强制（检查后设定事务级超时），超时未发出则回滚；`COMMIT` 发出后的刷盘与复制等待不可回滚，作为故障模型声明 |
| 来源水位探测间隔 `P_probe` | 5 s，只在水位将超期时探测，并发请求合并为一次 | 内部来源；回声与变更同一发件表 |
| 高风险操作的来源水位最大滞后 `D_src_high` | 60 s（D64） | 内部来源；超过即关闭依赖该来源的高风险分片；客户可在 profile 范围内调整 |
| 普通读取的来源水位最大滞后 `D_src_read` | 10 min（D64） | 内部来源；超过即关闭依赖该来源的读取分片 |
| 服务当前准入的本地证据窗口 `W_service` | 30 s | 两条路径；已建连接也不越界；严格路径下关键接受仍在接受事务内重验 |
| 有界输出批次最长时间 `D_chunk` | 5 s，且不晚于剩余 `cutoff` | 两条路径；字节预算及慢客户端行为由出口声明 |
| 跨主机时间比较的误差上限 `E_clock` | 1 s；超出或无法证明则保护 | 只用于需要比较墙钟的场合（例如证据的绝对终点）；视图有效期不依赖它；本机与多主机、时间回拨、恢复分别测，不把误差用作延长资格 |
| 单次 A 到首次 B 的激活上限 `T_activate` | 30 s，且不晚于 P 和资格终点 | 严格路径；不因重试延长；已建立 B 的持久后续不用这个期限伪造取消 |
| 一次等待提交屏障回执的交互预算 `T_barrier_wait` | 10 s | 严格路径；到期只返回处理中，不使撤销自动完成或重新开放 |

外部来源通知与对账上界 `D_source`、证书寿命与续期、证据获取预算、投影追赶和属主执行期限由相应适配与业务 profile 声明，缺必要项不准入。无合格 `D_source` 的身份源只能声明“本系统得知后”的保证，不能把空值算作 0。

小部署先用一个持久裁决域和默认路径，测量核验请求量、视图编译成本、生效点冲突与输出成本；并发和变化量增大后，可细分依赖域、增加身份与策略适配及观测。扩展依据尾延迟、排队、锁等待、来源滞后和预算，结构保证不靠无限副本或 service mesh 自动获得。

## 恢复、替换与审计

接受、激活、终止、收紧与屏障回执均持久化，记录主体、动作、内容／资源修订、代次、依据和结果，不记录可重放凭据。审计可靠保存继续由 I29 对应协议承担，不能因有这些记录就宣布长期审计闭环。

恢复先封闭业务准入，核对备份之后的撤销、安全事件、源事实、接受／消费记录和现存业务事实，使用不会重用的恢复／签发代次隔离旧实例及许可；补齐之前不服务。不能仅在旧库中把版本加一就证明它比所有外部旧证据更新；需要独立可信恢复控制和当前安全状态。

切换 IAM／Authz 或关系 provider 时保留稳定主体、作用域和历史依据，关闭旧接受者、登记新代次、核对在途许可与屏障状态。旧 A 要么在明确兼容窗口内继续限定激活，要么可靠终止并查询结果；不能静默失去它，也不能换个签名再给新权限。旧 B 与外部执行事实按业务恢复／更正处理。

视图核验、接受事务、失效代次、参与者登记及属主守卫的线结构、DDL／锁隔离、错误、证明格式和兼容版本仍须在正式编码阶段确定；本页不声称协议已可运行。

## 独立验收预期

下表是后续向量与故障测试的要求，尚未执行 SDK、数据库、broker 或真实网络验收。每条有合法正例、明确拒绝或未知及业务副作用断言。标注“严格路径”的条目只对启用严格路径的部署与操作适用。

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| AT01 | Check 成功后撤权，再请求 A（严格路径） | Check 不产生许可；缺剩余完整资格时 A 拒绝 |
| AT02 | A、撤销、B 的全部先后排列（严格路径） | 按同域串行裁决；A 在先的普通限定许可可激活，撤销在先不能借旧资格新接受 |
| AT03 | 仅有 P／草稿，用户离职／任职失效（严格路径） | 不启动系统后续，申请 A 重验后拒绝不合格请求 |
| AT04 | A 后字段、金额、owner 或资源修订变化 | 旧许可不激活新内容；合法相同意图正例只执行一次 |
| AT05 | A 后业务冻结、期间锁或审批依据失效 | B 检查当前业务守卫，不因旧授权接受跳过 |
| AT06 | 接受响应丢失、同键不同摘要、迟到旧回执 | 同键查询恢复，不扩权、不续期、不重复接受；冲突拒绝 |
| AT07 | B 已提交但结果未回报，权威认为许可已到期 | 查询属主事实恢复，不误报失败或再次执行；未达终态不清理证据 |
| AT08 | 激活期限与资格终点的边界及时间误差 | 最小终点保守检查，到期不激活；不能依靠清理才失效 |
| AT09 | B 档提交与本地屏障安装并发（严格路径） | 提交先取得守卫则在屏障完成前提交，屏障先完成则旧 B 拒绝 |
| AT10 | 一个属主失联／旧实例仍可写，重复／乱序屏障回执（严格路径） | 撤销保持处理中；不能因部分回执或删成员宣告 `R_commit` |
| AT11 | 撤销期间新增组件、扩容、属主分库或重启 | 登记闭包和当前代次合格前不准入，不遗漏新的写者 |
| AT12 | 窗口内／外旧视图，重复 304／缓存返回、冷启动 | 合格窗口内允许的读取可用，越界停止；无权威重新证明不续期 |
| AT13 | 查询开始合格，释放响应或下个流式批次时到期 | 停止未交付数据，不把早期检查扩成无限输出许可 |
| AT14 | 新权限视图配旧 owner；旧权限配撤销后新内容／附件 | 必要水位与事实不相容时拒绝／追赶，不靠客户端 revision 或 stale 标头放宽 |
| AT15 | 外部 IdP 停用未通知、同步心跳停止、本系统收紧中崩溃 | 区分外部发现与内部保证；证据不合格保护，收紧未完成不自动重开 |
| AT16 | 已建 mTLS 连接遇服务撤销／证据到期、仍继续发请求 | 每请求／批次准入生效，握手缓存不能永久放行 |
| AT17 | 用户导出排队后撤权、结果文件领取；旧预签名 URL | 用户路径重验；URL 按真实有限窗口或代理能力处理，不承诺即时追回 |
| AT18 | 普通用户撤权但 B 已成立；另发明确业务取消／安全冻结 | 必要限定后续和当前服务／业务控制分别判断，不混同撤权与已执行事实回滚 |
| AT19 | 恢复到撤销前备份，旧许可／证书仍持有，旧实例迟到 | 封闭恢复、补当前安全事实和新代次；不使旧许可重新激活 |
| AT20 | provider／模型切换，旧接受和水位不可直接比较 | 受控转换、兼容处置或阻止切换，不用版本数字碰巧更大放行 |
| AT21 | 撤销一份任职授予，其他完整授予仍合法且必要事实完整 | 只撤声明范围，仍合法资格按第一份模型判断；关闭／未补齐域不伪称已证明，冻结主体的正例另测 |
| AT22 | 过载、锁等待、来源滞后、证据刷新风暴与外壳争用 | 预算内恢复或保护，监控实际窗口；超时不自动完成屏障或降低风险档 |
| AT23 | 默认路径：撤权在 t0 提交，组件的视图在 t0 之前发出核验请求 | 依赖旧视图的判定不晚于 t0 + W，提交不晚于 t0 + W + `C_commit`；其后用旧权限的提交在事务内被拒绝 |
| AT24 | 默认路径：网络很慢，核验回复在发出后数秒才到 | 有效期从发出请求时起算；不因回复晚到而延长 |
| AT25 | 默认路径：组件与 authz 的墙钟相差数分钟 | 不影响上界，因为只用组件自己的单调时钟 |
| AT26 | 默认路径：事务开始时视图有效，提交前已过期 | 提交前的事务内检查拒绝，换新视图重试；不把开始时的检查当作提交依据 |
| AT27 | 默认路径：authz 短暂不可用（短于续期余量），以及长时间不可用；内部来源短暂停滞（短于 `D_src_high`） | 前者业务照常；后者在视图到期后高风险操作拒绝或暂缓、普通读取在其窗口到期后保护；不沿用过期视图；来源短暂停滞不影响业务 |
| AT28 | 默认路径：组件把缓存或重放的旧回复当作续期 | 不续期；只有 authz 本次计算的回复能产生新有效期 |
| AT29 | 默认路径：宿主挂起 10 分钟（或虚拟机暂停、容器冻结）后恢复 | 计时源计入挂起，或停顿检测作废全部视图；不继续使用旧视图 |
| AT30 | 员工组件提交即刻离职，消息系统随后中断 30 分钟 | Authz 经补取路径直接拉取，离职在 `D_src_high` 内生效；补取也失败时，高风险分片在 `D_src_high` 后关闭，不在中断期间按旧任职放行 |
| AT31 | 来源仍可达但其回声长期未到（来源故障、分区） | 同 AT30，按水位滞后关闭；回声恢复后重新开放 |
| AT32 | 已登记的离职日期到达，相关事件尚未发出 | 段的有效期终点随视图下发，到点在本地失效 |
| AT33 | 提交前检查通过，之后超过 `C_commit` 仍未发出 `COMMIT` | 数据库端超时，事务回滚；`COMMIT` 已发出后的刷盘延迟按故障模型声明，不称为回滚 |
| AT35 | 离职事件第一次处理失败、等待重投，其后的回声已被另一副本应用 | 水位停在失败事件之前，不越过它推进 |
| AT36 | 两个 Authz 副本，一个刚重启 | 水位与新鲜度都用主库事务时间判断，结果一致；主库切换后水位作废 |
| AT37 | 管理员直接在 Casdoor 控制台停用账号 | 适配组件探测时先拉取产品侧变更再写回声；产品不能拉取时按外部来源的 `D_source` 声明 |
| AT38 | 身份适配组件重启 1 分钟以内 | 高风险操作照常（`D_src_high` 内），普通读取照常 |
| AT34 | authz 用只读副本回答核验 | 不允许；核验读主库已提交状态 |

I19 的接受与撤销分支和 C10 有了两条路径的机制候选，不标已解决。冻结条件包括操作分类与路径声明、视图核验与接受／意图的 schema、资格变化与内容发布的因果协议、B 档登记与守卫、默认参数评审和真实反例验证。后续工作和未完细节见[接续清单](../work/04-next-steps.md)。

本页有两个最小模型：[时间模型](../work/checks/07-authorization-time-models.py)构造“Check 后撤销仍提交”的反例，枚举 6 种接受顺序和 4 种提交屏障顺序，核对证据不因旧缓存重取续期、新内容最低水位及恢复代次；[有界本地授权模型](../work/checks/10-bounded-local-authorization.py)在随机的撤权时刻、authz 不可用区间、网络延迟、事务时长、墙钟偏差与时钟漂移下，验证默认路径的上界、超期停止和短暂不可用期间的可用性，并以四个坏变体（从收到回复起算、用 authz 时间戳、只在开始时检查、重放旧回复）确认检查有效。两个模型都把守卫原子性、完整参与者集合和权威取证当作前提，不证明真实系统具备这些前提，不计作 AT 或 PA 向量执行通过。

2026-10-14 按独立复查（IR01、IR03、IR04）补充：有界本地授权模型的有效期改为 `W ×（1 − 漂移上限）`、上界检查收紧为 t0 + W；新增[内部来源水位模型](../work/checks/35-internal-source-watermark.py)（种子 20261013，3,000 次运行），演算员工来源的离职经有序流到达 Authz（流可停滞数分钟）、水位探测与回声、宿主挂起与预定结束日期：依赖在职状态的判定不晚于 s0 + `D_src` + W、预定结束后不再放行两项成立；不用水位、按回声到达时刻算水位、时钟在挂起时停止、视图不带结束日期四个坏变体都被发现。首轮失败是模型自身的流延迟函数破坏了保序，改为保序流后成立——这正是协议要求回声与变更在同一条有序流的原因。两个模型都不覆盖提交耗时 `C_commit`（AT33）与核验读主库（AT34），它们靠实现测试。

## 依据与独立判断

知识库 D11、ReBAC 的一致性／双写章节是中立参考；其中按请求现查的时效不能直接推导跨库业务提交的时效。本项目因此分别定义 A、B 和撤销完成，不将某个 provider 的一致性选项当作跨组件原子性。

[Zanzibar 论文](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/)与前述 SpiceDB 说明用于核对内容和授权的因果联系；[PostgreSQL 显式锁文档](https://www.postgresql.org/docs/18/explicit-locking.html)用于核对冲突守卫的事务结束边界。本页的分档、接受日志、属主提交屏障和恢复代次是项目候选设计，不声称这些来源已经替本项目证明正确。

D57 之前本页把 A 档作为关键动作的推荐路线；用户裁定默认使用有界本地授权，理由是小公司单实例部署中，authz 重启不应让付款和审批全部停止。有效期从发出请求时起算、用单调时钟，是租约协议的通行做法，本项目据此避免对时钟同步的依赖。
