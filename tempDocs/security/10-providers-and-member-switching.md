# 授权成员的能力与切换

> 状态：2026-10-13 第十份安全候选规格，尚未冻结。回答各类授权实现（标准、静态、关系图、策略引擎、嵌入库）分别能提供第九份能力目录中的哪些能力，以及新版本上线后客户怎样更换授权成员。外部产品的能力按其官方文档核对，日期与出处列在文末；不修改正式契约、SDK 或客户数据。

## 本页解决什么

用户要求权限方案“可以让客户选择使用某一套”（任务简报第二点）。前九份候选定义了共同语义、记录与编码；本页回答两件事：

1. 每种实现路线能承担哪些能力，哪些要由我们的适配层补，哪些根本做不到。
2. 客户从一个成员换到另一个成员时，怎样保证换完之后谁能看什么、能做什么完全不变，并且能回退。

## 基本设计：记录是唯一权威，引擎是派生索引

| 路线 | 判断 |
| --- | --- |
| 推荐：第九份的安全记录是唯一权威数据，保存在所选 Authz 成员自己的库中；外部引擎（OpenFGA、SpiceDB、OPA、Cerbos、Cedar、Casbin）只是由记录编译出的执行索引 | 换成员就是用同一批记录在新成员上重建索引；新旧是否等价可以逐主体比较有效段摘要；引擎故障或陈旧由我们的视图修订与有效期处理；客户的授权数据永远是同一种格式 |
| 外部引擎作为权威，客户直接维护元组或策略 | 引擎原生能力用得最充分；但完整授予的配对、来源、生命周期、管理上限都要在每种引擎里重新表达，换成员要逐引擎写双向转换，等价无法验证 |

推荐路线的代价是：引擎能做而我们的记录表达不了的东西用不上。这正是有意为之：第七份说明了，任意策略之间的包含无法判定，任意条件也不能保证下推成完整查询。超出共同表达的需求，按第七份的做法新增原子种类、写规范和验收，再在各成员上实现，不允许某个成员悄悄扩大语义。

由此，各类外部引擎在本项目中的价值分别是：

| 路线 | 价值 | 定位 |
| --- | --- | --- |
| 关系图（OpenFGA、SpiceDB） | 深层、大规模关系的计算（团队、项目成员、层级） | 为 `related` 原子提供完整候选集与单对象判定 |
| 策略引擎（OPA、Cerbos、Cedar） | 客户偏好用策略语言表达规则、已有统一策略平台 | 作为编写前端：只接受能编译成我们原子的受限子集；或只用于声明为“仅单对象”的操作的附加判定 |
| 嵌入库（Casbin） | 少一个服务进程 | 在我们的成员内作为求值实现，不改变记录与语义 |

## 外部产品的已核实能力

以下按官方文档核对（2026-10-13），只列与本项目能力目录直接相关的事实。

**OpenFGA**

- ListObjects 在期限（`listObjectsDeadline`，默认 3 秒）和条数上限（`listObjectsMaxResults`，默认 1000）内返回；流式版本 StreamedListObjects 没有固定条数上限，只受执行超时限制。
- 查询可指定一致性：`MINIMIZE_LATENCY` 可能使用缓存；`HIGHER_CONSISTENCY` 绕过缓存直接查库。
- 支持带条件（CEL）的关系元组，条件的上下文在请求时提供。
- 没有字段级权限的概念。

**SpiceDB**

- 一致性有四档：`minimize_latency`（可能陈旧）、`at_least_as_fresh`（不早于某个 ZedToken）、`at_exact_snapshot`（快照可能过期失败）、`fully_consistent`（绕过缓存）。ZedToken 表示单一数据存储中的某个时间点。
- LookupResources 支持游标，官方说明它适合中等规模的结果，约 1 万条以上可能有性能问题，建议改用批量 Check 做后过滤。
- 公开的安全公告中：CVE-2025-65111，schema 中某权限为 union、两侧引用同一关系且一侧经箭头指向另一定义的权限时，LookupResources 可能漏掉有效结果，而其他 API 计算正确（1.47.1 修复）；CVE-2024-48909，评估路径上有 caveat 时，LookupResources2 会错误地返回“条件成立、缺少上下文”（1.37.1 修复）。

**OPA**

- `/v1/compile/filters/include` 用部分求值把 Rego 规则编译成数据过滤条件，目标包括 PostgreSQL 等方言的 SQL WHERE 子句和 UCAST 结构；支持列掩码规则；无条件拒绝与无条件包含有明确的返回形式。
- 只有 Rego 的一个受限子集（官方称为 fragment）可以翻译，并非每种构造都支持每种目标。

**Cerbos**

- PlanResources 返回三种结果：总是允许、总是拒绝、条件（以 AST 表示）；官方提供把 AST 转为 Prisma、SQLAlchemy 等查询的适配器。

**Cedar**

- 官方最佳实践说明：以属性为主的策略难以回答“谁能访问什么”，需要逐条规则对照每个主体与资源；需要优化列表的产品可以改用角色为主的模型。批量操作需要逐个资源发起授权检查。

**Casbin**

- 进程内的授权库，支持多种模型配置；判定在调用进程中完成。

## 能力矩阵

“原生”表示引擎本身提供，适配层只做映射；“适配”表示需要我们的适配层完成，并列出条件；“记录层”表示由我们的记录与 SDK 承担，与引擎无关；“不可得”表示该路线不能声明此能力。全部能力都必须通过对应的一致性套件，才能把证据状态标为 `verified`（第九份）。

| 能力 | 标准成员 | 静态成员 | 关系图成员 | 策略引擎成员 | 嵌入库 |
| --- | --- | --- | --- | --- | --- |
| `authz.core` | 原生 | 原生 | 适配：引擎给出单对象判定，字段由记录层按命中段计算 | 适配：同左 | 适配：同左 |
| `authz.list.complete` | 原生（第七份编译） | 原生 | 适配：`related` 原子用引擎的完整候选集；必须能证明结果未截断（流式完成、未触及上限与期限），否则返回“查询不可完成” | 适配：只限能翻译成我们原子的受限子集；OPA 取结构化目标（UCAST）而非 SQL 文本，Cerbos 取 AST，再翻译成原子；翻译不了即不可完成 | 记录层 |
| `authz.atom.related` | 适配：组件本地关系投影加完整性水位 | 不可得 | 原生 | 不可得 | 不可得 |
| `authz.containment.*` | 原生（第七份） | 原生 | 记录层：包含证明只在我们的段上做 | 记录层：同左；引擎策略不参与包含证明 | 记录层 |
| `authz.management.delegated` | 原生 | 不可得（无运行时管理） | 记录层 | 记录层 | 记录层 |
| `authz.share.institutional`、`authz.delegation.*` | 原生 | 不可得 | 记录层，关系可由引擎计算 | 记录层 | 记录层 |
| `authz.impersonation.readonly`、`authz.break_glass` | 原生 | 不可得 | 记录层 | 记录层 | 记录层 |
| `authz.path.bounded_local` | 原生 | 原生（视图来自配置） | 适配：视图编译时以最强一致性读取引擎（OpenFGA `HIGHER_CONSISTENCY`，SpiceDB `fully_consistent`） | 适配：视图包含策略版本 | 原生 |
| `authz.path.strict_acceptance`、`strict_barrier` | 原生 | 不可得 | 记录层 | 记录层 | 记录层 |
| 字段逐行掩码 | 记录层 | 记录层 | 记录层（引擎无字段概念） | 记录层；OPA 的列掩码规则不替代按命中段的逐行计算 | 记录层 |

两点说明：

- 引擎的修订标识（SpiceDB 的 ZedToken、OpenFGA 的一致性选项）只在该引擎内有意义，不跨成员比较（第九份：修订只在同一域内比较）。我们的安全修订与恢复代次由成员的记录层维护，引擎索引滞后时视图不续期。
- 引擎的列表结果即使声称完整，也必须由一致性套件证明。上面 SpiceDB 的 CVE-2025-65111 说明，列表接口的完整性缺陷会出现在成熟产品中，而同一产品的单对象接口仍然正确，也没有错误提示；只用单对象判定做测试发现不了它。

## 静态成员

静态成员没有运行时管理界面。授权数据是一份按第九份编码的记录文件，随部署发布，文件摘要钉在部署配置中。

- 变更就是发布新的记录文件；第八份的生效点在部署时执行：装配工具重新做包含证明、最后管理员检查不适用（没有运行时管理员），然后发布。
- 默认路径照常：视图由成员从文件编译，核验回答由成员本次计算产生。
- **只有授予记录是静态的**。账号状态、任职实例、组织等运行时来源照常按第八份的有效段表求交，并按第三份的内部来源水位取得新鲜度；D30 的任职关联自动撤销与离职停用在静态成员下同样生效。
- 不提供分级管理、共享、委托、扮演、紧急访问和严格路径。需要这些能力的客户不能选静态成员（D07：缺能力即阻止装配，不静默降级）。
- 适合权限结构固定、几乎不变的小客户，或作为测试与演示的基线。

## 成员切换协议

适用于新版本上线之后，客户从一个授权成员换到另一个。默认在预告的维护窗口内进行（D25）。

1. **预检。**比较部署所需能力与新成员的能力声明（第九份的准入检查）；统计新成员无法表示的记录；确认新成员已声明订阅各内部来源并获准补取（协议 02），否则它的水位建立不起来。存在缺口时停止：要么不换，要么由客户先显式收窄业务范围或授权（只能收紧，不能借换成员扩权），再重新预检。
2. **进入切换窗口。**新的**放宽**类管理变更驳回（候选 reason `MEMBER_SWITCH_IN_PROGRESS`）；**收紧**（撤权、停用、安全处置）照常在旧成员上生效（第八份“收紧提交即生效”），并记入切换增量。来源事件（员工、IAM、组织）照常由旧成员消费，同样记入增量。严格路径停止新的接受，已有许可在 `T_activate` 内完成或终止。业务读写照常，组件继续使用旧成员的视图。
3. **导出。**从旧成员导出修订 R 的全部安全记录、依赖边、确认与计划记录，带每条记录的摘要，以及 R 对应的各来源消费进度。
4. **导入与编译。**新成员导入记录（记录身份不变），编译自己的引擎索引。
5. **等价核验。**对每个分片，两个成员分别计算视图；逐个主体 × 资源类型 × 操作比较规范化有效段集合的摘要。另在新成员上运行一致性套件的列表与字段部分。任何差异都中止切换，报告列出具体的主体、类型、操作。
6. **追平增量。**把 R 之后在旧成员上生效的收紧与来源事件重放到新成员，或让新成员从导出时记录的来源消费进度继续消费；再对受影响的分片做一次等价核验。增量追平之前不切换。
7. **切换**（按顺序，不留窗口）：
   1. 旧成员停止受理放宽类管理写入。在 7.4 围住旧成员之前，请求仍经旧地址到达旧成员；此后的**收紧**由旧成员受理，并应用到两个成员：旧成员**先在本地提交**（同一事务把这条收紧记入切换增量，标“待转发”），再转发新成员，新成员确认后把增量标为“已转发”，然后应答。本地提交失败时请求失败，两个成员都没有变化；转发失败或未确认时增量保持“待转发”，由旧成员重试。所以直到 7.4 围住旧成员，旧成员回答的核验都已包含这些收紧，新成员也不会领先于旧成员。
   2. 来源消费移交：旧成员停止消费员工、IAM、组织的事件；新成员从旧成员**最后连续已应用的位置**继续消费，而不是导出时的位置。此后旧成员的来源水位不再推进，超过 `D_src_high` 时旧成员关闭高风险分片——这是安全的，维护窗口的时长预期要计入它。
   3. 排空：把旧成员截至 7.2 移交位置的全部增量重放到新成员——第 6 步之后生效的收紧、7.1 之后“待转发”的收紧，以及旧成员在移交之前应用的来源事件——直到旧成员的增量中没有“待转发”或未重放的条目。增量不为空时不进入 7.4。
   4. **围住旧成员，放开新成员，旧成员此后代理**：部署变量中的授权地址（`$endpoint:` 引用）按组件滚动生效，不是瞬时的，所以不能让两个成员各自作答。先让旧成员停止自己作答（不再受理管理写入、不再用自己的状态回答核验），排空“待转发”为零；此后新成员以新的恢复代次开始受理管理写入与核验。旧成员把此后收到的核验与管理请求**代理**给新成员。代理不替调用者说话：部署声明“旧成员 → 新成员”的代理关系，新成员只在切换窗口内、只从旧成员接受附带原调用者凭据证明的请求（安全 02 的凭据转发），按原调用者的身份计算，不按旧成员的服务身份；也可以在传输层直通，使组件的会话直接终止在新成员。回答由新成员本次计算，带新成员的恢复代次，视图有效期仍从组件发出请求时起算，所以撤权上界不变，也不需要暂停受保护操作。然后滚动更新地址；已换地址的组件发现恢复代次变化，丢弃旧视图，直接向新成员核验；卡住的组件经代理照常工作。新成员不可达时，代理返回授权不可用，组件按有效期保护。
8. **观察与回退。**新成员开始作答（7.4）之前，回退就是解除围住：旧成员从自己的连续位置继续消费来源事件，丢弃转发给新成员的增量记录；7.4 之后，回退按本协议反向执行一次（从新成员的数据库导出增量——不要求新成员仍在线服务——旧成员重放、等价核验），新成员期间生效的收紧与来源事件不丢失；新成员不可用、数据也读不到时，按授权组件不可用与整套恢复处理。
9. **退役旧成员。**旧成员“待转发”为零、全部组件已换地址且一个观察期（起始 1 天）内不再收到代理请求之后才退役；退役前代理一直有效。审计与授权解释保存在审计记录中，不依赖旧成员在线；旧成员按 D54 的停用规则处理。

参考模型说明了第 5 步为什么必须比较内容摘要：它在随机存储上把一个无损的关系图式翻译与标准成员比较，全部一致；四种有损翻译（丢金额区间、按维度压平、丢写字段、忽略有效期）都被发现并定位到具体主体与操作；若只比较段的条数，四种都发现不了。

**模型没有覆盖的条款**（独立复查 IR14）：等价核验模型只比较修订 R 上的状态，没有建出切换窗口内的收紧与来源事件（PV21、PV22）；第 6、7 步的增量追平、移交与排空靠实现测试。

## 客户怎样选

| 客户情形 | 推荐 |
| --- | --- |
| 小公司，角色加范围就够 | 标准成员 |
| 权限结构固定，几乎不改，资源最少 | 静态成员（无运行时管理） |
| 大量项目、团队、层级关系，关系深且多 | 标准成员 + 关系图成员提供 `related` 原子；或整体换为关系图成员 |
| 已有统一策略平台（OPA、Cerbos），或希望用策略语言维护规则 | 策略引擎成员，策略只能写在可翻译成原子的受限子集内；超出部分的操作只能声明为“仅单对象” |
| 对撤权严格性要求高 | 任一具备 `authz.path.strict_acceptance` 的成员，按操作启用严格路径（D57） |

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| PV01 | 新成员缺少部署所需能力 | 预检停止并列出缺口；不切换 |
| PV02 | 新成员无法表示部分记录（例如金额区间） | 预检报告这些记录；客户只能先收紧，不能借切换扩权或丢弃 |
| PV03 | 切换窗口内提交管理变更 | 放宽驳回；收紧照常生效 |
| PV04 | 切换时有严格路径的许可在途 | 在激活期限内完成或终止；不跨成员延续 |
| PV05 | 新旧成员对某主体的有效段摘要不同 | 中止切换，报告主体、类型、操作 |
| PV06 | 切换后组件仍持有旧成员的视图 | 恢复代次不同，丢弃旧视图，向新成员核验 |
| PV07 | 切换中回退 | 新成员开始作答之前：解除围住，旧成员从自己的位置继续消费；之后：按反向协议迁回，新成员期间的收紧与来源事件不丢失 |
| PV08 | 新成员上已有变更生效后要回退 | 必须反向执行完整协议，不直接切回 |
| PV09 | 关系图成员的列表触及条数上限或期限 | 不能证明完整，返回“查询不可完成”；不把截断结果当完整 |
| PV10 | 关系图引擎以“最小延迟”一致性返回陈旧结果 | 编译视图时使用最强一致性；陈旧索引不续期视图 |
| PV11 | 比较 ZedToken 与我们的安全修订，或比较两个成员的修订 | 不允许；只在同一域内比较 |
| PV12 | 策略引擎的规则超出可翻译子集 | 该操作的列表不可完成；只可声明为“仅单对象” |
| PV13 | OPA 返回 SQL 文本 | 适配层不使用 SQL 文本，改取结构化目标并翻译成原子 |
| PV14 | 引擎的列掩码规则与按命中段的字段结果不同 | 以记录层的逐行字段为准；不一致时套件失败 |
| PV15 | 引擎声称列表完整，但一致性套件发现漏行 | 能力证据不能标为 `verified`，装配拒绝依赖它的功能 |
| PV16 | 静态成员的部署请求启用分级管理或委托 | 装配拒绝 |
| PV17 | 静态成员发布新记录文件，其中授予超出管理上限 | 装配时包含证明失败，发布被拒 |
| PV18 | 切换后审计与授权解释的查阅 | 仍可查，不依赖旧成员在线 |
| PV19 | 切换导入后记录身份 | 与旧成员相同；摘要相同 |
| PV20 | 只比较条数的等价核验 | 不合格；必须比较规范化内容摘要 |
| PV21 | 切换窗口内撤销一份授予 | 在旧成员上立即生效，记入增量，切换前重放到新成员 |
| PV22 | 切换窗口内员工离职事件到达 | 移交前由旧成员应用并在排空中重放；移交后由新成员从旧成员最后连续已应用位置继续消费；切换后不丢失 |
| PV23 | 选用静态成员，员工任职结束 | 任职关联授予照常失效 |
| PV24 | 追平增量之后、更新地址之前撤销一份授予 | 旧成员受理并同时应用到两个成员；切换后不复活 |
| PV25 | 切换后回退，新成员期间消费了离职事件 | 反向迁回，离职不丢失 |
| PV26 | 排空之后、换地址之前撤销付款权 | 旧成员先在本地提交并记入增量，再转发新成员；旧成员此后回答的核验已收紧 |
| PV27 | 7.1 之后撤销付款权，旧成员本地提交成功、转发新成员失败 | 增量保持“待转发”，由旧成员重试；排空为零之前不换地址；旧成员的核验已收紧 |
| PV28 | 7.1 与 7.2 之间旧成员应用了一条离职事件 | 排空包括它；新成员从移交位置之后继续消费，离职不丢失 |
| PV29 | 换地址期间，管理入口已指向新成员并撤销付款权，付款组件仍指向旧成员 | 旧成员把核验代理给新成员，回答已收紧；撤权上界不变，不暂停受保护操作 |
| PV30 | 某组件卡住，一直没换到新地址 | 经旧成员代理照常工作；旧成员在不再收到代理请求、观察期结束之前不退役 |
| PV31 | 代理期间，新成员收到旧成员转来的核验请求 | 只在切换窗口内、只从声明的旧成员接受，并按附带的原调用者凭据证明计算；不按旧成员的服务身份计算 |

## 仍未解决与下一步

- 各成员的一致性套件：在第七份参考模型与第九份共同向量的基础上，形成可对运行中的成员执行的黑盒套件（brickKit 的 T15 类测试）。
- 关系图成员中 `related` 原子的具体映射（关系类型、锚点、深度到引擎模型的对应），以及关系属主的投影协议。
- 策略引擎“可翻译子集”的正式定义：哪些 Rego／Cerbos 条件对应哪些原子。
- 静态成员记录文件的签名与发布流程。
- 本页尚未涉及身份成员（IAM）的切换；身份侧的稳定主体与迁移规则在第二份，切换协议待身份专题统一写。
