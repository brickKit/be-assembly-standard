# 安全记录的状态与变更协议

> 状态：2026-10-13 第八份安全候选规格，尚未冻结。承接前七份候选与 D30、D35–D37、D57、D59，给授权管理、身份关联、任职、共享、委托、扮演、紧急访问和恢复定出共同的状态与变更协议；不修改正式契约、SDK 或客户数据。

## 本页解决什么

前几份候选分别写了各类安全记录“应当怎样”：管理上限（第四份）、共享与委托（第五份）、可信身份（第二份）、接受与撤销（第三份）。但每类记录的状态怎样流转、谁在什么时候让变更生效、变更没做完时权限是什么样，还没有统一的协议。本页回答四个问题：

1. 全部安全记录用什么状态，怎样流转。
2. 一个变更在哪一刻、经过哪些检查才算生效；结果不明时怎么办。
3. 来源变化之后（任职结束、上限收紧、委托人缩权），依赖它的记录怎样立即失效或缩小，后续清理做什么。
4. 哪些操作需要独立确认；只有一名管理员的小公司怎么办；最后一个管理员、首次安装和恢复怎样处理。

## 两条基本原则

**一、一套通用生命周期，管全部安全记录。**各类记录（管理职责、管理持有、角色修订、授予、任职、账号关联、共享、委托、扮演、紧急访问、安装认领、批量计划）使用同一组状态和同一个生效点，按记录类型配置参数：需要谁确认、最长有效期、能否续期、通知谁。这与知识库授权决定 D9 的建议一致：所有临时授予形式“共用同一个底层结构：带期限、可撤销、记录了来源的授予”，不要每种各建一套。

**二、有效性由来源推出，不靠清理作业。**一条记录实际能提供的访问，等于它自己保存的段，与它的每个来源当前约束的交集。这个交集在编译授权包时，用[第七份](07-finite-expressions-containment-and-queries.md#求交委托和扮演的派生段)的逐维求交算出。因此来源一收紧，依赖它的记录立即缩小，不必等影响闭包作业跑完。闭包作业只负责记账、标记复核、通知和清理；它晚到、失败或重复，都不会放出多余的权限。

## 方案比较

| 路线 | 判断 |
| --- | --- |
| 推荐：通用生命周期 + 来源交集求有效 + 闭包作业只记账 | 一处实现、一组向量；收紧即时生效，不依赖作业；新记录类型只加参数 |
| 每类记录各写状态机，收紧时由作业逐条改状态 | 写法直观，但状态与失效规则各写一遍；作业延迟或漏边期间旧权限仍然有效，这正是“到期了还能用”的来源 |
| 收紧时同步改写所有依赖记录 | 生效即时，但一次收紧可能牵动成千上万条记录，长事务、锁争用；依赖索引有缺口时还会漏改 |

## 受本协议管理的记录

| 记录 | 属主 | 来源（有效性依赖谁） | 放宽时需要 | 谁能收紧 |
| --- | --- | --- | --- | --- |
| 管理职责单元 | Authz | 父职责单元的可授出上限 | 父单元的管理资格 + 包含证明 + 独立确认 | 父单元的管理者；安全处置 |
| 管理持有资格 | Authz | 职责单元当前状态；绑定的任职实例；账号状态 | 该单元的管理资格 + 独立确认 | 该单元或上级的管理者；本人放弃；安全处置 |
| 客户角色修订 | Authz | 已注册且未退役的权限键 | 角色管理资格；新增权限按 D37 确认 | 角色管理者 |
| 普通授予 | Authz | 治理单元的当前上限；绑定的任职实例；角色修订；账号状态 | 管理资格 + 包含证明（第七份） | 管辖该授权域的管理者；受授人放弃；来源收紧 |
| 任职实例 | 员工组件 | 员工在职状态；组织单元有效 | 员工组件的人事流程 | 员工组件 |
| 账号与员工关联 | IAM（账号侧），员工组件提供员工事实 | 账号状态；员工在职 | 身份管理资格 + 独立确认 | 身份管理者；安全处置 |
| 机构共享 | Authz | 资源治理的可共享上限；资源当前归属；接收人账号状态 | 共享管理资格 + 包含证明 | 资源治理者；接收人放弃；来源收紧 |
| 个人委托边 | Authz | 委托人当前的直接权限；创建时的上限；委托人绑定的任职实例 | 委托人本人（及 profile 要求的确认）+ 包含于委托人当前权限 | 委托人；受托人放弃；来源收紧 |
| 只读扮演会话 | IAM 签发会话，Authz 记许可 | 被查看人当前读取权限；操作者的扮演资格 | 扮演资格 + 原因与工单 + profile 要求的批准 | 操作者退出；被查看人账号停用；管理者撤销；到期 |
| 紧急访问会话 | Authz | 预置的紧急角色；操作者的紧急资格 | 按次批准，或合同约定的先用后审 | 到期；管理者撤销 |
| 安装认领 | Authz | 部署代次 | 精确身份匹配或一次性确认码 | 认领即消耗 |
| 变更计划 | Authz | 计划内各项的目标修订 | 各项分别满足其记录类型的要求 | 计划发起人取消；到期 |

任职实例和账号关联不归 Authz 所有，但它们的状态变化同样走本页的方向规则：收紧立即生效，放宽要完整事实。Authz 保存的是它们的受控视图（第二份）。

## 通用生命周期

| 状态 | 含义 | 是否提供访问 |
| --- | --- | --- |
| 申请 | 候选内容已记录 | 否 |
| 待确认 | 等待 profile 要求的确认 | 否 |
| 待生效 | 已确认，生效时间在未来 | 否；到时间后经生效点重新检查才转为生效 |
| 生效 | 正常提供访问 | 是，等于自身段 ∩ 来源约束 |
| 受保护暂停 | 因安全处置，或来源约束无法计算，暂不提供访问 | 否 |
| 结束 | 终态，记录结束原因：到期、撤销、放弃、来源结束、被替代、驳回、取消、撤回 | 否 |

规则：

- **结束是终态。**结束的记录永不复活；重新授予是一条新记录，引用旧记录作为前身。续期、扩权、改目标也一样（第五份的同一规则在此推广到全部类型）。
- **到期在求值时生效。**有效期按左闭右开比较，到达终点即不提供访问；把状态改为“结束（到期）”是记账，由闭包作业完成，晚做不影响安全。
- **受保护暂停只能经生效点恢复。**恢复为“生效”必须重新做一次完整检查，内容不变；内容要变就是新记录。
- **修订不改身份。**记录的内容修订（例如普通授予的范围缩小）生成新修订号，记录身份不变；扩大范围则按放宽处理。

## 变更方向

每个变更先归类：

| 方向 | 例子 | 规则 |
| --- | --- | --- |
| 收紧 | 撤销、缩小范围、结束任职、停用账号、暂停、降低上限 | 有权收紧者一提交即生效，不需要包含证明，也不需要确认；任何主体都可以放弃自己的授予、委托或共享 |
| 放宽 | 新增授予、扩大范围或字段、延长期限、新增管理资格、激活会话 | 在生效点重新检查请求者当前资格、包含证明、所需确认、来源事实与预算，全部通过才生效 |
| 中性 | 显示名、说明、标签 | 不改变任何访问；仍记修订与审计 |

**同时有收紧和放宽的变更拆成两步，先收紧后放宽。**例如把一份授予从法人甲改到法人乙：先缩去甲（立即生效），再按放宽为乙申请。调岗时旧任职在 T 时刻结束、新任职在 T 时刻开始：旧授予在 T 失效，新授予在 T 经生效点检查后才生效；中间不出现“新旧都有效”的窗口。

收紧不需要证明，是因为它只会减少访问；但“谁有权收紧”仍要检查（第四份：回收只作用于自己管辖的授权域，不能借管理一个人撤掉其不归自己管的跨域授予）。

## 生效点

每个放宽变更，以及每个改变状态的收紧变更，都在 Authz 的一个本地事务里完成，这个事务就是生效点：

1. 按变更涉及的治理域加守卫（第三份的同一类守卫），防止并发的收紧与放宽交错。
2. 重新检查：请求者此刻的身份与管理资格；目标记录与来源的修订是否仍是预览时的值；包含证明（第七份，现场重算，不复用旧见证）；所需确认是否齐全且未过期；预算；最后管理员不变量（见下文）。
3. 写入新状态与修订，推进受影响域的安全修订号，同事务写 Outbox：投影更新、通知意图、审计意图。
4. 返回结果：已生效、已驳回（附原因）、处理中；调用方收到超时或未知时，用同一个变更键查询，不重复提交。

变更键按请求者命名空间区分（现行 0507 的同一原则）。同一变更键、不同内容，按冲突驳回。

**与 D57 的关系。**本页定义的是安全记录“何时变了”；“变了之后各组件何时不再放行”由第三份定义。按 D57，默认路径是：生效点提交并推进安全修订号后，各组件的本地授权视图在短有效期内经过权威核验，超期即拒绝或暂缓高风险操作；客户选用严格路径时，再加持久接受与提交屏障。两条路径共用本页的生效点。

## 有效段的计算

编译授权包时，每条生效中的记录按下表与来源求交，结果才是下发的段：

| 记录 | 有效段 |
| --- | --- |
| 普通授予 | 授予的段 ∩ 治理单元当前的上限段；绑定的任职实例不在生效中、或受授账号已停用时为空 |
| 管理持有资格（作为授出上限） | 职责单元当前上限 ∩ 父单元当前上限（逐级）；持有资格本身、绑定任职或账号失效时为空 |
| 机构共享 | 共享的段 ∩ 资源治理当前的可共享上限；资源已移出原治理范围时为空 |
| 个人委托边 | 委托人当前直接权限的每个段 ∩ 创建时上限 ∩ 委托边的范围与期限（第五份）；多层链逐边求交 |
| 只读扮演会话 | 被查看人当前的读取段 ∩ 会话上限；操作者自己的权限不参与 |
| 紧急访问会话 | 预置紧急角色的段（默认只读） |

求交在第七份的原子代数里总能算出（每种原子在求交下封闭）。只有一种情况算不出：来源或记录使用了提供方私有的表达。这时该记录进入“受保护暂停”，直到能证明为止。

**对第四份的修正。**第四份写道，治理上限收紧后“无法证明部分边界时暂停该受影响授予”。按本页，部分越界的授予应当保持生效、标记待复核，其有效段自然就是交集；整体暂停会把仍在上限之内的合法访问一起停掉。参考模型的坏变体（整体暂停）因此改变了有效访问，被检查判为错误。只有出于安全处置的收紧，才整体暂停。

## 影响闭包

来源收紧后，闭包作业按依赖索引找出受影响的记录，逐条处理：

| 情况 | 处理 |
| --- | --- |
| 有效段已为空（例如绑定的任职已结束、全部落在新上限之外） | 转为“结束（来源结束）”，写审计与通知 |
| 部分越界 | 保持生效，标记待复核，通知有权管理者；复核结论是缩小（生成新修订）或接受现状（有效段本来就是交集） |
| 来源约束无法计算 | 转为“受保护暂停” |
| 依赖索引本身不完整或不可用 | 不判断为“无人受影响”；把整个来源域标为待复核，按最保守的方式计算有效段 |

作业持久记录进度，可重复执行，结果幂等。正确性不依赖它：参考模型验证了在任何时刻运行闭包作业，所有人的有效访问都不变。

## 确认与受保护操作

确认要求写在 profile 里：要几个独立确认人、谁有资格、确认多久内有效。独立指不同的自然人：关联到同一员工的多个账号算一个人（第二份）；申请人不能确认自己的申请。

标准受保护操作（需要至少一名独立确认人）：

1. 新增或扩大管理职责、授出管理持有资格、再下放管理。
2. 授予或变更系统角色的持有（见下节）。
3. 建立或变更账号与员工的关联。
4. 紧急访问的激活（合同事先约定的情形可以先用后审，但必须立即通知并在期限内复核）。
5. 超过阈值的批量计划（阈值在 profile 中）。
6. 恢复流程。

普通授予、普通角色修订不默认要求第二人（D35：小公司的集中管理不强制第二名员工）。

**只有一名管理员时。**受保护操作找不到独立确认人，不能取消这一要求（第四份）。候选做法是“部署所有者确认”：安装时生成一份部署所有者凭据，由客户离线保管（例如打印或存入客户的密码保险库），与日常登录凭据分开；受保护操作由它作为第二道确认，使用后记录并通知。这让单人公司也能完成受保护操作，同时让“管理员账号被盗”不足以独自扩大管理权限。

## 系统角色与最后管理员

系统角色由产品预置，客户不能修改其内容，只能管理谁持有：

| 系统角色 | 用途 | 默认持有 |
| --- | --- | --- |
| 授权管理员 | 全范围的管理上限，用于集中管理 | 安装认领者 |
| 审计查看员 | 查看审计与授权解释，不改任何授权 | 无 |
| 紧急只读 | 紧急访问会话使用的预置角色 | 无人常驻持有，只经紧急访问会话生效 |
| 超级用户 | D37 所述对已注册未退役权限键的特殊补齐 | 生产环境默认无人持有 |

**最后管理员不变量**：任何普通变更生效后，部署中必须至少有一份“可用”的授权管理员持有资格，即持有资格生效、账号有效、绑定的任职生效。生效点在治理域守卫内检查这个不变量；两名管理员并发互相撤销时，守卫使它们串行，后提交者被驳回。

安全处置（账号被盗、强制停用）不受这个不变量约束：它照常生效。若因此没有可用管理员，部署进入“待恢复”状态，期间除恢复流程外的管理变更一律驳回，业务授权照常按各自来源计算。参考模型中，约一半的随机序列在强制停用后进入了待恢复状态，其余不变量在这些序列中同样成立。

## 安装认领、恢复与紧急访问

**安装认领**（承接现行 0303 的方向）：安装时登记一条认领记录，内容是精确的外部身份（签发方 + 主体）或一次性确认码的摘要，带到期时间。首次登录匹配成功时，在同一事务里创建授权管理员持有资格并把认领标为已消耗；唯一约束保证只能消耗一次。认领与部署代次绑定，用旧备份恢复不会重新打开已消耗的认领。

**恢复**：没有可用管理员，或需要撤换被盗的管理员时使用。由部署所有者用离线凭据，在部署机上执行恢复命令：

1. 进入恢复窗口：除恢复操作外，管理变更全部驳回。
2. 为指定的精确身份创建新的授权管理员持有资格；推进恢复代次（第三份），使旧会话与旧许可失效。
3. 通知全部现有管理员与登记的联系人，写审计；要求事后复核并记录结论。
4. 轮换部署所有者凭据。

恢复不经过可能已经失效的身份系统；不提供绕过认证的接口，也不自动授出超级用户。

**紧急访问**：用于正常流程来不及的情形，例如生产故障需要查看业务数据。按知识库的通行做法：预置紧急只读角色；按次批准（或合同约定的先用后审）；激活即通知客户管理员，不能关闭；会话期限有上限，延长要重新批准；默认只读、禁止导出；每个请求的审计带会话标识；事后在期限内复核。身份系统不可用时，紧急访问需要不依赖它的认证路径；所选 IAM 成员不具备这项能力时，紧急访问在该部署中不启用。

**项目团队访问客户系统也走这里。**按 D55，项目团队与 AI 维护客户版本；团队成员（或代其执行的 AI 工具）进入客户的业务系统，应当是一次获批的紧急访问或临时访问：客户批准、有期限、全程审计、结束后给客户访问记录。不设供应商常驻账号。

## 员工、账号与任职

- **任职实例**由员工组件拥有：计划中 → 生效 → 结束。法人、部门、岗位等有安全含义的变化，结束旧实例、创建新实例（第四份），不在原实例上改。员工组件发布带实例身份与修订的事件。
- **账号与员工关联**：申请 → 待确认（受保护）→ 生效 → 结束。一个员工可以关联多个账号，一个账号最多关联一个员工。关联的建立和变更都是受保护操作，因为它决定了任职授予作用到哪个账号，也决定了职责分离把哪些账号视为同一人。
- **新任职的授权建议**（D30）：员工组件发布新任职后，Authz 按岗位模板生成授权建议，建议以“申请”状态存在，由合格管理者确认后才成为普通授予；建议本身不提供访问。旧任职关联的授予在任职结束时由来源交集立即失效（D30 的“自动撤销”），闭包作业随后把它们记为结束。

## 批量计划

批量计划本身是一条记录：草稿 → 已预览 → 已确认 → 执行中 → 已完成、部分完成或已取消。计划内的每一项另有状态：待执行、已生效、已驳回、待复核。

- 预览时记下每一项的候选内容与目标修订；确认针对这些内容。
- 执行时每一项分别经过生效点。目标修订已变的项转为“待复核”，需要重新确认，不按旧确认生效。
- 计划报告每一项的最终状态，不以“整批成功”掩盖未执行项；取消只停止未执行的项，已生效的项要用新的收紧变更撤回。
- 新增人员、新增角色使用者不自动进入已确认的计划（第四份）。

## 共享、委托与扮演的参数

这三类记录的行为规则在第五份；在本协议中，它们是通用生命周期的三组参数：

| 参数 | 机构共享 | 个人委托边 | 只读扮演会话 |
| --- | --- | --- | --- |
| 发起者 | 有共享管理资格的人 | 委托人本人 | 有扮演资格的支持人员 |
| 确认 | 按资源治理 profile | 按委托类型 profile；审批代理通常由委托人或上级确认 | 按 profile 批准，必须带原因与工单 |
| 最长期限 | 允许“无固定终点”，但仍随治理上限与接收资格变化 | 按委托类型，例如休假日历；起始值待定 | 15 分钟（起始候选），不可刷新 |
| 续期 | 新记录 | 新记录 | 新会话，重新申请 |
| 授出者卸任 | 不影响（机构来源，D36 同理） | 委托人失去来源时，有效段随之为空 | 不适用 |
| 再委托 | 不允许 | 基础 profile 不允许；扩展 profile 有限层数（第五份） | 不允许 |
| 激活时的通知 | 接收人 | 受托人；审批代理通知相关流程 | 被查看人，激活事务内写通知意图 |

**通知落点。**会话类记录（扮演、紧急访问）在激活的同一事务里写通知意图，由通知组件投递并写入站内通知；投递失败按通知组件的重试与告警处理，不回滚已激活的会话。部署中没有可用的站内通知能力时，这两类会话不启用（第五份 SD17）。

## 参考模型与运行结果

[参考模型](../work/checks/09-change-protocol.py)用有限原子集合代替第七份的段代数，对抽象授权存储随机执行 3,000 条、每条 40 步的操作序列：放宽请求与生效、上限收紧、任职结束、撤销管理资格、新增管理员、强制停用、撤销与重新授予、委托、闭包作业、批量计划、管理员正常卸任。2026-10-13 运行结果：

| 检查 | 结果 |
| --- | --- |
| 有效访问 = 记录 ∩ 来源约束；收紧后、闭包前不存在超出新约束的访问；委托所得不超过委托人当前直接权限 | 成立 |
| 闭包作业在任何时刻运行，都不改变任何人的有效访问 | 成立（修正第四份的暂停规则之后） |
| 普通变更后始终有可用管理员；强制停用可以打破，此后进入待恢复状态 | 成立；1,429 条序列进入待恢复状态 |
| 结束的记录永不复活 | 成立 |
| 请求与生效之间失去管理资格的请求者，其请求不能生效 | 成立 |
| 管理员正常卸任不结束其发出的普通授予 | 成立 |
| 批量计划每一项都有明确结果 | 成立 |

8 个坏变体（部分越界整体暂停、有效计算忽略上限、忽略任职状态、生效点不重查请求者、跳过最后管理员检查、卸任时连带结束授予、重新激活已结束记录、委托不与委托人当前权限求交）全部使模型失败。第一轮有两个变体未被发现，原因是检查写成了同义反复或只检查单条记录；修正检查后均能发现。

模型只说明协议在抽象层面自洽，不是 SDK、数据库或任何提供方的运行结果，也不计作 CP 或 PA 场景执行通过。

| CP02 | 新增授予在预览后、生效前，请求者失去管理资格 | 生效点驳回 |

## 依据与独立判断

知识库授权决定 D9 与《委托与临时授权》中的紧急访问一节提供了中立参考：共用一个“带期限、可撤销、记来源”的结构；判定时比较有效期，不靠清理作业；紧急访问预置、按次批准、激活即通知、默认只读、不依赖故障系统、事后复核。本页与之一致。

项目的独立选择有两处与知识库不同：一是管理上限与本人业务权限分开（D35，已在[知识库反馈 PR #10](https://github.com/ZhijieQ/knowledge-base/pull/10) 中说明）；二是允许扩展 profile 下有限层数的再委托（第五份），而知识库建议委托不能再转委托。后者是项目为集团客户保留的扩展能力，基础 profile 仍不允许再委托。

“有效性由来源推出”是本页的项目设计，正确性依靠上面的参考模型、后续三语言向量和真实数据库验证，知识库与外部资料不替它证明。
