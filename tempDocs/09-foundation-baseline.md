# 底层方案推荐与冻结条件

> 状态：2026-10-13 全局理论复审的推荐基线，尚未获整套冻结确认。已有用户决定继续有效；本页新增的技术方案是待审建议，不能当作已实现、已验收或已批准实施。

## 审查结论

独立组件、部署时合并、唯一事实权威、身份与授权分离、能力匹配和按客户维护精确组合，适合本项目的长期目标。保留这些原则不要求保留旧代码、旧组件划分或旧 SDK 的求值算法。

目前不能宣布全部底层逻辑已确定。主要缺口是授权与提交的时间边界、历史转层协议、增量事件处理、跨组件预占／取消、期间关闭及恢复后的外部事实核对。它们会影响正确性，不能只留一句“实现时验证”。应先确定具体协议与反例，再用实现证明它。

本次[面向最终目标的文档审查](work/rounds/06-final-goal-document-audit.md)进一步定位作业认领后的恢复、List／Can 谓词适用域、审计保存回执与传输清理、局部投影完整修复四个文字规则反例，并补客户导入／期初、引用生命周期及扩展字段的规格缺口。反例的纯状态模型已运行，尚无 SDK／数据库运行证明；具体规则应在对应协议收敛，不在本页复制新算法。

选择依据是业务正确性、独立选配／替换价值、团队和 AI 的维护负担、整套部署成本及可演进性。旧方案的作者或模型代际不作为证据；新方案同样需要反例与验证。

## 推荐组合与改选条件

| 方面 | 当前推荐 | 有意义的其他方案与改选条件 |
| --- | --- | --- |
| 组件边界 | 按独立业务变化与数据权威划分；强不变量留在本地一致性边界 | 两块总是共同变化、需共同提交且无独立选配价值时合并；已有独立成本等用户决定保持，先证明协调 |
| 在线数据库 | PostgreSQL；小型部署共实例、每组件独立 schema 和访问身份 | 需要故障／安全隔离或某组件成为热点时独立数据库／实例；跨方言按客户要求专项，不做所有数据库通用的薄弱抽象 |
| 权限 | 完整授予 + 有限、可验证的条件／查询表达；标准 Authz 本地执行与严格路径复核 | 复杂关系比较 OpenFGA 等；复杂策略比较策略引擎。选型要证明列表、字段、管理与新鲜度，不能只比较 Check |
| 冷热数据 | 热数据和仍常查的历史保留关系型路径；封存历史使用 Parquet + 版本清单 | 在线恢复／争用超预算时增加独立历史库；多引擎并发维护、频繁文件改写时评估 Iceberg，重分析另选分析引擎 |
| 本地事务 | 短事务、数据库约束／条件更新／固定锁序；复杂集合不变量用明确串行化点或 SERIALIZABLE | 不用全局提高隔离级别替代规则设计，也不禁止有依据的局部 SERIALIZABLE |
| 跨组件事务 | 业务属主持久协调；库存／信用用可查询的预占协议；可补偿流程明确中间状态 | 真正必须同时提交且不能容忍中间状态时重划边界；复杂长流程再选执行引擎，不以外壳提供共同事务 |
| 消息 | 业务提交与 Outbox 同事务；可靠运输 + 本地 Inbox／业务唯一性 + 重建／对账 | JetStream 默认与 PG 队列第二适配器方向承接；按各自能力、故障范围和成本验收，不新增通用 bus 组件 |
| 部署 | 单跑、外壳、混合均保留；低负载兼容成员外壳优先候选 | 需要独立扩容、频繁发版、重处理或安全隔离时拆出；Docker／Podman 的默认按整套实测决定 |
| 交付 | 有限稳定维护线、精确客户组合、允许维护窗口，团队维护 Fork | 连续升级、共享 SaaS、跨地域主动写入和任意旧版永久支持均另有成本与专项设计 |

这些是有前提的推荐，不是为每个客户给出同一套基础设施。小客户不必预装历史库、湖仓、分析集群或工作流服务器；大客户也不因为规模大就把每个组件单独部署。

## 身份、授权与信任边界

完整授予、有限查询／管理上限、授权接受节点和内部服务认证的具体推荐统一在[权限执行规范](02-security-and-permissions.md#全局复审后的执行推荐)，不在本页维护第二套求值规则。优先证明列表／详情／字段一致、撤销与接受竞争、新内容／旧关系、伪造服务身份和权限迁移。

一个客户一套私有部署继续承接，法人是内部业务维度；即使共宿主或复用客户资源，部署受众、凭据、对象空间和备份仍需隔离，预留 token 字段不证明共享 SaaS 已支持。外壳是共同进程信任域，角色切换防串扰；高保护对象按所需信任边界选择独立进程／凭据。

迁移属主密钥在服务容器可见的已接受限制保留，不再次提出 BrickKit 专用密钥需求。普通授权与当前业务强约束分开，精简部署和替换不降低必需保证。

## 工程、性能与运行保障

协议只定义共同外部语义，SDK 实现共同机制，组件实现业务资格与状态。SDK 不应成为通用 ERP 规则引擎，也不应把供应商任意策略翻译逻辑散入每个业务仓库。三语言保留共同向量与差分验收，不要求内部代码结构相同。

契约新增字段、枚举或新事件不自动意味着兼容。要验证未知字段／枚举、缺省、错误、权限语义、新旧消费者和客户 Fork；改变授权或完成语义需要明确兼容版本。数据库已存在会话只是版本观察信号，不能证明离线作业、旧客户端及稍后启动的旧版本已退出；破坏性迁移需部署准入与版本栅栏。

搜索、BFF、报表、打印、附件、通知各自保持权限与事实边界。用户聚合请求有扇出／批量预算；打印不取全权业务数据，渲染模板、文件处理和回调输入需受控；通知内容按接收者和渠道允许范围形成，扫描／回调成功不自行放行业务。具体协议回到所属专篇。

所有预算合并计算：前台、消息、作业、导出、冷读及外壳成员共用数据库／CPU／内存时，要有并发上限、队列上限和保留的服务能力。连接名额不是 CPU 或磁盘隔离；需要固定保留名额或加权调度才能证明其他成员不会被耗尽。仅成员上限相加不能保证公平。

明确“本地提交成功”的故障模型、数据库刷盘／复制条件及容许数据损失。单机、多副本、异步复制及备份分别承担不同故障；多个容器共用同一宿主／磁盘不构成独立故障域。支持版本、修复、凭据轮换、持久审计、告警和恢复演练进入客户组合，数值按已定通用 ERP 画像测量。

## 可以定下什么，哪些还不能定

可以作为冻结候选：唯一事实权威、组件与进程分离、同事务写 Outbox／审计意图、完整授予、必需能力缺失拒绝、未知结果不伪称失败、当前授权覆盖所有数据出口、先验证再删除、正式数据升级保留。

仍须完成理论规格：授权时间保证、有限表达和管理上限、各代表业务协调状态机、归档目录／序列化／路由、重放与去重寿命、关账屏障及一致性恢复。规范、状态、反例和明确不可支持的条件都写清之后，才能称底层逻辑已形成可冻结基线。

必须由实现确认：SQL／SDK／provider 等价、真实并发与崩溃恢复、各存储和运输适配能力、外壳停止／争用、升级恢复、容量与延迟。后续新业务或客户约束仍可推动修订，理论审查不承诺架构永久无需改变。

首批具体反例集中在[数据与一致性矩阵](validation/data-and-consistency-matrix.md)。先收敛权限／消息／预占／归档的少量高风险协议，再构建带真实身份、跨组件写和恢复的代表链路；保留已定先行部署实验与全量升级的顺序。
