# 设计迭代、开发顺序与货架扩展路线

> 状态：基于新目标的待审路线。旧执行记录保留为事实，未来任务顺序可重新编排。

设计与实施任务都要落实到[具体组件、仓库与替换关系](components/selection-map.md)，仓库事实看[货架](components/catalog.md)，方案比较看[选型专篇](replacements/README.md)。授权的静态／关系图计划与长期策略引擎评估在[权限选型](replacements/authorization.md)分别标明；出现候选名称不自动进入近期开发或发版清单。

## 三条范围线

1. **长期产品蓝图**：原始完整货架和后续新能力；包含边界、扩展点、依赖与可选组合。
2. **底层设计冻结**：本次把所有适用底层方面、项目规范和验收要求审清楚。
3. **近期实施与证明**：现有组件／SDK／工具升级，以及证明部署和代表性替换所需的工作。

未来功能参与设计，不全部进入近期实施。若已有组件需拆分、合并或删除，先说明对当前业务闭环、契约、注册身份、数据和 Fork 的影响，再更新实施计划。

## 审查轮次

| 轮次 | 主要问题 | 出口 |
| --- | --- | --- |
| 0 基线 | 用户要求、原始全景、已定／已做／未验证和缺前提 | 可继续的任务章程、目录、清单和交接 |
| 1 组件与组合 | 全量货架怎样划；客户最小组合怎样成立 | 上下文图、边界卡、依赖／事件图和组合候选 |
| 2 权限与替换 | 统一安全语义与方案迁移怎样成立 | 权限矩阵、契约能力、迁移与替换验收 |
| 3 数据与一致性 | 事务、MQ、冷热、时间金额和恢复 | 不变量、状态机、失败时序和关键实验清单 |
| 4 部署与性能 | 外壳、混合、多副本与客户成本 | 测试矩阵、资源预算、可配置约束和测量计划 |
| 5 交叉复核 | 规范、客户资料、开发接口和证据是否一致 | 闭环问题、保留限制、冻结候选与独立复核 |

发现高风险问题时回到对应议题，修正所有受影响项。轮数是组织方式，不是完成条件。每轮记录问题与证据的增量；新增项过多时整体重读并重构相关内容。

跨会话的任务顺序见[接续清单](work/04-next-steps.md)，各设计文档的状态与待补的设计见[设计地图](work/03-design-map.md)。它们是设计推进入口，不替代本页的冻结与正式切换条件，也不授权开始开发。

全局复审将可冻结原则、推荐及剩余协议集中在[底层基线](09-foundation-baseline.md)。下一增量先收敛内部认证、完整授予／接受节点、事件模式与去重、代表订单预占、归档目录及期间屏障，不再只追加待验证事项。业务组合、负载、资源和容许延迟分别设计，默认以小公司规模开发；没有统一终局数字不阻止定义配置、专项组件、监控和部署扩展路线，不再重复询问规模，也不允许虚构容量。

## 开发的前提与顺序

按 D59，现有代码（阶段 06 的组件、SDK、工具与外壳）只作参考和教训，不作为设计边界或迁移对象；终局设计视为第一个正式版本。开发分五步，顺序不变：

1. **设计写到可冻结**（D56）：本工作区的设计地图全部到达“可冻结”，用户确认后迁入正式文档。
2. **代表部署实验**（D41）：按新设计开发实验所需的少量代表组件、SDK 与外壳，比较外壳与独立进程、Docker 与 Podman、连接池代理与仅 PG 等关键选择，据结果修订设计。
3. **重建当前范围**：按新设计重建当前阶段约 20 个组件所覆盖的业务范围（组件数量可能因边界调整略有增减），连同 SDK、外壳与工具。
4. **全部部署模式的测试与开销测量**：用这 20 多个组件跑完整部署矩阵（单跑、外壳、混合、多副本 × Docker、Podman、Kubernetes）与完整性能基线，测量整套开销，作为向客户和 BrickKit 证明这些部署模式真实可用的依据（任务简报中用户原话的目的）。
5. **扩展货架**：之后按客户需求与替换验证的需要分批开发其余组件，覆盖代表性业务和替换组合，而不是以当前组件数量限定设计。

各处文档中“重建当前范围”“部署矩阵”即指第 3、4 步。新关注点进入设计地图；需要改变顺序时用明确的验证目标和成本说明裁定。

部署组合按实测定案，组件独立开发与验证，外壳优先仅为候选取向。代表性实验比较少组件与较完整组合、单跑／外壳／混合、Docker 与 Podman，同时衡量资源与物理独立性代价；实验规格见[代表性部署对照实验](07-validation.md#代表性部署对照实验)。

身份方案先沿 Casdoor、Keycloak 和通用 OIDC／目录适配路线设计与验证；精简本地 IAM 保留评估项，不进入已承诺开发清单。最低部署实测不能满足或客户需求明确时，再提出方案、安全验收与实施范围；先行资源实验仍需单独安排。

## 中文稿与正式文档的切换

1. 完成中文内容、客户路线、开发路线、图和全部决定的复核。
2. 建旧内容承接表：每项仍有效的语义都指向新正文；无效项记录被什么替代。
3. 提取工作记录仍承载的有效结论到正文，清除正文对工作记录、旧文档、归档和本机知识库路径的依赖。
4. 审核冻结报告和新实施计划；经过用户确认后执行切换。
5. 归档旧 `docs`，以冻结中文稿构建英文和中文镜像；核对语义、图、标题、链接和生成物。
6. 更新根入口、组件说明、工具检查与实际命令；现行内容对旧路径和归档的引用清零。
7. 原始设计来源与过程保留在归档／Git，面向客户和开发的文档可独立使用。

中文设计期间，旧 `docs` 仍描述当前运行规则；`tempDocs` 标明新建议与已定目标。最终切换前先迁移需要保留的内容，避免先归档再发现新稿缺信息。

## 问题反馈与项目完成后的整体总结

2026-10-13 用户要求：真实发现问题才向 BrickKit 或知识库反馈；项目任务完成后再整理整个项目的成果。现在记录条件与材料要求，不提前提交成功案例，也不为反馈数量寻找问题。

具体错误、实质覆盖缺口和可定位的说明矛盾，核对版本、上下文及已有反馈后及时提交，说明反例与证据边界。业务选择不同、尚未完成自己的协议或尚未证明平台不支持，不直接记成对方问题。知识库反馈经独立贡献分支／PR，由维护方审查；平台反馈遵循其贡献方式。阶段成果与最终完成分开记录。

整体总结在用户确认的任务范围完成、关键协议与实现一致、声明支持的组合及必要恢复／升级验收完成后准备。长期货架未实现部分继续保留计划状态，不将若干代表组合通过扩写成所有组合通过；如仅阶段任务完成，报告标题与结论明确该阶段。

| 材料 | 最少保存的证据 | 对应价值 |
| --- | --- | --- |
| 项目背景与范围 | 目标、约束、所选能力、版本／commit、实施范围与未完成蓝图 | 读者知道成果适用在哪些客户和条件 |
| 组件与替换 | 独立业务闭环、真实替换／多选／范围路由、迁移步骤与改动成本 | 向 BrickKit 汇报组件装配及部署理念如何在业务中成立 |
| 部署与资源 | 同版同负载的单跑／外壳／混合、引擎和观测档位，整套资源与延迟、故障影响 | 证明收益及代价，不只展示进程数减少 |
| 正确性与恢复 | 权限允许／拒绝、跨组件事实、并发／崩溃、升级及恢复结果、已知限制 | 证明业务保证，而非仅健康或生成物正确 |
| AI 开发与维护 | 契约／SDK／组件的变更过程、实际修复、Fork 适配及可重现检查；效率数据有基准才比较 | 给知识库提供有证据的工程经验，不以模型名称证明优势 |
| 问题与经验 | 曾失败的路径、反馈及处理状态、独特选择的理由、尚未验证项 | 提供可复用判断，项目事实与通用推荐分开 |

材料随实施保存版本和可重现入口，任务完成后组织为一份项目整体总结，再按受众整理 BrickKit 使用／验证报告和知识库项目案例；两份使用同一证据来源，不复制整套项目文档。外发前核对可分享范围，移除秘密与客户私有资料；知识库案例通过 PR 提交，不自动合并。届时按任务范围、材料完整度与用户要求确定提交内容和时点，不现在宣称已经成功。
