# 数据归属、共享语义与生命周期

> 状态：已定数据归属与 2026-10-13 冷热／恢复推荐方案；具体协议尚未冻结。产品和运行容量仍须验证，旧实现不作为设计约束。

本页定义数据权威和生命周期。具体更换对象在[数据与存储组件定位](replacements/data-and-storage.md#选择对象与组件仓库)和[附件组件定位](replacements/files-and-attachments.md#选择对象与组件仓库)：PostgreSQL／RustFS 是基础资源，存储与冷查询适配在 SDK，`infra/attachment` 是附件业务候选。三者的替换责任不同，不能一概称为换数据库或换附件组件。

## 数据归属

每类业务事实只有明确的写入者。其他组件通过契约读取、订阅事件或维护声明过的投影。关联表、迁移状态、平台表、对象存储桶和搜索索引也要有属主、凭据、权限、生命周期和恢复责任。

存货成本子账已定归独立成本组件，引用库存数量及必要价格／费用等事实，保留计价依据、暂估与调整关联；财务总账按成本事实过账。成本调整不直接改写库存数量历史，来源与处理范围要支持完整性核对、重算和恢复，详见[存货计价的功能分工](replacements/finance-and-settlement.md#存货计价的功能分工)。具体模型、存储和迁移未实施。

客户与供应商共享统一业务伙伴基础身份，角色资料、权限和业务状态分别管理；应收应付与信用政策保留各自业务权威。伙伴由 `mdm/partner` 承接，角色按法人开通（[主数据卡](components/mdm.md#mdmpartner)）；按 D59 不承担旧身份的迁移兼容。归属见[业务伙伴与角色](01-component-boundaries.md#业务伙伴与角色)。

正式联络基础资料由伙伴主数据维护；CRM 和采购的私有业务关系留在各自能力，不能借共享联络资料向其他上下文泄露。历史快照见[协议 07](protocols/07-references.md)，联系人关联的失效随伙伴的详细模型设计；分类见[正式联络资料与业务私有关系](01-component-boundaries.md#正式联络资料与业务私有关系)。

核心字段语义在建表前明确：主键与人读单号、时间与业务日期、法人、金额与币种、数量与单位、并发版本、自定义字段、权限范围。每种语言与客户 Fork 必须保留相同的外部语义。

标准财务每法人一个正式会计账簿，其他报告口径采用受控调整与报表；多法人、多币种方向保留。调整与正式账务事实的来源、权限、版本及差异要能核对，完整多账簿由专项财务实现或 Fork 承担，见[每法人单账簿的标准范围](replacements/finance-and-settlement.md#每法人单账簿的标准范围)。具体数据模型未实施。

审批中的关键修改采用新修订与重新审批，旧版本及审批依据保留；其存储和生命周期要支持审计及执行前复核，不能只保留最后一版可编辑记录。行为与边界见[审批依据与修订](02-security-and-permissions.md#审批依据与修订)。

## 重复主数据的确认与合并

系统查重、提示疑似重复和字段冲突；标准版正式合并默认由有权限的人确认。大批量可以先审核合并计划再批量执行，查重分数或联络信息相同不能直接改变主体身份。

保留原身份映射、来源和变更记录。未经确认不改变角色、业务引用或权限关系；合并不自动扩大权限，也不改写历史单据快照和已执行事实。审核与实际执行之间资料可能变化，需要复核；合并的执行、别名、拆回与引用方的处理见[协议 07](protocols/07-references.md#合并与别名)，冲突的细则随伙伴的详细模型设计。

误合并的拆回要检查后续业务与关联，不能承诺随时一键回退。合并后的别名解析、历史引用不改写、在途引用的处理、资格引用与悬空引用的修复见[协议 07：跨组件引用的生命周期](protocols/07-references.md)。幂等请求去重和按明确 ID 更新同一记录不属于此处的合并；平台级导入仍按原路线后续设计。

## 发生时归属与当前责任

业务对象分别表达发生时的组织归属和当前负责归属。历史业绩默认保留发生口径；正在处理的单据通过明确交接调整当前责任。人员调岗不自动搬走其全部旧单据，交接也不改变原交易法人或账务事实。

需要按现组织重算的管理报表另设清晰口径，不能静默覆盖历史归属。必要的历史更正通过有记录的业务过程处理。各实体何时确定发生归属、哪些信息需要快照、哪些对象允许交接，按业务逐项设计。

读取与操作仍按调用者当前有效授权判断，发生时归属不是永久访问权。投影、搜索、报表和冷数据须保留各自判定所需的归属信息；仍允许交接的对象要定义如何变更当前责任而不改写历史事实；数据集同时保存发生时与当前组织（[协议 13](protocols/13-search-reports-and-datasets.md#数据集)），各对象的交接动作随组件设计。

## 数据库选择与更换

数据库的使用规则（结构、角色、事务、超时、连接池）以及身份、单号、时间、金额、游标与迁移的共同规则，见[协议 14：数据基础](protocols/14-data-foundations.md)。

协议兼容发行版、不同 SQL 方言、分析引擎和冷存储是不同替换点。更换 PostgreSQL 部署，不证明任意数据库可换；SQL、驱动、迁移、锁、角色、分区、精度和恢复均需检查。详见[数据与存储选择](replacements/data-and-storage.md)。

连接池、事务超时、隔离级别、重试、语句缓存和属主／运行角色要在单跑和外壳下分别验证。一个数据库实例容纳多个 schema 不意味着允许任意跨组件 SQL 或共享事务。

推荐 PostgreSQL 作为在线 OLTP 标准：短事务、约束、条件更新、JSON 扩展及各组件明确 SQL，避免为任意数据库制造最低能力交集。共实例／每组件独立 schema 是小型组合；需要隔离或某组件形成热点时，可保留相同职责迁到独立数据库／实例。外壳能否共享池取决于相同数据库、凭据和成员预算，不应成为禁止独立数据部署的终局理由。

跨方言是一条有迁移和验收成本的专项路线，不把线协议兼容当作隔离、DDL、锁和恢复兼容。分片也不能仅按 schema 证明热点已解决：一整个库存 schema 落在一个节点时，该组件内部热点仍然存在。先查查询／索引、争用和恢复预算，再决定只读副本、历史分离、组件数据分离或组件内部的分片键。

只读副本用于容许明确延迟的读取负载，不替代历史分离或备份。库存可用、额度资格与提交不变量仍由写权威判断；写后立即读取需要响应中的状态、回到权威或验证副本水位。副本中的对象授权属性也不能比该路径允许的新鲜度更旧。

这些是本轮推荐，正式规则切换前仍执行当前运行约定。数据库共享只适用于约定的可信组件；外壳角色可切换多个成员身份，不能当作受侵代码之间的安全墙。

### 在线数据库怎样分离

实例指一套 PostgreSQL 服务及其数据目录；一个实例可含多个数据库，一个数据库可含多个 schema。这里的分离是改变数据的物理放置与连接目标，业务权威、接口和本地事务责任仍归原组件。

| 形态 | 适用目的 | 仍共享的边界／代价 |
| --- | --- | --- |
| 共实例、共数据库、每组件独立 schema | 小到中型基础组合，集中维护与连接预算 | CPU、内存、磁盘、WAL、实例故障及物理恢复；schema 分工不提供机器隔离 |
| 共实例、每组件独立数据库 | 分开数据库访问与部分管理，满足明确交付条件 | 仍共享实例资源、WAL 与实例级故障／物理恢复；每个连接只指向一个数据库，不能因此承诺独立容量 |
| 同宿主、独立实例 | 分别设置版本、连接及资源上限，分别重启 | 宿主和底层磁盘故障仍相关，需额外备份／恢复与调度；限制资源不等于增加硬件 |
| 不同宿主、独立实例 | 独立配置容量，按真实故障域改善隔离 | 更多网络、运维与恢复责任；仍需核对共享存储／供电等，换机器不自动证明 HA |

例如销售、库存、财务起初共实例；库存写负载成为独立瓶颈后，迁到另一实例。只读副本、历史库、分析库和组件在线库分离分别解决读取、历史积累、重分析及在线隔离问题，不能将任一“多一个库”都称为扩容成功。层级依据：[PostgreSQL 数据库管理概述](https://www.postgresql.org/docs/18/manage-ag-overview.html)；具体恢复范围依备份类型及[恢复协议](#标准灾难恢复范围)。

迁移需清点业务表、平台状态、身份／角色、权限投影、迁移历史、Outbox／Inbox、作业／幂等和对象引用；固定源版本与写入切点，复制并校验，切换连接／部署，验证真实业务与恢复，最后退出旧写路径。标准可用已定维护窗口，在线迁移另验增量追赶、旧写者隔离和切点；目标写入后不能仅改回旧地址撤销新事实，按[共同切换协议](replacements/README.md#选配变更与替换的共同协议)处理。

外壳的共享池按数据库目标划分：同一目标的成员共享一个池，不同目标各用一个池（协议 14 的连接池规则）。多数据库或实例的组合仍待实测：可以将对应组件先单跑，也可以设计按目标分池的外壳并验证身份与总预算；不声称现有外壳只改地址已支持。迁移不引入跨组件 SQL 或把多库提交伪装成本地 ACID。

扩展字段（客户在可扩展实体上增加的字段）的定义、按字段 ID 存储、演进规则、边界与各出口的承接，见[协议 08：扩展字段](protocols/08-extension-fields.md)。

## 冷热分层设计

推荐区分在线业务、可交互历史、封存历史与分析副本。冷热是访问和维护方式的差异，不要求从第一天安装两套数据库。按访问、修改、恢复和成本目标制定类别，而非统一设置“几个月后变冷”。持续修改的主数据、未完成单据、待重试消息、业务余额及长期去重证据不能只凭年龄搬走。

| 类别 | 设计重点 |
| --- | --- |
| 在线可变数据 | 完整权限、写入一致性、索引与延迟预算 |
| 已完成历史 | 终态判定、迟到更正、期间锁与关联完整性 |
| 冷归档 | 格式／清单版本、校验、搬运恢复、重复执行与副本完整性 |
| 分析投影 | 新鲜度、权限重评、重建、原始来源与恢复 |
| 清理／销毁 | 数据类别的最短／最长保留、保全、个人信息、审计证明 |

没有明确法规或客户合同的保留年限标为待确认。会计资料与个人信息可能有不同约束，需要分别处理。

### 存储路线与选配条件

| 路线 | 推荐用途 | 收益、代价与升级信号 |
| --- | --- | --- |
| 同一 PostgreSQL 的表／分区 | 在线可变数据、仍常查的业务历史；小型客户最低路线 | 不增加查询服务，关系、定位与权限集中；历史仍占主库存储、备份和恢复预算 |
| 独立 PostgreSQL 历史库／实例 | 历史需频繁详情、关联、分页，主库恢复或争用超预算 | 继续关系型读取；增加路由、版本与恢复责任。属主仍是原组件，不给其他组件任意 SQL 权限 |
| 对象存储 Parquet + 版本清单 | 真正封存、偶发查询的历史与可核对数据包 | 开放格式和压缩，在线主库可减负；要维护查询、校验、清单、擦除及恢复，不能当作第二个在线事务库 |
| Iceberg 等表格式 | 冷数据需多引擎并发维护、频繁更正／删除及结构演进 | 有快照和元数据协议，增加目录与维护成本；不作为所有小客户必装项 |
| 独立分析引擎 | 重聚合、探索或数据集扫描影响交易预算 | 隔离分析负载；投影、口径与新鲜度独立验收，不接替历史事实与正式账簿 |

优先设计按业务属主路由的能力端口，冷读执行位置按资源预算选择。嵌入读取适合受限扫描，重读可由受控工作者承担；DuckDB 等作为读取适配候选评估，不能接收用户任意 SQL／对象 URL 或读全桶。具体引擎、仓库、语言依赖和部署尚未选定。产品依据：[DuckDB Parquet 读取](https://duckdb.org/docs/stable/data/parquet/overview)、[Iceberg 快照与提交规范](https://iceberg.apache.org/spec/)。它们提供技术能力，不提供本项目业务权限。

### 分区、归档单元与唯一性

分区用于增长、查询和维护，归档单元用于业务完整性，两者不必相同。一个月份中有长期未完订单时，不能因多数记录终态就整月删除；可继续保留整块，或采用明确的终态聚合搬运并维护位置目录。订单及其明细、关联事实必须一起可解释，但不要求把不同权威组件的所有表合成一次搬运事务。

推荐大规模追加流水和明确按时间增长的表在模型阶段确定不可变切分键；小型有界主数据和活跃余额不机械按月分区。月／周粒度按数据及管理开销选择，业务日期不等于技术创建时间，UUIDv7 时间只在声明了对应关系时可帮助定位。导入旧记录、父子不同 ID 时间、财务按期间分区，都不能仅凭 ID 时间推导冷文件位置。

PostgreSQL 原生分区表的唯一／主键约束必须包含分区键；`(id, created_at)` 不单独保证 id 跨所有分区唯一。业务单号、外部事实 ID、幂等或对象位置需要分别选择非分区身份／唯一登记、可证明固定的键映射，或明确的复合身份，登记与业务修改同事务。不把随机 ID 的低碰撞概率当作所有业务唯一规则的数据库保证。[官方分区限制](https://www.postgresql.org/docs/current/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS)

未来分区提前创建，边界完整、不重叠；异常边界不能仅跳过告警后称维护成功。DDL 有自己的权限、锁预算与崩溃恢复，不进入普通请求热路径。并发摘分区仍有锁和适用限制，必须核对目标版本及引用关系，不承诺“CONCURRENTLY 就不会阻塞”。

## 生命周期状态与跨层查询

本节的阶段表与查询原则已落成协议：单元目录、封存与写屏障、代次发布、读取租约、保全与销毁、跨层读取，见[协议 11：冷热转层](protocols/11-tiering.md)。

推荐把每个归档单元、数据版本和处理进度保存在原属主的目录中。物理搬运与法律保全／处理限制分别建模，不用一串状态码涵盖所有正交条件。

| 阶段 | 前置条件与提交证据 | 失败／竞争处理 |
| --- | --- | --- |
| 选择与封存 | 确认所选聚合终态、来源处理完整、无未交接任务；与写入路径共享封存状态／版本裁决 | 写入先赢则重新选择，封存先赢则迟到写转明确更正；所有写入口都检查，不能只让归档任务互斥 |
| 复制 | 封存版本的稳定集合、不可变对象 key／版本、导出任务身份与进度 | 网络操作在 DB 事务外进行；重试不能覆盖已发布内容，失效工作者不能发布新目录 |
| 校验 | 行数、主／子完整性、类型／内容摘要、完整读回、索引／定位及权限所需属性 | 任一差异保留源，不以行数相同代替内容一致 |
| 发布读路由 | 在本地事务内校验源版本与任务代次，原子发布清单版本及范围 | 只有已验证清单可成为权威路径；新旧副本共存时目录决定选哪份，不能双计 |
| 宽限与退出在线层 | 查询支持已满足，备份／恢复窗口明确，正在使用旧路径的读取已结束或可重试 | 宽限期加读取租约／快照引用管理；摘分区／清理中断可以从目录继续，不留下静默缺口 |
| 删除源或销毁 | 转层删除源有验证副本；最终销毁另验保留到期、当前保全／审批、关联与所有副本 | 保全与删除通过共同控制点决定先后；备份恢复重放销毁／限制记录；不能仅靠昨天检查结果删除 |

“先复制再删”还不够：复制后发生写入、发布后旧读仍在进行、销毁前新增保全，都需要明确裁决。单元锁／租约只保护协作中的工作者；执行提交还要验证代次或 fencing token，租约过期的旧工作者不能继续改目录。文件清理只删除目录证明无人引用且已过恢复窗口的对象。

### 内容摘要、历史更正与结构演进

摘要输入使用版本化、无歧义的类型编码，显式区分 null、空字符串、普通文本及分隔字符，固定十进制、时间／时区、二进制、列顺序和记录顺序。不能直接用数据库 text 输出加未转义分隔符：不同内容可能生成相同字节。格式及摘要版本进入清单，使用跨语言独立向量验证。

摘要／链可用于内容一致性和有可信锚点时的变更检测，不能凭同库一条可重算的链承诺防恶意篡改；需声明锚点、签名／保存身份和威胁边界。保留策略校验最短、最长及保全条件，延长也不能绕过明确的最长限制，不照搬全系统永久记录的默认。

封存后的更正以受控新版本／调整事实及关联表达；事实保留原内容，当前责任和合法擦除有可维护的受控元数据。不可变文件遇到允许的字段擦除时生成新文件／清单，并按保全与恢复规则清理旧版本。稳定的替代标识只是去标识化／假名化手段，不自动证明匿名化；法律资格按真实数据、映射与目标地区核对。

解冻默认恢复受限读取，不自动重开原业务写入。旧结构读入新版本需要明确转换、原始摘要核对和转换后结果校验；丢列／填默认值后不能再要求与原结构摘要直接相同。事件、数据集、导出和备份各有副本清单，不能只清理在线表就记录全系统擦除完成。

查询要定义按 ID、按条件列表、跨层排序分页、报表、导出和解冻的行为。冷查询可以更慢或异步，但必须显式告诉调用者；不能静默返回不完整数据。是否允许再次修改冷单据由业务规则决定。

游标绑定筛选、稳定排序键、目录／数据版本和计划摘要（安全 07）；冷／热重叠范围由权威目录去重。目录变化时保留可用快照或明确要求重试，不让游标跳到另一套集合。跨层总计、混合排序及导出必须覆盖声明的完整范围，能力不足时返回明确不可完成状态。

业务内容快照与当前授权分开：撤权／当前责任变更不能因为游标绑定旧快照而永久保留访问。长查询／文件领取按声明节点重验，授权变化后选择安全中止／重新生成，不要求继续旧分页仍绝对完整。默认在线窗口和显式历史／冷热查询分别向用户说明，普通列表不得悄悄漏掉请求范围里的冷单据。

列表的默认读取范围不能只按创建时间截断。ERP 有大量很早创建、至今未关闭的单据（未收款发票、未完成采购、长期挂账），按“最近 N 天”默认读取会让“全部未收款发票”这类常用列表静默漏掉旧单据。默认范围定为“未关闭，或最近 N 天内创建”，与“关闭后才封存”的分层一致；现行 `09-data-lifecycle` 中“不带范围的列表只读 hot 窗口”的规则需在正式迁移时同步修订。（2026-10-13 盲审对照 K7 补充。）

恢复目录、定位索引、清单版本和真实对象要共同核对。目录标 cold 但对象缺失时是故障，不能回答记录不存在；对象存在但目录未发布时是待恢复副本，不能未经验证直接开放。

## 标准灾难恢复范围

本节的方向已落成协议：恢复组、独立证据存储、按消费者进度补发、恢复流程与演练，见[协议 15：备份、恢复与一致性恢复](protocols/15-backup-and-recovery.md)。

标准优先设计并验证客户整套部署的一致性恢复，覆盖业务数据、对象及冷数据引用、消息／作业、配置与权限等必要状态。选择性组件历史恢复按场景专项设计；普通纠错和可重建投影仍可以采用验证过的局部修复，不要求所有故障整套回滚。

组件能独立部署不证明任意时间点单独回退已受支持。数据库或 schema 恢复成功，也不证明订单、库存、财务和消息之间已对齐。备份清单、恢复点／恢复组、存储版本、状态校验、对账补齐和恢复服务条件需一起设计。

发货、付款等外部事实不会随备份回退，恢复后必须核对，不能盲目重放副作用。恢复旧权限不能忽略之后的撤销记录和安全事件。各状态的恢复责任与流程见[协议 15](protocols/15-backup-and-recovery.md)；具体工具、恢复目标和资源成本仍待验证，不凭有备份文件宣称可恢复。

推荐恢复流程先进入维护与执行冻结，恢复数据库及对应对象／清单版本，核对运输保留、Inbox／业务去重和所有未决作业，再通过权威外部结果查验、业务对账及后续撤权／销毁记录重放形成可用状态。数据库恢复点与 broker 进度不保证原子：旧 DB 配已向前的 consumer ack 可能缺事实，旧去重配未清消息又可能重复；两种情况分别恢复，不能直接启动消费者盲跑。

安全变更、销毁控制与外部执行证据需存放在声明的独立恢复责任中，不能在同一次旧备份回退中全部丢失后仍声称已核对。无法找到必要证据时暂停受影响动作、明确数据损失／人工核对范围，再决定恢复服务。可重建副本先清楚地重建；真实账簿和外部事实不能用当前列表假造完整历史。

## 成长路线与验收

业务组件不再启用时，历史数据与关联对象仍需明确属主、查询、权限和保全／恢复责任；不能只保留库文件而没有可用查阅路径。标准保留原组件受限查阅，完全卸载走专项历史迁移；方向与验收见[业务组件停用与退出](replacements/component-lifecycle.md)，具体数据与退出协议未实施。

报表和分析的交付方式、数据供给、指标口径、权限适配与资源验证见[报表与分析选型](replacements/analytics-and-reporting.md)。标准版内置基础报表和看板，自助 BI 按需选配；具体数据集、时效等级与存储未定，不能把分析工具接入成功当作数据完整或授权正确。

设计当前级别和以后增加分区、归档、冷查询、分析库的触发条件。小客户可选择较简运行形态，契约预留升级路线；未来冷层不要求全部在本轮实现。

验收包含分区窗口、旧数据与在途任务升级、备份恢复、关联数据、跨层权限、搬运故障、重复执行和查询结果完整性。容量、恢复时间和查询预算作为带环境条件的测量，不从文档默认值推导保证。

具体设计反例见[数据与一致性矩阵](validation/data-and-consistency-matrix.md)。本页选型与状态机制的协议见协议 11、14、15；每类实际数据仍需在组件设计时绑定声明、API、SDK／存储版本和保护预算。
