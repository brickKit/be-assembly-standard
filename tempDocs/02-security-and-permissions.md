# 权限、身份与安全边界

> 状态：用户优先级已定；统一语义与具体实现需要逐轮审查。

## 权限方案选择与替换入口

本页定义所有授权实现必须保持的安全语义；客户要看权限类型、具体组件／仓库、优劣势、部署及切换，进入[授权模型与组件选型](replacements/authorization.md)。当前 `infra/authz` 已有，`infra/authz-static`、`infra/authz-openfga` 为计划替代成员；属性／策略引擎适配与嵌入库等是进一步评估方向，正式身份与开发范围未确定。

角色、范围、属性条件、字段、共享与关系可以在一个成员内组合。客户按已启用业务所需能力选择实现，模型名称不等同于互斥组件；IAM、组织、任职与 Authz 的职责和候选分图见[身份授权与组织分图](components/selection-map.md#身份授权与组织分图)。完整授予、管理边界和撤销等保证不因换模型或精简部署而降低。

## 目标和分工

认证证明调用者是谁；授权决定他能做什么、看哪些对象与字段；组织和任职提供业务事实；业务组件拥有对象与业务约束；审计记录决策和操作。认证产品与授权产品分别选择，不能把登录产品的名称当作全部权限能力。

初期所有组件由项目维护，允许受控的配置、适配代码和工具修改，使方案能够方便替换。需要明确适配落点，避免每个业务组件重复翻译同一套 provider 语义。

## 必须定义的统一语义

| 方面 | 必须写清的结果 |
| --- | --- |
| 身份 | 平台用户与外部身份映射、服务身份、访问与刷新令牌、撤销与失效 |
| 功能 | 菜单、按钮、接口和命令的权限键；拒绝与公开接口 |
| 数据范围 | 本人、组织、法人、仓库、项目、区域等维度及组合 |
| 对象关系 | 拥有、共享、协作、交接、继承、到期、撤销 |
| 字段与动作 | 脱敏、读写限制、敏感字段过滤／排序、导出与批量动作 |
| 业务控制 | 审批资格、职责分离、金额门槛、期间锁；归属授权或业务规则 |
| 一致性 | 权限变更后何时生效、修订令牌、缓存过期、同步失败行为 |
| 运行身份 | 用户请求、服务调用、后台任务、事件处理分别如何授权 |
| 多层数据 | 主库、投影、搜索、报表、冷数据、文件和缓存的访问边界 |

## 当前已定的授权边界

| 方面 | 已定保证 | 仍需设计 |
| --- | --- | --- |
| 能力与替换 | 共同安全语义一致，扩展能力可分档；缺少已启用功能所需能力时阻止装配或切换 | 最终档位、能力版本、检查落点与迁移 |
| 新鲜度与风险 | 高风险满足更严格的新鲜度，低风险读取可以使用有时效上限的策略；不满足时拒绝或暂缓 | 分类依据、窗口、确认时点与在途行为 |
| 多任职与汇总 | 日常逐份判断有效授权后汇总；关键履职操作选择任职；操作／范围／条件／字段不得错配 | 授予结构、关键操作、主体识别、委托与职责分离 |
| 授权管理 | 同时支持集中与受限分级管理；业务使用权与管理权分别声明，下级只能在明确对象、可授权限及范围／条件上限内操作 | 管理契约、多级结构、角色变更影响、管理资格撤销、授予生命周期与交接 |
| 管理员交接 | 正常卸任不使其合法发出的普通业务授予自动失效，接任者或上级接管；被授予人的任职／有效期／撤销规则继续适用 | 接管流程、来源追踪、复核与批量撤销、安全事件和上限收紧 |
| 普通角色升级 | 标准角色是版本化参考模板；客户实际角色新增权限经授权管理人员确认，不因升级自动扩权，可批量审核 | 模板与实际角色关系、差异、确认协议、退役权限与安全修复 |
| 任职变更与授予 | 旧任职关联授予自动撤销，新授予默认人工确认；其他有效兼任按条件保留，直接授予单独复核 | 绑定、岗位模板、可授予范围、批量计划、撤销传播及离职／停用 |
| 审批与流程 | 允许兼任，启用人工审批时默认防本人自审；可选择明确的无人工审批流程，必需控制保留，在途审核不静默跳过 | 责任主体、适用单据、定义契约、在途迁移与审计 |
| 审批依据与修订 | 审批中允许新修订；审批通过且未执行的普通单据默认原单修订重审，暂停受影响执行；旧记录保留，严格业务可锁定或要求变更单 | 关键字段、重审范围、并发失效、实例衔接、执行前复核与已执行事实更正 |
| 流程版本 | 在途绑定原流程与相关配置版本，新规则默认用于新实例；旧实例变更显式处理，权限与必需控制不冻结 | 旧执行语义、版本窗口、审批人解析、迁移和升级验证 |
| 审批任务交接 | 原处理人失去资格后，未处理任务按绑定职责规则与当前组织／资格寻找合格接任者并转交；无合法替代时暂停转人工 | 解析、事件与映射、失效／新任务切换、人工改派权限及并发恢复 |
| 审批超时 | 普通人工审批默认提醒／升级并继续待处理；申请到期另有业务策略，不伪造人工结论、不延长单据与预占期限 | 时限与日历、提醒／升级路径、状态并发、积压保护与业务到期协调 |
| 对象归属与责任 | 发生时归属与当前责任分开，交接明确变更责任；访问仍按当前有效授权，历史归属不代表永久访问权 | 各权限点使用的归属、交接、组织重组、历史更正与跨层一致性 |
| 审计覆盖 | 按风险与明确动作清单可靠记录必要动作；敏感读取／导出纳入，普通低风险读取保留访问日志 | 动作分类、读取／拒绝保存机制、故障保护、客户扩展、保留与查询 |
| 后台授权 | 用户查询／导出重验当前授权，已达明确业务授权节点的后续由受限服务主体推进；取消／冻结保留 | 分类、授权节点、服务权限与范围、长任务检查和结果领取 |

用户可以先明确调整业务范围，再选择精简方案；不能静默忽略既有权限规则或降低保护。新鲜度不能仅用“有轮询／有缓存”描述，必须有可验证的时间与故障边界。具体数值在设计与测量后确定，不从现有 15 秒轮询推导保证。

授权汇总的单位是一份授予及其全部条件，不是先把功能、范围、条件和字段分别取最宽再组合。列表、详情和字段输出必须保持这一规则；按任职签署的操作要保留可审计的具体工作归属。

承接现行“不提供管理员可配置 Deny”的方向。角色／授予决定能够做什么，业务强约束决定当前单据是否可以执行动作；本人自审、期间锁等不能因另一个允许授予被跳过。两者的执行位置和解释机制要统一设计，不能只靠前端隐藏。

## 全局复审后的执行推荐

> 以下为 2026-10-13 技术推荐，未冻结接口或预算。原已定目标保持，具体模型优先在协议中确定，不能依据旧 SDK 的能力收窄需求。

### 查询和授权管理采用有限表达

推荐标准成员采用有限、带类型的授权表达及共同中间表示，完整授予内的范围／条件保持组合，授予之间只并集合规结果。单对象检查、SQL／冷查询过滤和逐记录字段从同一语义产生；空值、未知属性、部门路径边界、条件与字段上限明确，拒绝无法表达或超预算的查询。

图或策略引擎的结果要通过相同查询／字段契约。可用候选集加权威检查，但不能先分页再删除无权行、截断 ListObjects 后当完整集合，或把超时当作零条。不能满足所选业务完整查询能力时阻止启用，或者选择明示且受控的异步查询。

受限管理员的授予上限要能证明。标准只开放可验证包含关系的范围／条件表达；任意策略语言之间的蕴含关系不能无条件自动判定。无法证明不越界时拒绝或转合格上级确认，角色修改的间接影响同样处理。

### 决策新鲜度与接受节点

普通读取可按已定风险使用有上限的有效本地策略；高风险动作建议在指定业务接受节点获取绑定主体、动作、对象修订、授权版本与期限的决策证据，本地事务核对对象、状态及证据，再进入明确的持久后续处理。

必须规定撤销与接受节点的先后、已合法接受的动作是否继续、旧证据有效上限和不满足时的行为。实时远程检查仍与本地提交有间隙；要求撤销生效后禁止任何未提交动作时，需要受保护接受／撤销屏障协议或边界调整，不能以“再查一次”或短缓存证明。此项是理论冻结前阻塞，不留到实现时猜。

新内容、共享／交接属性、组织／任职与授权版本需要兼容水位。权限是新的而记录负责人投影仍旧，同样可能越权；当前数据截至时间不证明所有变化已完整应用。旧授权读取窗口与严格操作的确认点分别实例化，不承诺所有动作同时零延迟撤销。

### 内部服务也要认证

推荐系统调用验证部署绑定的服务凭据和受众／允许动作，`be-caller`、actor 元数据及内网 gRPC 端口本身不提供认证。用户请求继续走受限用户路径，内部 actor 只记录审计时不能凭其名字授予访问；事件发布身份／允许主题和回调来源也须验证。

此建议调整旧“只凭内部调用名即可识别主体”的假设，具体凭据、轮换、装配与 SDK 契约待设计；不要求先引入 service mesh。多个客户共宿主或复用基础资源时，部署受众、凭据、对象空间与备份必须隔离。

同一外壳是共同进程信任域，schema／角色切换防串扰而非隔离受侵成员。迁移属主密钥可见的既有接受限制保留；需要对恶意代码或更高保护对象隔离时选独立进程和凭据。完整推荐与冻结边界见[底层推荐基线](09-foundation-baseline.md#身份授权与信任边界)。

## 授权管理与生命周期

### 授权管理与授出上限

标准设计同时支持集中管理和受限分级管理，客户按需启用；小客户可继续集中管理。总部指定下级管理员可管理的人员／业务对象、可授权限及范围／条件上限，每个管理动作都在服务端检查该边界。

业务使用权与授予管理权分别声明。能使用某个功能不自动获得授出权，管理员也不必因此拥有被管理者全部业务操作权。自己的其他账号、角色内容修改或授出管理权不能成为绕过上限的路径；批量操作和角色修改的实际影响范围也要校验，具体模型与协议待设计。

分级管理以管理员自己的身份进行，不是扮演或 AI 代理。保留管理来源、资格与审计；普通授予与正常卸任的关系见[普通授予与管理员交接](#普通授予与管理员交接)，不混同于依赖委托人当前权限的代办。范围／上限收紧、组织撤销、安全事件、初始管理员和紧急恢复需各有明确协议与验收。

### 任职变更与授予确认

任职事实变更与新业务授权确认分开。旧任职相关授予自动撤销，新任职生成权限建议／待确认授予，由有权限的人确认后生效；批量调岗可以先审核变更计划。维护岗位的权限不直接等于授予新业务权限的权限。

只撤销本次失效任职关联的授予，其他有效兼任按自身条件保留；独立直接授予单独复核，不能一律保留或删除。授予保留来源、任职绑定、有效期与审计；员工与账号非一一对应，离职／账号停用范围、未处理业务和单据责任交接另行设计。

自动撤销是已定目标，关联映射、确认权限及可授予范围、跨组件协议、传播预算和同步故障保护仍待设计与验收；不承诺零延迟，也不从有事件推导已可靠撤销。授予确认前任职已变化、重复或乱序事件、多任职及联动失败均进入验收。

### 普通授予与管理员交接

管理员正常卸任或更换，被授予人的任职与业务资格未变化时，已有合法普通业务授予不因授予操作人卸任自动失效；仍按自身任职、有效期、撤销与必需控制判断。由接任管理员或上级接管管理，卸任者失去继续授予／修改的资格，原授予来源与审计链保留。

被授予人旧任职失效仍撤销对应授予，不能用管理员交接规则保留；用户代办／委托继续依赖委托人当前权限。管理范围／上限收紧、组织撤销、账号受侵或发现越权另行复核与撤销，不视为普通卸任。

接管流程、复核与批量撤销、异常处理及传播预算待设计。验收区分管理员本人撤权与其他员工的授予状态，覆盖同期调岗／到期、接任为空、委托失效、重复／乱序通知与 provider 切换；不承诺自动交接已实现或零延迟。

### 普通业务角色与升级确认

标准业务角色提供版本化参考模板，客户实际角色保持明确授权。升级展示新增权限及差异，由有权限的人确认后加入，支持审核批量变更计划；安装新功能不自动扩大普通业务角色权限。新功能可能需要一次权限配置才能使用，交付时应清楚说明。

确认遵守管理对象、授出上限、范围、字段与职责分离约束。安全修复、权限退役和必需控制另按明确升级协议处理，不能因保留旧角色而绕过；权限键不改名或复用，相同键的语义变化也要审查。模板版本、差异分类、计划有效性、确认生效与迁移待设计。

已有系统角色保护、最后一个管理员保护、专用 superuser 自动补齐未退役键的方向分别承接，生产默认无人持有该超级角色；不套用普通业务模板的更新规则。正式业务模板需要独立设计，现有演示种子角色不直接作为生产模板。验收覆盖新权限未自动加入、确认者越界、审核期间角色／管理资格变化、重复确认和 provider 切换。

## 审批与流程控制

### 审批依据与修订

审批依据绑定被审的具体内容。影响审批结论的关键修改使受影响审批失效，明确重新审批；旧版本、依据和处理记录保留，新内容不能依靠旧审批执行。编辑、审批和执行是不同动作，分别检查资格与权限。

| 修改所处阶段 | 已定默认路径 |
| --- | --- |
| 审批中 | 有权限的人可提交新修订并触发重审；严格业务可锁定关键内容 |
| 全部审批通过，但尚未发生受影响执行事实或必须单独变更的对外承诺 | 保留原单号、生成新修订并重审，暂停受影响执行；严格业务保留独立变更单路径 |
| 已执行或存在必须单独变更的对外承诺 | 按业务更正／冲销／变更协议处理，不直接改写已执行事实 |

组件明确声明无需重审的非关键字段及其规则；严格业务可以锁定审批中的关键内容。关键字段、失效范围和流程状态逐业务定义，不能从通用记录版本检查推导审批仍有效。执行前必须证明所用审批适用于当前内容。

预占、预处理和部分执行按具体业务状态处置，不以一个“尚未执行”标志涵盖全部单据。新修订与审批实例如何衔接、所用流程版本及受影响动作的暂停／恢复协议仍需设计。

跨组件验证修改与同意／执行竞争、旧任务和放行结果迟到、重复动作、崩溃恢复及新旧任务切换。待办显示已处理不能代替业务放行证据；具体权威与协调协议仍需设计。

### 流程版本与在途实例

审批实例绑定启动时的流程与相关配置版本。新规则默认用于新实例，在途审批继续原版本；需要旧实例改走新规则时，明确暂停、审核迁移或重新发起，并记录影响。客户升级必须保留支持范围内旧实例所需的执行语义，具体兼容窗口与清理条件待设计。

流程绑定不能冻结当前执行主体的权限或人工审批者的有效任职，也不能绕过本人自审限制、期间锁等执行时适用的控制。紧急收紧或旧逻辑缺陷要明确处理受影响的在途实例，不能只发布新规则就宣称已有单据全部受控。审批人解析、迁移映射与重发协议待设计；定价、税务等其他政策不由此推导同一绑定时点。

### 审批任务与人员变化

按组织职责规则分配的未处理审批任务，原审批人离职、卸任或失去资格后，按已绑定的流程／职责规则和当前权威组织、资格信息重新解析；找到合格接任者后自动转交，保留旧任务、变化依据、历史并通知。严格流程可以要求人工确认；找不到合法替代者或规则没有替代路径时暂停，转人工处理，不自动通过。

指定个人且没有合法替代路径的任务不能凭上级或管理员身份任意改派。重新分配不自动授予权限，不改变业务责任归属或已作出的审批事实；提交决定时仍检查当前资格／权限、职责分离与单据修订。流程／相关配置版本绑定继续适用，人员有效资格不冻结。

流程／业务处理方拥有任务和合法替代判断，统一待办入口不自行放行。事件、映射、解析时点、任务切换、人工改派权限与传播预算仍待设计；验收覆盖资格变化与提交决定竞争、接任者无权限、申请人成为候选、无人可替代、旧任务结果迟到、重复／乱序通知、崩溃恢复及多副本处理。

### 审批处理截止与业务到期

普通人工审批到处理截止仍未完成时，默认提醒处理人，按明确规则升级处理责任，继续待处理。需要截止后申请到期的业务另声明策略；升级不自动获得批准资格，找不到合格处理人仍转人工处理。具体转交／会签等行为按流程协议定义，不由“升级”一词隐含。

超时不记作某个人的同意或拒绝，申请到期需有独立可解释的结果。单据有效期、库存／信用预占期限与付款限制等仍按所属业务规则处理，审批等待不延长这些期限，不直接取消已执行事实，也不能成为无限保留资源的依据。

截止、工作日历、提醒频率、升级路径与积压保护需设计，具体数值未定。验收覆盖超时与完成竞争、重复通知、恢复后过期作业、无人可升级、业务单据或预占先到期、申请到期策略和状态提示；本轮未实现超时作业或修改在途任务。

## 审计动作与读取范围

长期业务审计按风险和明确动作清单覆盖必要变更、权限／配置变化、敏感读取与导出、代操作及安全拒绝等；普通低风险读取保留访问日志。规范和组件声明共同给出必需动作，客户可以在允许范围内扩展，具体默认分类和缺漏检查待设计。

成功业务变更继续承接审计 Outbox 与业务同事务写入、可靠转运的方向。读取、失败和拒绝没有已提交业务变更，需要自己的可靠采集与保存机制；必要审计不能以采样访问日志替代。完整响应和明文敏感字段不复制进日志，审计查询也受授权控制。

验收动作清单、敏感读取／导出、代理与拒绝、记录失败、容量保护、查询权限和恢复。保留年限按具体类别、地区与客户要求核对，不编统一法定下限；记录机制与审计组件尚未因本轮选择完成实现。

## 后台任务的身份与授权

| 类型 | 已定授权边界 |
| --- | --- |
| 仍代表用户的查询／导出 | 执行和交付结果时按当前有效授权重验，保留发起人，不用系统身份扩大数据范围 |
| 已确认业务的持久后续处理 | 达到明确业务授权节点后，由受限服务主体按既定范围和输入推进，检查当前业务状态及必需控制 |

仅接收请求或保存草稿不代表已到业务授权节点。不能把所有异步操作都归为系统任务；服务权限失效、业务取消／冻结、内容修订与重新审批各按明确控制处理。原发起人离职不自动撤销已执行事实，也不自动停止全部必要后续。

保留原发起人与实际执行者的审计链。任务分类、各业务授权节点、长任务检查时点、结果与下载链接失效、服务范围及交接的并发协议待设计；撤权、取消和恢复都要进入验收。

## 方案替换的验收

已定方向的正反场景集中在[权限验收矩阵](validation/authorization-matrix.md)，覆盖完整授予、查询与字段、授权管理、审批控制、服务任务、新鲜度、替换及证据。矩阵是待实例化的验收规格，具体契约、接口与版本尚需绑定，不表示这些行为已经实现或测试通过。

统一契约必须规定能力集合、版本和缺失能力的明确响应。不同模型不能只比较同名 API：角色并集、条件规则和关系图的对象语义可能不同。用独立向量和真实请求证明允许与拒绝、列表与单对象判断、分享与撤销、字段裁剪相符。各实现同时满足客户组合要求的能力与该操作的新鲜度保证。

矩阵 PA01／PA25 同时覆盖伪造服务主体和部署受众；PA07／PA29 覆盖列表截断及超时；PA15 覆盖无法证明管理上限；PA27／PA28 覆盖远程授权检查与提交竞争、新内容配旧关系。实例化时写具体的允许节点与拒绝预期，不只检查最终撤权。

迁移不仅搬角色名称，还要处理主体、权限键、对象关系、授予到期、撤销、审计和投影修订。方案在离线、延迟、陈旧、重启与切换期间的行为必须可解释。详见[授权选择](replacements/authorization.md)与[身份选择](replacements/identity.md)。

## 本轮发现

旧 SDK 与新的协议候选版采用不同权限模型；三个开发中的 SDK 尚有 explain、共享和修订令牌的差异。它们是新的验收输入，不能先视为统一机制已经完成。

Casdoor tokenFormat 的既有问题属于尚未修复的已知项，原排期并入 IAM 3.0.0。新路线须明确修复与验证门槛。公开的客户资料不会把未修复方案写成已达到安全验收。

## 待确认的前提

按通用 ERP 覆盖典型权限场景，再由选择的客户样板明确角色矩阵、职责分离与敏感数据要求。无具体客户时不猜测法定保存期和合规结论。IAM、授权、目录、法人组织之间的归属要与组件边界同步裁定。
