# 备份、恢复与一致性恢复

> 状态：2026-10-13 运行协议第十五份候选，尚未冻结。承接 C37（备份恢复／HA）、I25（数据库与消息进度的恢复不原子，外部事实与安全记录不能随旧备份回退）、D26（优先保证整套部署的一致性恢复）与[数据与生命周期的标准灾难恢复范围](../04-data-and-lifecycle.md#标准灾难恢复范围)；按 D59 从零设计。

## 本页解决什么

数据库恢复成功，不等于业务恢复成功。整套部署恢复到较早的时刻 T 之后：

1. T 之后已经发出的事件、已经执行的外部操作、已经做出的撤权与销毁，怎样不丢失、不重复、不复活？
2. 恢复的步骤、顺序与检查是什么？谁来确认可以重新开放？
3. 损失的范围怎样确定并告诉用户？
4. 高可用切换与恢复有什么不同？

## 方案比较

| 路线 | 判断 |
| --- | --- |
| 推荐：整套部署恢复到同一时刻 T；消息流重建并按各消费者在 T 的进度补发；外部事实与安全记录从独立的证据存储补回；恢复期冻结一切对外动作；以对账与检查清单决定重新开放 | 不出现幽灵事件与丢失事件；不重复付款；撤权与销毁不复活；损失范围可列出 |
| 只恢复数据库，其余照常启动 | 消息流中留有 T 之后的事件（幽灵事件），消费者却回到 T 之前；在途的外部操作被盲目重发；撤权失效 |
| 按组件分别恢复为标准能力 | 不受影响的组件可以继续服务，但跨组件事实的对齐要逐组件设计；D26 未作为标准，按专项场景设计 |

## 恢复组与备份清单

标准的恢复组是客户的整套部署：

| 状态 | 备份方式 | 恢复后的地位 |
| --- | --- | --- |
| 全部组件的数据库 | 物理备份 + 预写日志归档，支持恢复到任意时刻 | 权威；恢复到 T |
| 对象存储 | 对象版本保留与异地副本；对象在备份窗口内不物理删除（[协议 11](11-tiering.md)、[协议 12](12-attachments-and-object-storage.md)） | 按恢复后目录与附件记录核对 |
| 消息流 | 不作为权威备份；恢复时重建 | 由各组件的发件表补发 |
| 配置与密钥引用 | 随客户基线版本管理（协议 19） | 恢复到与 T 一致的基线；密钥本身按密钥管理恢复 |
| 独立证据存储（由审计组件兼任） | 只追加、单独保存与复制，不随部署备份回退 | 恢复后用于补回 T 之后的外部事实与安全记录 |
| 审计存储 | 按[协议 03](03-audit-durability.md) 单独保存 | 不回退；T 之后的审计保留，用于确定损失范围 |

**独立证据存储**保存恢复时不能丢的记录：安全记录的变更（授予、撤销、任职变化，[安全 08](../security/08-state-and-change-protocol.md)）、销毁与擦除记录、对外命令的终态与外部单号（[协议 10](10-external-integration.md)）。它由审计组件兼任（[基础能力卡](../components/infra.md#infraaudit)）：审计组件已经有回执、备份水位与“不回退”的保存，不再另设一个基础资源；证据与审计记录分开存放与查询。

写入方式：

- 一般记录在本地事务提交后经发件表写入，有回执，回执之前的记录在本地保留。
- **收紧类安全记录**（撤销、停用、任职结束、销毁与擦除）在生效点提交后，由同一请求**同步**写入证据并等待回执，然后才向请求者返回“已生效”。证据组件不可达时收紧照样生效（不能为了证据而推迟撤权），但部署进入“证据待补”状态并立即告警；告警写入部署之外的观测与告警渠道（协议 17），带时间段。
- 因此，收紧类安全记录的恢复点目标等于“证据待补”的持续时间。恢复到落在这段时间之后的时刻时，恢复报告列出这段时间，要求有权限的人复核并重新执行其间的收紧（第 6 步）。

多个数据库集群时，各集群按同一时刻恢复；跨集群的恢复不是原子的，下文的对账负责对齐。

## 发件表的保留与消费者进度

整套恢复依赖两件事，平时就要做到：

- **消费者记录进度**：每个消费者在自己的数据库中按来源记录已处理的事件（收件表，或按来源的连续序号）。
- **发件表的保留**分成两个量，互不牵连：
  - **未发布积压**：尚未发布到运输的行。D14 的保护只看它（超过阈值时按协议 17 限制受影响业务），因为这才是运输故障。
  - **补发保留**：已发布的行按固定上限保留（时间与容量，起始值见参数表），只为整套恢复时补发。它不看有哪些消费者、消费者是否确认，所以后加的消费者不需要生产者变更，下游故障也不会反向限流上游。消费者落后超过保留上限时只告警。

恢复时，每个生产者按各消费者在 T 的进度补发，而不是按固定的时间窗：固定时间窗会漏掉在 T 时已经落后超过窗口的消费者（参考模型的“只补发固定时间窗”坏变体）。需要的行已经超出补发保留时，该消费者按[协议 02](02-projections.md) 的完整快照修复，或按协议 05 的增量事实按序号向产生方补取与对账，并记入恢复报告；恢复流程从各消费者的数据库读取进度，生产者不需要事先知道有哪些消费者。

## 恢复流程

| 步骤 | 内容 | 完成的依据 |
| --- | --- | --- |
| 1. 宣布与选择 T | 有权限的人宣布恢复，选择恢复时刻 T（数据损坏之前、日志可达的最晚时刻） | 恢复记录：原因、T、批准人 |
| 2. 冻结 | 边缘入口返回维护中；停止定时任务、后台工作、发件转发、消费者与适配器的发送；外部回调入口返回暂不可用，外部按其重试 | 所有执行者停止，确认没有在途发送 |
| 3. 恢复数据库 | 各集群恢复到 T | 恢复日志与校验 |
| 4. 推进恢复代次 | 部署的恢复代次加一：所有工作项的租约代次、转层与对外命令的代次推进，旧执行者即使残留也被拒绝 | 代次记录 |
| 5. 重建消息流 | 删除并重建流与持久消费者；生产者按各消费者在 T 的进度补发，事件 ID 不变，消费者按收件表去重 | 每个消费者的补发清单 |
| 6. 补回安全记录 | 从证据存储重放 T 之后的安全记录变更与销毁、擦除记录；T 之后若有“证据待补”的时间段，列入报告，由有权限的人复核并重新执行其间的收紧 | 重放清单、待补时间段与复核结论 |
| 7. 外部对账 | 每个适配器查询外部在 T 之后的记录：本地处于发送或结果未知的命令先查询，不重发；外部有、本地没有的，从证据存储与外部查询补回 | 每个适配器的对账结果 |
| 8. 内部一致性检查 | 跨组件的对账：预占与订单（协议 04）、出账与来源、子账与总账（协议 05）、期间状态（协议 06）、引用（协议 07）、目录与对象（协议 11、12）、投影完整性（协议 02） | 检查清单，全部通过或差异有处置 |
| 9. 损失范围 | 用审计存储与访问日志列出 T 之后用户提交、但恢复后不存在的业务操作 | 损失清单，按用户与单据 |
| 10. 重新开放 | 有权限的人依据检查清单与损失清单决定开放；先开放查询，再开放写入与对外动作；通知受影响的用户重新录入 | 开放记录 |

**幽灵事件**：T 之后发布到旧消息流中的事件，其源数据在恢复后不存在。保留旧消息流会让消费者处理它们（参考模型的“保留旧消息流”坏变体），所以消息流必须重建。

**外部操作**：恢复后的数据库中处于“发送中”的命令，在 T 之后可能已经执行；直接重发会重复执行（参考模型的坏变体）。

**安全记录**：只从备份恢复安全状态，T 之后的撤权就失效了（参考模型的坏变体）；重放证据存储中的记录使其继续有效。T 之后新增的授予同样重放，它们有自己的批准记录；被引用的对象在恢复后不存在时，授予成为悬空引用，按协议 07 处理。

## 部分恢复与局部修复

- 可重建的副本（投影、数据集、搜索索引）出错时，按协议 02、13 重建，不需要整套恢复。
- 普通的业务错误按业务更正流程处理（冲销、更正单据），不使用恢复。
- 只恢复一个组件不是标准能力（D26）；需要时作为专项场景设计：列出它与其他组件的全部事实关联，按本页的对账步骤逐项对齐。

## 高可用与故障切换

| 方式 | 数据损失 | 说明 |
| --- | --- | --- |
| 同步复制的数据库切换 | 已提交的事务不丢失 | 切换期间写入中断；仍需推进代次以隔离旧主库上的执行者 |
| 异步复制的数据库切换 | 可能丢失最后一段已提交事务 | 视为恢复到切换时刻的特例：执行第 4–9 步，范围较小 |
| 消息系统的集群副本 | 按其复制设置 | 消息流不是权威；丢失时按第 5 步补发 |
| 单节点部署 | 依靠备份 | 小客户的标准组合；恢复目标按备份频率声明 |

高可用是可选的部署组合，按客户基线声明；故障切换的演练与恢复演练分别进行。

## 恢复目标与演练

- 每个客户基线声明恢复点目标与恢复时间目标；标准组合的起始值见下表，实际值由代表部署实验与客户的数据量测得后承诺。
- 演练在隔离环境中进行：用真实的备份恢复，执行完整流程，记录每一步的时间与检查结果；演练中包含“T 之后有外部付款”“T 之后有撤权”“某消费者在 T 时落后”的场景。
- 演练记录进入客户的运行档案；没有演练记录，不宣称恢复目标已满足。

## 参数起始值

| 参数 | 起始值 |
| --- | --- |
| 预写日志归档间隔 | 不超过 1 分钟 |
| 完整物理备份 | 每日一次，保留 30 天 |
| 恢复点目标（标准组合） | 5 分钟 |
| 恢复时间目标（标准组合） | 4 小时（实测后承诺） |
| 已发布行的补发保留 | 7 天，且不超过声明的容量上限 |

| 收紧类安全记录写证据的等待 | 2 秒；超时则进入“证据待补”并告警 |
| 消费者落后告警 | 1 小时 |
| 恢复演练 | 每季度一次 |

## 参考模型

[一致性恢复模型](../work/checks/27-consistent-recovery.py)（种子 20261013，3,000 次运行）：生产者写事实与发件表，转发发布，消费者经收件表处理；适配器执行外部命令（外部保留自己的记录）；撤权写入数据库与证据存储；随机选择较早的时刻 T 恢复整套部署。

| 检查 | 结果 |
| --- | --- |
| 消费者没有处理恢复后不存在的事实 | 成立 |
| 恢复后存在的每个事实都已被消费者处理 | 成立 |
| 外部不重复执行 | 成立 |
| 外部执行过的命令在本地都可知 | 成立 |
| T 之后的撤权在恢复后仍然有效 | 成立 |

5 个坏变体全部被发现：保留旧消息流、重建消息流但不补发、只补发固定时间窗、不查询就重发发送中的命令、只从备份恢复安全状态。首轮的正确版本按固定时间窗补发，模型发现在 T 时落后超过窗口的消费者会丢事件；改为按各消费者在 T 的进度补发后成立，固定时间窗成为坏变体。模型不是数据库、消息系统或备份工具的运行结果。

2026-10-14 按独立复查（IR12、IR13）扩展：已发布行按固定上限保留，超出部分由消费者从生产者的事实修复；撤销时证据组件有两成概率不可达，此时进入“证据待补”并在恢复后复核重做。正确版本仍全部成立；新增“不做消费者修复”“证据不可达时既不标记也不复核”两个坏变体，都被发现。模型假设复核能找回待补时间段内的撤销，这一假设靠恢复演练验证。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| RC01 | 恢复到 T 后启动服务 | 先冻结、推进代次、重建消息流，再开放 |
| RC02 | T 之后发布的事件 | 不被处理（消息流已重建） |
| RC03 | 某消费者在 T 时落后两天 | 按它的进度补发，不丢事件 |
| RC04 | 需要补发的发件表行已被清理 | 该消费者做完整快照修复或增量事实对账，并记入损失范围 |
| RC05 | 本地处于发送中的付款 | 先查询外部，不重发 |
| RC06 | T 之后外部已收款，本地无记录 | 从证据存储与外部查询补回 |
| RC07 | T 之后撤销的权限 | 恢复后仍然撤销 |
| RC08 | T 之后执行的销毁 | 重新执行 |
| RC09 | 残留的旧执行者在恢复后提交 | 因代次不符被拒绝 |
| RC10 | 用户在 T 之后录入的订单 | 列入损失清单并通知用户 |
| RC11 | 目录指向的冷对象缺失 | 检查不通过，按协议 11 处理后才开放 |
| RC12 | 投影出错 | 重建投影，不做整套恢复 |
| RC13 | 只恢复库存组件的请求 | 不是标准能力，按专项场景设计 |
| RC14 | 异步复制的主库故障切换 | 按恢复的特例执行代次、对账与损失范围 |
| RC15 | 没有演练记录 | 不宣称恢复目标已满足 |
| RC16 | 恢复期间外部回调到达 | 入口暂不可用，外部按其重试；开放后处理 |
| RC17 | 撤销付款权时证据组件不可达，随后恢复到撤销之前 | 撤销照样生效并告警“证据待补”；恢复报告列出该时间段，复核后重新执行撤销 |
| RC18 | 某消费者落后超过补发保留 | 只告警，不限流上游；恢复时该消费者走快照修复或按序号补取，记入恢复报告 |
| RC19 | 新增一个消费者组件 | 生产者不需要变更 |
| RC20 | 报表组件故障一周 | 上游的订单确认不受影响 |

## 仍未解决与下一步

- 备份工具（例如 pgBackRest）、对象存储的复制方式、消息系统的重建步骤，在代表部署实验中选定并实测。
- 证据在审计组件中的存放形态（独立表或只追加日志）与保护方式，随审计组件设计确定。
- 恢复时间目标在实测后按客户数据量承诺。
- 恢复流程的操作手册随正式运行文档（`docs/en/05-operations/`）编写。

C37 与 I25 有了协议与模型；未运行备份恢复演练，不标关闭。
