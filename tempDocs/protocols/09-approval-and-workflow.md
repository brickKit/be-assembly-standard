# 审批与流程

> 状态：2026-10-13 业务协议第九份候选，尚未冻结。承接 C27 的审批部分，以及 D10（职责分离）、D11（无人工审批流程）、D18（审批中修订重审）、D19（待办与流程分开）、D23（在途实例绑定流程版本）、D29（用户任务与已确认业务的后续处理）、D33（批准后未执行的修订）、D38（人员变化的重分配）、D39（超时与申请到期）；按 D59 从零设计，现行 `infra/workflow` 只作参考。

## 本页解决什么

[安全总览的审批与流程控制](../02-security-and-permissions.md#审批与流程控制)写了已定的方向；本页把它们落成一套协议，回答：

1. 谁拥有单据、审批实例、任务、待办显示？各自的权威在哪里？
2. 审批结论怎样绑定被审的内容，怎样保证旧审批不能放行新内容？
3. 本人自审怎样在账号映射、代理、角色切换之下都被挡住？
4. 人员变动、超时、配置变更、引擎替换时，在途审批怎样继续而不被静默放行？

## 方案比较

| 路线 | 判断 |
| --- | --- |
| 推荐：业务组件拥有单据与放行；流程管理方（组件内的简单流程，或可选引擎）拥有实例与任务；统一待办只聚合与转发；放行时由业务组件按内容摘要核对审批 | 三方权威不重叠；换引擎不影响放行语义；小客户不必部署引擎 |
| 待办箱同时是流程引擎，业务组件只看引擎结论 | 部署简单，但引擎“已通过”会直接变成执行依据，修订与审批迟到的竞争只能靠引擎自己处理；换引擎时放行语义跟着变 |
| 业务组件各自实现审批与待办 | 每个组件都要重做任务、分配、超时、通知；用户没有共同入口 |
| 只用记录版本号判断审批是否有效 | 非关键修改也会让审批失效，或不同字段集合的变化无法区分；版本号不能证明审过的就是现在的内容（D18） |

## 三方分工

| 角色 | 拥有 | 不做 |
| --- | --- | --- |
| 业务组件 | 单据、修订、关键字段声明、流程选择、执行放行 | 不把待办显示或引擎通知当作放行证据，放行前自己核对 |
| 流程管理方 | 审批实例、步骤、任务、分配与重分配、决定的记录、截止与提醒 | 不决定业务能否执行；不改单据 |
| 统一待办 | 任务的聚合显示、动作转发、处理结果的如实显示 | 不记录决定，不判断替代者是否合法，不在本地把任务标为完成 |

流程管理方有两种实现：

- **简单流程**：SDK 提供的流程内核，运行在业务组件里，实例与任务存在业务组件自己的库中，与单据同库同事务。多数单据用这种。
- **可选引擎**：独立组件，经流程契约接入。需要客户自己画流程、长期流程、复杂会签时启用。

两种实现都向统一待办发布任务投影（[协议 02](02-projections.md)），接受同样的动作契约。逻辑分工不要求每个角色单独一个进程。

## 审批实例与审批依据

### 实例

| 字段 | 说明 |
| --- | --- |
| 实例 ID | 流程管理方生成 |
| 单据引用 | 业务组件、单据类型、单据 ID |
| 修订号 | 被审的单据修订 |
| 审批依据摘要 | 见下文；每个步骤一个 |
| 流程定义版本 | 启动时绑定（D23） |
| 相关配置版本 | 只包括影响审批路由的配置（金额阈值、步骤选择），不包括定价、税务等其他政策 |
| 发起责任主体 | 发起、录入、受益等责任主体的账号与对应的人（D10） |
| 状态 | `running`、`approved`、`rejected`、`returned`、`withdrawn`、`superseded`、`expired`、`paused` |

### 审批依据

- 业务组件为每种单据声明**关键字段**；其余字段为非关键字段，修改不触发重审。没有声明时，全部业务字段都是关键字段。
- 审批依据摘要 = 按 [安全 09 的规范编码](../security/09-encoding-and-profiles.md) 对“修订号以外的关键字段值”计算的带类型前缀摘要。
- 默认每个步骤的依据覆盖全部关键字段。组件可以为某个步骤声明更窄的字段组（例如财务步骤只审科目与金额）；字段组必须包含影响该步骤路由的全部字段（金额阈值、法人、类别等）。只有该字段组没有变化时，该步骤的决定才可能在新修订下继续有效（条件见“修订与重审”）。
- 严格业务可以声明“审批中锁定关键内容”：修改要先撤回实例。

### 流程选择（D11）

业务组件为每种单据声明可用流程：一种或多种人工审批流程，以及在允许时的“无需人工审批”流程。选择规则（按法人、金额等）是版本化配置，由有权限的管理员维护。

- 组件声明为“必须人工审批”的场景（例如超过阈值的付款），选择规则不能改为无人工审批；配置校验拒绝。
- 选择在实例启动时绑定。配置变更不影响已启动的实例；待审单据不会因为改成无人工审批而静默通过。
- 无人工审批流程照常执行授权、库存、金额、期间等必需校验，留下一条实例记录：所选流程、版本、校验结果；它没有任务，状态直接为 `approved` 或 `rejected`。

## 决定的提交

处理人在待办或业务界面中提交决定（同意、拒绝、退回），动作到达流程管理方。流程管理方在一个本地事务里检查并记录：

1. 任务处于待处理，且实例未被取代。
2. 处理人是任务的当前处理人，或其有效代理（[安全的共享与委托](../02-security-and-permissions.md#共享委托与只读扮演)）。
3. 处理人当前有该步骤的资格与权限：权限按[安全 03 的有界本地授权](../security/03-authorization-acceptance-and-revocation.md#默认路径有界本地授权)；岗位资格按员工与组织的投影，行完整且来源水位在有效期内（[协议 02 的来源水位](02-projections.md#来源水位)）。
4. **职责分离（D10）**：处理人对应的人，以及代理链上每一个人，都不是本实例的发起责任主体。比较以人为单位，不以账号为单位：同一个人的第二个账号、借助代理或切换角色，都不能审批本人发起的单据。严格业务可以另外声明静态互斥角色。未装员工组件时无法把账号归到人，按[安全 02](../security/02-trusted-identity-and-attributes.md) 的规则至少比较稳定的发起主体（账号）；同一个人的多个账号无法识别，这一风险在装配时告知客户。
5. 实例的修订号仍是单据的当前修订（简单流程在同一事务中读单据；引擎以单据的修订事件为准，放行时业务组件再核对）。
6. 每个任务至多一个决定：决定以任务 ID 唯一；动作带幂等键，重试返回同一个结果，不产生第二个决定。

决定记录：任务、决定、处理人账号与对应的人、代理链、依据摘要、修订号、资格证据的时刻。拒绝的检查结果（自审、无资格、已取代）也记录，并如实返回给用户。

步骤规则：

| 形式 | 完成条件 |
| --- | --- |
| 单人 | 唯一任务有决定 |
| 任一 | 第一个同意完成该步骤，其余任务转为 `superseded` |
| 会签 | 全部同意；任何一个拒绝即该步骤拒绝 |
| 法定人数 | 达到声明的同意数；剩余可能的同意数不够时拒绝 |

拒绝默认结束实例为 `rejected`；流程可以声明“退回发起人”（实例 `returned`，发起人修改后以新修订重新提交）。发起人可以在实例完成前撤回（`withdrawn`）。

## 执行放行

业务组件在**开始执行的事务里**核对：

- 存在状态为 `approved` 的实例（或无人工审批流程的通过记录），其修订号等于单据当前修订；
- 用当前单据内容重新计算各步骤的依据摘要，与实例记录的相同；
- 实例使用的流程版本与配置在选择时合法（已经在启动时校验，这里核对绑定记录存在）。

任一不满足，不执行。引擎发来的“已通过”只是证据，放行由业务组件自己核对。这样，修订与同意并发、同意结果迟到、引擎重复发送，都不会让旧审批放行新内容（参考模型的“审批沿用到新修订”坏变体）。

## 修订与重审（D18、D33）

| 阶段 | 处理 |
| --- | --- |
| 审批中，修改关键字段 | 业务组件在一个事务里创建新修订，标记当前实例待取代，并写出“修订已提交”事件；流程管理方把旧实例转为 `superseded`、旧任务转为 `superseded`，按新修订启动新实例 |
| 审批中，只改非关键字段 | 新修订，实例继续；依据摘要不变 |
| 全部批准、尚未执行 | 同上创建新修订并重审；在同一事务里暂停受影响的执行（例如待发货的明细）；重审通过后恢复 |
| 已部分执行 | 只能修订未执行部分；已执行的事实走更正、冲销或变更协议 |
| 严格业务 | 不改原单，提交独立的变更单，变更单有自己的审批；批准后由业务组件应用 |

- **新实例用哪个流程版本**（D60）：关键内容修改触发的重审是新实例，按当时生效的流程版本；只有非关键修改，或组件为某类单据明确声明“按原版本重审”时，才沿用原版本。这样改单不能绕过修改时已经生效的新规则。
- 旧决定只在以下条件全部成立时沿用到新实例，新实例跳过该步骤并记录引用：新实例与旧实例使用同一流程版本、该步骤的定义相同；该步骤的字段组未变（依据摘要相同）；原处理人此刻仍有该步骤的资格且职责分离仍成立（版本绑定不冻结人）。其他情况重新审批。
- 预占（[协议 04](04-order-reservation.md#取消到期与修订)）与其他预处理按各自协议处置，审批等待不延长它们的期限。

迟到的结果：旧实例的决定在取代之后到达，流程管理方按第 1 条拒绝；引擎在取代前已记录、取代后才送达的通过结论，在放行核对时因修订号或摘要不符被拒绝。

## 流程版本与迁移（D23）

- 流程定义与相关配置都是不可变的版本；发布新版本不改旧版本。
- 在途实例继续原版本。旧版本在仍有实例使用时不能删除；支持范围内的升级必须保留旧版本的执行语义。
- 需要在途实例改走新规则时（紧急收紧、旧规则有缺陷），有权限的管理员发起**迁移**：选定受影响实例，暂停它们，逐个审核节点映射或改为重新发起，记录影响。迁移需要业务确认（[安全 08 的业务确认](../security/08-state-and-change-protocol.md#确认与受保护操作)，不是安全受保护操作），不是发布新规则的副作用。
- 版本绑定不冻结人：处理人的资格、权限、职责分离与期间锁仍在每次提交时检查。

## 分配与重分配（D38）

任务的分配规则在流程定义中声明，并随版本绑定：

| 规则 | 解析 |
| --- | --- |
| 岗位或职务持有人 | 指定组织单元内持有该岗位的人 |
| 关系 | 例如发起人的直接上级、成本中心负责人 |
| 角色持有人 | 持有某业务角色的人 |
| 指定个人 | 一个确定的人；可以声明替代规则 |

解析时总是排除职责分离要求排除的人（以人为单位）。

重分配由组织事件驱动：

1. 流程管理方订阅组织、员工、任职与资格的变化（协议 02 的投影）。
2. 变化发生后，一个工作项（[协议 01](01-background-work.md)）找出处理人受影响的待处理任务，按**当前**权威组织数据重新解析绑定的规则。投影不完整时等待，不按旧数据解析。
3. 找到合格接任者：旧任务转为 `superseded`（原因“重分配”、依据为组织变化），新建任务给接任者，通知双方；严格流程可以要求先由有权限的人确认。
4. 找不到合法替代（例如指定个人且没有替代规则、岗位空缺、唯一候选是发起人本人）：任务转为 `paused`，进入流程管理方的异常入口并告警。
5. 人工改派需要单独的权限；改派的目标仍要通过资格与职责分离检查。上级或管理员身份不能直接放行，也不能把任务改给不合格的人。

重新解析以“任务 + 组织修订”为幂等键，按当前状态而不是事件内容解析，所以重复与乱序的组织事件不会产生多个任务。离任者的决定与重分配并发时，以流程管理方事务的先后为准：决定先提交且当时资格有效，则决定有效；重分配先提交，迟到的决定被拒绝。

## 截止、提醒、升级与申请到期（D39）

- 任务创建时按工作日历计算处理截止，日历版本随实例绑定。
- 提醒与升级由工作项执行，补跑策略为合并（停机后恢复只发一次提醒，不补发多次）；同一处理人的多条提醒合并为摘要。
- 到截止时的默认动作：提醒处理人，并通知流程声明的升级对象（通常是岗位的负责人）。升级对象可以按上节规则改派，或者本身合格时处理；升级不自动给予批准资格。
- 超时**从不**产生同意或拒绝。没有合格升级对象时，任务保持待处理并进入异常入口。
- **申请到期**是业务另外声明的策略：到期后实例转为 `expired`（独立的结果，不是拒绝），任务关闭，单据按业务规则回到可修改或作废。单据有效期、库存与信用预占、付款限制各按所属业务规则到期，审批等待不延长它们。

## 统一待办

- 待办是任务投影的消费者：任务身份（流程管理方 + 任务 ID）、单据引用、摘要、处理人、状态、截止、版本。摘要字段按读者的字段资格掩码（[安全 07](../security/07-finite-expressions-containment-and-queries.md)）。
- 用户的动作经待办转发到流程管理方，带任务版本与幂等键；待办只在得到权威结果后更新显示。转发超时显示“处理中，结果未确认”，不显示“已完成”；用户重试使用同一个幂等键。
- 待办不保存决定，也不在本地关闭任务（参考模型的“待办本地记录决定”坏变体会产生同一任务的多个决定）。
- 流程管理方不可达时，待办照常显示投影中的任务，并标明可能不是最新；动作被拒绝或暂缓。
- 待办保存历史投影，供已完成任务的查询；引擎替换后旧历史仍可读。
- **未装统一待办时**，人工审批照常由业务组件内的流程内核管理，任务在各业务组件自己的页面中处理，只是没有跨组件的统一入口；不因为缺统一待办就只能用无人工审批流程。

## 引擎接入契约

可选引擎以适配器实现流程契约：

| 方向 | 内容 |
| --- | --- |
| 业务组件 → 引擎 | 启动实例（单据引用、修订号、各步骤依据摘要、流程版本、发起责任主体）；取代或撤回实例 |
| 引擎 → 业务组件 | 实例完成（结果、修订号、依据摘要、决定记录引用） |
| 引擎 → 待办 | 任务投影 |
| 待办 → 引擎 | 决定动作（任务、版本、幂等键、处理人） |

引擎必须执行本页的决定检查（职责分离以人为单位、资格、唯一决定）；业务组件的放行核对不依赖引擎是否正确实现了这些检查之外的部分。替换引擎时，在途实例在原引擎中完成，或按迁移办法重新发起。

## 后续处理的身份（D29）

审批全部通过后，按批准内容继续的后续处理（例如批准后的自动下单、到期提醒）以业务组件的受限服务身份执行，依据是批准记录与当前单据状态，不依赖发起人或审批人仍在职；取消、冻结与修订仍走本页的控制。

## 参考模型

[审批流程模型](../work/checks/21-approval-flow.py)（种子 20261013，3,000 次运行）：随机交错决定（含重试）、关键字段修订、岗位任免（含发起人的第二个账号获得岗位）、截止到达与执行尝试。

| 检查 | 结果 |
| --- | --- |
| 执行只在批准的修订等于当前修订、且该实例有同意决定时发生 | 成立 |
| 任何同意都不来自发起人或与其对应同一个人的账号 | 成立 |
| 每个任务至多一个决定，无论动作重试几次 | 成立 |
| 截止从不产生同意或拒绝 | 成立 |
| 未处理任务的处理人始终是当前合格的岗位持有人 | 成立 |

5 个坏变体全部被发现：审批沿用到新修订、职责分离只比较账号、截止自动同意、待办本地记录决定、重分配给发起人的上级而不看岗位。模型不是 SDK、流程引擎或业务组件的运行结果。

**模型没有覆盖的条款**：步骤级的窄字段组与旧决定沿用的条件（AP28）、关键修改后的重审按当时版本（D60，AP27）没有建模；它们是规则执行检查，靠实现测试。

## 独立预期
