# 订单确认中的预占：库存与信用

> 状态：2026-10-13 数据与业务协议第四份候选，尚未冻结。承接问题 I23 的预占分支、C13、C14，以及 D02、D03、D12、D13、D14、D44；把[事务与消息](../05-transactions-and-messaging.md#订单确认与预占协调的推荐协议)中的推荐协议落成状态机与时序。按 D59 从零设计。

## 本页解决什么

确认一张销售订单，要同时在库存组件占住货、在信用组件占住额度。这是三个独立组件、三个数据库，没有共同事务。本页回答：

1. 什么时候可以告诉用户“订单已确认”？
2. 一方占住了、另一方没占住，或者响应丢了、进程崩了，怎样不超卖、不漏放、不重复占用？
3. 取消与预占交错、暂存到期与确认交错时，以谁为准？
4. 确认之后的取消、修订、发货和开票，怎样与预占衔接？

## 方案比较

| 路线 | 判断 |
| --- | --- |
| 推荐：销售拥有一个持久的确认过程；库存、信用各自拥有带状态的预占分支；全部分支进入“确认占用”后，销售才在本地提交订单确认 | 不需要跨库事务；任何一步失败都能从持久状态恢复；参与方各自用本地事务保证不超用 |
| 两阶段提交（XA）或全局事务 | 跨组件、跨数据库、可能跨语言，协调者故障时参与者长期持锁；与“每个组件独立部署”的原则冲突 |
| 先确认订单，再异步预占 | 用户当场看到“已确认”，之后才发现缺货或超额，违反 D12 |
| 销售读取库存与信用快照后自行判断 | 读与写之间别人可能占走；资源归属方之外的判断不是权威（原书：库存是物理命令的唯一写者） |

## 参与方

参加哪几方，由订单策略与已启用的能力决定（D44）：

| 订单内容 | 库存分支 | 信用分支 |
| --- | --- | --- |
| 含实物明细 | 必需；库存未安装时实物类型不能启用 | 按客户的信用政策 |
| 只有服务明细 | 不参加 | 按客户的信用政策 |
| 客户无信用控制（例如现款） | 按内容 | 不参加 |

参加方在过程创建时确定并持久记录，之后不因配置变化而增减；能力变更涉及在途订单时另行处理（D44 尚未裁定的部分）。

## 分支状态机

每个参与方为每张订单的每次确认保存一条分支，分支身份由销售生成并在所有命令中携带。

| 状态 | 含义 | 占用额度 |
| --- | --- | --- |
| `held` | 暂存预占：额度已占，带暂存期限 | 是 |
| `committed` | 确认占用：不再受暂存期限约束，只能由明确的取消或消耗结束 | 是 |
| `consumed` | 已消耗：发货已扣减实物，或开票已转为应收占用（部分消耗按数量与金额记录） | 已转出 |
| `released` | 已释放：由取消或修订释放 | 否 |
| `expired` | 暂存到期而自动释放 | 否 |
| `rejected` | 预占时额度不足 | 否 |
| `cancelled` | 取消先于预占到达，留下墓碑 | 否 |

| 转换 | 触发者 | 规则 |
| --- | --- | --- |
| 无 → `held` | 销售的预占命令 | 参与方在一个本地事务中检查可用额度并写入分支；额度不足则写 `rejected` |
| 无 → `cancelled` | 销售的取消命令（预占尚未到达） | 写墓碑；之后迟到的同一分支预占被拒绝 |
| `held` → `committed` | 销售的确认命令 | 只能从 `held` 转入；已 `expired` 的分支不能被确认复活 |
| `held` → `expired` | 参与方的暂存期限 | 由参与方自己的工作项执行，与确认命令在同一行上原子裁决 |
| `held`／`committed` → `released` | 销售的取消或修订命令 | — |
| `committed` → `consumed` | 发货（库存）或开票形成应收（信用，见协议 05） | 可以分多次部分消耗 |

关键规则：

- **确认占用没有自动到期。**参与方不能自行释放 `committed` 的分支；订单在业务上过期（例如长期未发货），由销售按订单生命周期发起取消。否则会出现订单显示有效、资源却已分给别人的情况（参考模型的“参与方自行到期确认占用”坏变体）。
- **每条命令按分支身份幂等。**同一分支身份、同样内容的重复命令返回已有结果；同一身份、不同内容（数量或金额不同）按冲突拒绝。
- **每个参与方提供按分支身份查询的接口**，返回当前状态；结果未知时先查询，不换身份重发。

## 参与方的命令

| 命令 | 输入 | 结果 |
| --- | --- | --- |
| 预占 | 分支身份、订单与修订、明细（库存：产品、仓库、基本单位数量；信用：客户、法人、币种、金额）、暂存期限 | `held` 或 `rejected`（附不足原因）；已有分支则返回其状态 |
| 确认 | 分支身份 | `committed`；分支已 `expired`、`released`、`cancelled` 时返回该状态，不改变它 |
| 取消 | 分支身份 | `released`；分支不存在时写 `cancelled` 墓碑 |
| 查询 | 分支身份 | 当前状态与数量或金额 |
| 消耗 | 分支身份、消耗身份、数量或金额 | 部分或全部 `consumed`；消耗身份幂等 |
| 调整 | 分支身份、新修订、新数量或金额 | 减少直接释放差额；增加按预占规则检查（见“修订”） |

库存的一条分支包含该订单的全部实物明细，在一个本地事务中全部占住或全部拒绝；多行加锁按“产品 + 仓库”的固定顺序，避免死锁。允许部分满足（缺货另行补货）是订单策略的选项，默认全部满足。

## 销售的确认过程

销售为每次确认创建一条持久的过程记录：过程身份、订单与修订、参加方与各自的分支身份、每步的状态、操作者与请求的幂等键、开始时刻与期限。

| 过程状态 | 含义 |
| --- | --- |
| `reserving` | 正在向各参加方预占 |
| `committing` | 全部 `held`，正在确认 |
| `confirmed` | 全部 `committed`，订单确认已在本地提交（与审计、Outbox 同事务） |
| `rejecting` | 有参加方拒绝或分支已到期，正在释放其余分支 |
| `rejected` | 释放完成，订单未确认，附原因 |
| `cancelling`、`cancelled` | 用户取消：向全部参加方发取消，完成后 `cancelled` |

推进规则：

1. 创建过程与“订单进入确认中”在一个本地事务中提交；确认期间订单不能被修改。
2. 并行向各参加方发预占。任一返回 `rejected` 或 `cancelled`：转 `rejecting`，对其余分支发取消。
3. 全部 `held`：转 `committing`，并行发确认。任一返回 `expired`：转 `rejecting`，释放已确认与已暂存的分支，原因为“处理超时”；不自动重新预占，由用户重试（一次新的确认过程）。
4. 全部 `committed`：在一个本地事务中把订单标为已确认、写审计与 Outbox，过程转 `confirmed`。**只有这一步之后才能返回“已确认”。**
5. 任何一步结果未知：按分支身份查询；查询仍失败则按[协议 01](01-background-work.md) 的 `idempotent_external` 工作项退避重试，过程保持当前状态。

## 同步路径与恢复（D12）

| 情形 | 返回给用户 |
| --- | --- |
| 预算内完成第 4 步 | 已确认 |
| 预算内有参加方明确拒绝，释放已完成或已排入 | 未确认，附原因（缺货、超额度） |
| 预算用完或有结果未知 | 处理中，附过程身份；后台按同一过程继续，用户可查询；同一幂等键的重试返回同一过程 |

同步路径与后台恢复执行的是同一个过程、同一套状态转换，不是两套逻辑。消息系统短暂故障不影响确认：预占与确认是同步调用；确认之后的事件进入 Outbox，按 D14 积压与补发。

## 取消、到期与修订

- **确认中取消**：过程转 `cancelling`，对全部参加方发取消。取消可能先于预占到达参加方，参加方留下墓碑，迟到的预占被拒绝（参考模型的“无墓碑”坏变体会让迟到预占重新占住额度）。
- **已确认后取消**：对全部分支发取消，已消耗的部分不能取消，需要退货或冲销等业务流程。
- **暂存期限**只覆盖“预占到确认”之间的协调时间，包括协调者崩溃后恢复的时间；过程恢复时若发现分支已到期，按第 3 步处理。
- **已确认订单的修订**（D33：未执行的普通单据默认原单修订重审）：重审通过后，销售以新修订对各分支发调整。减少数量或金额直接释放差额；增加的部分按预占规则检查，不足则修订不能生效，原确认保持。已部分执行的明细只能修订未执行部分。

## 消耗与后续

- **发货**：库存在出库事务中消耗对应分支的数量，出库单引用分支身份。
- **开票**：信用占用从“订单占用”转为“应收占用”，由信用组件在应收形成时消耗分支金额（协议 05，待写）。
- **财务**：订单确认产生的入账事实由财务异步处理，业务状态与入账状态分开显示（D13）。

## 参考模型

[订单预占模型](../work/checks/16-order-reservation.py)（种子 20261013，3,000 次运行）：多张订单竞争有限的库存与信用额度；响应随机丢失，协调者随机崩溃（预占与确认之间可能相隔多轮），暂存随机到期，取消随机在确认前后到达。

| 检查 | 结果 |
| --- | --- |
| 暂存加确认占用不超过库存与信用额度 | 成立 |
| 已确认订单的全部分支都是确认占用，并保持到订单取消 | 成立 |
| 系统静止后，未确认订单不残留暂存或确认占用 | 成立 |
| 取消之后迟到的预占被拒绝 | 成立 |
| 重复命令不会重复占用 | 成立 |

5 个坏变体全部被发现：预占后即确认订单（依赖暂存）、参与方自行到期确认占用、无取消墓碑、允许从已到期状态确认（造成超卖）、预占不幂等。第一轮“允许从已到期状态确认”未被发现，原因是模型中预占与确认总在同一轮完成；拆到不同轮并允许中间崩溃后，超卖被发现。模型不是 SDK、数据库或网络的运行结果。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| RS01 | 两张订单抢最后一件库存 | 只有一张预占成功；另一张未确认并附缺货原因 |
| RS02 | 库存预占成功、信用额度不足 | 释放库存分支；订单未确认 |
| RS03 | 预占成功的响应丢失 | 按分支身份查询得到 `held`；不重复占用 |
| RS04 | 取消先到参加方，预占迟到 | 墓碑使预占被拒绝 |
| RS05 | 协调者在全部 `held` 后崩溃，恢复时一方已到期 | 释放其余分支，订单未确认，原因“处理超时” |
| RS06 | 全部确认占用后、本地确认提交前崩溃 | 恢复后完成第 4 步；不重复确认，不丢失占用 |
| RS07 | 同步预算用完 | 返回处理中与过程身份；后台完成后可查询结果 |
| RS08 | 用户用同一幂等键重试确认 | 返回同一过程的结果 |
| RS09 | 确认中修改订单 | 拒绝，提示确认中 |
| RS10 | 已确认订单长期未发货 | 参与方不自行释放；由销售按订单生命周期取消 |
| RS11 | 已确认订单修订减少数量 | 释放差额；原确认其余部分不变 |
| RS12 | 已确认订单修订增加数量，库存不足 | 修订不能生效，原确认保持 |
| RS13 | 已部分发货的订单取消 | 只释放未消耗部分；已发货部分走退货 |
| RS14 | 只有服务明细的订单，库存未安装 | 只走信用分支（若有）即可确认 |
| RS15 | 含实物明细的订单，库存未安装 | 装配阶段已禁止该类型；运行时拒绝 |
| RS16 | 多行订单，两个并发请求以相反顺序锁定产品 | 固定加锁顺序，不死锁；全部满足或全部拒绝 |
| RS17 | 同一分支身份、不同数量的预占 | 冲突拒绝 |
| RS18 | 消息系统不可用时确认订单 | 确认照常；确认事件进入 Outbox 等待补发 |
| RS19 | 发货扣减与分支消耗 | 同一出库事务；出库单引用分支身份 |
| RS20 | 开票后的信用占用 | 由协议 05 转为应收占用，分支金额被消耗 |

## 仍未解决与下一步

- 审批与预占的先后（审批通过后才预占，或提交审批时先暂存）作为订单策略选项，具体默认值随销售组件设计确定。
- 部分满足与补货、批次与序列号在预占阶段还是拣货阶段分配，随库存与复杂仓储（D45）的协议确定。
- 信用组件的额度计算（多法人、多币种、应收与订单占用的合并）随信用组件设计确定。
- 分支状态与命令的正式字段，按安全 09 的编码约定在冻结时写出。

## 依据与独立判断

原书第 4 章的“同步失败必有补偿”“超时先查状态再补偿”“幂等”“定时对账兜底”在本页落实为分支身份、查询接口、取消墓碑与过程恢复。原书提到的 TCC 变种在本项目中不作为全局保证：这里是带语义的持久预占，允许中间状态可见（订单“确认中”），而不是要求所有参与方同时提交。Odoo 的预留与缺货策略、ERPNext 的库存预留是参考对象（原书第 5.11.1 节已列出这些分歧），本页只取“占用由资源属主裁决”的共同点，具体策略留给订单与库存的配置项。
