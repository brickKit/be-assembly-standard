# 出账、核销与成本调整

> 状态：2026-10-13 数据与业务协议第五份候选，尚未冻结。承接问题 I23 的出账、核销与成本分支，C13、C14、C17、C18、C28，以及 D02、D03、D13、D46–D51；把[财务与结算专篇](../replacements/finance-and-settlement.md)确定的职责分工落成跨组件协议。按 D59 从零设计。

## 本页解决什么

财务相关的事实分属几个独立组件（D46–D51）：来源业务（销售、项目）拥有可出账的依据；客户出账组件拥有正式账单；财务拥有应收应付、核销与总账；收付款组件拥有资金结果；信用组件拥有额度与占用；存货成本组件拥有成本子账。本页回答它们之间的四条衔接：

1. 多次部分出账、来源同时被修改时，怎样保证不超额、不重复出账？
2. 订单从“信用占用”变成“应收占用”的过程中，客户的总占用怎样保持正确？
3. 一笔资金核销多张单据、部分退款或冲正同时发生时，怎样不多分、不漏分？
4. 成本怎样在消息乱序、补发票、迟到流水的情况下算对？

## 共同规则：不可遗漏的增量事实

本页所有跨组件传递的财务事实（已出账、应收形成、资金到账、核销、出入库流水、成本结果、供应商票据确认）都是**不可遗漏的增量事实**，按[事务与消息](../05-transactions-and-messaging.md#事件分类重放与去重寿命)的分类处理，而不是可覆盖的状态投影（[协议 02](02-projections.md) 的规则不适用）：

- 每条事实有稳定的事实身份，由产生方在其业务事务中生成。
- 接收方在同一个本地事务中写入去重记录（Inbox）与业务效果；去重记录的保留期按业务要求，资金与账务事实长期保留，不随 30 天的请求幂等键过期。
- 需要按顺序处理的事实（成本计算的流水）带连续序号，接收方按序处理，发现缺口就等待或按序号向产生方补取。序号与[协议 02](02-projections.md#来源一侧编号纪元与补取) 的发布位置一样在锁内分配、写作（纪元，序号），纪元的定义与定序相同：产生方的库异步切换或恢复后，丢失的流水连同序号回退，新纪元的序号从 1 开始。按序号范围查询的响应声明产生方当前的纪元，接收方只采用更大的纪元（规则同协议 02 的纪元变化）；采用后按序号范围查询与对账，从新纪元重新对齐。流水“是否存在”按**事实身份**判断，不按序号：事实已复制、只是编号丢失而在新纪元重新编号的同一流水，按身份去重，不冲销；已处理、但新纪元中按身份也不存在的流水，按协议 15 第 9 步列入损失范围，并以冲销更正已据此计算的结果（例如重新计算受影响的移动平均成本），不静默保留。
- 产生方提供按事实身份或序号范围的查询，接收方据此对账，补回运输中丢失的事实。

## 一、出账额度：来源裁决的认领

**来源维护“可出账台账”**。每条来源明细（订单行、项目里程碑、订阅期）记录：

| 字段 | 含义 |
| --- | --- |
| `billable` | 按出账政策可以出账的数量或金额（例如按订单或按已交付） |
| `claimed` | 出账草稿已认领、尚未正式化的部分（含已确认、不再自动到期的认领） |
| `billed` | 已正式出账的部分（扣除已更正冲回的） |

来源在本地事务中保证 `claimed + billed ≤ billable`。

**认领沿用[协议 04](04-order-reservation.md) 的分支模式**，认领身份由出账组件生成：

| 命令（出账 → 来源） | 规则 |
| --- | --- |
| 认领 | 按认领身份幂等；额度不足则拒绝；同一身份、不同数量按冲突拒绝 |
| 确认 | 出账组件给账单正式编号**之前**发出；来源把认领转为“已确认”，不再自动到期，只能由出账组件显式释放或正式化；认领已到期则拒绝，出账组件不编号 |
| 正式化 | 出账组件在本地提交正式账单（含正式编号）之后发出；来源把已确认的认领转为已出账；重复无害 |
| 释放 | 草稿作废或未确认的认领超过期限；已确认的认领只能由出账组件显式释放；只能释放尚未正式化的认领 |
| 冲回 | 正式账单被更正（贷项）时，按更正身份把已出账数量冲回，`billed` 减少 |

**来源修改的约束**：来源要把 `billable` 改小（交付更正、订单修订、取消）而低于 `claimed + billed` 时，修改被拒绝，提示先更正出账或释放草稿。不能让出账依据一个已经变小的来源继续正式化（参考模型的“来源减少不核对认领”坏变体会超额出账）。

**草稿认领的期限**：草稿长期不正式化会一直占着额度，所以未确认的认领带期限（起始 7 天，可续期）；到期由来源的工作项释放。**确认与到期**在来源的同一行上原子裁决，与协议 04 的暂存规则相同。确认按认领身份幂等：应答丢失时用同一身份重试，结果相同。已确认、但出账组件此后放弃的认领，由出账组件的恢复工作项在期限内显式释放或正式化，不会永久占额度。**出账组件本地，已确认的草稿只能以一次原子状态变更走向“已编号”或“已作废”之一**：恢复工作项先在本地把超期未编号的草稿改为已作废，提交后才向来源释放认领；编号事务同样只接受“已确认”状态。不能不经本地作废就释放——那会与正在进行的编号竞争，释放后额度被另一张草稿认领，两张正式账单覆盖同一数量。

**正式化的顺序**（与协议 04 让确认占用不自动到期同一理由）：

1. 出账组件向来源发“确认认领”；来源在同一行上原子裁决：未到期则转为已确认，已到期则拒绝。
2. 确认成功后，出账组件在本地提交正式账单（含正式编号）。
3. 再向来源发正式化，来源把已确认的认领转为已出账。

第 2、3 步之间崩溃时，认领仍是已确认、不会到期，由出账组件的恢复工作项（协议 01）重发正式化；不会出现“来源已记已出账、账单却不存在”，也不会出现认领到期后另一张账单认领同一额度、两张正式账单覆盖同一数量。第 1 步之后出账组件放弃（例如编号前作废）时，显式释放已确认的认领。

## 二、应收形成与信用占用的转换

1. 出账组件正式化账单后，发布“已出账”事实（账单身份、法人、客户、币种、金额、关联的订单与信用分支）。
2. 财务接收后，在一个本地事务中形成应收与必要的总账意图，发布“应收已形成”事实。业务状态与入账状态分开显示（D13）。
3. 信用组件接收“已出账”事实，在**一个本地事务中**消耗对应订单信用分支的金额、增加该客户的应收占用。客户总占用 = 确认占用的订单分支 + 未结清应收，这个总数在转换前后不变。
4. 财务核销或冲销后发布“应收结清／重开”事实，信用组件据此减少或恢复应收占用。

把第 3 步拆成两个事务（先加应收、后消耗分支），中间崩溃会让占用被重复计算，客户被错误地判为超额；反过来则会少算、放出超额信用（参考模型的“转换拆成两步”坏变体）。“应收结清”事实先于“已出账”到达时，信用组件暂存它，等对应的应收占用建立后再处理。

## 三、核销：财务本地事务内的分配

资金事实（到账、付款、退款、冲正）由收付款组件产生，进入财务。核销在财务的一个本地事务中完成：

1. 按固定顺序（单据身份升序）锁定所涉的应收或应付明细行与资金事实行。
2. 在锁内读取各自的未核销余额与未分配余额，分配金额不超过两者的较小值。
3. 写入分配记录（分配身份幂等）、更新两侧余额、写总账意图与审计，并发布“已核销”事实。

| 情形 | 规则 |
| --- | --- |
| 同一笔资金分给多张单据 | 每次分配都在锁内核对未分配余额，总分配不超过资金金额 |
| 部分退款或资金冲正 | 产生反向分配记录，原分配保留；被冲回的应收恢复为未结清，并发布“应收重开” |
| 币种不同 | 按法人账簿规则（D51）声明汇率来源与日期，汇兑差额单独入账；不在核销时临时取汇率 |
| 资金暂挂（无法识别付款方） | 资金事实保持未分配，进入暂挂，不自动分给任何单据 |

在事务外先读余额、再写分配，两个并发核销会各自看到“还够”，合计超分（参考模型的“事务外核对余额”坏变体）。

## 四、存货成本

**输入**：库存的出入库流水（每条带“产品 + 法人”的连续计价序号）；采购收货的暂估单价；供应商票据经财务应付匹配后的实际单价（D50）；运费等费用分摊。

**计价序列**：库存固定按“产品 + 法人”为每条流水分配**计价序号**（一条连续序列），与成本组件是否安装、计价范围怎样声明无关；成本组件的计价范围只能等于或细于法人，细分时按过滤得到子序列，顺序不变。同一法人内不同库位的流水共用这一条序列，先后由库存的提交顺序确定；每条流水另带供关账使用的**参与方序号**（协议 06）。范围内的调拨不改变计价，在同一序列内记为一笔（或成对的两笔连续序号），跨计价范围的调拨在两条序列各记一笔，按出方的成本转入。按库位分序列时，同一计价范围内库位甲的入库与库位乙的出库先后没有定义，移动平均结果会随处理交错而变。

**计算**：成本组件按每个“产品 + 法人”（或其过滤得到的计价范围子序列）的计价序号顺序计算。乱序到达的流水先缓存，等前面的序号到齐再处理；缺口超过等待期限时，按序号向库存补取。按到达顺序直接计算，移动平均等方法的结果会随消息顺序而变（参考模型的“按到达顺序计算”坏变体）。

**暂估与调整**：

- 收货时按暂估单价入账，标记为暂估。
- 票据到达后计算差异：对仍在库的部分调整库存价值；对已经出库的部分，按成本政策计入当期销售成本差异。差异作为新的成本事实发布，不改写原流水与原成本事实。
- 迟到的倒填流水（业务日期早于已处理流水）：期间未关闭时，在该期间内重新计算受影响的出库成本并发布调整事实；期间已关闭时，按[协议 06](06-period-close.md) 的迟到规则计入下一开放期间。改写历史（重算并替换）与追加调整层是两种成熟做法（原书 5.11.1 节列出的分歧），标准实现采用“追加调整”，不改写已发布的成本事实。

**输出**：每条出库的成本事实与每次调整事实，带稳定身份，发给财务过账。财务以这些事实为存货与销售成本的唯一依据，不另算同一口径的成本（D46）。成本组件与财务按期间对账：成本子账余额与总账存货科目一致。

**成本组件未安装**：需要存货成本的能力（例如按实际成本过账）不能启用；不能返回虚构的成本（D46）。

## 五、供应商票据与应付

供应商票据的登记、匹配与应付确认在财务应付内部完成（D50）。匹配依据是采购订单、收货或服务验收的事实；匹配通过后形成应付，并向成本组件发布“票据单价确认”事实，触发第四节的暂估调整。匹配差异超出容差时，票据进入差异处理，不形成应付；付款经收付款组件执行，结果作为资金事实回到财务核销。

| 参数 | 起始值 |

## 参考模型

[出账、核销与成本模型](../work/checks/17-billing-settlement-costing.py)（种子 20261013，每个子模型 2,000 次运行）：

| 检查 | 结果 |
| --- | --- |
| 出账：并发认领、正式化、作废与来源修改下，`claimed + billed` 不超过 `billable`；同一认领身份不会有两份有效认领 | 成立 |
| 信用：重复与乱序的“已出账”“应收结清”事实下，客户总占用在每一步都等于真实值 | 成立 |
| 核销：并发分配与冲正下，应收与资金的分配都不超额 | 成立 |
| 成本：乱序到达的流水按序号处理后，移动平均成本与按顺序处理一致 | 成立 |

5 个坏变体全部被发现：认领不幂等（重复出账）、来源减少不核对认领（超额出账）、信用转换拆成两步（占用错算）、事务外核对余额（超分）、按到达顺序计算成本。第一轮“认领不幂等”未被发现（额度检查仍在，不会超额）；补上“同一认领身份最多一份有效认领”的检查后被发现。模型不是 SDK、数据库或真实账务规则的运行结果。

[出账正式化模型](../work/checks/36-billing-formalization.py)（种子 20261013，3,000 次运行）：认领会到期，来源可长时间不可达，确认请求可迟到到认领到期之后，应答可丢失并按同一认领身份重试，已确认的草稿可被放弃，恢复工作项按“先本地作废、再释放”收尾。

| 检查 | 结果 |
| --- | --- |
| 正式账单覆盖的数量从不超过可出账额度 | 成立 |
| 来源可达后，每个已确认的认领最终已出账或已释放 | 成立 |

5 个坏变体全部被发现：先编号后正式化、已确认的认领仍会到期、恢复不释放被放弃的已确认认领、应答丢失后换新认领身份重试（旧认领被遗弃）、恢复不经本地作废就释放已确认的认领（与编号竞争）。各轮修改的经过见[证据记录](../work/evidence.md)。

**模型没有覆盖的条款**：成本模型只建了一条“产品 + 库位”序列，没有建出同一计价范围内多库位共用序列与跨计价范围调拨（BL22、BL23），靠实现测试。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| BL01 | 两张草稿并发认领同一订单行的剩余数量 | 只有不超额的认领成功 |
| BL02 | 同一草稿重试认领 | 返回原认领，不重复占用额度 |
| BL03 | 订单减量低于已认领加已出账 | 订单修改被拒绝，提示先更正出账 |
| BL04 | 正式账单已提交、向来源正式化前崩溃 | 恢复后重发正式化；不出现来源已记出账而账单不存在 |
| BL05 | 草稿超过认领期限 | 来源释放认领；草稿正式化被拒绝 |
| BL06 | 正式账单更正（贷项） | 按更正身份冲回已出账数量，原账单保留 |
| BL07 | 信用组件先收到“应收结清”再收到“已出账” | 暂存结清事实，应收占用建立后处理；总占用始终正确 |
| BL08 | “已出账”事实重复到达 | 去重，不重复消耗分支或增加应收 |
| BL09 | 同一笔资金同时核销两张应收 | 锁内核对，总分配不超过资金金额 |
| BL10 | 已核销的资金被冲正 | 反向分配记录，应收重开，信用占用恢复 |
| BL11 | 外币应收与本币资金核销 | 按声明的汇率来源入账汇兑差额 |
| BL12 | 无法识别付款方的到账 | 暂挂，不自动分配 |
| BL13 | 出库流水乱序到达成本组件 | 按序号处理；结果与顺序处理一致 |
| BL14 | 流水序号缺口超过等待期限 | 按序号向库存补取，缺口补齐前不计算后续出库成本 |
| BL15 | 收货按暂估入账，票据单价不同 | 在库部分调库存价值，已出库部分计成本差异；原事实不改写 |
| BL16 | 期间已关闭后到达的倒填流水 | 按协议 06 计入下一开放期间 |
| BL17 | 成本组件未安装，启用按实际成本过账 | 装配拒绝；不返回虚构成本 |
| BL18 | 供应商票据与收货差异超容差 | 进入差异处理，不形成应付 |
| BL19 | 财务事实的去重记录在 30 天后 | 仍然保留，重投的旧事实不再生效 |
| BL20 | 成本子账与总账存货科目不一致 | 对账报告差异，告警，不自动改写任何一方 |
| BL21 | 认领在出账组件本地提交与正式化之间到期 | 不会发生：编号前先确认认领，已确认的认领不自动到期；确认时已到期则不编号 |
| BL22 | 同一法人内两个库位的入库与出库交错到达 | 按库存分配的同一条计价序号处理，结果唯一 |
| BL23 | 跨法人调拨（或跨细分的计价范围） | 两条序列（或子序列）各记一笔，转入成本取出方的成本 |
| BL24 | 确认应答丢失 | 用同一认领身份重试，来源返回同一结果；不换新身份认领 |
| BL25 | 恢复工作项释放超期未编号的已确认认领，同时用户正在为该草稿编号 | 本地先把草稿改为已作废，编号事务看到已作废即失败；不会出现已释放的认领又被编号 |
| BL26 | 确认请求迟到，到达时认领已到期并被另一张草稿认领 | 来源拒绝确认，出账组件不编号，草稿作废 |
| BL27 | 库存库异步切换，成本组件已处理的两条出库流水在新纪元中不存在，新纪元的流水重用了它们的序号 | 成本组件只采用更大的纪元，按序号范围对账重新对齐；丢失的流水列入损失范围并冲销据此算出的成本，不把新流水当作已处理 |
| BL28 | 库存库异步切换，一条流水的事实已复制、只是编号丢失，在新纪元重新编号 | 按事实身份去重，不当作丢失，不冲销 |

## 仍未解决与下一步

- 出账政策（按订单、按交付、按里程碑、按周期）与可出账台账在各来源组件中的具体形态，随销售、项目组件设计确定。
- 成本方法的选择（移动平均、先进先出、标准成本）属于成本组件的实现与替换（D27、D46），本页只规定输入、顺序、调整与输出的协议。
- 汇率来源、汇兑差额的科目与日期规则，随多币种设计统一。
- 税额（D49）在出账中的位置：税计算的结果作为出账明细的一部分，由出账组件在正式化前取得并绑定规则版本。

I23 的出账、核销与成本分支有了协议与模型；期间关闭见协议 06。未运行 SDK、数据库或真实账务验收，不标关闭。
