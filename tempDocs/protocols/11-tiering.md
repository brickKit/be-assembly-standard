# 冷热转层

> 状态：2026-10-13 数据协议第十一份候选，尚未冻结。承接 C22（热温冷与保留）、C23（冷查询与数据治理）、I17（冷数据不应只靠年龄决定）、I21（转层的写／读／保全竞争、分区唯一与定位），以及[数据与生命周期](../04-data-and-lifecycle.md#冷热分层设计)已写的推荐（存储路线、归档单元、阶段表、摘要与查询原则）；按 D59 从零设计。

## 本页解决什么

数据正文已经给出方向：按业务完整的单元转层，不按年龄；先复制、校验、发布，再退出在线层；目录决定读哪一份。本页把它落成协议：

1. 一个单元什么时候可以封存？封存之后迟到的写入去哪里？
2. 复制、校验、发布、释放在线层各由谁、在什么事务里做？工作者失效时怎样不留下错的目录？
3. 读取（按 ID、列表、导出）怎样在转层期间既不漏、也不重复？
4. 保全、保留到期、销毁、擦除和恢复怎样与转层互不破坏？

## 方案比较

| 路线 | 判断 |
| --- | --- |
| 推荐：属主组件的单元目录是唯一权威；封存与写入共用同一个控制点；工作项带代次推进，发布时核对代次；读取按目录快照选层；释放在线层等读取租约结束；销毁在决定事务中检查保全 | 每一步的竞争都有确定的裁决；转层可以中断、重做；不同存储路线共用同一套协议 |
| 按时间批量搬走（例如每月搬走 6 个月前的数据） | 简单，但会搬走未完成的单据、仍在使用的去重证据；读者不知道去哪里找 |
| 归档任务自己判断封存，写入路径不检查 | 封存之后的迟到写入只进了在线层，复制品没有，删除在线层后丢失（参考模型的“只有归档任务检查封存”坏变体） |
| 用数据库的分区摘除代替目录 | 分区是存储手段，不表达业务完整、保全与读取路由；仍然需要目录 |

## 数据类别与转层资格

每个组件为自己的每类数据声明转层类别；年龄只是挑选候选的条件之一，不单独决定转层。

| 类别 | 例子 | 能否转层 |
| --- | --- | --- |
| 在线可变 | 主数据、未完成单据、余额、预占、待处理任务 | 不转层 |
| 长期证据 | 业务唯一登记（单号、外部事实 ID）、幂等与去重记录、别名与墓碑 | 不转层；按自己的保留规则清理 |
| 已完成历史 | 已关闭的订单、已过账的凭证、已完成的流水 | 满足下文的封存条件后可以转层 |
| 审计与证据 | 审计记录、外部回调原始报文 | 按[协议 03](03-audit-durability.md) 与[协议 10](10-external-integration.md) 的保留规则；可以转层 |
| 可重建副本 | 投影、搜索索引、分析副本 | 不转层；需要时重建 |

业务唯一登记不随单元移出在线层：分区表的唯一约束必须包含分区键，单号与外部事实 ID 的唯一性由不分区的登记表保证，登记与业务写入同事务（数据正文的唯一性一节）。

## 归档单元与目录

**归档单元**是属主组件选定的一组聚合，例如“法人甲 2026 年 3 月关闭的销售订单及其明细”。它可以与数据库分区重合，也可以不重合；分区为增长与维护服务，单元为业务完整服务。

属主组件的**单元目录**为每个单元保存一条记录：

| 字段 | 说明 |
| --- | --- |
| 单元 ID | 属主生成 |
| 数据类别与选择条件 | 哪类数据、哪个法人与期间、哪些聚合 |
| 成员数与内容摘要 | 封存时计算；摘要按[安全 09](../security/09-encoding-and-profiles.md) 的规范编码，对按主键排序的规范行计算 |
| 状态 | `open`、`sealed`、`published`、`released`、`destroyed` |
| 路由 | 当前权威副本所在的层与清单版本 |
| 代次 | 每次认领加一；发布时核对 |
| 清单 | 对象位置、编码与结构版本、摘要版本、行数、子表完整性 |
| 保留类别 | 最短与最长保留、起算日期 |
| 保全 | 正交于状态的保全记录列表（见下文） |

**定位索引**（记录 ID → 单元）随发布在同一事务中更新，按 ID 读取时不依赖 ID 中的时间推测位置。

## 封存与写屏障

封存在属主的一个本地事务中进行：

1. 检查封存条件：单元内全部聚合处于终态；没有引用它们的未完成工作项、待发事件或未结束的预占；需要期间关闭的数据（财务）所属期间已关闭（[协议 06](06-period-close.md)）；跨组件引用已对账。
2. 计算成员与摘要，状态转为 `sealed`。

**写屏障**：属主的每一个写入口（接口、事件消费者、后台工作、导入）在写入单元内的聚合时，在自己的事务里检查单元状态，与封存使用同一行的锁或版本。封存先提交，则迟到的写入不改原记录，而是写成**更正记录**：放在当前开放的单元里，引用被更正的记录；业务是否允许更正由业务规则决定（例如已关账期间按协议 06 顺延）。写入先提交，则封存时重新计算成员与摘要。

只让归档任务检查封存、写入路径不检查，会让封存后的写入只进入在线层而没有进入复制品（参考模型的坏变体）。

## 复制、校验与发布

转层由工作项（[协议 01](01-background-work.md)）执行，认领时得到租约与代次：

1. **复制**：在数据库事务外读取封存的成员，写入目标层；对象位置包含单元 ID、代次与清单版本，写入后不覆盖。
2. **校验**：完整读回目标副本，核对行数、主子完整性、内容摘要，以及按 ID 定位与授权过滤所需的列。任何差异都保留源数据，工作项失败并告警。
3. **发布**：在属主的一个本地事务中检查“状态仍为 `sealed`、代次等于目录中的代次、源摘要未变”，然后写入清单、把路由改为目标层、更新定位索引，状态转为 `published`。

租约过期的旧工作者可能仍在运行；它的发布因代次不符而被拒绝，它写下的对象成为孤儿，由清理工作在验证窗口后删除（参考模型的“发布不核对代次”坏变体会让旧工作者的不完整副本成为权威）。

## 释放在线层

发布后在线数据仍保留一段宽限期。满足以下全部条件时，才删除在线层的行（单元等于分区时，摘除分区）：

- 宽限期已过；
- 没有仍按旧路由读取的读取租约（长读取、导出在开始时登记租约，结束或过期时释放）；
- 已有一次包含新清单与目标副本的备份完成，恢复到此刻之后不会出现“目录指向在线层而在线层已删”的组合。

完成后状态转为 `released`。只等宽限期、不看读取租约，会让正在进行的长读取读到不完整的结果（参考模型的坏变体）。摘除分区的锁与适用限制按目标数据库版本核对，不在请求路径上执行。

## 保全、保留与销毁

- **保留类别**由组件为每类数据声明：最短保留（之前不能销毁）、最长保留（之后必须销毁或匿名化）、起算日期（单据关闭、期间关闭或合同结束）。没有法规或客户合同依据的年限标为待确认，由客户在上线时确定（协议 16）。
- **保全**是独立的记录：来源（法律、审计、纠纷）、范围（单元、客户、单据）、授权人、开始与解除。保全期间不能销毁，也不能做会丢失内容的擦除；保全优先于最长保留，冲突时告警并由有权限的人处理。
- **销毁**：工作项在一个事务中检查保留已到期、没有生效的保全、需要的批准已完成，然后把单元转为 `destroyed`，目录保留墓碑（单元 ID、范围、摘要、销毁依据与时间），再删除对象。保全检查必须在这个决定事务中进行；先查保全、过一段时间再删，会删掉中间被保全的单元（参考模型的坏变体）。
- **擦除**：个人信息的合法擦除（[协议 07](07-references.md#销毁与擦除)）落在封存单元上时，生成新的清单版本（擦除后的副本），旧版本在保全与恢复规则允许后清理；摘要随新版本重算，擦除记录保留旧摘要与依据。
- 销毁与擦除记录存放在独立的恢复责任中，从备份恢复后重新执行（协议 15）。

## 读取

### 按 ID

经定位索引找到单元，按目录路由读取。路由指向冷层而对象缺失时是故障，返回“暂时无法读取”并告警，不回答“不存在”。

### 列表与导出

- 列表的默认范围是“未关闭，或最近 N 天内创建”（数据正文已定），所以常用的“全部未收款发票”不会因为单据很旧而漏掉；明确请求历史时才进入冷层。
- 一次列表或导出在开始时取得**目录快照**（目录版本），每个单元只按快照中的路由读取一次。同时读在线层与冷层、不按目录去重，会在宽限期内把同一单元算两次（参考模型的坏变体）。
- 游标绑定筛选、稳定排序键、目录版本与授权上下文；目录在分页之间变化时，用快照继续或要求重新开始，不跳到另一套集合。
- 冷层可以更慢或异步，但必须明确告诉调用者：同步结果完整，或返回异步任务，或返回“不能完整完成”；不能静默返回部分数据。
- 授权按当前授权：冷读取同样应用[安全 07](../security/07-finite-expressions-containment-and-queries.md) 的段编译与字段掩码；冷读取器不能执行某个谓词时，在受控工作者中读后过滤，不放宽。
- 冷读取由属主组件的冷读取端口执行（嵌入式读取或受控工作者），按资源预算限并发；不接受调用方的任意 SQL 或对象地址。

### 解冻

解冻把单元复制到受限的临时读取区，有到期时间，只读；不重开原业务写入。需要修改历史单据时走业务更正流程，产生更正记录。

## 结构演进

清单记录编码、结构与摘要版本。读取旧版本由属主的转换器完成，转换后的结果另行校验；丢列或填默认值后不再要求与原摘要相同，原摘要仍用于核对原副本。新版本发布前，用每个仍在保留期内的旧结构版本的样本验证读取。

## 存储路线的更换

同一 PostgreSQL 的分区、独立的历史 PostgreSQL、对象存储 Parquet、表格式（Iceberg 等）都是目录中的路由类型。从一种路线换到另一种，是同一个协议：把已发布单元当作源，复制、校验、发布到新路线，再释放旧路线。路线的选择条件见数据正文的存储路线表。

## 恢复时的核对

恢复后，目录、清单、定位索引与实际对象一起核对：

| 发现 | 处理 |
| --- | --- |
| 目录指向冷层，对象缺失 | 故障；暂停该单元的读取，从备份或副本恢复对象 |
| 对象存在，目录未发布 | 待清理的孤儿或未完成的转层；不直接开放读取，按工作项重做或清理 |
| 目录为 `released`，在线层仍有行 | 释放未完成；继续释放 |
| 销毁记录晚于恢复点 | 重新执行销毁 |

| 参数 | 起始值 |

## 参考模型

[转层模型](../work/checks/23-tiering.py)（种子 20261013，3,000 次运行）：一个单元从开放到封存、复制、校验、发布、释放在线层、销毁；同时有迟到的写入、租约过期后的接替工作者（旧工作者继续运行）、长读取与跨层列表、保全的设置与解除。

| 检查 | 结果 |
| --- | --- |
| 被接受进单元的写入都在发布的副本中；封存后的写入成为更正记录 | 成立 |
| 每次读取封存单元都得到恰好它的行，不缺、不重复 | 成立 |
| 租约过期的工作者从不改变目录 | 成立 |
| 保全中的单元从不被销毁 | 成立 |

5 个坏变体全部被发现：只有归档任务检查封存、发布不核对代次、不等读取租约就删除在线层、列表不按目录快照读取两层、销毁使用较早的保全检查。第一版模型的调度过于随机，四个坏变体没有走到需要的交错；改为按参与者轮流推进后全部发现。模型不是数据库、对象存储或 SDK 的运行结果。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| TR01 | 一个月的订单大多已关闭，少数仍未完成 | 只封存已关闭的聚合；未完成的留在在线层 |
| TR02 | 封存后发生对已封存订单的更正 | 写成更正记录，原记录不变 |
| TR03 | 封存与写入同时提交 | 至多一方先赢；写入先赢则封存重新计算 |
| TR04 | 转层工作者在复制中途停顿，租约过期，另一个工作者接替 | 只有新工作者能发布；旧工作者的对象被清理 |
| TR05 | 校验发现行数相同但内容摘要不同 | 不发布；保留源数据并告警 |
| TR06 | 发布后有一个持续 30 分钟的导出仍按旧路由读取 | 在线层在导出结束或租约过期前不删除 |
| TR07 | 宽限期内列出全部历史订单 | 每个单元只出现一次 |
| TR08 | 按 ID 读取已转层的订单 | 经定位索引读冷层 |
| TR09 | 目录指向冷层但对象缺失 | 返回暂时无法读取并告警，不说不存在 |
| TR10 | 默认列表“未收款发票” | 包含很早创建、仍未关闭的发票 |
| TR11 | 冷读取不能完整完成 | 返回异步任务或明确的不能完成，不返回部分数据 |
| TR12 | 撤权后继续翻页冷数据 | 按当前授权检查；不因游标绑定旧快照而保留访问 |
| TR13 | 保留到期但有法律保全 | 不销毁 |
| TR14 | 销毁工作检查保全后、删除前设置了保全 | 删除决定在同一事务内检查，保全生效，不销毁 |
| TR15 | 已封存单元中有人申请个人信息擦除 | 生成新清单版本；保全中则推迟并告警 |
| TR16 | 从备份恢复到销毁之前 | 重新执行销毁 |
| TR17 | 恢复后发现未发布的冷对象 | 不开放读取；重做或清理 |
| TR18 | 解冻一个单元 | 只读、有到期时间；不重开写入 |
| TR19 | 读取旧结构版本的单元 | 经转换器读取，转换结果另行校验 |
| TR20 | 从同库分区换到对象存储 | 同一协议完成复制、校验、发布、释放 |
| TR21 | 单号唯一性 | 由不分区的登记表保证，登记不随单元转层 |
| TR22 | 去重与幂等记录按年龄搬走 | 不允许；按自己的保留规则清理 |
| TR23 | 财务凭证所在期间未关闭 | 不能封存 |
| TR24 | 没有法规或合同依据的保留年限 | 标为待确认，上线时由客户确定 |

## 仍未解决与下一步

- 各组件的数据类别、单元选择条件与保留类别，随组件设计逐个声明。
- 冷读取端口的第一个实现（嵌入式读取或受控工作者）与资源预算，随代表部署实验测量（D41）。
- Parquet 的规范结构、摘要的跨语言向量，随 SDK 共同契约（协议 18）统一。
- 保全记录的属主（各组件自持或共同能力）随全货架边界卡确定。

C22、C23、I17、I21 有了协议与模型；未运行数据库、对象存储或 SDK 验收，不标关闭。
