# 验证体系与证据管理

> 状态：审查框架；实际用例、命令和运行条件逐轮补齐。

被测对象从[组件／仓库清单](components/catalog.md)及各[选型专篇](replacements/README.md)的具体对象表绑定，不能只写“权限方案”“消息系统”或“外壳”作为验收对象。权限替换绑定[明确的 Authz 成员](replacements/authorization.md#哪些组件可以相互替换)，其他基础资源与 SDK 适配分别记录，不将抽象能力的测试当作所有候选实现通过。

## 三种验证阶段

第一份具体矩阵为[权限验收矩阵与反例](validation/authorization-matrix.md)。后续数据／事务／部署矩阵沿用本页的记录格式，按对象写真实预期，不把只列专项名称当作用例已经完成。

第二份为[数据、事务与恢复的反例](validation/data-and-consistency-matrix.md)，DT01–DT30 覆盖全局唯一、封存竞争、内容编码、目录切换、预占、出账／核销／关账、增量运输、长期去重和恢复。它们均为未执行规格。理论冻结候选与剩余阻塞统一见[底层推荐基线](09-foundation-baseline.md)。

设计审查检查覆盖、理由、模型、状态和跨层约束；最小实验验证可能推翻结构的关键假设；实现验收证明具体版本按规格运行。三者分别记录，不用某一类替代另一类。

从对象与能力展开测试：组件、协议／多实现、外壳、多实例任务、跨事务流程、持久数据、前端、客户 Fork 和交付环境。每条记录对象 → 必须证明的结果 → 测试或实验 → 责任方 → 档位与命令 → 环境／版本 → 证据与限制。

## 首批必须覆盖的专项

| 对象 | 最少要证明 |

| 替换与 Fork | 切换步骤、调用适配、权限／数据迁移、失败恢复和来源可追溯 |
| 业务停用与退出 | 标准停用后原组件受限查阅及合法维护、停用／提交竞争、未完业务与依赖处理、迟到事件／外部结果、历史单据／关联／对象与当前权限；完全卸载专项另验迁移部分失败、对账恢复和支持范围 |

| 报表与分析 | 不装额外 BI 的标准组合完成声明的基础报表，选配自助 BI 另验适配；指标口径／来源／版本和数据截至明确；页面、合计／下钻、缓存、导出／订阅不越权；更正／重建、冷热覆盖、重查询资源限制及工具替换分别验证 |
| 性能 | 按画像测关键链路、尾延迟、业务完成、资源、争用与长期运行 |
| 客户交付 | 安装／升级／必要的并存、普通业务角色新增权限确认、在途状态、备份恢复与承诺的环境范围 |
| 版本维护与修复 | 团队维护的稳定线与客户定制组合分别验修复效果、安全与业务回归、依赖／外壳传播、旧数据和在途状态、前端／扩展及失败恢复；升级候选与实际部署分清，客户选择后才实施，不以 AI 完成或主干通过代替组合验收 |
| 有限业务设置 | 管理权限、范围与关联校验、并发更新、版本／生效、历史依据、审计和升级迁移 |

## 代表性部署对照实验

> 状态：已定先于全量升级开展；规格初稿与具体实施计划仍需补齐，尚未实施或测量。完整性能基线仍按原排期，此实验用于部署选择与结构验证。

组件选配、运行拓扑、部署引擎分别作为变量，默认方案等实测后确定。实验先控制变量，再补代表性组合，不盲做完整笛卡尔积。

| 维度 | 代表范围 | 控制与限制 |
| --- | --- | --- |
| 组件选配 | 少组件的真实业务闭环；较完整的当前已实现组合 | 从所选版本的必需依赖闭包派生成员；不把未开发信用等未来组件假装装入，也不把少组件样板当成全部客户都适用 |
| 运行拓扑 | 全部单跑；兼容成员外壳合并；重任务等独立的混合形态 | 同一组成员、精确版本、配置、契约与基础资源；不借合并改变业务调用或事务语义 |
| 部署引擎 | Docker 对照；Podman 重点候选；Kubernetes 按支持目标另验 | 记录引擎／工具与宿主版本、实际运行方式、持久卷／网络／权限；引擎对比时固定拓扑、组件和负载 |

前置条件：先明确代表链路、目标协议与 SDK、组件及外壳版本。当前开发 SDK 尚未通过 widget 黑盒，四个外壳尚无真实成员组装；实验须补齐最小条件并验证。旧发布版本可形成标明限制的基线，不能证明目标架构。安全与一致性前提不满足时记录缺口，不跳过检查或用代桩签发客户方案通过结论。

执行顺序已定：先审清涉及的规格，按隔离的新实施计划补齐最小目标条件并验证代表格，用结果修订设计，再推广现有组件全量升级。具体版本、链路、命令、每项改动与耗时预算要在计划里明确，不直接恢复旧开发清单；完整容量与长期性能基线仍在阶段 06 后。

规模前提按[扩展准备和本机参考档位](03-deployment-and-resources.md#扩展准备与改选信号)组织：小到中型基础、业务广但低资源／容许等待、较高并发或诊断需求分别取代表组合。不能把客户人数、成员数量和容器数量混成一轴。本机资源不足的完整货架／多故障域实验明确留未测，不用拆批的结果假称 70 多组件已同机运行通过。

实验按以下顺序收敛：

1. 固定少组件组合与一个引擎，验证单跑的真实授权请求、跨组件调用和持久事件／业务完成，再比较外壳与混合；生成成功或健康不作为业务通过。
2. 固定组合与拓扑，对照 Docker 与 Podman；把必要适配、维护步骤和限制记录为交付成本，不只对比启动耗时。
3. 对较完整组合复核代表格，覆盖后台／批量／渲染等争用；改变成员数量时明确是哪一项带来差异，不与引擎差异混算。
4. 验证重启、资源争用、依赖中断、在途恢复、升级及拆回。未支持的格说明原因，结构性失败反馈到设计再测，不把“该格未跑”计为通过。

| 证据 | 必须比较的结果 |
| --- | --- |
| 正确性与安全 | 相同业务效果、拒绝与数据范围、事件／任务恢复、重复保护；性能好不能抵消行为错误 |
| 客户整套资源 | 空闲与代表负载的 CPU／内存／连接，数据库、身份、消息、存储与观测等基础资源，磁盘与维护对象 |
| 请求与业务完成 | 响应尾延迟、真正完成时间、错误与处理中比例、积压年龄；负载、数据形状及重复测量条件明确 |
| 物理独立性代价 | 成员故障影响哪些业务、资源争用、能否局部扩容／发布、组合升级与拆回步骤 |

输出包括精确版本与环境、命令／参数、选择的代表格、实际结果、限制、必要适配和待修复项；据此给出候选保留／拆分／淘汰理由。最低客户预算、容量与默认配置仍待确定，较完整样板也不代表未来全部货架已验证。

观测分档对照在固定部署条件下单独进行，不增加全部维度的笛卡尔积。各档演练组件／外壳重启后日志仍可查、受保护请求与跨成员故障可关联、事件／作业积压和磁盘容量风险可告警，以及采集或告警接收方故障时的丢失边界与恢复。记录各档资源、保存与查询条件、定位步骤和限制；完整方案通过不代表基本方案通过，基本方案精简也不取消业务审计验收。具体用例、阈值与命令待补，尚未执行。

## 组合变更的必测情形

> ST01–ST12 为理论验收规格，均未执行；沿用各专题的业务预期，绑定[共同切换流程](replacements/README.md#选配变更与替换的共同协议)，不另定义更宽的权限或事务语义。

| 编号 | 变化／反例 | 必须断言 |
| --- | --- | --- |
| ST01 | 少组件初装，缺所选业务必需依赖或权限能力；合格组合做正例 | 缺件拒绝并明确原因，合格闭环可用；缺 optional 能力只按声明降级 |
| ST02 | 已有授予／共享／字段规则后切到能力较少的 provider | 不丢规则、不静默放宽；未承接的状态阻止切换，显式改变业务范围另审 |
| ST03 | 同一法人配置两个权威、缺一个范围；多渠道多选 | 冲突／缺口阻止对应范围启用，多选按明确路由，不双执行 |
| ST04 | 新增消费者／渠道，又移除有待发／未知回调的旧成员 | 历史初始化及待处理责任明确，不自动重发全部历史，不丢结果或盲切重试 |
| ST05 | 复制后源又写入、旧 worker 延迟执行、目标部分发布 | 切点与版本／代次有效，未完成范围暂停，只有合格权威可写 |
| ST06 | 目标开始新写／已外部执行后请求退回旧方案 | 保留新事实，按可验证的恢复／反向转换处理，不只改旧地址或重放副作用 |
| ST07 | 单跑进外壳／拆回，成员版本和数据库目标不匹配 | 组合拒绝或走已支持路径，同版身份／状态／端口行为一致；共同池不误指其他库 |
| ST08 | 配置字段改对但运行仍旧；无效候选、跨成员部分生效 | 显示实际应用版本，错误不覆盖合格快照，部分不算完成，不放宽必需控制 |
| ST09 | 密钥同长度替换、读取失败、新旧连接及多副本更新不同步 | 检测实际版本，连接／签名与验证按规则切换，过期／撤销不无限沿用旧值 |
| ST10 | 新旧前端／SDK／worker 组合，旧版稍后恢复上线 | 能力／数据／作业及权限语义按准入处理，未知不伪装兼容，破坏性迁移后旧写者拒绝 |
| ST11 | 基本／完整观测切换，低资源广业务组合，作业预算收紧 | 必需审计／告警保留，不删除业务队列；背压和实际诊断／资源条件可验证 |
| ST12 | 停用／卸载组件后仍有历史依赖、附件、在途和更正 | 退出阻止或交接明确，历史与当前授权可用，依赖闭包不能仅按现有菜单判断 |

每项同时记录操作管理身份、源／目标精确组合、变化切点、正例／反例、副作用和对账、恢复服务条件及实际命令；未实现支持的格保留限制。ST 的适配与切换验证复用 PA／DT 的细节断言，不能只比生成物或健康检查。

## 证据状态

“规范写了”“测试存在”“执行通过”分别记；通过还要写对象、精确版本、参数、硬件／引擎、实际命令、结果与观察日期。待实现、待验证、不适用和需用户裁定都有明确说明。

目前一致性套件对 rawstub 的自测记录，不是对三个 SDK 的验收；生成文件、dry-run、健康检查也不是业务闭环或容量证据。旧测试是否仍证明新规格，需要检查断言后再承接。

## 独立复核与文档冻结

独立复核者从用户目标、冻结候选规格和证据进入，先找反例，再核对原作者的理由。可用新的会话完成，不要求增加 agent。当前沿用主会话逐步工作的方式。

冻结条件：所有适用项有设计与验收去处；结构性问题闭环；必要的先行实验通过；保留限制可理解；未完成实现明确排期；通过独立复核和用户确认。冻结的是设计基线，不是对尚未实现内容签发运行合格证明。
