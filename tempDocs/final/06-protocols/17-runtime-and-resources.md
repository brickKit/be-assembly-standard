# 运行与资源

同一组组件可以单独运行、合并进外壳、混合部署，也可以多副本运行。本页给出共同的运行规则：

1. 组件声明哪些资源预算？外壳怎样合并这些预算，避免一个成员饿死其他成员？
2. 过载、依赖故障、启动与停止时怎样表现？
3. 多副本运行时哪些工作只能有一个执行者，怎样保证？
4. 观测的最低要求是什么？性能与容量怎样测量和承诺？

依据的决定：D25（维护窗口）、D40（组件独立开发，外壳优先候选，测后定案）、D41（先做代表部署对照）、D42（联网路径优先）、D43（基本与完整观测方案）。部署形态与外壳的风险见[部署与运行](../04-foundations/01-deployment-and-runtime.md)。

## 方案比较

| 路线 | 判断 |
| --- | --- |
| **采用**：组件声明预算（并发、连接、队列上限、内存估计）；外壳为每个成员保留最低份额，前台优先、后台限额且保证进展；所有队列有上限，超出立即返回可重试的错误 | 外壳中一个成员的后台高峰不会拖垮其他成员的前台；后台不会被永久饿死；负载可预期 |
| 外壳中成员共用一个先来先服务的池 | 实现最简单；一个成员的批量工作会让其他成员的请求无限等待（参考模型的坏变体） |
| 后台只在前台空闲时运行 | 前台好看，但月结等后台工作在忙碌的系统中永远完不成（参考模型的坏变体） |
| 依靠多副本与 Kubernetes 自动扩容解决 | 扩容不能解决数据库写入热点、锁与跨组件事务；单副本迁入 Kubernetes 也不会自动获得高可用 |

## 组件的资源声明

每个组件在自己的声明中给出（数值随版本，客户可在合法范围内调整）：

| 声明项 | 说明 |
| --- | --- |
| 前台并发上限 | 同时处理的用户请求数 |
| 后台并发上限 | 同时执行的工作项与消费者处理数 |
| 数据库连接 | 最低保留、前台上限、后台上限 |
| 队列上限 | 前台等待队列与后台待领取的上限 |
| 出站并发 | 对每个下游组件与外部系统的并发上限 |
| 内存估计 | 空闲与满载的估计，用于外壳与部署的预算核对 |
| 超时 | 每类请求的处理时限（[协议 14 的数据库](14-data-foundations.md#数据库)规定的数据库超时之外） |
| 补取与探测 | 作为水位来源时补取接口的并发上限；作为消费者时需要水位的来源与新鲜度（[协议 02](02-projections.md#来源水位)） |

配置只能改变预算与选择，不能关掉权限检查、破坏事务不变量或降低交付保证。

## 外壳中的预算合并

- 外壳的总预算（数据库连接、内存、CPU）按客户基线声明；成员声明的最低保留之和不能超过总预算，否则装配检查失败。
- 共享池的形态（外壳级登录角色，事务内切到成员角色）见[协议 14 的数据库](14-data-foundations.md#数据库)。
- **前台优先、按成员轮转**：空闲连接先分给等待中的前台请求，成员之间轮转；每个前台成员保留最低份额，后台不能占用。
- **后台限额并保证进展**：后台使用的连接不超过声明的上限；只要前台保留之外有空闲，后台就能领取，不等前台完全空闲。
- **有界等待**：前台请求等待超过时限即返回可重试的错误（带重试时间），不无限排队。
- **出站与工作队列**同样按成员隔离。
- 外壳中的成员共享进程：一个成员的内存泄漏或不可恢复的崩溃会影响全部成员。外壳是资源与部署的合并，不是安全隔离；把不同可信程度的成员合进同一外壳，按[外壳的风险](../04-foundations/01-deployment-and-runtime.md#外壳的风险)处理。

## 过载与依赖故障

| 情况 | 表现 |
| --- | --- |
| 前台队列已满 | 立即返回“服务繁忙，请稍后重试”（带重试时间） |
| 下游组件慢或不可用 | 调用按超时失败；连续失败时熔断（见下表），暂停调用并快速失败；按业务声明降级（例如显示快照、提交暂缓） |
| 外部系统不可用 | 按[协议 10](10-external-integration.md) 排队与查询，不阻塞用户请求 |
| 数据库连接耗尽 | 前台有界等待后失败；后台暂停领取 |
| 热点行（库存、编号序列） | 缩短事务、限流、业务允许时分区或批量；不靠增加副本 |
| 授权组件或水位来源不可用 | 按[安全 03](security/03-authorization-acceptance-and-revocation.md#授权服务不可用时) 的有效期保护：高风险操作先停，普通读取在 `W_read` 内继续 |

熔断按每个下游分别维护：

| 当前状态 | 事件 | 守卫条件 | 结果状态 |
| --- | --- | --- | --- |
| 关闭 | 调用失败 | 最近窗口内的失败比例超过阈值 | 打开 |
| 打开 | 新的调用 | 冷却时间未到 | 打开（快速失败，不发出） |
| 打开 | 冷却时间到 | — | 试探 |
| 试探 | 少量试探调用成功 | — | 关闭 |
| 试探 | 试探调用失败 | — | 打开（重新计时） |

熔断只决定“发不发”，不改变已发出调用的结果语义：非幂等调用在打开前已发出、结果未知的，仍按协议 01、10 处理。

**健康检查**只报告进程存活，不检查数据库、消息系统或其他组件：一个下游故障会让所有上游被判为不健康并重启，外壳中则所有成员一起重启。下游的可用性体现在请求的结果与指标中。

## 启动与停止

| 当前状态 | 事件 | 守卫条件 | 结果状态 | 动作 |
| --- | --- | --- | --- | --- |
| （无） | 进程启动 | — | 启动中 | 检查数据库持久设置（协议 14）；执行或确认迁移（[协议 14 的结构迁移](14-data-foundations.md#结构迁移与版本兼容)） |
| 启动中 | 迁移失败或持久设置不合格 | — | 已停止 | 报告原因退出；不接收请求 |
| 启动中 | 成员按依赖顺序初始化完成 | — | 就绪 | 开始接收请求、领取工作、消费事件 |
| 就绪 | 收到终止信号 | — | 停止中 | 停止接收新请求；停止领取新工作 |
| 停止中 | 处理中的请求完成；执行中的工作项完成当前事务并释放租约（[协议 01](01-background-work.md)）；消费者停止（未确认的消息由消息系统重投） | 在停止时限内 | 已停止 | 退出 |
| 停止中 | 停止时限到 | — | 已停止 | 强制退出；未完成的工作由租约到期后的接替者恢复 |

- 正确性不依赖停止流程完成：未释放的租约到期后由接替者接管，代次核对挡住旧执行者（协议 01）。
- 外壳的停止按成员并行进行，总时限覆盖最慢的成员。
- 启动时 SDK 检查进程级的计时源（安全 03 的有效期按计入挂起的时钟计算）与数据库的持久设置（协议 14 第 5 条），不合格不进入就绪。

## 多副本

| 工作 | 多副本时的规则 |
| --- | --- |
| 用户请求 | 任一副本处理；不依赖会话粘滞 |
| 工作项 | 原子认领 + 租约 + 代次（协议 01） |
| 定时任务 | 槽位唯一（协议 01），多副本同时触发也只执行一次 |
| 发件转发 | 租约只减少争用；发布位置在计数行的锁内编号，旧租约持有者也只能排队取锁（[协议 02 的来源一侧](02-projections.md#来源一侧编号纪元与补取)） |
| 消费者 | 共享持久消费者；处理以收件表或连续位置去重 |
| 补取与回声 | 同一来源的并发补取在消费者一侧合并为一次（协议 02 第 5 步） |
| 本地缓存 | 默认不缓存授权与业务数据；授权视图按安全 03 的有效期；其他需要缓存的按声明的新鲜度与失效方式 |
| 投影与数据集的维护 | 与消费者相同 |

多副本提高处理能力与进程故障的恢复速度，不提供跨组件事务，也不解决数据库的写入上限。

## 部署引擎与矩阵

- 引擎：Docker、Podman、Kubernetes 按客户基线声明；Podman 是小型部署的重点候选（D40），与 Docker 分别验证。
- 矩阵不做全组合：按风险选代表格（单跑、外壳、混合 × 单副本、多副本 × 引擎），每格写明代表什么、哪些不适用（[真机矩阵与证据](../04-foundations/01-deployment-and-runtime.md#真机矩阵与证据)）。
- 每格验证：迁移、启动、受保护的真实请求、事件、故障恢复（杀进程、断数据库、断消息系统）、重复部署、停止与收尾；记录资源与延迟。
- 联网的安装与升级路径优先验证（D42）；完全离线交付按客户需求专项设计。

## 观测

两档方案（D43）共享同一组输出契约：

| 输出 | 基本档 | 完整档 |
| --- | --- | --- |
| 日志 | 结构化日志：时间、级别、组件与成员、版本、请求 ID、追踪 ID、主体（假名化）；本地持久保存并可按请求 ID 检索 | 加集中检索与看板 |
| 指标 | 每个路由类别的请求数、错误率、延迟分布；资源使用；下表的业务健康指标 | 加长期保存与看板 |
| 追踪 | 请求与事件之间的关联 ID 在日志中可追溯 | 加完整的分布式追踪存储 |
| 告警 | 下表的必需告警，送到客户声明的渠道 | 同左，加自定义告警 |

**业务健康指标与必需告警**：

| 指标 | 告警条件（起始值） |
| --- | --- |
| 发件表未发布的最老年龄 | 超过 5 分钟 |
| 消费者落后 | 超过 1 小时（[协议 15](15-backup-and-recovery.md)） |
| 来源水位的年龄（用水位的消费者，按来源） | 超过所需新鲜度的一半仍未推进；来源处于对齐中 |
| 计数倒退或回声核对失败（协议 02、03、14 的绊线） | 出现即告警（严重） |
| 工作项积压与最老年龄 | 超过声明的时限 |
| 进入死信或暂停的工作项 | 出现即告警；摘要经发件表送到死信监控（D68） |
| 对外命令处于结果未知的数量与最老年龄 | 超过 1 小时（协议 10） |
| 审计未转运的数量与最老年龄 | 按[协议 03](03-audit-durability.md) |
| 投影不完整的数量；按主体隔离的事件 | 持续超过 15 分钟；隔离出现即告警 |
| 暂停转人工的审批任务 | 出现即提醒（协议 09） |
| 前台被拒绝的请求比例 | 超过 1% |
| 授权视图核验失败、分片关闭 | 出现即告警（安全 03） |
| 证书与密钥的到期 | 30 天内到期 |
| 双通道失效（证据与外部告警渠道都不可达） | 出现即告警（严重，协议 15） |

- **脱敏**：日志不写密钥、令牌、受限字段的值与个人信息原文；主体以假名身份记录；字段类别决定能否进入日志（[安全 09a 的定义](security/09a-encoding-and-records.md#定义资源维度操作与字段)）。
- **不外传**：遥测不发送到客户声明之外的目的地（D42 的联网不等于允许回传）。
- 业务审计（协议 03）与运行日志分开：日志可以采样与短期保留，审计不可以。

## 性能与容量

- **测量协议**：固定组件组合、拓扑、引擎、观测档与数据量，每次只改变一个因素；负载包含空闲、日常、批量与月结的混合；记录每个路由类别的 p50／p95／p99 延迟、吞吐、错误率、业务过程完成时间（例如订单确认到预占完成）、队列最老年龄、每个成员的 CPU 与内存、数据库连接、补取与探测量、恢复时间。
- **预算模板**：每个客户基线声明前台延迟目标（例如 p95 不超过 500 毫秒）、后台完成时限（例如月结在维护窗口内完成）与资源上限；目标在代表部署实验与客户实测之后承诺。
- **代表部署实验**（D41）先于重建当前范围；完整部署矩阵与性能基线用重建后的组件运行（[路线](../00-overview/06-roadmap.md)的开发五步）。实验计划在设计冻结后写成，经用户确认后执行。
- 结果只对测过的组合有效；不从线程数或机器规格换算客户人数。

## 维护窗口中的升级

标准升级（D25）：预告维护窗口 → 按协议 15 的冻结步骤停止入口与执行者 → 备份 → 执行迁移（协议 14）→ 启动新版本 → 真实业务验证 → 开放。开放前发现问题按备份恢复；开放后只向前修复。连续运行的客户选择经过专项验收的在线升级方案（[正式客户升级与维护窗口](../04-foundations/01-deployment-and-runtime.md#正式客户升级与维护窗口)）。

## 参考模型

[共享预算模型](../../work/checks/29-shared-budgets.py)（种子 20261013，3,000 次运行）：三个成员共享 6 个数据库连接；成员甲持续提交长时间的后台工作，成员乙、丙随机提交前台请求。

| 检查 | 结果 |
| --- | --- |
| 前台请求在时限内得到连接，或立即得到可重试的拒绝 | 成立 |
| 队列不超过声明的上限 | 成立 |
| 后台工作持续进展 | 成立 |

4 个坏变体全部被发现：整个池先来先服务、后台不设上限、队列无上限、后台只在前台空闲时运行。后两个坏变体需要后台事务足够长、空闲判断包含处理中的前台请求才会暴露，模型按这样构造。模型不是 SDK、外壳或数据库的运行结果；熔断、启动与停止的状态、告警，靠实现测试。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| RT01 | 外壳中成员甲开始月结批量工作 | 乙、丙的前台请求仍在时限内得到服务 |
| RT02 | 前台持续繁忙 | 后台仍按限额进展 |
| RT03 | 成员最低保留之和超过外壳总预算 | 装配检查失败 |
| RT04 | 前台队列已满 | 立即返回可重试的错误与重试时间 |
| RT05 | 下游组件持续失败 | 熔断后快速失败；按业务声明降级 |
| RT06 | 数据库不可用 | 健康检查仍报告存活，不触发重启 |
| RT07 | 收到终止信号时有处理中的工作项 | 完成当前事务后释放租约；超时由接替者恢复 |
| RT08 | 两个副本同时触发同一定时任务 | 只执行一次 |
| RT09 | 两个副本同时运行发件转发 | 编号在计数行的锁内串行，同一位置不会编给两行 |
| RT10 | 库存行成为热点 | 不靠加副本；按事务优化、限流或业务分区处理 |
| RT11 | 日志中出现受限字段的值 | 不允许；按字段类别脱敏 |
| RT12 | 基本观测档下按请求 ID 查找日志 | 可以检索 |
| RT13 | 审计采样 | 不允许；只有运行日志可采样 |
| RT14 | 对外命令结果未知超过 1 小时 | 告警 |
| RT15 | 遥测发往客户未声明的地址 | 不允许 |
| RT16 | 只改变观测档位做性能比较 | 其他因素固定，结果注明档位 |
| RT17 | 维护窗口升级在开放前失败 | 按备份恢复 |
| RT18 | Podman 与 Docker 的同一组合 | 分别验证，不互相代替 |
| RT19 | 启动时数据库的 `synchronous_commit` 为 `off` | 不进入就绪，报告原因退出 |
| RT20 | 熔断打开时，一笔非幂等调用在打开前已发出、结果未知 | 熔断不改变它的处理：按结果未知查询或暂停（协议 01、10） |
| RT21 | 某来源的水位停住超过所需新鲜度的一半 | 告警；依赖它的判断超过新鲜度后按无法证明处理 |
| RT22 | 来源核对发现消费者最后的回声已不在原位置 | 严重告警；消费者完整重新取回（协议 02） |

## 已知风险与待定

- 各组件的资源声明数值，随组件设计与代表部署实验确定。
- 外壳总预算的声明格式与装配检查，随配置与发布协议（[协议 19](19-config-secrets-registries-release.md)）及 BrickKit 的能力确定；需要平台支持的部分，经验证后作为功能请求反馈。
- 默认部署组合（单跑、外壳或混合；引擎）在代表部署实验后确定（D40、D41）。
- 告警的操作处置写在运维手册（`05-operations/`）。
- 以上预期尚未在 SDK、外壳或部署引擎上运行。
