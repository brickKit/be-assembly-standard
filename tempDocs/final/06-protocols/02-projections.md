# 本地副本（投影）的完整性与修复

本页定义组件怎样保存、更新与修复别的组件数据的本地副本（投影），什么时候可以用它，以及怎样证明一份用于安全或资格判断的副本“此刻仍然正确”（来源水位）。写给实现投影的消费者组件、提供投影契约的来源组件，以及 SDK 的开发者。来源水位的机制只在本页完整定义；授权组件对内部来源的风险分档与身份产品的规定见[安全 03 的内部来源的收紧与来源水位](security/03-authorization-acceptance-and-revocation.md#内部来源的收紧与来源水位)。

组件常在本地保存别的组件数据的副本，称为投影：销售保存客户名称与信用状态摘要，用来渲染订单列表；授权保存组织树与任职视图；库存保存产品的计量单位。投影由来源组件的事件更新，可能遇到事件延迟、乱序、重复、丢失，也可能需要整体重建。本页回答：

1. 投影里的一行什么时候可以认为“与来源某个版本完全一致”？
2. 只带部分字段的事件、丢失的事件、丢失的删除，怎样最终修复？
3. 重建或回填时，怎样不覆盖已经收到的更新数据？
4. 哪些用途可以用投影，哪些必须直接问来源？
5. 用于安全判断的投影，怎样证明此刻仍然正确？来源库切换、来源更换实现时怎么办？

本页只处理“可覆盖的状态投影”。不可遗漏的增量事实（出入库、过账、收付）与必须按序处理的增量，按[事务与消息的事件分类](../04-foundations/03-transactions-and-messaging.md#事件分类重放与去重寿命)另行处理，不能用“新版本覆盖旧版本”的规则。审计副本也不是可覆盖的投影（[协议 03](03-audit-durability.md)）。

**额度反例**：本地 v10 的额度为 100；v11 把额度降为 50，但这个事件延迟了；v12 只改名称，先到。局部更新把本地标成 v12，额度却仍是 100；v11 到达时因版本更旧被跳过；之后取回完整的 v12，又因“版本必须严格更大”被拒绝。副本永远停在错误的额度上，而版本号显示它是最新的。本页的接收规则修复这个反例（PJ01）。

## 方案比较

| 路线 | 判断 |
| --- | --- |
| **采用**：版本号只代表完整快照；只带部分字段的事件把行标为“不完整”并触发取回完整状态；版本相等但本地不完整时接受完整快照；定期对账补回丢失的事件与删除 | 规则少，适用于任何事件运输；对账兜住丢失；不要求来源改成事件溯源 |
| 每个字段各带版本 | 局部事件可以直接合并；但每个投影字段都要额外的版本列，字段多时存储与比较的成本高，跨字段的不变量（例如“额度与币种一起变”）仍可能被拆开 |
| 严格连续的增量（只接受 V = 本地 + 1） | 不需要完整快照；但任何一个事件丢失都会阻塞后续全部更新，必须有补齐机制，等于又回到取回完整状态 |
| 不保留副本，每次直接调用来源 | 永远最新；但列表渲染要逐行远程调用（N+1），来源不可用时页面不可用 |

采用的路线与常见的四层防线（发件表、版本号跳变检测、定时对账、死信）一致，并补上了“相同版本却不完整”这一缺口。

## 什么时候可以用投影

| 用途 | 规则 |
| --- | --- |
| 列表、下拉、搜索结果中的显示摘要 | 可以用投影；显示时可以附“同步于某时刻” |
| 详情页 | 调来源的读取接口（展示用摘要，详情问权威来源） |
| 业务提交依赖当前值（例如确认订单时的信用状态） | 不用投影作依据：由拥有该事实的组件在它的命令中检查（信用占用由信用组件裁决），或同步读取来源、在命令中带上来源修订供对方核对 |
| 安全或资格判断（授权视图中的组织树、任职；[协议 07](07-references.md) 的资格证据；[协议 09](09-approval-and-workflow.md) 的岗位资格） | 只用状态为“完整”、且该来源的**水位**在声明的新鲜度内的行（见[来源水位](#来源水位)）；否则按“无法证明”处理（安全 03、安全 08） |
| 报表与分析 | 按报表口径声明可接受的滞后，并显示数据截至的时刻 |

## 投影行的字段

| 字段 | 含义 |
| --- | --- |
| `source_id` | 来源记录的身份 |
| `version` | 本行内容对应的来源整体版本 |
| `source_epoch` | 取得该版本时来源的纪元（见[纪元变化](#纪元变化)）；版本只在同一纪元内比较 |
| `state` | `complete`（与来源该版本完全一致）、`incomplete`（只应用了部分字段，等待完整快照）、`tombstone`（来源已删除） |
| `need_version` | `incomplete` 时：取回的完整快照至少要达到的版本 |
| `synced_at` | 最近一次确认与来源一致的时刻（取回完整快照或对账一致时更新）；只用于显示与对账，不用于新鲜度判断 |
| 投影字段 | 声明投影的那些字段，不多存 |

## 来源要提供什么

投影协议要求来源组件在契约中提供：

1. **整体版本**：每条记录一个单调递增的版本号，每次修改加一。已删除的记录被恢复时，版本继续递增（恢复是一次新的修改）。
2. **事件声明类型**：每种事件声明是“完整状态”（带全部可投影字段）还是“部分字段”；删除事件带删除时的版本。推荐来源优先发布完整状态事件：可投影的字段通常不多，带全也不贵，消费者也最简单。
3. **按 ID 批量读取当前完整状态**，带版本；已删除的记录返回墓碑与版本。不能直接返回“查无此记录”，否则消费者无法区分删除与从未存在。
4. **按范围的对账摘要**：给定 ID 范围与字段集合（订阅时声明的投影），返回该范围内每条记录 `(id, version, 是否删除, 内容摘要)` 的组合摘要；内容摘要按[安全 09a 的规范编码](security/09a-encoding-and-records.md#规范编码与摘要)计算请求的字段集合；不一致时可以缩小范围直到具体的 ID。批量读取、对账摘要与补取的响应都声明来源**当前的纪元**与**实现实例**（见[来源更换实现](#来源更换实现)）。
5. **墓碑保留期**不短于消费者的最长对账周期，否则对账无法发现删除。
6. **水位回声与补取**（在组件卡上声明为“水位来源”的组件必须提供；只有这些来源可用于安全或资格判断的投影路径，其余一律同步查询）：补取接口（请求即探测）；与变更同一张发件表的回声行；锁内的提交后编号与纪元；事件只含可投影字段，信封携带投影语义；超出补发保留时返回“需要完整快照”；纪元的声明（只在主库上作答时声明）。具体规则见[来源水位](#来源水位)。补取接口只对声明订阅了该来源的服务身份开放，并写审计；用水位的订阅按“分区的全部事件类型（含将来新增的）”声明，补取对这类订阅不按类型过滤，其余订阅只返回它订阅的类型。

## 来源水位

一行投影“现在是否仍然正确”，不能用它最近一次更新的时刻判断：长期没有变化的行可能完全正确，刚收到事件的行也不能证明此后没有新变化。可以证明的是**来源水位**：消费者直接问来源“到此刻为止的变更”，来源在同一条有序流里放一条回声作答，消费者应用到这条回声为止，就证明了此刻之前提交的变更都已应用。

下面四小节分别写来源一侧、消费者一侧、纪元变化与来源更换实现；缺任何一部分，变更都可能被当作已应用而跳过，水位却照常推进。步骤的编号在全页连续，其他文档按编号引用。

### 来源一侧编号、纪元与补取

1. **补取即探测**：消费者以直接调用（不经消息系统）调用来源的补取接口，请求带探测随机数、消费者在每个分区的连续已应用位置，以及它最后应用的那条回声的位置与随机数；没有单独的探测接口。来源先核对自己在该位置的行就是那条回声（随机数相同）；不同，说明来源的内容回退过（例如恢复了库却没有推进部署恢复代次），返回“需要完整快照”并告警。回声每隔不到新鲜度的一半就写一次，所以这条回声总在补发保留期之内。来源先把带同一随机数与目标消费者的回声行写进与变更相同的发件表（每个分区一条）并提交，再执行第 2 步的编号，然后返回调用者位置之后、直到这条回声的全部行。响应过大时分页，回声只在最后一页。调用者的位置早于来源的补发保留时，返回“需要完整快照”。响应声明来源当前的纪元与实现实例。
2. **提交后编号**（临界区）：每个分区在来源库中有一行编号计数。编号事务只做三件事：**先锁计数行**；取得锁之后，再用新的语句快照选出可见、尚未编号的发件行，按插入顺序编连续的发布位置；与计数一起提交。
   - 事务内不做网络调用（发布在提交之后另行进行）；锁等待与事务时长由数据库端限时（起始 `lock_timeout` 2 秒、事务 5 秒；PostgreSQL 17 起用 `transaction_timeout`，更早的版本用 `statement_timeout` 与 `idle_in_transaction_session_timeout` 组合，列入实验核实），超时回滚。
   - 发件转发与补取调用同一段编号逻辑；转发的租约（[协议 17](../../protocols/17-runtime-and-resources.md)）只用来减少争用，不承担正确性，停顿后恢复的旧租约持有者也只能排队取锁。
   - 回滚的行从不可见，不留空洞；长事务只推迟它自己的行。
   - 探测在变更提交之后才到达来源，回声的插入晚于该变更的提交；编号在锁内取快照，凡能编到回声的那次编号一定也看得见该变更，所以变更的发布位置一定在回声之前。流与补取携带同一个发布位置，写作（实现实例，纪元，序号）；实现实例见第 12 步。
3. **纪元**：按[协议 14 的库内计数与纪元](14-data-foundations.md#库内计数与纪元)，来源库的纪元按（**部署恢复代次**，当前写入时间线）定序，系统标识（`pg_control_system()`）只作身份核对。
   - 时间线取当前 WAL 文件名的时间线部分，不用检查点记录中的时间线（后者在提升后要等检查点才变化）。
   - 高可用切换只使切换了的集群的时间线变大；任何使库内容回退、或使系统标识、时间线变化的操作（整套恢复、卷快照、单库恢复或重建、主版本升级）都推进部署恢复代次。
   - 编号事务读到的纪元与计数行记录的不同时，开启新纪元，序号从 1 开始；读不到任何一项时拒绝编号。
   - 主库作答的读取声明纪元（`pg_is_in_recovery()` 为假）；副本作答的读取声明副本回放到的时间线。
   - 各项在 PostgreSQL 与托管数据库上的读取方式（含权限、提升后立即编号、卷快照恢复）列入代表部署实验。

### 消费者一侧订阅、应用与水位

4. **时钟**：`m_p` 与之后的新鲜度判断都取消费者**主库的事务时间**，多副本与重启都使用同一个时钟。消费者记录观察到的最大主库时间与自己主库的纪元（同第 3 步的定义）；当前时间小于这个最大值（时钟回拨）或纪元变化时，全部水位作废，等待新的回声。主库主机只用平滑校时，残余的回拨计入 `E_clock`。
5. **触发**：某来源的水位年龄达到所需新鲜度的一半时，消费者先在主库记下 `m_p`，再发起补取；同一来源的并发请求合并为一次。探测量随“正在做资格判断的消费者”增长，不随全部消费者与来源的乘积增长；只用于显示的投影不需要水位。探测量列入性能实验。
6. **订阅与应用**：
   - 用水位的消费者订阅来源每个分区的**全部事件**（来源保证事件只含可投影字段，受限字段不进事件；代价是这些消费者能读到分区的全部可投影字段），所以位置上的空洞只可能是丢失或未到，不是过滤。
   - 事件信封携带投影语义（来源的实现实例与纪元、记录身份、版本、完整、部分或删除、受影响的主体）；不认识的事件类型按“部分字段”处理：把该行标为不完整并取回，不隔离、不跳过。
   - 消费者按位置应用，并在同一事务记录每个分区“连续已应用的发布位置”；处理失败、等待重投的事件之后的位置都不算连续。补取的结果是到回声为止的完整区间，应用完最后一页后，连续位置设为回声的位置。
   - **计数倒退的绊线**：同一纪元内，补取响应中回声的位置低于消费者已记录的连续位置，或来源按第 1 步核对发现消费者最后的回声已不在原位置时，说明来源的内容回退了（多半是有人恢复了来源却没有推进部署恢复代次）。消费者告警，停止推进该来源的水位，并按第 11 步做一次完整的重新取回；告警给出出口：确认来源的数据情况后推进部署恢复代次。只比较位置的高低，检测不到“回退后又产生了足够多的新提交”的情形，所以第 1 步另外核对回声本身。
   - 只订阅部分事件类型的消费者不用连续位置与水位，按收件表去重。
7. **持续失败的事件**（重投达到上限，起始 3 次或 30 秒）按主体隔离：信封列出该事件影响的全部主体（账号、员工、组织单元；信封与正文分开版本化），这些主体在安全或资格判断中按“无法证明”处理——判断检查它读取的每一行所对应的主体——并告警；隔离记录与“连续位置越过它”在同一事务提交；补取路径按同一规则。信封无法解析、列不出主体、或主体超过上限（起始 1,000）时，不隔离，该来源的水位停住。修复后重新处理隔离的事件，成功才解除。主体被隔离使管理员暂时不可用时只告警，不单独触发 D62 的待恢复。
8. **水位**：某来源的水位 = 各分区连续已应用位置之内，最后一条回声的 `m_p` 的最小值。只要有一个事件在等待重投，水位就停在它之前；流上出现的回声同样在连续区间内推进水位，只起加速作用。
9. **判断**：某行可用于安全或资格判断，当且仅当：它是完整的；属于来源当前的纪元与实现实例；它的主体没有被隔离；该来源不在对齐中；它来源的水位不早于“当前时刻 − 声明的新鲜度”。回答时在同一个读快照中先读水位、再读行。

```mermaid
sequenceDiagram
    participant C as 消费者
    participant S as 来源（主库）
    participant Q as 消息系统
    S->>Q: 变更（位置 p1）
    Note over Q: 延迟、中断或丢失
    C->>C: 水位年龄达到新鲜度的一半，记下 m_p
    C->>S: 补取（随机数，连续位置）
    S->>S: 写回声，锁内编号（回声位置 p2 > p1）
    alt 来源可达
        S-->>C: 位置之后到回声为止的全部行（可分页），声明纪元
        C->>C: 按位置应用到 p2，水位 = m_p
    else 来源不可达或响应丢失
        Note over C: 水位不推进；超过新鲜度后判断按“无法证明”
    else 回声位置低于自己的连续位置（同一纪元）
        C->>C: 告警，停止推进水位，完整重新取回
    end
    Q-->>C: p1 迟到
    C->>C: 已应用，按位置忽略
```

结论：水位只在“回声之前的全部位置都已连续应用”时推进；来源不可达、位置有空洞、事件等待重投或信封无法解析，水位都停住，依赖它的判断在超过新鲜度后按“无法证明”处理（PJ20、PJ21、PJ27、PJ28）。

### 纪元变化

来源库异步切换、从备份恢复或跨集群非原子恢复后，丢失的提交连同它们的发布位置与记录版本一起回退，新主库会重用它们。所以纪元变化时，位置与版本都不能再与旧纪元比较。高可用部署的前提：新主库受理写入之前，旧主库已被隔离（不再受理写入与读取）；全部写入同步提交（D66，[协议 15](15-backup-and-recovery.md)），所以切换只可能丢失“对外已可见、备库尚未确认”的极短窗口；降级切换按整套恢复处理。

10. **只采用更大的纪元**：
    - 补取、批量读取或对账摘要的响应声明的纪元**大于**消费者记录的纪元时，消费者采用它：作废该来源的水位与连续位置，放弃仍在进行的旧纪元补取；该来源的全部行视为待对齐。
    - 声明的纪元更小（迟到的旧响应）时忽略；连续收到更小的纪元超过 `D_src_high` 时告警（多半是有人恢复了来源却没有推进部署恢复代次），告警给出出口：确认来源的数据情况后推进部署恢复代次。系统标识不同而纪元不更大时，同样停住并告警；系统标识变化而部署恢复代次更大（主版本升级、迁移）时，正常采用。
    - 副本作答的响应，只在它声明的时间线与已采用的纪元相同时使用，否则丢弃，也不用于采用。
    - 流上出现尚未采用的纪元的事件，只触发一次补取，本身不应用；采用新纪元之后，旧纪元的事件一律忽略（内容由对齐取得）。不用水位的消费者同样在看到其他纪元的事件时做一次批量读取。
11. **对齐**：用水位的消费者把该来源的全部行**重新取回**（安全来源的行数在万到十万级），重新取回**只读主库**：
    - 开始前，消费者先发一次只要回声的补取，得到新纪元中回声的位置 P0；然后分页读取快照。快照全部写完后，连续位置设为 P0，之后的补取从 P0 起，所以快照读取期间来源的新变更不会被跳过（P0 与快照之间重复的变更按版本忽略）。
    - 快照的每一行经接收规则写入：本地行仍属旧纪元（或旧实现实例）时直接覆盖，不比较版本；本地行已属新纪元（对齐期间从流上应用的新纪元事件）时按版本比较。所以对齐期间先应用的较新变更（例如离职）不会被较早读到的快照盖回去。
    - 来源没有的行转墓碑，只对仍属旧纪元的本地行适用；对齐期间新建的行已属新纪元，不会被墓碑压住。不用水位的消费者可以改用按订阅字段集合计算的内容摘要对账，只取回不一致的行。**对齐完成之前，补取与流上的回声都不推进水位，依赖该来源的判断立即按“无法证明”处理**（不等水位超期）；对齐完成后，下一次补取的回声恢复水位。

```mermaid
sequenceDiagram
    participant C as 消费者
    participant S as 来源（新主库，纪元 g2）
    S-->>C: 补取响应，声明纪元 g2（大于记录的 g1）
    C->>C: 采用 g2：作废水位与连续位置，放弃旧补取；判断按“无法证明”
    C->>S: 只要回声的补取
    S-->>C: 回声位置 P0（纪元 g2）
    C->>S: 重新取回全部行（只读主库）
    S-->>C: g2 的快照：旧纪元的本地行直接覆盖，已属 g2 的行按版本比较；仍属旧纪元而来源没有的行转墓碑
    C->>C: 连续位置设为 P0
    opt 迟到的旧响应（声明 g1）
        S-->>C: 旧响应
        C->>C: 纪元更小，忽略
    end
    C->>S: 补取（新纪元）
    S-->>C: 回声
    C->>C: 对齐完成，恢复水位
```

结论：纪元变化期间，消费者只认更大的纪元、只从主库重新取回、对齐完成前不推进水位且判断按“无法证明”，所以切换中丢失或重用的位置与版本，不会让一次收紧被当作已应用而跳过（PJ26、PJ31、PJ32、PJ38、PJ39）。

### 来源更换实现

12. **来源更换实现**：计划内把一个来源换成另一个实现（例如身份成员从 Casdoor 适配组件换成 Keycloak 适配组件，[安全 11](security/11-identity-member-switching.md)），新实现有自己的库，纪元与位置和旧实现之间没有可比性，纪元也不一定更大。所以来源的身份包含**实现实例**（响应中声明），消费者把“实现实例变了”当作一次来源更换处理，不比较纪元：
    - 更换由部署按计划发起，消费者事先登记“该来源的新实现实例”；收到声明新实现实例的响应时，作废旧实例的水位与连续位置，对新实例做一次完整的重新取回（第 11 步的对齐，只读新实例的主库），对齐完成之前依赖该来源的判断按“无法证明”处理。
    - 没有事先登记的实现实例变化一律不采用，停住并告警（防止误配置的地址把消费者接到另一个库）。
    - 更换之前，旧实现必须已停止受理变更、并把截至停止时的变更全部交给新实现（由更换协议保证，例如安全 11 的排空与围住）；所以对齐新实例得到的状态包含旧实现的全部变更。
    - 回退是反方向的又一次来源更换，规则相同。

保证：来源在时刻 s0 提交的变更，依赖它之前状态的判断不晚于 s0 + 新鲜度 + `E_clock` 之后停止（再加判断结果自身的有效期，例如授权视图的 W）；纪元变化与来源更换期间，判断按“无法证明”处理，不放宽这个上界。前提：旧主库（或旧实现）已隔离，未隔离时上界加上两者并存的时长；任何使来源库内容回退的操作都推进部署恢复代次（第 3 步），第 1 步与第 6 步的绊线只是漏推时的检测，不是保证的一部分。

这个办法不依赖来源与消费者的墙钟同步。来源不可达、补取中断时，水位停止推进，依赖它的判断按“无法证明”处理。授权组件对内部来源使用同一机制，另有风险分档与身份产品的规定（安全 03）。

## 接收规则

消费者在一个本地事务中处理每个事件或快照。**实现实例与纪元的判断先于全部规则（包括墓碑）**：

- 输入属于非当前的实现实例：已登记、尚未采用的新实例，只触发一次补取（由响应按第 12 步决定是否更换）；其余（包括旧实例在围住后残留的重发）一律忽略，不按位置等待，也不比较版本。两个实现的纪元在数值上可能相同，所以不能只看纪元。
- 输入属于当前实现实例：本地行属于旧纪元（或旧实现实例）、输入属于已采用的纪元时，完整快照与删除直接覆盖，部分字段事件把行记为该纪元与 `incomplete`；属于旧纪元的输入在采用新纪元后忽略；属于尚未采用的纪元的流上事件不应用，只触发一次补取。

下表的版本比较只在同一实现实例、同一纪元内进行；表中凡写入、覆盖、合并的动作，本地 `version` 都设为输入的 V。

| 当前状态 | 输入 | 守卫条件（同一纪元） | 结果状态 | 动作 |
| --- | --- | --- | --- | --- |
| （无此行） | 完整快照或完整状态事件，版本 V | — | `complete` | 写入 |
| （无此行） | 部分字段事件，版本 V | — | `incomplete` | 写入已知字段，`need_version = V`；排入取回工作项 |
| （无此行） | 删除，版本 V | — | `tombstone` | 写入墓碑，`version = V` |
| `complete` | 完整快照或完整状态事件 | V > 本地版本 | `complete` | 覆盖 |
| `complete` | 完整快照或完整状态事件 | V ≤ 本地版本 | 不变 | 忽略 |
| `incomplete` | 完整快照或完整状态事件 | V ≥ `need_version` 且 V ≥ 本地版本 | `complete` | 覆盖（版本相等但本地不完整时也覆盖，额度反例由此修复） |
| `incomplete` | 完整快照或完整状态事件 | V < `need_version` | `incomplete` | 忽略，取回工作项继续 |
| `complete`、`incomplete` | 部分字段事件 | V > 本地版本 | `incomplete` | 合并字段，`need_version = V`；排入取回工作项 |
| `complete`、`incomplete` | 部分字段事件 | V ≤ 本地版本 | 不变 | 忽略 |
| `complete`、`incomplete` | 删除 | V ≥ 本地版本 | `tombstone` | 写入墓碑 |
| `complete`、`incomplete` | 删除 | V < 本地版本 | 不变 | 忽略 |
| `tombstone` | 任何输入 | V ≤ 墓碑版本 | `tombstone` | 忽略：墓碑不能被同版本或更旧的数据复活 |
| `tombstone` | 完整快照或完整状态事件 | V > 墓碑版本 | `complete` | 覆盖（来源恢复了这条记录，恢复是一次新修改） |
| `tombstone` | 部分字段事件 | V > 墓碑版本 | `incomplete` | 不合并字段（墓碑没有字段可合并），`need_version = V`；排入取回工作项 |
| `tombstone` | 删除 | V > 墓碑版本 | `tombstone` | 更新墓碑版本 |
| 任一状态（旧纪元或旧实现实例） | 已采用纪元的完整快照或删除 | — | `complete` 或 `tombstone` | 直接覆盖，写入该纪元与版本，不比较版本 |
| 任一状态（旧纪元或旧实现实例） | 已采用纪元的部分字段事件 | — | `incomplete` | 记为该纪元，`version = V`、`need_version = V`；排入取回工作项 |
| 任一状态 | 尚未采用的纪元的流上事件 | — | 不变 | 不应用；触发一次补取（第 10 步） |
| 任一状态 | 非当前实现实例的输入 | 已登记、尚未采用的新实例 | 不变 | 不应用；触发一次补取（第 12 步） |
| 任一状态 | 非当前实现实例的输入 | 其余 | 不变 | 忽略 |
| `complete`、`incomplete`（仍属旧纪元或旧实现实例） | 对齐时来源没有该行 | 新纪元或新实现实例的重新取回 | `tombstone` | 写入墓碑 |

- `incomplete` 的行绝不标为 `complete`，直到取回的完整快照版本不低于 `need_version`。参考模型的坏变体“局部更新后直接标为完整”会产生内容错误、却标为完整的行。
- 用水位的消费者按来源记录连续已应用的发布位置，其余消费者按收件表去重；二者都与行的更新同事务。整套恢复时，生产者按消费者的进度补发（[协议 15 的发件表的保留与消费者进度](15-backup-and-recovery.md#发件表的保留与消费者进度)）。位置丢失、或需要的事件已被清理时，按下文的对账与重建修复。

## 修复不完整的行

行转为 `incomplete` 时，同事务排入一个取回工作项（[协议 01](01-background-work.md) 的 `local` 种类）：在事务外按 ID 批量调用来源，取回当前的完整状态；再在一个本地事务中按接收规则写入。多个不完整的行合并成批量读取，受批量上限（起始 500 个 ID）与来源的调用预算限制。来源不可用时按退避重试，行保持 `incomplete`。

## 对账

对账以协议 01 的 cron 工作项定期运行：

1. 把 ID 空间分成若干段，向来源请求每段的对账摘要，与本地同一段的摘要比较。
2. 摘要不一致的段继续二分，直到找到具体的 ID。
3. 对不一致的 ID 取回完整状态（或墓碑），按接收规则写入。
4. 一致的段更新其中各行的 `synced_at`。

对账兜住了事件运输无法保证的部分：丢失的事件、丢失的删除、消息系统因保留期或容量丢弃的消息。没有对账时，丢失的删除会让已删除的记录永远留在副本里（参考模型的“不对账”坏变体）。

## 重建与回填

重建一个投影时，回填与实时事件同时进行，二者都走同一套接收规则：回填读到的快照版本低于本地已有的版本时，被忽略。所以不需要停止事件消费，也不需要全局的切点；同一纪元内行的版本不倒退（参考模型的“回填无条件覆盖”坏变体会让版本倒退）。回填完成后执行一次完整对账，结束重建。

## 墓碑的清理

墓碑在超过对账周期与来源墓碑保留期两者中较长的那个之后，才可以删除。提前删除，迟到的旧快照可能重新写入已删除的记录（参考模型的“删除时直接删行”坏变体）。

## 参数起始值

| 参数 | 起始值 |
| --- | --- |
| 对账周期 | 每日一次；用于安全判断的投影（组织、任职）每小时一次 |
| 对账分段 | 每段约 1,000 条，按需二分 |
| 不完整行的取回 | 合并成批量读取，每批不超过 500 个 ID |
| 墓碑保留 | 来源与消费者都不少于 7 天，且长于对账周期 |
| 安全判断可以接受的新鲜度 | 按来源水位；授权组件的内部来源用安全 03 的 `D_src_high` 与 `D_src_read`（D64），协议 07 的资格证据用它的 W，协议 09 的岗位资格用 `D_src_high` |
| 补取（探测）的触发 | 水位年龄达到所需新鲜度的一半，并发合并；只对声明为水位来源的来源 |
| 编号事务的限时 | `lock_timeout` 2 秒，事务 5 秒 |
| 持续失败事件的隔离 | 重投 3 次或 30 秒；一条事件的主体上限 1,000 |

## 参考模型

[投影修复模型](../../work/checks/14-projection-repair.py)（种子 20261013，3,000 次运行）：来源随机产生完整状态事件、部分字段事件与删除；事件随机延迟、乱序、重复、丢失；回填在随机时刻读取几个版本之前的旧快照；不完整的行随机触发取回；最后执行一次对账。

| 检查 | 结果 |
| --- | --- |
| 标为完整的行，内容一定等于来源该版本的内容 | 成立 |
| 流量停止并对账一次后，每行等于来源的最新状态 | 成立 |
| 额度反例被修复 | 成立 |
| 处理过删除的记录不会以未删除的状态重新出现 | 成立 |
| 行的版本永不倒退 | 成立 |

5 个坏变体全部被发现：只接受严格更大的版本（额度反例无法修复）、局部更新后标为完整（内容错误却标为完整）、不对账（丢失的事件与删除无法修复）、删除时直接删行（旧快照复活已删除的记录）、回填无条件覆盖（版本倒退）。同一模型的切换子模型建出了来源异步切换后的版本重用与撤销的删除、新纪元的完整、部分字段与删除事件、逐行重新取回（经接收规则写入），三个坏变体（不分纪元、比较内容但仍按版本接受、墓碑规则先于纪元判断）都被发现（PJ31、PJ40）。

[内部来源水位模型](../../work/checks/35-internal-source-watermark.py)（种子 20261013，3,000 次随机运行，另有三个定向场景各 50 个种子）演算 PJ19–PJ21、PJ23、PJ25–PJ28、PJ32、PJ34、PJ38、PJ39：锁内的提交后编号与回滚空洞、长事务、重投、流停滞与逐渐落后、消息系统丢失事件、来源异步切换（在离职之前或之后，收紧同步提交）、只采用更大的纪元、迟到的旧响应、重新取回读主库、对齐完成前不推进、探测即补取及其响应延迟，并逐时刻断言来源可达时水位不超期。18 个坏变体全部被发现（清单见[安全 03 的参考模型](security/03-authorization-acceptance-and-revocation.md#参考模型)）。把上界收紧到 s0 + 新鲜度的一半时，正确的协议在 3,000 次运行中有 150 次违反，说明这项检查不是空的。

两个模型都不是 SDK、数据库或消息系统的运行结果。**靠实现测试的条款**：多副本与主库切换的消费者时钟域（PJ22）、多分区取最小值、补取的分页与“需要完整快照”（PJ29）、持续失败事件的隔离（PJ30、PJ37）、编号的限时（PJ35）、未知事件类型（PJ36）、补取接口的订阅与授权检查（PJ24）、旧主库未隔离（PJ41）、纪元在 PostgreSQL 上的读取、计数倒退的绊线与回声核对（PJ44）、来源更换实现与实现实例的判断（PJ43、PJ45）、对齐的起点 P0 与对齐期间的版本比较（PJ42）、墓碑被更高版本恢复。“采用新纪元时作废水位”是保守的规则：上界的证明不依赖它（旧纪元的水位只证明切换前的状态），模型也不检验它。模型中的纪元是单调递增的整数：系统标识变化、纪元变小时的停住与出口、副本作答的时间线声明都没有建出，只建出“重新取回读落后的副本”这一种副本情形。

| PJ17 | 不完整行的积压超过阈值 | 告警；按批量与预算取回，不压垮来源 |
| PJ18 | 消息系统因保留期丢弃未消费的事件 | 对账补齐；不依赖重放 |
| PJ19 | 来源一行长期没有变化，用于资格判断 | 按来源水位判断，不按 `synced_at`；水位新鲜即可用 |
| PJ20 | 来源的回声中断，事件仍零星到达 | 水位停止推进，超过新鲜度后资格判断按无法证明处理 |
| PJ21 | 一条事件处理失败等待重投，其后的回声已应用 | 水位停在失败事件之前 |
| PJ22 | 消费者有两个副本 | 水位与新鲜度都按主库事务时间判断 |
| PJ23 | 来源的一笔事务回滚、另一笔长事务稍后提交 | 提交后编号不留空洞；水位照常推进 |
| PJ24 | 补取接口被未订阅该来源的服务调用 | 拒绝并写审计 |
| PJ25 | 发件转发与补取同时编号，或旧租约持有者停顿后恢复 | 计数行的锁使编号串行；同一个位置不会编给两行，变更的位置在回声之前 |
| PJ26 | 来源库异步切换，丢失最后的提交，消费者的连续位置超前 | 新主库开启新纪元；消费者从补取响应得知新纪元，作废水位与连续位置，放弃进行中的补取，对齐完成后从新纪元继续；切换后的变更不被跳过 |
| PJ27 | 消息系统丢失一条事件，其后的事件已到达 | 安全消费者订阅全部事件，看到空洞即不推进；下一次补取返回完整区间 |
| PJ28 | 消息系统中断，来源可达；或流逐渐落后 | 补取按水位年龄触发，水位始终不超过新鲜度；流恢复后重复到达的行按位置忽略 |
| PJ29 | 补取响应很大，或消费者的位置早于补发保留 | 分页返回，回声只在最后一页，应用完最后一页才推进水位；早于保留时返回“需要完整快照”，重建后继续 |
| PJ30 | 一条事件始终无法处理，信封可以解析 | 重投达到上限后按主体隔离并告警，其他主体照常；修复后重新处理才解除 |
| PJ31 | 来源异步切换，丢失的修改（v7）已被消费者应用，新主库之后把同一记录改到 v7（离职） | 对齐时内容摘要不同，按新纪元的快照覆盖，不比较版本；离职被应用 |
| PJ32 | 采用新纪元之后，流上又到达旧纪元编号的事件（切换前已编号、新主库才发布，或等待重投） | 忽略，不换纪元、不推进位置；内容由对齐取得 |
| PJ33 | 流上先出现新纪元的事件，补取尚未发生 | 触发一次补取，由补取响应决定是否换纪元；事件本身不应用 |
| PJ34 | 高可用部署中员工库切换，切换前刚提交离职 | 离职已同步提交（D66），切换后仍在；授权组件采用新纪元、重新取回后看到离职 |
| PJ35 | 转发在发布时被消息系统阻塞 | 编号事务不含发布，补取仍能在限时内取得计数行的锁并编号 |
| PJ36 | 来源升级新增一种事件类型，旧消费者收到它 | 按部分字段处理：把该行标为不完整并取回；不隔离、不跳过 |
| PJ37 | 一条持续失败的事件影响 3 个账号与 1 个部门 | 信封列出的 4 个主体都被隔离；读取这些主体的行的判断按无法证明处理 |
| PJ38 | 采用新纪元之后，切换前发出的补取响应迟到，声明旧纪元 | 纪元更小，忽略；不回到旧纪元 |
| PJ39 | 对齐时读取来自落后的只读副本 | 不用于对齐；对齐只读主库；副本声明的时间线与已采用的纪元不同时，它的响应被丢弃 |
| PJ40 | 本地行是旧纪元的墓碑，新纪元的同一记录以更低的版本出现 | 纪元判断先于墓碑规则，新纪元的快照覆盖墓碑 |
| PJ41 | 旧主库没有被隔离，与新主库并存 30 秒 | 不满足高可用的前提；上界加上并存的时长，代表部署实验验证隔离 |
| PJ42 | 对齐时先读到 X 的快照 v5（在职），随后流上的新纪元 v6（离职）被应用，再写入 v5 | v5 按版本比较被忽略，X 保持离职；对齐完成后补取从 P0 起，不跳过 v6 之后的变更 |
| PJ43 | 身份来源更换实现后，两个实现的纪元数值相同；旧实例在围住后重发一条“启用 Y”的旧事件 | 按实现实例判断，旧实例的输入忽略，不按位置等待、不比较版本；Y 不被启用 |
| PJ44 | 来源库被恢复到 900 条之前却没有推进部署恢复代次，之后又提交 150 次，计数超过消费者的连续位置 | 补取时来源核对消费者最后的回声不在原位置，返回需要完整快照并告警；消费者完整重新取回，不跳过回退期间的离职 |
| PJ45 | 来源更换实现，某个只显示用的消费者没有事先登记新实例 | 停住并告警；不把新实例从小数开始的版本当作旧值忽略 |

## 已知风险与待定

- 各来源组件的投影契约（版本、事件类型声明、批量读取返回墓碑、对账摘要接口、实现实例的声明）在组件设计时逐个写入。
- 授权视图是一种特殊的投影，另外受安全 03 的有效期与安全 08 的有效段规则约束；两套规则的衔接在冻结复查时核对。
- 纪元各组成部分在 PostgreSQL 与托管数据库上的读取方式、编号事务的限时、探测量，列入代表部署实验。
