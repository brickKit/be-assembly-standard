# 身份成员的切换

本页定义客户从一个身份成员换到另一个时怎样做：例如从 Casdoor 适配组件换到 Keycloak 适配组件，或者同一适配组件背后的外部身份源发生更换。它与授权成员的切换（[安全 10](10-providers-and-member-switching.md#成员切换协议)）结构相同，另外处理身份特有的几件事：外部账号到稳定平台主体的映射、账号停用不能丢、签名密钥与会话、MFA、授权组件对身份来源的重新对齐。选择哪个身份方案见[身份的选型说明](../../00-overview/guides/identity.md)。

## 要保持的结果

- **平台主体不变**：业务、授权、审计引用的都是部署内稳定的平台主体（[安全 02](02-trusted-identity-and-attributes.md#稳定主体与身份链接)）。换身份成员只改变“外部账号 → 平台主体”的映射，不改变任何平台主体的身份；授权记录、账号与员工的关联（员工组件拥有）、审计都不迁移、不改写。
- **没有人因切换获得更多访问**：映射只能是预先登记、唯一、精确的；不按邮箱或登录名自动认人，不把两个平台主体合并，也不能把一个外部账号映射到另一个人的平台主体。映射的建立与变更是受保护操作（[安全 08](08-state-and-change-protocol.md#确认与受保护操作)）。
- **停用不丢失**：旧成员中已停用、已安全冻结的账号，在新成员中仍是停用或冻结；切换期间发生的停用，切换后仍然有效。重新启用只能经新成员明确办理。
- **撤权上界不变**：账号停用传到各组件的上界，切换前后都按[安全 03 的内部来源水位](03-authorization-acceptance-and-revocation.md#内部来源的收紧与来源水位)成立；切换过程中依赖身份来源的判断按“无法证明”处理，而不是放行。新成员不能保持这个上界时（例如不能提供拉取，只能按外部来源的 `D_source` 声明），预检停止，除非客户书面接受新的上界，产品说明相应改写。
- **认证强度不降低**：MFA 登记通常不能迁移；需要 MFA 的操作，在用户于新成员登记 MFA 之前不能执行（操作 profile 照常要求 MFA，不因切换豁免）。登记本身也要有与原强度相当的证明，否则只掌握泄露密码的人可以抢先替受害人登记（见第 1 步的 MFA 重新登记）。
- **可以回退**：切换的每一步都能撤回；新成员开始签发之后的回退，停用也不丢失。

授权组件的数据、恢复代次与授权成员都不因身份切换而改变。

## 步骤

默认在预告的维护窗口内进行（D25）。

1. **预检。**
   - **能力**：按[身份的共同验收](../../00-overview/guides/identity.md#共同验收)核对新成员：访问与刷新令牌、issuer、audience 与类型、撤销与注销、密钥轮换（含预先发布的备用密钥，[协议 19](../19-config-secrets-registries-release.md)）、MFA 与敏感声明、平台主体映射、用户停用、目录事件；授权组件补取时需要的“拉取截至此刻的变更”（安全 03）；声明实现实例（[协议 02](../02-projections.md#来源更换实现)）。
   - **依赖身份的授权能力**：重查部署中依赖身份成员的授权能力是否仍然满足，例如紧急访问需要的独立认证路径（[安全 09b](09b-capabilities-and-profiles.md#能力目录) 的 `authz.break_glass`）；不满足时，或停止切换，或客户确认在新成员下不启用该能力。
   - **映射**：为每个平台主体准备新成员中的外部身份（`(issuer, subject)`）。来源可以是预先登记的映射表、目录联邦中的稳定标识，或经确认的绑定流程（安全 02）。多对一一律拒绝。每个可用的授权管理员都必须有映射，否则停止：没有映射的管理员切换后不能登录，受保护操作的确认会无人能做。其他没有映射的平台主体列入清单，切换后不能登录，直到经确认的绑定完成。
   - **控制台**：确认旧身份产品的管理控制台可以锁为只读（产品设置，或在网络上禁止管理入口）；做不到时停止，因为第 6.2 步之后在旧控制台停用的账号无人接手。
   - **身份来源的消费者**：由订阅登记列出订阅了身份来源的全部消费者（授权组件、员工组件中账号与员工的关联、显示用的投影，以及以身份产品的目录事件为来源的适配组件）。每个消费者都要在第 6.5 步事先登记新成员的实现实例并完成对齐；协议 02 规定没有事先登记的实现实例变化一律不采用，漏登记的消费者会停住，或把新实例从小数开始的版本全部当作旧值忽略。
   - **账号管理的入口**：账号管理（停用、冻结、撤销会话）经适配组件的接口办理，由平台授权判断；切换窗口内，新适配组件接受两个成员签发的用户令牌（两套公钥都已预先发布），所以第 6.2 步之后旧适配组件代理过来的请求能被办理，不依赖新产品接受旧 issuer 的令牌。
   - **MFA 重新登记**：MFA 不能迁移时，选定新成员中首次登记的证明方式，强度不低于原来的认证：（a）切换窗口内，用户在旧成员上（已过 MFA）预先登记新成员的因素，由旧适配组件签发绑定该用户的一次性登记码；（b）管理员经受保护操作（安全 08）为用户发放一次性登记码，经带外渠道交付；（c）客户规定的带外确认。原来没有 MFA 的账号按新成员的普通流程登记。密码不能迁移时，新成员的密码重设流程不能比旧成员弱（例如不能只凭邮箱，而旧成员要求邮箱加 MFA）。
   - 存在缺口时停止：要么不换，要么先补齐，再重新预检。
2. **进入切换窗口。**旧成员中的**放宽**类账号变更（新开账号、重新启用、新的外部链接、MFA 降级）被驳回；首次登录的自动开通关闭（没有映射的外部账号不能登录，也不会新建平台主体）。**收紧**（停用、安全冻结、撤销会话）照常在旧成员上生效，并记入切换增量。登录照常在旧成员上进行；选了方式（a）的，用户在这段时间预先登记新成员的 MFA。
3. **导出。**从旧成员导出截至某一时点的全部账号状态（`active`、`disabled`、`security_frozen`）、每条停用的产品坐标（安全 03）、平台主体映射与外部链接，以及已删除的平台主体与已解除的链接（作为墓碑，使新成员不会让它们复活）。密码与 MFA 登记通常不能迁移；能否迁移由两种产品的能力决定，不能迁移的，切换后按第 1 步选定的方式重新设置。
4. **导入与核验。**新成员按映射导入账号与状态。新适配组件为每条导入的停用与冻结记一条本地停用记录，坐标取写入新产品后的变更标识（安全 03 的产品坐标），所以新产品以后回退丢失这次停用时，拉取到的“启用”会被判为回退。逐个平台主体核对：状态相同；没有一个平台主体在新成员中的状态比旧成员宽（停用的不能变成启用）；墓碑没有复活；映射一对一。任何差异都中止切换并列出。
5. **追平增量。**把导出时点之后在旧成员上生效的收紧重放到新成员（同样记本地停用记录），再核对一次受影响的平台主体。
6. **切换**（按顺序；前一小步完成才进入下一小步）：
   1. **收紧先旧后新。**此后的收紧由旧成员受理：先在本地提交并记入增量（“待转发”），本地提交成功后调用者即得到“已生效”，再转发新成员（新适配组件记本地停用记录）；转发失败时由旧成员重试。
   2. **围住旧成员。**依次：旧产品的管理控制台锁为只读；旧适配组件向产品做最后一次“截至此刻”的拉取，把拉到的收紧（包括控制台里刚提交、还没被定时拉取取到的停用）记入增量；然后旧适配组件停止受理任何账号变更，此后收到的收紧代理给新成员（按安全 02 转发原用户的凭据，新适配组件按第 1 步接受），放宽一律驳回；旧成员停止签发与刷新令牌；旧适配组件不再写回声、不再回答补取。最后一次拉取失败时不继续，重试或回退。
   3. **排空。**把全部“待转发”与未重放的增量重放到新成员，直到为零。排空为零是进入 6.4 的守卫：围住在前、排空在后，所以围住之后不会再有新的“待转发”，排空为零就意味着旧成员上生效过的每一次收紧都已到达新成员。
   4. **新成员开始签发，恢复放宽。**新成员开始签发令牌（签名公钥已按 6.6 预先发布）；放宽类账号变更在新成员上恢复受理。6.2 到这里之间不能登录，已签发的访问令牌在有效期内照常使用；这段时间通常很短，因为 6.1 一直在持续转发。
   5. **各消费者更换身份来源。**第 1 步列出的每个消费者，按[协议 02 的来源更换实现](../02-projections.md#来源更换实现)：事先登记新成员的实现实例；把自己用于补取与批量读取的身份来源地址（一个单独的部署变量，与登录、公钥地址分开）指向新成员；做一次完整的重新取回，对齐完成之前依赖身份来源的判断按“无法证明”处理，完成后由新成员的回声恢复水位。授权组件最先进行。6.2 之后旧成员已不回答补取，所以各消费者的水位从 6.2 起就停住，依赖它的判断在超过 `D_src` 后已按无法证明处理；维护窗口的时长要计入这段对齐。
   6. **签名密钥、服务凭据与会话。**
      - 新成员的签名公钥事先加入身份族的公钥集合（预先发布，协议 19）；切换窗口内，两个成员发布的公钥集合都同时包含新旧公钥，组件无论从哪个地址取得公钥都能验证两边的令牌。
      - 组件在旧访问令牌的有效期内仍接受旧成员签发的令牌（停用照常经授权组件的视图生效，不依赖令牌过期）；旧成员的刷新令牌不被新成员接受。
      - 浏览器会话由身份适配组件在服务端持有，旧适配组件的会话随之失效，用户重新登录；边缘丢弃缓存的旧令牌（[协议 20 的登录与会话](../../../protocols/20-frontend.md#登录与会话)）。
      - 服务凭据：组件之间的服务身份默认来自部署信任域签发的证书（安全 02 的基础路线），不受身份切换影响；部署采用身份成员签发的服务令牌时，按同样的方式切换：新成员的服务令牌公钥先加入、再切换签发、旧的到期后移除。
   7. **换地址。**部署变量中的身份族地址（`$endpoint:` 引用）与前端回调地址指向新成员；滚动生效期间，旧适配组件对新的登录请求重定向到新成员，不再自己签发。

各阶段由谁处理请求：

| 阶段 | 收紧（停用、冻结、撤销会话） | 放宽（开通、重新启用、新链接） | 登录与刷新 | 补取与批量读取（各消费者） |
| --- | --- | --- | --- | --- |
| 第 2–5 步 | 旧成员，记入增量 | 驳回 | 旧成员 | 旧成员 |
| 6.1 | 旧成员，记入增量并转发新成员 | 驳回 | 旧成员 | 旧成员 |
| 6.2–6.3 | 经旧适配组件代理到新成员 | 驳回 | 暂停；已签发的访问令牌照常使用 | 旧成员不作答，水位停住 |
| 6.4 之后、该消费者完成 6.5 之前 | 新成员 | 新成员 | 新成员 | 新成员已可作答；该消费者对齐前按无法证明 |
| 该消费者完成 6.5 之后 | 新成员 | 新成员 | 新成员 | 新成员 |

7. **观察与回退。**
   - 第 6.2 步之前：回退就是撤销切换窗口，旧成员恢复受理放宽、恢复自动开通的原设置，新成员的导入丢弃。
   - 第 6.2 步之后：按本协议反向执行一次：从新成员导出账号状态与增量，旧成员导入、核对，停用不丢失；授权组件把身份来源再更换回旧成员（协议 02 的来源更换实现）。旧成员的重新启用规则仍按产品坐标（安全 03）判断，期间在新成员停用的账号不会因回退而复活。
   - 成功切换、观察期结束后，首次登录的自动开通按客户原来的设置在新成员上恢复（映射规则仍按安全 02）。
8. **退役旧成员。**旧成员签发的最后一个访问令牌过期、全部组件已换地址、观察期（起始 1 天）内没有请求到达旧成员之后，从公钥集合中移除旧成员的公钥（协议 19 的退役步骤），再退役旧成员。

```mermaid
sequenceDiagram
    participant Op as 账号管理
    participant Old as 旧身份成员
    participant New as 新身份成员
    participant Z as 授权组件（及其他消费者）
    participant U as 用户与边缘
    Note over Old,New: 第 2–5 步：窗口内只收紧；导出、导入、核验、追平
    Op->>Old: 停用账号
    Old->>Old: 本地提交，记入增量“待转发”
    Old-->>Op: 已生效
    Old->>New: 转发停用（新成员记本地停用记录）
    alt 转发失败
        Old->>Old: 保持“待转发”，重试
    end
    Note over Old: 6.2 围住：控制台只读 → 最后一次拉取记入增量 → 停止受理与签发、不再作答补取
    alt 最后一次拉取失败
        Old->>Old: 不继续；重试或回退
    end
    Op->>Old: 再停用一个账号
    Old->>New: 代理（转发原用户凭据）
    New-->>Op: 已生效
    Note over Old,New: 6.3 排空“待转发”为零（进入 6.4 的守卫）
    Note over New: 6.4 新成员开始签发，恢复放宽
    Note over Z,New: 6.5 各消费者更换身份来源（来源更换实现）
    Z->>New: 完整重新取回账号状态
    New-->>Z: 全部账号状态（含停用）
    Note over Z: 对齐完成前依赖身份来源的判断按“无法证明”

    Old-->>U: 拒绝，重新登录
    U->>New: 登录（映射到同一平台主体）
    New-->>U: 新令牌
```

结论：围住旧成员之前的停用都先落旧成员（控制台里的由最后一次拉取取到），并在排空为零之前全部到达新成员；围住之后的停用只能落在新成员；消费者在排空之后才更换来源，并完整对齐。所以切换既不会让停用的账号复活、也不会让某次停用失去上界，任何人也不会因切换获得更多访问（IM01–IM23）。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| IM01 | 新成员缺少停用、撤销或密钥轮换等必需能力 | 预检停止并列出缺口；不切换 |
| IM02 | 两个旧账号映射到新成员的同一个外部身份 | 拒绝多对一；不合并平台主体 |
| IM03 | 某平台主体没有映射 | 切换后不能登录，直到经确认的绑定完成；不按邮箱或登录名自动认人，不自动开通新的平台主体 |
| IM04 | 旧成员中已停用的账号 | 新成员中仍是停用；核验发现变宽即中止切换；新产品以后回退丢失这次停用时，按本地停用记录判为回退并重新停用 |
| IM05 | 切换窗口内停用一个账号，转发新成员失败 | 调用者得到“已生效”；增量保持“待转发”并重试；排空为零之前不进入 6.4；切换后仍是停用 |
| IM06 | 切换窗口内新开账号或重新启用 | 驳回 |
| IM07 | 授权组件更换身份来源 | 事先登记新实现实例，完整重新取回，对齐前依赖身份来源的判断按无法证明处理；没有登记的实现实例变化不采用 |
| IM08 | 用户用旧成员的刷新令牌续期 | 拒绝，重新登录；旧访问令牌在有效期内仍被接受，停用照常经授权视图生效 |
| IM09 | 切换后账号与员工的关联、授权记录与审计 | 不变；都引用同一平台主体 |
| IM10 | 新成员签发之后回退 | 反向执行本协议；期间在新成员停用的账号回退后仍是停用 |
| IM11 | 旧成员的最后一个访问令牌尚未过期 | 旧成员的公钥保留在两个成员的公钥集合中，直到过期后才移除 |
| IM12 | 初始管理员的安装认领 | 不因切换重新打开；管理员按映射登录到原平台主体 |
| IM13 | 6.2 之后有人在旧产品控制台停用账号 | 控制台已只读，停用无法在旧产品落地；不能锁为只读的部署在预检时停止 |
| IM14 | 某个可用的授权管理员没有映射 | 预检停止；不进入切换 |
| IM15 | 新成员不能提供拉取，只能按 `D_source` 声明上界 | 预检停止，除非客户书面接受新的上界并改写产品说明 |
| IM16 | 用户切换后执行需要 MFA 的操作，尚未在新成员登记 MFA | 拒绝，引导登记；不因切换豁免 MFA |
| IM17 | 控制台锁定前一刻有人在控制台停用账号，定时拉取尚未取到 | 6.2 的最后一次拉取把它记入增量，排空后到达新成员；最后一次拉取失败时不继续 |
| IM18 | 攻击者持有某管理员泄露的密码，切换后抢先在新成员登录并登记 MFA | 首次登记需要第 1 步选定的证明（旧成员上预先登记、管理员发放的一次性码或带外确认）；没有证明不能登记，需要 MFA 的操作拒绝 |
| IM19 | 员工组件也订阅了身份来源 | 预检列出；6.5 事先登记新实例并对齐；漏登记时它停住并告警，不把新实例的版本当作旧值忽略 |
| IM20 | 6.2 之后、6.4 之前发现账号被盗 | 经旧适配组件代理到新成员停用；新适配组件接受旧成员签发的令牌办理 |
| IM21 | 6.2 之后、排空为零之前有人重新启用账号 | 驳回；放宽在 6.4 才恢复 |
| IM22 | 旧成员中已删除的平台主体与已解除的链接 | 作为墓碑导出导入，在新成员中不复活 |
| IM23 | 6.2 之后、6.4 之前用户登录 | 暂停登录；已签发的访问令牌在有效期内照常使用 |

## 已知风险与待定

- 各身份产品之间凭据（密码、MFA 登记）能否迁移，按具体产品核对；不能迁移的，客户说明写明用户需要重新设置。
- 目录联邦（LDAP、AD）作为外部身份源时，映射使用目录中的哪个稳定标识，随具体产品确定。
- 各身份产品的管理控制台能否锁为只读、怎样锁，随具体产品核对。
- 切换窗口与授权组件重新对齐身份来源的实际时长，在代表部署实验中测量。
- 以身份产品的目录事件为来源的组织、员工适配（企业目录同步）随部署设计确定；它们作为身份来源的消费者，按第 6.5 步更换来源。
- 本页没有参考模型；停用不丢失、映射一对一与来源更换，靠实现测试与切换演练。
