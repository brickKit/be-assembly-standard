# 权限与安全

本目录定义所有授权实现都必须保持的安全语义：身份、授权的求值与时间、授权管理、共享与委托、共同契约、有限表达、状态与变更、编码、提供方与成员切换（授权与身份）。本页是总览：目标与分工、必须统一的语义、已定的授权边界与它们的设计位置，以及审批、审计、后台任务与方案替换的安全要求。

客户想看权限的类型、具体组件、优劣势、部署与切换，从[授权的选型说明](../../00-overview/guides/authorization.md)进入；身份、授权与组织的职责与选择关系见[选择方式与关系](../../00-overview/04-selection.md)。角色、范围、属性条件、字段、共享与关系可以在一个成员内组合；客户按已启用业务所需的能力选择实现，模型名称不等同于互斥的组件。完整授予、管理边界与撤销等保证，不因换模型或精简部署而降低。

## 目标与分工

认证证明调用者是谁；授权决定他能做什么、看哪些对象与字段；组织与任职提供业务事实；业务组件拥有对象与业务约束；审计记录决策与操作。认证产品与授权产品分别选择，不能把登录产品的名称当作全部权限能力。

初期所有组件由项目维护，允许受控的配置、适配代码与工具修改，使方案能够方便地替换。适配的落点要明确，避免每个业务组件重复翻译同一套提供方语义。

## 必须统一的语义

| 方面 | 必须写清的结果 |

| 功能 | 菜单、按钮、接口与命令的权限键；拒绝与公开接口 |
| 数据范围 | 本人、组织、法人、仓库、项目、区域等维度及其组合 |
| 对象关系 | 拥有、共享、协作、交接、继承、到期、撤销 |
| 字段与动作 | 脱敏、读写限制、敏感字段的过滤与排序、导出与批量动作 |
| 业务控制 | 审批资格、职责分离、金额门槛、期间锁；归授权还是归业务规则 |
| 一致性 | 权限变更后何时生效、修订令牌、缓存过期、同步失败时的行为 |

| 多层数据 | 主库、投影、搜索、报表、冷数据、文件与缓存的访问边界 |

| 后台授权 | 用户的查询与导出重新验证当前授权；已到明确业务授权节点的后续由受限的服务主体推进；取消与冻结保留（D29） | [协议 01](../01-background-work.md) 的发起主体与服务身份、协议 13 的导出 |

三条贯穿的原则：

- **新鲜度要有可验证的边界**：用户可以先明确调整业务范围，再选择精简的方案；不能静默忽略已有的权限规则或降低保护。新鲜度不能只用“有轮询、有缓存”描述，必须有可以验证的时间与故障边界（安全 03）；具体数值在设计与测量后确定，不从某个轮询间隔推出保证。
- **汇总的单位是一份授予**：授权汇总的单位是一份授予及其全部条件，不是先把功能、范围、条件与字段分别取最宽再组合。列表、详情与字段输出都保持这一规则；按任职签署的操作保留可审计的具体工作归属。
- **没有管理员可配置的 Deny**：角色与授予决定能做什么，业务强约束决定当前单据能否执行动作；本人自审、期间锁等不能因另一份允许的授予而被跳过。两者的执行位置与解释机制统一设计，不能只靠前端隐藏。

## 查询与授权管理采用有限表达

- 求值的核心是完整授予的有限中间表示：按完整段保留操作、范围、条件、字段与资格来源，分别定义读取集合、动作资格与字段输出；单对象与 SQL、冷查询从同一语义产生（安全 01）。段是每个已声明维度恰好一个原子的合取，原子种类有限且在求交下封闭，所以包含可以逐维判断，委托的派生可以逐维求交，列表可以逐段编译、用命中位图逐行确定字段（安全 07）。
- 图或策略引擎的结果要通过相同的查询与字段契约。可以用“候选集加权威检查”，但不能先分页再删除无权的行，不能把截断的 ListObjects 当作完整集合，也不能把超时当作零条。满足不了所选业务的完整查询能力时，阻止启用，或选择明示且受控的异步查询。
- 受限管理员的授予上限要能证明。标准只开放可以验证包含关系的范围与条件表达；任意策略语言之间的蕴含关系不能无条件自动判定。无法证明不越界时，拒绝或转合格的上级确认；角色修改的间接影响同样处理（安全 04）。

## 内部服务也要认证

服务凭据与用户身份分别证明；按声明的入口模式检查部署、目标方法与业务资格；资源、组织、任职与授权的属性各有权威（安全 02）。`be-caller`、actor 名字与内网端口不构成认证；系统补全、事件、后台任务与回调不能扩大用户的范围。基础路线是 mTLS 证书与受控轮换，复杂部署可以接平台证实，不要求先引入服务网格。多客户的受众与凭据隔离、恶意成员需要独立进程，这两条边界保持。

## 授权管理与生命周期

集中与受限的分级管理共用一套管理上限与任职生命周期（安全 04）：

- 管理者以自己的身份操作，管理权与业务使用权分开；每个新增或扩大的授予的完整段，都需要可以证明的上限见证；自己的其他账号、角色编辑、批量与再下放都不能绕过。回收另验管辖权，不要求先有权重新授出旧的宽许可。
- 采用机构的管理职责、个人持有的资格与明确的治理来源，区分交接与收紧；管理的生效与接受在同一事务中完成，或有等价的提交屏障。
- 任职事实、建议、确认与生效的授予分开：旧任职的绑定失效，新的授予默认由合格的管理者确认，其他兼任与独立的直接授予按各自的依据判断；资格实例不复用，调岗、重新入职、多账号绑定、未来生效与预先审核的计划都要重新验证。跨组件的收紧不从“有事件”推出零延迟撤销；业务责任的交接不自动授出新的权限。
- 正常卸任结束个人的管理资格，不自动结束机构的治理边界或合法的普通业务授予，原来源保留；接任经合法确认，无人接任时由已声明的上级或受控恢复接管。被授予人的任职失效、机构上限的收紧或撤销、安全事件与个人委托各有不同的处置。
- 标准模板、客户实际的角色版本与授予绑定分别维护，新增的权限默认经客户确认；发布新的角色修订不就地扩大全部旧绑定。批量计划与上限在各生效点重新验证；旧角色不能绕过已退役的键、当前的安全修复或必需控制。
- 系统角色、最后一名管理员与专用超级用户单独保护；生产环境默认无人持有超级角色；演示数据不作为生产模板。最后管理员的保护不能维持已受侵的身份，安全处置转受控恢复；员工离职等来源事实照常生效，可用管理员为零时部署进入待恢复（D62）。

## 共享、委托与只读扮演

普通资源共享由明确的机构治理资格授出有限的读取，不能从个人的临时阅读权转换成持久共享；正常授出操作人卸任，不自动撤销合法的机构共享，治理范围、接收资格与资源变化仍然检查。个人的临时查看与代办，使用当前来源的完整许可与创建上限，不能与代理人自己更宽的角色拼接。只读扮演保留真实与被查看的主体、必要的日志与通知，后端按副作用 profile 保护，不只禁止 HTTP 的写动词；再委托在基础档关闭，复杂的链要有显式的有限能力（安全 05）。

## 审批与流程控制

完整协议在[协议 09](../09-approval-and-workflow.md)。安全上必须保持的结论：

- 审批依据绑定被审的具体内容（关键字段的摘要）；影响结论的关键修改使受影响的审批失效并重新审批，旧审批不能放行新内容；放行由业务组件在执行事务内核对，待办显示“已处理”或引擎的通知都不是放行证据。
- 本人自审以人为单位比较，账号、代理与角色切换都不能绕过（D10）。
- 在途实例绑定流程版本，但版本绑定不冻结人：资格、权限、职责分离与期间锁在每次提交时检查（D23、D60）。
- 人员变化时按绑定规则与当前组织重新分配；找不到合法替代时暂停转人工；改派不授予权限，不凭上级身份放行（D38）。
- 超时不产生同意或拒绝；申请到期是独立的结果；审批等待不延长单据、预占与付款的期限（D39）。

## 审计的动作与读取范围

长期业务审计按风险与明确的动作清单覆盖：必要的变更、权限与配置的变化、敏感读取与导出、代操作、安全拒绝等；普通低风险的读取保留访问日志。规范与组件声明共同给出必需的动作，客户可以在允许的范围内扩展，默认的必需类别见[协议 03 的“什么需要审计”](../03-audit-durability.md#什么需要审计)；缺漏由操作定义中的 `audit: required` 与一致性套件检查。

成功的业务变更，审计记录与业务在同一事务中写入审计专用的本地发件表，再可靠转运；删除资格绑定审计组件的回执与备份水位，而不是运输的期限（协议 03）。读取、失败与拒绝没有已提交的业务变更，需要自己可靠的采集与保存机制；必要的审计不能用采样的访问日志代替。完整响应与明文的敏感字段不复制进日志，审计查询本身也受授权控制。

验收动作清单、敏感读取与导出、代理与拒绝、记录失败、容量保护、查询权限与恢复。保留年限按具体类别、地区与客户要求核对，不编造统一的法定下限。

## 后台任务的身份与授权

| 类型 | 授权边界 |
| --- | --- |
| 仍然代表用户的查询与导出 | 执行与交付结果时按当前有效的授权重新验证，保留发起人，不用系统身份扩大数据范围 |
| 已确认业务的持久后续处理 | 到达明确的业务授权节点后，由受限的服务主体按既定的范围与输入推进，检查当前的业务状态与必需控制 |

只接收请求或保存草稿，不代表已到业务授权节点。不能把所有异步操作都归为系统任务；服务权限失效、业务取消或冻结、内容修订与重新审批，各按明确的控制处理。原发起人离职，不自动撤销已执行的事实，也不自动停止全部必要的后续。

保留原发起人与实际执行者的审计链。任务分类与服务身份见[协议 01](../01-background-work.md)，结果的领取与下载链接见协议 12、13；各业务的授权节点随组件声明；撤权、取消与恢复都进入验收。

## 方案替换的验收

正反场景集中在[权限与授权的验收矩阵](../../01-conventions/validation/authorization-matrix.md)：完整授予、查询与字段、授权管理、审批控制、服务任务、新鲜度、替换与证据。矩阵是待实例化的验收规格，具体的契约、接口与版本随实现绑定。

- 统一契约规定能力集合、版本与缺失能力时的明确响应。不同模型不能只比较同名的 API：角色并集、条件规则与关系图的对象语义可能不同。用独立的向量与真实的请求，证明允许与拒绝、列表与单对象的判断、分享与撤销、字段裁剪都相符。各实现同时满足客户组合要求的能力与该操作的新鲜度保证。
- 矩阵中 PA01、PA25 同时覆盖伪造的服务主体与部署受众；PA07、PA29 覆盖列表截断与超时；PA15 覆盖无法证明的管理上限；PA27、PA28 覆盖远程授权检查与提交的竞争、新内容配旧关系。实例化时写具体的允许节点与拒绝预期，不只检查最终撤权。
- 迁移不只搬角色名称，还要处理主体、权限键、对象关系、授予的到期、撤销、审计与投影的修订。方案在离线、延迟、陈旧、重启与切换期间的行为必须可以解释。详见[授权的选型说明](../../00-overview/guides/authorization.md)与[身份的选型说明](../../00-overview/guides/identity.md)。
- 继续选用 Casdoor 时，它 tokenFormat 的已知问题必须在身份适配中修复并验证；对客户的资料不把未修复的方案写成已达到安全验收。三种语言的 SDK 必须由同一组黑盒向量证明行为一致。

## 已知风险与待定

- 按通用 ERP 覆盖典型的权限场景，再由选定的客户样板明确角色矩阵、职责分离与敏感数据的要求。没有具体客户时，不猜测法定的保存期与合规结论。
- 仍需实现与实测确定的：能力的命名与版本规则（安全 09）；新鲜度参数的实测（安全 03）；关键操作清单、管理清单、岗位模板、适用审批的单据、关键字段、各业务的授权节点，随组件声明；退役权限与安全修复的升级演练；组织重组时的历史更正，随组件设计；审批任务交接的运行验证、审批超时的数值实测与流程版本的升级验证；客户扩展审计的管理界面。
- 身份、授权、目录与法人组织之间的归属，已按 D05、D06 与[安全 02 的权威分工](02-trusted-identity-and-attributes.md#权威分工与属性登记)确定；组件边界变化时同步复核。
