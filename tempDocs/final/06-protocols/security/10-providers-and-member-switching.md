# 授权成员的能力与切换

客户可以选择使用哪一套授权实现。[安全 01](01-authorization-evaluation.md)到[安全 09b](09b-capabilities-and-profiles.md)定义了所有成员共同的语义、记录与编码；本页回答两件事：

1. 各类授权实现（标准、静态、关系图、策略引擎、嵌入库）分别能承担[能力目录](09b-capabilities-and-profiles.md#能力目录)中的哪些能力：哪些由引擎原生提供，哪些要由我们的适配层补，哪些根本做不到。
2. 新版本上线之后，客户从一个授权成员换到另一个时，怎样保证换完之后谁能看什么、能做什么完全不变，并且能回退。

外部产品的能力按官方文档核对（2026-10-13），出处列在[依据与独立判断](#依据与独立判断)。身份成员（IAM）的切换不在本页，见[已知风险与待定](#已知风险与待定)。通用的选配变更阶段见[选配变更、替换与停用](../../00-overview/05-change-and-retirement.md)；本页是其中授权成员的专门协议。

## 基本设计：记录是唯一权威，引擎是派生索引

| 路线 | 判断 |
| --- | --- |
| **采用**：[安全 09a](09a-encoding-and-records.md#安全记录)的安全记录是唯一的权威数据，保存在所选授权成员自己的库中；外部引擎（OpenFGA、SpiceDB、OPA、Cerbos、Cedar、Casbin）只是由记录编译出的执行索引 | 换成员就是用同一批记录在新成员上重建索引；新旧是否等价，可以逐主体比较有效段的摘要；引擎的故障或陈旧由我们的视图修订与有效期处理；客户的授权数据永远是同一种格式 |
| 外部引擎作为权威，客户直接维护元组或策略 | 引擎的原生能力用得最充分；但完整授予的配对、来源、生命周期、管理上限都要在每种引擎里重新表达，换成员要逐个引擎写双向转换，等价无法验证 |

采用的路线有代价：引擎能做、而我们的记录表达不了的东西用不上。这是有意的：[安全 07](07-finite-expressions-containment-and-queries.md) 说明了，任意策略之间的包含无法判定，任意条件也不能保证下推成完整查询。超出共同表达的需求，按安全 07 的做法新增原子种类、写规范与验收，再在各成员上实现；不允许某个成员悄悄扩大语义。

由此，各类外部引擎在本项目中的价值与定位如下：

| 路线 | 价值 | 定位 |
| --- | --- | --- |
| 关系图（OpenFGA、SpiceDB） | 深层、大规模关系的计算（团队、项目成员、层级） | 为 `related` 原子提供完整候选集与单对象判定 |
| 策略引擎（OPA、Cerbos、Cedar） | 客户偏好用策略语言表达规则，或已有统一的策略平台 | 作为编写前端：只接受能编译成我们原子的受限子集；或者只用于声明为“仅单对象”的操作的附加判定 |
| 嵌入库（Casbin） | 少一个服务进程 | 在我们的成员内作为求值实现，不改变记录与语义 |

## 外部产品的已核实能力

以下按官方文档核对（2026-10-13），只列与本项目能力目录直接相关的事实。

**OpenFGA**

- ListObjects 在期限（`listObjectsDeadline`，默认 3 秒）与条数上限（`listObjectsMaxResults`，默认 1000）内返回；流式版本 StreamedListObjects 没有固定的条数上限，只受执行超时限制。
- 查询可以指定一致性：`MINIMIZE_LATENCY` 可能使用缓存；`HIGHER_CONSISTENCY` 绕过缓存直接查库。
- 支持带条件（CEL）的关系元组，条件的上下文在请求时提供。
- 没有字段级权限的概念。

**SpiceDB**

- 一致性有四档：`minimize_latency`（可能陈旧）、`at_least_as_fresh`（不早于某个 ZedToken）、`at_exact_snapshot`（快照可能过期而失败）、`fully_consistent`（绕过缓存）。ZedToken 表示单一数据存储中的某个时间点。
- LookupResources 支持游标。官方说明它适合中等规模的结果，约 1 万条以上可能有性能问题，建议改用批量 Check 做后过滤。
- 公开的安全公告中：CVE-2025-65111，schema 中某权限为 union、两侧引用同一关系、且一侧经箭头指向另一定义的权限时，LookupResources 可能漏掉有效结果，而其他 API 计算正确（1.47.1 修复）；CVE-2024-48909，评估路径上有 caveat 时，LookupResources2 会错误地返回“条件成立、缺少上下文”（1.37.1 修复）。

**OPA**

- `/v1/compile/filters/include` 用部分求值把 Rego 规则编译成数据过滤条件，目标包括 PostgreSQL 等方言的 SQL WHERE 子句与 UCAST 结构；支持列掩码规则；无条件拒绝与无条件包含有明确的返回形式。
- 只有 Rego 的一个受限子集（官方称为 fragment）可以翻译，并非每种构造都支持每种目标。

**Cerbos**

- PlanResources 返回三种结果：总是允许、总是拒绝、条件（以 AST 表示）；官方提供把 AST 转为 Prisma、SQLAlchemy 等查询的适配器。

**Cedar**

- 官方最佳实践说明：以属性为主的策略难以回答“谁能访问什么”，需要逐条规则对照每个主体与资源；需要优化列表的产品可以改用以角色为主的模型。批量操作需要逐个资源发起授权检查。

**Casbin**

- 进程内的授权库，支持多种模型配置；判定在调用进程中完成。

## 能力矩阵

“原生”表示引擎本身提供，适配层只做映射；“适配”表示需要我们的适配层完成，并列出条件；“记录层”表示由我们的记录与 SDK 承担，与引擎无关；“不可得”表示该路线不能声明此能力。全部能力都必须通过对应的一致性套件，才能把证据状态标为 `verified`（[安全 09b 的能力声明](09b-capabilities-and-profiles.md#能力声明)）。

| 能力 | 标准成员 | 静态成员 | 关系图成员 | 策略引擎成员 | 嵌入库 |
| --- | --- | --- | --- | --- | --- |
| `authz.core` | 原生 | 原生 | 适配：引擎给出单对象判定，字段由记录层按命中段计算 | 适配：同左 | 适配：同左 |
| `authz.list.complete` | 原生（[安全 07 的编译](07-finite-expressions-containment-and-queries.md#编译)） | 原生 | 适配：`related` 原子用引擎的完整候选集；必须能证明结果未截断（流式完成、未触及上限与期限），否则返回“查询不可完成” | 适配：只限能翻译成我们原子的受限子集；OPA 取结构化目标（UCAST）而不是 SQL 文本，Cerbos 取 AST，再翻译成原子；翻译不了即不可完成 | 记录层 |
| `authz.atom.related` | 适配：组件本地的关系投影加完整性水位 | 不可得 | 原生 | 不可得 | 不可得 |
| `authz.containment.*` | 原生（[安全 07 的包含证明](07-finite-expressions-containment-and-queries.md#包含证明)） | 原生 | 记录层：包含证明只在我们的段上做 | 记录层：同左；引擎的策略不参与包含证明 | 记录层 |
| `authz.management.delegated` | 原生 | 不可得（没有运行时管理） | 记录层 | 记录层 | 记录层 |
| `authz.share.institutional`、`authz.delegation.*` | 原生 | 不可得 | 记录层，关系可以由引擎计算 | 记录层 | 记录层 |
| `authz.impersonation.readonly`、`authz.break_glass` | 原生 | 不可得 | 记录层 | 记录层 | 记录层 |
| `authz.path.bounded_local` | 原生 | 原生（视图来自配置） | 适配：编译视图时以最强一致性读取引擎（OpenFGA `HIGHER_CONSISTENCY`，SpiceDB `fully_consistent`） | 适配：视图包含策略版本 | 原生 |
| `authz.path.strict_acceptance`、`strict_barrier` | 原生 | 不可得 | 记录层 | 记录层 | 记录层 |
| 字段逐行掩码 | 记录层 | 记录层 | 记录层（引擎没有字段概念） | 记录层；OPA 的列掩码规则不替代按命中段的逐行计算 | 记录层 |

- **引擎的修订标识只在该引擎内有意义**：SpiceDB 的 ZedToken、OpenFGA 的一致性选项不跨成员比较；修订只在同一域内比较（[安全 09a 的代次与修订的编码](09a-encoding-and-records.md#视图与核验)）。我们的安全修订与恢复代次由成员的记录层维护，引擎索引滞后时视图不续期。
- **引擎的列表结果即使声称完整，也必须由一致性套件证明**。SpiceDB 的 CVE-2025-65111 说明，列表接口的完整性缺陷会出现在成熟产品中，而同一产品的单对象接口仍然正确，也没有错误提示；只用单对象判定做测试发现不了它。

## 静态成员

静态成员没有运行时管理界面。授权数据是一份按[安全 09a](09a-encoding-and-records.md) 编码的记录文件，随部署发布，文件摘要钉在部署配置中。

- 变更就是发布新的记录文件。[安全 08 的生效点](08-state-and-change-protocol.md#生效点)在部署时执行：装配工具重新做包含证明，然后发布；最后管理员检查不适用（没有运行时管理员）。
- 默认路径照常：视图由成员从文件编译，核验回答由成员本次计算产生。
- **只有授予记录是静态的**。账号状态、任职实例、组织等运行时来源，照常按[安全 08 的有效段的计算](08-state-and-change-protocol.md#有效段的计算)求交，并按[安全 03 的内部来源水位](03-authorization-acceptance-and-revocation.md#内部来源的收紧与来源水位)取得新鲜度；D30 的任职关联授予自动撤销与离职停用，在静态成员下同样生效。
- 不提供分级管理、共享、委托、扮演、紧急访问与严格路径。需要这些能力的客户不能选静态成员（D07：缺能力即阻止装配，不静默降级）。
- 适合权限结构固定、几乎不变的小客户，或者作为测试与演示的基线。

## 成员切换协议

适用于新版本上线之后，客户从一个授权成员换到另一个。默认在预告的维护窗口内进行（D25）。

### 步骤

1. **预检。**比较部署所需的能力与新成员的能力声明（[安全 09b 的准入检查](09b-capabilities-and-profiles.md#准入检查)）；统计新成员无法表示的记录；确认新成员已声明订阅各内部来源、并获准补取（[协议 02](../02-projections.md)），否则它的水位建立不起来。存在缺口时停止：要么不换，要么由客户先显式收窄业务范围或授权（只能收紧，不能借换成员扩权），再重新预检。
2. **进入切换窗口。**新的**放宽**类管理变更被驳回（reason `MEMBER_SWITCH_IN_PROGRESS`）；**收紧**（撤权、停用、安全处置）照常在旧成员上生效（[安全 08 的变更方向](08-state-and-change-protocol.md#变更方向)：收紧一提交即生效），并记入切换增量。来源事件（员工、IAM、组织）照常由旧成员消费，同样记入增量。严格路径停止新的接受，已有许可在 `T_activate` 内完成或终止。业务读写照常，组件继续使用旧成员的视图。
3. **导出。**从旧成员导出修订 R 的全部安全记录、依赖边、确认与计划记录，带每条记录的摘要，以及 R 对应的各来源消费进度。
4. **导入与编译。**新成员导入记录（记录身份不变），编译自己的引擎索引。
5. **等价核验。**对每个分片，两个成员分别计算视图；逐个“主体 × 资源类型 × 操作”比较规范化有效段集合的摘要。另在新成员上运行一致性套件的列表与字段部分。任何差异都中止切换，报告列出具体的主体、类型与操作。
6. **追平增量。**把 R 之后在旧成员上生效的收紧与来源事件重放到新成员，或者让新成员从导出时记录的来源消费进度继续消费；再对受影响的分片做一次等价核验。增量追平之前不切换。
7. **切换**（按顺序，不留窗口）：
   1. **旧成员停止受理放宽类管理写入。**在 7.4 围住旧成员之前，请求仍经旧地址到达旧成员；此后的**收紧**由旧成员受理，并应用到两个成员：旧成员**先在本地提交**（同一事务把这条收紧记入切换增量，标“待转发”），再转发新成员；新成员确认后，旧成员把增量标为“已转发”，然后应答。本地提交失败时请求失败，两个成员都没有变化；转发失败或未确认时，增量保持“待转发”，由旧成员重试。所以直到 7.4 围住旧成员，旧成员回答的核验都已包含这些收紧，新成员也不会领先于旧成员。
   2. **来源消费移交。**旧成员停止消费员工、IAM、组织的事件；新成员从旧成员**最后连续已应用的位置**继续消费，而不是从导出时的位置。此后旧成员的来源水位不再推进，超过 `D_src_high` 时旧成员关闭高风险分片。这是安全的；维护窗口的预期时长要计入它。
   3. **排空。**把旧成员截至 7.2 移交位置的全部增量重放到新成员：第 6 步之后生效的收紧、7.1 之后“待转发”的收紧，以及旧成员在移交之前应用的来源事件；直到旧成员的增量中没有“待转发”或未重放的条目。增量不为空时不进入 7.4。
   4. **围住旧成员，放开新成员，旧成员此后代理。**部署变量中的授权地址（`$endpoint:` 引用）按组件滚动生效，不是瞬时的，所以不能让两个成员各自作答。先让旧成员停止自己作答（不再受理管理写入，不再用自己的状态回答核验），排空“待转发”为零；此后新成员以新的恢复代次开始受理管理写入与核验。旧成员把此后收到的核验与管理请求**代理**给新成员。代理不替调用者说话：
      - 核验是组件以服务身份发出的系统面调用，服务凭据（mTLS 身份）不能转发，所以核验只用**传输层直通**：旧成员把连接原样转给新成员，组件的会话直接终止在新成员（新成员的证书在切换窗口内也包含旧名称）。
      - 管理请求属于用户面，可以按[安全 02](02-trusted-identity-and-attributes.md#用户链路系统命令与委托)转发原用户的凭据，新成员按原用户的身份计算。
      - 回答由新成员本次计算，带新成员的恢复代次，视图有效期仍从组件发出请求时起算，所以撤权上界不变，也不需要暂停受保护操作。
      - 然后滚动更新地址。已换地址的组件发现恢复代次变化，丢弃旧视图，直接向新成员核验；卡住的组件经代理照常工作。新成员不可达时，代理返回授权不可用，组件按有效期保护。
8. **观察与回退。**
   - 新成员开始作答（7.4）之前，回退就是解除围住：旧成员从自己的连续位置继续消费来源事件，丢弃转发给新成员的增量记录。
   - 7.4 之后，回退按本协议反向执行一次：从新成员的数据库导出增量（不要求新成员仍在线服务，所以成员的能力声明包含“离线增量导出”），旧成员重放，再做等价核验；新成员期间生效的收紧与来源事件不丢失。
   - 新成员不可用、数据也读不到时，按授权组件不可用与整套恢复处理（[协议 15](../../../protocols/15-backup-and-recovery.md)）。
9. **退役旧成员。**旧成员“待转发”为零、全部组件已换地址、且一个观察期（起始 1 天）内不再收到代理请求之后，才退役；退役前代理一直有效。审计与授权解释保存在审计记录中，不依赖旧成员在线；旧成员按 D54 的停用规则处理。

### 各阶段由谁处理请求

下表从上面的步骤整理，说明切换的每个阶段中，各类请求由哪个成员处理。标“待定”的组合见[已知风险与待定](#已知风险与待定)。

| 阶段 | 放宽类管理变更 | 收紧（撤权、停用、安全处置） | 来源事件（员工、IAM、组织） | 组件的核验 | 严格路径 |
| --- | --- | --- | --- | --- | --- |
| 切换窗口（第 2–6 步） | 驳回，`MEMBER_SWITCH_IN_PROGRESS` | 旧成员生效，记入切换增量 | 旧成员消费，记入切换增量 | 旧成员作答 | 停止新的接受；已有许可在 `T_activate` 内完成或终止 |
| 7.1 到 7.2 | 旧成员不受理 | 旧成员本地提交并记“待转发”，转发新成员，确认后应答 | 旧成员消费 | 旧成员作答，已含这些收紧 | 同上 |
| 7.2 到 7.4 | 旧成员不受理 | 同上 | 新成员从旧成员最后连续已应用的位置继续消费；旧成员的水位不再推进，超过 `D_src_high` 关闭高风险分片 | 旧成员作答 | 同上 |
| 7.4 之后 | 管理写入由新成员受理；经旧地址到达的，由旧成员转发原用户凭据 | 新成员受理；经旧地址到达的，同左 | 新成员消费 | 新成员本次计算；经旧地址到达的，旧成员在传输层直通 | 待定 |

结论：直到 7.4，作答的始终是旧成员，新成员只接收转发与重放；7.4 之后，只有新成员作答，旧成员只做代理，所以任何时刻都不会有两个成员各自作答。

### 切换过程的状态

| 当前状态 | 事件 | 守卫条件 | 结果状态 | 动作 |
| --- | --- | --- | --- | --- |
| 旧成员服务 | 发起切换 | — | 预检 | 比较能力、统计无法表示的记录、确认来源订阅与补取 |
| 预检 | 预检完成 | 有缺口 | 不切换 | 报告缺口；客户可以先显式收紧，再重新预检 |
| 预检 | 预检完成 | 无缺口 | 切换窗口 | 驳回放宽；收紧与来源事件记入增量；严格路径停止新接受 |
| 切换窗口 | 导出、导入与编译、等价核验 | 有差异 | 中止 | 报告具体的主体、类型、操作 |
| 切换窗口 | 追平增量 | 增量尚未追平 | 切换窗口 | 不切换，继续追平 |
| 切换窗口 | 对受影响的分片再次等价核验 | 有差异 | 中止 | 报告具体的主体、类型、操作 |
| 切换窗口 | 对受影响的分片再次等价核验 | 已追平、无差异 | 停止放宽写入（7.1） | 此后的收紧本地提交并转发新成员 |
| 停止放宽写入（7.1） | 来源消费移交 | — | 来源已移交（7.2） | 新成员从旧成员最后连续已应用的位置继续消费 |
| 来源已移交（7.2） | 排空 | 仍有“待转发”或未重放的条目 | 来源已移交（7.2） | 继续重放，不进入 7.4 |
| 来源已移交（7.2） | 排空 | 增量为空 | 新成员作答（7.4） | 围住旧成员；新成员以新的恢复代次受理；旧成员代理；滚动更新地址 |
| 切换窗口到 7.4 之前的任一状态 | 回退 | — | 旧成员服务 | 解除围住；旧成员从自己的连续位置继续消费，丢弃转发给新成员的增量记录 |
| 新成员作答（7.4） | 回退 | 新成员的数据库可读 | 旧成员服务 | 反向执行本协议：导出新成员的增量（可离线），旧成员重放，等价核验 |
| 新成员作答（7.4） | 回退 | 新成员不可用、数据也读不到 | 整套恢复 | 按授权组件不可用与整套恢复处理 |
| 新成员作答（7.4） | 观察期结束 | “待转发”为零、全部组件已换地址、观察期（起始 1 天）内没有代理请求 | 旧成员退役 | 按 D54 停用旧成员；审计与授权解释不依赖旧成员 |
| 新成员作答（7.4） | 观察期结束 | 上述任一项不满足 | 拒绝 | 不退役，代理继续有效 |

切换增量中，每个条目也有自己的状态：

| 当前状态 | 事件 | 守卫条件 | 结果状态 | 动作 |
| --- | --- | --- | --- | --- |
| — | 切换窗口内、7.1 之前的收紧，或 7.2 移交之前的来源事件，在旧成员生效 | — | 未重放 | 记入切换增量 |
| 未重放 | 第 6 步追平或 7.3 排空时重放到新成员 | — | 已重放 | — |
| — | 7.1 之后，收紧到达旧成员 | 本地提交成功 | 待转发 | 同一事务记入增量，再转发新成员 |
| — | 7.1 之后，收紧到达旧成员 | 本地提交失败 | 拒绝 | 请求失败，两个成员都没有变化 |
| 待转发 | 新成员确认 | — | 已转发 | 应答调用者 |
| 待转发 | 转发失败或未确认 | — | 待转发 | 旧成员重试 |
| 已转发、已重放 | 7.4 之前回退 | — | 丢弃 | 旧成员从自己的连续位置继续消费 |

### 切换的时序

下图画第 7 步的四个子步骤与失败分支。

```mermaid
sequenceDiagram
    participant Admin as 管理入口
    participant Comp as 业务组件
    participant Old as 旧成员
    participant New as 新成员
    participant Src as 来源（员工、IAM、组织）
    Note over Old,New: 7.1 旧成员停止受理放宽类管理写入
    Admin->>Old: 收紧（撤权、停用）
    alt 本地提交失败
        Old-->>Admin: 请求失败，两个成员都没有变化
    else 本地提交成功，同一事务记入增量“待转发”
        Old->>New: 转发收紧
        alt 新成员确认
            New-->>Old: 确认
            Old->>Old: 增量标“已转发”
            Old-->>Admin: 应答
        else 转发失败或未确认
            Old->>Old: 增量保持“待转发”，稍后重试
        end
    end
    Note over Old,Src: 7.2 来源消费移交
    Src->>New: 从旧成员最后连续已应用的位置继续投递
    Note over Old: 来源水位不再推进，超过 D_src_high 关闭高风险分片
    loop 7.3 排空，直到没有“待转发”或未重放的条目
        Old->>New: 重放截至移交位置的增量
    end
    Note over Old,New: 7.4 旧成员停止自己作答，新成员以新的恢复代次开始受理
    Comp->>Old: 核验（地址尚未更新）
    alt 新成员可达
        Old->>New: 传输层直通，会话终止在新成员
        New-->>Comp: 本次计算的回答，带新的恢复代次
    else 新成员不可达
        Old-->>Comp: 授权不可用，组件按有效期保护
    end
    Admin->>Old: 管理请求（仍指向旧地址）
    Old->>New: 代理，转发原用户的凭据
    Comp->>New: 地址更新后直接核验
    New-->>Comp: 回答，组件发现恢复代次变化，丢弃旧视图
```

结论：收紧在 7.1 之后总是先在旧成员落地、再到新成员，所以新成员不会领先于旧成员，旧成员的核验也始终已收紧；7.4 之后核验无论走旧地址还是新地址，都由新成员本次计算，有效期从组件发出请求时起算，撤权上界不变。

## 客户怎样选

| 客户情形 | 推荐 |
| --- | --- |
| 小公司，角色加范围就够 | 标准成员 |
| 权限结构固定，几乎不改，资源最少 | 静态成员（没有运行时管理） |
| 大量项目、团队、层级关系，关系深且多 | 标准成员加关系图成员提供 `related` 原子；或者整体换为关系图成员 |
| 已有统一的策略平台（OPA、Cerbos），或者希望用策略语言维护规则 | 策略引擎成员；策略只能写在可以翻译成原子的受限子集内，超出部分的操作只能声明为“仅单对象” |
| 对撤权的严格性要求高 | 任一具备 `authz.path.strict_acceptance` 的成员，按操作启用严格路径（D57） |

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| PV01 | 新成员缺少部署所需的能力 | 预检停止并列出缺口；不切换 |
| PV02 | 新成员无法表示部分记录（例如金额区间） | 预检报告这些记录；客户只能先收紧，不能借切换扩权或丢弃 |
| PV03 | 切换窗口内提交管理变更 | 放宽驳回；收紧照常生效 |
| PV04 | 切换时有严格路径的许可在途 | 在激活期限内完成或终止；不跨成员延续 |
| PV05 | 新旧成员对某主体的有效段摘要不同 | 中止切换，报告主体、类型、操作 |
| PV06 | 切换后组件仍持有旧成员的视图 | 恢复代次不同，丢弃旧视图，向新成员核验 |
| PV07 | 切换中回退 | 新成员开始作答之前：解除围住，旧成员从自己的位置继续消费；之后：按反向协议迁回，新成员期间的收紧与来源事件不丢失 |
| PV08 | 新成员上已有变更生效后要回退 | 必须反向执行完整协议，不直接切回 |
| PV09 | 关系图成员的列表触及条数上限或期限 | 不能证明完整，返回“查询不可完成”；不把截断的结果当完整 |
| PV10 | 关系图引擎以“最小延迟”一致性返回陈旧结果 | 编译视图时使用最强一致性；陈旧的索引不续期视图 |
| PV11 | 比较 ZedToken 与我们的安全修订，或比较两个成员的修订 | 不允许；只在同一域内比较 |
| PV12 | 策略引擎的规则超出可翻译子集 | 该操作的列表不可完成；只能声明为“仅单对象” |
| PV13 | OPA 返回 SQL 文本 | 适配层不使用 SQL 文本，改取结构化目标并翻译成原子 |
| PV14 | 引擎的列掩码规则与按命中段的字段结果不同 | 以记录层的逐行字段为准；不一致时套件失败 |
| PV15 | 引擎声称列表完整，但一致性套件发现漏行 | 能力证据不能标为 `verified`，装配拒绝依赖它的功能 |
| PV16 | 静态成员的部署请求启用分级管理或委托 | 装配拒绝 |
| PV17 | 静态成员发布新的记录文件，其中授予超出管理上限 | 装配时包含证明失败，发布被拒 |
| PV18 | 切换后查阅审计与授权解释 | 仍可查，不依赖旧成员在线 |
| PV19 | 切换导入后的记录身份 | 与旧成员相同；摘要相同 |
| PV20 | 只比较条数的等价核验 | 不合格；必须比较规范化内容的摘要 |
| PV21 | 切换窗口内撤销一份授予 | 在旧成员上立即生效，记入增量，切换前重放到新成员 |
| PV22 | 切换窗口内员工离职事件到达 | 移交前由旧成员应用，并在排空中重放；移交后由新成员从旧成员最后连续已应用的位置继续消费；切换后不丢失 |
| PV23 | 选用静态成员，员工任职结束 | 任职关联的授予照常失效 |
| PV24 | 追平增量之后、更新地址之前撤销一份授予 | 旧成员受理，并同时应用到两个成员；切换后不复活 |
| PV25 | 切换后回退，新成员期间消费了离职事件 | 反向迁回，离职不丢失 |
| PV26 | 排空之后、换地址之前撤销付款权 | 旧成员先在本地提交并记入增量，再转发新成员；旧成员此后回答的核验已收紧 |
| PV27 | 7.1 之后撤销付款权，旧成员本地提交成功、转发新成员失败 | 增量保持“待转发”，由旧成员重试；排空为零之前不换地址；旧成员的核验已收紧 |
| PV28 | 7.1 与 7.2 之间旧成员应用了一条离职事件 | 排空包括它；新成员从移交位置之后继续消费，离职不丢失 |
| PV29 | 换地址期间，管理入口已指向新成员并撤销付款权，付款组件仍指向旧成员 | 旧成员把核验代理给新成员，回答已收紧；撤权上界不变，不暂停受保护操作 |
| PV30 | 某组件卡住，一直没有换到新地址 | 经旧成员代理照常工作；旧成员在不再收到代理请求、观察期结束之前不退役 |
| PV31 | 代理期间组件向旧地址发核验 | 旧成员在传输层直通到新成员，组件的会话终止在新成员；新成员按组件自己的服务身份计算，不按旧成员的身份 |

## 参考模型

[成员切换等价核验模型](../../../work/checks/12-member-switch-equivalence.py)（种子 20261013，2,000 个随机存储）说明了第 5 步为什么必须比较内容摘要。它把一个无损的关系图式翻译（关系元组加逐元组的条件，再重建段）与标准成员比较，全部一致；四种有损翻译（丢金额区间、按维度压平、丢写字段、忽略有效期）都被发现，并定位到具体的主体与操作。若只比较段的条数，四种都发现不了。

模型只比较修订 R 上的状态，没有建出切换窗口内的收紧与来源事件（PV21、PV22）；第 6、7 步的增量追平、移交与排空靠实现测试。模型也不是 OpenFGA、SpiceDB、OPA、Cerbos、Cedar 或 Casbin 的模型。

## 已知风险与待定

- **一致性套件**：在安全 07 的参考模型与安全 09a 的共同向量的基础上，形成可以对运行中的成员执行的黑盒套件（brickKit 的 T15 类测试）。
- **关系图成员的映射**：`related` 原子到引擎模型的具体对应（关系类型、锚点、深度），以及关系属主的投影协议。
- **策略引擎的可翻译子集**：正式定义哪些 Rego 与 Cerbos 条件对应哪些原子。
- **静态成员**：记录文件的签名与发布流程。
- **身份成员（IAM）的切换**：本页没有涉及。身份侧的稳定主体与迁移规则见[安全 02 的稳定主体与身份链接](02-trusted-identity-and-attributes.md#稳定主体与身份链接)，切换协议待身份专题统一写。
- **切换中的请求处理**：7.4 之后放宽类管理变更何时恢复受理、严格路径何时恢复新的接受，以及等价核验中止之后切换窗口怎样结束，待定。
- **增量追平、移交与排空**（第 6、7 步）不在参考模型内，靠实现测试验证（PV21、PV22、PV24–PV28）。
