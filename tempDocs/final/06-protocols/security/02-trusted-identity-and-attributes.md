# 可信身份、调用链与属性来源

本页为[统一授权求值](01-authorization-evaluation.md)提供可信的上下文：服务与用户怎样分别证明身份，一个请求里的各种身份怎样区分，授权所用的属性从哪里来，事件、后台任务、外部回调与外壳中的身份怎样处理。它不另定义权限的组合公式。

要证明的结果：用户不能自报角色、任职或服务名来扩权；服务凭据不能替用户取得更宽的数据；跨组件、事件、后台任务与外壳都保留正确的责任主体；身份或授权实现替换后，主体与属性的含义仍然对齐。

默认按小公司落地；较复杂的客户可以改用工作负载身份、受众更窄的令牌交换与专用观测。共同的身份与属性保证不随部署精简而取消。验签通过不等于提交时仍然合法：接受与撤权的先后、失效窗口、长连接的紧急停止与持久业务许可，见[安全 03](03-authorization-acceptance-and-revocation.md)。

## 服务凭据的路线

| 路线 | 适用条件 | 代价与边界 |
| --- | --- | --- |
| **基础路线**：每个部署独立的信任根；组件使用有期限的 mTLS 证书，受控签发、文件交付与轮换 | 单机或少量主机、离线机房，没有现成的工作负载身份服务 | 不强制增加常驻的身份组件；要有签发、续期、热加载、到期告警与恢复的工具；不接受永久证书或共用全权私钥 |
| 平台证实与自动签发：SPIFFE/SPIRE、合格的服务网格或平台身份适配 | 动态实例较多、跨主机或集群、运维已有平台，人工续期成本过高 | 多一个信任与可用性的依赖；平台身份必须精确映射到部署与组件，不能只验证“同一个 CA 或集群” |
| 专用的短期服务令牌，经过已认证且加密的通道传递 | 平台提供令牌证实，或目标协议无法使用双向证书 | 受众、用途、持有者与重放风险必须明确；不能复用用户访问令牌的验证器，也不能悄悄退回共享的 API Key |

基础路线是本项目的基础实现，不是自研密码协议，也不是指定新的组件。平台原生机制满足保证时优先复用；只有 Kubernetes 默认的 service account 令牌、IP 或容器网络地址，不构成合格的适配。证书校验交给成熟的 TLS 库，令牌校验交给成熟的 JOSE 库与共同的验证入口。不要求先引入服务网格。

服务证书证明调用方的身份；目标组件、接口与操作的允许关系，在服务端独立检查。客户端也校验目标的身份，不能只检查服务器证书来自同一个根。采用服务令牌时还校验目标受众；接受者不能按调用方自报的地址决定自己是谁。具体的身份 URI、证书 profile、令牌类型与配置键在线协议中登记（[安全 09](09a-encoding-and-records.md)）。

## 权威分工与属性登记

| 信息 | 权威属主 | 接受规则 |
| --- | --- | --- |
| 部署的信任域、获准运行的组件、服务身份到组件的映射 | 部署管理者，以及受控签发或平台证实的机制 | 装配声明的是意图；运行时必须验证凭据，组件不能凭自己的配置自行申请任意身份 |
| 平台账号、外部身份的链接、账号启停、会话与认证证据 | 选定的身份入口（IAM） | 登录产品适配成共同语义；多个外部身份源不能在各业务组件各建一份主体权威 |
| 法人、部门、岗位、汇报关系 | 业务组织组件（D05） | 身份源或 SCIM 的组只是来源数据，经过明确的映射才成为业务组织事实 |
| 员工、在职状态、有效任职 | 员工与任职组件（D06） | 不由身份产品的角色名或用户选择的部门代替；未安装的能力不能伪造成“全部有效” |
| 账号与员工、责任身份的关联 | 员工组件拥有关联（账号身份由身份组件提供，替换身份成员时关联不随之迁移）；建立与变更的确认记录由授权组件的受保护操作保存（[安全 08](08-state-and-change-protocol.md)） | 绑定的变更受专门的管理权限与审核约束，保存两侧的身份与修订；不靠姓名或工号字符串自动认人 |
| 完整授予、管理上限、委托与共享的授权视图 | 授权属主，以及声明的业务关系属主 | 授权组件可以保存受控的投影或求值视图，不接管员工与组织的权威 |
| 对象的归属、金额、币种、状态、修订、审批与执行依据 | 对应的业务组件 | 从本地权威事实、或有完整性证据的属主视图取得；命令输入先经业务校验 |
| 登录因素、真实的认证时刻、客户端、设备证据 | 身份组件，或明确受信的认证适配 | 换令牌或刷新不是重新认证；用户填写 `mfa=true` 无效 |

每个用于授权的属性都登记：类型、来源、修改权限、修订域、有效期或允许的陈旧程度、缺失时的行为、可用的路径。显示名、语言与普通的追踪标签不自动成为安全属性。员工组件不扩张为所有联系人的通用自然人库；非员工的账号仍可以存在，其资格由明确的授予与业务契约提供。

## 稳定主体与身份链接

- **稳定主体**：业务只引用部署内稳定的平台主体标识；姓名、邮箱、登录名与组件版本都不是主体身份。主体不复用。服务的逻辑身份与运行实例的身份分开：多个副本可以代表同一个组件，但使用可以分别轮换与追踪的实例凭据。版本升级不自动变成另一个业务主体，权限能力的升级仍经版本准入。
- **外部账号**：默认以受信身份源下的 `(issuer, subject)` 精确关联。身份源允许的客户端与 issuer 配置先经管理校验，不能从未验证的令牌 URL 拉取任意密钥。首次开通可以创建没有业务授予的普通账号，是否允许自动开通由客户配置；自动开通不自动授出员工、任职或管理员资格。
- **绑定、关联与迁移**：绑定已有账号、SCIM 到 OIDC 的关联、合并与身份源迁移，使用预先登记且唯一的映射或显式的确认流程。“邮箱已验证”或“登录名相同”不是无条件接管账号的证据；身份源的 subject 碰巧相同，也不跨 issuer 合并。改邮箱或登录名不改主体；解除链接、停用、删除与恢复分别处理。删除保留必要的不可复用标识与受保护的历史引用；具体的擦除与保全由生命周期协议定义，不能直接清空已有的业务审计。
- **初始管理员**：使用限定受信身份源与精确身份的预先登记，或有期限、一次性的离线部署确认；绑定与“已消耗”的状态持久保存，并发下唯一。仅凭公开的邮箱或不区分大小写的名字抢先登录，不能成为管理员。常规管理不再使用初始化流程；紧急恢复另走有记录的部署恢复流程，不开放绕过全部认证的接口。
- **更换身份成员**：保留平台主体与已审核的关联；旧服务与用户密钥的验证接受范围显式切换。相同的稳定 issuer 不会让旧令牌立即消失，公钥缓存、会话与旧实例一起纳入时间与迁移协议（[安全 10](10-providers-and-member-switching.md)）。

## 一个请求中的身份结构

下面是行为字段，不是 JSON 或 proto 的形状（编码见安全 09）。

| 字段组 | 含义 |
| --- | --- |
| 部署与凭据用途 | 所属的部署、受众、凭据类别（用户、服务、回调等）、凭据与校验策略的版本 |
| 直接调用的服务 | 已验证的对端组件、实例与凭据身份；浏览器或移动端的直接请求没有内部服务身份，不能自己填一个 |
| 实际操作者 | 正常请求中的用户，或合法委托、扮演链中实际行事的一方；完整的链留作审计 |
| 被代表的主体 | 正常请求中与实际用户一致；合法代办时明确目标主体，不能由请求体覆盖 |
| 履职与上限 | 经过验证的选定任职、有效的委托身份或链、操作范围与字段上限；不等同于客户端的可选参数 |
| 认证与安全状态的证据 | 凭据的有效期、真实的认证时刻与因素、会话或安全修订、所需的新鲜度与证据来源 |
| 资源与资格事实 | 按本页的来源规则取得的事实及各自的修订，供求值使用 |
| 原始发起与业务依据 | 后台流程的原发起人、任务或业务接受的引用；历史的发起信息不冒充当前用户的授权 |

实际操作者、被代表主体、直接服务与历史发起人，不能塞进同一个 `sub` 再按场景猜。上下文只由 SDK 受信的验证入口与受限的作业启动器构造，业务代码显式传递；客户端 JSON 中的 `verified=true`、`actor` 或“系统模式”字段不是验证结果。

本地的并发任务继承已验证请求的上下文与取消、截止时间；长任务另建明确的任务类型。上下文不得有进程级的“当前用户”，也不得有连接建立时捕获的用户槽；复用连接上的每个请求分别构造，防止用户甲的身份被用户乙复用。

## 入口与调用模式

每个入口声明唯一的业务调用模式与可接受的凭据 profile。公开入口也显式声明边界；业务认证与服务认证不能按“有没有某个头”动态猜测。同一个业务处理函数同时服务直接用户与内部代理时，使用明确分开的入口，或由受信的监听与入口配置选择验证 profile；缺少服务证据的代理请求，不能改走同一入口的直接用户分支来绕过方法许可。

| 模式 | 必需证明 | 放行后仍要检查 |
| --- | --- | --- |
| 直接用户入口 | 合格的会话或平台用户访问凭据 | 当前账号与资格、完整授权、资源与业务约束 |
| 服务代理用户的读取或命令 | 已认证的服务与允许的代理路径；原用户凭据或受信交换的凭据 | 被代表主体的授权与上限；服务的权限不能代替用户的范围 |
| 系统查询、系统命令 | 已认证的服务、目标方法的许可与规定的资源范围 | 系统契约的输入、业务状态、来源与接受依据、幂等；不因在内网就免查 |
| 事件处理、固定的维护任务 | 受限的消费者或作业身份与类型，事件或任务的来源合格 | 属主事实、当前的必需控制与允许的副作用 |
| 外部回调、开放 API | 对应渠道或外部应用的专用认证 | 部署、商户或对象的映射、重放与幂等、业务核对；不是普通员工身份 |
| 明确的公开接口 | 声明的公开用途、所需的流量与输入保护 | 不返回受保护的业务数据；凭据无效时不自动退成更宽的匿名路径 |

服务端先验证凭据与部署、用途，再检查服务到目标方法的许可，然后在相应的业务模式中执行求值或系统契约。用户凭据不适用于系统方法；服务凭据不适用于普通用户数据接口。缺用户证据的代理请求拒绝，不降级为系统调用；声称是系统任务的用户输入同样拒绝。

**服务到方法的许可由部署声明**（随客户基线发布），不来自授权视图。所以授权组件不可用时（例如整套恢复的第 6 步，[协议 15](../../../protocols/15-backup-and-recovery.md)），系统方法之间的调用仍按它准入，不形成循环依赖。

`be-caller` 至多是与验证结果核对的标签，不能创建服务身份；保留该标签却与凭据的映射不同时，拒绝并记录安全事件。`be-actor-*`、trace、baggage、来源 IP 与反向代理的头只提供声明或追踪，不能直接成为用户或授权的属性。用户代理入口如果保留当前的 actor 标签，必须与受信的用户证据相容；历史发起人用独立的历史字段，不与当前操作者混用。

**调用面**：系统调用走 gRPC 系统面，用户请求走 HTTP 用户面；用户面的服务代理请求另加服务身份的验证。以后如果要支持用户 gRPC，必须单独声明调用模式与兼容版本，不能因为请求带了用户令牌就开放系统方法。

## 用户链路、系统命令与委托

- **转发原凭据**：基础路线允许在同一部署内、已批准的用户面调用中，经加密且目标已认证的链路转发原平台访问凭据；下游重新验证它的部署、用途、时效与当前所需的安全状态。凭据只留在请求的私有槽里，不写日志、不进消息、不发给第三方，不从任意 URL 选择下游。部署受众的意思是允许在声明的部署内用于用户面，不是允许调用所有系统方法；重定向不能把凭据带出受信的目标集合。
- **令牌交换**：客户需要进一步限制泄漏影响，或跨越信任边界时，用受信的交换入口签发目标与用途更窄的凭据。交换检查服务资格、原凭据、被代表主体与委托边界；不能由每个业务服务随意签发“我是用户甲”。扩大受众、延长原证据的期限、增加字段或动作权限，都不由普通转发产生。交换成功也不证明业务动作已被接受。
- **技术转发不是代办**：普通的技术转发不改变业务责任，不自动变成代办。真实的代办与扮演有专门的授予、期限与上限，保留实际操作者与被代表主体；委托的管理与链上撤销见[安全 05](05-sharing-delegation-and-impersonation.md)与[安全 08](08-state-and-change-protocol.md)。RFC 的 `act` 嵌套表达的是历史身份，不自动证明嵌套中每个人此刻都有资格，也不自动构成本项目的上限求值规则。
- **系统命令**：销售确认后向库存发起预占等系统命令，按跨组件的业务契约取得受限的调用资格；不要求用户凭空拥有每个下游的系统权限键，也不允许只带服务身份就跳过销售的确认资格。上游的校验责任、命令来源、单据修订与接受证据在命令契约中写明，下游检查自己拥有的业务控制。只带历史 actor 的名字不能充当接受证据；接受点与证据的持久语义见[安全 03](03-authorization-acceptance-and-revocation.md)。
- **按 ID 补全不是授权例外**：调用方已有 ID，不证明用户能看补全的字段。系统的 BatchGet 可以为合法的业务内部计算服务，但用户响应必须按已声明的用户读取契约与字段许可裁剪，不能用系统的全量结果绕过普通读取或导出。

## 任职选择、责任主体与本人自审

客户端可以请求选用某个任职；服务端验证它确实关联当前主体、在时间窗内有效、指向合法的法人、组织与岗位，并与本动作的授予绑定相容。不能用用户名、部门路径或单独一个任职 ID 认定资格。没有选择任职的普通读取按求值规则逐份汇总，不能临时指定“权限最大的任职”。

员工与账号允许不是一一对应。启用“按人员责任防本人自审”的流程时，单据记录真实的发起账号与经过验证的责任主体或履职身份；审核检查实际行事方、被代表方与适用的责任绑定。两个账号关联同一个员工时，不能当作两个独立的审批人。关联不能从姓名、邮箱或客户端填写的员工号推出。

普通的、没有代办的单账号流程，至少比较稳定的发起主体；需要覆盖多账号或代办责任的流程，声明相应的关联能力，无法证明责任分离时暂停或拒绝该审核，不能把未知的关联当作“不是同一个人”。本设计不宣称能识别所有未登记的同一自然人；客户确实需要人员级的分离时，须完成受控的绑定与业务范围的准入。这项保护不要求另建通用的自然人组件，具体的责任规则由审批契约承接 D10（[协议 09](../../../protocols/09-approval-and-workflow.md)）。

## 属性取证、修订与故障

- **令牌只携带身份**：签名证明声明由谁签发，不证明它的业务内容永远正确或仍然有效。授权不以登录时 `roles`、`dept_path` 的快照授予当前的业务资格：权限从完整授予视图取得，组织与任职按权威来源与所需的新鲜度提供。令牌不携带角色、部门等授权属性；属性服务不可用时，不能退回用令牌内容放行。
- **资源事实来自属主**：资源的负责人、法人、金额与当前状态从业务属主读取；新建或修改的候选输入经业务规则得到候选事实，不能用输入覆盖权威的旧事实。涉及单位、汇率、组织路径与派生属性时，记录语义版本与必要的来源，不能只给一个没有单位的数值。
- **投影与水位**：普通读取可以使用声明过的有界投影；关键动作要求协议规定的权威证据或兼容的水位证据。账号状态、任职、组织树、授权、资源事实各有自己的版本：不比较不同聚合的裸数字，也不以 `updated_at` 较大或“当前时间已同步”证明全部变化已经应用。属性视图必须有完整快照与增量恢复的机制（[协议 02](../02-projections.md)）。
- **缺失即无法决策**：必要的属性没取得、已过期、来源不可信或水位不相容时，判为无法决策并按规定保护；明确的空集合与“已知没有任职”是不同的状态。装配时缺少所需的能力，阻止启用该功能；运行时无法取证，不返回伪装的空结果，不临时扩大权限。
- **不同的失效事件**：账号停用、员工离职、某个任职失效、服务凭据失效是不同的事件。一个任职结束，撤销它绑定的资格；其他合法的兼任与独立的直接授予按各自的规则处理。是否同时停用账号由声明的身份生命周期政策确定，不由任意消费者猜。安全事件可以要求更广的冻结，但要有明确的权威与审计。传播、窗口与接受竞争见[安全 03](03-authorization-acceptance-and-revocation.md)。

## 事件、后台任务与外部来源

| 路径 | 保护规则 |
| --- | --- |
| 事件发布 | 每个部署隔离消息服务的身份与命名空间；组件只能发布声明拥有的主题、订阅获准的主题，不能共用全权的发布账户 |
| 事件消费 | 校验主题、来源成员、契约、聚合与版本；`ce-source` 或 actor 不能单独证明来源。依赖受信的消息服务与排他的发布权限映射时，记录这一信任前提 |
| 重放、死信、中继 | 有独立受限的工具身份、允许的主题与对象、操作记录；保留原来源与重放来源，不能用宽泛的通配发布权伪造原业务事实 |
| 用户的查询与导出任务 | 持久保存发起主体、合法代办的引用与筛选意图，不保存可重放的用户令牌；执行与交付时按当前有效的用户资格取证，结果文件同样受领取权限控制 |
| 已接受业务的后续任务 | 保留业务接受的引用、限定的资源与修订、原发起信息；消费者用当前受限的服务资格执行，不因发起人离职删除已发生的事实，也不把新范围当成原许可 |
| 固定的系统维护 | 由受限的作业入口按类型构造服务上下文；声明预算、对象域、允许的副作用与停止规则；用户不能提交任意 SQL 或对象范围来启动系统任务 |
| 渠道回调 | 按渠道协议验证签名或凭据、目标部署、商户、时间与重放、原始内容；核对交易或单据的身份与状态；回调里的用户名不是员工授权 |

消息服务的 ACL 不校验任意消息头，也不证明发布者执行过正确的业务规则。采用“主题到唯一获准业务发布者”的映射时，消费者仍核对载荷的来源与该映射一致；维护工具的例外明确登记。跨越不受信的中继需要额外的来源证明或属主回读，不能直接继承这一信任。事件来源证明与重放许可的细节与消息协议一起确定（[事务与消息](../../04-foundations/03-transactions-and-messaging.md)）。

基础资源允许清单的编译，要验证实际的拒绝行为：缺配置或空清单不能被消息服务解释为无限权限。NATS 的空允许清单就有这个风险，所以生成明确禁止对应操作的配置并验收；这属于基础设施的限制，不是增加管理员可配置的业务 Deny。消费者的读取与确认，和 stream、consumer 的管理许可分别限制，不能用全权的 JetStream API 权限绕过数据主题的边界。配置语义依据 [NATS 授权说明](https://docs.nats.io/learn/security/authorization)，具体清单在消息适配器中验证。

## 凭据生命周期、部署与外壳

- **初始化**：部署初始化在受控的管理环境建立信任根与签发权限；根与签发私钥不挂载给全部业务组件。每个组件得到限定身份的凭据、目标信任材料与服务方法许可。开发与测试也各自隔离，不能把生产的根或业务凭据复制过去。多个客户复用宿主、消息服务或存储时，身份与授权空间显式隔离，不能只改一个环境变量。
- **签发与 profile**：基础证书路线允许受控的工具签发、提前续期与文件轮换；工具没有证明目标工作负载身份的机制时，登记为由部署管理员承担的交付信任边界，不冒充平台的自动证实。有效期、提前量、时钟偏差、刷新与缓存上限、已有连接的寿命、信任重叠与故障保护组成一个完整的 profile；缺少必要参数的配置不是生产合格的配置。默认数值在时间协议与代表部署实验中确定，不用某个旧 SDK 的固定间隔作为安全保证。
- **轮换与紧急撤销**：常规轮换先分发下一份信任材料，再切换签发与使用的凭据，最后在声明的接受窗口之后退役旧材料。紧急撤销不能等常规的重叠窗口；撤下公钥、停止续发或更新 CA 文件，不证明已缓存的公钥与已有的 mTLS 连接立即失效，必须按[安全 03](03-authorization-acceptance-and-revocation.md)约束每个请求的准入与连接的处置。
- **故障与日志**：续期失败、信任材料陈旧与时间异常都有告警；新请求无法满足 profile 时停止放行，不自动改成明文或共享口令。恢复时核对当前的冻结与撤销状态，不能从旧备份重新信任已泄漏的私钥。凭据、私钥、完整令牌、恢复码与敏感属性不进入日志、trace 或指标标签；记录稳定主体、证据标识、版本与结果。
- **外壳**：每个外壳成员继续经真实网络、用同样的凭据与方法许可调用。成员的逻辑身份防止误配置与串扰；但同一进程内可以读到其他成员的内存与凭据，不能声称隔离了恶意成员。需要这种隔离时拆成独立进程，并分别限制各自的凭据与基础资源权限；不用外壳的名字统一授出全部成员的权限。

## 独立预期

预期的设计，尚未执行攻击、SDK、证书或消息服务的测试。每条同时安排合法的正例、失败前没有业务副作用、不泄露凭据的检查。

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| TI01 | 没有服务凭据，只伪造合法的 `be-caller` | 系统方法拒绝；同一身份的合法凭据正例可以进入方法准入 |
| TI02 | 同一根下另一个组件的证书，或另一部署、测试环境的证书 | 部署、组件或目标方法不匹配则拒绝，不因证书签名有效而放行 |
| TI03 | 客户端请求打到同一根下的错误目标；中间人替换服务名 | 客户端验证目标失败，不发送用户凭据 |
| TI04 | 用户访问令牌、身份源 ID 令牌、刷新令牌、服务令牌互相替换 | 用途不对即拒绝；算法、issuer、audience、类型与时效的负例分别覆盖 |
| TI05 | 公开入口填写内部的 actor、任职或 verified 字段 | 不构造受信上下文；合法的选择只在权威验证之后使用 |
| TI06 | 已认证的服务在用户路径漏了用户凭据，或原用户没有字段权限 | 不降级为系统模式；服务自身的宽权限不扩大用户的结果 |
| TI07 | 服务凭据的身份与 `be-caller` 不同，actor 名字与用户证据不同 | 拒绝身份冲突；原始未验证的 actor 不参与授权 |
| TI08 | 复用 HTTP 或 gRPC 连接交替请求用户甲与乙，并派生并发任务 | 每个请求保留各自的身份；缺上下文不默认为系统主体 |
| TI09 | 选择他人的任职、已失效的任职、与当前授权段不相容的任职 | 拒绝相应的履职；普通读取仍只汇总自己合法的完整段 |
| TI10 | 登录后调岗；令牌仍含旧角色与部门，属性源不可用 | 不借旧声明恢复资格；按声明的新鲜度保护，不假称即时传播 |
| TI11 | 相同邮箱或登录名，或相同 subject、不同 issuer | 不自动接管已有的平台主体；受控的精确映射正例保留身份 |
| TI12 | 两次首次登录并发抢初始管理员；恢复旧的初始化状态 | 只允许合格精确身份的一次绑定；不能重开授予，也不能按名字抢占 |
| TI13 | 两个账号绑定同一员工审批；代办人与被代表方涉及申请人 | 按声明的责任规则防本人自审；缺必要的关联证据不当作不同的人 |
| TI14 | 伪造负责人、金额、部门属性，或新授权配旧的资源投影 | 不覆盖权威事实；兼容证据不足不放行；合法完整快照的正例成立 |
| TI15 | 事件 actor 写成管理员；非属主发布主题、伪造来源头；空允许清单 | 消息服务拒绝越界发布；空清单不扩为无限；来源映射不匹配时不产生授权或业务副作用 |
| TI16 | 宽权限的重放工具、重复事件、跨不受信的中继 | 只执行声明的重放许可与幂等动作，不把历史 actor 恢复成当前用户的凭据 |
| TI17 | 用户的导出排队后被停用，结果文件仍在 | 执行与领取按当前资格保护，不用消费者的服务身份交付 |
| TI18 | 已到业务接受点的后续任务，原发起人离职、单据又被冻结 | 不自动删除事实；用当前受限的服务资格与业务控制判断，时间细节按安全 03 |
| TI19 | 伪造支付回调、错误的商户、重复的合法回调 | 认证或映射失败时没有副作用；合法的重复不再次记账；不获得员工权限 |
| TI20 | 到期、续期失败、未知密钥、时钟异常与已建立的连接 | 按 profile 停止无法证明的新请求；缓存与长连接的撤销按安全 03，不只测握手 |
| TI21 | 外壳成员共进程；拆分后使用相同的逻辑身份 | 正常模式下语义一致；共进程不能列为“恶意成员隔离”通过 |
| TI22 | 身份或证书提供方切换，旧密钥仍被缓存 | 平台主体保留；旧凭据的退役按完整的迁移与时间协议验证，不宣称切换地址即失效 |

## 依据与独立判断

知识库的认证集成、服务身份、架构主体，以及它的 D8、D10 提供中立参考；本项目保留独立组件与真实网络，把本地证书路线作为低部署成本的基础实现，不强制采用知识库的具体身份产品或默认的浏览器会话数值。浏览器会话、移动端的安全存储与登录防护见[协议 20](../../../protocols/20-frontend.md#登录与会话)：会话由身份适配组件在服务端持有，边缘按会话缓存它签发的短期令牌并注入请求（D61），不新增独立的 BFF 组件。

JWT 的算法、issuer 与受众，以及不同用途的互斥验证，参考 [RFC 8725 §3](https://www.rfc-editor.org/rfc/rfc8725.html#section-3)。令牌交换与实际行事方的表达参考 [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)，本项目的多级资格与上限是额外的应用语义。工作负载与信任域的概念参考 [SPIFFE 官方说明](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/)，共同进程不据此宣称身份隔离。[Kubernetes service account 文档](https://kubernetes.io/docs/concepts/security/service-accounts/)用于核对平台凭据与受众的路线；[NATS 授权文档](https://docs.nats.io/learn/security/authorization)支持按发布与订阅的主题限制权限，消息头与业务证据的校验仍由本项目的协议承担。

## 已知风险与待定

- 线结构、服务方法与属性的注册、证书或令牌的 profile、责任关联的契约、配置与工具，随安全 06、09 与 SDK 确定；以上预期尚未执行，也未跑真实的跨组件路径。
- 数据库结构迁移所用的属主角色凭据在服务容器中可见，是已接受的平台限制（[底层选择](../../04-foundations/README.md#跨方面的约束)）。
- 多客户的受众与凭据隔离、恶意成员需要独立进程，这两条边界保持不变。
