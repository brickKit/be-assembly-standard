# 配置、密钥、注册表与发布

本页回答：

1. 配置有哪几类、谁是权威、怎样校验与生效？
2. 密钥怎样交付与轮换，泄露时怎样处置？
3. 注册表中哪些是不可变的身份、哪些是可变的说明？地址怎样得到？
4. 版本、产物、发布、客户基线与升级怎样做，供应链怎样把关？

依据的决定：D32（有限业务设置）、D55（团队与 AI 维护客户版本）、D58（每客户精确基线）。工程规范中的对应规则见[配置生效与密钥轮换](../01-conventions/01-engineering.md#配置生效与密钥轮换)、[版本与升级](../01-conventions/01-engineering.md#版本与升级)与[客户交付版本的维护](../01-conventions/01-engineering.md#客户交付版本的维护)；本页是它们的完整协议。

## 方案比较

| 路线 | 判断 |
| --- | --- |
| **采用**：三类配置各有一个权威；配置以完整候选快照校验后整体生效，记录目标与实际版本；密钥只以引用出现、分阶段轮换并预先发布备用签名密钥；注册表分不可变身份与可变说明；产物不可原地修改，发布带来源与摘要；每客户精确基线 | 每一项都有确定的权威与可核对的状态；轮换不中断；升级与修复可追溯 |
| 增加集中配置中心 | 动态配置方便，但小客户多一个必需服务；与 BrickKit 三层文件的权威冲突 |
| 签名密钥直接切换到新密钥 | 尚未取得新公钥的验证方会拒绝新令牌（参考模型的坏变体） |
| 注册表行可以编辑 | 已发布的端口、权限键被改名或复用，依赖它的组件与授予静默失效 |

## 配置

| 类别 | 权威 | 变更 |
| --- | --- | --- |
| 部署与装配值 | BrickKit 的三层文件（组合、部署、组件配置）与生成结果 | 改文件后重新生成与部署；组件只经 SDK 的运行时读取自己声明的键，SDK 负责从环境变量与挂载的文件取值；模块代码不直接读进程环境（外壳中各成员共用一份进程环境，会互相覆盖） |
| 有限业务设置（D32） | 所属业务组件中的版本化设置 | 客户授权的管理员经管理界面调整；有校验、审计与生效规则（[有限业务设置](../01-conventions/01-engineering.md#有限业务设置)） |
| 密钥 | 每部署、每属主的密钥存储；配置中只有引用 | 按下文的轮换步骤 |

同一项设置只能有一个权威，不同时出现在部署配置与业务界面中。

**配置声明**（组件为每个键声明）：名称（大写下划线，不以 `_ENDPOINT` 结尾，不用平台保留名）、类型、范围、是否必填、缺省值、生效方式（重新部署、动态更新、随业务版本）、作用范围（组件、成员、法人）、是否敏感。

**生效**：

| 当前状态 | 事件 | 守卫条件 | 结果状态 | 动作 |
| --- | --- | --- | --- | --- |
| （无） | 提交候选配置快照 | — | 校验中 | 解析完整快照 |
| 校验中 | 逐项校验类型、范围、必填与关联约束 | 任何一项失败 | 已拒绝 | 当前配置保持；报告失败项 |
| 校验中 | 同上 | 全部通过 | 待生效 | — |
| 待生效 | 动态更新的键 | — | 已生效 | 在声明的作用范围内原子替换 |
| 待生效 | 需要重新部署的键 | 部署完成 | 已生效 | 随部署生效 |
| 已生效 | 工具比较目标与组件自描述中报告的实际配置摘要 | 不一致 | 不一致（告警） | 不把“文件已改”当作“已生效” |

需要多个成员同时切换的配置，用共同切换控制或维护窗口（[从候选到生效](../00-overview/05-change-and-retirement.md#从候选到生效)）。

**地址**：组件之间与对基础资源的地址一律由 BrickKit 派生（`$endpoint:` 等），不手写服务名或版本化的主机名；升级不需要修改地址配置。授权与身份成员的地址同样用 `$endpoint:` 引用；身份成员切换时，各消费者用于补取与批量读取的身份来源地址是一个单独的部署变量，与登录、公钥地址分开切换（[安全 11](security/11-identity-member-switching.md)）。

## 密钥

- 配置中只出现密钥引用（`${NAME}` 或文件）；密钥以文件交付，组件按声明的间隔重读；不打印、不写入日志、事件、审计正文或任务载荷。
- 每个属主组件使用自己的凭据（数据库角色、对象存储前缀、外部账户），不共享（[协议 12 的对象的属主与凭据](12-attachments-and-object-storage.md#对象的属主与凭据)）。

**签名密钥的生命周期**：

| 当前状态 | 事件 | 守卫条件 | 结果状态 |
| --- | --- | --- | --- |
| （无） | 生成并发布到公钥集合 | — | 备用（只发布，不签名） |
| 备用 | 常规轮换 | 发布已超过验证方的最长缓存时间 | 当前（签名）；同时生成新的备用 |
| 当前 | 被新的当前替代 | — | 退役（只验证，不签名） |
| 退役 | 它签发的最后一个令牌过期，再过最长缓存时间 | — | 移除 |
| 任一 | 泄露 | — | 吊销：立即从公钥集合移除，并作为收紧记入证据（[协议 15](15-backup-and-recovery.md)）；签名改用已分发的备用（或未泄露的退役密钥），同时生成并发布新的备用 |
| 退役 | 泄露吊销时被临时改用 | 未泄露 | 当前；移除计时作废，之后按“被新的当前替代”重新进入退役 |
| 任一 | 整套恢复之后 | — | 按证据重新吊销恢复点之后吊销过的密钥；签名一律切到新生成的密钥，发布新的备用（协议 15 第 6 步）。事件签名密钥与身份族的公钥集合分开：第 5 步之前，由各生产者的签名密钥属主生成新的事件签名密钥并发布它的公钥集合（不等第 6 步）；补发之前按证据得到已吊销的事件签名密钥清单，用它签过的旧事件由生产者用新密钥重新签名后补发，消费者因此不会验签失败 |

**常规轮换**：

| 密钥类型 | 步骤 |
| --- | --- |
| 签名密钥（令牌、事件签名） | 按上表；事件签名的旧公钥另外保留到补发保留期（协议 15）结束，使整套恢复时补发的旧事件仍能验签：始终预先发布一把备用密钥；备用发布超过验证方的最长缓存时间后，切换签名到它，并发布新的备用；旧公钥保留到旧令牌全部过期再加缓存时间后移除。身份成员切换时，新成员的签名公钥按同一方式预先加入（安全 11） |
| 回调与 Webhook 的签名密钥 | 新旧两把同时有效一段时间（[协议 10 的凭据与出站网络](10-external-integration.md#凭据与出站网络)） |
| 数据库密码 | 两个运行角色交替：新角色先建好并分发，组件切换到新角色的新连接，旧连接自然结束后停用旧角色；或在维护窗口中更换 |
| 外部账户与对象存储凭据 | 按对方支持的方式先加后删；不支持并存时安排维护窗口 |
| 服务凭据（mTLS 证书） | 按[安全 02](security/02-trusted-identity-and-attributes.md) 的基础路线：提前续期、文件轮换、信任重叠，不用永久证书 |

**泄露处置**：立即吊销泄露的密钥，不等待常规宽限；签名密钥改用已分发的备用密钥（或仍在退役期内、未泄露的旧密钥），使新令牌立即可被验证。短时间内连续泄露、没有已分发的密钥可用时，新令牌在最长缓存时间内可能被部分验证方拒绝——这是声明的可用性影响，安全优先。

**未知密钥标识**：验证方遇到不认识的密钥标识时，先做一次限频的即时刷新再判断，作为预先发布之外的第二道保护（知识库的令牌验证篇采用同样做法）；限频防止伪造的标识引发刷新风暴。

**刷新失败**：验证方的密钥集合超过最长缓存时间仍刷新失败时，回答“暂时无法验证”，不无限沿用最后一次成功取得的集合（参考模型的“刷新失败时无限沿用旧集合”坏变体：轮换后签发的新令牌一直被拒绝；同样的沿用也会让已移除的密钥一直被接受，模型没有建出这一面）。

密钥的备份与恢复和数据备份分开记录（[协议 15](15-backup-and-recovery.md)）；整套恢复后会话、刷新令牌与服务凭据全部失效并重新签发（协议 15 第 6 步）。

## 注册表

注册表记录项目范围内必须全局唯一的名称：组件 ID、端口、schema 与数据库角色、资源类型（带属主组件）、权限键（带属主组件）、事件类型（含共享任务契约的任务类型）、数据集 ID、附件类别、错误原因、能力名。

| 部分 | 规则 |
| --- | --- |
| 身份列（名称、端口号、权限键本身） | 只追加；发布后不修改、不删除、不复用 |
| 说明列（描述、属主、状态） | 可以修改，修改有历史；“已退役”是状态，不删除行 |
| 退役 | 标记退役与日期；名称永不再分配给其他含义 |
| 检查 | 发布检查确认组件使用的名称都已登记、未退役、属于该组件；端口不落入平台保留区间 |

只追加约束的是身份，不是说明：所以“只追加”与“标记退役”不冲突。权限键退役后，对应的段立即为空（[安全 08 的有效段的计算](security/08-state-and-change-protocol.md#有效段的计算)）。

## 版本与产物

- 每次改动发布新版本；版本精确，不使用范围。组件与外壳各自按语义版本；Go 组件同时打供 Go 使用的 `v` 标签，模块路径带主版本。
- **产物不可原地修改**：标签、镜像、锁文件所指的内容发布后不变；修复发布新版本。
- **Fork**：保留组件 ID，按正常规则升版；记录来源、差异与精确版本。
- **契约兼容**：同一主版本内只追加；追加不自动等于语义兼容——含义变化（例如字段的计算口径改变）按破坏性变化处理，发新主版本或新字段。
- **发布候选清单**：源码提交、契约与生成工具版本、依赖锁、产物摘要、软件物料清单、许可、已知漏洞的处置、一致性套件报告（[协议 18](18-sdk-and-conformance.md)）。

## 供应链

- 依赖精确锁定；新增依赖经评审（许可、维护状态、替代方案）。
- 构建可重复：从清单记录的源码与锁文件得到相同摘要的产物；镜像以摘要引用。
- 产物签名与来源证明随发布生成；部署前核对摘要与签名。
- 漏洞：发布时扫描；受支持的客户基线定期扫描；按严重程度与可利用性分级处置，安全修复回补到稳定线（D55）。
- 基础镜像带 shell 与 `wget`（健康检查需要），并随安全更新重建。

## 客户基线与升级

- **客户基线**（D58）：组件、SDK、外壳、基础资源与适配的精确版本与产物摘要，配置与环境，已验证的范围；外壳的成员清单与依赖锁由工具从基线生成。
- **升级候选**：目标基线、变化（功能、权限、数据、契约）、升级路径（[协议 14 的结构迁移](14-data-foundations.md#结构迁移与版本兼容)）、验证证据、维护窗口与恢复办法；由团队与 AI 准备，客户决定接受、暂缓或拒绝。
- **实施**：按[协议 17 的维护窗口](17-runtime-and-resources.md#维护窗口中的升级)步骤；实施后核对实际版本与业务结果，记录到基线。
- **维护线**：稳定修复与功能升级分开（D55）；支持期与并存数量在正式交付前确定。

## 参数起始值

| 参数 | 起始值 |
| --- | --- |
| 密钥文件重读间隔 | 60 秒 |
| 验证方的最长缓存时间 | 5 分钟 |
| 令牌最长有效期 | 15 分钟（访问令牌） |
| 签名密钥常规轮换 | 90 天 |
| 回调签名密钥的新旧并存期 | 7 天 |
| 受支持基线的漏洞扫描 | 每周 |

## 参考模型

[密钥轮换模型](../../work/checks/31-key-rotation.py)（种子 20261013，3,000 次运行）：签发方用当前密钥签发令牌，三个验证方随机刷新公钥集合（部分刷新失败）；随机进行常规轮换与紧急吊销。

| 检查 | 结果 |
| --- | --- |
| 未过期、未吊销的密钥签发的令牌，被缓存未超时的验证方接受（连续泄露的声明窗口除外） | 成立 |
| 紧急吊销后，超过最长缓存时间不再有验证方接受该密钥 | 成立 |

3 个坏变体全部被发现：切换到尚未分发的新密钥、旧公钥在旧令牌过期前移除、刷新失败时无限沿用旧集合。紧急吊销时启用一把新生成的密钥，会被尚未刷新的验证方拒绝新令牌（模型最初就是这样发现的）；所以始终预先发布备用密钥，只剩“短时间内连续泄露”的情形，作为声明的可用性影响。模型不是身份组件或 SDK 的运行结果。

## 独立预期

| 编号 | 场景 | 固定预期 |
| --- | --- | --- |
| CF01 | 候选配置中一项超出范围 | 整个候选不生效，当前配置保持 |
| CF02 | 改了配置文件但组件未重新部署 | 工具报告目标与实际不一致 |
| CF03 | 同一项设置同时出现在部署配置与业务界面 | 不允许 |
| CF04 | 手写版本化的服务地址 | 不允许；由 BrickKit 派生 |
| CF05 | 日志中出现密钥 | 不允许 |
| CF06 | 签名密钥常规轮换 | 先发布备用，超过缓存时间后切换；旧公钥在旧令牌过期加缓存时间后移除 |
| CF07 | 签名密钥泄露 | 立即吊销，改用已分发的备用密钥 |
| CF08 | 验证方连续刷新失败超过缓存时间 | 回答暂时无法验证 |
| CF09 | 数据库密码轮换 | 两个运行角色交替，或维护窗口 |
| CF10 | 已发布的权限键需要改名 | 不改名；新键登记，旧键退役 |
| CF11 | 退役的端口号分配给新组件 | 不允许 |
| CF12 | 修改已发布镜像的内容 | 不允许；发布新版本 |
| CF13 | 字段的计算口径改变但名称不变 | 按破坏性变化处理 |
| CF14 | 部署前产物摘要与清单不符 | 拒绝部署 |
| CF15 | 受支持基线中发现严重漏洞 | 回补到稳定线，客户决定实施时间 |
| CF16 | Fork 组件改动 | 保留组件 ID，正常升版并记录差异 |
| CF17 | 客户暂缓升级 | 保留当前基线、已知限制与可选处理 |
| CF18 | 外壳成员版本与基线不符 | 外壳由工具从基线生成，不手工编辑 |
| CF19 | 验证方遇到不认识的密钥标识 | 限频的即时刷新后再判断；伪造的标识不引发刷新风暴 |
| CF20 | 身份成员切换，各消费者的身份来源地址 | 单独的部署变量，与登录、公钥地址分开切换 |

## 已知风险与待定

- 支持期、基线并存数量、修复时效，在正式交付前确定（D55）。
- 签名、来源证明与软件物料清单的工具，按交付环境选定。
- 有限业务设置的存储模型与管理界面，随各组件设计与前端协议确定。
- 外壳总预算与配置声明格式中需要 BrickKit 支持的部分，验证后作为功能请求反馈。
- 运行中需要动态更新的配置（允许的实现实例集合、恢复阶段的下发）与“组件只在启动时读取配置”的做法相矛盾；先确认 BrickKit 支持哪种下发方式，经验证后作为功能请求反馈。成员切换与恢复模式的下发依赖这一项。
- 以上预期尚未在轮换演练、发布流程或供应链工具上运行。
