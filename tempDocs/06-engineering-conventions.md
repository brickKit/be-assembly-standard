# 工程与项目规范的整理

> 状态：新规范的审查范围；具体规则尚未逐项冻结。现有运行与发版仍执行现行约定。

具体组件／仓库与替换对象由[货架](components/catalog.md)、[选择关系](components/selection-map.md)和各[选型专篇](replacements/README.md)定位；SDK 与外壳仓库见[运行组件表](replacements/runtime-and-deployment.md#选择对象与组件仓库)，授权模型与实现成员见[权限选型](replacements/authorization.md)。本页规范不另维护一份候选产品或成员清单。

| 层 | 拥有什么 | 应产出的文档与检查 |

## 必须重审的规范

契约优先与业务规格；语言／栈准入；生成代码的新鲜度；配置权威源与密钥轮换；注册表身份；数据库属主／运行角色；接口权限注册；事件与错误命名；Fork 版本与来源；依赖升级；外壳成员；发布检查；数据与测试隔离；文档路由与语言；AI 一次任务的读取和变更范围。

规范解释目的、适用条件、错误症状和验证方法。机械检查另验自己真的能捕捉违规。规矩之间发生冲突时记录影响与裁定，不靠追加例外让读者猜。

全局推荐与冻结条件见[底层基线](09-foundation-baseline.md)。规则改变分别评估语法兼容、业务含义、权限、数据和在途副作用；新增字段／枚举也可能影响旧消费者。破坏性迁移需要部署版本准入及明确旧任务／客户端处理，不能只凭数据库当前没有旧会话证明旧版本不会再启动。

金额／数量外部十进制字符串、单位与汇率／舍入依据、UTC 时刻与业务日期／法人日历、稳定 ID 与正式单号继续作为共享语义。精度、舍入／分摊顺序、日期依据、未知字段／枚举和规范化编码由协议向量确定；不把不同数据库 text 输出或浮点 JSON 当作跨语言标准。具体实体与向量尚须绑定，不声称旧规则已全文迁完。

组件需声明必需审计动作与风险分类，覆盖敏感读取／导出及必要变更、代操作、安全拒绝等；普通低风险查询与长期业务审计分别处理。具体声明格式和缺漏门禁待设计，要求见[审计动作与读取范围](02-security-and-permissions.md#审计动作与读取范围)。

## 可配置与可定制

| 变化 | 设计候选 |
| --- | --- |
| 资源与运行预算 | 带范围与关联约束的配置 |
| 客户业务参数 | 已定由所属业务组件维护有限设置，客户授权人员通过界面调整；具体项目和生效协议待设计 |
| 多种模型都合理 | 统一契约的替换能力，或受控适配 |
| 某客户独有规则 | 独立版本的 Fork 或明确扩展点 |
| 模型与外部语义改变 | 新契约版本、调用方迁移与数据转换 |

Fork 不复用已发布版本的产物身份。保留组件 ID 的 Fork 与新身份的实现替换是不同路径；后者允许有控制地改装配和调用方。具体取舍见[业务定制与通道](replacements/business-and-channels.md)。

## 有限业务设置

部署／运行参数继续纳入 BrickKit 配置与运行时读取约定。有限业务设置归所属业务组件，由客户授权人员通过管理界面调整，组件负责范围与关联校验、版本／生效规则及审计。不能将同一项设置同时交给部署配置与业务界面争夺权威；具体存储模型、接口和界面组合尚待设计，不据此新增通用配置组件。

组件明确允许调整的项目、管理权限和合法范围。算法和模型变更另按扩展、替换或 Fork 处理；界面不提供任意编程，也不能关闭必需的权限、职责分离或库存／会计完整性控制。具体界面按组件路线实施，不提前开发自定义字段管理或通用规则引擎。

设置的生效时点、适用范围与历史解释逐业务定义。审批在途版本规则继续适用，不推导全部业务政策统一冻结或立即生效。验收覆盖越权修改、无效组合、并发更新、生效边界、旧业务依据、升级迁移及单跑／外壳一致性。

## 配置生效与密钥轮换

> 推荐执行规则，具体配置／秘密的协议键、刷新能力与命令仍须绑定目标版 SDK 和部署方案；不新增配置中心或默认要求小客户运行密钥服务器。

| 类别 | 权威与变更方式 | 必须检查 |
| --- | --- | --- |
| 装配／部署值 | BrickKit 三层文件与生成结果，组件通过 runtime 读取 | 键、类型、范围、必需条件及成员隔离，秘密只引用；修改目标值不等于运行已生效 |
| 有限业务设置 | 所属组件的版本化设置，客户有权人员调整 | 合法组合、范围、并发、生效点与旧业务解释；不能重复在部署配置维护同一项 |
| 身份／连接等秘密 | 每部署、每属主的明确来源，经受控文件／秘密载体交付，SDK 使用 | 实际版本、读取资格、可用期、刷新与连接重建、失效保护；不打印内容或复制进任务载荷 |

每个可变配置声明需重新部署、允许动态更新还是随业务版本生效，记录目标版本和实际应用版本。先解析并核对完整候选快照，再原子应用到声明的组件／作用范围；无法保证同时更新的多个成员使用共同切换控制或明确维护窗口。错误候选不覆盖当前合格配置，也不因部分成员成功就宣布全部完成。

减少组件、缩小能力档位、改法人路由、换身份／授权／MQ 地址和压缩保留期都重新校验能力、在途状态与安全条件；运行预算收紧要处置超额作业，不能强行删除已持久化业务。安装和配置的共同步骤见[选配变更协议](replacements/README.md#选配变更与替换的共同协议)。

常规秘密轮换区分准备新值、各使用方可读取／验新版本、切换新使用、退役旧值。数据库密码与服务凭据分别考虑现存连接和新连接；支持重叠时明确截止，不支持重叠时安排受控维护或可验证的身份转换。签名密钥先发布新公钥并验证各消费者，再切换签名，旧验签材料保留到合法旧凭证与容许时钟范围结束；泄漏撤销使用安全处置规则，不等待常规宽限。JWK 的密钥集合／标识依据见 [RFC 7517](https://www.rfc-editor.org/rfc/rfc7517.html)，具体轮换预算由项目定义。

SDK 的文件重读不证明远端已接受新凭据；仅文件 mtime／size 相同也不能证明内容未换。刷新失败有错误、告警与有上限的旧值使用策略，过期／已撤销值和严格动作不得无限沿用“最后成功值”。缓存、长连接、后台重试、跨实例和外壳分别验实际生效，不能写成“改文件一定无重启成功”。秘密恢复责任与备份密钥共同记录，属主密钥的既有接受限制保持。

## 版本与升级

已有历史的业务组件停用或退出运行，要先交接未完业务与依赖，保留明确的历史访问、授权、数据／对象及恢复责任。标准停用后保留原组件受限查阅和必要维护，完全卸载走专项历史迁移，见[业务组件停用与退出](replacements/component-lifecycle.md)。停用菜单与 BrickKit 移除操作不能代替业务退出验收。

普通业务角色的升级新增权限经客户授权管理人员确认后加入，标准角色提供版本化参考模板，客户实际角色保持自己的明确授权；支持审核批量变更计划。系统管理角色单独处理，安全修复与权限退役另有明确协议，不能因保留旧角色绕过必需控制。具体要求见[普通业务角色与升级确认](02-security-and-permissions.md#普通业务角色与升级确认)。

审批流程与相关配置变更默认影响新实例，在途实例保留绑定版本；组件或引擎升级需要保留所需的旧执行语义，或提供明确迁移。升级验收包含停在不同节点的实例和权限撤销，不能只测试新建流程。具体边界见[流程版本与在途实例](02-security-and-permissions.md#流程版本与在途实例)。

标准正式升级允许预告维护窗口，但必须保留客户数据，并验证受影响业务暂停、迁移与在途接续、失败恢复和恢复服务条件；实验库重建规则不适用。连续服务方案另作专项验收，详见[正式客户升级与维护窗口](03-deployment-and-resources.md#正式客户升级与维护窗口)。

当前公网访问无硬性限制，正常联网安装／升级优先验证，不改变精确版本与依赖声明；网络或材料缺失有明确失败与恢复行为。完全离线交付按具体需求专项设计与真实断网验收，不能沿用联网通过结论，详见[私有化交付网络前提](03-deployment-and-resources.md#私有化交付网络前提)。

前端同一入口默认构建时组合选中的页面模块，生成确定版本并共同验证发布；局部页面源码更新需重建所在入口，不要求 PC／移动／仓库入口一起发版。模块边界、注册与装配生成另定，客户有限业务设置和已选页面的权限菜单仍按运行时语义处理，详见[同一入口的构建与发布](replacements/frontend.md#同一入口的构建与发布)。

## 客户交付版本的维护范围

> 状态：稳定维护线与责任分工已获用户明确同意；需求与维护由项目团队统一承担，AI 执行，客户决定是否升级。支持年限、并存数量和补丁时效仍待明确。

采用有限的稳定交付版本线，必要安全／重大正确性修复优先回补，新功能继续在后续版本推进。标准版和项目承接的客户定制／Fork 均由项目团队维护，不以客户自己编写代码、合并补丁或维护旧版为交付前提。客户选择升级或暂缓，项目团队准备适配、验证、迁移与恢复材料并配合实施；必要修复的部署变化也纳入客户决定。

组件可以独立发版，客户交付基线记录实际选择的组件、SDK、外壳、基础资源与适配的精确版本和验证范围；不要求所有组件使用同一版本号。当前实验版本也不能自动称为正式稳定交付基线。

| 路线 | 优势 | 代价与适用条件 |
| --- | --- | --- |
| 已选：稳定维护线与后续功能版本分开 | 客户可在支持窗口内先取得必要修复，再安排功能升级；项目团队承接定制适配 | 增加修复回补、依赖及组合升级验收；需明确版本与客户组合清单，AI 执行仍有维护成本 |
| 未选：只维护最新功能线 | 项目团队维护范围较小，迭代较集中 | 客户取得修复通常需同时跟进功能升级，团队也要较频繁迁移客户定制；不将旧版责任推给客户 |

“稳定”不表示无须打补丁或冻结安全控制。修复优先尽量减少功能变化；不能可靠回补时，说明必要升级及影响，并提供可行的临时保护方案，由客户决定实施安排，不承诺所有修复都可完全不升级。任何修复都发布新版本和产物，不改写既有标签、镜像或锁所指的内容。

稳定线的支持以已记录的组件／依赖及客户组合为对象，包含仍保留查阅的停用组件及必要运行环境。第三方 SDK、身份、数据库或存储的支持边界变化，可能要求基线升级；团队说明继续维护的条件、替代／升级方案与限制，客户选择是否实施。暂缓升级不等于所有旧依赖永远可安全维护，不默认强制更新、停止客户实例或外传遥测。

客户 Fork 允许继续偏离，并由项目团队记录来源、差异、精确版本和受影响修复，使用 AI 完成必要适配与验收。客户未记录的外部修改先核清，再纳入维护清单；标准补丁不能未经验证直接覆盖定制，也不自动证明所有组合兼容。不能照搬知识库场景中禁止 Fork 的统一核心做法。

### 客户版本清单与升级交付

| 记录 | 最少要表达 |
| --- | --- |
| 客户当前组合 | 组件／SDK／外壳与基础资源精确版本、来源与产物、配置及环境、当前已验证范围 |
| 定制差异 | 偏离标准的能力与契约、代码／数据差异、历史与在途状态、标准修复受影响范围 |
| 支持与修复 | 受支持基线／组合、必要修复及适用条件、未修复限制、维护责任和支持退出／升级路径 |
| 升级候选 | 目标精确组合、功能与权限变化、数据／依赖／定制适配、验证证据、维护窗口及恢复办法 |
| 客户决定与实施 | 接受、暂缓或拒绝本次升级及其适用范围，实际执行版本、结果与后续处理；不能把仅准备好的候选记成已部署 |

团队先分析受影响版本与客户差异，由 AI 形成修复／升级候选，跑对应组合的契约、业务与恢复验收，再交付客户可审查的变更及实施材料。客户选择后，团队通过 BrickKit 配合执行并核对实际版本与业务结果；暂缓的客户保留当前组合记录、已知限制与可选处理方案。具体清单格式、交付渠道和命令另定，本轮不创建客户数据仓库或发送通知。

AI 用于开发和维护，不等于 ERP 产品中的 AI 业务能力提前启用，也不替代测试和实际环境的证据。客户数据的开发使用仍遵守其访问与处理边界，不能因使用 AI 或允许公网访问就默认传送客户资料。

验收应覆盖受支持基线上的修复效果、安全拒绝与业务回归、必要依赖及外壳版本传播、旧数据／在途状态、页面和客户扩展兼容、迁移／失败恢复，以及受影响版本和修复适用范围清单。修复只在最新主干通过，不证明已经适用于旧稳定线；具体矩阵、发布步骤与维护成本仍待设计验证。

后续正式交付前需确定支持期、基线数量、选定与退出条件、修复分类／处置时效、客户通知方式和升级路径。当前已定维护模式、责任与升级自主权，不复制季度 LTS、固定月数或供应商周期，也不现在建立多个发布分支。

发行候选清单还记录源码／契约／生成工具来源、依赖锁、可校验产物摘要及实际许可／支持条件，核对已知安全和正确性问题及处置范围。精确版本号不替代产物与来源核验；未纳入支持或未解决必需安全缺口的候选不得仅因构建成功作为合格交付。具体扫描／签名／验证工具按交付环境设计，不为此默认增加常驻服务。

功能参考：[PostgreSQL 版本政策](https://www.postgresql.org/support/versioning/)将新功能大版本与受支持版本的修复发布分开管理；[SemVer](https://semver.org/)解释版本号如何表达兼容性及已发布内容不可原地修改。它们不替本项目决定支持周期，PostgreSQL 的具体版本编号方式也不直接等同于本项目的组件版本。

## 面向 AI 的说明

项目文档同时承担客户自我介绍与开发规范。客户从项目全景进入能力分图、组件／仓库与替换关系、方案比较和组合部署；开发者从边界、协议、SDK、规范和验收进入。客户路线以[能力分图与替换关系](components/selection-map.md)和[统一介绍要求](replacements/README.md#每篇最终应达到的标准)组织，不要求先阅读源码或全部开发规则。

每个组件有自己的术语、数据归属、契约、禁用行为和实际测试入口。共享协议和规范只维护一份权威定义，组件文档链接到它。项目级全景与选型摘要负责解释能力、取舍与仓库关系，具体版本事实回到契约、运行锁、来源和组件文档核对；避免另抄一套配置键、接口或版本历史。

图过大时按能力分图；功能归属、协作、替换、运行期调用与启动依赖分别标注。节点／连线直接写单选实现、多选并存、按范围单选且跨范围并存、多选协作能力或模型组合，并写作用范围；统一含义见[选择方式图例](components/selection-map.md#图上的选择方式)。选型说明据此区分渠道、法人、入口、策略和 Fork；独立仓库不自动成为可互换实现。计划仓库和已接入源码、已实现和已验证分别标状态，正式切换前核对目录覆盖、链接、状态和证据。

旧文档规范中“刻意不做一份覆盖全部组件的摘要”与最新用户的全景／仓库／选型展示要求不同。新中文设计按用户要求承接项目级介绍，并用唯一事实来源与组合检查控制过时风险；正式文档迁移时同步更新旧规则，不把本轮文档调整视为所有组件的新边界已冻结。

设计可以推翻任何现有结构，但执行前必须明确迁移与验收。平台问题按最小复现和新旧行为整理；知识库差异先区分项目的独特选择和通用知识错误。反馈建议记在工作台账，跨仓库修改另按对应流程处理。
