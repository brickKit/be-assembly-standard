## 持续前提与审查范围

最新用户前提：**默认以小公司规模开发，长期按不同客户的业务、负载、资源与观测需求提供配置、专项组件和部署路线。没有统一规模计划，不再重复询问统一并发量、单据量或年限，不把缺少统一数字当作设计阻塞。**完整原话保存于[任务简报](../00-brief.md#本次终局审查的规模前提重申)。

这要求底层先有能力、边界和演进规则，再按客户实例化参数。不能据此承诺任意性能瓶颈都只改配置可解决：某些升级需要数据分离、迁移、适配器或业务范围分片，文档应明确其代价与未支持条件。

本次全量清点与本地链接目标检索涉及 474 份 Markdown：正式英文文档 85 份及中文镜像 85 份，审查工作区 42 份，身份／授权契约 16 份，组件文档 137 份，外壳文档 28 份，工具／协议文档 81 份。数字排除了 node_modules、vendor、build、dist 等依赖或产物目录，且是本轮新增文件之前的快照。

语义审查以 `tempDocs` 的 28 份主体／目录／选型／验收文档为主；正式文档的 43 项决策、27 个底层专题及约定按主题交叉检查，进一步核对协议 P1／P5／P6／P12–P18／P20 和身份、授权族契约的相关要求。其他协议章节参与目录与规则检索。原始蓝图作为目标与能力来源，组件文档作为边界输入，未把其实现选择当作终局约束。

工作记录用于核对已答前提与既有发现；没有重新逐字翻译每份镜像、穷读历史过程或审查所有业务代码。全量静态检索不等于全部文档逐条完成独立证明，也不等于法律、密码学或所有客户组合已验收。旧审查结论本轮按文本重新判断，未直接继承“已合理”的标签。

## 可以保留的总体设计

| 原则 | 独立判断与成立条件 |
| --- | --- |
| 按能力装配、组件独立维护 | 符合客户定制和 AI 局部迭代目标；组件必须有独立变化价值，不能按菜单或算法名称机械拆分 |
| 战略 DDD，内部结构按复杂度选择 | 合理；“一个组件就是一个 Domain”不是强制等式，核心约束是术语、事实权威和一致性边界 |
| 唯一事实权威 | 数量、成本、账务、资金、出账各自有明确属主；引用和投影不获得第二份写权威 |
| 独立组件与部署进程分开 | 单跑／外壳／混合可以承担不同成本；外壳共享故障和信任域，不产生共同事务 |
| 短本地事务与持久协调 | 合理；未知结果必须查询、幂等恢复，不能把 Saga 或 broker 当作全局 ACID |
| 完整授予与全出口授权 | 方向正确；不能将不同授予的动作、范围、条件和字段分别取最宽再拼接 |
| PostgreSQL 在线，按需要分离历史／分析 | 有条件的合理起点；热、交互历史、封存和分析是不同负载，不要求小客户预装全部层 |
| 精确客户组合与团队维护 Fork | 符合已定责任；组件独立发版不自动证明任意版本组合兼容，稳定线的支持范围须有界 |

允许独立成本、信用、资金等边界，不等于其协调已经成立。真实不可补偿的不变量若无法在所选边界满足，仍应重新划分边界。已有名称、注册预留、参考产品的菜单和仓库数量都不能替代这个判断。

## 本轮发现的具体设计问题

P0 表示相关协议的冻结阻塞，P1 表示相关能力启用或正式交付前必须补齐。优先级不表示当前产品已发生事故。

### R01：认领一次不保证定时作业完成或可恢复（P0，I27）

依据：[Jobs 基础设计](../../../docs/en/04-foundations/19-background-jobs.md#port-contract)、[协议 P14](../../../tools/be-protocol/spec/14-background-jobs.md#the-five-kinds)。两处均用 `(name, slot_at)` 的唯一插入认领 cron 时间槽，插入者执行后设置 `done_at`，同时声称时间槽执行恰好一次；P14.2 又要求失败重启。

反例：认领事务提交 → 进程在执行业务前崩溃 → 新进程插入同槽遇到冲突 → 没有执行资格。现有声明没有未完成槽的接管状态、租约或重试路径；`done_at` 为空也不会自动改变唯一键。认领唯一性只能保证一次初始认领，不能证明工作完成。

另一个窗口是业务效果已提交、`done_at` 尚未写入就崩溃；若直接重试，效果又可能重复。因此不能仅补“失败再运行”四个字。[PostgreSQL 的 INSERT 文档](https://www.postgresql.org/docs/18/sql-insert.html#SQL-ON-CONFLICT)说明冲突分支只处理数据库插入／更新，不负责随后工作恢复。

修订建议：时间槽保留持久 `pending/running/done/dead` 状态、尝试次数、租约与代次；以原槽身份接管未完成工作。可恢复作业按至少一次尝试设计，以业务操作身份保证副作用唯一；不可重做的作业明确暂停核对。补认领后、效果提交后、完成登记前三个故障点及正常正例。截止、补跑、DST 重复／缺失时刻和未完成槽清理资格也须明确。

### R02：List／Can 的通用一致性定义使用了不同谓词（P0，I28）

依据：[族契约 E10](../../../contracts/infra/authz/EVALUATION.md#e10-decision-for-one-record)、[协议 P6.6–P6.7](../../../tools/be-protocol/spec/06-authorization.md#requirements)。E10 定义 `Can.visible = vis(view_key,r)`、`Can.allowed = visible AND vis(K,r)`，列表却使用 `vis(K,r)`；P6.7 要求列表等于 `Can(K,r).visible`。

当 `K != view_key`，且调用者的 K 范围覆盖某记录、view_key 范围不覆盖时：列表谓词为真，Can.visible 和 Can.allowed 均为假。这是公式的适用域不一致，独立于多维授予错误。普通列表始终使用 view_key 时不会触发这一反例；当前文档未把通用一致性承诺限定在这种情形。

修订建议：分别定义读取集合、动作可执行集合与字段输出。读取列表与读取 Can 用同一个可见性谓词；按动作筛选的集合应同时满足可见和该动作资格，字段与业务状态另检查。也可明确禁止非 view_key 的列表，但需声明其限制。先确定契约，再补不同读取键／动作键范围的独立向量；不能简单把测试中的 K 全改成 view_key 就宣布原通用承诺成立。

这不是已经执行的 SDK 泄漏测试。原 [PA07](../../validation/authorization-matrix.md)主要检查同一读取动作，需要补此公式的适用域与动作集合反例。

### R03：broker 确认与长期审计落地之间缺少删除资格（P0，I29）

依据：[审计路径与已知限制](../../../docs/en/04-foundations/23-observability.md)、[P12.1／P12.11／P12.15](../../../tools/be-protocol/spec/12-events.md#requirements)、[审计目标](../../02-security-and-permissions.md#审计动作与读取范围)。现行文字称审计通过 Outbox 到 `infra/audit`，审计尚未接入时记录留在 Outbox；但 Outbox 在 broker 确认后默认只保留 14 天，stream 默认 7 天，清理未绑定审计存储回执。

反例：审计记录和业务提交 → broker 确认 → 审计消费者未安装或长期未保存 → stream 和已发布 Outbox 到期 → 没有长期审计副本。业务行的最终状态不能重建每次操作、拒绝或敏感读取。不能把记录初次原子写入视为长期保存已经成立。

修订建议：生产组合明确必需审计的最低持久落点，可以是本地独立审计记录，也可以是有应用层保存回执的可靠转运。只有指定审计属主确认持久保存或另一合格副本已核验后，传输副本才具备删除资格；故障期间有积压保护和暂停规则。保留政策按动作类别／适用地区确定，不继承全系统统一法定年限。必要审计能力不能因监控方案精简而省略。

### R04：局部状态更新可以阻止同版本完整修复（P0，I30）

依据：[P15.1–P15.3](../../../tools/be-protocol/spec/15-snapshots.md#requirements)、[P12.6](../../../tools/be-protocol/spec/12-events.md#requirements)。P15 允许局部事件更新已有行，同时要求所有事件／read-through／回填只接受严格更大的整体版本。

反例：本地 v10 的额度为 100；v11 将额度降为 50；v12 只改名称且先到。局部更新把本地标成 v12，额度仍是 v10 的 100。v11 被旧版本保护跳过；之后取回完整 v12，因 `local.version < incoming.version` 不成立，也无法修复。这里的金额是模型标签，不代表实际授信政策。

修订建议：整体版本只表示完整快照。采用完整状态事件，或在不连续局部更新出现时先标不完整／待修复，并允许同版本完整快照受控补齐；也可声明逐字段版本或严格连续增量协议。安全或资格判断不得使用无法证明完整的副本。取回完整状态的网络操作仍在数据库事务外。该问题是既有 I22 的具体状态投影分支，新增 I30 用于追踪其明确修复条件。

四个反例均用[纯状态模型](../checks/06-document-counterexamples.py)演算；没有连接数据库、broker 或调用 SDK。模型只能证明给定文字规则下的反例，不证明具体产品的实现行为。

## 覆盖不足的方面及应补规范

### R05：跨组件引用没有完整生命周期（P1，I31）

UUID／opaque ID／无跨库外键有规定；[标识专题](../../../docs/en/04-foundations/04-identifiers-and-numbering.md#known-limits)却只说悬空引用由属主返回不存在发现。伙伴合并和历史退出已有原则，尚不能覆盖产品、组织、员工、仓库等所有引用。

需按引用类型定义：引用谁的资源类型与作用范围；新业务引用资格；停用／删除／合并后的稳定定位；历史身份与发生时快照；别名／墓碑保留；跨法人一致性；缺失、暂不可达、不可见、已销毁的内部处理；对账与修复责任。不能因属主暂不可达清理引用，也不能向普通用户暴露其无权知道的内部状态。

“引用前查存在”与本地提交之间仍有并发间隙。仅要求历史可解释的弱引用可以保留稳定身份／快照；若要求提交时对象必须有效，就需属主资格证据／受控停用协议，或调整一致性边界。全部引用不必使用重型统一协调服务。

### R06：首次上线、期初事实和业务导入未纳入完整覆盖（P1，I32）

现行[数据约定](../../../docs/en/01-conventions/05-data.md)定义演示种子和测试数据；它们不是客户主数据迁入、期初库存／成本、应收应付、总账余额和未完单据。既有 G4 暂缓平台级导入的实施排期继续保留，不能据此从终局规范中省略设计。

应定义导入模板／版本、来源 ID 映射、预检与确认、业务入口与逐对象权限、批次／行幂等、整批或逐项提交语义、部分失败与续跑、错误资料及敏感文件保存、来源／对账证明。期初事实要有受控业务入口和来源，不能只写余额而没有可解释的流水；也不必把所有历史伪造为真实发生的新交易。

上线切点必须区分期初、已迁历史和切换后的新事实，防止重复形成库存、应收、成本或凭证。补客户核对、试迁移与首次真实业务的验收。覆盖新增 C43；本轮不开发平台导入器。

### R07：自定义字段与可替换策略缺少演进边界（P1，I33）

现有 C20 明确待逐实体审查；有限业务设置已定，但不能代替字段扩展协议。需限定可扩展对象、稳定字段 ID、类型／基数／精度、必填与缺省、合法验证、字段权限、搜索／排序／索引、配额和复杂度上限、弃用与类型迁移、导入／导出、事件／报表、冷热与客户 Fork 承接。

扩展字段不能改变核心不变量或隐式加入必需授权属性。策略替换要有输入依据／版本、错误、超时和历史结果解释；有状态策略或远程算法必须说明提交前依据和失效处理。不能把本地纯函数替换直接推广为远程服务仍保持同一事务。本轮不新增自定义字段管理界面或通用脚本引擎。

### R08：应用安全与最低运维仍是原则集合（P1，归 C35–C37）

身份契约已写 OIDC／PKCE、nonce、令牌类型、刷新轮换、主体映射等，不能称认证“完全没设计”。但整体还需威胁与保护基线：前端访问／刷新凭据保存及登出清理、多标签页刷新结果协调、刷新提交后应答丢失的重认证路径；浏览器输入与富文本、渲染器／文件／回调／URL 的信任边界；秘密、数据和 AI 开发环境的访问范围。

按所选认证载体确定 CSRF 等适用控制，声明 CSP／内容处理、SSRF／出站限制、解压／渲染资源上限、回调认证和重放窗口；不要求每个风险都新增常驻安全组件。刷新轮换与重放检测的依据可参照 [RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)，具体应答丢失策略仍由项目定，不能靠“单次刷新”自动证明。

基本／完整观测各自需要最低指标、告警、持久日志、查询与故障定位流程；恢复需有备份清单、保管身份、当前安全证据与外部事实查验。客户尚无具体 SLA 数字不妨碍先定义参数、责任和保护动作。具体产品、默认预算和容量分别验证，不把未来监控或 Kubernetes 当作正确性方案。

### R09：全货架需要边界卡和闭环故事（P1，归 I26／C01–C03）

60 个条目已进入目录、选择图与 12 个选型专篇，展示覆盖明显好于旧入口；这只证明没有漏列能力。制造、质量、维护、考勤、请假、招聘、佣金、项目等大量能力还没有足以判断边界的模型和不变量。

至少补每组的事实属主、业务生效／政策版本、关键状态、外部输入与资格、成功／取消／部分完成／更正／恢复故事，再判断合并或拆分。例如：质检冻结如何约束库存可用与执行；制造物料消耗／报工／成本怎样关联；考勤修订与薪资封算怎样衔接；项目工时、费用、出账资格和成本怎样归属。每个故事需能落到接口／事件与最小能力闭包，不要求本轮开发全部组件。

应明确哪些是标准版支持、哪些是未来设计、哪些是客户专项。例如完整多账簿、共享多客户 SaaS、跨地域主动写入、复杂离线业务已不是标准默认；声明边界合理，不把“另审”统一当成设计错误，也不能将目录存在说成已覆盖其全部业务。

## 默认小公司与长期适配路线

以下是审查建议，不选择新产品或新增开发承诺。保留现有 JetStream 默认与 PG 队列第二适配器方向；各条路线按已定目标与测量决定，不重复问用户选默认 MQ。

| 情形／触发信号 | 规范先预留什么 | 后续可调整什么 | 仍必须成立 |
| --- | --- | --- | --- |
| 默认小公司、预算有限 | 最小能力闭包、基本审计／观测、所有队列有界 | 外壳／混合、作业并发、合格低成本运输与资源档位 | 安全、持久状态和关键业务不变量 |
| 业务广、低并发、容许等待 | 同语言合并规则、公平与前后台总预算 | 合并更多低负载成员，减少重任务并发 | 不无界排队，不被单成员耗尽必要服务能力 |
| 请求并发上升 | 入口／出站／DB 预算、幂等、多副本认领 | 拆热点进程、加副本、按环境使用 Kubernetes | 不超卖、不双执行；热点数据仍由写权威保护 |
| 单库存／编号行争用 | 不变量对应的串行化点、热点观测 | 优化锁持有、批处理或合法业务分片 | 不靠复制进程绕过同一额度／序列 |
| 批量、导出、渲染、冷查拖慢交易 | 重任务独立预算、取消／恢复、结果领取授权 | 专门 worker 或移出外壳，必要时独立查询资源 | 当前授权和完整结果 |
| 消息积压／回放需求上升 | 链范围、进度、缺口检测与可靠重建 | 调保留／并发，换合格适配器或按业务链增配运输 | 不丢事实、不重复副作用 |
| 历史增长或恢复超预算 | 数据属主目录、身份／引用、转层协议 | 分区、独立历史实例、封存、分析层 | 历史可解释、可查询、当前权限和恢复 |
| 监控／诊断需求提高 | 统一 telemetry、最低指标与告警、事件／操作关联 | 增配 Collector／存储／看板及专门诊断能力 | 必要审计和最低可运维能力不被选配取消 |
| 高保护或高可用需求 | 信任／故障域、持久与恢复的能力档 | 独立进程／凭据、独立宿主、合格复制／备份方案 | 多副本不自动变成 HA，外部执行证据不能丢 |

每档需要默认值、合法范围、保护动作和测量办法；客户具体参数在交付时实例化。**客户没有统一规模数字，不是缺口；缺的是尚未定义清楚的档位机制和保护规则。**

## 建议的闭环顺序与完成标准

1. 先统一安全与事实语义：内部身份、完整授予／List–Can、接受／撤销、事件／投影模式、作业恢复和审计保存资格。
2. 用代表业务写状态与提交点：订单／库存／信用，资金／核销，来源出账／成本／关账；每条包括未知、取消、迟到和崩溃。
3. 补数据生命周期与客户上线：引用／合并、期初与导入、扩展字段、冷热／附件、跨系统恢复。
4. 同步能力／范围元数据、预算分档、正式规范与契约的替代关系；再按已定顺序准备代表链路与部署实验，随后推广现有组件升级。
5. 全量未来组件完成边界卡和闭环规格；未实现部分分期，专项范围明确。通过独立复核后才形成整套冻结候选。

每项闭环至少包含：责任方与输入、能力／版本／范围、可检验不变量、允许状态与提交点、并发／故障／权限行为、恢复与退出、独立正反预期。涉及公共协议还需 schema／向量／错误与兼容范围，涉及运维还需配置和执行入口。SQL 语句或 API 名不必全部写在业务总览，但必须有唯一的可定位规格；一句“使用 SDK／可靠消息／可配置”不满足完成标准。
