## 目标

现在的 tempDocs 是设计工作区：约 70 个文件、1 万多行，分多轮写成，又经过十多轮复查修补。它能用，但不适合长期阅读：

- 过程痕迹散在正文里：“候选”字样两百多处、引用旧实现十几处、“按第 X 轮复查补充”的段落、指向复查记录的链接、状态说明；
- 安全 03、协议 02、协议 15 等经过多次修补，读起来仍有层叠感；
- 面向客户的说明与面向开发的规范混在同一批文档里。

整理的结果是一套**终稿**：每份只写最终做法，读者一次读懂；过程与经过只留在 `work/`。整理同时是冻结前最后一次完整的一致性通读——每份都整份重读、重写，矛盾在这时暴露。

## 终稿的写法

- **只写最终做法**：不写“候选”“按第 X 轮补充”“现行实现是……”；状态只在设计地图中维护。确有未定的，统一放在每份末尾的“已知风险与待实验”一节，写明由哪项实验验证、属于首批还是后期（高可用为后期，见 D66）。
- **每份的骨架**：解决什么问题；做法（规则与步骤）；为什么这样做（简短，指向决定记录）；独立预期；参考模型（一段，写实际覆盖与不覆盖）；已知风险与待实验。
- **一件事只写在一处**：同一机制在多份文档中出现时，写在主文档，其他处一句话引用（例如来源水位只在协议 02）。
- **拆分过长的文档**：一份覆盖几件独立的事、或超过约 300 行时，按主题拆开（候选：安全 09 编码与 profile、安全 03 接受与撤销）。
- **细节一条不丢**：每份重写后，与原稿逐条对照（规则、参数、预期编号、模型结论），对照结果记在本页的批次记录里；预期编号不改（检查 33）。
- **链接**：终稿之间互相链接；终稿不链接 `work/`、复查记录与归档（搬到正式位置后由 `make docs-boundary` 检查）。

- **意图类与事实类分开**：意图类（迁移表、决策表、带失败分支的时序图、上下文地图、C4 的 Context 与 Container）手写、先改、评审，测试读同一张表；事实类（组件依赖图、物理 ER 图、事件拓扑、部署图、接口文档）从 `component.yaml`、迁移、契约、部署文件生成，不手画，CI 检查生成物最新。
- **防过时**：图与表里的名字用代码的标识符；每张图后写一两句结论；用文本格式（Markdown 表格、Mermaid）放进仓库；配名字存在性、生成物最新、测试读表三类检查。
- **分层**：系统层（本项目）放术语表、C4 的 Context 与 Container、上下文地图、跨组件流程的时序图与协议、事件拓扑（生成）、组件清单与客户组合；组件层（各组件仓库）放一页说明（`BRICKKIT.md`）、本组件的迁移表、决策表、权限点、组件内流程、ER（生成），只写依赖的上游、不写下游的消费者；最后是代码。

安排：

1. 第 2 批在 `01-conventions/` 新增“图与表的规范”（上面四条的完整写法、每层放什么、记法与检查）。

## AI 导航与信息定位（用户 2026-10-15 提出）

用户问：加上图的规范后，能否形成一整套让 AI 快速了解项目、快速定位任何信息（包括代码）的规范与机制。现有的机制：根 `AGENTS.md`（概览、约定摘要、按任务找文档、易错点、组件表）、技能（按任务的流程）、`docs/` 的索引、`registry/` 的清单、各组件的 `AGENTS.md`／`BRICKKIT.md`／`component.yaml`／`contracts/`、设计阶段的地图与台账。它们回答“某类任务怎么做”；还缺的是“某个业务概念在哪、对应哪段代码、改了影响谁”。第 2 批在 `01-conventions/` 写一篇《AI 导航与信息定位》，与《图与表的规范》配套，内容：

1. **入口即路由**：根 `AGENTS.md` 按三种问法路由——按任务（现有的表）、按名字（组件、协议、决定、权限键、事件）、按现象（报错、症状）；每层的入口都短，只指路。
2. **术语表（统一语言）**：每个业务概念写一行：业务叫法、定义、代码标识符、所属组件、所在文档；跨组件的在系统层，组件内的在组件仓库。图与表、代码、文档用同一套标识符。
3. **生成的索引**：组件清单（ID、仓库、版本、范围）、契约方法与事件（谁提供、谁订阅）、权限键与数据范围（属于谁）、配置键，从 `component.yaml`、契约、`registry/` 生成，不手写，CI 检查最新。
4. **追踪链**：决定（D）→ 协议条款 → 独立预期编号（AT、PJ……）→ 测试 → 代码；测试名或注释带预期编号，生成“预期 → 测试”的对照表，未覆盖的预期一目了然。
5. **组件仓库的标准布局与代码地图**：每个组件仓库的目录结构一致；`AGENTS.md` 有固定的“代码地图”一节（入口、命令与查询的处理器、状态机、迁移、生成代码的位置），能生成的部分（契约方法 → 处理函数）由工具生成。
6. **读取预算**：按任务列出必读集（改一个组件读什么、做跨组件改动读什么），避免每次通读（承接工程规范中的读取预算）。
7. **检查**：链接、名字存在性（文档与图里的标识符在代码中存在）、生成物最新、预期覆盖。
8. **局部的 AI 说明**（用户 2026-10-15 授权）：作者可以按每个仓库、每个目录的情况，定制更适合 AI 的文档——在需要的子目录建自己的 `AGENTS.md`（只写该目录的局部约定、代码地图与易错点，不重复上层），并配一个只含 `@AGENTS.md` 的 `CLAUDE.md`，使 Codex 与 Claude Code 在该目录工作时都会读到。何时值得建、写什么、怎样避免与上层重复，写进本规范；同一份知识只在一层维护。

依据：知识库 14.04“项目知识”（AGENTS.md 短而准、多模块时知识放在哪一层）与 14.04.03“图与表”；知识库是中立参考，本项目按自己的组件化与多仓库形态调整。
